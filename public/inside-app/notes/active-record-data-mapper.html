Active Record vs Data Mapper

TL;DR

Two ways to save objects. Active Record: one object per row that holds data and knows how to save() and find() itself (Rails, Laravel, Django). Quick and clear when rules are few. Data Mapper: plain domain objects that know nothing about the database, and a separate mapper or ORM session that loads and saves them (Hibernate, EF Core, Doctrine). More setup, but rules stay testable and the schema can differ from the model. Pick per area, by how complex the rules are.

  • Family: data source pattern
  • From: Fowler, PoEAA (2002)
  • Active Record in: Rails, Laravel, Django
  • Data Mapper in: Hibernate, EF Core, Doctrine, MikroORM

1The problem why do we even need this?

Teams pick a persistence style by habit, then find it fighting the code in the areas it doesn't suit.

  • Business rules tangled with save(); every test needs a database.
  • Or four layers of mapping for a four-field admin form.
  • Arguments about which ORM is “right” for the whole company.

2Real-life analogy filing letters

In a small office, each letter carries a note saying which drawer it goes in, and anyone files it. Fast and simple. In a big legal firm, a records clerk does all the filing; letters know nothing about drawers, so the filing system can change without rewriting a single letter.

  • Self-filing letters are Active Record.
  • The clerk is a Data Mapper.

3How it solves it two styles, pick per area

Active Record maps one class to one table, so the model follows the schema. Data Mapper lets the model and schema differ (value objects in columns, aggregates over several tables). That freedom is what rich domains need, and what CRUD doesn't.

  1. Look at the rules

    Few rules and forms? Active Record. Many rules, invariants, aggregates? Data Mapper.

  2. Use your framework's default where it fits

    Rails and Laravel shine at Active Record; don't fight them for CRUD.

  3. Keep rules out of callbacks

    In Active Record, avoid business logic in before-save hooks.

  4. Keep persistence out of the model

    In Data Mapper, entities don't import the ORM's session.

  5. Mix by area

    Active Record for admin and reporting, Data Mapper for the core.

  6. Revisit when an area grows

    Rules multiplying in an Active Record class? Extract a domain object.

Vocabulary for the exam

Active Record
An object wrapping a database row, with data, some logic and its own persistence.
Data Mapper
A layer that moves data between objects and the database, keeping them independent.
Persistence ignorance
Domain objects that don't know how they're stored.
Callback / hook
Code run before or after save in Active Record frameworks.
Object-relational mismatch
The differences between objects and tables that mappers bridge.
ORM
Object-relational mapper: a library implementing one or both styles.
two-styles.tsthe same change in each style
// Active Record (e.g. TypeORM BaseEntity, Rails, Eloquent): the row saves itself
const hours = await OpeningHours.findOneByOrFail({ storeId, day: "mon" });
hours.closes = "21:00";
await hours.save();

// Data Mapper (e.g. MikroORM, Hibernate, EF Core): a plain object, a session saves it
const order = await em.findOneOrFail(Order, orderId);   // Order has no persistence code
order.addLine(productId, Quantity.of(2), price);        // rules on the object
await em.flush();                                       // the mapper writes the changes

tools: Rails ActiveRecord, Laravel Eloquent, Django ORM and TypeORM's BaseEntity for Active Record; Hibernate/JPA, EF Core, Doctrine, MikroORM and SQLAlchemy's ORM for Data Mapper; query builders (Kysely, jOOQ) when you want neither.

then & now built in now

Then Fowler, PoEAA 2002

Fowler described both, plus Table Data Gateway and Row Data Gateway, as patterns you might implement by hand, with advice on when each fits.

Now 2026

Every major ORM is one or the other: Rails, Laravel and Django are Active Record; Hibernate, EF Core, Doctrine and MikroORM are Data Mappers. You choose a style by choosing a framework, and Fowler's advice on when each fits is still exactly right.

Verdict: Built in now: you don't write them, but knowing which one you're using tells you where your rules should live.

4Gains vs losses nothing is free

What we gain

  • Active Record: very little code for CRUD.
  • Data Mapper: rules testable without a database.
  • Data Mapper: model and schema can differ.
  • Choosing per area gives the best of both.

What we lose

  • Active Record: rules and persistence tangle as logic grows.
  • Data Mapper: more mapping and configuration.
  • Two styles in one codebase to explain.
  • Switching later takes refactoring.

6Common pitfalls the usual ways this goes wrong

  • Rules in callbacks

    Before-save hooks send emails and change other rows. Fix → explicit service or domain methods; keep hooks for timestamps.

  • Active Record in a rich core

    A 2,000-line model class with rules and queries mixed. Fix → extract a domain object, or move that area to Data Mapper.

  • Data Mapper for forms

    Entity, mapper, repository and DTO for a settings page. Fix → plain Active Record or a direct query.

  • Leaking the session

    Entities call the ORM session to load more data. Fix → load what's needed in the application service.

7When to use it (and when not)

Use it when…

  • Choosing an ORM or persistence approach for an area.
  • An Active Record class whose rules are growing.
  • Tests that need a database only because of persistence style.

Skip it when…

  • Read-only reporting: plain SQL or a query builder is simpler than either.
  • Rewriting a working CRUD app just to be “clean”.

8Self-check quiz

What is Active Record?

An object that wraps a database row and contains both data, some logic and its own save/find methods.

What is Data Mapper?

A separate layer that loads and saves plain domain objects, so they don't know about the database.

When does Active Record fit best?

Simple CRUD areas with few rules, where model and table match closely.

Can one app use both?

Yes: Active Record for simple areas and Data Mapper for the rich core is a common mix.

what would you do?Your Rails app's Subscription model has 1,800 lines: billing rules, callbacks that call Stripe, and scopes. Every test needs the database and stubs Stripe. What's a first step?

Extract the billing rules into a plain Ruby domain object (or service) that takes values and returns decisions, move the Stripe calls out of callbacks into an explicit application step, and keep the Active Record model for persistence and simple scopes.

try it

Pick one model class in your app and count its business rules and its persistence methods. If rules dominate, extract the three most important into a plain object with no ORM imports and test it without a database.
