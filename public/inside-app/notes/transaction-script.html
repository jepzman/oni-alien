Transaction Script vs Domain Model

TL;DR

Two ways to organise business logic. A transaction script is one procedure per use case: validate, load, compute, save, top to bottom. Simple, obvious, ideal when rules are few. A domain model puts rules on objects that collaborate (entities, value objects, aggregates). More setup, but it stays sane when rules are many and shared. Choose per area, and move from script to model when rules start repeating and branching.

  • Family: domain logic pattern
  • From: Fowler, PoEAA (2002)
  • Also there: Table Module (now retired)
  • Pairs with: subdomains and anemic model (Vol. 7)

1The problem why do we even need this?

Picking one style for the whole app means it's too heavy in some places and too weak in others.

  • A returns script grew to 2,000 lines of nested ifs.
  • A two-field sign-up form got aggregates and domain events.
  • Rules copied between scripts drift apart.

2Real-life analogy the recipe card and the chef

For a simple dish, a recipe card with numbered steps is perfect: anyone can follow it. For a restaurant with a changing menu, allergies and substitutions, a card with a thousand margin notes fails; you need a trained chef who understands the ingredients and the rules.

  • The card is a transaction script.
  • The chef is a domain model.

3How it solves it choose per area, move when it hurts

Fowler's third option, Table Module (one class per table working on record sets), suited .NET DataSets in 2002 and is rarely used now. The real choice today is script or model, often both in one app, decided by the subdomain (Vol. 7).

  1. Start simple

    A new area with few rules: a script per use case is fine.

  2. Watch for repetition

    The same rule copied into several scripts is the first signal.

  3. Watch for state branching

    if (status === …) chains about what's allowed when.

  4. Extract rules onto objects

    Move the repeated rule to an entity or value object method.

  5. Grow the model gradually

    One rule at a time, with tests, not a big rewrite.

  6. Keep scripts where they fit

    Reports, admin screens and imports can stay as scripts.

Vocabulary for the exam

Transaction script
A procedure that handles one request from start to finish.
Domain model
Objects that hold both data and the business rules.
Table module
One class per table handling all its rows; mostly retired.
Use case
One thing a user or system wants to do.
Shotgun surgery
One change requiring edits in many places: a sign of copied rules.
Refactor to a model
Gradually moving rules from scripts onto objects.
returns.tsa script, and the rule that outgrew it
// transaction script: clear and fine while rules are few
export async function requestReturn(orderId: OrderId, lineId: LineId) {
  const order = await db.orders.find(orderId);
  if (!order) throw new NotFound();
  if (daysSince(order.deliveredAt) > 30) throw new Error("Return window closed");
  await db.returns.insert({ orderId, lineId, status: "requested" });
}

// the 30-day rule now appears in returns, refunds and exchanges -> move it onto the model
export class Order {
  canBeReturned(now: Date) { return this.deliveredAt && daysBetween(this.deliveredAt, now) <= 30; }
}

tools: none special: plain functions for scripts; for models, the building blocks in Vol. 7. Refactoring tools and characterization tests help when moving a script to a model.

then & now still core

Then Fowler, PoEAA 2002

Fowler offered three ways to organise domain logic (transaction script, table module, domain model) with a famous chart: scripts are cheapest for simple logic, models win as complexity grows.

Now 2026

The chart still holds. Table module faded with .NET DataSets. The choice is now usually made per subdomain, and functional programming adds a third way: pure functions over precise types, which behaves like a model without classes.

Verdict: Still core: it's the real choice behind most “anemic or rich?” debates.

4Gains vs losses nothing is free

What we gain

  • Scripts: fastest to write and read for simple logic.
  • Models: rules in one place as complexity grows.
  • Choosing per area avoids both failure modes.
  • Gradual move from one to the other.

What we lose

  • Scripts rot into duplication when rules grow.
  • Models cost design time and more code.
  • Two styles in one app to explain.
  • Knowing when to switch takes judgement.

6Common pitfalls the usual ways this goes wrong

  • One style everywhere

    A rich model for CSV exports, or scripts for the pricing engine. Fix → decide per area by how complex the rules are.

  • Scripts that never move

    Rules copied into the fifth script. Fix → extract on the second or third copy.

  • Big-bang rewrite

    “Let's rebuild returns as a domain model” for six months. Fix → move one rule at a time behind tests.

  • Scripts calling scripts

    Procedures chained into a hidden workflow. Fix → name the workflow, or move rules onto objects.

7When to use it (and when not)

Use it when…

  • Deciding how to structure logic for a new area.
  • A procedure that keeps growing branches.
  • Reviewing whether an area is over- or under-engineered.

Skip it when…

  • Pure data pipelines and reports (scripts or SQL).
  • Debating style for an area that hasn't caused problems.

8Self-check quiz

What is a transaction script?

A single procedure that handles one request or use case from start to finish.

When does a domain model pay off?

When rules are many, shared between use cases, and depend on state.

What's a signal to move from script to model?

The same rule copied into several scripts, or long conditionals about state.

Can one app use both?

Yes, and it usually should: scripts for simple areas, a model for the core.

what would you do?A colleague wants to rewrite the 2,000-line returns script as a full domain model before adding a new “exchange” feature. The deadline is in six weeks. What do you suggest?

Don't rewrite first. Write characterization tests around the script, extract the rules the exchange feature also needs (return window, condition checks) onto Order and a small value object, and build exchange on those. Move more rules later, one at a time.

try it

Find your longest procedure-style function. Mark each business rule in it, then search the codebase for the same rule elsewhere. Move the most-copied one onto an object and replace the copies.
