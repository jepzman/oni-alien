Unit of Work & Identity Map

TL;DR

A unit of work keeps a list of every object created, changed or deleted during one business operation, and writes them all in one transaction at the end. An identity map makes sure each row is loaded once per operation, so two parts of the code never hold two diverging copies of the same customer. Your ORM session (DbContext, EntityManager, Session) is both. Keep it short-lived: one per request.

  • Family: object-relational behaviour
  • From: Fowler, PoEAA (2002)
  • In your ORM as: DbContext, EntityManager, Session
  • Lifetime: one per request or command

1The problem why do we even need this?

Saving each object by hand leads to half-saved changes and duplicate copies of the same row.

  • Four saves in a row; the third fails, the first two stay.
  • The same customer loaded twice; one change overwrites the other.
  • Forgotten saves: an object changed but never written.

2Real-life analogy the waiter's order pad

A good waiter writes every change on the pad (another drink, swap the side, cancel the soup) and sends the whole page to the kitchen at once. Each dish appears once on the pad, however many times the table mentions it.

  • The pad's change list is the unit of work.
  • One line per dish is the identity map.
  • Sending the page is the commit.

3How it solves it track, de-duplicate, commit once

Most of the time you use these patterns rather than write them. What matters is the lifetime: a session per request or per command, never shared between threads or kept for hours.

  1. One session per operation

    Open a DbContext or EntityManager per request, command or job.

  2. Load through it

    So the identity map can return the same object for the same row.

  3. Change objects, don't call save on each

    The unit of work tracks what changed.

  4. Commit once at the end

    SaveChanges() or flush() in one transaction.

  5. Dispose it

    Don't reuse a session across requests or threads.

  6. Write events in the same commit

    Outbox rows go into the same unit of work.

Vocabulary for the exam

Unit of work
Tracks changes during a business transaction and writes them together.
Identity map
Ensures each row is loaded into one object per unit of work.
Change tracking
Detecting which loaded objects were modified.
Flush
Writing pending changes to the database.
Scoped lifetime
A dependency created per request in a DI container.
Detached entity
An object that's no longer tracked by a session.
place-order.tsone unit of work per command
// MikroORM shown; EF Core's DbContext and JPA's EntityManager work the same way
export async function handlePlaceOrder(cmd: PlaceOrderCommand, orm: MikroORM) {
  const em = orm.em.fork();                       // new unit of work + identity map
  const order    = await em.findOneOrFail(Order, cmd.orderId);
  const customer = await em.findOneOrFail(Customer, order.customerId);
  const again    = await em.findOneOrFail(Customer, order.customerId);
  console.assert(customer === again);             // identity map: same object

  customer.reserveCredit(order.total());          // tracked
  order.place(new Date());                        // tracked
  em.persist(new OutboxMessage(order.events));    // new
  await em.flush();                               // one transaction, all or nothing
}

tools: EF Core DbContext, JPA/Hibernate EntityManager and Session, SQLAlchemy Session, MikroORM EntityManager; request-scoped lifetimes in DI containers.

then & now built in now

Then Fowler, PoEAA 2002

Fowler described both patterns in detail, because in 2002 many teams wrote their own data layer and had to implement change tracking, commit ordering and identity maps themselves.

Now 2026

Every Data Mapper ORM has them built in (Hibernate's Session, EF Core's DbContext, SQLAlchemy's Session). Nobody writes them now; the skill is choosing the session's lifetime and knowing when it flushes.

Verdict: Built in now: know they exist, and keep the session short.

4Gains vs losses nothing is free

What we gain

  • All or nothing: no half-saved operations.
  • One copy per row: no diverging duplicates.
  • No forgotten saves: changes are tracked.
  • Fewer round trips: batched writes.

What we lose

  • Hidden writes: it's not obvious what flush will do.
  • Memory grows with tracked objects.
  • Stale data in long-lived sessions.
  • Not thread-safe.

6Common pitfalls the usual ways this goes wrong

  • Long-lived sessions

    One DbContext for a whole desktop app or a batch of a million rows. Fix → one session per request or per batch chunk.

  • Sharing across threads

    A singleton DbContext in a web server. Fix → scoped lifetime per request.

  • Surprising flushes

    Loading a query triggers an automatic flush of half-made changes. Fix → make changes, then flush once, explicitly.

  • Saving per entity anyway

    SaveChanges() after every line. Fix → one commit at the end of the operation.

7When to use it (and when not)

Use it when…

  • Any operation that changes several rows together.
  • Code that loads the same entity from several places in one request.
  • Choosing session lifetimes in a web app or job.

Skip it when…

  • Bulk data loads (use the database's bulk tools, not tracked objects).
  • Read-only queries (turn tracking off for speed).

8Self-check quiz

What does a unit of work do?

Tracks changes made during an operation and writes them all in one transaction.

What does an identity map guarantee?

Each row is loaded into a single object per unit of work, so there are no diverging copies.

What's the right lifetime for an ORM session in a web app?

One per request (scoped), never shared between requests or threads.

Why turn off tracking for read-only queries?

Tracking costs memory and time and isn't needed when nothing will be saved.

what would you do?A nightly import of 2 million products slows to a crawl and runs out of memory after an hour. It uses one DbContext for the whole run. What do you change?

Process in chunks with a fresh context per chunk (say 1,000 rows), turn off tracking for reads, and for pure inserts use the database's bulk copy instead of tracked entities.

try it

In your app, find where the ORM session is created and how long it lives. Log the number of tracked entities at the end of one request and of one background job. If either is in the thousands, shorten the lifetime or turn off tracking for its reads.
