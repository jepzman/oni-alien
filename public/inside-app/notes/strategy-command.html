Strategy & Command as Functions

TL;DR

Strategy: choose behaviour at runtime by swapping an algorithm, such as a discount rule or a sort order. Command: turn a request into an object you can queue, log, retry or undo. In 1994 both needed an interface and a class per variant. With first-class functions, a strategy is just a function (often in a map), and a command is a data object plus a handler. Keep the ideas, drop the boilerplate.

  • Family: behavioural patterns (GoF)
  • From: Gamma et al., Design Patterns (1994)
  • Today: functions, lambdas, message objects
  • Pairs with: open–closed, job queues

1The problem why do we even need this?

Applying 1994 class-based recipes in modern languages creates class explosions for one-line behaviour.

  • An interface, five classes, a factory and a registry for five discount rules.
  • Command classes with an execute() that wraps one call.
  • Reading one rule means opening four files.

2Real-life analogy route choice and order slips

In a navigation app you pick fastest, shortest or no tolls, and the app swaps its route rule. A waiter's order slip turns a spoken request into paper that can wait in a queue, be passed to another cook, or be torn up if the guest cancels.

  • The route setting is a strategy.
  • The slip is a command: a request turned into data.

3How it solves it functions and data, not class trees

Peter Norvig showed in 1996 that 16 of the 23 GoF patterns become simpler or invisible in dynamic, functional languages. Strategy and Command are the clearest cases: the language feature replaced the pattern, but the need it names didn't go away.

  1. Strategy: write each variant as a function

    (basket) => Money, named after the rule.

  2. Choose by passing or looking up

    Pass the function in, or keep a map from key to function.

  3. Use a class only for state

    If a variant needs configuration or caching, a small object is fine.

  4. Command: make the request data

    A typed object with a type and its fields.

  5. One handler per type

    A function that performs it; register handlers in a map.

  6. Exploit that it's data

    Store, log, retry, schedule and audit commands.

Vocabulary for the exam

A function you can pass, store and return like any value.
Higher-order function
A function that takes or returns functions.
Discriminated union
A typed way to describe several command shapes.
Undo
Reversing a command, possible when it's recorded as data.
discounts.tsstrategy as functions, command as data
// Strategy: a map of functions
type Discount = (b: Basket) => Money;
const discounts: Record<DiscountName, Discount> = {
  none:        ()  => Money.zero("EUR"),
  tenPercent:  (b) => b.total().percent(10),
  freeShipping:(b) => b.shippingCost(),
};
const total = basket.total().minus(discounts[customer.discount](basket));

// Command: data + a handler, so it can be queued, retried and audited
type Command =
  | { type: "ReserveStock"; orderId: OrderId }
  | { type: "SendInvoice";  orderId: OrderId; email: EmailAddress };

const handlers: { [K in Command["type"]]: (c: Extract<Command, { type: K }>) => Promise<void> } = {
  ReserveStock: async (c) => stock.reserve(c.orderId),
  SendInvoice:  async (c) => mailer.sendInvoice(c.orderId, c.email),
};
await jobs.enqueue({ type: "SendInvoice", orderId, email });   // runs later, retries on failure

tools: plain functions and maps, discriminated unions for command types, job queues (BullMQ, Sidekiq, Hangfire, Temporal for long workflows), MediatR-style handler registries.

then & now built in now

Then Gamma et al., 1994

The GoF described Strategy and Command with interfaces and a class per variant, because C++ and Smalltalk-era Java had no convenient first-class functions.

Now 2026

Lambdas and first-class functions are in every mainstream language, so a strategy is a function and a command is a message object. The needs (swap behaviour, queue work) are as real as ever; job queues and workflow engines are Command at scale.

Verdict: Built in now: the language does the pattern. Know the names, write the functions.

4Gains vs losses nothing is free

What we gain

  • Much less code for the same flexibility.
  • Rules readable in one place.
  • Commands as data: queue, retry, audit.
  • Easy to test: call the function.

What we lose

  • Less structure for big, stateful variants.
  • Unfamiliar to teams trained on class diagrams.
  • Map lookups can fail at runtime without types.
  • Handlers spread without a registry.

6Common pitfalls the usual ways this goes wrong

  • Classes by habit

    A Strategy interface and factory for one-liners. Fix → functions and a map.

  • Untyped lookups

    discounts[name] is undefined for a new name. Fix → typed keys, and fail loudly on unknown ones.

  • Commands with behaviour inside

    Command objects that call services from execute(), so they can't be serialised. Fix → data in the command, behaviour in the handler.

  • Strategies that need everything

    A function taking twelve parameters. Fix → pass a small context object, or reconsider the split.

7When to use it (and when not)

Use it when…

  • Several interchangeable rules chosen at runtime.
  • Work that should be queued, retried, scheduled or audited.
  • Replacing GoF boilerplate in a modern codebase.

Skip it when…

  • One rule with no variants (just write it).
  • Simple synchronous calls with nothing to queue.

8Self-check quiz

What does the Strategy pattern do?

Lets you choose an algorithm at runtime by swapping interchangeable implementations.

What's the modern lightweight form of Strategy?

A function, often chosen from a map keyed by name.

Why make a command a data object?

So it can be queued, logged, retried, scheduled or undone.

Where should the command's behaviour live?

In a handler, separate from the data, so the command stays serialisable.

what would you do?A pull request adds IShippingStrategy, four strategy classes of two lines each, a factory and a DI registration, for four carrier price rules. What do you suggest in review?

Replace them with a map from carrier to a pricing function in one file, typed so a missing carrier fails to compile. Keep a class only if a carrier needs configuration or state.

try it

Find a Strategy or Command class hierarchy in your code. Rewrite one as functions (or data plus a handler), run the tests, and compare the number of files and lines before and after.

remember!!

Pick a route rule; write an order slip. Neither needs a factory.
