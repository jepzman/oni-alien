Lazy Loading

TL;DR

Lazy loading fetches related data only when code first touches it (order.customer), through a proxy. It feels free, which is the problem: in a list it causes the N+1 query problem, and after the session closes it throws. Today the advice is to decide per use case: projections for lists, explicit eager includes for details, and lazy only on rare paths. Many teams turn it off by default.

  • Family: object-relational behaviour
  • From: Fowler, PoEAA (2002)
  • Famous failure: the N+1 query problem
  • Pairs with: batch loading (Vol. 3), DTOs

1The problem why do we even need this?

Lazy loading hides database calls behind property access, so the code looks cheap and isn't.

  • A list of 50 orders runs 51 queries.
  • A template touches a relation after the session closed, and crashes.
  • Performance depends on which fields a view happens to read.

2Real-life analogy the minibar and the catering order

A hotel minibar is lazy: everything is there, and you take one item when you want it. Great for a midnight snack; terrible for feeding a meeting of fifty, one trip each. For the meeting, you order catering: everything at once.

  • The minibar is lazy loading.
  • Fifty trips is N+1.
  • Catering is eager loading or a projection.

3How it solves it decide per use case

A projection (selecting just the fields the screen needs into a DTO) is often better than loading entities at all for read screens. Keep entity loading for use cases that change things.

  1. Turn lazy loading off by default

    Or at least know where it's on.

  2. List pages: project

    Select only the needed fields with joins into a DTO, in one query.

  3. Detail and write use cases: include

    Eager-load the aggregate's parts explicitly.

  4. Lazy only on rare paths

    Associations needed in one case out of a hundred.

  5. Keep the session open only inside the use case

    Not during view rendering (avoid open-session-in-view).

  6. Count queries in tests

    Fail a test when a page exceeds its query budget.

Vocabulary for the exam

Lazy loading
Loading related data on first access, through a proxy.
Eager loading
Loading related data up front with the main query (Include, JOIN FETCH).
N+1 problem
One query for a list plus one per item.
Proxy
A stand-in object that loads the real data when touched.
Projection
A query that selects specific fields into a shape for one screen.
Open session in view
Keeping the ORM session open while rendering, which hides lazy queries.
orders-list.tsa projection instead of lazy entities
// lazy: looks innocent, runs 1 + 50 queries
const orders = await em.find(Order, { status: "placed" }, { limit: 50 });
orders.map((o) => ({ id: o.id, customer: o.customer.name }));   // each .customer = a query

// projection: exactly what the page shows, one query
const rows = await db.selectFrom("orders as o")
  .innerJoin("customers as c", "c.id", "o.customer_id")
  .select(["o.id", "o.placed_at", "c.name as customer", "o.total_cents"])
  .where("o.status", "=", "placed").orderBy("o.placed_at", "desc").limit(50)
  .execute();

// detail use case: load the aggregate explicitly
const order = await em.findOneOrFail(Order, id, { populate: ["lines", "customer"] });

tools: ORM include/populate options (Include in EF Core, JOIN FETCH and entity graphs in JPA, populate in MikroORM), query builders for projections, DataLoader for GraphQL, query counters in tests (e.g. Hibernate statistics, Bullet for Rails).

then & now built in now

Then Fowler, PoEAA 2002

Fowler described four ways to implement lazy load (lazy initialisation, virtual proxy, value holder, ghost) for teams writing their own data layers, with a warning about “ripple loading”, his name for N+1.

Now 2026

ORMs build lazy proxies in. Experience turned the warning into the main lesson: many teams disable lazy loading by default (EF Core has it off unless enabled), and projections, DataLoader and query budgets are standard.

Verdict: Built in now, and best used sparingly: load deliberately per use case.

4Gains vs losses nothing is free

What we gain

  • Predictable queries per use case.
  • No N+1 surprises.
  • No closed-session errors.
  • Faster list pages with projections.

What we lose

  • More explicit code for loading.
  • Over-fetching if includes are too broad.
  • Several shapes of the same data.
  • Lazy convenience lost for prototypes.

6Common pitfalls the usual ways this goes wrong

  • Lazy loading in loops

    A template or mapper touching a relation per row. Fix → projection or eager include for lists.

  • Open session in view

    Lazy loads keep working during rendering, invisibly. Fix → close the session at the end of the use case.

  • Include everything

    Every query eager-loads ten relations “to be safe”. Fix → include what the use case needs, no more.

  • No measurement

    N+1 found by customers, not tests. Fix → count queries in tests and log slow pages.

7When to use it (and when not)

Use it when…

  • Deciding loading strategies in an ORM-based app.
  • Slow list pages or GraphQL resolvers.
  • Lazy-initialisation errors in production.

Skip it when…

  • Prototypes where speed of writing beats speed of running.
  • Rarely-used associations on single objects (lazy is fine there).

8Self-check quiz

What is lazy loading?

Loading related data only when it is first accessed, through a proxy.

What's the N+1 problem?

One query loads N items, then one more query runs per item for a related object.

What's usually best for list pages?

A projection query that selects just the shown fields, with joins, into a DTO.

Why avoid open-session-in-view?

It lets lazy queries run invisibly during rendering, hiding N+1 problems.

what would you do?A GraphQL query for 100 orders with their customers and products takes 4 seconds; logs show 301 SQL queries. What do you do?

Batch the related loads per request with DataLoader (or the ORM's batch fetching), so customers and products load in one query each, and add a test that fails if the query count for this request exceeds a small budget.

try it

Turn on SQL logging, open your app's busiest list page, and count the queries. If it's more than three, rewrite it as one projection query and compare the timings.
