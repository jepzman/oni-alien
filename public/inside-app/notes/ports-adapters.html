Ports & Adapters

TL;DR

Put the business core (use cases and domain) in the middle, with no framework, database or SDK imports. The core declares ports: what it offers (use cases) and what it needs (repositories, payments). Adapters connect the outside world: HTTP, queues, CLIs and tests drive the core; Postgres, Stripe and email are driven by it. All dependencies point inward, so the core runs, and is tested, without the outside.

  • Family: application architecture
  • From: Alistair Cockburn (2005)
  • Cousins: onion (2008), clean architecture (2012)
  • Built on: dependency inversion

1The problem why do we even need this?

When business rules live inside the framework's handlers, they can't be tested, reused or kept through a framework change.

  • Rules sit in route handlers calling the ORM directly.
  • A queue consumer for the same use case copies the logic.
  • Tests need a running server and a database.

2Real-life analogy the laptop and its ports

A laptop has standard ports. It doesn't care which brand the monitor is, or whether power comes from a wall or a power bank: adapters connect whatever you have. In a hotel abroad, you change the plug adapter, not the laptop.

  • The laptop is the core.
  • USB-C is a port.
  • Cables and plugs are adapters.

3How it solves it a core with ports, adapters around it

Onion and clean architecture draw the same thing as rings with more layers. The essential rule in all three is one: source dependencies point toward the core. Don't add rings you don't need; two sides and a core is usually enough.

  1. Pull rules out of handlers

    Each use case becomes a function or class in the core.

  2. Define driving ports

    The use cases' input and output types, independent of HTTP.

  3. Define driven ports

    Interfaces for what the core needs, in its own words.

  4. Write adapters

    HTTP handler → use case; Postgres and Stripe implement driven ports.

  5. Wire at start-up

    A composition root builds adapters and injects them.

  6. Enforce the direction

    Architecture tests: the core imports nothing from adapters or frameworks.

Vocabulary for the exam

Hexagonal architecture
Cockburn's name for ports and adapters; the hexagon has no meaning beyond “many sides”.
Port
An interface at the core's border.
Driving (primary) adapter
Calls the core: HTTP, CLI, queue, tests.
Driven (secondary) adapter
Called by the core: database, payment, email.
Onion / clean architecture
Ring-shaped variants with the same inward rule.
Composition root
Where adapters are created and plugged in.
layout.txtone service, ports and adapters
src/
  core/                      # no imports from express, prisma, stripe
    orders/
      place-order.ts         # use case (driving port: handle(cmd))
      order.ts               # domain model
      ports.ts               # OrderRepository, PaymentPort (driven ports)
  adapters/
    http/orders.routes.ts    # express → placeOrder.handle()
    queue/orders.consumer.ts # same use case, from a queue
    postgres/orders.repo.ts  # implements OrderRepository
    stripe/payments.ts       # implements PaymentPort
  main.ts                    # composition root: wires adapters into the core
test/
  place-order.test.ts        # core + in-memory fakes, no server, no database

tools: plain modules and constructor injection; dependency-cruiser, ArchUnit, NetArchTest or Nx module boundaries to enforce inward dependencies; framework templates (NestJS, Spring) that can be bent to this layout.

then & now matters more now

Then Cockburn, 2005

Cockburn described the hexagonal architecture in 2005 so applications could be driven equally by users, programs and tests, and run without their databases. Onion (Palermo, 2008) and clean architecture (Martin, 2012) followed with rings.

Now 2026

It's now the default shape for services with real logic, and the reason fast core tests are possible. The lesson learned since: keep it to a core and adapters; the many-ringed versions often add mapping without benefit.

Verdict: Matters more now, in its simple form: a core, ports, adapters, and dependencies pointing in.

4Gains vs losses nothing is free

What we gain

  • Core tested in milliseconds, no server or database.
  • Many entry points, one use case.
  • Frameworks and providers swappable.
  • Clear place for every kind of code.

What we lose

  • More files and interfaces.
  • Mapping between adapters and core types.
  • Overkill for thin CRUD services.
  • Ring obsession: too many layers in clean-architecture variants.

6Common pitfalls the usual ways this goes wrong

  • Hexagon for CRUD

    Ports and adapters around a service that just saves forms. Fix → use it where the core has real rules.

  • Too many rings

    Entities, use cases, interface adapters, frameworks, each with its own models and mappers. Fix → core and adapters; add layers only for a reason.

  • Leaky ports

    A port method takes an Express Request or returns a Prisma type. Fix → ports use the core's own types.

  • No enforcement

    One shortcut import and the direction is gone. Fix → architecture tests in CI.

7When to use it (and when not)

Use it when…

  • Services with real business rules that must be tested well.
  • One use case reached from several entry points (HTTP, queue, CLI).
  • Infrastructure likely to change.

Skip it when…

  • Thin CRUD services and prototypes.
  • Scripts and small tools.

8Self-check quiz

What's the one essential rule of ports and adapters?

Source dependencies point inward: the core imports nothing from adapters or frameworks.

What's the difference between driving and driven adapters?

Driving adapters call the core (HTTP, CLI, tests); driven adapters are called by it (database, payments).

How do onion and clean architecture relate?

They are ring-shaped variants of the same idea, with more named layers.

When is it overkill?

In thin CRUD services and prototypes with few rules.

what would you do?Your team must add a Kafka consumer that places orders, but all the order logic lives in an Express handler. Copying it is the fastest option. What do you do?

Extract the logic into a PlaceOrder use case in a core module with ports for its repository and payments, make the Express handler call it, then write the Kafka consumer as a second driving adapter calling the same use case. Add tests on the use case with fakes.

try it

Take one route handler with business rules in it. Move the rules into a function in a core folder that takes plain inputs and ports, make the handler call it, and write a test of the function without HTTP or a database.
