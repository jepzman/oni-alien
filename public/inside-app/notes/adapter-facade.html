Adapter & Facade

TL;DR

Two structural patterns you'll use weekly. An adapter makes an existing interface fit the one you need: each carrier SDK is wrapped to implement your ShippingPort, converting names, units and errors. A facade puts a simple door in front of a complicated subsystem: invoicePdf.render(invoice) hides fifteen setup steps. Both keep foreign APIs at the edge, so an upgrade or a swap touches one file.

  • Family: structural patterns (GoF)
  • From: Gamma et al. (1994)
  • Today as: adapters in ports & adapters, SDK wrappers, BFFs
  • Pairs with: anti-corruption layer (Vol. 7)

1The problem why do we even need this?

Calling foreign APIs directly from many places spreads their shapes and quirks through your code.

  • Three carrier SDKs with different names, units and errors, used in twenty places.
  • A PDF library's fifteen setup steps copied nine times.
  • An SDK upgrade touches every caller.

2Real-life analogy the plug adapter and the concierge

A travel plug adapter makes a foreign socket fit your charger, without changing either. A hotel concierge hides a whole city: you say “dinner and a taxi at eight” and they deal with the restaurant, the taxi company and the timing.

  • The plug adapter is an adapter: one shape to another.
  • The concierge is a facade: one simple door to a complicated system.

3How it solves it fit a shape, or simplify a subsystem

An adapter converts an interface; a facade simplifies one. An anti-corruption layer (Vol. 7) is adapters and facades with an extra job: translating a whole model, not just method names.

  1. Define what you need

    A port in your terms: bookParcel(order, weight: Grams).

  2. Adapt each provider

    One adapter per SDK, converting names, units and errors.

  3. Translate errors

    Provider errors become your error types; callers never catch SDK exceptions.

  4. Facade complex libraries

    One small class with the operations you use, hiding setup.

  5. Keep them at the edge

    Only adapters and facades import the SDK.

  6. Contract-test adapters

    The same tests against every adapter of a port.

Vocabulary for the exam

Adapter
Converts one interface into another that clients expect.
Facade
A simple interface to a complex subsystem.
Wrapper
A loose term for either.
Anti-corruption layer
Adapters and facades that also translate a foreign model.
SDK
A provider's client library.
Leaky abstraction
A wrapper that still exposes the wrapped API's details.
shipping/dhl.adapter.tsadapter: their SDK, your port
export interface ShippingPort {
  bookParcel(p: { orderId: OrderId; weight: Grams; to: Address }): Promise<TrackingNo>;
}

export class DhlShippingAdapter implements ShippingPort {
  constructor(private dhl: DhlClient) {}
  async bookParcel({ orderId, weight, to }) {
    try {
      const res = await this.dhl.createShipment({
        reference: orderId, weightKg: weight.value / 1000, receiver: toDhlAddress(to) });
      return trackingNo(res.shipmentTrackingNumber);
    } catch (e) {
      if (e instanceof DhlValidationError) throw new InvalidAddress(to, e.message);
      throw new CarrierUnavailable("dhl", e);
    }
  }
}

// facade: one door to a complicated library
export const invoicePdf = { render: (inv: InvoiceView) => renderWithPdfLib(inv /* 15 steps inside */) };

tools: plain classes or functions; contract tests per port; SDK generators (OpenAPI generator) behind your own adapter; dependency-cruiser rules so only adapters import vendor SDKs.

then & now still core

Then Gamma et al., 1994

The GoF described Adapter (make incompatible interfaces work together) and Facade (a unified interface to a subsystem) with examples from GUI toolkits and compilers.

Now 2026

Both are daily tools: adapters are the “adapters” of ports and adapters, every SaaS integration needs one, and facades sit in front of SDKs, BFFs and complex libraries. The names stuck because the needs never went away.

Verdict: Still core, and more common than in 1994 because systems now talk to so many vendors.

4Gains vs losses nothing is free

What we gain

  • Foreign APIs at the edge, in one file each.
  • Swap or upgrade providers in one place.
  • Your own errors and units everywhere else.
  • Simple calls for complex libraries.

What we lose

  • More code: one adapter per provider.
  • Lowest common denominator: special features get hidden.
  • Leaky wrappers if done carelessly.
  • Another layer to step through when debugging.

6Common pitfalls the usual ways this goes wrong

  • Leaky adapters

    The port returns the SDK's response type. Fix → return your own types; convert inside.

  • Lowest common denominator

    A carrier's useful feature can't be reached through the port. Fix → add an optional capability, or a second port for it.

  • Facade that grows into a god class

    Every library feature added to the facade. Fix → only the operations your app uses.

  • Wrapping stable standard libraries

    A facade around fetch or Date with no added meaning. Fix → wrap only what's volatile or awkward.

7When to use it (and when not)

Use it when…

  • Integrating several providers for the same job.
  • A complicated library used in many places.
  • Third-party APIs likely to change or be replaced.

Skip it when…

  • Stable, well-designed standard libraries.
  • A one-off call in a script.

8Self-check quiz

What's the difference between an adapter and a facade?

An adapter converts one interface into another; a facade simplifies a complex subsystem behind a simple interface.

How does an anti-corruption layer relate?

It's built from adapters and facades, with the extra job of translating a foreign model.

Why translate provider errors?

So callers handle your own error types and never depend on an SDK's exceptions.

What's a leaky adapter?

One whose interface still exposes the wrapped API's types or details.

what would you do?Your company switches SMS provider. The old provider's client is imported in 31 files, each building messages slightly differently. What do you do first?

Define an SmsSender port in your terms, write an adapter for the old provider, and move the 31 callers onto the port (behaviour unchanged). Then write an adapter for the new provider, contract-test both, and switch in the composition root.

try it

Search your code for imports of one vendor SDK. Count the files. Write a port and one adapter for it, move two callers over, and add a lint rule that only the adapter may import the SDK.
