Interface Segregation

TL;DR

Clients shouldn't depend on methods they don't use. Instead of one fat interface (a 14-method PaymentGateway), define small role interfaces shaped by each client's needs (ChargePayments, Refunds, Payouts). One class can implement several. Clients get simpler fakes, and changes to one role don't ripple to the others.

  • Family: SOLID principle
  • From: Robert C. Martin (1996, at Xerox)
  • Today: role interfaces, structural types
  • Pairs with: dependency inversion, test doubles

1The problem why do we even need this?

A fat interface couples every client to every method, even the ones it never calls.

  • Checkout depends on a 14-method gateway but uses one method.
  • Every fake in every test implements all 14.
  • A change to payouts forces checkout to rebuild and redeploy.

2Real-life analogy the remote control

A universal remote with sixty buttons controls everything, and a guest can't find the volume. A simple remote with power, volume and channel does what most people need. The TV supports both; each person gets the remote for their job.

  • The TV is the implementation.
  • Each remote is a role interface.

3How it solves it interfaces shaped by their clients

Let the client define the interface it needs, in its own words: that's also what dependency inversion asks. In TypeScript and Go, structural typing makes this almost free: any object with the right methods fits.

  1. List each client's calls

    Which methods does each user of the interface actually call?

  2. Group by role

    Methods used together by the same kind of client form a role.

  3. Define small interfaces

    Named after the role, owned near the client.

  4. Implement several in one class

    The adapter can implement all roles.

  5. Narrow dependencies

    Each client asks for the smallest role it needs.

  6. Simplify fakes

    Tests fake one small role, not the whole gateway.

Vocabulary for the exam

Interface segregation principle
No client should be forced to depend on methods it doesn't use.
Role interface
An interface describing one role a client needs.
Header interface
An interface that mirrors every public method of one class: usually too fat.
Structural typing
Type compatibility by shape, as in TypeScript and Go.
Pick<T, K>
TypeScript helper to take just some members of a type.

One interface serving many unrelated clients.
payments.tsrole interfaces, owned by their clients
// checkout/ports.ts
export interface ChargePayments { charge(amount: Money, card: CardToken): Promise<ChargeId> }

// returns/ports.ts
export interface Refunds { refund(charge: ChargeId, amount: Money): Promise<void> }

// infrastructure/stripe.ts : one adapter, several roles
export class StripeAdapter implements ChargePayments, Refunds, Payouts { /* ... */ }

// a test fake now needs one method, not fourteen
const fakeCharge: ChargePayments = { charge: async () => chargeId("ch_test_1") };

tools: TypeScript and Go structural typing, Pick and Omit types, Kotlin and C# interfaces, mocking libraries (which become simpler with small interfaces).

then & now still core

Then Martin, 1996

Martin found it at Xerox, where a single Job class used by every printer task made every change recompile everything. In C++ and Java, splitting interfaces was the way to cut compile and deploy coupling.

Now 2026

Compile times matter less, but the coupling, the fakes and the deploy ripple are the same. Structural typing in TypeScript and Go made role interfaces nearly free, and the idea reappears in API design (small, focused endpoints) and micro-frontends.

Verdict: Still core, and cheaper to apply than ever.

4Gains vs losses nothing is free

What we gain

  • Smaller dependencies per client.
  • Simpler fakes in tests.
  • Changes don't ripple across unrelated clients.
  • Clear roles named in client terms.

What we lose

  • More interfaces to name and find.
  • Too fine-grained if split per method everywhere.
  • Implementations list several interfaces.
  • Navigation: where's the full picture?

6Common pitfalls the usual ways this goes wrong

  • One interface per method

    Fifty single-method interfaces nobody can navigate. Fix → group methods used together by the same client.

  • Header interfaces

    IOrderService mirroring every public method of OrderService. Fix → define interfaces from the client's side.

  • Splitting but still passing the whole

    Small interfaces exist, but functions still take the concrete class. Fix → ask for the smallest role in each signature.

  • Ignoring language features

    Writing adapter classes to narrow interfaces in TypeScript. Fix → structural types and Pick do it for free.

7When to use it (and when not)

Use it when…

  • An interface with many methods and many different clients.
  • Tests that need large fakes for small uses.
  • Changes in one area forcing rebuilds elsewhere.

Skip it when…

  • An interface with one client that uses all of it.
  • Small interfaces already (3–5 methods used together).

8Self-check quiz

What does interface segregation say?

No client should depend on methods it doesn't use.

What's a role interface?

A small interface describing one role a client needs, often owned by that client.

Can one class implement several role interfaces?

Yes, and that's typical: one adapter, several roles.

How does this help tests?

Fakes implement only the small role the code under test uses.

what would you do?Every unit test in your service creates a mock of ICustomerService, which has 22 methods; most tests stub one. Mocks break whenever a method is added. What do you change?

Introduce role interfaces from the callers' side (for example CustomerLookup, CustomerCredit), make each caller depend on its role, and let the existing service implement them. Tests then fake one or two methods.

try it

Pick the largest interface in your code and list which methods each caller uses. Define one role interface for the most common caller, switch that caller to it, and rewrite one of its tests with a hand-written fake.
