Open–Closed

TL;DR

Code should be open for extension but closed for modification: adding a new case (a carrier, a payment method, a report format) should mean adding code, not editing a growing switch that every case shares. Today you get there with functions, maps and small interfaces, not inheritance trees, and only where new cases really keep coming.

  • Family: SOLID principle
  • From: Bertrand Meyer (1988); Robert C. Martin (1996)
  • Today: registries, functions, plug-in points
  • Pairs with: strategy, YAGNI

1The problem why do we even need this?

When every new case means editing shared code, each addition risks breaking the cases that already work.

  • A shipping switch statement grows with each carrier.
  • Adding one carrier needs a retest of all the others.
  • Several developers edit the same function in parallel.

2Real-life analogy the wall socket

A house's wiring ends in standard sockets. A new kettle just plugs in; nobody opens the wall. The wiring is closed for change and open for any appliance with the right plug.

  • The socket is the extension point.
  • Each appliance is a new case, added without touching the wiring.

3How it solves it extension points where change really happens

Don't make everything pluggable “just in case”: that's speculative generality. Add an extension point the second or third time the same kind of change arrives.

  1. Spot the repeating change

    The same switch or if-chain edited for each new kind of thing.

  2. Name the shape

    What does each case need to provide? (order: Order) => Money.

  3. Move each case out

    One small module per case, all with the same shape.

  4. Register them

    A map or registry the core looks up by key.

  5. Add by adding

    A new case is a new file and one registration line.

  6. Stop there

    Leave other code concrete until it shows the same pattern.

shipping.tsa registry instead of a switch
type RateFn = (order: Order) => Money;

const carriers = new Map<CarrierId, RateFn>();
export const registerCarrier = (id: CarrierId, fn: RateFn) => carriers.set(id, fn);

export function shippingCost(order: Order): Money {
  const rate = carriers.get(order.carrier);
  if (!rate) throw new Error(`Unknown carrier ${order.carrier}`);
  return rate(order);
}

// carriers/bike.ts  — added without touching anything above
registerCarrier("bike", (o) => o.distanceKm <= 5 ? Money.eur(4) : Money.eur(9));

tools: plain maps and functions, dependency-injection containers with multi-bindings, plug-in systems (webpack and ESLint plug-ins are the same idea), and feature flags for switching implementations.

then & now rethought

Then Meyer, 1988; Martin, 1996

Meyer meant extension through inheritance: subclass a module instead of editing it. Martin reframed it around abstract interfaces and polymorphism, which in C++ and Java meant class hierarchies.

Now 2026

The goal holds, the means changed: functions, maps, composition and plug-in registries. Experience also added a warning: predicting where change will come often fails, so extension points are added when change actually repeats.

Verdict: Rethought: aim for “add, don't edit” where change repeats, with functions instead of inheritance.

4Gains vs losses nothing is free

What we gain

  • New cases without editing old ones.
  • Smaller, safer changes and reviews.
  • Parallel work on different cases.
  • Each case tested alone.

What we lose

  • Indirection: harder to see all cases at once.
  • Wrong guesses about where change happens.
  • More files.
  • Registration can be forgotten.

6Common pitfalls the usual ways this goes wrong

  • Everything pluggable

    Interfaces for code that has one implementation forever. Fix → wait for the second or third real case.

  • Inheritance trees

    A deep class hierarchy to add one rule. Fix → functions or small interfaces and composition.

  • Silent missing registration

    A new carrier isn't registered and orders fail at runtime. Fix → fail loudly on unknown keys, and test the registry.

  • A switch in disguise

    The registry is fine, but callers still branch on carrier. Fix → push carrier-specific logic into the carrier module.

7When to use it (and when not)

Use it when…

  • The same kind of change keeps arriving (carriers, payment methods, formats).
  • Several teams add cases to the same feature.
  • A growing switch keeps breaking.

Skip it when…

  • Code with one case and no sign of more.
  • A small, stable switch that's clearer than a registry.

8Self-check quiz

What does open–closed mean?

Add behaviour by adding code, without modifying code that already works.

How was it usually done in 1988–1996, and how today?

Then through inheritance and abstract classes; today mostly through functions, maps and small interfaces.

When should you add an extension point?

When the same kind of change has come two or three times, not in advance.

What's speculative generality?

Flexibility built for changes that never arrive, which adds cost without benefit.

what would you do?A new developer proposes an abstract ReportGenerator with a factory and three subclasses, for the one CSV export the product has. What do you say?

Keep the single concrete export. Add an extension point when a second or third format is actually requested; until then the abstraction is speculative.

try it

Find a switch or if-chain in your code that has been edited for each new case. Replace it with a map from key to function, move two cases into their own modules, and add a test that fails on an unknown key.
