Vertical Slices

TL;DR

Organise code by feature instead of by technical layer. Each slice (place-order/, cancel-order/) holds its own endpoint, handler, request and response types, data access and tests. Slices share the domain model and basic infrastructure, not a giant OrderService. A new feature is a new folder; changing one rarely touches another; each slice can be as simple or rich as it needs.

  • Family: application architecture
  • Named by: Jimmy Bogard (2018)
  • Instead of: controllers/ services/ repositories/ folders
  • Pairs with: CQRS, single responsibility

1The problem why do we even need this?

Layered folders spread every feature across the codebase and grow shared services that every feature depends on.

  • A small feature edits five folders.
  • OrderService has forty methods used by twenty features.
  • A change for one feature breaks another nobody was looking at.

2Real-life analogy the layered cake

You don't serve one guest the whole sponge layer and another the whole cream layer. You cut a slice with some of every layer. Each slice is complete on its own, and cutting one doesn't disturb the others.

  • The layers are technical layers: endpoint, logic, data.
  • A slice is a feature, end to end.

3How it solves it one folder per feature

Slices pair naturally with CQRS: each command and query is a slice. They also combine with ports and adapters: the slices live in the core, and adapters stay outside. Watch for duplication between slices; when real rules repeat, push them into the domain model.

  1. Pick one feature

    New features are the easiest start; don't move everything at once.

  2. Create its folder

    Endpoint, handler, request and response types, tests, all together.

  3. Choose the slice's style

    A simple query for reads; domain model calls for rich writes.

  4. Share the domain, not services

    Rules go on entities and value objects that slices call.

  5. Retire the giant service

    Move its methods into the slices that use them, one at a time.

  6. Keep cross-cutting concerns in middleware

    Logging, auth and validation as pipeline behaviours.

tools: MediatR or similar handler libraries, NestJS or Fastify modules per feature, Next.js and Remix route folders (slices by default), architecture tests to stop slices importing each other.

then & now matters more now

Then Fowler, PoEAA 2002 (layering); Bogard, 2018

PoEAA opened with layering: presentation, domain and data source as separate layers, which most frameworks turned into folders of controllers, services and repositories.

Now 2026

Layers still describe dependencies well, but as a folder structure they scatter features. Vertical slices (Bogard, 2018), feature folders and route-based frameworks like Next.js organise by feature instead, often combined with CQRS and a shared domain.

Verdict: Matters more now: layers for dependency direction, slices for folders.

4Gains vs losses nothing is free

What we gain

  • Feature changes stay local: one folder.
  • No giant shared services.
  • Each slice picks its style: simple or rich.
  • Easy to find, delete or own a feature.

What we lose

  • Some duplication between slices.
  • Rules can scatter if not pushed into the domain.
  • Unfamiliar to teams used to layers.
  • Cross-cutting changes touch many folders.

6Common pitfalls the usual ways this goes wrong

  • Copying rules between slices

    The same discount check in three handlers. Fix → move shared rules onto the domain model.

  • Slices importing slices

    cancel-order calls place-order's handler. Fix → share the domain; communicate through it or events.

  • Big-bang reorganisation

    A month-long PR moving every file. Fix → new features as slices; migrate old ones when touched.

  • No shared conventions

    Every slice structured differently. Fix → a template for slice layout and naming.

7When to use it (and when not)

Use it when…

  • Feature-heavy apps where most changes are “add or change a feature”.
  • Shared services that keep growing and breaking.
  • Teams that own features end to end.

Skip it when…

  • Libraries and frameworks (layers by concept make sense there).
  • Tiny apps with a handful of endpoints.

8Self-check quiz

What is a vertical slice?

All the code for one feature or use case, from endpoint to data access and tests, kept together.

What do slices share?

The domain model and infrastructure basics, not large services.

How do slices pair with CQRS?

Each command and each query becomes its own slice.

What's the main risk?

Business rules duplicated across slices instead of living in the domain model.

what would you do?Two teams keep breaking each other's features through a shared CustomerService with 55 methods. Reorganising the whole codebase isn't possible this quarter. What do you do?

Build every new feature as a slice, and when a team changes an existing feature, move the methods it uses out of CustomerService into that feature's slice (rules onto the domain). The service shrinks over time; add a rule that no new methods go into it.

try it

Take the next feature you build and put everything for it in one folder: endpoint, handler, types and tests. After it's merged, count how many files outside that folder the pull request touched.
