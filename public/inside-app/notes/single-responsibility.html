Single Responsibility

TL;DR

A module should have one reason to change, which Robert Martin later clarified as one actor: one group of people who ask for changes. Keep together code that changes for the same people, and separate code that changes for different ones (finance's tax rules, design's PDF layout, operations' archiving). It does not mean “a class should do one tiny thing”.

  • Family: SOLID principle
  • From: Robert C. Martin, 2000–2003; clarified 2014
  • Really about: who asks for changes
  • Pairs with: vertical slices, bounded context

1The problem why do we even need this?

When code that serves different people lives in one class, a change for one of them breaks the others.

  • Finance, design and operations all edit the same Invoice class.
  • A tax change shifts a number on the printed PDF.
  • Merge conflicts between unrelated work, every sprint.

2Real-life analogy one employee, three bosses

An employee who takes instructions from sales, accounts and the warehouse is always undoing one boss's request for another. Give each job to someone with one boss, and each boss can change their instructions without upsetting the others.

  • Each boss is an actor.
  • Each job with one boss is a module with one reason to change.

3How it solves it split by who asks

The test is not “does it do one thing?” but “who would ask me to change this?”. If the answer is two different groups, split it. If it's one group, keep it together, even if it's long.

  1. List who asks for changes

    For a big class, write the people or teams whose requests have changed it.

  2. Group code by actor

    Mark each method with the actor it serves.

  3. Split along actors

    One module per actor; a small coordinating object if needed.

  4. Don't split further

    A long module that serves one actor is fine. Tiny classes with one method each are a different problem.

  5. Check with history

    Files that always change together belong together; files changed for unrelated reasons may not.

  6. Apply at every level

    Functions, classes, modules and services: the same question.

invoice.tssplit by actor, not by size
// before: one class, three actors
class Invoice {
  calculateVat() { /* finance's rules */ }
  renderPdf()    { /* design's layout */ }
  archive()      { /* operations' storage */ }
}

// after: each actor's code changes on its own
export class TaxCalculator  { vatFor(lines: Line[], country: Country): Money { /* finance */ } }
export class InvoicePdf     { render(inv: InvoiceView): Buffer { /* design */ } }
export class InvoiceArchive { store(inv: InvoiceView, pdf: Buffer): Promise<void> { /* operations */ } }

export class Invoice {
  constructor(readonly lines: Line[], private tax: TaxCalculator) {}
  total(country: Country) { return sum(this.lines).add(this.tax.vatFor(this.lines, country)); }
}

then & now rethought

Then Martin, 2000–2003

“A class should have only one reason to change.” Widely read as “a class should do one thing”, which led to codebases full of tiny Manager, Helper and Validator classes.

Now 2026

Martin himself clarified it in 2014 (“The Single Responsibility Principle”) and in Clean Architecture (2017): one actor, not one task. Today it's applied to modules and services too, and backed by change-coupling data from version history.

Verdict: Rethought: still useful once you read “responsibility” as “who asks for changes”.

4Gains vs losses nothing is free

What we gain

  • Changes stay local to one actor's module.
  • Fewer merge conflicts between unrelated work.
  • Clear ownership: which team owns which module.
  • Easier testing of each concern.

What we lose

  • More modules to navigate.
  • Judgement: actors aren't always obvious.
  • Over-splitting when misread as “one thing”.
  • Coordination code between the pieces.

6Common pitfalls the usual ways this goes wrong

  • Reading it as “do one thing”

    Forty one-method classes nobody can follow. Fix → split by actor, not by size.

  • Splitting by technical layer only

    A Validator, Mapper and Helper per entity, all changed together. Fix → keep together what changes together.

  • Shared “utils” for everyone

    A helpers file every team edits. Fix → move helpers to the module whose actor needs them.

  • Ignoring history

    Splitting on a guess. Fix → look at which files really change together.

7When to use it (and when not)

Use it when…

  • A class or module changed by several teams or for unrelated reasons.
  • Frequent merge conflicts between unrelated work.
  • One actor's change keeps breaking another's feature.

Skip it when…

  • A long module that serves one actor: length alone isn't a reason.
  • Tiny scripts and prototypes.

8Self-check quiz

What does “one reason to change” mean, in Martin's later wording?

A module should be responsible to one actor: one group of people who request changes.

Does SRP mean every class should do one small thing?

No. That's a common misreading; a long module serving one actor is fine.

How can version history help?

Files that always change together probably belong together; files changed for unrelated reasons may need splitting.

What's the cost of over-applying it?

Many tiny pieces and coordination code, making the system harder to read.

what would you do?A reviewer asks you to split a 300-line ShippingRates class into twelve one-method classes “for SRP”. Every change to it comes from the logistics team. What do you answer?

That it already has one reason to change: logistics. Splitting it into twelve classes would scatter one actor's rules. Split only if another group (say finance) starts changing parts of it.

try it

Take the most-changed class in your codebase. Read its last 20 commits and write who asked for each change. If two or more groups appear, sketch the split along those lines.

remember!!

Give every module one boss, and let it be as long as that boss needs.
