The Pattern Museum

TL;DR

Some famous patterns solved problems that languages, frameworks and platforms now solve for you, or caused problems we only saw later. Worth recognising in old code and interviews, rarely worth writing today: Singleton (use one injected instance), Service Locator (use constructor injection), Visitor (use pattern matching), Page/Front Controller and Template View (your framework), Table Module and data gateways (an ORM or query builder), and server session state (stateless tokens and a shared store).

  • Family: retired patterns
  • From: GoF (1994), PoEAA (2002), Fowler (2004)
  • Use for: reading old code, interviews, history
  • Replace with: DI, pattern matching, frameworks, ORMs

1The problem why do we even need this?

Copying patterns from old books and tutorials brings their old costs without their old reasons.

  • Singletons hold global state, so tests leak into each other.
  • A service locator hides what each class depends on.
  • Session state in server memory breaks autoscaling.

2Real-life analogy the technology museum

A museum of technology has a typewriter, a fax machine and a slide rule behind glass. They solved real problems, and they shaped what followed (our keyboards still use the typewriter's layout). But nobody faxes this week's invoices.

  • The exhibits are the retired patterns.
  • The plaques explain what replaced them.

3How it solves it each exhibit and its replacement

  • Singleton (GoF): global access to one instance. Problems: hidden global state, hard-to-isolate tests. Now: create one instance in the composition root and inject it (a “singleton lifetime”, not a singleton class).
  • Service Locator (Fowler, 2004): ask a registry for dependencies. Problems: hidden dependencies, runtime failures. Now: constructor injection.
  • Visitor (GoF): add operations to a class hierarchy without editing it. Now: union types and exhaustive pattern matching (still useful in compilers and AST tools).
  • Page Controller, Front Controller, Template View, Transform View (PoEAA): how to build web pages by hand. Now: your framework's router and components.
  • Table Module, Table and Row Data Gateway (PoEAA): hand-written data access styles. Now: an ORM or a typed query builder.
  • Server Session State (PoEAA): user state in server memory. Now: stateless tokens and a shared store (Redis, a database), so any server can answer.
  1. Recognise the exhibit

    In legacy code, name the pattern and the problem it was solving.

  2. Check the reason still applies

    Sometimes it does: Visitor in a compiler, a true singleton for a hardware handle.

  3. Pick the modern replacement

    From the guide above.

  4. Replace at the edges first

    New code uses injection; old singletons get an injectable wrapper.

  5. Migrate behind tests

    Characterization tests before removing global state.

  6. Teach the history

    Knowing why a pattern existed helps people spot when its problem returns.

Vocabulary for the exam

Singleton
A class that ensures only one instance and global access to it.
Service Locator
A registry code calls to fetch its dependencies.
Visitor
Double dispatch to add operations to a class hierarchy.
Front Controller
One handler for all web requests that dispatches to commands.
Table Module
One class handling all rows of a table.
Server Session State
Keeping a user's session in server memory.
museum-to-modern.tsSingleton and Visitor, then and now
// museum: Singleton with global state
class Config { private static instance?: Config; static get() { return this.instance ??= new Config(); } }
const tax = Config.get().vatRate;          // hidden dependency, shared across tests

// now: one instance, created once, injected
const config = loadConfig(process.env);    // composition root
const pricing = new Pricing(config);       // dependency is visible and replaceable in tests

// museum: Visitor for a small hierarchy -> now: a union + exhaustive switch
type Shape = { kind: "circle"; r: number } | { kind: "rect"; w: number; h: number };
const area = (s: Shape) => {
  switch (s.kind) { case "circle": return Math.PI * s.r ** 2; case "rect": return s.w * s.h; }
};

tools: DI containers or hand-written composition roots, TypeScript/Kotlin/Rust/Java 21 pattern matching, web frameworks' routers and components, ORMs and query builders, Redis or database-backed sessions and signed tokens.

then & now mostly retired

Then GoF, 1994; Fowler, PoEAA 2002 and 2004

Each was a reasonable answer in its day: global access without globals (Singleton), decoupling without containers (Service Locator), new operations on fixed hierarchies (Visitor), and hand-built web and data layers before frameworks existed.

Now 2026

DI with constructor injection, pattern matching over union types, full-stack web frameworks, ORMs and query builders, and stateless horizontally-scaled services made them unnecessary in most code. Singleton and Service Locator are now generally called anti-patterns.

Verdict: Mostly retired: learn to recognise them, and reach for their replacements.

4Gains vs losses nothing is free

What we gain

  • No global state leaking between tests.
  • Visible dependencies.
  • Less hand-written machinery: frameworks do it.
  • Scalable services without sticky sessions.

What we lose

  • Migration effort in legacy code.
  • Some cases still need them (compilers, hardware handles).
  • Interview questions still ask about them.
  • Unlearning habits takes time.

6Common pitfalls the usual ways this goes wrong

  • Retiring by dogma

    Ripping out a working Visitor in a compiler. Fix → keep it where its problem still exists.

  • Singleton by another name

    A module-level mutable object imported everywhere. Fix → same problem: create once, inject.

  • Locator inside DI

    Classes take the container itself as a dependency. Fix → inject what the class needs, not the container.

  • Sticky sessions as a fix

    Load balancer pinning users to servers to keep session state. Fix → move state to a shared store or tokens.

7When to use it (and when not)

Use it when…

  • Reviewing legacy code full of 2000s-era patterns.
  • Preparing for interviews that still ask about them.
  • Teaching why modern tools look the way they do.

Skip it when…

  • Compilers and AST tools (Visitor still fits).
  • True hardware or process singletons (but still inject them).

8Self-check quiz

What replaced the Singleton pattern in most code?

Creating one instance in the composition root and injecting it (a singleton lifetime, not a singleton class).

Why is Service Locator considered an anti-pattern?

It hides a class's dependencies and fails at runtime instead of at construction.

Where is Visitor still a good fit?

Compilers and tools walking syntax trees with many operations over a stable set of node types.

What replaced server session state?

Stateless tokens and a shared store, so any server can handle any request.

what would you do?Your test suite passes alone but fails when run in parallel. The cause is a CurrencyRates.getInstance() singleton that tests modify. How do you fix it without a big rewrite?

Create CurrencyRates once in the composition root and pass it into the classes that use it, starting with the ones under test; give tests their own instances. Keep a temporary getInstance() delegating to the injected one for old callers, then remove it.

try it

Search your codebase for getInstance(), static mutable fields or a global container lookup. Pick one, make it a constructor parameter in two classes, and give their tests their own instance.
