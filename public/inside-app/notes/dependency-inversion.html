Dependency Inversion

TL;DR

High-level business code shouldn't depend on low-level details like databases, HTTP clients or SDKs. Both should depend on an abstraction, and the abstraction belongs to the business side: the core defines PaymentPort in its own words, and a Stripe adapter implements it. Dependencies point inward; a composition root wires real adapters at start-up, tests wire fakes.

  • Family: SOLID principle
  • From: Robert C. Martin (1996)
  • Not the same as: a DI container
  • Pairs with: ports & adapters, interface segregation

1The problem why do we even need this?

When business rules create and call infrastructure directly, they can't be tested or changed without it.

  • PlaceOrder news up a database client and a payment SDK.
  • Unit tests need a database and a sandbox account.
  • Changing payment provider means editing business code.

2Real-life analogy the lamp and the grid

A lamp doesn't depend on a particular power station. The lamp and the grid both depend on the plug standard. The country can move from coal to wind without changing a single lamp, and you can test a lamp with a battery.

  • The lamp is the business core.
  • The plug standard is the port (interface).
  • The grid is an adapter; the battery is a fake.

3How it solves it the core owns the interfaces

“Inversion” means the interface moves: not StripeClient's own interface, but one the core writes in its language. A DI container is optional; a plain function that wires objects at start-up does the same job.

  1. Find direct infrastructure calls

    new of clients, SDK imports and SQL inside business code.

  2. Write a port in the core's words

    PaymentPort.charge(amount, card), not Stripe's API shape.

  3. Implement it in an adapter

    The Stripe code lives in infrastructure and implements the port.

  4. Inject through the constructor

    The use case receives the port; it never creates it.

  5. Wire at the composition root

    One place at start-up builds real adapters; tests build fakes.

  6. Guard the direction

    An architecture test forbids core imports of infrastructure.

Vocabulary for the exam

Dependency inversion principle
High-level modules don't depend on low-level ones; both depend on abstractions owned by the high level.
Port
An interface the core defines for what it needs.
Adapter
An implementation of a port using a real technology.
Dependency injection
Passing dependencies in instead of creating them.
Composition root
The one place where the object graph is assembled.
DI container
A library that automates the composition root; optional.
place-order.tsthe core owns the port; start-up wires it
// core/ports.ts : in the core's words
export interface PaymentPort { charge(amount: Money, card: CardToken): Promise<ChargeId> }

// core/place-order.ts
export class PlaceOrder {
  constructor(private orders: OrderRepository, private payments: PaymentPort) {}
  async handle(cmd: PlaceOrderCommand) {
    const order = await this.orders.get(cmd.orderId);
    await this.payments.charge(order.total(), cmd.card);
    order.place(new Date());
    await this.orders.save(order);
  }
}

// main.ts : composition root
const placeOrder = new PlaceOrder(new PostgresOrders(db), new StripeAdapter(stripeKey));
// test: new PlaceOrder(new InMemoryOrders(), { charge: async () => chargeId("ch_1") })

tools: plain constructor injection and a hand-written composition root, or containers like NestJS DI, InversifyJS, .NET's built-in container, Spring; ArchUnit or dependency-cruiser to keep imports pointing inward.

then & now matters more now

Then Martin, 1996

Martin described it for C++ and Java layered systems: high-level policy shouldn't depend on low-level detail. It became the basis of DI frameworks like Spring (2003), which often hid it behind heavy configuration.

Now 2026

It's the heart of hexagonal, onion and clean architecture, and of fast test suites. Lighter DI (constructor injection, hand-written composition roots) replaced XML-heavy containers, and architecture tests keep the direction honest.

Verdict: More important now: it's the principle under most modern application architectures.

4Gains vs losses nothing is free

What we gain

  • Business rules testable without infrastructure.
  • Infrastructure swappable in one adapter.
  • Ports in the business's words.
  • Clear direction of dependencies.

What we lose

  • More interfaces and wiring code.
  • Indirection when reading.
  • Over-abstraction of things that never change.
  • Container magic if a framework is overused.

6Common pitfalls the usual ways this goes wrong

  • Ports shaped like the vendor

    PaymentPort copies Stripe's API, so switching still hurts. Fix → write the port from the core's needs.

  • Interfaces for everything

    An interface for a pure helper with one implementation. Fix → invert only dependencies on infrastructure or volatile code.

  • Service locator

    Code calls container.get(PaymentPort) deep inside. Fix → constructor injection, wired at the composition root.

  • Wrong direction creeping back

    A core file imports an ORM type “just once”. Fix → an architecture test fails the build.

7When to use it (and when not)

Use it when…

  • Business rules that call databases, APIs or SDKs.
  • You want fast tests of the core.
  • Infrastructure that may change (providers, storage).

Skip it when…

  • Small scripts and CRUD apps where the framework is the app.
  • Pure, stable libraries (no need to hide Math).

8Self-check quiz

What is “inverted” in dependency inversion?

Ownership of the interface: the high-level core defines it, and low-level code depends on it.

Is a DI container required?

No. A composition root that wires objects by hand applies the principle just as well.

What's a composition root?

The single place at start-up where real implementations are created and passed in.

Why shouldn't a port copy the vendor's API?

Then the core still depends on that vendor's shape, and switching still means changing the core.

what would you do?Your use cases import @prisma/client types directly, and unit tests spin up a real database, taking 9 minutes. What do you change first?

Define repository ports in the core's own types, implement them with Prisma in an adapter, inject them into the use cases, and give tests in-memory implementations. Add an import rule so the core can't import Prisma again.

try it

Find one place where business code creates an infrastructure client with new. Define a port in business terms, move the client into an adapter, inject it, and write a test with a fake. Measure the test time before and after.
