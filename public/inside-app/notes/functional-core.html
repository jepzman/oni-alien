Functional Core, Imperative Shell

TL;DR

Split code into a pure core that makes decisions from plain values (no database, network, clock or randomness) and a thin imperative shell that gathers inputs, calls the core, and performs the effects it returns. The core gets values in and returns a decision; it's trivial to test without mocks. The shell has few branches and is covered by a handful of integration tests.

  • Named by: Gary Bernhardt (2012)
  • Related: impureim sandwich, ports and adapters

1The problem why do we even need this?

When decisions are interleaved with input and output, every test needs a pile of mocks in the right order.

  • Load, decide, call an API, decide, call another, decide, save.
  • Tests need five mocks and break when the call order changes.
  • Nobody can see the business decision for the plumbing.

2Real-life analogy the architect and the builder

An architect draws plans from measurements: no concrete, no cranes. Plans can be checked, copied and changed for free. The builder takes the plans and does the heavy, risky work on site. Mistakes are cheap on paper and expensive in concrete.

  • The architect is the functional core.
  • The builder is the imperative shell.
Translating it to software

3How it solves it gather, decide, perform

Mark Seemann calls the shape an impureim sandwich: impure, pure, impure. It's ports and adapters at the scale of a single function. When the core needs more data midway, return a decision that says “need X” and let the shell loop, or gather more up front.

  1. Find the decision

    In a tangled function, what's the business decision being made?

  2. Gather inputs first

    Load everything the decision needs, including the current time.

  3. Write the pure function

    Plain values in, a decision or list of effects out; no I/O, no Date.now().

  4. Perform effects after

    Save, call APIs and publish based on the returned decision.

  5. Test the core with examples

    Tables of inputs and expected decisions; property-based tests fit well.

  6. Keep the shell dumb

    If the shell grows branches, move decisions into the core.

Vocabulary for the exam

Pure function
Same inputs, same output, no side effects.
Side effect
Anything observable outside the function: I/O, mutation, time, randomness.
Functional core
The pure part that makes decisions.
Imperative shell
The thin part that does I/O around the core.
Impureim sandwich
Impure gather, pure decide, impure perform.
Decision object
A returned value describing what should happen.

// core: pure, no I/O, no clock
export type CheckoutDecision =
  | { ok: true; total: Money; slot: Slot; reserve: Line[] }
  | { ok: false; reason: "out-of-stock" | "no-slot"; missing?: ProductId[] };

export function decideCheckout(basket: Basket, rates: TaxRates, stock: StockLevels,
                               slots: Slot[], now: Date): CheckoutDecision {
  const missing = basket.lines.filter((l) => (stock.get(l.productId) ?? 0) < l.qty).map((l) => l.productId);
  if (missing.length) return { ok: false, reason: "out-of-stock", missing };
  const slot = slots.find((s) => s.start > addHours(now, 2));
  if (!slot) return { ok: false, reason: "no-slot" };
  return { ok: true, total: priceWithTax(basket, rates), slot, reserve: basket.lines };
}

// shell: gather -> decide -> perform
const d = decideCheckout(await baskets.get(id), await tax.rates(), await stock.levels(ids), await slots.free(), new Date());
if (d.ok) { await stockApi.reserve(d.reserve); await orders.save(Order.place(id, d.total, d.slot)); }

tools: plain functions and types; property-based testing (fast-check, Hypothesis) for the core; functional libraries (Effect, fp-ts, Arrow) if your team wants effects modelled explicitly, though they aren't needed.

then & now matters more now

Then Bernhardt, 2012 (not in the 2002–2005 books)

The enterprise books of 2002–2005 had no such split: logic lived in objects or scripts that called repositories and services freely, tested with mocks.

Now 2026

Gary Bernhardt's “Boundaries” talk (2012) named it, functional programming made it mainstream, and Mark Seemann's “impureim sandwich” gave it a recipe. It's the small-scale version of ports and adapters, and the easiest way to cut mock-heavy tests.

Verdict: A newer idea that matters more and more; use it wherever decisions hide among I/O.

4Gains vs losses nothing is free

What we gain

  • Decisions tested without mocks.
  • Clear business logic, separate from plumbing.
  • Deterministic: time and randomness passed in.
  • Easy to reuse the core elsewhere.

What we lose

  • Gathering up front may load more than needed.
  • Awkward when decisions need data in several rounds.
  • Decision types to define.
  • Unfamiliar to object-oriented habits.

6Common pitfalls the usual ways this goes wrong

  • Hidden effects in the core

    The “pure” function calls Date.now() or a logger. Fix → pass time in; return log entries if needed.

  • A fat shell

    The shell grows if-statements about business cases. Fix → move decisions into the core; the shell just follows them.

  • Mocking the core

    Tests of the shell mock the pure function. Fix → test the core with values; test the shell end to end, lightly.

  • Forcing it everywhere

    Contortions for a simple CRUD save. Fix → use it where decisions are rich enough to deserve tests.

7When to use it (and when not)

Use it when…

  • Functions that make business decisions and also do I/O.
  • Tests full of mocks and call-order assertions.
  • Logic that depends on time or randomness.

Skip it when…

  • Pure plumbing with no decisions (just a save).
  • Decisions that truly need many rounds of I/O (use a state machine or workflow).

8Self-check quiz

What goes in the functional core?

Pure decision-making: plain values in, a decision out, no I/O, clock or randomness.

What does the shell do?

Gathers inputs, calls the core, and performs the effects it decides.

How do you handle the current time?

The shell reads it and passes it in as a value.

Why does this reduce mocking?

The core has no dependencies, so tests pass values and check results.

what would you do?A test for the delivery-fee rule needs mocks for the database, the clock, the maps API and the feature-flag client, and fails whenever someone reorders calls. How do you restructure it?

Gather the basket, address distance, current time and flag value in the shell, pass them as values to a pure deliveryFee(…) function, and test that function with a table of examples. Keep one integration test for the shell.

try it

Pick a function in your code that both reads from somewhere and decides something. Split it into gather, a pure decide function, and perform. Write five example tests for the pure part with no mocks.
