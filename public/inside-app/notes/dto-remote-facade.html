DTOs & Remote Facade

TL;DR

Across a network, every call costs. A remote facade offers coarse-grained operations (one call per screen or use case) on top of a fine-grained domain. A DTO (data transfer object) is the shape sent over the wire: just the fields the client needs, separate from your entities. You get fewer round trips, no leaked internals, and an API contract that can stay stable while the domain changes.

  • Family: distribution pattern
  • From: Fowler, PoEAA (2002)
  • Today also: BFF, GraphQL, OpenAPI-typed DTOs
  • Pairs with: open host service (Vol. 7), BFF

1The problem why do we even need this?

Exposing fine-grained objects over a network leads to chatty APIs or leaked internals.

  • A screen needs fifteen calls on a slow mobile network.
  • Entities serialised straight to JSON leak hashes and internal flags.
  • A database rename breaks the mobile app.

2Real-life analogy the mail-order form

You don't phone the shop once per item to ask its size, price and stock. You fill in one order form and get one confirmation with what you need. The form is designed for customers, not a photocopy of the warehouse ledger.

  • The shop counter is the remote facade.
  • The form and the confirmation are DTOs.
Translating it to software
In real lifeIn your code

3How it solves it coarse calls, shaped data

Fowler designed these to cut round trips in the EJB era. Today the bigger reason is the contract: a DTO is your published language (Vol. 7), and keeping it separate from entities lets both change at their own pace. For many differently-shaped clients, a BFF or GraphQL lets each client shape its own DTOs.

  1. Start from the screen or use case

    What does the client need in one go?

  2. Design the DTO for that

    Only those fields, named for the client, with no internal IDs or flags.

  3. Offer one coarse operation

    GET /order-summary/7, POST /checkout.

  4. Map inside the facade

    Domain → DTO in one place, tested.

  5. Document and version it

    OpenAPI schema; additive changes, new versions for breaking ones.

  6. Consider a BFF or GraphQL

    When several clients need very different shapes.

Vocabulary for the exam

DTO
A plain object carrying data across a boundary, with no behaviour.
Remote facade
A coarse-grained interface over fine-grained objects, for remote callers.
Chatty interface
One that needs many small calls to do one job.
Over-posting / mass assignment
Accepting fields in a request that clients shouldn't set.
BFF
Backend for frontend: a server-side facade per client type.
Mapper
Code that converts between domain objects and DTOs.
order-summary.tsa DTO for one screen, mapped inside
// the contract: what the app needs, nothing more
export type OrderSummaryDto = {
  number: string; status: "placed" | "shipped" | "delivered";
  deliverTo: { name: string; street: string; city: string };
  lines: { name: string; qty: number; price: string }[];
  total: string;
};

app.get("/order-summary/:id", async (req, res) => {
  const order = await orders.get(orderId(req.params.id));
  const customer = await customers.get(order.customerId);
  res.json(toSummary(order, customer));   // never res.json(order)
});

const toSummary = (o: Order, c: Customer): OrderSummaryDto => ({
  number: o.number, status: o.status, deliverTo: c.deliveryAddress.toDto(c.name),
  lines: o.lines.map((l) => ({ name: l.productName, qty: l.qty.value, price: l.subtotal().format() })),
  total: o.total().format(),
});

tools: OpenAPI with generated client types, Zod or class-validator schemas for request DTOs, mapping helpers (or plain functions), BFF services, GraphQL with DataLoader, gRPC/Protobuf messages for service-to-service DTOs.

then & now rethought

Then Fowler, PoEAA 2002

Fowler introduced DTOs and remote facades mainly for performance: remote calls in EJB and CORBA were expensive, so you batched data into serialisable objects and offered coarse operations.

Now 2026

The performance reason still applies on mobile networks, but the main reason now is the contract: DTOs as OpenAPI or Protobuf schemas, separate from entities, safe against over-posting. BFFs and GraphQL let each client shape its own DTOs.

Verdict: Rethought: same patterns, now mostly for stable, safe contracts rather than raw speed.

4Gains vs losses nothing is free

What we gain

  • Fewer round trips.
  • No leaked internals or over-posting.
  • Stable API while the domain changes.
  • Clear contracts for clients and docs.

What we lose

  • Mapping code to write and test.
  • More types: DTOs per use case.
  • Coarse calls may over-fetch for some clients.
  • Duplication between DTO and entity fields.

6Common pitfalls the usual ways this goes wrong

  • Returning entities

    res.json(customer) leaks the password hash. Fix → always map to a DTO; never serialise entities.

  • Binding requests to entities

    Clients set isAdmin by adding a field. Fix → request DTOs with an allow-list of fields.

  • One DTO for everything

    A 60-field OrderDto used by every screen. Fix → DTOs per use case or per client (BFF).

  • Generic CRUD over HTTP

    Every table exposed as fine-grained endpoints. Fix → design operations around use cases.

7When to use it (and when not)

Use it when…

  • Any API crossing a network, especially to mobile or third parties.
  • Screens that need data from several objects.
  • Keeping an API stable while the domain changes.

Skip it when…

  • In-process calls between modules (pass domain objects or plain values).
  • Prototypes where the API and the model are deliberately the same.

8Self-check quiz

What's a remote facade?

A coarse-grained interface over fine-grained objects, so remote clients need few calls.

What's a DTO?

A plain data object shaped for transfer across a boundary, with no behaviour.

Why not return entities as JSON?

They leak internals, invite mass assignment, and tie clients to the database shape.

When do a BFF or GraphQL help?

When different clients need very different shapes of the same data.

what would you do?A security review finds that PATCH /users/:id accepts any JSON and saves it into the User entity; a tester made themselves an admin. What do you change?

Accept a request DTO with an explicit allow-list of editable fields (name, phone), validate it, map it onto the entity through domain methods, and never bind request bodies to entities directly. Add a test that sending isAdmin has no effect.

try it

Find one endpoint that returns an ORM entity directly. Write a DTO type with only what the client uses, a mapper function with a test, and compare the JSON size before and after.

remember!!

Send one order form, never the warehouse ledger.
