Liskov Substitution

TL;DR

If code works with a type, it must keep working with any subtype or implementation of it. A subtype may not demand more (stricter inputs) or promise less (weaker results, new exceptions) than its parent. When an implementation can't keep a promise, it isn't really that type: split the interface by ability instead of throwing “not supported”.

  • Family: SOLID principle
  • From: Barbara Liskov (1987); Liskov & Wing (1994)
  • Applies to: subclasses, interfaces, API versions
  • Check with: contract tests

1The problem why do we even need this?

A subtype that quietly breaks a promise of its parent compiles fine and fails at runtime, far from where it was written.

  • ReadOnlyCart extends Cart, but add() throws.
  • A cached repository returns stale data where callers expect fresh.
  • Callers fill up with if (x instanceof …) checks.

2Real-life analogy the substitute teacher

When a teacher is ill, the substitute must teach from the same plan, take the register and mark homework. One who only answers in French or refuses to mark isn't really a substitute: the class plan breaks.

  • The lesson plan is the contract.
  • A good substitute is a proper subtype.
  • The class shouldn't notice the swap.

3How it solves it keep the promises, or split the type

The rules: preconditions can't be stronger, postconditions can't be weaker, invariants must hold, and no new exceptions callers don't expect. It applies to interface implementations and to API versions too.

  1. Write the contract down

    What does the type accept, return and promise? Comments, types and tests.

  2. Check each implementation

    Does it accept everything the parent accepts and return what the parent promises?

  3. Watch for “not supported”

    An implementation that throws for part of the interface is a sign of a wrong type.

  4. Split by ability

    Separate interfaces for what different implementations really can do.

  5. Prefer composition

    Reuse code by holding an object, not by inheriting one you can't fully honour.

  6. Run one contract test for all

    The same test suite against every implementation.

Vocabulary for the exam

Liskov substitution principle
Subtypes must be usable wherever their base type is expected.
Precondition
What must be true before calling: a subtype can't demand more.
Postcondition
What's true after: a subtype can't promise less.
Invariant
What's always true about the object.
Contract test
A test suite every implementation of an interface must pass.
Refused bequest
A subclass that doesn't want what it inherits: a hint of the wrong hierarchy.
cart.contract.test.tsone contract, every implementation
export interface CartView     { lines(): readonly Line[]; total(): Money }
export interface EditableCart extends CartView { add(p: ProductId, q: Quantity): void }

// every EditableCart must pass this, whatever its storage
export function editableCartContract(make: () => EditableCart) {
  test("adding a product increases the total", () => {
    const cart = make();
    const before = cart.total();
    cart.add(productId("BIKE-42"), Quantity.of(1));
    expect(cart.total().cents).toBeGreaterThan(before.cents);
  });
}

describe("InMemoryCart", () => editableCartContract(() => new InMemoryCart()));

then & now still core

Then Liskov, 1987; Liskov & Wing, 1994

Liskov's 1987 keynote defined behavioural subtyping; with Wing (1994) it became precise rules about preconditions, postconditions and invariants. Martin made it the “L” in SOLID, mostly about class hierarchies.

Now 2026

Deep inheritance is rarer, but the principle applies equally to interface implementations, plug-ins, mocks and API versions. Contract tests and consumer-driven contracts are the practical tools.

Verdict: Still core. It's the most precise of the five, and the least fashion-dependent.

4Gains vs losses nothing is free

What we gain

  • Safe substitution: swap implementations without surprises.
  • No type checks scattered through callers.
  • Honest types: they say what things can do.
  • Reusable tests across implementations.

What we lose

  • More, smaller interfaces.
  • Contracts take thought to write down.
  • Reworking hierarchies that already exist.
  • Behaviour isn't checked by compilers alone.

6Common pitfalls the usual ways this goes wrong

  • “Not supported” methods

    An implementation throws for half the interface. Fix → split the interface by ability.

  • Inheriting for reuse

    A class extends another only to reuse a few methods. Fix → compose: hold the other object instead.

  • Stricter inputs in a subtype

    The subclass rejects values the parent accepts. Fix → accept at least what the parent accepts.

  • Trusting the compiler

    Signatures match, so it “must” be fine. Fix → contract tests check behaviour, not just types.

7When to use it (and when not)

Use it when…

  • Designing interfaces with several implementations (storage, payment, carriers).
  • Class hierarchies where callers check concrete types.
  • Versioning an API that old clients still call.

Skip it when…

  • There's only one implementation and no hierarchy.
  • Internal test doubles that deliberately do less (keep them in tests).

8Self-check quiz

State the Liskov substitution principle simply.

Code that works with a type must keep working with any of its subtypes or implementations.

Can a subtype require stricter inputs than its parent?

No: preconditions may not be strengthened.

What does a method that throws “not supported” suggest?

The type is wrong: the implementation can't honour the contract, so split the interface.

How do you check behaviour across implementations?

A shared contract test suite run against each one.

what would you do?Your FileStorage interface has delete(), and the new archive storage throws “archives are immutable” on delete. A cleanup job crashed overnight. What do you change?

Split the interface: a readable/writable storage for everything, and a deletable one only for storages that support it. The cleanup job asks for the deletable kind, so the archive can't be passed to it. Add a contract test for each interface.

try it

Pick an interface with two or more implementations in your code. Write three contract tests describing what every implementation must do, run them against each, and fix or split whatever fails.

remember!!

A good substitute follows the whole lesson plan.
