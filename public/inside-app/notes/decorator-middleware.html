Decorator & Middleware

TL;DR

A decorator wraps an object with another that has the same interface, adding one behaviour (logging, retries, timeouts, caching, metrics, authorisation) before or after passing the call on. Stack several: log(retry(timeout(stripe))). Callers can't tell the difference. HTTP middleware and interceptors are the same idea for requests. Write cross-cutting code once, compose it per use.

  • Family: structural pattern (GoF)
  • From: Gamma et al. (1994)
  • Everywhere as: middleware, interceptors, higher-order functions
  • Pairs with: retry with backoff, circuit breaker (Vol. 1)

1The problem why do we even need this?

Cross-cutting concerns copied into every method drift apart and bury the real logic.

  • Logging, retries, timeouts and metrics copied into forty methods.
  • One copy forgot the timeout and hung checkout.
  • Changing the retry policy means forty edits.

2Real-life analogy gift wrapping

A present goes in paper, then a ribbon, then a padded envelope for posting. Each layer adds one thing, and from the outside it's still something you can hand over. Add or remove a layer without touching the present.

  • The present is the real implementation.
  • Each layer is a decorator.
  • “Something you can hand over” is the shared interface.

3How it solves it same shape, one extra behaviour per layer

In functional style a decorator is a higher-order function: withRetry(fn) returns a new function with the same signature. Order matters: a retry outside a timeout retries timed-out calls; inside, it doesn't.

  1. Identify the shared interface

    The port or function signature all layers will have.

  2. Write one decorator per concern

    Timeout, retry, logging, caching, each small and tested alone.

  3. Compose in the composition root

    Wrap the real adapter in the order you want.

  4. Think about order

    Usually: metrics outside, then retry, then timeout, then the real call.

  5. Use middleware for requests

    Auth, validation, correlation IDs as an HTTP or handler pipeline.

  6. Keep business rules out

    Decorators handle cross-cutting concerns, not domain decisions.

Vocabulary for the exam

Decorator
A wrapper with the same interface that adds behaviour.
Cross-cutting concern
Behaviour needed in many places: logging, security, retries.
Middleware
A pipeline of functions around request handling, each calling the next.
Interceptor
A framework hook that wraps calls (Angular, gRPC, NestJS).
Higher-order function
A function that takes a function and returns a wrapped one.
AOP
Aspect-oriented programming: framework-level decoration by rules.
payments.compose.tsdecorators as wrappers with the same interface
const withTimeout = (ms: number) => (p: PaymentPort): PaymentPort => ({
  charge: (a, c) => Promise.race([p.charge(a, c), rejectAfter(ms, "payment timeout")]),
});
const withRetry = (times: number) => (p: PaymentPort): PaymentPort => ({
  charge: (a, c) => retry(() => p.charge(a, c), { times, backoffMs: 200, jitter: true }),
});
const withMetrics = (p: PaymentPort): PaymentPort => ({
  charge: (a, c) => timed("payment.charge", () => p.charge(a, c)),
});

// composition root: the use case never knows
const payments = withMetrics(withRetry(3)(withTimeout(2000)(new StripeAdapter(key))));

// HTTP middleware: the same idea for requests
app.use(correlationId(), requestLogging(), authenticate(), rateLimit({ perMinute: 60 }));

tools: HTTP middleware (Express, Fastify hooks, ASP.NET Core middleware), interceptors (NestJS, gRPC, Angular HTTP), resilience libraries (Polly, resilience4j, cockatiel) that are decorators, Python and TypeScript decorators syntax.

then & now still core

Then Gamma et al., 1994

The GoF's Decorator added responsibilities to objects dynamically, with examples like adding borders and scroll bars to GUI widgets, as a flexible alternative to subclassing.

Now 2026

It's everywhere, often unnamed: HTTP middleware, gRPC and NestJS interceptors, resilience libraries like Polly and resilience4j, and higher-order functions. Language decorators (Python, TypeScript) put it in the syntax.

Verdict: Still core: one of the GoF patterns used more today than in 1994.

4Gains vs losses nothing is free

What we gain

  • Write each concern once.
  • Real logic stays clean.
  • Compose per use: different stacks for different callers.
  • Each layer tested alone.

What we lose

  • Order bugs: layers in the wrong order.
  • Debugging through layers.
  • Hidden behaviour if composition is buried.
  • Wrapping every method of a big interface.

6Common pitfalls the usual ways this goes wrong

  • Wrong order

    Retry inside the timeout, so a slow call is never retried, or retries exceed the caller's deadline. Fix → decide the order deliberately and test it.

  • Business rules in decorators

    A “discount decorator” around the price calculator. Fix → decorators for cross-cutting concerns; rules in the domain.

  • Invisible magic

    Annotations apply caching and transactions nobody can see. Fix → compose explicitly in one place, or document the rules.

  • Retrying non-idempotent calls

    A retry decorator charges a card twice. Fix → idempotency keys, or no retry for that call.

7When to use it (and when not)

Use it when…

  • Logging, metrics, retries, timeouts, caching, auth around many calls.
  • Request pipelines in web frameworks.
  • Adding behaviour to a third-party client you can't change.

Skip it when…

  • A concern needed in exactly one place (just write it there).
  • Business decisions (those belong in the domain).

8Self-check quiz

What does a decorator do?

Wraps an object with another that has the same interface and adds one behaviour.

How is HTTP middleware related?

It's the same idea for requests: a pipeline of wrappers, each calling the next.

Why does order matter?

Each layer sees what the inner layers do: a retry outside a timeout behaves differently from one inside.

What should never go in a decorator?

Business rules; decorators are for cross-cutting concerns.

what would you do?After adding a retry wrapper to all outgoing HTTP calls, some customers are charged twice when the payment provider is slow. What went wrong, and what do you change?

The retry repeated a non-idempotent charge after a timeout that had actually succeeded. Send an idempotency key with each charge so the provider ignores duplicates, or exclude non-idempotent calls from the retry decorator.

try it

Find a cross-cutting concern copied into several methods (timing, logging, retries). Write it once as a wrapper with the same interface, apply it in the composition root, and delete the copies.

remember!!

Wrap the present layer by layer; never open the box to add a ribbon.
