Offline Locks & ETags

TL;DR

A database transaction can't stay open while a person edits a form for ten minutes, so two people can overwrite each other without knowing. An optimistic offline lock saves a version with the data; a save succeeds only if the version is unchanged, otherwise the user sees a conflict instead of silently losing work. Over HTTP this is ETag + If-Match → 412. Use a pessimistic lock (a lease with an expiry) only where conflicts are costly and frequent.

  • Family: offline concurrency
  • From: Fowler, PoEAA (2002)
  • Over HTTP: ETag, If-Match, 412 Precondition Failed
  • Pairs with: optimistic locking (Vol. 3)

1The problem why do we even need this?

When two people edit the same record over minutes, the second save silently erases the first.

  • Two agents edit one order; one agent's address change vanishes.
  • A mobile app syncs an old copy over a newer one.
  • No error, so nobody knows until the parcel goes astray.

2Real-life analogy the shared document and the room key

A shared online document warns you: “this paragraph was changed since you opened it”, and lets you review. A meeting room works differently: one person takes the key for an hour; others wait.

  • The warning is an optimistic lock: check at save time.
  • The key is a pessimistic lock: block others up front.

3How it solves it versions, ETags and conflicts

This is the same idea as optimistic locking in the database (Vol. 3), stretched over a whole user session: the version travels to the browser and back. Conflicts are rare in most apps, so optimistic is the default.

  1. Add a version

    A column incremented on every update (or a timestamp, or a hash).

  2. Send it to the client

    As an ETag header or a field in the response.

  3. Require it on save

    If-Match header or a version field; reject saves without one.

  4. Update conditionally

    UPDATE … WHERE id = ? AND version = ?; zero rows means conflict.

  5. Show the conflict

    412 or 409 with the current data; let the user merge or retry.

  6. Pessimistic only where needed

    A lease with an owner and an expiry, released on save or timeout.

Vocabulary for the exam

Lost update
A later save overwriting an earlier one without noticing.
Optimistic offline lock
Check a version at save time; fail on conflict.
Pessimistic offline lock
Mark the record as being edited so others can't.
ETag
An HTTP header identifying a version of a resource.
If-Match
A request header: only apply if the ETag still matches.
412 Precondition Failed
The response when If-Match doesn't match.
orders.route.tsETag and If-Match on an edit endpoint
app.get("/orders/:id", async (req, res) => {
  const o = await orders.find(req.params.id);
  res.set("ETag", `"${o.version}"`).json(toDto(o));
});

app.put("/orders/:id", async (req, res) => {
  const ifMatch = req.get("If-Match");
  if (!ifMatch) return res.status(428).send("If-Match required");
  const expected = Number(ifMatch.replaceAll('"', ""));
  const updated = await db.updateTable("orders")
    .set({ ...fromDto(req.body), version: expected + 1 })
    .where("id", "=", req.params.id).where("version", "=", expected)
    .executeTakeFirst();
  if (Number(updated.numUpdatedRows) === 0) return res.status(412).json(await currentDto(req.params.id));
  res.set("ETag", `"${expected + 1}"`).sendStatus(204);
});

tools: ORM version columns (@Version in JPA, concurrency tokens in EF Core, Rails lock_version), HTTP ETag/If-Match support in frameworks and API gateways, merge UIs for conflicts.

then & now still core

Then Fowler, PoEAA 2002

Fowler described optimistic, pessimistic, coarse-grained and implicit offline locks for web and rich-client apps where a business transaction spans several requests.

Now 2026

Exactly the same problem, with more clients (tabs, phones, offline apps). HTTP's ETag and If-Match made the optimistic version a web standard, and ORMs add version columns with one annotation.

Verdict: Still core: every app where two people can edit the same thing needs it.

4Gains vs losses nothing is free

What we gain

  • No silent lost updates.
  • No long database locks.
  • Standard HTTP mechanism for clients.
  • Users see conflicts and can fix them.

What we lose

  • Conflict handling UI to build.
  • Version field on every editable resource.
  • Retries under heavy contention.
  • Pessimistic leases need expiry and cleanup.

6Common pitfalls the usual ways this goes wrong

  • Version not sent back

    The client never sends If-Match, so nothing is checked. Fix → require it: 428 Precondition Required without it.

  • Database transactions across user think time

    A transaction open while the form is on screen. Fix → short transactions; carry a version instead.

  • Pessimistic locks without expiry

    Sam goes home; the order stays locked all weekend. Fix → leases with an owner, an expiry and an admin override.

  • Unhelpful conflicts

    “Error 412” with no detail. Fix → return the current data and show what changed.

7When to use it (and when not)

Use it when…

  • Records edited by several people or devices.
  • APIs where clients read, edit and write back.
  • Offline-capable or mobile apps that sync.

Skip it when…

  • Append-only data (new rows, no edits).
  • Single-user data where nobody else can edit it.

8Self-check quiz

What is a lost update?

A later save overwriting an earlier one without noticing.

How does an optimistic offline lock work?

A version travels with the data; a save succeeds only if the stored version is unchanged.

What do ETag and If-Match do in HTTP?

ETag identifies the version; If-Match makes the server apply the change only if that version is still current, else 412.

When is a pessimistic lock worth it?

When conflicts are frequent and costly to merge, with a lease that expires.

what would you do?Warehouse staff on tablets keep complaining that stock counts “jump back”. Two tablets edit the same bin and the last sync wins. What do you change?

Add a version per bin, send it with each sync, and reject stale updates with a conflict the tablet must resolve. Better still for counts, send deltas (“−3”) instead of absolute values so concurrent changes add up.

try it

Pick one edit screen in your app. Open it in two tabs, change different fields in each, and save both. If the first change disappears, add a version column, return it as an ETag, and reject mismatched saves with 412.

remember!!

If it changed since you opened it, say so; never overwrite silently.
