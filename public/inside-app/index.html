Inside the Application

My notes on what goes on inside one application: the SOLID principles read with today's eyes, the enterprise patterns hiding inside your ORM, ways to shape an app so it stays easy to change, and the classic object patterns that still earn their place. 18 patterns in four collections, rated on the same nine code-design qualities as Vol. 7. The sources are mostly from 1994 to 2005 (the Gang of Four, Fowler's Patterns of Enterprise Application Architecture, Robert C. Martin), so every note has a then & now box with a verdict, and the last note is a museum of patterns you can retire. Examples use TypeScript.

SOLID, read today five principles, minus the misreadings

  1. 01Single Responsibility rethoughtKeep together what changes for the same people, and apart what changes for different ones.p. 01
  2. 02Open–Closed rethoughtAdd new cases by adding code, not by editing a growing switch.p. 02
  3. 03Liskov Substitution still coreA subtype must keep every promise its parent makes, or callers break.p. 03
  4. 04Interface Segregation still coreDepend on small interfaces shaped by what you use, not on fat ones.p. 04
  5. 05Dependency Inversion matters more nowBusiness code defines the interfaces; databases and APIs plug into them.p. 05

Inside your ORM enterprise patterns you use every day without naming them

  1. 06Active Record vs Data Mapper built in nowObjects that save themselves, or a separate mapper that saves them: pick by complexity.p. 06
  2. 07Unit of Work & Identity Map built in nowTrack what changed in one request, keep one copy of each row, and save it all at once.p. 07
  3. 08Lazy Loading built in nowLoad related data only when it's touched, and know when that's a trap.p. 08
  4. 09Offline Locks & ETags still coreStop one user's save silently overwriting another's, across minutes of editing.p. 09
  5. 10DTOs & Remote Facade rethoughtSend one shaped message per use case, not your entities, and not thirty small calls.p. 10

Shaping the app where code goes, so it stays easy to change

  1. 11Transaction Script vs Domain Model still coreOne procedure per use case, or objects that hold the rules: choose per area.p. 11
  2. 12Ports & Adapters matters more nowPut the business core in the middle; HTTP, databases and APIs are adapters around it.p. 12
  3. 13Vertical Slices matters more nowOrganise code by feature, end to end, instead of by technical layer.p. 13
  4. 14Functional Core, Imperative Shell matters more nowMake decisions in pure functions; do all the input and output around them.p. 14

Classic patterns the Gang of Four, what to keep, and what to retire

  1. 15Strategy & Command as Functions built in nowSwap behaviour and queue actions with functions and data, not class hierarchies.p. 15
  2. 16Decorator & Middleware still coreWrap a thing in another with the same shape to add logging, retries or caching.p. 16
  3. 17Adapter & Facade still coreMake a foreign interface fit yours, and hide a complicated one behind a simple door.p. 17
  4. 18The Pattern Museum mostly retiredSingleton, Service Locator, Visitor and friends: what replaced them, and why.p. 18

★The nine code-design ratings what a reviewer would ask in a pull request

Every note scores the pattern from 1 (poor) to 5 (great) on the same nine things, comparing an app without the pattern to the same app with it.

Simplicity
A new teammate can read the code and predict what it does.
Domain clarity
The code uses the words the business uses, and its rules are easy to find.
Correctness
Invalid states and broken business rules are hard or impossible to create.
Changeability
A new rule or feature touches a few places, not twenty.
Testability
Business rules can be tested without a database, a network or a framework.
Low coupling
One module or team can change without breaking the others.
Performance
Queries, memory and latency stay reasonable. High = no extra cost.
Low ceremony
Few extra classes, layers and mappings to write. High = light.
Team scalability
Several teams can work on the system without stepping on each other.
kept gained with the pattern lost with the pattern

⟳Then & now is a twenty-year-old idea still worth it?

Most ideas in this volume come from books written twenty or more years ago. Every note ends its “how” section with what the book said, what changed since, and one of these verdicts:

still core × 6
As useful as when it was written.
matters more now × 4
More relevant today than when it was written.
built in now × 4
Your framework or language does it for you; know it to use the tool well.
rethought × 3
The idea holds, the way the book did it has changed.
mostly retired × 1
Rarely worth doing the original way today.
first law

A pattern is a name for a solution to a problem you have. If you can't name the problem, you don't need the pattern, however famous the book.
