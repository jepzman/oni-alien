Just-Enough Up-Front Design

TL;DR

Just-enough up-front design means deciding before building only the things that are expensive to change later (one-way doors: data ownership, contracts, identifiers, technology commitments), and leaving the rest to be learned while building. Timebox it (often one to two weeks), write it short (a design note and an ADR), and spike the riskiest unknown. Too little design costs wrong turns; too much costs months of guessing what code would teach.

  • Lives in: a short design note and an ADR per big change

1The situation Larder, 10 April 2028

The utility tree put checkout at 60,000 orders a day first, and that means giving Ordering its own database. Ben's team wants to start coding on Monday; Eli wants a three-month design phase. One side risks a costly wrong turn; the other risks designing for months what code would teach in weeks.

  • Some decisions are cheap to change later; some aren't.
  • Long design phases guess at things building would show.
  • No design at all leaves the expensive decisions to chance.

2Real-life analogy planning a long hike

Before a long hike you decide what you can't change on the trail: the route, the hut bookings, the water points. You don't plan every step; you choose those on the path, looking at the ground in front of you.

3How it solves it decide the one-way doors, timeboxed

Ana gave the design two weeks. Decided up front, because they're hard to undo: Ordering owns its database; other modules get order data only from events and the Ordering API; order ids stay the same; money in integer cents. Left to learn while building: the exact schema, caching, instance counts, batch sizes. Output: a two-page design note, ADR 0027, and a spike on the riskiest part, copying live data. Ben's team started in week three.

  1. List the decisions

    Everything the design needs to settle.

  2. Sort into one-way and two-way doors

    Expensive to change later, or cheap.

  3. Timebox the design

    One to two weeks for most changes.

  4. Decide the one-way doors

    In an ADR, with options.

  5. Spike the riskiest unknown

    Code to answer one question.

  6. Leave the rest to building

    And record decisions as they're made.

Vocabulary for the exam

Up-front design
Design done before building starts.
Just enough
Only what's costly to change later.
One-way door
A decision that's hard or expensive to reverse.
Spike
Short, throwaway code to answer one question.
Timebox
A fixed amount of time for an activity.
Big design up front
Designing everything before building (the anti-pattern).

4Gains vs losses nothing is free

What we gain

  • The expensive decisions made deliberately.
  • Weeks, not months, before building.
  • Learning from code for the rest.
  • A short note people actually read.
  • Spikes reduce the biggest unknown.

What we lose

  • Some rework on two-way doors.
  • Judging one-way vs two-way takes experience.
  • Pressure to extend the timebox.
  • Not every risk shows in a spike.

6Common pitfalls the usual ways this goes wrong

  • Designing everything

    Schema in a 40-page document. Fix → only the one-way doors.

  • Designing nothing

    Data ownership decided by accident. Fix → two weeks on what's hard to change.

  • No timebox

    Design drifts into month three. Fix → fix the time, then decide.

  • No spike

    The risky part assumed. Fix → code to answer it.

7When to use it (and when not)

Use it when…

  • Big changes: new services, data moves, new platforms.
  • When teams disagree on how much design is needed.
  • Before committing to a vendor or technology.
  • When a mistake would be costly to undo.

Skip it when…

  • Small, reversible changes inside one module.

try it

Take your next big change. List every decision it needs, mark each one-way or two-way, and give yourself one week to decide only the one-way ones, with one spike for the biggest unknown.
