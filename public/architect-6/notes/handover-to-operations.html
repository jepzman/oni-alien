Handover to Operations

TL;DR

When a system passes from the team that built it to the team that will run it, hand it over properly: acceptance criteria set by the receiving team (runbooks tested, alerts and SLOs, dashboards, known issues), practice (game days where the new owners drive), and a warranty period where the builders stay reachable as second line. The receivers take the pager only when they're ready; the customers never notice the change.

  • Origin: service transition (ITIL); SRE production readiness

1The situation Larder, 4 September 2028

The Ordering database split is done; Ben's team wants to move on to Grace's next bets. From October the new reliability team will run Ordering on call. Last time a system changed hands (Dispatch, 2026), the runbook was a wiki page from the build, and the first incident took four hours because nobody knew the failover. A handover by wiki page.

  • Builders know things that aren't written down.
  • Runbooks written during the build go stale.
  • The first incident is a bad time to learn.

2Real-life analogy the bedside shift handover

A good nurse hands over a patient at the bedside: what's wrong, what's been done, what to watch for, what to do if it happens. And the outgoing nurse stays reachable for the first hours of the next shift. The patient never notices the change.

3How it solves it receivers' criteria, practice, warranty

The reliability team wrote the acceptance criteria: runbooks for the top ten alerts, tested; SLOs and dashboards they agreed; two game days where they ran failovers while Ben's team watched; known issues and debt listed. Then a four-week warranty with Ben's team as second line. On 1 October the reliability team took the pager. First incident, 9 October: a lagging replica, fixed in 18 minutes from the runbook.

  1. Let the receivers set criteria

    What they need to run it.

  2. Write and test runbooks

    For the alerts that will actually fire.

  3. Agree SLOs and dashboards

    With the people who'll watch them.

  4. Practise with game days

    The new owners drive.

  5. List known issues

    Debt, quirks, workarounds.

  6. Give a warranty period

    Builders as second line for weeks.

Vocabulary for the exam

Handover
Passing responsibility for a system to another team.
Runbook
Steps to diagnose and fix a known problem.
Game day
A planned exercise that simulates failures.
Warranty period
Time when the builders support the new owners.
Production readiness
A system's fitness to be run in production.
Second line
The people the first responders escalate to.

4Gains vs losses nothing is free

What we gain

  • A smooth first incident.
  • Knowledge passed on, not lost.
  • Builders freed for new work.
  • Receivers confident.
  • Customers notice nothing.

What we lose

  • Weeks of preparation.
  • Builders' time during the warranty.
  • Game days carry some risk.
  • Receivers may push back on gaps.

6Common pitfalls the usual ways this goes wrong

  • Builders set the criteria

    “Looks done to us.” Fix → the receivers decide.

  • Untested runbooks

    Written, never tried. Fix → game days.

  • Clean break

    Builders vanish on day one. Fix → a warranty period.

  • Hidden debt

    Quirks discovered at 3 a.m. Fix → list known issues.

7When to use it (and when not)

Use it when…

  • Systems moving from a build team to a run team.
  • New on-call rotations.
  • Contractors handing over to staff.
  • Before builders move to other work.

Skip it when…

  • Teams that build and run their own systems (you build it, you run it).

8Self-check quiz

Who sets the acceptance criteria?

The receiving team.

What's a game day for?

Letting the new owners practise failures while the builders watch.

What's the warranty period?

Four weeks with the builders as second line.

How did the first incident go?

A lagging replica, fixed in 18 minutes from the runbook.

try it

Pick a system your team built that someone else runs (or will). Ask them what they'd need to be confident, run one game day where they drive, and agree a warranty period.
