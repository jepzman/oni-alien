Migration Planning

TL;DR

Migration planning moves a live system (data, traffic, users) in small, reversible steps instead of one big switch. A common shape: expand (build the new, copy data), shadow (run both, compare), switch in slices (one city, store or customer group at a time), then contract (remove the old once proven). Every step has a test, a rollback and a stop point, so there's never a night with no way back.

  • Origin: expand/contract (parallel change); strangler fig; database migration practice
  • Lives in: a migration plan per move, with each step's test and rollback

1The situation Larder, 29 May 2028

Ordering's data must move from Larder Core's shared database to its own (ADR 0027), while 30,000 orders a day keep flowing in six cities. The first draft is one weekend: copy everything on Saturday night, switch on Sunday. If anything's wrong on Monday, there's no way back.

  • Big-bang switches turn small mistakes into outages.
  • Problems often show only under real traffic.
  • Without a rollback, every surprise is a crisis.

2Real-life analogy moving a hospital ward

A hospital moving a ward to a new building doesn't move every patient in one night. It moves one room at a time, keeps the old room ready until the new one is proven, and uses a checklist at each step. There's never a moment when a patient has nowhere to go.

3How it solves it expand, shadow, slice, contract

Ben, Eli and Ana planned five steps. Expand: a new database, change data capture copying every order, checked daily. Shadow: Ordering reads both and compares (0.01 % differences found and fixed). Switch writes city by city, Eindhoven first, with the old database kept in sync backwards. All cities; Ghent and Haarlem are born on the new database. Contract after two quiet weeks. Each step had a test, a rollback and a stop point. Done by 21 August, no orders lost.

  1. Choose the slices

    Cities, stores, customer groups: smallest first.

  2. Expand

    Build the new; copy data continuously.

  3. Shadow

    Run both; compare results; fix differences.

  4. Switch slice by slice

    Keep the old in sync backwards.

  5. Define test, rollback, stop

    For every step, before starting.

  6. Contract when proven

    Remove the old after quiet weeks.

Vocabulary for the exam

Expand/contract
Add the new alongside, then remove the old.
Change data capture
Streaming database changes to another system.
Shadow read
Reading both old and new and comparing.
Slice
A part of traffic or data moved at once.
Rollback
Returning to the previous state.
Stop point
A moment to decide whether to continue.

4Gains vs losses nothing is free

What we gain

  • Always a way back.
  • Problems found in one city, not six.
  • Real traffic tests each step.
  • No big weekend.
  • Calm for operations and support.

What we lose

  • Takes weeks, not a weekend.
  • Two databases to run for a while.
  • Sync code to build and remove.
  • Coordination across teams.

6Common pitfalls the usual ways this goes wrong

  • Big bang

    Everything Saturday night. Fix → slices, smallest first.

  • No rollback

    “We'll fix forward.” Fix → a way back for every step.

  • Skipping shadow

    Differences found by customers. Fix → compare before switching.

  • Never contracting

    Old tables forever. Fix → remove them when proven.

7When to use it (and when not)

Use it when…

  • Moving data between databases or systems.
  • Replacing a system with live traffic.
  • Splitting a monolith's database.
  • Changing providers (payments, hosting).

Skip it when…

  • Systems you can take offline with no harm.
