Baseline Before You Build

TL;DR

Before you change anything, measure today properly: how the number is defined, where it comes from, how reliable that source is, and what it is for each important segment. Fix the measurement first if you have to. Without a trustworthy baseline you can't tell whether a change worked, and every later argument becomes a fight about the data instead of the result.

1The situation Larder, the famous 6 %

Everyone at Larder quotes “6 % of orders end in a refund ticket”. Grace asks where it comes from: support's “substitution” tag. But agents pick tags from a dropdown, in a hurry, and the first option wins. In a quick look, some “substitution” tickets are about late orders, and some swap problems are tagged “missing item”. If the team builds the fix now, it can't tell whether a change in the number comes from the fix or from the tagging.

  • Numbers everyone quotes are often the least checked.
  • A measurement that changes mid-project ruins the comparison.
  • Averages hide differences between segments (express vs slots).

2Real-life analogy the bathroom scale

Starting a diet on an old scale that reads three kilos light, then buying a new one halfway through, you'll never know whether you lost weight or changed scales. Check the scale against a known weight, write the starting number down, and keep the same scale until the end.

3How it solves it define, check, sample, fix the source

Write the definition first, then check the source against reality with a sample you read by hand. If the source is unreliable, fix it before the change, so before and after use the same ruler. Split by the segments the change might affect differently.

  1. Define the number

    What counts, what doesn't, over which period: “a refund ticket within 7 days caused by a substitution”.

  2. Find the source

    Where it comes from today, and how it's produced (a dropdown chosen in a hurry).

  3. Check a random sample by hand

    Read 200–400 cases with a written rule; measure how often the source is wrong.

  4. Split by segment

    Express vs slots, stores, new vs returning: the fix may affect them differently.

  5. Fix the measurement first

    Change the tag rule or tracking before the product change, then wait a few weeks.

  6. Write the baseline card

    Number, definition, method, date, error margin, owner. Everyone quotes the card.

Vocabulary for the exam

Baseline
The measured value before a change, used for comparison.
Operational definition
An exact, repeatable rule for what counts.
Random sample
Cases picked by chance, so they represent the whole.
Measurement error
How far the source differs from reality.
Segment
A group that may behave differently (express vs slots).
Before/after comparison
Comparing the baseline to the number after a change.

tools: a spreadsheet and two people reading tickets for a day. Your helpdesk's export, a random-number column, and a written rule are enough. Later, the product analytics tool keeps the number current.

4Gains vs losses nothing is free

What we gain

  • Results you can prove: before and after use the same ruler.
  • Better targets: express needs more help than slots.
  • Fewer data fights: everyone quotes the same card.
  • A cleaner source for every future measurement.
  • Surprises early: the tag was wrong 38 % of the time.

What we lose

  • Delay: weeks before the product change starts.
  • Tedious work: reading tickets by hand.
  • Error margins remain, even after sampling.
  • Awkward when the “famous number” turns out wrong.

6Common pitfalls the usual ways this goes wrong

  • Trusting the famous number

    Everyone quotes 6 %; nobody knows how it's made. Fix → trace the source and check a sample by hand.

  • Changing the ruler mid-way

    New tags arrive in the same week as the fix. Fix → fix the measurement first, wait, then change the product.

  • Averages only

    One number for all orders. Fix → split by the segments the change will affect.

  • No definition

    Two analysts get two different baselines. Fix → write an exact rule anyone can apply.

7When to use it (and when not)

Use it when…

  • Before any change you'll want to claim credit for.
  • When a number comes from manual tagging or surveys.
  • When segments might react differently.
  • Setting targets for a new outcome.

Skip it when…

  • Tiny reversible tweaks where a quick A/B test is enough.
  • When the source is already audited and stable.
  • Emergencies: fix first, measure the next one properly.

8Self-check quiz

Why fix the measurement before the product change?

So before and after use the same ruler; otherwise you can't tell the fix from the tagging.

How did Grace check the 6 %?

A random sample of 400 tickets re-tagged by hand with a written rule.

What did the baseline show by segment?

Express 7.4 %, slots 3.5 %: express needs the fix most.

What goes on a baseline card?

Definition, period, method, result with error margin, segments, source quality, owner.

try it

Pick the number your team quotes most. Write its exact definition, then check 50 random cases by hand. How often does the source agree with what you read? Write a baseline card and share it.
