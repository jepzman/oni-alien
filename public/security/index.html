Security Patterns

My dossier on security patterns for people who build things: who gets in, where secrets live, how to treat input from strangers, and how to notice and contain the day something goes wrong. 15 patterns in four collections, with the same eight sections as the other volumes, rated on nine security qualities like confidentiality, integrity, containment and usability. Examples use TypeScript, SQL and cloud config, but the ideas work everywhere. Defensive only: nothing here teaches you to break in.

Identity & access who are you, and what may you do?

  1. 01Zero TrustNever trust a request because of where it comes from; verify every one.p. 01
  2. 02Least PrivilegeGive every person, service and key only the access it needs, for as long as it needs it.p. 02
  3. 03OAuth 2.0 with PKCELet users sign in through a trusted provider without your app ever seeing their password.p. 03
  4. 04Short-Lived TokensCredentials that expire in minutes, refreshed safely, so a stolen one is soon useless.p. 04

Secrets & data keep keys, passwords and personal data safe

  1. 05Secrets ManagementKeep keys and passwords in a vault, not in code, and rotate them automatically.p. 05
  2. 06Envelope EncryptionEncrypt data with a data key, and encrypt that key with a master key you never export.p. 06
  3. 07Password HashingStore passwords as slow, salted hashes, so a leaked table doesn't leak passwords.p. 07

Untrusted input treat everything from outside as hostile

  1. 08Validate at the BoundaryCheck every input against an allow-list schema as it enters, and reject the rest.p. 08
  2. 09Parameterized QueriesSend SQL and values separately, so data can never be run as code.p. 09
  3. 10Output Encoding & CSPEscape data for where it's shown, and let the browser block anything you didn't send.p. 10
  4. 11CSRF ProtectionMake sure a state-changing request really came from your own page, not another site.p. 11

Building & running design for attacks, notice them, contain them

  1. 12Threat ModellingAsk “what can go wrong?” on a diagram before you build, and plan the defences.p. 12
  2. 13Audit LoggingRecord who did what, when and from where, in a log attackers can't quietly edit.p. 13
  3. 14Supply-Chain HygienePin, scan and verify the packages and images you depend on.p. 14
  4. 15Defence in DepthStack independent layers so one failure doesn't mean a breach.p. 15

★The nine security ratings confidentiality, integrity, availability and friends

Every note scores the pattern from 1 (poor) to 5 (great) on the same nine things, comparing an app without the pattern to the same app with it.

Simplicity
Few moving parts, so the secure path is also the obvious one.
Usability
Users and admins aren't pushed to work around it. High = smooth.
Confidentiality
Data and credentials are only seen by those allowed to see them.
Integrity
Data and actions can't be changed or forged without detection.
Availability
Keeps serving real users, even when someone is trying to break it.
Containment
One stolen key or broken part only exposes a little. High = small.
Auditability
Who did what, when and from where can be answered afterwards.
Low cost
Tools, infrastructure and people time. High = cheap.
Developer experience
Developers can follow it without being security experts.

first law

Everything in architecture is a trade-off. If you think you've found one that isn't, you haven't found the cost yet.
