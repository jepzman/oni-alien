Envelope Encryption

TL;DR

Encrypt each piece of data with its own data key, then encrypt (“wrap”) that data key with a master key that lives in a KMS or HSM and never leaves it. Store the wrapped key next to the data. Stealing the disk gets ciphertext and wrapped keys only; every unwrap is authorised and logged; and rotating the master key means re-wrapping small keys, not re-encrypting terabytes.

  • Family: encryption at rest
  • Services: AWS KMS, Google Cloud KMS, Azure Key Vault, HSMs
  • Algorithms: AES-256-GCM data keys
  • Pairs with: secrets management, least privilege

1The problem why do we even need this?

“We encrypt everything” often means one key, stored next to the data. Whoever gets the server or the backup gets the key too, and changing the key means re-encrypting everything.

  • The AES key sits in a config file on the same machine.
  • Backups contain both encrypted data and the key.
  • Nobody can tell who decrypted what.

2Real-life analogy room safes and a master vault

A hotel room has a small safe with its own code. The hotel doesn't write codes on the doors; they're kept in a master vault that never leaves the building, and only authorised staff can look one up, with a log entry.

  • Each room safe's code is a data key.
  • The master vault is the KMS.
  • Changing the vault's lock doesn't mean opening every room safe: cheap master-key rotation.

3How it solves it wrap the key that wraps the data

Big data is encrypted locally and fast with the data key; only the tiny data key travels to the KMS. That's how cloud storage encryption works under the hood.

  1. Create a master key in KMS

    Non-exportable, with a key policy naming who may encrypt and decrypt.

  2. Generate a data key per object

    GenerateDataKey returns plaintext + wrapped copies.

  3. Encrypt locally

    AES-256-GCM with a fresh nonce; then wipe the plaintext key from memory.

  4. Store the wrapped key with the data

    In the file header or a column next to the ciphertext.

  5. Decrypt via KMS

    Send the wrapped key to Decrypt; permission checked, call logged.

  6. Rotate and shred

    Rotate master keys yearly; destroying a tenant's key makes their data unreadable (crypto-shredding).

HSM
Tamper-resistant hardware that holds keys.
Wrapping
Encrypting a key with another key.
Crypto-shredding
Deleting data by destroying its key.
vault-files.tsAWS KMS + Node crypto
import { KMSClient, GenerateDataKeyCommand, DecryptCommand } from "@aws-sdk/client-kms";
import { createCipheriv, randomBytes } from "node:crypto";

const kms = new KMSClient({});

export async function encryptFile(plain: Buffer, tenantKeyId: string) {
  const { Plaintext, CiphertextBlob } = await kms.send(
    new GenerateDataKeyCommand({ KeyId: tenantKeyId, KeySpec: "AES_256" }));
  const iv = randomBytes(12);
  const c = createCipheriv("aes-256-gcm", Plaintext!, iv);
  const body = Buffer.concat([c.update(plain), c.final()]);
  Plaintext!.fill(0);                                  // drop the plaintext key
  return { wrappedKey: CiphertextBlob, iv, tag: c.getAuthTag(), body };
}

export async function unwrap(wrappedKey: Uint8Array) {
  return (await kms.send(new DecryptCommand({ CiphertextBlob: wrappedKey }))).Plaintext!;
}

tools: AWS KMS + Encryption SDK, Google Cloud KMS + Tink, Azure Key Vault, HashiCorp Vault Transit, cloud HSMs, database TDE and column encryption that use the same model.

4Gains vs losses nothing is free

What we gain

  • Keys never sit next to data.
  • Every decrypt is authorised and logged.
  • Cheap master-key rotation.
  • Per-tenant keys and crypto-shredding.

What we lose

  • KMS calls add latency and cost.
  • KMS availability becomes critical.
  • Crypto details (nonces, modes) are easy to get wrong by hand.
  • Doesn't protect data in use by a compromised app.

6Common pitfalls the usual ways this goes wrong

  • Rolling your own crypto

    Reused nonces, ECB mode, no auth tag. Fix → use the Encryption SDK or Tink.

  • Keeping plaintext data keys

    Cached forever in memory or logged. Fix → wipe after use; short, bounded caches only.

  • Over-broad key policies

    Every role can call Decrypt on every key. Fix → least privilege on key policies; per-tenant keys.

  • Calling KMS per tiny record

    Thousands of KMS calls per second. Fix → data-key caching with limits, or encrypt batches.

7When to use it (and when not)

Use it when…

  • Files and blobs with sensitive data.
  • Per-tenant encryption and crypto-shredding.
  • Field-level encryption of personal data.

Skip it when…

  • When managed storage encryption already meets your needs.
  • Data that's public anyway.

8Self-check quiz

Why not store the encryption key next to the data?

Whoever steals the data (server, backup) gets the key too.

What does the KMS return from GenerateDataKey?

A plaintext data key to use now, and the same key encrypted under the master key to store.

Why is master-key rotation cheap?

Only the small wrapped data keys need re-wrapping, not the data itself.

What is crypto-shredding?

Making data unreadable by destroying the key that protects it.
