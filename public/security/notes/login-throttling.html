Rate-Limited Login

TL;DR

Login is attacked by guessing (one account, many passwords) and credential stuffing (many accounts, passwords leaked elsewhere, from thousands of IPs). One limit can't stop both. Layer them: per account (growing delays and a challenge after a few failures, never a permanent lock), per IP and network, and site-wide (step up checks when the failure rate spikes). Add breached-password checks, identical error messages, new-sign-in alerts, and passkeys.

1The problem why do we even need this?

Attackers take 2 million email/password pairs leaked from other sites and try them on the shop's login, spread over 5,000 IP addresses at a few attempts each. About 0.5% work, because people reuse passwords: roughly 10,000 accounts taken over, and no single IP ever looked unusual.

  • A per-IP limit alone misses attacks spread over many IPs.
  • A per-account permanent lock lets attackers lock out anyone, including your biggest customers.
  • Different error messages for “no such user” and “wrong password” tell attackers which emails exist.

2Real-life analogy the cash machine

Three wrong PINs and the cash machine keeps the card. But the bank also watches the machine (many cards failing at the same one) and the whole network (an unusual spike of failures everywhere). Each pattern gets its own limit and its own response.

3How it solves it three layers of limits, plus fewer passwords

Count failures in a fast store (Redis) by account, by IP and network, and overall, with sliding windows. Respond in steps: a short delay, then a challenge (CAPTCHA or proof of work), then a temporary block for that source. Give the same message for unknown user and wrong password. Reduce what's worth stealing: block known-breached passwords, and move people to passkeys.

  1. Count by account, source and overall

    Failures per account (15 min), per IP and per /24 or ASN (1 h), and site-wide per minute.

  2. Respond in steps

    Delay, then challenge, then temporary block for the source. Never a permanent account lock without a recovery path.

  3. Hide which accounts exist

    The same response and timing for unknown user and wrong password, also on reset and sign-up pages.

  4. Block breached passwords

    Check new and changed passwords against known breach lists (k-anonymity range queries).

  5. Watch and alert

    Alert on failure-rate spikes; notify users of sign-ins from new devices; log every attempt for the audit trail.

Vocabulary for the exam

Credential stuffing
Trying username/password pairs leaked from other sites.
Brute force
Trying many passwords against one account.
Password spraying
Trying a few common passwords against many accounts.
Lockout
Blocking an account after failures; risky if permanent.
Step-up challenge
An extra check (CAPTCHA, second factor) when risk is high.
Account enumeration
Learning which usernames exist from different responses.
login-limits.tsNode.js + Redis (rate-limiter-flexible)
import { RateLimiterRedis } from "rate-limiter-flexible";

const perAccount = new RateLimiterRedis({ storeClient: redis, keyPrefix: "fail:acct", points: 5, duration: 15 * 60 });
const perIp      = new RateLimiterRedis({ storeClient: redis, keyPrefix: "fail:ip",   points: 50, duration: 60 * 60 });

app.post("/login", async (req, res) => {
  const email = normalise(req.body.email);
  const [acct, ip] = await Promise.all([perAccount.get(email), perIp.get(req.ip)]);
  if ((ip?.consumedPoints ?? 0) >= 50) return res.status(429).json({ error: "Too many attempts. Try again later." });
  if ((acct?.consumedPoints ?? 0) >= 5 && !(await verifyChallenge(req))) {
    return res.status(401).json({ error: "Please complete the check.", challenge: true });
  }

  const user = await users.findByEmail(email);
  const ok = await verifyPassword(user?.passwordHash ?? DUMMY_HASH, req.body.password);  // same timing
  if (!user || !ok) {
    await Promise.all([perAccount.penalty(email), perIp.penalty(req.ip)]);
    audit("login.failed", { email, ip: req.ip });
    return res.status(401).json({ error: "Email or password is incorrect." });  // same message
  }
  await perAccount.delete(email);
  await startSession(res, user, req);   // and alert the user if this device is new
});

tools: rate-limiter-flexible, express-rate-limit with a Redis store, Cloudflare / AWS WAF bot and login protection, Have I Been Pwned Pwned Passwords range API, Cloudflare Turnstile or hCaptcha, identity providers' built-in attack protection.

4Gains vs losses nothing is free

What we gain

  • Stuffing and guessing slowed down by orders of magnitude.
  • No easy lockout attacks on real users.
  • Fewer accounts with leaked passwords.
  • Attacks become visible in metrics and logs.

What we lose

  • Some real users see delays or challenges.
  • Shared IPs (offices, mobile carriers) need higher limits.
  • Tuning: limits that are too strict or too loose.
  • Doesn't fix password reuse: passkeys do.

6Common pitfalls the usual ways this goes wrong

  • Only per-IP limits

    Stuffing spread over thousands of IPs passes untouched. Fix → add per-account and site-wide limits.

  • Permanent lockout

    Attackers lock out real users on purpose by failing their logins. Fix → delays and challenges instead; temporary blocks for sources, not accounts.

  • Telling attackers who exists

    “No account with that email” on login, reset or sign-up. Fix → the same message and timing for every case.

  • Forgetting other doors

    Login is limited, but the mobile API, password reset and the old v1 endpoint are not. Fix → apply the same limits to every way of checking a password or sending a reset.

7When to use it (and when not)

Use it when…

  • Every password login, reset and second-factor check.
  • APIs that accept username and password (move them to tokens if you can).
  • Sign-up and reset forms that reveal whether an account exists.

Skip it when…

  • Passkey-only sign-in has less to guess (still limit, more loosely).
  • Machine credentials: use short-lived tokens, not passwords.
  • Never: there's no login that shouldn't have limits.

8Self-check quiz

Why isn't a per-IP limit enough?

Credential stuffing spreads attempts across thousands of IPs, so no single IP reaches the limit.

Why avoid permanent account lockouts?

Attackers can lock out real users on purpose just by failing their logins.

What is account enumeration?

Learning which emails have accounts because responses or timing differ for unknown users.

What reduces the value of leaked passwords most?

Blocking known-breached passwords and moving users to passkeys.

what would you do?Overnight, failed logins jump from 2,000 to 900,000 an hour, spread over 40,000 IPs, at about 20 attempts per IP. Successful logins from new devices also rise. What do you do first?

Treat it as credential stuffing: switch on site-wide step-up (a challenge for all logins, or for logins from new devices), tighten per-account and per-network limits, and alert or force resets for accounts that signed in from new devices during the attack. Then review the logs and offer passkeys.

try it

On your own login in a local or staging environment, send 20 wrong passwords for one account and then 20 for 20 different accounts from one IP (a small script). Check what each layer did. Then compare the responses and timing for a real and a non-existent email, and make them identical.

remember!!

Limit by account, by source and overall. Slow the guessers, never lock out the users.
