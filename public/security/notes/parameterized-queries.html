Parameterized Queries

TL;DR

Never build SQL (or shell commands, or LDAP/NoSQL queries) by gluing strings. Send the query text with placeholders and the values separately; the database parses the query first and binds values as pure data, so input can never change the command. Use your driver's parameters or a query builder/ORM, and allow-list anything that can't be a parameter (column names, sort order).

  • Family: injection prevention
  • Prevents: SQL injection (OWASP A03)
  • Also for: shell, NoSQL, LDAP, XPath queries
  • Pairs with: input validation, least privilege

1The problem why do we even need this?

When a query is built by concatenating input, data and code share one string. A single quote in the input can end the value and turn the rest into SQL. Injection has been in the OWASP Top 10 for over twenty years.

  • Login forms, search boxes and filters are the classic entry points.
  • Escaping by hand misses edge cases (encodings, numeric contexts).
  • The impact is whatever the database user can do.

2Real-life analogy the printed form

A bank transfer form has printed wording and labelled boxes. Whatever you write in the amount box is read as an amount, even if you write instructions there. The wording of the form can't be changed by what you put in the boxes.

  • The printed wording is the SQL text.
  • The boxes are placeholders ($1, ?).
  • What you write is always just a value.

3How it solves it code and data never meet

Parameters work because the database knows the structure before it sees the values. Escaping tries to make data look harmless; parameters make it impossible for data to be code.

  1. Use placeholders everywhere

    db.query("… WHERE email = $1", [email]), including LIMIT and numeric values.

  2. Prefer a query builder or ORM

    They parameterize by default (Prisma, Drizzle, Kysely, SQLAlchemy).

  3. Watch the raw escape hatches

    $queryRawUnsafe, string-built sql fragments, .raw().

  4. Allow-list identifiers

    Column names and sort directions can't be parameters: map user choices to known values.

  5. Same rule for shells

    Use argument arrays (execFile), never shell strings with input.

  6. Limit the damage

    Run the app with a least-privilege database role.

Vocabulary for the exam

Injection
Input interpreted as part of a command.
Placeholder
A marker in the query for a value.
Bind parameter
A value sent separately from the query text.
Prepared statement
A query parsed once and run with different values.
Identifier
A table or column name (can't be bound).
Second-order injection
Stored input later used unsafely in a query.

4Gains vs losses nothing is free

What we gain

  • Injection becomes impossible for bound values.
  • Simpler code than manual escaping.
  • Prepared statements can be faster.
  • Easy to enforce with linters.

What we lose

  • Identifiers need allow-lists.
  • Dynamic queries take a little more care.
  • Raw escape hatches remain a risk.

6Common pitfalls the usual ways this goes wrong

  • Raw-query escape hatches

    queryRawUnsafe(`… ${input}`) in one admin report. Fix → ban unsafe APIs with a linter; review raw SQL.

  • User-chosen column names

    ORDER BY ${req.query.sort}. Fix → map choices to a fixed allow-list.

  • Second-order injection

    A stored value is later glued into a query. Fix → parameterize everywhere, not just at input time.

  • Shell commands with input

    exec(`convert ${file}`). Fix → argument arrays (execFile) and validated paths.

7When to use it (and when not)

Use it when…

  • Every database query that includes any variable.
  • Shell commands, NoSQL filters, LDAP and XPath queries.
  • Stored procedures that build dynamic SQL.

Skip it when…

  • Never; there's no good reason to concatenate input into a query.

8Self-check quiz

Why do parameters prevent SQL injection?

The database parses the query before seeing values, and binds them as data only.

Can table or column names be parameters?

No. Map user choices to an allow-list of known identifiers.

What's second-order injection?

Input stored safely, later read and concatenated into another query.

How do you run an external program safely with user input?

Pass arguments as an array (e.g. execFile), never through a shell string.
