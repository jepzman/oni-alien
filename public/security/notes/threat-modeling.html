Threat Modelling

TL;DR

Before (and while) you build, sit down with a diagram of how data flows, mark the trust boundaries, and ask “what can go wrong?” for each part, using a checklist like STRIDE. Write down threats, mitigations and owners, turn them into tickets and tests, and revisit when the design changes. Design flaws are cheapest to fix on the whiteboard.

  • Family: secure design
  • Frameworks: STRIDE, LINDDUN (privacy), attack trees
  • Four questions: Adam Shostack
  • Pairs with: defence in depth, least privilege

1The problem why do we even need this?

Security is often checked at the end: a pen test just before launch. By then, the worst problems are design flaws, not bugs, and fixing them means rework and delays.

  • “Anyone can read anyone's files” is a storage design problem.
  • Nobody thought about what happens if the webhook sender is spoofed.
  • Security reviews become a gate people try to dodge.

2Real-life analogy planning for a holiday

Before a family goes away, they look at the house plan and ask “what could go wrong?”: a burst pipe, a burglar through the back window, the cat. For each, they decide a fix: water off, lock the window, ask the neighbour. One afternoon, far cheaper than coming home to a flood.

  • The house plan is a data-flow diagram.
  • Doors and windows are trust boundaries.
  • The list of fixes is your mitigations.

3How it solves it four questions, on a diagram

Shostack's four questions: What are we working on? What can go wrong? What are we going to do about it? Did we do a good job? An hour with the team beats a perfect document nobody reads.

  1. Draw it

    Users, services, data stores, external systems and the flows between them.

  2. Mark trust boundaries

    Where data crosses from less trusted to more trusted.

  3. Walk STRIDE per element

    Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.

  4. Decide and record

    Mitigate, accept, transfer or avoid; owner and ticket per threat.

  5. Verify

    Turn mitigations into tests and review checks.

  6. Keep it alive

    Update with each significant design change; keep it in the repo next to the code.

Vocabulary for the exam

Threat
Something that could go wrong, caused by someone or something.
Data-flow diagram
Picture of processes, stores and flows.
Trust boundary
Where the level of trust changes.
STRIDE
Mnemonic for six threat categories.
Mitigation
A control that reduces a threat.
Residual risk
Risk left after mitigations, accepted on purpose.

## File uploads — threat model (v3, 2026-11)

Flow: browser → API → object storage (private bucket) → thumbnail worker

| # | STRIDE | Threat                                   | Mitigation                                   | Owner | Status |
|---|--------|------------------------------------------|----------------------------------------------|-------|--------|
| 1 | I      | User reads another user's files          | Per-user prefix + signed URLs, 5 min expiry  | ana   | done   |
| 2 | T      | Malicious file exploits the thumbnailer  | Sandbox worker, allow-list types, size limit | ben   | doing  |
| 3 | D      | 10 GB uploads exhaust storage            | 25 MB limit, per-user quota, rate limit       | cho   | done   |
| 4 | R      | “I never deleted that file”              | Audit log of upload/delete with user id      | ana   | todo   |

Accepted risk: EXIF metadata kept on originals (owner-only access).

4Gains vs losses nothing is free

What we gain

  • Design flaws found early, when cheap.
  • Shared understanding of risks across the team.
  • Focused effort: fix what matters most.
  • Documented decisions for audits and newcomers.

What we lose

  • Meeting time.
  • Can become paperwork if over-formalised.
  • Goes stale without updates.
  • Depends on who's in the room.

6Common pitfalls the usual ways this goes wrong

  • A 60-page document

    Nobody reads or updates it. Fix → a diagram and a table in the repo.

  • Only security people attend

    Developers don't own the outcome. Fix → the building team runs it; security coaches.

  • Once per project

    The design changes; the model doesn't. Fix → revisit with each significant change.

  • Threats without owners

    A long list that never turns into work. Fix → owner + ticket per mitigation.

7When to use it (and when not)

Use it when…

  • New features handling sensitive data, money or uploads.
  • New services, integrations and trust boundaries.
  • Before big architecture changes.

Skip it when…

  • Tiny UI tweaks with no new data flows.
  • Don't model everything at once; start with the riskiest flow.

8Self-check quiz

What does STRIDE stand for?

Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.

What is a trust boundary?

A place in the system where data or control passes between parts with different trust levels.

Name Shostack's four questions.

What are we working on? What can go wrong? What are we going to do about it? Did we do a good job?

When should you update a threat model?

Whenever the design changes significantly, such as a new data flow, store or integration.
