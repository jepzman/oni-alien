CSRF Protection

TL;DR

Browsers attach cookies to requests even when another site triggers them. If your app trusts the cookie alone, a hidden form elsewhere can act as the user. Defend in layers: SameSite session cookies, a CSRF token (or a custom header) on every state-changing request, an Origin check on the server, and never change state on GET.

  • Family: request forgery
  • Defences: SameSite cookies, synchronizer / double-submit tokens, Origin checks
  • Not needed for: APIs using Authorization headers only
  • Pairs with: output encoding & CSP

1The problem why do we even need this?

Cookie-based sessions have a catch: the browser sends your cookie to your site no matter which site started the request. A malicious page can make the user's browser submit a form to your app, fully authenticated.

  • A hidden form transfers money or changes the account email.
  • An image tag hits GET /delete?id=5.
  • The server sees a valid session and does it.

2Real-life analogy the restaurant's own order pad

In a busy restaurant, waiters only accept orders written on the restaurant's own order pads, each with a unique stamp. A note slipped under the door saying “table 5 wants champagne” is ignored, even though table 5 is real.

  • The stamped pad is a CSRF token only your pages have.
  • The note under the door is a cross-site request.
  • Checking it came from inside is the Origin check.

3How it solves it prove the request came from you

Modern browsers default cookies to SameSite=Lax, which blocks the classic attack, but set it explicitly and keep a token or header check as a second layer.

  1. Set SameSite explicitly

    Set-Cookie: session=…; HttpOnly; Secure; SameSite=Lax (Strict where usable).

  2. Require a token on unsafe methods

    POST, PUT, PATCH, DELETE carry a per-session token in a hidden field or header.

  3. Or require a custom header

    APIs called with fetch can require X-Requested-With/JSON content type, which cross-site forms can't send without CORS.

  4. Check Origin

    Reject unsafe requests whose Origin isn't yours.

  5. Keep GET safe

    GET and HEAD never change state.

  6. Use the framework's built-in protection

    Rails, Django, Laravel, Spring and Next.js server actions include it.

Vocabulary for the exam

CSRF
Cross-site request forgery: another site acts with the user's session.
SameSite
Cookie attribute controlling cross-site sending (Strict, Lax, None).
Synchronizer token
Random token stored server-side and embedded in forms.
Double-submit cookie
Token in a cookie and a header that must match.
Origin header
Browser-set header naming the requesting site.
Safe method
GET/HEAD/OPTIONS: must not change state.
csrf.tsExpress
// session cookie: never sent on cross-site POSTs
res.cookie("session", sid, { httpOnly: true, secure: true, sameSite: "lax" });

// second layer for every state-changing request
const UNSAFE = new Set(["POST", "PUT", "PATCH", "DELETE"]);
app.use((req, res, next) => {
  if (!UNSAFE.has(req.method)) return next();

  const origin = req.get("origin");
  if (origin && origin !== "https://bank.example") return res.sendStatus(403);

  const token = req.get("x-csrf-token") ?? req.body?._csrf;
  if (!token || !timingSafeEqual(token, req.session.csrfToken)) return res.sendStatus(403);
  next();
});

// pages embed the token:  <input type="hidden" name="_csrf" value="{{csrfToken}}">

tools: built-in CSRF protection in Rails, Django, Laravel, Spring Security, ASP.NET; csrf-csrf / lusca for Express; Next.js server actions (Origin checks); browser SameSite defaults.

4Gains vs losses nothing is free

What we gain

  • Forged requests rejected.
  • Cookie sessions stay usable safely.
  • Built into most frameworks.
  • Cheap: a few checks per request.

What we lose

  • Tokens to plumb into forms and fetch calls.
  • SameSite=Strict can break inbound links' logged-in state.
  • Cross-site embeds and SSO need careful exceptions.

6Common pitfalls the usual ways this goes wrong

  • State changes on GET

    GET /logout or /delete?id=5. Fix → use POST/DELETE for changes.

  • Disabling protection for “the API”

    The same cookie session is used by the API. Fix → if it uses cookies, it needs CSRF protection.

  • SameSite=None everywhere

    Set for one embed, applied to the session. Fix → only on cookies that truly need cross-site use.

  • Tokens in URLs

    Leak via logs and referrers. Fix → put tokens in bodies or headers.

7When to use it (and when not)

Use it when…

  • Any app using cookie-based sessions.
  • Forms and fetch calls that change state.
  • Admin panels and account settings especially.

Skip it when…

  • APIs authenticated only by Authorization headers (bearer tokens), which browsers don't attach automatically.

8Self-check quiz

Why does CSRF work at all?

Browsers automatically attach cookies to requests to your site, even when another site triggers them.

What does SameSite=Lax do?

Stops the cookie being sent on cross-site POSTs and other unsafe cross-site requests.

Why must GET never change state?

GET requests are easy to trigger cross-site (links, images) and aren't covered by token checks.

Do bearer-token APIs need CSRF tokens?

Usually not, because browsers don't attach Authorization headers automatically.
