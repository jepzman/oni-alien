Validate at the Boundary

TL;DR

Treat every input from outside (bodies, query strings, headers, files, webhooks) as hostile. Check it once, at the boundary, against an allow-list schema: types, ranges, lengths, formats, and drop unknown fields. Reject anything else with a clear error. Inside, code works with typed, trusted data. Validation is your first filter, not your only defence.

  • Family: input handling
  • Approach: allow-list (positive) validation
  • Tools: Zod, Valibot, JSON Schema, Pydantic
  • Pairs with: parameterized queries, output encoding

1The problem why do we even need this?

Without a clear checkpoint, every layer assumes another one checked. Bad input slips through and breaks logic, data and sometimes security.

  • A negative quantity gives the customer a refund.
  • An extra role: "admin" field is copied straight into the user (mass assignment).
  • A 4 MB “name” fills logs and slows the service.

2Real-life analogy airport security

An airport has one checkpoint with a strict list of what's allowed. Every bag is checked at the entrance; anything not on the list is refused. Inside, gates and shops can rely on the fact that bags were checked.

  • The checkpoint is your API boundary.
  • The list of allowed items is an allow-list schema.
  • “Not on the list = refused” beats “on the banned list = refused”.

3How it solves it one schema, at the edge

Validate syntax and shape at the edge (is it a number 1–99?), and business rules in the domain (is this product in stock?). Both are needed; neither replaces safe output and queries.

  1. Define a schema per endpoint

    Types, min/max, lengths, enums, formats, for body, query, params and headers.

  2. Allow-list, don't block-list

    Describe what's valid; don't try to list every bad pattern.

  3. Strip unknown fields

    Prevents mass assignment (role, isAdmin).

  4. Limit sizes

    Request body limits, array lengths, string lengths, file types and sizes.

  5. Fail clearly

    400 with field errors; don't echo raw input back unescaped.

  6. Validate webhooks and files too

    Check signatures, content types (by content, not extension) and sizes.

Vocabulary for the exam

Allow-list
Only listed values/shapes are accepted.
Block-list
Listed bad values are rejected; easy to bypass.
Mass assignment
Copying request fields straight onto objects.
Schema
A machine-checkable description of valid input.
Canonicalisation
Normalising input (unicode, paths) before checks.
Trust boundary
Where data crosses from untrusted to trusted.
orders.route.tsZod + Express
import { z } from "zod";

const CreateOrder = z.object({
  productId: z.string().uuid(),
  qty: z.number().int().min(1).max(99),
  note: z.string().trim().max(500).optional(),
  deliverOn: z.coerce.date().min(new Date("2020-01-01")).max(new Date("2030-12-31")),
}).strip();                                   // unknown fields (role, price…) are dropped

app.post("/orders", express.json({ limit: "10kb" }), async (req, res) => {
  const parsed = CreateOrder.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ errors: parsed.error.flatten().fieldErrors });
  }
  const order = await orders.create(req.user.id, parsed.data);   // typed and trusted
  res.status(201).json(order);
});

tools: Zod, Valibot, Yup, Ajv / JSON Schema, OpenAPI request validators, Pydantic (Python), Bean Validation (Java), FluentValidation (.NET), file-type sniffing libraries.

4Gains vs losses nothing is free

What we gain

  • Bad data stopped at the door.
  • No mass assignment.
  • Typed data inside: simpler code.
  • Clear errors for honest clients.

What we lose

  • Schemas to write and keep in sync.
  • False rejections when rules are too strict (names, addresses).
  • Not a full defence: still need safe queries and output.

6Common pitfalls the usual ways this goes wrong

  • Block-lists

    Filtering out “<script>” and calling it safe. Fix → allow-list valid shapes; encode output separately.

  • Client-side validation only

    The browser checks; the API trusts. Fix → always validate on the server.

  • Passing req.body through

    User.update(req.body). Fix → pick known fields via the schema.

  • Over-strict names and addresses

    Rejecting “O'Brien” or non-Latin names. Fix → validate length and type; don't guess what a name looks like.

7When to use it (and when not)

Use it when…

  • Every API endpoint, form handler, webhook and message consumer.
  • File uploads (type, size, content).
  • Config and environment variables at start-up.

Skip it when…

  • Never skip it; just keep business-rule checks in the domain layer.

8Self-check quiz

Why prefer allow-lists over block-lists?

It's impossible to list every bad input; describing valid input rejects everything else by default.

What is mass assignment?

Copying request fields directly onto objects, letting attackers set fields like role or isAdmin.

Is client-side validation enough?

No. It's for user experience; the server must validate everything.

Does validation make SQL injection impossible?

No. Use parameterized queries as well; validation is one layer.

remember!!

One checkpoint, a strict list, and everything else refused.
