Zero Trust

TL;DR

Stop trusting requests because they come from inside the network. In zero trust, every request, from a user or a service, proves who it is (strong identity), comes from a healthy device, is checked against policy for that one resource, and travels encrypted. A phished laptop or a compromised service then gets very little, not the keys to the kingdom.

  • Family: access architecture
  • Origin: John Kindervag (Forrester, 2010); Google BeyondCorp
  • Standard: NIST SP 800-207
  • Pairs with: least privilege, short-lived tokens

1The problem why do we even need this?

The classic model is a castle and moat: a firewall around the office network, and anything inside is trusted. Today people work from anywhere, apps live in several clouds, and attackers only need one foothold.

  • One phished laptop on the VPN can reach the database and admin tools.
  • A compromised internal service can call every other service.
  • “It's only reachable internally” is used as a reason to skip authentication.

2Real-life analogy the badge at every door

In a modern office you badge in at the front door, then again at your floor, and again at the server room, which your badge doesn't open, because it's not your job. Being inside the building doesn't open every door.

  • The badge is a strong identity.
  • Each reader is a policy check for one resource.
  • A lost badge only opens a few doors, and can be cancelled: small blast radius.

3How it solves it verify explicitly, every time

Zero trust isn't a product. It's three habits: verify explicitly, use least privilege, and assume breach, so design as if an attacker is already inside.

  1. Inventory

    List users, devices, services and the resources each needs.

  2. Strong identity for people

    Single sign-on with phishing-resistant MFA (passkeys, security keys).

  3. Identity for services too

    Workload identities and mutual TLS instead of “internal network = trusted”.

  4. Put a policy check in front of each app

    An identity-aware proxy or gateway decides per request: who, device, action, context.

  5. Encrypt everything

    TLS everywhere, including inside the network.

  6. Log and adapt

    Feed decisions into monitoring; step up checks when behaviour looks odd.

Vocabulary for the exam

Perimeter security
Trust based on being inside the network.
Identity-aware proxy
A gateway that checks identity and policy per request.
mTLS
Mutual TLS: both client and server prove their identity.
Device posture
Whether a device is managed, patched and encrypted.
Assume breach
Design as if an attacker is already inside.
Lateral movement
An attacker hopping from one system to the next.
policy.regoOpen Policy Agent
package app.authz

default allow := false

# every request: who, what, which resource, from which device
allow if {
  input.identity.verified_mfa
  input.device.managed
  input.device.disk_encrypted
  some role in input.identity.roles
  permitted[role][input.action][input.resource.type]
}

permitted := {
  "support": {"read":  {"ticket": true, "customer": true}},
  "billing": {"read":  {"invoice": true}, "refund": {"invoice": true}},
}
# no rule says "allow if source IP is internal"

tools: identity-aware proxies (Google IAP, Cloudflare Access, Pomerium, Tailscale), SSO with WebAuthn/passkeys (Okta, Entra ID), service meshes for mTLS (Istio, Linkerd), SPIFFE/SPIRE workload identity, Open Policy Agent.

4Gains vs losses nothing is free

What we gain

  • Small blast radius: one stolen login reaches little.
  • Works anywhere: office, home, cloud, no VPN needed.
  • Every access is logged with identity and context.
  • Stops lateral movement between services.

What we lose

  • A big programme, not a switch.
  • More moving parts: identity provider, proxies, policies.
  • Friction if checks are clumsy.
  • Identity provider becomes critical: if it's down, nobody gets in.

6Common pitfalls the usual ways this goes wrong

  • Buying a product called zero trust

    A new VPN box, same flat network behind it. Fix → change the model: identity and policy on every request.

  • Forgetting service-to-service traffic

    Users are checked; internal APIs still trust each other. Fix → give workloads identities and use mTLS.

  • Weak MFA

    SMS codes get phished or SIM-swapped. Fix → use phishing-resistant MFA (passkeys, security keys).

  • All-or-nothing migration

    A two-year big bang that never ships. Fix → start with the most sensitive apps, one at a time.

7When to use it (and when not)

Use it when…

  • Remote or hybrid teams.
  • Apps spread across clouds and SaaS.
  • Sensitive data or admin tools.
  • Microservices that call each other.

Skip it when…

  • Never skip the idea; scale the tooling to your size.
  • A tiny team can start with SSO + MFA + no flat internal trust.

8Self-check quiz

What does zero trust stop trusting?

Network location: being inside the network no longer grants access.

Name the three core principles.

Verify explicitly, use least privilege, assume breach.

How do services prove identity to each other?

Workload identities, typically with mutual TLS (often via a service mesh).

Why does zero trust shrink the blast radius?

Each request is checked for one resource, so a stolen credential or compromised device reaches only what it's allowed.
