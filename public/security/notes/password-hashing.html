Password Hashing

TL;DR

Never store passwords, and never “encrypt” them. Store a slow, salted, memory-hard hash: Argon2id (or scrypt / bcrypt) with a unique random salt per user and a cost tuned so one hash takes tens of milliseconds. A stolen table then costs attackers years, not seconds. Better still, offer passkeys so there's no password to steal.

  • Family: credential storage
  • Use: Argon2id · scrypt · bcrypt
  • Never: plain text, MD5, SHA-1/256 alone, reversible encryption
  • Pairs with: MFA / passkeys, rate limiting

1The problem why do we even need this?

Databases leak. If passwords are stored in plain text or fast hashes, the leak becomes a list of real passwords, and people reuse them for email and banking.

  • Plain text: readable immediately.
  • MD5/SHA-256: billions of guesses per second on one GPU.
  • No salt: identical passwords share a hash; lookup tables crack them instantly.

2Real-life analogy the slow grinder

Put a steak through a grinder and you get mince. You can check whether another steak makes the same mince, but you can never turn mince back into steak. Add a unique pinch of spice per steak so identical steaks give different mince, and use a deliberately slow grinder so trying a million steaks takes forever.

  • Grinding is hashing (one-way).
  • The spice is the salt.
  • The slow grinder is the work factor.

3How it solves it salted, slow, upgradable

Modern hash strings carry their own algorithm, parameters and salt, so you can raise the cost later and upgrade hashes as users log in.

  1. Pick Argon2id

    OWASP baseline: m=19 MiB, t=2, p=1 or stronger; bcrypt cost ≥ 10 if Argon2 isn't available.

  2. Use a library

    It generates the salt and encodes parameters in the hash string.

  3. Verify in constant time

    Use the library's verify function; don't compare strings yourself.

  4. Rehash when needed

    If the stored parameters are outdated, re-hash after a successful login.

  5. Protect the endpoint

    Rate limits, breached-password checks (k-anonymity APIs), MFA.

  6. Offer passkeys

    WebAuthn passkeys remove shared secrets entirely.

Vocabulary for the exam

Hash
One-way function from input to fixed-size output.
Salt
Random value stored with each hash so equal passwords differ.
Work factor
How expensive one hash is (time, memory).
Memory-hard
Needs lots of RAM, which slows GPU cracking.
Pepper
An extra secret kept outside the database (optional).
Credential stuffing
Trying leaked passwords on other sites.
passwords.ts@node-rs/argon2
import { hash, verify } from "@node-rs/argon2";

const PARAMS = { memoryCost: 65536, timeCost: 3, parallelism: 1 };   // ~50 ms on our servers

export async function setPassword(userId: string, password: string) {
  if (await isBreached(password)) throw new WeakPassword("found in a known breach");
  const h = await hash(password, PARAMS);         // salt generated and embedded
  await db.query("UPDATE users SET password_hash = $1 WHERE id = $2", [h, userId]);
}

export async function checkPassword(user: User, password: string) {
  const ok = await verify(user.password_hash, password);   // constant-time
  if (ok && needsRehash(user.password_hash, PARAMS)) {
    await setPassword(user.id, password);         // upgrade old hashes on login
  }
  return ok;
}

tools: Argon2 libraries (@node-rs/argon2, argon2-cffi, libsodium), bcrypt, Django/Rails/Spring/ASP.NET Identity defaults, Have I Been Pwned “Pwned Passwords” range API, WebAuthn/passkey libraries (SimpleWebAuthn).

4Gains vs losses nothing is free

What we gain

  • Leaks don't reveal passwords quickly.
  • Each guess is expensive for attackers.
  • Upgradable as hardware gets faster.
  • Simple with a good library.

What we lose

  • CPU and memory per login.
  • Login DoS risk if unthrottled.
  • Weak passwords still fall eventually.
  • Doesn't stop phishing (passkeys do).

6Common pitfalls the usual ways this goes wrong

  • Encrypting passwords

    Reversible: whoever has the key has every password. Fix → hash, never encrypt.

  • Fast hashes

    SHA-256 is designed to be fast; GPUs love it. Fix → Argon2id, scrypt or bcrypt.

  • One global salt

    Equal passwords still share hashes. Fix → a unique random salt per hash (libraries do it).

  • Never raising the cost

    2012 parameters on 2026 hardware. Fix → store params in the hash; rehash on login.

7When to use it (and when not)

Use it when…

  • Any system that stores user passwords.
  • API keys you only need to verify, not read (hash them too).

Skip it when…

  • When you can avoid passwords entirely (passkeys, SSO).
  • Secrets you must read back (use a secrets manager instead).

8Self-check quiz

Why is SHA-256 a bad password hash?

It's fast, so attackers can try billions of guesses per second.

What does a salt prevent?

Identical passwords producing identical hashes, and precomputed lookup tables.

How do you upgrade old hashes?

Store parameters in the hash and re-hash with new parameters after a successful login.

Why should passwords never be encrypted?

Encryption is reversible; anyone with the key can recover every password.
