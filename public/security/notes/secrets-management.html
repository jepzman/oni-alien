Secrets Management

TL;DR

Keep API keys, passwords and certificates out of code, images and chat. Store them in a secrets manager, let each app fetch them at runtime with its own identity, log every read, and rotate them automatically (or use dynamic credentials that expire). Add secret scanning so a key that slips into a commit is blocked or revoked within minutes.

  • Family: secrets
  • Tools: Vault, AWS/GCP/Azure secret managers, Doppler, 1Password
  • Guards: gitleaks, GitHub push protection
  • Pairs with: least privilege, short-lived tokens

1The problem why do we even need this?

Secrets spread. A password starts in a config file, then lands in git history, chat, .env files and CI variables. It never changes because nobody knows what would break, and leaked keys are found by bots within minutes.

  • Deleting the line doesn't delete it from git history.
  • Everyone who ever cloned the repo has the production password.
  • Rotating means a scary, manual, all-hands change.

2Real-life analogy the bank vault

You don't leave your valuables under the doormat. A bank keeps them in a vault: you prove who you are to open your box, every visit is logged, and the bank can change the locks on a schedule without you rebuilding your house.

  • The vault is the secrets manager.
  • Proving who you are is the app's workload identity.
  • Changing locks is rotation.

3How it solves it fetch at runtime, log, rotate

The best secret is one nobody ever sees: dynamic credentials created per app, per hour, and destroyed automatically.

  1. Find what you have

    Scan repos and history (gitleaks, trufflehog); list every secret and who uses it.

  2. Move them into a manager

    One path per app and environment (prod/billing/db).

  3. Fetch at runtime

    The app authenticates with its identity (IAM role, Kubernetes service account) and reads only its own secrets.

  4. Rotate automatically

    Scheduled rotation, or dynamic credentials with short leases.

  5. Block new leaks

    Pre-commit hooks and push protection; revoke immediately if one slips through.

  6. Revoke on leak

    Treat a committed secret as public: rotate first, then clean history.

Vocabulary for the exam

Secret
Anything that grants access: keys, passwords, tokens, certificates.
Secrets manager
A service that stores, controls and audits secrets.
Rotation
Replacing a secret with a new one on a schedule.
Dynamic secret
A credential created on demand with a short lease.
Secret sprawl
Copies of a secret spreading across systems.
Push protection
Blocking a push that contains a known secret format.
db.tsAWS Secrets Manager
import { SecretsManagerClient, GetSecretValueCommand } from "@aws-sdk/client-secrets-manager";

// the pod's IAM role allows reading ONLY prod/billing/db
const sm = new SecretsManagerClient({});

async function dbConfig() {
  const { SecretString } = await sm.send(
    new GetSecretValueCommand({ SecretId: "prod/billing/db" }));
  const { username, password, host } = JSON.parse(SecretString!);
  return { user: username, password, host, ssl: true };
}
// rotation is configured on the secret (every 30 days);
// the pool re-reads it on auth failure, so rotation needs no deploy

4Gains vs losses nothing is free

What we gain

  • No secrets in code, images or chat.
  • Every access logged.
  • Rotation without drama.
  • Leaks caught early by scanners.

What we lose

  • A critical dependency: if the manager is down, apps can't start.
  • Setup and migration effort.
  • Bootstrapping: the app still needs an identity to log in.
  • Cost per secret and per API call.

6Common pitfalls the usual ways this goes wrong

  • Deleting instead of rotating

    The committed key is removed from the file, but still valid and in history. Fix → rotate immediately; then clean history.

  • One master secret for everything

    Every app reads every secret. Fix → per-app paths and policies.

  • Secrets in Docker images

    Baked in at build time; anyone with the image has them. Fix → inject at runtime.

  • Logging secrets

    A debug log prints the config object. Fix → redact secrets in logs and error reports.

7When to use it (and when not)

Use it when…

  • Every production credential: databases, APIs, signing keys.
  • CI/CD credentials (better: short-lived OIDC).
  • Certificates and encryption keys.

Skip it when…

  • Truly public values (publishable keys, feature flags) don't need a vault.
  • Local dev can use dummy values.

Related patterns

  • Least privilege
  • Short-lived tokens
  • Envelope encryption
  • Audit logging

8Self-check quiz

A secret was committed to git. What's the first step?

Rotate (revoke) it immediately; removing it from the file doesn't make it safe.

How does an app get secrets without a stored password?

It authenticates to the manager with its workload identity (IAM role, service account).

What's a dynamic secret?

A credential created on demand for one app, with a short lease, then destroyed automatically.

Why not bake secrets into Docker images?

Anyone who can pull the image can read them, and rotation requires a rebuild.

remember!!

No keys under the doormat. Sign in at the vault, and change the locks often.
