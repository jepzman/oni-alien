Short-Lived Tokens

TL;DR

Credentials that never expire become a time bomb. Issue access tokens that live minutes, pair them with refresh tokens that rotate on every use (reuse = revoke the session), and give workloads automatically issued credentials instead of static keys. A stolen token is soon useless, and revocation becomes routine.

  • Family: credentials
  • Typical lifetimes: access 5–15 min · refresh hours–days
  • Workloads: cloud workload identity, OIDC federation
  • Pairs with: OAuth + PKCE, secrets management

1The problem why do we even need this?

Long-lived API keys and passwords get copied into laptops, CI, chats and wikis. When one leaks, it works until someone notices, and rotating it might break systems nobody remembers.

  • A key from 2021 still works, and nobody knows every place it's used.
  • Sessions stay valid for months after a laptop is stolen.
  • CI holds cloud admin keys that never expire.

2Real-life analogy today's cinema ticket

A cinema ticket is valid for one showing, today. Drop it on the street and it's useless by tonight. Your membership card gets you a fresh ticket each visit, and if you lose the card, you cancel it once.

  • The ticket is an access token.
  • The membership card is a refresh token, kept safe.
  • A ticket showing up twice is a sign of theft.

3How it solves it expire fast, rotate on use

Short lifetimes turn revocation from a crisis into a default: even if you can't find every copy, the copies stop working on their own.

  1. Short access tokens

    5–15 minutes; validate expiry on every request.

  2. Rotating refresh tokens

    Each refresh returns a new refresh token and invalidates the old one.

  3. Detect reuse

    If an already-used refresh token appears, revoke the whole token family.

  4. Store them safely

    Browser: httpOnly, Secure, SameSite cookies, not localStorage. Mobile: OS keychain.

  5. No static keys for workloads

    CI and services get credentials via OIDC federation or cloud workload identity, valid for an hour.

  6. Make revocation easy

    Sign-out, password change and admin action revoke refresh tokens immediately.

Vocabulary for the exam

Access token
Short-lived credential sent with each API call.
Refresh token
Longer-lived credential used only to get new access tokens.
Rotation
Replacing a credential on every use or on a schedule.
Reuse detection
Spotting an old refresh token being used again.
Workload identity
Credentials issued automatically to a running service.
OIDC federation
Trading a signed identity token (from CI) for cloud credentials.

4Gains vs losses nothing is free

What we gain

  • Leaks expire on their own.
  • Theft is detectable via refresh reuse.
  • No static keys in CI or config.
  • Revocation is routine, not an emergency.

What we lose

  • More token plumbing: refresh logic, storage.
  • Clock and expiry edge cases.
  • Dependence on the token issuer being available.
  • Revoking access tokens mid-life still needs extra work.

6Common pitfalls the usual ways this goes wrong

  • Long access tokens

    “Short-lived” tokens valid for 30 days. Fix → minutes for access, rotate refresh.

  • Tokens in localStorage

    Any XSS can read and exfiltrate them. Fix → httpOnly secure cookies or a backend-for-frontend.

  • Static keys in CI

    Cloud admin keys stored as CI secrets forever. Fix → OIDC federation with short role sessions.

  • No reuse detection

    A stolen refresh token keeps working alongside the real one. Fix → rotate and revoke the family on reuse.

7When to use it (and when not)

Use it when…

  • User sessions in web and mobile apps.
  • API access by third parties.
  • CI/CD and services calling cloud APIs.

Skip it when…

  • Truly offline devices that can't refresh (use other controls).
  • Legacy systems that only accept static keys (wrap them in a vault with rotation).

8Self-check quiz

Why keep access tokens short-lived?

So a stolen one stops working within minutes, without needing to find and revoke it.

What's refresh-token rotation?

Each refresh returns a new refresh token and invalidates the old one.

What should happen if an old refresh token is reused?

Treat it as theft and revoke the whole session (token family).

How can CI deploy to the cloud without stored keys?

With OIDC federation: CI presents a signed identity token and receives short-lived role credentials.
