OAuth 2.0 with PKCE

TL;DR

Never ask users for their password to another service. With OAuth 2.0, the user signs in at the provider and approves a narrow scope; your app gets a one-time code and swaps it for tokens. PKCE ties the code to a secret only your app knows, so an intercepted code is useless. Use the authorization code flow + PKCE for every client type, and OpenID Connect on top for sign-in.

  • Family: delegated authorization
  • Specs: OAuth 2.0 (RFC 6749), PKCE (RFC 7636), OAuth 2.1 draft
  • Sign-in layer: OpenID Connect
  • Pairs with: short-lived tokens, least privilege

1The problem why do we even need this?

Apps used to ask for your actual password to another service to get your data. That hands over everything, forever, with no way to revoke one app. And rolling your own sign-in is where most auth bugs come from.

  • The app can read all your mail when it only needed your calendar.
  • Revoking it means changing your password everywhere.
  • Old “implicit” flows leaked tokens in browser URLs and history.

2Real-life analogy the valet key

Some cars come with a valet key: it starts the car and opens the driver's door, but not the boot or glovebox. You hand that to the attendant, never your house keys, and you can cancel it any time.

  • The valet key is an access token with a scope.
  • The car maker issuing it is the authorization server.
  • Your house keys (password) never leave your pocket.

3How it solves it code flow + PKCE

PKCE (“pixy”) is small: hash a random secret, send the hash first, prove you know the secret later. It protects mobile apps, SPAs and server apps alike, which is why OAuth 2.1 makes it mandatory.

  1. Use a provider and a library

    Don't hand-roll: use your identity provider's SDK or a certified OIDC client.

  2. Generate verifier + challenge

    A random code_verifier; send S256 hash as code_challenge, plus a random state.

  3. Redirect to the provider

    The user signs in and consents to narrow scopes; your app never sees the password.

  4. Exchange the code

    Back-channel POST with the code and the verifier; check state.

  5. Validate tokens

    Check signature, issuer, audience and expiry of the ID token; store tokens safely (server side or secure cookies).

  6. Avoid old flows

    No implicit flow, no password grant.

login.tsoauth4webapi-style, server side
// ① start sign-in
const verifier = generateRandomCodeVerifier();
const challenge = await calculatePKCECodeChallenge(verifier);   // S256
const state = generateRandomState();
session.set({ verifier, state });

redirect(`${issuer}/authorize?` + new URLSearchParams({
  response_type: "code", client_id, redirect_uri,
  scope: "openid email calendar.read",
  code_challenge: challenge, code_challenge_method: "S256", state,
}));

// ③ callback: check state, swap code + verifier for tokens
const params = validateAuthResponse(as, client, callbackUrl, session.state);
const res = await authorizationCodeGrantRequest(as, client, params, redirect_uri, session.verifier);
const { id_token, access_token } = await processAuthorizationCodeOpenIDResponse(as, client, res);

tools: identity providers (Auth0, Okta, Entra ID, Keycloak, Cognito, Google), libraries like oauth4webapi, openid-client, Auth.js, Spring Security, AppAuth for mobile.

4Gains vs losses nothing is free

What we gain

  • No password sharing with third-party apps.
  • Narrow, revocable access via scopes and tokens.
  • Intercepted codes are useless thanks to PKCE.
  • Sign-in handled by experts (MFA, passkeys, lockouts).

What we lose

  • More concepts: flows, tokens, scopes, redirects.
  • Dependency on an identity provider.
  • Misconfiguration risks: redirect URIs, token validation.
  • Extra redirects in the user journey.

6Common pitfalls the usual ways this goes wrong

  • Implicit flow or password grant

    Tokens in URLs or apps handling passwords. Fix → use authorization code + PKCE everywhere.

  • Loose redirect URIs

    Wildcards let attackers receive codes. Fix → register exact redirect URIs.

  • Not validating ID tokens

    Accepting any token that parses. Fix → check signature, issuer, audience, expiry, nonce.

  • Huge scopes

    Asking for “full access” when you need one calendar. Fix → request the narrowest scopes, incrementally.

7When to use it (and when not)

Use it when…

  • Any “sign in with…” or SSO.
  • Third-party access to user data (APIs, integrations).
  • SPAs, mobile and desktop apps (PKCE is essential).

Skip it when…

  • Machine-to-machine calls with no user (use client credentials or workload identity).
  • Internal tools already behind an identity-aware proxy.

8Self-check quiz

What problem does OAuth solve?

Delegated access: an app gets limited, revocable access to a user's data without ever seeing their password.

What does PKCE protect against?

An intercepted authorization code being exchanged by someone else: they don't have the code verifier.

What does OpenID Connect add?

Sign-in: an ID token that tells the app who the user is.

Which flows should you avoid?

The implicit flow and the resource-owner password grant.
