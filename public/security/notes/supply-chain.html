Supply-Chain Hygiene

TL;DR

Most of your app is other people's code. Keep it under control: lock exact versions with integrity hashes, take updates through small automated PRs that run your tests, scan for known vulnerabilities and malicious packages, produce an SBOM so you know what's inside, sign builds with provenance, and deploy only what you signed, on minimal, pinned base images.

  • Family: software supply chain
  • Frameworks: SLSA, OpenSSF Scorecard, NIST SSDF
  • Artefacts: lockfiles, SBOM (CycloneDX/SPDX), signatures
  • Pairs with: least privilege, defence in depth

1The problem why do we even need this?

A typical app has a handful of direct dependencies and hundreds of transitive ones, plus base images, CI actions and build tools. Any of them can be vulnerable, abandoned, typosquatted or hijacked.

  • Floating versions pull a malicious release into the next build.
  • Nobody can say whether a newly announced vulnerability affects you.
  • A two-year-old base image carries dozens of known CVEs.
  • A CI action pinned to a tag is quietly changed upstream.

2Real-life analogy checking the deliveries

A good kitchen checks every delivery: known suppliers, seals intact, an ingredient label on every package, and a batch number logged. When a supplier recalls a batch, the kitchen knows exactly which dishes used it.

  • The order sheet is your lockfile.
  • The ingredient label is the SBOM.
  • The seal is a signature; the batch log is provenance.

3How it solves it lock, update, scan, sign, verify

Small, frequent updates are safer than rare big ones: each PR is easy to review and test, and you're never years behind when a critical fix lands.

  1. Lock everything

    Commit lockfiles; install with npm ci; pin CI actions and base images by digest/SHA.

  2. Review new dependencies

    Is it maintained? How many maintainers? Install scripts? Prefer fewer, well-known packages.

  3. Automate updates

    Dependabot or Renovate: small PRs, tests, grouped minor updates, auto-merge only for low risk.

  4. Scan continuously

    Known vulnerabilities (OSV, npm audit) and malicious package feeds; fail builds on criticals.

  5. Generate an SBOM

    CycloneDX or SPDX per build, stored with the artefact.

  6. Sign and verify

    Sign images with provenance (Sigstore/cosign, SLSA); admission control accepts only signed images.

steps:
  - uses: actions/checkout@08eba0b27e820071cde6df949e0beb9ba4906955   # pinned SHA
  - run: npm ci --ignore-scripts          # exact lockfile, no install scripts
  - run: npx osv-scanner --lockfile=package-lock.json
  - run: docker build -t $IMAGE .         # FROM node:22.11-slim@sha256:…
  - run: syft $IMAGE -o cyclonedx-json > sbom.json
  - run: cosign sign --yes $IMAGE         # keyless, via the CI's OIDC identity
  - run: cosign attest --yes --type cyclonedx --predicate sbom.json $IMAGE

# cluster admission policy: only images signed by this repo's workflow may run

4Gains vs losses nothing is free

What we gain

  • Reproducible builds: the same code every time.
  • Fast answers to “are we affected?”
  • Poisoned updates blocked or caught early.
  • Only trusted artefacts reach production.

What we lose

  • A steady stream of update PRs.
  • Scanner noise and false positives.
  • Pipeline complexity for signing and verification.
  • Pinned versions need active updating.

6Common pitfalls the usual ways this goes wrong

  • Ignoring the update PRs

    200 open Dependabot PRs; nobody looks. Fix → group updates, auto-merge low-risk, own the queue.

  • Pinning but never updating

    Locked to versions with known CVEs for years. Fix → small, regular updates.

  • Install scripts

    A package's postinstall runs arbitrary code in CI. Fix → --ignore-scripts where possible; review packages that need them.

  • Unpinned CI actions

    uses: some/action@v1 changes underneath you. Fix → pin third-party actions by commit SHA.

7When to use it (and when not)

Use it when…

  • Every project with dependencies (all of them).
  • Container images and CI pipelines.
  • Software you ship to customers.

Skip it when…

  • Don't skip; scale it. A small project can start with a lockfile, Dependabot and one scanner.

8Self-check quiz

Why are transitive dependencies a risk?

They make up most of your code, and you didn't choose or review them directly.

What is an SBOM for?

Knowing exactly which components and versions are in a build, so you can answer “are we affected?” quickly.

Why pin CI actions by commit SHA?

Tags can be moved to point at different code; a SHA can't change.

What does signing images with provenance give you?

Proof that an image was built by your trusted pipeline, which deploys can verify.
