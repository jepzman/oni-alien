Signed Webhooks

TL;DR

A webhook endpoint is a public URL that changes things (“order paid”, “subscription cancelled”). Anyone who finds it can call it. Verify every request: the sender signs the exact raw body plus a timestamp with a shared secret (HMAC), you recompute and compare in constant time, reject old timestamps to stop replays, and ignore event ids you've already handled. Then answer quickly and process in the background.

  • Family: untrusted input
  • Mechanism: HMAC-SHA256 over timestamp + raw body
  • Standard: Standard Webhooks spec; Stripe, GitHub, Slack all sign
  • Pairs with: idempotent consumer, validate at the boundary, secrets management

1The problem why do we even need this?

A shop's /webhooks/payment endpoint ships an order whenever it receives a JSON body saying “paid”. Someone who finds the URL (in a log, a browser extension, a guess) sends their own “order 812 paid”, and the order ships without payment.

  • Webhook URLs are public by nature; obscurity is not protection.
  • A captured real notice can be sent again later (replay).
  • Providers retry deliveries, so the same event can legitimately arrive twice.

2Real-life analogy a sealed, dated letter

A notary's letter carries a wax seal pressed with a stamp only the notary has, and a date. You open it only if the seal is intact and matches, and the date is recent. A forged letter has no matching seal; an old genuine letter posted again is refused because of its date.

3How it solves it five checks before you trust it

The sender computes HMAC-SHA256(secret, timestamp + "." + raw_body) and sends it in a header with the timestamp. You recompute it over the bytes you received, before parsing (re-serialised JSON won't match), and compare with a constant-time function. Check the timestamp is recent and the event id is new, then return 2xx quickly and queue the work.

  1. Keep the raw body

    Configure the route to give you the bytes (express.raw, request.get_data()) before any JSON parsing.

  2. Recompute and compare

    HMAC-SHA256 with the endpoint's secret over the exact signed string; compare with a timing-safe function.

  3. Reject stale timestamps

    Older than ~5 minutes (or in the future): refuse, so captured requests can't be replayed later.

  4. Deduplicate by event id

    Store processed ids with a unique constraint; a retry of the same event is a no-op.

  5. Answer fast, work later

    Return 2xx within a second or two and process from a queue, or the sender retries and duplicates pile up.

Vocabulary for the exam

Webhook
An HTTP call a provider makes to your URL when something happens.
HMAC
A keyed hash: only holders of the secret can produce the right value.
Constant-time compare
Comparing without leaking how many characters matched.
Replay
Sending a captured, genuine request again later.
Event id
A unique id per event, used to drop duplicates.
Secret rotation
Switching to a new signing secret while accepting both for a while.
webhooks.tsNode.js + Express
import crypto from "node:crypto";

app.post("/webhooks/payment", express.raw({ type: "application/json" }), async (req, res) => {
  const ts = req.header("webhook-timestamp") ?? "";
  const sig = req.header("webhook-signature") ?? "";
  const age = Math.abs(Date.now() / 1000 - Number(ts));
  if (!ts || age > 300) return res.status(400).send("stale or missing timestamp");

  const expected = crypto.createHmac("sha256", process.env.WEBHOOK_SECRET!)
    .update(`${ts}.`).update(req.body)                 // the exact raw bytes
    .digest("base64");
  const ok = sig.length === expected.length &&
             crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
  if (!ok) return res.status(401).send("bad signature");

  const event = JSON.parse(req.body.toString("utf8"));
  const isNew = await db.webhookEvents.insertIfAbsent(event.id);   // unique on id
  if (isNew) await queue.publish("payment-events", event);          // work happens later
  res.status(204).end();
});

tools: Standard Webhooks libraries (standardwebhooks.com), Stripe constructEvent, GitHub X-Hub-Signature-256, Svix (sending and verifying), smee.io / ngrok for local testing, secrets managers for the signing secrets.

4Gains vs losses nothing is free

What we gain

  • Only the real sender can trigger the endpoint.
  • Replays are refused by the timestamp check.
  • Duplicates are harmless with event ids.
  • Cheap: a hash per request.

What we lose

  • A secret to manage and rotate per endpoint.
  • Raw body handling trips up frameworks that parse JSON first.
  • Clock skew can reject genuine requests if servers drift.
  • Every provider differs in header names and formats.

6Common pitfalls the usual ways this goes wrong

  • Verifying parsed JSON

    The framework parsed and re-serialised the body; the signature never matches, so someone disables the check. Fix → verify the raw bytes before parsing.

  • Plain string compare

    sig === expected leaks timing information. Fix → use a constant-time comparison.

  • No timestamp check

    A captured genuine notice can be sent again weeks later. Fix → sign the timestamp and reject anything older than a few minutes.

  • Slow handler

    The endpoint does all the work before answering; the provider times out and retries, and orders ship twice. Fix → answer 2xx fast, queue the work, and deduplicate by event id.

7When to use it (and when not)

Use it when…

  • Every incoming webhook that changes state: payments, subscriptions, deployments.
  • Sending webhooks to customers: sign them the same way.
  • Internal callbacks between systems over the internet.

Skip it when…

  • The sender can't sign: then allow-list its IPs and use mutual TLS, and treat the payload as a hint to fetch the real state.
  • Read-only notifications with no effect (still cheap to verify, though).
  • Calls inside a private network already authenticated by mTLS.

8Self-check quiz

Why must the signature be checked over the raw body?

The signature covers exact bytes; parsing and re-serialising JSON changes spacing or order, so the check would fail or be skipped.

What does the timestamp check prevent?

Replays: a captured genuine request sent again later is rejected as too old.

Why compare signatures in constant time?

A normal comparison can leak, through timing, how much of a guessed signature was right.

Why store event ids?

Providers retry deliveries; the id lets you process each event only once.

what would you do?Your endpoint verifies signatures correctly, but customers are sometimes charged twice for one order. The provider's dashboard shows many retries after timeouts on your endpoint. What do you change?

Answer 2xx as soon as the request is verified and recorded, and do the work from a queue; and deduplicate by the event id with a unique constraint, so a retried delivery is ignored. Make the charge-side action idempotent too.

Add signature checking to one webhook endpoint (or write a toy one).
