Least Privilege

TL;DR

Give every person, service and key only the permissions its job needs, on only the resources it touches, for only as long as it needs them. Use narrow roles per workload, just-in-time elevation for humans, and remove unused rights regularly. When something leaks, it can only do a little.

  • Family: access control
  • Origin: Saltzer & Schroeder, 1975
  • Tools: IAM roles, RBAC/ABAC, JIT access, access analyzers
  • Pairs with: zero trust, secrets management

1The problem why do we even need this?

Permissions are granted generously (“just give it admin so it works”) and almost never taken away. Every over-powered key is a bigger prize for an attacker, and a bigger mess when someone makes a mistake.

  • A read-only report runs as the database admin.
  • Ex-employees and old services still have access years later.
  • A typo in a script deletes production because the script could.

2Real-life analogy the hotel key card

Your hotel card opens your room and the gym, and stops working at check-out. The cleaner's card opens one floor, during the shift. The master key lives in the manager's safe and is signed out when needed.

  • Your card is a narrow role.
  • “Until Sunday” is an expiry.
  • Signing out the master key is just-in-time elevation, with a log.

3How it solves it narrow, short, reviewed

Least privilege works best when it's the default: new roles start empty, and every permission has a reason, an owner and, ideally, an expiry.

  1. One identity per workload

    No shared “app” user; each service, job and person has its own identity.

  2. Start from zero

    Grant specific actions on specific resources (SELECT on sales), not wildcards.

  3. Separate duties

    Runtime roles can't change schema; deploy roles can't read customer data.

  4. Time-box human admin

    Just-in-time elevation with approval, expiry and logs; no standing admin.

  5. Review and prune

    Use access analyzers and last-used data; remove what hasn't been used in 90 days.

4Gains vs losses nothing is free

What we gain

  • Small blast radius for leaks and mistakes.
  • Clear ownership: every permission has a reason.
  • Easier audits and compliance.
  • Fewer accidents: scripts can't do what they shouldn't.

What we lose

  • More roles to define and maintain.
  • “Permission denied” friction while getting it right.
  • Reviews take time.
  • Too narrow can break things in production.

6Common pitfalls the usual ways this goes wrong

  • Wildcards “for now”

    "Action": "*" ships and stays for years. Fix → start from zero; lint policies for wildcards.

  • Shared accounts

    Five services use one database user. Fix → one identity per workload.

  • Standing admin for humans

    Every engineer is always admin. Fix → just-in-time elevation with expiry.

  • Never removing access

    Old services and leavers keep permissions. Fix → automated reviews using last-used data.

7When to use it (and when not)

Use it when…

  • Every system, every identity: it's a default, not a feature.
  • Especially service accounts, CI pipelines and API keys.
  • Admin access to production and customer data.

Skip it when…

  • Don't skip it; just don't spend weeks on throwaway prototypes with no real data.

8Self-check quiz

What does least privilege limit?

Which actions, on which resources, for how long each identity can act.

What's just-in-time access?

Temporary elevated access granted when needed, with approval and an expiry, instead of standing admin rights.

Why one identity per workload?

So each one gets only its own permissions, and logs and revocation are precise.

How do you find permissions to remove?

Use last-used data and access analyzers; remove what hasn't been used in a set period.
