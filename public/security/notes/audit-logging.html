Audit Logging

TL;DR

For every security-relevant action (sign-ins, permission changes, exports, deletes, admin actions), write a structured audit event: who, what, on which target, result, when, from where. Ship it to a separate, append-only store that app admins can't edit, keep it long enough, and alert on unusual patterns. Never log secrets or more personal data than needed.

  • Family: detection & forensics
  • Log: who · what · target · result · when · where
  • Store: append-only / WORM, separate account
  • Pairs with: history tables (Vol. 3), zero trust

1The problem why do we even need this?

When something goes wrong, the first questions are who, what and when. Application logs are built for debugging, so they often can't answer them, or they've already been rotated away.

  • “GET /export 200” with no user or tenant.
  • Logs deleted after 7 days; the breach is noticed after 40.
  • An attacker with admin rights quietly deletes the evidence.

2Real-life analogy the ship's logbook

A ship keeps a logbook in ink with numbered pages. Every entry says the time, who was on watch and what happened. A torn-out page would be noticed, and copies are sent ashore, beyond the crew's reach.

  • Entries are audit events.
  • Ink and numbered pages are append-only, tamper-evident storage.
  • Copies ashore are a separate account the app's admins can't touch.

3How it solves it structured, separate, append-only

Audit logs are a product feature for your security team and your customers' admins: define the events, their fields and retention on purpose, not by accident.

  1. List auditable actions

    Sign-in/out, MFA changes, role changes, exports, deletes, settings, admin and support access.

  2. Use a fixed schema

    actor, actor type, tenant, action, target, result, timestamp (UTC), IP, user agent, request id.

  3. Write at the decision point

    Log where the action is authorised and performed, including failures.

  4. Ship to a separate store

    Different account/project; append-only or WORM retention.

  5. Protect privacy

    No passwords, tokens or full card numbers; minimise personal data.

  6. Alert and review

    Rules for bulk exports, privilege changes, impossible travel; regular reviews.

audit.tsstructured audit events
type AuditEvent = {
  at: string; actor: { id: string; type: "user" | "service" }; tenantId: string;
  action: string; target: string; result: "ok" | "denied" | "error";
  ip?: string; requestId: string; meta?: Record<string, unknown>;
};

export function audit(e: Omit<AuditEvent, "at">) {
  auditSink.write({ ...e, at: new Date().toISOString() });   // separate pipeline
}

// at the decision point, success AND failure
if (!can(user, "customers.export", tenant)) {
  audit({ actor: { id: user.id, type: "user" }, tenantId: tenant.id,
          action: "customers.export", target: "all", result: "denied", requestId, ip });
  throw new Forbidden();
}
audit({ actor: { id: user.id, type: "user" }, tenantId: tenant.id,
        action: "customers.export", target: "all", result: "ok", requestId, ip,
        meta: { rows: count } });

tools: cloud audit trails (CloudTrail, GCP Audit Logs, Azure Activity Log), S3 Object Lock / immutable storage, SIEMs (Splunk, Elastic Security, Microsoft Sentinel, Panther), OpenTelemetry logs for shipping, WorkOS / Retraced-style audit log products.

4Gains vs losses nothing is free

What we gain

  • Answer who, what, when after an incident.
  • Detect abuse early with alerts.
  • Evidence that survives an admin compromise.
  • Compliance and customer trust (admin audit views).

What we lose

  • Storage costs for long retention.
  • Privacy risk if logs hold too much personal data.
  • Alert fatigue with noisy rules.
  • Effort to define and maintain events.

6Common pitfalls the usual ways this goes wrong

  • Logging secrets

    Tokens and passwords end up in the audit store. Fix → redact by schema; never log credentials.

  • Same account as the app

    An attacker with app admin deletes the logs. Fix → ship to a separate account with append-only retention.

  • Only successes

    Failed attempts, which show probing, are missing. Fix → log denied and failed actions too.

  • Unstructured text

    “User did export” can't be searched or alerted on. Fix → fixed fields, machine-readable JSON.

7When to use it (and when not)

Use it when…

  • Authentication, authorization and admin actions.
  • Exports, deletes, payments and settings changes.
  • Support staff accessing customer data.

Skip it when…

  • Every page view or debug detail (that's for app logs/metrics).
  • Data you aren't allowed to keep (minimise).

8Self-check quiz

What fields should an audit event have?

Actor, action, target, result, timestamp, tenant, source IP and a request id.

Why ship audit logs to a separate account?

So an attacker or insider with app admin rights can't alter or delete them.

Should denied actions be logged?

Yes; failed attempts reveal probing and abuse.

What must never appear in audit logs?

Secrets such as passwords and tokens, and more personal data than needed.

remember!!

Write it in ink: who, what, when. And send a copy ashore.
