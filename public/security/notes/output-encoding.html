Output Encoding & CSP

TL;DR

Cross-site scripting happens when data is shown as code. Prevent it with two layers: encode output for its context (HTML text, attribute, URL, JavaScript), which modern frameworks do by default, so avoid innerHTML and dangerouslySetInnerHTML; and send a strict Content Security Policy so the browser refuses to run scripts you didn't send. Sanitize the rare rich HTML with a proven library.

  • Family: XSS prevention
  • Layers: contextual encoding + CSP
  • Tools: framework escaping, DOMPurify, CSP nonces
  • Pairs with: input validation, CSRF protection

1The problem why do we even need this?

Any place that shows user content (comments, names, search terms, error messages) can become a way to run a stranger's script in your users' browsers, with their session and their permissions.

  • A comment with a script tag runs for every visitor.
  • A search term echoed into the page runs via a crafted link.
  • Tokens in localStorage are read and sent away.

2Real-life analogy text behind glass

In a museum, an exhibit label can say anything, even “open all the cases!”, but it's behind glass: visitors can read it, it can't do anything. And the museum only lets in guides wearing an official badge.

  • Glass is output encoding: shown, never executed.
  • The badge rule is CSP: only scripts you approved may act.

3How it solves it encode, then restrict

Encoding stops injected markup becoming code. CSP is the safety net for the bug you'll eventually ship anyway.

  1. Let the framework escape

    React, Vue, Angular, Svelte and server templates escape text by default; keep it that way.

  2. Avoid raw HTML sinks

    innerHTML, dangerouslySetInnerHTML, v-html, document.write.

  3. Sanitize rich content

    If you must render user HTML or Markdown, sanitize with DOMPurify (or server-side equivalent).

  4. Check URLs

    Allow only http(s) in user links; block javascript:.

  5. Add a strict CSP

    script-src 'nonce-…' 'strict-dynamic', object-src 'none', base-uri 'none'; start in report-only mode.

  6. Keep tokens out of JS reach

    httpOnly cookies, so even a successful XSS can't read them.

Vocabulary for the exam

Turning special characters into harmless text.

CSP
Header telling the browser which content may load and run.
Nonce
Random value per response allowing specific scripts.
Sanitizer

comment.tsx + headers.tsReact + Express
// ✓ React escapes text automatically
<p className="comment">{comment.body}</p>

// rich text: sanitize first, then render
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(markdownToHtml(c.body)) }} />

// links: allow only http(s)
const safeHref = /^https?:\/\//i.test(url) ? url : "#";

// strict CSP with a fresh nonce per response
app.use((req, res, next) => {
  res.locals.nonce = crypto.randomBytes(16).toString("base64");
  res.setHeader("Content-Security-Policy",
    `script-src 'nonce-${res.locals.nonce}' 'strict-dynamic'; ` +
    "object-src 'none'; base-uri 'none'; frame-ancestors 'none'");
  next();
});

tools: framework auto-escaping, DOMPurify, sanitize-html, Trusted Types, CSP Evaluator, report-uri / report-to endpoints, Helmet (Express), eslint-plugin-react rules for dangerous props.

4Gains vs losses nothing is free

What we gain

  • User content stays text.
  • CSP blocks injected scripts even when a bug slips through.
  • Framework defaults do most of the work.
  • CSP reports reveal attacks and mistakes.

What we lose

  • CSP takes tuning (third-party scripts, inline handlers).
  • Rich text needs a sanitizer.
  • Easy to bypass with one raw HTML sink.

6Common pitfalls the usual ways this goes wrong

  • Raw HTML sinks

    el.innerHTML = name in one widget. Fix → use textContent / framework rendering; lint sinks.

  • Sanitizing with regex

    Stripping “<script>” misses event handlers and SVG. Fix → use DOMPurify.

  • A CSP with 'unsafe-inline'

    The policy allows exactly what attackers inject. Fix → nonces + strict-dynamic, no unsafe-inline.

  • javascript: links

    User-supplied URLs run code on click. Fix → allow only http(s) schemes.

7When to use it (and when not)

Use it when…

  • Every page that shows user or third-party content.
  • Admin panels (attackers love targeting admins).
  • Any HTML email or PDF generated from user data.

Skip it when…

  • Never skip encoding; CSP can be phased in with report-only mode.

8Self-check quiz

What makes XSS possible?

User-controlled data is placed into a page in a way the browser interprets as code.

Why does encoding depend on context?

Different places (HTML text, attributes, URLs, scripts) have different special characters.

What does a nonce-based CSP do?

Only scripts carrying the per-response nonce may run, so injected scripts are blocked.

How do you render user-supplied HTML safely?

Sanitize it with a proven library like DOMPurify before inserting it.
