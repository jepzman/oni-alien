Passkeys

TL;DR

A passkey replaces the password with a key pair: the private key stays on the user's device (or their password manager, synced between devices), the site stores only the public key. To sign in, the site sends a challenge, the user unlocks the device with a fingerprint, face or PIN, and the device signs it, only for the real domain. Nothing reusable crosses the network, so passkeys resist phishing, password reuse and database leaks. Built on WebAuthn / FIDO2.

  • Family: identity
  • Standard: WebAuthn (W3C) + FIDO2 (FIDO Alliance)
  • Stops: phishing, credential stuffing, leaked password hashes
  • Pairs with: short-lived tokens, rate-limited login, OAuth with PKCE

1The problem why do we even need this?

A customer gets a convincing email, signs in on shop-1ogin.com, and types their password and the six-digit code from their phone. The fake site replays both to the real one within seconds and takes over the account. The code was real; it was just typed into the wrong place.

  • Passwords are reused, guessed and leaked in other sites' breaches.
  • One-time codes by SMS or app stop guessing, but not phishing: a person can type them anywhere.
  • Password resets and support calls are a large, ongoing cost.

2Real-life analogy a key cut for one door

Your house key turns your front door. If someone builds a fake door that looks exactly like yours, the key simply doesn't fit, so there's nothing to steal by tricking you into trying it. And the key never leaves your keyring: the door checks it, it doesn't keep a copy.

3How it solves it a challenge, signed on the device

At registration the device creates a key pair for this site and gives the site the public key. At sign-in the site sends a random challenge; the browser only offers passkeys for the site's own domain; the device asks the user to unlock and signs the challenge; the site checks the signature. The biometric never leaves the device, and the site holds nothing an attacker could reuse.

  1. Use a maintained library

    SimpleWebAuthn, webauthn4j, py_webauthn or your identity provider; don't implement WebAuthn by hand.

  2. Offer it where people already are

    “Create a passkey” after a successful sign-in, and in account settings. Keep the old method for now.

  3. Use autofill

    autocomplete="username webauthn" lets the browser offer passkeys right in the sign-in field.

  4. Store per credential

    Public key, credential id, sign counter, a name and last-used date; let users see and remove them.

  5. Plan recovery

    A second passkey, a recovery process with real checks, or a synced passkey provider. Recovery is the new weak spot.

Vocabulary for the exam

Passkey
A FIDO credential (key pair) used instead of a password.
WebAuthn
The browser API for creating and using passkeys.
Relying party
The site the passkey is for, identified by its domain.
Challenge
A random value the device signs to prove it holds the key.
Synced passkey
A passkey backed up across a user's devices by their platform or password manager.
User verification
The device checking it's really the user: biometric or PIN.
passkeys.tsSimpleWebAuthn, server side
import { generateAuthenticationOptions, verifyAuthenticationResponse } from "@simplewebauthn/server";

const rpID = "shop.example";                    // passkeys only work for this domain

app.post("/passkeys/login/options", async (req, res) => {
  const options = await generateAuthenticationOptions({ rpID, userVerification: "preferred" });
  req.session.challenge = options.challenge;    // remember it: it may be used once
  res.json(options);                            // the browser calls navigator.credentials.get()
});

app.post("/passkeys/login/verify", async (req, res) => {
  const cred = await db.passkeys.findById(req.body.id);
  const result = await verifyAuthenticationResponse({
    response: req.body,
    expectedChallenge: req.session.challenge,
    expectedOrigin: "https://shop.example",
    expectedRPID: rpID,
    credential: { id: cred.id, publicKey: cred.publicKey, counter: cred.counter },
  });
  delete req.session.challenge;
  if (!result.verified) return res.status(401).end();
  await db.passkeys.touch(cred.id, result.authenticationInfo.newCounter);
  await startSession(res, cred.userId);
  res.status(204).end();
});

tools: SimpleWebAuthn (JS), py_webauthn, webauthn4j / java-webauthn-server, go-webauthn, Auth0 / Okta / Entra ID / Cognito passkey support, passkeys.dev for guides and device support.

4Gains vs losses nothing is free

What we gain

  • Phishing-resistant: a look-alike site gets nothing usable.
  • Nothing to leak: the site stores public keys only.
  • Faster sign-in: a fingerprint instead of typing.
  • Fewer resets and less support work.

What we lose

  • Recovery when every device is lost needs careful design.
  • Mixed support on older devices and in some enterprise setups.
  • Two methods for a while: passwords stay during the transition.
  • New UX to explain to users.

6Common pitfalls the usual ways this goes wrong

  • Recovery by email link only

    Passkeys are strong, but anyone with the user's email can reset them away. Fix → make recovery as strong as sign-in: a second passkey, identity checks, a waiting period with notifications.

  • Hiding the button

    Passkeys live on a settings page no one visits. Fix → offer to create one right after a successful sign-in, and use autofill.

  • Not binding to the domain

    Hand-rolled verification skips the origin or rpID check. Fix → use a library and always check origin, rpID and the challenge.

  • Reusing challenges

    The same challenge works twice. Fix → one random challenge per attempt, stored server side, deleted after use.

7When to use it (and when not)

Use it when…

  • Consumer and staff sign-in on the web and mobile.
  • Accounts worth phishing: money, data, admin rights.
  • Replacing SMS codes as a second factor.

Skip it when…

  • Machine-to-machine access (use workload identity and short-lived tokens).
  • Shared kiosks with no personal device.
  • You can't yet offer a sound recovery process; build that first.

Related patterns

  • Short-lived tokens
  • Rate-limited login

8Self-check quiz

Why can't a phishing site use a passkey?

The browser only offers and signs for passkeys registered to the real site's domain; a look-alike domain gets no signature.

What does the site store for a passkey?

The public key, the credential id and a counter: nothing an attacker could use to sign in.

Does the fingerprint or face scan go to the site?

No. It only unlocks the private key on the device.

What becomes the weak point once passkeys are used?

Account recovery: if it's just an email link, attackers go after that instead.

what would you do?Your bank app adds passkeys, but keeps “forgot password? we'll email you a link” as the only recovery, which also removes all passkeys. An attacker who has the user's email can now take over the account. What do you change?

Make recovery at least as strong as sign-in: encourage a second passkey, require stronger identity checks for recovery, add a waiting period with notifications to every registered device, and don't let recovery silently delete existing passkeys.

try it

Clone a SimpleWebAuthn example (or your identity provider's passkey sample), run it on localhost, and register a passkey with your laptop or phone. Then change the expected rpID or origin in the server code and see the sign-in fail. Look in the database at what was stored for the credential: a public key, not a secret.
