Choosing a Cloud Service Model

TL;DR

The cloud offers the same thing at different levels: virtual machines (IaaS), Kubernetes, managed or serverless containers, functions (FaaS), platforms (PaaS) and finished SaaS. Each step up, the provider runs more and you control less. Choose by the workload's shape (always on? long connections? spiky?) and, above all, by who will run it at 3 a.m.: pick the highest level that fits, and step down only for a reason you can name.

1The situation Larder, 6 April 2026

RFC-003 is accepted: Dispatch becomes its own service. Where does it run? Eli proposes managed Kubernetes: “we'll need it eventually”. Ben proposes functions: “serverless, pay per use”. Both are in fashion. But Larder has one platform engineer, Eli, who already patches Larder Core's virtual machines by hand. Dispatch must hold connections from 300 courier phones, each sending a location every 5 seconds, all evening.

  • Platforms chosen for the future team leave today's team on call for them.
  • Fashion picks the level, not the workload.
  • The running cost that matters most is people's time, and it's rarely in the comparison.

2Real-life analogy pizza as a service

Pizza for dinner: home-made (you do it all), take and bake (they make it, you bake it), delivery (you set the table), or dine out (they do everything). Each step up you control less, pay more per pizza, and do far less. On a busy Tuesday, nobody kneads dough to prove they could.

3How it solves it the highest level that fits the workload

Functions are cheap for spiky, short work, but can't hold long-lived connections well. Kubernetes can do everything, and needs people to run it. Managed containers run Dispatch's always-on service, scale with cities, and leave Eli only the code and a few settings (ADR 0010, 8 April). Revisit when Larder runs more than five services or needs something the container service can't do.

  1. Describe the workload

    Always on or spiky? Long connections? State? Start-up time? Peak vs average.

  2. Count who runs it

    Who's on call, what they know, how many hours a week they have for it.

  3. Start at the top

    SaaS if it's context. Then PaaS or serverless containers. Then functions for spiky, short jobs.

  4. Step down only for a reason

    A named need (long connections, GPUs, special networking) justifies more control.

  5. Compare total cost

    Provider bill + people's time + the cost of moving later.

  6. Write the ADR with a trigger

    “Revisit when we run more than five services” or “if we need X”.

Vocabulary for the exam

IaaS
Infrastructure as a service: virtual machines; you run the rest.
Kubernetes
A container platform; powerful, and needs running.
Serverless containers
Run a container image; the provider runs servers and scaling.
FaaS
Functions as a service: small pieces of code run per event.
PaaS
Platform as a service: push code, the platform runs it.
Operational load
The people-time a platform needs to stay healthy.

4Gains vs losses nothing is free

What we gain

  • Less to run: the team's hours go to the product.
  • Fit for the workload: long connections, spikes, state.
  • Honest cost: people's time counted with the bill.
  • Easier to move when the unit is a standard container.
  • A trigger says when to step down a level.

What we lose

  • Less control: limits and features are the provider's.
  • Higher unit price at large scale.
  • Provider-specific settings creep in.
  • Mixed levels across services can confuse newcomers.

6Common pitfalls the usual ways this goes wrong

  • Building for the future team

    Kubernetes for 14 engineers “because we'll grow”. Fix → choose for the team you have; set a trigger for the one you'll have.

  • Ignoring the workload

    Functions for long-lived connections. Fix → describe the workload's shape first.

  • Bill only

    The cheapest bill, with eight hours a week of care. Fix → count people's time in the cost.

  • Deep lock-in

    Code shaped around one provider's functions. Fix → prefer standard units (containers) when moving matters.

7When to use it (and when not)

Use it when…

  • Every new service or workload.
  • When a team proposes a new platform.
  • When ops load is crowding out product work.
  • Reviewing costs at a new scale.

Skip it when…

  • When the organisation already has a mature platform team and golden path: use it.
  • SaaS decisions: that's build vs buy.

8Self-check quiz

What changes as you move from VMs to SaaS?

The provider runs more; you control less and run less.

Why were functions a poor fit for Dispatch?

Dispatch holds long-lived connections from 300 phones; functions handle short, event-driven work.

What cost is often left out of the comparison?

People's time to run the platform.

What's the rule of thumb?

Pick the highest level that fits the workload; step down only for a named reason.

try it

For one service you run, list the layers you operate yourselves (OS, cluster, scaling, runtime) and estimate the hours each takes per month. Then ask: which level would remove the most hours without breaking the workload's needs? Write it as a one-page ADR draft with a revisit trigger.
