RFCs & Design Docs

TL;DR

An ADR is one page about one decision. When a change is big enough that people will build it differently in their heads, write a design doc first and open it as an RFC (request for comments): goals, non-goals, the proposal, the alternatives, the rollout and the open questions. Give it named reviewers and a fixed comment window, settle what's left in one short meeting, then record the key decision as an ADR and freeze the RFC.

  • Origin: IETF RFCs (1969); design docs at Google; RFC processes at Rust, Uber, Spotify
  • Lives in: docs/rfcs/ as a pull request

1The situation Larder, 18 March 2026

ADR 0002 said: extract Dispatch first. Ben, on the orders team, and Eli, on platform, both start. Two weeks later their code doesn't fit: Ben has Ordering call Dispatch over HTTP and wait; Eli has Ordering publish events that Dispatch reads from Kafka. Both pictures were reasonable. Neither was written down, so nobody saw the difference until the code met.

  • A one-line decision (“extract Dispatch”) leaves the design to everyone's imagination.
  • Big designs discussed in meetings reach only the people in the room.
  • Without a comment window, review is either endless or skipped.

2Real-life analogy the planning application

Before a building goes up, the drawings are published: on the fence and online. The people affected (neighbours, the fire service) can comment, but only within a fixed window. Then the council decides, with reasons, and the permit stays on file. Nobody pours concrete on a picture that lives in the architect's head.

3How it solves it write the picture down before the code

An RFC is for changes that span teams or weeks: a new service, a new integration, a migration. The most useful sections are the ones people skip: non-goals (what this won't do) and alternatives (what else we considered). The RFC can be long; the ADR it produces stays one page.

  1. Decide if it needs one

    Spans teams, takes more than two weeks, or changes an interface others use → RFC. Otherwise an ADR or a line in the log.

  2. Write the draft together

    The people who'll build it write it. Two to six pages; diagrams welcome.

  3. Say what it won't do

    Non-goals stop scope creep and settle half the comments in advance.

  4. Open it with a window

    A pull request in docs/rfcs/, named reviewers, a closing date: five working days.

  5. Close it

    Resolve comments in the PR; a 30-minute meeting for the rest. The owner decides, not the loudest reviewer.

  6. Record and freeze

    Write the ADR for the key decision, link it, mark the RFC accepted. Later changes are new RFCs or ADRs.

Vocabulary for the exam

RFC
Request for comments: a proposal opened for review by a date.
Design doc
The written design: problem, goals, proposal, alternatives, rollout.
Non-goals
Things the design deliberately won't do.
Comment window
The fixed time reviewers have to respond.
Named reviewer
A person from an affected team who must read it.
Frozen
Accepted and no longer edited; changes need a new record.

# RFC-003: Dispatch as a service
Authors: Eli (platform), Ben (orders)   Reviewers: Ana, Cho, Sanne
Status: accepted 2026-03-27 → ADR 0008  Comments close: 2026-03-25

## Summary
Move courier assignment out of Larder Core into a Dispatch service that
owns couriers, locations and assignments. Ordering tells it an order is
ready; Dispatch tells Ordering when it's collected and delivered.

## Goals
- Rotterdam opens on Dispatch (27 Apr); Amsterdam moves the week after.
- Courier locations every 5 s without touching the Core database.
## Non-goals
- New routing algorithm (separate evaluation, May). - Courier app changes.

## Proposal
Ordering publishes order.ready_for_dispatch via the outbox (ADR 0007).
Dispatch publishes courier.assigned, order.collected, order.delivered.
No synchronous calls from Ordering to Dispatch.

## Alternatives
A. Ordering calls Dispatch over HTTP: simpler, but checkout waits on it.
B. Dispatch reads Core tables directly: fast to build, couples the schemas.

## Rollout        RTM-0 test store → Rotterdam → Amsterdam, cron kept as fallback
## Open questions  Who owns courier shifts? (→ Joost, by 3 Apr)

tools: Markdown in the repo, reviewed as a pull request, works best. Google Docs or Notion with comments are fine for early drafts; move the final version next to the code. Templates: Google-style design docs, the Rust RFC template, “Design Docs at Google” (Malte Ubl).

4Gains vs losses nothing is free

What we gain

  • One shared picture before anyone builds.
  • Everyone affected gets a say, including people not in the meeting.
  • Non-goals and alternatives stop the same debates resurfacing.
  • A fixed window: review happens, and ends.
  • Better designs: writing exposes the gaps a whiteboard hides.

What we lose

  • Days of writing before code starts.
  • Can become bureaucracy if every change needs one.
  • Bikeshedding: easy topics get all the comments.
  • Goes stale if people keep editing it after acceptance.

6Common pitfalls the usual ways this goes wrong

  • RFC for everything

    A two-day change waits a week for comments. Fix → only cross-team, multi-week or interface-changing work.

  • No closing date

    Comments trickle in for a month. Fix → a fixed window, then the owner decides.

  • Decided by comment count

    The longest thread wins. Fix → the owner weighs comments; the decision and its reasons go in the ADR.

  • A living document

    The RFC is edited after acceptance and no longer says what was agreed. Fix → freeze it; changes go in new RFCs or ADRs.

7When to use it (and when not)

Use it when…

  • New services, integrations or migrations.
  • Changes to interfaces other teams depend on.
  • Work that spans more than one team or more than two weeks.
  • When two people already picture the design differently.

Skip it when…

  • Small, local changes: a pull request description is enough.
  • A single clear-cut decision: write the ADR directly.
  • Urgent fixes: fix first, write an ADR afterwards if it matters.

8Self-check quiz

When does a change need an RFC rather than just an ADR?

When it spans teams or weeks, or changes an interface others use, so people need a shared design before building.

Why write non-goals?

They stop scope creep and settle many review comments in advance.

How does an RFC end?

Comments close on a fixed date, the owner decides, the key decision becomes an ADR and the RFC is frozen.

Who should write the RFC?

The people who will build it, with the architect reviewing.

try it

Open it as a pull request with three named reviewers and a five-day window, and note how many comments would otherwise have surfaced in integration.
