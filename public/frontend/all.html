Frontend Design Patterns

Components, state and data, rendering and performance, and architecture for UIs that stay fast and easy to change.

Components split the UI into pieces that are easy to reuse

  1. 01Container & PresentationalSplit components that fetch and decide from components that only display.p. 01
  2. 02Compound ComponentsA set of components that work together and share state, like select and option.p. 02
  3. 03Custom HooksPull reusable stateful logic out of components into small, testable functions.p. 03
  4. 04Headless ComponentsShip behaviour and accessibility without markup or styles; you bring the looks.p. 04

State & data where data lives and how it changes

  1. 05Global Store (Flux)One store for shared app state, changed only through named actions.p. 05
  2. 06Server-State CacheTreat API data as a cache: show it instantly, revalidate in the background.p. 06
  3. 07Optimistic UIShow the result before the server confirms, and roll back if it fails.p. 07
  4. 08State MachinesModel UI as explicit states and allowed transitions, so impossible states can't happen.p. 08

Rendering & performance get pixels on screen fast and keep them smooth

  1. 09SSR & HydrationRender HTML on the server for a fast first view, then make it interactive in the browser.p. 09
  2. 10Islands ArchitectureShip static HTML and hydrate only the small interactive parts of the page.p. 10
  3. 11Code Splitting & Lazy LoadingLoad only the code a screen needs now; fetch the rest when it's needed.p. 11
  4. 12List VirtualizationRender only the rows on screen, even when the list has 100,000 items.p. 12

Architecture & resilience scale the codebase, the teams and the failures

  1. 13Micro-FrontendsSplit a big frontend into apps owned and deployed by separate teams.p. 13
  2. 14Design TokensName every colour, size and font once, and use those names everywhere.p. 14
  3. 15Error BoundariesCatch a crashing part of the UI and show a fallback, instead of a blank page.p. 15
