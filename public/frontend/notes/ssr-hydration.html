SSR & Hydration

TL;DR

Render the page to HTML on the server (with its data) so the browser can show content immediately, and search engines and link previews see it. Then the same JavaScript runs in the browser and hydrates the HTML: it attaches event handlers and state so the page becomes interactive.

  • Family: rendering strategy
  • Frameworks: Next.js, Remix/React Router, Nuxt, SvelteKit, Angular SSR
  • Variants: streaming SSR, partial/progressive hydration
  • Pairs with: code splitting, islands, server-state cache

1The problem why do we even need this?

A purely client-side rendered (CSR) app sends an almost empty HTML file and a large JavaScript bundle. Nothing appears until the JS has downloaded, run and fetched data.

  • On a mid-range phone and 4G, that's a blank screen for several seconds.
  • Search crawlers and social link previews may see an empty page.
  • Core Web Vitals (LCP) suffer, and so do conversions.

2Real-life analogy the lamp delivered assembled

Some furniture shops deliver a lamp already assembled. The moment you open the box, it looks finished and you can put it where it belongs. It doesn't light up until you plug it in.

  • Assembled in the warehouse: rendered on the server.
  • Plugging in: hydration makes it work.
  • If you press the switch before plugging in, nothing happens: the gap between visible and interactive.

3How it solves it render on the server, hydrate in the browser

The server runs your components with real data and streams HTML. The browser paints it, downloads the JS, and React (or Vue, Svelte…) re-runs the components to attach to the existing DOM instead of rebuilding it.

  1. Fetch on the server

    Load data in a loader / server component so it's ready before HTML is sent.

  2. Render to HTML (and stream it)

    Send the shell first and stream slower sections as they resolve (Suspense), so the top of the page appears fast.

  3. Embed the data

    Serialise the data the client needs so hydration doesn't refetch it.

  4. Hydrate

    The client renders the same tree and attaches event handlers. Output must match the server's HTML exactly.

  5. Shrink the gap

    Ship less JS, hydrate important parts first, and avoid layout shifts while JS loads.

app/orders/page.tsxNext.js App Router
// runs on the server: data + HTML, no client JS for this part
export default async function OrdersPage() {
  const orders = await db.order.findMany({ take: 20, orderBy: { createdAt: "desc" } });
  return (
    <main>
      <h1>Your orders</h1>
      <OrderTable orders={orders} />                 {/* plain HTML from the server */}
      <Suspense fallback={<p>Loading suggestions…</p>}>
        <Suggestions />                               {/* streamed in when ready */}
      </Suspense>
      <ReorderButton lastOrderId={orders[0]?.id} />  {/* "use client": hydrated */}
    </main>
  );
}

// ReorderButton.tsx
"use client";
export function ReorderButton({ lastOrderId }: { lastOrderId?: string }) {
  const [pending, start] = useTransition();
  return <button disabled={pending} onClick={() => start(() => reorder(lastOrderId))}>Reorder</button>;
}

4Gains vs losses nothing is free

What we gain

  • Fast first paint and better LCP.
  • SEO and link previews see real content.
  • Works before JS for reading (and forms, with progressive enhancement).
  • Data fetched close to the database, not over slow mobile networks.

What we lose

  • Server cost and complexity: a Node/edge server per request.
  • Hydration cost: all that JS still runs on the client.
  • The uncanny valley: visible but not yet clickable.
  • Hydration mismatches (dates, random ids, window checks).

6Common pitfalls the usual ways this goes wrong

  • Hydration mismatches

    new Date() or Math.random() renders differently on server and client, and React throws away the HTML. Fix → compute such values once on the server and pass them down, or render them only after mount.

  • SSR with a giant bundle

    Content shows at 1 s but buttons don't work until 6 s. Fix → code splitting, server components, islands for mostly static pages.

  • Accessing window on the server

    window is not defined crashes the render. Fix → browser-only code in effects or client components.

  • Slow data blocks the whole page

    One slow API delays the entire HTML. Fix → stream with Suspense; show the shell first.

7When to use it (and when not)

Use it when…

  • Public pages where SEO, link previews or first paint matter (shops, content, marketing).
  • Users on slow devices and networks.
  • Data that's close to the server (database, internal APIs).
  • You already use a framework that supports it.

Skip it when…

  • Apps behind a login where SEO doesn't matter and users are on fast machines (internal dashboards).
  • Mostly static content: pre-render at build time or use islands instead.
  • You can't run or afford servers (static hosting only).

8Self-check quiz

What does hydration do?

It runs the components in the browser and attaches event handlers and state to the server-rendered HTML instead of rebuilding the DOM.

What causes a hydration mismatch?

The client's first render differs from the server HTML, e.g. using dates, random values or window-only checks during render.

Does SSR reduce the JavaScript users download?

Not by itself; the same components still hydrate. Server components, islands and code splitting reduce it.

What is the “uncanny valley” of SSR?

The time when content is visible but not yet interactive because JS hasn't hydrated.
