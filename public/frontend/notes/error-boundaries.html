Error Boundaries

TL;DR

Wrap regions of the UI in error boundaries: components that catch rendering errors in their children, show a fallback for just that region (with a retry), and report the error. One broken widget no longer turns the whole page white.

  • Family: resilience
  • Mechanism: React error boundaries, Vue onErrorCaptured, Angular ErrorHandler
  • Frameworks: Next.js error.tsx, React Router errorElement
  • Pairs with: code splitting, micro-frontends

1The problem why do we even need this?

In React, an error thrown while rendering unmounts the entire tree by default. The user sees a blank page, even if only one small widget was broken.

  • An API returns null where an array was expected, and the recommendations panel throws.
  • The whole dashboard disappears, including the parts that worked.
  • A lazy chunk fails to download after a deploy, and the app is gone.
  • Nobody knows it happened unless users complain.

2Real-life analogy the theatre understudy

In a theatre, if one actor forgets their lines, the understudy steps in for that scene. The curtain doesn't come down and the audience doesn't go home. The stage manager notes what happened for later.

  • The problem is contained to one scene.
  • The cover is simpler than the original performance: a fallback UI.
  • Only if the whole theatre loses power does the show stop: the app-level boundary.

3How it solves it catch close to the problem

Place boundaries in layers: one at the app root (last resort), one per route, and around risky or optional widgets (third-party embeds, recommendations, charts, lazy chunks).

  1. Add a root boundary

    A friendly full-page error with a reload button, so users never see a white screen.

  2. Add route boundaries

    Frameworks make this easy (error.tsx, errorElement); navigation and layout stay usable.

  3. Wrap risky widgets

    Optional features get small inline fallbacks: “Recommendations unavailable. Retry”.

  4. Offer recovery

    A retry resets the boundary (and refetches data); reset automatically when the route or key changes.

  5. Report every catch

    Send the error and component stack to monitoring (Sentry, Datadog) with release info.

Vocabulary for the exam

Graceful degradation

Event handler errors

Dashboard.tsxreact-error-boundary
function WidgetFallback({ resetErrorBoundary }: FallbackProps) {
  return (
    <div role="alert" className="widget-error">
      <p>Recommendations are unavailable right now.</p>
      <button onClick={resetErrorBoundary}>Try again</button>
    </div>
  );
}

export function Dashboard() {
  const { reset } = useQueryErrorResetBoundary();       // also refetch on retry
  return (
    <main className="dashboard">
      <Orders />
      <Stats />
      <ErrorBoundary FallbackComponent={WidgetFallback} onReset={reset}
                     onError={(error, info) => monitoring.capture(error, { extra: info })}>
        <Recommendations />                               {/* if this throws, only this box changes */}
      </ErrorBoundary>
    </main>
  );
}

4Gains vs losses nothing is free

What we gain

  • No more white screens: failures stay local.
  • Users keep working with the rest of the page.
  • Recovery through retry without a full reload.
  • Visibility: every caught error is reported.

What we lose

  • Doesn't catch everything: event handlers, async code, SSR need their own handling.
  • Can hide bugs if fallbacks aren't monitored.
  • Design work for many fallback states.
  • Too many boundaries clutter the tree.

6Common pitfalls the usual ways this goes wrong

  • Expecting it to catch everything

    An error in an onClick handler or a promise isn't caught, and nothing happens. Fix → try/catch in handlers, error states from data libraries, and a global unhandledrejection reporter.

  • Only one boundary at the root

    Any error still wipes the whole page, just with a nicer message. Fix → add route and widget boundaries.

  • Fallbacks that hide problems

    Errors are caught but never reported, so the widget has been broken for weeks. Fix → report every caught error with release info.

  • No way to recover

    The fallback stays until a full reload. Fix → retry buttons and reset keys tied to route/data changes.

7When to use it (and when not)

Use it when…

  • Every React app (at least a root and route boundaries).
  • Optional or risky widgets: third-party embeds, recommendations, charts.
  • Lazy-loaded chunks and micro-frontends.
  • Dashboards with many independent panels.

Skip it when…

  • Wrapping every tiny component (too fine-grained to be useful).
  • Expected states like “no results” or validation errors: render them normally.
  • Errors you can handle where they happen (handlers, data hooks).

8Self-check quiz

What do error boundaries catch, and what not?

They catch errors during rendering, lifecycle methods and constructors of their children; not errors in event handlers, async code (like setTimeout or promises) or server rendering.

Where should you place boundaries?

At the app root, per route, and around risky or optional widgets.

How does a user recover from a caught error?

A retry button that resets the boundary (and refetches data), or automatic reset when the route or key changes.

Which Vol. 1 pattern is the backend cousin of this?

Bulkhead (and circuit breaker): contain failures so one part can't take down everything.
