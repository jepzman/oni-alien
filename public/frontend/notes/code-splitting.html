Code Splitting & Lazy Loading

TL;DR

Instead of one giant JavaScript bundle, let the bundler split the code into chunks: one per route and per heavy feature. Load the small entry chunk first, and lazy-load the others with dynamic import() when the user needs them (or prefetch them just before).

  • Family: performance / loading
  • Mechanism: dynamic import(), React.lazy, Suspense
  • Bundlers: Vite / Rollup, webpack, esbuild, Turbopack
  • Pairs with: SSR, islands, error boundaries

1The problem why do we even need this?

Bundlers combine your code into files the browser can load. By default you often get one big bundle containing every page and every library.

  • A visitor to the home page downloads the admin panel, the charting library and the rich-text editor.
  • JS is the most expensive byte: it must be downloaded, parsed, compiled and run.
  • One small change invalidates the whole cached bundle, so returning users download it all again.

2Real-life analogy streaming episodes

You don't download a whole TV season before watching episode 1. You stream the episode you're on, the next one preloads while you watch, and the episodes you never watch are never downloaded.

Translating it to software
In real lifeIn your code
The whole seasonThe full application code
Episode 1 nowThe entry chunk for the current route
Next episode preloadingPrefetching the next likely chunk
Episodes you never watchFeatures the user never opens, never downloaded
A short buffering spinnerSuspense fallback while a chunk loads

3How it solves it split by route and by heavy feature

Every dynamic import() tells the bundler “make this a separate chunk”. Frameworks split by route automatically; you add splits for heavy, rarely used features.

  1. Measure first

    Use a bundle analyser to see what's big and who uses it.

  2. Split by route

    Each page gets its own chunk (frameworks do this for you).

  3. Lazy-load heavy features

    Editors, charts, maps, PDF export: React.lazy(() => import("./Editor")) behind a click or when visible.

  4. Show a fallback

    Wrap lazy parts in Suspense with a skeleton; wrap in an error boundary in case the chunk fails to load.

  5. Prefetch likely next steps

    On link hover, on idle, or with <link rel="prefetch">, so the split doesn't add waiting.

Vocabulary for the exam

import() that loads a module on demand.
Lazy loading
Loading something only when it's needed.
Prefetch / preload
Fetch soon-needed / needed-now resources early.

routes.tsxReact + Vite
const AdminPage = lazy(() => import("./pages/AdminPage"));          // own chunk
const RichTextEditor = lazy(() => import("./components/RichTextEditor"));

export function App() {
  return (
    <ErrorBoundary fallback={<p>Couldn't load this part. <a href="">Reload</a></p>}>
      <Suspense fallback={<PageSkeleton />}>
        <Routes>
          <Route path="/" element={<HomePage />} />                  {/* in entry chunk */}
          <Route path="/admin/*" element={<AdminPage />} />          {/* loaded on visit */}
        </Routes>
      </Suspense>
    </ErrorBoundary>
  );
}

// heavy feature behind an interaction, prefetched on hover
function EditButton() {
  const [editing, setEditing] = useState(false);
  return editing
    ? <Suspense fallback={<EditorSkeleton />}><RichTextEditor /></Suspense>
    : <button onMouseEnter={() => import("./components/RichTextEditor")} onClick={() => setEditing(true)}>Edit</button>;
}

tools: Vite / Rollup manualChunks, webpack SplitChunks, Next.js / React Router route splitting, next/dynamic, rollup-plugin-visualizer or webpack-bundle-analyzer, Lighthouse “Reduce unused JavaScript”, loading="lazy" for images and iframes.

4Gains vs losses nothing is free

What we gain

  • Much smaller first load and faster interactivity.
  • Better caching: unchanged chunks stay cached.
  • Pay only for what you use.
  • Heavy libraries isolated from the main path.

What we lose

  • Waiting later: a spinner when a chunk is first needed.
  • More requests and a waterfall if chunks load chunks.
  • Chunk load failures after deploys (old chunk names gone).
  • More moving parts in the build.

6Common pitfalls the usual ways this goes wrong

  • Splitting too small

    Hundreds of tiny chunks cause request overhead and waterfalls. Fix → split at routes and genuinely heavy features.

  • Lazy-loading what's above the fold

    The hero component is lazy, so the main content appears later than before. Fix → keep first-view components in the entry chunk.

  • No error handling for chunk loads

    After a deploy, old tabs request deleted chunks and the app breaks. Fix → error boundary + reload, and keep old assets for a while.

  • Waterfalls

    The route chunk loads, then requests its data, then another chunk. Fix → preload data and chunks in parallel (route loaders, prefetch).

7When to use it (and when not)

Use it when…

  • Bundles over ~200 kB of JS (compressed).
  • Apps with many routes or rarely used heavy features.
  • Users on mobile or slow networks.
  • Admin areas or tools only some users open.

Skip it when…

  • Tiny apps where the whole bundle is small.
  • Code needed on every screen (keep it in the entry).
  • Static content pages (islands or plain HTML ship even less).

8Self-check quiz

What does a dynamic import() tell the bundler?

To put that module (and its dependencies) into a separate chunk that's loaded on demand.

Prefetch vs preload?

Preload fetches a resource needed for the current page right away; prefetch fetches something likely needed soon at low priority.

Why wrap lazy components in an error boundary?

Chunk downloads can fail (network or deploys), and the boundary shows a fallback instead of crashing the app.

Name something you should not lazy-load.

Above-the-fold content or code needed on every screen.
