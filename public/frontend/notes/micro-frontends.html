Micro-Frontends

TL;DR

Split a large frontend into smaller apps owned end-to-end by separate teams (usually by business area: search, product, checkout). Each is built and deployed independently; a thin shell composes them into one experience, sharing layout, routing, auth and the design system.

  • Family: frontend architecture / organisation
  • Coined: ThoughtWorks Tech Radar, 2016
  • Techniques: route-based, module federation, web components, server composition
  • Pairs with: design tokens, API gateway / BFF

1The problem why do we even need this?

Backends were split into services so teams could move independently. Many frontends stayed one big monolith, and became the bottleneck.

  • Five teams merge into one repo and one release train; one team's broken test blocks everyone.
  • Builds take 40 minutes; releases happen every two weeks.
  • Upgrading a framework means coordinating every team at once.
  • Ownership is blurry: who fixes the shared header?

2Real-life analogy the food court

A food court has independent stalls. Each has its own kitchen, menu and staff, and can change its recipes or opening hours without asking the others. They share the building, the seating, the trays and the signs, so customers experience one place.

  • If the taco stall closes for a day, you can still get noodles: isolation.
  • If every stall used different trays and signs, it would feel chaotic: you need a shared design system.
  • Too many tiny stalls and it's hard to find dinner: don't split too fine.

3How it solves it split by business area, compose in a shell

Split vertically by business capability (a team owns checkout from database to button), not horizontally by layer. Then choose how to compose: separate routes/pages (simplest), runtime loading (module federation), web components, or server-side composition.

  1. Split by domain, not by component

    Search, product, checkout, account. Each maps to one team and ideally its own backend services.

  2. Build a thin shell

    Layout, top-level routing, authentication, error handling, and loading the right app.

  3. Share a design system, not code

    Tokens and components as a versioned package so everything looks like one product.

  4. Define small contracts

    URLs, a few documented browser events (cart:updated), and shared auth. No reaching into each other's state.

  5. Deploy independently

    Each app has its own pipeline; the shell discovers versions from a manifest.

shell/routes.tsxroute-based composition (module federation)
// each remote is built and deployed by its own team; the shell only knows the contract
const SearchApp   = lazy(() => import("search/App"));     // remote: search.example.com/remoteEntry.js
const CheckoutApp = lazy(() => import("checkout/App"));   // remote: checkout.example.com/remoteEntry.js

export function Shell() {
  const user = useSession();                               // shared by the shell
  return (
    <DesignSystemProvider theme="brand">
      <Header user={user} />
      <ErrorBoundary fallback={<SectionDown />}>           {/* one app failing doesn't kill the page */}
        <Suspense fallback={<PageSkeleton />}>
          <Routes>
            <Route path="/search/*" element={<SearchApp />} />
            <Route path="/checkout/*" element={<CheckoutApp user={user} />} />
          </Routes>
        </Suspense>
      </ErrorBoundary>
    </DesignSystemProvider>
  );
}

// contract between apps: a documented browser event, not shared state
window.dispatchEvent(new CustomEvent("cart:updated", { detail: { count: 3 } }));

tools: Webpack / Rspack Module Federation, Vite federation plugins, single-spa, Piral, Nx / Turborepo monorepos, web components (Lit), edge/server composition (ESI, Podium); many teams start with simple route-based splitting across separate apps.

4Gains vs losses nothing is free

What we gain

  • Team autonomy: build, test and deploy independently.
  • Faster, smaller releases per area.
  • Isolated failures and incremental upgrades.
  • Clear ownership by business capability.
  • Gradual migration from legacy frontends (strangler fig).

What we lose

  • Inconsistent UX without a strong design system.
  • Duplicate dependencies and bigger bundles.
  • Complex tooling: federation, versioning, shared deps.
  • Harder end-to-end testing and debugging.
  • Overkill for small teams.

6Common pitfalls the usual ways this goes wrong

  • Splitting by component, not domain

    One team owns “buttons”, another “forms”, and every feature needs all of them. Fix → split vertically by business capability.

  • Shared global state between apps

    Apps read each other's Redux stores, so they're coupled again. Fix → communicate via URL, events and backend APIs.

  • No design system

    Five slightly different headers and buttons. Fix → a versioned design system and tokens owned by a platform team.

  • Doing it with two teams

    The tooling costs more than the coordination it saves. Fix → a modular monolith until team count makes it hurt.

  • Five copies of React

    Each app bundles its own framework. Fix → share core dependencies as singletons, or align versions.

7When to use it (and when not)

Use it when…

  • Several teams (roughly 4+) work on one product frontend.
  • Different areas release at different speeds.
  • Migrating a legacy frontend piece by piece.
  • Clear business areas map to teams.

Skip it when…

  • One or two teams: a well-structured monolith is simpler.
  • Performance budgets are tight and can't afford duplication.
  • No capacity to run a shared design system and platform.

8Self-check quiz

Why split micro-frontends by business area rather than by UI layer?

So one team can deliver a whole feature end to end without coordinating with others.

How should micro-frontends communicate?

Through URLs, a few documented browser events, and backend APIs, not by sharing each other's state.

What keeps micro-frontends looking like one product?

A shared, versioned design system with design tokens, plus a shell that owns layout.

When are micro-frontends overkill?

With one or two teams, where tooling cost outweighs the coordination they'd save.
