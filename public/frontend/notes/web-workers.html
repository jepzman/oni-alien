Web Workers

TL;DR

The browser's main thread runs your JavaScript, handles input and draws frames. A long task there (parsing a big file, image processing, crypto, search over thousands of items) freezes the page. A Web Worker runs code on another thread: you send it data with postMessage, it works, it posts the result back. Use it for CPU-heavy work over ~50 ms; transfer large buffers instead of copying them; keep DOM work on the main thread.

  • Family: rendering & performance
  • Kinds: dedicated workers · shared workers · service workers (a different job)
  • Can't touch: the DOM
  • Pairs with: code splitting, debounce & throttle, offline-first sync

1The problem why do we even need this?

An import screen parses a 40 MB CSV and computes column statistics in the browser. It takes 2.8 seconds on the main thread: the spinner stops, taps are ignored, and the browser offers to kill the page.

  • JavaScript, input handling and rendering share one thread. Anything over ~50 ms is noticeable; over a few hundred feels broken.
  • Splitting the work with setTimeout helps a little but makes the code hard to follow.
  • Interaction to Next Paint (INP), a Core Web Vital, gets worse with every long task.

2Real-life analogy the waiter and the kitchen

A waiter keeps talking to guests and taking orders. Baking bread would stop all of that, so it goes to the kitchen, which works out of sight and sends word when the bread is ready. They don't reach into each other's work; they pass orders and plates.

3How it solves it messages between two threads

Create a worker from a separate module. Send it the input; it runs on its own thread with its own event loop and posts messages back. Large binary data (an ArrayBuffer) can be transferred instead of copied, which is instant. Libraries like Comlink make the messaging look like ordinary async function calls.

  1. Find the long task

    Record in the performance panel; look for tasks over 50 ms that are pure computation.

  2. Move it to a worker module

    new Worker(new URL("./parse.worker.ts", import.meta.url), { type: "module" }). Bundlers handle the rest.

  3. Send data, transfer buffers

    Pass the file's ArrayBuffer in the transfer list so it isn't copied.

  4. Report progress, allow cancel

    Post progress messages; terminate the worker (or send a cancel message) if the user leaves.

  5. Keep the DOM on the main thread

    The worker returns data; the main thread renders it.

parse.worker.ts + import.tsVite / any modern bundler
// parse.worker.ts: runs on its own thread
self.onmessage = (e: MessageEvent<ArrayBuffer>) => {
  const text = new TextDecoder().decode(e.data);
  const rows = text.split("\n");
  const stats = computeStats(rows, (pct) => self.postMessage({ type: "progress", pct }));
  self.postMessage({ type: "done", stats });
};

// import.ts: on the main thread
export function parseInWorker(file: File, onProgress: (pct: number) => void) {
  const worker = new Worker(new URL("./parse.worker.ts", import.meta.url), { type: "module" });
  return new Promise<Stats>(async (resolve, reject) => {
    worker.onmessage = (e) => {
      if (e.data.type === "progress") onProgress(e.data.pct);
      else { resolve(e.data.stats); worker.terminate(); }
    };
    worker.onerror = reject;
    const buf = await file.arrayBuffer();
    worker.postMessage(buf, [buf]);       // transfer: no 40 MB copy
  });
}

tools: Web Workers API, Comlink, Vite / webpack worker imports, Partytown (third-party scripts in a worker), OffscreenCanvas (drawing in a worker), WebAssembly in workers for number crunching.

4Gains vs losses nothing is free

What we gain

  • The page stays responsive during heavy work.
  • Better INP and no “unresponsive” warnings.
  • Real parallelism on multi-core devices.
  • Progress and cancel become easy to add.

What we lose

  • No DOM in the worker: results must come back.
  • Copying costs for large non-transferable data.
  • More moving parts: a second file, messages, errors.
  • Start-up cost (tens of ms) for tiny jobs.

6Common pitfalls the usual ways this goes wrong

  • Chatty messages

    The worker posts a message per row, and the main thread drowns in messages. Fix → batch: post progress every few percent and one final result.

  • Copying huge data

    A 40 MB object is cloned into the worker and back, freezing both sides. Fix → transfer ArrayBuffers; send only what the worker needs.

  • A worker for 2 ms of work

    Worker start-up and messaging cost more than the work. Fix → measure first; use a worker for tasks over ~50 ms.

  • Forgetting to clean up

    Each import creates a worker that never ends. Fix → terminate when done, or reuse one long-lived worker.

7When to use it (and when not)

Use it when…

  • Parsing, compressing or encrypting large files in the browser.
  • Image, audio or video processing.
  • Searching or sorting large lists on the client.
  • Any pure computation over ~50 ms that blocks input.

Skip it when…

  • The work is waiting on the network: async/await already frees the thread.
  • The work is mostly DOM changes: optimise rendering instead.
  • The job is tiny or rare.

8Self-check quiz

Why does heavy JavaScript freeze the page?

The main thread runs JavaScript, handles input and renders frames; while it computes, it can't do the other two.

What can't a web worker do?

Touch the DOM; it must send results to the main thread to render.

What does transferring an ArrayBuffer save?

The copy: ownership moves to the worker instantly, instead of cloning the bytes.

Does fetching data need a worker?

No; network waits are already asynchronous and don't block the main thread.

what would you do?Typing in a client-side search box over 20,000 products feels sluggish: each keystroke runs a fuzzy search that takes 120 ms. What do you do?

Debounce the input (200 ms), and move the fuzzy search into a web worker that holds the index, so typing never waits on it. Show results when the worker answers, and ignore answers for an outdated query.

try it

Write a function that does 2 seconds of busy work and call it from a button: try clicking another button while it runs. Move the function into a web worker and post the result back, then try again. Record both runs in the performance panel and compare the long tasks.

remember!!

The main thread is for people. Heavy lifting goes to the kitchen.
