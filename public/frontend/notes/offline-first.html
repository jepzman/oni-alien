Offline-First Sync

TL;DR

For apps used where the network is bad (warehouses, trains, field work), make the local store the source the UI reads and writes: IndexedDB in the browser, SQLite on mobile. Every change goes into an outbox; a sync step pushes it when online, pulls other devices' changes, and resolves conflicts by a rule you chose on purpose. The app never waits for the network, and no work is lost.

  • Family: state & data
  • Local store: IndexedDB · SQLite · OPFS
  • Sync tools: Replicache, PowerSync, ElectricSQL, CouchDB/PouchDB, CRDT libraries
  • Pairs with: optimistic UI, idempotent consumer, service workers

1The problem why do we even need this?

A warehouse worker counts stock in a basement with no signal. Each save spins, then fails; the counts typed so far are lost, and the worker goes back to paper and types it all in again upstairs.

  • Apps that call the server for every read and write stop working the moment the network does.
  • Flaky connections are worse than none: requests time out halfway and users don't know what was saved.
  • Two devices editing the same record offline will disagree when they reconnect.

2Real-life analogy the field notebook

A field worker writes everything in a notebook first, so work never waits for the office. Whenever there's signal, they phone the office, read out the new entries and hear what changed there. If the office has a different note for the same item, they settle it with a rule both sides agreed on.

3How it solves it local store, outbox, sync

The UI never calls the server directly. Writes go to the local store and an outbox in one local transaction. A sync loop runs whenever there's a connection: it sends outbox entries (with ids, so retries are safe), then pulls changes since its last cursor and applies them locally. The server decides the final order and resolves conflicts by the agreed rule.

  1. Choose what works offline

    Which screens and data must work without a network; download that data ahead of time.

  2. Read and write locally

    IndexedDB (via Dexie or a sync library) in the browser, SQLite on mobile. The UI updates instantly.

  3. Queue changes in an outbox

    Each change with a unique id, so sending it twice is harmless.

  4. Sync in both directions

    Push the outbox when online (retry with backoff), then pull changes since the last cursor.

  5. Decide conflicts on purpose

    Per field last writer wins for simple data; counters as increments, not totals; CRDTs for shared documents; show the user when it matters.

Vocabulary for the exam

Offline-first
The app works fully without a network and syncs when it can.
Local store
The on-device database the UI uses (IndexedDB, SQLite).
Outbox
The queue of local changes not yet confirmed by the server.
Sync cursor
A marker of the last server change this device has seen.
Conflict
Two devices changed the same thing differently while apart.
CRDT
A data type that merges concurrent edits without conflicts.
stock-db.tsDexie (IndexedDB) + a small sync loop
import Dexie from "dexie";
const db = new Dexie("stock");
db.version(1).stores({ counts: "sku, updatedAt", outbox: "++seq, id" });

export async function saveCount(sku: string, qty: number) {
  const change = { id: crypto.randomUUID(), sku, qty, at: Date.now() };
  await db.transaction("rw", db.counts, db.outbox, async () => {
    await db.counts.put({ sku, qty, updatedAt: change.at });   // the UI reads this at once
    await db.outbox.add(change);                                // and sync sends this later
  });
}

export async function sync() {
  for (const c of await db.outbox.orderBy("seq").toArray()) {
    const r = await fetch("/api/counts", { method: "POST", body: JSON.stringify(c),
                                          headers: { "Idempotency-Key": c.id } });
    if (!r.ok) return;                                          // try again on the next sync
    await db.outbox.delete(c.seq);
  }
  // then pull: GET /api/counts?since=<cursor> and put each change into db.counts
}
addEventListener("online", sync);

tools: Dexie.js (IndexedDB), SQLite (mobile, or WASM + OPFS in the browser), Replicache, PowerSync, ElectricSQL, RxDB, CouchDB/PouchDB, Automerge and Yjs (CRDTs), Workbox Background Sync.

4Gains vs losses nothing is free

What we gain

  • Always responsive: no spinner for local reads and writes.
  • No lost work on bad connections.
  • Works in the field: basements, trains, planes.
  • Fewer requests: batches instead of one call per action.

What we lose

  • Conflicts must be designed for, not discovered.
  • Two copies of the data: storage limits, schema migrations on the device.
  • Harder to reason about: “saved” means saved locally.
  • Security: data at rest on devices, and access that changes while offline.

6Common pitfalls the usual ways this goes wrong

  • Conflicts discovered in production

    Two devices edit the same stock count offline; one silently wins. Fix → pick a rule per kind of data before building, and store changes as operations (+3) where you can.

  • Unsafe retries

    A sync that times out is sent again and doubles a change. Fix → a unique id per change, and an idempotent server endpoint.

  • “Saved” that isn't

    Users think a change reached the office while it's still in the outbox. Fix → show pending and synced states, and the last sync time.

  • Stale permissions and schema

    A device offline for a week syncs data it may no longer see, in an old shape. Fix → check permissions on the server for every change, and version the local schema.

7When to use it (and when not)

Use it when…

  • Field, warehouse, travel or retail apps with bad connections.
  • Note-taking, forms and documents where losing input is unacceptable.
  • Apps that should feel instant everywhere.

Skip it when…

  • Data that must be live and exact (bank balances, seat booking at checkout).
  • Users are always online on fast connections; optimistic UI is enough.
  • The data is too large or sensitive to keep on devices.

8Self-check quiz

In offline-first, what does the UI read and write?

The local store on the device; the network is only used by sync.

Why does each change need a unique id?

So a change sent twice (after a timeout) can be recognised and applied only once.

Why store a stock change as “+3” instead of “now 15”?

Increments from two devices can both be applied; two totals conflict and one is lost.

When is offline-first a bad fit?

When data must be live and exact, like a checkout or a seat booking, or too sensitive to keep on devices.

what would you do?Two warehouse tablets counted the same shelf while offline: one says 12, the other 15. They sync an hour later and the server keeps whichever arrives last. Users complain counts “jump around”. What do you change?

Make the conflict rule explicit: store each count with who and when, flag simultaneous counts of the same shelf for review instead of silently overwriting, and for adjustments send operations (+3, −2) rather than totals, so they can be merged.

try it

Take a small to-do or notes app. Store items in IndexedDB (with Dexie) and add an outbox table; make the UI read only from IndexedDB. Turn the network off in devtools, add and edit items, then turn it back on and watch the outbox drain. Edit the same item in two tabs while offline and see which rule your sync applies.

remember!!

Write to the notebook first. Phone the office when you can, and agree how to settle clashes.
