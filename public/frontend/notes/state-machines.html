State Machines

TL;DR

Instead of a pile of booleans (isLoading, isError…), describe a UI as a finite set of states (idle, loading, success, failure) and the events allowed in each. The component is always in exactly one state, and transitions not drawn simply can't happen.

  • Family: state modelling
  • Theory: finite-state machines, Harel statecharts (1987)
  • Libraries: XState, Zag, Robot
  • Pairs with: headless components, global store

1The problem why do we even need this?

UI state is often tracked with independent booleans. Four booleans allow 16 combinations, and most of them make no sense. The bugs live in impossible combinations.

  • A spinner and an error message show at the same time.
  • The submit button is clickable while a request is already in flight, so the form is submitted twice.
  • A late response arrives after the user cancelled and overwrites the screen.
  • Nobody can say exactly which states the checkout flow has.

2Real-life analogy the traffic light

A traffic light is red, green or amber: never two at once, never purple. It moves in a fixed order. Pressing the pedestrian button while it's already red does nothing. That's a state machine.

  • Exactly one state at a time: no impossible combinations.
  • Only certain moves are allowed: transitions.
  • Inputs that don't apply right now are ignored, not half-handled.

3How it solves it states, events, transitions

Draw the states and arrows first; the code follows the drawing. A plain useReducer with a status field already gets you most of the way; libraries like XState add nested and parallel states, guards, timers and a visualiser.

  1. List the real states

    Replace booleans with one status: "idle" | "loading" | "success" | "failure".

  2. List the events

    FETCH, RESOLVE, REJECT, RETRY, CANCEL: things that happen, named in the past or imperative.

  3. Define allowed transitions

    For each state, which events move where. Anything else is ignored.

  4. Attach data to states

    Errors only exist in failure; results only in success (a TypeScript discriminated union enforces it).

  5. Render by state

    switch (state.status) renders exactly one view; the button is disabled because the state says so.

Vocabulary for the exam

Finite-state machine
A model with a fixed set of states and transitions.
Statechart
State machines with nesting, parallel regions and history.
Event
Something that happened and may cause a transition.
Guard
A condition that must be true for a transition.
Discriminated union
A TS type where a tag field decides the shape.
Impossible state
A combination of values that should never occur.
useRequest.tsa tiny state machine with useReducer
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: Order[] }
  | { status: "failure"; error: string };
type Event = { type: "FETCH" } | { type: "RESOLVE"; data: Order[] } | { type: "REJECT"; error: string } | { type: "RETRY" };

function machine(state: State, event: Event): State {
  switch (state.status) {
    case "idle":    return event.type === "FETCH" ? { status: "loading" } : state;
    case "loading": return event.type === "RESOLVE" ? { status: "success", data: event.data }
                         : event.type === "REJECT" ? { status: "failure", error: event.error } : state;
    case "failure": return event.type === "RETRY" ? { status: "loading" } : state;
    case "success": return event.type === "FETCH" ? { status: "loading" } : state;
  }
}

// render exactly one view per state
switch (state.status) {
  case "loading": return <Spinner />;
  case "failure": return <ErrorPanel message={state.error} onRetry={() => send({ type: "RETRY" })} />;
  case "success": return <OrderList orders={state.data} />;
  default:        return <button onClick={() => send({ type: "FETCH" })}>Load orders</button>;
}

tools: XState (+ Stately visual editor), Zag.js (state machines behind Ark UI widgets), Robot, @xstate/store; plain TypeScript discriminated unions + useReducer for small cases.

4Gains vs losses nothing is free

What we gain

  • Impossible states can't happen.
  • Every flow is documented as a diagram you can run.
  • Fewer race-condition bugs (late events are ignored).
  • Easy to test: given state + event, expect state.
  • Shared language with designers and product.

What we lose

  • More upfront modelling than a few booleans.
  • Unfamiliar to many teams.
  • Library weight if you use a full statechart engine.
  • Overkill for a simple toggle.

6Common pitfalls the usual ways this goes wrong

  • Booleans next to the machine

    A status field plus an extra isSubmitting flag that drifts out of sync. Fix → derive everything from the one state; no parallel flags.

  • A machine for every toggle

    An accordion open/closed gets a full XState setup. Fix → use a boolean or useReducer for trivial cases.

  • Handling every event in every state

    Defensive code reacts to events that shouldn't be possible, recreating the mess. Fix → let unlisted events be ignored by design.

  • Not drawing it

    The machine exists only in code and nobody can review it. Fix → keep a diagram (or use a visual editor) in the PR.

7When to use it (and when not)

Use it when…

  • Multi-step flows: checkout, onboarding, wizards, uploads.
  • Async UI with loading, error, retry and cancel.
  • Complex widgets (comboboxes, date pickers, drag and drop).
  • Bugs keep appearing in “weird” combinations.

Skip it when…

  • A single toggle or open/closed flag.
  • Static pages with no interaction.
  • A server-state library already models loading/error for you (use its status).

8Self-check quiz

Why are four independent booleans risky?

They allow 2⁴ = 16 combinations, many of which are impossible (like loading and error together) and cause bugs.

What happens to an event not allowed in the current state?

It's ignored; the machine stays in its current state.

How does TypeScript help?

A discriminated union ties data to states (error only exists in failure), so invalid access fails to compile.

What do statecharts add to plain state machines?

Nested (hierarchical) states, parallel regions, history and guards, which keep complex machines manageable.

remember!!

If you can draw it, you can trust it. One state at a time, and only the arrows you drew.
