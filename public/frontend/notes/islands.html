Islands Architecture

TL;DR

Render the page as plain HTML (at build time or on the server) with no JavaScript by default. Mark only the interactive parts as islands; each one loads and hydrates its own small script, independently, often only when it's visible or the browser is idle.

  • Family: rendering strategy
  • Coined by: Katie Sylor-Miller, popularised by Jason Miller (2020)
  • Frameworks: Astro, Fresh, Eleventy + is-land
  • Pairs with: SSR, code splitting, design tokens

1The problem why do we even need this?

Content sites (blogs, docs, marketing, shops' product pages) are mostly static. Yet many are built as single-page apps that ship and hydrate JavaScript for the entire page.

  • An article with one like button ships 400 kB of framework code.
  • Phones spend seconds parsing and running JS for paragraphs that never change.
  • One heavy widget delays interactivity for everything else.

2Real-life analogy the museum room

In a museum, most exhibits are paintings: they hang on the wall and need nothing. A few exhibits are interactive screens, each plugged into its own socket. Nobody runs power cables to the paintings, and if one screen breaks, the rest of the room is fine.

3How it solves it opt in to JavaScript, island by island

The framework renders every component to HTML. Only components you mark get their JS shipped, and you choose when each hydrates.

  1. Default to zero JS

    Every component renders to HTML; nothing hydrates unless asked.

  2. Mark the islands

    <LikeButton client:visible />, <SignupForm client:idle />.

  3. Choose a hydration trigger

    load (now), idle (when the browser is free), visible (scrolled into view), media (on a breakpoint).

  4. Keep islands small and independent

    Pass serialisable props; share state through tiny stores or custom events, not a global app tree.

  5. Mix frameworks if needed

    Islands can even use different UI libraries on one page (sparingly).

Vocabulary for the exam

Island
An interactive component hydrated on its own.
Partial hydration
Hydrating only some components on a page.
Progressive hydration
Hydrating parts over time, by priority.
Client directive
Astro's client:* attribute that controls hydration.
MPA
Multi-page app: each navigation loads a new HTML page.
View transitions
Browser API for smooth animations between pages.

<Layout title={post.title}>
  <article>
    <h1>{post.title}</h1>
    <Fragment set:html={post.html} />          <!-- static: 0 kB JS -->
  </article>

  <LikeButton client:visible postId={post.id} />  <!-- hydrates when scrolled into view -->
  <SignupForm client:idle />                      <!-- hydrates when the browser is idle -->
</Layout>

frameworks: Astro, Fresh (Deno), Eleventy with is-land, Marko, Qwik (resumability, a cousin idea), Enhance; React Server Components share the “ship less JS” goal.

4Gains vs losses nothing is free

What we gain

  • Tiny JS bundles for content pages.
  • Fast load and interaction, even on cheap phones.
  • Independent islands: one slow widget doesn't block others.
  • Great SEO and accessibility from real HTML.
  • Use the right tool per island.

What we lose

  • Sharing state between islands is awkward.
  • Not for app-like UIs where most of the page is interactive.
  • Full page loads on navigation (mitigated with view transitions).
  • Another mental model: what runs where, and when.

6Common pitfalls the usual ways this goes wrong

  • Building an app as islands

    A dashboard with 40 interacting widgets turns into 40 islands passing events around. Fix → use an SPA/SSR framework for app-like UIs.

  • Everything client:load

    Every island hydrates immediately, and you're back to a heavy page. Fix → default to visible or idle; load only above-the-fold essentials.

  • Shared state through globals

    Islands poke each other's DOM or window variables. Fix → a tiny shared store (nanostores) or custom events with clear contracts.

  • Huge island props

    The whole post object is serialised into every island. Fix → pass ids and the few fields the island needs.

7When to use it (and when not)

Use it when…

  • Content-heavy sites: blogs, docs, marketing, product pages.
  • Mostly static pages with a few interactive widgets.
  • Performance on low-end devices matters.
  • Teams that want to mix or migrate UI frameworks.

Skip it when…

  • Highly interactive apps (editors, dashboards, chat).
  • Lots of shared client state across the page.
  • You need SPA-style instant navigations everywhere.

8Self-check quiz

What is an island?

An interactive component on an otherwise static HTML page that loads and hydrates its own JavaScript independently.

What's partial hydration?

Hydrating only the components that need interactivity instead of the whole page.

Name two hydration triggers.

On load, on idle, on visible (in viewport), on media query, or on interaction.

When are islands a poor fit?

App-like UIs where most of the page is interactive and shares state.
