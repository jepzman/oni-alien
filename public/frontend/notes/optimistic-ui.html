Optimistic UI

TL;DR

For actions that almost always succeed (like, star, rename, reorder, send a message), update the UI immediately as if the server said yes. Send the request in the background. If it fails, roll back to the saved snapshot and tell the user, with a way to retry.

  • Family: data mutations / UX
  • Seen in: chat apps, likes, todo lists, Figma, Linear
  • Built into: React useOptimistic, TanStack Query
  • Pairs with: server-state cache, idempotency keys

1The problem why do we even need this?

Network round trips take 100 ms to several seconds. If every tap waits for the server, the app feels sluggish, even though the action almost never fails.

  • A like button shows a spinner for 800 ms before turning red.
  • Users tap again because nothing seemed to happen, sending duplicate requests.
  • Reordering a list snaps back and forth while waiting.
  • On slow mobile networks the whole app feels broken.

2Real-life analogy ordering at a café

You order a flat white, the barista says “coming right up!”, and you go and sit down straight away. You don't stand at the counter until it's made. Almost always the coffee arrives. Very rarely, someone comes over: “sorry, we're out of oat milk, would you like something else?”

3How it solves it update, remember, confirm or undo

The key is keeping a snapshot so you can undo, and making the request safe to retry. Many libraries handle the bookkeeping.

  1. Pick the right actions

    High success rate, low cost of being briefly wrong: likes, toggles, renames, reorder, messages. Not payments.

  2. Snapshot

    Save the current cached value before changing it.

  3. Apply the change locally

    Update the cache/state so the UI shows the new result instantly; mark it pending if useful (a faint “sending…”).

  4. Send the request

    With an idempotency key so retries are safe.

  5. Settle

    On success, reconcile with the server's response (or invalidate). On error, restore the snapshot and show a clear message with retry.

Vocabulary for the exam

Optimistic update
Show the expected result before the server confirms.
Pessimistic update
Wait for the server, then update the UI.
Rollback
Restoring the previous state after a failure.
Reconciliation
Replacing the optimistic value with the server's truth.
Pending state
Visual hint that a change isn't confirmed yet.
Idempotency key
Lets a retried request be recognised as the same one.
useToggleLike.tsTanStack Query optimistic mutation
export function useToggleLike(postId: string) {
  const qc = useQueryClient();
  const key = ["post", postId];
  return useMutation({
    mutationFn: (liked: boolean) =>
      api.put(`/posts/${postId}/like`, { liked }, { headers: { "Idempotency-Key": crypto.randomUUID() } }),
    onMutate: async (liked) => {
      await qc.cancelQueries({ queryKey: key });          // no stale refetch overwrites us
      const before = qc.getQueryData<Post>(key);           // ① snapshot
      qc.setQueryData<Post>(key, (p) => p && { ...p, liked, likes: p.likes + (liked ? 1 : -1) });  // ② show now
      return { before };
    },
    onError: (_err, _liked, ctx) => {
      qc.setQueryData(key, ctx?.before);                   // roll back
      toast.error("Couldn't save your like. Try again?");
    },
    onSettled: () => qc.invalidateQueries({ queryKey: key }),   // reconcile with the server
  });
}

built-in support: React 19 useOptimistic + actions, TanStack Query onMutate/rollback, SWR optimisticData, Apollo optimisticResponse, Remix/React Router fetcher.formData; local-first tools (Replicache, Zero, Automerge) take the idea further.

4Gains vs losses nothing is free

What we gain

  • Feels instant, even on slow networks.
  • Fewer double taps and duplicate requests.
  • Users keep flowing instead of waiting.
  • Perceived performance improves without backend changes.

What we lose

  • Briefly showing something untrue when it fails.
  • Rollback logic and edge cases (concurrent edits).
  • Harder testing: success, failure and race paths.
  • Wrong for risky actions (payments, deletes without undo).

6Common pitfalls the usual ways this goes wrong

  • Optimistic payments or deletes

    The UI says “Paid!” and the card is declined a second later. Fix → only for safe, reversible actions; add undo for deletes instead.

  • Silent rollbacks

    The heart quietly turns grey again and the user never knows why. Fix → explain the failure and offer retry.

  • Refetch overwrites the optimistic value

    A background refetch lands mid-mutation and the like flickers. Fix → cancel in-flight queries before applying the change.

  • Not idempotent

    A retry after a timeout likes the post twice. Fix → idempotency keys or naturally idempotent requests (PUT liked=true).

7When to use it (and when not)

Use it when…

  • Actions that succeed 99%+ of the time.
  • Small, reversible changes: likes, toggles, renames, reorders, messages.
  • Users on slow or mobile networks.
  • Interactions where speed defines the experience (chat, editors, boards).

Skip it when…

  • Payments, bookings, irreversible actions.
  • Actions that often fail validation on the server.
  • Results that depend on server computation the client can't predict.

8Self-check quiz

What's the difference between optimistic and pessimistic updates?

Optimistic updates show the result immediately and roll back on failure; pessimistic updates wait for the server before changing the UI.

What must you save before an optimistic update?

A snapshot of the previous state, so you can roll back if the request fails.

Why cancel in-flight queries first?

So a background refetch that started earlier can't overwrite the optimistic value with old data.

Name an action that should not be optimistic.

A payment (or any irreversible or often-rejected action).
