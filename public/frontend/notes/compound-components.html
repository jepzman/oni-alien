Compound Components

TL;DR

Instead of one component with dozens of props, offer a family of small components that are used together (<Tabs>, <Tabs.List>, <Tabs.Tab>, <Tabs.Panel>). The parent shares state through context, and users compose the children however their design needs.

  • Family: component API design
  • Seen in: Radix, Reach UI, Headless UI
  • Mechanism: React context
  • Pairs with: headless components, design tokens

1The problem why do we even need this?

A shared component starts simple: <Tabs items={...} />. Then the requests arrive, and every one becomes another prop.

  • “A badge on one tab” → badges. “An icon on the right” → iconPosition. “Custom panel markup” → renderPanel.
  • After a year: 25 props, some contradicting each other, and a component nobody dares to change.
  • Users who need something unplanned fork the component or hack around it with CSS.

2Real-life analogy the bento box

A bento box gives you compartments and a lid that covers them all. You decide what goes in each compartment and in what order. The pieces belong together: a compartment on its own isn't much use.

  • The box keeps everything in sync (one lid): shared state.
  • You arrange the contents yourself: composition instead of configuration.
  • HTML already works like this: <select> with <option>, <table> with <tr>.

3How it solves it share state through context, compose in markup

The parent owns the state and puts it in a context. Each child reads only what it needs. Users write normal JSX, so badges, icons and custom markup need no new props.

  1. Create a context

    TabsContext holds activeIndex and setActive, plus ids for ARIA wiring.

  2. Parent provides it

    <Tabs> owns the state (or accepts it as controlled props) and renders the provider.

  3. Children consume it

    Tabs.Tab knows if it's active and how to activate; Tabs.Panel shows itself only when active.

  4. Guard misuse

    Children throw a clear error if rendered outside <Tabs>.

  5. Handle accessibility once

    Roles (tablist, tab, tabpanel), aria-selected, arrow-key navigation live in the family, not in every usage.

Vocabulary for the exam

Composition
Building UI by nesting components instead of configuring one.
Context
React's way to share values with deep children without props.
Controlled
The parent's state is passed in from outside.
Uncontrolled
The component keeps its own state.
Prop explosion
A component with too many configuration props.
Slot
A place in a component where users supply their own content.
Tabs.tsxcompound API with context
const TabsCtx = createContext<{ active: number; setActive: (i: number) => void } | null>(null);
const useTabs = () => {
  const ctx = useContext(TabsCtx);
  if (!ctx) throw new Error("Tabs.* must be used inside <Tabs>");
  return ctx;
};

export function Tabs({ children, defaultIndex = 0 }: { children: ReactNode; defaultIndex?: number }) {
  const [active, setActive] = useState(defaultIndex);
  return <TabsCtx.Provider value={{ active, setActive }}>{children}</TabsCtx.Provider>;
}
Tabs.Tab = function Tab({ index, children }: { index: number; children: ReactNode }) {
  const { active, setActive } = useTabs();
  return <button role="tab" aria-selected={active === index} onClick={() => setActive(index)}>{children}</button>;
};
Tabs.Panel = function Panel({ index, children }: { index: number; children: ReactNode }) {
  return useTabs().active === index ? <div role="tabpanel">{children}</div> : null;
};

// usage: badges and icons need no new props
<Tabs>
  <div role="tablist"><Tabs.Tab index={0}>Overview</Tabs.Tab><Tabs.Tab index={1}>Reviews <Badge>12</Badge></Tabs.Tab></div>
  <Tabs.Panel index={0}><Overview /></Tabs.Panel>
  <Tabs.Panel index={1}><Reviews /></Tabs.Panel>
</Tabs>

4Gains vs losses nothing is free

What we gain

  • Flexible layouts without new props for every request.
  • Readable usage that looks like the UI it creates.
  • Smaller, focused pieces that are easier to maintain.
  • Accessibility handled once inside the family.
  • Fewer forks of shared components.

What we lose

  • More to learn: users must know which pieces exist and how they nest.
  • Context re-renders if the shared value changes often.
  • Easier to misuse (wrong nesting, missing pieces) without guards.
  • Typing and docs take more effort than a single props list.

6Common pitfalls the usual ways this goes wrong

  • No guard outside the parent

    Someone renders Tabs.Panel alone and gets a cryptic “cannot read property of null”. Fix → throw a clear error from the context hook.

  • Index-based wiring everywhere

    Users must keep tab and panel indexes in sync by hand. Fix → register children automatically, or use string values (value="reviews").

  • One huge context value

    Every child re-renders when anything changes. Fix → split contexts or memoise the value.

  • Forgetting ARIA and keyboard

    Tabs look right but arrow keys and screen readers don't work. Fix → follow the WAI-ARIA Authoring Practices pattern or use a headless library.

7When to use it (and when not)

Use it when…

  • Shared design-system components with many layout variations.
  • Components with natural parts: tabs, menus, accordions, selects, dialogs.
  • You keep adding props for one-off layouts.
  • Accessibility wiring between parts is non-trivial.

Skip it when…

  • Simple components with a handful of stable props (a Button).
  • One-off components used in a single place.
  • Users need a quick “just give me tabs from this array” API (offer both).

8Self-check quiz

Which HTML elements already follow this pattern?

select/option, table/tr/td, details/summary, ul/li, dl/dt/dd.

How do children get the shared state?

Through a React context provided by the parent component.

What's the main problem it solves?

Prop explosion: endless configuration props for every layout variation.

Why throw an error when a child is used outside the parent?

So misuse fails loudly with a clear message instead of a confusing null error.

remember!!

Don't add a prop for every wish. Give people the pieces and let them arrange the box.
