Global Store (Flux)

TL;DR

Keep truly shared client state (cart, signed-in user, UI preferences) in one store outside the component tree. Components select the slice they need, and change it only by dispatching named actions handled by pure functions, so every change is predictable and traceable.

  • Family: state management
  • Origin: Flux (Facebook, 2014), Redux (2015)
  • Modern options: Redux Toolkit, Zustand, Pinia, signals
  • Pairs with: server-state cache, state machines

1The problem why do we even need this?

Some state is needed in many places far apart in the tree: the cart count in the header and at checkout, the signed-in user everywhere. Passing it down by hand becomes prop drilling, and keeping copies leads to out-of-sync UIs.

  • Props travel through layers that don't use them, so every refactor touches five files.
  • Two components keep their own copy of “cart”, and the header says 3 while checkout says 2.
  • Anything can change state from anywhere, so bugs are hard to trace: who set this to null?

2Real-life analogy the family calendar on the fridge

A family keeps one calendar on the fridge. Everyone reads it. To change something you don't scribble over it: you leave a note (“add dentist on Tuesday”) and the changes are written in, one at a time.

  • There's one truth, so nobody turns up on the wrong day: single source of truth.
  • The notes are a history of what changed and why: actions + devtools time travel.
  • But not everything belongs on the fridge. Your own homework stays in your room: local state stays local.

3How it solves it one-way data flow

The Flux idea is a one-way loop: views dispatch actions, the store computes new state, views re-render. Modern libraries cut the boilerplate, but the loop is the same.

  1. Decide what's global

    Only state needed by distant components: cart, session, feature flags, theme. Forms, toggles and server data usually aren't.

  2. Model state and actions

    A slice like cart with actions addItem, removeItem, clear.

  3. Write pure reducers

    Given the old state and an action, return the new state. No API calls, no randomness.

  4. Select narrowly

    Components subscribe to the smallest slice they need (s => s.cart.count) so they re-render only when it changes.

  5. Keep side effects at the edges

    API calls live in thunks, listeners or (better) a server-state cache, not in reducers.

Vocabulary for the exam

Store
Object holding the shared state, outside components.
Action
A plain object describing what happened.
Reducer
Pure function: (state, action) → new state.
Selector
Function that picks a slice of state for a component.
Prop drilling
Passing props through components that don't use them.
Time-travel debugging
Replaying actions to step through state changes.
cartSlice.tsRedux Toolkit
const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [] as { id: string; qty: number }[] },
  reducers: {
    addItem(state, action: PayloadAction<string>) {
      const line = state.items.find((i) => i.id === action.payload);
      if (line) line.qty += 1;                 // Immer makes this immutable
      else state.items.push({ id: action.payload, qty: 1 });
    },
    clear(state) { state.items = []; },
  },
});
export const { addItem, clear } = cartSlice.actions;
export const selectCount = (s: RootState) => s.cart.items.reduce((n, i) => n + i.qty, 0);

// anywhere in the tree, no prop drilling
function CartBadge() {
  const count = useSelector(selectCount);       // re-renders only when count changes
  return <span aria-label={`${count} items in cart`}>{count}</span>;
}

options: Redux Toolkit (+ DevTools), Zustand, Jotai, MobX, NgRx (Angular), Pinia (Vue), signals (Preact, Solid, Angular). For many apps, React context + useReducer is enough.

4Gains vs losses nothing is free

What we gain

  • One source of truth for shared state.
  • No prop drilling for distant components.
  • Predictable changes: every update is a named action.
  • Great debugging: action logs, time travel, state snapshots.
  • Reducers are trivial to test: pure functions.

What we lose

  • Boilerplate and indirection (less with modern tools).
  • Everything drifts into the store, even local state.
  • Performance traps with broad selectors.
  • A poor fit for server data (caching, refetching) without extra tools.

6Common pitfalls the usual ways this goes wrong

  • Putting everything in the store

    Form inputs, hover flags and modals all live globally; every keystroke dispatches an action. Fix → keep local state local; globalise only what's shared.

  • Caching server data by hand

    You write loading/error/refetch logic for every API call in reducers. Fix → use a server-state cache for API data (note 06).

  • Broad selectors

    useSelector(s => s) re-renders the component on every change. Fix → select the smallest slice; memoise derived data.

  • Side effects in reducers

    A reducer calls the API or generates ids, so replays and tests break. Fix → keep reducers pure; effects in thunks/listeners.

7When to use it (and when not)

Use it when…

  • State used by many distant components (session, cart, preferences, flags).
  • Complex client-side state with many ways to change it.
  • You need traceable, debuggable changes.
  • Several teams touch the same shared state.

Skip it when…

  • Small apps where context + useReducer is enough.
  • State that's only used by one component or one subtree.
  • Data that really belongs to the server (use a server-state cache).

8Self-check quiz

What is the one-way data flow in Flux?

View dispatches an action → the store/reducer computes new state → views that selected that state re-render.

Why must reducers be pure?

So the same state and action always give the same result, which makes testing, replay and time-travel debugging possible.

Should API data live in the global store?

Usually not. A server-state cache handles fetching, caching, deduping and refetching better.

How do you avoid needless re-renders with a store?

Select the smallest slice a component needs and memoise derived values.
