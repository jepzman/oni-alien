Custom Hooks

TL;DR

When several components need the same stateful logic (debounced search, media queries, form handling, online status), move it into a function whose name starts with use. Each component that calls the hook gets its own state, and the logic is written, fixed and tested once.

  • Family: logic reuse
  • Replaced: mixins, HOCs, render props
  • Framework: React (Vue: composables)
  • Pairs with: container/presentational, headless components

1The problem why do we even need this?

Components often need the same behaviour, not the same markup. Without a way to share it, logic gets copy-pasted, and the copies drift apart.

  • Three search inputs each implement debounce, fetch and cleanup slightly differently.
  • A bug fixed in one copy (cancelling stale requests) stays in the other two.
  • Older sharing tools had costs: mixins clashed, higher-order components and render props created deep “wrapper hell”.

2Real-life analogy one recipe card, many dishes

A good tomato-sauce recipe card can be used for pasta and for pizza. Each cook follows the same steps but makes their own pot; nobody shares a pot by accident. Improve the recipe once and every dish gets better.

3How it solves it extract, name, reuse

A custom hook is just a function that calls other hooks. It returns values and callbacks, never markup. Calls are independent: two components using it don't share state unless the hook reads a shared store.

  1. Spot repeated stateful logic

    The same useState + useEffect combination in more than one component.

  2. Extract to a use-function

    Move state, effects and handlers into useSomething(); return what callers need.

  3. Design a small API

    Return an object ({ query, setQuery, results, isLoading }) or a tuple for two values.

  4. Clean up properly

    Clear timers, abort requests and remove listeners in effect cleanups, once, inside the hook.

  5. Test the hook alone

    Use renderHook to test behaviour without any markup.

useDebouncedSearch.tsone hook, many search boxes
export function useDebouncedSearch<T>(search: (q: string, s: AbortSignal) => Promise<T[]>, delayMs = 250) {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState<T[]>([]);
  const [isLoading, setLoading] = useState(false);

  useEffect(() => {
    if (!query) { setResults([]); return; }
    const ctrl = new AbortController();
    const timer = setTimeout(async () => {
      setLoading(true);
      try { setResults(await search(query, ctrl.signal)); }
      catch (e) { if ((e as Error).name !== "AbortError") throw e; }
      finally { setLoading(false); }
    }, delayMs);
    return () => { clearTimeout(timer); ctrl.abort(); };   // cleanup, written once
  }, [query, search, delayMs]);

  return { query, setQuery, results, isLoading };
}

// any component: its own state, shared behaviour
const { query, setQuery, results } = useDebouncedSearch(searchUsers);

4Gains vs losses nothing is free

What we gain

  • Logic written and fixed once.
  • Components stay small and focused on markup.
  • Testable without UI via renderHook.
  • No wrapper hell compared with HOCs and render props.
  • Composable: hooks can use other hooks.

What we lose

  • Hidden complexity behind a friendly name.
  • Rules of hooks to learn (no conditional calls).
  • Dependency arrays are easy to get wrong.
  • Over-abstraction: hooks for logic used only once.

6Common pitfalls the usual ways this goes wrong

  • Assuming hooks share state

    Two components call useCart() and expect the same cart, but each gets its own. Fix → put shared state in context or a store and read it from the hook.

  • Missing cleanup

    Timers fire after unmount and set state on a gone component; old requests overwrite new results. Fix → clear timers and abort requests in the effect's cleanup.

  • Wrong dependency arrays

    The effect uses a stale value or loops forever. Fix → follow the exhaustive-deps lint rule; memoise callbacks.

  • A hook for everything

    useButtonColor() wraps one line of logic. Fix → extract when logic is reused or complex enough to test.

7When to use it (and when not)

Use it when…

  • The same stateful logic appears in two or more components.
  • Logic is complex enough to deserve its own tests.
  • You're replacing HOCs or render props.
  • Wrapping a browser API (resize, media queries, online status, storage).

Skip it when…

  • Pure calculations: a plain function is simpler.
  • Logic used once and easy to read in place.
  • State that must be shared between components (use context or a store).

8Self-check quiz

Two components call the same custom hook. Do they share state?

No. Each call has its own state, unless the hook reads from a shared store or context.

Why must hooks be called at the top level?

React tracks hooks by call order; calling them conditionally would change the order between renders.

What did custom hooks replace?

Mixins, higher-order components and render props for sharing stateful logic.

How do you test a hook without a component?

With a helper like renderHook from Testing Library.

remember!!

Share the recipe, not the pot. A hook is logic with a name, and every caller cooks their own state.
