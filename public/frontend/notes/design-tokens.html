Design Tokens

TL;DR

Store every design decision (colours, spacing, type sizes, radii, shadows, motion) as named tokens in one source, like color.action.primary or space.4. Components use the names, never raw values. A build step outputs them for every platform, and themes (dark mode, brands) are just different values for the same names.

  • Family: design systems
  • Origin: Salesforce Lightning (2014)
  • Standard: W3C Design Tokens format (DTCG)
  • Pairs with: headless components, micro-frontends

1The problem why do we even need this?

Without tokens, design decisions are copied as raw values everywhere: hex colours, pixel sizes, font stacks.

  • A codebase ends up with 47 slightly different blues and 12 grey borders.
  • A rebrand means find-and-replace across hundreds of files on web, iOS and Android.
  • Dark mode or a second brand is almost impossible to add.
  • Designers and developers talk past each other: “the blue” vs #1E4FB4.

2Real-life analogy the paint swatches

A paint shop names its colours: Ocean 500, Sand 100. Paint every room by name, never by mixing your own. Want a fresh look? Change what Ocean 500 means, and every room using it follows.

  • Everyone (designer, decorator, owner) uses the same words.
  • A “night” palette can map the same names to darker paints: themes.
  • The rule “accent walls use Coral 400” is a semantic decision built on a raw swatch.

3How it solves it three tiers, one source, many outputs

Most systems use three tiers: primitives (the raw palette), semantic tokens (meaning and theme), and optional component tokens. Components only ever reference semantic or component tokens.

  1. Collect the decisions

    Audit colours, spacing, type, radii, shadows, motion durations; merge near-duplicates.

  2. Define primitives

    The raw scale: blue.50 … blue.900, space.1 … space.12.

  3. Add semantic names

    color.text.default, color.surface.raised, color.action.primary: say what it's for, not what it looks like.

  4. Generate per platform and theme

    Style Dictionary (or similar) turns one JSON source into CSS variables, Swift, Kotlin and Figma variables, per theme.

  5. Enforce usage

    Lint rules forbid raw hex/px in components; contrast checks run on token pairs.

Vocabulary for the exam

Design token
A named design decision with a value.
Primitive token
Raw value in a scale (blue-600, space-4).
Semantic token
Purpose-based alias (action-primary).
Theme
A set of values for the same semantic names.
Style Dictionary
Tool that builds tokens for many platforms.
DTCG format
The W3C community group's JSON format for tokens.
tokens.json → tokens.cssDTCG-style JSON and generated CSS
{
  "blue":  { "300": { "$value": "#8EB5FF" }, "600": { "$value": "#1D4EB5" } },
  "color": {
    "action": { "primary": { "$value": "{blue.600}" } },
    "text":   { "default": { "$value": "#272B33" } }
  },
  "space": { "2": { "$value": "8px" }, "4": { "$value": "16px" } }
}

/* generated */
:root {
  --color-action-primary: #1D4EB5;
  --space-4: 16px;
}
[data-theme="dark"] {
  --color-action-primary: #8EB5FF;      /* same name, dark value */
}

/* components: names only, never raw values */
.button { background: var(--color-action-primary); padding: var(--space-2) var(--space-4); }

tools: Style Dictionary, Tokens Studio for Figma, Figma Variables, Theo, Terrazzo (DTCG), Tailwind theme config, Panda CSS / vanilla-extract themes; Stylelint rules to ban raw colour values.

4Gains vs losses nothing is free

What we gain

  • One change updates everything: rebrands in hours.
  • Themes and dark mode become value swaps.
  • Consistency across web, iOS, Android and Figma.
  • Shared vocabulary between design and code.
  • Accessible contrast checked once, at the token level.

What we lose

  • Upfront audit and naming work.
  • Naming is hard: too many tokens or vague names.
  • Build tooling to maintain.
  • Governance: someone must own and review changes.

6Common pitfalls the usual ways this goes wrong

  • Naming by looks

    color-blue used for buttons, so the rebrand to green leaves a token called blue that's green. Fix → semantic names by purpose (action-primary).

  • Components using primitives

    Buttons reference blue-600 directly, so dark mode can't remap them. Fix → components use semantic tokens only.

  • Token explosion

    3,000 tokens, many used once, so nobody can find the right one. Fix → start small; add tokens when a decision repeats.

  • Raw values sneaking back

    A quick fix hard-codes #333 and it spreads. Fix → lint for raw colours and sizes in CI.

7When to use it (and when not)

Use it when…

  • More than one product, platform, brand or theme.
  • Dark mode or high-contrast themes are needed.
  • A design system is shared by several teams.
  • Designers and developers keep drifting apart.

Skip it when…

  • A small one-off site with a handful of styles (plain CSS variables are enough).
  • Prototypes where the design isn't settled yet (add tokens when it stabilises).

8Self-check quiz

Primitive vs semantic token?

A primitive holds a raw value in a scale (blue-600); a semantic token names its purpose (color-action-primary) and points to a primitive.

Why should components avoid primitive tokens?

Themes remap semantic tokens; components using primitives can't change with the theme.

How does dark mode work with tokens?

The dark theme assigns different values to the same semantic token names.

What tool turns one token file into CSS, iOS and Android outputs?

Style Dictionary (or similar tools like Terrazzo / Theo).
