List Virtualization

TL;DR

When a list or table has thousands of items, render only the rows that are visible (plus a few extra above and below). A spacer element keeps the full scroll height, and as the user scrolls, rows are recycled to show the new items. 100,000 items, ~30 DOM rows.

  • Family: rendering performance
  • Libraries: TanStack Virtual, react-window, Virtuoso
  • CSS cousin: content-visibility: auto
  • Pairs with: server-state cache (infinite queries), debounce

1The problem why do we even need this?

Browsers are fast, but not at hundreds of thousands of DOM nodes. Logs, transactions, chat history, spreadsheets and product grids easily get there.

  • Rendering 100,000 rows × 6 cells creates 600,000 elements: seconds of rendering and huge memory.
  • Scrolling stutters because layout and paint have so much to do.
  • Every state update re-renders the whole list.

2Real-life analogy the train window

A train route is 500 km long, but through the window you only ever see a few hundred metres. Nobody builds the whole landscape in front of you; the view simply changes as you move. The timetable still tells you how long the whole journey is, like the scrollbar.

3How it solves it render the window, fake the rest

The virtualizer knows the scroll position and each row's size (fixed or measured), so it can calculate which items are visible and where to place them.

  1. Give the list a scroll container

    A fixed-height element with overflow: auto.

  2. Add a spacer

    An inner element with the total height (count × row height) so the scrollbar is correct.

  3. Compute the visible range

    From scrollTop and row sizes, find the first and last visible index, plus overscan.

  4. Render only those rows

    Absolutely position them (or translate them) at their offsets.

  5. Handle variable sizes and a11y

    Measure rows that vary; keep keyboard navigation and set aria-rowcount/aria-rowindex so screen readers know the real size.

Vocabulary for the exam

Virtualization / windowing
Rendering only the visible part of a long list.
Overscan
Extra rows rendered beyond the viewport to avoid blank flashes.
Spacer
Element that holds the full scroll height.
Dynamic measurement
Measuring rows whose height varies.
Infinite scroll
Loading more data as the user nears the end.
content-visibility
CSS that lets the browser skip rendering off-screen content.
TransactionList.tsxTanStack Virtual
export function TransactionList({ rows }: { rows: Transaction[] }) {
  const scrollRef = useRef<HTMLDivElement>(null);
  const v = useVirtualizer({
    count: rows.length,                         // 100,000
    getScrollElement: () => scrollRef.current,
    estimateSize: () => 40,                     // px per row
    overscan: 5,
  });

  return (
    <div ref={scrollRef} role="table" aria-rowcount={rows.length} style={{ height: 600, overflow: "auto" }}>
      <div style={{ height: v.getTotalSize(), position: "relative" }}>   {/* spacer */}
        {v.getVirtualItems().map((item) => (
          <div key={item.key} role="row" aria-rowindex={item.index + 1}
               style={{ position: "absolute", top: 0, width: "100%", transform: `translateY(${item.start}px)` }}>
            <TransactionRow tx={rows[item.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}

libraries: TanStack Virtual, react-window / react-virtualized, React Virtuoso, vue-virtual-scroller, Angular CDK virtual scroll, AG Grid / MUI DataGrid (built in); CSS content-visibility: auto for simpler long pages.

4Gains vs losses nothing is free

What we gain

  • Constant render cost no matter how many items.
  • Smooth scrolling and low memory.
  • Fast first render of huge lists.
  • Cheap updates: only visible rows re-render.

What we lose

  • Find in page (Ctrl+F) misses off-screen rows.
  • Accessibility work: row counts, focus and keyboard need care.
  • Variable row heights make scrolling jumpy if estimated badly.
  • More complex code than a plain map().

6Common pitfalls the usual ways this goes wrong

  • Virtualizing short lists

    A list of 50 items gets windowing and loses Ctrl+F for nothing. Fix → virtualize only when lists are long (hundreds+) or rows are heavy.

  • Losing focus on scroll

    The focused row is recycled away and keyboard users lose their place. Fix → keep the focused row rendered; manage focus by index.

  • Bad size estimates

    Rows are 120 px but estimated at 40 px, so the scrollbar jumps. Fix → measure rows dynamically or estimate realistically.

  • Breaking screen readers

    Assistive tech thinks the table has 30 rows. Fix → aria-rowcount and aria-rowindex, or use a grid library that handles it.

7When to use it (and when not)

Use it when…

  • Lists or tables with hundreds to millions of rows.
  • Chat history, logs, transaction tables, spreadsheets.
  • Heavy rows (images, many cells) that make even 200 rows slow.
  • Infinite scroll feeds.

Skip it when…

  • Short lists where rendering everything is fast.
  • Content that must be fully searchable with Ctrl+F or printable.
  • Pagination is the better UX anyway (search results).

Related patterns

  • Server-state cache (infinite queries)
  • Code splitting
  • Custom hooks
  • Headless components (TanStack Table)

8Self-check quiz

What does the spacer element do?

It has the full height of all rows so the scrollbar size and position reflect the whole list.

What is overscan?

Extra rows rendered just outside the viewport so fast scrolling doesn't show blank gaps.

Name an accessibility concern with virtualization.

Screen readers only see rendered rows; use aria-rowcount/rowindex and keep focus stable.

What CSS property offers a lighter alternative for long pages?

content-visibility: auto, which lets the browser skip rendering off-screen sections.
