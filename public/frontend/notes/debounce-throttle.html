Debounce & Throttle

TL;DR

Some events fire far more often than you need to react: keystrokes, scroll, resize, mouse moves. Debounce runs the handler once, after the events stop for a moment (search-as-you-type, autosave). Throttle runs it at most once per interval while events keep coming (scroll position, drag, infinite scroll). Cancel the work that a newer event made obsolete, and clean up timers when the component goes away.

  • Family: rendering & performance
  • Debounce for: search, autosave, validation, resize end
  • Throttle for: scroll, drag, pointer move, analytics
  • Pairs with: custom hooks, server-state cache, rate limiter

1The problem why do we even need this?

A search box calls the API on every keystroke. Typing “running shoes” sends 13 requests; the answers come back out of order and the results flicker. On the same page a scroll handler runs 120 times a second, measuring the layout each time, and scrolling stutters.

  • Each event triggers expensive work (a request, a layout read, a re-render) the user never sees.
  • The server takes many times the load the feature needs.
  • Slow handlers on high-frequency events block the main thread and make the page feel broken.

2Real-life analogy the lift and the tram

A lift door waits until nobody has stepped in for a few seconds, then closes: every new person restarts the wait. That's debounce. A tram leaves the stop at most every five minutes, however many people arrive: that's throttle. Both serve everyone, without moving for every single person.

3How it solves it two timers, two shapes

Debounce keeps one timer and restarts it on every event; when it finally fires, it runs once with the latest value. Throttle runs at the first event, then ignores events until the interval passes, usually running once more at the end so the last value isn't lost. Neither one stops an old request that's already on its way, so cancel those with an AbortController.

  1. Pick the shape

    React to the final value? Debounce. Need steady updates while it happens? Throttle.

  2. Pick the time

    Debounce search at 200–300 ms, autosave at 1–2 s; throttle scroll and drag at 50–100 ms (or once per animation frame).

  3. Use the latest value

    The handler reads the newest input when it fires, not the one from the first event.

  4. Cancel stale work

    Abort the previous request when a new one starts, so an old answer can't overwrite a newer one.

  5. Clean up

    Cancel pending timers when the component unmounts; flush pending saves before navigating away.

Vocabulary for the exam

Debounce
Run once after events stop for a set time.
Throttle
Run at most once per interval while events continue.
Leading / trailing edge
Run at the start of a burst, at the end, or both.
requestAnimationFrame
Run once per screen frame: the natural throttle for visual work.
AbortController
Cancels a fetch that is no longer needed.
Passive listener
A scroll or touch listener that promises not to block scrolling.
useDebouncedSearch.tsReact + TypeScript
import { useEffect, useState } from "react";

export function useDebouncedValue<T>(value: T, ms = 250) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), ms);   // restart on every change
    return () => clearTimeout(t);                           // and on unmount
  }, [value, ms]);
  return debounced;
}

export function useSearch(query: string) {
  const q = useDebouncedValue(query.trim(), 250);
  const [results, setResults] = useState<Product[]>([]);
  useEffect(() => {
    if (!q) return setResults([]);
    const ctrl = new AbortController();                     // cancel the previous request
    fetch(`/api/search?q=${encodeURIComponent(q)}`, { signal: ctrl.signal })
      .then((r) => r.json()).then(setResults).catch(() => {});
    return () => ctrl.abort();
  }, [q]);
  return results;
}

4Gains vs losses nothing is free

What we gain

  • Far fewer requests and re-renders.
  • Smoother scrolling and typing.
  • Calmer results: no flicker from out-of-order answers (with cancellation).
  • Less server load for the same feature.

What we lose

  • A small delay before the reaction.
  • Timers to manage: stale closures, cleanup on unmount.
  • Harder tests: need fake timers.
  • Wrong choice hurts: debounced scroll feels dead; throttled search wastes calls.

6Common pitfalls the usual ways this goes wrong

  • Debouncing scroll feedback

    A sticky header only updates after scrolling stops, and looks broken. Fix → throttle (or requestAnimationFrame) for anything that should follow the finger.

  • A new debounce on every render

    debounce(fn) inside a component creates a fresh timer each render, so nothing is ever debounced. Fix → create it once (useMemo / useRef) or debounce the value, as in the hook above.

  • Old answers win

    Debouncing fewer requests doesn't stop an old one landing after a newer one. Fix → abort the previous request, or ignore answers for an old query.

  • Losing the last value

    A leading-only throttle drops the final scroll position or the last keystroke. Fix → use trailing (or both) edges for anything that saves or shows the final state.

7When to use it (and when not)

Use it when…

  • Search-as-you-type, filters and validation while typing.
  • Autosave of forms and documents.
  • Scroll, resize, drag and pointer-move handlers.
  • Analytics events that fire continuously.

Skip it when…

  • Discrete actions like a submit or a click (use a disabled state or idempotency instead).
  • Visibility checks: IntersectionObserver does it without scroll handlers.
  • The work is already cheap and synchronous.

Related patterns

  • Custom hooks
  • Server-state cache
  • Web workers
  • Rate limiter (Vol. 1)

8Self-check quiz

Debounce or throttle for search-as-you-type?

Debounce: you want one request after the user pauses, with the final text.

Debounce or throttle for updating a progress bar while scrolling?

Throttle (or requestAnimationFrame): it must keep updating while the scroll continues.

Why doesn't debouncing alone fix out-of-order search results?

An earlier request can still finish after a later one; cancel it or ignore old answers.

Why can calling debounce(fn) inside a React component fail?

A new debounced function is created on every render, so each event gets its own timer.

what would you do?An autosave debounced at 2 seconds loses the user's last edit when they close the tab right after typing. What do you change?

Flush the pending save when the page is hidden or the user navigates away (visibilitychange / pagehide, sendBeacon or keepalive fetch), and show “saving…” while a save is pending, so a debounced save is never silently dropped.

try it

Add a counter to a search box's input handler and type a few words: count the calls. Debounce it at 250 ms and count again. Then throttle a scroll handler that logs scrollY to 100 ms, compare the number of calls in the console, and check scrolling in the performance panel before and after.

remember!!

Debounce waits for the pause. Throttle keeps a steady beat.
