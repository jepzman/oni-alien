Headless Components

TL;DR

A headless component (or hook) provides state, keyboard handling and ARIA for a tricky widget (combobox, menu, dialog, table) but no markup or styles. You render your own elements, spread the props it gives you, and style them with your design system.

  • Family: component design / design systems
  • Examples: Radix, React Aria, Headless UI, TanStack Table
  • Mechanism: hooks + prop getters
  • Pairs with: compound components, design tokens

1The problem why do we even need this?

Widgets like comboboxes, menus, date pickers and dialogs are hard to build accessibly: focus management, keyboard shortcuts, ARIA roles, typeahead, screen-reader announcements.

  • Styled libraries solve the hard parts but bring their own look, so you fight them with overrides.
  • Hand-built widgets match the brand but usually miss keyboard support and ARIA, failing users and audits.
  • Each team re-solves the same accessibility bugs in its own dropdown.

2Real-life analogy the car chassis

Car makers often share one chassis across several models: the engine, steering, brakes and crash structure are engineered and safety-tested once. Each model gets its own body and paint on top.

  • You don't re-engineer brakes for every new car: the risky, hard part is done properly once.
  • The bodies can look completely different: a family car and a sports car on one platform.

3How it solves it behaviour in, markup out (yours)

Headless libraries usually expose prop getters: functions that return the props an element needs (roles, ids, aria attributes, event handlers). You call them on your own elements, merging in your own props.

  1. Pick the hard widget

    Combobox, menu, listbox, dialog, tabs, date picker, data table.

  2. Use a headless primitive

    A hook (useCombobox) or unstyled components (Radix, React Aria Components).

  3. Render your own elements

    Use your design-system components and tokens for every visual detail.

  4. Spread the prop getters

    <input {...getInputProps()} /> wires ARIA, ids and keyboard handlers.

  5. Test like a user

    Keyboard-only walkthrough and a screen-reader check; let the library own the hard cases.

FruitPicker.tsxDownshift-style combobox
export function FruitPicker({ items }: { items: string[] }) {
  const [input, setInput] = useState("");
  const shown = items.filter((i) => i.toLowerCase().includes(input.toLowerCase()));
  const { isOpen, highlightedIndex, getLabelProps, getInputProps, getMenuProps, getItemProps } =
    useCombobox({ items: shown, onInputValueChange: ({ inputValue }) => setInput(inputValue ?? "") });

  return (
    <div className="field">
      <label {...getLabelProps()}>Fruit</label>
      <input {...getInputProps()} className="input" />           {/* ARIA + keys wired */}
      <ul {...getMenuProps()} className="menu" hidden={!isOpen}>
        {shown.map((item, index) => (
          <li key={item} {...getItemProps({ item, index })}
              className={index === highlightedIndex ? "option is-active" : "option"}>
            {item}
          </li>
        ))}
      </ul>
    </div>
  );
}

headless libraries: Radix UI primitives, React Aria (Adobe), Headless UI (Tailwind Labs), Ark UI / Zag (state machines), Downshift, TanStack Table and TanStack Form, Floating UI for positioning.

4Gains vs losses nothing is free

What we gain

  • Accessibility done right by specialists, once.
  • Total control of looks; fits any design system.
  • Smaller CSS: no library styles to override.
  • Reusable across brands and products.
  • Upgrades don't break your styles.

What we lose

  • You write all the markup and styles, so more upfront work.
  • Easy to undo the a11y by not spreading props or changing elements.
  • More concepts: prop getters, controlled state, render order.
  • A dependency for core interactions.

6Common pitfalls the usual ways this goes wrong

  • Not spreading every getter

    The input gets its props but the list items don't, so screen readers can't read the options. Fix → spread every prop getter on the element it's meant for.

  • Swapping elements

    Replacing a button with a div breaks keyboard support the library assumed. Fix → keep the element types the docs expect, or pass as props correctly.

  • Overriding handlers

    Your onKeyDown replaces the library's, so arrow keys stop working. Fix → pass your handlers through the getter so they're merged.

  • Skipping the visual focus state

    Keyboard users can't see which option is active. Fix → style the highlighted/focused state clearly.

7When to use it (and when not)

Use it when…

  • Building a design system or a branded component library.
  • Complex widgets: combobox, menu, dialog, tabs, date picker, data grid.
  • Several products or brands share behaviour but not looks.
  • Accessibility is a requirement (it should be).

Skip it when…

  • A styled library already matches your design closely.
  • Simple elements where native HTML is enough (button, details, select).
  • Prototypes where speed matters more than polish (temporarily).

Related patterns

  • Compound components
  • Custom hooks
  • Design tokens
  • State machines (Zag, XState under the hood)

8Self-check quiz

What does a headless component give you, and what doesn't it?

It gives state, behaviour, keyboard handling and ARIA; it doesn't give markup or styles.

What is a prop getter?

A function (like getInputProps) that returns the props an element needs, which you spread onto your own element.

Why not just build the dropdown yourself?

Accessible widgets have many edge cases (focus, keys, ARIA, screen readers) that are easy to get wrong and costly to maintain.

When is native HTML better than a headless library?

For simple controls like button, select, details/summary or dialog where the native element already behaves accessibly.
