Container & Presentational

TL;DR

Split UI code into containers that fetch data, hold state and decide what happens, and presentational components that only receive props and render markup. The looks become reusable and easy to test; the logic lives in one obvious place.

  • Family: component design
  • Popularised by: Dan Abramov, 2015
  • Modern form: hooks + server components
  • Pairs with: custom hooks, design tokens

1The problem why do we even need this?

Components tend to grow. A page component starts small, then gains fetching, loading flags, error handling, filters, analytics and all the markup. Soon it's 600 lines that do everything.

  • The search page needs the same product card, but it's tangled up with the product page's fetching.
  • Testing the card means mocking the network, the router and the analytics client.
  • Designers can't preview states (empty, loading, error) in Storybook without a running backend.
  • Every change risks breaking both the logic and the layout.

2Real-life analogy the kitchen and the plate

In a restaurant the kitchen buys ingredients, cooks, and decides what goes out. The plate just presents what it's handed. It doesn't know where the fish came from.

  • The same plate design works for any dish: reuse.
  • You can photograph a plate with plastic food for the menu: Storybook with fake data.
  • Changing suppliers changes the kitchen, not the plates.

3How it solves it split the deciding from the drawing

Ask of every component: does it know where data comes from? If yes, it's a container. If it only uses its props, it's presentational. Today the “container” is often a custom hook or a server component rather than a class.

  1. Find the pure UI

    Pull out the markup that only needs data and callbacks: cards, lists, forms, empty and error states.

  2. Give it a props interface

    items, isLoading, onAddToCart. No fetch, no global store, no router inside.

  3. Keep logic in the container

    The container (or a custom hook it uses) fetches, transforms, and passes plain props down.

  4. Story every state

    Write Storybook stories for loading, empty, error and long-content states using fake props.

  5. Don't overdo it

    Small components that are used once don't need splitting. Split when reuse or testing hurts.

Vocabulary for the exam

Container
Knows how things work: data, state, side effects.
Presentational
Knows how things look: renders props.
Props interface
The typed inputs a component accepts.
Pure component
Same props in → same output, no side effects.
Storybook
A workshop for rendering components in isolation.
Server component
Runs on the server, can fetch data, sends rendered UI.
ProductList.tsxReact + TypeScript
// presentational: props in, markup out
type Props = { items: Product[]; isLoading: boolean; onAdd: (id: string) => void };

export function ProductList({ items, isLoading, onAdd }: Props) {
  if (isLoading) return <Skeleton rows={6} />;
  if (items.length === 0) return <EmptyState title="No products yet" />;
  return (
    <ul className="grid">
      {items.map((p) => (
        <li key={p.id}><ProductCard product={p} onAdd={() => onAdd(p.id)} /></li>
      ))}
    </ul>
  );
}

// container: data and decisions
export function ProductListContainer({ category }: { category: string }) {
  const { data = [], isLoading } = useProducts(category);   // custom hook
  const addToCart = useAddToCart();
  return <ProductList items={data} isLoading={isLoading} onAdd={addToCart} />;
}

where you see it today: hooks as the “container” part, React Server Components fetching on the server and passing props to client components, Storybook for the presentational side.

4Gains vs losses nothing is free

What we gain

  • Reusable UI across pages and apps.
  • Easy tests and stories: render with props, no network.
  • Clear ownership: logic in one place, looks in another.
  • Designers and developers can work on looks independently.
  • Simpler refactors: swap the data source without touching markup.

What we lose

  • More files and props to pass around.
  • Prop drilling when containers sit far above the UI.
  • Over-splitting tiny components adds noise.
  • Rules blur: hooks let any component fetch, so teams must agree.

6Common pitfalls the usual ways this goes wrong

  • Splitting everything by rule

    Every component gets a “Container” twin, even a 10-line button. Fix → split when reuse or testing actually hurts.

  • Prop drilling five levels deep

    Data travels through components that don't use it. Fix → put containers close to where data is used, or use context / a custom hook.

  • Presentational components that fetch “just once”

    A card calls an API for its avatar, and now it can't be storied. Fix → pass the URL or data in as props.

  • Leaking server shapes into UI props

    The card takes the raw API response, so an API change breaks the UI. Fix → map to a small UI-friendly type in the container.

7When to use it (and when not)

Use it when…

  • A piece of UI is (or will be) used on several screens.
  • You want Storybook stories and fast component tests.
  • A component mixes data fetching with a lot of markup.
  • Several people work on the same feature's logic and looks.

Skip it when…

  • Tiny components used once.
  • The split would only move code around without making anything easier.
  • The framework already separates them (server components fetching, client components drawing).

8Self-check quiz

How do you tell a presentational component from a container?

A presentational component only uses its props to render; a container knows where data comes from (fetches, reads stores, handles side effects).

Why are presentational components easy to test?

You render them with props and assert on output; no network, store or router needs mocking.

Has the pattern died with hooks?

The class-based form faded, but the idea lives on: hooks or server components hold the logic, pure components draw.

What's a sign you've over-applied it?

Lots of one-line containers that only forward props to a single component.
