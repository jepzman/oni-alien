Server-State Cache

TL;DR

Data from the server isn't really your state; it's a cache of someone else's. Fetch it by a key through a cache that dedupes requests, shows cached data instantly, revalidates in the background, and invalidates after mutations. Components just ask for the key.

  • Family: data fetching
  • Libraries: TanStack Query, SWR, RTK Query, Apollo
  • Built on: HTTP stale-while-revalidate idea
  • Pairs with: optimistic UI, global store

1The problem why do we even need this?

Fetching in useEffect looks simple, but real apps need much more: loading and error states, caching, deduplication, retries, refetching on focus, pagination, invalidation. Doing it by hand everywhere goes wrong.

  • Three components fetch the same user, so three requests and three spinners.
  • Navigating back shows a spinner again for data you had a second ago.
  • After editing the profile, the header still shows the old name.
  • Race conditions: a slow old response overwrites a newer one.

2Real-life analogy the newspaper on the doorstep

You read the newspaper you already have, right away, even though it's from this morning. A new edition is on its way, and when it arrives you swap it in. The whole house reads one copy; nobody orders their own.

  • Instant reading, slightly old news: stale-while-revalidate.
  • A paper older than a week goes in the recycling: garbage collection of unused cache entries.
  • Big news (you changed the data)? Throw out today's copy and fetch a fresh one: invalidation.

3How it solves it cache by key, revalidate in the background

Every query has a key (["user", "me"], ["products", { page: 2 }]) and a fetch function. The cache decides when to use stored data and when to fetch.

  1. Name queries by key

    Keys describe the data and its parameters, so identical requests share one cache entry.

  2. Read through the cache

    useQuery({ queryKey, queryFn }) returns data, status and errors; concurrent calls share one request.

  3. Decide freshness

    staleTime: how long data counts as fresh. Stale data is still shown, then refetched on mount, focus or reconnect.

  4. Mutate and invalidate

    After a POST/PUT, invalidate affected keys (or update the cache directly) so every screen refreshes.

  5. Prefetch the next step

    Hover or route intent can prefetch data so the next screen opens without a spinner.

Vocabulary for the exam

Server state
Data owned by the server that you only cache.
Query key
The identity of a cached query.
Stale time
How long cached data is considered fresh.
Revalidation
Refetching in the background to update the cache.
Invalidation
Marking cached data out of date after a change.
Deduplication
Merging identical in-flight requests into one.
profile.tsxTanStack Query
const userQuery = { queryKey: ["user", "me"], queryFn: () => api.get<User>("/me"), staleTime: 60_000 };

function Header() {
  const { data: user } = useQuery(userQuery);          // same key → same cache, 1 request
  return <Avatar name={user?.name} />;
}

function ProfileForm() {
  const qc = useQueryClient();
  const { data: user, isPending } = useQuery(userQuery);
  const save = useMutation({
    mutationFn: (patch: Partial<User>) => api.patch("/me", patch),
    onSuccess: () => qc.invalidateQueries({ queryKey: ["user", "me"] }),   // all screens refresh
  });
  if (isPending) return <Skeleton />;
  return <Form initial={user} onSubmit={(v) => save.mutate(v)} />;
}

libraries: TanStack Query (React, Vue, Svelte, Solid), SWR (Vercel), RTK Query, Apollo Client / urql for GraphQL; frameworks: Next.js and Remix data caching, Angular resource().

4Gains vs losses nothing is free

What we gain

  • Instant screens from cache; fewer spinners.
  • Fewer requests through deduplication.
  • Fresh data via background revalidation and invalidation.
  • Less code: loading, error, retry and race handling built in.
  • Global store stays small (only client state).

What we lose

  • Stale data is shown briefly; must be acceptable.
  • Cache keys must be designed carefully.
  • Invalidation bugs leave screens out of date.
  • Another library and its mental model.

6Common pitfalls the usual ways this goes wrong

  • Copying query data into local state

    The form copies the user into useState and never sees updates. Fix → read from the query, or reset the form when data changes.

  • Keys missing parameters

    ["products"] for every page, so page 2 shows page 1. Fix → put every input in the key: ["products", { page, filter }].

  • Forgetting to invalidate

    After saving, other screens show the old name until reload. Fix → invalidate (or update) affected keys in onSuccess.

  • Server data in the global store too

    Two caches disagree. Fix → server data in the query cache; client state in the store.

7When to use it (and when not)

Use it when…

  • Most apps that read data from APIs.
  • The same data is shown on several screens.
  • You want instant back-navigation and fewer spinners.
  • Data changes on the server and should refresh on focus or reconnect.

Skip it when…

  • Real-time data streams (use websockets + a store or a subscription-aware cache).
  • The framework's own data layer already caches (e.g. server components with fetch caching).
  • A one-page app with one request.

8Self-check quiz

What does stale-while-revalidate mean?

Show the cached (possibly stale) data immediately, then fetch fresh data in the background and update when it arrives.

Two components call useQuery with the same key at once. How many requests?

One. The cache deduplicates identical in-flight queries.

Why invalidate after a mutation?

So every screen using that data refetches and shows the change, instead of the old cached value.

What's the difference between server state and client state?

Server state is owned by the backend and only cached locally; client state (theme, open dialogs, cart draft) is owned by the app.

remember!!

Server data is a copy. Show it fast, refresh it quietly, and throw it out when you know it changed.
