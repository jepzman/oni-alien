Where Is That Written Down?

TL;DR

Operations knowledge is useful only if the person on call can find it, trust it and act on it. Keep it next to what it describes (service pages and runbooks in the repo), use the same few headings everywhere, write down why things are the way they are as well as how, and prune: an archive is fine, but three pages that disagree are worse than none. Test it by asking someone to answer real questions from the docs alone.

1The situation Larder, 1 June 2026

Larder's wiki has 312 pages. 40 % haven't been edited for more than a year, and three different pages about restarting Larder Core disagree with each other. None of them says why Core has a second database user called legacy_rw: Jasper created it, and Jasper left in August 2025. On 1 June Dee tries to answer ten everyday operations questions from the wiki alone. She manages three.

  • Old pages look as true as new ones.
  • The how is sometimes there; the why almost never.
  • So people ask Eli, and the rota stays one person deep.

2Real-life analogy the family recipe box

A good family recipe box keeps each card by the dish it's for. The cards say why a step matters: “rest the dough 30 minutes, or it shrinks in the oven”. Then a cousin can change the recipe without ruining it. Grandma's cards nobody uses any more go into a separate old box. They're kept, but not mixed in with the ones you cook from.

3How it solves it next to the code, five headings, the why, and a test

Eli's rules, from 1 June:

  • Docs live next to what they describe. Each service gets a page in ops/services/ in the repo, reviewed like code, and updated in the same pull request as the change.
  • Five headings, always: what it is · owner and tier · depends on (the map) · how to run it (links to runbooks) · why it's like this, with links to Ana's decision records.
  • Prune on purpose. Of the 312 wiki pages, 120 are archived (kept and marked, but not searchable by default), 61 are moved and rewritten, and the rest belong to other teams.
  • Ask the people who remember. legacy_rw's reason turns up in an old chat from 2024: a one-off data import. It goes into the “why” section, and in July the user is removed.

On 30 June Dee repeats her test with ten new questions. This time she answers eight from the docs alone.

  1. Test first: ten questions, docs only

    Ask someone other than the author.

  2. Put service docs next to the code

    Changed in the same pull request.

  3. Use the same headings everywhere

    People find things by position.

  4. Write the why, with links

    Decision records, tickets, incidents.

  5. Archive instead of leaving stale pages

    Kept, marked, out of the way.

  6. Repeat the test every quarter

    With new questions and a new person.

Vocabulary for the exam

Docs as code
Documentation kept in the repo and reviewed like code.
Tacit knowledge
What someone knows but has never written down.
Bus factor
How many people would have to leave before nobody knows how something works.
Archive
Old pages kept for history, marked and kept out of everyday search.
Decision record
A short note of a decision and its reasons (Ana's ADRs).

6Common pitfalls the usual ways this goes wrong

  • Writing only the how

    People follow the steps, but can't tell when they no longer apply. Fix → a “why it's like this” section on every page.

  • Keeping everything live

    Stale pages are trusted by mistake. Fix → archive on purpose.

  • Docs far from the code

    They drift on the first change. Fix → change them in the same pull request.

  • Never testing

    The author thinks it's clear. Fix → someone else answers real questions from the docs alone.

7When to use it (and when not)

Use it when…

  • People ask one person instead of reading.
  • Pages disagree, or nobody knows how old they are.
  • Someone important has left.
  • Before sharing on-call more widely.

Skip it when…

  • Truly throwaway work: a scratch script for one afternoon.

8Self-check quiz

What are Larder's five headings for a service page?

What it is; owner and tier; depends on; how to run it; why it's like this.

Why write the why, not just the how?

So people can tell when the steps no longer apply, and change old things safely.

What's the difference between archiving and deleting?

Archived pages are kept for history but marked and kept out of everyday search.

How does Eli test the docs?

Someone else answers ten real questions from the docs alone (Dee: 3 → 8).

What is the bus factor?

How many people would have to leave before nobody knows how something works.

what would you do?You find a strange cron job nobody can explain. What do you do before deleting it?

Search old chats, tickets and commit history for its reason, ask whoever might remember, write down what you find in the service's “why” section, and then remove it on purpose, with a way back.

try it

Write ten questions a new on-call person would ask about your systems. Give them to a colleague who didn't write the docs, and count how many they can answer from the docs alone. Rewrite the page behind the first one they couldn't.

remember!!

If the answer is only in someone's head, it leaves when they do. Write the why next to the how.
