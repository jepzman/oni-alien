Late-Arriving Data

TL;DR

Data arrives late: tills upload after an outage, partners resend, returns change old orders. File every row by its event time (when it happened), never by load time. Let each batch rebuild the periods its events belong to, not just “today”. Pick a lateness window (say 7 days) after which closed periods are not changed and late data becomes an adjustment in the current period.

1The problem why do we even need this?

The Delft shop's till loses its connection on Saturday and uploads its sales on Monday morning. The pipeline files rows by load date, so Saturday is €8,400 short, Monday is €8,400 too high, and Saturday's report has already gone to the regional managers.

  • The wrong day gets the revenue; both days are wrong.
  • A pipeline that only processes “today's partition” never fixes Saturday.
  • Returns days later change orders from closed weeks.

2Real-life analogy the postmark

The tax office counts your return as filed on the postmark date, even if it reaches the desk three days later. The clerk reopens the folder for that date. After the year is closed, a late letter is handled as a correction in the current year, not by rewriting last year's books.

3How it solves it event time decides the period

Carry the event time on every row from the source, and partition facts by event date. When a batch arrives, look at which event dates it contains and rebuild (or merge into) exactly those partitions. That is idempotent, so a late batch, a resend or a replay all do the right thing.

Decide with the business how late is too late. Within the window, the past is corrected. After it, periods are closed: the late row is booked as an adjustment in the current period, and the closed report never changes.

  1. Keep event time

    Every fact row has the time it happened, in a known time zone.

  2. Partition by event date

    Not by load date; load time is a column for debugging.

  3. Rebuild touched dates

    Each batch finds its distinct event dates and replaces or merges those partitions.

  4. Set a lateness window

    With finance: e.g. 7 days, or until month close.

  5. Book later data as adjustments

    Dated in the current period, linked to the original date, and measure lateness.

Vocabulary for the exam

Event time
When it happened in the business.
Processing time
When the pipeline handled it.
Lateness
Processing time minus event time.
Lateness window
How long a closed period may still change.
Adjustment
A correction booked in the current period.
Watermark (streaming)
The point after which a window is considered complete.
load_fact_sales_late.sqlgeneric warehouse SQL
-- which days does this batch touch?
CREATE TEMP TABLE touched AS
SELECT DISTINCT CAST(sold_at AT TIME ZONE 'Europe/Amsterdam' AS date) AS d
FROM   stg_till_sales_batch;

-- inside the window: rebuild those days only (idempotent)
DELETE FROM fact_sales
WHERE  order_date IN (SELECT d FROM touched WHERE d >= current_period_start - 7);
INSERT INTO fact_sales
SELECT * FROM stg_sales_enriched
WHERE  order_date IN (SELECT d FROM touched WHERE d >= current_period_start - 7);

-- outside the window: an adjustment in today's period
INSERT INTO fact_sales_adjustments (booked_on, original_date, store_key, amount)
SELECT :run_date, order_date, store_key, amount
FROM   stg_sales_enriched
WHERE  order_date IN (SELECT d FROM touched WHERE d < current_period_start - 7);

tools: dbt incremental models with incremental_predicates on the touched dates, BigQuery and Spark dynamic partition overwrite, Apache Beam and Flink event-time windows with allowed lateness, Kafka timestamps.

4Gains vs losses nothing is free

What we gain

  • Right day, right number, even after outages.
  • Replays and resends are safe: same dates, same result.
  • Closed periods stay closed, with a clear rule.
  • Lateness is measured, so slow sources are visible.

What we lose

  • Old reports change within the window; users must know.
  • More work per batch: several partitions, not one.
  • A business rule to agree: the window and adjustments.
  • Time zones become your problem, explicitly.

6Common pitfalls the usual ways this goes wrong

  • Partitioned by load date

    Late rows land in today, and nothing ever moves them. Fix → partition facts by event date; keep load time as a column.

  • Only today is processed

    The job rebuilds today's partition and ignores the Saturday rows in the batch. Fix → rebuild every distinct event date in the batch.

  • Time zone at random

    Some days are cut in UTC and others in local time; orders near midnight jump days. Fix → convert to the business time zone once, in staging.

  • No window

    A return two years later changes a filed annual report. Fix → agree a window; after it, book adjustments.

7When to use it (and when not)

Use it when…

  • Sources that can be offline: tills, mobile apps, devices.
  • Partners that resend or batch their data.
  • Facts that change after the event (returns, corrections).
  • Any report by day, week or month.

Skip it when…

  • Operational counters where “what arrived today” is the question.
  • Append-only logs analysed only by arrival time.
  • When you need every past version, not just the corrected one: use bitemporal tables.

8Self-check quiz

What is the difference between event time and processing time?

Event time is when it happened; processing time is when the pipeline handled it.

Why rebuild the event dates in a batch rather than today?

Late rows belong to the day they happened; only rebuilding those dates puts them there.

What happens to data older than the lateness window?

It is booked as an adjustment in the current period, so closed periods don't change.

Why convert to one time zone in staging?

So orders near midnight fall on the same day in every report.

what would you do?A partner sends last month's sales corrections on the 3rd of each month, but finance closes the month on the 2nd. What do you agree and build?

Agree that the month closes on the 2nd and later corrections are adjustments: load them into an adjustments fact dated in the current month with the original date kept, and show “adjustments to prior months” as its own line. Alternatively, finance moves the close to the 4th.

try it

Take a table of sales with sold_at. Load three days, then load a batch with one row from day 1. Rebuild only “today”, and compare day 1 with the source. Then rebuild the distinct dates in the batch, and compare again.
