Quality Checks & Quarantine

TL;DR

Check data on every load, at two levels. Row checks (not null, accepted values, ranges, foreign keys) send failing rows to a quarantine table with a reason, so good rows keep flowing. Batch checks (row count, totals and the share of bad rows against the usual band) decide whether the batch may be published at all. Quarantined rows are fixed and replayed, never silently dropped.

1The problem why do we even need this?

After a till firmware update, the Delft shop sends prices in cents: the €39 kettle arrives as €3,900, and Delft's revenue jumps by €1.2 million. In the same batch, rows with no shop id vanish in an inner join. Both problems reach the report, one loudly and one silently.

2Real-life analogy the factory quality line

On a factory line, an inspector pulls bad items into a side bin with a tag saying what's wrong, and the line keeps running. If too many items are bad, the inspector pulls the cord and stops the line, because something upstream is broken.

3How it solves it rows to quarantine, batches to a gate

Row checks split each batch: good rows continue, bad rows go to quarantine with the reason. Nothing disappears silently. Batch checks look at the whole: is the row count or revenue far from the usual for this weekday, are more than 1 % of rows quarantined, are there duplicates, is the newest event recent? A failed batch check stops the publish (write–audit–publish), because a broken source is likely.

Give each check a severity: warn (notify) or error (stop). Start with few, strong checks on what reports depend on.

  1. List what reports depend on

    Keys, amounts, dates, shop and product ids.

  2. Add row checks

    Not null, accepted values, ranges (0 < price < 2,000), foreign keys that resolve.

  3. Route failures to quarantine

    Same columns plus reason, batch id, time; alert the owner.

  4. Add batch checks with thresholds

    Count and sum within ±30 % of the same weekday's median; quarantined share < 1 %.

  5. Fix and replay

    Correct at the source or map in staging, then reprocess the quarantined rows.

Vocabulary for the exam

A rule each row must pass.

load_till_sales.sql + schema.ymlSQL · dbt tests
-- row checks: split the batch, never drop rows silently
INSERT INTO quarantine_till_sales
SELECT b.*, CASE WHEN b.shop_id IS NULL THEN 'shop_id missing'
                 WHEN b.unit_price NOT BETWEEN 0.01 AND 2000 THEN 'price out of range'
            END AS reason, :batch_id, now()
FROM   stg_till_batch b
WHERE  b.shop_id IS NULL OR b.unit_price NOT BETWEEN 0.01 AND 2000;

INSERT INTO stg_till_sales_clean
SELECT * FROM stg_till_batch
WHERE  shop_id IS NOT NULL AND unit_price BETWEEN 0.01 AND 2000;

# schema.yml · batch-level checks in dbt
models:
  - name: fct_sales
    tests:
      - dbt_utils.expression_is_true:
          expression: "(select count(*) from quarantine_till_sales where batch_id = '{{ var('batch_id') }}') < 0.01 * (select count(*) from stg_till_batch)"
    columns:
      - name: order_line_id
        tests: [unique, not_null]

4Gains vs losses nothing is free

What we gain

  • Bad rows don't reach reports, and good rows aren't held back.
  • Nothing vanishes silently: every rejected row has a reason.
  • Broken sources are caught by volume and sum checks.
  • Fix and replay instead of hand-editing facts.

What we lose

  • Checks to write and tune: too loose misses, too strict cries wolf.
  • Quarantine needs an owner, or it fills up unread.
  • Reports can be incomplete while rows wait in quarantine.
  • Extra compute on every load.

6Common pitfalls the usual ways this goes wrong

  • Inner joins as filters

    Rows with a missing key vanish without a trace. Fix → check foreign keys explicitly; quarantine or use an unknown member.

  • Alert fatigue

    Fifty warnings a day, all ignored, including the real one. Fix → few checks, tuned thresholds, error only on what matters.

  • Quarantine nobody reads

    Thousands of rows rot there; revenue is quietly short. Fix → an owner, a daily count on the dashboard, and an age limit.

  • Fixed thresholds

    “At least 90,000 rows” fails every Sunday and every holiday. Fix → compare with the same weekday's median, or use anomaly detection.

7When to use it (and when not)

Use it when…

  • Every load that feeds a report people act on.
  • Sources you don't control: tills, partners, spreadsheets.
  • Data with known valid ranges.
  • Pipelines with write–audit–publish.

Skip it when…

  • Raw landing: keep everything there, check downstream.
  • Exploratory data where “bad” isn't defined yet.
  • Duplicating checks the source already enforces with constraints you trust.

Related patterns

  • Write–audit–publish
  • Idempotent loads
  • Data contracts
  • Late-arriving data

8Self-check quiz

What is the difference between row checks and batch checks?

Row checks judge each row and quarantine failures; batch checks judge the whole batch and can stop publishing.

Why quarantine instead of dropping bad rows?

So nothing disappears silently: rows can be fixed and replayed, and counted.

Why compare volume with the same weekday rather than a fixed number?

Volume varies by weekday and season; a fixed threshold either misses problems or fails every Sunday.

What should happen when 5 % of a batch is quarantined?

A batch check should fail and stop the publish, because a source is probably broken.

what would you do?A new shop opens and its till sends a product code the warehouse doesn't know. Its sales are missing from the report. What should have happened, and what do you build?

The rows should have gone to quarantine with “unknown product” and alerted the owner, or loaded against an unknown-member product key. Add a foreign-key row check with quarantine, a daily quarantine count on the dashboard, and a replay once the product is added.

try it

Take a day of real data and write three row checks and two batch checks. Run them, and look at what the quarantine table catches. Then change one threshold to the same weekday's median and see which alerts disappear.

remember!!

Bad items to the tagged bin. Too many? Stop the line.
