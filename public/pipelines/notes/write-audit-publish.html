Write–Audit–Publish

TL;DR

Never load straight into the table people read. Write the new data into a hidden copy, audit it there (keys, counts, sums, reconciliation), and publish it with an atomic swap only if the audits pass. If they fail, readers keep yesterday's correct table, with a clear “data as of” note, instead of today's wrong one.

1The problem why do we even need this?

On Monday the 06:00 load writes straight into fct_sales. The source export was truncated, so half of Sunday is missing. At 07:00 the finance dashboard shows revenue down 40 %. The tests run at 07:30 and fail correctly, but the CFO has already taken the number to the 08:00 meeting.

  • Tests that run after publishing only tell you what people have already seen.
  • A half-loaded table is visible for as long as the load takes.
  • Trust is lost faster than it's rebuilt: next week nobody believes the dashboard.

2Real-life analogy the newspaper

A newspaper is written, then proofread, then printed. If the proofreader finds a wrong headline, the presses wait and yesterday's paper stays on the stand. Nobody prints first and proofreads afterwards.

3How it solves it hidden copy, audits, atomic swap

The load writes into a copy that readers can't see: a _next table, a zero-copy clone, or a branch in Iceberg, Nessie or lakeFS. Audits run against that copy. Publishing is one atomic step (a table swap, a view pointing at the new table, a branch fast-forward), so readers see the old version or the new one, never half of either.

  1. Write hidden

    Build fct_sales_next (or a branch) from the same models.

  2. Audit there

    Unique keys, not nulls, row counts and sums against the usual band, reconciliation with the source.

  3. Publish atomically

    ALTER TABLE … SWAP WITH, a rename, a view switch, or a branch merge.

  4. On failure, keep the old

    Alert the owner; dashboards show the data's real age.

  5. Clean up

    Drop or keep the failed copy for debugging, with a short retention.

Zero-copy clone
A copy that shares storage until changed (Snowflake, Delta).
Branch

publish_fct_sales.sqlSnowflake-style SQL
-- 1 · write: build the next version where nobody reads
CREATE OR REPLACE TABLE fct_sales_next CLONE fct_sales;
MERGE INTO fct_sales_next t USING stg_sales_changes s ON …;   -- the normal load

-- 2 · audit: every check must return zero rows
SELECT order_line_id FROM fct_sales_next GROUP BY 1 HAVING count(*) > 1;
SELECT 1 FROM (SELECT count(*) n FROM fct_sales_next WHERE order_date = :day) x
 WHERE n < 0.7 * (SELECT avg_lines FROM expected_volume WHERE weekday = dayofweek(:day));

-- 3 · publish: one atomic step
ALTER TABLE fct_sales SWAP WITH fct_sales_next;

tools: Apache Iceberg WAP and branches, Project Nessie, lakeFS, Delta Lake clones, Snowflake zero-copy clones and SWAP, BigQuery table snapshots, dbt build (tests before downstream models) and blue-green deployment macros.

4Gains vs losses nothing is free

What we gain

  • Readers never see unaudited data.
  • Failures are quiet: yesterday stays, an alert fires.
  • No half-loaded tables during long loads.
  • Easy rollback: swap back to the previous copy.

What we lose

  • Freshness pauses when an audit fails.
  • Extra storage and compute for the copy.
  • Audits to maintain: too strict and every run fails.
  • Cross-table consistency needs publishing several tables together.

6Common pitfalls the usual ways this goes wrong

  • Audits after the swap

    The steps are in the wrong order, and readers see bad data first. Fix → publish is the last step, and only on success.

  • Swapping tables one by one

    Facts are new, dimensions still old; joins break for an hour. Fix → publish related tables together (a branch merge or a schema swap).

  • Audits that always pass

    Only “table not empty” is checked. Fix → check counts and sums against a usual band, and reconcile with the source.

  • Silent staleness

    The audit fails every day for a week and nobody notices, because the dashboard looks fine. Fix → alert on failed publishes and show data age on every dashboard.

7When to use it (and when not)

Use it when…

  • Tables that people make decisions from.
  • Loads that take long enough to be seen half-done.
  • Sources that sometimes send broken or partial data.
  • Any table with an external audience.

Skip it when…

  • Exploration sandboxes.
  • Streaming tables where seconds matter: check in the stream instead.
  • Small internal tables where a wrong hour does no harm.

8Self-check quiz

What are the three steps of WAP?

Write into a hidden copy, audit it with checks, publish it with an atomic swap only if the checks pass.

What do readers see when an audit fails?

The previously published, audited table, with its real age shown.

Why must publishing be atomic?

So readers see either the old version or the new one, never half of each.

Why publish facts and dimensions together?

So joins between them always see matching versions.

what would you do?A partner's file sometimes arrives with only half its rows. Your load and tests both run at 06:00, and dashboards refresh at 06:05. What do you change?

Load into a hidden copy, audit row counts and totals against the usual band for that weekday, and swap only on success. On failure keep yesterday's table, alert the owner, and show “data as of yesterday” on the dashboard until the partner resends.

try it

In any SQL database, build a _next copy of a table, insert a deliberately broken batch, write two audit queries that must return zero rows, and only rename the copy into place when they do. Then try it with a good batch.

remember!!

Write, proofread, then print. Yesterday's paper beats today's wrong one.
