Metrics Layer

TL;DR

Define each business number once, in code: what it sums, which rows it excludes, its time dimension, the dimensions it can be split by, its owner. Dashboards, spreadsheets and notebooks don't write their own SQL for it; they ask the metrics layer, which generates the query, picks the joins safely and computes ratios correctly. Change the definition once and every tool follows.

  • Family: serving reports
  • Also called: semantic layer, headless BI
  • Lives in: dbt Semantic Layer, Cube, LookML, Malloy
  • Pairs with: conformed dimensions, aggregates

1The problem why do we even need this?

For the same week the finance dashboard says revenue was €1.92M (net, after returns), marketing's says €2.31M (gross, including VAT), and a spreadsheet says €2.05M (net, but without gift cards). All three are called “revenue”, and Monday's meeting is spent arguing about which is right.

  • Every tool has its own copy of the SQL, and each drifts.
  • Ratios are averaged wrongly (average of averages).
  • Nobody knows who owns the definition.

2Real-life analogy the franchise recipe card

Every branch of a burger chain cooks from the same recipe card: same weights, same steps. When head office changes the sauce, it changes the card once, and every branch follows. Branches can choose how to plate it, not what's in it.

3How it solves it one definition, many tools

The layer knows the model: facts, dimensions, how they join (through conformed dimensions), and which measures are additive. A metric is a named measure plus filters and a time dimension. When a tool asks for “revenue by category by week”, the layer writes the SQL, joins only along safe paths (no fan-out), and computes ratios as a ratio of sums, not an average of ratios.

  1. Pick the top ten numbers

    Revenue, orders, average order value, return rate: the ones in meetings.

  2. Agree each definition

    With its owner: what's in, what's out, net or gross, which date.

  3. Write them in code

    Measures, filters, time dimension, allowed dimensions, description, owner; reviewed in git.

  4. Point tools at the layer

    BI tools, spreadsheets and notebooks query it instead of tables.

  5. Retire copies

    Remove hand-written revenue SQL from dashboards as they move over.

Vocabulary for the exam

Metric
A named business number with a fixed definition.
Measure
The aggregation behind it (sum of net amount).
Dimension
What you can split a metric by.
Entity
A join key the layer uses to connect models (customer, product).
Ratio metric
Numerator and denominator summed first, then divided.
Headless BI
Definitions served by an API, independent of the dashboard tool.
models/metrics/revenue.ymldbt Semantic Layer (MetricFlow)
semantic_models:
  - name: sales
    model: ref('fct_sales')
    defaults: { agg_time_dimension: order_date }
    entities:
      - { name: order_line, type: primary, expr: order_line_id }
      - { name: product,    type: foreign, expr: product_key }
      - { name: shop,       type: foreign, expr: shop_key }
    dimensions:
      - { name: order_date, type: time, type_params: { time_granularity: day } }
    measures:
      - { name: amount_net, agg: sum }
      - { name: orders,     agg: count_distinct, expr: order_id }

metrics:
  - name: revenue
    label: Revenue (net, after returns, excl. gift cards)
    type: simple
    type_params: { measure: amount_net }
    filter: "{{ Dimension('product__is_gift_card') }} = false"
  - name: average_order_value
    type: ratio                      # sum / count, never an average of averages
    type_params: { numerator: revenue, denominator: orders }

tools: dbt Semantic Layer (MetricFlow), Cube, Looker (LookML), Malloy, AtScale, Power BI semantic models; definitions reach Excel, Google Sheets and notebooks through the layer's API or SQL interface.

4Gains vs losses nothing is free

What we gain

  • One number per name, in every tool.
  • Safe joins and correct ratios, generated for you.
  • Owned, reviewed definitions with descriptions.
  • Tool freedom: change dashboards without re-deriving revenue.

What we lose

  • Another layer to run and learn.
  • Not every tool connects well to every layer.
  • Agreeing definitions is political work.
  • Unusual questions may need the raw SQL anyway.

6Common pitfalls the usual ways this goes wrong

  • Metrics layer as a dump

    Four hundred metrics, half of them “revenue_v2_final”. Fix → start with the numbers in meetings; one owner each; deprecate duplicates.

  • Definitions still in dashboards

    The layer exists, but old dashboards keep their own SQL. Fix → migrate and remove the copies; flag dashboards that bypass the layer.

  • Averages of averages

    Average order value averaged across shops gives every shop equal weight. Fix → define ratios as sums divided, in the layer.

  • No business owner

    Engineers decide what revenue means. Fix → every metric has a named business owner who approves changes.

7When to use it (and when not)

Use it when…

  • Several tools or teams report the same numbers.
  • Numbers are discussed in meetings and disagree.
  • Ratios and averages are common.
  • You want self-service without everyone writing SQL.

Skip it when…

  • One dashboard, one analyst.
  • Exploratory analysis of brand-new data.
  • Before the underlying model (facts, dimensions) is stable.

8Self-check quiz

What does a metrics layer store?

Named business metrics defined once in code: measure, filters, time dimension, allowed dimensions, owner.

How should average order value be computed across shops?

Total revenue divided by total orders, not the average of each shop's average.

Why does the layer generate the joins?

So queries only join along safe paths and don't multiply rows.

What's the first step in adopting one?

Agree definitions for the handful of numbers used in meetings, each with an owner.

what would you do?Marketing wants “revenue” to include VAT, finance wants it net. Both will use the same metrics layer. What do you do?

Define two clearly named metrics, revenue_net (owner: finance) and revenue_gross_incl_vat (owner: marketing), with descriptions, and make dashboards label which one they show. “Revenue” alone points to the company's official one, agreed by finance.

try it

Search your BI tool and spreadsheets for every place revenue is calculated. Write down each formula. Agree one with its owner, define it in a metrics layer (or a single SQL view if that's what you have), and repoint the two most-used dashboards.
