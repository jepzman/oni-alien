Lambda vs Kappa

TL;DR

To get fresh numbers without losing correct ones, lambda runs a batch layer (complete, recomputed) and a speed layer (recent, approximate) and merges them, at the cost of writing every rule twice. Kappa uses one stream job over a replayable log; to fix logic, replay the log through a new version. Today: one code path, stream only if minutes matter, and often a 5–15 minute micro-batch is enough.

  • Family: serving reports
  • Origin: Nathan Marz (2011), Jay Kreps (2014)
  • Lives in: Kafka, Flink, Spark, streaming warehouses
  • Pairs with: late-arriving data, event sourcing

1The problem why do we even need this?

On promotion days the store managers want today's sales live. A streaming counter was added beside the nightly batch. All day it shows €48,200; next morning the batch says €46,900. The stream counted retried events twice and missed late till uploads, and every rule exists twice: once in Java, once in SQL.

2Real-life analogy election night

On election night, TV projections are fast and approximate, and the official count comes later and is final: two counts, by two teams. Another way: publish one count as ballots are counted, keep every ballot in the box, and if a counting rule was wrong, recount from the box with the corrected rule.

3How it solves it two paths, or one path you can replay

Lambda: the batch layer recomputes everything from the master data; the speed layer covers only what the batch hasn't processed yet; a serving layer merges them. Correct in the end, but two implementations that must agree.

Kappa: all events go into a log that keeps them long enough to replay. One stream job uses event time, windows and watermarks, and writes idempotently. To change logic, start version 2 from the start of the log, let it catch up, switch readers, stop version 1.

  1. Ask how fresh it must be

    Seconds? Minutes? If 15 minutes is fine, micro-batch the normal pipeline.

  2. Keep a replayable log

    Kafka or similar with retention long enough to rebuild (or raw in the warehouse).

  3. Write one job, in event time

    Windows and watermarks; allowed lateness; idempotent sink.

  4. Replay to change logic

    Run v2 from the start beside v1, compare, switch readers.

  5. Reconcile

    Compare stream results with the warehouse daily; differences mean a bug.

CREATE TABLE till_sales (
  order_line_id BIGINT, shop_id INT, amount DECIMAL(12,2), sold_at TIMESTAMP(3),
  WATERMARK FOR sold_at AS sold_at - INTERVAL '10' MINUTE      -- allowed lateness
) WITH ('connector' = 'kafka', 'topic' = 'till-sales', 'scan.startup.mode' = 'earliest-offset');

-- one job: revenue per shop per 15 minutes, in event time
INSERT INTO shop_revenue_15m                                  -- upsert sink, keyed
SELECT shop_id, window_start, SUM(amount) AS revenue
FROM TABLE(TUMBLE(TABLE till_sales_dedup, DESCRIPTOR(sold_at), INTERVAL '15' MINUTE))
GROUP BY shop_id, window_start;

-- till_sales_dedup: ROW_NUMBER() OVER (PARTITION BY order_line_id ORDER BY sold_at) = 1

then & now rethought

Then Marz, 2011 · Kreps, 2014

Nathan Marz proposed lambda because Hadoop batch jobs were the only way to be complete and correct, so a separate, approximate speed layer covered the hours they took. Jay Kreps answered with kappa: keep the log and reprocess it with one stream job instead.

Now 2026

Stream processors now have event-time windows, watermarks and exactly-once sinks, so one path can be correct. Streaming warehouses and incremental views blur the line further. Many teams find that the normal batch pipeline every 5–15 minutes is all the freshness they need.

Verdict: One code path. Stream only if minutes matter, keep the data replayable, and reconcile against the warehouse.

4Gains vs losses nothing is free

What we gain

  • Fresh numbers during the day.
  • Kappa: one implementation of every rule.
  • Replay fixes logic for the whole history.
  • Lambda: batch remains the safety net.

What we lose

  • Lambda: rules written twice, and they drift.
  • Kappa: long log retention and replay time.
  • Streaming is harder to run: state, checkpoints, lateness.
  • Often unnecessary: micro-batches would do.

6Common pitfalls the usual ways this goes wrong

  • Streaming without need

    A Flink cluster for a dashboard people check twice a day. Fix → micro-batch the normal pipeline every 15 minutes first.

  • Processing time windows

    Late till uploads land in the wrong window. Fix → window by event time with watermarks and allowed lateness.

  • Log too short to replay

    Kafka keeps 7 days; the fix needs 90. Fix → keep raw events in the warehouse or tiered storage long enough to replay.

  • No reconciliation

    Live and daily numbers differ by 3 % and nobody knows why. Fix → compare stream output with the warehouse every day.

7When to use it (and when not)

Use it when…

  • Decisions that need numbers within minutes (stock, fraud, promotions).
  • Events already flowing through a log.
  • A team able to run stream processing.
  • Logic that must be identical live and historically.

Skip it when…

  • Freshness of 15 minutes or more is enough: micro-batch.
  • Reports read once a day.
  • No replayable source of events.

8Self-check quiz

What are lambda's three layers?

A batch layer, a speed layer and a serving layer that merges them.

How does kappa change logic for past data?

By replaying the log from the start through a new version of the job, then switching readers.

What is lambda's main cost?

Every rule is implemented twice, and the two drift apart.

When is neither needed?

When a batch pipeline run every 5–15 minutes is fresh enough.

what would you do?Store managers want stock levels “live” on promotion days. Your batch pipeline is idempotent and runs hourly. What do you try first?

Run the same pipeline every 10–15 minutes for the stock tables (micro-batch), and show “as of” on the dashboard. Only if minutes still matter, move the stock calculation to one stream job over the CDC log, with event-time windows and daily reconciliation against the warehouse.

try it

Write down, for your three most important dashboards, how old the data can be before a decision changes. If every answer is “an hour” or more, schedule the batch more often and stop there.

remember!!

One count, kept ballots. Recount when the rule changes.
