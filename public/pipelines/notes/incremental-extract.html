Incremental Extract

TL;DR

Instead of copying a whole table every night, copy only the rows that changed since the last run, found by a column such as updated_at and a saved watermark. Two rules make it safe: re-read a small overlap behind the watermark (transactions commit late) and merge by key so the overlap does no harm. It cannot see hard deletes; for those use CDC or a key comparison.

  • Family: getting data in
  • Needs: a trusted, indexed updated_at
  • Also called: delta load, high-water mark
  • Pairs with: idempotent loads, change data capture

1The problem why do we even need this?

The shop copies all of order_lines every night. At 60 million rows and 25 GB it now starts at 01:00 and is still running when the shops open, while the replica it reads from falls behind and slows the app. Only about 108,000 rows changed since yesterday.

  • The work grows with the size of the table, not with the size of the change.
  • The report can't be fresher than once a night.
  • Every run puts the heaviest possible read on the source.

2Real-life analogy the meter reader

A meter reader doesn't count every unit since the house was built. They write down today's value and bill the difference since the last reading, which is on the card. The card is updated only after the bill goes out, so a lost bill never skips a month.

3How it solves it watermark, overlap, merge, then move the watermark

Keep a small table of watermarks, one per source table. Each run reads rows changed after the watermark minus an overlap, merges them into staging on the primary key, and then stores the largest updated_at it saw. The overlap exists because a row is stamped when it is written but becomes visible when its transaction commits, which can be later than the next run.

  1. Find a reliable change column

    updated_at set by the database (a trigger or default), never by app clocks; or an always-increasing id for append-only tables.

  2. Index it

    So each run is a short range scan, not a full scan.

  3. Read with an overlap

    updated_at > watermark − 10 min: longer than your longest transaction.

  4. Merge by key

    So rows read twice are updated, not duplicated.

  5. Save the watermark last

    In the same transaction as the merge, or after it commits, never before.

Vocabulary for the exam

Watermark
The last change position loaded, saved between runs.
Overlap window
How far behind the watermark each run re-reads.
Delta
The rows that changed since the last run.
Full refresh
Copy the whole table again.
Hard delete
A row removed from the table; invisible to timestamp extracts.
Reconciliation
Comparing counts, sums or keys between source and copy.
extract_order_lines.sqlsource: PostgreSQL
-- 1 · read the delta, with a safety overlap behind the watermark
SELECT *
FROM   order_lines
WHERE  updated_at >  :watermark - interval '10 minutes'
  AND  updated_at <= now() - interval '1 minute'   -- leave in-flight rows for next time
ORDER  BY updated_at;

-- 2 · in the warehouse: MERGE the rows into stg_order_lines on order_line_id

-- 3 · only then move the watermark
UPDATE etl_watermarks
SET    last_value = :max_updated_at_seen
WHERE  table_name = 'order_lines';

-- in the source, once: make updated_at trustworthy
CREATE TRIGGER order_lines_touch BEFORE UPDATE ON order_lines
FOR EACH ROW EXECUTE FUNCTION set_updated_at_now();

tools: Airbyte and Fivetran (“incremental” sync modes with a cursor column), dbt is_incremental(), AWS Glue job bookmarks, Azure Data Factory watermark pattern; for deletes and exact ordering use CDC (Debezium) instead.

4Gains vs losses nothing is free

What we gain

  • Work grows with change, not with table size.
  • Fresher: cheap enough to run every 15 minutes or hourly.
  • Light on the source: an index range scan, not a full scan.
  • No new infrastructure: just SQL and one small table.

What we lose

  • Blind to hard deletes.
  • Trusts one column: a script that skips updated_at hides its changes.
  • Late commits are missed without an overlap.
  • Only the latest version is seen; changes between runs are lost.

6Common pitfalls the usual ways this goes wrong

  • No overlap

    A transaction that commits after the run with an older timestamp is skipped forever. Fix → re-read a window longer than your longest transaction, and cap transaction time.

  • updated_at set by the app

    A bulk UPDATE script doesn't set it, and its changes never arrive. Fix → set it in the database with a trigger or default, so every write path updates it.

  • Watermark moved too early

    The job saves the watermark, then fails loading; those rows are skipped. Fix → save it in the same transaction as the load, or after it commits.

  • Deletes forgotten

    Cancelled orders that were hard-deleted stay in revenue. Fix → use soft deletes, CDC, or a periodic comparison of all keys.

7When to use it (and when not)

Use it when…

  • Large tables where only a small share changes each day.
  • Sources where you can't get log access for CDC.
  • Append-only tables with an increasing id (events, logs).
  • SaaS APIs that offer “changed since” queries.

Skip it when…

  • Small tables: a full copy is simpler and always right.
  • Tables with hard deletes you must see: use CDC.
  • You need every intermediate version, not just the latest: use CDC.

8Self-check quiz

Why re-read an overlap behind the watermark?

Rows are stamped when written but visible when committed; a long transaction can commit after the run with an older timestamp.

Why must the load merge rather than append?

The overlap reads some rows twice; a merge updates them, an append would duplicate them.

When should the watermark be saved?

After the load commits, or in the same transaction, so a failed load is retried rather than skipped.

What can an incremental extract by timestamp never see?

Hard-deleted rows, because no row is left to select.

what would you do?A support script fixes 3,000 order totals with a plain UPDATE once a month. The warehouse never shows the fixes. Why, and what do you change?

The script doesn't set updated_at, so the extract never sees those rows. Set updated_at in the database with a trigger on every update, then re-extract the affected period once (reset the watermark or run a targeted backfill).

try it

In PostgreSQL, open a transaction, insert a row with updated_at = now(), and keep it open. In another session, run your extract and save the watermark. Commit the first transaction and run the extract again. Did it find the row? Add a 10-minute overlap and a merge, and try again.

remember!!

Read past the bookmark, minus a little, merge by key, and move the bookmark last.
