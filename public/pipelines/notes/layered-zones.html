Layered Zones (Raw, Staging, Marts)

TL;DR

Give the warehouse three layers with clear promises. Raw holds data exactly as received, append-only. Staging holds one clean, typed row per source key. Marts hold facts and dimensions with business definitions, and are the only layer reports read. Each layer is built only from the one before it, so staging and marts can always be rebuilt from raw.

1The problem why do we even need this?

Analysts query the raw change tables directly. Each dashboard removes duplicates and deletes its own way, so five dashboards show five different revenue numbers. To “help”, someone deletes bad rows from raw, and now the original data is gone as well.

  • Cleaning logic is copied into every report, each slightly different.
  • A fix means editing forty dashboards, and missing some.
  • Raw edited in place can never be replayed.

2Real-life analogy a restaurant kitchen

A kitchen has a delivery bay where crates are kept as delivered and labelled, a prep station where vegetables are washed and chopped into containers, and the pass where dishes are plated. Guests only see what leaves the pass, and nobody plates straight from a crate.

3How it solves it three promises, one direction

Each layer makes one promise. Raw: nothing is ever changed or lost. Staging: one current, typed row per source key, nothing else (no joins between sources, no business rules). Marts: business meaning, one definition per measure. Data flows one way, and permissions follow the layers: analysts can't even see raw.

  1. Land in raw

    One table per source table, append-only, with _loaded_at, _source and the log position.

  2. One staging model per raw table

    Rename, cast, dedupe to the latest row per key, flag deletes. No joins.

  3. Build marts from staging

    Facts and dimensions, joins and business rules live here.

  4. Lock the layers

    Pipelines write raw; only marts are granted to analysts and BI tools.

  5. Name by layer

    raw., stg_, fct_, dim_, so lineage is readable at a glance.

models/staging/stg_order_lines.sqldbt
-- staging: rename, cast, latest version per key, deletes flagged. No business rules.
with ranked as (
    select
        cast(id as bigint)            as order_line_id,
        cast(order_id as bigint)      as order_id,
        cast(qty as int)              as qty,
        cast(line_total as numeric)   as amount,
        _op = 'd'                     as is_deleted,
        _lsn,
        row_number() over (partition by id order by _lsn desc) as rn
    from {{ source('raw', 'order_lines_changes') }}
)
select * from ranked where rn = 1

4Gains vs losses nothing is free

What we gain

  • One cleaning, one definition: every report agrees.
  • Replay: rebuild everything from raw after any fix.
  • Clear ownership: each layer has a promise and an owner.
  • Safer access: analysts never touch raw or personal fields.

What we lose

  • More tables and storage: three copies of some data.
  • More latency: each layer is one more step.
  • Ceremony for a tiny project with one source.
  • Layer drift: rules sneak into staging unless reviewed.

6Common pitfalls the usual ways this goes wrong

  • Business rules in staging

    Revenue logic creeps into a staging model and is hidden from mart reviewers. Fix → staging only renames, casts and dedupes; rules belong in marts.

  • Reports on staging

    A dashboard reads stg_ tables “just this once”, and breaks at the next source change. Fix → grant only marts to BI roles.

  • Raw without retention

    Raw grows forever, with personal data nobody needs. Fix → set a retention per source and a deletion process for personal data.

  • Layers by name only

    Schemas are called bronze and gold but anything reads anything. Fix → enforce the one-way rule with permissions and a lineage check in CI.

7When to use it (and when not)

Use it when…

  • Several reports or teams use the same sources.
  • Data arrives as change events or with duplicates.
  • You need to rebuild after fixes.
  • Raw data contains fields analysts shouldn't see.

Skip it when…

  • One source, one report, one person: a view may do.
  • Real-time paths where each layer's delay is too much; keep the stream short.
  • Adding a fourth and fifth layer “for flexibility”.

8Self-check quiz

What does each of the three layers promise?

Raw: nothing changed or lost. Staging: one clean row per key. Marts: business definitions for reports.

Why should reports read only marts?

So cleaning and definitions live in one place, and source changes stop at staging.

What belongs in a staging model?

Renaming, casting, deduping to the latest row per key and flagging deletes; no joins or business rules.

Why must raw never be edited?

It is the only copy that lets every other layer be rebuilt.

what would you do?A data scientist asks for read access to raw because “marts don't have the column I need”. What do you do?

Don't grant raw. Add the column to the staging model (rename and cast it) and expose it in the right mart, or build a mart for their use case. Then everyone gets it, cleaned once, and permissions on personal data stay intact.

try it

Take a dashboard that reads source tables directly. List every cleaning step its SQL does. Move those steps into one staging model, point the dashboard at a mart built from it, and check its number matches before and after.
