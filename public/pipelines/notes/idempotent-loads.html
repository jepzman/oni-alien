Idempotent Loads

TL;DR

Every load will be rerun one day: after a failure, a fix, a backfill or a scheduler retry. Make sure running a batch twice gives the same table as running it once. Either replace the whole slice (delete and insert a day, or overwrite its partition, in one transaction) or MERGE on a key with a “newer only” guard. Never blindly append, and keep hidden clocks such as now() out of the transform.

  • Also called: rerunnable, deterministic loads

1The problem why do we even need this?

The load for 31 March fails halfway, after appending 52,000 of 100,000 lines. The on-call engineer does the right thing and reruns it. The load appends all 100,000 again, and 31 March now holds 152,000 lines. The dashboard shows the best day of the year.

  • Append-only loads turn every retry into duplicates.
  • Engineers learn to fear reruns, and fix data by hand instead.
  • Backfills after a bug fix need special scripts, and get them wrong.

2Real-life analogy rewriting the ledger page

A careful bookkeeper redoing 31 March doesn't add the day's lines again at the bottom. They rub out the page for 31 March and rewrite it from the receipts. Do it once or five times: the page is the same.

3How it solves it replace a slice, or merge on a key

Replace the slice when a batch is “everything for this day”: delete the day and insert it, in one transaction, or use the warehouse's partition overwrite. Merge on a key when a batch is “these rows changed”, as with CDC or an incremental extract: match on the source key and update only if the incoming version is newer, so a replayed or out-of-order row changes nothing.

Idempotent also means deterministic: the transform must use only its inputs and the period it was given, never now() or current_date, or a rerun for last Tuesday gives a different answer.

  1. Choose the slice or the key

    Daily batches: slice by event date. Change streams: the source's primary key.

  2. Make it one transaction

    Delete and insert together, or a single MERGE, so a crash leaves the old slice or the new one, never half.

  3. Guard merges with a version

    Update only when the incoming updated_at or log position is newer.

  4. Pass the period in

    The scheduler's logical date is a parameter; no now() inside.

  5. Test it

    Run the load twice in CI and compare: the tables must be identical.

Vocabulary for the exam

Idempotent
Doing it twice has the same effect as doing it once.
Deterministic
The same inputs always give the same output.
Partition overwrite
Replace one partition's contents atomically.
Logical date
The period a run is for, as opposed to when it ran.
Backfill
Running the normal job for past periods.
Newer-only guard
A merge condition that ignores older versions.
load_fact_sales.sqlgeneric warehouse SQL
-- A · replace the slice: one day, one transaction
BEGIN;
DELETE FROM fact_sales WHERE order_date = :day;
INSERT INTO fact_sales
SELECT * FROM stg_sales_enriched WHERE order_date = :day;
COMMIT;

-- B · merge on the key, newer versions only
MERGE INTO fact_sales t
USING stg_sales_changes s
   ON t.order_line_id = s.order_line_id
WHEN MATCHED AND s.updated_at > t.updated_at THEN
  UPDATE SET qty = s.qty, amount = s.amount, updated_at = s.updated_at
WHEN NOT MATCHED THEN
  INSERT (order_line_id, order_date, product_key, qty, amount, updated_at)
  VALUES (s.order_line_id, s.order_date, s.product_key, s.qty, s.amount, s.updated_at);

tools: dbt incremental strategies (merge, delete+insert, insert_overwrite), BigQuery and Spark partition overwrite, Snowflake and Databricks MERGE, Airflow and Dagster logical dates and partitions for backfills.

4Gains vs losses nothing is free

What we gain

  • Reruns are boring: retry, fix and backfill with the same job.
  • No duplicates after failures or scheduler retries.
  • Late updates handled (merge): a return can update an old day.
  • Backfills are just runs for past dates.

What we lose

  • Slice replace rewrites whole days even for one changed row.
  • MERGE reads the target to find matches, which costs on huge tables.
  • Needs a real key or a clean slice boundary.
  • Discipline: one now() breaks determinism.

6Common pitfalls the usual ways this goes wrong

  • Delete and insert in two transactions

    A crash between them leaves the day empty. Fix → one transaction, or an atomic partition overwrite.

  • Merge without a guard

    A late, older event overwrites the newer row. Fix → compare updated_at or log position in the WHEN MATCHED clause.

  • Hidden clock

    current_date in a model means a rerun on Thursday rebuilds the wrong day. Fix → use the run's logical date, passed in.

  • Duplicates in the batch itself

    Two versions of one key in a batch make MERGE fail or pick one at random. Fix → dedupe the batch to the latest version per key first.

7When to use it (and when not)

Use it when…

  • Every load into staging, facts and dimensions.
  • Any job a scheduler may retry automatically.
  • Pipelines that are backfilled after logic changes.
  • Change streams that may deliver an event twice.

Skip it when…

  • The raw landing layer: append there on purpose, and dedupe downstream.
  • One-off exports nobody will ever rerun (but they usually are).
  • Append-only logs where duplicates are filtered by an id later.

8Self-check quiz

What makes a load idempotent?

Running it twice gives the same table as running it once.

Why must delete and insert be in one transaction?

Otherwise a failure between them leaves the slice empty or half-loaded.

Why add a newer-only guard to a MERGE?

So a replayed or out-of-order older version doesn't overwrite a newer row.

Why is now() a problem inside a transform?

A rerun for a past period then gives a different answer; the period should be a parameter.

what would you do?Your scheduler retries failed tasks three times. A load into fact_sales appends rows and sometimes fails on a timeout after committing. Revenue is occasionally 2× for a day. What do you change?

Make the load replace its day (delete and insert in one transaction, or partition overwrite) or merge on order_line_id, so retries after a commit change nothing. Add a uniqueness test on order_line_id that fails the run.

try it

Write a load that appends a day's rows into a table. Run it twice and count rows. Change it to delete-and-insert in one transaction, run it three times, and compare the table with EXCEPT against a single run. Then add current_date somewhere and see your test break.

remember!!

Rub out the whole page, or match by line number. Never just add more lines.
