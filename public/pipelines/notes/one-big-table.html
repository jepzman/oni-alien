One Big Table vs Star

TL;DR

A one big table joins the fact with every dimension column into one wide, flat table: easy for BI tools, spreadsheets and ML, and cheap to scan on columnar engines. A star keeps facts and dimensions apart: reusable, easy to change, history-friendly. The common answer is both: model as a star, serve wide tables (or views) where a tool or team needs them, and rebuild them from the star.

  • Debate: Kimball vs Inmon vs wide tables
  • Lives in: BigQuery, ClickHouse, Snowflake, Druid
  • Pairs with: star schema, metrics layer

1The problem why do we even need this?

A store manager opens the BI tool and sees seven tables with lines between them. They drag product next to shop, the tool picks the wrong join path, the total doubles, and they go back to Excel exports.

  • Business users can't (and shouldn't have to) choose joins.
  • Some BI and ML tools work best on one flat table.
  • But a 300-column table rebuilt from scratch every night is expensive and fragile.

2Real-life analogy phone book vs card index

A printed phone book puts everything on one line: name, street, city, number. It's easy to read and terrible to correct: one moved family means a reprint. A card index with cross-references is harder to read, and you fix one card when something changes. Libraries kept the card index and printed directories from it.

3How it solves it star underneath, wide on top

Columnar engines store each column separately and compress repeated values, so a wide table with “Kitchen” repeated a million times costs little, and a query reads only the columns it names. That made one big tables practical. What they still cost: every dimension change (a type 1 fix, a new attribute) means rebuilding the wide table, and nothing is shared between wide tables.

Keep the star as the modelled source of truth. Build wide tables or views from it for the tools that need them, and treat them as disposable outputs.

  1. Model the star first

    Facts at a clear grain, conformed dimensions, type 2 where needed.

  2. Find the consumers

    Which tool or team needs flat data? Self-service BI, a spreadsheet extract, an ML feature set.

  3. Build the wide table from the star

    A view first; a table if it's slow. Only the columns they use.

  4. Rebuild it, don't edit it

    It's an output: regenerate from the star on every load.

  5. Keep definitions upstream

    Measures live in the star or the metrics layer, not in the wide table.

then & now rethought

Then Inmon, 1992 · Kimball, 1996

Inmon argued for a normalised enterprise warehouse feeding marts; Kimball for dimensional stars. Both avoided flattening everything: on row stores, wide tables wasted disk and every query read every column.

Now 2026

Columnar engines skip unused columns and compress repeated strings, so wide tables are cheap to scan, and some engines (ClickHouse, Druid) prefer them. Joins also got much cheaper. The debate moved from “which shape” to “which shape for whom”.

Verdict: Model as a star, serve wide tables to the tools that want them. Neither shape alone fits every reader.

4Gains vs losses nothing is free

What we gain

  • Easy for users: no joins to choose, no fan-out.
  • Fast scans on columnar engines.
  • Good for tools: BI self-service, spreadsheets, ML.
  • Simple to document: one table, one grain.

What we lose

  • Rebuild on any dimension change.
  • No reuse: each wide table repeats the same joins.
  • Schema churn: hundreds of columns, many unused.
  • History is frozen into whatever the row said at build time.

6Common pitfalls the usual ways this goes wrong

  • Only the wide table

    No star underneath; every new question copies and edits the 300-column SQL. Fix → keep the star as the source of truth.

  • Mixed grain in one table

    Order totals repeated on every line get summed by users. Fix → one grain per wide table; put order-level data in its own table.

  • Measures defined in the wide table

    Each wide table computes margin slightly differently. Fix → define measures once, upstream or in the metrics layer.

  • Everything, just in case

    600 columns nobody reads, rebuilt hourly. Fix → include what consumers use; add columns on request.

7When to use it (and when not)

Use it when…

  • Self-service BI for non-technical users.
  • Columnar engines that prefer wide tables (ClickHouse, Druid).
  • ML feature tables and spreadsheet extracts.
  • A dashboard with a fixed set of columns.

Skip it when…

  • As the only model of the warehouse.
  • Dimensions that change often and must be correct everywhere at once.
  • Many-to-many relationships that would multiply rows.

8Self-check quiz

What is a one big table?

A wide, flat table that joins facts with all their dimension columns.

Why are wide tables cheap on columnar engines?

Queries read only the columns they name, and repeated values compress well.

What does a wide table cost when a dimension changes?

It has to be rebuilt, because the old values are copied into every row.

What is the usual compromise?

Model as a star and build wide tables or views from it for the tools that need them.

what would you do?A product manager asks you to drop the star and keep only one big table, “because that's what everyone uses”. What do you answer?

Keep the star as the source of truth and generate the wide table from it on every load. Users keep their one table; you keep type 2 history, conformed dimensions for other facts, and the ability to rebuild everything when a definition changes.

try it

Build a view that flattens your star into one table, and point a BI tool at it. Count the clicks to answer “sales by region by month” with the star and with the view. Then change one product's category and see what each needs to reflect it.
