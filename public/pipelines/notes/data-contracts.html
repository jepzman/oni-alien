Data Contracts

TL;DR

When a pipeline reads another team's data, write down the agreement: fields and types, what each means, quality rules, freshness, the owner and a version. Keep the contract in the producer's repository, check it in their CI so breaking changes are blocked before release, and validate incoming data against it. Breaking changes become a new version that runs alongside the old one for a while.

1The problem why do we even need this?

The app team renames line_total to amount_gross in a normal Tuesday release. CDC carries the new column; the warehouse still reads the old one, which is now always empty. Revenue shows €0 for a week, until the finance meeting.

  • The app team didn't know anyone used that column.
  • The warehouse found out from its users, not from a test.
  • Every source change is a surprise, so the data team spends its weeks firefighting.

2Real-life analogy the supplier's spec sheet

A bakery and a supermarket agree a spec: an 800 g loaf, these label fields, delivered by 06:00. If the bakery wants to sell 750 g loaves, it announces version 2 a month ahead and supplies both for a while. The shelf never empties because of a change.

3How it solves it written down, owned by the producer, checked twice

The contract is a small file (YAML) in the producer's repository. Their CI compares every schema change with it: adding a nullable column passes; removing, renaming or retyping a field fails unless the version is bumped. At the warehouse door, the pipeline validates data against the same file and quarantines rows that don't fit.

The best contracts aren't on raw tables at all. The producer publishes a designed interface (a view, an outbox event, a published dataset) so their tables stay private and free to change.

  1. Find the critical inputs

    Which source fields do important reports depend on? Start with those.

  2. Write the contract with the producer

    Fields, types, nullability, meaning, rules, freshness, owner, version.

  3. Check it in their CI

    A breaking change fails the build unless it's a new version.

  4. Validate on arrival

    The pipeline checks schema and rules; failures go to quarantine and alert both teams.

  5. Version breaking changes

    Publish v3 alongside v2, migrate consumers, then retire v2 on a date.

Vocabulary for the exam

Data contract
A versioned agreement on a dataset's shape, meaning and quality.
Producer / consumer
The team that creates the data / the teams that use it.
Breaking change
Removing, renaming or retyping a field, or tightening its meaning.
Schema registry
A service storing message schemas and checking compatibility.
Deprecation
Announcing that a version will be retired on a date.
Data product
A dataset published for others with an owner and a contract.
contracts/order_lines.yamlODCS-style contract
dataset: shop.order_lines
version: 2.1.0
owner: team-checkout            # who to call, who approves changes
description: One row per order line, as charged to the customer.
freshness: { max_delay: 15m }
fields:
  - name: order_line_id   type: bigint   required: true   unique: true
  - name: order_id        type: bigint   required: true
  - name: sku             type: string   required: true
  - name: qty             type: int      required: true   min: 1
  - name: line_total      type: decimal(12,2)   required: true
    description: Gross amount charged in EUR, including VAT, after discounts.
  - name: updated_at      type: timestamp       required: true
breaking_changes: new major version, both served for 30 days

tools: Open Data Contract Standard (ODCS) and the Data Contract CLI, dbt model contracts (contract: enforced), Confluent Schema Registry with Avro or Protobuf compatibility modes, Soda and Great Expectations for the rules, Gable.

4Gains vs losses nothing is free

What we gain

  • Breaking changes caught before release, in the producer's CI.
  • Clear ownership: who to ask, who approves.
  • Meaning is written down: “gross, incl. VAT” is no longer folklore.
  • Producers stay free to change everything not in the contract.

What we lose

  • Upfront work and negotiation between teams.
  • Producers take on a duty they may resist.
  • Versioning effort: serving two versions for a while.
  • Contracts can rot if nobody checks them automatically.

6Common pitfalls the usual ways this goes wrong

  • Contracts nobody checks

    A wiki page describes the schema; the next release ignores it. Fix → check it in CI and at arrival, automatically.

  • Contracts on raw tables

    Every internal refactor of the app becomes a contract change. Fix → publish a designed view or event, and contract that.

  • Imposed by the data team

    Producers see it as someone else's paperwork and route around it. Fix → agree it together; start with the few fields that matter.

  • Schema only

    Types match, but “amount” switched from net to gross. Fix → write meaning and rules too, and test ranges and sums.

7When to use it (and when not)

Use it when…

  • Reports depend on another team's data.
  • Several consumers use the same source.
  • Sources change often or have broken pipelines before.
  • Data leaves your company (partners, regulators).

Skip it when…

  • Your own team produces and consumes the data in one repository.
  • Short-lived exploration.
  • A source that never changes and has one consumer.

8Self-check quiz

What does a data contract contain?

Fields and types, their meaning, quality rules, freshness, the owner and a version.

Where should the contract be checked first?

In the producer's CI, so a breaking change fails before it's released.

How should a breaking change be handled?

As a new version served alongside the old one, with a deprecation date.

Why contract a view or event rather than raw tables?

So the producer can change its own tables freely while the published interface stays stable.

what would you do?The checkout team says contracts will slow them down. Revenue broke three times this year from their changes. How do you start?

Start small and together: a contract for the five order-line fields revenue depends on, checked in their CI with a tool that only fails on breaking changes to those fields. Everything else stays free. Show them the three incidents it would have caught.

try it

Write a contract for one source table your reports use: five fields, their meaning in one sentence each, two rules, a freshness limit and an owner. Show it to the team that owns the table and ask which line surprises them.

remember!!

A spec sheet the producer owns. Changes come as a new version, never a surprise.
