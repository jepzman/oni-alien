Slowly Changing Dimensions

TL;DR

Dimension values change: a product moves category, a customer moves city. Decide per column what a change means. Type 1 overwrites (fix a typo; history follows the new value). Type 2 adds a new row with a new surrogate key and valid dates, so old facts keep the label they had. Type 3 keeps a “previous” column; type 6 mixes them. Use type 2 for anything reports group by.

  • Origin: Ralph Kimball (1990s)

1The problem why do we even need this?

In April the March report says Kitchen sold €412k. On 12 May the kettle moves to Small appliances and the product table is copied over the old dimension. In June, the same March report says Kitchen sold €371k. Nobody touched March's sales.

  • Filed reports change without anyone noticing.
  • “Sales by region last year” moves customers to where they live now.
  • Nobody can answer “what category was it in when we sold it?”

2Real-life analogy whiteboard vs address book

On a whiteboard you wipe the old address and write the new one: the old one is gone. In an address book you cross out the old address with an end date and write the new one underneath with a start date. Letters sent last year still went to the old address, and you can see that.

3How it solves it one new row per version, facts keep their key

A type 2 dimension has a surrogate key per version, the source's natural key (the SKU), and valid_from, valid_to and is_current. When a tracked column changes, the load closes the current row and inserts a new one. When a fact is loaded, it looks up the version that was valid at the event time, and keeps that key forever.

  1. Classify every column

    Type 1 (corrections, descriptions), type 2 (anything reports group or filter by), or type 0 (never changes, e.g. original signup date).

  2. Add version columns

    Surrogate key, natural key, valid_from, valid_to, is_current.

  3. Detect changes

    Compare tracked columns (or a hash of them) with the current row on each load.

  4. Close and insert

    Set valid_to on the old row, insert the new one with a new key, in one transaction.

  5. Look up by event time

    Facts join on the natural key where the sale time is between valid_from and valid_to.

Vocabulary for the exam

Type 0
Keep the original value forever.
Type 1
Overwrite; history follows the new value.
Type 2
New row and key per version, with valid dates.
Type 3
A column for the previous value.
Type 6
Type 2 rows plus a current-value column on every row (1 + 2 + 3).
Natural key
The source's id for the thing (SKU), shared by all versions.

from   stg_order_lines s
join   dim_product p
  on   p.sku = s.sku
 and   s.sold_at >= p.valid_from
 and   s.sold_at <  coalesce(p.valid_to, '9999-12-31')

then & now still core

Then Kimball, 1996

The Data Warehouse Toolkit named types 1, 2 and 3 and set out how to load them in ETL code, with surrogate keys generated by the ETL server and careful hand-written change detection.

Now 2026

The idea is unchanged and everywhere. dbt snapshots and MERGE build type 2 in a few lines; temporal tables and CDC give the history for free; columnar storage makes the extra rows cheap. Some teams skip type 2 dimensions and join facts to a full history table at query time instead.

Verdict: Still the way to keep reports stable as the business reorganises. Decide per column, and default to type 2 for anything people group by.

4Gains vs losses nothing is free

What we gain

  • Filed reports stay filed: March is March forever.
  • Both views: “as it was” and, with type 6, “as it is now”.
  • Audit: you can say when a category changed.
  • Cheap: dimensions are small; extra rows cost little.

What we lose

  • More complex loads: change detection, closing rows.
  • Lookups by date are easy to get wrong (boundaries).
  • Surprise for users: “why is the kettle in two categories?”
  • Fast-changing columns explode the row count.

6Common pitfalls the usual ways this goes wrong

  • Type 2 on everything

    A last-login column creates a new customer version every day. Fix → type 2 only for columns people group or filter by; move fast-changing ones to a fact or a mini-dimension.

  • Joining facts on the natural key

    Every fact matches every version and sales are multiplied. Fix → store the surrogate key on the fact, or join with the date range.

  • Overlapping or gapped dates

    A sale at exactly midnight matches two versions, or none. Fix → half-open ranges: >= valid_from AND < valid_to, and test for overlaps.

  • Late-arriving changes

    A category change is backdated after facts were loaded with the old key. Fix → re-key affected facts, or accept the change from its load date; decide with the business.

7When to use it (and when not)

Use it when…

  • Categories, regions, segments, price bands: anything reports group by.
  • Reports that are filed, audited or compared year on year.
  • Dimensions that change slowly (weekly or less).
  • Regulated reporting that must be reproducible.

Skip it when…

  • Typos and corrections: type 1.
  • Values that change every day: model them as facts.
  • Small reports where “as it is now” is all anyone asks.

8Self-check quiz

What does a type 2 change do?

Closes the current dimension row and inserts a new one with a new surrogate key and valid dates.

Why do facts store the surrogate key, not the natural key?

The surrogate key names one version; the natural key matches every version and multiplies rows.

When is type 1 right?

For corrections and descriptions where the past should show the fixed value.

What is type 6?

Type 2 rows that also carry the current value on every row, so reports can choose “as it was” or “as it is now”.

what would you do?Regional managers want last year's sales by the region each shop belongs to now, but finance wants them by the region at the time. One dimension, two answers. What do you build?

A type 6 shop dimension: type 2 rows with the historical region, plus a current_region column updated on every version. Finance groups by region, managers by current_region, both from the same fact table.

try it

Make a three-row product dimension with type 2 columns, a fact table pointing at it, and a monthly report. Change one product's category, apply type 1, and rerun the report for an old month. Undo, apply type 2, and rerun.

remember!!

Cross it out and date it. Facts remember the key they were sold under.
