Conformed Dimensions & the Bus Matrix

TL;DR

Build each dimension once (date, product, customer, shop) and share it across every fact table: sales, returns, web sessions, stock. Then any two processes can be compared by the attributes they share. Plan it with a bus matrix: business processes as rows, shared dimensions as columns. Combine facts by drilling across: aggregate each fact on its own, then join the results on the shared attributes.

  • Family: modelling
  • Origin: Kimball's enterprise data warehouse bus (1990s)
  • Tool: the bus matrix
  • Pairs with: bounded context, metrics layer

1The problem why do we even need this?

The sales team built dim_product from the ERP; the web team built its own from the website catalogue. The kettle is Kitchen in one and Kitchenware in the other, with different ids. “Return rate by category” combines both, and nothing lines up.

  • Each mart answers its own questions; none can be combined.
  • The same customer has three ids in three marts.
  • Every cross-team question becomes a one-off mapping project.

2Real-life analogy maps with one key

A city's transport map, bike map and tourist map share one key: the same district names and the same symbols. Lay one over another and they line up. If each map named the districts its own way, you couldn't plan a bike-and-tram trip.

3How it solves it shared dimensions, planned on one grid

Pick the business processes (rows) and the dimensions they share (columns). Build each column once, owned by one team, with one surrogate key and one set of attributes. A coarser fact (stock by month and category) uses a shrunken dimension that is a strict subset (dim_month, dim_category), so it still conforms.

To compare processes, never join two fact tables row to row (that multiplies rows). Aggregate each fact to the shared attributes first, then join the small results.

  1. List business processes

    Sales, returns, web sessions, stock: each becomes a fact table.

  2. Draw the bus matrix

    Mark which dimensions each process needs.

  3. Build each dimension once

    One owner, one key, one set of attribute names and values; map sources to it.

  4. Shrink, don't fork

    Coarser grains use subsets (month, category) of the same dimension.

  5. Drill across

    Aggregate each fact separately, join on shared attributes.

Vocabulary for the exam

Conformed dimension
A dimension shared, identically, by several facts.
Bus matrix
Processes × dimensions grid, used to plan a warehouse.
Drill across
Combining results from two facts via shared attributes.
Shrunken dimension
A conformed subset at a coarser grain (month, category).
Fan-out
Rows multiplied by joining two facts directly.
Master data
The agreed, cleaned version of core entities across systems.
return_rate_by_category.sqldrill across
with sales as (
    select p.category, sum(f.qty) as sold
    from fct_sales f join dim_product p using (product_key)
    where f.date_key between 20260101 and 20260331
    group by 1
),
returns as (
    select p.category, sum(r.qty) as returned
    from fct_returns r join dim_product p using (product_key)   -- the same dimension
    where r.date_key between 20260101 and 20260331
    group by 1
)
select s.category, s.sold, coalesce(r.returned, 0) as returned,
       round(100.0 * coalesce(r.returned, 0) / s.sold, 1) as return_rate_pct
from sales s left join returns r using (category);

tools: dbt (one model per dimension, referenced by every mart), metrics layers that join facts through shared dimensions (dbt Semantic Layer, Cube, LookML explores), master data tools for the source mapping.

then & now matters more now

Then Kimball, 1998

The Data Warehouse Lifecycle Toolkit introduced the bus architecture: build marts one process at a time, but on conformed dimensions agreed up front, recorded in a bus matrix.

Now 2026

More sources and more teams make it matter more: SaaS tools, web events and acquisitions each bring their own customer and product. Metrics layers rely on conformed dimensions to join facts safely, and data mesh teams publish them as shared data products.

Verdict: Agree the shared dimensions before the second fact table. The bus matrix is still the cheapest planning tool in analytics.

4Gains vs losses nothing is free

What we gain

  • Cross-process questions just work.
  • One definition of category, region, customer.
  • Incremental build: add processes one at a time.
  • Safe joins through shared attributes.

What we lose

  • Agreement takes time between teams.
  • A shared owner becomes a dependency.
  • Source mapping (ERP id to web id) is real work.
  • Changes ripple to every mart that uses the dimension.

6Common pitfalls the usual ways this goes wrong

  • Joining two facts directly

    Sales joined to returns on product multiplies rows and doubles totals. Fix → aggregate each fact first, then join (drill across).

  • “Almost conformed”

    The web team adds two extra categories, so totals differ by a few percent. Fix → a shrunken or extended dimension must map exactly; test that sums match.

  • No owner

    Everyone edits dim_customer and it drifts. Fix → one owning team; others request changes.

  • Waiting for the perfect model

    A year of meetings before the first mart. Fix → agree the matrix and the first two dimensions, then build process by process.

7When to use it (and when not)

Use it when…

  • Two or more business processes share dimensions.
  • Several teams build marts.
  • Data comes from several source systems for the same entities.
  • You want a metrics layer to join facts safely.

Skip it when…

  • One fact table, one team: just build the star.
  • Exploration sandboxes that will be thrown away.
  • Forcing unrelated domains to share a dimension they don't share.

8Self-check quiz

What makes a dimension conformed?

It is shared, identically (same keys, attributes and values), by several fact tables.

What is a bus matrix?

A grid of business processes against shared dimensions, marking which process uses which dimension.

Why not join two fact tables directly on product?

Each side has many rows per product, so the join multiplies rows; aggregate each side first.

What is a shrunken dimension?

A conformed subset at a coarser grain, such as month from date or category from product.

what would you do?The shop buys a second chain whose product codes differ from yours. Management wants combined sales by category next month. What do you do?

Keep one dim_product as the conformed dimension. Map the new chain's codes to it (or add its products with your category values) in staging, owned by the dimension's team, and load the new chain's sales into the same fct_sales. Test that category totals match the new chain's own reports.

try it

Draw a bus matrix for your own data: four business processes down the side, five dimensions across. Mark the crosses. Circle every dimension that exists twice today under different names.
