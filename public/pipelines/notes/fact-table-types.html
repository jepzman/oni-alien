Fact Table Types

TL;DR

Not every question is a sum of events. Transaction facts store one row per event (sales lines). Periodic snapshots store the state of something each period (stock at month end). Accumulating snapshots store one row per process instance, updated at each milestone (order placed → delivered). Factless facts record that something happened or applied, with no number (products on promotion). Start every fact table by writing down its grain.

1The problem why do we even need this?

The shop has one fact table: order lines. Then three questions arrive. Stock on hand at each month end means summing five years of stock movements in every query. Days from order to delivery means joining four status tables to themselves. Promotions that sold nothing has no rows to count, because nothing was sold.

2Real-life analogy four bank documents

Your bank gives you four kinds of document. A transaction list (every payment), a monthly statement (the balance on the last day), an application tracker for your mortgage (one line, with the date of each step), and, at school, a class register (who was there, no amounts). Each answers different questions, and you wouldn't compute your balance from twenty years of payments every time.

3How it solves it choose by the question, state the grain

The grain says what one row is. Write it down before choosing columns: “one row per order line”, “one row per product per shop per month”, “one row per order”. Measures must fit the grain, and the type follows from the question. Transaction measures add up across everything. Snapshot balances add across shops but not across time (average or take the last). Accumulating rows are updated as milestones happen, so they need idempotent merges.

  1. Write the grain

    One sentence: “one row per …”. If you can't, the table isn't designed yet.

  2. Pick the type from the question

    Events → transaction; state over time → periodic snapshot; a process with steps → accumulating; coverage or attendance → factless.

  3. Add dimensions at that grain

    Date, product, shop, customer, promotion.

  4. Mark measure additivity

    Additive, semi-additive (balances), non-additive (ratios: store the parts).

  5. Load accordingly

    Append or merge; snapshot each period; update milestones; insert coverage rows.

Vocabulary for the exam

Grain
What one fact row represents.
Additive
Can be summed across every dimension (amount).
Semi-additive
Sums across some dimensions, not time (stock on hand).
Non-additive
Can't be summed (a ratio); store numerator and denominator.
Lag
Days between two milestones in an accumulating row.
Coverage table
A factless fact recording what applied, e.g. promotions.
fact_tables.sqlgeneric warehouse DDL
-- periodic snapshot: state at the end of each month
CREATE TABLE fct_stock_monthly (
  month_key int, product_key int, shop_key int,
  on_hand int,               -- semi-additive: sum across shops, not months
  on_order int
);

-- accumulating snapshot: one row per order, updated at each milestone
CREATE TABLE fct_order_lifecycle (
  order_id bigint PRIMARY KEY,
  placed_date_key int, paid_date_key int, shipped_date_key int, delivered_date_key int,
  days_to_ship int, days_to_deliver int,
  order_amount numeric
);

-- factless: which products were on which promotion, each day
CREATE TABLE fct_promo_coverage (date_key int, product_key int, promo_key int, shop_key int);

-- “promoted but sold nothing” = coverage EXCEPT sales
SELECT date_key, product_key, promo_key FROM fct_promo_coverage
EXCEPT
SELECT date_key, product_key, promo_key FROM fct_sales;

tools: any warehouse; dbt incremental models for snapshots (one partition per period) and merges for accumulating rows; BI tools need semi-additive measures declared (LookML, Power BI, Cube).

then & now still core

Then Kimball & Ross, 2002

The second edition of The Data Warehouse Toolkit set out the three fact table types plus factless facts as the core of dimensional design, built because summing raw transactions was too slow on row stores.

Now 2026

Columnar engines can sum billions of transactions quickly, so some snapshots are now views over transactions. But the questions haven't changed: balances still can't be summed over time, and processes still have milestones. Metrics layers now ask you to declare the same additivity rules.

Verdict: Still the vocabulary every analytics engineer needs. Write the grain first, every time.

4Gains vs losses nothing is free

What we gain

  • Each question gets a fast, natural shape.
  • Clear grain stops double counting.
  • Process metrics (lags) become one column.
  • “What didn't happen” becomes answerable.

What we lose

  • More tables to build and explain.
  • Snapshots duplicate state every period.
  • Accumulating rows are updated, so loads must merge.
  • Semi-additive traps for unaware users.

6Common pitfalls the usual ways this goes wrong

  • Mixed grain

    Order-level shipping cost stored on every order line, then summed. Fix → store measures only at their own grain, or allocate them explicitly.

  • Summing balances over time

    “Total stock in Q1” adds three month-ends together. Fix → declare on_hand semi-additive; use last or average over time.

  • Ratios stored as facts

    Average margin per line is averaged again in the report. Fix → store the parts (revenue, cost) and divide at query time.

  • Accumulating rows appended

    Each milestone adds a new row, and orders are counted four times. Fix → merge on the order id; one row per order.

7When to use it (and when not)

Use it when…

  • Any new fact table: start with the grain.
  • Balances and levels: stock, account balances, headcount.
  • Processes with steps: orders, claims, tickets, onboarding.
  • Coverage or eligibility: promotions, rosters, enrolments.

Skip it when…

  • When one transaction fact and a fast engine already answer the question well.
  • Processes with many loops and unknown steps: an event table fits better.
  • Snapshots nobody reads; generate them on demand from transactions.

Related patterns

  • Star schema (Vol. 3)
  • Aggregates and rollups
  • Idempotent loads

8Self-check quiz

What is the grain of a fact table?

A precise statement of what one row represents, e.g. one row per order line.

Why can't you sum stock on hand across months?

It is a balance (semi-additive): each month-end repeats the stock; take the last or the average over time.

How does an accumulating snapshot change over time?

Its row for each order is updated as milestones happen, filling in dates and lags.

How do you find promotions that sold nothing?

Compare a factless coverage table with the sales fact: coverage rows with no matching sales.

what would you do?Customer service wants “average days from order to delivery, by carrier, by week”. Today they join orders to four status tables and it takes minutes. What do you build?

An accumulating snapshot, fct_order_lifecycle: one row per order with a date key per milestone and days_to_deliver, merged on order_id as statuses arrive. The question becomes an average of one column grouped by carrier and week.

try it

Take your sales table and write its grain in one sentence. Then write the grain for “stock at month end” and for “order to delivery”. If either needs a new table, sketch its columns and mark each measure additive, semi-additive or non-additive.

remember!!

Grain first. Payments, balances, trackers and registers are different documents.
