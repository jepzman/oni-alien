ETL vs ELT

TL;DR

ETL transforms data on its way to the warehouse and stores only the result. ELT copies the source data into the warehouse unchanged, then transforms it there with SQL. Cheap columnar storage made ELT the default: keep the raw data, and any transform can be fixed and rerun over the whole history. Transform before loading only what must never be stored, such as card numbers.

  • Family: getting data in
  • Origin: ETL tools of the 1990s; ELT with cloud warehouses, 2012+
  • Lives in: dbt, SQLMesh, Fivetran, Airbyte
  • Pairs with: layered zones, idempotent loads

1The problem why do we even need this?

Since 2019 the shop's nightly job reads orders, applies tax rules and the category mapping in a Python script, and writes daily totals by category to the warehouse. Fourteen months later finance finds that refunds were taxed twice. The raw orders were never stored in the warehouse, and the app has changed since, so the past cannot be recomputed.

  • Logic in the extract: business rules live in a script on a server nobody owns, untested and unversioned.
  • Only the answer is kept: “revenue by hour” or “by customer segment” needs a new job, and has no history.
  • A bug is permanent: the input is gone, so the output can never be corrected.

2Real-life analogy meal kit vs pantry

A meal kit arrives cut and portioned for one recipe. Convenient, but if the recipe was wrong, the vegetables are already diced. A pantry of whole groceries takes more room, and you cook any recipe from it later, or cook it again.

  • Pantries were expensive when shelf space was. Cloud warehouses made shelf space cheap.
  • Some things you still prepare before they come in: you don't store what you're not allowed to keep.

3How it solves it extract, load, then transform in SQL

The extract and load step is a copy and nothing more: tables land in a raw schema as they were in the source, with a load timestamp. The transform step is a set of SQL models in git that build staging tables and then marts. They run inside the warehouse, so they scale with it, and they can be tested and reviewed like any other code.

  1. Copy, don't change

    A connector (Fivetran, Airbyte, Debezium or your own) lands source tables in raw, unchanged.

  2. Mask only what must be

    Drop or hash card numbers and secrets before landing; nothing else happens in flight.

  3. Write transforms as SQL models

    One file per table: staging models clean, mart models shape. Versioned in git.

  4. Test and review them

    Unique keys, not-null columns, accepted values, run in CI and on every load.

  5. Rerun freely

    A changed rule means change the model and rebuild; the raw data is still there.

Vocabulary for the exam

ETL
Extract, transform, load: shape the data before it reaches the warehouse.
ELT
Extract, load, transform: land raw data, shape it inside the warehouse.
Raw
Source data stored as it arrived, never edited.
Model
One SQL SELECT that builds one table or view (dbt's word).
Connector
The tool that copies data from a source into the warehouse.
Reverse ETL
Copying warehouse results back into apps such as a CRM.

select
    s.order_date,
    p.category,
    sum(s.amount_net)                  as revenue_net,
    sum(s.amount_net * s.tax_rate)     as tax
from {{ ref('fct_sales') }}   s

then & now rethought

Then Kimball & Caserta, 2004

The Data Warehouse ETL Toolkit describes a separate ETL server that cleans, conforms and loads data, because warehouse disk and CPU were expensive. Only the finished, conformed tables were stored; the staging area was temporary.

Now 2026

Columnar cloud warehouses split storage from compute, and keeping raw data costs little. Transforms became SQL in git, tested and reviewed (dbt, from 2016). ETL survives where data must be masked before landing, and inside streaming jobs that enrich events in flight.

Verdict: Load first and keep raw; transform in the warehouse. Transform before loading only what must never be stored.

4Gains vs losses nothing is free

What we gain

  • History can be fixed: change a rule and rebuild every year from raw.
  • New questions are cheap: the detail is there, not just yesterday's totals.
  • Logic is code: SQL in git, reviewed, tested, with lineage.
  • One engine: transforms scale with the warehouse, not a side server.

What we lose

  • More storage: raw and every layer are kept.
  • Sensitive data lands unless you mask it in flight on purpose.
  • Warehouse compute bills grow with every rebuild.
  • SQL sprawl: hundreds of models need naming rules and ownership.

6Common pitfalls the usual ways this goes wrong

  • Transforming in the loader

    Business rules creep into connector settings and scripts again. Fix → keep the load a plain copy; every rule is a model.

  • Raw that isn't raw

    Someone “cleans up” raw in place, and the original is gone. Fix → make raw append-only and read-only for everyone but the loader.

  • Personal data landed by accident

    A new source column with card numbers lands in raw and is queryable. Fix → mask or drop listed columns in flight, and scan raw for patterns.

  • Rebuild everything, every hour

    Full rebuilds of large models eat the compute budget. Fix → build big models incrementally (idempotent loads); rebuild fully only after a logic change.

7When to use it (and when not)

Use it when…

  • A warehouse with cheap storage and SQL compute.
  • Rules that change and need to apply to the past.
  • Analysts who ask new questions every week.
  • Several sources that have to be combined.

Skip it when…

  • Data that must be masked or dropped before it may be stored: do that part in flight.
  • Streams that must be enriched in milliseconds; transform in the stream processor.
  • A tiny report from one table, where a view on a read replica is enough.

Related patterns

  • Layered zones
  • Idempotent loads
  • Star schema (Vol. 3)
  • Change data capture (Vol. 3)

8Self-check quiz

What does ELT change compared with ETL?

The data is loaded unchanged first, and transformed inside the warehouse with SQL, so raw data is kept.

Why can an ELT pipeline fix last year's numbers?

Raw data is still stored; change the model and rebuild it over all history.

When should you still transform before loading?

For data that must never be stored, such as card numbers: mask or drop it in flight.

What is a model in dbt?

A SQL SELECT in a file that builds one table or view, referencing other models.

what would you do?Finance finds that a discount was counted twice in revenue since January. Your pipeline stores only monthly totals. What do you change, beyond fixing the formula?

Start landing the order lines unchanged in raw and build revenue as a SQL model from them. Then the fix is a change to one model and a rebuild; for January to now, reload the order lines from the source (or a backup) once.

try it

Take one report built by a script. Land its source tables unchanged in a raw schema (DuckDB is enough), rewrite the logic as two SQL views (staging, then the report), and change one rule. Rebuild and compare last year's numbers before and after.

remember!!

Keep the groceries, not just the meal. Transform in the warehouse, and you can always cook it again.
