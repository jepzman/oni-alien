a.k.a. “hubs, links and satellites”

Data Vault

TL;DR

When many sources describe the same things and keep changing, put an insert-only integration layer between staging and the marts. Hubs hold business keys (customer number). Links hold relationships (order ↔ customer). Satellites hold descriptive attributes, per source, dated and never updated. A new source adds satellites without touching what exists, and you can answer “what did each source say, when?”. Stars for reporting are built on top.

1The problem why do we even need this?

Customers reach the warehouse from the ERP, the web store, the CRM, the loyalty app, and now the ERP of a chain the shop bought. Each new or changed source means rewriting dim_customer and its load. Then an auditor asks what the CRM said about customer 77 on 1 March, and nobody can say.

2Real-life analogy the library card catalogue

An old library catalogue has one card per book, identified by its ISBN, that never changes. Cross-reference cards link a book to its authors. Behind each card, librarians pin dated slips with notes; nobody erases a slip, they add a newer one. A new librarian adds their own slips without rewriting anyone else's.

3How it solves it keys, relationships and dated details, apart

Splitting keys, relationships and attributes means each changes independently. Hubs and links almost never change shape. A new source adds a satellite. A changed source adds columns to its own satellite. Every table is insert-only with a load date and record source, so the vault is a full, auditable history. Hash keys computed from business keys let every table load in parallel without lookups.

The vault is not for reporting. Stars (often as views) are built on top for the marts.

  1. Find the business keys

    Customer number, order number, SKU: what the business uses, not database ids.

  2. Build hubs

    One per key, with a hash key, load date and source.

  3. Build links

    One per relationship or transaction between hubs.

  4. Build satellites

    Split by source and by how fast attributes change; insert a row when the hash of attributes changes.

  5. Build marts on top

    Star schemas (views or tables) read the latest or point-in-time satellite rows.

Vocabulary for the exam

Hub
Unique list of business keys for one concept.
Link
Unique list of relationships between hubs.
Satellite
Descriptive, dated attributes of a hub or link.
Hash key
A hash of the business key, used as the join key.
Hashdiff
A hash of a satellite's attributes, to detect changes.
PIT table
Point-in-time helper that speeds up “as of” queries.
vault.sqlgeneric warehouse SQL
CREATE TABLE hub_customer (
  customer_hk  char(32) PRIMARY KEY,   -- md5(upper(trim(customer_no)))
  customer_no  text, load_date timestamp, record_source text);

CREATE TABLE sat_customer_crm (
  customer_hk char(32), load_date timestamp, hashdiff char(32),
  name text, city text, record_source text,
  PRIMARY KEY (customer_hk, load_date));

-- insert-only: add a satellite row only when the attributes changed
INSERT INTO sat_customer_crm
SELECT s.customer_hk, :load_ts, s.hashdiff, s.name, s.city, 'crm'
FROM   stg_crm_customers s
LEFT JOIN (SELECT customer_hk, hashdiff,
                  row_number() OVER (PARTITION BY customer_hk ORDER BY load_date DESC) rn
           FROM sat_customer_crm) cur
  ON cur.customer_hk = s.customer_hk AND cur.rn = 1
WHERE  cur.hashdiff IS DISTINCT FROM s.hashdiff;

tools: AutomateDV (formerly dbtvault) for dbt, datavault4dbt, WhereScape, VaultSpeed, Coalesce; any warehouse with MERGE or insert-select.

then & now rethought

Then Linstedt, 2000

Dan Linstedt designed the data vault in the 1990s for large enterprise warehouses: a normalised, auditable integration layer loaded by hand-written ETL, with sequence keys and many sources.

Now 2026

Data Vault 2.0 (2013) replaced sequence keys with hash keys for parallel loads, and tools now generate most of the SQL. It is common in banks, insurers and large multi-source shops, usually under a layer of stars. Smaller teams with a few sources mostly skip it for staging plus stars.

Verdict: Worth it when many changing sources and audit needs meet. Generate it with a tool; never hand-write a vault for three sources.

4Gains vs losses nothing is free

What we gain

  • New sources are additive: new satellites, no rewrites.
  • Full, auditable history per source.
  • Parallel loads: hash keys, no lookups.
  • Resilient to source change: damage stays in one satellite.

What we lose

  • Many tables and joins: a vault is hard to query directly.
  • Needs a layer on top for any report.
  • Steep learning curve and modelling rules.
  • Overkill for a few stable sources.

6Common pitfalls the usual ways this goes wrong

  • Reporting from the vault

    Analysts join twelve tables to get a customer's city. Fix → build stars or views on top; grant only those.

  • Source keys as business keys

    Each system's internal id becomes a hub, and nothing integrates. Fix → find the key the business uses, and map sources to it.

  • One giant satellite

    Fast-changing points and slow-changing names share one satellite; it grows on every change. Fix → split satellites by source and by rate of change.

  • Hand-written vault

    Hundreds of near-identical load scripts with subtle differences. Fix → generate loads from metadata with a tool or macros.

7When to use it (and when not)

Use it when…

  • Many sources for the same entities, and more coming.
  • Sources that change shape often.
  • Audit or regulation needs “what did each source say, when”.
  • Several teams loading in parallel.

Skip it when…

  • A few stable sources: staging plus type 2 stars is enough.
  • A small team without tooling to generate the SQL.
  • Purely analytical sandboxes.

Related patterns

  • Layered zones
  • Slowly changing dimensions
  • Bitemporal data (Vol. 3)
  • Conformed dimensions

8Self-check quiz

What do hubs, links and satellites hold?

Hubs: business keys. Links: relationships between keys. Satellites: dated descriptive attributes.

Why are vault tables insert-only?

So the full history per source is kept and loads are simple, parallel and auditable.

What happens when a new source arrives?

It adds its own satellites (and maybe hubs or links) without changing existing tables.

Why build stars on top of a vault?

A vault is hard to query; stars give analysts simple, fast tables.

what would you do?Your shop has three sources and two analysts. A consultant proposes a data vault. Is it worth it?

Probably not yet: three stable sources fit staging plus type 2 dimensions in stars, which is far simpler. Revisit if sources multiply (acquisitions), change often, or an auditor needs per-source history; then generate the vault with a tool.

try it

Model the shop's customers from two sources (CRM and loyalty app) as one hub and two satellites. Load two days of data where only the loyalty tier changes on day 2. Count rows in each satellite, then write the query for “the customer's city and tier on day 1”.

remember!!

Keys in hubs, relationships in links, dated details in satellites. Never erase a slip.
