DAG Orchestration & Lineage

TL;DR

Describe the pipeline as a graph of steps and their inputs (a DAG), and let a scheduler run each step when everything it depends on has succeeded for that period, with retries and alerts. Runs are per period (logical date), so backfills are the same graph for old dates. The same graph is your lineage: trace a wrong number back to its source, and a broken source forward to every affected report.

1The problem why do we even need this?

Three cron jobs: extract at 01:00, transforms at 03:00, dashboard refresh at 06:00. One night the extract runs until 03:40. The transforms start at 03:00 on half the data, the dashboards refresh with half a day, and when finance asks which reports are wrong, nobody can say.

  • Timings are guesses; slack is added until the pipeline takes all night.
  • A failure upstream doesn't stop the steps after it.
  • There's no map of what feeds what.

2Real-life analogy baking a cake

You bake, then cool, then ice. You ice when the cake has cooled, not at three o'clock. If the cake burns, you know exactly which steps to redo, and which other dishes used the same oven batch.

3How it solves it steps, dependencies, periods

Each step declares its inputs. The scheduler starts the graph on a schedule (or when new data arrives) and runs each step as soon as its inputs succeeded for the same period, with retries and backoff. If a step fails, nothing downstream runs, and the owner is alerted. Each run is for a logical date, so a backfill is the same graph run for old periods, which only works if every step is idempotent.

Because dependencies are declared, the graph doubles as lineage: tools draw it, and you can ask “what feeds this dashboard?” or “what breaks if this source is late?”.

  1. Declare inputs, not times

    Each step lists what it reads; only the first step has a schedule.

  2. Run per period

    Pass the logical date to every step; no now().

  3. Retry, then alert

    Retries with backoff for flaky sources; a clear owner when retries run out.

  4. Set deadlines

    Alert if the revenue dashboard isn't fresh by 07:00, whatever the reason.

  5. Publish lineage

    Table- and column-level lineage from the DAG and SQL, so impact is one click away.

Vocabulary for the exam

The period a run is for.
Sensor
A step that waits for data to arrive.

sales_daily.pyAirflow 2 TaskFlow
from airflow.decorators import dag, task
from pendulum import datetime

@dag(schedule="0 1 * * *", start_date=datetime(2026, 1, 1), catchup=False,
     default_args={"retries": 3, "retry_exponential_backoff": True})
def sales_daily():
    @task
    def extract(table, ds=None):          # ds = the logical date, passed in
        load_raw(table, day=ds)

    @task
    def transform(ds=None):               # dbt build for that day, tests included
        run_dbt("build --select fct_sales+", vars={"day": ds})

    @task
    def refresh_dashboards(ds=None):
        refresh("revenue", day=ds)

    [extract("orders"), extract("order_lines"), extract("products")] >> transform() >> refresh_dashboards()

4Gains vs losses nothing is free

What we gain

  • Steps run when inputs are ready: no guessing, no slack.
  • Failures stop downstream instead of spreading.
  • Backfills are just runs for old periods.
  • Lineage for free: impact and root cause in a click.

What we lose

  • A scheduler to run and keep upgraded.
  • Python and config to learn.
  • One broken step blocks everything after it (on purpose).
  • Graphs grow into hundreds of steps without naming rules.

6Common pitfalls the usual ways this goes wrong

  • Times between steps

    Each task still has its own cron time inside the scheduler. Fix → schedule only the start; everything else waits on dependencies.

  • Non-idempotent tasks

    Retries and backfills duplicate data. Fix → make every task safe to run twice for the same period.

  • Work inside the scheduler

    Heavy transforms run on the scheduler's workers and starve it. Fix → the scheduler triggers; the warehouse or a job runner does the work.

  • Lineage that stops at the warehouse

    Nobody knows which dashboards use a table. Fix → include BI dashboards and exports in lineage.

7When to use it (and when not)

Use it when…

  • More than two steps that depend on each other.
  • Pipelines that are retried or backfilled.
  • Several teams' pipelines sharing tables.
  • Deadlines that matter (“fresh by 07:00”).

Skip it when…

  • One script that runs once a day and nothing depends on.
  • Pure streaming pipelines; they run continuously.
  • Replacing a scheduler you have with another for fashion.

8Self-check quiz

What does a DAG scheduler use to decide when a step runs?

Whether all the step's upstream dependencies succeeded for the same period.

Why pass a logical date to every task?

So each run is for a specific period and backfills rerun the same code for old dates.

What does lineage let you answer?

What a dataset is built from, and what is affected if a source is broken or late.

Why must tasks be idempotent?

Schedulers retry them and backfills rerun them; they must not duplicate data.

what would you do?Finance asks every Monday “is the dashboard right today?”. Your jobs are cron entries an hour apart. What do you build first?

Put the jobs in one DAG with declared dependencies so nothing runs on half-finished inputs, add a freshness deadline alert for 07:00, and show “data as of” on the dashboard. Then finance sees the answer before asking.
