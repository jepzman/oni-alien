Multi-tenant & Embedded Reporting

TL;DR

When customers, shops or franchisees see reports inside your product, each must see only their own rows, and their dashboards mustn't slow the app down. Take the tenant from a signed token issued by your backend, never from the URL; enforce it with row-level security in the data layer, not only in the dashboard; and serve from the warehouse or a serving store with per-tenant aggregates and caching, not from production.

1The problem why do we even need this?

Each shop manager gets a “my shop” dashboard that filters on ?shop=12 in the address. The Delft manager changes it to 13 and sees Leiden's revenue. The same dashboards query the production database, and on Saturdays checkout slows down.

  • Tenant filters in the browser are suggestions, not security.
  • Every new report must remember to filter, and one will forget.
  • Reporting load competes with customers paying.

2Real-life analogy apartment mailboxes

An apartment building has one wall of mailboxes. The postman sorts mail into them, and each resident's key opens only their own box. Nobody is handed the whole sack and trusted to take only their own letters.

3How it solves it tenant from a token, enforced on every row

Your backend, which knows who signed in, issues a short-lived signed token (a JWT) with the tenant id and the reports allowed. The embedded dashboard passes it to the reporting layer, which sets the tenant for the session. A row-level security policy on the tables then adds the tenant condition to every query, including ones a careless report author writes.

Serve from the warehouse or a fast serving store, with aggregates per tenant and a cache. Give big tenants their own extracts or limits so one franchisee's export can't slow the others.

  1. Put tenant ids on every row

    Shop, franchisee or customer id on facts and aggregates.

  2. Issue signed embed tokens

    From your backend, with tenant id, allowed reports and a short expiry.

  3. Enforce row-level security

    A policy in the warehouse or semantic layer that reads the tenant from the session.

  4. Serve away from production

    Warehouse or serving store; per-tenant aggregates; cache; per-tenant query limits.

  5. Test the boundary

    An automated test that signs in as shop 12 and tries to read shop 13.

row_access.sql + embed.tsSnowflake-style policy · TypeScript
-- the database enforces the tenant on every query
CREATE ROW ACCESS POLICY shop_only AS (shop_id INT) RETURNS BOOLEAN ->
  shop_id = TRY_TO_NUMBER(CURRENT_SESSION_CONTEXT('shop_id'))   -- set from the token
  OR IS_ROLE_IN_SESSION('HEAD_OFFICE');
ALTER TABLE agg_sales_daily ADD ROW ACCESS POLICY shop_only ON (shop_id);

// the portal backend: the tenant comes from the signed-in user, never the URL
app.get("/reports/embed", requireLogin, (req, res) => {
  const token = jwt.sign(
    { shop_id: req.user.shopId, reports: ["my-shop"], exp: nowSeconds() + 600 },
    process.env.EMBED_SECRET,
  );
  res.json({ url: `${REPORTS_URL}/embed/my-shop#token=${token}` });
});

4Gains vs losses nothing is free

What we gain

  • Tenants see only their own data, whatever the URL says.
  • Enforced once, in the data layer, for every report.
  • App stays fast: reports never touch production.
  • New reports are safe by default.

What we lose

  • Token plumbing between app, BI tool and warehouse.
  • Policies to test on every table and aggregate.
  • Serving costs for app-facing query volumes.
  • Cross-tenant questions need a separate, privileged role.

6Common pitfalls the usual ways this goes wrong

  • Tenant from the URL or the browser

    Anyone can edit it. Fix → tenant only from a token your backend signs.

  • Filters in each report

    One new report forgets the WHERE and shows everyone's numbers. Fix → row-level security on the tables, so forgetting is impossible.

  • Long-lived tokens

    A token copied into an email works for months. Fix → expire tokens in minutes and re-issue on page load.

  • Shared caches across tenants

    A cached result for shop 12 is served to shop 13. Fix → include the tenant in every cache key.

7When to use it (and when not)

Use it when…

  • Reports shown inside your product to customers or partners.
  • Internal dashboards where managers must see only their area.
  • Many tenants on shared tables.
  • Reporting load that must not touch production.

Skip it when…

  • Head office reporting where everyone may see everything.
  • A tiny number of tenants with separate databases already.
  • Data so sensitive it should be physically separate per tenant.

8Self-check quiz

Where must the tenant id come from?

From a token signed by your backend for the signed-in user, never from the URL or browser.

Why enforce tenancy with row-level security rather than report filters?

So every query is filtered, including reports that forget, and nobody can bypass it.

Why not serve embedded reports from production?

Report queries compete with the app and slow it down; serve from the warehouse or a serving store.

What must cache keys include?

The tenant, so one tenant's cached results are never served to another.

what would you do?A franchisee asks for a CSV export of “all their sales ever” every morning, and it slows other franchisees' dashboards. What do you do?

Give heavy exports their own path: a nightly per-tenant extract written to storage, or a query queue with per-tenant limits. Dashboards keep using aggregates; the export never competes with them. Row-level security still applies to the export query.

try it

Open one of your dashboards and look for where the tenant comes from. Try changing it in the address or the request. Then add a test that signs in as one tenant and tries to read another's data, and keep it in CI.

remember!!

Your key, your box. Never hand out the sack.
