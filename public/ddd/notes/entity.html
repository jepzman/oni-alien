Entity

TL;DR

An entity is something the business tracks through time: a customer, an order, a parcel. It has an identity that never changes (an ID you generate, not an email or a name), while its other details do change, through methods with business names that check the rules. Two entities are equal only if their IDs are equal.

  • Family: tactical building block
  • From: Evans (2003), ch. 5
  • Identity: UUID or ULID, created by the app
  • Pairs with: value object, aggregate

1The problem why do we even need this?

When identity is tied to data that changes, one thing splits in two, or two things merge into one.

  • A customer changes email and loses their order history.
  • Two John Smiths become one record.
  • Setters let any code change anything, so rules are skipped.

2Real-life analogy a person through life

Over a lifetime a person changes name, address, hair and job, yet they are the same person, tracked by a passport number that never changes. Two people with the same name and birthday are still two people.

  • The person is an entity.
  • The passport number is its identity.
  • The address is a value that gets replaced when they move.

3How it solves it identity plus behaviour

Keep entities small: identity, a few attributes, and the behaviour that changes them. Push details into value objects. And prefer methods named after business actions over public setters.

  1. Ask “is it tracked over time?”

    If the business cares which one it is, not just what it contains, it's an entity.

  2. Generate the ID early

    A UUID v7 or ULID created in the code when the entity is born, not by the database later.

  3. Never use changing data as the ID

    Not email, name or address. Those are attributes.

  4. Replace setters with actions

    order.ship(), customer.moveTo(address), each checking its rules.

  5. Equality by ID

    Two Customer objects with the same ID are the same customer.

  6. Extract value objects

    Address, Money, EmailAddress live inside the entity as values.

Vocabulary for the exam

Entity
An object with a lasting identity whose attributes can change.
Identity
What makes it the same thing over time: usually a generated ID.
Natural key
An ID taken from the data (email, tax number); risky if it can change.
Surrogate key
An ID with no meaning, generated for the purpose.
Lifecycle
The states an entity goes through, from creation to archive.
UUID v7 / ULID
Unique IDs that also sort by creation time.
customer.tsan entity: ID plus behaviour
export class Customer {
  private constructor(
    readonly id: CustomerId,                 // never changes
    private email: EmailAddress,             // value objects inside
    private address: Address,
  ) {}

  static register(email: EmailAddress, address: Address): Customer {
    return new Customer(CustomerId.new(), email, address);   // uuidv7, created here
  }

  changeEmail(newEmail: EmailAddress, verified: boolean) {
    if (!verified) throw new Error("Verify the new address first");
    this.email = newEmail;
  }
  moveTo(newAddress: Address) { this.address = newAddress; }

  equals(other: Customer) { return other.id === this.id; }
}

tools: UUID v7 or ULID generators, ORM entity mappings (JPA, EF Core, Prisma, TypeORM) that allow private fields, and lint rules that flag public setters on domain classes.

then & now still core

Then Evans, 2003

Evans defined entities by continuity and identity, and warned against letting them become bags of attributes. IDs were often database sequences, assigned on insert.

Now 2026

Same idea. The details changed: IDs are now usually generated in code (UUID v7 and ULID sort well in indexes), ORMs can map private fields, and the advice to keep entities small and push detail into value objects is stronger.

Verdict: Still core. Fewer entities than you think, and each with behaviour, not setters.

4Gains vs losses nothing is free

What we gain

  • Stable identity while details change.
  • Rules in named methods, not scattered setters.
  • IDs before saving: easier events and tests.
  • Clear equality: same ID, same thing.

What we lose

  • Mapping private fields can fight the ORM.
  • Generated IDs are long and not human-friendly.
  • More thought than a public-fields data class.
  • Easy to over-use for things that are really values.

6Common pitfalls the usual ways this goes wrong

  • Email or name as the key

    A change of email splits the history. Fix → generated ID; the email is an attribute with a unique index.

  • Public setters everywhere

    Any code can set status = 'shipped' without a parcel. Fix → business-named methods that check rules.

  • Database-generated IDs only

    No ID until saved, so events and links can't be made earlier. Fix → create the ID in code (UUID v7, ULID).

  • Equality by fields

    Two different customers with the same name compare as equal. Fix → compare entities by ID only.

7When to use it (and when not)

Use it when…

  • Things the business tracks over time and refers to: customers, orders, accounts, parcels.
  • Objects whose details change but whose history matters.

Skip it when…

  • Things defined only by their values (money, address, date range): use value objects.
  • Read-only reporting rows with no behaviour.

8Self-check quiz

What makes something an entity?

A lasting identity: the business cares which one it is, and it changes over time.

Why not use an email address as the ID?

Emails change; the identity must not, or one customer becomes two.

How are two entities compared?

By ID only.

Why generate the ID in code rather than in the database?

The entity has an identity from birth, so events, links and tests can use it before it's saved.

what would you do?Support merges duplicate customer accounts every week, because sign-up creates a new customer whenever someone uses a different email at checkout. How do you fix the model?

Give Customer a generated ID independent of email, let a customer have a verified email that can change, and match guest checkouts to existing customers by a deliberate process rather than creating one per email.

try it

Pick one class in your code with public setters. Replace two setters with methods named after business actions, each with one rule, and write a test for each rule. Check what the class uses as its identity.
