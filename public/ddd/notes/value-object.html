Value Object

TL;DR

Replace plain numbers and strings with small types like Money, EmailAddress or DateRange. A value object is defined by its value (two €10 are equal), is immutable (to change it, make a new one), and checks itself when created, so an invalid one can't exist. Its rules (adding money, overlapping ranges) live inside it, written once.

  • Family: tactical building block
  • From: Evans (2003), ch. 5
  • Language support: records, data classes, branded types
  • Pairs with: entity, make illegal states unrepresentable

1The problem why do we even need this?

Using raw numbers and strings for business concepts (primitive obsession) scatters the rules and lets invalid data in.

  • Euros get added to pounds because both are just numbers.
  • “bob@” is stored as an email address.
  • The same validation is copied into many places, and missing from some.

2Real-life analogy banknotes

A ten-euro note is defined by its value: you don't care which one you get as change. You can't turn it into a twenty by writing on it; you swap it for another note. And the till rejects fakes at the door.

  • Equal if the value is equal.
  • Immutable: replace, don't edit.
  • Validated on the way in.

3How it solves it small, immutable, self-checking types

Most of a domain model is value objects; entities are fewer than people think. A good test: “if two of these have the same data, are they the same?” If yes, it's a value object.

  1. Spot the primitives

    Prices as numbers, emails as strings, date pairs, percentages, quantities with units.

  2. Make a type for each

    Money, EmailAddress, DateRange, Percentage. Use the business's words.

  3. Validate on creation

    A private constructor and a factory that returns the value or an error.

  4. Make it immutable

    Readonly fields; operations return new instances.

  5. Compare by value

    Implement equals, or use the language's records or data classes.

  6. Move rules inside

    Adding money, checking overlaps, formatting: methods on the type, written once.

money.tsa value object
export class Money {
  private constructor(readonly cents: bigint, readonly currency: Currency) {}

  static of(cents: bigint, currency: Currency): Money {
    if (cents < 0n) throw new Error("Money can't be negative");
    return new Money(cents, currency);
  }
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("Different currencies");
    return Money.of(this.cents + other.cents, this.currency);   // a new object
  }
  times(qty: Quantity): Money { return Money.of(this.cents * BigInt(qty.value), this.currency); }
  equals(o: Money) { return o.cents === this.cents && o.currency === this.currency; }
}

const total = Money.of(1999n, "EUR").times(Quantity.of(3));   // EUR 59.97

tools: records in Java and C#, data classes in Kotlin and Python (frozen=True), branded types or Zod schemas in TypeScript, ORM support for embedded values (JPA @Embeddable, EF Core owned types).

then & now matters more now

Then Evans, 2003

Evans described value objects as immutable, attribute-defined objects, and encouraged making as many things values as possible. In Java in 2003 that meant writing equals, hashCode and constructors by hand.

Now 2026

Languages caught up: Java and C# records, Kotlin data classes, Python frozen dataclasses, TypeScript branded types. Immutability became mainstream through functional programming. Making a value object is now a one-liner.

Verdict: More useful now: the idea was always right, and today it's nearly free to apply.

4Gains vs losses nothing is free

What we gain

  • Rules in one place, not copied.
  • Invalid values can't exist.
  • Immutability removes a class of bugs.
  • Code reads like the business: price.add(tax).

What we lose

  • More small types to write.
  • Mapping to and from the database and JSON.
  • Some allocation for immutable copies.
  • Team habits: people reach for strings by default.

6Common pitfalls the usual ways this goes wrong

  • Mutable value objects

    Two orders share one Address object; changing one changes both. Fix → make it immutable; operations return new instances.

  • Validation outside

    Money can be built negative, and a service checks later (sometimes). Fix → private constructor plus factory; no invalid instance can exist.

  • Everything is an entity

    Address gets an ID and its own table and lifecycle. Fix → ask “if the data is the same, is it the same thing?”

  • Floats for money

    0.1 + 0.2 ≠ 0.3 on an invoice. Fix → integer minor units (cents) or a decimal type, inside Money.

7When to use it (and when not)

Use it when…

  • Any concept with rules: money, quantities, emails, ranges, percentages, codes.
  • The same validation appears in more than one place.
  • Mixing units or currencies would be a real bug.

Skip it when…

  • A field with no rules at all (a free-text note).
  • Hot loops where allocation really is measured as a problem.

8Self-check quiz

What makes something a value object?

It's defined by its value (equal when its fields are equal), immutable, and usually validates itself.

How do you change a value object?

You don't: you create a new one, often with a method that returns a new instance.

Why store money in cents (or a decimal), not floats?

Floating point can't represent many decimal amounts exactly, so totals drift.

What's primitive obsession?

Using raw strings and numbers for domain concepts, which scatters their rules.

what would you do?A bug report: an order total showed €59.969999. Prices are number and every service rounds “its own way”. What do you change?

Introduce a Money value object with integer cents (or a decimal type) and a currency, put rounding and arithmetic inside it, and replace raw numbers at the boundaries, starting with order totals.

try it

Find one concept in your code that is a plain string or number but has rules (an email, a price, a percentage). Write a value object with a factory that validates, one operation, and equality, then replace it in one function and its tests.
