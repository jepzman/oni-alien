Make Illegal States Unrepresentable

TL;DR

Design your types so that invalid combinations can't be built. Instead of one class with many optional fields and a status string, use one type per state (a union), each with exactly the fields that make sense: a Delivered parcel always has a delivery date; a Pending one never has a tracking number. Parse input into these types once at the edge, and the compiler enforces the rules everywhere else.

  • Family: modelling with types
  • Coined by: Yaron Minsky (2011)
  • Popular from: Wlaschin (2018), “Parse, don't validate” (2019)
  • Pairs with: value object, aggregate

1The problem why do we even need this?

One class with many optional fields and a status string allows combinations the business says are impossible, so every function must check for them.

  • A parcel is “delivered” but has no delivery date.
  • A “pending” parcel already has a tracking number.
  • Null checks everywhere, and the one that's missing causes the bug.

2Real-life analogy the well-designed form

A badly designed paper form lets you tick both “married” and “single”, and always asks for a spouse's name. A good one has one choice, and only shows the spouse field if you picked “married”. Wrong answers can't be written down, so nobody has to check for them later.

  • One choice: a union of states.
  • The spouse field only with “married”: state-specific fields.
  • No checking later: the type system did it.

3How it solves it types that match the business's states

This is the type-level version of value objects and aggregates: the same goal, impossible to break the rules, enforced by the compiler instead of runtime checks. It works best in languages with union types and pattern matching: TypeScript, Kotlin, Swift, Rust, F#, Scala, and Java 21 sealed types.

  1. List the states

    With the experts: what states can this thing be in, and what's always true in each?

  2. One type per state

    Each with exactly the fields that exist in that state, none optional by accident.

  3. A union of them

    type Parcel = Pending | InTransit | Delivered | Failed.

  4. Transitions as functions

    ship(p: Pending): InTransit. You can't ship a delivered parcel.

  5. Parse at the edge

    Turn JSON or rows into these types once, rejecting what doesn't fit.

  6. Match exhaustively

    Handle every state with a switch the compiler checks is complete.

Vocabulary for the exam

Union type
A type that is exactly one of several alternatives (sum type, sealed class).
Discriminator
A field like kind that tells which alternative it is.
Exhaustive matching
The compiler checks every alternative is handled.
Parse, don't validate
Turn raw input into a precise type once, instead of re-checking it everywhere.
Smart constructor
A function that only builds a value if it's valid.
State machine
The allowed states and transitions between them.
parcel.tsone type per state
type Pending   = { kind: "pending";    id: ParcelId };
type InTransit = { kind: "in-transit"; id: ParcelId; trackingNo: TrackingNo };
type Delivered = { kind: "delivered";  id: ParcelId; trackingNo: TrackingNo; deliveredAt: Date };
type Failed    = { kind: "failed";     id: ParcelId; trackingNo: TrackingNo; reason: FailureReason };
export type Parcel = Pending | InTransit | Delivered | Failed;

export const ship    = (p: Pending, t: TrackingNo): InTransit => ({ kind: "in-transit", id: p.id, trackingNo: t });
export const deliver = (p: InTransit, at: Date): Delivered => ({ ...p, kind: "delivered", deliveredAt: at });

export function label(p: Parcel): string {
  switch (p.kind) {                                   // the compiler checks all four are handled
    case "pending":    return "Waiting for pickup";
    case "in-transit": return `On its way (${p.trackingNo})`;
    case "delivered":  return `Delivered ${p.deliveredAt.toDateString()}`;  // always there
    case "failed":     return `Failed: ${p.reason}`;
  }
}

tools: TypeScript discriminated unions with Zod or Valibot to parse at the edge, Kotlin and Java sealed classes, Rust and Swift enums with data, F# and Scala ADTs, XState for state machines.

then & now matters more now

Then Minsky, 2011; Wlaschin, 2018 (after Evans)

In 2003 the DDD way to protect rules was runtime checks: constructors that validate, methods that throw, invariants asserted in aggregates. Languages like Java had no practical union types.

Now 2026

Mainstream languages gained union types and pattern matching (TypeScript, Kotlin, Swift, Rust, Java 21). Wlaschin's Domain Modeling Made Functional showed DDD done with types, and “parse, don't validate” spread widely. The compiler now does part of the aggregate's job.

Verdict: A modern addition that makes the old goals cheaper to reach. Use it wherever your language allows.

4Gains vs losses nothing is free

What we gain

  • Bugs become compile errors.
  • Fewer null checks and defensive code.
  • Types document the rules: read the type, know the states.
  • Safe refactoring: add a state, the compiler lists every place to update.

What we lose

  • Mapping to tables and JSON takes work.
  • Unfamiliar to teams used to classes with setters.
  • Weaker in languages without union types.
  • Can over-engineer simple data.

6Common pitfalls the usual ways this goes wrong

  • Optional fields “just in case”

    deliveredAt? on every parcel. Fix → put each field only on the states where it exists.

  • Validating instead of parsing

    Check JSON, then keep passing the raw object around. Fix → parse into the precise type once; pass that type inward.

  • Non-exhaustive switches

    A new state is added and silently falls into default. Fix → no default case; let the compiler require every state.

  • Types for trivial data

    A union for a field that has no rules. Fix → use it where wrong combinations are real bugs.

7When to use it (and when not)

Use it when…

  • Things with clear states and different data in each (orders, parcels, payments).
  • Bugs caused by impossible combinations or missing null checks.
  • Languages with union types or sealed classes.

Skip it when…

  • Simple data with no states or rules.
  • Teams and languages where it would fight every tool you use.

8Self-check quiz

What does “make illegal states unrepresentable” mean?

Design types so invalid combinations of data can't be constructed at all.

What's a union (sum) type?

A type that is exactly one of several alternatives, each with its own fields.

What does “parse, don't validate” mean?

Turn raw input into a precise type once at the edge, instead of checking it and passing raw data around.

Why avoid a default case in a switch over states?

So the compiler forces you to handle any new state you add.

what would you do?A payment class has status, refundedAt?, failureCode? and capturedAmount?. Last month a refund was issued on a payment that had failed. How would you redesign it?

Model a union: Authorised, Captured (with amount), Failed (with code), Refunded (with date and amount). Make refund accept only a Captured payment, so refunding a failed one doesn't compile, and parse stored rows into these types at the repository.

try it

Find a class in your code with a status field and several optional fields. Write its states as a union of types, each with only its own fields, and one transition function. Count how many null checks disappear.
