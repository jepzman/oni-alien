Anemic Domain Model

TL;DR

An anemic domain model has objects with data and getters/setters, and all the rules in services around them. Fowler called it an anti-pattern in 2003, and in a complex core domain it still is: rules scatter, get copied and get skipped. But in simple CRUD and supporting areas, plain data with a transaction script is fine, and functional code separates data and functions on purpose. The smell is complex rules on plain data.

  • Family: anti-pattern (in the right place)
  • Named by: Martin Fowler (2003)
  • Fine for: CRUD, supporting subdomains
  • Fix with: behaviour on entities, value objects

1The problem why do we even need this?

In a complex domain, objects that only hold data leave the rules nowhere in particular, so they spread, get copied and get skipped.

  • Order has setters for everything; any code can set any status.
  • The cancel rule exists in some services, not in others.
  • Nobody can list the rules of an order by reading the Order.

2Real-life analogy a car and a wheelbarrow

A car has its safety rules built in: it won't shift into reverse at speed. Leaving those to the driver would be dangerous. A wheelbarrow has no rules and needs none: adding a computer would be silly. The question isn't “rich or plain?” but “how complex is the job?”

  • The car is a rich model for a complex domain.
  • The wheelbarrow is plain data for CRUD.
  • The problem is a car built like a wheelbarrow.

3How it solves it put behaviour where the complexity is

Use the subdomain sort (note 02): core domains with real rules get rich models; supporting and generic ones can be plain data and scripts. In functional code, plain data plus pure functions in the same module, with precise types, is not anemic: the rules still have one clear home.

  1. Ask how complex the rules are

    Many rules and states? Core-like. Mostly forms and lists? CRUD.

  2. In a complex area, find the setters

    Each setter called from several services is a missing method.

  3. Move rules onto the object

    order.cancel() instead of order.setStatus('cancelled') plus checks elsewhere.

  4. Hide the setters

    Private fields; changes only through business methods.

  5. Keep services thin

    Application services load, call, save, nothing more.

  6. In simple areas, don't bother

    Plain records, validation at the edge, a transaction script. That's a choice, not a smell.

Vocabulary for the exam

Anemic domain model
Domain objects with data but no behaviour; logic lives in services.
Rich domain model
Objects that hold both data and the rules that change it.
Transaction script
A procedure per use case that does all the work (Fowler, PoEAA).
Tell, don't ask
Tell an object what to do rather than asking for data and deciding outside.
Feature envy
Code that uses another object's data more than its own: a hint the logic is misplaced.
Functional core
Pure functions over immutable data, kept together by module.
order.tsfrom anemic to rich, only where it matters
// anemic: the rule lives (or doesn't) in whichever service remembers it
order.setStatus("cancelled");

// rich: the rule lives on Order, so every caller gets it
export class Order {
  cancel(reason: CancellationReason, now: Date) {
    if (this.status === "shipped") throw new Error("Shipped orders are returned, not cancelled");
    if (this.status === "cancelled") return;                       // idempotent
    this.status = "cancelled";
    this.events.push({ type: "OrderCancelled", orderId: this.id, reason, at: now });
  }
}

// a supporting CRUD area: plain data is fine
type OpeningHours = Readonly<{ storeId: StoreId; day: Weekday; opens: Time; closes: Time }>;

tools: code review (“where does this rule live?”), static analysis that flags public setters and feature envy, architecture tests that keep business rules out of controllers, and the subdomain chart to decide where rich models are worth it.

then & now rethought

Then Fowler, 2003

Fowler named the anemic domain model an anti-pattern in 2003: objects that look like a domain model but have no behaviour, “procedural design in object clothing”, paying the cost of a domain model without the benefit.

Now 2026

Still true for complex domains. But the industry learned two nuances: most of a system is CRUD, where plain data is the right choice (see subdomains), and functional programming separates data and functions deliberately, with types doing much of the protecting.

Verdict: Rethought: an anti-pattern in the core, a sensible choice elsewhere. Judge it by where the rules are.

4Gains vs losses nothing is free

What we gain

  • Rich model in the core: rules in one place, can't be skipped.
  • Plain data elsewhere: less code where rules are few.
  • A clear test for code review: where does this rule live?
  • Effort matches complexity.

What we lose

  • Judgement: the line between core and CRUD moves.
  • Two styles in one codebase to explain.
  • Refactoring cost when a CRUD area grows rules.
  • ORMs sometimes push toward public setters.

6Common pitfalls the usual ways this goes wrong

  • Calling all plain data “anemic”

    A team rewrites a simple admin screen with aggregates and events. Fix → rich models only where the rules are complex.

  • Setters left public

    Methods are added, but code still calls setStatus. Fix → make fields private once the methods exist.

  • Logic in controllers

    Rules move out of services and into HTTP handlers instead. Fix → into the domain object, not one layer up.

  • Ignoring growth

    A “simple” returns screen grows 30 rules over two years, still as scripts. Fix → revisit when a supporting area's rules multiply.

7When to use it (and when not)

Use it when…

  • Reviewing a complex domain whose rules are hard to find.
  • Deciding how much modelling an area deserves.
  • Bugs caused by setters bypassing business rules.

Skip it when…

  • Simple CRUD and admin screens: plain data is the right choice.
  • Pure functional code with precise types, where data and functions are kept together by module.

8Self-check quiz

What is an anemic domain model?

Domain objects with data and getters/setters but no behaviour; the rules live in services around them.

When is plain data with services perfectly fine?

In simple CRUD and supporting areas where there are few rules.

What's the usual fix in a complex domain?

Move rules onto the objects as business-named methods and hide the setters.

Is functional code with data types and separate functions anemic?

Not necessarily: with precise types and functions grouped by module, the rules still have one clear home.

what would you do?A reviewer rejects a pull request for a store-opening-hours admin screen because “the model is anemic, add aggregates and domain events”. The screen has two rules. What do you answer?

That opening hours are a simple supporting area: plain records, validation at the edge and a transaction script are the right size. Rich models are for the core, where rules are many and costly to get wrong. Agree to revisit if the rules grow.

try it

Pick one class in your core domain and search for every call to its setters. For the most-called one, write a method named after the business action, move the checks into it from the callers, and make the setter private.

remember!!

Don't build a car without brakes, and don't put a computer on a wheelbarrow.
