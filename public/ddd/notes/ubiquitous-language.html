Ubiquitous Language

TL;DR

Agree one vocabulary with the people who know the business, and use it everywhere: in meetings, in class and method names, in tests and on screens. Each word has one meaning inside one model. When the code and the experts use different words, a translation happens in someone's head, and bugs live in translations.

  • Family: strategic design
  • From: Eric Evans, Domain-Driven Design (2003), ch. 2
  • Lives in: a glossary, the code, the tests
  • Pairs with: bounded context, event storming

1The problem why do we even need this?

When the experts say one thing and the code says another, every conversation needs a translation, and translations go wrong quietly.

  • The manager's “order” means a paid purchase; the code's Order exists from the first item in the basket.
  • Developers say “status 3”; nobody in the business knows what that is.
  • Rules get lost: a sentence in a meeting never becomes a method anyone can find.

2Real-life analogy the kitchen's own words

A busy restaurant kitchen has its own language: “fire table four”, “eighty-six the salmon”, “on the pass”. Each phrase means one exact thing, everyone uses it, and a new cook learns it in the first week. Orders move fast because nobody translates.

  • The phrases are the ubiquitous language.
  • They only work inside this kitchen: the bar next door has its own.
  • When the menu changes, the words change for everyone at once.

3How it solves it one glossary, four places

The language is discovered, not invented: listen to how experts describe the work, write the terms down with their meaning, and push back where a word is vague. Then make the code say the same thing.

  1. Listen first

    Sit with the people who do the work. Note the nouns and verbs they use, and the words they argue about.

  2. Write a glossary

    One line per term: the word, what it means here, and an example. Keep it next to the code.

  3. Name the code after it

    Classes, methods, events and modules use the glossary words, not technical ones like Manager or Data.

  4. Use it in tests

    Test names read like business examples: “a paid order can be refunded within 30 days”.

  5. Challenge vague words

    When “customer” means three things, that's a sign of three models: split them or qualify the word.

  6. Refactor when the language changes

    A new word in a workshop means a rename in the code. Do it while it's cheap.

Vocabulary for the exam

Ubiquitous language
The shared vocabulary of a team and its experts, used everywhere within one context.
Domain expert
Someone who knows how the business works: a buyer, a planner, a support lead.
Glossary
The written list of terms and their meanings.
Knowledge crunching
Evans's name for working through the domain with experts until the model is clear.
Model
A simplified view of the business that the code is built on.
Translation cost
The effort, and the bugs, of mapping one vocabulary to another.

tools: a glossary file in the repository (docs/glossary.md), Context Mapper or a wiki page per context, event storming boards, and code review that asks “is that the word the business uses?”

then & now still core

Then Evans, 2003

Evans made the shared language the heart of the method: developers and experts “crunch knowledge” together until one model and one vocabulary emerge, used in speech, diagrams and code.

Now 2026

Nothing has replaced it. The tools changed: event storming and domain storytelling find the language faster, glossaries live in the repository, and test names in BDD style carry it. The one refinement is that the language belongs to one context, not the company.

Verdict: Still the first thing to get right. It costs little and pays off in every other pattern in this volume.

4Gains vs losses nothing is free

What we gain

  • Fewer translation bugs: one word, one meaning.
  • Experts can read test names and even some code.
  • Rules are easy to find: search for the business word.
  • Faster onboarding: learn the glossary, then the code.

What we lose

  • Time with experts, which is scarce.
  • Renames when the language changes.
  • Arguments about words, which feel slow (but find real gaps).
  • Only works inside one context; it is not a company dictionary.

6Common pitfalls the usual ways this goes wrong

  • A company-wide dictionary

    One meaning of “customer” is forced on sales, billing and support, and fits none of them. Fix → keep one language per bounded context; let words differ between contexts.

  • Developers invent the words

    The code says FulfilmentEntity; the warehouse says “pick list”. Fix → use the words the experts already use, and ask when unsure.

  • Glossary nobody reads

    A wiki page from 2023 that disagrees with the code. Fix → keep it in the repository and update it in the same pull request as the rename.

  • Technical names win

    Manager, Processor, Data classes hide what really happens. Fix → name classes and methods after business things and actions.

7When to use it (and when not)

Use it when…

  • The business rules are rich, and getting them wrong costs money.
  • Developers and experts talk often, and misunderstandings keep showing up.
  • New people take months to understand what the code does.

Skip it when…

  • Simple CRUD or a technical tool where the “domain” is the technology itself.
  • You have no access to domain experts at all (fix that first).

8Self-check quiz

Where should the ubiquitous language be used?

Everywhere inside one context: conversations, documents, class and method names, tests and the user interface.

Why is one meaning per word so important?

Every place where a word means two things needs a translation in someone's head, and that's where bugs come from.

Is the ubiquitous language the same across the whole company?

No. It holds inside one bounded context. Billing and shipping can use “customer” differently.

Who decides the words?

They come from the domain experts, refined together with the developers. Developers shouldn't invent them alone.

what would you do?In a refinement meeting the warehouse lead keeps saying “pick list”, but the code and tickets say FulfilmentTask. A new developer built the wrong screen because of it. What do you do?

Adopt the experts' word: add “pick list” to the glossary with its meaning, rename the class, the table and the tickets in one change, and ask in review whether new names match the words people really use.

try it

Take one feature you work on and list the ten nouns and verbs in its code. Next to each, write the word a business person would use. Wherever they differ, ask an expert which is right, add it to a glossary file, and rename one class in the code.

remember!!

If the code needs a translation, the bug is already in the translation.
