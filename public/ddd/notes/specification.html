Specification

TL;DR

Turn an important yes/no business rule (“qualifies for free delivery”, “overdue invoice”) into a named object or function you can test, combine with and/or/not, and reuse: to check one object, to filter a query, or to describe what to build. The rule is written once. Today a plain, well-named predicate function is often enough.

  • Family: supple design
  • From: Evans & Fowler (1997); Evans (2003), ch. 9
  • Today: named predicates, expression trees
  • Pairs with: value object, repository

1The problem why do we even need this?

An important rule written as scattered conditions gets copied and drifts: each copy slightly different.

  • The same rule lives in checkout, a SQL export and the front end.
  • A change of threshold is applied in one place only.
  • Nobody can say exactly what “qualifies” means.

2Real-life analogy the menu labels

A kitchen defines “vegan”, “gluten-free” and “nut-free” once. The same labels are used to check a dish, to filter the menu for a guest and to plan a meal, and they combine: “vegan and gluten-free”. If gluten-free changes meaning, every use follows.

  • Each label is a specification.
  • Combining labels is and / or / not.
  • Check, filter and plan are the three uses.

3How it solves it named rules you can combine

Use it for important rules that appear in more than one place or need combining. For a one-off condition, a well-named function is the specification, and that's fine. Avoid deep class hierarchies of specifications: they were the 2003 way, and they're hard to read.

  1. Find a rule that repeats

    The same condition in code, SQL or the front end, or a rule people argue about.

  2. Name it in the domain's words

    QualifiesForFreeDelivery, IsOverdue.

  3. Write it once

    As a predicate function or a small object with isSatisfiedBy.

  4. Compose from smaller rules

    and / or / not, each part named and tested.

  5. Reuse for queries if needed

    Translate to a query filter (expression tree, query builder) instead of duplicating it in SQL.

  6. Test with examples

    A table of baskets and expected yes/no, written with the business.

Vocabulary for the exam

Specification
An object or function that says whether something satisfies a business rule.
Predicate
A function that returns true or false.
Composite specification
Specifications combined with and, or and not.
isSatisfiedBy
The classic method name for checking one candidate.
Expression tree
Code as data, which an ORM can translate into SQL (C# LINQ).
Selection / validation / construction
Evans's three uses: filter, check, and describe what to create.
free-delivery.tsspecification as small composable predicates
type Spec<T> = { isSatisfiedBy(c: T): boolean };
const spec = <T>(f: (c: T) => boolean): Spec<T> => ({ isSatisfiedBy: f });
const and = <T>(...s: Spec<T>[]) => spec<T>((c) => s.every((x) => x.isSatisfiedBy(c)));
const or  = <T>(...s: Spec<T>[]) => spec<T>((c) => s.some((x) => x.isSatisfiedBy(c)));

const isVip          = spec<Basket>((b) => b.customer.tier === "vip");
const over           = (m: Money) => spec<Basket>((b) => b.total().cents >= m.cents);
const notRemoteZone  = spec<Basket>((b) => !REMOTE_POSTCODES.has(b.address.postcode));

export const qualifiesForFreeDelivery = and(or(isVip, over(Money.eur(60))), notRemoteZone);

qualifiesForFreeDelivery.isSatisfiedBy(basket);   // true / false, tested with a table of examples

tools: plain predicate functions, Ardalis.Specification and LINQ expression trees in .NET, Spring Data JPA Specification, query builders (Kysely, jOOQ) to turn a rule into a WHERE clause.

then & now rethought

Then Evans & Fowler, 1997; Evans, 2003

Specifications were objects with isSatisfiedBy, combined through composite classes, and used for validation, selection and construction. In Java in 2003 this meant a fair amount of class machinery.

Now 2026

First-class functions made a specification just a named predicate. In .NET, LINQ expression trees let one spec run in memory and as SQL. The heavy class-hierarchy version is mostly gone; the idea of naming and composing important rules is alive.

Verdict: Rethought: keep the idea, write it as small named predicates.

4Gains vs losses nothing is free

What we gain

  • A rule written once, used everywhere.
  • Readable: named in business terms.
  • Composable from small tested parts.
  • Testable with a table of examples.

What we lose

  • Extra abstraction for simple conditions.
  • Query translation is hard outside .NET and JPA.
  • Class hierarchies of specs get unreadable.
  • Performance: in-memory checks can't replace indexed queries.

6Common pitfalls the usual ways this goes wrong

  • Specs for everything

    IsNotNull and IsPositive specifications. Fix → only for important, repeated or combined business rules.

  • Deep class hierarchies

    AndSpecification<OrSpecification<…>> nobody can read. Fix → small functions and a couple of combinators.

  • Duplicating it in SQL anyway

    The spec is used in code, the export still has its own WHERE. Fix → translate the spec to a query, or generate the export from it.

  • Filtering in memory

    Load 2 million customers to apply a spec. Fix → use the query form for selection; in-memory only for single checks.

7When to use it (and when not)

Use it when…

  • An important yes/no rule appears in several places.
  • Rules that combine (eligible AND not blocked OR override).
  • Business people argue about what a rule means: name it and test it.

Skip it when…

  • A condition used once: a well-named function or variable is enough.
  • Performance-critical selection where a hand-tuned query is needed.

8Self-check quiz

What is a specification?

A named, testable business rule that says whether a candidate satisfies it, and can be combined with others.

Name Evans's three uses of a specification.

Validation (check one object), selection (filter a collection or query) and construction (describe what to build).

What's the simplest modern form?

A well-named predicate function, with small and/or helpers when needed.

Why not apply a specification to every row in memory?

Selection over large data needs an indexed database query; translate the spec to a filter instead.

what would you do?Marketing's “eligible for the loyalty bonus” count never matches what checkout gives. The rule lives in a Java method and a 40-line SQL view written separately. What do you do?

Make the rule one specification with a business name and an example table agreed with marketing, then generate the query from it (or have the export call the same code), and add a test that runs both forms on the same sample data.

try it

Find one business condition written in two places (code and SQL, or back end and front end). Write it once as a named predicate built from two or three smaller ones, write a table of six examples, and replace one of the copies.

remember!!

Define “gluten-free” once; then check, filter and plan with the same label.
