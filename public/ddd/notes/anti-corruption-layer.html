Anti-Corruption Layer

TL;DR

When you must integrate with a model you don't like and can't change (legacy, a vendor, another team's mess), put a translation layer at your border. It talks to the other system in its terms and gives your code only your types, in your language. The other model's names, codes and quirks stop at the layer, so your model stays clean and the other system stays replaceable.

  • Family: context relationship
  • From: Evans (2003), ch. 14
  • Made of: facades, adapters, translators
  • Pairs with: strangler fig, conformist (the alternative)

1The problem why do we even need this?

Integrating directly with a poor or foreign model lets its names and quirks leak into your code, until your model is theirs.

  • Legacy field names and magic codes appear in new code.
  • Rules are written in the other system's terms: LIFSD === '01'.
  • Replacing the old system later means touching everything.

2Real-life analogy the interpreter

At an international meeting, an interpreter sits at the edge of the table and translates both ways. The hosts never learn the visitors' grammar; the visitors never learn the hosts'. If something is ambiguous, one person, whose job it is, sorts it out.

  • The interpreter is the anti-corruption layer.
  • Each side keeps its own language.
  • A new delegation means a new interpreter, not new hosts.

3How it solves it translate at the border, both ways

An ACL is the opposite of conformist: it costs code, but keeps your model yours. It's also the main tool of the strangler fig: new code sits behind an ACL while the old system is replaced piece by piece.

  1. Define your model first

    Write the types your code wants, in your language, ignoring the other system.

  2. Wrap the other system

    A facade that hides its protocol, sessions and error codes.

  3. Translate

    Pure functions that map their records to your types and back. Test them with real examples.

  4. Expose a port

    Your code depends on an interface (CustomerDirectory), not on the facade.

  5. Guard the border

    An architecture test fails if anything outside the layer imports the other system's client or types.

  6. Translate events too

    Their webhooks become your domain events, in your words.

// Ordering's own port, in Ordering's language
export interface CustomerDirectory {
  find(id: CustomerId): Promise<Customer | undefined>;
}

// The ACL: the only place that knows about the ERP
export class ErpCustomerDirectory implements CustomerDirectory {
  constructor(private erp: ErpClient) {}
  async find(id: CustomerId) {
    const r = await this.erp.read("KNA1", { KUNNR: toErpNumber(id) });
    return r && toCustomer(r);
  }
}

const toCustomer = (r: Kna1Row): Customer => ({
  id: fromErpNumber(r.KUNNR),
  name: r.NAME1.trim(),
  deliveryBlocked: r.LIFSD === "01" || r.LIFSD === "02",   // ERP code -> our rule
});

tools: plain code (ports and adapters), an integration platform or API gateway for protocol translation, ArchUnit or dependency-cruiser to forbid imports of the other system's client outside the layer.

then & now still core

Then Evans, 2003

Evans described the ACL for integrating with legacy systems: a layer of facades, adapters and translators that let a new model talk to an old one without being corrupted by it.

Now 2026

It's everywhere: in front of SaaS and ERP systems, in strangler-fig migrations, and in hexagonal architecture as an adapter behind a port. Architecture tests now enforce the border automatically.

Verdict: Still core, and even more common now that most systems integrate with several vendors.

4Gains vs losses nothing is free

What we gain

  • Your model stays yours, in your language.
  • The other system is replaceable: only the layer changes.
  • One place to understand the integration.
  • Testable: translators are pure functions.

What we lose

  • More code to write and maintain.
  • Translation can lose or distort meaning.
  • Extra latency if it's a separate service.
  • Needs discipline: one shortcut import breaks it.

6Common pitfalls the usual ways this goes wrong

  • A layer that only renames

    Fields are copied 1:1 with new names; the old concepts survive. Fix → translate meaning, not just names (LIFSD codes → deliveryBlocked).

  • Leaky shortcuts

    One team imports the ERP client “just this once”. Fix → an architecture test that fails the build.

  • One giant ACL for everything

    A central integration team becomes a bottleneck. Fix → each context owns the ACL at its own border.

  • Over-using it

    An ACL in front of a well-designed internal API that fits your model. Fix → if the upstream model is good, conforming is cheaper.

7When to use it (and when not)

Use it when…

  • Integrating with legacy systems, ERPs or vendors with a different or poor model.
  • Replacing a system gradually (with the strangler fig).
  • Another team's model doesn't fit yours and they can't change it.

Skip it when…

  • The upstream model is good and fits yours (conform).
  • A short-lived integration you'll remove soon (weigh the cost).

8Self-check quiz

What does an anti-corruption layer protect?

Your model and language, from another system's model leaking in.

What's the alternative relationship, and when is it better?

Conformist: use the upstream model directly. Better when that model is good and fits yours.

Name three building blocks of an ACL.

A facade over the other system, translators that map data, and adapters that implement your ports.

How does an ACL help when replacing a legacy system?

Your code only depends on your own port, so the old system can be swapped behind the layer without changing your model.

what would you do?A new team integrates with a CRM and their code is full of crm_status_cd and acct__c. The company plans to switch CRM next year. What do you ask them to change?

Define their own Customer types and a port, and move every CRM name and code into an anti-corruption layer that translates both ways. Add an architecture test so only the layer imports the CRM client. Next year, only the layer is rewritten.

try it

Find one place where your code uses another system's field names or status codes directly. Define your own type for it, write a pure translator function with three example tests, and route all access through one adapter.

remember!!

Let their words stop at the door; inside, speak your own language.
