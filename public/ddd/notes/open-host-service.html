Open Host Service & Published Language

TL;DR

When many contexts need your data, don't build a custom integration for each. Offer an open host service: one well-documented API (and event stream) for everyone. Describe its data in a published language: a documented, versioned format like an OpenAPI spec, JSON Schemas or Protobuf. Consumers translate into their own model if they need to; you version carefully instead of breaking them.

  • From: Evans (2003), ch. 14
  • Today: OpenAPI, AsyncAPI, Protobuf, CloudEvents
  • Pairs with: API versioning, contract testing

1The problem why do we even need this?

An upstream team that builds one integration per consumer ends up maintaining integrations instead of its domain.

  • An API for the website, a CSV for marketing, a dump for search.
  • Each consumer's change means a new variant.
  • Nobody knows which format is the “real” one.

2Real-life analogy the shipping container

A port doesn't build a special crane for every ship. It works with one container standard, documented and shared, and every ship, truck and train that follows it can load and unload. The port grows by handling more containers, not by rebuilding itself for each customer.

  • The port's loading service is the open host service.
  • The container standard is the published language.
  • A new container size comes with a transition period.

3How it solves it one interface, one documented language

The published language should be designed for integration, not a dump of your internal model. Internals can change freely; the published language changes slowly and in versions.

  1. Collect consumer needs

    What do all consumers actually need? Design for the common shape, not each one's wish.

  2. Design the published language

    Resources and events in clear terms, separate from your internal classes.

  3. Document it as a spec

    OpenAPI for requests, AsyncAPI and JSON Schema or Protobuf for events.

  4. Version it

    Additive changes are free; breaking changes get a new version and a deprecation date.

  5. Test it

    Consumer contract tests and schema compatibility checks in CI.

  6. Retire variants

    Move old custom feeds onto the open host, one consumer at a time.

Vocabulary for the exam

Open host service
A protocol or API offered to all consumers, instead of one integration each.
Published language
A documented, shared format for exchanging data between contexts.
Schema
A machine-readable description of a message or resource.
Backward compatible
A change existing consumers can ignore safely.
Deprecation period
Time during which old and new versions both work.
Schema registry
A service storing event schemas and checking compatibility.

asyncapi: 3.0.0
info: { title: Catalogue events, version: 2.1.0 }
channels:
  productPublished:
    address: catalogue.product-published.v2
    messages:
      ProductPublished:
        payload:
          type: object
          required: [productId, title, price, publishedAt]
          properties:
            productId:   { type: string, format: uuid }
            title:       { type: string }
            price:       { $ref: "#/components/schemas/Money" }
            weightGrams: { type: integer, minimum: 0 }   # added in 2.1, optional
            publishedAt: { type: string, format: date-time }

tools: OpenAPI and AsyncAPI specs, JSON Schema, Protobuf or Avro, a schema registry with compatibility checks (Confluent, Apicurio, Buf), CloudEvents for event envelopes, and contract tests.

then & now built in now

Then Evans, 2003

Evans suggested an open protocol for all consumers and a well-documented shared language for exchange; his examples were industry formats like chemical markup or XML standards.

Now 2026

This is how APIs are built today: OpenAPI and AsyncAPI specs, JSON Schema and Protobuf, schema registries that refuse incompatible changes, CloudEvents envelopes. The pattern became the default toolset.

Verdict: Built in now: you rarely name it, but every well-run public API and event stream is one.

4Gains vs losses nothing is free

What we gain

  • One integration to maintain, not one per consumer.
  • Self-service for new consumers.
  • Internals can change behind a stable language.
  • Clear documentation and tooling from the spec.

What we lose

  • Designing for everyone fits no one perfectly.
  • Versioning discipline is needed.
  • Slower to change than a private interface.
  • Consumers translate into their own models.

6Common pitfalls the usual ways this goes wrong

  • Publishing your internals

    The API is a JSON dump of the ORM classes. Fix → design the published language separately and map to it.

  • Breaking without versions

    A renamed field breaks every consumer the same day. Fix → additive changes only, or a new version with a deprecation period.

  • Bending for one consumer

    Special fields and endpoints for the loudest team. Fix → serve the common need; let a backend-for-frontend adapt it.

  • No spec, only code

    Consumers reverse-engineer payloads from logs. Fix → a spec in the repository, published as docs, checked in CI.

7When to use it (and when not)

Use it when…

  • Many contexts or external partners need the same data.
  • An upstream team spends much of its time on integrations.
  • Events that several teams subscribe to.

Skip it when…

  • A single consumer that you work closely with (customer–supplier is enough).
  • Internal module calls inside one context.

8Self-check quiz

What's the difference between an open host service and a published language?

The open host service is the one interface offered to all; the published language is the documented format of the data it exchanges.

Why shouldn't the published language be your internal model?

Then every internal change breaks consumers. A separate, designed language lets internals change freely.

Give three modern forms of a published language.

OpenAPI specs, AsyncAPI with JSON Schema, Protobuf or Avro, CloudEvents.

How do you make a breaking change?

Publish a new version alongside the old one, with a deprecation period and a migration guide.

what would you do?Search, marketing and the app each ask the Catalogue team for a slightly different product feed. The team has five feeds and no time for catalogue work. What do you propose?

One open host service: a documented, versioned product API and a ProductPublished event with a schema in a registry. Migrate consumers onto it one by one and retire the custom feeds; consumers that need a special shape adapt it on their side.

try it

Write an OpenAPI or AsyncAPI spec for one API or event your team owns. Compare it with the internal classes: mark every field that leaks an internal detail, and decide which ones to rename, hide or keep.

remember!!
