Shared Kernel & Partnership

TL;DR

Two teams that work closely can share a small piece of model (like Money, Address, a few IDs) as a shared kernel: jointly owned, changed only by agreement, tested by both. In a partnership, the two teams go further and plan and release together. Keep the kernel tiny: the bigger it gets, the more it becomes a shared monolith in disguise.

  • Family: context relationship
  • From: Evans (2003), ch. 14
  • Size: small: a few types, not entities
  • Watch out: the “common” library that ate everything

1The problem why do we even need this?

“Let's put the shared classes in a common library” is how many systems end up with every team coupled to every other.

  • The common package grows from Money to Order, Customer and Product.
  • Every change needs every team to upgrade together.
  • Versions drift; nobody dares to change anything.

2Real-life analogy the garden wall

Two neighbours share a garden wall. They agreed neither changes it without asking, and they trim the hedge on top together each spring. They don't share their houses: only the wall.

  • The wall is the shared kernel.
  • “Only together” is the joint ownership.
  • Trimming together each spring is a partnership.

3How it solves it share little, change together

Partnership is about the teams: they coordinate plans and succeed or fail together. Shared kernel is about the code: a small model they both use. They often go together, but either can exist alone.

  1. Ask if you need it

    Can each side keep its own copy of these few types instead? Often yes, and that's simpler.

  2. Keep it to value types

    Money, Address, IDs, maybe a shared enum. Not entities or aggregates.

  3. Own it jointly

    Both teams review every change; neither can merge alone.

  4. Test with both

    Both teams' test suites run on every change to the kernel.

  5. Release together

    Or version it carefully, and upgrade both sides in the same sprint.

  6. Watch its size

    If it keeps growing, the contexts may really be one, or need separating.

Vocabulary for the exam

Shared kernel
A small part of the model shared by two contexts, changed only together.
Partnership
Two teams that coordinate plans and releases and succeed or fail together.
Common library
The usual (often over-large) implementation of a shared kernel.
Lockstep release
Deploying two components together because they depend on the same change.
Duplication
Keeping separate copies instead of sharing: often the cheaper choice.
Schema registry
A modern way to share event shapes without sharing code.
packages/shared-kernel/index.tssmall, value types only
// Owned by: ordering-team AND shipping-team (CODEOWNERS requires both)
export type OrderId = string & { readonly __brand: "OrderId" };

export class Money {
  private constructor(readonly cents: bigint, readonly currency: "EUR" | "GBP") {}
  static of(cents: bigint, currency: "EUR" | "GBP") { return new Money(cents, currency); }
  add(o: Money) { /* same currency only */ return Money.of(this.cents + o.cents, this.currency); }
}

export type Address = Readonly<{ street: string; postcode: string; city: string; country: string }>;

// NOT here: Order, Customer, Product. Those belong to one context each.

tools: a small package in a monorepo with CODEOWNERS listing both teams, both pipelines triggered on change, or a schema registry (Confluent, Apicurio) for shared event shapes instead of shared code.

then & now rethought

Then Evans, 2003

Evans offered the shared kernel as a way for two closely working teams to share part of a model, with a continuous integration process covering both.

Now 2026

With microservices, a shared code library became a known trap: it couples deployments. Teams today prefer duplication, or sharing schemas (Protobuf, JSON Schema, a schema registry) instead of code. Partnership survived as a team pattern; the shared kernel survived only in small doses.

Verdict: The idea holds, but keep it tiny. Share schemas, not classes, wherever you can.

4Gains vs losses nothing is free

What we gain

  • No duplicate code for truly shared concepts.
  • Consistent money, address and ID handling.
  • Close collaboration where it really helps.
  • Partnership: two teams move as one on joint goals.

What we lose

  • Coupling: neither team can change it alone.
  • Coordination cost on every change.
  • Tends to grow into a shared model.
  • Lockstep releases if not versioned carefully.

6Common pitfalls the usual ways this goes wrong

  • The common library that ate everything

    Started with Money, now holds Order with fields for six services. Fix → value types only; entities stay in their context.

  • Shared kernel across many teams

    Ten teams share it, so nothing ever changes. Fix → two teams, maybe three; beyond that, publish a language instead.

  • One side changes it alone

    A “small fix” breaks the other team's build. Fix → CODEOWNERS with both teams, both test suites in CI.

  • Sharing to avoid five lines of code

    Coupling two teams to save a tiny copy. Fix → duplication of small value types is usually cheaper.

7When to use it (and when not)

Use it when…

  • Two teams that already work closely, sharing a few important value types.
  • Concepts that must be identical on both sides (money rounding, ID formats).
  • Partnership: two contexts that must deliver a feature together.

Skip it when…

  • Many teams, or teams that rarely talk.
  • When a copy of a few small types would do.
  • To share entities or aggregates (use events or an API).

8Self-check quiz

What belongs in a shared kernel?

A small set of shared types, usually value types and IDs, owned jointly by two teams.

What's the difference between shared kernel and partnership?

Shared kernel is shared code or model; partnership is two teams coordinating plans and releases. They often come together.

What's the main risk?

It grows into a shared model that couples the contexts and forces lockstep changes.

What's often a better alternative?

Each context keeps its own small copy, or shares only an event schema through a published language.

what would you do?Your company's @acme/common package is used by twelve services and contains Order, Customer and Product. Upgrading it takes a month of coordination. What do you do?

Shrink it: move each entity into the context that owns it, let others keep their own small read models filled by events, and leave only value types (Money, IDs) in a much smaller kernel, or replace sharing code with a published event schema.

try it

Look at a shared or “common” package in a codebase you know. Sort its types into “value type” and “belongs to one context”. For the second group, name the owning context and sketch how others could get that data instead.
