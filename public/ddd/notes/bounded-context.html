Bounded Context

TL;DR

Don't build one model for the whole company. Draw borders, and inside each border keep one model with one language, where every word means exactly one thing. Catalogue's product and Shipping's product can be different classes with different fields; they share an ID and talk through translated messages. A bounded context is also a natural unit for a team, a module or a service.

  • Family: strategic design
  • From: Evans (2003), ch. 14
  • Becomes: a module, a service, a team's area
  • Pairs with: context map, anti-corruption layer

1The problem why do we even need this?

One model for everybody grows until it means nothing precise to anybody.

  • A Product class with eighty fields, half of them null for any given use.
  • Every team edits it; every change risks breaking someone else.
  • Meetings argue about what “product” or “customer” really means.

2Real-life analogy the word “table” in different rooms

“Table” means a piece of furniture in the dining room, a grid in the office, and a proposal in parliament. Nobody is confused, because everyone knows which room they're in. Trouble only starts if you insist the word must mean the same thing everywhere.

  • Each room is a bounded context.
  • The word is part of each room's language.
  • Walking between rooms means translating.

3How it solves it borders around models

Look for borders where language changes, where different experts are in charge, or where data changes for different reasons. A context is a language border first: it can be a module in a monolith long before it is a service.

  1. Find where words change meaning

    “Customer” in sales has leads and deals; in billing it has invoices and a tax ID. That's a border.

  2. Name each context

    Catalogue, Pricing, Ordering, Shipping, Billing. Write one sentence on what each is responsible for.

  3. Give each its own model

    Its own classes, schema (or tables) and language. Duplication of a few fields across contexts is fine.

  4. Share IDs, not objects

    Contexts refer to each other's things by ID and never reach into another's tables.

  5. Connect through contracts

    Events or APIs at the border, translated into each side's language.

  6. Align teams

    One team per context where you can, so the model and its owners change together.

Vocabulary for the exam

Bounded context
A border inside which one model and one language apply consistently.
Model
The classes and rules that represent the business inside the context.
Context border
Where translation happens between two models.
Big ball of mud
A system with no clear borders, where everything depends on everything.
Modular monolith
One deployable app split into modules along context borders.
Conway's law
Systems tend to mirror the communication structure of the teams that build them.
two-products.tssame thing, two models, one shared ID
// catalogue/product.ts : what shoppers see
export class Product {
  constructor(readonly id: ProductId, public title: string,
              public photos: PhotoUrl[], public description: Markdown) {}
}

// shipping/item.ts : what the warehouse needs
export class ShippableItem {
  constructor(readonly productId: ProductId,     // the only shared thing
              readonly weight: Grams, readonly size: Dimensions,
              readonly fragile: boolean) {}
}

// shipping listens to catalogue events and keeps only what it needs
on("catalogue.ProductPublished", (e) =>
  shippingItems.upsert(e.productId, { weight: e.weightGrams, size: e.dimensions }));

then & now matters more now

Then Evans, 2003

Evans introduced the bounded context in part IV, as a way to keep large models consistent: an explicit border, a model inside it, and a context map between them. Many teams at the time read the book for its object patterns and skipped it.

Now 2026

Since about 2014 it's the most quoted idea in DDD, because microservices needed a way to draw service borders, and team topologies a way to draw team borders. The modern advice: find contexts first, start them as modules, and only split into services when you need to.

Verdict: Matters more today than when it was written. If you take one thing from this volume, take this.

4Gains vs losses nothing is free

What we gain

  • Precise models: each word means one thing.
  • Teams change their model alone.
  • Natural seams for modules, services and teams.
  • Smaller classes with only the fields each use needs.

What we lose

  • Some duplication of fields and data.
  • Translation work at every border.
  • Eventual consistency between contexts.
  • Wrong borders are expensive to move later.

6Common pitfalls the usual ways this goes wrong

  • One context per entity

    Separate “contexts” for Customer, Order and Product, chatting constantly. Fix → split by language and business capability, not by noun.

  • Shared database tables

    Two contexts read and write the same table, so they're really one. Fix → each context owns its tables; others ask through an API or event.

  • Services before borders

    Microservices are cut first, and the models stay tangled across them. Fix → find contexts first; start as modules in one app and split later if needed.

  • Borders that never move

    The business changed, but the contexts from year one stay. Fix → revisit borders when language or teams change; moving a module is cheaper than moving a service.

7When to use it (and when not)

Use it when…

  • A system larger than one team can keep in its head.
  • The same word means different things to different departments.
  • Before deciding on modules, services or team ownership.

Skip it when…

  • A small app with one team and one consistent language (it's already one context).
  • Very early, before you understand where the language changes.

8Self-check quiz

What is a bounded context?

A border inside which one model and one language apply consistently, so every term has one meaning.

Can two contexts have different classes for the same real-world thing?

Yes, and they usually should: each keeps only what it needs, and they share an ID.

Is a bounded context the same as a microservice?

No. It's a language and model border. It can be a module in a monolith, one service, or occasionally several.

Name two signs of a border.

A word changes meaning; different experts are in charge; data changes for different reasons; different teams own it.

what would you do?Shipping and Catalogue both write to the products table. A Catalogue migration renames weight to weight_kg and the warehouse labels break overnight. What do you change?

Give each context its own data. Shipping keeps its own item table with weight and size, filled from a catalogue event or API, and nobody outside Catalogue touches Catalogue's tables. Add an architecture test that forbids cross-context table access.

try it

Pick one overloaded word in your system (customer, product, account). Write down what it means to three different departments and which fields each uses. Sketch three small classes, one per context, and the one ID they share.

remember!!

Every word is fine in its own room. Trouble starts when you knock down the walls.
