Repository

TL;DR

Give each aggregate root a repository: an interface that looks like a collection (get(id), save(order), a few named queries) and hides how the aggregate is stored. Business code asks for whole aggregates, never rows, and never writes SQL. The interface lives in the domain; the database code implements it, and tests use an in-memory version.

  • Family: tactical building block
  • From: Evans (2003), ch. 6; Fowler, PoEAA (2002)
  • One per: aggregate root
  • Pairs with: aggregate, unit of work, ORM

1The problem why do we even need this?

When business rules fetch their own data, SQL spreads through the domain and every rule's test needs a database.

  • Different queries load “the same” order differently, some without its lines.
  • Rules can't be tested without a database.
  • A schema change means hunting through dozens of files.

2Real-life analogy the library desk

At a library you ask the librarian for book 823.9 and get the whole book, cover and pages together. You don't wander the stacks or get loose chapters, and you hand the whole book back when you're done. How the stacks are arranged is the librarian's business.

  • The librarian is the repository.
  • The book is the aggregate.
  • The stacks are the database.

3How it solves it a collection-like door to storage

Keep the interface small and named in the domain's language. For reports and screens that need lists, joins and paging, don't stretch the repository: use a separate query service or read model (CQRS-style).

  1. One per aggregate root

    OrderRepository, CustomerRepository. Never OrderLineRepository.

  2. Define the interface in the domain

    In the domain's terms: get, save, awaitingShipment().

  3. Implement it in infrastructure

    With your ORM or SQL, mapping rows to the aggregate and back.

  4. Load and save whole aggregates

    With a version for optimistic locking.

  5. Keep queries few and named

    A handful of business queries; everything else goes to a read model.

  6. Use an in-memory version in tests

    So domain and application tests run in milliseconds.

Vocabulary for the exam

Repository
A collection-like interface for loading and saving aggregates.
Aggregate root
The only thing a repository returns and saves.
Data mapper
Code that moves data between objects and tables (often the ORM).
Unit of work
Tracks changes and commits them together; most ORMs include one.
Generic repository
A one-size Repository<T> for every table; usually adds nothing over the ORM.
Read model
A separate model optimised for queries and screens.
order-repository.tsinterface in the domain, implementation outside
// domain/ordering/order-repository.ts
export interface OrderRepository {
  get(id: OrderId): Promise<Order>;                 // whole aggregate, or throws
  save(order: Order): Promise<void>;                // optimistic lock on version
  awaitingShipment(limit: number): Promise<Order[]>;
}

// infrastructure/postgres-orders.ts
export class PostgresOrders implements OrderRepository {
  constructor(private db: Kysely<DB>) {}
  async get(id: OrderId) {
    const row = await this.db.selectFrom("orders").where("id", "=", id).selectAll().executeTakeFirstOrThrow();
    const lines = await this.db.selectFrom("order_lines").where("order_id", "=", id).selectAll().execute();
    return OrderMapper.toDomain(row, lines);
  }
  // save(): update orders WHERE version = ?, replace lines, insert outbox events
}

// tests: new InMemoryOrders()  — same interface, a Map inside

tools: ORMs that already act as repositories and units of work (EF Core DbSet, Spring Data, Hibernate, Prisma), query builders like Kysely or jOOQ for the implementation, and a simple in-memory fake for tests.

then & now built in now

Then Evans, 2003; Fowler, PoEAA 2002

Evans and Fowler described repositories as collection-like interfaces over a data mapper, hiding query construction. In 2003 you wrote them yourself, often with hand-written SQL.

Now 2026

Modern ORMs (EF Core, Spring Data, Hibernate, Prisma) already provide repositories and units of work. Wrapping them in a generic repository is now seen as an anti-pattern. A thin, specific repository per aggregate root is still valuable for a rich domain and fast tests.

Verdict: Built in now: use your ORM's version, and add your own interface only for aggregate roots in a rich domain.

4Gains vs losses nothing is free

What we gain

  • No SQL in business rules.
  • Fast domain tests with an in-memory repository.
  • Whole aggregates loaded the same way every time.
  • Storage can change without touching the domain.

What we lose

  • An extra layer over an ORM that already does this.
  • Mapping code between rows and aggregates.
  • Tempting to bloat with query methods.
  • Loading whole aggregates can be wasteful for small reads.

6Common pitfalls the usual ways this goes wrong

  • A repository per table

    OrderLineRepository lets code change lines without the root. Fix → one repository per aggregate root.

  • Generic repository over the ORM

    Repository<T> with getAll() just wraps DbSet and leaks IQueryable. Fix → use the ORM directly, or write specific repositories with named methods.

  • Query explosion

    findByStatusAndCityAndDateBetween… for every screen. Fix → send screen queries to a read model or query service.

  • Saving inside the domain

    Entities call repositories to save themselves. Fix → application services load, call and save; the domain stays storage-free.

7When to use it (and when not)

Use it when…

  • A rich domain model with aggregates.
  • You want business rules tested without a database.
  • Storage details are complex or may change.

Skip it when…

  • CRUD apps where the ORM already gives you all you need.
  • Reporting and list screens (use queries or read models).

8Self-check quiz

How many repositories should an aggregate have?

One, for its root. Children are loaded and saved through the root.

Where does the repository interface live?

In the domain layer, in domain terms. The implementation lives in infrastructure.

Why is a generic Repository<T> over an ORM often pointless?

The ORM already is a repository and unit of work; the wrapper adds a layer without adding meaning.

What do you use for complex list and report queries?

A separate query service or read model, not more repository methods.

what would you do?Your OrderRepository has 46 methods, most of them for admin screens with filters and paging, and it returns half-loaded orders. What do you change?

Cut it back to the aggregate's needs: get, save and a few business queries that return whole orders. Move screen queries to a query service that returns flat DTOs straight from SQL, without loading aggregates.

try it

Pick one aggregate in your code. Write a repository interface with only get, save and one business query, an in-memory implementation, and rewrite one domain test to use it instead of the database. Time the test before and after.
