Domain Events

TL;DR

When something happens that the business cares about, record it as an event in the past tense: OrderPlaced, PaymentFailed, ParcelDelivered. The aggregate records the event; it's saved with the change and then published. Other parts of the system react in their own time: reserve stock, send an email, add points. The order code doesn't need to know who's listening.

  • Family: tactical building block
  • Not in: the 2003 book (added by Evans in 2004+)
  • Delivered by: outbox + message broker
  • Pairs with: aggregate, transactional outbox, event storming

1The problem why do we even need this?

One method that does the change and every reaction to it becomes slow, fragile and impossible to extend safely.

  • placeOrder() calls stock, email, loyalty and analytics in a row.
  • A slow or broken side service breaks the main action.
  • Every new reaction means editing the core method again.

2Real-life analogy the birth announcement

When a baby is born, the parents send one announcement: “Mia was born on 4 March.” They don't ring the registry, the grandparents, the employer and the nursery one by one and wait for each. Each recipient decides what to do: register, knit a hat, arrange leave.

  • The announcement is a domain event: a fact, in the past tense.
  • The recipients are subscribers.
  • The parents don't depend on them.

3How it solves it record the fact, publish it, react separately

Domain events stay inside a context and use its language. When you share them with other contexts, publish a stable integration event (part of a published language) and keep the internal one free to change.

  1. Name events in the past tense

    From the business's words: OrderPlaced, not OrderCreatedEvent or SendEmail.

  2. Record them in the aggregate

    The method that changes state also appends the event to a list.

  3. Save with the change

    Write events to an outbox table in the same transaction as the aggregate.

  4. Publish reliably

    A relay or change-data-capture moves outbox rows to the broker.

  5. Handle idempotently

    Each handler can receive an event twice; make that harmless.

  6. Separate internal and integration events

    Translate to a versioned public event before other contexts see it.

Vocabulary for the exam

Domain event
A record of something that happened in the domain, in the past tense.
Integration event
A published, versioned event meant for other contexts.
Event handler
Code that reacts to an event.
Transactional outbox
Saving events in the same transaction as the change, then publishing.
Idempotent handler
Processing the same event twice has the same effect as once.
Eventual consistency
Other parts catch up shortly after the event.
order.tsrecord, save with the change, react elsewhere
type OrderPlaced = { type: "OrderPlaced"; orderId: OrderId; total: Money; placedAt: Date };

export class Order {
  readonly events: OrderPlaced[] = [];
  place(now: Date) {
    if (this.lines.length === 0) throw new Error("Empty order");
    this.status = "placed";
    this.events.push({ type: "OrderPlaced", orderId: this.id, total: this.total(), placedAt: now });
  }
}

// repository: save state and events in one transaction (outbox)
await db.tx(async (t) => {
  await t.orders.update(order);
  await t.outbox.insertMany(order.events);
});

// elsewhere, in its own transaction, idempotent
on("OrderPlaced", async (e) => { await email.sendConfirmation(e.orderId); });

tools: an outbox table plus a relay or Debezium, brokers like Kafka, RabbitMQ, SNS/SQS or Azure Service Bus, in-process dispatchers (MediatR notifications, Spring application events) for reactions inside one service.

then & now matters more now

Then Evans, 2004+ (not in the 2003 book)

Domain events are missing from the 2003 book. Evans added them afterwards (talks from 2004, the DDD Reference in 2015), after teams found that “something happened” was a key part of the model.

Now 2026

They are now central: event storming starts from them, event-driven architecture and microservices run on them, and the outbox pattern and brokers like Kafka made publishing them reliable.

Verdict: Grew from an afterthought into one of the most used DDD ideas.

4Gains vs losses nothing is free

What we gain

  • Decoupled reactions: add a subscriber without touching the order.
  • Resilience: a broken side service doesn't break the main action.
  • Audit trail of what happened in business terms.
  • Matches the language from event storming.

What we lose

  • Eventual consistency: reactions happen a bit later.
  • Harder to follow the flow by reading code.
  • Infrastructure: outbox, broker, retries.
  • Duplicates and ordering must be handled.

6Common pitfalls the usual ways this goes wrong

  • Publishing before committing

    The event goes out, then the transaction rolls back: a ghost order. Fix → transactional outbox: save events with the change, publish after commit.

  • Commands dressed as events

    SendWelcomeEmail published as an “event”. Fix → events state facts in the past tense; the subscriber decides what to do.

  • Leaking internal events

    Other teams subscribe to internal events, so you can't change them. Fix → translate to versioned integration events at the border.

  • Non-idempotent handlers

    A redelivered event sends two emails or adds points twice. Fix → store processed event IDs, or make the effect naturally idempotent.

7When to use it (and when not)

Use it when…

  • Several reactions to one business fact.
  • Side effects that shouldn't slow down or break the main action.
  • Integrating contexts loosely, or building read models.

Skip it when…

  • A single reaction that must happen in the same transaction (just do it).
  • Tiny apps where a direct call is simpler and failure is fine.

8Self-check quiz

How should domain events be named?

In the past tense, using the business's words: OrderPlaced, PaymentFailed.

Why save events in the same transaction as the change?

So an event is published if and only if the change was committed (transactional outbox).

What's the difference between a domain event and an integration event?

A domain event is internal to a context; an integration event is a published, versioned contract for other contexts.

Why must handlers be idempotent?

Brokers deliver at least once, so a handler may see the same event twice.

what would you do?Customers sometimes get an order confirmation email for an order that doesn't exist. Logs show the email handler ran, but the order transaction rolled back. What's wrong?

The event was published before the transaction committed. Save the event in an outbox table in the same transaction, and publish it only after commit through a relay, so a rolled-back order never produces an event.

try it

Find a method in your code that changes something and then calls two or more side effects. Make it record an event instead, write the event to a table in the same transaction, and move one side effect into a handler that reads it.

remember!!

Send one announcement, in the past tense, and let everyone who cares decide for themselves.
