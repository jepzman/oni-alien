Domain & Application Services

TL;DR

Put a business rule that belongs to no single object (a transfer between two accounts, a price that depends on customer, basket and promotions) in a domain service: stateless, named in the domain's language, with no database or HTTP code. Put the use case (load, call the domain, save, publish) in an application service, which has no business rules of its own. Both stay thin; most logic belongs on entities and value objects.

  • Family: tactical building block
  • From: Evans (2003), ch. 5; Fowler's service layer (2002)
  • Today often: command handlers, use-case classes
  • Pairs with: repository, aggregate

1The problem why do we even need this?

Without a clear home for rules that span objects, and for use-case plumbing, both end up in a giant “service” class that does everything.

  • One OrderService mixes HTTP, transactions, email and pricing rules.
  • Or one entity reaches into another to apply a shared rule.
  • Business rules are tested only through HTTP.

2Real-life analogy the hospital

In a hospital the coordinator books the theatre, gets forms signed and calls the team, but makes no medical decisions. The surgeon makes them. A move between two wards is decided by the bed manager, because neither ward can decide it alone.

  • The coordinator is the application service.
  • The surgeon's knowledge lives in entities and aggregates.
  • The bed manager is a domain service.

3How it solves it two kinds of service, both thin

Try the entity first. Only when a rule truly needs several aggregates or an outside policy (exchange rates, tax tables) does it become a domain service. If a domain service grows large, the model is probably missing a concept.

  1. Put rules on objects first

    If a rule is about one order, it's a method on Order.

  2. Spot cross-object rules

    Transfers, pricing across basket and customer, matching. Those become domain services.

  3. Name them as domain actions

    PointsTransfer, PricingPolicy, not CustomerHelper.

  4. Keep domain services pure

    Stateless, no repositories, no HTTP: values in, decisions out.

  5. One application service per use case

    TransferPoints: authorise, load, call the domain, save, publish.

  6. Keep controllers dumb

    Parse input into a command, call the use case, map the result.

Vocabulary for the exam

Domain service
A stateless operation expressing a domain rule that doesn't belong to one entity.
Application service
Coordinates a use case: transaction, loading, calling the domain, saving.
Service layer
Fowler's term for the application layer's boundary of use cases.
Command handler
A modern shape of an application service: one class per command.
Use case
One thing a user or system wants to do, end to end.
God service
A huge service class that holds everything.
transfer-points.tsapplication service + domain service
// domain: pure rule across two aggregates
export class PointsTransfer {
  transfer(from: Customer, to: Customer, points: Points, policy: LoyaltyPolicy) {
    if (from.tier === "basic" && points.value > policy.basicTransferLimit)
      throw new Error("Basic members can transfer at most " + policy.basicTransferLimit);
    from.spendPoints(points);
    to.receivePoints(points);
  }
}

// application: one use case, no business rules
export class TransferPoints {
  constructor(private customers: CustomerRepository, private tx: UnitOfWork,
              private rule = new PointsTransfer(), private policy: LoyaltyPolicy) {}
  async handle(cmd: { from: CustomerId; to: CustomerId; points: number }) {
    await this.tx.run(async () => {
      const [a, b] = await Promise.all([this.customers.get(cmd.from), this.customers.get(cmd.to)]);
      this.rule.transfer(a, b, Points.of(cmd.points), this.policy);
      await this.customers.saveAll([a, b]);
    });
  }
}

tools: command and handler libraries (MediatR, Axon, NestJS CQRS module), use-case or “interactor” classes in clean architecture, and architecture tests that keep HTTP and database imports out of the domain layer.

then & now rethought

Then Evans, 2003; Fowler, PoEAA 2002

Evans separated domain services (stateless domain operations) from application services; Fowler's service layer defined the application's boundary. Both warned that services can drain the model of its behaviour.

Now 2026

The split held, but the shape changed: one big service per entity gave way to one handler per command or use case, vertical slices and clean architecture “interactors”. Functional styles make domain services simply pure functions.

Verdict: Rethought: the two roles are still right; write them as small use-case handlers and pure functions, not big service classes.

4Gains vs losses nothing is free

What we gain

  • Business rules have a clear home.
  • Use cases are easy to find: one class each.
  • Domain tests without infrastructure.
  • Thin controllers and thin services.

What we lose

  • More classes than one big service.
  • Judgement needed: entity or domain service?
  • Domain services can become dumping grounds.
  • Overkill for CRUD.

6Common pitfalls the usual ways this goes wrong

  • Everything is a service

    Entities are data bags; all logic sits in services. Fix → put rules on entities first; services only for what spans objects.

  • Rules in the application service

    if (vip && total > 100) inside the use case. Fix → move the decision into the domain; the use case just calls it.

  • Domain services with repositories

    The pricing rule loads customers from the database itself. Fix → pass in what it needs; loading is the application's job.

  • Helper and Manager names

    OrderHelper, CustomerManager hide what they do. Fix → name after the domain action.

7When to use it (and when not)

Use it when…

  • Rules that involve several aggregates or an outside policy.
  • A codebase where use cases are hard to find.
  • You want business rules tested without infrastructure.

Skip it when…

  • Simple CRUD: one handler that saves a form is enough.
  • A rule that clearly belongs on one entity.

Related patterns

8Self-check quiz

What's the difference between a domain service and an application service?

A domain service holds a business rule that spans objects; an application service coordinates a use case (load, call, save) with no business rules.

Should a domain service use repositories?

Preferably not: the application service loads what's needed and passes it in.

When should a rule be a domain service rather than an entity method?

When it involves several aggregates or an outside policy, and doesn't naturally belong to one.

What's a common modern shape for application services?

One command handler or use-case class per operation.

what would you do?A code review shows a new DiscountService that loads the customer and basket from the database, checks VIP status, calls the payment API and writes an audit log. What do you suggest?

Split it: a pure domain service (or a method on the basket) that decides the discount from values passed in; an application service that loads the customer and basket, calls it, saves and publishes; and the payment call and audit log in infrastructure behind ports.

try it

Take the biggest service class in your code. Highlight the lines that are business rules in one colour and plumbing (HTTP, transactions, mapping, logging) in another. Move one rule into an entity or a pure domain service and test it without a database.
