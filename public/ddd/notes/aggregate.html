Aggregate

TL;DR

Group objects that must stay consistent together (an order and its lines) into an aggregate with one root. Outside code can only talk to the root, which checks every rule before changing anything inside. One aggregate is loaded and saved in one transaction; other aggregates are referenced by ID and updated separately, often by events. Keep aggregates small.

  • Family: tactical building block
  • From: Evans (2003), ch. 6; Vernon (2011)
  • Rule of thumb: one aggregate per transaction
  • Pairs with: repository, domain events, optimistic locking

1The problem why do we even need this?

When any code can change any object, business rules that span several objects (invariants) get broken, especially under concurrency.

  • Lines are added straight to the line table, bypassing the order's limits.
  • Two requests change the same order at once and both “pass” the check.
  • One transaction locks orders, customers and stock at the same time.

2Real-life analogy the table's waiter

In a restaurant you don't walk into the kitchen and add dishes to your own ticket. You ask your table's waiter, who checks the rules (kitchen closing, set menu, sold out) and updates the ticket. One waiter per table means two guests can't put conflicting orders on it at the same time.

  • The ticket and its items are the aggregate.
  • The waiter is the aggregate root.
  • Other tables are other aggregates, served separately.

3How it solves it a consistency boundary with one door

Vaughn Vernon's four rules (2011): protect true invariants inside the border; design small aggregates; reference others by ID; and use eventual consistency between aggregates. Ask “does this rule really have to be true at every instant, or within a few seconds?”

  1. Find the invariants

    Rules that must be true at every moment: “at most ten lines”, “total within credit limit”.

  2. Draw the smallest border around them

    Only objects that take part in such a rule go inside.

  3. Pick the root

    The one entity outside code may hold and call. Everything else is reached through it.

  4. Refer to others by ID

    Order stores customerId, not a Customer object.

  5. One aggregate per transaction

    Load, call a method, save, with a version number for optimistic locking.

  6. Between aggregates, use events

    “Order placed” → reserve stock in another transaction, eventually consistent.

Vocabulary for the exam

Aggregate
A cluster of objects treated as one unit for changes.
Aggregate root
The single entry point that enforces the aggregate's rules.
Invariant
A rule that must always hold within the aggregate.
Consistency boundary
The border inside which changes are immediately consistent.
Optimistic concurrency
Save only if the version hasn't changed since loading.
Eventual consistency
Other aggregates catch up shortly after, through events.
order.tsthe root guards the rules
export class Order {
  private lines: OrderLine[] = [];
  private status: "draft" | "placed" = "draft";
  private constructor(readonly id: OrderId, readonly customerId: CustomerId,  // by ID
                      private creditLimit: Money, public version = 0) {}

  addLine(productId: ProductId, qty: Quantity, unitPrice: Money) {
    if (this.status !== "draft") throw new Error("Order is already placed");
    if (this.lines.length >= 10) throw new Error("At most 10 lines");
    const next = this.total().add(unitPrice.times(qty));
    if (next.cents > this.creditLimit.cents) throw new Error("Over credit limit");
    this.lines.push(new OrderLine(productId, qty, unitPrice));
  }
  total(): Money { return this.lines.reduce((t, l) => t.add(l.subtotal()), Money.zero("EUR")); }
}

tools: ORMs with optimistic locking (@Version in JPA, concurrency tokens in EF Core), document databases that store one aggregate per document, and event stores (EventStoreDB, Marten) for event-sourced aggregates.

then & now matters more now

Then Evans, 2003; Vernon, 2011

Evans described aggregates as clusters with a root and a boundary, but gave little guidance on size, and early implementations were often large object graphs loaded through ORM lazy loading.

Now 2026

Vernon's “Effective Aggregate Design” (2011) rethought the sizing: small aggregates, references by ID, eventual consistency between them. Aggregates then became the unit of event sourcing, of documents in NoSQL stores, and of consistency in microservices.

Verdict: More important today than in 2003: it's the tactical pattern that matters most, as long as you keep it small.

4Gains vs losses nothing is free

What we gain

  • Invariants always hold, even under concurrency.
  • One door: easy to see how state can change.
  • Small transactions, fewer lock conflicts.
  • Natural unit for storage, caching and events.

What we lose

  • Hard to size right: too big locks too much, too small can't protect rules.
  • Eventual consistency between aggregates must be designed.
  • Loading the whole aggregate for a small change.
  • Queries across aggregates need separate read models.

6Common pitfalls the usual ways this goes wrong

  • Giant aggregates

    Customer contains all orders, all addresses and all payments; every change locks it. Fix → small aggregates around true invariants; reference by ID.

  • Changing two aggregates in one transaction

    Placing an order also updates stock and loyalty points atomically. Fix → one aggregate per transaction; the rest via events.

  • Bypassing the root

    A repository for OrderLine lets code add lines directly. Fix → repositories only for roots; children reached through the root.

  • No concurrency control

    Two requests load version 7 and both save. Fix → optimistic locking with a version column; retry on conflict.

7When to use it (and when not)

Use it when…

  • Rules that span several objects and must always hold.
  • Concurrent changes to the same business object.
  • A rich core domain with real behaviour.

Skip it when…

  • CRUD screens with no rules across objects.
  • Reporting and queries (use read models).

8Self-check quiz

What is an aggregate root?

The one entity outside code may reference and call; it enforces the aggregate's rules.

Why reference other aggregates by ID?

So each aggregate stays small, is loaded and saved alone, and isn't accidentally changed through another.

How many aggregates should one transaction change?

One, as a rule. Others are updated afterwards, usually through domain events.

How do you stop two concurrent changes from breaking an invariant?

Optimistic locking: save only if the version is unchanged, otherwise retry.

what would you do?Your Customer aggregate holds every order, address and payment method. Saving it takes 800 ms and checkout fails with lock timeouts during sales. What do you change?

Split it: make Order its own aggregate referencing the customer by ID, keep in Customer only what its own invariants need, and update anything else (loyalty, stats) through events after the order is placed. Add optimistic locking per aggregate.

try it

Pick one business rule that involves several objects (an order's maximum, a booking's capacity). Write the root class with one method that enforces it and a test that fails when the rule is broken. Then decide which other objects it should reference only by ID.
