Context Map

TL;DR

Draw every bounded context and, for each pair that talks, how they relate: who is upstream (others depend on it) and who is downstream, and which pattern they use (partnership, customer–supplier, conformist, anti-corruption layer, open host service, shared kernel). The map shows the real dependencies, technical and human, before they break something.

  • Family: strategic design
  • From: Evans (2003), ch. 14
  • Shows: contexts, dependencies, team relationships
  • Tools: Context Mapper, a whiteboard

1The problem why do we even need this?

Contexts and teams depend on each other in ways nobody wrote down, so a change in one breaks others by surprise.

  • A renamed field upstream breaks three teams downstream.
  • Nobody knows which team has to agree before a change.
  • The architecture diagram shows boxes and lines but not who depends on whom.

2Real-life analogy a political map

A political map shows borders, trade routes, who supplies water and power to whom, and where the customs posts are. A diplomat reads it before any negotiation, because who depends on whom decides what's possible.

  • Countries are bounded contexts.
  • Supply lines show upstream and downstream.
  • Customs posts are anti-corruption layers.

3How it solves it contexts, arrows and patterns

The map describes what is, not what you wish. If Ordering in fact copies whatever Payments sends, write “conformist”, even if you'd like an anti-corruption layer. The gaps between the map you have and the one you want become your to-do list.

  1. List the contexts

    Including external systems and SaaS: they are contexts you don't control.

  2. Draw who talks to whom

    One line per pair that exchanges data or calls.

  3. Mark upstream and downstream

    Upstream changes affect downstream, not the other way round. Write U and D on each end.

  4. Name the pattern

    Partnership, shared kernel, customer–supplier, conformist, ACL, open host service, published language, separate ways.

  5. Add the teams

    Who owns each context. Many problems are team problems, not code problems.

  6. Keep it alive

    Update it when integrations change; review it when planning big changes.

Vocabulary for the exam

Context map
A diagram of contexts and the relationships between them.
Upstream
The side whose model and changes affect the other side.
Downstream
The side that depends on the upstream's model.
Relationship pattern
A named way two contexts and teams relate, such as conformist.
Separate ways
Two contexts that deliberately don't integrate at all.
Big ball of mud
A part of the map with no clear borders; mark it honestly.

tools: Context Mapper (an Eclipse/VS Code plug-in with a small DSL that draws the map), the DDD Crew's context mapping cheat sheet, or a whiteboard photo kept next to the code.

then & now still core

Then Evans, 2003

Evans described the context map as a document of the contexts and their relationships, with a set of named patterns, many of them about teams and politics rather than code.

Now 2026

The same patterns are used daily, now for microservices, SaaS integrations and team design. Team Topologies' interaction modes (collaboration, X-as-a-service, facilitating) map closely to them. Context Mapper turns the map into a small DSL.

Verdict: Still core. The patterns were always as much about people as code, which is why they aged well.

4Gains vs losses nothing is free

What we gain

  • Dependencies are visible before a change.
  • Team relationships are named and can be improved.
  • A shared picture for planning and onboarding.
  • Shows where to invest: missing ACLs, risky conformists.

What we lose

  • Takes effort to draw honestly.
  • Goes stale if nobody owns it.
  • Uncomfortable truths (“we are conformist to that mess”).
  • Pattern names are jargon outside DDD circles.

6Common pitfalls the usual ways this goes wrong

  • Drawing the wished-for map

    Every line says “ACL” but the code copies upstream fields everywhere. Fix → draw what is true today; draw the target separately.

  • Only technical arrows

    Lines show HTTP calls but not which team must agree to a change. Fix → add team names and the relationship pattern.

  • A one-off poster

    Drawn in a workshop, never updated. Fix → keep it in the repository and review it in architecture meetings.

  • Leaving out external systems

    The payment provider isn't on the map, but it shapes Ordering's model. Fix → every external system is a context too.

7When to use it (and when not)

Use it when…

  • More than three contexts or teams that integrate.
  • Before a big change that crosses borders.
  • When integration problems keep surprising people.

Skip it when…

  • One team, one context, nothing to map.
  • As a substitute for talking to the other team.

8Self-check quiz

What does “upstream” mean on a context map?

The context whose model and changes affect the other; the downstream side depends on it.

Should a context map show how things are, or how you want them?

How they are. Draw the target separately; the difference is your plan.

Name four relationship patterns.

Partnership, shared kernel, customer–supplier, conformist, anti-corruption layer, open host service, published language, separate ways.

Why add team names to the map?

Many integration problems are about who must agree and who can change what, not about technology.

what would you do?A team wants to change the format of its OrderPlaced event. They ask “who uses it?” and nobody can answer in less than a day of grepping. What do you set up?

A context map that shows every consumer of each context, kept in the repository, plus consumer-driven contract tests or a schema registry that lists subscribers, so the answer is a lookup, not an investigation.

try it

Draw the context map of a system you know, including external services. For every line, write U and D, and the pattern you think it is. Then circle the one relationship that worries you most and write why.

remember!!

Before you change a context, read the map: the arrows tell you who you're about to break.
