CQRS

TL;DR

Command Query Responsibility Segregation: use one model to change data (commands, with all the business rules) and separate models to read it (queries), each shaped for the screens that use it. Read models are kept up to date from the write side, usually through events.

  • Family: data management
  • Lives in: inside one service (not across services)
  • Coined by: Greg Young, from Bertrand Meyer's CQS
  • Pairs with: event sourcing, outbox, materialised views

1The problem why do we even need this?

One data model usually serves both writes and reads. As the system grows, those two jobs pull the model in opposite directions.

  • Writes want normalised tables, strict validation, transactions and invariants (“stock can't go negative”).
  • Reads want data pre-joined, pre-summed and shaped for each screen: dashboards, search, mobile lists.
  • Reads usually outnumber writes 10:1 or 100:1, but both are scaled together.
  • Heavy report queries lock rows and slow down checkout.

2Real-life analogy the restaurant kitchen and the menu board

In a restaurant, taking an order and answering “what's on today?” are handled very differently.

  • Orders go on tickets to the kitchen, where there are rules: check stock, cook in order, one chef per station. That's the write side.
  • Customers read the menu board, which is written for reading: big, simple, no kitchen details. That's a read model.
  • When the fish sells out, the kitchen updates the board a moment later. For a short while the board can be slightly out of date: eventual consistency.
  • You can have several boards: one outside, one at the bar, one on the website. Several read models from the same kitchen.

3How it solves it two models, joined by events

Commands change state and return little or nothing. Queries return data and change nothing. In CQRS each side gets its own model, and often its own store.

  1. Split commands from queries

    PlaceOrder, CancelOrder go to the write model; GetOrderSummary, SearchOrders go to read models.

  2. Keep the write model strict

    Normalised schema, invariants, transactions. It only needs what's required to make decisions.

  3. Publish changes

    Every successful command emits events (via an outbox, or as the events themselves with event sourcing).

  4. Build read models per need

    Projections listen to events and update denormalised tables, caches or a search index, shaped exactly like the screen.

  5. Handle the lag

    Tell users their action was accepted, show the optimistic result, or read your own write from the write side for that one screen.

Light CQRS

Same database, separate code paths and maybe a few SQL views or materialised views for reads. Cheap and often enough.

Full CQRS

Separate read stores (Elasticsearch, Redis, a reporting DB), updated from events. More power, more moving parts.

Vocabulary for the exam

Command
A request to change state (“PlaceOrder”). May be rejected.
Query
A request for data that changes nothing.
Write model
The model that enforces business rules.
Read model
A denormalised view optimised for one kind of query.
Projection
Code that updates a read model from events.
Read-your-writes
Seeing your own change straight after making it.
orders-cqrs.tswrite side + projection + query
// WRITE side: rules, then events
export async function placeOrder(cmd: { orderId: string; items: Item[] }) {
  if (cmd.items.length === 0) throw new Error("Empty order");
  await db.transaction(async (tx) => {
    await tx.insert("orders", { id: cmd.orderId, status: "PLACED" });
    await tx.insert("outbox", { type: "OrderPlaced", payload: cmd });
  });
}

// PROJECTION: keeps a read model shaped for the dashboard
bus.on("OrderPlaced", async (e) => {
  await readDb.upsert("dashboard_orders", {
    id: e.orderId, item_count: e.items.length,
    total: sum(e.items.map((i) => i.price)), placed_at: e.at,
  });
});

// READ side: no joins, no rules, just fast
export const recentOrders = () =>
  readDb.query("SELECT * FROM dashboard_orders ORDER BY placed_at DESC LIMIT 20");

building blocks: MediatR (.NET) for command/query handlers, Axon (Java), Marten projections, Postgres materialised views, Debezium → Elasticsearch, Redis as a read cache.

4Gains vs losses nothing is free

What we gain

  • Fast reads shaped for each screen, no expensive joins.
  • Scale reads and writes separately; reads are usually the bigger side.
  • Simpler write model focused only on rules.
  • Many views from one source: dashboards, search, reports.
  • Less contention: reports no longer lock rows checkout needs.

What we lose

  • Eventual consistency. Read models lag behind writes.
  • More code and infrastructure: projections, read stores, events.
  • Duplicated data in several shapes.
  • Rebuilding read models needs tooling and time.
  • Overkill for simple CRUD screens.

6Common pitfalls the usual ways this goes wrong

  • CQRS for every service

    A settings page with 3 fields gets commands, events, projections and two databases. Fix → use it where reads and writes truly differ; plain CRUD elsewhere.

  • Ignoring the lag in the UI

    User saves, the list reloads from the read model and the item “isn't there”. They click save again. Fix → optimistic UI, read-your-writes for that view, or show “processing”.

  • Projections that aren't idempotent

    A replay or duplicate event doubles the totals on the dashboard. Fix → idempotent projections (upsert by id, track last event position).

  • Querying the write model for screens

    Shortcuts creep in and the write DB serves reports again. Fix → keep queries on read models; guard the boundary in code review.

  • No way to rebuild

    A projection bug corrupts the read model and there's no replay. Fix → keep the events (or outbox history) and a rebuild command.

7When to use it (and when not)

Use it when…

  • Reads and writes have very different shapes or volumes.
  • Complex domains with rich rules on the write side.
  • Many different views of the same data (dashboards, search, mobile).
  • You already use event sourcing.

Skip it when…

  • Simple CRUD where the form and the table look the same.
  • Users must always see their changes instantly everywhere.
  • A small team that can't run the extra infrastructure.
  • A read replica or a cache would solve the performance problem.

8Self-check quiz

What's the difference between a command and a query?

A command asks to change state and can be rejected; a query only returns data and never changes anything.

Why are read models eventually consistent?

They're updated asynchronously from events after the write commits, so there's a short delay.

Does CQRS require event sourcing?

No. They're often combined, but CQRS works with a normal database plus an outbox or even SQL views.

A user saves a change but the list doesn't show it yet. Two ways to fix the experience?

Optimistically show the change in the UI, or read that one item from the write side (read-your-writes), or show a “processing” state.

remember!!

Write with rules, read with speed. Two models, one source of truth, a short delay in between.
