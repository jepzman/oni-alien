Publish–Subscribe

TL;DR

When something happens, the producer publishes one event to a topic and moves on. Any number of services subscribe to that topic and each receives its own copy. The producer doesn't know who's listening, so you can add new consumers without touching it.

  • Family: communication / messaging
  • Lives in: a message broker (topics)
  • Also called: event-driven, fan-out
  • Pairs with: outbox, idempotent consumer, saga (choreography)

1The problem why do we even need this?

With direct calls, the service where something happens must know about, call and wait for every service that cares.

  • Tight coupling: Order has hard-coded calls to Email, Shipping, Analytics and Loyalty.
  • Slow and fragile: if Analytics is slow or down, placing an order is slow or fails.
  • Hard to extend: a new Fraud service wants order events, so the Order team must change and redeploy.
  • Wrong ownership: Order's code ends up full of other teams' concerns.

2Real-life analogy the radio station

A radio station broadcasts a show on its frequency. It doesn't phone each listener. Anyone who has tuned in hears it; anyone who hasn't, doesn't.

  • The station doesn't know or care how many radios are on. A new listener can tune in without the station changing anything.
  • A radio that's switched off simply misses it. (Brokers improve on radio: durable subscriptions keep messages until the subscriber comes back.)
  • Different stations for different topics: news, sport, traffic.

3How it solves it topics and subscriptions

A broker sits in the middle. Producers write to topics; consumers read through subscriptions. Each subscription receives every message, independently of the others.

  1. Name events as facts

    OrderPlaced, PaymentFailed: past tense, about the producer's domain, not instructions to a consumer.

  2. Publish reliably

    Use the transactional outbox so the event is published if and only if the change committed.

  3. Subscribe per consumer

    Each consuming service gets its own subscription (or Kafka consumer group), so it reads at its own pace.

  4. Handle duplicates and order

    Expect at-least-once delivery; make handlers idempotent. Order is usually only guaranteed per key/partition.

  5. Version the contract

    Add fields, don't rename or remove them. Publish a schema (Avro, JSON Schema, Protobuf) and check compatibility.

Thin event

OrderPlaced { id: 42 }. Small and safe, but consumers may call back for details.

Fat event (event-carried state)

OrderPlaced { id, items, total, address }. Consumers have what they need; bigger and harder to change.

Vocabulary for the exam

Topic
A named channel events are published to.
Subscription
A consumer's registration to receive a topic's messages.
Fan-out
One published message delivered to many consumers.
Durable subscription
Messages are kept while the subscriber is offline.
Consumer group
Kafka's version of a subscription shared by a service's instances.
Schema registry
A store of event schemas with compatibility checks.
order-events.tspublish once; subscribers are independent
// producer: knows the topic, not the consumers
await outbox.add({ topic: "orders", type: "OrderPlaced",
                   key: order.id, data: { id: order.id, total: order.total } });

// consumer 1 (Email service, its own subscription)
broker.subscribe("orders", { group: "email" }, async (e) => {
  if (e.type === "OrderPlaced") await sendReceipt(e.data.id);   // idempotent!
});

// consumer 2, added months later; Order never changed
broker.subscribe("orders", { group: "fraud-check" }, async (e) => {
  if (e.type === "OrderPlaced") await scoreRisk(e.data);
});

brokers: Apache Kafka, RabbitMQ (fanout / topic exchanges), Google Pub/Sub, AWS SNS + SQS, Azure Service Bus topics, NATS, Redis Streams.

4Gains vs losses nothing is free

What we gain

  • Loose coupling. Producers don't know or call consumers.
  • Easy to extend. New consumers subscribe without changes to the producer.
  • Faster, more resilient producers; slow consumers don't slow them down.
  • Each consumer scales and fails independently.
  • A record of business events others can build on.

What we lose

  • Eventual consistency between producer and consumers.
  • Harder to follow the flow. “Who reacts to OrderPlaced?” needs tooling.
  • Duplicates and ordering must be handled by consumers.
  • Event contracts are public APIs; changing them is hard.
  • A broker to run, secure and monitor.

6Common pitfalls the usual ways this goes wrong

  • Events that are commands in disguise

    SendWelcomeEmail on a shared topic: the producer is still telling a specific consumer what to do. Fix → publish facts (UserRegistered); consumers decide what to do.

  • Breaking the event schema

    A field is renamed and three teams' consumers crash on deploy. Fix → additive changes only, schema registry, versioned events.

  • Assuming global order

    Consumers assume OrderCancelled always arrives after OrderPlaced, but they're on different partitions. Fix → partition by entity key; handle out-of-order events.

  • Event spaghetti

    50 services reacting to each other's events; nobody can explain a checkout end to end. Fix → an event catalogue, tracing, and orchestration for long flows.

  • Publishing without an outbox

    The DB commit succeeds but the publish fails, so consumers never hear. Fix → transactional outbox.

7When to use it (and when not)

Use it when…

  • Several services need to react to the same business event.
  • You want to add consumers over time without changing producers.
  • The producer shouldn't wait for consumers to finish.
  • Integrating bounded contexts owned by different teams.

Skip it when…

  • The caller needs an answer now (use a request/response call).
  • Exactly one known receiver should do a specific task (use a queue / command).
  • Strict, immediate consistency between producer and consumers is required.
  • A tiny system where a direct call is clearer.

8Self-check quiz

What's the difference between a topic subscription and a work queue?

In pub/sub every subscription gets a copy of every message; in a work queue each message goes to just one of the competing consumers.

Why name events in the past tense?

They describe facts that already happened in the producer's domain, so consumers decide how to react, which keeps the producer decoupled.

How do you guarantee events for one order arrive in order?

Use the order id as the partition/message key, so all its events go to one partition and are read in sequence.

A new Fraud service wants order events. What changes in the Order service?

Nothing. Fraud creates its own subscription to the existing topic.
