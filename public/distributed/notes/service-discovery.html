Service Discovery

TL;DR

In the cloud, service instances come and go with new addresses. Instead of hard-coding IPs, each instance registers in a service registry (and keeps sending heartbeats); callers look up a name and get the current list of healthy instances to load-balance across.

  • Family: communication / infrastructure
  • Lives in: registry + client, proxy or DNS
  • Examples: Kubernetes DNS, Consul, Eureka
  • Pairs with: health checks, load balancing, sidecars

1The problem why do we even need this?

In a data centre of the past, servers had fixed addresses for years. Today, instances are cattle, not pets: autoscaling, deploys, spot instances and crashes create and destroy them all day.

  • A hard-coded list of IPs is wrong within minutes: callers hit dead instances and miss new ones.
  • Scaling Payments from 3 to 10 instances doesn't help if callers only know about the old 3.
  • A crashed instance keeps receiving traffic until someone edits the config.
  • Different environments (dev, staging, prod) need different addresses everywhere.

2Real-life analogy the phone directory

You don't memorise the phone number of every shop. You look it up by name in the directory (or a maps app) and get the current number. When a shop moves, it updates its listing; you don't have to do anything.

  • Shops that close are removed, so you don't call dead numbers (health checks + heartbeats).
  • A chain lists several branches; you pick the nearest or least busy one (load balancing).
  • You might keep a recent lookup on a sticky note for a while (client-side caching with a TTL).

3How it solves it register, check, look up

There are two flavours:

  • Client-side discovery: the caller (or its library/sidecar) queries the registry and picks an instance itself.
  • Server-side discovery: the caller sends to a load balancer or DNS name, which looks up the registry for it.
  1. Register

    On startup an instance registers its name, address, port and metadata (version, zone), or the platform (Kubernetes) does it automatically.

  2. Stay healthy

    The instance sends heartbeats or the registry runs health checks. Missing ones get removed after a short TTL.

  3. Look up by name

    Callers ask for “payments” and get the list of healthy instances (via an API, DNS, or the sidecar).

  4. Load-balance

    Pick an instance (round robin, least requests, same zone first) and keep the list cached briefly.

  5. Deregister on shutdown

    On a graceful stop, remove the instance first and drain in-flight requests.

4Gains vs losses nothing is free

What we gain

  • No hard-coded addresses; instances can move freely.
  • Autoscaling just works; new instances get traffic right away.
  • Dead instances are removed automatically.
  • Same code in every environment; only the registry differs.
  • Smarter routing by zone, version or health.

What we lose

  • The registry is critical; it must be highly available.
  • Stale data windows: a crashed instance may get traffic until its TTL expires.
  • More moving parts outside a platform like Kubernetes.
  • DNS caching surprises (clients ignoring TTLs).
  • Debugging “why did it call that instance?” gets harder.

6Common pitfalls the usual ways this goes wrong

  • Caching lookups forever

    A client resolves DNS once at startup and keeps calling an instance that died an hour ago. Fix → respect TTLs; re-resolve; use a client that refreshes.

  • Health checks that check nothing

    /health always returns 200, even when the DB is unreachable, so broken instances stay in rotation. Fix → readiness checks that test what the instance needs to serve.

  • Health checks that check too much

    Every instance's health depends on a shared DB, so a DB blip marks all of them unhealthy at once. Fix → liveness = “am I stuck?”; readiness = “can I serve?”; avoid deep cascading checks.

  • No graceful deregistration

    Pods are killed mid-request because they were still in the registry. Fix → deregister first, drain, then stop (preStop hooks).

  • A single registry node

    The registry dies and nothing can find anything. Fix → a replicated registry cluster and client-side caches.

7When to use it (and when not)

Use it when…

  • Instances are dynamic: containers, autoscaling, spot instances.
  • Many services call each other.
  • You deploy to several environments or regions.
  • You want health-aware load balancing.

Skip it when…

  • A few long-lived servers with stable addresses.
  • A single service behind one load balancer.
  • Your platform already does it (Kubernetes Services, serverless). Use that, don't add another registry.

8Self-check quiz

Client-side vs server-side discovery?

Client-side: the caller queries the registry and picks an instance. Server-side: the caller hits a load balancer or DNS name that does the lookup.

How does a registry learn an instance has died?

Missed heartbeats (TTL expiry) or failed health checks remove it from the list.

What's the difference between liveness and readiness checks?

Liveness asks “is the process stuck and in need of a restart?”; readiness asks “can it serve traffic right now?”, which decides whether it stays in rotation.

What does Kubernetes use for service discovery?

Service objects with stable DNS names, backed by EndpointSlices that list the ready pods.

remember!!

Call services by name, never by address. The registry knows who's alive; your config shouldn't have to.
