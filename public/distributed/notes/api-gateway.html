API Gateway

TL;DR

Put a single entry point in front of your services. Clients call the gateway; it handles the shared chores (TLS, authentication, rate limiting, logging), routes each request to the right internal service, and can combine several calls into one response.

  • Family: communication / edge
  • Lives in: the edge of your system
  • Variant: Backends for Frontends (BFF)
  • Pairs with: rate limiter, service discovery, circuit breaker

1The problem why do we even need this?

With microservices, one screen might need data from five or six services. If clients call them directly, problems pile up.

  • Chatty clients: a mobile app on a slow network makes six round trips to draw one screen.
  • Leaky internals: clients know every service's address and API, so you can't split, merge or move services without breaking apps.
  • Duplicated chores: each service re-implements authentication, rate limits, CORS, logging and TLS, all slightly differently.
  • Security surface: every service is exposed to the internet.

2Real-life analogy the hotel front desk

In a hotel you don't wander into the kitchen to order food or find housekeeping's office for towels. You go to the front desk. They check your key card once, take the request, and pass it to the right team behind the scenes.

  • Guests only need to know one place. The hotel can reorganise its teams without telling anyone.
  • The desk can combine requests: “late checkout and a taxi” in one conversation.
  • If the desk is closed, nobody gets anything. It must be well staffed and always open.

3How it solves it handle chores once, then route

The gateway is a reverse proxy with extra powers. Typical jobs, roughly in order for each request:

  1. Terminate TLS

    HTTPS ends at the gateway; inside, services can use mTLS via the mesh.

  2. Authenticate and authorise

    Validate the token once, then pass the user's identity to services in a header.

  3. Protect

    Rate limits per client, request size limits, IP allow/deny lists, WAF rules.

  4. Route and transform

    Map public paths to internal services (/api/orders/* → Orders), translate protocols (REST → gRPC), version APIs.

  5. Aggregate and observe

    Optionally fan out to several services and merge the results; log, measure and trace every request.

One gateway or one per client type?

Single gateway

One edge for everyone. Simple to run, but can grow into a shared “god” layer every team has to change.

Backends for Frontends (BFF)

A small gateway per client type (web BFF, mobile BFF), owned by that frontend team and shaped for its screens.

routes:
  - path: /api/orders/*
    service: http://orders.internal:8080
    plugins:
      - jwt-auth: { issuer: "https://login.example.com" }
      - rate-limit: { per_key: 100/min }
      - timeout: 2s
  - path: /api/catalog/*
    service: http://catalog.internal:8080
    plugins:
      - cache: { ttl: 60s }
  - path: /api/home          # one call, three services
    aggregate:
      - GET http://users.internal/me
      - GET http://catalog.internal/featured
      - GET http://orders.internal/recent?limit=3

products: Kong, NGINX, Envoy Gateway, Traefik, AWS API Gateway, Azure API Management, Google Apigee, Spring Cloud Gateway, YARP (.NET). GraphQL federation is a popular aggregation flavour.

4Gains vs losses nothing is free

What we gain

  • One stable public API; internals can change freely behind it.
  • Cross-cutting concerns in one place: auth, limits, TLS, logging.
  • Fewer round trips for clients through aggregation.
  • Smaller attack surface: services stay on the private network.
  • Easier API versioning and gradual migrations (e.g. strangler fig).

What we lose

  • An extra network hop on every request.
  • A critical component: if it's down, everything is down.
  • Can become a bottleneck for teams if all changes go through it.
  • Business logic creep: it slowly turns into a monolith.
  • Another thing to scale, secure and monitor.

6Common pitfalls the usual ways this goes wrong

  • Business logic in the gateway

    Discount rules and order validation creep into gateway scripts until it's a hidden monolith. Fix → keep it to routing and cross-cutting concerns; logic stays in services.

  • One gateway owned by one team

    Every feature needs a ticket to the platform team to add a route. Fix → self-service config, or BFFs owned by the client teams.

  • Single instance, single zone

    The gateway pod restarts and the whole product is down. Fix → run several instances across zones behind a load balancer.

  • No timeouts or breakers on backends

    One slow service fills the gateway's connections and everything stalls. Fix → per-route timeouts, circuit breakers and bulkheads.

  • Aggregation without partial results

    Reviews is down, so the whole home page fails. Fix → return what you have, mark missing parts, use fallbacks.

7When to use it (and when not)

Use it when…

  • Several services are used by external or mobile clients.
  • You need consistent auth, rate limiting and logging at the edge.
  • Clients would otherwise need many round trips per screen.
  • You want to hide or evolve the internal structure.

Skip it when…

  • One service and one client: a plain load balancer is enough.
  • Service-to-service traffic inside the cluster (that's the mesh's job).
  • You'd put business rules in it.
  • Latency budgets so tight that one hop matters (rare).

8Self-check quiz

Name three cross-cutting concerns a gateway typically handles.

Any three of: TLS termination, authentication, rate limiting, logging/metrics/tracing, CORS, caching, request size limits.

What's a BFF and why use one?

A Backend for Frontend: a gateway per client type, owned by that frontend team and shaped for its screens, so one shared gateway doesn't become a bottleneck.

How do you stop the gateway being a single point of failure?

Run multiple instances across zones behind a load balancer, keep it stateless, and add timeouts and breakers to backend calls.

Gateway vs service mesh: which handles north–south traffic?

The gateway handles north–south (clients ↔ system); the mesh handles east–west (service ↔ service).

remember!!

One front door for clients, many rooms behind it. Keep the door smart about security, and dumb about business.
