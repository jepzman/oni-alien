Rate Limiter

TL;DR

Decide how many requests each client (user, API key, IP, tenant) may make in a period, for example 100 per minute. Count them, and when a client goes over, reject the extra requests quickly with 429 Too Many Requests and a hint about when to retry.

  • Family: resilience / protection
  • Lives in: API gateway, load balancer, or the service
  • Also called: throttling
  • Pairs with: retries with Retry-After, quotas, API keys

1The problem why do we even need this?

A service has limited capacity: CPU, memory, database connections, a paid third-party quota. Without limits, any single client can use all of it.

  • A buggy script calls your API in a tight loop: 5,000 requests a second.
  • A big customer runs a bulk import at 9 a.m. on Monday.
  • A bot scrapes every product page, or someone tries passwords by brute force.
  • Your own retry storm after an outage (see note 02).

In every case, well-behaved clients get slow responses or errors because of someone else.

2Real-life analogy the turnstile at a theme park ride

A popular ride can only take so many people a minute. A turnstile lets guests through at a steady rate. If you arrive when it's at its limit, you wait or come back later. The ride never gets overloaded, and everyone gets a fair turn.

  • Think of it as a bucket of ride tokens that refills slowly. Each guest takes a token. A group can go in together if enough tokens have saved up (a burst).
  • Annual-pass holders get a bigger bucket: different limits per plan.
  • The sign says “next entry in 4 s”, so guests know when to try again (Retry-After).

3How it solves it count, compare, allow or reject

Every request is mapped to a key (API key, user ID, IP, tenant). The limiter keeps a counter per key and decides in microseconds whether the request fits. Common algorithms:

  • Token bucket: tokens refill at rate r up to size b; each request spends one. Allows short bursts, enforces the average. The most common choice.
  • Leaky bucket: requests drain from a queue at a fixed rate. Smooths output completely.
  • Fixed window: count per calendar minute. Simple, but allows 2× the limit around the minute boundary.
  • Sliding window: counts over the last 60 s. Fairer, a bit more work.
  1. Choose the key

    Per API key for partners, per user for logged-in traffic, per IP for anonymous traffic, per tenant for SaaS.

  2. Choose the limits

    Base them on capacity and fairness, e.g. 100 req/min with bursts of 20; higher for paid plans; stricter on expensive endpoints like login or search.

  3. Count somewhere shared

    With many instances, keep counters in a shared store (Redis, the gateway) or give each instance limit ÷ N.

  4. Reject clearly

    Return 429 Too Many Requests with Retry-After and RateLimit-* headers so clients can back off.

  5. Monitor and tune

    Track rejections per key. A key that's always limited may be a bug, an attacker, or a customer who needs a bigger plan.

Vocabulary for the exam

Rate limit
Max requests per key per period (e.g. 100/min).
Quota
A larger allowance over a long period (e.g. 1M calls/month).
Burst
Short spike above the average that the limiter tolerates.
429 Too Many Requests
The HTTP status for “you're over your limit”.
Retry-After
Header saying how many seconds to wait before retrying.
Load shedding
Dropping low-priority work when the whole system is overloaded.
token-bucket.tsone bucket per key, in Redis in real life
type Bucket = { tokens: number; updated: number };
const buckets = new Map<string, Bucket>();

export function allow(key: string, ratePerSec = 10, capacity = 20): number {
  const now = Date.now() / 1000;
  const b = buckets.get(key) ?? { tokens: capacity, updated: now };
  // refill for the time that passed, but never above capacity
  b.tokens = Math.min(capacity, b.tokens + (now - b.updated) * ratePerSec);
  b.updated = now;
  buckets.set(key, b);
  if (b.tokens >= 1) { b.tokens -= 1; return 0; }        // allowed
  return Math.ceil((1 - b.tokens) / ratePerSec);         // seconds to wait
}

app.use((req, res, next) => {
  const wait = allow(req.apiKey ?? req.ip);
  if (wait === 0) return next();
  res.set("Retry-After", String(wait)).status(429).send("Too Many Requests");
});

ready-made: API gateways (Kong, AWS API Gateway usage plans, Azure APIM), NGINX limit_req, Envoy local / global rate limit, Cloudflare rate limiting, Redis + a Lua script for a shared token bucket.

4Gains vs losses nothing is free

What we gain

  • Protects capacity from floods, bugs and abuse.
  • Fairness. One client can't starve the others.
  • Predictable cost for expensive or paid downstream calls.
  • Security against brute force and scraping.
  • Product tiers. Limits become part of free vs paid plans.

What we lose

  • Legit traffic gets rejected when limits are too tight.
  • Shared counters add a dependency (Redis) and a little latency.
  • Hard to choose the key. Many users behind one office IP look like one client.
  • Clients must handle 429 properly, or they'll just retry harder.
  • More config per plan, endpoint and key.

6Common pitfalls the usual ways this goes wrong

  • Limiting by IP only

    A whole university or company shares one IP and hits the limit together. Fix → limit by API key or user where you can; use IP only for anonymous traffic.

  • Per-instance counters

    10 instances each allow 100/min, so the real limit is 1,000/min and changes as you scale. Fix → a shared store, or divide the limit by the instance count.

  • No Retry-After

    Clients get 429 with no hint and retry instantly in a loop. Fix → send Retry-After and RateLimit headers; document them.

  • Fixed windows at the boundary

    A client sends 100 at 12:00:59 and 100 at 12:01:00: 200 in two seconds. Fix → token bucket or sliding window.

  • Same limit for every endpoint

    Cheap GETs and an expensive report endpoint share one number. Fix → weight expensive endpoints or give them their own limits.

  • Limiter fails closed

    Redis goes down and the limiter rejects every request. Fix → decide on purpose: usually fail open with a local fallback limit.

7When to use it (and when not)

Use it when…

  • Public or partner APIs.
  • Expensive endpoints: login, search, exports, AI calls.
  • Multi-tenant SaaS where tenants share capacity.
  • Calls to a paid third party with its own quota.

Skip it when…

  • Internal calls between your own services, where backpressure, bulkheads or queues fit better.
  • Traffic is tiny and trusted.
  • You actually need to smooth bursts of work. Use a queue (note 12).
  • Clients can't handle rejection at all (e.g. hardware devices that never retry).

8Self-check quiz

What's the difference between the bucket's refill rate and its size?

The refill rate is the long-run average allowed; the size is the largest burst a client can send at once after being idle.

Why can fixed-window counting let through 2× the limit?

A client can send the full limit at the end of one window and again at the start of the next, so two windows' worth arrive within seconds.

Which HTTP status and header should a limiter return?

429 Too Many Requests, with Retry-After (and ideally RateLimit-Limit / RateLimit-Remaining / RateLimit-Reset).

Should the limiter fail open or closed if its counter store is down?

Usually open, with a conservative local limit, so an outage of the limiter doesn't become an outage of the API. Security-critical endpoints like login may fail closed.

remember!!

Everyone gets a fair share. Over your share? Get a fast 429 and a time to come back, never a slow death for everyone.
