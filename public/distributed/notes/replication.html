Leader–Follower Replication

TL;DR

Keep copies of the same data on several machines. One node, the leader, accepts all writes and streams its change log to followers, which apply the changes in order. Followers serve reads and can be promoted if the leader fails.

  • Family: data / availability
  • Lives in: the database layer
  • Also called: primary–replica, master–slave (old term)
  • Pairs with: leader election, sharding, CQRS

1The problem why do we even need this?

A single database server is both a single point of failure and a single bottleneck.

  • If its disk or machine dies, the app is down until it's restored, and data since the last backup is lost.
  • All reads land on one machine: app queries, reports and analytics compete for CPU.
  • Users far away (another continent) get slow responses from one location.
  • Maintenance (patching, upgrades) means downtime.

2Real-life analogy the teacher's board

In class, only the teacher writes on the board. Every student copies it into their own notebook. When you need to check something, you read your own copy instead of crowding round the board.

  • If the teacher steps out, a student with good notes can take over at the board (a failover).
  • A student who looked away is a line or two behind: replication lag. Reading from their notebook might miss the latest line.
  • For an exam answer that must be exactly right, you check the board itself: read from the leader.

3How it solves it a log, shipped in order

The leader writes every change to a log (Postgres WAL, MySQL binlog). Followers receive the log and replay it in the same order, so they end up with the same data.

  1. Send all writes to the leader

    One place decides the order of writes, so there are no write conflicts.

  2. Stream the log

    The leader ships each change to followers. Synchronous: the commit waits for at least one follower (no data loss on failover, slower). Asynchronous: it doesn't wait (fast, but recent writes can be lost).

  3. Read from followers

    Route read-only queries, reports and analytics to followers. Accept that they may lag by milliseconds or seconds.

  4. Handle read-your-writes

    After a user changes something, read their data from the leader (or wait for the follower to catch up) for a short time.

  5. Fail over safely

    Detect the leader is down, promote the most up-to-date follower, repoint clients, and make sure the old leader can't keep accepting writes (fencing).

db.tsroute reads and writes
const leader   = new Pool({ host: "db-leader" });
const follower = new Pool({ host: "db-replicas" });          // load-balanced replicas

export async function placeOrder(order: Order) {
  await leader.query("INSERT INTO orders ...", [order.id]);   // writes: leader only
  recentlyWrote.set(order.customerId, Date.now());
}

export async function myOrders(customerId: string) {
  // read-your-writes: just after a write, read from the leader
  const fresh = Date.now() - (recentlyWrote.get(customerId) ?? 0) < 5_000;
  const pool = fresh ? leader : follower;
  return pool.query("SELECT * FROM orders WHERE customer_id = $1", [customerId]);
}

built in: Postgres streaming replication (+ Patroni for failover), MySQL replication / Group Replication, AWS RDS / Aurora read replicas and Multi-AZ, MongoDB replica sets, Redis replicas + Sentinel.

4Gains vs losses nothing is free

What we gain

  • High availability: a follower can take over in seconds.
  • Read scale: add followers for more read capacity.
  • Isolation: reports and backups run on followers.
  • Lower latency with followers near users in other regions.
  • Durability: data exists on several machines.

What we lose

  • Replication lag: followers can return stale data.
  • Writes don't scale: still one leader.
  • Failover is tricky: lost async writes, split brain.
  • More machines and monitoring.
  • App complexity for routing and read-your-writes.

6Common pitfalls the usual ways this goes wrong

  • Reading your own write from a follower

    A user updates their profile, the page reloads from a lagging follower and shows the old name. Fix → read-your-writes from the leader for a short window, or wait for the follower's position.

  • Assuming async = no data loss

    The leader dies with 2 seconds of unreplicated writes; they're gone after failover. Fix → synchronous (or semi-sync) to at least one follower for important data.

  • Split brain

    The old leader comes back and keeps accepting writes alongside the new one. Fix → fencing (see note 18), a consensus-based failover manager.

  • Followers as backups

    Someone runs DELETE without WHERE, and it replicates everywhere within milliseconds. Fix → replicas are not backups; keep point-in-time backups too.

  • Unmonitored lag

    A follower falls 3 hours behind and serves very stale reports. Fix → alert on lag; remove lagging followers from the read pool.

7When to use it (and when not)

Use it when…

  • You need the database to survive a machine or zone failure.
  • Reads far outnumber writes.
  • Reports and analytics shouldn't slow the app.
  • Users in several regions need fast reads.

Skip it when…

  • Writes are the bottleneck (shard instead, or as well).
  • Every read must be perfectly up to date and you can't route to the leader.
  • A dev/test database where downtime doesn't matter.
  • Your managed database already does it (just turn it on).

8Self-check quiz

Sync vs async replication: which can lose data on failover?

Asynchronous: the leader may have acknowledged writes that never reached a follower before it died.

Does adding followers increase write capacity?

No. All writes still go through the single leader; followers add read capacity and availability.

What is read-your-writes consistency?

A user always sees their own recent changes, e.g. by reading from the leader just after they write.

Why are replicas not a backup?

Mistakes like accidental deletes replicate to every follower; backups let you go back in time.

remember!!

One writer, many readers, and every reader might be a little behind. Know which reads can wait and which must ask the leader.
