Cache-Aside

TL;DR

Keep a copy of frequently read data in a fast cache (like Redis). The application checks the cache first; on a miss it reads the database and puts the result in the cache with an expiry (TTL). On a write, it updates the database and deletes the cached copy, so the next read loads fresh data.

  • Family: data / performance
  • Lives in: the application (cache is a side store)
  • Also called: lazy loading
  • Pairs with: TTLs, read replicas, CQRS

1The problem why do we even need this?

Many systems read the same data far more often than it changes: product details, prices, user profiles, configuration.

  • The product page asks the database for the same popular item 5,000 times a minute.
  • Each query takes 40 ms and uses CPU, so the database gets busy doing repeated work.
  • Users wait for every one of those queries, and the database needs a bigger (pricier) machine.

2Real-life analogy the fridge and the grocery store

When you want milk, you check the fridge first. If it's there, you're done in seconds. If not, you go to the store (slow), buy some, and put it in the fridge so next time is quick.

  • Milk has a use-by date. After that you throw it out and buy fresh. That's a TTL.
  • If you switch to oat milk, you throw out the old carton straight away so nobody pours the wrong one: invalidate on write.
  • The fridge is small, so the stuff you rarely use gets pushed out: eviction (LRU).
  • If ten flatmates find the fridge empty at once and all run to the store, that's a cache stampede.

3How it solves it lazy loading + invalidation

The cache doesn't talk to the database; the app sits beside both and manages the cache itself (that's the “aside”).

  1. Read: try the cache

    GET product:42. Hit? Return it. This is often under 1 ms.

  2. Miss: load and fill

    Read from the database, then SET product:42 … EX 300 (5-minute TTL), then return.

  3. Write: update, then delete

    Update the database first, then DEL product:42. Deleting (not overwriting) avoids racing writers putting old values back.

  4. Always set a TTL

    Even with invalidation, a TTL bounds how long any mistake or missed delete can serve stale data. Add a little random jitter to TTLs.

  5. Protect against stampedes

    When a hot key expires, let one request reload it (a lock or “single flight”) while others wait or get the stale value.

Vocabulary for the exam

Cache hit / miss
Found in the cache / not found, go to the source.
TTL
How long a cached item lives before expiring.
Invalidation
Removing a cached item because the source changed.
Eviction (LRU)
Dropping least-recently-used items when memory is full.
Cache stampede
Many requests missing at once and hammering the DB.
Hit ratio
Hits ÷ all lookups; the main health metric.
product-cache.tscache-aside with Redis
export async function getProduct(id: string): Promise<Product> {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);                       // hit

  const product = await db.one("SELECT * FROM products WHERE id = $1", [id]);  // miss
  const ttl = 300 + Math.floor(Math.random() * 60);           // TTL + jitter
  await redis.set(key, JSON.stringify(product), { EX: ttl });
  return product;
}

export async function updatePrice(id: string, price: number) {
  await db.query("UPDATE products SET price = $1 WHERE id = $2", [price, id]);
  await redis.del(`product:${id}`);                           // delete, don't set
}

caches: Redis / Valkey, Memcached, AWS ElastiCache, Azure Cache for Redis; in-process caches (Caffeine, MemoryCache) for tiny hot data; CDNs do the same idea for HTTP responses.

4Gains vs losses nothing is free

What we gain

  • Much faster reads: sub-millisecond instead of tens of milliseconds.
  • Less database load, so a smaller or cheaper database.
  • Absorbs read spikes on hot items.
  • Only caches what's actually used (lazy loading).
  • Cache outage is survivable: the app falls back to the database.

What we lose

  • Stale data for up to the TTL, or longer if invalidation is missed.
  • Cache invalidation is famously hard to get right.
  • First request after a miss is slower (extra round trip).
  • Another system to run, size and monitor.
  • Stampedes and hot keys need extra care.

6Common pitfalls the usual ways this goes wrong

  • Updating the cache instead of deleting

    Two writers race; the older value is written to the cache last and stays there until TTL. Fix → update the DB, then delete the key.

  • No TTL

    A missed invalidation serves the wrong price for weeks. Fix → always set a TTL as a safety net.

  • Cache stampede

    A hot key expires and 2,000 requests hit the database at the same moment. Fix → single-flight locking, early refresh, TTL jitter.

  • Caching everything

    Rarely read data fills memory and evicts the hot items. Fix → cache what's read often; measure the hit ratio.

  • Caching per-user data under shared keys

    User A's cart is shown to user B. Fix → include every varying input (user, locale, permissions) in the key.

7When to use it (and when not)

Use it when…

  • Data is read much more often than it changes.
  • Slight staleness (seconds to minutes) is acceptable.
  • Database load or latency is the bottleneck.
  • The same items are requested by many users.

Skip it when…

  • Data changes constantly and must always be exact (balances, stock at checkout).
  • Every request is unique (low hit ratio).
  • The database is already fast enough.
  • You can't find all the places that change the data.

8Self-check quiz

Why delete the cache key on write instead of setting the new value?

Concurrent writers can race and leave an older value in the cache; deleting forces the next read to load the latest value from the database.

What is a cache stampede and one way to prevent it?

Many requests miss on the same expired hot key and hit the database together. Use a lock/single-flight so one request reloads, or refresh early, or add TTL jitter.

Cache-aside vs read-through: who loads the data on a miss?

In cache-aside the application loads it and fills the cache; in read-through the cache library/service loads it from the database itself.

What's the main metric to watch?

The hit ratio (plus latency and evictions).

remember!!

Fridge first, store second, and throw out what changed. Every cached thing gets an expiry date.
