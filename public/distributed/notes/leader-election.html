Leader Election

TL;DR

When a job must be done by exactly one instance at a time (a scheduler, a shard owner, the primary database), the instances elect a leader through a coordination service. The leader holds a lease that it must keep renewing; if it dies or stalls, the lease expires and another instance takes over. A fencing token stops a stale old leader from doing damage.

  • Family: coordination
  • Lives in: a consensus store (etcd, ZooKeeper, Consul)
  • Built on: Raft / Paxos / ZAB
  • Pairs with: replication, sharding, distributed locks

1The problem why do we even need this?

You run several copies of a service for availability, but some work must happen exactly once.

  • A nightly invoice job runs on all three instances, so customers get three invoices.
  • Pin it to “server 1” instead, and when server 1 dies, nobody gets invoices.
  • Two database nodes both think they're the primary and accept conflicting writes (split brain).
  • Two workers both think they own partition 5 and process it twice.

2Real-life analogy the talking stick

In a group meeting, only the person holding the talking stick takes the official notes. Everyone agrees who holds it. Their turn lasts a fixed time and they have to renew it by saying “still here”. If they leave, the stick goes back on the table and the next person picks it up.

  • Exactly one note-taker at a time, but never zero for long.
  • If Ana nods off and wakes up later, she might still think she's the note-taker. So each new turn gets a number, and the official notebook only accepts notes from the latest number: a fencing token.

3How it solves it leases, watches and fencing

Don't invent your own election algorithm. Use a strongly consistent coordination service that already runs consensus, and build on its leases.

  1. Campaign

    Each instance tries to create the key /election/billing with a lease (e.g. 15 s TTL). The store guarantees only one succeeds.

  2. Lead and renew

    The winner becomes leader and renews its lease well before it expires (e.g. every 5 s). It stops leading the moment a renewal fails.

  3. Watch

    Followers watch the key. When it disappears (leader crashed or partitioned away), they campaign again.

  4. Fence

    Every new leadership term gets a higher number (fencing token). Downstream systems reject writes with an older token, so a paused old leader can't overwrite the new one's work.

  5. Design for the gap

    During failover there's briefly no leader. Make the work resumable and idempotent so a new leader can pick up where the last one stopped.

Vocabulary for the exam

Leader
The one instance currently allowed to do the job.
Lease
Time-limited leadership that must be renewed.
Consensus
Agreement among nodes despite failures (Raft, Paxos).
Split brain
Two nodes acting as leader at the same time.
Fencing token
A number that increases with every new leader.
Quorum
A majority of nodes needed to make a decision.
billing-scheduler.tsetcd-style election (pseudo-client)
const election = etcd.election("billing-scheduler", { leaseTtlSeconds: 15 });

for (;;) {
  const term = await election.campaign(myId);         // blocks until we win
  log.info(`leader for term ${term.token}`);           // token always increases
  try {
    while (await term.isStillLeader()) {               // lease auto-renewed
      const job = await nextDueJob();
      if (job) await runInvoices(job, { fencingToken: term.token });
      await sleep(1_000);
    }
  } finally {
    await term.resign();                                // step down cleanly
  }
}

// downstream: refuse work from an old leader
// UPDATE jobs SET ... WHERE id = $1 AND last_token <= $2

4Gains vs losses nothing is free

What we gain

  • Exactly-one execution without a single fixed server.
  • Automatic failover when the leader dies.
  • No split brain when combined with fencing.
  • Simple model for singleton jobs (schedulers, compactors).
  • Foundation for replication and sharding ownership.

What we lose

  • Depends on a consensus cluster that must itself be highly available.
  • Failover gap: a few seconds with no leader.
  • The leader is a bottleneck for its work.
  • Subtle bugs around clocks, GC pauses and partitions.
  • Hard to test without fault injection.

6Common pitfalls the usual ways this goes wrong

  • Rolling your own election

    A homemade “lowest IP wins” scheme breaks during a network partition and two leaders appear. Fix → use etcd / ZooKeeper / Consul or a library built on them.

  • No fencing

    The old leader pauses for 20 s (GC), its lease expires, a new leader starts, then the old one wakes and keeps writing. Fix → fencing tokens checked by the resource being written.

  • Lease shorter than pauses

    A 2-second lease with frequent 3-second GC pauses causes constant leader flapping. Fix → lease TTL comfortably above worst-case pauses; renew at about 1/3 of TTL.

  • Trusting the local clock

    Leader decides it still holds the lease based on its own clock, which drifted. Fix → rely on the coordination service's view and stop work as soon as renewal fails.

  • Leader does everything

    All work goes through one leader, which becomes the bottleneck. Fix → elect leaders per shard/partition, not one global leader.

7When to use it (and when not)

Use it when…

  • A job must run exactly once at a time (scheduler, cron, compaction).
  • One node must own a resource (a shard, a partition, the primary DB).
  • You need automatic failover for that role.
  • You already run (or can use) etcd, ZooKeeper or Consul.

Skip it when…

  • The work can be split and done by everyone (use competing consumers).
  • Duplicates are harmless and the job is idempotent anyway.
  • A managed scheduler or database already handles failover for you.
  • A single instance with a fast restart is good enough.

8Self-check quiz

Why does a leader need a lease that expires?

So that if the leader crashes or is cut off, leadership is automatically released and another instance can take over.

What problem does a fencing token solve?

A stale leader that was paused or partitioned can't overwrite the new leader's work, because resources reject requests with an older (lower) token.

Why use etcd or ZooKeeper instead of a simple database row?

They provide consensus-backed, strongly consistent leases and watches that stay correct during network partitions and node failures.

Your leader is overloaded. What's the usual fix?

Partition the work and elect a leader per partition/shard, spreading leadership across instances.

remember!!

Exactly one leader, never for free: borrow leadership with a lease, keep renewing it, and fence off the ghosts of leaders past.
