Sharding

TL;DR

When one database can't hold or handle all the data, split it horizontally: each shard is a separate database holding only some of the rows, chosen by a shard key (e.g. customer id). A router sends every query to the shard that owns its key, so storage and load spread across many machines.

  • Family: data / scaling
  • Lives in: the data layer (or the database itself)
  • Also called: horizontal partitioning
  • Pairs with: consistent hashing, replication, CQRS

1The problem why do we even need this?

You can make one database server bigger (scale up) only so far. At some point the data or the write load outgrows the biggest machine.

  • The dataset is 4 TB and growing 300 GB a month; disks and backups can't keep up.
  • 40,000 writes per second at peak; one primary can't take more.
  • Indexes no longer fit in memory, so every query gets slower.
  • Read replicas help reads, but every write still goes to one primary.

2Real-life analogy the library card catalogue

An old library catalogue doesn't keep every card in one giant drawer. It's split into drawers by the first letter of the surname: A–F, G–M, N–S, T–Z.

  • To find “Tagunicar”, you go straight to T–Z. You never look in the others. That's routing by the shard key.
  • Four people can search four drawers at once. That's parallel load.
  • But if lots of surnames start with S, the N–S drawer overflows: a hot shard. You'd have to re-split the drawers: resharding.
  • “Find every book borrowed on Tuesday” means opening every drawer: a cross-shard query.

3How it solves it pick a key, route by it

Everything depends on the shard key. Common strategies:

  • Range (A–F, G–M; or dates): simple and good for range scans, but easily skewed (“everyone's writing to this month's shard”).
  • Hash (hash(key) % N): spreads evenly, but range queries hit every shard, and changing N moves most keys.
  • Consistent hashing: keys and shards sit on a ring; adding a shard moves only about 1/N of the keys.
  • Directory / lookup: a table says which shard each tenant lives on; flexible, but the table must be fast and available.
  1. Choose the shard key

    High cardinality, even spread, and present in most queries. customer_id or tenant_id are classic; country or created_date are usually skewed.

  2. Keep related data together

    Put a customer's orders, addresses and payments on the same shard, so most queries and transactions stay on one shard.

  3. Route every query

    In the app, a proxy (Vitess, ProxySQL) or the database itself (Citus, MongoDB, Cassandra, DynamoDB).

  4. Plan for cross-shard work

    Reports and global search go to a separate store (CQRS read model, data warehouse) instead of scatter-gather on every request.

  5. Plan to reshard

    Start with many small logical shards mapped onto few machines, so growth means moving shards, not re-splitting data.

Vocabulary for the exam

Shard
One partition of the data, usually its own database.
Shard key
The column that decides which shard a row lives on.
Hot spot
A shard getting far more load than the others.
Consistent hashing
Hash ring where adding a node moves only ~1/N of keys.
Scatter-gather
Sending a query to all shards and merging results.
Resharding
Moving data to a new shard layout.
shard-router.tsmany logical shards on a few machines
const LOGICAL_SHARDS = 1024;                      // fixed forever
const placement = new Map<number, string>([       // logical shard -> DB, can change
  ...range(0, 512).map((s) => [s, "db-a"] as const),
  ...range(512, 1024).map((s) => [s, "db-b"] as const),
]);

function shardFor(customerId: string): number {
  return murmurhash(customerId) % LOGICAL_SHARDS;
}

export function dbFor(customerId: string) {
  return pools.get(placement.get(shardFor(customerId))!);   // one shard per query
}

// all of a customer's data lives together, so this is a normal local transaction
await dbFor("c-731").transaction(async (tx) => { /* order + payment rows */ });

sharded databases and helpers: Vitess (MySQL), Citus (Postgres), MongoDB sharding, Cassandra / ScyllaDB, DynamoDB partitions, CockroachDB / Spanner / YugabyteDB (automatic ranges), Kafka partitions for streams.

4Gains vs losses nothing is free

What we gain

  • Near-unlimited scale for storage and writes by adding shards.
  • Smaller indexes per shard, so queries stay fast.
  • Fault isolation: a shard outage affects only its slice of users.
  • Parallel work: backups, migrations and queries run per shard.
  • Data locality: shards can live in the user's region.

What we lose

  • Cross-shard queries and joins are slow or impossible.
  • Cross-shard transactions need sagas or 2PC.
  • Resharding is hard and risky.
  • Hot spots if the key is skewed.
  • Much more operational complexity: N databases to run.

6Common pitfalls the usual ways this goes wrong

  • A skewed shard key

    Sharding by country puts 60% of users on the US shard. Fix → high-cardinality keys (customer id), or hash them.

  • Most queries need all shards

    The main screen searches across all customers, so every request hits every shard. Fix → shard by what most queries filter on; build a separate read model for the rest.

  • hash(key) % N with real machines

    Going from 4 to 5 servers moves ~80% of all keys at once. Fix → consistent hashing or many fixed logical shards mapped to machines.

  • Sharding too early

    A 50 GB database is split into 16 shards “for the future”. Fix → scale up, add read replicas, tune and cache first. Shard when you must.

  • Celebrity / hot keys

    One tenant is 100× bigger than the rest and overloads its shard. Fix → give big tenants dedicated shards; split hot keys.

7When to use it (and when not)

Use it when…

  • Data or write volume exceeds what one machine can handle.
  • Most queries are scoped to one key (customer, tenant, device).
  • You need data in specific regions (data residency).
  • You want to limit the blast radius of a database failure.

Skip it when…

  • The data fits on one machine with headroom (most systems!).
  • Reads are the bottleneck: try replicas and caching first.
  • Queries routinely join across all entities.
  • Your database can partition for you automatically. Use that.

Related patterns

  • Leader–follower replication · each shard is replicated
  • Cache-aside
  • CQRS · global read models
  • Saga · cross-shard work
  • Consistent hashing

8Self-check quiz

Why is hash(key) % N a problem when N changes?

Most keys map to a different shard when N changes, so nearly all data has to move at once.

What makes a good shard key?

High cardinality, an even spread of data and load, and present in most queries so they hit one shard.

How do you run a report across all customers in a sharded system?

Scatter-gather across shards for occasional use, or better, feed all shards into a separate analytics/read store.

Replication vs sharding?

Replication copies the same data to several machines (availability, read scale); sharding splits different data across machines (write and storage scale). Real systems do both.

remember!!

Split by the key your queries already use. Shard late, shard many small pieces, and keep each customer's data together.
