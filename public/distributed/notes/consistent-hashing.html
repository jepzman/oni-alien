Consistent Hashing

TL;DR

Spreading keys with hash(key) % N works until N changes: then almost every key moves. Consistent hashing places nodes and keys on the same ring; each key belongs to the next node clockwise. Adding or removing a node moves only the keys next to it, about 1/N of them. Virtual nodes (many points per server) keep the load even. Used by caches, sharded databases and load balancers that need stickiness.

  • Family: scaling data
  • Introduced: Karger et al. (1997), for web caches
  • Variants: virtual nodes · jump hash · rendezvous (HRW) hashing
  • Used by: Cassandra, DynamoDB, Memcached clients, Envoy ring-hash

1The problem why do we even need this?

A cache cluster spreads keys with hash(key) % 4. Traffic grows and a fifth node is added: now it's % 5, and about 80% of keys map to a different node. Almost every lookup misses at once, and the database behind the cache takes the full load.

  • Adding capacity causes an incident instead of preventing one.
  • Losing a node is just as bad: every key's home shifts.
  • For sharded data, “moving” means copying most of the data between machines.

2Real-life analogy a round table

Guests have name cards placed around a round table, and each is served by the first host clockwise from their card. When a new host sits down, only the guests between the new chair and the previous host move to the new host. Everyone else keeps their host.

3How it solves it a ring, virtual nodes, the next node clockwise

Hash every node many times (say 100–200 virtual nodes each) onto a ring, and keep the points sorted. For a key, hash it and find the first point at or after it (a binary search). To store copies, walk on to the next distinct nodes. A new node's points land all around the ring, so it takes a small slice from every other node.

  1. Hash nodes onto a ring

    Each node at many points: hash("node-3#0") … hash("node-3#149"). Keep the points sorted.

  2. Look up by the next point

    Hash the key, binary-search for the first point ≥ it, wrap to the start if needed.

  3. Use virtual nodes

    100–200 points per node keep the spread within a few percent; give bigger machines more points.

  4. Replicate along the ring

    Store copies on the next 2 distinct physical nodes clockwise.

  5. Move only what changed

    When a node joins or leaves, only the keys between it and its neighbour points move; copy those, nothing else.

Vocabulary for the exam

Hash ring
The hash space treated as a circle.
Virtual node
One of many ring positions belonging to the same physical node.
Key movement
The share of keys that change node when membership changes.
Jump hash
A fast, memory-free variant for numbered buckets (Lamping & Veach).
Rendezvous hashing
Each key picks the node with the highest hash(key, node).
Hot spot
A node that gets more than its share of keys or traffic.
ring.tsTypeScript, no library
import { createHash } from "node:crypto";
const h = (s: string) => createHash("md5").update(s).digest().readUInt32BE(0);

export class Ring {
  private points: { at: number; node: string }[] = [];

  constructor(nodes: string[], private vnodes = 150) { nodes.forEach((n) => this.add(n)); }

  add(node: string) {                       // many points per node keep the spread even
    for (let i = 0; i < this.vnodes; i++) this.points.push({ at: h(`${node}#${i}`), node });
    this.points.sort((a, b) => a.at - b.at);
  }

  remove(node: string) { this.points = this.points.filter((p) => p.node !== node); }

  nodeFor(key: string): string {            // first point at or after hash(key), wrapping around
    const k = h(key);
    let lo = 0, hi = this.points.length;
    while (lo < hi) { const mid = (lo + hi) >> 1; if (this.points[mid].at < k) lo = mid + 1; else hi = mid; }
    return this.points[lo % this.points.length].node;
  }
}
// 4 → 5 nodes: about 20% of keys move. With hash % N it would be about 80%.

tools: Envoy and NGINX ring-hash / Maglev load balancing, Memcached clients (ketama), Cassandra and ScyllaDB token rings, DynamoDB partitioning, Redis Cluster (16,384 fixed slots: the same goal by another route), Go hashring and Java Guava Hashing.consistentHash.

4Gains vs losses nothing is free

What we gain

  • Adding or removing a node moves ~1/N of keys, not almost all.
  • Smooth scaling of caches and shards.
  • Even load with virtual nodes, weighted by machine size.
  • Natural replica placement: the next nodes on the ring.

What we lose

  • More complex than a modulo.
  • Uneven without virtual nodes: a few points per node gives lumpy load.
  • Hot keys still land on one node; the ring doesn't split a key.
  • Every client must agree on the ring, or keys are looked up in the wrong place.

6Common pitfalls the usual ways this goes wrong

  • Too few virtual nodes

    Each server at one point on the ring: one server owns 40% of the keys. Fix → use 100–200 virtual nodes per server and check the spread.

  • Clients with different rings

    Two app versions hash with different functions or node lists, and look in different places. Fix → share one membership source and one hash function; roll changes out everywhere together.

  • Expecting it to fix hot keys

    One popular key still lands on one node. Fix → cache hot keys locally, or split them (key#0…key#7).

  • Forgetting the data move

    For stored data, the ring says where keys belong now, but the bytes are still on the old node. Fix → copy the moved ranges before switching, or read from both during the move.

7When to use it (and when not)

Use it when…

  • Caches and shards whose node count changes.
  • Sticky routing: the same user or session to the same backend.
  • Placing replicas in a peer-to-peer or leaderless store.

Skip it when…

  • The node count never changes; a modulo is simpler.
  • A fixed number of logical shards with a map already solves movement (see Sharding).
  • One managed service already does the placement for you (DynamoDB, Redis Cluster).

Related patterns

  • Sharding · logical shards are the other answer
  • Cache-aside
  • Leader–follower replication
  • Service discovery

8Self-check quiz

Why does hash % N move most keys when N changes?

The result depends on N, so for most keys the remainder changes: going from 4 to 5 nodes moves about 80% of keys.

On a ring, which node owns a key?

The first node position at or after the key's hash, going clockwise and wrapping around.

What problem do virtual nodes solve?

Uneven load: many points per node spread each node's share evenly around the ring.

Roughly what share of keys moves when going from 4 to 5 nodes?

About one fifth: the new node takes small slices from each of the others.

what would you do?A Memcached cluster of 6 nodes uses consistent hashing, but one node handles 35% of the traffic. Its key share is normal (about 17%). What's going on, and what do you do?

The keys are spread evenly, but a few hot keys on that node get far more requests. Consistent hashing can't split a single key: add a small local cache in the app for the hottest keys, or split them into several sub-keys, and track requests per key to find them.

try it

Hash 100,000 random keys onto 4 nodes with hash % 4, then with % 5, and count how many keys changed node. Do the same with the ring above (150 virtual nodes), then with only 1 virtual node per server, and compare both the share of keys that moved and the largest node's share.

remember!!

Nodes and keys on one ring. A new node takes a little from everyone, not everything from everyone.
