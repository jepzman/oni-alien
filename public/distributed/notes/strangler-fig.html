a.k.a. “replace it a route at a time”

Strangler Fig

TL;DR

Don't rewrite a big old system in one go. Put a routing facade (a proxy or gateway) in front of it, then move one route or capability at a time to new code, behind the same URLs. Each move is small, ships on its own, and can be switched back by changing a route. The old system shrinks until nothing routes to it, and then you turn it off.

  • Family: communication · migration
  • Named by: Martin Fowler (2004), after the strangler fig tree
  • Needs: a place to route traffic: proxy, gateway, or the app's own router
  • Pairs with: anti-corruption layer, change data capture, feature flags

1The problem why do we even need this?

A team decides to rewrite an eight-year-old monolith from scratch. Fourteen months later the rewrite is “60% done”, the old system has gained features the rewrite doesn't have, and users have received nothing new. The plan ends in one risky switch-over day.

  • Big-bang rewrites chase a moving target: the old system keeps changing.
  • Nothing reaches users until everything works, so the risk piles up at the end.
  • There's no small step back: switching over is all or nothing.

2Real-life analogy the strangler fig tree

A strangler fig starts as a seed in the branches of an old tree. Its roots grow down around the trunk, a little each year, carrying more of the weight, until the fig stands on its own and the old tree is no longer needed. At no point does anything fall down.

Translating it to software
In real lifeIn your code
The old treeThe legacy system, still serving users
Each new rootOne route or capability moved to new code
Growing around the trunkA facade in front that decides where each request goes
The fig carrying more weightMore routes pointing at new services
The old tree goneNo traffic to the monolith: switch it off

3How it solves it a facade and many small moves

Clients only ever talk to the facade. Routing rules decide which requests still go to the old system and which go to new services. Moving a capability means building it, testing it against real traffic, and changing a route; moving it back means changing the route back.

  1. Put a facade in front

    A reverse proxy or gateway that passes everything to the old system at first. Nothing changes for users.

  2. Pick a thin slice

    A capability with clear edges and real value: product search, invoices, one report. Not the hardest part first.

  3. Build it new, with its own data

    Sync the data it needs from the old database (change data capture), or call the old system through an anti-corruption layer.

  4. Shift traffic gradually

    Shadow requests to compare answers, then 1%, 10%, 100%. Keep the route switch as the rollback.

  5. Remove the old code

    Delete the old feature once nothing routes to it. Repeat until the monolith is empty.

Vocabulary for the exam

Facade
The single entry point that routes requests to old or new code.
Slice
One capability moved at a time, end to end.
Shadow traffic
Copying real requests to the new code without using its answers.
Anti-corruption layer
A translator that keeps the old model out of the new code.
Event interception
Capturing the old system's changes (CDC) to feed new services.
Big-bang rewrite
Replacing everything at once on one switch-over day.
facade.yamlEnvoy-style routes (generic)
# one facade, many small moves: each route is a separate, reversible change
routes:
  - match: { prefix: /search }          # moved in March: fully on the new service
    route: { cluster: search-v2 }

  - match: { prefix: /orders }          # moving now: 10% new, 90% old
    route:
      weighted_clusters:
        - { name: orders-v2,  weight: 10 }
        - { name: monolith,   weight: 90 }
    request_mirror_policies:            # also copy the old system's traffic to v2 to compare
      - { cluster: orders-v2-shadow, runtime_fraction: { default_value: { numerator: 100 } } }

  - match: { prefix: / }                # everything else: still the monolith
    route: { cluster: monolith }

tools: Envoy, NGINX, Traefik or a cloud API gateway as the facade; Kubernetes Gateway API HTTPRoutes; Debezium for change data capture; feature flags for slices inside one app; Diffy-style response comparison for shadow traffic.

4Gains vs losses nothing is free

What we gain

  • Value early: each slice ships on its own.
  • Small, reversible steps: a route change undoes a move.
  • Old and new run side by side, so real traffic tests the new code.
  • Can stop any time with a working system.

What we lose

  • Two systems to run for a long time.
  • Data sync between old and new databases is the hard part.
  • The facade is one more critical component.
  • Easy to stall at 80%, with the last hard parts never moved.

6Common pitfalls the usual ways this goes wrong

  • Facade with business logic

    The router starts translating, merging and fixing data. Fix → keep the facade to routing; put translation in an anti-corruption layer next to the new service.

  • Sharing the old database

    New services read and write the monolith's tables directly, so neither can change. Fix → give each new service its own data, synced by CDC or events.

  • Starting with the hardest part

    The first slice takes a year and the effort loses support. Fix → start with a thin, valuable, well-bounded slice.

  • Never finishing

    The last 20% stays in the monolith for ever, and you pay for both. Fix → plan and budget the removal of the old system, not only the new code.

7When to use it (and when not)

Use it when…

  • A large legacy system that must keep running while it's replaced.
  • Requests can be routed by path, host, tenant or message type.
  • You want value and learning before the whole migration ends.

Skip it when…

  • The system is small enough to rewrite in a few weeks.
  • Nothing can be routed separately (one huge batch job, a desktop app without seams).
  • The old system is being retired, not replaced.

8Self-check quiz

Why do big-bang rewrites so often fail?

The old system keeps changing, nothing ships until everything works, and the switch-over is one large, risky step.

What does the facade do?

It is the single entry point that routes each request to the old system or a new service.

How do you roll back a slice?

Change its route back to the old system.

What is usually the hardest part?

The data: keeping the old and new databases in step while both are in use.

what would you do?Six months into a strangler migration, three slices are live, but the new services all read the monolith's database directly, and a schema change in the monolith just broke two of them. What do you change?

Give each new service its own data, fed by change data capture or events from the old system, with an anti-corruption layer translating the old model. Then the monolith's schema can change without breaking the new services, and the old tables can be retired slice by slice.

try it

Put a local reverse proxy (NGINX, Caddy or Envoy) in front of any small app. Route one path to a second, new app, and send 10% of that path's traffic to it with a weight. Then move it to 100% and back to 0% by editing only the proxy config, and check the clients never noticed.

remember!!

Grow around it one root at a time. A route change is your undo button.
