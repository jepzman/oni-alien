Idempotent Consumer

TL;DR

Messages and retried requests can arrive more than once. Make the receiver idempotent: give every message or request a unique id, record the ids you've already handled (in the same transaction as the work), and when a duplicate shows up, skip the work and return the original result.

  • Family: data consistency / messaging
  • Lives in: every message consumer & write API
  • Also called: deduplication, idempotency keys
  • Pairs with: outbox, retries, saga

1The problem why do we even need this?

Almost every real messaging system gives you at-least-once delivery. “Exactly once” over a network is, in practice, at-least-once plus deduplication.

  • A consumer processes a message, then crashes before acknowledging it. The broker redelivers it.
  • The outbox relay publishes, then crashes before marking the row sent. The event goes out again.
  • A client times out waiting for POST /payments and retries, but the first one actually worked.
  • A rebalance moves a partition to another consumer, which re-reads the last few messages.

If the handler isn't idempotent, duplicates become double charges, double emails, double stock reservations.

2Real-life analogy the lift button

Pressing the lift button five times doesn't call five lifts. The first press registers the request; the others change nothing. That's idempotent: doing it again has the same effect as doing it once.

  • A cinema ticket with a number gets stamped once. Show it again and the usher says “already used”.
  • “Set the thermostat to 21 °C” is naturally idempotent. “Turn it up by 1 °C” is not: say it twice and it's 2 degrees warmer.

3How it solves it remember what you've done

There are two ways to get there, and good systems use both:

  • Make the operation naturally idempotent: “set status = PAID”, upserts, “reserve item X for order 42” (a unique constraint stops a second row).
  • Deduplicate by id: record each processed id and skip repeats. Needed for things like “add 100 points” or “send an email”.
  1. Give every message an id

    The producer sets a unique id (UUID or outbox row id). For HTTP, the client sends an Idempotency-Key header.

  2. Check and record in one transaction

    Insert the id into processed_messages with a unique constraint, in the same DB transaction as the business change.

  3. Duplicate? Skip

    If the insert hits the unique constraint, the work was already done: acknowledge the message (or return the stored response) and stop.

  4. Store the result for APIs

    For idempotent HTTP endpoints, save the response with the key so a retry gets exactly the same answer.

  5. Expire old ids

    Keep ids for longer than the longest possible redelivery or retry window (e.g. 7 days), then delete them.

handle-payment-captured.tsdedupe in the same transaction
export async function onPaymentCaptured(msg: { id: string; orderId: string; points: number }) {
  await db.transaction(async (tx) => {
    // the unique constraint on message_id does the dedupe
    const inserted = await tx.query(
      `INSERT INTO processed_messages (message_id) VALUES ($1)
       ON CONFLICT DO NOTHING RETURNING message_id`, [msg.id]);

    if (inserted.rowCount === 0) return;          // seen it: skip, just ack

    await tx.query(
      "UPDATE loyalty SET points = points + $1 WHERE order_id = $2",
      [msg.points, msg.orderId]);
  });                                             // both commit together
  // ack AFTER commit; a crash before this only causes a harmless redelivery
}

4Gains vs losses nothing is free

What we gain

  • Duplicates become harmless. Retries and redeliveries are safe.
  • Enables at-least-once everywhere, which is simple and reliable.
  • Safe client retries on payments and other writes.
  • Easier recovery. You can replay messages after an incident.
  • Clear, testable rule: send it twice, assert one effect.

What we lose

  • An extra table and write per message.
  • Must be in the same transaction, which is hard if the effect is an external call (e.g. sending email).
  • Id retention needs a policy and cleanup job.
  • Producers must send stable ids; a new id per retry defeats it.
  • Slightly more complex handlers everywhere.

6Common pitfalls the usual ways this goes wrong

  • Check, then act, outside a transaction

    “Have I seen m-42? No.” Then two consumer instances both process it at once. Fix → a unique constraint and the work in one transaction.

  • New id on every retry

    The client generates a fresh UUID each time it retries, so every retry looks new. Fix → create the key once per logical operation and reuse it on retries.

  • Side effects outside the transaction

    The email is sent, then the DB commit fails; the retry sends it again. Fix → record the intent in the DB (outbox) and send from there, or use the provider's idempotency key.

  • Forgetting ids too soon

    Ids expire after 1 hour, but the broker can redeliver after a 6-hour outage. Fix → keep ids longer than the maximum redelivery / retry window.

  • Relying on the broker's “exactly once”

    Kafka transactions cover Kafka-to-Kafka; your DB write is outside it. Fix → dedupe at your own system boundary anyway.

7When to use it (and when not)

Use it when…

  • Any message consumer on an at-least-once broker (that's nearly all).
  • Write APIs that clients may retry: payments, orders, bookings.
  • Saga steps and compensations.
  • Jobs you may want to replay after a bug fix.

Skip it when…

  • The operation is already naturally idempotent (set, upsert, delete by id).
  • Duplicates are truly harmless (refreshing a cache).
  • Read-only requests (GET) with no side effects.
  • You can't get a stable id from the producer. Fix that first.

8Self-check quiz

Is “UPDATE balance = balance + 10” idempotent? And “UPDATE status = 'PAID'”?

The first is not (twice adds 20). The second is (twice still PAID).

Why must the dedupe record and the work be in the same transaction?

Otherwise a crash between them either loses the record (work done twice) or loses the work (marked done but never happened).

A client retries POST /payments with a new UUID each time. What goes wrong?

The server sees every retry as a new request and may charge again. The key must stay the same across retries of one operation.

What does “exactly-once processing” usually mean in practice?

At-least-once delivery combined with idempotent (deduplicating) handling.

remember!!

Assume everything arrives twice. Give it an id, write the id with the work, and the second copy becomes a no-op.
