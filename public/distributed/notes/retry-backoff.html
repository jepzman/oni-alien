Retry with Backoff

TL;DR

Most network failures are short. So try the call again, but only for errors that can succeed later, with a timeout on every attempt, a growing, random wait between attempts (exponential backoff + jitter), and a hard limit before giving up.

  • Family: resilience
  • Lives in: the caller (client, SDK or proxy)
  • Also called: exponential backoff, jitter
  • Pairs with: timeouts, idempotency keys, circuit breaker

1The problem why do we even need this?

Networks are noisy. A packet gets dropped, a pod restarts during a deploy, a database pauses for a few hundred milliseconds. These transient failures fix themselves a moment later.

  • If the caller gives up on the first error, users see an error for something that would have worked half a second later.
  • If the caller retries instantly and forever, every client hits the struggling service at the same moment. That's a retry storm (or “thundering herd”), and it keeps the service down.
  • If a call has no timeout, it can hang forever, holding a thread, a connection and a user.
  • If the call wasn't safe to repeat, a retry can charge a card twice.

numbers from class: 3 layers (app → gateway → SDK) each retrying 3 times = 3 × 3 × 3 = 27 calls for one click.

2Real-life analogy calling the pizza place on a Friday

You call to order a pizza and the line is busy. You don't redial every second, because you'd never get through and you'd be annoying. You wait a minute, try again, then wait a bit longer.

  • You hang up after 30 seconds of ringing instead of holding forever. That's a timeout.
  • Each wait gets longer: 1 minute, 2, then 4. That's exponential backoff.
  • Your neighbours, who also want pizza, don't all redial at 7:01:00 exactly. That's jitter.
  • After three tries you order from the app instead. That's the retry limit and a fallback.
  • If the call dropped mid-order, you say “this is order 42 again” so they don't bake two. That's an idempotency key.

3How it solves it retry the right errors, the right way

A retry policy answers four questions: what to retry, how long each try may take, how long to wait between tries, and when to stop.

  1. Set two clocks

    A timeout for each attempt (say 2 s) and an overall deadline for the whole operation (say 8 s). The deadline is what the user is willing to wait.

  2. Classify the error

    Retry timeouts, connection resets, 429, 502, 503, 504. Never retry 400, 401, 403, 404 or 409: they'll fail the same way again.

  3. Wait with full jitter

    Sleep a random time between 0 and min(cap, base × 2attempt). If the server sends Retry-After, honour it.

  4. Make writes repeatable

    Send an Idempotency-Key header so a repeated POST returns the first result instead of doing the work again.

  5. Give up loudly

    After N attempts or at the deadline, return the error, count it in a metric, and alert when the give-up rate climbs.

Why jitter matters

No jitter

1,000 clients fail at 12:00:00.000. They all retry at 12:00:00.200, then all at 12:00:00.600… Every retry is a synchronised spike.

Full jitter

Each client picks a random wait inside the window. The same 1,000 retries spread over the whole window, so the service sees a gentle slope.

Vocabulary for the exam

Transient failure
A failure that goes away on its own after a short time.
Exponential backoff
Wait base × 2n before attempt n+1, up to a cap.
Jitter
Randomness added to the wait so clients don't retry in sync.
Retry budget
A cap on retries as a % of normal traffic (e.g. 10%).
Deadline propagation
Passing the remaining time to downstream calls.
Idempotency key
A unique ID that lets the server recognise a repeated request.
with-retry.tsfull jitter + per-try timeout
export async function withRetry<T>(
  fn: (signal: AbortSignal) => Promise<T>,
  { attempts = 4, baseMs = 200, capMs = 5_000, timeoutMs = 2_000 } = {},
): Promise<T> {
  for (let i = 0; ; i++) {
    try {
      return await fn(AbortSignal.timeout(timeoutMs));   // every try gets a timeout
    } catch (err) {
      if (i + 1 >= attempts || !isRetryable(err)) throw err;
      const windowMs = Math.min(capMs, baseMs * 2 ** i);
      await sleep(Math.random() * windowMs);           // full jitter
    }
  }
}

const isRetryable = (e: any) =>
  e.name === "TimeoutError" || [429, 502, 503, 504].includes(e.status);

// a POST is only safe to retry with an idempotency key
await withRetry((signal) =>
  fetch("/payments", {
    method: "POST", signal,
    headers: { "Idempotency-Key": order.id },
    body: JSON.stringify(order),
  }));

4Gains vs losses nothing is free

What we gain

  • Transient blips never reach the user. Most single failures succeed on the next try.
  • Bounded waiting. Timeouts and a deadline give every call a known worst case.
  • Gentle on a struggling service. Backoff and jitter spread the load out.
  • Cheap to add. A few lines or a library setting.
  • Safe writes when combined with idempotency keys.

What we lose

  • Higher latency on failure. Retries add waiting time to the slow path (p99).
  • Extra load. Every retry is another request; layered retries multiply.
  • Duplicates. Without idempotency, a retried write can run twice.
  • Hides problems. Calls that “succeed on the third try” look green on dashboards.
  • Tuning. Attempts, base, cap and timeout all need sensible values.

6Common pitfalls the usual ways this goes wrong

  • Retrying at every layer

    Client, gateway and SDK each retry 3 times: one click becomes 27 calls to the bottom service, exactly when it's weakest. Fix → retry in ONE layer, usually the one closest to the failing call.

  • Retrying without idempotency

    A payment times out after it succeeded. The retry charges the card again. Fix → idempotency keys on writes, or don't retry the write.

  • No jitter

    Every client backs off by exactly 200, 400, 800 ms, so the retries still arrive in synchronised waves. Fix → full jitter: a random wait inside the window.

  • Timeouts longer than the caller's patience

    The backend works for 30 s after the frontend gave up at 5 s. The work is wasted and queues grow. Fix → pass the remaining deadline down with each call.

  • Retrying errors that can't succeed

    Retrying a 400 Bad Request three times just triples the noise. Fix → only retry timeouts, connection errors, 429 and 5xx (except 501).

  • Silent retries

    Everything “works” on the third try while the dependency quietly falls over. Fix → a metric for every retry, not just for final failures.

7When to use it (and when not)

Use it when…

  • Calling anything over a network: HTTP, gRPC, databases, queues, cloud APIs.
  • Failures are usually short (deploys, failovers, network blips).
  • The operation is idempotent, or you can make it so with a key.
  • A user or job can afford a little extra latency for a better success rate.

Skip it when…

  • The error can never succeed on retry (validation, auth, not found).
  • The operation isn't safe to repeat and can't be made idempotent.
  • Another layer already retries the same call.
  • The user can't wait (a hard real-time budget). Fail fast instead.

8Self-check quiz

Why add jitter to exponential backoff?

Without randomness, clients that failed together retry together, creating synchronised spikes. Jitter spreads their retries across the window.

Which of these should you retry: 400, 404, 429, 503, timeout?

429, 503 and timeouts. 400 and 404 will fail the same way every time.

A gateway and the app both retry 3 times. How many calls can one request create?

Up to 3 × 3 = 9 calls to the service behind them (plus whatever the SDK does). Retry in one layer only.

How do you make retrying a POST safe?

Send an idempotency key so the server can recognise the repeat and return the original result instead of doing the work twice.

remember!!

Every call gets a timeout. Every retry gets a random wait. Every retry loop gets a limit, and every limit gets an alarm.
