Event Sourcing

TL;DR

Instead of storing only the current state and overwriting it, store every change as an immutable event in an append-only log (Deposited 100, Withdrew 30…). The current state is derived by replaying the events. You never lose history, and you can build new views of the past at any time.

  • Family: data management
  • Lives in: the service that owns the data
  • Popular with: finance, logistics, audit-heavy domains
  • Pairs with: CQRS, outbox, snapshots

1The problem why do we even need this?

Most systems store state with UPDATE: each change overwrites the previous value. That's simple, but it throws away the story.

  • Audit: “Who changed this order's address, and when?” Not recorded, or scattered across logs.
  • Debugging: “How did this account end up negative?” You only see the end result.
  • New questions: “How many people added an item and then removed it?” The removes were overwritten.
  • Integration: other services want to know what happened, not just the latest snapshot.

2Real-life analogy the bank passbook

An old bank passbook (or any accountant's ledger) doesn't have a single “balance” box that gets rubbed out and rewritten. It has lines: every deposit and withdrawal, in order. The balance is just those lines added up.

  • Accountants never erase. A mistake is fixed by adding a correcting entry.
  • You can answer “what was the balance on 1 March?” by adding up the lines until that date.
  • Adding up thousands of lines every time is slow, so the book prints a carried-forward balance at the top of each page (a snapshot).

3How it solves it append facts, derive state

Events are facts in the past tense. They're appended to a stream per entity (an “aggregate”), and everything else is calculated from them.

  1. Model events as past-tense facts

    OrderPlaced, ItemAdded, AddressChanged, each with the data needed to apply it and a timestamp.

  2. Handle a command

    Load the aggregate's events (or the latest snapshot + newer events), replay them to get current state, and check business rules.

  3. Append new events

    Write the resulting events to the stream with an expected version number, so two concurrent writers can't both succeed (optimistic concurrency).

  4. Project for reading

    Subscribers turn events into read models: a balance table, a search index, a statement. These can be rebuilt from scratch at any time.

  5. Snapshot and version

    Save a snapshot every N events to keep loading fast, and version event schemas so old events still replay after the code changes.

Vocabulary for the exam

Event
An immutable record of something that happened.
Event store
Append-only database of events, grouped into streams.
Aggregate / stream
One entity's events, e.g. all events for acc-1.
Projection
Code that turns events into a read model.
Snapshot
Saved state at event N, to avoid replaying from zero.
Upcasting
Converting old event versions to the current shape on read.
account.tsreplay, decide, append
type Event =
  | { type: "Deposited"; amount: number }
  | { type: "Withdrew"; amount: number };

const apply = (balance: number, e: Event) =>
  e.type === "Deposited" ? balance + e.amount : balance - e.amount;

export async function withdraw(accountId: string, amount: number) {
  const { events, version } = await store.load(`account-${accountId}`);
  const balance = events.reduce(apply, 0);            // replay
  if (amount > balance) throw new Error("Insufficient funds");   // decide
  await store.append(`account-${accountId}`,          // append, never update
    [{ type: "Withdrew", amount }],
    { expectedVersion: version });                     // optimistic concurrency
}

tools: EventStoreDB (Kurrent), Marten (Postgres, .NET), Axon (Java), Eventuous, or a plain append-only table with a (stream_id, version) unique key. Kafka is a log, but not a per-aggregate event store by itself.

4Gains vs losses nothing is free

What we gain

  • Complete audit trail for free: every change, who, when.
  • Time travel. Rebuild state at any point in the past.
  • New read models any time by replaying history.
  • Natural integration. Events are already there for other services.
  • Append-only writes are fast and conflict-friendly.

What we lose

  • Steep learning curve and an unusual way of thinking.
  • Event schema changes are forever. Old events must still replay.
  • Querying current state needs projections (usually CQRS).
  • Eventual consistency between the log and the read models.
  • Deleting data (e.g. GDPR) needs special techniques.

6Common pitfalls the usual ways this goes wrong

  • Using it everywhere

    Every CRUD table becomes event-sourced, and simple screens need projections and replays. Fix → use it only where history and audit really matter.

  • Events that are really commands or CRUD

    Events like OrderUpdated with the whole object say nothing about intent. Fix → small, past-tense, meaningful events (AddressChanged).

  • Changing old events

    Someone edits stored events to fix a bug, and replays now disagree with what happened. Fix → never edit; add correcting events and use upcasters.

  • Querying the event store directly

    Screens scan millions of events to show a list. Fix → build projections (CQRS) for every query.

  • No snapshots on long streams

    An account with 2 million events takes seconds to load. Fix → snapshot every N events, or close and reopen streams per period.

7When to use it (and when not)

Use it when…

  • Audit and history are core requirements (finance, healthcare, logistics).
  • The business thinks in events (“booked”, “shipped”, “refunded”).
  • You need to answer new questions about the past later.
  • You already need events for integration and want one source of truth.

Skip it when…

  • Simple CRUD with no history requirements.
  • The team is new to it and the deadline is tight.
  • Strong, immediate read-after-write consistency on every screen is a must.
  • You'd need to delete data often and can't encrypt-and-forget.

8Self-check quiz

How do you fix a wrong event in an event-sourced system?

You don't edit it. You append a new, correcting event, just as an accountant adds a correcting entry.

Why do event-sourced systems usually need CQRS?

Replaying events is great for one aggregate but bad for queries across many, so separate read models (projections) are built for querying.

What problem do snapshots solve?

Long streams are slow to replay; a snapshot stores the state at version N so you only replay events after it.

What does “expected version” protect against?

Two writers changing the same aggregate at once; the second append fails because the stream version moved, so it reloads and retries.

remember!!

State is just the sum of the story. Keep the story, and you can always rebuild the state, or any new view of it.
