Backpressure

TL;DR

When work arrives faster than it can be finished, an unlimited queue only hides the problem until memory runs out. Give every buffer a limit, and decide what happens when it's full: block the producer, drop or sample the extras, reject with 429/503 and a retry hint, or let consumers pull only what they can handle. The slowness then travels back to the source, where it can be seen and dealt with.

  • Family: resilience
  • Built into: TCP flow control, Kafka consumers, reactive streams
  • Opposite: unbounded queues and buffers
  • Pairs with: rate limiter, competing consumers, autoscaling

1The problem why do we even need this?

An API accepts 2,000 requests a second and hands each one to an in-memory queue. The worker behind it manages 1,200. The queue grows by 800 every second, latency grows with it, and after four minutes the process runs out of memory and everything queued is lost.

  • Unbounded buffers hide overload: no errors, just slower and slower answers.
  • By the time the queue is noticed, the requests at the front are too old to matter; the user gave up minutes ago.
  • The crash loses all queued work, not just the excess.

2Real-life analogy the restaurant host

A kitchen can cook 40 meals an hour. When the ticket rail is full, the host stops seating tables and tells new guests “about 20 minutes”. Guests wait outside for a while, but nobody sits at a table for two hours, and the kitchen never drowns.

3How it solves it a limit, and a rule for when it's full

Every place work waits (a queue, a channel, a thread pool, a socket buffer) gets a maximum size. When it's full, one of four things happens, chosen on purpose for that kind of work. The signal then flows back upstream, step by step, until it reaches something that can slow down, retry later or show a message.

  1. Find every buffer

    In-memory queues, worker pools, connection pools, message brokers, HTTP clients' request queues.

  2. Give each a limit

    Size it from throughput × acceptable wait: 1,200/s and 2 s of waiting is about 2,400 items, not “unlimited”.

  3. Choose the full-buffer rule

    Block (internal pipelines), drop or sample (metrics, telemetry), reject (public APIs), pull (consumers of a broker).

  4. Propagate it

    A rejected downstream call becomes a 503 upstream; a full consumer stops pulling. Don't swallow the signal halfway.

  5. Watch queue age

    Alert on how old the oldest waiting item is, and scale or shed load before it matters to users.

Vocabulary for the exam

Backpressure
A signal from a slow consumer that makes the producer slow down.
Bounded buffer
A queue with a maximum size.
Load shedding
Rejecting some work on purpose to keep the rest fast.
Pull-based
The consumer asks for more work when it has capacity.
Flow control
The protocol-level version (TCP windows, HTTP/2 streams).
Queue age
How long the oldest item has waited: the number that matters.
ingest.tsNode.js + Express
// a bounded queue in front of a slower worker: reject early instead of growing for ever
const MAX = 2_400;                        // ≈ 1,200 jobs/s × 2 s of acceptable waiting
const queue: Job[] = [];

app.post("/events", (req, res) => {
  if (queue.length >= MAX) {
    res.set("Retry-After", "2");          // tell the client when to come back
    return res.status(503).json({ error: "busy, try again shortly" });
  }
  queue.push(toJob(req.body));
  res.status(202).end();                  // accepted, not done
});

// the worker pulls at its own pace
async function work() {
  for (;;) {
    const job = queue.shift();
    if (!job) { await sleep(10); continue; }
    metrics.queueAgeMs.set(Date.now() - job.receivedAt);
    await handle(job);
  }
}

tools: Node.js streams (highWaterMark, pipeline), Go buffered channels, Reactive Streams / Project Reactor / RxJS, Kafka and SQS (pull consumers), Envoy and NGINX connection and request limits, Akka Streams.

4Gains vs losses nothing is free

What we gain

  • No out-of-memory crashes from runaway queues.
  • Fast answers for accepted work, instead of slow answers for all.
  • Overload is visible: rejections and queue age, not mystery latency.
  • Clients can react: retry later, show a message, slow down.

What we lose

  • Some work is refused or dropped during peaks.
  • Every producer must handle “full”: retries, messages, waiting.
  • Limits need tuning, and wrong ones reject too early or too late.
  • Blocking can spread a slowdown upstream if used everywhere.

6Common pitfalls the usual ways this goes wrong

  • A limit in one place only

    The API rejects, but an unbounded in-memory retry queue in the client brings the problem back. Fix → check every buffer along the path, clients included.

  • Swallowing the signal

    A middle service catches 503s from below and queues them internally. Fix → pass the pushback upstream as a 503 or 429.

  • Queue length, not age

    10,000 items looks scary, but they may be 50 ms old; 200 items can be 10 minutes old. Fix → alert on the age of the oldest item.

  • Blocking a request thread

    The producer blocks inside a web request, and the server runs out of threads. Fix → reject quickly at the edge; block only inside internal pipelines.

7When to use it (and when not)

Use it when…

  • Producers can outrun consumers, even briefly.
  • Ingest endpoints, event pipelines, streaming and batch imports.
  • Anywhere an in-memory queue sits between two steps.

Skip it when…

  • Work must never be refused and there is no peak (rare: use a durable queue and capacity instead).
  • Single synchronous calls with timeouts already bound the work.
  • The producer is a person typing; ordinary rate limits are enough.

8Self-check quiz

Why is an unbounded queue dangerous?

It hides overload as growing latency until memory runs out; then the crash loses every queued item.

Name the four things that can happen when a buffer is full.

Block the producer, drop or sample the extras, reject with an error, or let consumers pull only what they can handle.

Which HTTP status codes signal pushback?

429 Too Many Requests and 503 Service Unavailable, ideally with a Retry-After header.

Why alert on queue age rather than queue length?

Age is what users feel: how long work waits. Length says little without the processing rate.

what would you do?A metrics agent buffers data points in memory when the metrics backend is slow. During a backend outage, the agent on every host grows to 4 GB and the hosts start swapping. Which full-buffer rule fits metrics, and what do you set?

Drop or sample: losing some metric points during an outage is acceptable, slowing the hosts isn't. Cap the agent's buffer (by size or age), drop the oldest points when full, and count what was dropped so the gap is visible.

try it

Write a tiny producer that sends 2,000 jobs a second to a worker that handles 1,000, through an in-memory array. Watch memory grow. Then cap the queue at 2,000 items and return 503 when full, and graph accepted jobs, rejected jobs and the age of the oldest queued job.

remember!!

Every queue needs a limit and a “when full” rule. Push back; don't pile up.
