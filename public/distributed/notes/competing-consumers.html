Competing Consumers

TL;DR

Put work items on one queue and run several identical workers that pull from it. Each message is processed by exactly one worker. Add workers when the queue grows, remove them when it shrinks. The queue also absorbs spikes, so producers never wait for the work to finish.

  • Family: communication / messaging
  • Lives in: a message queue + a worker pool
  • Also called: work queue, queue-based load levelling
  • Pairs with: idempotent consumer, autoscaling, dead-letter queue

1The problem why do we even need this?

Some work is slow or bursty: resizing images, sending emails, generating PDFs, importing files. Doing it inside the request makes users wait, and doing it with one worker can't keep up.

  • At 9 a.m., 10,000 uploads arrive. One worker at 20 per second needs over 8 minutes.
  • If that worker crashes, nothing is processed at all.
  • Sizing for the peak wastes money the rest of the day; sizing for the average melts at the peak.

2Real-life analogy the supermarket checkout

A well-run supermarket has one queue feeding several tills. The next customer goes to whichever cashier is free. Nobody gets stuck behind a slow lane, and when the queue gets long the manager opens more tills.

  • Each customer is served by exactly one cashier.
  • If a cashier has to leave mid-scan, the customer goes back to the front of the queue for the next one.
  • A customer whose card fails five times is sent to customer service instead of blocking the line (the dead-letter queue).

3How it solves it pull, lock, process, acknowledge

The queue hands each message to one consumer and hides it from the others while it's being worked on. Only an acknowledgement removes it for good.

  1. Producers enqueue and return

    The web request just adds ResizeImage {id: 42} to the queue and responds “processing”.

  2. Workers pull

    Each worker takes a message (or a small batch). The broker locks it for a visibility timeout, e.g. 60 s.

  3. Process, then ack

    Do the work, then acknowledge. If the worker crashes or the timeout passes, the message reappears for another worker.

  4. Handle poison messages

    After N failed attempts, move the message to a dead-letter queue and alert, so it doesn't block or loop forever.

  5. Scale on the backlog

    Autoscale workers on queue depth or age of the oldest message (KEDA, SQS + ASG). Make handlers idempotent: redelivery happens.

resize-worker.tsrun N copies of this
// producer (web request): enqueue and return immediately
await queue.send("image-resize", { imageId: "img-42" });
res.status(202).json({ status: "processing" });

// worker: run as many copies as you need
for await (const msg of queue.receive("image-resize", { visibilityTimeout: 60 })) {
  try {
    await resize(msg.body.imageId);          // idempotent: same output if repeated
    await msg.ack();                         // only now is it removed
  } catch (err) {
    if (msg.attempts >= 5) await msg.deadLetter(String(err));
    else await msg.nack({ delaySeconds: 2 ** msg.attempts });   // retry later
  }
}

queues: AWS SQS, RabbitMQ, Azure Service Bus queues, Google Cloud Tasks, Kafka consumer groups (one partition per consumer), Celery / Sidekiq / BullMQ job queues; autoscale with KEDA.

4Gains vs losses nothing is free

What we gain

  • Throughput scales by adding workers.
  • Spikes are absorbed by the queue (load levelling).
  • Workers fail independently; messages move to a healthy one.
  • Producers respond fast; slow work happens in the background.
  • Cost-efficient: scale workers with the backlog, even to zero.

What we lose

  • No ordering guarantee across workers.
  • Duplicates when a worker crashes after doing the work.
  • Work is asynchronous; users need status updates.
  • Poison messages and DLQs need monitoring and tooling.
  • Shared downstream limits: 50 workers can overload one database.

6Common pitfalls the usual ways this goes wrong

  • Handlers that aren't idempotent

    A worker resizes and uploads, then crashes before ack; another worker does it again and charges the CDN twice. Fix → idempotent handlers keyed by message id.

  • Visibility timeout shorter than the work

    Jobs take 90 s, the lock lasts 60 s, so a second worker starts the same job. Fix → timeout above the p99 job time, or extend the lock while working.

  • No dead-letter queue

    One malformed message fails forever and keeps being retried, wasting workers. Fix → max attempts → DLQ, plus an alert and a replay tool.

  • Assuming order

    “Account created” and “account updated” are processed by different workers in the wrong order. Fix → partition by key (FIFO groups / Kafka keys) when order matters.

  • Scaling workers past the bottleneck

    100 workers all hit one database with 50 connections. Fix → cap workers to what downstream can take; use bulkheads.

7When to use it (and when not)

Use it when…

  • Work is slow, bursty or can happen in the background.
  • Throughput must scale with demand.
  • Each job is independent of the others.
  • Users can accept “we're processing it”.

Skip it when…

  • The caller needs the result in the same request.
  • Strict global ordering is required.
  • Volume is tiny and steady.
  • Every consumer should see every message (that's pub/sub).

8Self-check quiz

Pub/sub vs competing consumers: who gets a message?

In pub/sub every subscription gets a copy; with competing consumers exactly one worker in the pool gets each message.

A worker crashes halfway through a job. What happens to the message?

It was never acknowledged, so after the visibility timeout it becomes visible again and another worker picks it up.

What is a dead-letter queue for?

Messages that keep failing are moved there after N attempts, so they stop blocking or wasting workers and can be inspected and replayed.

What metric should drive autoscaling?

Queue depth or the age of the oldest message, not CPU alone.

remember!!

One queue, many hands. Ack only when done, expect redelivery, and send the troublemakers to the dead-letter queue.
