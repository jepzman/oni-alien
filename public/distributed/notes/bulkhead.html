Bulkhead

TL;DR

Split a service's resources (threads, connections, memory, even whole instances) into separate pools per dependency or per kind of work. When one dependency gets slow and fills its own pool, the others keep their pools and keep working.

  • Family: resilience / isolation
  • Lives in: the caller, or the deployment layout
  • Named after: ship hull compartments
  • Pairs with: timeouts, circuit breaker, load shedding

1The problem why do we even need this?

Most services share one pool of something: one thread pool, one HTTP connection pool, one database connection pool. That's efficient, until one dependency gets slow.

  1. The Reviews service starts taking 20 s per call.
  2. Requests that need reviews grab threads from the shared pool and sit there waiting.
  3. Within seconds every thread is waiting on Reviews.
  4. A request for the cart or checkout arrives. Those dependencies are healthy, but there's no thread left to run them.
  5. The whole shop is down because the least important feature got slow.

Key insight: shared resources couple failures. Anything that shares a pool can be starved by its noisiest neighbour.

2Real-life analogy the watertight walls in a ship

Ships aren't one big open hull. They're divided into watertight compartments by walls called bulkheads. If the hull is breached, water floods one compartment and the walls stop it there. The ship stays afloat.

  • A ship with no walls sinks from a single hole. A ship with walls survives with one compartment flooded.
  • The walls cost something: less open space and more structure. You accept that for survival.
  • You decide where the walls go based on what must keep working (the engine room gets its own).

another everyday one: a supermarket with a separate “10 items or fewer” lane. A trolley full of shopping can't block the quick shoppers.

3How it solves it separate pools, sized on purpose

Give each dependency, or each class of work, its own limited pool. When a pool is full, new work for it is rejected immediately (or queued briefly) instead of stealing from the others.

  1. Find what you share

    List the pools a service uses: worker threads, HTTP client connections, DB connections, queues, memory, CPU.

  2. Split by dependency or by priority

    One pool per downstream service, or separate pools for “checkout” vs “browse” vs “admin reports”.

  3. Size each pool

    Use Little's law: concurrent calls ≈ requests/s × latency (s). 50 req/s × 0.2 s = 10 in flight, so a pool of ~15 leaves headroom.

  4. Decide what happens when it's full

    Reject at once with a clear error or a fallback. A short bounded queue is fine; an unbounded one just moves the problem.

  5. Watch the pools

    Graph pool usage and rejections per pool. A pool that's always full is either undersized or protecting you from a real problem.

Bulkheads at different sizes

Inside one process

Separate thread pools or semaphores per dependency (e.g. max 20 concurrent calls to Reviews).

Connection pools

Separate HTTP / DB connection pools so a slow query can't take every connection.

Separate deployments

Run the admin/reporting API on different instances from the customer API.

Cells / per-tenant

Split customers into “cells”, each a full copy of the stack, so one tenant's spike hits only its cell.

Noisy neighbour

Cell-based architecture
Whole copies of the stack, each serving a subset of users.
bulkhead.tssemaphore per dependency
class Bulkhead {
  private inFlight = 0;
  constructor(private name: string, private max: number) {}

  async run<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (this.inFlight >= this.max) {        // pool full: don't wait, don't steal
      metrics.inc(`bulkhead.rejected.${this.name}`);
      return fallback();
    }
    this.inFlight++;
    try {
      return await fn();                    // fn still needs its own timeout!
    } finally {
      this.inFlight--;
    }
  }
}

// one pool per dependency, sized from traffic × latency
const reviews  = new Bulkhead("reviews", 20);
const checkout = new Bulkhead("checkout", 40);   // critical path gets more

const stars = await reviews.run(() => reviewsApi.get(id, { timeoutMs: 800 }), () => []);

in practice: Resilience4j Bulkhead / ThreadPoolBulkhead (Java), Polly Bulkhead (.NET), separate connection pools per client, Kubernetes resource limits, Envoy max-connections / max-pending-requests per cluster.

4Gains vs losses nothing is free

What we gain

  • Failures stay contained. One slow dependency can't starve the rest.
  • Critical paths are protected. Checkout keeps its capacity even when browsing is overloaded.
  • Fast, honest rejections instead of everything slowly timing out.
  • Clear signals. A full pool points straight at the guilty dependency.
  • Fairness. One tenant or feature can't hog everything.

What we lose

  • Less efficient use of resources. Idle threads in one pool can't help a busy one.
  • Sizing is hard. Too small rejects good traffic; too big doesn't isolate.
  • More config and more metrics to look after.
  • More rejected requests under load, which need fallbacks.
  • Cost when the bulkheads are whole deployments or cells.

6Common pitfalls the usual ways this goes wrong

  • No timeouts inside the pool

    The pool is isolated, but each call waits 60 s, so it fills up with stuck calls and rejects everything. Fix → always pair bulkheads with tight timeouts.

  • Unbounded queues in front of the pool

    Requests pile up in a queue forever, using memory and blowing response times. Fix → a small queue (or none) and fast rejection.

  • Pools sized by guesswork

    A pool of 5 for a dependency that normally needs 30 in flight rejects healthy traffic all day. Fix → size from Little's law and real traffic, then load-test.

  • Isolating the wrong thing

    Separate thread pools, but every pool shares one DB connection pool, which is the real bottleneck. Fix → find the real shared resource and split that.

  • Too many tiny pools

    Twenty pools of 3 threads waste memory and make tuning impossible. Fix → group dependencies by criticality, not one pool each by reflex.

7When to use it (and when not)

Use it when…

  • One service calls several dependencies with very different reliability.
  • Some features are critical (checkout, login) and others are nice-to-have.
  • You host many tenants and one can overload the others.
  • You've seen one slow dependency take the whole service down.

Skip it when…

  • The service has one dependency and nothing to protect from it.
  • Resources are so tight that splitting them leaves every pool too small.
  • Work is async through queues, where separate queues/consumers already isolate it.
  • You haven't added timeouts yet. Do that first.

8Self-check quiz

Where does the name come from?

From ships: watertight walls (bulkheads) split the hull so one breach floods only one compartment.

A pool for Reviews is full. What should happen to a new Reviews call?

Reject it at once (or after a very short bounded wait) and use a fallback, such as showing the page without reviews.

50 requests/s, each call takes 0.3 s. Roughly how many concurrent calls does the pool need?

About 50 × 0.3 = 15 in flight (Little's law), so size it a bit above that, e.g. 20.

What's the main cost of bulkheads?

Less efficient resource use: capacity reserved for one pool can't be borrowed by another, plus sizing and config effort.

remember!!

Don't let the least important dependency use up the resources the most important one needs. Walls first, then the ship survives a leak.
