Transactional Outbox

TL;DR

When a service must update its database and publish an event, don't do two separate writes. Write the change and the event (into an outbox table) in one local transaction. A separate relay reads the outbox and publishes the events to the broker, retrying until each one is sent.

  • Family: data consistency / messaging
  • Lives in: the service + its own database
  • Solves: the dual-write problem
  • Pairs with: saga, idempotent consumer, CDC

1The problem why do we even need this?

In event-driven systems a service often has to do two things together: save a change and tell others about it. Those are writes to two different systems (database + message broker), and there's no transaction that covers both.

  • DB first, then publish: crash in between and the order exists but nobody hears about it. Shipping never ships.
  • Publish first, then DB: crash in between and everyone hears about an order that was never saved.
  • Wrapping the publish in a DB transaction doesn't help: the broker isn't part of it, and the publish can't be rolled back.

This is the dual-write problem, and it's one of the most common sources of “ghost” and “missing” data in microservices.

2Real-life analogy the office out-tray

In an old-style office you don't walk every letter to the post office yourself. You write it, and in the same moment you drop it in your own out-tray. A mail clerk comes round on a schedule, collects everything in the tray, posts it, and ticks it off in a log.

  • Writing the letter and putting it in the tray is one action at your own desk. It can't half-happen.
  • If the clerk is off sick, the letters wait safely and go out tomorrow. Nothing is lost.
  • If the clerk posts a letter but forgets to tick it off, it might be posted twice. The receiver should notice a duplicate.

3How it solves it one transaction, then a relay

The trick is to turn two writes into one local write plus a reliable background job.

  1. Add an outbox table

    Columns like id, aggregate_id, type, payload, created_at, sent_at. It lives in the same database as the business data.

  2. Write both in one transaction

    BEGIN; insert the order; insert an OrderPlaced row into the outbox; COMMIT. Both happen or neither does.

  3. Relay the rows

    A poller selects unsent rows in order (or a CDC tool like Debezium tails the DB log) and publishes each one to the broker.

  4. Mark as sent (or delete)

    After the broker confirms, set sent_at. If the relay crashes first, it publishes again on restart: delivery is at least once.

  5. Make consumers idempotent

    Each event carries its outbox id; consumers skip ids they've already processed (see note 07). Clean up old outbox rows regularly.

Vocabulary for the exam

Dual write
Writing to two systems without a shared transaction.
Outbox table
A table of events waiting to be published, in the service's DB.
Message relay
The process that moves outbox rows to the broker.
Change data capture (CDC)
Reading the DB's transaction log to stream changes.
At-least-once delivery
Every message arrives, maybe more than once.
Inbox table
The consumer-side twin: records processed message ids.
place-order.sql + relay.tsPostgres, polling relay
-- ① the service: both rows in ONE transaction
BEGIN;
INSERT INTO orders (id, customer_id, total) VALUES ('o-42', 'c-7', 49.00);
INSERT INTO outbox (id, type, aggregate_id, payload)
VALUES (gen_random_uuid(), 'OrderPlaced', 'o-42', '{"total":49.00}');
COMMIT;

// ② the relay: runs every second, safe with several copies running
const rows = await db.query(`
  SELECT * FROM outbox WHERE sent_at IS NULL
  ORDER BY created_at LIMIT 100
  FOR UPDATE SKIP LOCKED`);              // two relays never grab the same row
for (const row of rows) {
  await broker.publish(row.type, { id: row.id, ...row.payload });
  await db.query("UPDATE outbox SET sent_at = now() WHERE id = $1", [row.id]);
}

tools: Debezium (CDC from Postgres / MySQL logs to Kafka), MassTransit and NServiceBus outbox (.NET), Spring Modulith / Eventuate Tram (Java), AWS DynamoDB Streams.

4Gains vs losses nothing is free

What we gain

  • No lost or ghost events. The change and the event commit together.
  • Works with any broker; no distributed transactions needed.
  • Survives outages. If the broker is down, events wait in the outbox.
  • Keeps event order per aggregate when the relay reads in order.
  • An audit trail of what was published and when.

What we lose

  • At-least-once, not exactly-once. Consumers must handle duplicates.
  • A little delay between commit and publish (polling interval).
  • Another moving part: the relay or CDC pipeline to run and monitor.
  • Extra DB load and a table that needs cleaning up.
  • Ordering across instances needs care if several relays run.

6Common pitfalls the usual ways this goes wrong

  • Publishing inside the transaction anyway

    Code calls broker.publish() before COMMIT “to be safe”, bringing the dual write back. Fix → only the relay publishes; the service only writes rows.

  • Consumers that can't handle duplicates

    The relay crashes after publishing but before marking the row, so the event goes out twice and an email is sent twice. Fix → idempotent consumers keyed by the event id.

  • Several relays stepping on each other

    Two relay instances read the same rows and publish everything twice, out of order. Fix → FOR UPDATE SKIP LOCKED, partitioning, or a single active relay.

  • Never cleaning the outbox

    The table grows to 500 million rows and the polling query slows the whole DB. Fix → delete or archive sent rows; index sent_at IS NULL.

  • Huge payloads in the outbox

    Whole documents are copied into every event, bloating the DB and the broker. Fix → send ids plus the fields consumers actually need.

7When to use it (and when not)

Use it when…

  • A service changes its own data and must notify others reliably.
  • You use sagas or event-driven integration between services.
  • The broker doesn't share a transaction with your database (almost always).
  • Losing or inventing an event would cost money or trust.

Skip it when…

  • Nobody else needs to know about the change.
  • The database and queue really are the same system with one transaction.
  • A short delay before others hear about the change is unacceptable.
  • A lost notification is harmless (e.g. a best-effort cache refresh).

8Self-check quiz

What is the dual-write problem?

Writing to two systems (e.g. a database and a broker) without one transaction covering both, so a crash in between leaves them inconsistent.

Why does the outbox give at-least-once delivery, not exactly-once?

The relay can publish a message and crash before marking it sent; on restart it publishes it again.

Polling relay or CDC: what's the difference?

A poller queries the outbox table on a schedule; CDC reads the database's transaction log and streams new rows, with lower latency and no polling load.

Where must the outbox table live?

In the same database as the business data, so both inserts are in one local transaction.

remember!!

Never write to two places at once. Write once, locally, and let a relay carry the news, and expect the news to arrive twice.
