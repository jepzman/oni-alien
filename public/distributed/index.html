Distributed Design Patterns

My class notes on distributed design patterns, written up properly. 18 patterns in five collections. Each note covers the problem a pattern solves, a real-life analogy with doodles, how it works, what you gain and lose, how it scores on nine architecture characteristics, and the mistakes people make with it.

Resilience keep one failure from becoming everyone's failure

  1. 01Circuit BreakerStop calling a dependency that keeps failing; fail fast with a fallback, then test carefully.p. 01
  2. 02Retry with BackoffTry again after short failures, with timeouts, growing random waits and a limit.p. 02
  3. 03BulkheadGive each dependency its own pool of resources so one leak can't sink the ship.p. 03
  4. 04Rate LimiterCap how many requests each client can make, so nobody can flood the service.p. 04

Data consistency keep data correct across services and databases

  1. 05SagaA transaction across services as local steps, with compensating “undo” steps when one fails.p. 05
  2. 06Transactional OutboxSave the change and the event in one transaction, then publish the event reliably.p. 06
  3. 07Idempotent ConsumerHandle the same message twice without doing the work twice.p. 07
  4. 08Event SourcingStore every change as an event and rebuild the current state from the log.p. 08
  5. 09CQRSUse one model to change data and separate, fast models to read it.p. 09

Communication how services find and talk to each other

  1. 10API GatewayOne front door for clients that routes, authenticates and shapes requests.p. 10
  2. 11Publish–SubscribeAnnounce events once; anyone interested subscribes, nobody calls each other.p. 11
  3. 12Competing ConsumersMany workers pull from one queue so load is shared and spikes are smoothed.p. 12
  4. 13Sidecar & Service MeshMove networking chores into a helper process that runs next to every service.p. 13
  5. 14Service DiscoveryLook up where a service is running right now instead of hard-coding addresses.p. 14

Scaling data store and read more data, faster

  1. 15ShardingSplit data across many databases by a key, so each holds only a slice.p. 15
  2. 16Leader–Follower ReplicationCopy data to followers for reads and failover; one leader takes the writes.p. 16
  3. 17Cache-AsideCheck a fast cache first; on a miss, load from the database and keep a copy.p. 17

Coordination agree on who does what

  1. 18Leader ElectionPick exactly one node to do a job, and safely pick a new one when it dies.p. 18

★The nine ratings architecture characteristics

Every note scores the pattern from 1 (poor) to 5 (great) on the same nine things, comparing an app without the pattern to the same app with it.

Simplicity
Fewer moving parts, fewer surprises.
Low cost
Infrastructure, tooling and people. High = cheap.
Deployability
Small, independent, safe releases.
Testability
Isolated parts with clear contracts.
Scalability
Handles more users and data by adding machines.
Elasticity
Scales up and back down quickly for spikes.
Fault tolerance
One failure stays contained.
Performance
How fast a typical request is.
Evolvability
How easily the system can change shape.

first law

Everything in architecture is a trade-off. If you think you've found one that isn't, you haven't found the cost yet.
