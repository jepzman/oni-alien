Flaky Test Quarantine

TL;DR

A flaky test passes and fails on the same code. Left alone, flakes teach everyone to press “re-run” and ignore red. Detect them automatically (fail then pass on retry), quarantine them into a non-blocking job so the main suite stays trusted, give each an owner and a deadline, and fix the root cause: shared state, timing, order or the outside world.

  • Family: test reliability
  • Usual causes: async timing, shared state, order, time, network
  • Tools: retries with reporting, flaky dashboards
  • Pairs with: controlled time & randomness, throwaway containers

1The problem why do we even need this?

One flaky test costs a re-run. A hundred flaky tests cost the team's trust in red builds, and then real failures get merged.

  • “Just re-run it” becomes the team's reflex.
  • Merges wait for green by luck; CI time doubles.
  • A genuine regression is dismissed as “probably flaky”.

2Real-life analogy the smoke alarm that beeps at random

If one smoke alarm beeps for no reason, people start pulling batteries, and soon nobody reacts to any alarm. The right move: take that alarm to the workbench, keep the others working, repair it, test it and put it back.

  • Pulling batteries is “just re-run it”.
  • The workbench is quarantine.
  • Putting it back is returning the test to the blocking suite once fixed.

3How it solves it detect, isolate, own, fix

Quarantine is a hospital, not a graveyard: tests go in with an owner and come back out fixed, or get deleted on purpose.

  1. Detect automatically

    Retry failed tests once; if a retry passes on the same commit, record it as flaky (don't hide it).

  2. Quarantine

    Tag it (@flaky) and run it in a separate, non-blocking job that still reports.

  3. Assign an owner and deadline

    A ticket per flaky test; a cap on how many can be quarantined.

  4. Find the cause

    Run it 100× locally, in random order, in parallel; check timing, shared data, test order, real clock, network.

  5. Fix and return

    Fix the cause (not with a sleep), then move it back. Delete tests nobody will fix.

Vocabulary for the exam

Flaky test
Passes and fails on the same code.
Quarantine
Running a test without letting it block merges.
Retry-on-failure
Re-running a failed test to detect flakiness.
Order dependence
A test that only passes after (or before) another.
Race condition
Result depends on which async step finishes first.
Auto-waiting
Assertions that retry until a condition holds or time runs out.

4Gains vs losses nothing is free

What we gain

  • A trusted main suite: red means broken.
  • No blind re-runs; faster merges.
  • Visible flakiness with owners and trends.
  • Root causes fixed, not hidden.

What we lose

  • Quarantined tests don't protect you while quarantined.
  • Process overhead: tickets, owners, dashboards.
  • Retries can hide flakiness if not reported.
  • Risk of a quarantine graveyard.

6Common pitfalls the usual ways this goes wrong

  • Retries without reporting

    Retries quietly turn flaky tests green forever. Fix → report every pass-on-retry as flaky.

  • A quarantine graveyard

    200 quarantined tests, none being fixed. Fix → owner, deadline and a cap; delete tests nobody will fix.

  • Fixing with sleep

    waitForTimeout(5000) makes it slower and still racy. Fix → wait for a condition (auto-waiting assertions).

  • Blaming the test runner

    “CI is just slow.” Fix → reproduce: run 100×, shuffle order, run in parallel.

7When to use it (and when not)

Use it when…

  • Any suite with UI, async or integration tests.
  • Teams where “re-run” has become a habit.
  • Large monorepos with shared CI.

Skip it when…

  • Tiny suites where you can fix a flake on the spot.
  • As an excuse not to fix: quarantine is temporary.

8Self-check quiz

What makes a test flaky?

It passes and fails on the same code, because of timing, shared state, order, time or external systems.

Why are flaky tests worse than no tests?

They teach people to ignore red builds, so real failures get dismissed and merged.

What does quarantine mean?

The test still runs and reports, but in a non-blocking job, with an owner and deadline to fix it.

What's the right fix for a test that sleeps 2 seconds?

Wait for the actual condition with an auto-waiting assertion or polling, not a fixed delay.
