Arrange–Act–Assert

TL;DR

Write every test as three visible blocks: Arrange the world, Act with one call, Assert the outcome. Name the test after the behaviour (“applies a 20% coupon”), not the method. One behaviour per test means a failure tells you exactly what broke.

  • Family: test structure
  • a.k.a.: Given–When–Then (BDD)
  • Origin: Bill Wake, 2001
  • Pairs with: test data builders, test doubles

1The problem why do we even need this?

Tests grow by accretion. Someone adds “one more check” to an existing test, then another action, then another check. Soon you have test2(): sixty lines that test six things, and nobody dares touch it.

  • When it fails, you have to debug the test before the code.
  • An early assertion fails and hides five other problems.
  • The test name says nothing about the behaviour it protects.

2Real-life analogy the lab write-up

A school science report always has the same headings: Method (how you set up), Experiment (the one thing you changed), Result (what you saw). Any teacher can read any report in seconds, because the shape never changes.

  • Method is Arrange; Experiment is Act; Result is Assert.
  • Change one variable per experiment: one Act per test.

3How it solves it three blocks, one behaviour

The blank lines between the blocks are the point: a reader sees the setup, the trigger and the expectation without reading every line.

  1. Name the behaviour

    it("applies a 20% coupon to the total"), not it("applyCoupon works").

  2. Arrange only what matters

    Hide the boring defaults in builders or helpers (note 03).

  3. Act once

    One call. If you need two, you probably have two tests.

  4. Assert the outcome

    Check results and visible effects, not private internals.

  5. Separate the blocks

    Blank lines or // arrange / act / assert comments.

Vocabulary for the exam

Arrange
Set up inputs, objects and doubles.
Act
Run the single behaviour under test.
Assert
Check the outcome.
Given–When–Then
The same shape in BDD language.
Assertion roulette
Many unlabelled asserts; you can't tell which failed.
Behaviour name
Describes what should happen, not which method runs.
cart.test.tsVitest
describe("Cart", () => {
  it("applies a 20% coupon to the total", () => {
    // arrange
    const cart = aCart().with(aProduct().priced(20)).build();

    // act
    cart.applyCoupon("SAVE20");

    // assert
    expect(cart.total).toBe(16);
  });

  it("rejects an expired coupon", () => {
    const cart = aCart().build();

    const result = () => cart.applyCoupon("SUMMER2019");

    expect(result).toThrow(/expired/);
  });
});

tools: any test runner (Vitest, Jest, pytest, JUnit, xUnit). Cucumber and Gherkin use Given–When–Then explicitly. Linters like eslint-plugin-jest can flag tests with no assertions.

4Gains vs losses nothing is free

What we gain

  • Readable tests: setup, trigger and expectation at a glance.
  • Precise failures: one behaviour per test.
  • Tests as documentation: names describe the rules.
  • Easier reviews: reviewers check the shape quickly.

What we lose

  • More, smaller tests (a bit more setup repetition).
  • Shared setup temptation moves Arrange far away.
  • Awkward for long flows like e2e journeys.

6Common pitfalls the usual ways this goes wrong

  • Several Acts in one test

    Add item, apply coupon, check out, refund: four behaviours. Fix → split into one test per behaviour.

  • Arrange in a distant beforeEach

    The setup that matters lives 200 lines away. Fix → keep the relevant setup inside the test.

  • Asserting internals

    Checking private fields or call order instead of the result. Fix → assert outcomes the caller can observe.

  • Vague names

    it("works"), test2. Fix → name the behaviour and the condition.

7When to use it (and when not)

Use it when…

  • Every unit and integration test.
  • Reviewing tests: check for the three blocks.
  • Teaching testing to new teammates.

Skip it when…

  • Long end-to-end journeys (use clear steps instead).
  • Exploratory scripts and quick spikes.

8Self-check quiz

What goes in each of the three blocks?

Arrange sets up inputs and doubles, Act runs one behaviour, Assert checks the outcome.

Why only one Act per test?

So a failure points to exactly one behaviour.

What's a good test name?

One that states the behaviour and condition, like “rejects an expired coupon”.

What's the BDD version of AAA?

Given–When–Then.

remember!!
