Snapshot (Approval) Testing

TL;DR

For big outputs (rendered HTML, invoices, API responses, generated SQL), save an approved copy once, and have the test compare new output to it. Any difference fails with a diff; a human decides whether it's a bug or an intended change to approve. Keep snapshots small and readable, and review snapshot changes in the PR like code.

  • Family: test technique
  • a.k.a.: approval testing, golden files
  • Tools: Vitest/Jest snapshots, ApprovalTests, Playwright visual
  • Pairs with: characterization tests

1The problem why do we even need this?

Some outputs are large and detailed: an invoice, an email, a JSON report, a rendered component. Asserting every line by hand is tedious, and most of the output ends up unchecked.

  • Forty assertions for one invoice, and lines 41–120 never checked.
  • A small intended layout change means an hour of editing asserts.
  • Nobody notices a stray field leaking into an API response.

2Real-life analogy the conservator's photograph

A museum conservator photographs a painting when it's approved. Every month they take a new photo and compare. Any difference is circled: either damage to fix, or an intended restoration, whose photo becomes the new approved one.

  • The approved photo is the snapshot.
  • Circled differences are the diff.
  • Signing off a restoration is updating the snapshot, consciously.
Translating it to software
In real lifeIn your code
The approved photographThe stored snapshot / golden file
This month's photoThe output of the current code
Circled differencesThe diff in the failing test
DamageA regression: fix the code
Intended restorationApprove: update the snapshot (-u)

3How it solves it compare to the approved copy

Snapshots turn “is this output right?” into “is this change right?”, which is much easier for a human to judge, as long as the diff is small and readable.

  1. Render to a readable form

    Pretty-printed JSON, normalised HTML or plain text, not binary blobs.

  2. Scrub the noise

    Replace dates, ids and random values with placeholders so snapshots are stable.

  3. Keep snapshots small

    Snapshot the invoice body, not the whole page; inline snapshots for short output.

  4. Review diffs like code

    Snapshot file changes appear in the PR; reviewers read them.

  5. Update deliberately

    Run with -u only after reading the diff, never to “make it green”.

invoice.test.tsVitest
it("renders an invoice for a Dutch customer", () => {
  const invoice = anInvoice().for(aCustomer().inNetherlands()).withLines(3).build();

  const text = renderInvoiceText(invoice)
    .replace(/\d{4}-\d{2}-\d{2}/g, "<date>")          // scrub unstable values
    .replace(/INV-\d+/g, "INV-<n>");

  expect(text).toMatchSnapshot();                     // __snapshots__/invoice.test.ts.snap
});

it("formats a small amount", () => {
  expect(formatMoney(1234.5, "EUR", "nl-NL")).toMatchInlineSnapshot(`"€ 1.234,50"`);
});
// intended change? read the diff, then:  vitest -u

4Gains vs losses nothing is free

What we gain

  • Whole output checked with one line.
  • Easy updates for intended changes.
  • Readable diffs show exactly what changed.
  • Catches surprises like leaked fields.

What we lose

  • Snapshot fatigue: people approve without reading.
  • Doesn't say what's right, only what changed.
  • Huge snapshots are unreviewable.
  • Unstable values need scrubbing.

6Common pitfalls the usual ways this goes wrong

  • Blind updates

    Tests fail, someone runs -u, the bug is now approved. Fix → read every diff; review snapshot changes in PRs.

  • Giant snapshots

    A 2,000-line snapshot of a whole page. Fix → snapshot the part that matters; prefer inline for small output.

  • Unscrubbed timestamps and ids

    Snapshots change on every run. Fix → freeze time, seed ids, or scrub them.

  • Snapshots instead of rules

    The snapshot of a total is “wrong” and nobody knows it. Fix → assert key rules explicitly too.

7When to use it (and when not)

Use it when…

  • Rendered emails, invoices, reports and HTML.
  • API response shapes and generated code or SQL.
  • Pinning legacy behaviour (see characterization tests).

Skip it when…

  • Small values where a direct assertion is clearer.
  • Output that changes on every run and can't be scrubbed.
  • Core business rules (assert them explicitly).

8Self-check quiz

What does a failing snapshot test tell you?

That the output changed compared to the approved copy, not whether the new output is right.

Why scrub dates and ids?

So snapshots don't change on every run for reasons that don't matter.

What's snapshot fatigue?

Updating snapshots without reading the diffs, which approves bugs.

When is an inline snapshot better?

For short outputs, so the expected value is visible right in the test.
