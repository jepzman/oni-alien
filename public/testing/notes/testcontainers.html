Throwaway Containers

TL;DR

For integration tests, don't share a test database or swap in SQLite. Start the real dependency (the same Postgres, Redis or Kafka version as production) in a container for the test run, run the migrations, isolate each test (rollback or a fresh schema), and throw it away afterwards. Real behaviour, no collisions, identical everywhere.

  • Family: integration testing
  • Library: Testcontainers (Java, Go, .NET, Node, Python…)
  • Needs: Docker or a compatible runtime
  • Pairs with: test pyramid (middle layer), fakes

1The problem why do we even need this?

Database code needs a real database to test. A shared test server means runs trample each other; an in-memory substitute means you're not testing what production runs.

  • Two CI runs insert the same user and both fail.
  • The shared database is on an old schema; tests fail for no reason.
  • Queries using JSONB, upserts or row locks pass on SQLite and fail in production.

2Real-life analogy the hotel room

Every hotel guest gets a freshly made room, identical to the others, theirs alone, and it's cleaned when they leave. You never inherit the last guest's mess.

  • The room is a container started for your run.
  • Identical rooms are the same image version everywhere.
  • Cleaning up is removing the container, automatically.

3How it solves it start, migrate, isolate, discard

Containers start in a few seconds. Start one per test run (not per test) and isolate tests inside it, so you keep realism without paying start-up time a thousand times.

  1. Pin the production version

    postgres:16.4, not latest.

  2. Start once per run

    A global setup starts the container and exports its connection string.

  3. Migrate

    Run the same migrations production runs.

  4. Isolate each test

    Wrap each test in a transaction and roll back, or give each worker its own schema or database.

  5. Clean up automatically

    Testcontainers' reaper removes containers even if the run crashes.

  6. Keep it in the middle layer

    Use it for repositories and adapters, not every unit test.

import { PostgreSqlContainer } from "@testcontainers/postgresql";

export async function setup() {
  const pg = await new PostgreSqlContainer("postgres:16.4").start();   // ~3 s
  process.env.DATABASE_URL = pg.getConnectionUri();
  await runMigrations(process.env.DATABASE_URL);
  return () => pg.stop();                                              // teardown
}

// each test runs in a transaction that is always rolled back
beforeEach(async () => { tx = await db.begin(); });
afterEach(async () => { await tx.rollback(); });

it("upserts by email", async () => {
  const repo = new PostgresUserRepo(tx);

  await repo.upsert(aUser({ email: "ana@x.io", name: "Ana" }));
  await repo.upsert(aUser({ email: "ana@x.io", name: "Ana T." }));

  expect(await repo.countByEmail("ana@x.io")).toBe(1);
});

4Gains vs losses nothing is free

What we gain

  • Real behaviour: the same engine and version as production.
  • No collisions: every run gets its own database.
  • Identical everywhere: laptops and CI match.
  • Self-cleaning: nothing left behind.

What we lose

  • Slower than in-memory: seconds to start.
  • Needs Docker on laptops and CI.
  • More CI resources (memory, image pulls).
  • Still not production: no real data volume or network.

6Common pitfalls the usual ways this goes wrong

  • A container per test

    1,000 tests × 3 s start-up. Fix → one container per run; isolate inside it.

  • Using latest

    A new major version breaks tests overnight. Fix → pin the exact production version.

  • Tests depending on each other's data

    Test B passes only after test A inserted a row. Fix → roll back or reset per test; build data in each test.

  • Everything becomes an integration test

    The suite slows to 20 minutes. Fix → keep logic in fast unit tests; containers for adapters.

7When to use it (and when not)

Use it when…

  • Repositories, SQL queries and migrations.
  • Message consumers (Kafka, RabbitMQ) and caches (Redis).
  • Anything where an in-memory substitute behaves differently.

Skip it when…

  • Pure business logic (unit tests with fakes).
  • Managed cloud services with no faithful container image.
  • Environments where Docker is unavailable (use a CI service container instead).

8Self-check quiz

Why not test Postgres code against SQLite?

They differ in SQL features, types, locking and constraints, so passing tests don't prove production behaviour.

Why start one container per run rather than per test?

Start-up takes seconds; isolating tests inside one container keeps the suite fast.

How do you isolate tests inside one database?

Wrap each test in a transaction and roll back, or give each worker its own schema.

Why pin the image version?

So tests match production and don't break when a new version is released.

remember!!

Every run gets a fresh room, the same as production, cleaned on check-out.
