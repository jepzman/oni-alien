Test Doubles (Stubs, Spies, Mocks)

TL;DR

Replace slow, costly or unpredictable dependencies with test doubles, and pick the right kind: a stub returns canned answers for things you read, a spy or mock checks things you send (emails, payments), a fake is a simple working version. Double only at boundaries you own, and don't mock the thing you're testing.

  • Family: isolation
  • Names from: Gerard Meszaros, xUnit Test Patterns
  • Kinds: dummy, stub, spy, mock, fake
  • Pairs with: fakes, contract testing

1The problem why do we even need this?

Real code talks to payment providers, email services and third-party APIs. If tests call them for real, they're slow, costly, flaky and sometimes dangerous.

  • Every test run charges a card or sends an email.
  • A third-party outage turns your build red.
  • You can't easily test “the payment was declined” or “the API timed out”.

2Real-life analogy stand-ins on a film set

A film set uses different stand-ins for different jobs: a cardboard cut-out while lights are set up, a stunt double for the dangerous fall, a crash-test dummy with sensors to record the impact. Using the wrong one wastes time or misses what you needed to know.

  • Cut-out = dummy (fills a slot).
  • Stunt double playing the scene = stub/fake (gives answers).
  • Crash dummy with sensors = spy/mock (records what happened to it).

3How it solves it pick the double by its job

A good rule: stub queries, verify commands. If a dependency gives you data, stub it and assert on your result. If your code must cause an effect (send, charge, publish), check that the effect was requested.

  1. Find the boundary

    Payments, email, clock, HTTP clients: things that are slow, costly or random.

  2. Wrap third-party APIs

    Put an interface you own (PaymentGateway) in front of the SDK; double your interface, not theirs.

  3. Inject it

    Pass the dependency in (constructor or parameter) so tests can swap it.

  4. Stub queries

    prices.get returns 20; assert on your own result.

  5. Verify commands

    Check email.send was called with the right address, once.

  6. Back it with integration tests

    One real-integration test per adapter proves the wrapper actually works.

Vocabulary for the exam

Test double
Any stand-in for a real dependency in a test.
Stub
Returns predetermined answers.
Spy
Records how it was called.
Mock
Has expectations that must be met.
Seam
A place where you can swap behaviour without editing code.
Over-mocking
Doubling so much the test only checks the mocks.
signup.test.tsVitest
it("sends a welcome email after a successful signup", async () => {
  const payments = { charge: vi.fn().mockResolvedValue({ ok: true }) };   // stub
  const email = { send: vi.fn() };                                         // spy
  const signup = makeSignup({ payments, email });

  await signup({ email: "ana@example.com", plan: "pro" });

  expect(email.send).toHaveBeenCalledOnce();
  expect(email.send).toHaveBeenCalledWith(
    expect.objectContaining({ to: "ana@example.com", template: "welcome" }));
});

it("does not email when the card is declined", async () => {
  const payments = { charge: vi.fn().mockResolvedValue({ ok: false }) };
  const email = { send: vi.fn() };

  await expect(makeSignup({ payments, email })({ email: "a@b.c", plan: "pro" }))
    .rejects.toThrow(/declined/);
  expect(email.send).not.toHaveBeenCalled();
});

tools: Vitest vi.fn, Jest mocks, Sinon (spies/stubs), MSW (stub HTTP at the network layer), unittest.mock (Python), Mockito (Java), NSubstitute (.NET).

4Gains vs losses nothing is free

What we gain

  • Fast, free, offline tests.
  • Hard cases on demand: declines, timeouts, errors.
  • No side effects on real customers.
  • Precise failures in your own code.

What we lose

  • Doubles can lie: the real API behaves differently.
  • Over-mocking ties tests to implementation details.
  • Setup noise when many doubles are needed.
  • Needs integration tests to cover the real wiring.

6Common pitfalls the usual ways this goes wrong

  • Mocking the thing under test

    Half the class is mocked, so the test checks your mocks. Fix → double only collaborators at boundaries.

  • Mocking libraries you don't own

    A mocked SDK call passes; the real SDK needs a different argument. Fix → wrap it in your interface and integration-test the wrapper.

  • Verifying every call

    Tests assert exact call order of internal helpers and break on every refactor. Fix → verify only commands with real effects.

  • Mocks for everything

    Five mocks per test, 40 lines of setup. Fix → prefer a fake (note 06) or a real dependency in a container.

7When to use it (and when not)

Use it when…

  • Payments, email, SMS, third-party APIs.
  • Simulating failures that are hard to trigger for real.
  • Fast unit tests of logic around side effects.

Skip it when…

  • Your own database queries (use a real database in a container).
  • Pure functions with no dependencies.
  • When a simple fake would be clearer than many mocks.

8Self-check quiz

Stub or spy for a price lookup?

A stub: it's a query, so return a canned price and assert on your own result.

Stub or spy for sending an email?

A spy or mock: it's a command, so check the email was requested correctly.

Why wrap third-party SDKs before doubling them?

So you double an interface you own and can prove the wrapper against the real SDK in an integration test.

What's the danger of over-mocking?

Tests become coupled to implementation details and pass even when the real system is broken.

remember!!

Stub what you read, spy on what you send, and only double what you own.
