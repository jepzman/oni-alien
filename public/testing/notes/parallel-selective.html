Parallel & Selective Runs

TL;DR

Two levers for fast feedback: run tests in parallel (workers and CI shards, balanced by past timing) and run only the tests a change can affect (using the dependency graph). Pull requests get answers in minutes, and the full suite still runs on main and nightly as a safety net. Tests must be isolated for either lever to work.

  • Family: test speed
  • Levers: parallel workers, CI sharding, test impact analysis
  • Tools: Vitest/Playwright shards, Nx, Turborepo, Bazel
  • Needs: isolated, order-independent tests

1The problem why do we even need this?

Suites grow linearly with the code, and so does the wait. A 42-minute CI run changes how people work: they context-switch, batch huge PRs and stop running tests locally.

  • A typo fix in one package runs 6,000 unrelated tests.
  • One CI job uses one core while the machine has eight.
  • Slow suites get skipped: “I'll let CI tell me.”

2Real-life analogy the supermarket checkout

A supermarket with one open lane has a long queue. Open eight lanes and it moves eight times faster. And nobody scans items that aren't in their basket.

  • More lanes = parallel workers and shards.
  • Balancing queues = splitting by past timing.
  • Scanning only your basket = selecting affected tests.

3How it solves it select, then split

Selection shrinks the work; parallelism shares what's left. Both need tests that don't depend on order or shared state, so isolation comes first.

  1. Make tests isolated

    No shared mutable data, no order dependence; each worker gets its own database schema or container.

  2. Use all cores

    Parallel workers in the runner (Vitest threads, Playwright workers).

  3. Shard in CI

    --shard=1/4 across machines; balance by timing data.

  4. Select affected tests

    Use the dependency graph (Nx/Turborepo/Bazel affected) or the runner's --changed.

  5. Keep a full run

    On main, before release and nightly, to catch anything selection missed.

  6. Watch the numbers

    Track p50/p95 CI time and the slowest tests; fix the outliers.

Vocabulary for the exam

Worker
A process running a subset of tests in parallel.
Shard
One slice of the suite run on its own CI machine.
Timing-based split
Balancing shards using past test durations.
Test impact analysis
Choosing tests based on what a change touches.
Affected graph
Packages that depend, directly or not, on a change.
Remote cache
Reusing results of unchanged tasks across machines.
.github/workflows/test.ymlGitHub Actions + Nx + Vitest
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { shard: [1, 2, 3, 4] }            # 4 machines in parallel
    steps:
      - uses: actions/checkout@v5
        with: { fetch-depth: 0 }
      - run: npm ci
      # only projects affected by this PR, split across the 4 shards
      - run: npx nx affected -t test --base=origin/main --
             --shard=${{ matrix.shard }}/4
      # on main and nightly a separate job runs:  npx nx run-many -t test

tools: Vitest/Jest workers and --shard, Playwright --shard and fullyParallel, Nx and Turborepo affected + remote cache, Bazel, Gradle test distribution, Knapsack Pro and CircleCI timing-based splitting, Launchable for predictive test selection.

4Gains vs losses nothing is free

What we gain

  • Minutes, not an hour for PR feedback.
  • Uses the hardware you already pay for.
  • Smaller, more frequent PRs become practical.
  • Scales with the repo instead of slowing down.

What we lose

  • Needs isolated tests; hidden shared state surfaces as flakes.
  • Selection can miss indirect effects (config, data files).
  • More CI machines at once.
  • More moving parts: graphs, caches, timing data.

6Common pitfalls the usual ways this goes wrong

  • Parallelising non-isolated tests

    Shared rows and global state turn into random failures. Fix → isolate first: per-worker schemas, unique data.

  • Trusting selection blindly

    A config change affects everything, but no tests are selected. Fix → mark global inputs; always run the full suite on main.

  • Unbalanced shards

    Three shards finish in 2 minutes, one takes 20. Fix → split by timing data, not by file count.

  • Ignoring the slowest tests

    Five tests take half the time. Fix → track and fix the slow tail.

7When to use it (and when not)

Use it when…

  • Suites slower than about 10 minutes.
  • Monorepos with many packages.
  • Teams that want small, frequent PRs.

Skip it when…

  • Small suites that already finish in a minute or two.
  • Tests that can't be isolated yet (fix that first).

8Self-check quiz

What are the two main levers for faster CI?

Run tests in parallel (workers and shards) and run only the tests a change can affect.

Why must tests be isolated before parallelising?

Shared state and order dependence cause random failures when tests run at the same time or in different orders.

Why split shards by timing rather than file count?

Files have very different run times; timing data balances shards so they finish together.

Why still run the full suite on main?

Selection can miss indirect effects; the full run is the safety net.
