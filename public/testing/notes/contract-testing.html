Contract Testing

TL;DR

When a service and its clients are built by different teams, each side's tests can pass against its own idea of the API while production breaks. With consumer-driven contracts, each client records exactly what it needs (request and response shape) into a contract, and the provider replays every contract in its CI. Breaking changes fail the provider's build, before deploy, without a shared staging environment.

  • Family: integration between teams
  • Tools: Pact, Spring Cloud Contract, schema checks
  • Style: consumer-driven (CDC)
  • Pairs with: API gateway (Vol. 1), micro-frontends (Vol. 2)

1The problem why do we even need this?

Each team mocks the other side. The mocks are written once and never updated, so both suites stay green while the real services drift apart.

  • A field is renamed; every client breaks in production.
  • The only real check is a slow, shared staging environment that's always half broken.
  • Providers are afraid to change anything because they don't know who uses what.

2Real-life analogy plug and socket

The company that makes your kettle and the electrician who wired your kitchen never meet. Both build to the same written standard, and each checks their own side against it. So the plug fits, every time.

  • The standard is the contract.
  • Each side tests alone, against the contract, not against each other.
  • With consumer-driven contracts, the plug makers write down what they need, and the socket maker checks every one.

3How it solves it record on one side, replay on the other

A contract captures only what the consumer actually uses, so providers can freely change everything else and know immediately when they'd break someone.

  1. Write consumer tests

    Against a mock provider generated by the tool; the interactions are saved as a contract.

  2. Publish the contract

    To a broker (Pact Broker / PactFlow), tagged with the consumer's version and branch.

  3. Verify on the provider

    The provider's CI starts the real service and replays every consumer's contract.

  4. Use provider states

    “Given order 42 exists” sets up data for each interaction.

  5. Gate deploys

    can-i-deploy checks that the versions about to meet in production have verified contracts.

Vocabulary for the exam

Consumer
The side that calls an API.
Provider
The side that serves the API.
Contract

Broker
Server that stores contracts and verification results.
Provider state
Named setup data for an interaction.
Schema test
Checking responses against OpenAPI/JSON Schema only.
orders.pact.test.tsPact JS (consumer side)
const provider = new PactV3({ consumer: "mobile-app", provider: "orders-api" });

it("shows an order's price", async () => {
  provider
    .given("order 42 exists")
    .uponReceiving("a request for order 42")
    .withRequest({ method: "GET", path: "/orders/42" })
    .willRespondWith({
      status: 200,
      body: { id: like(42), status: like("paid"), price: decimal(19.99) },
    });

  await provider.executeTest(async (mock) => {
    const order = await ordersClient(mock.url).get(42);
    expect(order.price).toBe(19.99);
  });
});
// provider CI:  pact verify --provider orders-api   →  fails if "price" disappears

tools: Pact and PactFlow (many languages), Spring Cloud Contract, Specmatic, OpenAPI diff tools (oasdiff) for breaking-change checks, GraphQL schema checks (Apollo GraphOS, graphql-inspector).

4Gains vs losses nothing is free

What we gain

  • Catches breaking API changes before deploy.
  • No shared staging needed to test integration.
  • Providers know who uses what, so they can change safely.
  • Fast: runs in each team's normal CI.

What we lose

  • Tooling and a broker to set up and run.
  • Learning curve: provider states, matchers, versions.
  • Checks shape, not meaning: business behaviour still needs tests.
  • Needs buy-in from both teams.

6Common pitfalls the usual ways this goes wrong

  • Contracts that test business logic

    Every pricing rule is encoded in the contract. Fix → contracts check shape and key interactions; logic stays in provider tests.

  • Over-specified responses

    Exact values everywhere; any data change breaks it. Fix → use type matchers (like, decimal).

  • Skipping can-i-deploy

    Contracts are verified but deploys don't check them. Fix → gate every deploy on the broker.

  • Only the provider writes contracts

    The “contract” is whatever the provider says. Fix → let consumers record what they actually use.

7When to use it (and when not)

Use it when…

  • Services and clients owned by different teams.
  • Many consumers of one API (web, mobile, partners).
  • Replacing slow shared staging environments.

Skip it when…

  • A frontend and backend in one repo, deployed together.
  • Public APIs with unknown consumers (use schema diff + versioning).
  • One team owning both sides with good integration tests.

8Self-check quiz

Why can both teams' tests pass while production breaks?

Each tests against its own mock of the other side, and those mocks drift from reality.

Who writes the contract in consumer-driven contract testing?

The consumer, by recording the interactions it actually relies on.

What does the provider do with contracts?

Replays them against the real service in its CI and fails if any expectation is broken.

What does can-i-deploy answer?

Whether the version you're about to deploy has verified contracts with the versions of its partners in that environment.
