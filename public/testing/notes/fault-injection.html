Fault Injection Tests

TL;DR

Timeouts, retries, fallbacks and error messages are code too, but in most test suites they never run, because the fakes and containers always answer quickly and correctly. Fault injection tests put a switchable fault between your code and a dependency (latency, dropped connections, errors, garbage responses) and assert that the code behaves well: it times out, retries safely, shows a useful message and recovers.

  • Family: reliability
  • Faults: latency · connection reset · 5xx · timeouts · bad payloads
  • Tools: Toxiproxy, WireMock faults, test doubles that fail
  • Vol. 6 cousin: chaos engineering on running systems

1The problem why do we even need this?

In every test the payment provider answers in 50 ms. In production it once took 30 seconds; checkout had no timeout, every thread waited, and the whole shop stopped. The retry and fallback code written for exactly this had never run once.

  • Fakes and test containers are always healthy, so error paths go untested.
  • Timeout and retry settings are configured and never checked until an incident.
  • Error handling that's never run is often wrong: double charges, swallowed errors, blank screens.

2Real-life analogy the fire drill

A school doesn't wait for a fire to learn whether the exits work. It sets off the alarm on purpose, on a calm day, with someone timing it. Blocked exits and missing classes are found while nothing is burning.

3How it solves it a switchable fault between you and the dependency

Route calls to a dependency through something you control in the test: a fault proxy (Toxiproxy) in front of a real container, or a fake that can be told to fail. Each test switches one fault on, exercises the feature, asserts the behaviour, and switches it off. Test the recovery too: once the fault is gone, the feature must work again.

  1. List the dependencies

    Database, cache, payment provider, email, other services: everything the feature calls.

  2. List the faults that matter

    Slow (above your timeout), down (connection refused), flaky (some 503s), wrong (malformed or partial answers).

  3. Add a switch

    A fault proxy in front of the container, or a test double with failure modes.

  4. Assert the behaviour

    Timeout in the expected time, safe retries (no double charge), a clear message, metrics and logs written.

  5. Assert recovery

    Remove the fault; the next request succeeds, and the circuit breaker closes.

Vocabulary for the exam

Fault injection
Causing failures on purpose to test how code handles them.
Fault proxy
A proxy that can add latency, drop or corrupt traffic on command.
Toxic
Toxiproxy's name for a fault (latency, timeout, reset).
Error path
The code that runs only when something fails.
Graceful degradation
Doing less, but still working, when a dependency fails.
Recovery test
Checking the system works again once the fault is removed.
checkout.faults.test.tsVitest + Testcontainers + Toxiproxy
// the service talks to the payment fake through Toxiproxy (set up once per run)
test("checkout times out quickly when payments hang, and doesn't charge twice", async () => {
  await paymentsProxy.addToxic({ type: "latency", attributes: { latency: 5_000 } });

  const started = Date.now();
  const res = await api.post("/checkout", { cartId: "c-42", idempotencyKey: "k-1" });

  expect(res.status).toBe(503);
  expect(res.body.message).toMatch(/try again/i);
  expect(Date.now() - started).toBeLessThan(2_500);        // our 2 s timeout, not 5 s

  await paymentsProxy.removeAllToxics();                    // recovery
  const retry = await api.post("/checkout", { cartId: "c-42", idempotencyKey: "k-1" });
  expect(retry.status).toBe(200);
  expect(await paymentsFake.chargesFor("c-42")).toHaveLength(1);
});

tools: Toxiproxy (with Testcontainers modules), WireMock fault responses and delays, MockServer, Polly's simmy (.NET), Chaos Mesh / Litmus for cluster-level tests (see Vol. 6), tc netem for network faults.

4Gains vs losses nothing is free

What we gain

  • Error paths actually run in CI.
  • Timeouts and retries are checked, not assumed.
  • Fewer incident surprises: the first slow dependency isn't in production.
  • Safe refactors of resilience code.

What we lose

  • Slower tests: waiting for timeouts takes real time.
  • More setup: proxies, fakes with failure modes.
  • Many combinations: you can't test every fault everywhere.
  • Not production: real failures can be stranger.

6Common pitfalls the usual ways this goes wrong

  • Faults only in fakes

    A fake that throws an exception tests nothing about real timeouts and sockets. Fix → inject faults on the network path (a proxy) for the critical dependencies.

  • Tight timing assertions

    “Within 2,000 ms” fails on a slow CI machine. Fix → assert with margin (under 2.5 s), or use fake timers where possible.

  • Forgetting recovery

    The service handles the outage but never recovers when the dependency comes back. Fix → always remove the fault and assert the next request succeeds.

  • Every fault, everywhere

    Hundreds of slow tests nobody can maintain. Fix → cover the critical paths (payment, login, checkout) with the faults that matter.

7When to use it (and when not)

Use it when…

  • Code that calls payment, identity, storage or other critical services.
  • Timeouts, retries, circuit breakers and fallbacks you rely on.
  • Before and after changing resilience settings.

Skip it when…

  • Pure logic with no external calls.
  • Dependencies whose failure is already handled by a platform you trust and tested there.
  • Running systems in staging or production: that's chaos engineering (Vol. 6).

8Self-check quiz

Why do error paths often go untested?

Fakes and containers in tests always answer quickly and correctly, so timeout, retry and fallback code never runs.

Name four kinds of fault worth injecting.

Latency above the timeout, connection refused or reset, intermittent 5xx errors, and malformed or partial responses.

Why inject faults with a proxy rather than a fake that throws?

A proxy exercises the real network path: socket timeouts, connection pools and retries behave as in production.

Why test recovery?

Code can handle an outage but stay broken after it ends, for example a breaker that never closes.

what would you do?A service sets a 3-second timeout on its calls to the inventory service, with 2 retries. In an incident, requests took 12 seconds before failing. Your tests never showed this. What test do you add, and what did it probably reveal?

An integration test with a fault proxy adding 10 s of latency to inventory, asserting the request fails within about 3–4 s. It would show the timeout applies per attempt, so 3 attempts × 3 s plus backoff ≈ 12 s; fix it with an overall deadline or fewer retries.

try it

Pick one feature that calls another service in an integration test. Put Toxiproxy (or WireMock with a fixed delay) between them and add 10 seconds of latency. Check how long the feature takes to fail and what the user sees. Then add a connection reset, and finally remove the fault and check that the next request succeeds.

remember!!

Your error handling is code. If no test makes it run, it doesn't work.
