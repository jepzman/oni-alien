Mutation Testing

TL;DR

Coverage tells you which lines ran, not whether any test would notice a bug in them. Mutation testing plants small bugs (mutants) in your code, like > → >= or deleting a line, and runs the tests. If a test fails, the mutant is killed; if all pass, it survived and shows you exactly where tests are blind.

  • Family: test quality
  • Origin: Richard Lipton, 1971; DeMillo et al., 1978
  • Tools: Stryker, PIT, mutmut, cargo-mutants
  • Measures: mutation score

1The problem why do we even need this?

Coverage is easy to game, even by accident. A test that calls a function and asserts nothing still “covers” every line it runs.

  • 94% coverage, yet an off-by-one in the discount rule goes unnoticed.
  • Tests check that no exception was thrown, not that the answer is right.
  • Teams chase a coverage number instead of real confidence.

2Real-life analogy the fire drill

Having smoke detectors installed doesn't prove they work. A safety officer runs a drill: fake fires in each room, one at a time. Any detector that stays silent is a gap, even though it's on the ceiling.

  • Installed detectors are coverage.
  • Each fake fire is a mutant.
  • A silent detector is a surviving mutant.

3How it solves it plant bugs, see who notices

Each survivor is a concrete to-do: “if this > were >=, no test would notice”. Add the assertion or case that kills it.

  1. Run it on core code

    Start with business logic, not the whole repo: it's slow.

  2. Read the survivors

    Each one shows the exact change no test noticed.

  3. Kill them

    Add the missing assertion or boundary case (here: discount(100) must apply).

  4. Ignore equivalent mutants

    Some mutants behave identically to the original; mark and skip them.

  5. Run incrementally

    On changed files in PRs, the full run nightly; set a threshold, not 100%.

Vocabulary for the exam

Mutant
A copy of the code with one small change.
Mutation operator
A rule for making mutants (> → >=).
Killed
At least one test failed against the mutant.
Survived
All tests passed against the mutant.
Equivalent mutant
A change that doesn't alter behaviour.
Mutation score
Killed mutants ÷ all (non-equivalent) mutants.

{
  "testRunner": "vitest",
  "mutate": ["src/pricing/**/*.ts", "!src/**/*.test.ts"],
  "incremental": true,
  "thresholds": { "high": 85, "low": 70, "break": 65 }
}

4Gains vs losses nothing is free

What we gain

  • Measures test strength, not just reach.
  • Concrete to-dos: each survivor is a missing check.
  • Finds weak assertions and untested boundaries.
  • Raises the bar without chasing coverage.

What we lose

  • Slow: the suite runs once per mutant.
  • Noise from equivalent mutants.
  • Needs a decent suite to be useful.
  • Another report to read and act on.

6Common pitfalls the usual ways this goes wrong

  • Running it on everything

    Six hours for a full run; nobody looks. Fix → start with core logic; use incremental mode in PRs.

  • Chasing 100%

    Hours spent on equivalent or trivial mutants. Fix → set a sensible threshold; ignore equivalents.

  • Killing mutants with silly tests

    Tests assert implementation details just to kill mutants. Fix → add meaningful behaviour checks.

  • Using it on a weak suite

    Hundreds of survivors, overwhelming. Fix → fix the obvious gaps first, then mutate.

7When to use it (and when not)

Use it when…

  • Core business logic: pricing, permissions, money.
  • Libraries other teams depend on.
  • When coverage is high but bugs still slip through.

Skip it when…

  • Glue code and generated code.
  • Very slow suites, until they're faster.
  • Early prototypes.

Related patterns

  • Property-based testing
  • Arrange–Act–Assert
  • Characterization tests
  • Parallel & selective runs

8Self-check quiz

Why isn't high coverage enough?

Coverage shows code ran, not that any assertion would fail if the code were wrong.

What's a surviving mutant?

A planted bug that no test noticed: every test still passed.

What's an equivalent mutant?

A change that doesn't alter behaviour, so no test could ever kill it.

How do you keep mutation testing affordable?

Limit it to core code and run it incrementally on changed files.

remember!!

Detectors on the ceiling aren't safety. Run the drill and fix the silent ones.
