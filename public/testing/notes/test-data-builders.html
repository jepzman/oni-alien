Test Data Builders

TL;DR

Create test objects through builders that start from a complete, valid default and let each test override only the detail it cares about: anOrder() .dueOn(yesterday) .build(). Tests get shorter and say what matters, and when a type gains a field you change one default, not 200 tests.

  • Family: test setup
  • Origin: Nat Pryce; Growing Object-Oriented Software (2009)
  • Cousins: object mother, factories (factory_bot, Fishery)
  • Pairs with: arrange–act–assert, property-based testing

1The problem why do we even need this?

Real objects have many required fields. If every test builds them by hand, the noise drowns the signal: you can't see which of 15 fields the test is actually about.

  • A test about overdue orders spells out addresses and card numbers.
  • A new required field breaks hundreds of tests that don't care about it.
  • People copy-paste setup and slightly different “valid” objects spread everywhere.

2Real-life analogy the regular sandwich

At your usual sandwich shop you don't list twelve ingredients. You say “the usual, but no tomato”. The shop knows the sensible defaults; you speak only the difference.

  • “The usual” is the builder's default.
  • “No tomato” is the override the test cares about.
  • When the shop adds a new sauce to the usual, nobody re-orders: one place changes.

3How it solves it valid defaults + named overrides

A builder is a tiny fluent API for your tests. Its method names become the domain vocabulary of your test suite.

  1. Start from a valid default

    Every field filled with a believable value that passes validation.

  2. Add intention-revealing methods

    .overdue(), .paidBy(card), .withItems(3), not just raw setters.

  3. Make defaults unique

    Generate ids and emails so tests don't collide.

  4. Compose builders

    Pass one builder into another: anOrder().for( aUser().inSpain()).

  5. Keep builders in one place

    test/builders/, shared by all tests.

Vocabulary for the exam

Test data builder
Fluent helper that builds valid test objects.
Object mother
Named ready-made objects (Orders.overdue()).
Default
The value used when a test doesn't care.
Override
The detail a test deliberately sets.
Fixture
Any data or state a test needs before it runs.
Irrelevant detail
Setup noise that hides the test's intent.
test/builders/order.tsTypeScript
let seq = 0;

export function anOrder(overrides: Partial<Order> = {}) {
  const order: Order = {
    id: ++seq,
    user: aUser().build(),
    items: [anItem().build()],
    shipping: "standard",
    dueDate: daysFromNow(14),
    ...overrides,
  };
  return {
    dueOn: (d: Date) => anOrder({ ...order, dueDate: d }),
    overdue: () => anOrder({ ...order, dueDate: daysFromNow(-1) }),
    build: () => order,
  };
}

// the test says only what matters
it("flags orders past their due date", () => {
  const order = anOrder().overdue().build();

  expect(isOverdue(order, today())).toBe(true);
});

tools: hand-written builders, Fishery and @faker-js/faker (TypeScript), factory_bot (Ruby), factory_boy (Python), Instancio and Lombok @Builder (Java), AutoFixture (.NET).

4Gains vs losses nothing is free

What we gain

  • Short tests that show only what matters.
  • One place to change when types grow.
  • Valid by default: fewer accidental validation failures.
  • A shared domain vocabulary for tests.

What we lose

  • Builder code to maintain.
  • Hidden defaults can matter without anyone noticing.
  • Over-clever builders become their own little framework.

6Common pitfalls the usual ways this goes wrong

  • A test relies on a hidden default

    It passes only because the default country happens to be “NL”. Fix → if a value matters to the assertion, set it explicitly.

  • Builders with logic

    The builder computes totals the same way the code does, so bugs hide in both. Fix → keep builders dumb; set values, don't compute them.

  • A builder per test file

    Five slightly different makeOrder helpers. Fix → one shared builder per type.

  • Shared mutable objects

    Tests reuse one built object and change it. Fix → build a fresh object per test.

7When to use it (and when not)

Use it when…

  • Domain objects with many required fields.
  • Any type built in more than a handful of tests.
  • Integration tests that insert rows (pair with a persist helper).

Skip it when…

  • Tiny value types (new Money(5, "EUR") is fine).
  • One-off tests of trivial functions.

8Self-check quiz

What does a builder's default have to be?

A complete, valid object, so tests only override what they care about.

Why do builders make type changes cheaper?

Only the builder's default has to change when a field is added.

When should a test set a value explicitly?

Whenever the assertion depends on that value.

Builder vs object mother?

An object mother offers fixed named objects; a builder offers defaults plus flexible overrides.
