Characterization Tests

TL;DR

Before changing legacy code with no tests, write tests that record what it does today, right or wrong. Feed it many realistic inputs, capture the outputs (a golden master), and assert they stay the same. Then refactor in small steps; any difference is either an intended change or a regression, and now you'll know.

  • Family: legacy code
  • Coined by: Michael Feathers, Working Effectively with Legacy Code (2004)
  • a.k.a.: golden master, pinning tests
  • Pairs with: snapshot testing, expand & contract

1The problem why do we even need this?

Legacy code is code without tests. Nobody knows all its rules, some of its “bugs” are features customers rely on, and every change is a gamble.

  • The author left; the spec, if it ever existed, is out of date.
  • You can't write “correct” tests because nobody knows what correct is.
  • So the code never gets cleaned up, and gets worse with every patch.

2Real-life analogy labelling the old wiring

A renovator in an old house doesn't rip out wires first. They photograph and label every wire: “red goes to the kitchen light”, “blue goes… somewhere, keep it!”. They don't judge whether it's right. After the work, they check that everything still connects the way it did.

  • The labels are characterization tests.
  • “Keep it, we don't know why” is a pinned odd behaviour.
  • Once the house is understood, the labels become a proper wiring diagram: real tests.

3How it solves it pin first, change second

The goal isn't to prove the code right. It's to make any change in behaviour visible, so refactoring becomes safe.

  1. Find a seam

    A place to call the code and observe output (a function, an HTTP endpoint, a file it writes).

  2. Collect realistic inputs

    Recorded production requests, combinations of options, plus a generator for coverage.

  3. Record the outputs

    Store them as a golden master (snapshot); include weird results.

  4. Assert “unchanged”

    One test compares current outputs to the master.

  5. Change in small steps

    Refactor, run, inspect any diff; approve intended changes only.

  6. Graduate

    As rules become clear, write named behaviour tests and retire golden cases.

Vocabulary for the exam

Legacy code
Code without tests (Feathers' definition).
Characterization test
A test that records current behaviour.
Golden master
Saved outputs for a large set of inputs.
Seam
A place to observe or alter behaviour without editing it.
Pinning
Locking current behaviour so changes become visible.
Sprout / wrap
Adding new code beside old code instead of inside it.
shipping.characterization.test.tsVitest
import inputs from "./fixtures/shipping-requests-2026-10.json";   // 1,000 recorded orders

it("calculates shipping exactly as it did before the refactor", () => {
  const results = inputs.map((req) => ({
    id: req.id,
    out: calculateShipping(req.weight, req.country, req.express, req.items),
  }));

  expect(results).toMatchSnapshot();          // golden master, odd results included
});

// pinned odd behaviour, written down when discovered
it("charges zero for exactly 30 kg to Belgium (legacy rule, ask Sales)", () => {
  expect(calculateShipping(30, "BE", false, 1)).toBe(0);
});

tools: ApprovalTests (“golden master” helpers, combination approvals), Vitest/Jest snapshots, recorded traffic (GoReplay, VCR-style cassettes), fast-check for generating input combinations, coverage reports to find unexercised branches.

4Gains vs losses nothing is free

What we gain

  • Safe refactoring of code nobody understands.
  • Quick to write: no need to know the rules first.
  • Documents surprises as you find them.
  • A path from legacy to well-tested code.

What we lose

  • Pins bugs too: wrong behaviour is locked in.
  • Opaque failures: a diff, not a named rule.
  • Brittle if outputs include noise.
  • Temporary: needs replacing with real tests later.

6Common pitfalls the usual ways this goes wrong

  • “Fixing” bugs while pinning

    You change behaviour before tests exist. Fix → pin first, change in a separate, deliberate step.

  • Unrepresentative inputs

    Ten hand-made inputs miss most branches. Fix → use recorded real inputs and check branch coverage.

  • Leaving golden masters forever

    Five years later nobody knows what they mean. Fix → graduate to named behaviour tests as you learn the rules.

  • Noise in outputs

    Timestamps make every run differ. Fix → scrub or control time and ids.

7When to use it (and when not)

Use it when…

  • Legacy code with no tests that must change.
  • Large refactors and rewrites (compare old and new).
  • Migrating to a new library or language version.

Skip it when…

  • New code (write behaviour tests from the start).
  • Code that will be deleted rather than changed.
  • Outputs that can't be made deterministic.

8Self-check quiz

What does a characterization test assert?

That the code behaves the way it does today, whether or not that's correct.

Why pin behaviour you think is a bug?

Customers may rely on it; you want to change it deliberately and visibly, not by accident.

Where do good inputs come from?

Recorded production requests, plus generated combinations to reach more branches.

What happens to characterization tests later?

They're gradually replaced by clear, named behaviour tests as the rules are understood.

remember!!

Label the old wiring before you touch it. Judge it later.
