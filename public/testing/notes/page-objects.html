Page Objects

TL;DR

Give each page or component of your UI a page object: a class with methods in user language (signInAs, addToCart) that hides the selectors and clicks. Tests read like stories, and when the markup changes you fix one page object, not forty tests. Prefer role and label locators so even the page object rarely changes.

  • Family: UI test structure
  • Popularised by: Selenium community, Martin Fowler (2013)
  • Variants: component objects, screenplay pattern
  • Pairs with: test pyramid (top layer), headless components

1The problem why do we even need this?

Browser tests click on things found by selectors. Copy those selectors into every test and the suite becomes as fragile as your CSS.

  • A designer renames a class and 40 tests fail with the same error.
  • Tests are full of nth-child(2) and nobody knows what they click.
  • Login steps are repeated, slightly differently, in every file.

2Real-life analogy the TV remote

You press Play on a remote without knowing how the TV is wired. The manufacturer can redesign every circuit, and the buttons stay the same.

  • The buttons are page-object methods.
  • The circuits are selectors and clicks, hidden inside.
  • You read the remote, not the circuit diagram: tests read like user stories.

3How it solves it tests talk to pages, pages talk to the DOM

Page objects are a thin translation layer: user intent above, DOM details below. Keep assertions in the tests and the “how to click” in the page objects.

  1. One object per page or component

    LoginPage, CartDrawer, CheckoutPage.

  2. Expose user actions

    signInAs(user), addToCart(name), returning the next page where useful.

  3. Use resilient locators

    getByRole("button", { name: "Pay" }) or test ids, not CSS paths.

  4. Keep assertions in tests

    Page objects may expose state (cart.count()), tests decide what's right.

  5. Share via fixtures

    Inject page objects with your runner's fixtures so tests stay short.

Vocabulary for the exam

Class wrapping one page's locators and actions.
Locator
How the test finds an element.
Role locator
Finds elements the way assistive tech sees them.
Test id
A data-testid attribute just for tests.
Component object
A page object for a reusable widget.
Screenplay pattern
Actors performing tasks: a more composable variant.
e2e/pages/login.ts + checkout.spec.tsPlaywright
export class LoginPage {
  constructor(private page: Page) {}
  async goto() { await this.page.goto("/login"); }
  async signInAs(user: { email: string; password: string }) {
    await this.page.getByLabel("Email").fill(user.email);
    await this.page.getByLabel("Password").fill(user.password);
    await this.page.getByRole("button", { name: "Sign in" }).click();
  }
}

// the test reads like a story
test("a signed-in user can pay for a lamp", async ({ page }) => {
  const login = new LoginPage(page), shop = new ShopPage(page);

  await login.goto();
  await login.signInAs(users.ana);
  await shop.addToCart("Lamp");
  await shop.checkout().payWith(cards.valid);

  await expect(page.getByText("Thanks for your order")).toBeVisible();
});

tools: Playwright (fixtures + getByRole), Cypress (custom commands or page objects), WebdriverIO, Selenium, Testing Library queries (getByRole, getByLabelText) for component tests.

4Gains vs losses nothing is free

What we gain

  • One place to fix when the markup changes.
  • Readable tests in user language.
  • Reusable steps like sign-in.
  • Accessible locators double as an a11y check.

What we lose

  • An extra layer of classes.
  • Bloated page objects if they grow every helper.
  • Assertions can leak in and hide what the test checks.

6Common pitfalls the usual ways this goes wrong

  • Assertions inside page objects

    signInAs secretly expects a welcome banner. Fix → keep checks in tests; expose state instead.

  • God page objects

    One AppPage with 120 methods. Fix → one object per page or component.

  • CSS paths as locators

    Page objects still break on every redesign. Fix → use roles, labels and test ids.

  • Wrapping every tiny thing

    clickButton(name) adds nothing over Playwright. Fix → wrap user intents, not single API calls.

7When to use it (and when not)

Use it when…

  • Any suite with more than a handful of UI tests.
  • Steps repeated across tests (sign-in, checkout).
  • UIs that change often.

Skip it when…

  • Two or three smoke tests.
  • Component tests with Testing Library, which already query by role.

8Self-check quiz

Where do selectors live in the page object pattern?

Inside the page objects, never in the tests.

Why prefer getByRole over CSS selectors?

Roles and accessible names change far less than classes, and they check what users and assistive tech see.

Should page objects contain assertions?

Generally no: they expose actions and state, tests decide what's expected.

What does a page object method usually represent?

One user intent, like signing in or paying.
