Controlled Time & Randomness

TL;DR

Anything that changes between runs (the clock, time zones, random numbers, generated ids) makes tests pass today and fail tomorrow. Inject them as dependencies: production gets the real ones, tests get a fixed clock, a seeded random and predictable ids. Then test the scary moments (month end, midnight, leap day) on purpose.

  • Family: test reliability
  • Sources of chaos: now(), time zones, Math.random(), UUIDs, ordering
  • Tools: fake timers, seeded RNGs, TZ pinning
  • Pairs with: flaky test quarantine, property-based testing

1The problem why do we even need this?

Code that calls new Date() or Math.random() directly behaves differently every run. Its tests pass on most days and fail on a few, which is the worst kind of test.

  • “Renews next month” fails on 31 January.
  • Passes on laptops in Amsterdam, fails on CI in UTC.
  • One random value in a hundred triggers an untested path.
  • Tests sleep(2000) waiting for time to pass, and are slow and still flaky.

2Real-life analogy a film, not a live broadcast

A live broadcast is never the same twice. A film plays the same frames in the same order every showing, and you can pause, rewind and jump to minute 87. Good tests are films.

  • The projector's frame counter is an injected clock.
  • Jumping to a scene is setting or advancing time.
  • The same print every showing is a seeded random generator.

3How it solves it make time and chance inputs

Treat time, randomness and ids as inputs, like any other argument. Then the edge cases become ordinary test cases you choose deliberately.

  1. Find the hidden inputs

    Search for Date.now, new Date(), Math.random, randomUUID, setTimeout.

  2. Inject them

    A Clock, Random and IdGenerator passed in, with real defaults in production.

  3. Pin the environment

    Run tests with TZ=UTC and a fixed locale.

  4. Use fake timers

    Advance time instead of sleeping (vi.useFakeTimers(), vi.setSystemTime).

  5. Test the edges on purpose

    Month ends, leap days, DST switches, midnight, year boundaries.

  6. Log seeds

    When randomness is part of the test, print the seed so failures can be replayed.

Vocabulary for the exam

Deterministic
Same inputs, same result, every time.
Injected clock
A time source passed in rather than read globally.
Fake timers
Test helpers that control timers and the date.
Seed
Starting value that makes random output repeatable.
DST
Daylight saving time: days with 23 or 25 hours.
Hidden input
Something code reads that the test doesn't control.
renewal.ts + renewal.test.tsVitest
export const systemClock = { now: () => new Date() };

export function nextRenewal(sub: Subscription, clock = systemClock) {
  return addMonthsClamped(sub.renewsOn ?? clock.now(), 1);    // 31 Jan → 28 Feb
}

// test: choose the scary moment on purpose
const fixed = (iso: string) => ({ now: () => new Date(iso) });

it("renews on the last day of February from 31 January", () => {
  const clock = fixed("2027-01-31T23:59:00Z");

  const next = nextRenewal(aSubscription().build(), clock);

  expect(next.toISOString()).toBe("2027-02-28T23:59:00.000Z");
});

it("expires a trial exactly 14 days later", () => {
  vi.useFakeTimers({ now: new Date("2027-03-01T00:00:00Z") });
  const trial = startTrial();
  vi.advanceTimersByTime(days(14));            // no sleeping
  expect(trial.isExpired()).toBe(true);
});

tools: Vitest/Jest fake timers and setSystemTime, Sinon fake timers, freezegun and time-machine (Python), java.time.Clock, seedable RNGs (seedrandom, pure-rand), TZ=UTC in the test script.

4Gains vs losses nothing is free

What we gain

  • Same result every run, on every machine.
  • Edge cases on demand: month end, DST, leap years.
  • No sleeping: time-based tests run instantly.
  • Replayable failures with seeds.

What we lose

  • Extra parameters (clock, random, ids) to pass around.
  • Fake timers can surprise async code and libraries.
  • Real-time bugs can hide if you never test real clocks.

6Common pitfalls the usual ways this goes wrong

  • Fixing one test, not the code

    Mocking Date globally in one test file. Fix → inject a clock into the code itself.

  • Forgetting time zones

    Green locally, red on UTC CI. Fix → set TZ=UTC for tests; test other zones deliberately.

  • sleep() in tests

    Slow and still racy. Fix → fake timers or polling with a deadline.

  • Unseeded randomness

    A random failure nobody can reproduce. Fix → seed it and log the seed.

7When to use it (and when not)

Use it when…

  • Anything involving dates: billing, trials, expiry, scheduling.
  • Code that generates ids, tokens or random choices.
  • Timers, retries and debouncing.

Skip it when…

  • Truly time-independent pure logic.
  • A small set of real-clock smoke tests that verify the wiring.

8Self-check quiz

Why is calling new Date() inside business logic a testing problem?

It's a hidden input that changes every run, so results depend on when and where tests run.

How do you test that a trial expires after 14 days without waiting?

Use fake timers or an injected clock and advance it by 14 days.

Why set TZ=UTC for tests?

So date results don't depend on the machine's time zone.

Name three date edge cases worth testing deliberately.

Month end (31st), leap day, daylight-saving switches (also midnight and year boundaries).
