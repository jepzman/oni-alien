Property-Based Testing

TL;DR

Instead of listing examples, state a property: a rule that must hold for every input (“the parts always add up to the total”). The tool generates hundreds of random inputs, including nasty edge cases, and when one fails it shrinks it to the smallest failing example. Great at finding the bugs nobody thought to write a test for.

  • Family: test technique
  • Origin: QuickCheck (Claessen & Hughes, 2000)
  • Libraries: fast-check, Hypothesis, jqwik, FsCheck
  • Pairs with: test data builders, example tests

1The problem why do we even need this?

Example tests only check the inputs you thought of. Bugs hide in the ones you didn't: zero, negative numbers, empty lists, rounding, unicode, very large values.

  • All three examples pass; a cent disappears for 10 ÷ 3.
  • Edge cases depend on how imaginative the author was that day.
  • Writing every combination by hand is impossible.

2Real-life analogy the furniture lab

A furniture lab doesn't test a chair by having someone sit on it three times. A machine drops thousands of random loads from random angles and checks one rule each time: “it must not break under 150 kg”. When it breaks, they find the smallest load that does it.

  • Random loads are generated inputs.
  • “Must not break under 150 kg” is the property.
  • Finding the smallest breaking load is shrinking.

3How it solves it state the rule, let the tool hunt

The hard part is finding good properties. Common shapes: round-trips (decode(encode(x)) = x), invariants (sorted output is ordered), conservation (nothing created or lost), and comparing to a simple model.

  1. Pick a property

    Round-trip, invariant, conservation, idempotence (f(f(x)) = f(x)) or “same as a simple reference version”.

  2. Describe the inputs

    Generators for amounts, people, strings, lists; constrain to valid domains.

  3. Run many cases

    100–1,000 per test in CI; more in a nightly job.

  4. Read the shrunk example

    It's usually the clearest possible bug report.

  5. Keep the failure

    Add the shrunk case as a regular example test, and record the seed.

split.prop.test.tsfast-check + Vitest
import fc from "fast-check";

it("never loses or creates a cent", () => {
  fc.assert(
    fc.property(
      fc.integer({ min: 0, max: 10_000_00 }),     // total in cents
      fc.integer({ min: 1, max: 50 }),            // people
      (total, people) => {
        const parts = splitBill(total, people);

        expect(parts).toHaveLength(people);
        expect(parts.reduce((a, b) => a + b, 0)).toBe(total);
        expect(Math.max(...parts) - Math.min(...parts)).toBeLessThanOrEqual(1);
      },
    ),
  );
});
// on failure: "Counterexample: [10, 3]  Shrunk 6 time(s)  seed: 1593201"

tools: fast-check (JS/TS), Hypothesis (Python), jqwik (Java), FsCheck (.NET), proptest (Rust), QuickCheck (Haskell, Erlang). Stateful/model-based testing modes can test whole APIs.

4Gains vs losses nothing is free

What we gain

  • Finds edge cases nobody imagined.
  • Shrunk failures are minimal, clear bug reports.
  • One property covers thousands of examples.
  • Forces you to state the real rule.

What we lose

  • Good properties are hard to think of at first.
  • Slower than one example.
  • Randomness needs seeds for reproducibility.
  • Easy to restate the implementation as the property.

6Common pitfalls the usual ways this goes wrong

  • Re-implementing the code in the test

    The property computes the answer the same way the code does. Fix → check rules and relations, not the algorithm.

  • Generators that are too narrow

    Only positive integers under 10, so nothing interesting happens. Fix → include zero, empties, huge and odd values.

  • Losing the failing case

    A random failure in CI can't be reproduced. Fix → log seeds; add shrunk cases as example tests.

  • Replacing all examples

    Nobody can read what the code should do. Fix → keep a few examples as documentation.

7When to use it (and when not)

Use it when…

  • Pure functions with clear rules: money, parsing, sorting, encoding.
  • Serializers and parsers (round-trip properties).
  • Data structures and state machines.

Skip it when…

  • UI layout and copy.
  • Logic with no general rule, only special cases.
  • Slow, side-effectful operations (unless you can fake them).

8Self-check quiz

What is a property?

A rule that must hold for every valid input, such as “the parts add up to the total”.

What does shrinking do?

Reduces a failing input to the smallest, simplest example that still fails.

Name three common property shapes.

Round-trip, invariant, conservation (also idempotence and comparing to a reference model).

How do you reproduce a failing random run?

Re-run with the reported seed, then add the shrunk case as an example test.
