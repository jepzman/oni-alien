Fuzzing

TL;DR

Code that reads untrusted input (parsers, file importers, decoders, protocol handlers) breaks on inputs nobody thought to write a test for. A fuzzer generates millions of mutated inputs, runs your code on each, and watches for crashes, hangs, sanitizer errors and failed assertions. Coverage-guided fuzzers keep inputs that reach new code, so they dig deeper over time. Run it continuously; turn every finding into a regular test.

  • Family: test techniques
  • Best for: parsers, decoders, file formats, protocols
  • Kinds: coverage-guided · grammar-based · API fuzzing
  • Pairs with: property-based testing, validate at the boundary

1The problem why do we even need this?

An invoice importer has twelve example tests with tidy files, all green. In production, file #4,812 has a cut-off line and a stray byte, and the parser loops for ever, hanging the import worker for every customer behind it.

  • Example tests check the inputs you imagined; real-world and hostile inputs are stranger.
  • Parser bugs are often security bugs: crashes, hangs and memory errors on attacker-chosen input.
  • Writing enough strange examples by hand is impossible.

2Real-life analogy the toddler test

Toy makers don't only press the buttons the way the manual says. They let machines bang, twist, drop and chew the toy thousands of times, because that's how a toddler will use it, and the crack nobody planned for shows up by try 3,000.

3How it solves it mutate, run, keep what's new

A coverage-guided fuzzer starts from a few real inputs (the seed corpus), changes them in small random ways, and runs your code on each, instrumented so it can see which branches ran. Inputs that reach new code are kept and mutated further. Sanitizers turn silent memory errors into crashes the fuzzer can see. Findings are shrunk to a small input that reproduces them.

  1. Pick a target

    A function that takes bytes or a string from outside: a parser, a decoder, an upload handler.

  2. Write a fuzz harness

    A few lines that pass the fuzzer's input to the target and assert anything that must always hold.

  3. Give it seeds

    A handful of real files, including odd ones; a dictionary of keywords helps text formats.

  4. Run it continuously

    Minutes per pull request, hours nightly (or a service like OSS-Fuzz for open source).

  5. Keep the findings

    Each crash becomes a regular test case and a fix; keep the corpus between runs.

Vocabulary for the exam

Fuzzing
Running code on huge numbers of generated inputs to find failures.
Harness
The small function that hands fuzzer input to your code.
Corpus
The set of interesting inputs the fuzzer keeps and mutates.
Coverage-guided
The fuzzer favours inputs that reach new code.
Sanitizer
Instrumentation that turns memory and undefined-behaviour bugs into crashes.
Minimisation
Shrinking a crashing input to the smallest that still fails.
invoice_fuzz_test.goGo 1.18+ native fuzzing
func FuzzParseInvoice(f *testing.F) {
    // seeds: real files, including odd ones we've seen
    f.Add([]byte("INV;2026-03-01;812;4.10\n"))
    f.Add([]byte("INV;;;\n"))

    f.Fuzz(func(t *testing.T, data []byte) {
        inv, err := ParseInvoice(bytes.NewReader(data))  // must never panic or hang
        if err != nil {
            return                                       // rejecting bad input is fine
        }
        // properties that must hold for anything we accept
        if inv.TotalCents < 0 {
            t.Fatalf("negative total from %q", data)
        }
        again, _ := ParseInvoice(strings.NewReader(inv.String()))
        if !reflect.DeepEqual(inv, again) {
            t.Fatalf("round trip changed the invoice")
        }
    })
}
// go test -fuzz=FuzzParseInvoice -fuzztime=10m ; crashes land in testdata/fuzz/

tools: Go native fuzzing, libFuzzer and AFL++ (C, C++, Rust via cargo-fuzz), Jazzer (Java), Atheris (Python), Jazzer.js (JavaScript), OSS-Fuzz and ClusterFuzzLite, RESTler and Schemathesis (API fuzzing).

4Gains vs losses nothing is free

What we gain

  • Finds bugs no one would write a test for.
  • Finds security bugs in input handling early.
  • Cheap per bug: machines do the searching.
  • Reproducible: every finding comes with its input.

What we lose

  • Needs a harness per target, and CPU time.
  • Mostly finds crashes: logic bugs need assertions or properties.
  • Slow to start on complex formats without good seeds or grammars.
  • Triage: findings need someone to look at them.

6Common pitfalls the usual ways this goes wrong

  • Fuzzing once

    A ten-minute run before release, never again. Fix → run it continuously; coverage keeps growing for days.

  • No assertions

    The fuzzer only finds crashes, while wrong results pass. Fix → assert properties: round trips, invariants, no negative totals.

  • Throwing away the corpus

    Each run starts from scratch and finds the same shallow bugs. Fix → store the corpus and reuse it between runs.

  • Fixing without a test

    A crash is fixed, and comes back a year later. Fix → add the crashing input as a regular test before the fix.

7When to use it (and when not)

Use it when…

  • Parsers, decoders, file importers and protocol handlers.
  • Anything that reads untrusted input from users or the network.
  • Code in memory-unsafe languages (C, C++, unsafe Rust).

Skip it when…

  • Code that doesn't take external input (most business logic: use property tests).
  • UI flows (use other tests).
  • No one will look at the findings.

8Self-check quiz

What kind of code benefits most from fuzzing?

Code that reads untrusted or complex input: parsers, decoders, file formats and protocol handlers.

What does “coverage-guided” mean?

The fuzzer keeps inputs that reach new code paths and mutates those further.

Why add assertions to a fuzz harness?

Without them the fuzzer only sees crashes and hangs; assertions turn wrong results into failures too.

What do you do with a crashing input?

Minimise it, add it as a regular test, then fix the bug.

what would you do?Your team wrote a new parser for a partner's file format. It has 30 example tests and ships next week. Security asks how you know a malformed file can't crash the import service. What do you add before release?

A fuzz harness for the parser with real partner files as seeds and a few properties (round trip, no negative amounts), run for several hours before release and then in CI and nightly. Add every finding as a regular test, and set a time and size limit on parsing as a second line of defence.

try it

Pick one function in your codebase that parses text or bytes. Write a fuzz harness for it (Go's testing.F, Jazzer.js, Atheris or cargo-fuzz), seed it with three real inputs, and run it for 15 minutes. Add any crashing input as a regular test, fix it, and run again.

remember!!

Your tests try what you imagined. A fuzzer tries what you didn't.
