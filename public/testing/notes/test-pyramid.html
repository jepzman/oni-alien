Test Pyramid

TL;DR

Write lots of small, fast unit tests, fewer integration tests that touch real boundaries (database, HTTP), and only a handful of end-to-end tests for the critical journeys. Push each check to the lowest layer that can catch it. You get a suite that runs in minutes, fails precisely, and still proves the whole thing works.

  • Family: test strategy
  • Origin: Mike Cohn, Succeeding with Agile (2009)
  • Variants: testing trophy, honeycomb
  • Anti-pattern: the ice-cream cone

1The problem why do we even need this?

Browser tests feel like the most honest tests: they click what users click. So teams write hundreds of them, and the suite turns into an ice-cream cone: slow, flaky, and vague about what broke.

  • CI takes an hour, so people batch changes and merge without waiting.
  • A failing end-to-end test could mean any of fifty causes.
  • Random timeouts teach everyone to press “re-run”.

2Real-life analogy the car factory

A car factory checks every bolt on a bench in seconds, checks assembled sections on a rig, and sends only a few finished cars on a full test drive. If a test drive finds a problem, they add a bench check so it's caught earlier next time.

  • Bench checks are unit tests: cheap, fast, precise.
  • The rig is integration tests: real joints, fewer of them.
  • The test drive is end-to-end: proof it all works together.

3How it solves it the right test at the right layer

The shape matters more than exact percentages. Each layer exists to catch what the cheaper layer below can't, never to repeat it.

  1. List the risks

    Business rules, data access, wiring, the critical user journeys.

  2. Rules → unit tests

    Pricing, validation, state changes: pure functions and small classes, tested in milliseconds.

  3. Boundaries → integration tests

    Queries against a real database, HTTP handlers, message consumers.

  4. Journeys → a few end-to-end tests

    Sign up, checkout, payment: the paths that must never break.

  5. Push bugs down

    When an e2e test catches a bug, add a lower-level test that would have caught it.

  6. Watch the shape

    Track counts and run time per layer; a growing top is a smell.

package.jsonone script per layer
{
  "scripts": {
    "test:unit":  "vitest run src --project unit",              // ~2,000 tests · 20 s
    "test:int":   "vitest run src --project integration",       // ~300 tests · 2 min
    "test:e2e":   "playwright test e2e/critical",               // ~25 tests · 6 min
    "test":       "npm run test:unit && npm run test:int"       // every push
  }
}
// CI: unit + integration on every push, e2e on merge to main and nightly

tools: Vitest and Jest (unit), Testcontainers and Supertest (integration), Playwright and Cypress (e2e). Kent C. Dodds's “testing trophy” and Spotify's “honeycomb” are variants for UI-heavy and microservice code.

4Gains vs losses nothing is free

What we gain

  • Fast feedback: most failures show up in seconds.
  • Precise failures: a red unit test points at one function.
  • Cheap to run on every push.
  • Still realistic: the top layer proves the journeys work.

What we lose

  • Unit tests can miss wiring bugs: things pass alone, fail together.
  • Over-mocking temptation to keep things “unit”.
  • Needs judgement about which layer each test belongs to.
  • Several tools and test setups to maintain.

6Common pitfalls the usual ways this goes wrong

  • Mocking everything to stay “unit”

    Every collaborator is mocked; tests pass while the real wiring is broken. Fix → test boundaries with real integrations at the middle layer.

  • Duplicating checks at every layer

    The same validation is tested in unit, API and e2e tests. Fix → test each rule once, at the lowest layer that can see it.

  • Chasing percentages

    “We need exactly 70% unit tests.” Fix → aim for the shape, judge by speed and confidence.

  • No e2e at all

    Everything passes, but the login page is blank. Fix → keep a small set of critical-path journeys.

7When to use it (and when not)

Use it when…

  • Almost any product with a growing codebase.
  • Teams whose CI is slow or flaky.
  • Business logic that can be tested without the UI.

Skip it when…

  • Thin UI glue with no logic (prefer integration tests, the “trophy”).
  • Tiny scripts where a couple of end-to-end checks are enough.
  • Exploratory prototypes you'll throw away.

Related patterns

8Self-check quiz

What's the ice-cream cone anti-pattern?

A suite with mostly slow end-to-end tests and few unit tests: the pyramid upside down.

Where should a pricing rule be tested?

In fast unit tests; the e2e layer only needs to show checkout works overall.

What should you do when an e2e test catches a bug?

Add a lower-level test that would have caught it, so the next one fails faster and more precisely.

Why keep any e2e tests?

They're the only layer that proves the whole system works together for real users.
