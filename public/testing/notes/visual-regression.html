Visual Regression Tests

TL;DR

Unit and end-to-end tests check text, state and clicks; they don't notice a button covering the total or a broken layout on phones. Visual regression tests render pages or components in a fixed browser, at fixed sizes, with fixed data, take screenshots, and compare them with approved baselines. A difference fails the build and shows a diff; a person decides whether it's a bug or the new look.

  • Family: test techniques
  • Unit of test: a component state or a page at a viewport size
  • Cousin: snapshot testing (text instead of pixels)
  • Pairs with: design tokens, page objects, Storybook

1The problem why do we even need this?

A developer adds 8 px of padding to a shared button. Every unit and end-to-end test passes. On the checkout page, the Pay button now covers the order total and is cut off on small phones. Customers notice first.

  • CSS changes travel: one shared style can break many pages.
  • Functional tests check what is on the page, not where or how it looks.
  • Manual checks of every page, at every screen size, after every change don't happen.

2Real-life analogy spot the difference

Two pictures side by side, the approved one and the new one, with every difference circled in red. You don't search the whole picture; you look at the circles and decide: a mistake to fix, or an intended change that becomes the new approved picture.

Translating it to software
In real lifeIn your code
The approved pictureThe baseline screenshot, stored with the tests
The new pictureThe screenshot from this build
Circles around differencesThe diff image, pixels above a threshold
“Mistake or intended?”Review: fix the bug, or approve the new baseline
Same light, same angleSame browser, fonts, data and viewport every run

3How it solves it render the same way, compare, review

The hard part is making screenshots repeatable: the same browser build, fonts loaded, animations off, fixed data and dates, no ads or live content. Then any pixel difference means something changed. Test at the component level (Storybook stories) for breadth, and a few full pages for layout.

  1. Choose what to capture

    Each component state (from stories) and a few key pages, at 2–3 widths (phone, tablet, desktop).

  2. Make rendering repeatable

    Pinned browser in a container, fonts loaded, animations and carets off, fixed data and clock, masks for live content.

  3. Store baselines

    In the repo (small sets) or a service; one baseline per browser and size.

  4. Compare with a small threshold

    Ignore tiny anti-aliasing noise; fail above it and attach the diff image.

  5. Review changes like code

    An intended change updates the baseline in the same pull request; a reviewer looks at the diffs.

Vocabulary for the exam

Baseline
The approved screenshot a new one is compared with.
Diff image
An image highlighting the pixels that changed.
Threshold
How much difference is tolerated as noise.
Mask
An area left out of the comparison (a clock, an ad, an avatar).
Viewport
The screen size the page is rendered at.
Flaky screenshot
One that differs between runs with no code change.
checkout.visual.spec.tsPlaywright
import { test, expect } from "@playwright/test";

for (const width of [375, 768, 1280]) {
  test(`checkout summary looks right at ${width}px`, async ({ page }) => {
    await page.setViewportSize({ width, height: 900 });
    await page.clock.setFixedTime(new Date("2026-03-01T10:00:00Z"));   // fixed dates
    await page.route("**/api/cart", (r) => r.fulfill({ path: "fixtures/cart.json" }));
    await page.goto("/checkout");
    await page.evaluate(() => document.fonts.ready);

    await expect(page.getByTestId("order-summary")).toHaveScreenshot(`summary-${width}.png`, {
      animations: "disabled",
      mask: [page.getByTestId("live-chat")],      // live content left out
      maxDiffPixelRatio: 0.002,                     // ignore anti-aliasing noise
    });
  });
}
// npx playwright test --update-snapshots   ← only for an intended change, reviewed in the PR

tools: Playwright toHaveScreenshot, Storybook test runner, Chromatic, Percy, Applitools, BackstopJS, Loki, Lost Pixel; run in a pinned Docker image so fonts and rendering match.

4Gains vs losses nothing is free

What we gain

  • Catches layout and style bugs that other tests miss.
  • Covers many screen sizes automatically.
  • Safer shared CSS: changes show every affected page.
  • Review by looking: diffs are quick to judge.

What we lose

  • Flaky without care: fonts, animations and live data.
  • Baselines to maintain for every intended change.
  • Storage and CI time for screenshots.
  • Tells you what changed, not why.

6Common pitfalls the usual ways this goes wrong

  • Screenshots that differ every run

    Fonts load late, a carousel moves, today's date changes. Fix → wait for fonts, disable animations, fix the clock and data, mask live areas.

  • Different machines, different pixels

    Baselines made on a Mac fail on Linux CI. Fix → make and compare screenshots in the same pinned container.

  • Approving without looking

    A big change updates 200 baselines and nobody checks them. Fix → keep shots small (components), and review diffs like code.

  • Only full pages

    One full-page shot changes for every tiny thing. Fix → mostly component states; a few pages for layout.

7When to use it (and when not)

Use it when…

  • Design systems and shared components.
  • Responsive layouts that must work at several sizes.
  • Refactors of CSS, themes or design tokens.

Skip it when…

  • Pages full of live, changing content you can't fix.
  • Very early prototypes whose look changes daily.
  • No one will review the diffs.

8Self-check quiz

What do visual regression tests catch that end-to-end tests usually don't?

How the page looks: overlaps, broken layouts, wrong colours or spacing, at different screen sizes.

Name three things that make screenshots flaky.

Fonts loading late, animations, and live data such as dates, ads or avatars.

Why compare screenshots in a container?

Different operating systems render fonts slightly differently; the same container makes runs comparable.

What happens when a change is intended?

The new screenshot is approved as the baseline in the same pull request, after review.

what would you do?Visual tests fail on about one run in five with tiny differences in text edges, and the team has started approving every diff without looking. What do you change?

Remove the noise: render in one pinned container, wait for fonts, disable animations, and set a small difference threshold. Once diffs only appear for real changes, require a reviewer to look at them, and keep screenshots small so diffs stay readable.

try it

Add one visual test with Playwright's toHaveScreenshot for a component or page at two widths, with fonts loaded and animations off. Run it twice to check it's stable, then change one CSS value (padding, colour) and look at the diff image it produces.

remember!!

Tests check what is there. Screenshots check how it looks.
