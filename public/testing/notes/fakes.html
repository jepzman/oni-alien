Fakes

TL;DR

A fake is a small, working implementation of a dependency, like an in-memory repository backed by a Map, or a fake payment gateway that remembers charges. Tests use it like the real thing: save, then find. No scripting of every call. Run one shared contract test against both the fake and the real implementation so the fake can't quietly drift.

  • Family: isolation
  • Examples: in-memory repo, fake clock, fake mail outbox
  • Kept honest by: shared contract tests
  • Pairs with: test doubles, throwaway containers

1The problem why do we even need this?

Mocks script a conversation call by call. For anything with state, like a repository or a cart service, the script grows long and re-implements the dependency badly, and tests break when you refactor harmless details.

  • Thirty lines of mockReturnValueOnce per test.
  • Calling find() twice in the code breaks 40 tests.
  • The mock says save succeeded, but nothing is actually stored for the next step.

2Real-life analogy the flight simulator

Pilots don't train in a real plane, and they don't train with a script (“press A, the screen shows B”). They use a simulator: simplified insides, but it really responds to whatever they do, in any order.

  • The simulator is the fake: real behaviour, simple insides.
  • The script is a mock: only works if you follow it exactly.
  • Simulators are certified against real planes: the contract test.

3How it solves it one interface, two implementations

Fakes shine for stateful dependencies. Write them once, share them across the suite, and prove them with the same tests the real implementation passes.

  1. Define the port

    An interface your code depends on: save, findById, findByEmail.

  2. Write the fake

    A Map or array; keep it small and obviously correct.

  3. Write contract tests

    One suite, parameterised by implementation: “save then find returns it”, “email is unique”.

  4. Run them on both

    The fake in unit runs; the real one against a database container.

  5. Use the fake everywhere

    Services, handlers and use-case tests get fast, realistic behaviour.

export class InMemoryUserRepository implements UserRepository {
  private rows = new Map<string, User>();
  async save(u: User) {
    const clash = [...this.rows.values()].find((x) => x.email === u.email && x.id !== u.id);
    if (clash) throw new DuplicateEmail(u.email);          // same rule as the DB
    this.rows.set(u.id, structuredClone(u));
  }
  async findById(id: string) { return structuredClone(this.rows.get(id)) ?? null; }
}

// one suite, every implementation
export function userRepositoryContract(make: () => Promise<UserRepository>) {
  it("finds what it saved", async () => {
    const repo = await make();
    await repo.save(aUser({ id: "7" }));
    expect(await repo.findById("7")).toMatchObject({ id: "7" });
  });
  it("rejects duplicate emails", async () => { /* … */ });
}
describe("in-memory", () => userRepositoryContract(async () => new InMemoryUserRepository()));
describe("postgres", () => userRepositoryContract(() => pgRepoInContainer()));

tools: hand-written fakes, MSW handlers with in-memory state, localstack (AWS), fake SMTP servers like MailHog/Mailpit, Firebase and Azurite emulators, SQLite in-memory (careful: it isn't Postgres).

4Gains vs losses nothing is free

What we gain

  • Natural tests: save, then find. No call scripts.
  • Refactor-friendly: tests check behaviour, not calls.
  • Fast: in-memory and in-process.
  • Reusable across the whole suite.

What we lose

  • Code to write and maintain.
  • Can drift from the real thing without contract tests.
  • Not the real engine: SQL quirks, transactions and locks aren't covered.

6Common pitfalls the usual ways this goes wrong

  • Fakes without contract tests

    The fake allows duplicate emails; production doesn't. Fix → run the same contract suite on fake and real.

  • Over-smart fakes

    The fake re-implements half of PostgreSQL. Fix → keep it tiny; test SQL-specific behaviour against a real database.

  • Returning shared references

    A test mutates a found object and changes the fake's state. Fix → return copies (structuredClone).

  • SQLite as a fake for Postgres

    Tests pass; real queries fail on JSONB or locking. Fix → use a real Postgres container for data-layer tests.

7When to use it (and when not)

Use it when…

  • Repositories, caches, queues, file stores.
  • Use-case and service tests with stateful collaborators.
  • Replacing long mock setups.

Skip it when…

  • Simple one-call queries (a stub is enough).
  • Testing SQL itself (use the real database).
  • Dependencies whose behaviour is too complex to fake honestly.

8Self-check quiz

How is a fake different from a stub?

A stub returns canned answers; a fake actually works, keeping state so calls in any order behave sensibly.

How do you stop a fake drifting from the real implementation?

Run one shared contract test suite against both.

Why return copies from an in-memory fake?

So tests can't change stored state by mutating returned objects, just like a real database.

When is a real database better than a fake?

When you're testing queries, constraints, transactions or engine-specific features.

remember!!

Train in a simulator, not from a script, and certify it against the real thing.
