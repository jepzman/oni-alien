Limits and kernel settings

Some of the resources that run out on a busy server aren't CPU, memory or disk, but numbers: how many files a process may open, how many connections may wait to be accepted, how many ports there are to connect from. This chapter shows where each limit is set, how to see which one you've hit, and how to raise the right one without copying a page of “tuning” from the internet.

By the end you can

  • Explain file descriptor limits at the system, process and application level, and read a process's limits.
  • Diagnose “Too many open files” and raise the limit for a systemd service.
  • Explain the listen backlog and spot a full accept queue with ss and nstat.
  • Read and set kernel parameters with sysctl, and make them persistent.
  • Decide which settings are worth changing, and say why.

Before you start

  • Chapter 2: file descriptors. Chapter 6: drop-ins. Chapter 5: /proc/<pid>.
  • A Linux VM with Python 3 and iproute2; for the nginx step, a VM with systemd and nginx (Appendix C).

At Stagedoor

Friday 10 July 2026 is the biggest on-sale in Stagedoor's history: a stadium date for a band that last played Portugal ten years ago. At 10:00:38, fans start seeing 502 Bad Gateway. On door-2, nginx's error log fills with two kinds of line: accept4() failed (24: Too many open files) and 768 worker_connections are not enough.

The CPUs are at 40%, memory is fine, the disks are idle. Nothing in the last six chapters has run out. Tiago reads the error number aloud: 24. Rafaela knows it from a hundred incidents at her old job: EMFILE, the process has hit its limit on open files.

12.1File descriptors, and why servers need many

A file descriptor is the small number a process uses for anything it has open (Chapter 2): a file, a pipe, and, on a server, every network connection. A web proxy like nginx uses two per request it forwards: one for the fan's connection and one for its connection to the app.

Each process can have only so many open at once, and the limit is enforced in three layers:

The middle layer is the one most often hit. Its soft limit is what's enforced; the hard limit is the ceiling a process may raise its own soft limit to. A soft limit of 1024 is a historical default that's still common, and it's far too low for a busy proxy: 1024 file descriptors, minus a few for logs and listening sockets, is about 500 proxied requests per nginx worker.

To see a running process's limits and usage, use /proc, not your own shell's ulimit (which shows only your shell's):

grep -i "open files" /proc/2187/limits          # soft and hard limit of process 2187
ls /proc/2187/fd | wc -l                        # how many it has open right now
sudo ls -l /proc/2187/fd | grep -c socket       # how many of those are sockets

12.2Raising the limit, in the right place

Limits are inherited from parent to child (Chapter 5), so where you set one decides who gets it:

  • For a service, in its unit or a drop-in: LimitNOFILE=65536 sets soft and hard; LimitNOFILE=4096:65536 sets them separately. This is the one that matters for servers, because services don't start from a login shell.
  • For one shell and the programs it starts: ulimit -n 4096 (up to the hard limit; raising the hard limit needs root).
  • For login sessions: /etc/security/limits.conf or a file in /etc/security/limits.d/, read by PAM at login. It has no effect on services, which is the most common reason “I raised the limit and nothing changed”.

Then the application's own setting, the innermost layer. nginx has two: worker_connections, the connections each worker may hold, and worker_rlimit_nofile, which raises the worker's own file limit. A useful rule: worker_rlimit_nofile at least twice worker_connections, and LimitNOFILE= at least that.

Key idea

After changing a limit, check the running process's /proc/<pid>/limits. Not your shell's, not the config file's: the process's.

12.3The listen backlog

Before a server's code sees a connection, the kernel has already done the TCP handshake (Handbook 1, Chapter 3) and put the finished connection in a queue for that listening socket, the accept queue. The program takes connections from it with accept(). The queue's length is the listen backlog: the number the program passes to listen(), capped by the kernel setting net.core.somaxconn.

Two consequences surprise people. First, clients can connect successfully to a program that will never serve them: the lab's crowd reports every connection as made while the server is stuck. Second, the symptom of a full queue is delay (clients retransmit their handshake after one second, then two, then four), not an error message anywhere. ss -lnt shows the queue for every listening socket, and nstat -az TcpExtListenOverflows counts drops since boot.

Since Linux 5.4, net.core.somaxconn defaults to 4096, which is enough for most servers; older kernels (and old “tuning” guides) used 128. The program's own value is usually the limiting one: nginx asks for 511 unless you write listen 443 ssl backlog=4096;.

12.4Kernel parameters with sysctl

The kernel exposes hundreds of settings as files under /proc/sys/: net.core.somaxconn is /proc/sys/net/core/somaxconn. sysctl reads and writes them:

sysctl net.core.somaxconn                          # read one
sudo sysctl -w net.core.somaxconn=8192             # change it now; lost at reboot
echo "net.core.somaxconn = 8192" | sudo tee /etc/sysctl.d/60-stagedoor.conf   # persist
sudo sysctl --system                               # reload every file in /etc/sysctl.d/

Files in /etc/sysctl.d/ are read in name order at boot, later ones winning. Put each setting in a file named for your purpose, with a comment saying why: the next person to see vm.swappiness = 10 deserves to know who decided that, and on what evidence.

Watch out: copied tuning

The internet is full of “Linux performance tuning” lists with forty sysctl lines. Many were written for kernels from 2010, some are harmful today (net.ipv4.tcp_tw_recycle broke clients behind NAT and was removed from the kernel), and almost none come with a measurement. Change a setting when you can name the limit you hit, show it in a counter or a log, and check afterwards that the counter stopped growing.

12.5Other limits you'll meet

  • Processes and threads: LimitNPROC= and TasksMax= per service (systemd's default task limit is a percentage of the system's), kernel.pid_max for the whole system. Hitting them shows as “Resource temporarily unavailable” when starting threads.
  • Ephemeral ports: every outgoing connection from one address to one destination address and port needs its own source port, and there are about 28,000 in the default range. A proxy that opens a new connection to its backend for every request, and closes it, can run out, helped by the 60 seconds each closed connection spends in TIME_WAIT. Keep-alive connections to the backend (nginx's keepalive in an upstream block) fix it far better than widening the range. ss -s shows the counts.
  • Memory locked, message queues, core file size: other Limit…= settings in man systemd.exec, needed rarely and by specific software, which documents them.

12.6Finding which limit you hit

Errors name limits by their errno numbers and names, and a few cover almost everything in this chapter:

Table 12.2 · Error numbers that mean “a limit”

With the number in hand: read the process's /proc/<pid>/limits, count what it has open in /proc/<pid>/fd, look at the listening socket with ss -lnt, and check the kernel's counters with nstat.

12.7Across distributions

The limits and sysctl settings are the kernel's and systemd's, so they work the same everywhere; defaults differ a little by kernel version. Two practical differences:

On older releases and other packages

Kernels before 5.4 (Ubuntu 18.04, RHEL 7 and 8, Amazon Linux 2's original kernel) default somaxconn to 128, a real limit for busy servers. Distribution nginx packages differ too: Ubuntu's sets worker_connections 768, nginx.org's packages 1024, and neither raises worker_rlimit_nofile. Whatever the defaults, read them on your server with sysctl and /proc/<pid>/limits rather than trusting a book or a blog, this one included.

12.8Lab: run out of file descriptors

Lab 12 · Too many open files, on purpose

You'll run a server that holds every connection open, give it a small file limit, send it a crowd, and watch it fail with errno 24 while the crowd believes it's connected; then fill its accept queue, raise its limit, and finally raise nginx's limits the systemd way. You need a Linux VM with Python 3; for the last step, systemd and nginx (sudo apt install nginx). Cost: nothing. Clean-up: stop the programs, remove the nginx drop-in and config change. Outputs come from the test VM (user tiago) and, for nginx, the systemd test system of Lab 6.

  2. The server and the crowd. In ~/lab12, save:

    holdserver.pyPython 3.8+

    # holdserver.py · accept connections and keep every one open, like a proxy waiting on slow checkouts
import os, socket, time

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 9000))
srv.listen(1024)
print(f"pid {os.getpid()} listening on 127.0.0.1:9000", flush=True)

held, errors = [], 0
while True:
    try:
        conn, _ = srv.accept()
        held.append(conn)                       # each open connection is one file descriptor
        if len(held) % 100 == 0:
            print(f"holding {len(held)} connections", flush=True)
    except OSError as e:
        errors += 1
        if errors in (1, 100, 1000):            # don't print the same error thousands of times
            print(f"accept failed ({errors}x) with {len(held)} held: {e}", flush=True)
        time.sleep(0.01)

    crowd.pyPython 3.8+

    # crowd.py N · open N connections to 127.0.0.1:9000, hold them 10 seconds, report how many got in
import socket, sys, time

wanted, conns, refused = int(sys.argv[1]), [], 0
for i in range(wanted):
    s = socket.socket()
    s.settimeout(2)
    try:
        s.connect(("127.0.0.1", 9000))
        conns.append(s)
    except OSError:
        refused += 1
print(f"connected {len(conns)} of {wanted}, failed {refused}", flush=True)
time.sleep(10)

That's what fans saw on 10 July: not a refusal, a page that never loaded, then a 502 from the load balancer.

12.9Common mistakes

MistakeWhat happensInstead
Raising limits in limits.conf for a serviceNothing changes: services don't use PAM login sessions.LimitNOFILE= in a drop-in.
Checking ulimit -n in your own shellYou see your shell's limit, not the service's./proc/<pid>/limits of the running process.
Raising one layer onlyThe next layer in is still the bottleneck.System, process and application, in that order (Figure 12.1).
Raising somaxconn but not the program's backlogThe program still asks for 511 or 128.Set the program's backlog (nginx listen … backlog=) too.
Copying tuning listsObsolete or harmful settings nobody can explain.Change what a counter or log proves you hit; comment why.
A new backend connection per requestEphemeral ports and TIME_WAIT pile up.Keep-alive connection pools.

✓Chapter summary

  • Every open file and network connection is a file descriptor; a proxy uses two per forwarded request.
  • File limits come in three layers: the system (fs.file-max, fs.nr_open), the process (RLIMIT_NOFILE, soft and hard) and the application (worker_connections, pool sizes). The smallest wins.
  • For services, set LimitNOFILE= in the unit; check the running process's /proc/<pid>/limits.
  • Finished handshakes wait in the accept queue, sized by the program's backlog capped by somaxconn. A full queue drops handshakes and looks like slowness; ss -lnt and nstat show it.
  • sysctl reads and sets kernel parameters; persist them in /etc/sysctl.d/, and change only what a measurement justifies.

Key terms

RLIMIT_NOFILE
The per-process limit on open file descriptors, with a soft (enforced) and a hard (ceiling) value.
Soft and hard limits
The enforced value of a resource limit, and the ceiling to which a non-root process may raise it.
EMFILE
Error 24, “Too many open files”: a process has reached its file descriptor limit.
Accept queue
The kernel's queue of fully established connections waiting for a program to call accept().
Listen backlog
The length of a listening socket's accept queue: the program's value, capped by net.core.somaxconn.
sysctl
The interface, and the command, for reading and setting kernel parameters under /proc/sys.
Ephemeral port
A temporary local port the kernel assigns to an outgoing connection.

Check your understanding

  1. Where do you look to find the open-file limit of the running PostgreSQL postmaster, and how many files it has open? recall

    Show answer

    /proc/<pid>/limits (the “Max open files” line) and ls /proc/<pid>/fd | wc -l, with the PID from systemctl show -p MainPID postgresql@16-main or pgrep. Not ulimit -n in your shell.

  2. Write a drop-in that gives stagedoor.service a soft limit of 8192 and a hard limit of 65536 open files. apply

    Show answer

    /etc/systemd/system/stagedoor.service.d/limits.conf with [Service] and LimitNOFILE=8192:65536; then sudo systemctl daemon-reload, sudo systemctl restart stagedoor, and check /proc/<pid>/limits.

  3. Explain why clients can report a successful connection to a server that's stuck with “Too many open files”. explain

    Show answer

    The kernel completes the TCP handshake and puts the connection in the listening socket's accept queue without involving the program. The client sees an established connection. Only when the program calls accept() does the connection need a file descriptor, and that's the step that fails, so the connection waits in the queue until the client gives up.

  4. After raising nofile in /etc/security/limits.conf and rebooting, nginx still logs “Too many open files”. Why, and what's the fix? debug

    Show answer

    limits.conf applies to login sessions through PAM; nginx is started by systemd, which uses the unit's LimitNOFILE=. Add a drop-in with LimitNOFILE=65536, set worker_rlimit_nofile (and enough worker_connections) in nginx's config, restart, and confirm in a worker's /proc/<pid>/limits.

  5. Design the checks for a load test before a big on-sale, so that limit problems show up a week early. design

    Show answer

    Generate more than the expected peak against a copy of the servers, and watch: nginx's error log for errno 24 and “worker_connections are not enough”; open descriptors per worker against its limit; TcpExtListenOverflows and ss -lnt queues; ss -s for TIME_WAIT and ephemeral port use; plus CPU, memory, disk and inode usage from Chapters 9–11. Fix each limit reached, then test again.

  6. Compare raising net.ipv4.ip_local_port_range with using keep-alive connections to the backend, for a proxy running out of ephemeral ports. compare

    Show answer

    Widening the range adds ports (at most about 64,000 per destination) and delays the problem. Keep-alive reuses a small pool of connections for many requests, so ports and TIME_WAIT entries barely grow with traffic, and it also saves handshakes and latency. Keep-alive fixes the cause; widening the range treats the symptom.
