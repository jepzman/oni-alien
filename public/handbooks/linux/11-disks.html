Disks, filesystems and inodes

Between a cloud volume and a file you can open sit three layers: a partition, a filesystem and a mount. This chapter takes them apart, shows how to find what filled a disk (including the case where the disk isn't full at all), and how to give a server more space without stopping it.

By the end you can

  • Describe the layers from block device to mounted filesystem, and inspect each one.
  • Find what's using space with df and du, and explain when they disagree.
  • Diagnose and fix inode exhaustion.
  • Write a safe /etc/fstab entry and check it before rebooting.
  • Grow a cloud volume, its partition and its filesystem, and explain what LVM adds.

Before you start

  • Chapter 3: inodes, mount points. Chapter 7: deleted-but-open files.
  • A Linux VM with sudo where you may create loop devices (Appendix C); sudo apt install cloud-guest-utils parted.

11.1From block device to file

A block device is storage the kernel reads and writes in fixed-size blocks: a physical disk, a cloud volume, a partition of either, or a file pretending to be a disk. Files only appear once a filesystem is laid over it and mounted into the tree.

lsblk shows the tree of block devices and partitions with their sizes and mount points; it's the first command on any unfamiliar machine. Device names depend on how the disk is attached: /dev/sda (SCSI and SATA), /dev/vda (virtio, common on KVM hosts such as Atlantica's), /dev/nvme0n1 (NVMe, how AWS attaches EBS volumes to current instances), with partitions numbered sda1, vda1, nvme0n1p1. Names can change between boots when disks are added, which is why fstab uses UUIDs (11.4).

11.2Partitions and filesystems

A partition table divides a disk into ranges; GPT is the modern format (the older MBR is limited to 2 TB). Cloud data volumes are often used whole, with no partition at all; boot disks always have one. parted, fdisk or sfdisk edit them.

A filesystem organises a block device into files and directories, with an inode table (Chapter 3) and data blocks. Two dominate on servers:

mkfs.ext4 /dev/vdb1 or mkfs.xfs /dev/vdb1 creates one, erasing whatever was there. A mount attaches it to a directory: sudo mount /dev/vdb1 /var/lib/stagedoor. Whatever was in that directory before is hidden, not deleted, until you unmount, a classic source of “where did my files go?”.

11.3What filled the disk?

Three commands answer it, and they answer different questions:

  • df -h asks the filesystem how many blocks are in use. It's the truth about space, including space held by deleted files still open (Chapter 7) and blocks reserved for root (ext4 keeps 5% by default so root can still log in and clean up).
  • du -xh --max-depth=1 /var | sort -h walks the directory tree and adds up the files it can see. -x stays on one filesystem. Repeat it one level down until you find the culprit; ncdu does the same interactively.
  • df -i asks how many inodes are in use. Every file and directory needs one, and on ext4 their number is fixed when the filesystem is created.

When df and du disagree, there are three usual reasons: deleted-but-open files (sudo lsof +L1), files hidden under a mount point, or a different filesystem than you think (du without -x wanders into other mounts). And when writes fail with “No space left on device” while df -h shows space, check df -i: an inode exhaustion. Millions of tiny files (caches, sessions, mail queues, thumbnails) can use every inode while using little space. du --inodes -x /var | sort -n | tail finds where they are.

Key idea

A filesystem can run out of two things: blocks and inodes. “No space left” with free space means df -i.

11.4Mounting at boot: /etc/fstab

Mounts you make by hand disappear at reboot. /etc/fstab lists the filesystems to mount at boot, one per line, six fields:

UUID=9024b159-9dd4-4d75-8f1e-7a99a652b68a  /var/lib/stagedoor  ext4  defaults,noatime,nofail  0  2
# what (by UUID)                           where               type  options                  dump  fsck order
  • Identify by UUID (from blkid or lsblk -f), never by device name: /dev/vdb today can be /dev/vdc after the next disk is attached.
  • nofail for anything that isn't needed to boot: if that volume is missing or broken, the machine still comes up and you can still log in. Without it, a detached data volume can leave a cloud server stuck in emergency mode, reachable only through the provider's serial console.
  • noatime stops a write on every read to update access times; a small, free win.
  • The last field orders boot-time checks: 1 for /, 2 for others, 0 for none (XFS ignores it).

Watch out: test fstab before you reboot

A typo in /etc/fstab is found at the next boot, when it's hardest to fix. After editing, run sudo findmnt --verify and sudo mount -a (which mounts everything listed that isn't mounted yet) and fix any error while you're still logged in. systemd turns each fstab line into a .mount unit, so also sudo systemctl daemon-reload.

11.5Growing a volume

On a cloud provider, making a disk bigger is a console click or an API call, and nowadays the instance doesn't even need to stop. But the click only grows the bottom layer of Figure 11.1. Each layer above needs its own step, all of them possible while the filesystem is mounted and in use:

Shrinking is another matter: XFS can't shrink at all, ext4 only unmounted, and cloud volumes generally can't be made smaller. To shrink, create a smaller volume and copy the data. Size data volumes with room to grow, and grow them before they're full rather than during an incident.

What LVM adds

The Logical Volume Manager (LVM) puts a flexible layer between partitions and filesystems. Disks or partitions become physical volumes; they're pooled into a volume group; and logical volumes, which you format and mount, are carved out of the pool. A logical volume can span several disks, be grown into free space in the group with lvextend --resizefs in one command, and be snapshotted. On physical servers like Stagedoor's at Atlantica, LVM is very useful: adding a second disk to a full volume group is how you grow without moving data. In the cloud, where volumes can be resized and snapshotted directly, many teams skip it for data volumes and use one filesystem per volume. Ubuntu Server's installer puts the root filesystem on LVM by default (/dev/ubuntu-vg/ubuntu-lv); sudo pvs, vgs and lvs show the layers.

11.6Swap files and other small jobs

Two more tasks you'll meet. A swap file (Chapter 10): sudo fallocate -l 8G /swapfile, sudo chmod 600 /swapfile, sudo mkswap /swapfile, sudo swapon /swapfile, then a line /swapfile none swap sw 0 0 in fstab. And disk health and speed: iostat -x 1 (from sysstat) shows each device's utilisation, queue and latency (%util near 100 and await in the tens of milliseconds mean the disk is the bottleneck, Chapter 9), and journalctl -k | grep -iE 'I/O error|ext4|xfs' shows errors the kernel saw.

11.7Cloud volumes

Cloud block storage (AWS EBS, Azure Managed Disks, Google Cloud Persistent Disk) is a network service that looks like a local disk. Three properties matter day to day. Performance is bought, not found: IOPS and throughput depend on the volume type and size (on AWS gp3, 3,000 IOPS baseline unless you pay for more, at the time of writing), so a slow disk may be a small or cheap one. Snapshots are cheap and incremental; take one before any resize or risky change. And instance-store or “local SSD” disks are fast but lose their data when the instance stops: use them only for things you can rebuild.

11.8Across distributions

On the RHEL family and Amazon Linux

The default filesystem is XFS, so inode exhaustion is rare and growing uses xfs_growfs /mount/point (it takes the mount point, not the device). RHEL's installer uses LVM for the root filesystem, as Ubuntu's does; Amazon Linux images don't. growpart comes from cloud-utils-growpart. On Ubuntu, growpart is in cloud-guest-utils, and cloud images grow their root partition automatically at first boot (cloud-init, Chapter 1), but not after later resizes.

11.9Lab: a disk in a file

Lab 11 · Partition, fill with inodes, grow

You'll make a disk out of a file (a loop device), partition it, create an ext4 filesystem with very few inodes, run out of inodes while most of the space is free, then grow the disk, partition and filesystem as you would a cloud volume, and check an fstab file without touching the real one. You need a Linux VM with sudo, parted and growpart (sudo apt install parted cloud-guest-utils); not a container. Cost: nothing. Clean-up: the last step. The UUIDs and device numbers on your machine will differ.

  1. Make a disk and partition it. A 200 MB file, attached as a block device (--partscan makes the kernel look for partitions on it), with one 99 MB partition and an ext4 filesystem limited to 2,048 inodes (-N), labelled thumbs: 
    mkdir -p ~/lab11 && cd ~/lab11
truncate -s 200M disk.img
dev=$(sudo losetup --find --show --partscan disk.img); echo "attached as $dev"
sudo parted -s "$dev" mklabel gpt mkpart data ext4 1MiB 100MiB
sudo mkfs.ext4 -q -N 2048 -L thumbs "${dev}p1"
sudo mkdir -p /mnt/lab11
sudo mount "${dev}p1" /mnt/lab11
    attached as /dev/loop0
    Now look at every layer: 
    lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS "$dev"; sudo blkid "${dev}p1"; df -h /mnt/lab11; df -i /mnt/lab11
    NAME       SIZE TYPE MOUNTPOINTS
loop0      200M loop 
`-loop0p1   99M part /mnt/lab11
/dev/loop0p1: LABEL="thumbs" UUID="9024b159-9dd4-4d75-8f1e-7a99a652b68a" BLOCK_SIZE="4096" TYPE="ext4" PARTLABEL="data" PARTUUID="4c4538ad-eafe-43e6-8eb6-562a595dc65e"
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0p1     95M   24K   88M   1% /mnt/lab11
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop0p1     2048    11  2037    1% /mnt/lab11
    The disk (200M), its partition (99M), the filesystem's type, label and UUID, its usable space (95M after ext4's own structures) and its inodes (2,048, 11 already used by the filesystem itself).
  2. Run out of inodes. Write up to 3,000 tiny “thumbnails”, stopping at the first failure: 
    sudo mkdir /mnt/lab11/thumbs; sudo chown "$USER": /mnt/lab11/thumbs
for i in $(seq 1 3000); do echo "thumbnail $i" > /mnt/lab11/thumbs/t$i.jpg || { echo "stopped at file $i"; break; }; done
df -h /mnt/lab11; df -i /mnt/lab11
    bash: line 2: /mnt/lab11/thumbs/t2037.jpg: No space left on device
stopped at file 2037
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop0p1     95M  8.1M   80M  10% /mnt/lab11
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop0p1     2048  2048     0  100% /mnt/lab11
    “No space left on device” with 80 MB available. The inodes are gone. Find where: 
    sudo du --inodes -x /mnt/lab11 | sort -n | tail -3; du -sh /mnt/lab11/thumbs
    1	/mnt/lab11/lost+found
2037	/mnt/lab11/thumbs
2039	/mnt/lab11
8.1M	/mnt/lab11/thumbs
    2,037 files in one directory, using only 8 MB. Clear them: rm -r /mnt/lab11/thumbs.
  3. Enlarge the disk, as a provider would, and tell the kernel: 
    truncate -s 400M disk.img
sudo losetup --set-capacity "$dev"
lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS "$dev"
    NAME       SIZE TYPE MOUNTPOINTS
loop0      400M loop 
`-loop0p1   99M part /mnt/lab11
    The disk is 400M; the partition is still 99M (Figure 11.2, step 1).
  4. Grow the partition (step 2): 
    sudo growpart "$dev" 1
    CHANGED: partition=1 start=2048 old: size=202752 end=204799 new: size=817119 end=819166
  5. Grow the filesystem (step 4). On a cloud server you'd do it while mounted, and normally that works: 
    sudo resize2fs "${dev}p1"
    On the test machine for this book, a sandboxed VM, the kernel refused the online resize (resize2fs: Permission denied to resize filesystem), so the filesystem was grown unmounted instead, which works everywhere: 
    sudo umount /mnt/lab11
sudo e2fsck -f -p "${dev}p1"
sudo resize2fs "${dev}p1"
sudo mount "${dev}p1" /mnt/lab11
df -h /mnt/lab11; df -i /mnt/lab11
    thumbs: 11/2048 files (9.1% non-contiguous), 1174/25344 blocks

    393 MB, and four times the inodes: ext4 keeps its inodes-per-space ratio when it grows.
  6. Check an fstab before trusting it. Write a test file with one good line (this filesystem, by UUID) and one bad one, and verify it with findmnt, which never touches /etc/fstab when given --tab-file: 
    uuid=$(sudo blkid -s UUID -o value "${dev}p1")
printf 'UUID=%s  /mnt/lab11  ext4  defaults,noatime,nofail  0  2\n' "$uuid" > fstab.test
printf 'UUID=00000000-1111-2222-3333-444444444444  /mnt/other  ext4  defaults  0  2\n' >> fstab.test
findmnt --verify --tab-file fstab.test; echo "exit status: $?"
    /mnt/other
   [E] unreachable on boot required target: No such file or directory
   [E] unreachable on boot required source: UUID=00000000-1111-2222-3333-444444444444

0 parse errors, 2 errors, 0 warnings
exit status: 1
    The good line passes. The bad one names a filesystem that doesn't exist and a mount point that doesn't exist, without nofail: in a real fstab, that's a server that doesn't finish booting.
  7. Clean up. 
    sudo umount /mnt/lab11
sudo losetup -d "$dev"
rm disk.img fstab.test

(2) Before step 4, run du -sh and df -h while a process holds a deleted file open on /mnt/lab11 (Chapter 3's Python one-liner), and see them disagree. (3) Run sudo tune2fs -l "${dev}p1" | grep -iE 'inode count|reserved block' and find ext4's 5% reserve for root.

11.10Common mistakes

MistakeWhat happensInstead
Checking only df -hInode exhaustion looks like a mystery.df -i too; alert on both.
Device names in fstabA new disk renames the old ones; the wrong disk is mounted, or none.UUIDs or labels.
No nofail on data volumesA missing volume stops the boot; the server is unreachable.nofail for anything not needed to boot.
Rebooting to test fstabErrors appear when you can't fix them.findmnt --verify and mount -a first.
Resizing the volume and stopping thereThe partition and filesystem stay the same size.growpart, then resize2fs or xfs_growfs.
Data and the operating system on one filesystemFilling one stops the other; logs fill the database's disk.Separate volumes for data that grows.
Resizing without a snapshotA mistake in the partition step loses the volume.Snapshot first; it's cheap.

✓Chapter summary

  • A block device is divided by a partition table, optionally pooled by LVM, formatted with a filesystem and mounted into the tree. lsblk shows the layers.
  • ext4 is Ubuntu's default with a fixed number of inodes; XFS is RHEL's default and allocates inodes as needed.
  • df counts used blocks, du adds up visible files, df -i counts inodes. Each answers a different question.
  • /etc/fstab mounts at boot: use UUIDs, nofail for data volumes, and verify before rebooting.
  • Growing a cloud volume is four steps: the provider, the partition (growpart), LVM if used, the filesystem (resize2fs, xfs_growfs). Snapshot first.

Key terms

Block device
Storage the kernel reads and writes in fixed-size blocks: a disk, a partition, a cloud volume or a loop device.
Partition table
The structure at the start of a disk that divides it into partitions; GPT is the modern format.
Filesystem
The on-disk structure of inodes, directories and data blocks that turns a block device into files.
Mount
Attaching a filesystem to a directory in the tree.
fstab
The file /etc/fstab, listing filesystems to mount at boot and their options.
Inode exhaustion
A filesystem running out of inodes, so no new files can be created although space is free.
LVM
The Logical Volume Manager, which pools disks into volume groups and divides them into resizable logical volumes.
Loop device
A block device backed by a file, used to treat a file as a disk.

Check your understanding

  1. Which command shows, in one view, the disks, their partitions, their sizes and where each is mounted? recall

    Show answer

    lsblk (add -f for filesystem types, labels and UUIDs).

  2. You've enlarged an EBS volume from 100 GB to 200 GB. lsblk shows nvme1n1 200G and nvme1n1p1 100G mounted at /data, which is XFS. Write the remaining commands. apply

    Show answer

    sudo growpart /dev/nvme1n1 1, then sudo xfs_growfs /data (XFS takes the mount point), then df -h /data to confirm. Both work while mounted.

  3. Explain why du -sh / can report much less than df -h /. Give two causes. explain

    Show answer

    du only adds up files it can reach by name; df counts every used block. Deleted files still held open by a process use blocks but have no name; files hidden underneath a mount point also can't be reached. (Ext4's reserved blocks and du skipping unreadable directories without sudo also contribute.)

  4. After adding a second data volume, a cloud server doesn't come back from a reboot, and the serial console shows “You are in emergency mode”. What's the likely cause, and how do you prevent it? debug

    Show answer

    An fstab line that can't be satisfied: a device name that changed (the new volume took the old one's name) or a volume that isn't attached, without nofail. Fix from the console (or by attaching the disk to another instance), then use UUIDs, add nofail for non-essential volumes, and verify with findmnt --verify and mount -a before every reboot.

  5. Design the disk layout for Stagedoor's new database server in the cloud. design

    Show answer

    A small root volume for the operating system. A separate data volume for PostgreSQL, mounted at /var/lib/postgresql by UUID with noatime, sized with room to grow and a volume type with enough IOPS; XFS or ext4 with enough inodes. Optionally a separate volume for write-ahead logs. Snapshots scheduled, and alerts on space and inodes for each filesystem.

  6. Compare using LVM and using whole cloud volumes directly for data. compare

    Show answer

    LVM can span disks, grow a logical volume and its filesystem in one step, and take LVM snapshots, which is valuable on physical servers where disks can't be resized. In the cloud, volumes can already be resized and snapshotted by the provider, so a filesystem directly on a volume is simpler, with one fewer layer to grow and debug. Use LVM where it solves a problem you have.
