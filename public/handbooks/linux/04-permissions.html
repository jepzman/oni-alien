Users, groups and permissions

Every file on a Linux server belongs to someone, and every process runs as someone. This chapter explains the small, strict rules the kernel uses to decide who may read, write and run what, how to grant exactly the access a program needs, and how to replace a shared root password with personal accounts and sudo.

By the end you can

  • Explain users, groups and IDs, and where Linux stores them.
  • Read and set permission bits on files and directories, in symbolic and octal form.
  • Predict the kernel's decision for any user, file and action.
  • Set up a shared directory where one program writes and another only reads, with setgid and umask.
  • Give people administrative access through sudo, and narrow it to single commands.

Before you start

  • Chapter 3: inodes and ls -l.
  • A Linux machine where you can use sudo: a VM or a container (Appendix C). The lab creates two users and removes them at the end.

4.1Users, groups and IDs

To the kernel, a user is a number: the user ID (UID). Names are for people. Every process runs with a UID, every file has an owner UID, and the permission check (4.3) compares the two.

A group is also a number, the GID, with a list of member users. Every user has one primary group (new files get it) and can belong to any number of supplementary groups. Groups are how you give several users, or several programs, the same access without giving each one separately.

Three kinds of user exist on every server:

  • root, UID 0. The kernel skips most permission checks for UID 0. It's not a person; it's a level of power.
  • System users for services: www-data (nginx on Ubuntu), postgres, sshd. They have low UIDs (below 1000 on Ubuntu), no password and usually no login shell (/usr/sbin/nologin). A service running as its own user can only damage what that user owns.
  • People, with UIDs from 1000 up, a home directory and a shell.

The databases are plain text files in /etc:

Table 4.1 · Where users and groups are stored
FileOne line perExample
/etc/passwduser: name, UID, primary GID, description, home, shell (readable by everyone; despite the name, no passwords)www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin

Read them with getent passwd name and getent group name rather than cat, because getent also asks any directory service the machine is connected to. id shows who you are right now: your UID, primary group and every group you're in.

Group changes and sessionsGroups are read when you log in. After adding yourself to a group, log out and in again (or run newgrp) before the new membership counts. Running services must be restarted for the same reason.

4.2Permission bits

Every inode carries nine permission bits: read, write and execute, for three classes of user. ls -l shows them after the file type:

The same three letters mean different things on a file and on a directory, and the directory meanings cause most surprises:

Table 4.2 · What r, w and x allow
BitOn a fileOn a directory
rread its contentslist the names in it
wchange its contentscreate, delete and rename entries in it, including other people's files
xrun it as a programenter it and reach things inside by name (“traverse”)

Two consequences are worth saying twice. Deleting a file is a change to the directory, not the file: if you can write to a directory, you can delete any file in it, whoever owns the file and whatever its own permissions say. That's what made Stagedoor's 777 directory dangerous. And to reach /var/lib/stagedoor/uploads/poster.jpg, a user needs x on every directory along the path, not only read on the file.

4.3How the kernel decides

When a process opens a file, the kernel compares the process's UID and groups with the file's owner and group, picks exactly one class, and checks only that class's bits:

Key idea

To debug “Permission denied”, ask three questions: which user and groups is the process running as, which class does that put it in for this file, and does every directory on the path allow it in?

namei -l /var/lib/stagedoor/uploads/poster.jpg answers the third question in one go: it lists the owner and permissions of every directory on the path, so a missing x stands out.

4.4Changing owners and permissions

chown user:group file changes the owner and group (only root may give a file away); chgrp group file changes only the group; chmod changes the bits, in either of two notations:

  • Symbolic: who (u, g, o, a), how (+, -, =), what (r, w, x). chmod g+r file, chmod o= file, chmod u=rwx,g=rx,o= dir. Good for small changes, because it leaves the other bits alone.
  • Octal: three digits, as in Figure 4.1. chmod 640 file. Good for setting everything at once, as scripts do.
Table 4.3 · Modes you'll use again and again
ModeSymbolicFor
644rw-r--r--ordinary files everyone may read: most of /etc
640rw-r-----files one service writes and one group reads
600rw-------secrets: private keys, .env files with passwords
755rwxr-xr-xprograms and directories everyone may enter
750rwxr-x---directories for one service and one group
2750rwxr-s---the same, and new files inherit the directory's group (4.5)
1777rwxrwxrwt/tmp: everyone may create, only owners may delete (4.5)
777rwxrwxrwxalmost never. If it “fixes” something, the real problem is ownership

chmod -R and chown -R change a whole tree. Be careful with chmod -R and octal modes: chmod -R 640 dir removes x from every directory inside, and nobody, not even the owner, can enter them any more. Use symbolic modes with a capital X (“execute only on directories, or where some x is already set”): chmod -R u=rwX,g=rX,o= dir.

4.5The special bits: setuid, setgid and sticky

Three more bits sit in front of the nine, as a fourth octal digit:

  • setuid (4000, shown as s in the owner's x) on a program makes it run as the file's owner, whoever starts it. /usr/bin/passwd is setuid root, so ordinary users can change their own password in /etc/shadow. Every setuid-root program is a door into root if it has a bug; you'll audit them in Chapter 18. Never set it on your own scripts.
  • setgid (2000, s in the group's x) on a directory makes new files and subdirectories inside it inherit the directory's group, instead of the creator's primary group. This is the tool for a directory shared between a writer and a reader, as the lab shows.
  • sticky bit (1000, t in the other's x) on a directory means that only a file's owner (or root) may delete or rename it, even though others may write to the directory. /tmp is 1777: everyone can create files there, nobody can delete anyone else's.

Stagedoor's /srv/uploads was 777, without even the sticky bit: any user on the machine could delete or replace any poster.

4.6umask: the default for new files

When a program creates a file, it asks for a mode (usually 666 for files, 777 for directories), and the kernel removes the bits set in the process's umask. A umask of 022 removes write for group and other: new files are 644, directories 755. A umask of 027 also removes everything for other: files 640, directories 750.

The umask belongs to the process and is inherited by its children, so a service's umask decides the permissions of every file it creates. umask with no argument shows your shell's; systemd sets a service's with UMask= (Chapter 6). For an app that writes files other programs shouldn't see, 027 is a good default.

4.7root and sudo

Logging in as root, especially with a shared password, has every problem a shared account has: nobody knows who did what, a leaver keeps the password, and every typo runs with unlimited power. The standard answer is sudo: people log in with their own accounts, and run individual commands as root when they need to, after proving who they are.

  • Who may do what is in /etc/sudoers and, better, in small files under /etc/sudoers.d/. On Ubuntu, members of the group sudo may run anything: %sudo ALL=(ALL:ALL) ALL.
  • Narrow rules name the exact command: tiago ALL=(root) /usr/bin/systemctl restart stagedoor lets Tiago restart the app and nothing else. Use full paths: the rule matches the program, not the name you type.
  • Edit with visudo (or check a file with visudo -cf file), never with a plain editor. A syntax error in sudoers can lock everybody out of sudo, and on a cloud VM without a root password that can mean rebuilding the machine.
  • Every use is logged, with the person's name, to /var/log/auth.log on Ubuntu (and the journal, Chapter 7). That's the accountability the shared root password couldn't give.
  • sudo -l shows what you may run; sudo -i opens a root shell when you really need several commands (prefer single commands, so each is logged).

Watch out: sudo rules that are root in disguise

A rule that allows an editor (sudo vim /etc/nginx/nginx.conf), a pager, tar, find or a script the user can modify gives full root, because each of these can start a shell or write any file. Allow specific, non-interactive commands; for editing files as root, use sudoedit, which edits a copy as you and writes it back.

4.8Access control lists

Owner, group and other is sometimes too coarse: you want one more user, or a second group, to read a directory without changing its owner or group. ACLs (access control lists) add named entries to an inode: setfacl -m u:tiago:rx dir gives Tiago read and enter on one directory. getfacl dir shows every entry; ls -l marks files that have an ACL with a + after the permission bits.

ACLs have a mask entry, which caps what the named entries and the group may have; when an ACL seems not to work, check the mask first. A default ACL on a directory (setfacl -d -m …) is copied to new files created in it.

Use ACLs sparingly. They're invisible in a normal ls -l apart from the +, some backup and copy tools drop them, and a server whose access only makes sense with getfacl is hard to review. When a group would do, use a group.

On the RHEL family

SELinux checks every access a second time, after the permission bits, against rules about what each kind of program may touch. nginx may read files labelled as web content and not, say, a user's home directory, even if the bits allow it. A “Permission denied” that survives a correct ls -l on RHEL is usually SELinux; ausearch -m avc -ts recent shows the denial. Chapter 18 covers it.

4.10Lab: fix the uploads directory

Lab 4 · From 777 to exactly enough

You'll recreate Stagedoor's world-writable uploads directory, abuse it as another user, then fix it so the app writes, nginx reads and nobody else gets in; then grant one extra reader with an ACL and one narrow sudo rule. You need a Linux VM or container where you can use sudo (Appendix C); on Ubuntu, the user www-data already exists. For the ACL step: sudo apt install acl. Cost: nothing. Clean-up: the last step removes everything. Outputs come from a user called tiago; your IDs, names and times will differ.

  3. Abuse it. As Marco, delete the app's poster and put your own in its place: 
    sudo -u marco rm /srv/lab4/uploads/poster-101.jpg

    No error. Marco can't write to the app's file (it's rw-rw-r--, and he's “other”), but he can write to the directory, so he can delete the file and create a new one with the same name (Table 4.2). nginx would now serve his file as venue 101's poster.
  4. Fix it. Remove both files, then give the directory to the app, with nginx's group, setgid, and nothing for anyone else; write a poster as the app with umask 027: 
    sudo rm /srv/lab4/uploads/poster-101.jpg /srv/lab4/uploads/poster-102.jpg

sudo ls -l /srv/lab4/uploads
    drwxr-s--- 2 stagedoor www-data 4096 Nov 27 08:05 /srv/lab4/uploads
total 4
-rw-r----- 1 stagedoor www-data 7 Nov 27 08:05 poster-101.jpg
    The directory is rwxr-s---: the app may do anything, the group www-data may list and enter, others nothing; the s is setgid. The new file got the group www-data from the directory, and mode 640 from the umask. (You needed sudo for the second ls: you're now “other” for this directory, too.)
  5. Test every user against Figure 4.2. nginx reads, nginx can't write, Marco can't even look: 
    sudo -u www-data cat /srv/lab4/uploads/poster-101.jpg

  6. Break it on purpose: without setgid. Remove the setgid bit and write another poster: 
    sudo chmod g-s /srv/lab4/uploads

✓Chapter summary

  • Users and groups are numbers (UID, GID) with names in /etc/passwd and /etc/group. Services get their own system users.
  • Nine permission bits give read, write and execute to the owner, the group and everyone else. On directories, w means create and delete entries, and x means enter.
  • The kernel picks exactly one class for a process (owner, group or other) and checks only that class. Root skips the check.
  • setgid on a directory makes new files inherit its group; the sticky bit stops people deleting each other's files; the umask sets the default mode of new files.
  • A shared directory for a writer and a reader: owner = writer, group = reader, mode 2750, writer's umask 027.
  • Personal accounts and sudo replace a shared root password; narrow rules name exact commands; every use is logged.
  • ACLs add named users or groups when a single group isn't enough; use them sparingly.

Key terms

User
An identity the kernel knows by its user ID (UID); processes run as a user and files are owned by one.
UID
The number that identifies a user to the kernel; 0 is root.
Group
A numbered set of users that can be given access together.
Permission bits
Read, write and execute for a file's owner, its group and everyone else.
setgid (directory)
A directory bit that makes new entries inherit the directory's group.
Sticky bit
A directory bit that lets only a file's owner (or root) delete or rename it.
umask
A per-process mask of permission bits removed from every new file and directory.
sudo
A program that lets permitted users run commands as root (or another user), with logging, according to rules in sudoers.
ACL
An access control list: extra permission entries for named users and groups on a file or directory.

Check your understanding

  1. Write rwxr-x--- and rw------- in octal, and say what each is typically used for. recall

    Show answer

    750: a directory (or program) for its owner, readable and enterable by one group, closed to everyone else. 600: a secret only its owner may read and write, such as a private key or a file with a password.

  2. A file is -rw----r-- 1 rafaela ops. Rafaela tries to read it. Is she allowed, and why? apply

    Show answer

    Yes: she's the owner, so only the owner bits count, and they include r. (If the owner bits had been ---, she would be denied even though “other” has r, because only one class is checked.)

  3. Why can a user delete a file they don't own and can't write to? explain

    Show answer

    Deleting removes a name from the directory, so it needs write (and execute) permission on the directory, not on the file. Without the sticky bit, anyone who can write to the directory can delete any entry in it.

  4. nginx returns 403 for /var/lib/stagedoor/uploads/plan-7.pdf, but sudo cat of the file works. List what you'd check, in order. debug

    Show answer

    sudo cat proves nothing, because root skips the checks. Check which user nginx's workers run as (ps -o user= -C nginx: the master is root, the workers that open files are www-data); run namei -l on the path to see that www-data can traverse every directory; check the file's group and mode (probably created without the setgid directory, so its group is stagedoor, or with a bad umask); test with sudo -u www-data cat. On RHEL, also check SELinux denials.

  5. Design permissions for /etc/stagedoor/stagedoor.env, which holds the database password: the app must read it, the deploy process (running as a person with sudo) must update it, nginx must not see it. design

    Show answer

    Owner root, group stagedoor, mode 640; the directory /etc/stagedoor owned root:stagedoor, mode 750. The app (user stagedoor) reads through the group but can't change it; deploys update it with sudo; nginx (www-data) is “other” and gets nothing. (Chapter 6 loads it with systemd's EnvironmentFile=.)

  6. Compare giving Tiago read access to the uploads by adding him to www-data with giving it through an ACL. compare

    Show answer

    Joining www-data gives him everything nginx's group can read, everywhere on the machine, which is broader than needed but visible in /etc/group. An ACL gives exactly this directory and nothing else, but it's less visible (only a + in ls -l) and easy to forget. For one person and one directory, the ACL is the narrower choice; for a role several people share, make a dedicated group.
