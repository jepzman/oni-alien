Containers are Linux

A container isn't a small virtual machine. It's an ordinary Linux process that the kernel shows a different view of the system: its own process numbers, its own network, its own root filesystem, and limits on what it may use. This chapter builds one by hand from the pieces you already know, then shows what that means for the containers you'll run: why PID 1 matters, where image layers come from, and how isolated a container really is.

By the end you can

  • Explain a container as namespaces, cgroups and a root filesystem, and build one with unshare.
  • Explain image layers with overlayfs, including how deletions work.
  • Write a container entrypoint that receives signals and doesn't leave zombies.
  • Find a container's process, limits and kernel messages from the host.
  • Compare containers and VMs for isolation, and choose between them.

Before you start

  • Chapter 5 (PID 1, signals, zombies), Chapter 10 (cgroups, OOM), Chapter 13 (network namespaces).
  • A Linux VM with sudo and Docker (sudo apt install docker.io) (Appendix C).

The same week Leonor asks a question that sounds simple: if each service runs in its own container, are they as separate as if each had its own server? Could the payment service share a machine with everything else?

19.1A container is a process

Run ps on a machine with containers and you'll find their programs in the list, next to everything else, because that's what they are: processes, started by the container runtime, running on the host's kernel. What makes them “containers” is three kernel features applied to them:

  • Namespaces change what a process can see: its own process IDs, mounts, network stack, hostname and users.
  • cgroups change what it can use: CPU, memory, number of processes, I/O (Chapters 9 and 10).
  • A root filesystem of its own, usually assembled from image layers by overlayfs, so it sees a whole distribution's files without a disk of its own.

Add security settings (dropped capabilities, a system-call filter, an AppArmor or SELinux profile: Chapter 18's list) and that's a container. Docker, Podman, containerd and Kubernetes all assemble the same kernel pieces.

Every process has a namespace of each type; ls -l /proc/<pid>/ns/ shows which, and two processes in the same container point to the same ones. unshare starts a program in new namespaces; nsenter runs a program inside an existing process's namespaces, which is what docker exec does, and a handy debugging trick: sudo nsenter -t <pid> -n ss -tlnp lists a container's listening sockets with the host's tools.

19.3cgroups: the limits

A container's limits are cgroup files (Chapter 10). docker run --memory 64m writes 64 MB into the memory controller's limit for the container's cgroup; --cpus 0.5 sets a CPU quota, --pids-limit caps the number of processes. When a container goes over its memory limit, the kernel's OOM killer acts inside that cgroup only, exactly as in Lab 10, and the container exits with 137. From the host, cat /proc/<pid>/cgroup shows a process's cgroup path, and the files under /sys/fs/cgroup/ show its limits and usage.

There are two versions of the cgroup interface. cgroup v2, one unified tree with files like memory.max, is the default on Ubuntu 22.04+, Debian 11+, RHEL 9 and Amazon Linux 2023. Older systems (and this book's test machine) use v1, with a tree per controller and files like memory.limit_in_bytes. Same idea, different file names.

19.4Images and layers

A container image is a stack of read-only layers, each a set of files produced by one step of the build (a COPY, a RUN apt-get install), plus metadata such as the command to run. When a container starts, the runtime stacks the layers with overlayfs and adds one writable layer on top:

Two practical consequences. Deleting a file in a later build step doesn't shrink the image (the earlier layer still contains it, hidden by a whiteout), which is why Dockerfiles install and clean up in one RUN, and why a secret copied into an early layer stays in the image even if a later step deletes it. And data a container must keep (uploads, a database) goes on a volume, a directory mounted from outside the overlay.

19.5PID 1 in a container

The first process in a PID namespace is PID 1 there, and the kernel treats PID 1 specially (Chapter 5):

  • No default signal actions. A signal that PID 1 hasn't installed a handler for is ignored, even SIGTERM. A program that would normally die on SIGTERM does nothing as PID 1; the runtime waits its stop timeout (10 seconds for docker stop, 30 for Kubernetes by default) and sends SIGKILL: exit status 137, requests in flight lost.
  • Orphans are adopted by PID 1, which must reap them. An application never written to be an init system doesn't, and finished orphans pile up as zombies.

Three habits fix both:

  1. Exec form in the Dockerfile: CMD ["python3", "/app/checkout.py"], not CMD python3 /app/checkout.py. The shell form runs /bin/sh -c "…", so PID 1 is a shell that neither forwards signals nor exits; the exec form makes your program PID 1. In an entrypoint script, end with exec "$@" (Chapter 5).
  2. Handle SIGTERM in the program: as PID 1 it's the only way it reacts at all.
  3. A tiny init as PID 1 when the program starts children: docker run --init (or tini in the image) runs a minimal init that forwards signals to your program and reaps orphans.

Key idea

In a container, your program is PID 1. Make it the program (exec form), make it handle SIGTERM, and give it an init if it has children.

19.6How isolated is a container?

All containers on a host share its kernel, so the kernel's system-call interface, hundreds of calls wide, is the boundary between them. A kernel vulnerability, a container run with --privileged, or a sensitive host path mounted in (the Docker socket, /) can let a process escape to the host. A VM's boundary is narrower: a hypervisor emulating a handful of virtual devices. That difference is the answer to “are containers as separate as servers?”: they're good isolation between cooperating workloads you trust roughly equally, and weaker isolation between strangers.

Between the two sit sandboxed runtimes: gVisor answers system calls in a user-space kernel; Kata Containers and Firecracker run each container or function in a lightweight VM. AWS Lambda and Fargate use Firecracker, and so, as Lab 1 noticed, did the machine this book was tested on. Whatever the runtime, the hardening from Chapter 18 applies inside: run as a non-root user, drop capabilities, read-only root filesystem, no --privileged.

19.7Across distributions

On the RHEL family

RHEL ships Podman instead of Docker: the same command-line options and image format, no central daemon, and rootless containers by default, using user namespaces so that root in the container is your own user on the host. It can also generate systemd units for containers (Quadlet), tying this chapter to Chapter 6. Ubuntu packages both Docker (docker.io) and Podman. Kubernetes uses containerd or CRI-O directly; Handbook 4 picks up from here.

At Stagedoor: an image that stops in a third of a second

Tiago's Dockerfile switches to the exec form with --init semantics built in: the image installs tini as its entrypoint, so the app receives SIGTERM directly and the PDF helpers' orphans are reaped. docker stop now takes under a second, the load test ends with no failed checkouts, and the zombie count stays at zero. The image runs as a non-root user, with a read-only root filesystem and uploads on a volume, following Chapter 18.

Leonor's question gets a written answer: containers on one host share its kernel, so they're separated well enough for Stagedoor's own services, which trust one another roughly equally, but the payment service, which handles card data, should not share a kernel with anything it doesn't have to. When Stagedoor moves to AWS, it will get its own VMs or Fargate tasks, each in its own Firecracker micro-VM. Handbook 4 tells the Kubernetes side; Handbook 5 the infrastructure.

✓Chapter summary

  • A container is a group of ordinary processes given their own view (namespaces), limits (cgroups) and root filesystem, on the host's shared kernel.
  • unshare and nsenter create and enter namespaces; containers are built from the same pieces.
  • Images are read-only layers stacked by overlayfs under a writable layer; deletions are whiteouts; data that matters goes on volumes.
  • Your program is PID 1: no default signal actions, and it must reap orphans. Use exec form, handle SIGTERM, add an init.
  • Containers share a kernel: good isolation between trusted services, weaker than VMs between strangers. Harden them like services (Chapter 18).

Key terms

Container
A process (or group of processes) isolated with namespaces, limited with cgroups and given its own root filesystem, on a shared kernel.
Namespace
A kernel feature that gives processes their own view of one kind of system resource, such as process IDs or the network.
Container image
A stack of read-only filesystem layers plus metadata, from which containers are started.
overlayfs
A filesystem that stacks read-only lower directories under a writable upper one and presents the merged result.
Whiteout
A marker in an upper overlay layer that hides a file present in a lower layer.
Exec form
A Dockerfile CMD or ENTRYPOINT written as a JSON list, run directly rather than through /bin/sh -c.
Init process
The process running as PID 1, responsible for handling signals and reaping orphaned children.

Check your understanding

  1. Which three kernel features make a process a container? recall

    Show answer

    Namespaces (its own view of PIDs, mounts, network, hostname, IPC, users), cgroups (resource limits and accounting) and its own root filesystem (usually overlayfs layers), plus security restrictions such as dropped capabilities and system-call filters.

  2. Rewrite CMD gunicorn app:app --bind 0.0.0.0:8000 so the container stops gracefully. apply

    Show answer

    CMD ["gunicorn", "app:app", "--bind", "0.0.0.0:8000"], so gunicorn is PID 1 and receives SIGTERM (gunicorn handles it gracefully). If it starts subprocesses that may be orphaned, add an init: ENTRYPOINT ["tini", "--"] or docker run --init.

  3. Explain why deleting a 500 MB file in a later Dockerfile step doesn't make the image smaller. explain

    Show answer

    Each step creates a new layer; the file is still in the earlier layer, and the deletion only adds a whiteout in the later one that hides it. The image contains every layer. Remove files in the same RUN step that created them, or use a multi-stage build that copies only what's needed into the final image.

  4. A container's log shows the app handling SIGTERM when you run it with docker run in the foreground and press Ctrl+C, but docker stop always takes 10 seconds. What's different? debug

    Show answer

    Ctrl+C sends SIGINT, which the app (or the shell in front of it) may handle; docker stop sends SIGTERM to PID 1. Most likely PID 1 is a shell (shell-form CMD or a wrapper script without exec) that ignores SIGTERM as PID 1 and doesn't forward it, or the app handles SIGINT but not SIGTERM. Check docker exec … cat /proc/1/cmdline.

  5. Design how Stagedoor should run the payment service and the public web app when it moves to containers. design

    Show answer

    Separate kernels for different trust levels: the payment service on its own VMs or in a sandboxed runtime (Fargate's Firecracker micro-VMs, or Kata/gVisor nodes), not on the same container hosts as public-facing services. Every container: non-root user, dropped capabilities, read-only root filesystem, resource limits, exec-form entrypoint with an init, secrets injected at run time, images scanned and pinned. Network policies between services (Handbook 4).

  6. Compare a container and a VM for running a nightly batch job from a vendor you don't fully trust. compare

    Show answer

    A container starts in a second and is cheap, but shares the host's kernel, so a kernel exploit or misconfiguration could reach other workloads. A VM costs more and starts more slowly, but its boundary is the hypervisor, much narrower than the system-call interface. For untrusted code, a VM (or a micro-VM sandbox) is the safer choice; a hardened container on a dedicated host is a middle ground.
