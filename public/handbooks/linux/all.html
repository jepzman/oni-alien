What a Linux server is

A server is just a computer that nobody sits in front of, and most of the ones in the cloud run Linux. This chapter separates the parts that word covers (the kernel, the distribution, the programs around them), follows a machine from power-on to a login prompt, and gives you a calm, read-only way to find out what you've been handed.

By the end you can

  • Explain what the kernel does and what the distribution adds around it.
  • Say which distribution and release a server runs, and until when it gets security updates.
  • Describe the boot sequence from firmware to PID 1, and what changes on a cloud VM or in a container.
  • Explain what a cloud image and cloud-init do at first boot.
  • Inventory an unfamiliar server without changing anything on it.

Before you start

  • A terminal on any Linux machine: a container, WSL on Windows, or a small VM. Appendix C shows how to get one.
  • You can type a command and press Enter. Chapter 2 covers the shell properly.

1.1Kernel, userland, distribution

“Linux” means three different things depending on who says it, and it helps to keep them apart from the start.

Strictly, Linux is a kernel: the one program on the machine that talks to the hardware directly. It starts first, stays in memory until the machine shuts down, and does five jobs for everything else:

  • Processes: it starts programs, gives each a share of the CPUs, and stops them (Chapter 5, Chapter 9).
  • Memory: it hands out memory, keeps each program's memory private from the others, and decides what to do when it runs out (Chapter 10).
  • Files: it turns blocks on a disk into files and directories (Chapter 3, Chapter 11).
  • Network: it sends and receives packets and keeps track of connections (Chapter 13).
  • Devices and permissions: it drives disks, network cards and consoles, and checks who may do what (Chapter 4).

Programs never touch the hardware themselves. When a program wants to open a file, send a packet or start another program, it asks the kernel with a system call: a numbered request such as openat, read, write or execve. The kernel checks the request, does the work and returns a result or an error. Everything outside the kernel, from the shell to your app, is called userland (or user space).

A kernel on its own can't do anything useful for you: there's no shell to type into and no program to start your web server. A distribution (a “distro”) packages the Linux kernel together with a userland (thousands of programs and libraries, mostly from the GNU project and others), a package manager to install and update them (Chapter 8), and a promise to ship security fixes for a stated number of years. Ubuntu, Debian, Red Hat Enterprise Linux and Amazon Linux are distributions. When people say “a Linux server”, they mean a machine running one.

Key idea

The kernel does the work; programs only ask. Almost every problem in this book, from “permission denied” to “too many open files”, is the kernel refusing or running out of something a program asked for.

Kernel space, user spaceThe CPU itself enforces the split: kernel code runs in a privileged mode that can touch hardware and any memory; user programs run in a restricted mode and can't. A bug in a program crashes the program. A bug in the kernel can crash the machine.

1.2Distributions and releases

The distributions you'll meet on cloud servers differ in their package format, their defaults and, most importantly for a server, how long each release is supported. A release is a numbered version of the whole distribution (Ubuntu 24.04, Debian 12) whose packages stay stable: during its support period you get security fixes and bug fixes, not new major versions that might change behaviour under you. When support ends, the fixes stop, and every new vulnerability stays open on that machine for good.

LTS means long-term support: a release meant to be run for years, as servers are. Ubuntu also publishes releases between LTS versions (24.10, 25.04) with nine months of support each; they're fine on a laptop and wrong on a server, because you'd have to upgrade twice a year.

Watch out: end of support is a date, not a feeling

A server past its release's end of support keeps working, which is exactly why it's dangerous: nothing breaks, so nobody notices that security fixes stopped. Write the end-of-support date on every server's card the day you meet it, and plan the upgrade or rebuild a few months before (Chapter 8).

Two files answer “what is this?” on any modern distribution. /etc/os-release names the distribution and release; uname -r prints the running kernel's version. They're different things: Ubuntu 24.04 ships a 6.8 kernel, can be moved to newer ones, and the kernel running can be older than the one installed if nobody has rebooted since the last kernel update.

1.3How a machine boots

Knowing the boot sequence pays off the first time a server doesn't come back after a reboot: each stage hands over to the next, and the question is always which hand-over failed.

  1. Firmware. The machine's built-in firmware (UEFI on modern machines, BIOS on old ones) checks the hardware and looks for something bootable on a disk.
  2. Bootloader. GRUB, on most distributions, loads two files from /boot into memory: the kernel (vmlinuz-…) and the initramfs, a small temporary filesystem with just enough drivers to find the real disk.
  3. Kernel. The kernel starts, detects hardware, uses the initramfs to find and mount the root filesystem (the one mounted at /), and throws the initramfs away.
  4. PID 1. The kernel starts exactly one program itself: /sbin/init, which becomes process number 1. On Ubuntu, Debian, RHEL and Amazon Linux, that's systemd. Every other process on the machine is started by PID 1 or by one of its descendants (Chapter 5).
  5. Services. systemd starts what's configured to run at boot, in dependency order: mounting disks, the network, SSH, then services such as nginx and your app (Chapter 6).

If a program was started by hand (someone logged in and typed a command) rather than as a service, step 5 doesn't know about it, and after a reboot it simply isn't running. That's one of the most common surprises on hand-built servers, and it's waiting for Stagedoor in this chapter's story.

1.4Cloud images and cloud-init

Nobody installs Linux from a USB stick on a cloud server. You pick an image: a ready-made copy of a disk with a distribution already installed (an AMI on AWS, an image on Azure and Google Cloud). Launching a VM copies the image to a new disk and boots it. Ubuntu, Debian, Red Hat and Amazon publish official images for every release and refresh them every few weeks with the latest updates.

An image is the same for everyone, so something must turn it into your server at first boot: set its hostname, create users, install your SSH key, maybe install packages and start your app. On nearly every cloud image, that something is cloud-init. It runs as a set of services early in boot (stage 5 of Figure 1.2), asks the cloud's instance metadata service (a web service only the VM can reach, at 169.254.169.254) for the user data you supplied when you launched the VM, and applies it. User data is usually a shell script or a YAML file that starts with #cloud-config:

user-data.yamlcloud-config (an illustration; Chapter 18 builds a tested one)

#cloud-config
hostname: door-4
users:
  - name: rafaela
    groups: [sudo]
    shell: /bin/bash
    ssh_authorized_keys:
      - ssh-ed25519 AAAAC3Nza…rafaela-laptop
package_update: true
packages: [nginx]
runcmd:
  - [systemctl, enable, --now, nginx]

Read it top to bottom: name the machine, create one personal user who can use sudo and log in with one key, update the package lists, install nginx and start it. cloud-init runs most of this only on the first boot of a new instance; rebooting doesn't repeat it. Its log, /var/log/cloud-init-output.log, is the first place to look when a new server didn't come up the way you described.

Try it locallyMultipass, a free tool for Ubuntu VMs on a laptop, accepts the same file: multipass launch --cloud-init user-data.yaml (Appendix C).

This is the first glimpse of an idea the whole book works towards: a server described in a file can be rebuilt in minutes, while a server built by hand over three years can only be repaired, carefully. Chapter 18 writes a hardened baseline as cloud-init, and Chapter 21 rebuilds one of Stagedoor's servers from a script.

1.5Finding out what you've been handed

The first hour on an unfamiliar server should change nothing. Every question below has a read-only command, and most of the answers come from two places the kernel keeps up to date: /proc and /sys. They look like directories full of files, but nothing in them is stored on a disk; the kernel generates each “file” when you read it (Chapter 3).

Watch out: “just a quick restart”

On a server you don't understand yet, a reboot is a change, not a check. If anything was started by hand, it won't come back. Do the inventory first, find out how each running program was started, and reboot only when you know what to expect.

1.6Pets and cattle

Operations people describe two ways of looking after servers. A pet server has a name, was built by hand, and is nursed back to health when it's ill, because nobody knows exactly how to make another one. Cattle are numbered, built from a description (an image, cloud-init, a script), and replaced when they misbehave. The terms are blunt, but the difference is real: a pet holds knowledge that exists nowhere else, and losing it loses the knowledge too.

Almost every company starts with pets, and that's fine. The way out isn't to throw them away but to move the knowledge out of the machine and into writing, one piece at a time:

  1. Inventory: what's on it, what runs, who logs in (this chapter).
  2. Understand: for each running program, how it starts, where its config and data live, where it logs (Chapters 3–8).
  3. Fix in place, writing each fix down as a command you could run again (Chapters 4–16).
  4. Script it: turn the written-down commands into a script or cloud-init (Chapters 17–18).
  5. Rebuild a copy from the script, test it, and replace the pet (Chapter 21).

1.7Across distributions

Everything in this chapter works the same on every mainstream distribution: the kernel, the boot sequence, /proc, systemd and cloud-init. What changes is mostly the package manager and where a few configuration files live, which Appendix B lists side by side.

On the RHEL family

Red Hat Enterprise Linux and its rebuilds (Rocky Linux, AlmaLinux) use .rpm packages and dnf, and turn on SELinux by default, an extra permission layer that Chapter 18 introduces. The release is in /etc/os-release as on Ubuntu, and also in /etc/redhat-release. Ten years of support per major version is why enterprises like it, and why you'll meet very old ones.

On Amazon Linux

Amazon Linux 2023 is based on Fedora, uses dnf, and is updated in place: instead of upgrading to a new release every few years, you move the machine to a newer, versioned snapshot of its package repository. Its older sibling, Amazon Linux 2, is at the end of its support period: check the date before building anything new on it. AWS's own tools come preinstalled, which is handy on EC2 and irrelevant elsewhere.

Key terms

Kernel
The program that runs the hardware and provides processes, memory, files, networking and permissions to everything else.
System call
A request from a program to the kernel, such as opening a file or starting a program.
Userland
Everything outside the kernel: init, shells, utilities, libraries and applications.
Distribution
A kernel, a userland and a package manager released and supported together, such as Ubuntu or Debian.
Release
A numbered version of a distribution whose packages receive fixes, not major changes, until its end of support.
LTS
Long-term support: a release meant to be run for years, with security updates for all of that time.
UEFI
The firmware on modern machines that checks hardware and starts the bootloader.
initramfs

Check your understanding

  1. Which of these is the kernel's job, and which is the distribution's: scheduling processes on CPUs, shipping a security fix for OpenSSL, deciding whether a program may open a file, providing ls? recall

    Show answer

    Kernel: scheduling processes and checking file permissions. Distribution: shipping the OpenSSL fix (as an updated package) and providing ls (part of the userland, from GNU coreutils). The distribution also ships the kernel itself as a package.

  2. uname -r prints 5.15.0-91-generic, and ls /boot shows vmlinuz-5.15.0-91-generic and vmlinuz-5.15.0-131-generic. What does that tell you, and what would you do? apply

    Show answer

    A newer kernel (131) is installed but the machine is still running the old one (91), so the kernel's security fixes since then aren't active. Plan a reboot, after checking that everything that should run is started as a service and will come back.

  3. Why does a program started by hand with nohup not come back after a reboot, while nginx does? explain

    Show answer

    After a reboot, the only programs that start are the ones PID 1 (systemd) is configured to start, plus their descendants. nginx is installed as a systemd service enabled at boot; the hand-started program was started by a person's shell, which no longer exists, and nothing records that it should run.

  4. A new VM launched from an Ubuntu image with your user data has no user rafaela. Where do you look first, and what might have gone wrong? debug

    Show answer

    Look at cloud-init's logs: /var/log/cloud-init-output.log and /var/log/cloud-init.log (and cloud-init status --long). Common causes: the file didn't start with #cloud-config, so it wasn't read as cloud-config; a YAML indentation error; or the user data was added to an instance that had already booted, and cloud-init only applies it at first boot.

  5. You've inherited a server nobody understands, and you've been asked to “tidy it up”. Write the first five things you'd do, in order. design

    Show answer

    One reasonable order: (1) record the release and its end of support, the kernel and uptime; (2) list running services and all running processes and find what was started outside systemd; (3) list listening ports and who logs in; (4) for each running program, find its config, data and logs; (5) write it all down, with the problems found, before changing anything. Only then start fixing, one written-down change at a time.

  6. Compare an Ubuntu LTS release with a RHEL major version as a choice for a server you expect to run for six years. compare

    Show answer

    Ubuntu LTS gives five years of standard security updates (more with Ubuntu Pro), so a six-year server either needs Pro or an upgrade along the way. A RHEL major version gets ten years, covering the whole period, at the cost of a subscription (or using a rebuild such as Rocky or AlmaLinux) and older package versions near the end. Either works; what matters is knowing the date and planning for it.

2.1What the shell does with a line

The shell is an ordinary program (on servers, usually bash) whose job is to read a line of text, turn it into one or more programs with arguments, run them, and wait. Most surprises come from not knowing that the shell rewrites the line before anything runs.

Two consequences follow. First, a program can't tell whether you typed *.log or the list of names the shell turned it into. Second, when a command does something odd, the question is usually “what arguments did it actually get?”, and echo is the quickest way to find out: put echo in front of the command, and the shell prints the expanded line instead of running it.

bash, sh, dashYour login shell on a server is usually bash. /bin/sh is a simpler shell for scripts: on Ubuntu and Debian it's dash, which lacks some bash features. A script that starts with #!/bin/sh but uses bash syntax works on one distribution and fails on another.

2.2Commands, options and arguments

After splitting, the first word is the command and the rest are its arguments. By convention, arguments starting with - are options: short ones are a single letter and can be combined (ls -l -a is ls -la); long ones start with -- (ls --all). Some options take a value: head -n 5, sort --key=2. A lone -- means “no more options”, which matters when a file name starts with a dash: rm -- -oops.txt.

The command itself is one of three things, and type tells you which:

  • A builtin, part of the shell itself: cd, echo, export, type. It has to be: cd changes the shell's own current directory, which a separate program couldn't do.
  • An alias or function defined in your shell's startup files, such as Ubuntu's ll for ls -alF.
  • A program: a file somewhere on disk. The shell looks for it in each directory listed in the PATH variable, in order, and runs the first match.
type cd ll grep         # cd is a shell builtin · ll is aliased to `ls -alF' · grep is /usr/bin/grep
echo "$PATH"            # /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin…

Watch out: PATH is not the same everywhere

Your interactive shell's PATH is set by its startup files. Programs started by cron or as services get a much shorter one. A command that works when you type it can fail with “command not found” at 03:00. Stagedoor meets exactly this in Chapter 6; the fix is to use full paths, or set PATH explicitly, in anything that runs unattended.

2.3Standard streams and redirection

Every program starts with three open channels, called standard streams, each identified by a small number, its file descriptor:

  • 0, standard input (stdin): where it reads input from. By default, your keyboard.
  • 1, standard output (stdout): where it writes its results. By default, your terminal.
  • 2, standard error (stderr): where it writes errors and progress messages. Also your terminal, which is why the two look the same until you separate them.

The split between 1 and 2 is what makes pipelines work: results flow on to the next program, while errors still reach you. Redirection tells the shell to connect a stream to a file instead:

2.4Pipes and the small tools

A pipe connects one program's standard output to the next one's standard input. All the programs in a pipeline run at the same time; each reads what the previous one writes, as it's written. That's why grep error huge.log | head -5 returns at once: when head has its five lines it exits, and grep is stopped the next time it writes.

2.5Expansion and quoting

Step 3 of Figure 2.1 is where most shell bugs live. Before running anything, bash performs several expansions on each word:

  • Tilde: ~ becomes your home directory.
  • Variables: $name or ${name} becomes the variable's value. $? (last exit status), $$ (the shell's process ID) and $1 (a script's first argument) are special variables.
  • Command substitution: $(cmd) becomes cmd's output, as in Lab 1's server card.
  • Arithmetic: $((2 * 60)) becomes 120.
  • Word splitting: the result of an unquoted expansion is split again at spaces, tabs and newlines.
  • Globbing (pathname expansion): an unquoted word containing *, ? or […] becomes the list of matching file names. If nothing matches, bash leaves the word as it is.

Quoting switches expansions off:

  • Single quotes '…' switch off everything. What you write is what the program gets.
  • Double quotes "…" allow variables, $( ) and arithmetic, but switch off word splitting and globbing. The result stays one argument, spaces and all.
  • A backslash switches off the special meaning of the next character.

In a directory containing only access.log, with event=os-lumes:

echo *.log; echo "*.log"; echo $event "$event" '$event'
access.log
*.log
os-lumes os-lumes $event

The dangerous case is a variable holding a space. Unquoted, it becomes two arguments:

f="on-sale report.txt"; touch "$f"; ls $f; ls "$f"
ls: cannot access 'on-sale': No such file or directory
ls: cannot access 'report.txt': No such file or directory
on-sale report.txt

The unquoted ls $f looked for two files, on-sale and report.txt. With ls that's an error message. With rm it deletes the wrong files, and with rm -rf $dir/ and an empty $dir, it's the classic way to delete far more than intended.

Key idea

Put double quotes around every variable and every $( ), unless you can say why not. Use single quotes for text that must reach the program untouched, such as awk and grep patterns.

2.6Exit codes

Every program finishes with an exit status, a number from 0 to 255. 0 means success; anything else means some kind of failure, and the program's manual page says which. The shell keeps the last one in $?. grep is a good example, because it distinguishes “no match” from “something went wrong”:

grep -q '" 504 ' access.log; echo $?     # a line with status 504 exists
grep -q '" 503 ' access.log; echo $?     # none with 503
grep -q 504 nosuch.log; echo $?          # the file doesn't exist

A few codes are set by the shell itself: 126 means the file exists but can't be executed (Lab 1), 127 means command not found, and 128 + n means the program was killed by signal n (so 137 is 128 + 9, SIGKILL, which you'll meet in Chapter 5 and Chapter 10).

Exit codes drive the shell's logic. a && b runs b only if a succeeded; a || b runs b only if a failed; a; b runs both regardless. if tests an exit status, not a true/false value: if grep -q ERROR app.log; then ….

A pipeline's exit status is, by default, the status of its last command. That hides failures:

grep 500 nosuch.log | wc -l; echo "status: $?"

2.7Getting help and moving fast

Nobody remembers every option. What you need is to know where the answers are:

  • man grep opens the manual page. Pages are grouped in numbered sections: 1 for commands, 5 for file formats (man 5 crontab), 8 for administration commands. Search inside with /; quit with q. man -k word searches page titles.
  • grep --help prints a shorter summary for most programs; help cd does the same for bash builtins.
  • Examples are often the fastest help: the EXAMPLES section near the end of many man pages, or a community tool such as tldr.
Minimal imagesCloud and container images often leave out manual pages to save space. On Ubuntu, sudo unminimize puts them back; or read them on your own machine, or at manpages.ubuntu.com.

And a few keys save hours: Tab completes commands and file names (press it twice to see choices); Ctrl+R searches your command history; Ctrl+C interrupts the running program; Ctrl+D ends input (and logs you out of an empty prompt); Ctrl+A and Ctrl+E jump to the start and end of the line. history lists what you typed, which, on a shared server, is also a way to learn what the last person did.

Watch out: secrets in your history

Anything you type is saved to ~/.bash_history when the shell exits, including a password passed as an argument (mysql -p'secret', curl -u user:secret). Prefer tools that prompt for secrets or read them from a file or environment variable. Arguments are also visible to other users in ps while the program runs.

2.8Across distributions

bash and the core tools behave the same on every distribution in this book: Ubuntu, Debian, the RHEL family and Amazon Linux all ship GNU bash, GNU coreutils, GNU grep and an awk. The differences you'll notice are small:

On the RHEL family and Amazon Linux

/bin/sh is bash itself (running in a compatibility mode), not dash. Scripts that start with #!/bin/sh but use bash features work there and break on Ubuntu and Debian, so write #!/usr/bin/env bash when you use bash features. awk is GNU awk (gawk) here, while Ubuntu and Debian install the smaller mawk by default; both handle everything in this chapter.

On your Mac

macOS uses zsh as the default shell and BSD versions of the core tools, whose options sometimes differ (sed -i, date, base64 -D). When a command from this book behaves strangely on a Mac, run it on the server or in a Linux container instead.

3.1One tree

Linux has no drive letters. Every file on the machine sits somewhere in one tree that starts at /, the root directory. Other disks, network shares and special filesystems are attached to the tree at a directory, called a mount point (Chapter 11), and from then on look like ordinary directories.

Where things go in that tree isn't arbitrary. The Filesystem Hierarchy Standard (FHS) describes the layout every mainstream distribution follows, and once you know it you can find your way around any server, including one somebody else built.

3.4Inodes, names and ls -l

A file's name is not the file. On Linux filesystems, a file is an inode: a numbered record that holds everything about the file (its type, owner, permissions, size, timestamps and where its data blocks are on the disk) except its name. A directory is just a table that maps names to inode numbers. ls -i shows the inode number next to each name.

With that picture, every column of ls -l makes sense:

Prefer relative targets inside one application's directory, so the whole tree can be moved or copied.

Switching versions with one rename

Symlinks make a clean deployment pattern possible. Install each version of an application into its own directory, never touching it again, and point a symlink called current at the live one. Everything else (the service, nginx, cron jobs) refers only to …/current. Deploying is: unpack the new version next to the old one, then point current at it. Rolling back is pointing it back.

The switch must be atomic: at every instant, current must point to one complete version, never to nothing and never to half of each. The kernel guarantees exactly that for one operation: renaming a name over an existing one, within one filesystem, replaces it in a single step. So the safe way is to create the new link under a temporary name and rename it over the old one:

ln -s releases/2026.02.2 current.new
mv -T current.new current            # -T: treat "current" as the name to replace, not a directory to move into

You'll often see ln -sfn releases/2026.02.2 current instead. Whether that's atomic depends on the version: the one on Ubuntu 24.04 creates a temporary link and renames it, as the lab shows with strace, while older versions removed the old link first and created the new one after, leaving a moment with no current at all. mv -T is atomic everywhere, so deploy scripts should use it.

Key idea

Never change a running application's files in place. Put the new version beside the old one, and switch with a single rename.

Running programs that already loaded the old code keep using it until they restart; that's a feature, and Chapter 5 shows how to restart them without dropping requests.

3.6Finding things

find walks a tree and tests every entry. Its arguments read as a sentence: where to start, then tests, then optionally an action (the default is to print the path).

find /etc -name '*.conf'                    # by name; quote the pattern so the shell doesn't expand it
find /var/log -type f -size +100M           # regular files over 100 MB
find /var/log -type f -mtime +30            # modified more than 30 days ago
find . -newer deploy.marker                 # changed since a reference file was touched
find / -xdev -type d -perm -0002            # world-writable directories on the root filesystem (Chapter 4)
find /tmp -user tiago -type f -delete       # an action: delete what matched. Run without -delete first!

Searching from / touches /proc and network mounts unless you add -xdev (stay on one filesystem), and prints “Permission denied” for directories you can't read unless you add 2>/dev/null or use sudo. For the other common questions: type cmd or command -v cmd finds a program on PATH; grep -rl 'pattern' /etc/nginx finds files containing a text; dpkg -S /usr/sbin/nginx says which package installed a file (Chapter 8); and readlink -f path follows every symlink to the real file.

Watch out: deleted is not freed

Deleting a file removes a name. If a running program still has the file open, the inode and its data stay on the disk until the program closes it or exits, even though no name points to it any more. Deleting a huge log that nginx or your app is still writing frees nothing, and the disk stays full. The lab shows how to see such files; Chapter 7 and Chapter 11 show how to free the space.

4.1Users, groups and IDs

To the kernel, a user is a number: the user ID (UID). Names are for people. Every process runs with a UID, every file has an owner UID, and the permission check (4.3) compares the two.

A group is also a number, the GID, with a list of member users. Every user has one primary group (new files get it) and can belong to any number of supplementary groups. Groups are how you give several users, or several programs, the same access without giving each one separately.

Three kinds of user exist on every server:

  • root, UID 0. The kernel skips most permission checks for UID 0. It's not a person; it's a level of power.
  • System users for services: www-data (nginx on Ubuntu), postgres, sshd. They have low UIDs (below 1000 on Ubuntu), no password and usually no login shell (/usr/sbin/nologin). A service running as its own user can only damage what that user owns.
  • People, with UIDs from 1000 up, a home directory and a shell.

The databases are plain text files in /etc:

4.5The special bits: setuid, setgid and sticky

Three more bits sit in front of the nine, as a fourth octal digit:

  • setuid (4000, shown as s in the owner's x) on a program makes it run as the file's owner, whoever starts it. /usr/bin/passwd is setuid root, so ordinary users can change their own password in /etc/shadow. Every setuid-root program is a door into root if it has a bug; you'll audit them in Chapter 18. Never set it on your own scripts.
  • setgid (2000, s in the group's x) on a directory makes new files and subdirectories inside it inherit the directory's group, instead of the creator's primary group. This is the tool for a directory shared between a writer and a reader, as the lab shows.
  • sticky bit (1000, t in the other's x) on a directory means that only a file's owner (or root) may delete or rename it, even though others may write to the directory. /tmp is 1777: everyone can create files there, nobody can delete anyone else's.

Stagedoor's /srv/uploads was 777, without even the sticky bit: any user on the machine could delete or replace any poster.

4.6umask: the default for new files

When a program creates a file, it asks for a mode (usually 666 for files, 777 for directories), and the kernel removes the bits set in the process's umask. A umask of 022 removes write for group and other: new files are 644, directories 755. A umask of 027 also removes everything for other: files 640, directories 750.

The umask belongs to the process and is inherited by its children, so a service's umask decides the permissions of every file it creates. umask with no argument shows your shell's; systemd sets a service's with UMask= (Chapter 6). For an app that writes files other programs shouldn't see, 027 is a good default.

4.7root and sudo

Logging in as root, especially with a shared password, has every problem a shared account has: nobody knows who did what, a leaver keeps the password, and every typo runs with unlimited power. The standard answer is sudo: people log in with their own accounts, and run individual commands as root when they need to, after proving who they are.

  • Who may do what is in /etc/sudoers and, better, in small files under /etc/sudoers.d/. On Ubuntu, members of the group sudo may run anything: %sudo ALL=(ALL:ALL) ALL.
  • Narrow rules name the exact command: tiago ALL=(root) /usr/bin/systemctl restart stagedoor lets Tiago restart the app and nothing else. Use full paths: the rule matches the program, not the name you type.
  • Edit with visudo (or check a file with visudo -cf file), never with a plain editor. A syntax error in sudoers can lock everybody out of sudo, and on a cloud VM without a root password that can mean rebuilding the machine.
  • Every use is logged, with the person's name, to /var/log/auth.log on Ubuntu (and the journal, Chapter 7). That's the accountability the shared root password couldn't give.
  • sudo -l shows what you may run; sudo -i opens a root shell when you really need several commands (prefer single commands, so each is logged).

Watch out: sudo rules that are root in disguise

A rule that allows an editor (sudo vim /etc/nginx/nginx.conf), a pager, tar, find or a script the user can modify gives full root, because each of these can start a shell or write any file. Allow specific, non-interactive commands; for editing files as root, use sudoedit, which edits a copy as you and writes it back.

4.8Access control lists

Owner, group and other is sometimes too coarse: you want one more user, or a second group, to read a directory without changing its owner or group. ACLs (access control lists) add named entries to an inode: setfacl -m u:tiago:rx dir gives Tiago read and enter on one directory. getfacl dir shows every entry; ls -l marks files that have an ACL with a + after the permission bits.

ACLs have a mask entry, which caps what the named entries and the group may have; when an ACL seems not to work, check the mask first. A default ACL on a directory (setfacl -d -m …) is copied to new files created in it.

Use ACLs sparingly. They're invisible in a normal ls -l apart from the +, some backup and copy tools drop them, and a server whose access only makes sense with getfacl is hard to review. When a group would do, use a group.

✓Chapter summary

  • Users and groups are numbers (UID, GID) with names in /etc/passwd and /etc/group. Services get their own system users.
  • Nine permission bits give read, write and execute to the owner, the group and everyone else. On directories, w means create and delete entries, and x means enter.
  • The kernel picks exactly one class for a process (owner, group or other) and checks only that class. Root skips the check.
  • setgid on a directory makes new files inherit its group; the sticky bit stops people deleting each other's files; the umask sets the default mode of new files.
  • A shared directory for a writer and a reader: owner = writer, group = reader, mode 2750, writer's umask 027.
  • Personal accounts and sudo replace a shared root password; narrow rules name exact commands; every use is logged.
  • ACLs add named users or groups when a single group isn't enough; use them sparingly.

  3. Why can a user delete a file they don't own and can't write to?

    Deleting removes a name from the directory, so it needs write (and execute) permission on the directory, not on the file. Without the sticky bit, anyone who can write to the directory can delete any entry in it.

  4. nginx returns 403 for /var/lib/stagedoor/uploads/plan-7.pdf, but sudo cat of the file works. List what you'd check, in order.

    sudo cat proves nothing, because root skips the checks. Check which user nginx's workers run as (ps -o user= -C nginx: the master is root, the workers that open files are www-data); run namei -l on the path to see that www-data can traverse every directory; check the file's group and mode (probably created without the setgid directory, so its group is stagedoor, or with a bad umask); test with sudo -u www-data cat. On RHEL, also check SELinux denials.

  5. Design permissions for /etc/stagedoor/stagedoor.env, which holds the database password: the app must read it, the deploy process (running as a person with sudo) must update it, nginx must not see it.

    Owner root, group stagedoor, mode 640; the directory /etc/stagedoor owned root:stagedoor, mode 750. The app (user stagedoor) reads through the group but can't change it; deploys update it with sudo; nginx (www-data) is “other” and gets nothing. (Chapter 6 loads it with systemd's EnvironmentFile=.)

  6. Compare giving Tiago read access to the uploads by adding him to www-data with giving it through an ACL.

    Joining www-data gives him everything nginx's group can read, everywhere on the machine, which is broader than needed but visible in /etc/group. An ACL gives exactly this directory and nothing else, but it's less visible (only a + in ls -l) and easy to forget. For one person and one directory, the ACL is the narrower choice; for a role several people share, make a dedicated group.
