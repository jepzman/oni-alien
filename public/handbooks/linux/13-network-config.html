Network configuration and tools

Every network problem eventually lands on one machine, and on that machine four things decide where a packet goes: its addresses, its routes, the sockets that are listening, and how it turns names into addresses. This chapter shows each one with the tool that reads it, and builds a small network of pretend servers on your own machine to practise on.

By the end you can

  • Read a server's interfaces, addresses and routes with ip, and ask which route a packet would take.
  • List listening sockets with ss, and spot a service listening only on localhost.
  • Explain how a name becomes an address on Linux, and why getent and dig can disagree.
  • Read an Ubuntu netplan file and apply a change safely.
  • Build a test network from network namespaces.

Before you start

  • Handbook 1, Chapters 2–5 (addresses and CIDR, TCP and ports, routing, DNS) help a lot; this chapter recaps what it needs.
  • A Linux VM with sudo and these packages: iproute2 iputils-ping netcat-openbsd dnsutils dnsmasq-base (Appendix C).

13.1The network as one host sees it

From inside a server, “the network” is four tables the kernel keeps. Nearly every connection problem is one of them being different from what you assumed.

One tool reads most of them. ip, from the iproute2 package, replaced the older ifconfig, route and arp (still found in old guides and on old servers, from net-tools): use ip, which shows everything, including what the old tools can't.

13.2Interfaces, addresses and routes

Table 13.1 · The ip commands you'll use

link state, MTU, MACip -br link

which route a packet to X would takeip route get 10.40.0.14
the neighbour (ARP) tableip neigh
add an address or route now (until reboot)sudo ip addr add 10.40.0.20/24 dev eth0, sudo ip route add 10.50.0.0/16 via 10.40.0.1

A server's routing table is short. Usually there's one route per directly connected network, added automatically from the interface's address (10.40.0.0/24 dev eth0 proto kernel scope link: anything in this range is on the wire, reachable directly), and a default route for everything else (default via 10.40.0.1: send it to this gateway). The kernel picks the most specific matching route, as Handbook 1, Chapter 4 explains. ip route get asks the kernel to make that choice for one address and shows the answer, including the source address it would use: the quickest way to settle “which interface does this go out of?” on a machine with several.

For addresses on the same network, the kernel needs the neighbour's hardware (MAC) address, which it learns with ARP and keeps in the neighbour table (ip neigh). An entry stuck in FAILED or INCOMPLETE means nothing answered: the other machine is down, on another network, or a firewall drops ARP.

Changes with ip don't lastAddresses and routes added with ip vanish at reboot. They're perfect for testing; the permanent configuration lives in netplan on Ubuntu (13.5).

13.3Who is listening?

A server program accepts connections on a listening socket: an address and a port. ss (which replaced netstat) lists them:

sudo ss -tlnp      # -t TCP, -l listening, -n numbers not names, -p the process (needs sudo for others' processes)
sudo ss -ulnp      # the same for UDP
ss -tn state established '( dport = :5432 )'   # established connections to port 5432

The address in Local Address:Port decides who can connect, and it's the cause of a classic failure:

  • 0.0.0.0:5432 (IPv4) or [::]:5432 (IPv6, often both): every address on the machine. Reachable from anywhere a route and firewall allow.
  • 10.40.0.14:5432: only that address.
  • 127.0.0.1:5432: only loopback, the machine talking to itself. Unreachable from any other machine, whatever the firewall says. Many services listen here by default to be safe: PostgreSQL (listen_addresses = 'localhost'), Redis, many admin interfaces.

What a client sees tells you which case you're in. Connection refused means the packet reached the machine and nothing was listening on that address and port, so the kernel answered with a reset. A timeout means nothing answered at all: wrong address, no route, or a firewall dropping the packet (Chapter 15).

Key idea

“Refused” means you reached the machine and nobody was listening there. “Timed out” means you didn't get an answer at all. They point at different layers.

13.4From a name to an address

When a program connects to db.stagedoor.internal, it calls the C library's resolver (getaddrinfo), which follows the hosts: line in /etc/nsswitch.conf. On a server that line is usually files dns: look in /etc/hosts first, and only if the name isn't there, ask DNS.

  • /etc/hosts is a plain list of addresses and names. It's handy for one machine's own name and for testing, and dangerous for anything else: an entry there wins over DNS on that machine, silently and for ever, long after everyone has forgotten it.
  • /etc/resolv.conf names the DNS servers. On Ubuntu it points at 127.0.0.53, a local stub run by systemd-resolved, which forwards queries to the real servers (from DHCP or netplan) and caches the answers. resolvectl status shows the real servers per interface; resolvectl query name resolves through it; resolvectl flush-caches empties its cache.
  • dig asks a DNS server directly and shows the whole answer, with its TTL (how long it may be cached, Handbook 1, Chapter 5). dig @10.40.0.1 name asks a particular server; dig +short name prints only the answer.

Watch out: “DNS is fine, I checked with dig”

dig proves what DNS says, not what your program gets. Applications also cache addresses themselves (connection pools, the JVM's DNS cache, long-lived connections that never look the name up again). To know what the app will do, use getent hosts on the same machine, and look at its real connections with ss -tnp.

13.5Making it permanent: netplan

On Ubuntu servers, the network configuration is written in YAML under /etc/netplan/, and netplan turns it into configuration for systemd-networkd (on servers) or NetworkManager (on desktops). Cloud images ship a file written by cloud-init that asks for an address by DHCP; servers on a private network like Atlantica's usually have static addresses:

/etc/netplan/60-stagedoor.yamlnetplan (an illustration of door-4's configuration)

network:
  version: 2
  ethernets:
    eth0:
      addresses: [10.40.0.14/24]
      routes:
        - to: default
          via: 10.40.0.1
      nameservers:
        addresses: [10.40.0.1]
        search: [stagedoor.internal]

Apply changes with sudo netplan try, not apply: it applies the new configuration and rolls it back after 120 seconds unless you confirm. If the change cuts off your SSH session, you can't confirm, and the old configuration returns by itself. On a remote server, that's the difference between a typo and a trip to the provider's console. netplan get shows the merged configuration; networkctl status shows what systemd-networkd did with it. File permissions matter too: netplan warns if a file is readable by others, since it may hold Wi-Fi or VPN secrets.

13.6A lab network from namespaces

To practise on several servers without renting any, this book uses network namespaces: the kernel can give a group of processes its own complete network stack, with its own interfaces, addresses, routes, firewall and sockets. Containers are built on exactly this (Chapter 19). A veth pair is a virtual cable with one end in each namespace; a bridge is a virtual switch. ip netns exec door-2 COMMAND runs a command “on” door-2: it sees only that namespace's network, while sharing the rest of the machine (files, users, processes).

The lab's script builds three pretend servers on one switch, with your machine as 10.40.0.1, their gateway and DNS server. Chapters 14–16 reuse it.

On the cloud

Cloud VMs get their address by DHCP from the provider, along with the provider's DNS resolver (on AWS, the VPC's resolver at the network's base address plus two, Handbook 1, Chapter 5). You rarely configure addresses on the VM itself: you configure the network around it (subnets, route tables, security groups) and the VM picks it up. The host-side tools in this chapter are how you check that what you configured is what the VM actually got.

13.8Lab: Stagedoor's dry run, in miniature

Lab 13 · Three servers, one switch, two bugs

You'll build a pretend Stagedoor network from network namespaces, look at it with ip, reproduce the dry run's two failures (a service listening on localhost, and a stale /etc/hosts entry beating DNS) and fix both. You need a Linux VM with sudo (not a container) and sudo apt install iproute2 iputils-ping netcat-openbsd dnsutils dnsmasq-base. Cost: nothing; nothing leaves your machine. Clean-up: the last step. MAC addresses, interface numbers and times will differ.

  1. Build the network. Save the script as netlab.sh, make it executable, and run it:

    netlab.shbash

    #!/usr/bin/env bash
# netlab.sh up|down · a pretend Stagedoor network on one Linux machine, built from network namespaces.
# Three "servers" (door-2, door-3, door-4) share a switch (a Linux bridge) with your machine, which is 10.40.0.1.
set -euo pipefail
hosts=(door-2:10.40.0.12 door-3:10.40.0.13 door-4:10.40.0.14)

up() {
  ip link add br-lab type bridge
  ip addr add 10.40.0.1/24 dev br-lab
  ip link set br-lab up
  for h in "${hosts[@]}"; do
    name=${h%%:*} addr=${h##*:} n=${name#door-}
    ip netns add "$name"
    ip link add "veth$n" type veth peer name eth0 netns "$name"   # a cable: one end on the switch, one in the server
    ip link set "veth$n" master br-lab up
    ip -n "$name" addr add "$addr/24" dev eth0
    ip -n "$name" link set eth0 up
    ip -n "$name" link set lo up
    ip -n "$name" route add default via 10.40.0.1
    mkdir -p "/etc/netns/$name"                                   # ip netns exec mounts these over /etc
    echo "nameserver 10.40.0.1" > "/etc/netns/$name/resolv.conf"
  done
  if iptables -L DOCKER-USER -n >/dev/null 2>&1; then              # Docker's firewall drops bridged traffic
    iptables -I DOCKER-USER -i br-lab -o br-lab -j ACCEPT           # by default; let the lab's own through
  fi
  echo "lab network up: 10.40.0.0/24 on br-lab"
}

down() {
  for h in "${hosts[@]}"; do
    name=${h%%:*}
    ip netns del "$name" 2>/dev/null || true
    rm -rf "/etc/netns/$name"
  done
  ip link del br-lab 2>/dev/null || true
  iptables -D DOCKER-USER -i br-lab -o br-lab -j ACCEPT 2>/dev/null || true
  echo "lab network removed"
}

case "${1:-}" in
  up) up ;;
  down) down ;;
  *) echo "usage: sudo $0 up|down" >&2; exit 2 ;;
esac
    chmod +x netlab.sh
sudo ./netlab.sh up

✓Chapter summary

  • On one host, a connection depends on four things: the name, the route, the interface, and a listening socket at the far end.
  • ip -br address, ip route, ip route get and ip neigh show addresses, routes, the chosen route and neighbours.
  • ss -tlnp lists listening sockets. A service on 127.0.0.1 can't be reached from other machines. Refused means nothing listening; a timeout means no answer.
  • Programs resolve names through nsswitch.conf: /etc/hosts first, then DNS (on Ubuntu via systemd-resolved at 127.0.0.53). getent hosts shows what a program gets; dig shows what DNS says.
  • Permanent configuration on Ubuntu is netplan; change it with netplan try.
  • Network namespaces give a process its own network stack: a cheap lab, and the basis of containers.

Key terms

Routing table
The kernel's list of destination ranges and where to send packets for each: directly on an interface or via a gateway.
Default route
The route used for any destination no more specific route matches, usually via a gateway.
Listening socket
An address and port on which a program accepts incoming connections.
Loopback
The interface (lo, 127.0.0.1) through which a machine talks to itself; unreachable from other machines.
nsswitch.conf
The file that tells the C library which sources to use, in which order, for names, users and other lookups.
systemd-resolved
The local DNS stub resolver and cache on Ubuntu, listening on 127.0.0.53.
netplan
Ubuntu's YAML network configuration, rendered for systemd-networkd or NetworkManager.
Network namespace
An isolated copy of the network stack (interfaces, routes, firewall, sockets) for a group of processes.

Check your understanding

  1. Which command tells you which interface and source address the kernel would use to reach 10.50.3.7? recall

    Show answer

    ip route get 10.50.3.7. It prints the chosen route, the outgoing device, the gateway if any, and the source address.

  2. ss -tlnp on a server shows 127.0.0.1:6379 for Redis. A web server on another machine needs it. What do you change, and what else must you check before you do? apply

    Show answer

    Make Redis listen on the server's private address (bind 10.x.y.z in its configuration) and restart it. Before that: require authentication, and make sure a firewall or security group allows only the web servers to reach the port, because Redis on a reachable address with no password is a well-known way to be compromised.

  3. Explain why dig and the app on the same server can disagree about a name's address. explain

    Show answer

    dig asks a DNS server directly. The app resolves through the C library, which follows nsswitch.conf and usually checks /etc/hosts first; it may also go through a local cache (systemd-resolved) or cache addresses itself. A stale /etc/hosts entry or cache gives the app a different answer from DNS.

  4. From a web server, nc -zv 10.40.0.14 5432 hangs for its whole timeout instead of failing at once. List three causes, and the command that checks each. debug

    Show answer

    No route or wrong gateway (ip route get 10.40.0.14); the machine is down or not on that network (ip neigh showing FAILED, no ping reply); a firewall dropping the packets on either host or in between (Chapter 15: nft list ruleset, the cloud's security groups). A refused connection would have meant the packet arrived and nothing listened.

  5. Design how Stagedoor's servers should find each other by name. design

    Show answer

    One internal DNS zone (stagedoor.internal) served by the provider's private DNS or a small resolver, with records per service (db, scan-api) rather than per machine, so a move changes one record; short TTLs (a few minutes) on records that move; no internal names in /etc/hosts; netplan pointing each server at that resolver with search: [stagedoor.internal].

  6. Compare netplan apply and netplan try for a change on a remote server. compare

    Show answer

    apply makes the change at once and permanently; if it breaks connectivity, you need a console to fix it. try applies it and reverts after a timeout unless you confirm, so a change that cuts your SSH session undoes itself. Use try on anything you reach over the network.
