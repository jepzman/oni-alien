Packages and updates

Almost every program on a server arrived as a package, and almost every security problem on a server is fixed by a newer one. This chapter explains how packages get from a signed repository onto your disk, how to answer “what is this file, and where did it come from?”, and how to keep servers patched without letting updates restart things at the worst possible moment.

By the end you can

  • Explain what a package, a repository and a signing key are, and how apt and dpkg divide the work.
  • Find which package owns a file, what a package installed, and which version would be installed and from where.
  • Hold a package at its version, and add a third-party repository safely.
  • Configure automatic security updates, and know when an update needs a service restart or a reboot.
  • Plan for a release's end of support.

Before you start

  • Chapter 1: distributions and releases. Chapter 6: services and timers.
  • An Ubuntu machine with sudo and internet access (Appendix C).

8.1Packages, repositories and keys

A package is an archive of files (programs, libraries, configuration, documentation) plus metadata: its name and version, what it depends on, and scripts to run when it's installed or removed. On Ubuntu and Debian packages are .deb files; on the RHEL family, .rpm.

Packages come from a repository: a web server holding thousands of packages and an index that lists them. Ubuntu's repositories are split into pockets per release, and the names show up everywhere in apt's output:

  • noble: the release as it shipped (24.04 is “noble”), never changed afterwards;
  • noble-security: security fixes only;
  • noble-updates: security fixes plus other bug fixes (security fixes appear in both);
  • noble-backports: newer versions of a few programs, off unless you ask for them.

Every repository index is signed. Your machine holds the distribution's public signing key (in /usr/share/keyrings/), and apt refuses an index whose signature doesn't verify. That's what makes it safe to download packages over plain HTTP from a mirror you don't control: the index lists every package's checksum, and the index is signed by Ubuntu. Trusting a repository means trusting whoever holds its key, so add third-party repositories rarely and carefully (8.4).

Two programs share the work. dpkg is the low-level tool: it installs a single .deb file, removes packages and keeps the database of what's installed (/var/lib/dpkg/), but knows nothing about repositories or dependencies it would need to fetch. apt sits on top: it reads repositories, resolves dependencies, downloads, and calls dpkg. Use apt to install and upgrade, dpkg to ask questions.

8.3Versions and holds

apt-cache policy answers the most useful question about any package: what's installed, what would be installed, and from where. Each source has a priority (500 for normal repositories, 100 for “what's already installed”), and apt picks the highest version among the highest-priority sources. A version string like 2.42-4ubuntu2.11 is the upstream version (2.42), then the distribution's revision: Ubuntu fixes security problems by patching the version it shipped, not by jumping to a newer upstream release, so a server's versions look old and are still patched.

Sometimes you need a package to stay exactly where it is for a while: a database whose upgrade you want to schedule, or a library a vendor tested against. Holding it stops apt upgrade from touching it: sudo apt-mark hold postgresql-16, apt-mark showhold, sudo apt-mark unhold. A hold is a promise to come back: write down why and until when, or it becomes a vulnerability nobody remembers choosing.

8.4Third-party repositories

Vendors such as Docker, PostgreSQL (the PGDG repository), nginx and Grafana publish their own repositories with newer versions than the distribution. Adding one is three things: download the vendor's signing key into /etc/apt/keyrings/, add a source file under /etc/apt/sources.list.d/ that names that key with Signed-By:, and apt update. The modern source format (“deb822”) looks like Ubuntu's own:

Types: deb
URIs: https://apt.postgresql.org/pub/repos/apt
Suites: noble-pgdg
Components: main
Signed-By: /etc/apt/keyrings/postgresql.asc

Watch out: a repository is root on your server

Packages run their install scripts as root. Whoever controls a repository you've added can run anything on your machines at the next upgrade. Add only vendors you'd trust with root, tie each key to its own repository with Signed-By: (never add keys to a global keyring, as old instructions with apt-key did), use HTTPS, and remove repositories you no longer need. The same thinking applies to curl … | sudo bash install scripts, which skip the signatures entirely.

8.5Staying patched

Ubuntu ships unattended-upgrades, which installs updates by itself every day. Two systemd timers drive it (Chapter 6): apt-daily.timer refreshes the indexes and apt-daily-upgrade.timer installs. Two files configure it. /etc/apt/apt.conf.d/20auto-upgrades switches it on or off:

APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";

and /etc/apt/apt.conf.d/50unattended-upgrades says what it may install. By default, only the release and its security pocket, not -updates:

Unattended-Upgrade::Allowed-Origins {
	"${distro_id}:${distro_codename}";
	"${distro_id}:${distro_codename}-security";
	// Extended Security Maintenance; doesn't necessarily exist for
	// every release and this system may not have it installed, but if
	// available, the policy for updates is such that unattended-upgrades
	// should also install from here by default.
	"${distro_id}ESMApps:${distro_codename}-apps-security";
	"${distro_id}ESM:${distro_codename}-infra-security";
//Unattended-Upgrade::Remove-Unused-Dependencies "false";
//Unattended-Upgrade::Automatic-Reboot "false";
// when Unattended-Upgrade::Automatic-Reboot is set to true
//Unattended-Upgrade::Automatic-Reboot-WithUsers "true";
//Unattended-Upgrade::Automatic-Reboot-Time "02:00";

(// starts a comment.) Leaving -updates out keeps automatic changes to security fixes, which are small and carefully tested; the larger bug-fix updates are applied in your maintenance window, where you can watch them. Change settings in a file of your own, such as /etc/apt/apt.conf.d/52stagedoor, which wins over 50 because it's read later; package upgrades then leave your choices alone.

Installing a fix is half the job (Figure 8.1). After an update:

  • Services still run the old code until they restart. needrestart, installed on Ubuntu servers, checks after each upgrade which processes use replaced libraries and either lists, asks about or restarts them, depending on $nrconf{restart} ('l' list, 'i' interactive, 'a' automatic) in /etc/needrestart/conf.d/. sudo needrestart -r l lists them on demand.
  • The kernel (and a few core libraries) needs a reboot. Ubuntu creates /var/run/reboot-required and lists the packages in /var/run/reboot-required.pkgs. unattended-upgrades can reboot by itself (Unattended-Upgrade::Automatic-Reboot and …-Time), which suits a fleet of identical servers behind a load balancer and is risky for a single database server.

Key idea

Don't solve “an update restarted something at a bad time” by switching updates off. Separate installing from restarting, and put restarts in a window you control.

8.6Release upgrades and end of support

Within a release, updates are small and safe by design. Moving to the next release (Ubuntu 22.04 to 24.04, Debian 11 to 12) changes major versions of everything at once: Python, OpenSSL, PostgreSQL, configuration formats. You can upgrade in place (do-release-upgrade on Ubuntu), but on a server there's a better way: build a new server on the new release from your notes or scripts, test it, move the work to it, and keep the old one until you're sure. It's slower the first time and much safer, and it's the cattle approach of Chapter 1 in practice. It also tests the thing you most need to know: whether you could rebuild this server at all.

Whichever way, start long before the date. A release past its end of support (Chapter 1, Table 1.1) gets no fixes, and Ubuntu Pro or a paid extended support offer only buys time.

On Amazon Linux 2023

Amazon Linux 2023 locks each instance to a dated snapshot of its repository, so two instances launched a month apart may have different package versions, and dnf upgrade alone never moves to a newer snapshot. You move deliberately, with dnf upgrade --releasever=<version>, or by launching from a newer image. It's the update-in-place release model from Chapter 1.

At Stagedoor: a patching policy

Rafaela writes Figure 8.2 into the wiki and sets it up the same week. On door-2 and door-3, unattended-upgrades is switched back on, for security updates only, with $nrconf{restart} = 'l' so nothing restarts by itself and no automatic reboots. Every Tuesday at 05:00 Lisbon time, unless an on-sale is booked that day, a maintenance script takes one web server out of the load balancer, applies all updates, restarts what needrestart lists, reboots if /var/run/reboot-required exists, waits for the health check, and moves to the next. The first run, on 14 April, installs about 140 updates per server and reboots both.

The same morning, with a maintenance notice sent to venues the week before, door-1 is rebooted for the first time in 500 days. PostgreSQL stops cleanly and is back in under a minute, on a kernel with seventeen months of fixes. For Debian 11's end of support, Leonor and Rafaela decide against an in-place upgrade: a new database server on Ubuntu 24.04 will be built from scratch by the end of August, and the data moved to it. (Handbook 6 tells the database side of that move.) It's the first server Stagedoor will build from a written checklist rather than from memory.

✓Chapter summary

  • A package is files plus metadata and scripts; a repository serves packages and a signed index. Trusting a repository means trusting its key holder with root.
  • apt fetches, resolves and upgrades; dpkg installs single packages and answers questions (-S, -L, -l).
  • Ubuntu splits each release into pockets: the release, -security, -updates, -backports. Fixes are backported, so versions look old and are patched.
  • unattended-upgrades installs security fixes daily. Installed isn't running: restart services (needrestart) and reboot for kernels, in a window you choose.
  • Replace a release before its end of support, preferably by building a new server.

Key terms

Package
An archive of files with metadata (name, version, dependencies) and install scripts, such as a .deb or .rpm.
Repository
A server that publishes packages and a signed index of them for one or more releases.
Pocket
One part of an Ubuntu release's repository: the release itself, -security, -updates or -backports.
Signing key
The public key a package manager uses to verify that a repository's index was published by its owner.
Hold
A mark that stops the package manager upgrading a package.
unattended-upgrades
Ubuntu and Debian's service that installs updates automatically, by default security updates only.
needrestart
A tool that finds processes still using replaced libraries after an upgrade, and lists or restarts them.

Check your understanding

  1. What does apt update change on the machine, and what does it not? recall

    Show answer

    It downloads and verifies the repositories' indexes, so apt knows which versions exist. It doesn't install or upgrade any package; apt upgrade does that.

  2. A server's openssl is version 3.0.13-0ubuntu3.16 and a scanner says “OpenSSL 3.0.13 is vulnerable to CVE-…, upgrade to 3.0.15”. How do you check whether you're actually affected? apply

    Show answer

    Ubuntu backports fixes into the version it shipped, so the upstream number alone says little. Check the package changelog (zcat /usr/share/doc/openssl/changelog.Debian.gz | grep CVE-…) or Ubuntu's security notice and CVE tracker for that CVE and release. If the fix is listed for your package revision or an earlier one, you're patched; if not, apt-cache policy openssl shows whether a fixed candidate is waiting.

  3. Explain why a server can be fully upgraded and still vulnerable to a bug in a library fixed last week. explain

    Show answer

    Processes that started before the upgrade still have the old library loaded in memory. Until they restart (or, for the kernel, until the machine reboots), the old code is what runs. needrestart and /var/run/reboot-required tell you what's still outstanding.

  4. apt upgrade says “The following packages have been kept back: postgresql-16 postgresql-client-16”. Give two possible reasons and how to tell them apart. debug

    Show answer

    Either a package is held (apt-mark showhold lists it), or the upgrade needs new packages installed or old ones removed, which apt upgrade won't do (apt-get -s full-upgrade shows the extra changes). Phased updates on Ubuntu can also keep packages back for a few days while they roll out gradually.

  5. Design an update policy for two identical web servers behind a load balancer and one database server. design

    Show answer

    Security updates installed daily on all three, with no automatic restarts or reboots. Web servers: in a weekly window, one at a time, out of the balancer, full updates, restarts, reboot if required, health check, back in; they could even reboot automatically, staggered. Database: a separate, announced monthly window (or a replica switchover once one exists), because restarting it is visible to everyone. A calendar of busy days when nothing is changed. A plan to replace each release months before its end of support.

  6. Compare upgrading a server to a new release in place with building a new server on the new release. compare

    Show answer

    In place is quicker and keeps everything, including the unknown hand changes, and is hard to roll back if it fails halfway. Building new takes longer the first time, but tests that you can rebuild the server, lets you compare old and new side by side, and leaves the old server as the rollback. For pets, building new is safer; for servers built from scripts, it's the normal way.
