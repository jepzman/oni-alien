What a Linux server is

A server is just a computer that nobody sits in front of, and most of the ones in the cloud run Linux. This chapter separates the parts that word covers (the kernel, the distribution, the programs around them), follows a machine from power-on to a login prompt, and gives you a calm, read-only way to find out what you've been handed.

By the end you can

  • Explain what the kernel does and what the distribution adds around it.
  • Say which distribution and release a server runs, and until when it gets security updates.
  • Describe the boot sequence from firmware to PID 1, and what changes on a cloud VM or in a container.
  • Explain what a cloud image and cloud-init do at first boot.
  • Inventory an unfamiliar server without changing anything on it.

Before you start

  • A terminal on any Linux machine: a container, WSL on Windows, or a small VM. Appendix C shows how to get one.
  • You can type a command and press Enter. Chapter 2 covers the shell properly.

At Stagedoor

Stagedoor sells tickets for about six hundred music venues in Portugal. Fans buy on the web and in the app; door staff scan the tickets on their phones. Most weeks the traffic is calm. Then a popular band announces a tour, tickets go on sale at 10:00 on a Friday, and for ten minutes everything is busy at once.

On Monday 5 January 2026, Rafaela Costa starts as Stagedoor's first operations engineer. Leonor Ferreira, the CTO, wrote the first version of the platform in 2023 and built its first server herself. She welcomes Rafaela, apologises for the state of things, and gives her three names, door-1, door-2 and door-3, and a pinned message in the team chat's #ops channel: the root password, unchanged since 2023. Nobody has written down what runs where. “It works,” Leonor says. “Mostly. Please don't break it during an on-sale.”

Rafaela's first rule, which she writes at the top of a new page in the wiki: nothing changes until it's written down. Her first job is to find out what she's been handed, without changing anything. Section 1.8 shows what she found.

1.1Kernel, userland, distribution

“Linux” means three different things depending on who says it, and it helps to keep them apart from the start.

Strictly, Linux is a kernel: the one program on the machine that talks to the hardware directly. It starts first, stays in memory until the machine shuts down, and does five jobs for everything else:

  • Processes: it starts programs, gives each a share of the CPUs, and stops them (Chapter 5, Chapter 9).
  • Memory: it hands out memory, keeps each program's memory private from the others, and decides what to do when it runs out (Chapter 10).
  • Files: it turns blocks on a disk into files and directories (Chapter 3, Chapter 11).
  • Network: it sends and receives packets and keeps track of connections (Chapter 13).
  • Devices and permissions: it drives disks, network cards and consoles, and checks who may do what (Chapter 4).

Programs never touch the hardware themselves. When a program wants to open a file, send a packet or start another program, it asks the kernel with a system call: a numbered request such as openat, read, write or execve. The kernel checks the request, does the work and returns a result or an error. Everything outside the kernel, from the shell to your app, is called userland (or user space).

A kernel on its own can't do anything useful for you: there's no shell to type into and no program to start your web server. A distribution (a “distro”) packages the Linux kernel together with a userland (thousands of programs and libraries, mostly from the GNU project and others), a package manager to install and update them (Chapter 8), and a promise to ship security fixes for a stated number of years. Ubuntu, Debian, Red Hat Enterprise Linux and Amazon Linux are distributions. When people say “a Linux server”, they mean a machine running one.

Key idea

The kernel does the work; programs only ask. Almost every problem in this book, from “permission denied” to “too many open files”, is the kernel refusing or running out of something a program asked for.

Kernel space, user spaceThe CPU itself enforces the split: kernel code runs in a privileged mode that can touch hardware and any memory; user programs run in a restricted mode and can't. A bug in a program crashes the program. A bug in the kernel can crash the machine.

1.2Distributions and releases

The distributions you'll meet on cloud servers differ in their package format, their defaults and, most importantly for a server, how long each release is supported. A release is a numbered version of the whole distribution (Ubuntu 24.04, Debian 12) whose packages stay stable: during its support period you get security fixes and bug fixes, not new major versions that might change behaviour under you. When support ends, the fixes stop, and every new vulnerability stays open on that machine for good.

LTS means long-term support: a release meant to be run for years, as servers are. Ubuntu also publishes releases between LTS versions (24.10, 25.04) with nine months of support each; they're fine on a laptop and wrong on a server, because you'd have to upgrade twice a year.

Watch out: end of support is a date, not a feeling

A server past its release's end of support keeps working, which is exactly why it's dangerous: nothing breaks, so nobody notices that security fixes stopped. Write the end-of-support date on every server's card the day you meet it, and plan the upgrade or rebuild a few months before (Chapter 8).

Two files answer “what is this?” on any modern distribution. /etc/os-release names the distribution and release; uname -r prints the running kernel's version. They're different things: Ubuntu 24.04 ships a 6.8 kernel, can be moved to newer ones, and the kernel running can be older than the one installed if nobody has rebooted since the last kernel update.

1.3How a machine boots

Knowing the boot sequence pays off the first time a server doesn't come back after a reboot: each stage hands over to the next, and the question is always which hand-over failed.

  1. Firmware. The machine's built-in firmware (UEFI on modern machines, BIOS on old ones) checks the hardware and looks for something bootable on a disk.
  2. Bootloader. GRUB, on most distributions, loads two files from /boot into memory: the kernel (vmlinuz-…) and the initramfs, a small temporary filesystem with just enough drivers to find the real disk.
  3. Kernel. The kernel starts, detects hardware, uses the initramfs to find and mount the root filesystem (the one mounted at /), and throws the initramfs away.
  4. PID 1. The kernel starts exactly one program itself: /sbin/init, which becomes process number 1. On Ubuntu, Debian, RHEL and Amazon Linux, that's systemd. Every other process on the machine is started by PID 1 or by one of its descendants (Chapter 5).
  5. Services. systemd starts what's configured to run at boot, in dependency order: mounting disks, the network, SSH, then services such as nginx and your app (Chapter 6).

If a program was started by hand (someone logged in and typed a command) rather than as a service, step 5 doesn't know about it, and after a reboot it simply isn't running. That's one of the most common surprises on hand-built servers, and it's waiting for Stagedoor in this chapter's story.

1.4Cloud images and cloud-init

Nobody installs Linux from a USB stick on a cloud server. You pick an image: a ready-made copy of a disk with a distribution already installed (an AMI on AWS, an image on Azure and Google Cloud). Launching a VM copies the image to a new disk and boots it. Ubuntu, Debian, Red Hat and Amazon publish official images for every release and refresh them every few weeks with the latest updates.

An image is the same for everyone, so something must turn it into your server at first boot: set its hostname, create users, install your SSH key, maybe install packages and start your app. On nearly every cloud image, that something is cloud-init. It runs as a set of services early in boot (stage 5 of Figure 1.2), asks the cloud's instance metadata service (a web service only the VM can reach, at 169.254.169.254) for the user data you supplied when you launched the VM, and applies it. User data is usually a shell script or a YAML file that starts with #cloud-config:

user-data.yamlcloud-config (an illustration; Chapter 18 builds a tested one)

#cloud-config
hostname: door-4
users:
  - name: rafaela
    groups: [sudo]
    shell: /bin/bash
    ssh_authorized_keys:
      - ssh-ed25519 AAAAC3Nza…rafaela-laptop
package_update: true
packages: [nginx]
runcmd:
  - [systemctl, enable, --now, nginx]

Read it top to bottom: name the machine, create one personal user who can use sudo and log in with one key, update the package lists, install nginx and start it. cloud-init runs most of this only on the first boot of a new instance; rebooting doesn't repeat it. Its log, /var/log/cloud-init-output.log, is the first place to look when a new server didn't come up the way you described.

Try it locallyMultipass, a free tool for Ubuntu VMs on a laptop, accepts the same file: multipass launch --cloud-init user-data.yaml (Appendix C).

This is the first glimpse of an idea the whole book works towards: a server described in a file can be rebuilt in minutes, while a server built by hand over three years can only be repaired, carefully. Chapter 18 writes a hardened baseline as cloud-init, and Chapter 21 rebuilds one of Stagedoor's servers from a script.

1.5Finding out what you've been handed

The first hour on an unfamiliar server should change nothing. Every question below has a read-only command, and most of the answers come from two places the kernel keeps up to date: /proc and /sys. They look like directories full of files, but nothing in them is stored on a disk; the kernel generates each “file” when you read it (Chapter 3).

Table 1.2 · An inventory in fourteen questions
QuestionCommandNotes
What is it called?hostnamealso in the shell prompt, usually
Which distribution and release?cat /etc/os-releasethen look up its end of support
Which kernel is running?uname -rcompare with ls /boot: a newer kernel there means it's waiting for a reboot
Is a reboot pending?cat /var/run/reboot-requiredUbuntu and Debian; “No such file” means no
How long has it been up?uptimealso the load average (Chapter 9)
What is PID 1?ps -o comm= -p 1systemd on a normal server
How many CPUs?nprocdetails in lscpu
How much memory?free -hread the available column (Chapter 10)
Which disks, how full?lsblk, df -hChapter 11
Which addresses?ip -brief addressChapter 13
What's listening?ss -tlnpwith sudo, -p names the program
Which services run?systemctl list-units --type=service --state=runningonly on machines where PID 1 is systemd
What else runs?ps -ef --forestprograms started by hand show up here but not above
Who logs in?last -n 20, getent passwdChapter 4, Chapter 16

The two rows about running programs are worth comparing on any hand-built server. Something in the ps list that isn't in the systemctl list was started some other way: from a terminal, from cron, from a forgotten script. It won't survive a reboot unless something starts it again.

Watch out: “just a quick restart”

On a server you don't understand yet, a reboot is a change, not a check. If anything was started by hand, it won't come back. Do the inventory first, find out how each running program was started, and reboot only when you know what to expect.

1.6Pets and cattle

Operations people describe two ways of looking after servers. A pet server has a name, was built by hand, and is nursed back to health when it's ill, because nobody knows exactly how to make another one. Cattle are numbered, built from a description (an image, cloud-init, a script), and replaced when they misbehave. The terms are blunt, but the difference is real: a pet holds knowledge that exists nowhere else, and losing it loses the knowledge too.

Almost every company starts with pets, and that's fine. The way out isn't to throw them away but to move the knowledge out of the machine and into writing, one piece at a time:

  1. Inventory: what's on it, what runs, who logs in (this chapter).
  2. Understand: for each running program, how it starts, where its config and data live, where it logs (Chapters 3–8).
  3. Fix in place, writing each fix down as a command you could run again (Chapters 4–16).
  4. Script it: turn the written-down commands into a script or cloud-init (Chapters 17–18).
  5. Rebuild a copy from the script, test it, and replace the pet (Chapter 21).

1.7Across distributions

Everything in this chapter works the same on every mainstream distribution: the kernel, the boot sequence, /proc, systemd and cloud-init. What changes is mostly the package manager and where a few configuration files live, which Appendix B lists side by side.

On the RHEL family

Red Hat Enterprise Linux and its rebuilds (Rocky Linux, AlmaLinux) use .rpm packages and dnf, and turn on SELinux by default, an extra permission layer that Chapter 18 introduces. The release is in /etc/os-release as on Ubuntu, and also in /etc/redhat-release. Ten years of support per major version is why enterprises like it, and why you'll meet very old ones.

On Amazon Linux

Amazon Linux 2023 is based on Fedora, uses dnf, and is updated in place: instead of upgrading to a new release every few years, you move the machine to a newer, versioned snapshot of its package repository. Its older sibling, Amazon Linux 2, is at the end of its support period: check the date before building anything new on it. AWS's own tools come preinstalled, which is handy on EC2 and irrelevant elsewhere.

1.8Lab: a server card

Lab 1 · Describe a machine without touching it

You'll write a small script that prints a one-page card for any Linux machine, run it, and read what it says, including what it says about the machine not being a normal server. You need a terminal on any Linux (Appendix C). Cost: nothing. Clean-up: delete the script; it changes nothing on the machine.

  1. Save the script as servercard.sh in your home directory. Every line is one command from Table 1.2 wrapped in echo; $( … ) means “run this and put its output here”, which Chapter 2 explains along with the pipes (|).

    servercard.shbash

    #!/usr/bin/env bash
# servercard.sh · a one-page description of this machine. It only reads; it changes nothing.

echo "== $(hostname) =="
echo "OS:        $(. /etc/os-release && echo "$PRETTY_NAME")"
echo "Kernel:    $(uname -r) on $(uname -m)"
echo "Up since:  $(uptime -s)"
echo "PID 1:     $(ps -o comm= -p 1)"
echo "CPUs:      $(nproc)"
echo "Memory:    $(free -h | awk '/^Mem:/ {print $2 " total, " $7 " available"}')"
echo "Root disk: $(df -h --output=size,pcent / | tail -1 | awk '{print $1 ", " $2 " used"}')"
echo "Addresses:"
ip -brief address | sed 's/^/  /'
echo "Listening on TCP:"
ss -tlnH | awk '{print "  " $4}' | sort -u
  2. Make it executable and run it: 
    chmod +x servercard.sh
./servercard.sh
    Here's what it printed on the machine this book's labs were tested on. Yours will differ, and that's the point: 
    == vm ==
OS:        Ubuntu 24.04.5 LTS
Kernel:    6.18.44-fc-v880 on x86_64
Up since:  2026-11-27 07:48:25
PID 1:     process_api
CPUs:      4
Memory:    15Gi total, 15Gi available
Root disk: 252G, 14% used
Addresses:
  lo               UNKNOWN        127.0.0.1/8 
  ifb0             DOWN           
  ifb1             DOWN           
  eth0             UP             192.0.2.2/24 
Listening on TCP:
  0.0.0.0:2024
  127.0.0.1:41381
  127.0.0.1:44513
  3. Read the card. This one has some surprises, and spotting them is the skill. The kernel's version string ends in -fc-…, not Ubuntu's usual -generic, and PID 1 is not systemd: it's a program called process_api. This machine is a lightweight virtual machine (a Firecracker microVM) whose provider boots its own kernel and its own small init program; Ubuntu supplies only the userland. That's a perfectly good Linux machine for most of this book's labs, but systemctl won't work on it, so the systemd chapters use a full VM instead. On a container you'd see something similar: PID 1 would be bash or your app. On a normal Ubuntu server you'd see systemd and a kernel such as 6.8.0-…-generic or …-aws.
  4. Compare running and installed kernels. Run uname -r and ls /boot. On a normal server, if /boot holds a vmlinuz- file with a newer version than uname -r, security fixes for the kernel are installed but not running. On a microVM or container, /boot may be empty or missing: the kernel comes from outside.
  5. Break it on purpose. Remove the execute permission and run the script again: 
    chmod -x servercard.sh
./servercard.sh; echo "exit status: $?"
    bash: ./servercard.sh: Permission denied
exit status: 126
    The kernel refused to run the file because its permissions don't allow it (Chapter 4), and the shell reports that with exit status 126 (Chapter 2). bash servercard.sh still works, because then the kernel runs bash, and bash merely reads the file. Put the permission back with chmod +x servercard.sh.

Stretch goals. (1) Add a line for “reboot pending” that prints yes if /var/run/reboot-required exists and no otherwise (hint: test -e, Chapter 2). (2) Add the number of running processes (ps -e --no-headers | wc -l). (3) Run the card on a second machine, or in a container (docker run --rm -it ubuntu:24.04), and list three differences.

1.9Common mistakes

MistakeWhat happensInstead
Running a release past its end of supportNew vulnerabilities are never fixed on that machine; nothing visibly breaks.Record the end-of-support date on day one; plan the move months ahead.
Choosing a non-LTS release for a serverSupport ends after nine months; you're forced into upgrades twice a year.Use an LTS (or the RHEL family's long releases) for servers.
Starting programs by hand on a serverThey don't come back after a reboot, and nobody knows how they were started.Run them as services (Chapter 6).
Installing kernel updates and never rebootingThe fixes are on disk but not running; months of exposure.Schedule reboots; check /var/run/reboot-required (Chapter 8).
Rebooting a server you don't understand to “see if it helps”Hand-started programs vanish; an outage becomes a mystery.Inventory first; reboot when you know what will start.
Changing things during the first lookYou can't tell your changes from what was there before.Read-only commands first, and write down what you find.

✓Chapter summary

  • The kernel is the only program that touches hardware; everything else asks it through system calls.
  • A distribution packages the kernel with a userland and a package manager, and supports each release for a stated number of years. Know the date for every server.
  • Boot goes firmware → bootloader → kernel → PID 1 (systemd) → services. Anything not started as a service won't come back after a reboot.
  • Cloud servers start from an image, and cloud-init turns it into your server at first boot from the user data you supply.
  • Inventory an unfamiliar server with read-only commands first; much of the answer comes from /proc and /sys.
  • Pets hold knowledge nobody wrote down. Move it into writing, then into scripts, then rebuild.

Key terms

Kernel
The program that runs the hardware and provides processes, memory, files, networking and permissions to everything else.
System call
A request from a program to the kernel, such as opening a file or starting a program.
Userland
Everything outside the kernel: init, shells, utilities, libraries and applications.
Distribution
A kernel, a userland and a package manager released and supported together, such as Ubuntu or Debian.
Release
A numbered version of a distribution whose packages receive fixes, not major changes, until its end of support.
LTS
Long-term support: a release meant to be run for years, with security updates for all of that time.
UEFI
The firmware on modern machines that checks hardware and starts the bootloader.
initramfs
A small temporary filesystem the kernel uses at boot to find and mount the real root filesystem.
systemd
The init system (PID 1) on most distributions; it starts and supervises services.
Image
A ready-made disk with an operating system installed, from which cloud VMs are launched.
cloud-init
The program on cloud images that configures a new instance at first boot from its user data.
Pet
A server built and repaired by hand, which can't easily be replaced; the opposite of cattle, built from a description.

Check your understanding

  1. Which of these is the kernel's job, and which is the distribution's: scheduling processes on CPUs, shipping a security fix for OpenSSL, deciding whether a program may open a file, providing ls? recall

    Show answer

    Kernel: scheduling processes and checking file permissions. Distribution: shipping the OpenSSL fix (as an updated package) and providing ls (part of the userland, from GNU coreutils). The distribution also ships the kernel itself as a package.

  2. uname -r prints 5.15.0-91-generic, and ls /boot shows vmlinuz-5.15.0-91-generic and vmlinuz-5.15.0-131-generic. What does that tell you, and what would you do? apply

    Show answer

    A newer kernel (131) is installed but the machine is still running the old one (91), so the kernel's security fixes since then aren't active. Plan a reboot, after checking that everything that should run is started as a service and will come back.

  3. Why does a program started by hand with nohup not come back after a reboot, while nginx does? explain

    Show answer

    After a reboot, the only programs that start are the ones PID 1 (systemd) is configured to start, plus their descendants. nginx is installed as a systemd service enabled at boot; the hand-started program was started by a person's shell, which no longer exists, and nothing records that it should run.

  4. A new VM launched from an Ubuntu image with your user data has no user rafaela. Where do you look first, and what might have gone wrong? debug

    Show answer

    Look at cloud-init's logs: /var/log/cloud-init-output.log and /var/log/cloud-init.log (and cloud-init status --long). Common causes: the file didn't start with #cloud-config, so it wasn't read as cloud-config; a YAML indentation error; or the user data was added to an instance that had already booted, and cloud-init only applies it at first boot.

  5. You've inherited a server nobody understands, and you've been asked to “tidy it up”. Write the first five things you'd do, in order. design

    Show answer

    One reasonable order: (1) record the release and its end of support, the kernel and uptime; (2) list running services and all running processes and find what was started outside systemd; (3) list listening ports and who logs in; (4) for each running program, find its config, data and logs; (5) write it all down, with the problems found, before changing anything. Only then start fixing, one written-down change at a time.

  6. Compare an Ubuntu LTS release with a RHEL major version as a choice for a server you expect to run for six years. compare

    Show answer

    Ubuntu LTS gives five years of standard security updates (more with Ubuntu Pro), so a six-year server either needs Pro or an upgrade along the way. A RHEL major version gets ten years, covering the whole period, at the cost of a subscription (or using a rebuild such as Rocky or AlmaLinux) and older package versions near the end. Either works; what matters is knowing the date and planning for it.
