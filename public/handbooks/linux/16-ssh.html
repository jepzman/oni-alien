SSH done right

SSH is how people get into Linux servers, so it's also how the wrong people get in. This chapter explains how SSH proves both the server's identity and yours, how to use keys, agents and jump hosts comfortably, how to harden the server side, and how to find and remove access that should no longer exist, the part most teams forget until someone finds it for them.

By the end you can

  • Explain host keys, user keys and what each side verifies.
  • Create a key, use an agent, and write an ssh_config with a jump host.
  • Harden sshd with a drop-in, and read its effective configuration.
  • Audit every authorized key on a server and remove a leaver's access completely.
  • Issue a short-lived SSH certificate, and compare it with keys and with session managers.

Before you start

  • Chapter 4 (users, locking accounts), Chapter 13 (netlab.sh) and Chapter 15 (firewalls).
  • Handbook 2, Chapter 2 (proving identity) and Chapter 15 (Session Manager) for the bigger picture.
  • A Linux VM with sudo, and sudo apt install openssh-server openssh-client.

16.1How SSH authenticates

An SSH connection proves two identities, in this order: the server proves it's the machine you meant, then you prove you're allowed in. Both use public-key cryptography (Handbook 2, Chapter 2).

  • The host key lives in /etc/ssh/ssh_host_*_key on the server. The first time you connect, your client shows its fingerprint and asks you to confirm it, then remembers it in ~/.ssh/known_hosts. This is trust on first use: check the fingerprint against one obtained another way (the provider's console output, a colleague, ssh-keygen -lf on the server) rather than typing “yes” from habit. If the key later changes, SSH refuses with a loud warning: the server was rebuilt, or someone is in the middle.
  • Your user key is a key pair you create. The public half goes into ~/.ssh/authorized_keys in the account you log in to, one key per line; the private half stays on your machine, protected by a passphrase. Logging in, the server checks that your key is listed (or that it's a certificate signed by a CA it trusts, 16.6) and the client proves it holds the private key by signing a challenge.
  • Then sshd checks the account: AllowUsers/AllowGroups, PermitRootLogin, and, through PAM, things like account expiry.

Watch out: a locked password doesn't lock SSH keys

usermod -L locks an account's password. On Ubuntu, where sshd uses PAM, a key login to a password-locked account still works, as the lab shows. Expiring the account (usermod -e 1) is what PAM refuses. And neither does anything about the person's key sitting in another account's authorized_keys, such as root's. Removing access means finding every key, not only locking the account.

16.2Keys and the agent

Create a key with ssh-keygen -t ed25519 -C "you@laptop". Ed25519 keys are short, fast and safe; RSA keys are fine at 3,072 bits or more, and needed only for very old servers. Always set a passphrase: it encrypts the private key on disk, so a stolen laptop or backup isn't a stolen login. The comment (-C) is just a label, but it's what makes an audit readable: name the person and the device.

Typing a passphrase for every connection gets old; ssh-agent fixes that. It holds your decrypted keys in memory and signs challenges on your behalf; you unlock each key once per session with ssh-add. ssh-add -l lists loaded keys; ssh-add -D forgets them; ssh-add -t 8h forgets after eight hours. Desktop environments and macOS start an agent for you. A hardware key (a FIDO2 security key, ssh-keygen -t ed25519-sk) goes further: the private key can't be copied at all, and each login needs a touch.

Watch out: agent forwarding

ssh -A (ForwardAgent yes) lets the remote server use your agent, so you can hop onwards with your key. It also lets anyone with root on that server use your agent for as long as you're connected. To reach a server through another, use a jump host (16.3) instead: the connection is tunnelled, and your keys never become usable on the middle machine.

16.3ssh_config and jump hosts

Everything you'd type on the command line can live in ~/.ssh/config, per host or for groups of hosts. The first value found for each setting wins, so specific Host blocks go before general ones. The lab's configuration:

ssh_configOpenSSH client configuration

# ssh_config for the lab · in real life, these lines go in ~/.ssh/config
Host door-2
    HostName 10.40.0.12
Host door-4
    HostName 10.40.0.14
    ProxyJump door-2                    # reachable only through door-2
Host door-*
    User tiago
    IdentityFile ~/lab16/id_tiago
    IdentitiesOnly yes                  # offer only this key, not every key the agent holds
    UserKnownHostsFile ~/lab16/known_hosts

With this, ssh door-4 works, and so do scp, rsync -e ssh and Ansible, which read the same file. A jump host (or bastion) is a server you connect through to reach others: ProxyJump (or ssh -J door-2 door-4) opens an SSH connection to door-2 and tunnels a second, end-to-end encrypted SSH connection through it to door-4. Authentication to door-4 happens from your laptop, with your key; door-2 only forwards encrypted bytes. That lets the database server accept SSH from the jump host alone (Chapter 15).

16.4Hardening sshd

Ubuntu's defaults are reasonable, but two of them are wrong for a server reached by a team. sudo sshd -T prints the effective configuration, every setting including defaults, which is the only reliable way to know what sshd will do. On a fresh Ubuntu 24.04 machine:

usepam yes
permitrootlogin without-password
pubkeyauthentication yes
passwordauthentication yes
kbdinteractiveauthentication no
x11forwarding yes

Password logins are on, and root may log in with a key (without-password is an old name for prohibit-password: “root by key only”). Change both, in a drop-in, never in the main file, which package upgrades may want to replace:

/etc/ssh/sshd_config.d/50-stagedoor.confsshd configuration

PermitRootLogin no                # people log in as themselves and use sudo (Chapter 4)
PasswordAuthentication no         # keys or certificates only: nothing to guess
KbdInteractiveAuthentication no
AllowGroups ssh-users             # only members of this group, whatever keys exist elsewhere
MaxAuthTries 3
X11Forwarding no
AllowAgentForwarding no
LogLevel VERBOSE                  # log the fingerprint of the key used for each login

Then sudo sshd -t (test: it prints nothing if the configuration is valid), and sudo systemctl reload ssh. As with firewalls (Chapter 15), keep your current session open and test with a new one before you log out. With LogLevel VERBOSE, every login names the key that was used, in /var/log/auth.log and the journal; without it, an audit can tell you who logged in, but not with which of their keys.

Key idea

One identity per person (no shared accounts, no root logins), keys or certificates only, and a list of who may log in that's enforced by sshd, not by hoping the key files are clean.

16.5Auditing and removing access

A server's real access list is every line of every authorized_keys file, plus every account that has a password, plus whatever sshd's configuration allows. Audit it regularly, and always when someone leaves:

sudo sh -c 'for f in /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys; do
  [ -f "$f" ] && { echo "== $f"; ssh-keygen -lf "$f"; }; done'
sudo grep -h "Accepted" /var/log/auth.log*                 # who logged in, with which key (VERBOSE)
sudo lastlog | grep -v "Never logged in"                  # each account's last login

When someone leaves, removing their access is a checklist, not a command: expire their account (usermod -e 1) and lock its password; remove their keys from every authorized_keys, their own and any shared ones; revoke any certificates they hold (16.6); check crontab -l -u and running processes for anything of theirs; change any shared secret they knew; and look at the logs for their keys' fingerprints. Logs only go back as far as they're kept, which is why Chapter 7 ships them somewhere with longer retention.

16.6Beyond keys: certificates and session managers

Keys in authorized_keys never expire and live on every server, which is how Marco's lasted two years. Two better models are common:

  • SSH certificates. An SSH certificate is a user's public key signed by a user CA, with a principal (the account it's for), an identity for the logs and a validity period. Servers trust the CA once (TrustedUserCAKeys) and need no authorized_keys at all. Each morning, a person gets a certificate valid for, say, eight hours, after signing in to the company's identity provider; when they leave, nothing needs to be removed from servers, because tomorrow they simply don't get a certificate. Tools such as Smallstep, Teleport and HashiCorp Vault run the CA; the lab does it by hand with ssh-keygen.
  • Session managers. AWS Systems Manager Session Manager (Handbook 2, Chapter 15), Azure Bastion and Google Cloud's IAP TCP forwarding open a shell through the provider's API, authorised by cloud IAM and recorded, with no SSH port open at all. On the cloud, this is often the best answer for people; SSH remains for automation and for machines outside the cloud.

16.7Brute force and noise

Any server with SSH open to the internet receives password guesses within minutes of booting: auth.log fills with “Invalid user admin”. With PasswordAuthentication no, these attempts can't succeed, and they're noise rather than a threat. Restricting the source with a firewall or security group (only the VPN or office), or not exposing SSH at all (a session manager), removes the noise too. Tools like fail2ban, which ban addresses after repeated failures, help with logs and load, but they're not what keeps you safe; keys are.

16.8Across distributions

On the RHEL family and Amazon Linux

The service is sshd, not ssh (sudo systemctl reload sshd), and recent releases also read drop-ins from /etc/ssh/sshd_config.d/. SELinux checks that authorized_keys files have the right label: a file copied in from elsewhere may be ignored until restorecon -R ~/.ssh. Amazon Linux and RHEL cloud images log in as ec2-user with the key pair chosen at launch, installed by cloud-init (Chapter 1). Ubuntu's default PermitRootLogin is prohibit-password; check every distribution's with sshd -T rather than assuming.

    #!/usr/bin/env bash
# sshlab.sh up|down · run a lab sshd inside door-2 and door-4 (run "netlab.sh up" first)
set -euo pipefail
dir=/etc/ssh/lab

up() {
  install -d -m 755 "$dir" /run/sshd
  install -m 644 sshd_lab.conf "$dir/sshd_lab.conf"
  touch "$dir/user_ca.pub"                                   # filled in later, in the certificate step
  for h in door-2:10.40.0.12 door-4:10.40.0.14; do
    name=${h%%:*} addr=${h##*:}
    install -d -m 755 "$dir/keys-$name"                       # this server's authorized_keys, one file per user
    [ -f "$dir/$name.key" ] || ssh-keygen -q -t ed25519 -N '' -C "$name host key" -f "$dir/$name.key"
    ip netns exec "$name" /usr/sbin/sshd -f "$dir/sshd_lab.conf" \
      -o "HostKey=$dir/$name.key" -o "ListenAddress=$addr" \
      -o "AuthorizedKeysFile=$dir/keys-$name/%u" -E "/var/log/sshd-$name.log"
    echo "sshd on $name ($addr), host key $(ssh-keygen -lf "$dir/$name.key.pub" | cut -d' ' -f2)"
  done
}

down() {
  pkill -f "sshd -f $dir/sshd_lab.conf" || true
  rm -rf "$dir" /var/log/sshd-door-2.log /var/log/sshd-door-4.log
  echo "lab sshd stopped"
}

case "${1:-}" in
  up) up ;;
  down) down ;;
  *) echo "usage: sudo $0 up|down" >&2; exit 2 ;;
esac

✓Chapter summary

  • SSH authenticates the server with its host key (checked against known_hosts, trust on first use) and then you with your key (checked against authorized_keys or a trusted CA), then checks the account.
  • Use Ed25519 keys with passphrases and an agent; reach inner servers with ProxyJump, not agent forwarding.
  • Harden sshd with a drop-in: no root logins, no passwords, AllowGroups, LogLevel VERBOSE. Check with sshd -t and sshd -T.
  • A locked password doesn't stop key logins; expire the account and remove every key, everywhere. Audit keys regularly.
  • SSH certificates expire by themselves and need no keys on servers; session managers need no SSH port at all.

Key terms

Host key
The key pair that identifies an SSH server; clients remember its public half in known_hosts.
Trust on first use
Accepting a server's key the first time you connect, and checking it on every later connection.
authorized_keys
The file listing the public keys allowed to log in to an account.
ssh-agent
A program that holds decrypted private keys in memory and signs authentication challenges on your behalf.
Jump host
A server you connect through to reach others, with the inner connection tunnelled end to end (ProxyJump).
SSH certificate
A public key signed by an SSH CA, with principals and a validity period, accepted by servers that trust the CA.
Session manager
A cloud service that opens a shell on a VM through the provider's API, authorised by IAM, without an open SSH port.

    Host db / HostName 10.40.0.14 / User rafaela / ProxyJump rafaela@jump.stagedoor.example / IdentityFile ~/.ssh/id_stagedoor / IdentitiesOnly yes. (A separate Host jump.stagedoor.example block can set its own user and key.)

  3. Explain why an attacker who has root on a jump host can use your agent if you connect with ssh -A, but not if you use ProxyJump. explain

    Show answer

    With agent forwarding, the jump host gets a socket connected to your agent, and anyone with root there can ask your agent to sign logins to other servers while you're connected. With ProxyJump, the jump host only forwards an encrypted TCP stream; the inner SSH session's authentication happens between your laptop and the target, so the jump host never has access to your agent or keys.

  4. After you add PasswordAuthentication no to /etc/ssh/sshd_config and reload, ssh -o PubkeyAuthentication=no server still offers a password prompt. What's the likely cause, and how do you confirm? debug

    Show answer

    Another file sets it first: in sshd, the first value obtained wins, and Include /etc/ssh/sshd_config.d/*.conf at the top of the main file reads drop-ins (such as a cloud image's 50-cloud-init.conf with PasswordAuthentication yes) before your line. Confirm with sudo sshd -T | grep passwordauthentication and grep -r PasswordAuthentication /etc/ssh/; put your setting in an earlier-sorting drop-in or fix the other file. (Also check KbdInteractiveAuthentication.)

  5. Design SSH access for Stagedoor's servers so that a leaver's access ends without anyone editing files on servers. design

    Show answer

    Servers trust a user CA (TrustedUserCAKeys) and have no personal authorized_keys; AllowGroups limits who may log in. People get short-lived certificates (for example eight hours) from the CA after signing in through the company identity provider with MFA; leaving means being removed from the identity provider, after which no new certificates are issued and old ones expire within hours. SSH is reachable only from the VPN or through a jump host; logins are logged with the certificate ID and shipped centrally. On AWS, Session Manager can replace the people part entirely.

  6. Compare authorized_keys keys, SSH certificates and a session manager for a ten-person team. compare

    Show answer

    Keys: simple, no infrastructure, but never expire and must be added and removed on every server. Certificates: one CA trusted by all servers, short-lived credentials, leavers age out; needs a CA and a way to issue certificates safely. Session manager: no SSH port, IAM-controlled and recorded access, nothing on servers to manage; only for that cloud's VMs and requires its agent. Many teams use a session manager for people and certificates or keys for automation.
