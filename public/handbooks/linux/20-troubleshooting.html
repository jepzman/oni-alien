A troubleshooting method

The chapters so far each explained one thing that can go wrong. Real incidents don't arrive labelled: “the site is slow” could be any of them, or none. This chapter turns the book into a method: describe the symptom precisely, ask what changed, sweep every resource for utilisation, saturation and errors, and confirm before you act, with a script that gathers the first five minutes of facts in one go.

By the end you can

  • Turn a vague report into a precise, testable symptom.
  • Apply the USE method (utilisation, saturation, errors) to CPU, memory, disk, network and limits.
  • Collect the first five minutes of evidence on a Linux server with one script, and read it.
  • Find what changed, act with the smallest safe step, and verify.
  • Write an incident note that helps the next person.

Before you start

  • Part III (Chapters 9–12) above all; Chapters 5–7 and 13–14 help.
  • A VM with systemd and sudo; sudo apt install sysstat.

At Stagedoor

Tiago has seen Rafaela do this a dozen times, and she has left him something better than memory: a script and a page in the wiki called “The first five minutes”. He logs in to door-2 and runs it.

20.1From a report to a symptom

“It's slow” isn't something you can test. Before touching a server, turn the report into a symptom you could check and later prove fixed.

  • What, exactly? Which page, API call or job; slow or failing; what error, if any.
  • For whom? Everyone, one venue, one region, mobile only? A problem for some users points at what those users share.
  • Since when? The start time is the most valuable fact you can get, because it can be matched against changes.
  • How much? Ten seconds instead of 300 milliseconds; 5% of requests failing. Measure it yourself (curl -w '%{time_total}', Chapter 14) so you can tell when it's fixed.

20.2The USE method

Brendan Gregg's USE method gives you a checklist that doesn't depend on guessing: for every resource, check its utilisation (how busy it is), saturation (how much work is waiting for it) and errors. A resource with high saturation or errors is a suspect; one that's idle with nothing waiting can be crossed off. Part III gave you the commands; here they are in one table:

Table 20.1 · USE on one Linux server

Key idea

Check every resource, not the one you suspect. The resource that's saturated is often not the one the symptom points to.

20.3The first five minutes

Under pressure, people check what they checked last time. A script doesn't: it runs the whole sweep in the same order every time, changes nothing, and produces one screen you can paste into the incident channel. The lab's first5.sh is one; adapt it to your servers. Then read the output in the order of Figure 20.1:

Read first5.sh's output top to bottom, comparing each number with what you know is normal (which is why it's worth running on a calm day too, as the lab does): the load against the CPU count, vmstat's r, b, wa and si/so, available memory, space and inodes, busy disks and their queues, the busiest processes by CPU and by I/O, processes stuck in D, listen-queue overflows, failed units, recent errors, and the kernel's own complaints. Usually one or two lines stand out; the rest rule things out, which is just as useful.

20.4What changed?

Most incidents follow a change: a deploy, a configuration edit, a timer that now runs at a different time, more traffic, a dependency that changed under you. Match the symptom's start time against:

journalctl --since "19:00" --until "19:45" -p notice     # everything notable on this server in the window
systemctl list-timers --all                             # what runs on a schedule, and when it last ran
grep -h " install \| upgrade " /var/log/dpkg.log | tail   # package changes
last -n 10; sudo journalctl -u ssh --since today | grep Accepted   # who logged in
git -C ~/ops log --since "2 days ago" --oneline        # changes to the operations repository

And outside the server: the deploy history, the provider's status page, the dependencies' dashboards. “Nothing changed” is a hypothesis to check, not a fact.

20.5Act small, verify, write it down

  • Mitigate first. Stop the harm with the smallest, most reversible step: stop a job, roll back a deploy, move traffic to another server. The root cause can wait until users are fine.
  • One change at a time, each noted with its time, so you know which one worked and can undo the others.
  • Verify with the same measurement you used for the symptom: the page loads in 300 ms again, not “the load went down”.
  • Write it down while it's fresh: the timeline, what you saw, what you did, what you're not sure of. A short, blameless incident review afterwards asks how the system let it happen and what would catch it earlier, not who to blame. Every chapter's story in this book ends with exactly that kind of note.

Watch out: restarting as diagnosis

Restarting a service or rebooting a server often makes a symptom go away, and takes the evidence with it: the stuck process, the full queue, the open file. Collect the first five minutes first (it takes about twenty seconds), then restart if that's the right mitigation. And if a restart “fixed” it, the cause is still there.

20.6When it isn't this server

A server that's healthy by every USE check can still be slow for its users, because it's waiting on something else: the database, a payment provider, DNS. Signs: requests take long but the CPUs are idle, wa is low and nothing is in D; many connections sit in ESTABLISHED to one address (ss -tn). Follow the dependency: run the same sweep on the next machine, or the connection method from Chapter 14 towards it. Doing this across many services at once is what metrics, traces and dashboards are for; Handbook 7 picks up there.

20.7Across distributions

History, not just now

Every tool in this chapter exists on every distribution; sysstat has to be installed on Ubuntu, Debian and Amazon Linux. Enable its collector (sudo systemctl enable --now sysstat) and it records CPU, memory, disk and network every ten minutes, so sar -d -f /var/log/sysstat/sa13 (on RHEL, /var/log/sa/sa13) can answer “what was the disk doing at 19:40 last Friday?” after the fact. On the cloud, the provider's agent sends the same numbers to its monitoring service.

20.8Lab: the mystery slow box

Lab 20 · Be the on-call engineer

You'll run the first-five-minutes script on a calm machine, then start a hidden problem without reading how it works, find it with the script and the USE method, confirm it, and stop it. You need a VM with systemd, sudo and sudo apt install sysstat; ideally Lab 18's app running, so there's something to look at. Cost: nothing. Clean-up: sudo ./mystery.sh stop; the problem also stops by itself after ten minutes. Outputs come from a fresh systemd test container named door-2.

  1. The script. Save as ~/lab20/first5.sh and make it executable:

    first5.shbash

    #!/usr/bin/env bash
# first5.sh · the first five minutes on a slow server: one screen of facts, nothing changed
set -uo pipefail                      # no -e on purpose: one failing check mustn't stop the others

section() { printf '\n== %s\n' "$1"; }

section "load ($(nproc) CPUs)"
uptime
section "CPU, run queue, blocked, swap, I/O wait: vmstat 1 5 (skip the first line)"
vmstat 1 5
section "memory"
free -h
section "space and inodes on /"
df -h /; df -i /
section "busy disks: utilisation and latency (iostat, second report)"
iostat -dx 1 2 | awk '
  /^Device/ { n++; for (i = 1; i <= NF; i++) col[$i] = i; if (n == 2) print "device  w/s  wkB/s  w_await  aqu-sz  %util"; next }
  n == 2 && NF && $col["%util"] > 0 { print $1, $col["w/s"], $col["wkB/s"], $col["w_await"], $col["aqu-sz"], $col["%util"] }'
section "top processes by CPU"
ps -eo pid,user,pcpu,pmem,stat,comm --sort=-pcpu | head -6
section "processes waiting on the disk (state D)"
ps -eo pid,user,stat,wchan:22,comm | awk 'NR == 1 || $3 ~ /D/'
section "processes doing disk I/O (pidstat, 3 seconds)"
pidstat -d 1 3 | awk '/^Average/ && ($4 + $5 > 0 || $NF == "Command")'
section "network: sockets and listen-queue overflows"
ss -s | head -2; nstat -az TcpExtListenOverflows | tail -1
section "failed units"
systemctl --failed --no-legend --no-pager
section "errors in the journal, last 15 minutes"
journalctl -p err --since -15min --no-pager -q | tail -5
section "kernel: OOM kills, I/O errors, hung tasks (last hour)"
journalctl -k --since -1h --no-pager -q | grep -iE 'killed process|i/o error|blocked for more' | tail -5
    No set -e: a check that fails (a tool not installed, say) mustn't hide the others. Only reading commands: it's safe to run on any server, at any time.

    ps -eo pid,ppid,etime,args | grep "[t]humbs-cleanup" | cut -c1-150
        384       1       00:44 timeout 600 bash -c while :; do /var/tmp/lab20/thumbs-cleanup if=/dev/zero of=/var/tmp/lab20/.cache bs=1M count=400 oflag=
    385     384       00:44 bash -c while :; do /var/tmp/lab20/thumbs-cleanup if=/dev/zero of=/var/tmp/lab20/.cache bs=1M count=400 oflag=direct statu
    491     385       00:00 /var/tmp/lab20/thumbs-cleanup if=/dev/zero of=/var/tmp/lab20/.cache bs=1M count=400 oflag=direct status=none
    A loop (PID 385) started 44 seconds ago, under timeout, that runs thumbs-cleanup again and again, each run writing 400 MB straight to disk. Each run lives only a fraction of a second, so pidstat credits most of the I/O to the parent loop. On a real server, the next questions are “what started the loop?” (ps -o ppid up the tree, systemctl status <pid> names the unit) and “since when?” (etime, the journal).
  6. Act and verify. Stop it, then run first5.sh again and compare with calm.txt: 
    sudo ./mystery.sh stop
    stopped
    Now read the mystery:

    mystery.shbash

    #!/usr/bin/env bash
# mystery.sh start|stop · make this machine slow in one particular way. Don't read it before the lab!
set -euo pipefail
dir=/var/tmp/lab20
case "${1:-}" in
  start)
    mkdir -p "$dir"
    cp /usr/bin/dd "$dir/thumbs-cleanup"                    # a familiar-sounding name
    nohup timeout 600 bash -c "while :; do $dir/thumbs-cleanup if=/dev/zero of=$dir/.cache bs=1M count=400 oflag=direct status=none; done" >/dev/null 2>&1 &
    echo "started: something is now slowing this machine down (it stops by itself after 10 minutes)" ;;
  stop)
    pkill -f "$dir/thumbs-cleanup" || true
    pkill -f "while :; do $dir/thumbs-cleanup" || true
    rm -rf "$dir"
    echo "stopped" ;;
  *) echo "usage: sudo $0 start|stop" >&2; exit 2 ;;
esac
    A copy of dd under a reassuring name: a reminder that a process's name tells you what someone called it, not what it does (/proc/<pid>/exe tells you what it is).

Skipping “what changed?”The cause sits in a deploy log nobody opened.Match the start time against changes, every time.

✓Chapter summary

  • Turn reports into a precise symptom: what, for whom, since when, how much.
  • The USE method checks utilisation, saturation and errors for every resource, so you don't depend on a hunch.
  • A first-five-minutes script runs the whole sweep, read-only, the same way every time; compare it with a calm baseline.
  • Ask what changed; confirm a candidate before acting; mitigate with the smallest safe step; verify with the original measurement.
  • Write it down, blamelessly. If this server is healthy, follow the dependency.

Key terms

USE method
A troubleshooting checklist: for every resource, check utilisation, saturation and errors.
Utilisation
The proportion of time, or of capacity, a resource is busy.
Saturation
The amount of work waiting for a resource because it's busy, such as a run queue or a disk queue.
Mitigation
An action that stops or reduces an incident's harm, separate from fixing its root cause.
Baseline (performance)
The normal values of a system's measurements, recorded when it's healthy, for comparison during incidents.
Blameless review
A write-up after an incident that examines how the system allowed it, not who to blame.

Check your understanding

  1. Give the utilisation, saturation and errors checks for memory. recall

    Show answer

    Utilisation: free -h, mainly available. Saturation: swapping (si/so in vmstat 1) and memory pressure (/proc/pressure/memory). Errors: OOM kills in journalctl -k or dmesg.

  2. A venue says “checkout is broken”. Write four questions that turn this into a symptom you can test. apply

    Show answer

    What exactly happens: an error message, a spinner, a wrong total? For which events, devices, payment methods? Since when, and is it every time or sometimes? Can you reproduce it, and how long does it take (time a request yourself with curl)? Also: is it only that venue?

  3. Explain why a script that changes nothing is preferable to a person typing commands during an incident. explain

    Show answer

    Under pressure, people skip steps and check what they suspect. A script checks everything, in the same order, in seconds, produces output that can be compared with a baseline and shared, and can't make things worse because it only reads. It also lets less experienced people do a thorough first look.

  4. first5.sh shows idle CPUs, low I/O wait, nothing in D, free memory and space, but users still wait ten seconds per request. What do you look at next? debug

    Show answer

    The server is probably waiting on something else. Look at where its requests go: ss -tnp for many connections to one address (a database, an API), the app's logs for slow downstream calls, then the dependency itself, with the same sweep or the connection method from Chapter 14. Also check limits that don't show as resource use: connection pools, accept queues, worker counts.

  5. Design the “first five minutes” page for Stagedoor's wiki. design

    Show answer

    Step 0: write the symptom and its start time in the incident channel. Step 1: run first5.sh on the affected server(s) and paste the output, next to the latest calm baseline. Step 2: check what changed: deploys, timers, config commits, the provider's status. Step 3: USE reading guide (which lines matter and what's normal for each server). Step 4: common mitigations with their commands (stop a job, roll back, take a server out of the load balancer). Step 5: notes template. Plus who to call, and when.

  6. Compare mitigating by restarting the app with mitigating by stopping the job that's saturating the disk. compare

    Show answer

    Restarting the app might briefly help, interrupts users and in-flight requests, destroys evidence and leaves the cause (the job) running, so the symptom returns. Stopping the job addresses the confirmed cause directly, is reversible (it can run again later) and keeps the app's state. Mitigate at the cause you've confirmed.
