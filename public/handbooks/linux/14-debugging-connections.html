Debugging connections

“It can't connect” is the most common sentence in operations, and the least informative. This chapter gives you a method: five questions, asked in order, each answered by one tool, from the name to the application. Then it takes apart TLS, the layer that fails most often for reasons that have nothing to do with the network, and shows how to watch the packets themselves when nothing else explains what's happening.

By the end you can

  • Locate a connection failure layer by layer: name, route, port, TLS, application.
  • Read curl -v output and curl's exit codes.
  • Inspect a server's certificate, chain and expiry with openssl.
  • Capture and read the packets of one connection with tcpdump.
  • Set up certificate renewal and expiry monitoring so certificates don't expire by surprise.

Before you start

  • Chapter 13: addresses, routes, sockets, name resolution, and its netlab.sh.
  • Handbook 1, Chapter 6 (HTTP, TLS and certificates) helps.
  • A Linux VM with sudo, and sudo apt install curl openssl tcpdump dnsutils netcat-openbsd dnsmasq-base.

At Stagedoor

At a second venue, the same. Staff start checking names against printed lists, and the queues reach the street.

Rafaela is on call. The rest of Stagedoor works. The scanners talk to one API, scan.stagedoor.example, served by nginx on the two web servers. From her laptop, the API's address resolves, the port answers, and her browser shows a full-page warning. She has the cause within five minutes, because she asks the questions in order.

14.1A method: five questions in order

Every connection passes through the same layers, and each one can fail independently. Start at the bottom and stop at the first layer that fails: everything above it is a symptom.

  1. Name. getent hosts scan.stagedoor.example on the machine that fails (Chapter 13), and dig to see what DNS says. Is it the address you expect?
  2. Route. ip route get ADDRESS; ping if ICMP is allowed (many cloud firewalls block it, so a failed ping proves little); traceroute -T -p 443 ADDRESS to see how far packets get, using TCP so firewalls treat it like real traffic.
  3. Port. nc -zv -w 3 ADDRESS 443: “succeeded”, “Connection refused” (nothing listening) or a timeout (dropped on the way). The difference between the last two is the most useful fact in network debugging (Chapter 13).
  4. TLS. openssl s_client -connect ADDRESS:443 -servername NAME (14.3).
  5. Application. curl -v (14.2), and the server's own logs for the same request.

Run the checks from the machine that fails, or as close to it as you can. From your laptop, a different resolver, different routes and different firewall rules may give different answers, which is useful information in itself: if it works from here and not from there, the difference is in what's between.

14.2curl, verbosely

curl -v narrates every layer of one request: the address it resolved, the TCP connection, the TLS handshake and certificate, the HTTP request and response headers. Lines starting with * are curl's own commentary, > what it sent, < what it received. A few options make it a precise instrument:

curl -v https://scan.stagedoor.example/health                     # the whole story
curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' URL     # just status and time
curl --resolve scan.stagedoor.example:443:10.40.0.12 URL          # this name, but at this address (test one server)
curl --connect-timeout 3 --max-time 10 URL                        # fail fast instead of hanging
curl -H 'Host: scan.stagedoor.example' http://10.40.0.12/          # a virtual host by IP (plain HTTP)

--resolve deserves a special mention: it connects to an address you choose while keeping the real name for TLS and HTTP, so you can test one server behind a load balancer, or a new server before DNS points at it, with exactly the request a client would make. And curl's exit status names the layer that failed:

Watch out: curl -k

-k (--insecure) skips certificate checks. It's fine for one look at what a server is sending; it never belongs in a script, a health check or application code, because it turns a broken certificate (or an attacker's) into a working connection. If a script needs a private CA, give it --cacert.

14.3TLS and certificates from the command line

A TLS client checks four things about the server's certificate (Handbook 1, Chapter 6): it's within its validity dates; it's issued for the name the client asked for (in the Subject Alternative Name); it chains, through any intermediate certificates the server sends, to a root CA the client trusts; and it hasn't been revoked. Most failures are the first three:

Table 14.2 · Certificate errors and what they mean
Error (curl / openssl)MeansUsual fix
certificate has expired / num=10now is after notAfterrenew; automate renewal
no alternative certificate subject name matches / num=62wrong name: a certificate for another hostright certificate for the name, or the right server block in nginx
unable to get local issuer certificate / num=20the client can't chain it to a root it trustssend the intermediate (fullchain.pem), or install a private CA on clients
self-signed certificate / num=18nobody vouches for it but itselfa certificate from a CA
certificate is not yet valid / num=9now is before notBefore, often a client clock that's wrongfix the clock (timedatectl, NTP)

openssl s_client shows the server's side of the handshake, the chain it sent and the result of verification:

openssl s_client -connect scan.stagedoor.example:443 -servername scan.stagedoor.example </dev/null
openssl s_client -connect HOST:443 -servername HOST </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
openssl x509 -in /etc/ssl/stagedoor/fullchain.pem -noout -enddate    # a certificate file on disk
openssl x509 -in cert.pem -noout -checkend 1814400                   # exit 1 if it expires within 21 days

Always pass -servername: it sends SNI, the name the client wants, and servers hosting several names pick the certificate by it. Without it, you may be looking at the wrong certificate and draw the wrong conclusion.

14.4Certificates that renew themselves

Certificates expire on purpose: short lifetimes limit the damage of a stolen key, and public certificates are getting shorter (under the CA/Browser Forum's schedule, at most 200 days since March 2026, 100 days from March 2027 and 47 days from March 2029, at the time of writing). A certificate renewed by a person once a year is an incident with a date already set, and it tends to land on whoever was on the renewal email. The fix is to stop renewing by hand:

  • ACME, the protocol Let's Encrypt created and many CAs support, lets a program prove control of a domain and get a certificate without a person. certbot (or acme.sh, or Caddy and Traefik, which do it built-in) installs a systemd timer that renews certificates about 30 days before expiry and reloads nginx.
  • Managed certificates on a cloud load balancer (AWS Certificate Manager, Azure and Google's managed certificates) renew themselves, as long as their DNS validation records stay in place.
  • Monitoring is separate from renewal. Check every public endpoint's expiry from outside, daily, and alert at 21 days. A renewal job can fail silently (a changed DNS record, a firewall rule, a full disk); the monitor is how you find out while there are still three weeks left.

Key idea

Renew automatically, and monitor expiry independently of the renewal. Either one alone eventually fails on a Sunday.

14.5Looking at packets

When every tool says something different, look at what actually crosses the wire. tcpdump captures packets on an interface, filtered by an expression, and prints one line per packet:

sudo tcpdump -i eth0 -nn 'host 10.40.0.14 and tcp port 5432'   # one conversation
sudo tcpdump -i any -nn -c 20 'tcp[tcpflags] & tcp-syn != 0'     # only connection attempts
sudo tcpdump -i eth0 -nn -w capture.pcap 'port 443'              # save for Wireshark

-nn keeps addresses and ports as numbers (no DNS lookups, which would themselves create traffic); -c stops after a number of packets. Each TCP line shows source and destination as address.port, then the flags: [S] SYN (open), [S.] SYN-ACK, [.] ACK, [P.] data pushed, [F.] FIN (close), [R] reset. The patterns tell the story at a glance:

  • [S], then nothing, then [S] again a second later: the SYN is being dropped (a firewall, or a wrong route back). That's a timeout in the making.
  • [S] answered by [R.]: refused, nothing listening.
  • A full handshake, a little data, then [R] from the server: the application or a proxy cut the connection.

Capture on the server and the client at the same time when you can: a SYN that leaves one and never arrives at the other was dropped in between. For TLS traffic, you'll see the handshake's packets but not the contents; that's the point of TLS.

14.6Across distributions

curl, OpenSSL, tcpdump and the dig family behave the same everywhere; the package names differ (dnsutils or bind9-dnsutils on Debian and Ubuntu, bind-utils on RHEL), and nc comes in two flavours with different options (netcat-openbsd on Ubuntu, nmap-ncat on RHEL). Where they differ is the system's trust store, the list of root CAs every program trusts:

On the RHEL family

Ubuntu and Debian keep trusted CAs in /etc/ssl/certs/; you add a private CA by copying it into /usr/local/share/ca-certificates/ (with a .crt extension) and running sudo update-ca-certificates. RHEL and Amazon Linux use /etc/pki/ca-trust/source/anchors/ and sudo update-ca-trust. Some programs ignore the system store entirely: Java has its own keystore, Python's requests uses the certifi bundle unless told otherwise, and Node.js needs NODE_EXTRA_CA_CERTS.

14.7Lab: an expired certificate, found in order

Lab 14 · Sunday 13 September, on your machine

You'll create a private CA and a certificate for scan.stagedoor.example that expired at 17:59 Lisbon time on 13 September 2026, serve it from door-4 in the lab network, find the failure layer by layer, replace it, add an expiry check, and capture one plain HTTP request with tcpdump. You need Chapter 13's netlab.sh and the packages in the chapter card. Cost: nothing. Clean-up: the last step. (Run it before 13 September 2026 and the “expired” certificate won't be expired yet: change the dates in mkcerts.sh to a past range.)

  1. Make the certificates. In ~/lab14, save and run:

    mkcerts.shbash

set -euo pipefail
mkdir -p ca/newcerts && touch ca/index.txt && echo 1000 > ca/serial
echo "unique_subject = no" > ca/index.txt.attr          # allow two certificates for the same name

[ca]

[lab]

new_certs_dir = $dir/newcerts
serial = $dir/serial
default_md = sha256
policy = any

[any]

CNF

# 1. the certificate authority (CA): a key and a self-signed certificate
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 3650 \
  -subj "/CN=Stagedoor Lab CA" -keyout ca.key -out ca.pem 2>/dev/null

# 2. the server's key and a certificate request for its name
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -subj "/CN=scan.stagedoor.example" -addext "subjectAltName=DNS:scan.stagedoor.example" \
  -keyout server.key -out server.csr 2>/dev/null

# 3. the CA signs it twice: once with dates in the past, once valid for 90 days from now
sign() {  # sign OUTFILE START END, dates as YYMMDDHHMMSSZ
  openssl ca -batch -config ca/ca.cnf -cert ca.pem -keyfile ca.key -in server.csr \
    -out "$1" -startdate "$2" -enddate "$3" -notext 2>/dev/null
}

sign valid.pem "$(date -u +%y%m%d%H%M%SZ)" "$(date -u -d '+90 days' +%y%m%d%H%M%SZ)"

✓Chapter summary

  • Debug a connection bottom-up: name (getent, dig), route (ip route get), port (nc -zv), TLS (openssl s_client), application (curl -v). Stop at the first failure.
  • curl -v narrates every layer; its exit code names the layer that failed; --resolve tests one server under its real name.
  • Certificates fail on dates, names and chains. openssl s_client -servername and openssl x509 -dates show which.
  • Renew certificates automatically (ACME, managed certificates) and monitor expiry separately.
  • tcpdump -nn shows the packets: unanswered SYNs mean drops, SYN then RST means refused.

Key terms

SNI
Server Name Indication: the host name a TLS client sends in its first message, so a server can choose the right certificate.
Certificate chain
The server certificate plus the intermediate certificates that link it to a trusted root CA.
Trust store
The set of root CA certificates a system or program trusts.
ACME
The protocol for obtaining and renewing certificates automatically, used by Let's Encrypt and others.
tcpdump
A command-line packet capture tool that prints or saves packets matching a filter.
TCP flags
Bits in a TCP segment that mark its role: SYN (open), ACK, PSH (data), FIN (close), RST (reset).

Check your understanding

  1. curl fails with exit code 6. Which layer failed, and what's the first command you'd run? recall

    Show answer

    Name resolution (“couldn't resolve host”). Run getent hosts NAME on the same machine, then dig NAME and resolvectl status to see which resolver it uses and what it answers.

  2. You've built a replacement web server, 10.40.0.15, not yet in DNS. Write the curl command that requests https://tickets.stagedoor.example/health from it, with full certificate checking. apply

    Show answer

    curl -v --resolve tickets.stagedoor.example:443:10.40.0.15 https://tickets.stagedoor.example/health. The connection goes to the new server, while SNI, certificate checks and the Host header use the real name.

  3. Explain why a site can work in a desktop browser and fail in curl and in a phone app with “unable to get local issuer certificate”. explain

    Show answer

    The server is sending its certificate without the intermediate. Some desktop browsers have the intermediate cached, or fetch it themselves from the certificate's AIA field, so they can complete the chain; curl and most apps don't, so they can't link the certificate to a trusted root. Configure nginx with the full chain.

  4. tcpdump on a client shows [S] to the server's port 443 repeated after 1, 3 and 7 seconds, with no reply. On the server, the same capture shows nothing. Where's the problem? debug

    Show answer

    Between the two: the SYN leaves the client and never reaches the server's interface. Check the path: the client's route, cloud security groups and network ACLs, any firewall or load balancer in between. If the server had seen the SYN and not answered, the server's own firewall would be the suspect (Chapter 15).

  5. Design certificate management for Stagedoor's public names after 13 September. design

    Show answer

    Every public name gets an ACME certificate (certbot or a managed certificate on a load balancer), renewed automatically about 30 days before expiry with a hook that reloads nginx and distributes the certificate to every server that needs it. An external daily check of every endpoint alerts 21 days ahead and on any verification error. CA and registrar accounts use a shared operations address. A list of all names and where their certificates live is kept in the wiki.

  6. Compare curl -v and openssl s_client for debugging a TLS problem. compare

    Show answer

    curl -v shows the whole request as a client would make it, including HTTP, and reports the verification result in one line. openssl s_client shows the TLS layer in detail: every certificate in the chain the server sent, each verification step with its error number, the negotiated protocol and cipher, and lets you extract the certificate for openssl x509. Start with curl; use s_client when the problem is the certificate or the handshake.
