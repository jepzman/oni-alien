Files and the filesystem layout

On a Linux server, nearly everything you'll configure, read or fix is a file in one big tree, and the tree has conventions: configuration here, data there, logs somewhere else. This chapter teaches the map, what a file really is underneath its name, and how links let you switch a whole application to a new version in one step.

By the end you can

  • Say where configuration, programs, data, logs and temporary files belong, and why.
  • Read every column of ls -l, and explain what an inode is.
  • Choose between a hard link and a symbolic link, and switch a release atomically with a symlink.
  • Find files by name, type, size and age with find.
  • Design a filesystem layout for your own application.

Before you start

  • Chapter 2: commands, quoting, pipes.
  • A Linux terminal as a normal (non-root) user (Appendix C).

At Stagedoor

In the week of 9 February 2026, Rafaela and Tiago set out to answer a simple question about door-2: where does the app live? nginx's configuration points at /srv/app. That turns out to be a link to /root/stagedoor, a Git checkout in the root user's home directory. In it: the code, a .env file with the database password, a venv directory, and nohup.out, 6.1 GB of everything the app has printed since it was last started. Deploying means logging in as root, running git pull in that directory, and restarting the app by hand.

Tiago asks the obvious question: what happens to a request that arrives while git pull is halfway through replacing files? Nobody knows. Section 3.7 is the answer they agree on.

3.1One tree

Linux has no drive letters. Every file on the machine sits somewhere in one tree that starts at /, the root directory. Other disks, network shares and special filesystems are attached to the tree at a directory, called a mount point (Chapter 11), and from then on look like ordinary directories.

Where things go in that tree isn't arbitrary. The Filesystem Hierarchy Standard (FHS) describes the layout every mainstream distribution follows, and once you know it you can find your way around any server, including one somebody else built.

3.2What goes where

The reason this matters is practical. A layout that follows the convention tells everyone, including tools, what each file is: backups include /etc and /var/lib; log rotation looks in /var/log; a security scanner expects /usr to change only when packages do. An app living in /root, with its secrets, data and logs in one directory, defeats all of them at once.

The /usr mergeUbuntu, Debian 12+, Fedora, RHEL and Amazon Linux have merged /bin, /sbin and /lib into /usr: the old names are symbolic links (3.5) to /usr/bin and so on. Both paths work.

3.3Everything is a file

“Everything is a file” is the oldest Unix slogan, and it's nearly true: the kernel presents many different things through the same interface of names in the tree that you can open, read and write. The first character of ls -l says which kind you're looking at:

Table 3.2 · File types
ls -lTypeExample
-regular file: bytes on a disk/etc/hostname, a program, a log
ddirectory: a list of names/etc
lsymbolic link: a name pointing to another path/bin → usr/bin
c, bcharacter and block devices: hardware, or kernel features, as files/dev/null, /dev/vda
ssocket: a connection point between programs/run/postgresql/.s.PGSQL.5432
pnamed pipe: a pipe (Chapter 2) with a namerare on servers

The files under /proc and /sys are a special case: they're regular files whose contents the kernel generates at the moment you read them. That's why ls -l /proc/loadavg shows a size of 0, and file calls it “empty”, while cat /proc/loadavg prints the current load. They're the kernel's dashboard, and many tools you'll meet (ps, free, top) are mostly readers of /proc.

3.4Inodes, names and ls -l

A file's name is not the file. On Linux filesystems, a file is an inode: a numbered record that holds everything about the file (its type, owner, permissions, size, timestamps and where its data blocks are on the disk) except its name. A directory is just a table that maps names to inode numbers. ls -i shows the inode number next to each name.

With that picture, every column of ls -l makes sense:

599380 -rw-r--r-- 2 tiago tiago 13 Nov 27 08:02 a.txt
│      │          │ │     │     │  │            └ the name, from the directory
│      │          │ │     │     │  └ modification time
│      │          │ │     │     └ size in bytes
│      │          │ │     └ group
│      │          │ └ owner
│      │          └ link count: how many names this inode has
│      └ type, then permissions (Chapter 4)
└ inode number (shown with ls -i)

stat shows the rest of the inode, including three timestamps: modify (the contents changed), change (the inode changed: permissions, owner, link count) and access (last read, often updated lazily to save writes). Note what's missing: there's no “creation time” you can rely on across filesystems, and none of the timestamps records who made the change. Accountability comes from logs (Chapter 7, Chapter 18), not from the filesystem.

3.5Hard links and symbolic links

Because names and inodes are separate, one file can have several names. There are two ways to do it, and they behave very differently:

Table 3.3 · Hard links and symbolic links compared
Hard link (ln target name)Symbolic link (ln -s target name)
What it isanother directory entry for the same inodea separate tiny file whose contents are a path
Delete the original namethe file lives on under the other namethe link now points nowhere (“dangling”)
Across filesystemsno: inode numbers are per filesystemyes: it's only a path
To a directorynot allowedallowed, and common
You can tell it's a linkonly from the link countls -l shows name -> target
Typical usebackup tools, package managers, saving space“current version”, compatibility names, config enabled from a library of files

Symbolic links (symlinks) are the ones you'll create on purpose. A relative target (releases/2026.02.1) is resolved from the directory the link is in, not from where you are; an absolute one (/opt/stagedoor/releases/2026.02.1) from /. Prefer relative targets inside one application's directory, so the whole tree can be moved or copied.

Switching versions with one rename

Symlinks make a clean deployment pattern possible. Install each version of an application into its own directory, never touching it again, and point a symlink called current at the live one. Everything else (the service, nginx, cron jobs) refers only to …/current. Deploying is: unpack the new version next to the old one, then point current at it. Rolling back is pointing it back.

The switch must be atomic: at every instant, current must point to one complete version, never to nothing and never to half of each. The kernel guarantees exactly that for one operation: renaming a name over an existing one, within one filesystem, replaces it in a single step. So the safe way is to create the new link under a temporary name and rename it over the old one:

ln -s releases/2026.02.2 current.new
mv -T current.new current            # -T: treat "current" as the name to replace, not a directory to move into

You'll often see ln -sfn releases/2026.02.2 current instead. Whether that's atomic depends on the version: the one on Ubuntu 24.04 creates a temporary link and renames it, as the lab shows with strace, while older versions removed the old link first and created the new one after, leaving a moment with no current at all. mv -T is atomic everywhere, so deploy scripts should use it.

Key idea

Never change a running application's files in place. Put the new version beside the old one, and switch with a single rename.

Running programs that already loaded the old code keep using it until they restart; that's a feature, and Chapter 5 shows how to restart them without dropping requests.

3.6Finding things

find walks a tree and tests every entry. Its arguments read as a sentence: where to start, then tests, then optionally an action (the default is to print the path).

find /etc -name '*.conf'                    # by name; quote the pattern so the shell doesn't expand it
find /var/log -type f -size +100M           # regular files over 100 MB
find /var/log -type f -mtime +30            # modified more than 30 days ago
find . -newer deploy.marker                 # changed since a reference file was touched
find / -xdev -type d -perm -0002            # world-writable directories on the root filesystem (Chapter 4)
find /tmp -user tiago -type f -delete       # an action: delete what matched. Run without -delete first!

Searching from / touches /proc and network mounts unless you add -xdev (stay on one filesystem), and prints “Permission denied” for directories you can't read unless you add 2>/dev/null or use sudo. For the other common questions: type cmd or command -v cmd finds a program on PATH; grep -rl 'pattern' /etc/nginx finds files containing a text; dpkg -S /usr/sbin/nginx says which package installed a file (Chapter 8); and readlink -f path follows every symlink to the real file.

Watch out: deleted is not freed

Deleting a file removes a name. If a running program still has the file open, the inode and its data stay on the disk until the program closes it or exits, even though no name points to it any more. Deleting a huge log that nginx or your app is still writing frees nothing, and the disk stays full. The lab shows how to see such files; Chapter 7 and Chapter 11 show how to free the space.

3.7A layout for your own application

Put the convention to work. For an application you deploy yourself (not from a distribution package), a layout that follows the FHS looks like this:

Table 3.4 · Stagedoor's app layout, agreed in February 2026
WhatWhereWhy there
Each release's code and its Python environment/opt/stagedoor/releases/2026.02.1/self-contained, never modified after it's unpacked
The live release/opt/stagedoor/current → releases/…one atomic rename to deploy or roll back
Configuration and secrets/etc/stagedoor/stagedoor.envoutside the code, so a release can't overwrite it; readable only by the app (Chapter 4)
Data the app keeps/var/lib/stagedoor/ (uploads in …/uploads)survives every deploy; included in backups
Logs/var/log/stagedoor/where log rotation and log shipping look (Chapter 7)
Runtime files/run/stagedoor/sockets and PID files; cleared at boot

Notice what this buys. A deploy can't destroy uploads or overwrite configuration, because they aren't in the release directory. Old releases stay on disk for instant rollback (keep the last few; delete older ones). Backups need only /etc/stagedoor and /var/lib/stagedoor. And nothing lives in a person's home directory, so nobody's account is load-bearing.

At Stagedoor: the new layout

Rafaela and Tiago write Table 3.4 into the wiki and try it on a copy of door-2's app first. The git pull question answers itself: a request arriving mid-deploy is served entirely by the old release or entirely by the new one, never by a mixture. Leonor likes the rollback most: “so going back is one command, not a git revert at 10:02 on a Friday?”

Two things have to happen before the app can move out of /root: it needs its own user, so the files can belong to something other than root (Chapter 4), and it needs to be a service, so something other than a person's terminal starts it (Chapter 6). The 6.1 GB nohup.out stays for now, with a note: still open by the app; deleting it frees nothing.

3.8Across distributions

The FHS is shared, so the big directories are the same everywhere. The differences are in where particular programs put their files:

Table 3.5 · Same idea, different paths
Ubuntu, DebianRHEL family, Amazon Linux
Defaults for a service's options/etc/default/<name>/etc/sysconfig/<name>
nginx sites/etc/nginx/sites-available/, enabled by a symlink in sites-enabled//etc/nginx/conf.d/*.conf
nginx's default web root/var/www/html/usr/share/nginx/html
PostgreSQL's data/var/lib/postgresql/<version>/main/var/lib/pgsql/data
System log file/var/log/syslog/var/log/messages

On the RHEL family

SELinux labels every file with a security context, and a file in an unexpected place can be refused even when its permissions are right. Moving an app to /opt or /srv on RHEL may need semanage fcontext and restorecon so nginx may read it; ls -Z shows the labels. Chapter 18 explains why this extra layer is worth having.

3.9Lab: names, inodes and a release switch

Lab 3 · Take a file apart, then deploy with a symlink

You'll look at real system files, watch a hard link outlive its original name and a symlink dangle, build Table 3.4's release layout in your home directory and switch it atomically, and catch a deleted file that still uses disk space. You need a Linux terminal as a normal user, Python 3, and optionally strace (sudo apt install strace). Cost: nothing. Clean-up: rm -r ~/lab3.     echo "app runs as root" >> b.txt

    door-2 notes
app runs as root
599380 -rw-r--r-- 1 tiago tiago 30 Nov 27 08:02 b.txt
    The text written through b.txt was there in a.txt, and removing a.txt only dropped the link count to 1. The data is untouched.
  3. A symbolic link, and how it breaks. 
    ln -s b.txt c.txt
ls -l c.txt

app runs as root

    The symlink stores the name b.txt. Renaming the target left it pointing at nothing. (A hard link would have followed, because it refers to the inode, not the name.)

  5. Deploy atomically: create the new link under another name, then rename it over the old one. 
    cd opt/stagedoor

    Rolling back is the same two commands with the old version.
  6. Optional: watch what ln -sfn does. strace prints the system calls a program makes (Chapter 1). Roll back with ln -sfn and watch: 
    strace -e trace=symlinkat,unlinkat,renameat,renameat2 ln -sfn releases/2026.02.1 current

symlinkat("releases/2026.02.1", AT_FDCWD, "Cuojojq4") = 0

releases/2026.02.1
    This version tried to create current, found it existed, made the link under a random temporary name, and renamed it over current: atomic. On an older system (Ubuntu 22.04, for example) run the same command and look for an unlinkat of current before the symlinkat: that gap is the moment with no link.
  7. Find things. Every symlink under the lab, and every VERSION file newer than notes.txt: 
    cd ~/lab3
find . -type l

    The broken c.txt still shows up: it's a symlink, whether or not its target exists. find . -xtype l lists only broken ones.
  8. Break it on purpose: delete a file that's still open. Start a small program that writes 10 MB to app.log and keeps the file open, the way an app keeps its log open. Then delete the file and look at the program's open files in /proc: 
    python3 -c 'import time; f = open("app.log", "a"); f.write("x" * 10_000_000); f.flush(); time.sleep(600)' &
sleep 1
ls -l app.log
rm app.log
ls -l /proc/$!/fd | grep deleted
kill $!
    -rw-r--r-- 1 tiago tiago 10000000 Nov 27 08:02 app.log
l-wx------ 1 tiago tiago 64 Nov 27 08:02 3 -> /home/tiago/lab3/app.log (deleted)
    $! is the process ID of the last program started in the background. Its file descriptor 3 (Chapter 2) still points at the file, marked (deleted): the 10 MB are still on the disk, and stay there until the kill ends the program. That's Stagedoor's nohup.out, in miniature.

Stretch goals. (1) Run stat notes.txt, then chmod o-r notes.txt and stat again: which timestamp changed, and why not the other? (2) Write a three-line script deploy.sh VERSION that switches current atomically and refuses to run if releases/VERSION doesn't exist. (3) Find the five largest files in your home directory: find ~ -type f -printf '%s %p\n' | sort -rn | head -5.

3.10Common mistakes

MistakeWhat happensInstead
Running an app from a home directoryThe app depends on a person's account; secrets, code and data mix./opt for code, /etc for config, /var/lib and /var/log for data and logs.
Deploying with git pull or cp into the live directoryRequests during the deploy see half-old, half-new code.Unpack beside the old release; switch a symlink with mv -T.
Keeping anything important in /tmpCleaned at boot or by a timer; readable by others if careless./var/lib/<app>; for scratch files, mktemp (Chapter 17).
Deleting a big log to free spaceThe app keeps it open; the space isn't freed.Truncate it (: > file) or rotate and signal the app (Chapter 7).
Absolute symlinks inside an app's treeCopying or moving the tree leaves links pointing at the old place.Relative targets within the app's directory.
find … -delete or -exec rm without a dry runDeletes more than you meant; there's no undo.Run the same find without the action first and read the list.

✓Chapter summary

  • Everything is in one tree from /. Programs live in /usr, configuration in /etc, changing data in /var; /proc, /sys, /dev and /run are made by the kernel.
  • Follow the convention for your own app: code in /opt, config in /etc, data in /var/lib, logs in /var/log.
  • A file is an inode; names are directory entries pointing at it. ls -l shows the inode's type, permissions, link count, owner, size and time.
  • A hard link is another name for the same inode; a symbolic link is a small file holding a path, and can dangle.
  • Switch releases atomically: new symlink under a temporary name, then mv -T over the old one.
  • Deleting a file that a program has open frees nothing until the program closes it.

Key terms

Root directory
The top of the single filesystem tree, written /.
FHS
The Filesystem Hierarchy Standard: the conventional layout of directories on Linux.
Mount point
The directory where another filesystem is attached to the tree.
Inode
The record of a file's type, owner, permissions, size, times and data location; everything except its name.
Hard link
An additional directory entry pointing to the same inode.
Symbolic link
A small file containing a path to another file or directory; also called a symlink.
Atomic operation
A change that happens completely or not at all, with no in-between state visible to others; renaming within a filesystem is atomic.
/proc
A filesystem generated by the kernel that shows processes and kernel state as files.

Check your understanding

  1. Where would you expect to find: nginx's configuration, PostgreSQL's data files, the python3 program, and a process's list of open files? recall

    Show answer

    /etc/nginx/; /var/lib/postgresql/… (on Ubuntu and Debian); /usr/bin/python3; /proc/<pid>/fd/.

  2. ls -l shows -rw-r----- 3 postgres postgres 8192 Feb 9 10:02 0001. What does the 3 tell you, and what doesn't ls tell you about it? apply

    Show answer

    The inode has three names (hard links), somewhere on the same filesystem. ls doesn't say where the other two names are; ls -i gives the inode number, and find / -xdev -inum <number> finds them.

  3. Explain why mv -T current.new current is safe during a deploy, and why rm current; ln -s releases/new current isn't. explain

    Show answer

    A rename within one filesystem replaces the old name in a single step, so any lookup of current finds either the old link or the new one. With rm then ln, there's a moment when current doesn't exist, and a request or a service restart in that moment fails.

  4. The disk on a server is full. You delete a 6 GB log file, but df still says 100%. Why, and how do you confirm it? debug

    Show answer

    A running process still has the file open, so its inode and data aren't freed. Confirm with ls -l /proc/*/fd 2>/dev/null | grep deleted or lsof +L1, which list open files with no names left. The space comes back when that process closes the file or is restarted; next time, truncate or rotate instead of deleting (Chapter 7).

  5. Design the layout for a small Go service called scanner that keeps a local cache of ticket barcodes and writes a log. Say where each part goes. design

    Show answer

    Binary per release in /opt/scanner/releases/<version>/ with a current symlink; configuration in /etc/scanner/; the barcode cache in /var/cache/scanner/ if it can be rebuilt from the server, otherwise /var/lib/scanner/; logs in /var/log/scanner/ (or the journal, Chapter 7); a socket or PID file in /run/scanner/.

  6. Compare a hard link and a symbolic link for keeping a “latest backup” name that always points to the newest backup file. compare

    Show answer

    A symlink suits it: it's visibly a pointer, can be switched atomically, and works across filesystems. A hard link would work only on the same filesystem, wouldn't show which backup it is without comparing inode numbers, and would keep an old backup's data alive after the backup itself was “deleted”.
