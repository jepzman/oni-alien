systemd: services, units and timers

A program you started by hand runs until something stops it. A service runs because the machine was told it should: started at boot, restarted when it crashes, stopped gracefully, logged, and limited. This chapter turns a hand-started app into a systemd service, explains the unit files behind every service on the machine, and replaces a fragile cron job with a timer.

By the end you can

  • Write a service unit that runs an app as its own user, with its configuration, umask and restart policy.
  • Start, stop, enable and inspect services with systemctl, and find out why one failed.
  • Override a packaged unit safely with a drop-in file.
  • Explain the difference between ordering (After=) and requirement (Wants=, Requires=).
  • Replace a cron job with a timer, and avoid the PATH and time-zone traps of scheduled jobs.

Before you start

  • Chapter 5: processes, signals, graceful shutdown. Chapter 4: users, umask.
  • A Linux machine where PID 1 is systemd: a VM or cloud server, not a plain container (Appendix C). Check with ps -o comm= -p 1.

6.1What systemd does

systemd is PID 1 on almost every Linux server (Chapter 1). It starts everything else, and it keeps doing a job for every service afterwards: a service manager, or supervisor.

Everything systemd manages is a unit, described by a small text file. The unit's type is its file extension: .service (a program), .timer (a schedule), .target (a group of units, like a milestone in the boot), .socket, .mount, .path. Unit files live in three places, and the order matters:

Table 6.1 · Where unit files live
DirectoryWho writes itWins over
/etc/systemd/system/you, the administratoreverything below
/run/systemd/system/programs, at runtime; gone at rebootpackages
/usr/lib/systemd/system/ (also /lib/…)packages; overwritten on upgradenothing

Never edit a file under /usr/lib: the next package upgrade replaces it. Put your own units in /etc/systemd/system/, and change a packaged one with a drop-in (6.4).

6.2A service unit, line by line

Here is the unit Rafaela and Tiago wrote for Stagedoor's app. It's the same one the lab installs, with a stand-in app:

/etc/systemd/system/stagedoor.servicesystemd unit

[Unit]
Description=Stagedoor ticketing app
After=network-online.target
Wants=network-online.target

[Service]
Type=exec
User=stagedoor
Group=stagedoor

ExecStart=/usr/bin/python3 /opt/stagedoor/current/app.py
Restart=on-failure
RestartSec=2
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target

LineMeans
[Unit] Description=the name shown in status and logs
After=network-online.target
Wants=network-online.target		start after the network is configured, and ask for that milestone to be reached (6.5)
Type=execthe service is “started” once the program has been executed successfully. simple (the default) doesn't even wait for that; notify waits for the app to say it's ready; oneshot is for jobs that run and finish

Restart=on-failure, RestartSec=2restart if it exits with an error or is killed by a signal, after 2 seconds; not after a clean stop

Notice what isn't there: no nohup, no &, no PID file, no redirection to a log. The app runs in the foreground and writes to standard output; systemd does the rest. That's the right shape for any program you write for a server, and for containers too.

Key idea

A server program should run in the foreground, log to standard output, and exit cleanly on SIGTERM. The service manager handles starting, restarting, stopping and logging.

Two states are easy to confuse. Enabled means “starts at boot”; active means “running now”. A service can be either without the other, and after a reboot only enabled services come back. On a server you've inherited, compare systemctl list-unit-files --state=enabled with what's actually running.

Watch out: restart loops

A service that fails immediately and has Restart=on-failure is restarted, fails, is restarted again: a restart loop. systemd stops it if it's started more than five times in ten seconds (StartLimitBurst=, StartLimitIntervalSec=), and then refuses to start it again with “Start request repeated too quickly” until you run systemctl reset-failed. With a long enough RestartSec=, the limit is never reached and the loop goes on for ever, filling the journal. Watch the restart counter in the log.

6.4Changing a unit: drop-ins

To change one setting of a unit, especially one a package installed, don't copy the whole file. Add a drop-in: a file in /etc/systemd/system/<unit>.d/ ending in .conf, containing just the sections and lines you want to change. sudo systemctl edit nginx opens an editor on /etc/systemd/system/nginx.service.d/override.conf and runs daemon-reload for you; or write the file and reload yourself.

# /etc/systemd/system/nginx.service.d/limits.conf: raise nginx's file-descriptor limit (Chapter 12)
[Service]
LimitNOFILE=65536

Drop-ins survive package upgrades, and systemctl cat shows the original and every drop-in together, so the next person can see exactly what you changed. Most settings in a drop-in replace the original's; list settings such as ExecStart= add to it, so to replace a command you first clear it with an empty line, ExecStart=, then give the new one.

6.5Dependencies and the boot

systemd starts units in parallel wherever it can, so the order has to be stated. Two separate kinds of relationship do that, and mixing them up is the most common unit-file mistake:

Boot milestones are targets. multi-user.target is “the normal server is up” (what WantedBy= usually names); network-online.target is “the network is configured”, which matters for an app that connects to a database on another machine at start-up. systemctl list-dependencies multi-user.target shows the tree, and systemd-analyze blame shows what made the last boot slow.

Even with the right order, a dependency on another machine can't be guaranteed: the database on door-1 might be restarting when door-2 boots. Apps should retry their connections for a while rather than exit on the first failure; Restart=on-failure is a safety net, not a substitute.

6.6Scheduled jobs: cron and timers

cron has run scheduled jobs on Unix since the 1970s, and you'll find it on every server. A line in a crontab (crontab -e for your user; files in /etc/cron.d/ for the system) has five time fields and a command: 0 3 * * * /opt/jobs/payouts.sh means 03:00 every day. It's simple, and it has three traps that all bit Stagedoor at once:

  • A minimal environment. cron doesn't read your shell's startup files. On Debian 11 and older releases, cron's PATH is only /usr/bin:/bin; newer versions, such as Ubuntu 24.04's, inherit a fuller one, which is exactly why a job can work on one server and not on the next. Your ~/.bashrc variables aren't there either.
  • Output goes to mail. Anything a job prints is emailed to the crontab's owner, which on most servers means a local mailbox nobody reads, or nowhere at all. A failing job fails silently.
  • No memory. If the machine was off or rebooting at 03:00, the job simply doesn't run that night. And two runs can overlap if one takes longer than the interval.

A systemd timer is a unit that starts another unit on a schedule. The job itself becomes an ordinary oneshot service, so it gets everything a service gets: a user, an environment, limits, its output in the journal with a timestamp and an exit status, and systemctl start to run it now, exactly as the schedule would.

Table 6.4 · cron and timers compared
cronsystemd timer
Schedule0 3 * * *OnCalendar=*-*-* 03:00:00 Europe/Lisbon

Run it now, the same waycopy the command and hope the environment matchessystemctl start payouts.service

Watch out: which time zone?

Cloud servers usually run in UTC, and both cron and timers use the machine's time zone unless told otherwise. Portugal is UTC in winter and UTC+1 in summer, so “03:00” on a UTC server is 03:00 in Lisbon for half the year and 04:00 for the other half. Write the zone into the timer (OnCalendar=… Europe/Lisbon) when the time matters to people, and check it with systemd-analyze calendar.

6.7A first look at sandboxing

Because systemd starts the process, it can also take things away from it before it starts. A few lines in the [Service] section shrink what a compromised app could do:

# can't gain privileges, e.g. through setuid programs (Chapter 4)
NoNewPrivileges=yes
# the whole filesystem is read-only to it, except these paths
ProtectSystem=strict
ReadWritePaths=/var/lib/stagedoor /var/log/stagedoor
# /home and /root are invisible; its own empty /tmp
ProtectHome=yes
PrivateTmp=yes

Comments in unit files go on lines of their own: systemd reads anything after the = as the value, so NoNewPrivileges=yes # comment is an invalid setting that is logged and ignored.

systemd-analyze security stagedoor scores a unit and lists what else could be restricted. Chapter 18 hardens Stagedoor's units this way; add these lines one at a time and test after each, because an app that writes somewhere unexpected will fail with “Read-only file system”.

6.8Across distributions

Ubuntu, Debian, the RHEL family and Amazon Linux all use systemd, so units, systemctl and timers are the same. Versions differ (Ubuntu 24.04 has systemd 255, Debian 11 has 247, RHEL 9 has 252), and a few newer settings don't exist on older ones: systemd-analyze verify on the target machine catches that. Package-provided services differ in name: ssh on Ubuntu is sshd on RHEL, cron is crond.

On containers and minimal systems

Containers normally don't run systemd: the container's main process is PID 1, and the container runtime or Kubernetes does the supervising, restarting, stopping and logging (Chapter 19). The ideas carry over directly: run in the foreground, log to standard output, handle SIGTERM. Alpine Linux uses OpenRC instead of systemd, and a few minimal distributions use others; their service files look different, but do the same jobs.

6.10Common mistakes

MistakeWhat happensInstead
Editing a unit under /usr/lib/systemdThe next package upgrade silently undoes it.A drop-in in /etc/systemd/system/<unit>.d/.
Forgetting daemon-reloadsystemd keeps using the old unit; it warns in status.Reload after every change (or use systemctl edit).
start without enableRuns now, gone after the next reboot.enable --now.

✓Chapter summary

  • systemd starts, supervises, stops, logs and limits services. Everything it manages is a unit.
  • Your units go in /etc/systemd/system/; change packaged ones with drop-ins; daemon-reload after every change.
  • A service unit names the user, environment, working directory, command (full path), restart policy and stop timeout. The app stays in the foreground and logs to standard output.
  • Enabled means it starts at boot; active means it runs now.
  • Wants=/Requires= pull units in; After=/Before= order them. Use both when you need both.
  • A timer runs a oneshot service on a schedule, with a known environment, logs, missed-run catch-up and a time zone; cron has none of these by default.

Key terms

Service manager
The program (systemd on most servers) that starts, supervises, restarts and stops services.
Unit
Anything systemd manages, described by a unit file: a service, timer, target, socket, mount or path.
Unit file
The text file that describes a unit, in sections such as [Unit], [Service] and [Install].
Drop-in
A small .conf file in a unit's .d/ directory that overrides or adds settings.
Target
A unit that groups other units into a milestone, such as multi-user.target.
Enabled
Hooked into a target so that the unit starts automatically at boot.
Restart loop
A service that fails at start and is restarted repeatedly by its restart policy.
Timer
A systemd unit that starts another unit on a schedule or after a delay.
cron
The traditional scheduler that runs commands from crontab files at given times.

Check your understanding

  1. A service is enabled but inactive (dead). What do those two words tell you? recall

    Show answer

    It will be started at the next boot (enabled), but it isn't running now (inactive): someone stopped it, or it finished or failed without a restart policy. systemctl status and journalctl -u show which.

  2. Write a drop-in that makes nginx restart automatically if it crashes, without touching the packaged unit. Where does the file go? apply

    Show answer

    /etc/systemd/system/nginx.service.d/restart.conf containing [Service], Restart=on-failure and, say, RestartSec=2; then sudo systemctl daemon-reload. systemctl cat nginx confirms it's applied.

  3. Explain why a unit with only After=postgresql.service may start before PostgreSQL on one machine and never start PostgreSQL at all on another. explain

    Show answer

    After= only orders: if both are being started in the same transaction, this unit waits. If PostgreSQL isn't enabled, nothing pulls it in, so it never starts. Add Wants= (or Requires=) to pull it in, and keep After= for the order.

  4. After you fix a typo in a unit and run systemctl restart, you get “Start request repeated too quickly”. What happened, and what do you run? debug

    Show answer

    The broken unit had been in a restart loop; with your restart, it crossed the start limit (by default five starts in ten seconds), so systemd refuses further starts. Run sudo systemctl reset-failed <unit>, then start it. Make sure you ran daemon-reload after fixing the file.

  5. Design a timer for a backup that must run once a night at 02:30 Lisbon time, must never run twice at once, and must run after a reboot if the machine was off at 02:30. design

    Show answer

    A backup.service with Type=oneshot, its own user and full paths, and a backup.timer with OnCalendar=*-*-* 02:30:00 Europe/Lisbon and Persistent=true, enabled with systemctl enable --now backup.timer. systemd never starts a service that's already running, so runs can't overlap; check with systemd-analyze calendar and test with systemctl start backup.service.

  6. Compare running an app with nohup … & and as a systemd service, for a reboot, a crash, a deploy and a question about last night's logs. compare

    Show answer

    Reboot: nohup doesn't come back; an enabled service does. Crash: nohup stays dead; the service is restarted. Deploy: with nohup someone signals and restarts by hand; the service gets systemctl restart with SIGTERM and a timeout. Logs: nohup.out grows without timestamps or limits; the journal stores timestamped, per-service logs with retention (Chapter 7).
