Part IV · Networking from the host

Host firewalls

A service that listens on a network address can be reached by anything that can route to it, unless something says no. This chapter shows how Linux filters packets, how to write a small default-deny ruleset with nftables (and its friendlier front end, ufw), how to test it without locking yourself out, and how a host firewall relates to the security groups of a cloud network.

By the end you can

  • Explain where netfilter's hooks sit in a packet's path, and what a stateful firewall remembers.
  • Write, check and load an nftables ruleset that denies inbound traffic by default.
  • Choose between dropping and rejecting, and predict what a client sees for each.
  • Use ufw for simple hosts, and know what it generates underneath.
  • Explain how a host firewall and a cloud security group divide the work.

Before you start

  • Chapter 13 (listening sockets, refused vs timed out) and its netlab.sh.
  • Handbook 1, Chapter 9 (security groups and network ACLs) for the cloud side.
  • A Linux VM with sudo, and sudo apt install nftables ufw netcat-openbsd.

At Stagedoor

In September 2026, a group of twelve venues asks Stagedoor for a security assessment before signing a contract, and Joana hires a small firm to test the servers. Their report arrives on Tuesday 6 October. The first finding is short: from either web server, every listening port on every other server is reachable. From door-3, the testers could reach PostgreSQL on door-4 (needed), SSH on every server from every other server (not needed), and a metrics exporter on port 9100 on door-4 that nobody remembered installing, which lists the database's settings to anyone who asks.

Atlantica's private network has no firewall between one customer's servers, and none of Stagedoor's servers has one of its own. If either web server, the machines that face the internet, were ever compromised, nothing would stand between the attacker and the database but its password.

15.1Netfilter: where packets are checked

Linux filters packets in the kernel, with a framework called netfilter. It offers hooks, points in a packet's path where rules can inspect it and decide: accept, drop, reject, or change it. Tools only differ in how you write the rules.

Netfilter's rules have been written with several tools over the years: iptables (since 2001, still everywhere in documentation), and nftables (nft), its replacement, the default on current Debian, Ubuntu and RHEL. On modern systems, the iptables command is usually iptables-nft, a compatibility layer that writes nftables rules, so both can be seen with nft list ruleset. Front ends such as ufw (Ubuntu) and firewalld (RHEL) generate the rules for you.

Netfilter is stateful: its connection tracking (conntrack) remembers every connection it has seen, so a rule can say “accept anything that belongs to a connection we already accepted”. That one rule is what lets a server with a strict inbound policy still receive the replies to its own outgoing connections, its DNS answers and its package downloads.

15.2An nftables ruleset, line by line

nftables organises rules into tables (a namespace for your rules; family inet covers IPv4 and IPv6 together), chains (lists of rules attached to a hook, with a default policy) and rules, evaluated top to bottom until one decides. Sets hold lists of addresses or ports a rule can match in one step. Here's the ruleset Stagedoor wrote for door-4:

door4.nftnftables

#!/usr/sbin/nft -f
# door4.nft · inbound firewall for the database server: deny by default, allow what's needed
flush ruleset

table inet filter {
    set web_servers {
        type ipv4_addr
        elements = { 10.40.0.12, 10.40.0.13 }
    }

    chain input {
        type filter hook input priority filter; policy drop;

        ct state established,related accept       # replies to connections already allowed
        ct state invalid drop
        iif "lo" accept                            # the machine talking to itself
        ip protocol icmp accept                    # ping and error messages such as "fragmentation needed"

        tcp dport 22 ip saddr 10.40.0.1 accept comment "SSH from the admin network"
        tcp dport 5432 ip saddr @web_servers accept comment "PostgreSQL from the web servers"

        counter comment "everything else is dropped"
    }
}
  • flush ruleset removes all existing rules first, so loading the file always gives exactly this ruleset, whatever was there before.
  • policy drop on the input chain is default deny: a packet that no rule accepts is dropped (Handbook 2, Chapter 1 used the same idea for permissions).
  • The first rule accepts packets of established connections (and related ones, such as ICMP errors about them). Without it, every reply to an outgoing connection would be dropped, as the lab shows.
  • Loopback is always allowed: programs on the server talk to each other on 127.0.0.1.
  • ICMP is allowed, because blocking it all breaks path-MTU discovery (Handbook 1, Chapter 3) and ping, which the next person debugging will want.
  • Then one rule per thing that should be reachable, from where. Each has a comment saying why.
  • The final counter counts what falls through to the policy: a cheap way to see how much is being dropped.

Load it with sudo nft -f door4.nft, after checking it with sudo nft -c -f door4.nft (-c: parse and check, change nothing). sudo nft list ruleset shows what's loaded; sudo nft -a list ruleset adds each rule's handle, for deleting single rules. To load it at boot, put it in /etc/nftables.conf (Debian and Ubuntu's location) and enable the service: sudo systemctl enable --now nftables.

Key idea

Deny inbound by default, accept established connections first, then allow each service only from the sources that need it, with a comment saying why.

15.3Drop or reject?

A firewall can refuse a packet in two ways, and the client notices the difference:

  • Drop: discard silently. The client hears nothing and retries until it times out, seconds later. Scanners learn little; legitimate clients that are blocked by mistake hang.
  • Reject: discard and answer, with a TCP reset (reject with tcp reset) or an ICMP “unreachable”. The client fails at once with “Connection refused”, indistinguishable from nothing listening.

A common compromise: drop by default (the policy), and reject on the specific ports where internal clients should fail fast rather than hang. Whichever you choose, remember Chapter 13's rule the other way round: a timeout points at a dropping firewall; a refusal may be a rejecting one, not only an empty port.

15.4Not locking yourself out

The classic firewall accident is a rule that cuts off the SSH session you're typing in. On a cloud server, that means the provider's serial console, or a rescue instance. Four habits prevent it:

  1. Accept established connections first. Your current SSH session is an established connection; with that rule at the top, a mistake further down usually spares it.
  2. Check before loading: nft -c -f.
  3. Load with an automatic undo: save the current rules (sudo nft list ruleset > /root/rules.before), schedule their return (echo "nft -f /root/rules.before" | sudo at now + 5 minutes, or sudo systemd-run --on-active=5min nft -f /root/rules.before), load the new ones, and cancel the undo only once you've opened a new SSH session successfully.
  4. Keep a second way in: the provider's console, or a session manager that doesn't depend on SSH (Chapter 16).

15.5ufw: the simple front end

ufw (“uncomplicated firewall”), installed on Ubuntu but inactive by default, writes rules for you from short commands:

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.40.0.1 to any port 22 proto tcp
sudo ufw allow 443/tcp
sudo ufw enable                    # asks for confirmation if you're connected over SSH
sudo ufw status verbose
sudo ufw status numbered; sudo ufw delete 2

It's a good choice for a single host with a handful of rules, and its limit rule (refuse an address that opens more than six connections in thirty seconds) is a cheap brake on SSH password guessing. Underneath it generates a lot: the lab counts 69 chains for two rules. For servers whose rules live in Git and are reviewed, a short nftables file says exactly what it does and is easier to read in a pull request. Use one or the other on a machine, never both.

Watch out: Docker and your firewall

Docker manages its own rules in the nat and filter tables. A port published with docker run -p 5432:5432 is forwarded to the container through the forward hook (Figure 15.1), so it bypasses ufw's and your own input rules: the database in a container is reachable from everywhere even though ufw status says otherwise. Publish on a specific address (-p 10.40.0.14:5432:5432 or 127.0.0.1:…), or put your rules in Docker's DOCKER-USER chain. Docker also sets the forward policy to drop, which is why this book's lab script needed a line for machines with Docker installed (Chapter 13).

15.6Host firewalls and security groups

In the cloud, the network itself can filter: AWS security groups and network ACLs (Handbook 1, Chapter 9), Azure network security groups, Google Cloud firewall rules. A security group is in many ways the same thing as this chapter's ruleset (stateful, default deny inbound, allow by source and port) but enforced by the provider, outside the VM.

Two differences matter in practice. A security group can't be switched off by someone who has broken into the VM, while a host firewall can (they'd need root, but that's what they're after). And a host firewall is the only filter between two VMs in the same security group or subnet that allow each other broadly, which is exactly the lateral movement Stagedoor's testers demonstrated. Defence in depth is having both, each written down.

15.7Across distributions

On the RHEL family

RHEL, Rocky, AlmaLinux and Fedora use firewalld, enabled by default, with zones (sets of rules applied to interfaces or source addresses) and services (named port lists): sudo firewall-cmd --add-service=https --permanent, sudo firewall-cmd --zone=internal --add-source=10.40.0.0/24 --permanent, then sudo firewall-cmd --reload. Without --permanent, a change lasts until the next reload, a handy built-in undo. firewalld writes nftables rules underneath. Amazon Linux 2023 has no host firewall enabled by default and relies on security groups.

15.8Lab: a firewall for door-4

Lab 15 · Default deny, tested from both sides

You'll start three listeners on door-4 as the testers found them, probe them from a web server and from the admin network, load Stagedoor's ruleset and probe again, break it twice to see why two of its lines exist, then try ufw. All the rules live inside the lab's namespaces, so your own machine's firewall is never touched. You need Chapter 13's netlab.sh and the packages in the chapter card. Cost: nothing. Clean-up: the last step.

  1. Set the scene. In ~/lab15, start the lab network and three listeners on door-4, standing in for SSH, PostgreSQL and the forgotten metrics exporter: 
    sudo ~/netlab.sh up
for p in 22 5432 9100; do sudo ip netns exec door-4 nc -lk 10.40.0.14 $p >/dev/null 2>&1 & done
  2. A probe. Save this script; it tries each port from door-2 (a web server) and from your machine (10.40.0.1, standing in for the admin network) and classifies the answer as in Chapter 13:

    probe.shbash

    #!/usr/bin/env bash
# probe.sh · try door-4's ports from door-2 (a web server) and from this machine (the admin network)
for port in 22 5432 9100; do
  for from in door-2 admin; do
    if [ "$from" = admin ]; then run=(); else run=(ip netns exec "$from"); fi
    out=$("${run[@]}" nc -zv -w 2 10.40.0.14 "$port" 2>&1)
    case "$out" in
      *succeeded*) result="open" ;;
      *refused*)   result="refused (nothing listening)" ;;
      *)           result="no answer (dropped)" ;;
    esac
    printf '%-7s -> 10.40.0.14:%-5s %s\n' "$from" "$port" "$result"
  done
done
    chmod +x probe.sh; sudo ./probe.sh

admin   -> 10.40.0.14:22    open
door-2  -> 10.40.0.14:5432  open
admin   -> 10.40.0.14:5432  open
door-2  -> 10.40.0.14:9100  open
admin   -> 10.40.0.14:9100  open

  3. Load the ruleset from 15.2 (save it as door4.nft), checking it first: 
    sudo ip netns exec door-4 nft -c -f door4.nft && echo "syntax OK"
sudo ip netns exec door-4 nft -f door4.nft
sudo ip netns exec door-4 nft list ruleset
    syntax OK

		type ipv4_addr

	}

    Probe again: 
    sudo ./probe.sh
    door-2  -> 10.40.0.14:22    no answer (dropped)

    SSH only from the admin network, PostgreSQL only from the web server, the exporter from nowhere, and everything refused silently (two-second timeouts). The counter saw it: 
    sudo ip netns exec door-4 nft list chain inet filter input | grep counter
    		counter packets 8 bytes 480 comment "everything else is dropped"
    Eight packets: the four blocked probes each sent a SYN and then a retry.
  4. Break it: forget the established rule. door-4 must also make outgoing connections (to DNS, to package mirrors, to a backup server). Give door-2 a listener and connect to it from door-4, first with the ruleset as it is, then with the ct state established,related accept line commented out: 
    sudo ip netns exec door-2 nc -lk 10.40.0.12 8080 >/dev/null 2>&1 &
sudo ip netns exec door-4 nc -zv -w 2 10.40.0.12 8080
    Connection to 10.40.0.12 8080 port [tcp/http-alt] succeeded!
    sed 's/^        ct state established,related accept/#&/' door4.nft > broken.nft
sudo ip netns exec door-4 nft -f broken.nft
sudo ip netns exec door-4 nc -zv -w 2 10.40.0.12 8080; echo "exit status: $?"
    nc: connect to 10.40.0.12 port 8080 (tcp) timed out: Operation now in progress
exit status: 1
    door-2's reply (its SYN-ACK) arrived at door-4's input hook and matched no rule. Outgoing traffic wasn't filtered at all; the reply was. Put the real ruleset back: sudo ip netns exec door-4 nft -f door4.nft.
  5. Reject instead of drop for the metrics port, so internal clients fail fast: 
    sed 's/^        counter comment "everything else is dropped"/        tcp dport 9100 reject with tcp reset comment "refuse metrics politely"\n&/' door4.nft > reject.nft
sudo ip netns exec door-4 nft -f reject.nft
sudo ./probe.sh | grep 9100
    door-2  -> 10.40.0.14:9100  refused (nothing listening)
admin   -> 10.40.0.14:9100  refused (nothing listening)
    The probe now says “refused (nothing listening)”, and so would any client: a reject looks exactly like a closed port, although nc is still listening on 9100 behind the firewall. Restore door4.nft.

At Stagedoor: four rulesets in Git

Rafaela and Tiago write one nftables file per server role, reviewed like code in the operations repository: web servers accept 80 and 443 from anywhere and SSH from the office's VPN address; door-4 accepts PostgreSQL from the two web servers and SSH from the VPN, exactly as in the lab. They roll it out on Thursday 8 October, one server at a time, each time with an automatic undo scheduled for five minutes later and a second SSH session open, and cancel the undo only after logging in afresh. The metrics exporter on door-4 is removed (a monitoring agent that pushes, rather than listens, replaces it), and /etc/nftables.conf with nftables.service loads the rules at every boot.

The testers' retest on 15 October finds only 443 open on the web servers and nothing reachable on door-4 from door-3 except PostgreSQL. In the move to AWS (Handbook 5 tells it), each of these files will become a security group as well, and the host firewall will stay as the second layer.

✓Chapter summary

  • Netfilter filters packets in the kernel at hooks: input (for this machine), forward (through it), output (from it). It's stateful, through connection tracking.
  • nftables organises rules into tables, chains with a policy, rules and sets. A server ruleset: policy drop, established first, loopback, ICMP, then each service from its sources, with comments.
  • Check with nft -c -f, load with an automatic undo, persist with /etc/nftables.conf and nftables.service.
  • Drop makes clients time out; reject makes them fail fast, looking like a closed port.
  • ufw (Ubuntu) and firewalld (RHEL) generate rules from simple commands. Docker's published ports bypass input rules.
  • Cloud security groups and host firewalls overlap on purpose: the first survives a compromised VM, the second stops neighbours and travels with the machine.

Key terms

Netfilter
The Linux kernel's packet-filtering framework, with hooks where rules inspect and act on packets.
nftables
The current rule language and tool (nft) for netfilter, replacing iptables.
Chain policy
What happens to a packet that no rule in a base chain decides: accept or drop.
Connection tracking
Netfilter's record of connections, which lets rules match packets by state such as new or established.
Drop and reject
Refusing a packet silently, or with a reset or ICMP error that tells the sender at once.
ufw
Ubuntu's simple firewall front end, which generates netfilter rules from short commands.
Security group
A cloud provider's stateful firewall attached to instances or network interfaces, enforced outside the VM.

Check your understanding

  1. Which netfilter hook sees a packet addressed to this server's PostgreSQL, and which sees a packet passing through a container host to a container? recall

    Show answer

    The input hook for traffic to a local process such as PostgreSQL. Traffic to a container on a bridged network goes through forward (after NAT in prerouting), which is why rules in input don't protect published container ports.

  2. Add a rule to door4.nft that allows the monitoring server 10.40.0.20 to reach port 9187 (a PostgreSQL exporter), and nothing else new. apply

    Show answer

    In the input chain, before the final counter: tcp dport 9187 ip saddr 10.40.0.20 accept comment "Postgres exporter for monitoring". Check with nft -c -f, load, and probe from the monitoring server and from somewhere else.

  3. Explain why a default-deny inbound policy breaks apt update if the established rule is missing, although apt only makes outgoing connections. explain

    Show answer

    An outgoing connection needs incoming replies: the DNS answer and the web server's SYN-ACK and data arrive as inbound packets and pass the input hook. Without a rule accepting packets of established (and related) connections, the policy drops them, so the connection times out.

  4. After you enable ufw with only allow 22/tcp on a VM running Docker, a container published with -p 6379:6379 is still reachable from the internet. Why, and what are two fixes? debug

    Show answer

    Docker's NAT rules forward published ports to the container through the forward hook, which ufw's input rules don't cover. Fixes: publish on a specific address (-p 127.0.0.1:6379:6379 or a private address), add filtering rules in the DOCKER-USER chain, and, in the cloud, close the port in the security group.

  5. Design the host firewall policy for Stagedoor's web servers. design

    Show answer

    Input policy drop; established/related accept; loopback; ICMP; TCP 80 and 443 from anywhere (or only from the load balancer's addresses, if all traffic comes through it); SSH from the admin VPN address only; a counter at the end. Outbound left open, or restricted to the database, DNS, package mirrors and the payment provider if you want to limit what a compromised server can reach. One file in Git, loaded by nftables.service, rolled out with an automatic undo.

  6. Compare a host firewall with a cloud security group for protecting a database VM. compare

    Show answer

    Both are stateful and can allow the database port only from the web servers. The security group is enforced by the provider, can't be changed from a compromised VM, and can name other groups as sources. The host firewall works anywhere, also filters between neighbours that the security group allows, and can be tested locally, but root on the VM can change it. Use the security group as the main control and the host firewall as a second layer.
