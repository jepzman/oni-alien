Answers to the exercises

Every “check your understanding” question in the book, with its worked answer. Try each question in its chapter first; come here to check.

1What a Linux server is

  1. Which of these is the kernel's job, and which is the distribution's: scheduling processes on CPUs, shipping a security fix for OpenSSL, deciding whether a program may open a file, providing ls?

    Kernel: scheduling processes and checking file permissions. Distribution: shipping the OpenSSL fix (as an updated package) and providing ls (part of the userland, from GNU coreutils). The distribution also ships the kernel itself as a package.

  2. uname -r prints 5.15.0-91-generic, and ls /boot shows vmlinuz-5.15.0-91-generic and vmlinuz-5.15.0-131-generic. What does that tell you, and what would you do?

    A newer kernel (131) is installed but the machine is still running the old one (91), so the kernel's security fixes since then aren't active. Plan a reboot, after checking that everything that should run is started as a service and will come back.

  3. Why does a program started by hand with nohup not come back after a reboot, while nginx does?

    After a reboot, the only programs that start are the ones PID 1 (systemd) is configured to start, plus their descendants. nginx is installed as a systemd service enabled at boot; the hand-started program was started by a person's shell, which no longer exists, and nothing records that it should run.

  4. A new VM launched from an Ubuntu image with your user data has no user rafaela. Where do you look first, and what might have gone wrong?

    Look at cloud-init's logs: /var/log/cloud-init-output.log and /var/log/cloud-init.log (and cloud-init status --long). Common causes: the file didn't start with #cloud-config, so it wasn't read as cloud-config; a YAML indentation error; or the user data was added to an instance that had already booted, and cloud-init only applies it at first boot.

  5. You've inherited a server nobody understands, and you've been asked to “tidy it up”. Write the first five things you'd do, in order.

    One reasonable order: (1) record the release and its end of support, the kernel and uptime; (2) list running services and all running processes and find what was started outside systemd; (3) list listening ports and who logs in; (4) for each running program, find its config, data and logs; (5) write it all down, with the problems found, before changing anything. Only then start fixing, one written-down change at a time.

  6. Compare an Ubuntu LTS release with a RHEL major version as a choice for a server you expect to run for six years.

    Ubuntu LTS gives five years of standard security updates (more with Ubuntu Pro), so a six-year server either needs Pro or an upgrade along the way. A RHEL major version gets ten years, covering the whole period, at the cost of a subscription (or using a rebuild such as Rocky or AlmaLinux) and older package versions near the end. Either works; what matters is knowing the date and planning for it.

2The shell, properly

  1. Which file descriptor does a program write error messages to, and why does it matter for pipelines?

    Standard error, file descriptor 2. Pipes only carry standard output (1), so error messages reach the terminal instead of being mixed into the data the next program processes.

  2. Write a pipeline that lists the five client addresses with the most requests in access.log, most first.

    awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5. The first sort groups equal addresses so uniq -c can count them; the second sorts by count, numerically and in reverse.

  3. dir= is accidentally empty. What does rm -rf $dir/* do, and how would quoting and a check have helped?

    The shell expands it to rm -rf /*: every top-level directory on the machine. Quoting alone ("$dir"/*) gives the same result with an empty variable; what helps is refusing to run with an empty value: rm -rf "${dir:?}"/* stops with an error if dir is empty or unset, and set -u (Chapter 17) catches unset variables in scripts.

  4. A script runs grep ERROR /var/log/app.log | wc -l and reports 0 errors every night. The log file was renamed a month ago. Why didn't anyone notice, and what's the fix?

    grep failed (exit 2, “No such file or directory” on stderr, which nobody reads in a cron job), but the pipeline's status was wc's, which succeeded and counted zero lines. Fix: set -o pipefail (or check that the file exists) so the failure is reported, and send the script's stderr somewhere someone reads.

  5. Joana now asks for the number of fans who lost a seat race (status 409) and later completed a checkout. Sketch how you'd answer it from the log, and say what the log can't tell you.

    Collect the addresses with a 409 on /api/hold (awk '$9 == 409 {print $1}' | sort -u > lost.txt), the addresses with a 200 on /api/checkout (… | sort -u > bought.txt), and count the lines in both (comm -12 lost.txt bought.txt | wc -l). The log can't tell you about people: addresses are shared and change, and it doesn't know which order belongs to whom. The order database can.

  6. Compare single and double quotes: what does each switch off, and when do you use each?

    Single quotes switch off every expansion; use them for text that must reach a program unchanged, such as awk programs and grep patterns containing $. Double quotes keep variable and command substitution but switch off word splitting and globbing; use them around variables and $( ) so the value stays one argument.

3Files and the filesystem layout

  1. Where would you expect to find: nginx's configuration, PostgreSQL's data files, the python3 program, and a process's list of open files?

    /etc/nginx/; /var/lib/postgresql/… (on Ubuntu and Debian); /usr/bin/python3; /proc/<pid>/fd/.

  2. ls -l shows -rw-r----- 3 postgres postgres 8192 Feb 9 10:02 0001. What does the 3 tell you, and what doesn't ls tell you about it?

    The inode has three names (hard links), somewhere on the same filesystem. ls doesn't say where the other two names are; ls -i gives the inode number, and find / -xdev -inum <number> finds them.

  3. Explain why mv -T current.new current is safe during a deploy, and why rm current; ln -s releases/new current isn't.

    A rename within one filesystem replaces the old name in a single step, so any lookup of current finds either the old link or the new one. With rm then ln, there's a moment when current doesn't exist, and a request or a service restart in that moment fails.

  4. The disk on a server is full. You delete a 6 GB log file, but df still says 100%. Why, and how do you confirm it?

    A running process still has the file open, so its inode and data aren't freed. Confirm with ls -l /proc/*/fd 2>/dev/null | grep deleted or lsof +L1, which list open files with no names left. The space comes back when that process closes the file or is restarted; next time, truncate or rotate instead of deleting (Chapter 7).

  5. Design the layout for a small Go service called scanner that keeps a local cache of ticket barcodes and writes a log. Say where each part goes.

    Binary per release in /opt/scanner/releases/<version>/ with a current symlink; configuration in /etc/scanner/; the barcode cache in /var/cache/scanner/ if it can be rebuilt from the server, otherwise /var/lib/scanner/; logs in /var/log/scanner/ (or the journal, Chapter 7); a socket or PID file in /run/scanner/.

  6. Compare a hard link and a symbolic link for keeping a “latest backup” name that always points to the newest backup file.

    A symlink suits it: it's visibly a pointer, can be switched atomically, and works across filesystems. A hard link would work only on the same filesystem, wouldn't show which backup it is without comparing inode numbers, and would keep an old backup's data alive after the backup itself was “deleted”.

4Users, groups and permissions

  1. Write rwxr-x--- and rw------- in octal, and say what each is typically used for.

    750: a directory (or program) for its owner, readable and enterable by one group, closed to everyone else. 600: a secret only its owner may read and write, such as a private key or a file with a password.

  2. A file is -rw----r-- 1 rafaela ops. Rafaela tries to read it. Is she allowed, and why?

    Yes: she's the owner, so only the owner bits count, and they include r. (If the owner bits had been ---, she would be denied even though “other” has r, because only one class is checked.)

  3. Why can a user delete a file they don't own and can't write to?

    Deleting removes a name from the directory, so it needs write (and execute) permission on the directory, not on the file. Without the sticky bit, anyone who can write to the directory can delete any entry in it.

  4. nginx returns 403 for /var/lib/stagedoor/uploads/plan-7.pdf, but sudo cat of the file works. List what you'd check, in order.

    sudo cat proves nothing, because root skips the checks. Check which user nginx's workers run as (ps -o user= -C nginx: the master is root, the workers that open files are www-data); run namei -l on the path to see that www-data can traverse every directory; check the file's group and mode (probably created without the setgid directory, so its group is stagedoor, or with a bad umask); test with sudo -u www-data cat. On RHEL, also check SELinux denials.

  5. Design permissions for /etc/stagedoor/stagedoor.env, which holds the database password: the app must read it, the deploy process (running as a person with sudo) must update it, nginx must not see it.

    Owner root, group stagedoor, mode 640; the directory /etc/stagedoor owned root:stagedoor, mode 750. The app (user stagedoor) reads through the group but can't change it; deploys update it with sudo; nginx (www-data) is “other” and gets nothing. (Chapter 6 loads it with systemd's EnvironmentFile=.)

  6. Compare giving Tiago read access to the uploads by adding him to www-data with giving it through an ACL.

    Joining www-data gives him everything nginx's group can read, everywhere on the machine, which is broader than needed but visible in /etc/group. An ACL gives exactly this directory and nothing else, but it's less visible (only a + in ls -l) and easy to forget. For one person and one directory, the ACL is the narrower choice; for a role several people share, make a dedicated group.

5Processes and signals

  1. A process shows state D and doesn't die after kill -9. Why?

    D is uninterruptible sleep: the process is inside the kernel waiting for I/O, usually a disk or a network filesystem. Signals, even SIGKILL, are delivered only when it returns from that wait. Find out what the I/O is stuck on (a failing disk, an unreachable NFS server); the process dies when the I/O completes or fails.

  2. A container exits with status 137, and nobody ran docker kill. Give two likely explanations.

    137 = 128 + 9, death by SIGKILL. Either the kernel's out-of-memory killer killed it (docker inspect shows OOMKilled: true; Chapter 10), or it was asked to stop and didn't exit within the stop timeout, so the runtime sent SIGKILL (for example because it never handles SIGTERM, or its PID 1 is a shell that doesn't forward it).

  3. Why does a redirection like python3 app.py > app.log still apply after the shell execs Python?

    The shell forks, and in the child it opens app.log as file descriptor 1 before calling exec. exec replaces the program but keeps the process's open file descriptors, so Python starts with its standard output already pointing at the file.

  4. systemctl stop myapp takes exactly 90 seconds every time, and the logs show no shutdown messages from the app. What's going on, and how do you fix it?

    The app isn't reacting to SIGTERM, so systemd waits for its default stop timeout (90 s) and then sends SIGKILL. Common causes: the service starts a shell script that doesn't exec the app; the app ignores or blocks SIGTERM; or the main process exits but leaves children behind. Fix the signal handling (or add exec), then set TimeoutStopSec= to a deadline that fits the app.

  5. Design a deploy for an app on two servers behind a load balancer so that no request in progress is lost.

    One server at a time: take it out of the load balancer (fail its health check or deregister it) and wait for the balancer to notice; send SIGTERM and wait up to a deadline longer than the slowest request; SIGKILL only if it's still running, and alert; start the new version; wait until its health check passes and the balancer sends it traffic; then repeat on the second server.

  6. Compare SIGHUP and SIGTERM for a daemon such as nginx.

    By convention, SIGHUP asks a daemon to reload its configuration without stopping, and nginx starts new workers with the new configuration while old workers finish their requests. SIGTERM asks it to shut down. For a program that doesn't handle SIGHUP, the default action is to terminate, so check before sending it to an unknown process.

6systemd: services, units and timers

  1. A service is enabled but inactive (dead). What do those two words tell you?

    It will be started at the next boot (enabled), but it isn't running now (inactive): someone stopped it, or it finished or failed without a restart policy. systemctl status and journalctl -u show which.

  2. Write a drop-in that makes nginx restart automatically if it crashes, without touching the packaged unit. Where does the file go?

    /etc/systemd/system/nginx.service.d/restart.conf containing [Service], Restart=on-failure and, say, RestartSec=2; then sudo systemctl daemon-reload. systemctl cat nginx confirms it's applied.

  3. Explain why a unit with only After=postgresql.service may start before PostgreSQL on one machine and never start PostgreSQL at all on another.

    After= only orders: if both are being started in the same transaction, this unit waits. If PostgreSQL isn't enabled, nothing pulls it in, so it never starts. Add Wants= (or Requires=) to pull it in, and keep After= for the order.

  4. After you fix a typo in a unit and run systemctl restart, you get “Start request repeated too quickly”. What happened, and what do you run?

    The broken unit had been in a restart loop; with your restart, it crossed the start limit (by default five starts in ten seconds), so systemd refuses further starts. Run sudo systemctl reset-failed <unit>, then start it. Make sure you ran daemon-reload after fixing the file.

  5. Design a timer for a backup that must run once a night at 02:30 Lisbon time, must never run twice at once, and must run after a reboot if the machine was off at 02:30.

    A backup.service with Type=oneshot, its own user and full paths, and a backup.timer with OnCalendar=*-*-* 02:30:00 Europe/Lisbon and Persistent=true, enabled with systemctl enable --now backup.timer. systemd never starts a service that's already running, so runs can't overlap; check with systemd-analyze calendar and test with systemctl start backup.service.

  6. Compare running an app with nohup … & and as a systemd service, for a reboot, a crash, a deploy and a question about last night's logs.

    Reboot: nohup doesn't come back; an enabled service does. Crash: nohup stays dead; the service is restarted. Deploy: with nohup someone signals and restarts by hand; the service gets systemctl restart with SIGTERM and a timeout. Logs: nohup.out grows without timestamps or limits; the journal stores timestamped, per-service logs with retention (Chapter 7).

7Logs

  1. Where would you look first for: why sudo was denied, what nginx served at 10:02, and why stagedoor.service restarted?

    sudo: /var/log/auth.log or journalctl -t sudo. nginx's requests: its own file, /var/log/nginx/access.log. The restart: journalctl -u stagedoor, which has both the app's output and systemd's messages about it.

  2. Write a journalctl command for errors or worse from stagedoor.service between 09:55 and 10:15 on 20 March 2026, newest first.

    sudo journalctl -u stagedoor -p err --since "2026-03-20 09:55" --until "2026-03-20 10:15" -r.

  3. Explain why, after a create-style rotation, a program can still be writing to app.log.1, and why this eventually fills the disk anyway.

    Renaming changes the directory entry, not the open file: the program's descriptor still refers to the same inode, now named app.log.1. Each later rotation renames and compresses it, and finally deletes it, but the program keeps it open, so its space is never freed and keeps growing until the program reopens or restarts.

  4. df says / is 100% full, but du -xsh / adds up to 40 GB on a 160 GB disk. What's the likely cause, and how do you confirm and fix it without a reboot?

    Deleted files still held open: du only counts files with names, df counts all used blocks. Confirm with sudo lsof +L1 or ls -l /proc/*/fd | grep deleted. Fix by truncating through /proc/<pid>/fd/<n>, or by restarting the program holding them, then stop the cause (rotation that the program supports).

  5. Design the logging for a new service on Stagedoor's servers so it can never fill a disk and its logs survive the server.

    Log to standard output at INFO, one structured line per event, with order and event IDs; run as a systemd service so the journal stores it; cap the journal (SystemMaxUse, SystemKeepFree); ship the journal to a central log service with retention; alert on disk usage above 80%; and make DEBUG a time-limited runtime switch.

  6. Compare copytruncate with a postrotate signal. When would you choose each?

    A signal (or systemctl reload) loses nothing and needs no extra disk space, but works only if the program can reopen its log files; use it for nginx, PostgreSQL and other daemons that support it. copytruncate works with any program, but needs space for the copy and can lose lines written between the copy and the truncate; use it for programs you can't change.

8Packages and updates

  1. What does apt update change on the machine, and what does it not?

    It downloads and verifies the repositories' indexes, so apt knows which versions exist. It doesn't install or upgrade any package; apt upgrade does that.

  2. A server's openssl is version 3.0.13-0ubuntu3.16 and a scanner says “OpenSSL 3.0.13 is vulnerable to CVE-…, upgrade to 3.0.15”. How do you check whether you're actually affected?

    Ubuntu backports fixes into the version it shipped, so the upstream number alone says little. Check the package changelog (zcat /usr/share/doc/openssl/changelog.Debian.gz | grep CVE-…) or Ubuntu's security notice and CVE tracker for that CVE and release. If the fix is listed for your package revision or an earlier one, you're patched; if not, apt-cache policy openssl shows whether a fixed candidate is waiting.

  3. Explain why a server can be fully upgraded and still vulnerable to a bug in a library fixed last week.

    Processes that started before the upgrade still have the old library loaded in memory. Until they restart (or, for the kernel, until the machine reboots), the old code is what runs. needrestart and /var/run/reboot-required tell you what's still outstanding.

  4. apt upgrade says “The following packages have been kept back: postgresql-16 postgresql-client-16”. Give two possible reasons and how to tell them apart.

    Either a package is held (apt-mark showhold lists it), or the upgrade needs new packages installed or old ones removed, which apt upgrade won't do (apt-get -s full-upgrade shows the extra changes). Phased updates on Ubuntu can also keep packages back for a few days while they roll out gradually.

  5. Design an update policy for two identical web servers behind a load balancer and one database server.

    Security updates installed daily on all three, with no automatic restarts or reboots. Web servers: in a weekly window, one at a time, out of the balancer, full updates, restarts, reboot if required, health check, back in; they could even reboot automatically, staggered. Database: a separate, announced monthly window (or a replica switchover once one exists), because restarting it is visible to everyone. A calendar of busy days when nothing is changed. A plan to replace each release months before its end of support.

  6. Compare upgrading a server to a new release in place with building a new server on the new release.

    In place is quicker and keeps everything, including the unknown hand changes, and is hard to roll back if it fails halfway. Building new takes longer the first time, but tests that you can rebuild the server, lets you compare old and new side by side, and leaves the old server as the rollback. For pets, building new is safer; for servers built from scripts, it's the normal way.

9CPU, load and scheduling

  1. A 4-vCPU server shows a load average of 3.1 5.6 7.9. What do the three numbers tell you?

    Over the last 15 minutes the load averaged about 7.9, almost twice the CPU count; over the last 5 minutes 5.6, and over the last minute 3.1, now below the CPU count. Something was overloaded and is recovering.

  2. vmstat 1 shows r 1 b 9 us 4 sy 3 id 41 wa 52 on an 8-vCPU database server. What's the bottleneck, and what would you look at next?

    The disk: nine threads blocked in I/O, half the CPU time spent waiting for I/O, CPUs mostly idle. Next: ps -eo pid,stat,wchan:20,comm | awk '$2 ~ /D/' for which processes, iostat -x 1 or pidstat -d 1 for which disk and who's using it (Chapter 11).

  3. Explain why a nice-19 backup job still runs at full speed on an idle server, and why that can still hurt the database at night.

    Nice only changes the share of CPU when CPUs are contended; with free CPUs, the job gets as much as it wants. And nice affects CPU, not the disk: a backup's I/O can still slow the database. Add ionice -c 3 or IOSchedulingClass=idle, and schedule it when the database is quiet.

  4. A web server's console graph shows 35% CPU, but its users report slowness and top inside the VM shows st at 40%. What's happening?

    The hypervisor isn't giving the VM the CPU time it wants: either a noisy neighbour on a shared host, or (very often) a burstable instance that has run out of CPU credits and is throttled to its baseline. Check the credit balance; move to a fixed-performance instance type, or stop and start to land on another host.

  5. Design monitoring alerts for CPU on Stagedoor's servers that would have pointed at the real problem on 8 May.

    Alert on CPU busy (user + system) above about 80% for several minutes, per server, and separately on I/O wait above about 30%, each with the top processes by CPU and the processes in D attached. Graph load per CPU for context rather than alerting on it. Add steal time for cloud VMs.

  6. Compare Nice=10 and CPUQuota=50% for a reporting service.

    Nice=10 lowers its share only when CPUs are contended; when the machine is idle it can use every CPU. CPUQuota=50% is a hard ceiling of half a CPU, even on an idle machine. Use nice (or CPUWeight=) to be polite; use a quota when the job must never take more than a fixed amount.

10Memory, swap and the OOM killer

  1. free -h shows total 32Gi, used 6Gi, free 400Mi, buff/cache 25Gi, available 25Gi. Is the server short of memory?

    No. Programs use about 6 GB; most of the rest is page cache, which the kernel gives back on demand, so about 25 GB is available. Low free on a long-running server is normal.

  2. A container exits with 137. How do you find out whether it was out of memory, and whose limit it hit?

    docker inspect shows OOMKilled: true if the container hit its own memory limit. The kernel log (dmesg or journalctl -k) has “Memory cgroup out of memory: Killed process …” for a cgroup limit, or “Out of memory: Killed process …” for a machine-wide shortage. If neither appears, something else sent SIGKILL, such as a stop timeout.

  3. Explain why adding up the RSS of all PostgreSQL processes gives more than the machine's RAM.

    PostgreSQL's shared buffers are shared memory mapped by every backend. Each backend's RSS includes the shared pages it has touched, so the same pages are counted many times. PSS (from smem or smaps_rollup) splits shared pages between the processes using them.

  4. A server becomes extremely slow for minutes at a time but nothing is killed. vmstat 1 shows si and so in the thousands. What's happening, and what would you do?

    Thrashing: memory demand exceeds RAM, and pages are continuously swapped out and back in. Find the processes with the largest resident and swapped memory (VmSwap in /proc/<pid>/status), reduce or limit them (a cgroup MemoryMax=), or add RAM. Swap bought time; the shortage is real.

  5. Design memory protection for a server that runs PostgreSQL and, at night, a Python export job that sometimes uses a lot of memory.

    Run the export as a systemd service or timer with MemoryHigh= and MemoryMax= well below what PostgreSQL needs, so it's killed first and alone. Give the postmaster OOMScoreAdjust=-1000. Size PostgreSQL's memory settings (shared buffers, work_mem per connection) with headroom. Add a little swap for warning time and alert on MemAvailable. Better still, run the export elsewhere, against a replica.

  6. Compare MemoryHigh= and MemoryMax=.

    MemoryHigh= is soft: above it, the kernel reclaims the cgroup's memory hard and throttles it, slowing it down, but nothing is killed. MemoryMax= is hard: the cgroup can't exceed it, and if reclaim fails the OOM killer kills one of its processes. Use High as a brake a little below Max.

11Disks, filesystems and inodes

  1. Which command shows, in one view, the disks, their partitions, their sizes and where each is mounted?

    lsblk (add -f for filesystem types, labels and UUIDs).

  2. You've enlarged an EBS volume from 100 GB to 200 GB. lsblk shows nvme1n1 200G and nvme1n1p1 100G mounted at /data, which is XFS. Write the remaining commands.

    sudo growpart /dev/nvme1n1 1, then sudo xfs_growfs /data (XFS takes the mount point), then df -h /data to confirm. Both work while mounted.

  3. Explain why du -sh / can report much less than df -h /. Give two causes.

    du only adds up files it can reach by name; df counts every used block. Deleted files still held open by a process use blocks but have no name; files hidden underneath a mount point also can't be reached. (Ext4's reserved blocks and du skipping unreadable directories without sudo also contribute.)

  4. After adding a second data volume, a cloud server doesn't come back from a reboot, and the serial console shows “You are in emergency mode”. What's the likely cause, and how do you prevent it?

    An fstab line that can't be satisfied: a device name that changed (the new volume took the old one's name) or a volume that isn't attached, without nofail. Fix from the console (or by attaching the disk to another instance), then use UUIDs, add nofail for non-essential volumes, and verify with findmnt --verify and mount -a before every reboot.

  5. Design the disk layout for Stagedoor's new database server in the cloud.

    A small root volume for the operating system. A separate data volume for PostgreSQL, mounted at /var/lib/postgresql by UUID with noatime, sized with room to grow and a volume type with enough IOPS; XFS or ext4 with enough inodes. Optionally a separate volume for write-ahead logs. Snapshots scheduled, and alerts on space and inodes for each filesystem.

  6. Compare using LVM and using whole cloud volumes directly for data.

    LVM can span disks, grow a logical volume and its filesystem in one step, and take LVM snapshots, which is valuable on physical servers where disks can't be resized. In the cloud, volumes can already be resized and snapshotted by the provider, so a filesystem directly on a volume is simpler, with one fewer layer to grow and debug. Use LVM where it solves a problem you have.

12Limits and kernel settings

  1. Where do you look to find the open-file limit of the running PostgreSQL postmaster, and how many files it has open?

    /proc/<pid>/limits (the “Max open files” line) and ls /proc/<pid>/fd | wc -l, with the PID from systemctl show -p MainPID postgresql@16-main or pgrep. Not ulimit -n in your shell.

  2. Write a drop-in that gives stagedoor.service a soft limit of 8192 and a hard limit of 65536 open files.

    /etc/systemd/system/stagedoor.service.d/limits.conf with [Service] and LimitNOFILE=8192:65536; then sudo systemctl daemon-reload, sudo systemctl restart stagedoor, and check /proc/<pid>/limits.

  3. Explain why clients can report a successful connection to a server that's stuck with “Too many open files”.

    The kernel completes the TCP handshake and puts the connection in the listening socket's accept queue without involving the program. The client sees an established connection. Only when the program calls accept() does the connection need a file descriptor, and that's the step that fails, so the connection waits in the queue until the client gives up.

  4. After raising nofile in /etc/security/limits.conf and rebooting, nginx still logs “Too many open files”. Why, and what's the fix?

    limits.conf applies to login sessions through PAM; nginx is started by systemd, which uses the unit's LimitNOFILE=. Add a drop-in with LimitNOFILE=65536, set worker_rlimit_nofile (and enough worker_connections) in nginx's config, restart, and confirm in a worker's /proc/<pid>/limits.

  5. Design the checks for a load test before a big on-sale, so that limit problems show up a week early.

    Generate more than the expected peak against a copy of the servers, and watch: nginx's error log for errno 24 and “worker_connections are not enough”; open descriptors per worker against its limit; TcpExtListenOverflows and ss -lnt queues; ss -s for TIME_WAIT and ephemeral port use; plus CPU, memory, disk and inode usage from Chapters 9–11. Fix each limit reached, then test again.

  6. Compare raising net.ipv4.ip_local_port_range with using keep-alive connections to the backend, for a proxy running out of ephemeral ports.

    Widening the range adds ports (at most about 64,000 per destination) and delays the problem. Keep-alive reuses a small pool of connections for many requests, so ports and TIME_WAIT entries barely grow with traffic, and it also saves handshakes and latency. Keep-alive fixes the cause; widening the range treats the symptom.

13Network configuration and tools

  1. Which command tells you which interface and source address the kernel would use to reach 10.50.3.7?

    ip route get 10.50.3.7. It prints the chosen route, the outgoing device, the gateway if any, and the source address.

  2. ss -tlnp on a server shows 127.0.0.1:6379 for Redis. A web server on another machine needs it. What do you change, and what else must you check before you do?

    Make Redis listen on the server's private address (bind 10.x.y.z in its configuration) and restart it. Before that: require authentication, and make sure a firewall or security group allows only the web servers to reach the port, because Redis on a reachable address with no password is a well-known way to be compromised.

  3. Explain why dig and the app on the same server can disagree about a name's address.

    dig asks a DNS server directly. The app resolves through the C library, which follows nsswitch.conf and usually checks /etc/hosts first; it may also go through a local cache (systemd-resolved) or cache addresses itself. A stale /etc/hosts entry or cache gives the app a different answer from DNS.

  4. From a web server, nc -zv 10.40.0.14 5432 hangs for its whole timeout instead of failing at once. List three causes, and the command that checks each.

    No route or wrong gateway (ip route get 10.40.0.14); the machine is down or not on that network (ip neigh showing FAILED, no ping reply); a firewall dropping the packets on either host or in between (Chapter 15: nft list ruleset, the cloud's security groups). A refused connection would have meant the packet arrived and nothing listened.

  5. Design how Stagedoor's servers should find each other by name.

    One internal DNS zone (stagedoor.internal) served by the provider's private DNS or a small resolver, with records per service (db, scan-api) rather than per machine, so a move changes one record; short TTLs (a few minutes) on records that move; no internal names in /etc/hosts; netplan pointing each server at that resolver with search: [stagedoor.internal].

  6. Compare netplan apply and netplan try for a change on a remote server.

    apply makes the change at once and permanently; if it breaks connectivity, you need a console to fix it. try applies it and reverts after a timeout unless you confirm, so a change that cuts your SSH session undoes itself. Use try on anything you reach over the network.

14Debugging connections

  1. curl fails with exit code 6. Which layer failed, and what's the first command you'd run?

    Name resolution (“couldn't resolve host”). Run getent hosts NAME on the same machine, then dig NAME and resolvectl status to see which resolver it uses and what it answers.

  2. You've built a replacement web server, 10.40.0.15, not yet in DNS. Write the curl command that requests https://tickets.stagedoor.example/health from it, with full certificate checking.

    curl -v --resolve tickets.stagedoor.example:443:10.40.0.15 https://tickets.stagedoor.example/health. The connection goes to the new server, while SNI, certificate checks and the Host header use the real name.

  3. Explain why a site can work in a desktop browser and fail in curl and in a phone app with “unable to get local issuer certificate”.

    The server is sending its certificate without the intermediate. Some desktop browsers have the intermediate cached, or fetch it themselves from the certificate's AIA field, so they can complete the chain; curl and most apps don't, so they can't link the certificate to a trusted root. Configure nginx with the full chain.

  4. tcpdump on a client shows [S] to the server's port 443 repeated after 1, 3 and 7 seconds, with no reply. On the server, the same capture shows nothing. Where's the problem?

    Between the two: the SYN leaves the client and never reaches the server's interface. Check the path: the client's route, cloud security groups and network ACLs, any firewall or load balancer in between. If the server had seen the SYN and not answered, the server's own firewall would be the suspect (Chapter 15).

  5. Design certificate management for Stagedoor's public names after 13 September.

    Every public name gets an ACME certificate (certbot or a managed certificate on a load balancer), renewed automatically about 30 days before expiry with a hook that reloads nginx and distributes the certificate to every server that needs it. An external daily check of every endpoint alerts 21 days ahead and on any verification error. CA and registrar accounts use a shared operations address. A list of all names and where their certificates live is kept in the wiki.

  6. Compare curl -v and openssl s_client for debugging a TLS problem.

    curl -v shows the whole request as a client would make it, including HTTP, and reports the verification result in one line. openssl s_client shows the TLS layer in detail: every certificate in the chain the server sent, each verification step with its error number, the negotiated protocol and cipher, and lets you extract the certificate for openssl x509. Start with curl; use s_client when the problem is the certificate or the handshake.
