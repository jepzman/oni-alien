Processes and signals

Everything that runs on a server is a process: started by another process, identified by a number, and stopped by a signal. This chapter shows how processes are born and how they die, how to read ps and top without guessing, and how to stop a server so that the requests it's handling finish instead of vanishing.

By the end you can

  • Explain how fork, exec, exit and wait create and end processes.
  • Read a process tree and the state column of ps, including zombies.
  • Choose the right signal (TERM, KILL, HUP, INT) and predict what it does.
  • Write a server that shuts down gracefully, and prove the difference with a test.
  • Read exit statuses such as 137 and 143.

Before you start

  • Chapter 2: exit codes, background jobs with &.
  • A Linux terminal with Python 3 and curl (Appendix C); two terminal windows help.

5.1What a process is

A process is a running program: the program's code plus everything the kernel tracks while it runs. A program is a file on disk; you can run it ten times at once and get ten processes.

For each process, the kernel keeps:

  • a PID (process ID), unique while the process exists, and the PPID, its parent's PID;
  • the user and groups it runs as (Chapter 4), its current directory, its environment variables and its umask;
  • its memory (Chapter 10), its open file descriptors (Chapter 2, Chapter 12), and its resource limits;
  • its state (running, sleeping, stopped…) and how much CPU time it has used.

All of it is visible under /proc/<pid>/: status for a readable summary, cmdline for the command, environ for the environment, fd/ for open files, limits for limits. /proc/self is always the process reading it.

5.2How processes are born, and how they end

Linux creates processes in two steps, and the split explains a lot of behaviour you'll see:

  1. fork() makes an almost exact copy of the calling process, with a new PID. The copy has the same memory (copied lazily, only when either side writes), the same open files, user, environment and current directory.
  2. exec() replaces the program running in a process with another one. The PID, open files, user and environment stay.
  3. exit(status) ends a process. Its memory and files are released at once, but the kernel keeps a tiny record, the exit status, for the parent.
  4. wait() is how the parent collects that status. Until it does, the finished child is a zombie: not running, holding no memory, but still listed, with state Z.

Zombies themselves are harmless; a parent that never waits for its children is a bug, and thousands of zombies can exhaust the PID space. If a parent dies first, its children become orphans and are adopted by PID 1, whose job includes waiting for them. That's one reason PID 1 is special, and why what runs as PID 1 inside a container matters (Chapter 19).

5.3Seeing processes

Every process except PID 1 has a parent, so all processes form a tree with PID 1 at the root. ps shows a snapshot; top (or the friendlier htop) a live view:

ps -ef --forest                          # every process, as a tree, with its full command
ps -o pid,ppid,user,stat,etime,cmd -C nginx   # chosen columns, for one program
pgrep -a uvicorn                         # PIDs and commands matching a name
pstree -p                                # the tree, compactly
top                                      # live; press P (CPU), M (memory), q to quit

The STAT column of ps (S in top) is the process's state. The first letter matters most:

5.4Signals

A signal is a small numbered message the kernel delivers to a process: “stop”, “hang up”, “your child died”. A process can catch most signals and run its own code (a handler), ignore them, or leave the default action, which for most signals is to terminate. Two signals can't be caught or ignored: SIGKILL and SIGSTOP. The kernel carries them out itself.

Table 5.2 · The signals you'll send and receive
SignalNo.DefaultUsed for
SIGTERM15terminate“please shut down”. The default of kill, and what systemd and Docker send first. Well-written servers catch it and shut down gracefully.
SIGINT2terminateCtrl+C in a terminal; Python raises KeyboardInterrupt.
SIGHUP1terminateoriginally “the terminal hung up”; by convention, daemons such as nginx catch it to reload configuration.
SIGKILL9terminate, can't be caughtthe last resort: the process gets no chance to finish anything.
SIGQUIT3terminate and dump coreCtrl+\; nginx uses it for a graceful stop.
SIGUSR1, SIGUSR210, 12terminatedefined by each program: nginx reopens its log files on USR1 (Chapter 7).
SIGCHLD17ignoresent to a parent when a child exits, so it can wait.
SIGPIPE13terminatewriting to a pipe nobody reads: why grep | head stops grep (Chapter 2).
SIGSTOP, SIGCONT19, 18stop, continuepause and resume; Ctrl+Z sends the catchable SIGTSTP.

Send signals with kill -s TERM 2187 (or kill -TERM, or kill -15), to every process with a name with pkill, and list them all with kill -l. Prefer names to numbers: they're the same on every machine and say what you mean. And be careful with pkill -f: it matches the whole command line, so pkill -f uvicorn also matches an editor with a file called uvicorn.conf open.

When a process dies from a signal, the shell reports exit status 128 + the signal number (Chapter 2): 143 is SIGTERM, 137 is SIGKILL, 130 is SIGINT. When a container or service exits with 137, ask who sent SIGKILL: a person, a stop timeout, or the kernel's out-of-memory killer (Chapter 10).

nohup and hangupsWhen you log out, your terminal's processes get SIGHUP and, by default, die. nohup cmd & makes cmd ignore it, which is why Stagedoor's app survived logouts. It doesn't make it a service: nothing restarts it, and it doesn't come back after a reboot (Chapter 6).

5.5Graceful shutdown

A server stopping is a normal event: every deploy, every reboot, every scale-down stops one. What matters is what happens to the work in progress. Compare the two ways Stagedoor's app can stop:

A graceful shutdown has four parts, and the lab builds each one:

  1. Catch SIGTERM. If the program doesn't, the default action kills it as abruptly as SIGKILL would. Many frameworks do this for you (uvicorn, gunicorn, nginx, PostgreSQL); check, don't assume.
  2. Stop taking new work: close the listening socket, or fail the health check, so new requests go to another instance.
  3. Finish the work in progress, within a time limit.
  4. Exit with status 0. Whoever sent SIGTERM waits for that, up to a deadline, and only then sends SIGKILL.

Key idea

Send SIGTERM, wait, and send SIGKILL only when the deadline passes. kill -9 first is not “stopping a server”; it's crashing it on purpose.

On a server you'll rarely send these signals by hand. systemd does exactly this sequence on systemctl stop (KillSignal= and TimeoutStopSec=, Chapter 6), Docker on docker stop, and Kubernetes when it removes a pod. Your job is to make sure the program handles SIGTERM well and that the deadline is longer than your slowest legitimate request.

Watch out: signals don't pass through shell wrappers

If a service is started by a shell script (start.sh that runs python3 app.py), the signal goes to the shell, which by default doesn't forward it, and the app never hears it. End such scripts with exec python3 app.py, so the app replaces the shell (Figure 5.1) and receives signals directly. The same trap catches container entrypoints (Chapter 19).

5.6Jobs, foreground and background

In an interactive shell, cmd & starts a command in the background: the shell doesn't wait, and $! holds its PID. jobs lists the shell's background jobs; Ctrl+Z stops the foreground one; bg resumes it in the background, fg brings it back. These are conveniences for a terminal session, and they die with it (or survive with nohup). For anything that must keep running, use a service; for long interactive work over SSH, use tmux so a dropped connection doesn't take your session with it.

5.7Across distributions

Processes, signals and /proc are the kernel's, so they're identical on every distribution. The tools come from the procps package everywhere (ps, top, pgrep, pkill, free), with pstree from psmisc. Two differences appear on small or unusual systems:

On minimal images and containers

Container base images often leave out ps entirely (apt install procps or dnf install procps-ng), and Alpine-based images use BusyBox versions with fewer options. You can always fall back to /proc: ls /proc | grep -E '^[0-9]+$' lists PIDs, and cat /proc/<pid>/cmdline | tr '\0' ' ' shows a command.

5.8Lab: stop a server without losing a checkout

Lab 5 · Three fans, three signals

You'll run a tiny checkout server, send it three slow requests, and stop it mid-request with SIGTERM and SIGKILL; then add a graceful handler and repeat. Finally you'll make a zombie and watch who cleans it up. You need a Linux terminal (two windows are easiest), Python 3 and curl. Cost: nothing. Clean-up: delete the lab directory. PIDs in the outputs will differ on your machine.

  1. Save the server as checkout.py in a new directory ~/lab5. Each request sleeps 3 seconds, standing in for a payment provider; --graceful switches on a SIGTERM handler.

    checkout.pyPython 3.8+

    # checkout.py · a tiny web server whose checkout takes 3 seconds, like a call to a payment provider
import http.server, os, signal, sys, threading, time

class Checkout(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        time.sleep(3)                                   # waiting for the payment provider
        body = f"order confirmed by pid {os.getpid()}\n".encode()
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):                       # keep the terminal quiet
        pass

server = http.server.ThreadingHTTPServer(("127.0.0.1", 8080), Checkout)
server.daemon_threads = False                           # at shutdown, wait for requests in progress

def graceful(signum, frame):
    print(f"got {signal.Signals(signum).name}: no new requests, finishing the ones in progress", flush=True)
    threading.Thread(target=server.shutdown).start()    # stop the accept loop

if "--graceful" in sys.argv:
    signal.signal(signal.SIGTERM, graceful)
print(f"pid {os.getpid()} listening on 127.0.0.1:8080", flush=True)
server.serve_forever()
server.server_close()                                   # waits for the request threads
print("all requests finished; exiting", flush=True)
  2. Save the fans as fans.sh and make it executable (chmod +x fans.sh). It starts three requests in the background, waits a second, and signals the server while they're in progress:

    fans.shbash

    #!/usr/bin/env bash
# fans.sh SIGNAL · start three checkouts, then send SIGNAL to the server while they're in progress
pid=$(pgrep -f '^python3 checkout.py')
for fan in 1 2 3; do
  ( curl -s -m 10 http://127.0.0.1:8080/checkout || echo "fan $fan: failed, curl exit status $?" ) &
done
sleep 1
echo "sending SIG$1 to pid $pid"
kill -s "$1" "$pid"
wait
    pgrep -f '^python3 checkout.py' finds the server by its command line; the ^ anchors the match at the start, so it can't match some other command that merely mentions the file.
  3. Stop it with SIGTERM, no handler. In window 1: cd ~/lab5 && python3 checkout.py. In window 2: cd ~/lab5 && ./fans.sh TERM. 
    sending SIGTERM to pid 6658
fan 2: failed, curl exit status 52
fan 3: failed, curl exit status 52
fan 1: failed, curl exit status 52
    In window 1 the server printed only its first line and stopped. Run echo $? there: 143, 128 + 15. The program didn't catch SIGTERM, so the default action terminated it mid-request, and the kernel closed all three connections (curl's status 52 means “empty reply from server”).
  4. Stop it with SIGKILL. Start the server again in window 1, then ./fans.sh KILL in window 2: 
    sending SIGKILL to pid 6675
fan 1: failed, curl exit status 52
fan 3: failed, curl exit status 52
fan 2: failed, curl exit status 52
    The same three failures, and echo $? in window 1 says 137. For this program TERM and KILL did the same damage, because it had no handler: that's Stagedoor's deploy on 26 February.
  5. Now gracefully. In window 1: python3 checkout.py --graceful. In window 2: ./fans.sh TERM. Window 2 shows: 
    sending SIGTERM to pid 6692
order confirmed by pid 6692
order confirmed by pid 6692
order confirmed by pid 6692
    and window 1: 
    pid 6692 listening on 127.0.0.1:8080
got SIGTERM: no new requests, finishing the ones in progress
all requests finished; exiting
    All three checkouts completed, about two seconds after the signal, and echo $? says 0. While the server was finishing, it had already stopped accepting: a fourth curl http://127.0.0.1:8080/ sent a fraction of a second after the signal fails to connect (curl's exit status 7) instead of starting a checkout that might not finish.
  6. Break it on purpose: a deadline that's too short. Start python3 checkout.py --graceful again, and in window 2 send SIGKILL half a second after the SIGTERM: 
    ./fans.sh TERM & sleep 1.5; pkill -KILL -f '^python3 checkout.py'
    sending SIGTERM to pid 6840
fan 2: failed, curl exit status 52
fan 1: failed, curl exit status 52
fan 3: failed, curl exit status 52
    Window 1 shows that the handler ran, and then nothing more: 
    pid 6840 listening on 127.0.0.1:8080
got SIGTERM: no new requests, finishing the ones in progress
    Nobody waited for it. A stop timeout shorter than your slowest request turns a graceful shutdown back into a crash.
  7. Make a zombie. Save this as zombie.py:

    zombie.pyPython 3.8+

    # zombie.py · a parent that never collects its child's exit status
import os, time

if os.fork() == 0:      # fork() returns 0 in the child
    os._exit(0)         # the child exits at once
time.sleep(60)          # the parent sleeps and never calls os.wait()
    Run it in the background and look at it, then kill the parent and look again: 
    python3 zombie.py &
sleep 1; ps -o pid,ppid,stat,cmd -C python3
kill $!
sleep 0.5; ps -o pid,ppid,stat,cmd -C python3
    On a normal Ubuntu server (PID 1 is systemd), the first ps shows the parent and its zombie child, Z and <defunct>: 
      PID  PPID STAT CMD
 6736  6735 S    python3 zombie.py
 6738  6736 Z    [python3] <defunct>
    and the second shows nothing but the header: when the parent died, the zombie was handed to systemd, which collected its status at once. 
        PID    PPID STAT CMD
    On the small VM where this book's labs were first tested, PID 1 isn't systemd (Lab 1), and the second ps said this instead: 
      PID  PPID STAT CMD
 6738     1 Z    [python3] <defunct>
    The zombie was adopted by PID 1 (its PPID is now 1), and that PID 1 never calls wait, so the zombie stays until the machine restarts. That's exactly the problem a container whose PID 1 is an ordinary app has, and Chapter 19 shows the fix.

Stretch goals. (1) Add a SIGHUP handler that prints “reloading” and keeps running; send it with kill -HUP. (2) Read /proc/<pid>/status for the running server and find its state, its threads and its signal masks (SigCgt lists the signals it catches, as a bitmask). (3) Put the server behind a wrapper script start.sh that runs python3 checkout.py --graceful without exec, signal the script's PID, and watch the requests fail; then add exec.

At Stagedoor: a deploy that waits

Tiago reproduces 26 February in the lab and adds the result to the incident note. uvicorn already handles SIGTERM gracefully; the deploy script never gave it the chance. The new script does three things on each server in turn, door-2 first: it fails the app's health check, so Atlantica's load balancer stops sending new fans there; it sends SIGTERM and waits up to 30 seconds (checkout's slowest normal request takes about 8); and only if the app is still running after that does it send SIGKILL, and say so loudly. Then it starts the new version, waits for the health check to pass, and moves on to door-3.

Rafaela points out that this is exactly what systemd does on systemctl restart, with less code to get wrong. Turning the app into a service is the next chapter, and the deploy script shrinks accordingly.

5.9Common mistakes

MistakeWhat happensInstead
kill -9 as the first resortRequests in progress fail; files and transactions are left half-written.SIGTERM, wait, then SIGKILL after a deadline.
A server that doesn't handle SIGTERMSIGTERM is as abrupt as SIGKILL.Handle it, or use a framework that does; test it as in the lab.
A shell wrapper without execThe signal reaches the shell; the app never hears it and is killed at the deadline.exec the app as the script's last line.
pkill -f name with a loose patternKills unrelated processes whose command line contains the word.Use the PID, a precise anchored pattern, or the service manager.
Stop timeouts shorter than the slowest requestGraceful shutdown is cut off and becomes a crash.Measure; set the deadline above the slowest legitimate request.
Running servers in a terminal with nohupNo restart on crash, no start at boot, signals sent by hand.A systemd service (Chapter 6).

✓Chapter summary

  • A process is a running program with a PID, a parent, a user, open files and a state; /proc/<pid>/ shows all of it.
  • fork copies a process, exec replaces its program, exit ends it, and the parent's wait collects the status. Uncollected children are zombies; orphans are adopted by PID 1.
  • States: R running, S sleeping, D waiting on I/O and unkillable, T stopped, Z zombie.
  • Signals are caught, ignored or take their default action. SIGTERM asks; SIGKILL can't be refused. Death by signal n gives exit status 128 + n.
  • Graceful shutdown: catch SIGTERM, stop accepting, finish in-flight work, exit 0; whoever stops it waits for a deadline before SIGKILL.

Key terms

Process
A running instance of a program, with its own PID, memory, open files and state.
PID
The number the kernel uses to identify a process; PID 1 is the first process, the init system.
fork and exec
The two steps that start a program: copy the current process, then replace the copy's program.
Zombie
A finished process whose exit status hasn't yet been collected by its parent.
Orphan
A process whose parent has exited; it is adopted by PID 1.
Signal
A numbered notification the kernel delivers to a process, such as SIGTERM or SIGKILL.
Signal handler
Code a program registers to run when it receives a particular signal.
Graceful shutdown
Stopping a server so it accepts no new work, finishes work in progress, and exits cleanly.

Check your understanding

  1. A process shows state D and doesn't die after kill -9. Why? recall

    Show answer

    D is uninterruptible sleep: the process is inside the kernel waiting for I/O, usually a disk or a network filesystem. Signals, even SIGKILL, are delivered only when it returns from that wait. Find out what the I/O is stuck on (a failing disk, an unreachable NFS server); the process dies when the I/O completes or fails.

  2. A container exits with status 137, and nobody ran docker kill. Give two likely explanations. apply

    Show answer

    137 = 128 + 9, death by SIGKILL. Either the kernel's out-of-memory killer killed it (docker inspect shows OOMKilled: true; Chapter 10), or it was asked to stop and didn't exit within the stop timeout, so the runtime sent SIGKILL (for example because it never handles SIGTERM, or its PID 1 is a shell that doesn't forward it).

  3. Why does a redirection like python3 app.py > app.log still apply after the shell execs Python? explain

    Show answer

    The shell forks, and in the child it opens app.log as file descriptor 1 before calling exec. exec replaces the program but keeps the process's open file descriptors, so Python starts with its standard output already pointing at the file.

  4. systemctl stop myapp takes exactly 90 seconds every time, and the logs show no shutdown messages from the app. What's going on, and how do you fix it? debug

    Show answer

    The app isn't reacting to SIGTERM, so systemd waits for its default stop timeout (90 s) and then sends SIGKILL. Common causes: the service starts a shell script that doesn't exec the app; the app ignores or blocks SIGTERM; or the main process exits but leaves children behind. Fix the signal handling (or add exec), then set TimeoutStopSec= to a deadline that fits the app.

  5. Design a deploy for an app on two servers behind a load balancer so that no request in progress is lost. design

    Show answer

    One server at a time: take it out of the load balancer (fail its health check or deregister it) and wait for the balancer to notice; send SIGTERM and wait up to a deadline longer than the slowest request; SIGKILL only if it's still running, and alert; start the new version; wait until its health check passes and the balancer sends it traffic; then repeat on the second server.

  6. Compare SIGHUP and SIGTERM for a daemon such as nginx. compare

    Show answer

    By convention, SIGHUP asks a daemon to reload its configuration without stopping, and nginx starts new workers with the new configuration while old workers finish their requests. SIGTERM asks it to shut down. For a program that doesn't handle SIGHUP, the default action is to terminate, so check before sending it to an unknown process.
