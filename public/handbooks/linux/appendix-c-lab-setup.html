C

Lab setup

Every lab in this book runs on your own machine, for free. Most need only a Linux terminal; some need a full virtual machine with systemd and root, which you can create and throw away in a minute. This appendix shows the options, which chapters need which, and exactly how this book's labs were tested.

Check what you have with the first command of the book: ps -o comm= -p 1. If it says systemd, every lab works; anything else (bash, sh, an agent's name) means a container or similar, fine for the first group of chapters only.

C.2A disposable VM with Multipass (recommended)

Multipass, from Canonical, runs Ubuntu VMs on Linux, macOS and Windows with one command, using the platform's own hypervisor. It's the easiest way to get a real Ubuntu server you can break:

multipass launch 24.04 --name lab --cpus 2 --memory 4G --disk 20G
multipass shell lab                         # a shell on the VM, as the user ubuntu (with sudo)
multipass transfer netlab.sh lab:           # copy files in
multipass stop lab; multipass delete --purge lab   # throw it away

Add --cloud-init user-data.yaml to launch to try Chapter 1's and Chapter 18's first-boot configuration. Take a snapshot before risky labs (multipass snapshot lab; restore with multipass restore), especially Chapter 15's firewall and Chapter 16's SSH changes if you apply them to the VM itself rather than the lab namespaces. Other hypervisors (VirtualBox, UTM on Apple silicon, GNOME Boxes, Hyper-V) work as well with an Ubuntu Server 24.04 image.

C.3Other options

  • WSL 2 on Windows: install Ubuntu from the Microsoft Store. Recent versions can run systemd as PID 1 if /etc/wsl.conf contains [boot] and systemd=true (then wsl --shutdown and start again); networking and loop-device labs may still behave differently, so prefer a VM for Parts III and IV.
  • A container: docker run --rm -it ubuntu:24.04 is fine for the shell, files and processes chapters; install what's missing with apt update && apt install -y python3 curl procps iproute2.
  • A small cloud VM: any provider's smallest Ubuntu 24.04 instance works for every lab (and lets you try cloud-init and instance metadata for real). Restrict SSH to your own address, and delete it when you're done; a forgotten instance is the only lab in this book that costs money.

C.4Packages

On Ubuntu 24.04, this installs everything the labs use (server images already have most of it):

sudo apt update
sudo apt install -y python3 curl procps psmisc iproute2 iputils-ping netcat-openbsd dnsutils dnsmasq-base \
  tcpdump nftables ufw openssh-server openssh-client acl strace lsof sysstat shellcheck \
  parted cloud-guest-utils xfsprogs nginx logrotate cloud-init lynis apache2-utils docker.io

Two of them change the machine as they install: nginx and openssh-server start services listening on ports 80 and 22, and docker.io changes the firewall's forwarding policy (which is why netlab.sh has two lines for Docker, Chapter 13). That's fine on a lab VM, and a reason not to do these labs on a machine you care about.

C.5The lab network and lab SSH servers

Part IV's labs share two scripts, printed in full where they're introduced: netlab.sh (Chapter 13) builds three pretend servers, door-2, door-3 and door-4, as network namespaces on a bridge, with your machine as 10.40.0.1; sshlab.sh (Chapter 16) runs an sshd inside two of them. Both have up and down, and down removes everything they created. If a lab is interrupted, run the down commands, then check that nothing is left: ip netns list and ip link show br-lab should print nothing, and pgrep -a dnsmasq, pgrep -af sshd_lab nothing of the lab's.

C.6How this book's labs were tested

Every lab script printed in this book is exactly the file that was run, and every output is copied from a real run, apart from the user and host names and timestamps, which will differ on your machine. The test machine was a small cloud VM running Ubuntu 24.04's userland on a Firecracker micro-VM kernel (Lab 1 shows its odd PID 1), with 4 vCPUs and 16 GB of memory. Three consequences, each mentioned where it matters:

  • Its PID 1 isn't systemd, so the systemd chapters (6, 7, 10, 18, 20, 21) were run in an Ubuntu 24.04 system container on it: a privileged Docker container running systemd as its PID 1. A few outputs show container traces, such as a /docker/… prefix in cgroup paths and a host name like lab or door-5.
  • It uses cgroup v1 and has IPv6 disabled; outputs involving cgroups and listening sockets reflect that.
  • Its kernel refused a few operations: online resize2fs (Chapter 11 shows the offline resize that ran), device-mapper (so LVM has no lab), negative oom_score_adj, and the kernel's audit system (so Chapter 18's auditd rules are shown, not run).

Debian 11's cron PATH (Chapter 6) is described from its documentation and reproduced by setting the same PATH explicitly. Netplan, firewalld, Session Manager and host certificates appear in prose or stretch goals only. Testing found real bugs in early drafts of two of the book's own scripts and one configuration file; each chapter says what was found, because that's the habit the book is trying to teach.

C.7Cleaning up

  1. Each lab ends with its own clean-up step; run it, especially those that create users (4, 6, 16), services and timers (6, 18), firewall rules (15) and Docker images (19).
  2. Lab directories live in your home directory (~/lab3 … ~/lab21, ~/build): rm -r ~/lab* when you're finished.
  3. The simplest clean-up of all: delete the VM (multipass delete --purge lab), or the cloud instance, and start fresh for the next part.
