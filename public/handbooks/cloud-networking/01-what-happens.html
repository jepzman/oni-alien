What happens when you open a web page

You type an address, press Enter, and less than a second later a page appears. In that second your laptop finds a server it has never heard of, opens a conversation with it across a dozen networks owned by different companies, and gets an answer back. This chapter follows that trip from start to finish. Every later chapter zooms in on one part of it.

By the end you can

  • Describe the steps of a page load, from typing a name to seeing the page.
  • Explain packets, layers and encapsulation in your own words.
  • Say which address (MAC, IP, port) is used for what, and which ones change on the way.
  • Tell from an error message which layer has the problem.

Before you start

  • A terminal on your own computer for the lab (macOS, Linux or Windows).

At Larder

Friday, 18:05. A customer in Rotterdam opens www.larder.example to order dinner. The page appears in 0.4 seconds. In Larder's office, Grace, the product owner, asks Eli, the platform engineer, a fair question: “That page is served from Frankfurt. What actually happens in those 0.4 seconds, and which parts could make it slow?”

Eli's answer is this chapter. In section 1.8 we'll take his stopwatch to it.

1.1The big picture

A network moves data from one program to another program on a different machine. Everything else in this book, from subnets to load balancers, is a way of doing that reliably, securely, cheaply or quickly. When you open a web page, the two programs are your browser and a web server, and the data has to cross several networks owned by different organisations: your home network, your internet provider, the internet's backbone, and finally the network where the server lives.

Here is the whole trip in eight steps. Don't worry if some words are new; each step gets a chapter of its own.

  1. Find the address. Computers don't route by names like www.larder.example; they route by IP addresses. The browser asks DNS, the internet's address book, to turn the name into an address (Chapter 5).
  2. Open a connection. The browser asks the operating system for a TCP connection to that address on port 443. TCP makes sure data arrives complete and in order (Chapter 3).
  3. Secure it. Browser and server agree on encryption keys with TLS, and the server proves it really is www.larder.example with a certificate (Chapter 6).
  4. Ask. The browser sends an HTTP request: “GET /, please”.
  5. Cross the networks. The request travels as packets. Every router on the way reads each packet's destination address and passes it one step closer (Chapter 4).
  6. Arrive and answer. At Larder, a load balancer picks a healthy app server (Chapter 16), which builds the page and sends it back.
  7. Come back. The reply crosses the same kinds of links in the other direction, not always along exactly the same path.
  8. Repeat. The page refers to stylesheets, scripts and images. The browser fetches each one, reusing the connection it already has where it can.

1.2Packets: data in small pieces

Networks don't send a web page as one long stream. They cut it into packets: small pieces, usually at most about 1,500 bytes each, that travel independently. A 200 KB page is roughly 140 packets.

Where 1,500 comes fromIt's the largest payload a classic Ethernet frame carries, called the MTU (maximum transmission unit). Inside cloud networks it's often larger (AWS allows 9,001 bytes within a VPC), which matters for VPNs in Chapter 13.

Every packet carries a header and a payload. The payload is a slice of your data. The header is the label on the outside: where the packet is from, where it's going, and a few more fields that help the network handle it.

Why bother cutting data up? Because it lets many conversations share the same cables fairly. A link carrying your page can, in the gaps between your packets, carry somebody's video call and somebody else's backup. If one packet is lost, only that piece needs to be sent again. And because each packet is routed on its own, the network can steer around a broken link in the middle of a conversation.

Key idea

A network only ever moves packets. Connections, web pages and video calls are things the two ends build on top of packets.

1.3Layers: each one does one job

Getting a web page across the world involves a lot of separate problems: radio signals on Wi-Fi, finding a path across networks, recovering lost packets, encrypting data, and asking for a page. Networks deal with that by splitting the work into layers. Each layer solves one problem and relies on the layer below it for everything else.

The model the internet actually uses is the TCP/IP model, with four layers:

Table 1.1 · The four layers of the internet
LayerIts jobAddress it usesExamples
ApplicationWhat the programs say to each othernames, like www.larder.exampleHTTP, DNS, TLS, SSH
TransportWhich program on the machine; reliability if neededport, like 443TCP, UDP, QUIC
InternetGetting a packet from one machine to another, across networksIP address, like 198.51.100.20IPv4, IPv6, ICMP
LinkGetting a frame across one physical link to the next deviceMAC address, like a4:83:e7:1f:02:9cEthernet, Wi-Fi
Layer 4, layer 7You'll also hear about the seven-layer OSI model. Nobody builds networks with it, but its numbers stuck: “layer 3” means IP, “layer 4” means TCP/UDP, and “layer 7” means the application, as in “a layer 7 load balancer” that reads HTTP.

Encapsulation: envelopes inside envelopes

When your browser sends a request, each layer wraps what it got from the layer above in its own header, like putting a letter in an envelope, then that envelope in a bigger one. This is called encapsulation.

At the other end the envelopes are opened in reverse order: the link layer removes the frame, the internet layer checks the IP address is its own, the transport layer hands the data to the program listening on port 443, and the program reads the request.

The practical value of layers is that you can reason about one at a time. A firewall rule that allows “TCP port 443 from anywhere” works on the transport and internet layers and doesn't care whether the data is a web page or a video. A load balancer that routes /api requests to one group of servers works at the application layer and doesn't care how packets got to it.

1.4Three addresses, three jobs

Every packet in Figure 1.2 carries three kinds of address. Mixing them up is the source of a great deal of confusion, so it's worth being precise.

  • The MAC address identifies a network interface on one local link. It says “which device on this cable or this Wi-Fi network should pick this frame up?”. It's only meaningful for one hop, so every router replaces it.
  • The IP address identifies a machine (strictly, an interface) across all networks. It says “where is this packet ultimately going?”. It normally stays the same from end to end; the one exception is NAT, which rewrites it on purpose (8.6 in Chapter 8).
  • The port identifies a program on that machine. Port 443 is the web server's HTTPS port; port 52814 is a temporary port the laptop picked for this one connection, so the reply finds its way back to the right browser tab.

Key idea

The MAC address gets the packet to the next hop. The IP address gets it to the right machine. The port gets it to the right program.

In the cloudYou'll almost never see a MAC address in a cloud network. The provider runs the link layer for you, and the VPC router answers for every next hop. IP addresses and ports are what you'll work with all day.

To see how they fit, picture the laptop's first packet. The laptop knows the server's IP address (from DNS) but the server isn't on the home network, so the laptop sends the frame to the home router's MAC address with the server's IP address inside. How does it know to do that? Its own route table says “anything not on my local network goes to the router”. That's a default route, and you'll see the same idea again in every cloud network you build.

1.5Hops, routers and the speed of light

A router is a device that connects networks and passes packets between them. Each time a packet passes through one, that's a hop. A packet from Rotterdam to Frankfurt typically makes 10 to 20 hops. At each one, the router:

  1. removes the link-layer frame it arrived in,
  2. reads the destination IP address and looks it up in its route table to choose the next hop (Chapter 4),
  3. lowers the packet's TTL (time to live) by one, and drops the packet if it reaches zero, so that packets caught in a routing loop don't circle forever,
  4. wraps it in a new frame addressed to the next hop, and sends it on.

No router knows the whole path. Each one only knows the best next step, the way a road sign shows the direction to the next town and not your whole route. The internet is tens of thousands of separately run networks, called autonomous systems, that tell each other which addresses they can reach, using a protocol called BGP. You'll meet BGP properly in Chapter 13, because it's also how your office network and your cloud network learn about each other.

Latency: distance costs time

Light in glass fibre covers about 200 km per millisecond. Fibre rarely runs in straight lines, and every router adds a little delay, so real round trips are slower than the straight-line distance suggests. Some typical round-trip times:

Table 1.2 · Typical round-trip times
BetweenRound trip
Two servers in the same cloud zonewell under 1 ms
Two zones in the same cloud regionabout 1–2 ms
Rotterdam and Frankfurtabout 8–12 ms
Home Wi-Fi to the internet providerabout 2–20 ms
Frankfurt and Virginia, USAabout 90 ms
Frankfurt and Sydneyabout 250–300 ms

These numbers matter more than they look, because loading a page takes several round trips before the first byte of content arrives: one for DNS (if the answer isn't cached), one for TCP, one for TLS, and one for the request itself. Four round trips to Sydney is over a second before anything happens. You can't make light faster, so the fixes are to need fewer round trips (connection reuse, TLS 1.3, HTTP/3) and to move content closer to users (CDNs, Chapter 17).

Watch out: latency is not bandwidth

Bandwidth is how much data a link can carry per second; latency is how long one trip takes. A faster connection gives you more bandwidth but barely changes latency. For web pages and API calls, which are lots of small exchanges, latency usually matters more. When someone says “the network is slow”, ask which one they mean.

1.6Where the cloud fits

In the cloud you don't plug in cables or configure routers, but every idea in this chapter is still there. The provider runs the physical network; you configure a virtual one on top of it. Here is where each step of the page load lands in a cloud network, and where this book covers it:

1.7Worked example: timing a page load

Back to Grace's question. Eli runs one command from a laptop in Rotterdam. curl fetches the page, and the -w option prints how long each step took, measured from the start:

terminalmacOS, Linux, or Windows with curl

curl -s -o /dev/null https://www.larder.example/ -w '
dns lookup:    %{time_namelookup}s
tcp connect:   %{time_connect}s
tls done:      %{time_appconnect}s
first byte:    %{time_starttransfer}s
total:         %{time_total}s
'
dns lookup:    0.012s
tcp connect:   0.023s
tls done:      0.046s
first byte:    0.201s
total:         0.388s

The times are cumulative, so subtract each from the next to see each step on its own:

Table 1.4 · Where the 388 ms went
StepTookWhat it tells Eli
DNS lookup12 msThe resolver had the answer cached. A cold lookup could take 50 ms or more.
TCP connect11 msOne round trip to Frankfurt. This is the network's distance, and the floor for everything else.
TLS handshake23 msAbout two round trips: a little slower than TLS 1.3's one. Worth checking the load balancer's settings (Chapter 6).
Waiting for the first byte155 msOne round trip plus the server's thinking time. Most of this is the application, not the network.
Downloading the page187 msThe HTML is large and not compressed. A size problem, not a distance problem.

Eli's answer to Grace: the network part, the distance to Frankfurt, costs about 11 ms per round trip and four round trips in total. The rest is the server building the page and the page's size. Moving the servers closer would save maybe 30 ms; compressing the page and caching it would save more than 150. Measuring each step turned a vague “is Frankfurt too far?” into two concrete tasks.

1.8Lab: watch it happen on your own machine

Lab 1 · The trip, step by step

You'll see your own addresses, your default route, a DNS lookup, the hops to a real server, and the timing of a real page load. You need a terminal. On Windows, use the commands in brackets. Cost: nothing.

  1. Your addresses. Run ip addr on Linux, ifconfig on macOS (ipconfig /all on Windows). Find your IP address, probably starting with 192.168. or 10., and your MAC address. Both are private to your home network.
  2. Your default route. Run ip route on Linux, netstat -rn on macOS (route print). Find the line for default or 0.0.0.0: its gateway is your home router. That one line is how every packet leaves your home.
  3. Your public address. Run curl https://checkip.amazonaws.com. The address it prints is different from step 1: your home router translates your private address into its public one (NAT, which you'll build yourself in Chapter 8).
  4. A DNS lookup. Run dig +short www.wikipedia.org (nslookup www.wikipedia.org). You get back one or more IP addresses, possibly after a CNAME line. Run it twice: the second answer is usually faster, because it's cached.
  5. The hops. Run traceroute www.wikipedia.org (tracert www.wikipedia.org). Each line is a router. The first is your home router; watch the times grow as the hops get further away. Lines of * * * are routers that don't answer traceroute, which is normal.
  6. The timing. Run the curl -w command from section 1.7 against any HTTPS site you like. Work out each step's own time as in Table 1.4. Try a site hosted on another continent and compare the TCP connect time.

Stretch goal. Run curl -v https://www.wikipedia.org -o /dev/null and find, in the output, the IP address it connected to, the TLS version, the certificate's subject, the HTTP request line and the response status. You've just seen four layers in one command.

1.9When it doesn't work: read the error's layer

Because each step depends on the one before, the error message usually tells you how far the request got. Learn to read these and you'll skip most of the guessing in every later troubleshooting session.

Table 1.5 · What the error tells you
You seeIt got as far asUsual causes
Could not resolve hostNowhere: no addressDNS: wrong name, missing record, resolver unreachable (Ch. 5)
Connection timed outPackets left, nothing came backNo route, or a firewall silently dropping packets (Ch. 8, 9)
Connection refusedThe machine answered “no”Reached the machine, but nothing listens on that port, or the app is down (Ch. 3)
Certificate errorsConnected, but TLS failedWrong or expired certificate, wrong name (Ch. 6)
HTTP 502, 503, 504Reached a proxy or load balancerThe servers behind it are down, unhealthy or slow (Ch. 16)
HTTP 4xxReached the applicationNot a network problem: the request itself was wrong or unauthorised

Key idea

A timeout means silence: something dropped the packets. A refusal means an answer: you reached the machine. That one difference halves the search.

1.10Common misconceptions

BeliefReality
“Ping fails, so the server is down.”Many networks block ping (ICMP), including cloud defaults. Test the real port: curl or nc -vz host 443.
“The internet is one big network.”It's tens of thousands of independent networks that agree to pass traffic. Any of them can be the slow or broken one.
“A faster connection makes pages load faster.”Only if size is the problem. Most page loads are limited by round trips, which bandwidth doesn't shorten.
“Packets of one request all take the same path.”Usually, but not always, and replies often return by a different path. Tools only ever show you one direction.
“HTTPS hides where I'm connecting.”It hides the content. The destination IP address, and usually the name (in the TLS handshake's SNI), are still visible.

✓Chapter summary

  • A page load is a chain: DNS, TCP, TLS, HTTP, then routing across many networks and back.
  • Networks move packets: small, independently routed pieces with a header and a payload.
  • Work is split into layers (application, transport, internet, link), each wrapping the one above: encapsulation.
  • MAC addresses get frames across one hop, IP addresses get packets end to end, ports pick the program.
  • Routers forward hop by hop, each knowing only the next step. Latency grows with distance and round trips, not bandwidth.
  • The error message tells you how far a request got: no address, timeout, refusal, TLS error, or an HTTP status.

Key terms

Packet
A small unit of data with a header (addresses and control fields) and a payload.
Layer
One level of the network's work, using only the layer below.
Encapsulation
Each layer wrapping the data from the layer above in its own header.
MAC address
A link-layer address, meaningful only on one local link.
IP address
An internet-layer address that identifies an interface across networks.
Port
A number that picks the program on a machine, like 443 for HTTPS.
Router / hop
A device that forwards packets between networks; each pass is one hop.
TTL
A counter in every IP packet, lowered at each hop, that stops endless loops.
Latency
How long a trip takes; usually given as a round trip in milliseconds.
Bandwidth
How much data a link can carry per second.
MTU
The largest packet a link can carry without splitting it, typically 1,500 bytes.

Check your understanding

  1. Put these in the order they happen when you open https://www.larder.example: TLS handshake, DNS lookup, HTTP request, TCP connection. recall

    Show answer

    DNS lookup, TCP connection, TLS handshake, HTTP request. Each needs the one before: you can't connect without an address, and you can't encrypt without a connection.

  2. As a packet travels from the laptop to the server, which of these change at each router: the source MAC address, the destination IP address, the destination port? explain

    Show answer

    Only the MAC addresses change at every hop, because each frame is for one link only. The destination IP address and port stay the same end to end, unless a NAT device rewrites them on purpose.

  3. A colleague's API call fails with Connection refused. Another says it must be a firewall. Are they likely right? apply

    Show answer

    Probably not. A refusal is an answer from the target machine, so the packets got there. Most cloud firewalls drop packets silently, which gives a timeout. Check whether the program is running and listening on the right port and address.

  4. A page makes four round trips before content starts to arrive. How long does that take at minimum for a user in Sydney if the servers are in Frankfurt? What are two ways to improve it? apply

    Show answer

    At about 280 ms per round trip, roughly 1.1 seconds. Improvements: fewer round trips (TLS 1.3, connection reuse, HTTP/3), or serving content from closer to the user with a CDN or a second region.

  5. Why does the internet cut data into packets instead of reserving a line for each conversation, like old telephone networks? explain

    Show answer

    Packets let many conversations share the same links, use capacity only when there is data to send, resend only the pieces that were lost, and route around failures in the middle of a conversation.
