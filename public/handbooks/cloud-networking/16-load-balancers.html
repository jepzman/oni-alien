Load balancers: layer 4 and layer 7

Almost every request to a cloud service passes through a load balancer first. It gives the service one stable address, spreads requests over healthy servers in several zones, and often handles TLS and routing too. Load balancers are easy to create and surprisingly easy to misconfigure: most mysterious 502s, 503s and dropped requests during deploys come from a handful of settings this chapter explains.

By the end you can

  • Choose between a layer 4 and a layer 7 load balancer.
  • Build listeners, rules and target groups, and route by host and path.
  • Design health checks that remove broken servers without causing outages.
  • Set timeouts and draining so deploys and quiet periods don't drop requests.

At Larder

Larder's ordering API returns a 502 Bad Gateway about once in every thousand requests. The app's own logs show no errors at all, as if those requests never arrived. Strangely, the rate is highest at quiet times, early in the morning and mid-afternoon, and almost zero during the evening rush. Retries always succeed, so for months it was “just the internet”.

It isn't. It's two timeouts that disagree, one in the load balancer and one in the app server. Section 16.5 finds them.

16.1The big picture

A load balancer sits between clients and a group of servers. Clients connect to the load balancer's address; it picks a healthy server and passes the request on. That one idea gives you several things at once: one stable name while servers come and go, spreading load across servers and zones, removing broken servers automatically, and a single place for TLS certificates and request routing.

Cloud load balancers are managed services. You don't size or patch them; they run in every zone you enable and scale with traffic. You configure what they listen for, where they send it, and how they decide a server is healthy.

16.2Layer 4 or layer 7?

Load balancers differ in how far into the traffic they look (Chapter 1). A layer 4 load balancer sees TCP or UDP connections and forwards them whole; it never reads the request. A layer 7 load balancer ends the client's connection, reads the HTTP request, and opens its own connection to a server, so it can route on the request's content.

For a web application or HTTP API, start with a layer 7 load balancer. Reach for layer 4 when the protocol isn't HTTP, when partners need fixed addresses to allow-list, or when you need to hand the TLS session to your servers untouched (Chapter 6).

16.3Listeners, rules and target groups

An AWS load balancer is configured in three layers:

  • A listener is a port and protocol the load balancer accepts, such as HTTPS on 443 with a certificate from ACM.
  • Rules on the listener (ALB only) match requests and choose an action: forward to a target group, redirect, or return a fixed response. Rules are checked in priority order; a default rule catches the rest.
  • A target group is a set of targets (instances, IP addresses, or Lambda functions), with a port, a protocol, and a health check.

Targets of type IP are what container platforms use: each task or pod registers its own address and port (Chapter 19). The load balancer must be able to reach them, which means a route (normally the VPC's local route) and a security group on the targets that allows the load balancer's group (Chapter 9).

16.4Health checks

Every few seconds the load balancer asks each target “are you healthy?”, typically an HTTP GET on a path like /healthz, and expects a 200 within a timeout. After a few failures in a row (the unhealthy threshold) the target stops getting traffic; after a few successes it's back.

The hard question is what the health check should check.

  • A shallow check (“the process is up and can answer”) removes crashed or stuck servers. That's exactly what a load balancer can fix: send the traffic to another server.
  • A deep check that also tests the database, the cache and the payment provider sounds more thorough, but when a shared dependency has a blip, every server fails at once. Removing all of them fixes nothing and turns a slow database into a total outage.

Key idea

A health check should fail only for problems that sending traffic elsewhere would fix. Check the server, not everything it depends on.

AWS's load balancers have a safety net: if every target in a group is unhealthy, they fail open and send traffic to all of them anyway, on the theory that a degraded answer beats none. Don't design around it, but know it exists when you see traffic going to “unhealthy” targets. If no healthy targets exist and failing open doesn't apply, clients get 503 (Chapter 6).

16.5Connections, timeouts and draining

A layer 7 load balancer keeps two sets of connections: from clients to itself, and from itself to targets. It reuses target connections for many requests, which saves handshakes. Each side has an idle timeout (Chapter 3): 60 seconds by default on an ALB.

Your app server has an idle timeout too, its keep-alive timeout, and often it's much shorter: a few seconds in many web servers' defaults. When the app closes an idle connection at the exact moment the load balancer sends a new request on it, the request hits a closed socket and the load balancer returns 502.

At Larder: solved

Larder's API ran under a Python web server with a keep-alive timeout of 2 seconds, its default. The ALB kept target connections for up to 60. During the evening rush, connections were never idle for 2 seconds, so the race never happened. In quiet periods, connections often sat idle for about 2 seconds, and now and then a new request landed on one just as the app closed it. The app never saw the request, so its logs were clean; the ALB's access logs showed the 502s with target_status_code empty.

The fix was one setting: the app's keep-alive timeout went to 75 seconds, longer than the ALB's 60, so the load balancer always closes idle connections first. The 502s went to zero.

Key idea

The side that reuses connections must be the one that closes them first. Set the target's keep-alive timeout longer than the load balancer's idle timeout.

Deploys without dropped requests

When a target is removed, during a deploy or a scale-in, the load balancer stops sending it new requests but lets requests in flight finish for the deregistration delay (also called connection draining; 300 seconds by default, often lowered to 30–60). Your app must cooperate: on the stop signal, keep serving for a few seconds, finish open requests, then exit. An app that exits instantly on SIGTERM drops whatever it was doing, and users see errors at every deploy.

The opposite end has a setting too: slow start sends a new target a gradually increasing share of traffic, for apps that need a moment to warm caches.

16.6Spreading load across zones and servers

  • Zones. A load balancer has a node in each zone you enable. With cross-zone load balancing, each node spreads requests across targets in all zones; without it, only across its own zone. It's always on for ALBs; for NLBs it's off by default, and turning it on adds cross-zone data charges (Chapter 7). Without it, keep the same number of targets in each zone, or some will be overloaded.
  • Algorithm. ALBs default to round robin; least outstanding requests is better when request costs vary a lot, because it avoids piling work on a server that's already busy.
  • Sticky sessions send a user back to the same target using a cookie. They hide state in a server's memory and unbalance load; prefer keeping session state in a shared store.

Who is the client?

Behind an ALB, every request comes from the load balancer's own addresses; the original client address travels in the X-Forwarded-For header (Chapter 6). Configure your framework to trust that header only from the load balancer, or anyone can claim any address. An NLB keeps the client's address for instance targets, and can add a proxy protocol v2 header for IP targets.

16.7Internal load balancers

Not every load balancer faces the internet. An internal load balancer lives in private subnets, has only private addresses, and gives a service inside your network the same benefits: a stable name, health checks, spreading. Larder's payment service sits behind an internal ALB that re-encrypts to its targets (Chapter 6), and the endpoint service Korenwolf uses is an internal NLB (Chapter 12). For many small internal services, a service mesh or the container platform's own service discovery can do this job instead (Chapter 19, Chapter 21).

On Google Cloud

The global external Application Load Balancer is unusual: one anycast IP address, announced from Google's edge worldwide, in front of backends in many regions. Users connect to the nearest edge, and traffic travels to the closest healthy backend over Google's network. It does in one product what takes a CDN plus regional load balancers elsewhere.

16.9Lab: an ALB with path routing, no servers

Lab 16 · Listener, rules, a Lambda target and a fixed response

You'll build an internet-facing ALB in your account's default VPC with a rule that sends /hello to a small Lambda function and a default rule that returns a fixed 404. No servers to run. You need the AWS CLI, Terraform, and a default VPC in eu-central-1 (most accounts have one). Cost: about $0.03 an hour for the ALB; Lambda calls are free at this volume.

main.tfTerraform ≥ 1.5, AWS provider 5.x, archive provider

provider "aws" { region = "eu-central-1" }

data "aws_vpc" "default" { default = true }
data "aws_subnets" "default" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.default.id]
  }
}

# a tiny function that answers like a web server
data "archive_file" "fn" {
  type        = "zip"
  output_path = "fn.zip"
  source {
    filename = "index.py"
    content  = <<-EOT
      def handler(event, context):
          return {"statusCode": 200, "isBase64Encoded": False,
                  "headers": {"Content-Type": "text/plain"},
                  "body": "hello from " + event["path"] + "\n"}
    EOT
  }
}
resource "aws_iam_role" "fn" {
  name = "handbook-lab16-fn"
  assume_role_policy = jsonencode({
    Version   = "2012-10-17"
    Statement = [{ Effect = "Allow", Action = "sts:AssumeRole",
                   Principal = { Service = "lambda.amazonaws.com" } }]
  })
}
resource "aws_lambda_function" "fn" {
  function_name    = "handbook-lab16"
  role             = aws_iam_role.fn.arn
  runtime          = "python3.12"
  handler          = "index.handler"
  filename         = data.archive_file.fn.output_path
  source_code_hash = data.archive_file.fn.output_base64sha256
}

# 16.3 · load balancer, listener, rules, target group
resource "aws_security_group" "alb" { vpc_id = data.aws_vpc.default.id }
resource "aws_vpc_security_group_ingress_rule" "http" {
  security_group_id = aws_security_group.alb.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "tcp"
  from_port         = 80
  to_port           = 80
}
resource "aws_lb" "lab" {
  name               = "handbook-lab16"
  load_balancer_type = "application"
  subnets            = data.aws_subnets.default.ids
  security_groups    = [aws_security_group.alb.id]
}
resource "aws_lb_target_group" "fn" {
  name        = "handbook-lab16-fn"
  target_type = "lambda"
}
resource "aws_lambda_permission" "alb" {
  statement_id  = "AllowALB"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.fn.function_name
  principal     = "elasticloadbalancing.amazonaws.com"
  source_arn    = aws_lb_target_group.fn.arn
}
resource "aws_lb_target_group_attachment" "fn" {
  target_group_arn = aws_lb_target_group.fn.arn
  target_id        = aws_lambda_function.fn.arn
  depends_on       = [aws_lambda_permission.alb]
}
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.lab.arn
  port              = 80
  protocol          = "HTTP"
  default_action {
    type = "fixed-response"
    fixed_response {
      content_type = "text/plain"
      message_body = "no rule matched\n"
      status_code  = "404"
    }
  }
}
resource "aws_lb_listener_rule" "hello" {
  listener_arn = aws_lb_listener.http.arn
  priority     = 10
  condition {
    path_pattern { values = ["/hello*"] }
  }
  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.fn.arn
  }
}

output "url" { value = "http://${aws_lb.lab.dns_name}" }
  1. Create it with terraform init and terraform apply, then wait a minute or two for the ALB to become active.
  2. Exercise the rules. curl -i $(terraform output -raw url)/hello/world returns 200 from the function; curl -i $(terraform output -raw url)/other returns the fixed 404. Which rule answered each?
  3. Look at the addresses. dig +short $(terraform output -raw url | cut -d/ -f3) a few times. The ALB has one address per zone, and they can change: that's why you always point DNS at its name, with an alias record (Chapter 5).
  4. Add a rule. Add a second rule at priority 5 that returns a fixed 200 with "maintenance" for /hello/admin*, apply, and check that it wins over the /hello* rule for that path only.
  5. Clean up with terraform destroy.

Stretch goal. Add an HTTPS listener with an ACM certificate for a domain you own, and change the port 80 listener's default action to a redirect to HTTPS, as Larder's does in Figure 16.1.

16.10Common mistakes

MistakeWhat happensInstead
App keep-alive shorter than the LB idle timeoutOccasional 502s, worst at quiet times; nothing in app logs.Target keep-alive longer than the LB's idle timeout.
Deep health checks on shared dependenciesA database blip marks every target unhealthy at once.Shallow checks; handle dependency failures in the app.
App exits instantly on stopErrors at every deploy and scale-in.Graceful shutdown within the deregistration delay.
Target security group doesn't allow the LBAll targets unhealthy; 503s.Allow the health-check and traffic port from the LB's group.
Trusting X-Forwarded-For from anyoneClients spoof their address in logs and rate limits.Trust it only from the load balancer.
Uneven targets per zone, no cross-zone balancing (NLB)Some targets overloaded, others idle.Equal targets per zone, or enable cross-zone.

✓Chapter summary

  • Load balancers give one stable address, spread load across zones and servers, remove broken servers, and centralise TLS.
  • Layer 7 (ALB) reads HTTP and routes on host and path; layer 4 (NLB) forwards connections, keeps client IPs and offers static addresses.
  • Configure listeners, rules and target groups; each target group has its own health check.
  • Health checks should test the server, not every dependency.
  • Make targets' keep-alive longer than the LB's idle timeout, and shut down gracefully within the deregistration delay.
  • Trust X-Forwarded-For only from the load balancer.

Key terms

Load balancer
A service that spreads client connections or requests over healthy targets.
Listener
A port and protocol a load balancer accepts traffic on.
Rule
A condition and action on an ALB listener, checked by priority.
Target group
A set of targets with a port, protocol and health check.
Health check
A periodic probe that decides whether a target gets traffic.
Fail open
Sending traffic to all targets when every one is unhealthy.
Deregistration delay
How long in-flight requests may finish after a target is removed.
Cross-zone load balancing
Each load balancer node spreading traffic across targets in all zones.

Check your understanding

  1. A partner must allow-list your service's IP addresses in their firewall. Which load balancer do you put in front of it, and why? apply

    Show answer

    A Network Load Balancer with Elastic IPs: it has fixed addresses per zone. An ALB's addresses change over time, so it can't be allow-listed by IP. (If you also need HTTP routing, put the ALB behind the NLB.)

  2. Your health check calls the database. The database fails over, taking 40 seconds. What do users see, and what would you change? explain

    Show answer

    Every target fails its health check together; the ALB either fails open or, briefly, has no healthy targets, so users get errors or 503s even for pages that don't need the database. Make the health check shallow, and let the app handle the database outage (errors for affected requests, cached data, retries).

  3. Why do keep-alive 502s happen more at quiet times than at busy times? explain

    Show answer

    When it's busy, each connection is reused before the app's short keep-alive timeout expires, so the app never closes one. When it's quiet, connections sit idle long enough for the app to close them, and occasionally the load balancer sends a request on a connection at the moment it's being closed.

  4. Users report errors every time you deploy. The ALB's deregistration delay is 300 seconds. Where do you look? apply

    Show answer

    At the app's shutdown: it probably exits immediately on SIGTERM, dropping requests in flight, or the platform kills it before it finishes. Handle the signal, stop accepting new work, finish open requests, then exit, within the platform's stop timeout and the deregistration delay.

  5. Write the rules (priority, condition, action) for: api.larder.example to the API, /static/* to an S3-backed service, HTTP to HTTPS, everything else to the web app. design

    Show answer

    On the :80 listener: default action redirect to HTTPS. On the :443 listener: priority 10, host header api.larder.example → forward to tg-api; priority 20, path /static/* → forward to the static target group; default → forward to tg-web. Host and path rules don't overlap here, but if they could, the lower priority number wins.
