HTTP, TLS and certificates

Most traffic in a cloud network is HTTP wrapped in TLS. Load balancers, CDNs, API gateways and firewalls all read it, end it, or pass it on, and most of their settings only make sense once you know what's inside. This chapter covers what a request looks like, how TLS protects it, what a certificate proves, and where in your network the encryption should start and stop.

By the end you can

  • Read an HTTP request and response, and say what 502, 503 and 504 mean.
  • Explain what TLS protects and how a TLS 1.3 handshake works.
  • Check a certificate's names, dates and chain, and fix a broken chain.
  • Choose where TLS terminates: at the load balancer, end to end, or passed through.

  • DNS names (Chapter 5).

At Larder

Eli moved the webhook endpoint that StockPilot calls, hooks.larder.example, onto a new server with a freshly bought certificate. He opened it in three browsers: a padlock every time. An hour later StockPilot's support desk wrote back: every call now fails with PKIX path building failed: unable to find valid certification path to requested target.

The browsers were right and StockPilot was right. They were checking different things. Section 6.5 explains how both can be true.

6.1The big picture

Three things travel together in almost every connection you'll configure. HTTP is the language: a client asks for something, the server answers. TLS is the sealed envelope: it encrypts the conversation and makes tampering detectable. A certificate is the ID card: it proves the server you reached really is the name you asked for.

The network devices in the rest of this book differ mainly in how far into this stack they look. A layer 4 load balancer only sees TCP and passes encrypted bytes along. A layer 7 load balancer holds the certificate, decrypts the request, reads the HTTP and routes on it. A CDN does the same at the edge of the internet. Knowing which one you're dealing with tells you where certificates must live and what each device can see.

6.2HTTP in one request

An HTTP request is plain structured text: a request line, headers, an empty line, and an optional body.

POST /v1/stock-updates HTTP/1.1
Host: hooks.larder.example
Content-Type: application/json
Authorization: Bearer eyJhbGciOi…
Content-Length: 58

{"store": "NOORD", "sku": "8710398", "on_hand": 14}

And the response:

HTTP/1.1 202 Accepted
Content-Type: application/json
Date: Wed, 25 Nov 2026 09:14:03 GMT

{"status": "queued"}

A few parts matter a lot for networking:

  • Host names the site being asked for. One server or load balancer can serve hundreds of sites on one IP address and pick the right one by this header. Load balancer rules often route on it (“api.* goes to the API servers”).
  • The path (/v1/stock-updates) is the other common routing key: “/api/* to one target group, everything else to another”.
  • X-Forwarded-For and X-Forwarded-Proto are added by proxies and load balancers. Behind a load balancer, the server sees the load balancer's address as the source; these headers carry the real client address and whether the client used HTTPS.

Status codes that point at the network

Status codes in the 4xx range are the client's fault; 5xx are the server's. Three 5xx codes almost always come from a proxy or load balancer, and each points at a different problem behind it:

Table 6.1 · The status codes a load balancer sends
CodeFrom a load balancer, it meansLook at
502 Bad GatewayIt reached a server, but got a broken or no response: connection refused, reset, or garbageIs the app listening on the target port? Did it crash? TLS mismatch to the target?
503 Service UnavailableIt has no healthy servers to send toHealth checks: why are all targets failing them? (Ch. 16)
504 Gateway TimeoutIt connected or sent the request, but the answer didn't come in timeSlow app, or a security group or route dropping traffic between load balancer and targets

HTTP versions

HTTP/1.1 sends one request at a time on each connection, so browsers open several connections at once. HTTP/2 sends many requests at once over a single TCP connection, in binary frames. HTTP/3 does the same over QUIC on UDP (Chapter 3), avoiding TCP's head-of-line blocking and cutting a round trip from new connections. Load balancers and CDNs often speak a newer version to clients and an older one to your servers; that's normal and usually invisible to your application.

6.3What TLS gives you

TLS (Transport Layer Security, the successor to SSL) sits between TCP and HTTP. HTTPS is simply HTTP over TLS. It provides three guarantees:

  • Confidentiality: nobody on the path can read the data.
  • Integrity: nobody can change it without detection.
  • Authentication: the client knows it's talking to the real server, because the server proves it holds the private key for a certificate issued to that name.

Use TLS 1.3 where you can and TLS 1.2 as the minimum. Older versions are broken and disabled by modern clients. Cloud load balancers express this as a security policy that you pick from a list; choose the newest one your clients support.

During the handshake, both sides contribute to a shared secret (the key shares), so even someone who later steals the server's private key can't decrypt recorded conversations. That property is called forward secrecy, and TLS 1.3 always has it.

6.4Certificates

A certificate is a small signed document that binds a public key to one or more names, for a limited time. Its important fields:

Table 6.2 · What's in a certificate
FieldExampleWhy it matters
Subject Alternative Names (SANs)hooks.larder.example, *.api.larder.exampleThe names the certificate is valid for. Clients check the name they asked for is listed.
ValidityNot before 2026-11-02, not after 2027-02-01Expired certificates fail everywhere at once.
IssuerAn intermediate certificate authorityWho vouches for it; the start of the chain.
Public keyEC P-256 or RSA 2048The server proves it holds the matching private key.

A wildcard like *.larder.example covers exactly one level: api.larder.example yes, larder.example and eu.api.larder.example no.

The chain of trust

Clients don't know your certificate. They know a set of root certificates built into the operating system or runtime: the trust store. Roots are kept offline, so they sign intermediate certificates, which sign yours. To trust your certificate, a client must build the chain from your leaf certificate, through the intermediate, to a root it already has.

Key idea

The server must send its own certificate and the intermediates. The client supplies only the root.

6.5Getting certificates right in the cloud

At Larder: solved

Eli had configured the web server with the leaf certificate only, not the intermediate. Desktop browsers quietly fix that: they remember intermediates they've seen before and can download missing ones. StockPilot's Java client does neither, so it couldn't build a chain to any root it trusted. Hence PKIX path building failed.

The immediate fix was serving the full chain file (leaf followed by intermediate). The lasting fix was moving the endpoint behind a load balancer with a certificate from AWS Certificate Manager, which always serves the complete chain and renews itself. Eli also added an external check that connects with a strict client, not a browser.

Managed certificate services remove most certificate problems at once:

  • AWS Certificate Manager (ACM) issues free public certificates for use on AWS load balancers, CloudFront and API Gateway, proves domain ownership with a CNAME record in your DNS, and renews automatically as long as that record stays in place. Azure (App Service and Front Door managed certificates, Key Vault) and Google Cloud (Certificate Manager, Google-managed certificates on load balancers) offer the same.
  • Inside your network, a private certificate authority (AWS Private CA and equivalents) issues certificates for internal names, trusted only by your own machines.
  • On servers you run yourself, use an ACME client such as certbot with Let's Encrypt, and automate renewal.

Watch out: certificates are getting shorter-lived

Public certificates are limited to 398 days today, and the browser and CA industry has agreed to cut that in steps to 47 days by 2029. Any certificate renewed by a person, from a calendar reminder, will eventually be missed. Automate renewal now, and monitor expiry dates from outside.

SNI: many certificates, one address

Because the client sends the name it wants in the ClientHello (Server Name Indication, SNI), one load balancer can hold many certificates and present the right one for each name. AWS Application Load Balancers do this automatically when you attach several certificates to a listener. The flip side is that SNI is visible to anyone on the path, which is why HTTPS hides what you fetch but not which site you fetch it from. Encrypted Client Hello (ECH) is starting to change that.

6.6Where TLS ends

Whoever holds the certificate's private key ends the TLS session and sees the HTTP inside. In a cloud network you choose where that is, and there are three common answers.

Table 6.3 · Choosing where TLS ends
OptionGood forCosts
TerminationSimplest; certificates managed in one place; path routing, WAF, headersPlain HTTP inside the VPC. Often acceptable, but not for regulated data.
Re-encryptionEverything a layer 7 load balancer offers, plus encryption on every hopCertificates on every server too (often from a private CA); a little more CPU
PassthroughThe server must see the client's TLS (mTLS with client certificates, non-HTTP protocols)No path routing, no WAF; certificates on every server

Larder terminates customer traffic at its Application Load Balancer, because it routes on paths and uses a WAF, and re-encrypts to the payment service, because card data must be encrypted on every hop. Chapter 16 builds both.

Mutual TLS

In ordinary TLS only the server shows a certificate. With mutual TLS (mTLS), the client shows one too, so both sides are authenticated. It's common for machine-to-machine traffic: partner APIs, service meshes (Chapter 21), and devices such as Larder's store routers. Load balancers and API gateways at all three providers can now check client certificates for you.

6.7Lab: take a certificate apart

Lab 6 · curl, openssl and broken certificates

You'll inspect a real handshake, read a certificate chain, check expiry, and trigger each classic certificate error on purpose. You need curl and openssl (both preinstalled on macOS and most Linux). Cost: nothing.

  1. Watch a handshake. curl -sv https://www.wikipedia.org -o /dev/null 2>&1 | grep -E 'SSL|TLS|subject|issuer|expire|ALPN|HTTP/'. Find the TLS version, the negotiated HTTP version (ALPN), the certificate's subject and issuer, and its expiry date.
  2. Read the chain. openssl s_client -connect www.wikipedia.org:443 -servername www.wikipedia.org -showcerts </dev/null. Count the certificates the server sends. The first is the leaf; the rest are intermediates. Is a root included? (It shouldn't need to be.)
  3. Check names and dates. Pipe the leaf into openssl x509: 
    openssl s_client -connect www.wikipedia.org:443 -servername www.wikipedia.org </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
    How many names does it cover? How many days until it expires?
  4. Break it. The badssl.com project runs deliberately broken sites. Run curl -sI against https://expired.badssl.com, https://wrong.host.badssl.com, https://self-signed.badssl.com and https://incomplete-chain.badssl.com. Note each error. Then open the same four in a browser: which ones does the browser accept that curl rejects?
  5. See SNI matter. Run step 3's command against www.wikipedia.org without -servername. Do you get the same certificate? Servers that host many names fall back to a default certificate when no name is sent.

Stretch goal. Write a ten-line script that takes a list of your own hostnames and prints how many days each certificate has left, using openssl x509 -enddate. Run it daily. That's a working expiry monitor.

6.8When it doesn't work

ErrorMeansFix
certificate has expiredPast its “not after” dateRenew; automate renewal; monitor from outside

unable to get local issuer certificate, PKIX path building failedThe client can't build a chain to a trusted rootServe the full chain; for private CAs, install the root on clients

✓Chapter summary

  • HTTP requests carry a method, path, Host and headers; load balancers route on host and path and add X-Forwarded-* headers.
  • From a load balancer, 502 = bad answer from a target, 503 = no healthy targets, 504 = no answer in time.
  • TLS gives confidentiality, integrity and authentication. TLS 1.3 adds one round trip and always has forward secrecy.
  • A certificate binds names to a public key for a time. Servers must send the full chain; clients bring the root.
  • Use managed certificates and automate renewal; lifetimes are shrinking toward 47 days.
  • Choose where TLS ends: termination, re-encryption or passthrough. mTLS authenticates clients too.

Key terms

HTTP
The request/response protocol of the web and most APIs.
Host header
The site name a request is for; lets one address serve many sites.
X-Forwarded-For
A header carrying the original client address through proxies.
TLS
The protocol that encrypts and authenticates a connection.
Certificate
A signed binding of names to a public key, valid for a time.
SAN
Subject Alternative Name: the names a certificate covers.
Chain of trust
Leaf, intermediates and a root the client already trusts.
SNI
The server name sent in the ClientHello, used to pick a certificate.
TLS termination
Decrypting TLS at a load balancer or proxy.
Mutual TLS
TLS in which the client also presents a certificate.
Forward secrecy
Past sessions stay safe even if the server's key is later stolen.

Check your understanding

  1. A load balancer returns 503 for every request, while the servers' own logs show nothing at all. What's the most likely cause? apply

    Show answer

    The load balancer has no healthy targets, so it isn't forwarding anything. Check the health checks: path, port and expected status, and whether the servers' security groups allow the load balancer's health check traffic.

  2. Does a certificate for *.larder.example cover larder.example and eu.shop.larder.example? recall

    Show answer

    Neither. A wildcard covers exactly one label in place of the *: shop.larder.example yes, the bare domain and deeper names no. Add them as separate SANs.

  3. Why can a browser show a padlock for a server whose chain is incomplete, while curl or a Java client fails? explain

    Show answer

    Browsers cache intermediates from other sites and can fetch missing ones from the URL in the certificate. Most programmatic clients only use what the server sends plus their root store, so they can't complete the chain.

  4. A compliance rule says traffic must be encrypted on every network hop, and you also need path-based routing and a WAF. Which TLS option do you choose? design

    Show answer

    Re-encryption: terminate at a layer 7 load balancer (so it can route on paths and apply the WAF), then open a new TLS connection to the targets, with certificates on the targets from a private CA.

  5. What does an observer on the network path still learn about an HTTPS request? explain

    Show answer

    The client and server IP addresses and ports, the timing and size of the traffic, and usually the server name, which is sent in the clear as SNI (unless Encrypted Client Hello is used). Not the path, headers or body.
