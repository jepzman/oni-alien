Firewalls in the cloud: security groups and network ACLs

Routes decide where a packet can go. Firewalls decide whether it's allowed to. Cloud networks give you firewalls on every network interface and at every subnet's edge, and the most useful thing you can learn about them is to describe who may talk to whom by role, not by address. Done that way, rules stay short, safe to change and easy to read a year later.

By the end you can

  • Explain how security groups and network ACLs differ, and where each one filters.
  • Write tiered rules that reference security groups instead of IP ranges.
  • Use network ACLs for coarse guardrails without breaking return traffic.
  • Change rules safely, and find which rule is blocking a connection.

At Larder

On Thursday 29 October 2026, at 18:10, the deploy pipeline applied a network rule tidy-up that Eli had written and had approved that afternoon (PR 233): a few address ranges on the database's security group looked unused, so they went. Within minutes Dispatch, the service that assigns couriers to orders, was struggling. Bram, on call, checked Dispatch, the database and the containers, and all of them looked healthy. At 18:35 he found PR 233 in the pipeline's history and reverted it. For 25 minutes, Joost's operations team assigned couriers by hand.

The rule change was wrong, but the interesting questions are why the review didn't catch it, and why everything Bram checked looked healthy. Section 9.6 answers both.

9.1The big picture

On AWS a packet between two servers can be filtered in two places that you configure inside the VPC. A security group wraps each network interface: it's stateful and contains only allow rules. A network ACL sits at each subnet's boundary: it's stateless, has numbered allow and deny rules, and checks every packet in both directions. A packet must get past every filter on its way, and so must its reply.

Further out there are more layers you'll meet later: network firewalls for inspecting traffic that leaves the VPC (Chapter 18), web application firewalls in front of HTTP services (Chapter 17), and policies inside Kubernetes (Chapter 19). But security groups do most of the everyday work, so most of this chapter is about them.

9.2Security groups

A security group is a set of rules attached to one or more network interfaces. Its behaviour fits in five lines:

  • Stateful. If a connection is allowed in one direction, its replies are allowed automatically (Chapter 3).
  • Allow rules only. Anything not allowed is denied. You can't write “deny”.
  • No order. All rules are checked together; if any rule allows a packet, it's allowed.
  • Inbound and outbound rules are separate. A new group allows all outbound traffic and no inbound traffic.
  • Per interface. An interface can have several groups (up to five by default); their rules add up.

Each rule names a protocol, a port or port range, and a source (for inbound) or destination (for outbound). The source can be a CIDR range, a prefix list (a named, reusable list of ranges), or, most usefully, another security group.

9.3Reference roles, not addresses

A rule like “allow 5432 from sg-app” means: allow traffic from any interface that has the security group sg-app attached, whatever its address is right now. When a container restarts with a new IP, or Dispatch scales from two copies to six, the rule still matches. Nobody edits it.

Key idea

Give each role its own security group, and write rules between groups. Use CIDR ranges only for things outside your VPC.

9.4Network ACLs

A network ACL (NACL) is attached to a subnet and filters every packet that enters or leaves it. It works very differently from a security group:

Table 9.2 · Security groups and network ACLs side by side

Attached tonetwork interfacessubnets
Statestateful: replies allowedstateless: replies need their own rules
Rule actionsallow onlyallow and deny

Because they're stateless and address-based, NACLs are a poor tool for everyday rules and a good one for coarse guardrails: “nothing outside the app tier may ever reach the data subnets”, or “block this range now” during an incident. Here's Larder's NACL for its data subnets:

Watch out: return traffic

Every stateless rule set needs the reverse direction too, and replies go to ephemeral ports, not the service port. Forgetting outbound rule 100 above makes every database query time out, while the security groups all look perfect. If you're not sure you need NACLs, leave the default (allow all) in place and do your filtering with security groups.

9.5How the layers combine

A connection works only if every filter on the path allows it, in both directions, and a route exists both ways (Chapter 4). When it doesn't work, check in the order a packet meets them, as in Figure 9.1:

  1. Source security group, outbound. Usually “all”, unless you've restricted egress.
  2. Source subnet NACL, outbound, then destination subnet NACL, inbound: only if the two are in different subnets.
  3. Destination security group, inbound. The most common culprit: wrong port, wrong source group, or a rule on the wrong group.
  4. The reply: destination NACL outbound and source NACL inbound, on ephemeral ports.

Security group denials don't send anything back; the packet just disappears, so blocked connections time out. A connection refused means you got through every firewall and reached a machine with nothing listening (Chapter 3).

9.6Changing rules safely

One detail of stateful filtering makes firewall changes behave in a way that surprises almost everyone the first time. When you remove a security group rule, connections that are already established and tracked usually keep working. Only new connections are blocked.

At Larder: solved

The database's security group still allowed Dispatch by address range, from before the move to containers, and the range that looked unused was the one Dispatch's tasks had recently started getting addresses from. The plan in PR 233 showed the removal clearly; it just didn't show who depended on it. When the rule went at 18:10, Dispatch's two running copies kept their pooled connections open: already tracked, so still allowed, which is why they looked healthy. But it was the start of the evening peak, so Dispatch scaled up, and every new copy timed out connecting to Postgres while the two old ones were swamped.

The network fixes, after the revert: replace every address-based rule inside the VPC with security group references (sg-dispatch in Figure 9.2), so a rule says who it's for; and add a step to the pipeline that runs Reachability Analyzer for the paths that matter, such as Dispatch → Postgres on 5432, after every network change. (The operations side of this incident, a change feed and no changes in the evening peak, is in Eli's IT Operations Notebook.)

The general lessons:

  • A change that “didn't break anything” hasn't been tested yet. Test with a new connection, not with an existing one.
  • Manage rules as code, reviewed like any other change, so the plan shows exactly what's removed (Chapter 24). A reviewed plan still can't tell you who depends on a rule; that's what role-based rules and reachability checks are for.
  • Automate reachability checks for critical paths. AWS Reachability Analyzer works out from configuration alone, without sending traffic, whether a path is open, and which rule blocks it if not.
  • Name and describe every rule. “Why is this here?” should be answerable from the rule's own description.

9.7Least privilege, including outbound

Most teams tighten inbound rules carefully and leave outbound at the default “allow everything”. That's convenient, but it means a compromised server can send data anywhere. Restrict outbound traffic where the stakes are highest:

  • Data tier: outbound only to what it needs: replies to the app tier, and S3 through the gateway endpoint using its prefix list as the destination.
  • App tier: to the database group, the cache group, and HTTPS out. Restricting HTTPS by domain name, not address, needs a different tool: a proxy or network firewall (Chapter 18).
  • Remember the basics the OS needs: DNS to the VPC resolver and time sync are handled by the VPC itself on AWS and aren't filtered by security groups.

On Azure

An NSG can sit on a subnet, a network interface, or both; traffic must pass both. Default rules allow traffic inside the VNet and from Azure's load balancer, and deny other inbound traffic. Group VMs by role with application security groups and refer to Azure services with service tags such as Storage.WestEurope instead of address ranges.

On Google Cloud

Firewall rules belong to the whole VPC network, not a subnet, and apply to the VMs they target, chosen by network tag or, better, by service account. The implied rules allow all egress and deny all ingress. Organisation and folder-level hierarchical firewall policies let a central team set rules that projects can't override.

9.9Lab: let the analyser find the blocking rule

Lab 9 · Security groups, a NACL and Reachability Analyzer

You'll build two subnets with a network interface each (no servers needed), tiered security groups and a stateless NACL, then ask Reachability Analyzer whether the app can reach the database, and break it two ways. You need the AWS CLI and Terraform (Appendix C). Cost: the network interfaces, groups and ACLs are free; each analysis costs $0.10, so about $0.40.

main.tfTerraform ≥ 1.5, AWS provider 5.x

provider "aws" { region = "eu-central-1" }

resource "aws_vpc" "lab" { cidr_block = "10.30.0.0/16" }

resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.lab.id
  cidr_block = "10.30.1.0/24"
}
resource "aws_subnet" "data" {
  vpc_id     = aws_vpc.lab.id
  cidr_block = "10.30.2.0/24"
}

# 9.3 · one group per role; the database allows 5432 from the app GROUP
resource "aws_security_group" "app" {
  name   = "sg-app"
  vpc_id = aws_vpc.lab.id
}
resource "aws_security_group" "db" {
  name   = "sg-db"
  vpc_id = aws_vpc.lab.id
}

# Terraform removes AWS's default allow-all egress rule, so add it back for the app
resource "aws_vpc_security_group_egress_rule" "app_out" {
  security_group_id = aws_security_group.app.id
  ip_protocol       = "-1"
  cidr_ipv4         = "0.0.0.0/0"
}
resource "aws_vpc_security_group_ingress_rule" "db_from_app" {
  security_group_id            = aws_security_group.db.id
  referenced_security_group_id = aws_security_group.app.id
  ip_protocol                  = "tcp"
  from_port                    = 5432
  to_port                      = 5432
  description                  = "Postgres from the app tier"
}

# 9.4 · a stateless guardrail on the data subnet
resource "aws_network_acl" "data" {
  vpc_id     = aws_vpc.lab.id
  subnet_ids = [aws_subnet.data.id]
  ingress {
    rule_no    = 100
    action     = "allow"
    protocol   = "tcp"
    cidr_block = "10.30.1.0/24"
    from_port  = 5432
    to_port    = 5432
  }
  egress {                                   # replies to the app subnet
    rule_no    = 100
    action     = "allow"
    protocol   = "tcp"
    cidr_block = "10.30.1.0/24"
    from_port  = 1024
    to_port    = 65535
  }
}

# stand-ins for an app server and a database: just network interfaces

}

  subnet_id       = aws_subnet.data.id

  2. Define the path and analyse it.

  A=$(aws ec2 start-network-insights-analysis --network-insights-path-id $P \

check
    You should see true: the path is open.
  3. Break the NACL. Delete the egress block from aws_network_acl.data, terraform apply, and run check again. The explanation names the network ACL and the direction: the reply has nowhere to go.
  4. Fix it and break the security group. Restore the egress block, change from_port and to_port in db_from_app to 3306, apply, and check. Now the explanation points at the security group.

✓Chapter summary

  • Security groups sit on interfaces: stateful, allow-only, unordered. NACLs sit on subnets: stateless, ordered, allow and deny.
  • A connection needs every filter on the path, both directions, to allow it. Blocked traffic times out.
  • Write rules between roles by referencing security groups; use CIDRs only for the outside world.
  • Use NACLs as coarse guardrails, and always allow the ephemeral-port replies.
  • Removing a rule doesn't cut tracked connections; test with new ones. Manage rules as code and check critical paths automatically.
  • Restrict outbound traffic where data is most sensitive.

Key terms

Security group
A stateful, allow-only firewall attached to network interfaces.
Network ACL
A stateless, ordered allow/deny list attached to a subnet.
Security group reference
A rule whose source or destination is another security group.
Prefix list
A named set of CIDR ranges usable in rules and routes.
Connection tracking
How a stateful firewall remembers connections and allows their replies.
Least privilege
Allowing only the traffic each role actually needs.
Reachability Analyzer
An AWS tool that checks from configuration whether a path is open.
NSG / ASG
Azure's network security groups and application security groups.

Check your understanding

  1. Two servers in the same subnet can't talk. Which filters could be responsible: the security groups, the NACL, or both? recall

    Show answer

    Only the security groups. A NACL filters traffic crossing the subnet boundary, and this traffic never leaves the subnet.

  2. Why is “allow 5432 from sg-app” better than “allow 5432 from 10.20.16.0/20”? explain

    Show answer

    It follows the role, not the address: any interface with sg-app is allowed, wherever it gets its address, and nothing else in that range is. It doesn't need editing when servers move, scale or change subnet.

  3. You remove a rule and everything keeps working, so you close the change. An hour later a deploy fails to connect. What happened? apply

    Show answer

    The existing connections were tracked, so they stayed allowed after the rule was removed. The deploy started new processes that opened new connections, which the remaining rules don't allow.

  4. Write the inbound and outbound NACL rules a public subnet needs for a web server to serve HTTPS to the internet. apply

    Show answer

    Inbound: allow TCP 443 from 0.0.0.0/0. Outbound: allow TCP 1024–65535 to 0.0.0.0/0 for the replies. (If the server also makes outbound calls, add outbound 443 and inbound 1024–65535 for those replies.)

  5. A platform team wants a rule that no team can override: nothing may reach the data subnets except from the app subnets. Which tools would you use on AWS, Azure and Google Cloud? design

    Show answer

    AWS: a NACL on the data subnets (managed centrally), or Firewall Manager policies. Azure: Virtual Network Manager security admin rules, which take precedence over NSGs. Google Cloud: a hierarchical firewall policy at the organisation or folder level.
