TCP, UDP and ports

IP gets a packet to the right machine. The transport layer gets it to the right program, and, if you want, makes sure nothing is lost on the way. Understanding how a connection opens, stays alive and closes explains most firewall rules, most “connection reset” mysteries, and the difference between a timeout and a refusal.

At Larder

Cho, who looks after payments, has an odd bug. A few times a day, a card payment fails with Connection reset by peer when Larder's servers call the payment provider. A retry always works. It happens most often at 07:00, when the first breakfast orders arrive, and almost never at 18:00, the busiest time of day.

A bug that gets rarer when it's busy is a clue. Section 3.7 explains it.

3.1The big picture

A server might run a web server, a database and a monitoring agent at the same time, all behind one IP address. The transport layer decides which program each packet belongs to, using port numbers, and offers two very different ways of sending data.

  • TCP (Transmission Control Protocol) sets up a connection first, then delivers a stream of bytes complete and in order, resending anything that's lost. The web, databases, SSH and most APIs use it.
  • UDP (User Datagram Protocol) just sends individual messages, with no connection and no guarantees. It's used where speed matters more than perfection, or where the program handles reliability itself: DNS, video calls, and QUIC, which carries HTTP/3.

Both carry port numbers. Everything else about them differs, and those differences shape how firewalls, load balancers and NAT gateways behave.

3.2Ports and sockets

A port is a 16-bit number, from 0 to 65,535. A server program listens on a port it chose in advance, so clients know where to find it. Some numbers are conventions everyone relies on:

The client doesn't need a well-known port. When your browser connects, the operating system picks a free ephemeral port for it, a temporary number from a high range: 32768–60999 on Linux, 49152–65535 on Windows and macOS. The reply comes back to that port, which is how the right browser tab gets it.

Five values make a connection

A connection is identified by five values, together called the 5-tuple: protocol, source IP, source port, destination IP, destination port. For example:

TCP  10.20.17.8:51544  →  10.20.64.12:5432

A second connection from the same app server to the same database differs only in its source port (say 51545), so the two never get mixed up. Firewalls, NAT gateways and load balancers all keep tables keyed on this 5-tuple. Keep it in mind; it explains a lot of behaviour later in the book.

SocketThe programmer's word for one end of a connection: an IP address and a port, plus the operating system's bookkeeping. “The app opened a socket” means it started or accepted a connection.

Which address is it listening on?

A program listens on a port and an address. Listening on 127.0.0.1 means “only this machine may connect”. Listening on 0.0.0.0 means “any of my addresses”. Plenty of tools and frameworks default to 127.0.0.1 for safety, and then a perfectly configured network still gets connection refused, because the program isn't listening where the packets arrive. ss -tlnp on Linux shows what's listening where.

3.3TCP: a connection in three packets

Before any data flows, TCP's two ends exchange three packets, the three-way handshake, to agree that they're both there and to pick starting sequence numbers. Sequence numbers count bytes: they let the receiver put data back in order and tell the sender exactly what arrived.

Once established, TCP keeps three promises:

  • Reliability. The receiver acknowledges what it got. Anything not acknowledged in time is sent again.
  • Order. Data reaches the program in the order it was sent, even if packets arrived out of order.
  • Pacing. Flow control stops a fast sender drowning a slow receiver, and congestion control slows everyone down when the network is overloaded.

A connection ends politely with a FIN from each side, or abruptly with a RST (reset), which means “I don't know this connection, stop”. You'll meet RST again in a moment, because it's behind both “connection refused” and “connection reset”.

3.4Refused, timed out, reset

Each of the three classic connection errors maps to something specific that happened, or didn't, in the handshake. This is the transport-layer version of Table 1.5 in Chapter 1.

Table 3.2 · What each error means at the TCP level
ErrorWhat happenedLook at
Connection refusedThe SYN arrived; the machine answered with RST. Nothing is listening on that port and address.Is the program running? Listening on 0.0.0.0 or only 127.0.0.1? Right port?
Connection timed outThe SYN got no answer at all. The client retried several times, then gave up.Routes and firewalls: something dropped the packets, going or returning.
Connection reset by peerAn established connection received a RST.The other end crashed or closed it, or a middlebox (NAT, load balancer, firewall) forgot it.

Watch out: timeouts are slow

On Linux, an unanswered SYN is retried six times with growing waits, so a connect attempt can hang for over two minutes before failing. Programs that don't set their own connect timeout freeze for that long whenever a firewall drops their traffic. Always set one: a couple of seconds is plenty inside a cloud region.

3.5UDP, and why HTTP/3 uses it

UDP sends a datagram: one self-contained message with source and destination ports, and nothing more. No handshake, no acknowledgements, no ordering. If it's lost, it's lost, unless the program notices and sends it again.

That sounds worse, but it's exactly right in some cases:

  • DNS: one small question, one small answer. A handshake would double the time; if the answer doesn't come, the client just asks again.
  • Voice and video: a late packet is useless, so resending it is pointless. Better to skip it and carry on.
  • QUIC, the transport under HTTP/3: it builds its own reliability and encryption on top of UDP, combining the transport and TLS handshakes so a new connection needs one round trip instead of two or three. It also survives a phone switching from Wi-Fi to mobile data, because connections aren't tied to the 5-tuple.

For cloud networking, the main thing to remember is that UDP traffic must be allowed separately from TCP. A security group that allows “TCP 443” doesn't allow HTTP/3; load balancers have separate UDP support; and DNS needs UDP 53 and TCP 53 (large answers fall back to TCP).

3.6Stateful and stateless filtering

Every connection has traffic in two directions: the request goes to the server's well-known port, and the reply comes back to the client's ephemeral port. A firewall has to allow both. There are two ways it can do that, and cloud providers offer both, so you need to know which one you're configuring.

Key idea

A stateful firewall remembers connections, so you write rules for who may start one. A stateless firewall remembers nothing, so you write rules for every packet, including replies to ephemeral ports.

In the cloud, security groups (AWS), network security groups (Azure) and firewall rules (Google Cloud) are stateful. AWS network ACLs are stateless. Chapter 9 uses both, and the ephemeral-port rule is the single most common mistake people make with network ACLs.

3.7Idle connections don't live forever

Anything that keeps a table of connections, whether a stateful firewall, a NAT gateway or a load balancer, has limited memory. So each one forgets connections that have been idle for a while. Neither end is told. The next packet on that connection arrives at a device that has never heard of it, and the device either drops it or answers with a RST.

At Larder: solved

Larder's payment client keeps a pool of open HTTPS connections to the payment provider, to save the handshakes. Those connections leave through a NAT gateway. During the night there are no orders, so pooled connections sit idle for hours. The NAT gateway forgets them after 350 seconds. At 07:00 the first order picks a pooled connection, sends a request, and the NAT gateway answers with RST: Connection reset by peer. At 18:00 connections are never idle long enough to be forgotten, so the bug disappears.

Cho made two changes: the pool now closes connections idle for more than 60 seconds, well under the NAT gateway's 350, and the client retries once on a reset, which is safe because payments carry an idempotency key. The resets stopped.

The general fix has two parts, and you should apply both whenever a connection crosses a NAT gateway, load balancer or firewall:

  1. Close idle connections before the middlebox forgets them. Set the client's or pool's idle timeout below the shortest timeout on the path.
  2. Or keep them visibly alive. TCP keepalives (with an interval below that timeout, not Linux's default of two hours) or application pings stop the connection from ever going idle.

3.9Lab: see a handshake with your own eyes

Lab 3 · Listen, connect, refuse, capture

You'll start a server, see what it listens on, connect to it, cause a refusal, and capture the handshake packets. You need macOS or Linux (on Windows, use WSL), Python 3, nc and tcpdump (preinstalled on macOS; apt install netcat-openbsd tcpdump on Ubuntu). Cost: nothing.

  1. Start a server on localhost only. In terminal 1: python3 -m http.server 8000 --bind 127.0.0.1.
  2. See what's listening. In terminal 2: ss -tlnp | grep 8000 on Linux, or lsof -nP -iTCP:8000 -sTCP:LISTEN on macOS. Note the address: 127.0.0.1:8000.
  3. Capture. In terminal 3: sudo tcpdump -i lo -n 'tcp port 8000' (on macOS the interface is lo0).
  4. Connect. In terminal 2: nc -vz 127.0.0.1 8000. In terminal 3, find the three handshake packets: [S], [S.] and [.] are SYN, SYN-ACK and ACK. Then the closing [F.] packets.
  5. Refuse. Run nc -vz 127.0.0.1 8001, where nothing listens. You get Connection refused at once, and tcpdump (change the filter to port 8001) shows a [S] answered by [R.]: the RST.
  6. The listen-address trap. Find your machine's network address (Lab 1) and run nc -vz <that address> 8000. Refused, even though the server is running. Restart it with --bind 0.0.0.0 and try again.

Stretch goal. Run curl -v https://example.com -o /dev/null while capturing with sudo tcpdump -n 'tcp port 443' on your main interface. Count the round trips before the first data packet from the server.

No connect timeout in the clientRequests hang for minutes when a firewall drops traffic.Set connect timeouts of a few seconds.
Connection pools that outlive middlebox timeoutsRandom connection reset after quiet periods.Idle-close below the shortest timeout, or keepalives.
Allowing TCP 53 but not UDP 53 (or the reverse)DNS fails intermittently, usually for large answers.Allow both for DNS.

✓Chapter summary

  • Ports pick the program. Servers listen on known ports; clients use temporary ephemeral ports.
  • A connection is identified by its 5-tuple: protocol, source IP and port, destination IP and port.
  • TCP opens with a three-way handshake and delivers bytes reliably and in order. UDP sends independent datagrams; QUIC builds HTTP/3 on it.
  • Refused = RST to a SYN (nothing listening). Timed out = silence (dropped). Reset = an established connection was killed or forgotten.
  • Stateful firewalls allow replies automatically; stateless ones need rules for return traffic to ephemeral ports.
  • NAT gateways, load balancers and firewalls forget idle connections. Keep pools' idle timeouts shorter.

Check your understanding

  1. Write the 5-tuple of the reply packet for a request TCP 10.20.17.8:51544 → 10.20.64.12:5432. recall

    Show answer

    TCP 10.20.64.12:5432 → 10.20.17.8:51544. Source and destination swap, ports included.

  2. Calls to a new service fail instantly with Connection refused. The security group allows the port. What do you check first? apply

    Show answer

    The service itself: is it running, on that port, and listening on an address other than 127.0.0.1? A refusal means the packets arrived, so the security group and routes aren't the problem.

  3. A network ACL allows inbound TCP 443 and outbound TCP 443. Web requests from the internet to a server behind it time out. Why? explain

    Show answer

    Network ACLs are stateless. Replies go from the server's port 443 to the client's ephemeral port, so the outbound rule must allow destination ports 1024–65535, not 443.

  4. Why does DNS use UDP, and when does it fall back to TCP? explain

    Show answer

    A DNS lookup is one small question and one small answer, so a handshake would double its time; a lost packet is simply asked again. Answers too large for a UDP response (common with DNSSEC or many records) are retried over TCP, so both must be allowed.

  5. A worker keeps a database connection open through an AWS Network Load Balancer and is idle for ten minutes between jobs. What will happen, and what are two fixes? design

    Show answer

    The load balancer forgets the connection after 350 seconds, and the worker's next query gets a reset. Fixes: close and reopen connections when idle for less than 350 seconds (or validate them before use), or enable TCP keepalives with an interval under 350 seconds. Raising the load balancer's timeout also helps.
