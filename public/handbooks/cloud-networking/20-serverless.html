Serverless and managed services in your network

Functions, managed databases, queues and container services all promise that you don't have to think about servers. You still have to think about networks: each of these services lives somewhere relative to your VPC, and that decides what it can reach, what can reach it, and what breaks when you move it. This chapter maps where managed services sit and how to connect them safely.

By the end you can

  • Say where a managed service lives: outside your VPC, inside it, or in a provider's network joined to it.
  • Attach functions to a VPC without losing internet access by surprise.
  • Connect to managed databases by name, through the right subnets and security groups.
  • Avoid connection storms from serverless code to databases.

Before you start

  • Private subnets and NAT (Chapter 8), security groups (Chapter 9).
  • Interface endpoints (Chapter 12).

At Larder

Larder's warehouse system sends stock changes as webhooks, and a small Lambda function receives them and calls WMS B's API back for details. It worked perfectly until the team decided the function should also write straight to Postgres, which lives in the isolated data subnets. Ben's team attached the function to the VPC, in the public subnets “so it keeps its internet access”. Every invocation now ends in a timeout calling WMS B, and the database writes never happen because they come after that call.

Putting a function in a public subnet seems like it should give it the internet. It doesn't. Section 20.2 explains why.

20.1The big picture

Every managed service sits in one of three places relative to your network, and the place decides how you connect to it.

Key idea

A service that puts interfaces in your subnets follows your subnets' rules: their routes, their security groups, their address limits. “Managed” doesn't change that.

20.2Functions and VPCs

By default, a Lambda function runs in a network AWS manages. It can reach the internet and public AWS endpoints, and nothing in your VPC. To reach private resources, such as a database in your data subnets, you attach the function to your VPC: choose subnets and security groups, and Lambda creates network interfaces there (shared between functions with the same subnet and security group combination). From then on, all of the function's traffic leaves through those interfaces and follows your subnets' route tables.

At Larder: solved

Lambda's network interfaces never get public IP addresses, even in a public subnet. A public subnet's default route goes to the internet gateway, which only translates for interfaces with public addresses (Chapter 8, 8.5), so the function's packets to WMS B had nowhere to go. Eli moved the function to the private app subnets, whose route tables send 0.0.0.0/0 to the NAT gateway in the same zone, and added a security group that allows it to reach Postgres. WMS B calls worked again. Secrets Manager calls went through the existing interface endpoint (Chapter 12), so they never touched the NAT gateway.

Three more rules for VPC-attached functions:

  • Use at least two subnets in different zones, so the function keeps working if one zone fails.
  • Leave room for interfaces. Interfaces are shared and few, but they still take addresses and need free space in the subnet to be created.
  • The execution role needs permission to manage network interfaces (AWS's AWSLambdaVPCAccessExecutionRole policy).

20.3Containers without servers

ECS tasks on Fargate use the awsvpc network mode: every task gets its own network interface, private address and security groups. That's the same VPC-native model as Kubernetes pods on EKS (Chapter 19), with the same consequences: each running task uses an address in its subnet, and deploys briefly double the count. Tasks in public subnets can be given public IPs; tasks in private subnets go out through NAT and endpoints, like everything else. Load balancers register tasks by IP.

20.4Managed databases in your VPC

RDS, Aurora, ElastiCache and similar services place their instances in subnets you choose through a subnet group: a list of subnets in at least two zones. The provider decides which subnet each instance lands in, and moves them during failover. Four rules follow:

  1. Use the endpoint name, never an address. On failover, the standby takes over and the endpoint's DNS record changes to its address (Chapter 5). Clients that cached the old address, or connect by IP, keep talking to the old one. Keep DNS caching in clients short.
  2. Put the subnet group in the data tier: isolated subnets with no internet route (Chapter 8).
  3. Allow clients by security group: “5432 from sg-app” on the database's group (Chapter 9).
  4. Count connections. Every database has a connection limit, and each connection uses memory.

Connection storms

The fourth rule bites hardest with serverless code. A busy function may run hundreds of copies at once, each opening its own database connection, and copies come and go faster than connections time out. The result is a database refusing new connections at the worst moment. A connection pooler between functions and the database fixes it: RDS Proxy on AWS keeps a small pool of database connections and shares them among many client connections, and also makes failovers faster for clients. Self-managed poolers like PgBouncer do the same for long-running services.

20.5Calling serverless things privately

The other direction: how do your private servers call managed services that live outside your VPC?

  • Queues, topics, storage, functions' APIs: through gateway and interface endpoints (Chapter 12), with endpoint policies.
  • Your own APIs on API Gateway: a private API is reachable only through an execute-api interface endpoint in your VPC, with a resource policy that names the endpoints allowed to call it.
  • Functions behind a load balancer: an internal ALB with a Lambda target group (Chapter 16's lab, made internal) gives a private HTTP address for a function.

On Azure and Google Cloud

Two ideas don't exist on AWS in the same form. Azure delegated subnets hand a whole subnet to one service, which places its own resources there; you can't put anything else in it. Google Cloud's private services access peers your VPC with a Google-managed one where services like Cloud SQL live; you reserve an address range for it from your plan (Chapter 10), and it can't overlap anything you'll ever connect.

20.8Lab: a function loses the internet

Lab 20 · Not attached, then attached to a VPC with no NAT

You'll deploy a function that fetches its own public IP address, run it outside a VPC, then attach it to private subnets with no NAT and watch it time out. You need the AWS CLI and Terraform. Cost: within Lambda's free tier; the VPC parts are free.

main.tfTerraform ≥ 1.5, AWS provider 5.x, archive provider

provider "aws" { region = "eu-central-1" }

variable "in_vpc" { default = false }

data "aws_availability_zones" "z" { state = "available" }
resource "aws_vpc" "lab" { cidr_block = "10.90.0.0/16" }
resource "aws_subnet" "private" {
  count             = 2
  vpc_id            = aws_vpc.lab.id
  cidr_block        = cidrsubnet(aws_vpc.lab.cidr_block, 8, count.index)
  availability_zone = data.aws_availability_zones.z.names[count.index]
}
resource "aws_security_group" "fn" { vpc_id = aws_vpc.lab.id }
resource "aws_vpc_security_group_egress_rule" "fn" {
  security_group_id = aws_security_group.fn.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}

data "archive_file" "fn" {
  type        = "zip"
  output_path = "fn.zip"
  source {
    filename = "index.py"
    content  = <<-EOT
      import urllib.request
      def handler(event, context):
          ip = urllib.request.urlopen("https://checkip.amazonaws.com", timeout=5).read()
          return {"my_public_ip": ip.decode().strip()}
    EOT
  }
}
resource "aws_iam_role" "fn" {
  name = "handbook-lab20-fn"
  assume_role_policy = jsonencode({
    Version   = "2012-10-17"
    Statement = [{ Effect = "Allow", Action = "sts:AssumeRole",
                   Principal = { Service = "lambda.amazonaws.com" } }]
  })
}
resource "aws_iam_role_policy_attachment" "vpc" {
  role       = aws_iam_role.fn.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaVPCAccessExecutionRole"
}
resource "aws_lambda_function" "fn" {
  function_name    = "handbook-lab20"
  role             = aws_iam_role.fn.arn
  runtime          = "python3.12"
  handler          = "index.handler"
  timeout          = 10
  filename         = data.archive_file.fn.output_path
  source_code_hash = data.archive_file.fn.output_base64sha256

  # 20.2 · attach to the VPC only when in_vpc = true
  dynamic "vpc_config" {
    for_each = var.in_vpc ? [1] : []
    content {
      subnet_ids         = aws_subnet.private[*].id
      security_group_ids = [aws_security_group.fn.id]
    }
  }
  depends_on = [aws_iam_role_policy_attachment.vpc]
}
  1. Outside the VPC. terraform init, terraform apply, then aws lambda invoke --function-name handbook-lab20 out.json && cat out.json. You get a public IP address: one of AWS's, shared and changing.
  2. Attach it. terraform apply -var in_vpc=true, invoke again. After 5 seconds: a timeout. The subnets have no route to the internet at all.
  3. Find its interface. In the EC2 console, under Network interfaces, filter on the VPC. The interface described as an AWS Lambda VPC interface is the function's way into your network. It has no public address, and never will.
  4. Think it through. What would you add for the function to reach the internet again, and what would it cost per hour? (Chapter 8's answer: a NAT gateway in a public subnet and a route to it from these subnets.)
  5. Clean up with terraform destroy. Removing a function's VPC interfaces can take several minutes; let it finish.

Stretch goal. Add a public subnet, an internet gateway and a NAT gateway (as in Lab 8), route the private subnets to it, invoke again, and compare the returned address with the NAT gateway's Elastic IP. Then destroy promptly: the NAT gateway bills by the hour.

✓Chapter summary

  • Managed services live outside your VPC, inside it with interfaces in your subnets, or in a provider network joined to yours.
  • Services inside your VPC follow your subnets' routes, security groups and address limits.
  • A VPC-attached function loses default internet access and never gets a public IP: use private subnets with NAT, plus endpoints.
  • Fargate tasks are VPC-native: one interface and address per task.
  • Use managed databases through subnet groups, endpoint names and security group references; pool connections from serverless code.
  • Call managed services privately through endpoints and private APIs.

Key terms

VPC-attached function
A function whose traffic goes through interfaces in your subnets.
awsvpc mode
ECS networking where each task has its own interface and address.
Subnet group
The subnets a managed database may place instances in.
Database endpoint
The DNS name that points at the current primary or reader.
Connection pooler
Shares a few database connections among many clients.
Private API
An API Gateway API reachable only through an interface endpoint.
Delegated subnet
An Azure subnet handed to one service for its resources.
Private services access
Google Cloud's peering link to the network where some managed services run.

Check your understanding

  1. Why does a VPC-attached Lambda function in a public subnet fail to reach the internet? explain

    Show answer

    Its interfaces never get public addresses, and an internet gateway only translates for interfaces with public addresses. Its packets have a route but no way to be translated, so they go nowhere.

  2. A function reads from S3 and writes to a private Postgres database. Design its network access with no NAT gateway. design

    Show answer

    Attach it to private subnets in two zones; add an S3 gateway endpoint to those subnets' route tables (and interface endpoints for any other AWS services it calls); allow 5432 from the function's security group on the database's (or RDS Proxy's) group. No internet route is needed.

  3. After a database failover, half the app servers keep failing for ten minutes. What's the likely cause? apply

    Show answer

    Those servers cached the endpoint's old address, through a long DNS cache in the runtime or connection pools holding connections to the old primary. Use endpoint names, keep client DNS caching short, and validate or recycle pooled connections on errors.

  4. Why does serverless code need a connection pooler more than a fleet of long-running servers does? explain

    Show answer

    Concurrency scales to hundreds of short-lived copies, each opening its own connection, faster than old connections close. Long-running servers keep a small, steady pool each. A pooler like RDS Proxy shares a few database connections among all those copies.

  5. On Google Cloud, you reserve 10.20.0.0/16 for private services access. What's the risk? apply

    Show answer

    That range is peered into your VPC for managed services, so it can't overlap any network you'll connect later. Larder's production VPC uses 10.20.0.0/16, so connecting the two clouds would be impossible. Reserve it from the address plan like any other block.
