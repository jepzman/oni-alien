Private access to cloud services

Your servers call dozens of services that aren't in your VPC: the provider's own APIs for secrets, keys, queues and container images, and other companies' services too. By default those calls go out through a NAT gateway and across the provider's public endpoints. This chapter shows how to reach them privately instead, and how to offer one of your own services privately to a partner, without connecting your networks at all.

By the end you can

  • Choose between gateway endpoints, interface endpoints and NAT for a service.
  • Explain how an interface endpoint's private DNS works, and when it surprises people.
  • Publish your own service with PrivateLink and connect a consumer to it.
  • Restrict what can be done through an endpoint with endpoint policies.

At Larder

Two requests land on Eli's desk in the same week. Korenwolf wants its office ordering system to call Larder's ordering API privately, and its network uses Larder's production range, 10.20.0.0/16 (Chapter 10). And Lena, the data protection officer, reviewing the data tier, asks why the database migration job in the isolated subnets has a route to the internet at all. The answer is that it needs Secrets Manager and the container registry, which live “on the internet”.

Both requests have the same answer, from opposite sides. This chapter builds it.

12.1The big picture

A cloud provider's services, like Secrets Manager or S3, are reached through regional endpoints with public addresses. A server in a private subnet calls them through a NAT gateway: out of the VPC, onto the provider's public front door, and back. It works, but it costs NAT processing fees, needs a route to the internet, and makes the traffic harder to restrict. There are two private alternatives on AWS, and a third for services you build yourself:

12.2Interface endpoints

An interface endpoint puts a network interface, with a private IP address from your subnet, into each zone you choose. Behind that interface, AWS PrivateLink carries traffic to the service, entirely on AWS's network. To your servers, the service now lives at a few addresses inside your own VPC.

Three details make interface endpoints work well, or badly:

  • Private DNS. With private DNS turned on, the service's ordinary public name (secretsmanager.eu-central-1.amazonaws.com) resolves to the endpoint's private addresses for anything using the VPC's resolver. No code or configuration changes. It needs the VPC's DNS resolution and DNS hostnames settings on (Chapter 5).
  • A security group on the endpoint decides who may use it. Allow 443 from the groups or ranges that need the service, and nothing else.
  • An endpoint policy decides what may be done through it, as an IAM-style policy. For example: only secrets belonging to Larder's own accounts, so a compromised job can't send data to a secret in an attacker's account through your endpoint.

The usual set for a private subnet

A workload in a subnet without NAT typically needs a handful of endpoints. Missing one shows up as a timeout in exactly one part of the startup.

Cost checkAn interface endpoint costs about $0.01 an hour per zone, roughly $22 a month across three zones, plus about $0.01 per GB. Seven endpoints in one VPC is around $150 a month: cheaper than NAT for heavy traffic, dearer for light use. Many companies centralise endpoints in the hub (12.5).

12.3Publishing your own service with PrivateLink

The same mechanism works for services you build. You put your service behind a Network Load Balancer and create an endpoint service from it. Consumers, in other VPCs or other companies' accounts, create interface endpoints that point to your endpoint service. Each consumer's endpoint appears in their subnets, with their addresses.

Building it takes five steps:

  1. Provider: a Network Load Balancer in front of the service, in the zones consumers will use, with target groups pointing at the app.
  2. Provider: an endpoint service on that NLB, with “acceptance required” on and Korenwolf's AWS account added as an allowed principal.
  3. Consumer: an interface endpoint to the endpoint service's name (com.amazonaws.vpce.eu-central-1.vpce-svc-…) in their subnets, with their own security group.
  4. Provider: accept the connection request.
  5. Names. Give the service a private DNS name such as orders.partner.larder.example; AWS asks you to prove you own the domain with a TXT record, then the name resolves to the endpoint inside the consumer's VPC.

At Larder: solved

Korenwolf's ordering system now calls orders.partner.larder.example, which inside their VPC resolves to 10.20.5.80, an address in their 10.20.0.0/16. Larder's production VPC is never routed to Korenwolf's network, so the identical ranges never meet. The API sees connections coming from its own NLB; to tell partners apart, the NLB adds proxy protocol v2 headers that carry the endpoint's ID, and the API authenticates each partner with mTLS on top (Chapter 6).

For Lena's question, the data tier got interface endpoints for ECR, Secrets Manager, KMS, logs and STS, with endpoint policies limited to Larder's accounts, and lost its route to the NAT gateway. It now has no way to the internet at all.

Watch out: zones must line up

A consumer can only create endpoint interfaces in zones where the provider's NLB has a presence, and zones are matched by zone ID, not name (Chapter 7). Run the NLB in every zone of the region, or agree zone IDs with partners up front.

12.4What PrivateLink is good for

  • One-way. The consumer can open connections to the service; the provider can't open connections back into the consumer's VPC. That's a much smaller trust relationship than peering or a VPN.
  • Service, not network. The consumer reaches one load balancer's listeners and nothing else, so there are no routes or firewall rules between networks to get wrong.
  • Overlap doesn't matter, as Korenwolf shows. That alone makes it the default for partners and SaaS providers.
  • It scales to many consumers: hundreds of customer VPCs can connect to one endpoint service. Many SaaS products, including monitoring and database vendors, offer PrivateLink endpoints this way.

Its limits: TCP only (and UDP for some newer setups), a load balancer and an endpoint per zone to pay for, and source addresses hidden behind the NLB unless you read the proxy protocol header.

12.5Endpoints and DNS across many VPCs

With ten VPCs, one set of seven endpoints in each costs ten times as much. A common pattern is to centralise interface endpoints in the hub VPC (Chapter 11) and let spokes reach them through the transit gateway. The difficulty is DNS: an endpoint's private DNS only answers inside its own VPC. So you turn private DNS off on the central endpoints, create your own private hosted zones for the service names (such as secretsmanager.eu-central-1.amazonaws.com) pointing at the endpoints, and associate those zones with every spoke VPC.

That design is cheaper and tidier, and it moves cross-VPC traffic through the TGW, which has its own per-GB charge. Do the sums for your traffic. Chapter 15 covers sharing DNS across VPCs and with on-premises networks, including how stores and offices can resolve endpoint names too.

On Azure

A private endpoint connects to one specific resource, say one storage account or one SQL database, and its name resolves through a private DNS zone such as privatelink.blob.core.windows.net, linked to your VNets. Forgetting to link that zone is the classic mistake: the name still resolves to the public address.

On Google Cloud

Private Google Access is a per-subnet switch that lets VMs without external IPs reach Google APIs. Private Service Connect gives you endpoints with internal addresses, for Google APIs or for services published by other projects and companies. Some managed services, such as Cloud SQL, use an older peering-based model called private services access.

12.8Lab: an interface endpoint and its DNS

Lab 12 · STS through an endpoint, no internet anywhere

You'll build a VPC with no internet gateway at all, an interface endpoint for STS with private DNS, and a stand-in client interface, then check the path and read the endpoint's DNS names. You need the AWS CLI and Terraform. Cost: the endpoint is about $0.02 an hour in two zones, plus $0.10 per analysis: about $0.40.

main.tfTerraform ≥ 1.5, AWS provider 5.x

provider "aws" { region = "eu-central-1" }

data "aws_availability_zones" "z" { state = "available" }

resource "aws_vpc" "lab" {
  cidr_block           = "10.50.0.0/16"
  enable_dns_support   = true      # both needed for private DNS
  enable_dns_hostnames = true
}
resource "aws_subnet" "s" {
  count             = 2
  vpc_id            = aws_vpc.lab.id
  cidr_block        = cidrsubnet(aws_vpc.lab.cidr_block, 8, count.index)
  availability_zone = data.aws_availability_zones.z.names[count.index]
}

resource "aws_security_group" "client" { vpc_id = aws_vpc.lab.id }
resource "aws_vpc_security_group_egress_rule" "client" {
  security_group_id = aws_security_group.client.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}

# 12.2 · the endpoint's own security group: 443 from the client group only
resource "aws_security_group" "endpoint" { vpc_id = aws_vpc.lab.id }
resource "aws_vpc_security_group_ingress_rule" "endpoint" {
  security_group_id            = aws_security_group.endpoint.id
  referenced_security_group_id = aws_security_group.client.id
  ip_protocol                  = "tcp"
  from_port                    = 443
  to_port                      = 443
}

resource "aws_vpc_endpoint" "sts" {
  vpc_id              = aws_vpc.lab.id
  service_name        = "com.amazonaws.eu-central-1.sts"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.s[*].id
  security_group_ids  = [aws_security_group.endpoint.id]
  private_dns_enabled = true
}

resource "aws_network_interface" "client" {
  subnet_id       = aws_subnet.s[0].id
  security_groups = [aws_security_group.client.id]
}

output "client_eni"  { value = aws_network_interface.client.id }
output "endpoint_id" { value = aws_vpc_endpoint.sts.id }
  1. Create it with terraform init and terraform apply. Note there's no internet gateway or NAT in this VPC.
  2. Read the endpoint's addresses and names. 
    aws ec2 describe-vpc-endpoints --vpc-endpoint-ids $(terraform output -raw endpoint_id) \
  --query 'VpcEndpoints[0].[State, PrivateDnsEnabled, DnsEntries[].DnsName, NetworkInterfaceIds]'
    You'll see endpoint-specific names (vpce-…sts.eu-central-1.vpce.amazonaws.com) and one interface per zone. With private DNS on, sts.eu-central-1.amazonaws.com itself resolves to those interfaces inside the VPC.
  3. Check the path. Create a Reachability Analyzer path from client_eni to the endpoint on TCP 443 (use the endpoint ID as the destination, or, if it isn't accepted, one of the endpoint's network interface IDs from step 2), and analyse it with the check function from Lab 9. Expect true.
  4. Break it. Change the endpoint's ingress rule to port 8443, apply, analyse again: the explanation names the endpoint's security group. Restore it.
  5. Clean up. Delete the insights path, then terraform destroy.

Stretch goal. Launch a tiny instance in the subnet with no public IP and an instance profile, connect with Session Manager (you'll need the three ssm endpoints from Table 12.2), and run aws sts get-caller-identity --region eu-central-1. It works with no route to the internet. Then run dig sts.eu-central-1.amazonaws.com on the instance and on your laptop and compare.

✓Chapter summary

  • Gateway endpoints (S3, DynamoDB) are routes and free; interface endpoints are network interfaces in your subnets, paid per hour and per GB.
  • Private DNS makes the service's normal name resolve to the endpoint inside the VPC; no code changes.
  • Control endpoints with a security group (who can use it) and an endpoint policy (what can be done through it).
  • PrivateLink endpoint services publish your service behind an NLB to other VPCs and accounts: one-way, service-level, and indifferent to overlapping ranges.
  • Centralise endpoints in a hub to save money, and handle their DNS with shared private zones.

Key terms

Interface endpoint
Network interfaces in your subnets that reach a service through PrivateLink.
Gateway endpoint
A free, route-based path to S3 or DynamoDB.
PrivateLink
AWS's technology for private, one-way access to a service across VPCs.
Endpoint service
Your service, behind an NLB, made available to consumers' endpoints.
Private DNS (endpoint)
The service's public name resolving to the endpoint's private addresses.
Endpoint policy
A policy limiting the actions and resources reachable through an endpoint.
Proxy protocol v2
A header the NLB adds so the service can see the original connection's details.

Check your understanding

  1. A job in a subnet with no NAT can pull its image manifest from ECR but hangs downloading layers. What's missing? apply

    Show answer

    The S3 gateway endpoint: ECR stores image layers in S3, so ecr.api and ecr.dkr interface endpoints aren't enough on their own.

  2. Why can Korenwolf reach Larder's API with PrivateLink even though both use 10.20.0.0/16? explain

    Show answer

    No routes are exchanged. Korenwolf talks to an endpoint with an address in its own VPC, and PrivateLink carries the connection to Larder's NLB, which forwards it to targets in Larder's VPC. Neither network ever needs to route to the other's addresses.

  3. An endpoint has private DNS on. Will a server in a peered VPC resolve the service name to the endpoint? apply

    Show answer

    No. Endpoint private DNS answers only for the VPC the endpoint is in. The peered VPC gets the public address unless you associate a private hosted zone for the name with it (and turn the endpoint's own private DNS off, as in 12.5).

  4. What do a security group and an endpoint policy each control on an interface endpoint? explain

    Show answer

    The security group controls which network sources may connect to the endpoint. The endpoint policy controls which API actions on which resources may be performed through it, regardless of who connects.

  5. Your monitoring vendor offers a PrivateLink endpoint or a public HTTPS endpoint. Your servers already have NAT. When is the PrivateLink option worth paying for? design

    Show answer

    When traffic is heavy (endpoint per-GB pricing beats NAT processing), when the sending subnets shouldn't have internet access, or when policy requires telemetry to stay off the internet. For light traffic from subnets that already have NAT, the public endpoint is fine.
