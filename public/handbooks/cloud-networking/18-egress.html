Part IV · Traffic in and out

18

Controlling egress: NAT at scale, proxies and firewalls

Most network security effort goes into what can get in. What gets out matters as much: stolen data leaves through outbound connections, malware calls home through them, and a poisoned library sends your secrets out through them. This chapter shows how to find out what your servers talk to, and then how to limit it by address, by name and at a central checkpoint, at a cost you can justify.

By the end you can

  • Explain what each egress control can see and stop, from security groups to proxies.
  • Build an inventory of outbound destinations before blocking anything.
  • Design centralised egress through a firewall VPC, with symmetric routing.
  • Filter outbound traffic by domain name, and know the limits of doing so.

Before you start

  • NAT gateways (Chapter 8) and security groups (Chapter 9).
  • Transit gateways and appliance mode (Chapter 11).
  • DNS query logs and DNS Firewall (Chapter 15).

At Larder

A routine look at the DNS query logs (Chapter 15) turns up something odd: the nightly reporting job has been looking up telemetry-collect.example every night for nine days. Nobody at Larder has heard of it. The cause is a Python package the job depends on, recently updated by its compromised maintainer, which sends the job's environment variables, database password included, to that address. The job had a route to the internet through the NAT gateway, and nothing stopped it.

Eli rotates every secret the job could see that same morning. Then Lena asks the question that takes longer: “What else can our servers send data to?” Nobody can answer. This chapter is how Larder learned to.

18.1The big picture

Egress is traffic leaving your network. A NAT gateway (Chapter 8) lets private servers reach the internet, but it doesn't choose which parts. Controlling egress means deciding what servers may reach, and enforcing it at points that can see enough to decide. Each tool sees a different amount:

Key idea

The safest egress rule is no internet route at all. Where a workload truly needs the internet, allow the specific names it needs, and block the rest.

18.2First, find out what's leaving

Block before you know, and you'll break something important on a Friday evening. Start with an inventory:

  • DNS query logs show every name each VPC looks up: the closest thing to a list of intended destinations.
  • VPC flow logs on NAT gateways show where connections actually went, by address and bytes (Chapter 22).
  • Group the results by workload and give each destination an owner and a reason: “payment provider, Cho, card payments”.

Larder's two weeks of logs produced a list of 37 domains for production. Most were expected: the payment provider, StockPilot, the courier maps API, the email service, package mirrors for builds. Some were AWS services that could move to endpoints (Chapter 12). Three were surprises: two forgotten monitoring trials and, of course, telemetry-collect.example.

18.3Centralised egress

With many VPCs, putting a NAT gateway and a firewall in each one is expensive and hard to keep consistent. The common alternative is centralised egress: spoke VPCs have no NAT gateway or internet gateway at all. Their default route points to the transit gateway (Chapter 11), which sends internet-bound traffic to one egress VPC with the firewall, the NAT gateways and the internet gateway.

The routing has to be right in both directions (Chapter 4). Outbound: spoke → TGW → the egress VPC's attachment subnet → firewall endpoint → NAT gateway → internet gateway. Inbound replies: internet gateway → NAT gateway → a route in the NAT subnet sending spoke ranges back to the firewall endpoint → TGW → spoke. Turn on appliance mode for the egress VPC's TGW attachment, so both directions of a connection use the same zone's firewall endpoint; without it, the stateful firewall sees half a connection and drops it.

Don't forget DNS and endpointsCentralised egress handles the internet. AWS services are better reached through interface endpoints, centralised the same way (Chapter 12), so that traffic never needs the firewall or NAT at all.

18.4Filtering by name

Most destinations worth allowing are names, not addresses: api.payments.example, not a list of IPs that changes weekly. Three ways to filter by name, each with a limit you should know:

  • DNS Firewall blocks (or allows only) the lookups. Cheap and easy, and it stops most malware, which looks up its servers by name. But a program that connects to an IP address directly never asks DNS, and isn't stopped. The lab demonstrates this.
  • A network firewall with domain rules (AWS Network Firewall stateful rules) reads the server name a client sends in the TLS handshake (SNI, Chapter 6) or the HTTP Host header, and allows or drops the connection. It works on direct-IP connections too. Its limit: a malicious client can put an allowed name in its SNI while connecting to a different server's address. Stricter firewalls check that the name resolves to the address being connected to.
  • A forward proxy makes clients send all requests through it, by configuration. It sees full URLs, can require authentication, and logs everything. Traffic that ignores the proxy must be blocked by the network, or the proxy is only a suggestion.

Watch out: TLS inspection

Firewalls can also decrypt and re-encrypt TLS to see inside it. That requires installing your own certificate authority on every client, breaks certificate pinning and mTLS, adds cost and latency, and turns the firewall into a store of everyone's plaintext. Reach for it only when a regulation demands it, and never for traffic to payment providers or other systems that pin certificates.

18.5Larder's egress, in phases

At Larder: solved

Eli rolled out egress control in four steps, each safe on its own. Week 1: DNS Firewall on every VPC with AWS's managed lists of malicious domains, in alert mode, then block. Weeks 2–3: the inventory from 18.2; AWS service traffic moved to interface endpoints; the data tier lost its internet route entirely (Chapter 12). Week 4: centralised egress through a firewall VPC for production and staging, with the 37 domains as an allow-list in alert mode. Week 6: after two weeks of alerts showed only one missed domain (the courier app's crash reporter), the allow-list switched to drop.

The reporting job's poisoned package would now be stopped at the network firewall: telemetry-collect.example isn't on the allow-list, and neither is a bare IP address. If the domain is on one of the managed malicious lists, DNS Firewall stops the lookup even earlier. Either way the alert reaches Eli the same night, not nine days later.

18.6Third-party appliances

Many companies already use a firewall vendor on premises and want the same in the cloud. The Gateway Load Balancer exists for this: it sends traffic transparently through a fleet of appliance instances, wrapped in GENEVE encapsulation so the original packets are untouched, and keeps both directions of each flow on the same appliance. Spokes and egress VPCs route to Gateway Load Balancer endpoints as their next hop, much like the firewall endpoint in Figure 18.1. You manage the appliances' sizing, patching and licences yourself.

18.7What it costs

Centralised egress swaps many NAT gateways for one set, and adds two new charges: the transit gateway's per-GB processing for every byte that crosses it, and the firewall. At the time of writing, AWS Network Firewall costs roughly $0.40 an hour per zone endpoint (about $290 a month) plus about $0.065 per GB processed; three zones start near $900 a month before data.

18.9Lab: DNS Firewall, and its limit

Lab 18 · Block a domain, then go around the block

You'll build a small instance you reach with Session Manager (no SSH), and a DNS Firewall rule that blocks example.org. Then you'll see the lookup fail, and the connection succeed anyway when you skip DNS. You need the AWS CLI and Terraform, and the console for Session Manager. Cost: a t4g.nano at about $0.005 an hour and a fraction of a cent of DNS Firewall queries.

main.tfTerraform ≥ 1.5, AWS provider 5.x

provider "aws" { region = "eu-central-1" }

data "aws_availability_zones" "z" { state = "available" }
data "aws_ssm_parameter" "al2023" {
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64"
}

# a public subnet, so Session Manager works without endpoints (Chapter 8)
resource "aws_vpc" "lab" {
  cidr_block           = "10.80.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true
}
resource "aws_internet_gateway" "igw" { vpc_id = aws_vpc.lab.id }
resource "aws_subnet" "pub" {
  vpc_id                  = aws_vpc.lab.id
  cidr_block              = "10.80.0.0/24"
  availability_zone       = data.aws_availability_zones.z.names[0]
  map_public_ip_on_launch = true
}
resource "aws_route" "out" {
  route_table_id         = aws_vpc.lab.main_route_table_id
  destination_cidr_block = "0.0.0.0/0"
  gateway_id             = aws_internet_gateway.igw.id
}

# no inbound rules at all; Session Manager connects outbound
resource "aws_security_group" "vm" { vpc_id = aws_vpc.lab.id }
resource "aws_vpc_security_group_egress_rule" "vm" {
  security_group_id = aws_security_group.vm.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}
resource "aws_iam_role" "vm" {
  name = "handbook-lab18-vm"
  assume_role_policy = jsonencode({
    Version   = "2012-10-17"
    Statement = [{ Effect = "Allow", Action = "sts:AssumeRole",
                   Principal = { Service = "ec2.amazonaws.com" } }]
  })
}
resource "aws_iam_role_policy_attachment" "ssm" {
  role       = aws_iam_role.vm.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}
resource "aws_iam_instance_profile" "vm" { role = aws_iam_role.vm.name }
resource "aws_instance" "vm" {
  ami                    = data.aws_ssm_parameter.al2023.insecure_value
  instance_type          = "t4g.nano"
  subnet_id              = aws_subnet.pub.id
  vpc_security_group_ids = [aws_security_group.vm.id]
  iam_instance_profile   = aws_iam_instance_profile.vm.name
  tags = { Name = "handbook-lab18" }
}

# 18.4 · DNS Firewall: block example.org and everything under it
resource "aws_route53_resolver_firewall_domain_list" "blocked" {
  name    = "handbook-lab18-blocked"
  domains = ["example.org", "*.example.org"]
}
resource "aws_route53_resolver_firewall_rule_group" "g" { name = "handbook-lab18" }
resource "aws_route53_resolver_firewall_rule" "block" {
  name                    = "block-example-org"
  action                  = "BLOCK"
  block_response          = "NXDOMAIN"
  firewall_domain_list_id = aws_route53_resolver_firewall_domain_list.blocked.id
  firewall_rule_group_id  = aws_route53_resolver_firewall_rule_group.g.id
  priority                = 100
}
resource "aws_route53_resolver_firewall_rule_group_association" "a" {
  name                   = "handbook-lab18"
  firewall_rule_group_id = aws_route53_resolver_firewall_rule_group.g.id
  priority               = 101
  vpc_id                 = aws_vpc.lab.id
}
  1. Create it with terraform init and terraform apply. Wait two or three minutes for the instance to register with Session Manager.
  2. Connect. In the EC2 console, select handbook-lab18, choose Connect, then Session Manager. No SSH keys, no open ports.
  3. Before and after. Before blocking anything, you'd get an address for example.org from your laptop: run dig +short example.org there and note one address. On the instance, run dig example.org: status: NXDOMAIN, the firewall's answer. dig +short example.com still works.
  4. Go around it. On the instance: curl -sI https://example.org --resolve example.org:443:<address from your laptop>. It connects and returns headers. DNS Firewall stopped the lookup, not the connection: an attacker who knows an address doesn't need DNS. That gap is what network firewalls with SNI rules, or no internet route at all, close.
  5. Clean up with terraform destroy.

Stretch goal. Turn on Resolver query logging for the VPC to CloudWatch Logs, repeat step 3, and find the blocked query in the log with the firewall rule's action. This is the alert that should have told Larder about telemetry-collect.example on day one.

MistakeWhat happensInstead
Blocking before an inventoryPayments or a partner integration break in production.Logs first, owners per destination, alert mode before drop.
Relying on DNS filtering aloneDirect-IP connections walk straight out.Combine with SNI rules or no internet route.

Spokes keeping their own NAT gatewayAn easy way around the checkpoint.Remove internet routes from spokes; enforce with policy.

✓Chapter summary

  • Egress is how data leaks and malware calls home. NAT allows the internet; it doesn't choose destinations.
  • Each control sees a different layer: addresses (security groups), names looked up (DNS Firewall), names in the handshake (network firewall), full URLs (proxy).
  • Start with an inventory from DNS and flow logs; give every destination an owner.
  • Centralised egress routes spokes through one firewall VPC; get both directions and appliance mode right.
  • DNS filtering is cheap but bypassable by direct IPs; combine it with SNI rules or no internet route.
  • Roll out in phases: alert, then block.

Key terms

Egress
Traffic leaving your network.
Exfiltration
Data stolen by sending it out of the network.
Centralised egress
All spokes reaching the internet through one checkpoint VPC.
Domain allow-list
The names workloads may reach; everything else is blocked.
SNI filtering
Allowing or blocking TLS connections by the server name in the handshake.
Forward proxy
A server that makes outbound requests on clients' behalf.
TLS inspection
Decrypting and re-encrypting traffic to see inside it.
Gateway Load Balancer
Sends traffic transparently through a fleet of appliances.

Check your understanding

  1. Why can't security groups alone restrict a server to “only the payment provider's API”? explain

    Show answer

    Security groups work on IP addresses, and the provider's API sits behind addresses that change and are shared with other services. Restricting by name needs DNS filtering, SNI-based firewall rules or a proxy.

  2. A DNS Firewall blocks bad.example. Malware on a server connects to 203.0.113.66:443 directly. What stops it? apply

    Show answer

    Not DNS Firewall: no lookup happens. A network firewall with an SNI/Host allow-list would drop it (the name won't be on the list), as would having no internet route at all. Security groups would only help if outbound traffic were restricted to known addresses.

  3. After centralising egress, connections from staging to the internet fail about half the time. What do you check first? apply

    Show answer

    Symmetric routing: whether appliance mode is on for the egress VPC's TGW attachment, and whether return routes in the NAT subnets send spoke ranges back through the same zone's firewall endpoint. A stateful firewall seeing only one direction drops the connection.

  4. Why build an inventory and run in alert mode before blocking? explain

    Show answer

    So you know every legitimate destination and its owner before anything is blocked; otherwise you break critical integrations. Alert mode shows what the rules would have blocked, so misses can be fixed without an outage.

  5. Your data tier needs Secrets Manager, KMS and S3, and nothing else. Design its egress. design

    Show answer

    No internet route at all; an S3 gateway endpoint and interface endpoints for Secrets Manager and KMS with endpoint policies limited to your accounts; security groups allowing outbound 443 only to the endpoints' group and the S3 prefix list; DNS Firewall and query logging as a backstop.
