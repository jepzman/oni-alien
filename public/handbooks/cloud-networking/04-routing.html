Routing: how packets find their way

Every device that sends a packet, from a phone to a cloud gateway, makes the same small decision: “where does this go next?”. It answers by looking up a route table, using one simple rule. Learn to read route tables the way a router does, and you can trace any packet through any network, in both directions.

By the end you can

  • Read a route table and pick the route a packet will use.
  • Explain connected, static and dynamic routes, and the default route.
  • Trace a packet's path and its reply's path, hop by hop.
  • Describe what BGP does and where you'll meet it in the cloud.

Amsterdam's stores, set up the same way, worked fine. Eli checked the tunnel, the firewalls and the handhelds. All fine.

Requests arriving but replies never coming back is one of the most common routing problems there is. You'll be able to find this one in section 4.6.

4.1The big picture

Routing is the job of choosing the next hop for each packet. There's no central map of the internet and no device that knows a whole path. Every device holds a route table, a list of “to reach this range, send to that next hop”, and makes one local decision per packet. A path is just the chain of those decisions.

This is true for your laptop, your home router, the internet's backbone routers, and every VPC, transit gateway and VPN in the cloud. The cloud hides the routers, but not the route tables: you'll write them yourself (Chapter 8). So it's worth learning to read them the way a router does.

4.2What's in a route

A route has two essential parts:

  • a destination: a range in CIDR notation, such as 10.20.0.0/16;
  • a next hop: where to send matching packets. That's either the address of a neighbouring router (a gateway) or an interface, meaning “it's on this link, deliver it directly”.

Routes get into a table in three ways:

Real route tables also carry a metric or priority, used to choose between two routes to the same destination. But the first and most important tie-breaker isn't the metric at all. It's the next section.

4.3Longest prefix match

A packet's destination often matches several routes at once, because ranges nest inside each other. 10.20.17.8 is inside 10.20.16.0/20, inside 10.20.0.0/16, inside 10.0.0.0/8, inside 0.0.0.0/0. A router resolves this with one rule:

Key idea

Of all the routes that match, use the one with the longest prefix, the most specific. Order in the table doesn't matter.

It's the rule a postal system uses: a letter addressed to a specific street goes to that street's local office, even though the national sorting centre could also handle it. The more specific instruction wins.

The third row is the interesting one. Someone once added a static route for the database range to the backup tunnel, probably during an outage, and forgot it. Because it's more specific, it quietly beats the main route forever. Longest prefix match is predictable, but it means one forgotten specific route can redirect traffic you thought was going elsewhere.

Equal prefixesOnly when two routes have the same prefix length does anything else decide: on AWS, static routes beat propagated ones; in BGP, a list of attributes (4.7). Some routers split traffic across equal routes (ECMP).

4.4The default route

The route 0.0.0.0/0 matches every IPv4 address with a prefix of zero bits, so it always loses to anything more specific. That makes it the route of last resort: the default route. (For IPv6 it's ::/0.)

Most devices have a tiny route table: their own network, and a default route to “the router”. Your laptop's whole knowledge of the internet is one default route. A device with no default route can only reach ranges it has explicit routes for, which is exactly what you want for a database subnet (Chapter 8, isolated subnets).

If no route matches at all, the packet is dropped, and the sender might get an ICMP “destination unreachable” message. In a cloud network it's usually just dropped silently, which looks like a timeout.

4.5The last hop: ARP

A route says “send it to 10.8.3.1”, but a frame on Ethernet or Wi-Fi needs a MAC address (Chapter 1). The Address Resolution Protocol (ARP) fills that gap: the device broadcasts “who has 10.8.3.1?” on the local link, the owner replies with its MAC address, and the answer is cached for a while. IPv6 does the same with Neighbour Discovery.

You'll rarely touch ARP in the cloud, and that's on purpose: the provider's virtual network answers every ARP request itself, and there are no broadcasts. That's also why some old tricks, like moving a “floating IP” between servers with a gratuitous ARP, don't work in a VPC. You move the address through the provider's API instead.

4.6Every packet, both directions

The most important consequence of hop-by-hop routing is that the reply is routed separately. The request's path is decided by route tables on the way there; the reply's path is decided by different route tables, looking up a different destination address, on the way back. A working connection needs both.

Walk through Figure 4.1 the way a router would:

  1. The handheld's destination 10.20.17.8 isn't on its local /24, so the default route sends it to the store router at 10.8.3.1.
  2. The store router's longest match is 10.20.0.0/16 → vpn, so it goes into the tunnel.
  3. The transit gateway in Frankfurt matches 10.20.0.0/16 and delivers it into Larder's VPC, where the local route reaches the app server.
  4. The reply is addressed to 10.8.3.40. The app subnet's table has no local match, so 10.0.0.0/8 → tgw wins.
  5. The transit gateway matches 10.8.0.0/16 → vpn and sends it back to Noord.

At Larder: solved

Rotterdam's stores were given 10.9.0.0/16, the next range in the company plan. The store router had its route to Frankfurt, so requests arrived. But the transit gateway in Frankfurt only had a route for 10.8.0.0/16, Amsterdam's stores. Replies to 10.9.x.x matched nothing there and were dropped. Step 5, not step 2.

Eli added the route, and then fixed the cause: the store VPNs now use BGP, so each store announces its own range and the transit gateway learns it automatically (section 4.7). The next city's stores needed no route changes at all.

Asymmetric routing

Sometimes the reply does have a route, just a different one from the request. That's asymmetric routing. On its own it's harmless; the internet is full of it. It becomes a problem when a stateful device sits on only one of the two paths.

You'll meet this again whenever traffic is sent through an inspection firewall or appliance: in transit designs (Chapter 11) and in centralised egress (Chapter 18). The cloud providers even have special settings for it, such as AWS Transit Gateway's appliance mode, which keeps both directions of a connection on the same firewall.

4.7Dynamic routing and BGP in one page

Static routes are fine for a handful of networks. They become a problem when networks change: every new store, VPC or office means editing route tables in several places, and a missed edit is a Rotterdam-style outage. Dynamic routing lets routers tell each other which ranges they can reach, so tables update themselves.

The protocol that matters for cloud networking is BGP, the Border Gateway Protocol. It's how the tens of thousands of networks on the internet exchange routes, and it's how your on-premises routers and the cloud exchange routes over VPNs and dedicated links.

  • Every BGP network has an autonomous system number (ASN). Public ones are assigned; for private connections you pick one from the private range 64512–65534. AWS gateways default to 64512.
  • Two routers open a BGP session (over TCP port 179) and advertise the ranges they can reach. Larder's Noord store router advertises 10.8.3.0/24; the AWS side advertises 10.20.0.0/16.
  • Each route carries attributes, notably the AS path: the list of networks it passed through. When several routes to the same prefix arrive, BGP prefers, among other things, the shortest AS path. That's how traffic fails over: if one tunnel's session goes down, its routes are withdrawn and the other tunnel's routes take over within seconds.
  • In the cloud, routes learned over BGP are propagated into your route tables, marked as such, next to the static routes you wrote.

Chapter 13 sets up a BGP session for real. For now, the main thing is that dynamic routes follow the same longest-prefix rule as everything else. BGP decides what's in the table; longest prefix match decides what's used.

4.8Routing in the cloud

A VPC has no routers for you to log in to. Instead:

  • An implicit VPC router sits behind every subnet (on AWS, at the subnet's .1 address). It forwards using the route table associated with the subnet the packet came from.
  • The local route makes every subnet reach every other subnet in the VPC (a connected route).
  • You add static routes to gateways: internet, NAT, peering, transit, VPN.
  • Gateways that speak BGP can propagate their routes into your tables automatically.
  • Transit gateways and their equivalents have their own route tables, which is where most multi-VPC routing happens (Chapter 11).

The same rules apply on Azure and Google Cloud, with different packaging: Azure has system routes, user-defined routes and BGP-learned routes per subnet; Google Cloud has routes per VPC network, scoped by tags, with BGP routes learned by Cloud Router. Chapter 8 compares them.

4.9Lab: ask your computer how it would route

Lab 4 · Route lookups by hand, by the OS and by code

You'll read your own route table, ask the operating system to make a lookup, and write a longest-prefix-match function. You need a terminal and Python 3. Cost: nothing.

  1. Read your table. ip route (Linux), netstat -rn -f inet (macOS) or route print -4 (Windows). Find the connected route for your home network and the default route. If you use a VPN, look for the routes it added.
  2. Ask for a decision. On Linux, ip route get 1.1.1.1 and ip route get 192.168.1.20 (use an address from your own network). On macOS, route -n get 1.1.1.1. The OS tells you which route and interface it would use. Explain each answer using longest prefix match.
  3. Write the lookup. In Python, implement it: 
    import ipaddress as ip

table = [("10.1.0.0/24", "lan"), ("10.0.0.0/8", "vpn"),
         ("10.20.64.0/22", "backup-vpn"), ("0.0.0.0/0", "isp")]

def lookup(dst):
    a = ip.ip_address(dst)
    matches = [(ip.ip_network(n), hop) for n, hop in table if a in ip.ip_network(n)]
    return max(matches, key=lambda m: m[0].prefixlen, default=(None, "drop"))[1]

for d in ["10.1.0.57", "10.20.17.8", "10.20.65.4", "151.101.1.1"]:
    print(d, "→", lookup(d))
    Check the output against Table 4.3.
  4. Trace both directions. Add the route tables from Figure 4.1 as four Python lists, and write a function that walks a packet from the handheld to the app server and the reply back. Then remove the transit gateway's 10.8.0.0/16 route and watch your function find the Rotterdam bug.

Stretch goal. Run traceroute to a site on another continent and look up a few of the hop addresses with whois. How many different networks (organisations) does your packet cross?

✓Chapter summary

  • Every device routes with its own route table: destination range → next hop. Paths are chains of local decisions.
  • Routes are connected, static or dynamic (learned by BGP).
  • Longest prefix match picks between overlapping routes; table order is irrelevant.
  • The default route 0.0.0.0/0 catches everything else. No match means the packet is dropped.
  • The reply is routed separately. Check both directions, and keep stateful devices on both paths.
  • BGP lets networks advertise their ranges, so routes update themselves; in the cloud it propagates into your tables.

Key terms

Route table
A device's list of destination ranges and next hops.
Next hop
The neighbouring router or interface a matching packet is sent to.
Connected route
A route to a network the device is directly attached to.
Static route
A route configured by hand or by code.
Dynamic route
A route learned from neighbours by a routing protocol.
Longest prefix match
The rule that the most specific matching route wins.
Default route
0.0.0.0/0 (or ::/0): the route of last resort.
ARP
Finds the MAC address for an IP address on the local link.
Asymmetric routing
Request and reply taking different paths.
BGP
The protocol networks use to exchange routes.
ASN
The number that identifies a network in BGP; 64512–65534 are private.
Route propagation
Routes learned over BGP added automatically to a cloud route table.

Check your understanding

  1. A route table holds 10.0.0.0/8 → A, 10.20.0.0/16 → B, 10.20.0.0/20 → C and 0.0.0.0/0 → D. Where do packets to 10.20.15.1, 10.20.16.1 and 10.21.0.1 go? apply

    Show answer

    10.20.15.1 is in 10.20.0.0/20 (0–15), so C. 10.20.16.1 is outside that /20 but in the /16, so B. 10.21.0.1 only matches the /8 and the /0, so A.

  2. Why does adding a route for 0.0.0.0/0 at the top of a table not send all traffic through it? explain

    Show answer

    Order doesn't matter: the longest matching prefix wins, and a /0 is the shortest possible, so every more specific route beats it.

  3. Requests from a new office reach a cloud server, but the office sees timeouts. The office router has a route to the VPC. What do you check next, and where? apply

    Show answer

    The return path: the route table of the server's subnet, and of every gateway on the way back (transit gateway, VPN), for a route that covers the office's range. Then any firewall on the return path, in case it's stateless or asymmetric.

  4. Two VPN tunnels connect a store to Frankfurt for redundancy. Why is BGP better than static routes here? design

    Show answer

    With BGP, when one tunnel fails its session drops and its routes are withdrawn, so traffic moves to the other tunnel within seconds, automatically. New ranges are also advertised without editing tables. With static routes, a failed tunnel can keep attracting traffic until someone changes the routes.

  5. Traffic between two VPCs is sent through an inspection firewall in a third VPC. Connections sometimes hang. What would you suspect, and what's a fix? design

    Show answer

    Asymmetric routing: the request and the reply pass through different firewall instances (or one direction bypasses the firewall), so a stateful firewall sees only half the connection. Fix the routes so both directions go through the same appliance, for example with Transit Gateway appliance mode.
