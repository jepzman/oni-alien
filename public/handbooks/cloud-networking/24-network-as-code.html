Networks as code and landing zones

Every good decision in this book, from the address plan to endpoints in every VPC, only matters if it's applied every time, by everyone, including the team that creates an account on a Friday afternoon. This chapter shows how to turn those decisions into code and guardrails: a network module that does the right things by default, a central network that teams plug into, policies that stop the wrong things before they happen, and the multi-account foundation, the landing zone, that holds it all together.

By the end you can

  • Design a reusable network module with safe defaults.
  • Split network code and state between a central team and application teams.
  • Enforce network rules with checks before deployment and guardrails in the cloud.
  • Explain a landing zone, and choose between shared VPCs and per-team VPCs.

Before you start

  • Terraform basics from the earlier labs.
  • The address plan (Chapter 10), transit gateways (Chapter 11), egress (Chapter 18).

At Larder

Larder's new data team gets its own AWS account and builds its network by hand in an afternoon, following a blog post: a VPC of 10.0.0.0/16, public subnets “to make things easier”, one NAT gateway, no flow logs, no endpoints. Three weeks later they ask Eli to connect it to the transit gateway so their jobs can read from production. The request fails on the first line: 10.0.0.0/16 overlaps Larder's office range (Chapter 10), and the network has nearly every gap this book has warned about.

Nobody on the data team did anything unreasonable. The company had decisions but no defaults. Section 24.5 shows what changed.

24.1The big picture

Networks built by hand drift apart and forget lessons. Networks built from code are reviewed, repeatable and recorded: a pull request shows exactly what will change (Chapter 9 showed what happens without one), and a module can carry every lesson into every new VPC. Around the code sits a landing zone: the multi-account structure, shared services and guardrails that new accounts land in, so that the safe way is also the default way.

24.2A network module with good defaults

A module is a reusable piece of infrastructure code with inputs and outputs. A good VPC module asks for little and decides a lot:

Table 24.1 · What Larder's VPC module asks for, and what it decides
Asks for (inputs)Decides for you (built in)
name, environment, owner teamRange allocated from IPAM, never typed (Ch. 10)
size (/16, /18, /20)Tiered subnets per zone, aligned (Ch. 2, Ch. 8)
zones (default: three)Route table per tier and zone; main table local-only; every subnet associated explicitly (Ch. 8)
tiers wanted (public? data?)S3 and DynamoDB gateway endpoints; no internet gateway unless public is asked for
Default route to the transit gateway (centralised egress, Ch. 18) and attachment to the right TGW route table (Ch. 11)
Flow logs on, to the central log account (Ch. 22); Resolver query logging; DNS Firewall rule groups (Ch. 15)
Association with the company's private hosted zones and forwarding rules (Ch. 15)
Outputs: VPC ID, subnet IDs by tier, route table IDsTags for cost and ownership (Ch. 23)

Key idea

A module is where lessons go to stay learned. Every incident in this book should end with a default in the module, not just a fix in one VPC.

24.3Who owns which code

Network code splits naturally into two layers with different owners and different rates of change:

  • The central network, owned by the platform team in a dedicated network account: IPAM pools, transit gateways and their route tables, the egress and inspection VPC, hybrid connections, Resolver endpoints and shared private zones. Changes are rare and reviewed carefully.
  • Workload networks, created by the module in each team's account: VPCs and subnets, security groups for their own services. Changes are frequent and owned by the team.

Keep their Terraform state separate, so a team's change can never accidentally plan to touch the transit gateway, and pass values between them through published outputs (SSM parameters or remote state that teams can read but not write). Apply only from CI with short-lived credentials, never from laptops, and post every plan in its pull request.

24.4Policy as code and guardrails

Defaults help people do the right thing. Policies stop the wrong things. Use three kinds, at three moments:

Table 24.2 · Where network rules are enforced
WhenToolExample rules
Before deploy: checks on the plan in CICheckov, tfsec/Trivy, OPA/Conftest, custom scriptsNo security group allows 0.0.0.0/0 inbound except on load balancers; every VPC has flow logs; no internet gateway outside public tiers
At the API: preventive guardrailsService control policies (SCPs) in AWS OrganizationsWorkload accounts can't create internet gateways or VPC peerings; nobody can delete flow logs or disable GuardDuty; VPCs only in approved regions
After deploy: detective controlsAWS Config rules, Network Access Analyzer, Security HubNo databases reachable from the internet; no unused Elastic IPs; no VPCs outside IPAM

Preventive guardrails are blunt and powerful: an SCP denying ec2:CreateInternetGateway in workload accounts makes centralised egress (Chapter 18) impossible to bypass, whatever anyone types. Use them for the few rules that must never be broken, and checks and detective controls for the rest, so teams aren't blocked by rules with exceptions.

24.5Landing zones

A landing zone is the multi-account setup that every workload lands in: an account structure, shared services, baseline configuration and guardrails, built and maintained as code. On AWS it's usually built with AWS Control Tower or a custom equivalent, with accounts grouped into organisational units (OUs):

Table 24.3 · A typical account structure, as Larder uses it
OU / accountHolds
Security: log archive, security toolingFlow logs, query logs and audit logs from every account; GuardDuty and Security Hub administration
Infrastructure: networkIPAM, transit gateways, egress VPC, VPN and Direct Connect, Resolver endpoints, shared private zones
Workloads: production, non-productionOne or more accounts per team and environment, with networks from the module
SandboxExperiments, isolated from the company network, with budgets and automatic cleanup

New accounts come from an account vending process (Control Tower's Account Factory, or a pipeline of your own) that creates the account in the right OU and applies the baseline: SCPs, logging, and, for workload accounts, a network from the module with a range from IPAM.

At Larder: solved

The data team's account was rebuilt in a day, from the vending pipeline. It got 10.21.0.0/16 from the Frankfurt IPAM pool, three zones of private subnets, gateway endpoints, flow logs to the log archive, the company's private zones, and an attachment to the non-production TGW route table, with no internet gateway allowed by SCP. Its heavy nightly copy from production got a direct peering (Chapter 23). Since then, a new team account takes about an hour from request to first deploy, and every one of them has the same network as the last.

24.6Shared VPCs or a VPC per team?

There are two ways to give teams networks. In VPC per account, each team account gets its own VPC from the module and attaches to the transit gateway. In VPC sharing, the network team owns a VPC per environment and shares specific subnets with team accounts through Resource Access Manager; teams launch resources into subnets they don't own and can't change.

Table 24.4 · Comparing the two models
VPC per accountShared VPC
Team autonomyhigh: own routes, endpoints, attachmentslower: network fixed by the central team
Address usea block per VPC, some unuseddense: one VPC per environment
CostNAT, endpoints and attachments in every VPC (or centralised)shared once per environment
Traffic between teamsthrough the TGW (charged)inside the VPC (free within a zone)
Blast radiusa team's mistake stays in its VPCsubnet and route mistakes affect all sharers
Fitsmany independent teams, strong isolation needsa few closely related teams, cost and simplicity first

Larder uses both: the product teams share the production and staging VPCs, which keeps their heavy traffic to each other free and simple, and teams with different needs, like the data team, get their own VPC from the module.

24.8Lab: a module, two networks and a policy check

Lab 24 · Plan only, then let a script review it

You'll write a small VPC module, use it for a good network and a bad one, produce a Terraform plan without creating anything, and check the plan with a Python policy script. You need Terraform, Python 3 and AWS credentials (the plan reads your account but changes nothing). Cost: nothing.

modules/vpc/main.tfTerraform ≥ 1.5, AWS provider 5.x

variable "name"   {}
variable "cidr"   {}
variable "azs"    { type = list(string) }
variable "public" { default = false }
variable "flow_log_bucket_arn" {}

data "aws_region" "current" {}

resource "aws_vpc" "this" {
  cidr_block = var.cidr
  tags       = { Name = var.name }
}
resource "aws_subnet" "app" {
  count             = length(var.azs)
  vpc_id            = aws_vpc.this.id
  cidr_block        = cidrsubnet(var.cidr, 4, count.index + 1)
  availability_zone = var.azs[count.index]
}
resource "aws_route_table" "app" {
  count  = length(var.azs)
  vpc_id = aws_vpc.this.id
}
resource "aws_route_table_association" "app" {   # never the main table
  count          = length(var.azs)
  subnet_id      = aws_subnet.app[count.index].id
  route_table_id = aws_route_table.app[count.index].id
}
resource "aws_vpc_endpoint" "s3" {                   # free, always
  vpc_id          = aws_vpc.this.id
  service_name    = "com.amazonaws.${data.aws_region.current.name}.s3"
  route_table_ids = aws_route_table.app[*].id
}
resource "aws_flow_log" "this" {                   # always on
  vpc_id               = aws_vpc.this.id
  traffic_type         = "ALL"
  log_destination_type = "s3"
  log_destination      = var.flow_log_bucket_arn
}
resource "aws_internet_gateway" "this" {           # only if asked for
  count  = var.public ? 1 : 0
  vpc_id = aws_vpc.this.id
}

output "vpc_id" { value = aws_vpc.this.id }

check_plan.pyPython 3

import ipaddress as ip, json, sys

RESERVED = [ip.ip_network("10.0.0.0/13"), ip.ip_network("10.8.0.0/13")]  # offices, stores (Ch. 10)
plan = json.load(open(sys.argv[1]))
problems = []
for rc in plan["resource_changes"]:
    after = (rc["change"].get("after") or {})
    if rc["type"] == "aws_internet_gateway":
        problems.append(f"{rc['address']}: internet gateways are not allowed in workload VPCs")
    if rc["type"] == "aws_vpc":
        net = ip.ip_network(after["cidr_block"])
        for r in RESERVED:
            if net.overlaps(r):
                problems.append(f"{rc['address']}: {net} overlaps reserved {r}")
print("\n".join(problems) or "plan OK")
sys.exit(1 if problems else 0)
  1. Plan, don't apply. terraform init, then terraform plan -out tf.plan and terraform show -json tf.plan > plan.json. Nothing is created.
  2. Review it with code. python3 check_plan.py plan.json. It reports the data team's internet gateway and its overlap with the office range, and exits with an error, which would fail a CI pipeline.
  3. Fix it the right way. Give data_team the range 10.21.0.0/16 and remove public = true; plan and check again: plan OK.
  4. Add a rule. Extend the script so every aws_vpc in the plan has a matching aws_flow_log in the same module. (Hint: compare the module part of each resource's address.)

Stretch goal. Run Checkov on the same folder (checkov -d .) and compare its findings with your script's. Which of your rules are company-specific, and which are general good practice?

24.9Common mistakes

MistakeWhat happensInstead
Decisions without defaultsEvery new team relearns every lesson.A module with safe defaults; vending that uses it.
One state for the whole networkEvery team's change risks the transit gateway; plans take ages.Separate central and workload state.
Applying from laptopsUnreviewed changes, conflicting state.Plans in pull requests; applies from CI.
SCPs for everythingTeams blocked by rules with legitimate exceptions.SCPs for the few absolute rules; checks and detection for the rest.
Console changes to networksDrift between code and reality.Read-only consoles for networks; scheduled drift plans.
Fixing incidents only in the affected VPCThe same incident in the next VPC.Every fix becomes a module default or a policy.

✓Chapter summary

  • Networks in code are reviewed, repeatable and recorded; modules carry lessons into every new VPC.
  • Split ownership: a central network (IPAM, TGW, egress, DNS, hybrid) and workload networks per team, with separate state.
  • Enforce with checks before deploy, guardrails (SCPs) at the API, and detection after.
  • A landing zone is the account structure, shared services and baseline that new accounts land in; account vending applies it.
  • Choose shared VPCs for closely related teams and cost, VPC per account for autonomy and isolation; many companies use both.

Key terms

Module
Reusable infrastructure code with inputs and outputs.
State
Terraform's record of what it manages; keep it separate per owner.
Policy as code
Rules checked automatically against plans or resources.
Service control policy
An AWS Organizations policy that limits what accounts may do.
Landing zone
The multi-account foundation that workloads are deployed into.
Account vending
An automated process that creates accounts with the baseline applied.
VPC sharing
One account's subnets shared with other accounts.
Drift
Real infrastructure differing from its code.

Check your understanding

  1. Name four things a good VPC module should do without being asked. recall

    Show answer

    Any four of: take its range from IPAM; create aligned tiered subnets per zone; associate every subnet with an explicit route table and keep the main table local-only; add S3/DynamoDB gateway endpoints; turn on flow logs and query logging; attach to the transit gateway's correct route table; associate the company's private zones; tag for cost and ownership.

  2. Why keep the transit gateway's code and state separate from teams' VPC code? explain

    Show answer

    So a team's change can never plan to modify the shared hub, plans stay fast and small, and the central network changes only through its own careful review.

  3. Which rule would you enforce with an SCP, and which with a CI check: “no internet gateways in workload accounts” and “every security group rule has a description”? apply

    Show answer

    The internet gateway rule is absolute and security-critical: an SCP. Descriptions are good hygiene with occasional exceptions and no security impact by themselves: a CI check.

  4. Two product teams exchange a lot of traffic and share releases. Shared VPC or a VPC each? design

    Show answer

    A shared VPC fits: their traffic stays inside one VPC (free within a zone, no TGW charges), and they gain little from separate network autonomy. Isolation between them still comes from security groups.

  5. An incident is caused by a subnet left on the main route table. What's the full fix? apply

    Show answer

    Fix the subnet's association now; then make the module always associate subnets explicitly and keep the main table local-only, and add a check (CI or Config rule) that flags any subnet on a main table, so it can't happen in any VPC again.
