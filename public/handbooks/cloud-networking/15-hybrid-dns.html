DNS across clouds and data centres

Once your offices, stores and VPCs are connected, packets can flow. Names often can't. A store's handheld asks its usual resolver for a cloud service's private name and gets “no such name”; a server in a VPC can't resolve the office's file server. This chapter connects the DNS worlds the same way Part III connected the networks: deliberately, in both directions.

By the end you can

  • Share private zones across VPCs and accounts.
  • Use split-horizon DNS without hiding your public records by accident.
  • Let sites resolve cloud names with an inbound resolver endpoint, and the cloud resolve site names with outbound rules.
  • Resolve PrivateLink endpoint names from outside their VPC.

Before you start

  • Endpoint private DNS (Chapter 12).

At Larder

Larder's new stock service lives at stock.internal.larder.example, in a private hosted zone attached to the production and hub VPCs. Inside the cloud, everything finds it. At the Noord store, the handhelds get NXDOMAIN. The VPN is up, the routes are right, and the handhelds can reach the service by IP address. They just can't find out what the address is.

Routing joined the networks; nothing joined the names. Section 15.3 does.

15.1The big picture

Every network has a resolver it trusts. In a VPC, it's the provider's resolver (Chapter 5), which knows your private zones. In a store or office, it's the router, a local DNS server, or the internet provider's resolver, which knows nothing about them. Hybrid DNS means teaching each side to forward questions about the other side's names to a resolver that knows the answer.

15.2Private zones across VPCs and accounts

Start inside the cloud. A private hosted zone answers only in the VPCs it's associated with (Chapter 5), so every VPC that needs internal.larder.example must be associated with the zone. That's a one-line setting for VPCs in the same account. For a VPC in another account, the zone's owner first authorises the association, then the VPC's owner completes it. Do it in code, as part of creating each VPC, so a new VPC is never born unable to resolve the company's internal names.

Larder keeps all private zones in the network account, alongside the transit gateway, and associates them with every VPC that's attached to the TGW. One owner for internal names, like one owner for the address plan (Chapter 10).

15.3Sites asking the cloud: inbound endpoints

The VPC resolver isn't reachable from outside the VPC: its address works only for traffic that starts inside. To let sites use it, create a Route 53 Resolver inbound endpoint: network interfaces with fixed private addresses in your subnets (at least two, in different zones), which accept DNS queries from anywhere you route to them and pass them to the VPC resolver.

Then, on each site's DNS server or router, add a conditional forwarder: “questions about internal.larder.example go to 10.16.1.10 and 10.16.2.10”. Everything else keeps going to the site's usual resolver.

At Larder: solved

Eli put an inbound endpoint in the hub VPC, with one address in each of two zones, and a security group allowing TCP and UDP port 53 from 10.0.0.0/13, the offices and stores. The store routers got a conditional forwarder for internal.larder.example, rolled out with the same template as the MSS clamp from Chapter 13. The handhelds now resolve the stock service, and because the hub VPC is associated with every Larder private zone, any new internal name works at every store the moment it's created.

Inbound endpoints cost about $0.125 an hour per address, so roughly $180 a month for two. One pair in the hub serves every site, as long as the hub VPC is associated with every zone the sites need.

15.4The cloud asking sites: outbound rules

The reverse problem: a server in a VPC needs files.office.larder.example, which only the office DNS server at 10.1.0.53 knows. Create an outbound endpoint (again, addresses in two zones) and a forwarding rule: “for office.larder.example, forward to 10.1.0.53 through this outbound endpoint”. Then associate the rule with each VPC that should use it. Rules can be shared with other accounts through Resource Access Manager, so the network team writes them once.

The VPC resolver picks the most specific rule that matches a name, as with routes (Chapter 4). There are also system rules, which say “answer this name the normal way”, for carving exceptions out of a broad forward.

Watch out: forwarding loops

If the office forwards larder.example to the cloud, and the cloud forwards larder.example to the office, queries bounce between them until they time out. Forward specific zones in each direction, and make sure no name is forwarded both ways.

15.5Split horizon without surprises

A private zone can have the same name as a public one: split-horizon DNS (Chapter 5). It's useful when the same name should lead to a private address inside and a public one outside, say api.larder.example resolving to an internal load balancer for VPC traffic. But there's a trap in how it works.

Key idea

Inside a VPC, a private zone replaces the public zone of the same name completely. Any record you didn't copy into the private zone doesn't exist there.

Create a private zone called larder.example with just api in it, and from inside the VPC www.larder.example, hooks.larder.example and the mail records all return NXDOMAIN. The resolver found the most specific zone it's responsible for and doesn't fall back to the public one. Safer patterns: put internal names under their own subdomain (internal.larder.example, as Larder does), or make the private zone as specific as possible (a zone for api.larder.example alone).

15.6Endpoint names from outside the VPC

Interface endpoints with private DNS (Chapter 12) make secretsmanager.eu-central-1.amazonaws.com resolve to private addresses, but only through the VPC's resolver. A server in an office or another VPC asks its own resolver and gets the public address. Two fixes:

  • For sites: add conditional forwarders for the service names (for example secretsmanager.eu-central-1.amazonaws.com) to the inbound endpoint in the endpoint's VPC. The VPC resolver answers with the endpoint's private addresses, and traffic flows over the VPN or Direct Connect.
  • For other VPCs: the centralised pattern from Chapter 12: private DNS off on the endpoints, your own private zones for the service names, associated with every spoke.

Forward only the specific service names you've built endpoints for. Forwarding all of amazonaws.com to the cloud sends every AWS lookup from the site there, including names you don't have endpoints for, which then resolve publicly anyway.

Two extras earn their place in most designs:

  • Query logging. Route 53 Resolver query logs record every name each VPC looks up. They're invaluable in incidents (“what was this server talking to?”) and cheap compared with what they answer. Chapter 22 uses them.
  • DNS firewall. Route 53 Resolver DNS Firewall blocks lookups of domains on lists you choose, including managed lists of known malicious domains. Because almost every connection starts with a lookup, it's one of the cheapest controls on what servers can reach (Chapter 18).

15.8Lab: a private zone, an inbound endpoint and a forwarding rule

Lab 15 · Both directions, built and inspected

You'll build a private zone with a record, an inbound endpoint that a site would forward to, and an outbound endpoint with a rule pointing at a (pretend) office DNS server, then inspect what you've built. You need the AWS CLI and Terraform. Cost: four endpoint addresses at about $0.125 an hour each, so about $0.50 an hour; the hosted zone is free if deleted within 12 hours. Destroy it within the hour.

main.tfTerraform ≥ 1.5, AWS provider 5.x

provider "aws" { region = "eu-central-1" }

data "aws_availability_zones" "z" { state = "available" }

resource "aws_vpc" "hub" {
  cidr_block           = "10.70.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true
}
resource "aws_subnet" "s" {
  count             = 2
  vpc_id            = aws_vpc.hub.id
  cidr_block        = cidrsubnet(aws_vpc.hub.cidr_block, 8, count.index + 1)
  availability_zone = data.aws_availability_zones.z.names[count.index]
}

# 15.2 · a private zone, associated with the hub VPC
resource "aws_route53_zone" "internal" {
  name = "internal.lab.example"
  vpc { vpc_id = aws_vpc.hub.id }
}
resource "aws_route53_record" "stock" {
  zone_id = aws_route53_zone.internal.zone_id
  name    = "stock.internal.lab.example"
  type    = "A"
  ttl     = 60
  records = ["10.70.1.50"]
}

# DNS from the sites (10.0.0.0/13) in, and to the office out
resource "aws_security_group" "dns" { vpc_id = aws_vpc.hub.id }
resource "aws_vpc_security_group_ingress_rule" "dns" {
  for_each          = toset(["udp", "tcp"])
  security_group_id = aws_security_group.dns.id
  cidr_ipv4         = "10.0.0.0/13"
  ip_protocol       = each.key
  from_port         = 53
  to_port           = 53
}
resource "aws_vpc_security_group_egress_rule" "dns" {
  security_group_id = aws_security_group.dns.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}

# 15.3 · sites forward internal.lab.example to these two addresses
resource "aws_route53_resolver_endpoint" "inbound" {
  direction          = "INBOUND"
  security_group_ids = [aws_security_group.dns.id]
  ip_address { subnet_id = aws_subnet.s[0].id }
  ip_address { subnet_id = aws_subnet.s[1].id }
}

# 15.4 · the VPC forwards office.lab.example to the office DNS server
resource "aws_route53_resolver_endpoint" "outbound" {
  direction          = "OUTBOUND"
  security_group_ids = [aws_security_group.dns.id]
  ip_address { subnet_id = aws_subnet.s[0].id }
  ip_address { subnet_id = aws_subnet.s[1].id }
}
resource "aws_route53_resolver_rule" "office" {
  domain_name          = "office.lab.example"
  rule_type            = "FORWARD"
  resolver_endpoint_id = aws_route53_resolver_endpoint.outbound.id
  target_ip { ip = "10.1.0.53" }
}
resource "aws_route53_resolver_rule_association" "office" {
  resolver_rule_id = aws_route53_resolver_rule.office.id
  vpc_id           = aws_vpc.hub.id
}

output "inbound_ips" {
  value = [for a in aws_route53_resolver_endpoint.inbound.ip_address : a.ip]
}
  1. Create it with terraform init and terraform apply. Endpoints take a few minutes.
  2. Read the inbound addresses: terraform output inbound_ips. These are what you'd type into a store router's conditional forwarder for internal.lab.example.
  3. Read the rules the VPC now follows: aws route53resolver list-resolver-rules --query 'ResolverRules[].[DomainName,RuleType,TargetIps[0].Ip]' --output table. Find your FORWARD rule and the built-in SYSTEM rule for ., which means “everything else, the normal way”.
  4. Find the split-horizon trap on paper. If you created a private zone named lab.example instead, what would a server in this VPC get for www.lab.example? Why is internal.lab.example safer?
  5. Clean up with terraform destroy, and check in the console that the endpoints are gone; they're the part that bills by the hour.

Stretch goal. If you built the VPN in Lab 13 with a real router at your end, point a conditional forwarder on it at the inbound addresses and run dig stock.internal.lab.example from your laptop.

MistakeWhat happensInstead
A private zone named after your whole public domainPublic records vanish inside the VPC.A subdomain such as internal., or very specific zones.

✓Chapter summary

  • Connected networks still need connected names: each side forwards questions about the other side's zones.
  • Associate private zones with every VPC that needs them, across accounts with authorisation; own them centrally.
  • Inbound endpoints give sites addresses to send cloud questions to, via conditional forwarders.
  • Outbound endpoints and forwarding rules send the cloud's questions about site names to site DNS servers.
  • A private zone replaces the public zone of the same name inside the VPC; use subdomains for internal names.
  • Resolve endpoint names from sites through inbound endpoints; log queries and filter them with a DNS firewall.

Key terms

Hybrid DNS
Resolving names across cloud and on-premises networks.
Conditional forwarder
A DNS server setting that sends questions about one zone to specific servers.
Inbound endpoint
Addresses in a VPC that accept DNS queries from outside and pass them to the VPC resolver.
Outbound endpoint
Addresses in a VPC through which the resolver forwards queries elsewhere.
Forwarding rule
A rule sending one domain's queries to chosen DNS servers.
Zone association
Linking a private zone to a VPC so its resolver answers for it.
DNS firewall
Blocking lookups of chosen domains at the resolver.

Check your understanding

  1. Why can't a store's router simply use the VPC resolver's address, 10.16.0.2, as its DNS server over the VPN? recall

    Show answer

    The VPC resolver only answers queries that originate inside the VPC. Traffic arriving from the VPN can't use it; an inbound endpoint provides addresses that can.

  2. Someone creates a private zone larder.example containing only api. What breaks, and where? apply

    Show answer

    Inside every VPC associated with the zone, every other larder.example name (www, hooks, mail records) returns NXDOMAIN, because the private zone replaces the public one there. Outside those VPCs nothing changes.

  3. A server in a VPC must resolve printer3.office.larder.example. List what you'd create. apply

    Show answer

    An outbound resolver endpoint (two subnets), a forwarding rule for office.larder.example targeting the office DNS server, an association of that rule with the server's VPC, and a route plus firewall rules allowing DNS from the endpoint to the office server over the VPN.

  4. Why forward only specific AWS service names, not all of amazonaws.com, from a site to an inbound endpoint? explain

    Show answer

    Only names that have interface endpoints with private DNS benefit; everything else would just resolve publicly through the cloud resolver instead of locally, adding a dependency on the VPN and the endpoint for every AWS lookup at the site.

  5. Design question: where should Larder's inbound and outbound endpoints live, and why? design

    Show answer

    In the hub VPC, which every site reaches through the TGW and which is associated with every private zone. One pair of each serves all sites and VPCs; forwarding rules are shared with other accounts through RAM and associated with each VPC.
