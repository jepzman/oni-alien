Planning your IP address space

One VPC can pick any range it likes. A company with dozens of VPCs, several regions, offices, stores and partners can't: every range it picks now decides what it can connect later. An hour spent on an address plan saves months of renumbering. This chapter shows how to size, divide and hand out address space so that it stays tidy for years, and what to do when you inherit a plan that isn't.

By the end you can

  • Estimate how much address space a company's cloud needs.
  • Design a hierarchical plan that never overlaps and summarises cleanly.
  • Hand out ranges with an IPAM tool instead of a spreadsheet.
  • Deal with running out: secondary ranges, Kubernetes pods, IPv6, overlapping partners.

Before you start

  • Route summarisation and longest prefix match (Chapter 4).

At Larder

Korenwolf, Larder's first large business customer, wants its office ordering system to call Larder's API over a private connection instead of the internet. Their network team sends over their address ranges. The first line reads 10.20.0.0/16: exactly the range of Larder's production VPC.

Nobody did anything wrong; 10.20.0.0/16 is a popular choice. But it means the two networks can't simply be routed together. Section 10.6 shows what Larder did instead.

10.1The big picture

An address plan is a written decision about which ranges are used for what, across everything you'll ever want to connect: VPCs in every account and region, offices, stores, VPN users, and the partners you can foresee. A good plan has three properties:

  • No overlap. Any two networks that might ever need to talk have different ranges (Chapter 2).
  • Room to grow. Each part has space for years of growth without being renumbered.
  • Hierarchy. Related networks sit in one larger block, so one route can cover them all.

Key idea

Addresses are free; renumbering is expensive. Plan generously, in aligned blocks, and hand ranges out from one place.

10.2How much space do you need?

Work outward from the VPCs. A typical company ends up with one VPC per account × environment × region, plus shared ones for networking and tooling. Then size each VPC from its subnets (Chapter 8): tiers × zones × subnet size, plus at least as much again kept free.

Why /16 per VPCIt's generous for most workloads and the largest a single AWS VPC block can be. Containers are the usual reason to need it (10.5). Smaller VPCs are fine if your plan has a way to add more space later.

10.3A hierarchical plan

Divide the top block by the thing that changes least, usually location (on-premises, then one block per region), then by environment or account, then by tier and zone inside each VPC. Each level is an aligned block inside the one above.

Notice how summarisation pays off. When Antwerp's stores come online in 10.10.0.0/16, nothing in Frankfurt changes: the route to 10.8.0.0/13 already covers it, and with BGP (Chapter 4) even that route is learned automatically.

10.4Handing out ranges: IPAM

A plan in a document is a good start. A plan that's enforced is better. IPAM (IP address management) tools hold the plan as a tree of pools and hand out ranges on request, so two teams can't pick the same block.

With Amazon VPC IPAM, Larder's plan becomes: a top-level pool 10.0.0.0/8; a regional pool 10.16.0.0/12 for eu-central-1; and pools per environment below it, each with rules such as “allocations must be /16” and “only these accounts may allocate”. A new VPC then asks for a range instead of naming one:

vpc.tfallocation from an IPAM pool

resource "aws_vpc" "team" {
  ipv4_ipam_pool_id   = var.prod_pool_id   # shared with this account through AWS RAM
  ipv4_netmask_length = 16                 # "give me the next free /16"
  tags = { Name = "orders-prod" }
}

IPAM also monitors: it flags VPCs whose ranges overlap or don't come from a pool, and shows how full each pool is. Azure Virtual Network Manager has IP address pools that work the same way, and Google Cloud offers internal ranges to reserve and track blocks.

10.5When a VPC runs out

The most common cause is containers. On AWS's managed Kubernetes, each pod gets a real VPC address by default, and a busy cluster can burn through a /20 faster than anyone expected. You have four options, from simplest to most involved:

  1. Add a secondary range to the VPC. AWS lets you add more CIDR blocks to a VPC (five by default, with some restrictions on mixing private ranges) and create new subnets in them. Take them from your plan like any other allocation.
  2. Pack addresses more tightly. Prefix delegation gives each node whole /28 blocks, reducing waste and API calls, but still uses VPC space.
  3. Give pods non-routed addresses. Put pods in a secondary range from 100.64.0.0/10 that's never routed outside the VPC, and let nodes translate pod traffic leaving the VPC. Every cluster can reuse the same range. Chapter 19 builds this.
  4. Use IPv6 for pods. Effectively unlimited, and no translation inside the VPC; the rest of the path must speak IPv6 or be translated.

You can add space but never shrink a VPC's ranges or a subnet's size in place. That asymmetry is why the plan should be generous from the start.

10.6When ranges overlap anyway

Your own plan can prevent overlap inside the company. It can't control partners, customers, or companies you acquire. When two overlapping networks must talk, there are three ways out:

Table 10.3 · Connecting overlapping networks
OptionHow it worksBest for
Expose a service privatelyThe provider connects a consumer's endpoint to your load balancer; no routes are exchanged (PrivateLink on AWS, Chapter 12)Partners and customers who call one of your services
Translate addresses (NAT)One side is shown to the other under a different, non-overlapping rangeWhen whole networks must reach each other and nobody can renumber
RenumberOne side moves to new rangesInside your own company, eventually; painful but permanent

At Larder: solved

Korenwolf only needed to call one service, Larder's ordering API, so Eli used AWS PrivateLink. Larder put the API behind a Network Load Balancer and published it as an endpoint service; Korenwolf created an endpoint in their own VPC, which appears there as a few addresses in their subnets. Each side keeps its own 10.20.0.0/16, no routes are exchanged, and Korenwolf can reach nothing at Larder except that one API. Chapter 12 builds it.

Sharing one network between teams, rather than giving every team its own VPC, saves a lot of space and is worth knowing about: a central team owns the VPC and its subnets, and shares specific subnets with team accounts. Chapter 24 compares the two models.

When to adopt IPv6

IPv6 removes the shortage, but not the need for a plan: you still want to know which /56 belongs to which VPC. New VPCs should be dual stack from the start, because adding IPv6 later is easy but adding it everywhere at once is not. Two practical reasons push in the same direction: AWS charges for every public IPv4 address, and IPv6 gives container platforms all the addresses they could want. Internal services that are IPv6-only are still rare, though; most teams run dual stack for years.

10.8Lab: an address plan you can test

Lab 10 · Plan as code

You'll write an address plan as data, test it automatically, and find the next free block, the core of what an IPAM tool does. You need Python 3. Cost: nothing.

plan.pyPython 3.8+

import ipaddress as ip

PLAN = {
    "10.0.0.0/8": {
        "10.0.0.0/13":  "offices",
        "10.8.0.0/13":  "stores",
        "10.16.0.0/12": {"10.16.0.0/16": "hub", "10.17.0.0/16": "dev",
                         "10.18.0.0/16": "staging", "10.20.0.0/16": "prod"},
        "10.32.0.0/12": "region-2",
    }
}

def check(tree, parent=None, path=""):
    nets = [ip.ip_network(c) for c in tree]          # raises on misaligned blocks
    for i, a in enumerate(nets):
        if parent: assert a.subnet_of(parent), f"{a} not inside {parent}"
        for b in nets[i + 1:]:
            assert not a.overlaps(b), f"{a} overlaps {b}"
    for cidr, child in tree.items():
        if isinstance(child, dict):
            check(child, ip.ip_network(cidr), path + "/" + cidr)

def next_free(parent, used, prefix):
    used = [ip.ip_network(u) for u in used]
    for cand in ip.ip_network(parent).subnets(new_prefix=prefix):
        if not any(cand.overlaps(u) for u in used):
            return cand

check(PLAN)
print("plan OK")
fra = PLAN["10.0.0.0/8"]["10.16.0.0/12"]
print("next /16 in Frankfurt:", next_free("10.16.0.0/12", fra, 16))
  1. Run it. python3 plan.py prints plan OK and the next free /16. Why is it 10.19.0.0/16 and not 10.21.0.0/16?
  2. Break it three ways and read each error: add "10.20.0.0/17": "test" to Frankfurt (overlap); add "10.40.0.0/16": "oops" to Frankfurt (outside its parent); add "10.36.0.0/12" at the top (misaligned).
  3. Reserve on purpose. Mark 10.19.0.0/16 as "spare" so next_free skips it, as Larder's plan does.
  4. Plan a city. Add a "stores" subtree with one /16 per city and allocate Antwerp with next_free.
  5. Make it a test. Turn check(PLAN) into a test that runs in CI whenever someone edits the plan. That's the review step an IPAM tool enforces.

Stretch goal. Write the plan's leaves out as a Terraform variables file (vpc_cidrs = { prod = "10.20.0.0/16", … }) so infrastructure code reads its ranges from the tested plan instead of typing them.

✓Chapter summary

  • A good address plan has no overlap, room to grow and a hierarchy that lets one route cover many networks.
  • Size from accounts × environments × regions, with each VPC sized from its tiers and zones, then double it.
  • Divide by location first, then environment, then tier and zone, in aligned blocks.
  • Enforce the plan with IPAM pools instead of a spreadsheet.
  • When a VPC runs out: secondary ranges, tighter packing, non-routed pod ranges, or IPv6. You can grow, never shrink.
  • For partners with overlapping ranges, expose services privately instead of routing networks together.

Key terms

Address plan
The written decision of which ranges are used for what.
Summarisation
Covering many networks with one shorter-prefix route.
IPAM
A tool that holds the plan as pools and allocates ranges from it.
Pool
A block in an IPAM tree, with rules for what can be allocated from it.
Secondary CIDR
An extra range added to an existing VPC.
VPC sharing
One central VPC whose subnets are shared with other accounts.
Dual stack
Every network has both IPv4 and IPv6 ranges.

Check your understanding

  1. Larder opens stores in a seventh city. Using Table 10.2, which range do they get, and what changes in Frankfurt's route tables? apply

    Show answer

    The next /16 in 10.8.0.0/13 after the existing cities, for example 10.14.0.0/16 if six are used (10.8–10.13). Nothing changes in Frankfurt: the existing route for 10.8.0.0/13 already covers it, and with BGP the store's route is learned anyway. An eighth city still fits; a ninth would need a new block.

  2. Why divide by location before environment, rather than the other way round? explain

    Show answer

    Routing follows location: offices, stores and other regions reach a region through one path, so a single block per region keeps routes short. Dividing by environment first would scatter each region's VPCs across several blocks and need more routes everywhere.

  3. An EKS cluster in a /16 VPC is running out of addresses. Name two fixes that don't involve a new VPC. apply

    Show answer

    Any two of: add a secondary CIDR and new subnets for pods; give pods a non-routed range from 100.64.0.0/10 (custom networking); use prefix delegation to reduce waste; move pods to IPv6.

  4. A partner overlaps your production range and needs to call one API. Why is PrivateLink better than a VPN with NAT here? design

    Show answer

    PrivateLink exchanges no routes, so overlap doesn't matter, and the partner can reach only that one service. A VPN with NAT works but is more complex, joins the networks more broadly, and needs translation rules maintained on at least one side.

  5. A colleague says “we're moving to IPv6, so we don't need an address plan”. What do you answer? explain

    Show answer

    Scarcity goes away, but you still need to know which prefix belongs to which VPC and region for routing, firewall rules, troubleshooting and summarisation. And you'll run IPv4 alongside for years, so its plan still matters.
