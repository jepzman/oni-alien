Identity as code and least privilege at scale

By now you've written trust policies, permission sets, SCPs and perimeters. Changing any of them in a console works fine until there are a hundred of them. Then nobody can say what changed, who approved it, or whether the console still matches what was agreed. This chapter puts identity in a repository: Terraform for every role and guardrail, checks that fail a pull request before a bad policy ships, and ways to keep shrinking permissions to what is actually used.

By the end you can

  • Manage permission sets, assignments, roles and SCPs in Terraform.
  • Build a pipeline that lints, validates and checks every policy change.
  • Use IAM Access Analyzer's custom checks to stop new access you didn't intend.
  • Narrow existing policies using generated policies and unused-access findings.
  • Set up review rules so that changing who can get in needs two people.

Before you start

  • Policies and evaluation (Chapters 9 and 10); permission sets (Chapter 12).
  • CI/CD with OIDC (Chapter 17); SCPs (Chapter 20).
  • Some Terraform helps; the snippets are short.

At Larder

In December 2027 Lena, preparing for the ISO 27001 audit, asked Eli a simple question: list every change in 2027 to who could reach production, and who approved each one. It took him two days. Permission sets had been made in the console in January; SCPs had been pasted into the console in June; roles were spread across service repositories' CloudFormation, the Terraform for Handbook 1's network, and hand-made fixes. CloudTrail recorded what changed, but approvals lived in chat threads and tickets, when they existed.

The first watch list day (Chapter 23) had made the same point from the other side: Eli's own assignment outside TEAM was a well-meant fix that nobody had reviewed. And the reporting team had just asked for a role to sync exports to their warehouse, with a policy they'd written themselves. Who would check it, and how?

24.1Why identity belongs in a repository

Infrastructure as code is old news for servers and networks. For identity it matters more, because identity changes are small, frequent and powerful: one line in a trust policy can let a whole other account in. A repository gives you:

  • One source of truth. What's in main is what should exist. Anything else is drift.
  • Review before change. Every change is a pull request, with a named author, named approvers and a reason.
  • History you can answer audits from. Lena's question becomes git log on a few folders.
  • Checks that run every time. A pipeline catches what reviewers miss at five on a Friday.
  • Reuse. A module for “a role that GitHub deploys with” encodes Chapter 17's conditions once.

Terraform, CloudFormation, the CDK, Pulumi: the choice matters less than having one. Larder already used Terraform for its network (Handbook 1), so identity went there too.

Keeping policy JSON in its own files rather than in Terraform's jsonencode or aws_iam_policy_document has one big advantage: the checks in 24.4 can read the same files without running Terraform.

24.3Moving existing resources in

You rarely start from nothing. Bring existing resources under code with Terraform's import blocks, one folder at a time, until terraform plan shows no changes: then the code describes reality exactly. Start with the most powerful things (SCPs, permission sets, trust policies of cross-account roles) and leave the long tail of small roles for later. When a folder is imported, make the code the only way in: take away the console permissions to change those resources from everyone but the apply role and break-glass, with an SCP or a permission boundary.

Then run terraform plan every night. Any difference is drift: a console change, TEAM misbehaving, or another tool fighting yours. Each drift report opens a ticket; the fix is either to revert or to put the change into code.

24.4The pipeline: checks before review

Checks run on every pull request, cheapest first:

  1. Format and plan. terraform fmt -check and terraform plan, with a read-only plan role assumed through OIDC (Chapter 17). The plan is posted on the pull request, so reviewers see what will change, not just what the code says.
  2. Your own lint rules, like the lab's lint.py: no whole services on *, no iam:PassRole on every role, nothing on the never-grant list, every role tagged with its team.
  3. Access Analyzer validation (validate-policy, Chapter 9): grammar errors, security warnings and suggestions, free.
  4. Access Analyzer custom checks, which use automated reasoning to prove things about a policy, whatever wildcards it uses (paid, a fraction of a cent per check):
    • check-access-not-granted: “this policy doesn't allow any of these actions (or these resources)”. Larder runs it with its never-grant list on every identity policy.
    • check-no-new-access: “the new version allows nothing the old one didn't”. Run on every trust policy and resource policy: if it fails, the change opens a new way in, and the pull request gets a new-access label that requires the security reviewer.
aws accessanalyzer check-access-not-granted --policy-type IDENTITY_POLICY \
  --policy-document file://policies/reporting-sync.json \
  --access '[{"actions": ["iam:CreateUser", "iam:CreateAccessKey", "s3:PutBucketPolicy"]}]'
aws accessanalyzer check-no-new-access --policy-type RESOURCE_POLICY \
  --existing-policy-document file://old/trust.json --new-policy-document file://new/trust.json

Key idea

Let machines answer “is this allowed?” and “is this new?”, so reviewers can spend their attention on “should it be?”.

24.5Review and who may apply

The pipeline holds the most powerful credentials in the company: its apply role in the management account can change every SCP. Protect it like break-glass:

  • The apply role trusts only the main branch of larder/larder-identity in a GitHub environment identity (Chapter 17's sub condition), and that environment requires approval.
  • Branch protection: no direct pushes to main; two approvals; a CODEOWNERS file names the platform team for everything and adds security for organization/ and for any pull request labelled new-access. The author's own approval doesn't count.
  • Pull requests from forks never get credentials, not even for plan.
  • Changes to the pipeline itself (workflow files, CODEOWNERS) need the same two approvals.
  • Break-glass (Chapter 14) stays outside the pipeline: when CI or GitHub is down, you still have a way in, with its alarm.

Separation of duties, again

Two approvals is Chapter 6's separation of duties put into practice: no single person can grant themselves access. It also protects people: when an auditor asks who approved a change, the answer is in the pull request.

24.6Least privilege at scale

Checks stop new bad policies. Existing policies still tend to be wider than needed, because people write them before they know exactly what the code calls. Three tools narrow them over time:

  • Policy generation. Access Analyzer can read up to 90 days of a role's CloudTrail history and generate a policy with the services and actions it actually used (resource ARNs for some services, placeholders for others). Treat it as a draft: it can only see what happened in that window, so the monthly job or the yearly report won't be there.
  • Unused access findings (Chapter 23): roles not used for 90 days, and unused services and actions in policies that are used. Each finding becomes a pull request that removes something, or a note saying why it stays.
  • Last accessed information in IAM shows, per service and for some services per action, when a role last used it. It's free and good for quick checks.

Scale also comes from writing fewer policies. ABAC (Chapter 6) with a team tag lets one statement cover every team's resources; a permission boundary (Chapter 10) lets teams create their own roles in their accounts without being able to escalate. Modules encode the patterns once. Larder's rule of thumb: if two policies differ only in a name, they should be one module.

24.7Testing policies

A check proves a property; a test checks behaviour. For important policies, write both. Write expected results as a table of requests: dispatch-task may PutObject routes/x; may not GetObject orders/x. Run them against the policy, with the policy simulator in an account (Chapter 11), or with a local evaluator like Chapter 10's lab for simple cases. Perimeter policies (Chapter 22) deserve real tests in staging: the requests that must still work, and the ones that must fail, run after every change.

On Azure

Azure splits identity code in two: azurerm manages role assignments and custom roles on subscriptions and resources; azuread manages Entra ID groups, app registrations and service principals. Use group-based role assignments and PIM-eligible assignments, so the code grants eligibility, not standing access.

On Google Cloud

Terraform's google_project_iam_member adds one binding; google_project_iam_policy replaces a project's whole policy, and can lock you out if you forget a binding. Prefer members or bindings, and let the IAM recommender's suggestions arrive as pull requests.

24.10Lab: a policy linter for CI

Lab 24 · Fail a pull request on a bad policy

You'll run a linter over a folder of policies, see it fail the reporting team's first attempt, fix the policy until the build passes, and optionally run Access Analyzer's checks on the same files. You need Python 3; for the optional part, the AWS CLI. Cost: free; the optional custom checks cost a fraction of a cent each.

lint.pyPython 3.8+

# lint.py · checks workload and team policies before they can be merged; exit code 1 fails the build
import fnmatch, glob, json, sys

NEVER_GRANT = ["iam:CreateUser", "iam:CreateAccessKey",          # Larder has no IAM users (Chapter 17)
               "organizations:LeaveOrganization", "cloudtrail:StopLogging",
               "kms:ScheduleKeyDeletion", "s3:PutBucketPolicy"]

def as_list(x):
    return x if isinstance(x, list) else [x]

def check(doc):
    problems = []
    for i, st in enumerate(as_list(doc["Statement"]), 1):
        if st["Effect"] != "Allow":
            continue
        where = st.get("Sid", f"statement {i}")
        actions = [a.lower() for a in as_list(st.get("Action", []))]
        resources = as_list(st.get("Resource", []))
        if "NotAction" in st:
            problems.append(("error", where, "Allow with NotAction grants everything else"))
        if "*" in resources and any(a == "*" or a.endswith(":*") for a in actions):
            problems.append(("error", where, "a whole service on every resource"))
        if "iam:passrole" in actions and "*" in resources:
            problems.append(("error", where, "iam:PassRole on every role"))
        for bad in NEVER_GRANT:
            if any(fnmatch.fnmatchcase(bad.lower(), a) for a in actions):
                problems.append(("error", where, f"grants {bad}, on the never-grant list"))
        read_only = all(a.split(":")[-1].startswith(("list", "describe", "get")) for a in actions)
        if "*" in resources and not read_only and not st.get("Condition"):
            problems.append(("warn", where, "Resource is * with no condition: say why in the review"))
    return problems

folder = sys.argv[1] if len(sys.argv) > 1 else "policies"
errors = 0
for path in sorted(glob.glob(f"{folder}/*.json")):
    problems = check(json.load(open(path)))
    errors += sum(level == "error" for level, _, _ in problems)
    print(f"{path}: {len(problems) or 'no'} problem(s)")
    for level, where, text in problems:
        print(f"  {level.upper():<5} {where}: {text}")
print(f"\n{errors} error(s)")
sys.exit(1 if errors else 0)

24.11Common mistakes

MistakeWhat happensInstead
Code and console both in useDrift; the next apply undoes a fix, or a change nobody reviewed stays.Deny console changes to managed resources; nightly drift plan.
The pipeline role is the weakest linkAnyone who can edit a workflow or push to a branch becomes admin of the organisation.Trust only main in a protected environment; code owners on workflow files.
Assigning permission sets to individuals in codeHundreds of assignments; leavers linger.Assign to groups; the IdP manages membership.
Reviewing the code, not the planA small diff with a big effect (a changed module) slips through.Post the plan on the pull request.
Accepting generated policies as finalA job that runs monthly or yearly breaks.Treat them as drafts; check against known schedules.
Replacing whole IAM policies on Google CloudA forgotten binding locks people out.Use member or binding resources.

✓Chapter summary

  • Put identity in one repository: SCPs, permission sets and group assignments, and roles, imported until the plan is clean.
  • Run checks before review: your own lint rules, Access Analyzer validation, check-access-not-granted and check-no-new-access.
  • Require two approvals through code owners, and protect the apply role like break-glass.
  • Catch drift with a nightly plan, and deny console changes to managed resources.
  • Shrink existing access with policy generation, unused access findings and last accessed data; write fewer policies with modules, ABAC and boundaries.

Key terms

Identity as code
Managing roles, policies and assignments as reviewed files that a pipeline applies.
Drift
A difference between what the code says and what exists.
check-no-new-access
An Access Analyzer check that a new policy version grants nothing the old one didn't.
check-access-not-granted
An Access Analyzer check that a policy doesn't allow listed actions or resources.
Policy generation
Drafting a policy from a role's recorded activity in CloudTrail.
Code owners
People or teams whose approval a repository requires for changes to given paths.

Check your understanding

  1. Name three things a repository gives you for identity that a console doesn't. recall

    Show answer

    Any three of: one source of truth, so drift is detectable; review before change with named approvers; history that answers audit questions; automatic checks on every change; reuse through modules.

  2. Why does check-no-new-access suit trust policies better than a text diff? explain

    Show answer

    It reasons about what the policy allows, not how it's written. A text diff of one changed condition can't tell whether the role is now open to more principals; the check proves whether any new access was granted, regardless of wildcards or rewording.

  3. Policy generation from 90 days of activity proposes a narrower policy for finance-reports. What would you check before merging it? apply

    Show answer

    Whether every scheduled job ran in the window: quarter-end and year-end reports may need actions not seen in 90 days. Also replace placeholder resources with real ARNs, and keep conditions the old policy had (such as aws:ViaAWSService for KMS).

  4. An engineer can edit .github/workflows/apply.yml in a branch. How could that become organisation admin, and what stops it? explain

    Show answer

    If the apply role trusted any branch, their workflow could assume it and do anything. It's stopped by trusting only main in a protected environment, branch protection with two approvals, and code owners on workflow files.

  5. Design the review rule for a pull request that changes wmsb-nightly-file's trust policy. design

    Show answer

    Checks: lint, validate, and check-no-new-access against main. If it fails, the new-access label adds the security reviewer; approvals from platform and security, neither being the author. The plan is posted, and the perimeter exception tag is checked as well, since the RCP depends on it.

  6. Compare how a Terraform mistake can lock you out on Google Cloud and how break-glass protects you on AWS. compare

    Show answer

    On Google Cloud, an authoritative google_project_iam_policy replaces all bindings, so a missing one removes access, perhaps your own. On AWS, a bad SCP or permission set could do the same, but the break-glass users and break-glass-admin sit outside the pipeline and are excepted in the guardrails, so there's a way back in.
