Every login screen, API key, IAM policy and “access denied” in this book is an answer to two questions: who is asking, and are they allowed to do this? At Larder

On Monday 16 November 2026, a database migration from Ben's orders team went wrong and quietly damaged three days of substitution records. The plan was simple: restore the orders database to Friday night and replay from there. It failed. The database kept automated backups for one day, not the fourteen everyone assumed.

The audit log showed the change: on Thursday 12 November at 22:14, someone set backup retention to one day, probably to save money. The log named who: ops. That's the IAM user engineers share for production fixes. Six people know its password, including Jasper, who left the company fifteen months ago. Nobody remembers doing it. Rebuilding the records from the order events took Ben's team two days.

Eli, the platform tech lead, is asked to find out who did it. Section 1.7 explains why that's the wrong question.

1.1Four questions

“Access control” sounds like one thing. It's really four questions, asked in order, and most confusion about identity comes from mixing them up:

  1. Identification: who do you say you are? A name: tomas@larder.example, an access key ID, a service account. Claiming a name proves nothing.
  2. Authentication: prove it. Something only the real owner of that name can show: a password, a passkey, a signed token, a private key. Authentication turns a claim into an identity you can rely on.
  3. Authorisation: may you do this? Given who you are, is this action on this resource allowed, right now? This is where policies live.
  4. Accountability: who did what, and when? A record, written as the request happens, that ties the action to the identity. Without it, you can't investigate, prove compliance or learn from mistakes.

When something goes wrong, the first job is to work out which question failed. “I can't log in” is authentication. “I logged in but the button is greyed out” is authorisation. “We don't know who changed it” is accountability. They have different causes and different owners.

401 vs 403HTTP mixes the words up. Status 401 Unauthorized actually means unauthenticated: you didn't prove who you are. 403 Forbidden means you did, and you're not allowed.

You'll often see the first three shortened to AuthN (authentication) and AuthZ (authorisation), and the whole field called IAM, identity and access management. AWS also uses IAM as the name of one specific service. This book says “AWS IAM” when it means the service.

1.2Principals: who can ask

A principal is anything that can make a request and be granted access: a person, or a piece of software acting on its own behalf. A principal has an identity (who it is), one or more credentials (how it proves it), and permissions (what it may do). These are three different things, and good designs keep them separate: you can rotate a credential without changing the identity, or move a person to a new team without issuing new credentials.

1.3Credentials: how a principal proves it

A credential is whatever a principal shows to authenticate. For people, the classic categories are called factors:

  • Something you know: a password or PIN.
  • Something you have: a phone with an authenticator app, a security key, a passkey stored on a device.
  • Something you are: a fingerprint or face, usually unlocking something you have, rather than sent anywhere.

Combining two different kinds is multi-factor authentication (MFA). Chapter 2 takes these apart, including which second factors actually stop phishing.

For software, credentials are keys and tokens: an API key, an access key pair, a signed token, a client certificate. The property that matters most is how long it lives:

  • A long-lived credential (an access key, an API key, a password) works until someone remembers to revoke it. If it leaks into a log, a laptop backup or a Git history, it keeps working for whoever finds it.
  • A short-lived credential (a session token valid for an hour) is issued after authenticating with something stronger, and expires by itself. A leak is a problem for minutes, not years.

Key idea

Prefer credentials that expire by themselves. Most of the work in this book is replacing long-lived secrets with short-lived ones.

1.4Resources, actions and context

Authorisation needs more than “who”. Every request carries four things, and every access rule you'll ever write is about some combination of them:

  • Principal: who is asking (after authentication).
  • Action: what they want to do: read, update stock, delete, change backup retention.
  • Resource: what they want to do it to: the Noord store's stock, the orders database, one S3 bucket.
  • Context: everything else known about the request: the time, the network it came from, whether MFA was used, the device, the tags on the principal and the resource.

Write a request as one sentence and the four parts fall out: “Tomás wants to set stock on Noord's bananas, at 06:12, from the store's tablet, signed in with a passkey.” A rule is a sentence of the same shape with blanks: “Store managers may set stock on their own store's items.” Chapter 9 writes these as AWS policies, and Chapter 6 compares the ways of filling the blanks (roles, attributes, relationships).

One more rule underpins all of them. Unless a rule allows a request, it's denied. This is default deny, and it means that a forgotten rule fails safe: something someone needs doesn't work, and they ask. The opposite, default allow, fails silently: something nobody intended works, and nobody notices.

Three roles in that picture have names you'll meet everywhere:

  • The identity provider (IdP) authenticates people and issues tokens that describe them. Larder's staff will sign in through one (Chapter 12).
  • The policy enforcement point (PEP) is the code that stops a request until it has an answer. Here it's the stock tool; on AWS, it's every service's API endpoint.
  • The policy decision point (PDP) holds the rules and answers allow or deny. In a small app it's a function; on AWS, it's the IAM policy engine, which evaluates every API call.

Notice what the token in step ② does. Tomás authenticates once; for the next 30 minutes, the stock tool trusts the token instead of asking for his password again. That's convenient, and it's also why a stolen token is as good as a stolen password while it lasts. Chapter 3 is about tokens.

1.6Trust: whose word are you taking?

In step ③, the stock tool doesn't check Tomás's passkey. It checks the token, and believes what the token says because it was signed by an identity provider it's configured to trust. Every access decision rests on a chain like this: the database trusts the stock tool, the stock tool trusts the identity provider, the identity provider trusts Tomás's passkey.

Trust isn't a feeling; it's configuration you can read. Somewhere there's a setting that says “accept tokens signed by this key, issued by this provider, meant for this app”. When that setting is too broad (any issuer, any audience), anyone who can get a token from somewhere gets in. Two places you'll meet this soon:

  • Federation: Larder trusts Korenwolf's identity provider to vouch for Korenwolf's office managers, so they don't need Larder passwords (Chapter 5).
  • Role trust policies on AWS, which say who may assume a role (Chapter 8). A trust policy that's too broad is one of the most serious IAM mistakes there is.

Key idea

For every access decision, you should be able to say whose word it takes, and where that trust is written down.

1.7Why shared identities break everything

A shared account, such as Larder's ops user, one login for a whole team, or one API key used by three services, looks like a convenience. Run it past the four questions and every one of them fails:

Table 1.2 · The ops user against the four questions
QuestionWith opsWith one identity per person
IdentificationThe name says ops, which is six people.The name is one person.
AuthenticationA shared password can't have a personal second factor; it's in a chat history and a former employee's memory.Each person has their own factors; a leaver's are switched off.
AuthorisationEveryone gets the union of what anyone needed: admin.Each person gets their own job's access.
AccountabilityThe log says ops. Investigation stops there.The log names the person, so you can ask them what they were trying to do.

And removing access, for one leaver, means changing the password for everyone, so it rarely happens. That's how a co-founder who left in 2025 still knew the production password in 2026.

At Larder: what Eli does instead

Eli can't find out who changed the backups, and he stops trying: there's no answer in the data, and asking six people to accuse each other helps nobody. The useful question is how to make the next log line name a person, and make the change impossible without deliberate effort. His plan, which the rest of this book carries out: an identity for every engineer through single sign-on (Chapter 12); admin access only when needed, with approval (Chapter 14); and a guardrail that denies shortening backup retention in production, whoever asks (Chapter 10 and Chapter 20). The ops user's password is changed that afternoon, and the user is deleted in Chapter 12.

Watch out: shared machine credentials

The same applies to software. One API key used by three services means you can't tell which one made a call, can't give each one only what it needs, and can't revoke one without breaking the others. Give each workload its own identity (Chapter 15).

On Azure

Entra ID (formerly Azure Active Directory) is the centre of everything: people, groups, apps and managed identities all live in one tenant, and the same directory signs people in to Microsoft 365. Azure RBAC then grants those identities roles on subscriptions and resources. Many companies already have Entra ID from Microsoft 365 before they use Azure at all.

On Google Cloud

People are Google accounts managed by Cloud Identity or Workspace, usually synced or federated from the company's IdP; software runs as service accounts, which are both identities and resources (you can grant someone permission to act as one). IAM policies attach to the organisation, folders, projects and individual resources.

1.9Lab: the four questions in forty lines

Lab 1 · Authenticate, authorise, record

You'll build a tiny access system with a shared identity, see what its log can and can't tell you, then give everyone their own identity and remove a leaver. You need Python 3, nothing else. Cost: nothing.

access.pyPython 3.8+

# access.py · authenticate → authorise → record, in one small file
import hashlib, hmac

def h(secret):
    return hashlib.sha256(secret.encode()).hexdigest()

# Who exists, the hash of the key each one proves itself with, and their groups
PRINCIPALS = {
    "ops": {"key_hash": h("ops-key-known-by-six-people"), "groups": ["admins"]},
}

# What each group may do: (action, resource prefix); "*" matches anything
POLICIES = {
    "admins":     [("*", "*")],
    "developers": [("db:Describe", "db/"), ("logs:Read", "logs/")],
}

AUDIT = []

def authenticate(name, key):
    p = PRINCIPALS.get(name)
    return p is not None and hmac.compare_digest(p["key_hash"], h(key))

def authorise(name, action, resource):
    for group in PRINCIPALS[name]["groups"]:
        for act, prefix in POLICIES[group]:
            if act in ("*", action) and (prefix == "*" or resource.startswith(prefix)):
                return True
    return False                      # default deny

def request(name, key, action, resource):
    if not authenticate(name, key):
        decision = "unauthenticated"
    elif not authorise(name, action, resource):
        decision = "denied"
    else:
        decision = "allowed"
    AUDIT.append(f"{name:<6} {action:<15} {resource:<14} {decision}")
    return decision

if __name__ == "__main__":
    shared = "ops-key-known-by-six-people"
    request("ops", shared, "db:Describe", "db/orders")              # Ben looks
    request("ops", shared, "db:SetBackups", "db/orders")            # someone changes backups
    request("ops", "a-guess", "db:Delete", "db/orders")             # a stranger tries
    print("\n".join(AUDIT))

✓Chapter summary

  • Access control is four questions: identify, authenticate, authorise, record. When something fails, find which one.
  • A principal (a person or a workload) has an identity, credentials and permissions; keep the three separate.
  • Every request has a principal, an action, a resource and context. Rules are sentences about those four.
  • Default deny: nothing is allowed unless a rule allows it.
  • Authentication happens once, at an identity provider; tokens carry the result; authorisation happens on every request.
  • Every decision rests on trust that's written down somewhere. Know where.
  • Shared identities fail all four questions at once. Prefer short-lived credentials to long-lived ones.

At Larder

On the night of Saturday 21 November 2026, Larder's login endpoint received about 40,000 sign-in attempts in four hours, from about 2,000 different addresses. Each tried one email address and one password, and moved on. 310 of them worked. Nobody had stolen anything from Larder. Its password database was intact, and properly hashed since Jasper first built it. The attackers had a list of email addresses and passwords leaked from other sites, and 310 Larder customers had used the same password here. 2.1How passwords fail

A password is a secret that the user and the system both know. That design has four weak points, and it helps to keep them apart because each has a different defence:

Table 2.1 · Four ways passwords get broken
AttackHow it worksMain defence
GuessingTry common passwords against many accounts (“password spraying”), or many passwords against one.Rate limits and lockouts; reject common passwords (2.3)
Credential stuffingReplay email–password pairs leaked from other sites, betting on reuse.Check against breached passwords; MFA; passkeys

Larder's Saturday night was credential stuffing. It's cheap for attackers, because billions of leaked pairs circulate, and it works because people reuse passwords. Strong hashing doesn't help against it: the attacker isn't attacking your database, just logging in. Only the defences in the last column do.

2.2Storing passwords: salted, slow hashes

You must be able to check a password without being able to read it. The tool is a hash function: a one-way calculation that turns any input into a fixed-size fingerprint. You store the fingerprint; at login you hash what was typed and compare. Never store passwords as they are, and never encrypt them: encryption can be reversed by anyone who gets the key, and in a breach they often do.

A plain hash such as SHA-256 isn't enough, for two reasons:

  • It's fast. Fast is good for checking files and bad for passwords: an attacker with your database can try billions of guesses a second on graphics cards. In the lab, one laptop core manages millions.
  • It's the same for everyone. Two customers with the password winter2026 get the same hash, so cracking one cracks both, and precomputed tables of common passwords work instantly.

The fix has two parts. A salt, a random value generated for each password and stored next to it, makes every hash unique even for identical passwords. A password hashing function is deliberately slow and, in modern designs, needs lots of memory, so that each guess costs real time and real hardware.

Table 2.2 · Password hashing functions, in order of preference

Better still, don't store passwords at all: use a managed identity service (Amazon Cognito, Microsoft Entra External ID, Google's Identity Platform, or a specialist provider), which does this for you.

2.3Password rules that actually help

Many familiar password rules make things worse. People forced to add a symbol write Password1!; people forced to change every 90 days write Winter2026, then Spring2027. NIST's Digital Identity Guidelines (SP 800-63B, revised in 2025) reflect what the evidence shows:

  • Length over complexity. At least 15 characters when a password is the only factor, at least 8 when it's combined with MFA; allow at least 64. No rules about mixing character types.
  • Check against breached and common passwords at sign-up and at password change, and reject matches. Services such as Have I Been Pwned's Pwned Passwords let you check without revealing the password: you send the first five characters of its SHA-1 hash and compare the returned list yourself.
  • No forced periodic changes. Force a change only when there's evidence of compromise.
  • Let password managers work: allow pasting, and don't block autofill.
  • Limit failed attempts per account, and watch failure rates across all accounts, which is how stuffing shows up.

2.4Second factors, and which ones stop phishing

Multi-factor authentication adds something you have to something you know. All of the factors below stop credential stuffing, because the attacker has the password but not the phone or key. They differ sharply against phishing.

A real-time phishing proxy sits between the user and the real site: it shows the real login page, passes along everything the user types, including the code, and keeps the session cookie the real site sends back. 2.5How a one-time code is made

An authenticator app's six-digit code is a TOTP, a time-based one-time password (RFC 6238). It's worth knowing exactly how it works, because it explains both its strengths and its limits:

  1. At enrolment, the server generates a random secret and shows it as a QR code. The app stores it; so does the server.
  2. Both sides count time steps: the Unix time divided by 30, rounded down. Every 30 seconds, the number goes up by one.
  3. Both compute an HMAC (a keyed hash, here with SHA-1) of the time step, using the secret as the key.
  4. Both take four bytes from the result, at a position chosen by its last byte, and keep the last six decimal digits. That's the code.

The server accepts the current code, usually plus or minus one step for clock drift, and should refuse a code that's already been used. Nothing is sent anywhere, which is why it works offline. But the server must store the secret in a form it can use, so a server breach exposes every secret; and a code is a value, so it can be phished.

2.6Passkeys and WebAuthn

A passkey replaces the shared secret with a key pair. It's built on the FIDO2 standards; the part browsers implement is called WebAuthn. At registration, the user's device creates a new key pair just for this site. The private key never leaves the device (or the user's password manager or platform keychain); the site stores only the public key.

At sign-in:

  1. The site sends a random challenge.
  2. The browser asks the device to sign it, and adds the origin it's actually on (https://larder.example) to what gets signed. The user unlocks the key with a fingerprint, face or PIN, which never leaves the device.
  3. The site checks the signature with the stored public key, and checks that the origin is its own.

Key idea

Passkeys resist phishing because the browser, not the user, decides which site a signature is for. There's no secret for the user to type into the wrong place.

There's also nothing worth stealing on the server: a database of public keys is useless to an attacker. Passkeys come in two kinds. Synced passkeys are backed up by the platform (Apple, Google, Microsoft or a password manager) across a person's devices; they're convenient and right for most customers. Device-bound passkeys live on one hardware security key and can't be copied; use them for administrators, where you want to know exactly where the key is.

Passkey or MFA?A passkey combines something you have (the device) with something you are or know (the unlock), so on its own it counts as phishing-resistant MFA. A security key used as a second factor after a password gives the same protection.

2.7Recovery: the back door

Every authentication system has a way in for people who've lost their phone or forgotten their password, and attackers know it. A strong passkey is worthless if “I lost my phone” to the help desk gets a new one by email. Design recovery as carefully as login:

  • Offer several registered factors (two passkeys, or a passkey and recovery codes), so losing one isn't a recovery event.
  • Give one-time recovery codes at enrolment, to be stored offline.
  • For staff, recovery goes through verified identity: a video call with a manager who knows them, or showing ID in person, never a phone call alone. Help-desk social engineering is behind many well-known breaches.
  • Notify on every change of factor or email address, through the old channel as well as the new.
  • Slow down sensitive changes after recovery: no payout-address changes for 24 hours, for example.

2.9Choosing for customers, staff and administrators

There's no single right answer, because the people and the risks differ. A reasonable baseline:

  • Customers: offer passkeys and make them the easy path; keep passwords with breached-password checks and rate limits; ask for extra verification on risky actions (a new delivery address with a saved card) rather than on every login.
  • Staff: single sign-on with MFA for everything (Chapter 12); push with number matching at minimum, passkeys preferred.
  • Administrators and production access: phishing-resistant factors only: device-bound passkeys or hardware security keys, two per person.

At Larder: what changed

By Sunday afternoon, the 310 accounts were locked and their owners emailed; the 41 orders were refunded, and Lena reported the incident to the Dutch data protection authority within the 72 hours GDPR allows. In the following two weeks, Dee's mobile team and Eli shipped four changes: failed-login limits per account and per address, with an alert when the overall failure rate jumps; a breached-password check at sign-up, login and password change; a step-up check (a code sent to the account's email) before a saved card can pay for an order to a new address; and passkeys in the app and on the web. Within a month, 18 % of active customers had added a passkey.

For staff, the incident started a harder conversation. Engineers used push approvals without number matching, and the ops user from Chapter 1 had no second factor at all. Eli ordered two hardware security keys for each of the nine people with production access; Chapter 12 puts them to use.

# totp.py · time-based one-time passwords (RFC 6238), from scratch
import base64, hashlib, hmac, struct, time

def hotp(key, counter, digits=6):
    mac = hmac.new(key, struct.pack(">Q", counter), hashlib.sha1).digest()
    offset = mac[-1] & 0x0F                                  # dynamic truncation
    code = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(code % 10 ** digits).zfill(digits)

def totp(key, at=None, step=30, digits=6):
    now = time.time() if at is None else at
    return hotp(key, int(now // step), digits)

def check(key, code, at=None, window=1):
    now = time.time() if at is None else at
    return any(hmac.compare_digest(totp(key, now + d * 30), code)
               for d in range(-window, window + 1))

3.1Why sessions exist

HTTP is stateless: each request stands alone, and the server doesn't remember the last one. So after a person authenticates, the server hands back a session credential, something the client sends with every following request to say “it's still me”. There are two ways to build one:

  • A server-side session: the server stores the session (who, since when, what was proved) and gives the client only a long random session ID, usually in a cookie. To check a request, the server looks the ID up.
  • A self-contained token: the server writes the facts into the token itself and signs it. To check a request, any server with the right key verifies the signature and reads the facts, with no lookup.

Neither is better. Self-contained tokens scale and cross boundaries easily; server-side sessions are easy to end. Most real systems use both, and the art is in combining them (3.6).

3.3Bearer tokens

APIs and mobile apps usually skip cookies and send a token in a header:

GET /v1/orders HTTP/1.1
Host: api.larder.example
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOi...

A bearer token is exactly what the name says: whoever bears it gets access. There's no proof that the sender is the party it was issued to. That makes bearer tokens simple, and it makes every copy dangerous: in a log line, a crash report, a screenshot, a browser's history, a support ticket. Treat them like passwords, and keep them short-lived.

Bearer tokens come in two forms. An opaque token is a random string; the API asks the issuer what it means (introspection), so it behaves like a server-side session. A structured token carries its own facts, signed, and the commonest format is the JWT.

Sender-constrained tokensStandards such as DPoP and mutual TLS bind a token to a key the client holds, so a stolen copy is useless without the key too. They're increasingly common in banking and high-risk APIs.

3.4Inside a JSON Web Token

A JSON Web Token (JWT, often pronounced “jot”) is three parts separated by dots: a header, a payload of claims, and a signature. The first two are JSON, encoded with base64url (base64 with URL-safe characters and no padding). Encoded is not encrypted: anyone who has a JWT can read it.

The registered claims you'll see everywhere:

  • iss (issuer): who signed it, usually a URL.
  • sub (subject): who it's about: a user or client ID.
  • aud (audience): which API or app it's meant for.
  • exp (expiry), nbf (not before), iat (issued at): Unix times.
  • jti (JWT ID): a unique ID, useful for revocation lists and replay detection.

Plus whatever the issuer adds: scopes, roles, group names, tenant IDs. Keep that short and non-sensitive: tokens end up in logs, and every request carries the whole thing.

3.5Checking a token: every step

The signature is only the beginning. An API that receives a JWT must check all of this, in this order, before it believes a single claim:

  1. Algorithm: accept only the algorithms you expect (an allow-list), whatever the header says. Never accept none.
  2. Key: find the right key for this issuer. For asymmetric tokens, issuers publish their public keys at a JWKS URL, and the header's kid says which key signed it. Cache the keys; refresh them when an unknown kid appears.
  3. Signature: verify it, comparing in constant time.
  4. Issuer: iss must be exactly the issuer you trust.
  5. Audience: aud must be you. A valid token for another API must fail here.
  6. Time: exp in the future and nbf in the past, allowing a small leeway (30–60 seconds) for clock differences.
  7. Then authorise: the token says who; your rules still decide whether this request is allowed (Chapter 1).

Watch out: letting the token choose the algorithm

Two famous bugs come from trusting the header. With "alg": "none", some libraries skipped the signature check entirely. With algorithm confusion, an attacker changes RS256 to HS256 and signs with the issuer's public key as if it were a shared secret; a library that picks the method from the header then verifies it. Always tell your library which algorithms and keys to accept, and use a well-maintained library rather than writing your own.

HS256 or RS256? HS256 uses one shared secret to sign and verify, so every API that checks tokens could also create them: fine inside one service, wrong across many. Asymmetric algorithms (RS256, ES256) sign with a private key only the issuer has, and verify with a public key anyone can have. Identity providers use asymmetric signatures for exactly that reason.

3.6Expiry, refresh and revocation

A self-contained token can't be taken back: every API that trusts the signer will accept it until exp. So the main defence is a short life. But nobody wants to sign in every ten minutes. The standard answer is two tokens:

  • An access token: self-contained, sent with every API call, short-lived (5–15 minutes).
  • A refresh token: opaque, sent only to the identity provider to get a new access token, longer-lived, and recorded server-side, so it can be revoked.

Refresh token rotation issues a new refresh token every time one is used, and treats a second use of an old one as theft: it revokes everything descended from that sign-in. Combine that with short access tokens, and you have revocation that works within minutes:

  • Sign out revokes this device's refresh token.
  • Sign out everywhere, password change and account lock revoke all of the user's refresh tokens.
  • If you need faster than the access token's lifetime, keep a small denylist of revoked token IDs (jti) or a per-user “sessions valid after” time, and check it on sensitive actions such as payments.

Key idea

A token you can't take back must die young. Keep the power to end a session in something you can revoke.

At Larder: solved

Refresh tokens rotate on every use, with reuse detection, and expire after 30 days without use. A password change, “sign out everywhere” (new, under Account → Devices, which lists every signed-in device) and an account lock all revoke every refresh token. And paying with a saved card checks a per-customer “sessions valid after” time, so a revoked phone can't order even in its last ten minutes.

Replayed against the new design, Tuesday's theft ends within ten minutes of the password change, and the thief's next refresh fails.

3.7Where tokens should live

  • Browsers: keep tokens out of JavaScript's reach. Storing an access token in localStorage means any injected script can read and send it. The safer pattern is a backend for frontend: the browser holds only an HttpOnly session cookie for your own server, which holds the tokens and calls the APIs.
  • Mobile apps: the platform's secure storage (Keychain on iOS, Keystore-backed storage on Android), never plain preferences or files.
  • Servers and workloads: in memory, fetched from the platform when needed (Chapter 15), not in environment files committed to Git.
  • Never in URLs (they end up in logs, browser history and the Referer header), and never logged in full. If you must log one, log its jti or a hash.

# tokens.py · make and check a JSON Web Token (HS256) with the standard library
import base64, hashlib, hmac, json, time

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def unb64url(text):
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))

def encode(part):
    return b64url(json.dumps(part, separators=(",", ":")).encode())

def sign(claims, key):
    signing_input = encode({"alg": "HS256", "typ": "JWT"}) + "." + encode(claims)
    signature = hmac.new(key, signing_input.encode(), hashlib.sha256).digest()
    return signing_input + "." + b64url(signature)

def verify(token, key, issuer, audience, now=None, leeway=30):
    now = time.time() if now is None else now
    try:
        h64, p64, s64 = token.split(".")
        header, claims = json.loads(unb64url(h64)), json.loads(unb64url(p64))
    except ValueError:
        return "rejected: malformed"
    if header.get("alg") != "HS256":                  # an allow-list; never obey the header
        return f"rejected: alg {header.get('alg')}"
    expected = hmac.new(key, f"{h64}.{p64}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(expected, unb64url(s64)):
        return "rejected: bad signature"
    if claims.get("iss") != issuer:
        return "rejected: wrong issuer"
    if claims.get("aud") != audience:
        return "rejected: wrong audience"
    if now > claims.get("exp", 0) + leeway:
        return "rejected: expired"
    scope = f" may {claims['scope']}" if "scope" in claims else ""
    return f"ok: {claims['sub']}{scope}"

At Larder

On Tuesday 1 December 2026, Korenwolf's finance team emailed Mo, Larder's key account manager. Their expense system, a SaaS product called Spendwise, could import supplier invoices automatically. Mo forwarded it to Eli with one line: “Is this OK?” It isn't. Spendwise would hold a password that can also place and cancel orders, change delivery addresses and see every office's history. It would work until the office manager changed jobs, and then break, or keep working for someone who's gone. The problem has a standard answer, and section 4.9 shows Larder adopting it.

4.1The problem: access without the password

Spendwise's request is the password anti-pattern: one application asks for your password to another. It gives the app everything you can do, for as long as the password lasts, and you can't take it back from that app alone. It also teaches people to type passwords into other sites, which is exactly what phishing relies on (Chapter 2).

OAuth 2.0 (RFC 6749) solves delegated authorisation: letting an application act on your behalf, with limited permissions, without ever seeing your password. You sign in at the service that holds your data, approve exactly what the app may do, and the app receives a token for that and nothing more. You can revoke it at any time without changing your password.

OAuth on its own says nothing about who you are; it's about what an app may do. OpenID Connect (OIDC) is a thin layer on top that adds sign-in: it tells the app who authenticated. Section 4.6 separates them.

4.2Four roles

Every OAuth integration has the same four parties. Name them first, and the rest of the protocol makes sense:

Table 4.1 · The four OAuth roles, in the Spendwise case

Clients also come in two kinds, and the difference matters for every flow. A confidential client runs on a server and can keep a secret (a client secret or a private key) to authenticate itself to the authorization server; Spendwise is one. A public client runs on the user's device (a single-page app, a mobile app, a CLI) where anything it contains can be extracted, so it can't keep a secret.

4.3The authorization code flow with PKCE

The flow you'll use for nearly every app that acts for a person is the authorization code flow, with PKCE (Proof Key for Code Exchange, pronounced “pixie”, RFC 7636). It's worth learning step by step:

Each parameter is there to stop a specific attack:

  • redirect_uri: where the code is sent. The authorization server must compare it exactly with the URIs registered for this client. A loose match (any path, any subdomain) lets an attacker send codes to a page they control.
  • state: a random value the client stores and checks when the browser returns. It ties the response to the request this browser started, which stops an attacker from injecting their own code into your session (a form of CSRF).
  • code: a one-time, short-lived (seconds to minutes) reference to the grant, safe to pass through the browser because it's useless on its own.
  • code_verifier and code_challenge: PKCE. The client makes a random verifier, sends only its SHA-256 hash (the challenge) in step ①, and reveals the verifier only on the back channel in step ⑤. Someone who steals the code from a redirect, a log or a malicious app on the same phone can't redeem it without the verifier.

Key idea

Use the authorization code flow with PKCE for every client that acts for a person: web, mobile, single-page or CLI, public or confidential.

PKCE was invented for mobile apps, which can't keep a client secret, but current guidance (OAuth 2.0 Security Best Current Practice, RFC 9700, and the upcoming OAuth 2.1) recommends it for confidential clients too, because it also protects against code injection. Confidential clients additionally authenticate at the token endpoint with their secret or, better, a signed assertion with a private key.

4.4Scopes and consent

A scope names a slice of access the client asks for: invoices:read, orders:write, openid. The authorization server shows the requested scopes on a consent screen, the user approves them (or a company administrator approves them for everyone), and the access token carries only the approved ones. The API must check the scope on every request, in addition to its own rules about the user: a token with invoices:read for an office manager lets the client read that manager's invoices, not anyone's.

Good scope design is coarse enough to understand on a consent screen and fine enough that common integrations need little: separate read from write, and money-moving actions from everything else. Ask for the minimum, and ask for more later when a feature needs it (incremental consent).

Consent phishingAttackers register real OAuth apps with convincing names and ask for broad scopes, such as reading all mail. Nothing is stolen; the user grants it. Companies limit which apps employees may approve, and review granted apps (Chapter 23).

4.6OpenID Connect: adding sign-in

People used OAuth for sign-in long before it was designed for it: “if this token can read my profile, I must be this person”. That's unsafe, because an access token says what a client may do, not who logged in to this client; a token issued to another app could be replayed. OpenID Connect fixes this by adding:

  • The openid scope, which asks for sign-in.
  • An ID token: a JWT for the client, saying who authenticated, when and how. Its aud is the client's own ID.
  • A nonce, sent in step ① and returned inside the ID token, so the client can check the token was made for this sign-in.
  • A UserInfo endpoint for extra profile details, and discovery: every OIDC provider publishes its endpoints, supported features and signing keys (JWKS) at /.well-known/openid-configuration.

4.7The security checklist

  1. Authorization code with PKCE for every client acting for a person. No implicit, no password grant.
  2. Exact redirect URI matching, registered per client; HTTPS only (or the platform's app-link schemes on mobile).
  3. state and nonce generated per request, stored, and checked.
  4. Mobile and desktop apps use the system browser, not an embedded web view, so the app can't read the password and the user's existing session (and passkeys) work.
  5. Minimal scopes, checked by the API on every call, together with its own rules about the user.
  6. Short access tokens, rotating refresh tokens (Chapter 3), revoked when the user disconnects the app.
  7. Validate tokens with a maintained library, configured with the issuer, audience and algorithms.

5.1What federation is for

Federation is an agreement between two systems: one authenticates people, the other accepts its word. The person signs in once, with the account their organisation manages, and gets into applications run by someone else. Everyone gains something:

  • The person has one login and one set of factors, instead of a password per supplier.
  • Their organisation keeps control: it decides who may use the app, enforces its MFA rules, and ends access by disabling one account.
  • The application stores no passwords for these people, and doesn't run their resets.

The same idea runs inside your own company: employees sign in to the AWS console, Slack and Jira through one identity provider (Chapter 12). And it works between machines, when a CI system's token is accepted by a cloud (Chapter 17). This chapter is about people and SAML; the principles carry over.

5.2Identity providers, service providers and metadata

SAML has two roles. The identity provider (IdP) authenticates the person and issues a signed statement about them: Korenwolf's Microsoft Entra ID. The service provider (SP) is the application that relies on it: Larder's login service. (OpenID Connect calls the SP a relying party.)

Before anyone signs in, the two exchange metadata, an XML document each publishes about itself. It's how trust is written down (Chapter 1, 1.6):

Certificates expire, and an unnoticed expiry stops every sign-in at once, so put the date in a calendar and agree how rollovers will work (most IdPs can publish the next certificate in advance).

5.3A sign-in, step by step

SAML moves messages through the user's browser, using redirects and auto-submitting HTML forms; the IdP and SP never talk directly during a sign-in. The usual flow starts at the application, so it's called SP-initiated:

Prefer SP-initiated; if you must accept IdP-initiated, keep validity windows short and keep a replay cache.

The SAML response carries an assertion: the IdP's signed statement about the person. Strip away the namespaces and it reads quite naturally:

Two details deserve attention:

  • The NameID identifies the person to this SP. Prefer a persistent format, an opaque ID that never changes for this person and this SP. An email address as NameID breaks when someone marries and changes their name, and can be reassigned to a new employee later. Together with the issuer, the NameID is the key for the account, like iss + sub in OIDC.
  • Attributes are whatever the IdP is configured to release: names, email, department, group memberships. The SP should ask for the minimum, and treat each one as a claim made by the IdP, which is only as trustworthy as the IdP's own data.

5.5Checking an assertion

A SAML response arrives as a form post from a browser, which anyone can make. Before trusting it, the SP must check:

  1. Signature: the assertion (or the whole response) is signed, the signature is valid, and it was made with the certificate from this IdP's metadata, not one embedded in the message.
  2. Issuer: exactly the IdP this connection trusts.
  3. Audience: your SP's entity ID.
  4. Recipient and destination: your ACS URL for this connection.
  5. Time: now is between NotBefore and NotOnOrAfter, with a small allowance for clock differences.
  6. InResponseTo: answers a request you sent and haven't seen answered.
  7. One use: the assertion ID hasn't been seen before (keep a cache until its expiry).
  8. Then your own rules about what this IdP may say (5.7), and map the attributes to the account.

Watch out: never write your own SAML validation

XML signatures sign a part of a document, identified by an ID. In signature wrapping attacks, the attacker keeps the validly signed part where the signature check finds it, and adds a second, unsigned assertion where the application reads its data. Code that checks one element and reads another is fooled. These bugs keep reappearing, even in mature libraries. Use a well-maintained SAML library or, better, a managed identity service, and keep it updated.

5.7How far to trust a partner's IdP

Here is the question that kept Eli busy. Once Larder trusts assertions signed by Korenwolf's IdP, those assertions can say anything: any email address, any group, any office. A misconfiguration at Korenwolf, a malicious administrator there, or an attacker who takes over their IdP could produce a perfectly signed assertion for eli@larder.example, or for an office manager at a different Larder business customer. The signature proves who said it, not that it's true.

Key idea

A federated IdP should only be able to vouch for its own people, inside its own organisation's account, with the attributes you need, and nothing more.

In practice, that means four rules on the SP side:

  1. Bind the connection to one tenant. Accounts created through Korenwolf's connection belong to Korenwolf's business account, always. No attribute in an assertion can move someone into another customer's account, or into Larder's staff tools.
  2. Bind it to the organisation's domains. Only email addresses at domains Korenwolf has proved it owns (korenwolf.example) are accepted from it. An assertion naming any other domain is rejected, however well signed.
  3. Key accounts on issuer + NameID, never on email alone, so an account can't be claimed by another IdP that asserts the same address.
  4. Ask the IdP to filter, and check anyway. Korenwolf assigns the Larder app only to its office managers' group, so other staff never get an assertion. Larder also requires that group in the assertion, so a mistake on one side isn't enough.

Then decide how accounts appear and disappear. With just-in-time provisioning, the SP creates the account at the first successful sign-in from the assertion's attributes; simple, but the SP never hears that someone left, only that they stopped signing in. With SCIM, the IdP pushes creations, changes and removals to the SP as they happen (Chapter 13). Either way, keep the SP's sessions short, because disabling someone at the IdP doesn't end a session they already have at the SP.

6.1The access matrix

Every access model is a way of writing down one big table: principals down the side, resources across the top, and in each cell the actions that principal may perform on that resource. This is the access control matrix. Nobody stores it whole (it would be enormous and mostly empty), but every model is a compression of it.

6.2Access control lists

An access control list (ACL) stores the matrix by column: each resource carries a list of who may do what to it. File permissions are ACLs; so are sharing settings on a document (“Anna can edit, the team can comment”). ACLs are easy to understand for one resource, and answer “who can reach this file?” instantly.

They're hard to manage at scale. “What can Aylin reach?” means reading every ACL in the system, and when Aylin changes jobs, someone must find and edit each one. They suit cases where the owner of each resource genuinely decides who shares it, as in document sharing, and little else.

S3 ACLsS3 still supports per-object ACLs from its early days, but new buckets have them switched off (Object Ownership: “bucket owner enforced”). AWS's advice, and this book's, is to keep them off and use policies (Chapter 9).

6.3Roles

Role-based access control (RBAC) adds a layer: permissions are granted to roles named after jobs (“store manager”, “picker”), and people are assigned roles. When someone changes job, you change their roles, and every permission follows. RBAC is the most widely used model, and for good reason: roles match how organisations already think, and “who has the store manager role?” is an easy question to answer and review.

RBAC goes wrong in two familiar ways:

  • Role explosion. Roles start as jobs, then pick up a second dimension: a job at a store, in a team, for a customer. Every new store multiplies the roles. Larder's four jobs times three stores is 12 roles; times twelve stores it's 48, before any exceptions. Soon nobody knows what noord-lead-2 was for.
  • Privilege creep. People collect roles as they cover, move and help out, and roles are rarely taken away, because nobody notices extra access until it's misused. Tomás's Zuid role is a textbook case. Regular access reviews (Chapter 13) and assignments that expire are the cures.

Good role design keeps roles about what a job does, and moves where or for whom into something else: attributes or relationships.

6.4Attributes

Attribute-based access control (ABAC) writes rules over attributes of the principal, the resource, the action and the context:

allow if  action in permissions_of(principal.job)
     and  resource.store in principal.stores
     and  context.time is within the principal's shift

One rule replaces every “job at store” role. Add Utrecht, and nothing in the rules changes: Utrecht's staff get stores = {utrecht} from the HR system, and Utrecht's stock items carry store = utrecht. You've already seen ABAC in AWS: comparing a principal tag with a resource tag (Chapter 9, 9.6) is exactly this.

ABAC has its own costs:

  • Auditing gets harder. “Who can adjust Zuid's stock?” is no longer a list you can read; you have to evaluate the rule against every person's attributes.
  • Attributes become security data. Whoever can change someone's stores attribute, or a resource's tag, can change access. Attributes must come from a trustworthy source (the HR system, not a free-text field users can edit) and be protected like permissions.
  • Missing attributes need a safe default. A resource without a store attribute should be denied, not open to everyone.

6.5Relationships

Some access follows from how things relate. A Korenwolf office manager may see their office's orders; Korenwolf's Head of Workplace may see the orders of every office in her organisation; a document is visible to members of the folder it's in. Neither roles nor attributes say this naturally. Relationship-based access control (ReBAC) stores facts as relationships (“Rotterdam office has manager J. de Vries”, “order B-1042 belongs to the Rotterdam office”) and answers questions by following them.

ReBAC is how large sharing systems work: Google described its global authorisation system, Zanzibar, which stores trillions of such relationships for Drive, YouTube and Cloud; open-source systems such as OpenFGA and SpiceDB follow the same design. It suits multi-tenant products with organisations, teams, folders and sharing. It needs a place to store the relationships, kept in step with your application's data.

6.6Principles that apply to every model

  • Least privilege: each principal gets the access its job needs, and no more, for no longer than needed. Every model can express it; only discipline achieves it.
  • Default deny: no rule, no access (Chapter 1). Missing attributes and broken relationships deny.
  • Separation of duties: split powerful tasks so one person can't complete them alone. The person who adds a supplier shouldn't approve its payments; the engineer who writes a production change shouldn't be the only reviewer.
  • Deny overrides: a small number of explicit “never” rules (no one deletes backups; nothing leaves the EU) that win over any allow. AWS builds this into policy evaluation (Chapter 10).
  • Time limits: temporary needs get access that expires by itself. Tomás's July cover should have ended in July without anyone remembering.

Watch out: checking the action but not the object

The most common authorisation bug in web APIs isn't a wrong role; it's checking that a user may “view orders” and then returning whichever order ID they ask for. Change /orders/1042 to /orders/1043 and you see someone else's. OWASP ranks this, broken object-level authorisation, as the number one API security risk. Every request for a specific object must check that this principal may access this object, which is exactly the question ABAC and ReBAC ask.

7.1What an account is

An AWS account is a container for resources, identities and a bill. Each has a 12-digit account ID (111122223333 in this book's examples) and is isolated from every other account by default:

  • Resources: a bucket, database or VPC belongs to exactly one account.
  • Identities: IAM users and roles exist inside one account, and by default can only touch that account's resources.
  • Permissions: nothing crosses an account boundary unless both sides allow it (Chapter 10, Chapter 21).
  • Quotas and billing: limits (such as the number of VPCs) and costs are per account.

That makes the account AWS's strongest security boundary, which is why companies use many of them: one per environment, per team, per workload (Chapter 20). A mistake or a breach in the development account then can't reach production. Larder has two: Jasper's original account, which runs production (and still holds the network hub from Handbook 1), and a second account for development and staging that Eli opened in 2025. They aren't part of an organisation yet.

Is an account ID secret?No: it appears in every ARN, and AWS doesn't treat it as a secret. But it tells an attacker which account to target, so don't publish it needlessly. Never rely on its secrecy.

7.2The root user

When you create an account, you give an email address and a password. That pair is the root user: an identity with complete, unrestricted access to everything in the account. Three properties make it special:

  • IAM policies can't limit it. There's no policy you can attach to root. The only thing that restricts a root user is an organisation-level guardrail (an SCP) when the account is a member of an AWS Organization (Chapter 20).
  • It can do a few things no one else can (Table 7.1).
  • It's tied to an email address, and whoever controls that mailbox can reset the password.

7.3Locking it away

Because it can't be limited, the root user must be impossible to use casually and hard to steal. The checklist:

  1. No access keys. Root keys give unlimited programmatic access and can't be restricted. Delete any that exist, after checking when they were last used and by what.
  2. Phishing-resistant MFA, more than one device. Register two or more FIDO2 security keys or passkeys (an account's root user can have up to eight MFA devices), kept in different places. AWS now requires MFA for root users in most accounts.
  3. A long, random password in the company's password vault, ideally readable only by two people together.
  4. A company-owned email address that's a group, such as aws-root@larder.example, delivered to several trusted people. Never a personal address, and never one person's work mailbox, which disappears when they leave.
  5. A company-owned phone number as the account's primary contact, because AWS uses it to verify you during recovery (7.4).
  6. Alternate contacts for billing, operations and security, so AWS's security notices reach a team, not a former employee.
  7. Alerts on root sign-in. Any use of root should page someone (Chapter 23). If root is used, it should be because you planned to.

Key idea

Treat the root user like the deeds to a building: kept safe, owned by the company, needed rarely, and missed immediately if anyone touches them.

7.4Getting root back

Root access is lost more often than it's stolen: the person who set it up leaves, a phone is replaced, a mailbox is closed. AWS's recovery paths all depend on the account's contact details, which is why 7.3 insists they belong to the company:

  • Lost password: “Forgot password” on the root sign-in page sends a reset link to the root email address.
  • Lost MFA device: the sign-in page offers to sign in with alternative factors: AWS verifies the root email address, then calls the account's primary contact phone number.
  • Lost email or phone too: AWS Support can help, but expect identity checks and time.

Watch out: root on someone's personal email

If the root email is a founder's personal address, or a freelancer's, that person owns your account in every way that matters. They can reset the password, and you can't. Moving root to a company group address is one of the first jobs in any AWS account review.

7.5Seeing every credential: the credential report

The credential report is a CSV file listing every IAM user in the account, plus the root user, with the state of each credential: whether a password is set and when it was last used, whether MFA is on, and for each access key when it was created and last used, in which region and for which service. It's generated on request (at most once every four hours) and is the fastest way to see what's lying around in an account. The lab reads one.

Two other quick views help: aws iam get-account-summary reports whether the root user has MFA (AccountMFAEnabled) and access keys (AccountAccessKeysPresent); and the IAM console's dashboard shows the same as security recommendations.

7.6Root in an organisation

When accounts belong to an AWS Organization (Chapter 20), root works differently:

  • The management account, which pays for and governs the organisation, has a root user that nothing can restrict. Secure it most carefully of all, and run no workloads in that account.
  • The root users of member accounts are limited by service control policies, like every other principal there.
  • With centralised root access, the organisation can remove root credentials (password, keys, MFA) from member accounts entirely. When a root-only task is needed, such as unlocking a bucket policy that denies everyone, an administrator in the management account performs it through a short-lived, task-scoped root session (sts:AssumeRoot). New member accounts then never have root credentials at all.

Azure and Google Cloud have no single “root user” per subscription or project, but they have the same problem one level up: a few all-powerful administrator identities that must be locked away and never lost.

8.1IAM users

An IAM user is a long-lived identity inside one account. It can have a console password and up to two access keys for the CLI and SDKs. An access key is a pair: an access key ID starting with AKIA, and a secret access key, shown once when it's created. Two keys are allowed so you can rotate: create the new one, switch everything to it, then delete the old.

Users get permissions from policies attached to them directly or, better, to groups they belong to.

8.2Groups

An IAM group is a set of users that share policies: attach a policy to developers, and every user in it gets those permissions. Groups are simple, with three limits worth knowing: a group isn't a principal (you can't name it in a trust or resource policy, or sign in as it); groups can't contain other groups; and they only hold IAM users, not roles or federated people. Groups in your identity provider are a different thing, and much more useful (Chapter 12).

8.3Why users are a legacy pattern

IAM users were AWS's original answer to “how do people get in?”, and they still work. But they carry every problem from Part I:

  • Long-lived credentials. Passwords and access keys last until someone deletes them. Larder's credential report shows the result: a key two and a half years old, and three more belonging to people who've left (Chapter 3).
  • One account at a time. A user exists in one account. With ten accounts, a person needs ten users, ten passwords and ten MFA devices, or you build cross-account roles anyway.
  • A separate directory. Joiners and leavers in your company's directory don't reach IAM. Someone must remember to create and delete users by hand (Chapter 13).

The modern answer is: people sign in through IAM Identity Center or another identity provider and get temporary role sessions (Chapter 12); workloads on AWS use roles provided by the platform (Chapter 15); workloads outside AWS exchange their own platform's tokens for role sessions (Chapter 17). An IAM user is acceptable only where nothing else works: a third-party tool that can only take an access key, or an emergency break-glass account (Chapter 14), and then with a narrow policy, monitoring and rotation.

8.4Roles

An IAM role is an identity with permissions but no credentials of its own: no password, no access keys. Instead, trusted principals assume it and receive temporary credentials for a session. A role is defined by two kinds of policy, and keeping them apart is most of the battle:

  • The trust policy is a resource-based policy on the role itself. Its Principal names who may call sts:AssumeRole (or its web identity and SAML variants) on this role, and its conditions say under what circumstances.
  • The permission policies are ordinary identity-based policies (Chapter 9): what a session of this role may do.

Roles serve every kind of principal from Chapter 1: people (through single sign-on or, as at Larder this month, from IAM users), AWS services acting for you (an ECS task, a Lambda function), pipelines outside AWS, and principals in other accounts.

8.5Assuming a role

Assuming a role is an API call to AWS STS, the Security Token Service:

aws sts assume-role \
  --role-arn arn:aws:iam::111122223333:role/prod-operator \
  --role-session-name eli \
  --source-identity eli

STS checks the trust policy and the caller's own permissions (Chapter 10), and returns temporary credentials:

{
  "Credentials": {
    "AccessKeyId": "ASIAQEXAMPLE7RTHUNA",
    "SecretAccessKey": "…",
    "SessionToken": "IQoJb3JpZ2luX2VjE…",
    "Expiration": "2026-12-07T10:42:13+00:00"
  },
  "AssumedRoleUser": {
    "Arn": "arn:aws:sts::111122223333:assumed-role/prod-operator/eli"
  },
  "SourceIdentity": "eli"
}

Things to notice:

  • Temporary keys start with ASIA, long-lived ones with AKIA. Seeing AKIA in a log or a leak tells you a long-lived key is involved.
  • All three parts are needed: key ID, secret and session token. Tools pass them as AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY and AWS_SESSION_TOKEN.
  • The session expires: by default after one hour; you can ask for 15 minutes up to the role's maximum session duration, which you set between 1 and 12 hours.
  • The session has its own ARN: assumed-role/role-name/session-name. That's what CloudTrail records, so choose session names that identify the person or job.
  • Source identity is a value set when the role is first assumed, which can't be changed afterwards and is recorded in CloudTrail for every action in the session, even across further role assumptions. It's how you keep Chapter 1's accountability when people share a role.
Role chainingUsing a role session to assume another role is called role chaining. AWS limits chained sessions to one hour, whatever the maximum session duration says.

8.6Writing trust policies

A trust policy has the same grammar as any policy (Chapter 9), with a Principal and an action from STS. The principal says what kind of thing may assume the role:

Table 8.1 · Who can be trusted to assume a role
PrincipalExampleMeaning
A specific user or role{"AWS": "arn:aws:iam::111122223333:user/eli"}exactly that identity
An account{"AWS": "arn:aws:iam::111122223333:root"}any principal in that account whose own policies allow it; the account's administrators decide who
An AWS service{"Service": "ecs-tasks.amazonaws.com"}that service, acting for you (8.7)
A federated provider{"Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"}people or workloads authenticated by that SAML or OIDC provider (Chapter 5, Chapter 17)

Despite the name, arn:aws:iam::111122223333:root in a principal doesn't mean the root user. It means “the account”, handing the decision to that account's IAM policies. Conditions then narrow the trust:

prod-operator-trust.jsontrust policy

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "EngineersWithMfaAndTheirOwnName",
    "Effect": "Allow",
    "Principal": { "AWS": [
      "arn:aws:iam::111122223333:user/ben",
      "arn:aws:iam::111122223333:user/eli"
    ] },
    "Action": ["sts:AssumeRole", "sts:SetSourceIdentity"],
    "Condition": {
      "Bool": { "aws:MultiFactorAuthPresent": "true" },
      "StringEquals": { "sts:SourceIdentity": "${aws:username}" }
    }
  }]
}

Read aloud: “Allow Ben's and Eli's users to assume this role, only if they signed in with MFA, and only if they set the source identity to their own user name.” The last condition stops anyone from recording a colleague's name. Other conditions you'll meet: sts:ExternalId for third parties (Chapter 21), aws:SourceAccount and aws:SourceArn for services (8.7), and the sub and aud claims of OIDC tokens (Chapter 17).

Watch out: trust that's too wide

"Principal": {"AWS": "*"} without strong conditions lets any AWS account in the world try to assume your role. Trusting another company's whole account trusts every administrator they have. And trusting a federated provider without conditions on which identities (such as which GitHub repository) lets anyone that provider authenticates in. A role's permissions are only as safe as its trust policy.

8.7Roles for AWS services, and iam:PassRole

Many services act for you: an ECS task reads from S3, a Lambda function writes to DynamoDB, CloudFormation creates resources. Each does it by assuming a role you give it:

  • A service role is an ordinary role whose trust policy names the service (ecs-tasks.amazonaws.com, lambda.amazonaws.com). You write its permissions.
  • An instance profile is the wrapper that lets an EC2 instance use a role (Chapter 15).
  • A service-linked role is created and managed by a service for its own needs, with a fixed policy. You can see it but not edit it.

Handing a role to a service is itself a permission: iam:PassRole. Whoever can launch a task and pass any role can run code with that role's permissions, including an administrator role. That's one of the classic ways to escalate privileges in AWS. Limit it to the roles a person or pipeline actually needs to pass, and to the service that should receive them:

{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/dispatch-task",
  "Condition": { "StringEquals": { "iam:PassedToService": "ecs-tasks.amazonaws.com" } }
}

Service role trust policies should also say which of your resources may use them, with aws:SourceAccount or aws:SourceArn, so a service acting for someone else can't be tricked into using your role (the “confused deputy” of Chapter 21).

8.9Changing roles from the console

People with IAM users can also switch role in the AWS console: the console assumes the role for them, with MFA if the trust policy requires it, and shows the role's name in the top bar. A CLI profile does the same:

[profile prod-operator]
role_arn = arn:aws:iam::111122223333:role/prod-operator
source_profile = eli
mfa_serial = arn:aws:iam::111122223333:mfa/eli-phone
role_session_name = eli

The CLI then asks for a six-digit code before assuming the role. One limit to know: MFA for API and CLI calls accepts only one-time-code devices (an authenticator app or a hardware TOTP token), not FIDO2 security keys or passkeys, which work for console sign-in only. With single sign-on (Chapter 12), this whole step disappears: people sign in once, with whatever factor the identity provider requires, choose an account and a permission set, and get a role session directly.

9.1What a policy is

An IAM policy is a JSON document that allows or denies actions on AWS resources. Every request to AWS (an API call from the console, the CLI, an SDK or another AWS service) is checked against the policies that apply to it, and AWS answers allow or deny before anything else happens.

Policies come in two main families, depending on what they're attached to:

  • An identity-based policy is attached to a user, a group or a role, and says what that identity may do. “Dispatch's role may read objects under config/.” Most of this chapter is about these.
  • A resource-based policy is attached to a resource, such as an S3 bucket, a KMS key or an SQS queue, and says who may use it. “This bucket may be read by the Dispatch role.” These matter most when access crosses accounts (Chapter 21).

Both use the same grammar. Two rules decide what an unlucky combination of them means, and they're worth learning before anything else:

Key idea

Nothing is allowed until a statement allows it, and an explicit deny beats any allow.

There are more policy types (permission boundaries, session policies, and the organisation-wide guardrails called SCPs and RCPs), and the full order in which AWS combines them is the subject of Chapter 10. For now, one identity and its policies are enough.

9.2Anatomy of a statement

A policy is a Version and a list of statements. Each statement is one rule. Here is the smallest useful policy, with one statement:

read-config.jsonidentity-based policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadConfig",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::larder-dispatch-prod/config/*",
      "Condition": { "Bool": { "aws:SecureTransport": "true" } }
    }
  ]
}

Field by field:

  • Version is the version of the policy language, not of your policy. Always write "2012-10-17". The only older value, "2008-10-17", doesn't understand policy variables (9.6), and leaving Version out means the old one.
  • Sid (statement ID) is an optional label. Use it: ReadConfig tells the next reader why the statement exists, and it shows up in some tools' output.
  • Effect is Allow or Deny.
  • Action is one action or a list of them (9.3).
  • Resource is one ARN or a list of them (9.4).
  • Condition is optional and narrows when the statement applies (9.5).
  • Principal appears only in resource-based policies and trust policies, because an identity policy's principal is whoever it's attached to.
Reading habitBefore you approve any policy change, read each statement aloud in the form “Allow / Deny actions on resources, when conditions.” Vague sentences (“allow everything on S3”) are the bugs.

When a policy has several statements, they are not checked in order. Every statement that matches the request counts, and the two rules from 9.1 combine them: any matching Deny wins; otherwise any matching Allow allows; otherwise the request is denied.

9.3Actions

An action names one API operation, written service:Operation: s3:GetObject, secretsmanager:GetSecretValue, ec2:StartInstances. The prefix is the service's short name, and action names are case-insensitive (s3:getobject works, but nobody will thank you for it).

You can use * and ? as wildcards. s3:Get* matches every S3 action that starts with Get, and s3:* matches all of them. Wildcards look tidy, but they age badly: when AWS adds a new action whose name happens to match, your policy grants it without anyone reviewing it. s3:Get* already covers dozens of actions today, including reading bucket policies and object ACLs. Prefer listing exact actions; it's a few more lines and every one of them is a decision someone made.

Where do the names come from? The Service Authorization Reference (linked in Going further) lists, for every service, each action, the resource types it accepts, and the condition keys it supports. Keep it open while you write policies. Two surprises it will show you:

  • One API call can need several actions. Copying an object needs s3:GetObject on the source and s3:PutObject on the destination. Reading a secret encrypted with your own KMS key needs secretsmanager:GetSecretValue and kms:Decrypt (Chapter 18).
  • Action names don't always match API names. The S3 API call ListObjectsV2 is authorised by the action s3:ListBucket, and HeadObject by s3:GetObject.

Watch out: NotAction with Allow

NotAction means “every action except these”. In an Allow statement, "NotAction": "iam:*" with "Resource": "*" grants every action in every other service, including all the ones AWS launches next year. It has a narrow legitimate use in Deny statements (“deny everything except these, outside the approved regions”), which you'll meet in Chapter 20. In an Allow, treat it as a bug.

9.4Resources and ARNs

Every AWS resource has an Amazon Resource Name (ARN), a string that identifies it uniquely across all of AWS. The Resource element lists the ARNs a statement applies to, with the same * and ? wildcards as actions. Unlike actions, ARNs are case-sensitive.

The most common mistake in all of IAM lives in the first two rows. A bucket and the objects in it are different resources, and each S3 action works on one of them:

  • s3:ListBucket (list the keys) acts on the bucket: arn:aws:s3:::larder-dispatch-prod.
  • s3:GetObject, s3:PutObject and s3:DeleteObject act on objects: arn:aws:s3:::larder-dispatch-prod/* or a narrower path.

Put ListBucket on the object ARN, or GetObject on the bucket ARN, and the statement simply never matches. AWS doesn't complain when you save it; the request is just denied later.

403, not 404Without s3:ListBucket, asking for an object that doesn't exist returns AccessDenied instead of NoSuchKey: S3 won't tell you what's missing if you aren't allowed to list. That's why “access denied” sometimes really means “typo in the key”.

Finally, some actions don't work on a specific resource at all. s3:ListAllMyBuckets, ec2:DescribeInstances and sts:GetCallerIdentity only accept "Resource": "*"; the Service Authorization Reference shows a blank resource type for them. That's the one legitimate reason to write "*" in a Resource element. If an action does support resource ARNs, use them.

9.5Conditions

Actions and resources say what. A condition says when: only from this network, only over TLS, only in these regions, only for resources tagged with my team. A condition block has three levels: a condition operator, then a condition key (a value AWS knows about the request), then the value or values to compare it with.

Condition keys come in two kinds:

  • Global keys start with aws: and exist for most requests: aws:SourceIp, aws:SecureTransport, aws:RequestedRegion, aws:PrincipalTag/key, aws:ResourceTag/key, aws:PrincipalOrgID (the data perimeter key of Chapter 22).
  • Service keys start with the service's prefix and exist only for some of its actions: s3:prefix for ListBucket, ec2:InstanceType for RunInstances. The Service Authorization Reference lists which keys each action sends.

A missing key fails the check. If a statement has StringEquals on aws:ResourceTag/team and the resource has no team tag, the condition is false and the statement doesn't match. Add IfExists to the operator (StringEqualsIfExists) to mean “check it if it's there, otherwise pass”. Use that carefully: in an Allow, it lets untagged resources through.

Keys with several values. A few keys carry a list rather than one value, such as the tag keys in a tagging request (aws:TagKeys). For them, prefix the operator with ForAnyValue: (at least one value in the request matches) or ForAllValues: (every value in the request matches).

Watch out: ForAllValues and the empty list

ForAllValues is true when every value matches, and if the request has no values at all, every one of none matches: it's true. So an Allow meant as “only these tag keys” also allows a request with no tags. Pair it with a Null check that the key is present, or write the rule as a Deny with ForAnyValue:StringNotEquals.

9.6Policy variables and tags

A policy variable is a placeholder, written ${…}, that AWS fills in from the request when it evaluates the policy. Variables let one policy serve many identities. They work in Resource and in condition values (and need "Version": "2012-10-17").

The classic example gives each IAM user a home folder:

{ "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::larder-scratch/home/${aws:username}/*" }

aws:username only exists for IAM users, and you'll stop using IAM users in Chapter 8 and Chapter 12. With roles, the useful variables are tags. A principal tag is a key-value pair on the role (or passed in from your identity provider when someone signs in), and a resource tag is one on the resource. Compare the two, and one statement covers every team:

team-secrets.jsonattribute-based access control

{
  "Sid": "ReadOwnTeamsSecrets",
  "Effect": "Allow",
  "Action": "secretsmanager:GetSecretValue",
  "Resource": "*",
  "Condition": {
    "StringEquals": { "aws:ResourceTag/team": "${aws:PrincipalTag/team}" }
  }
}

Read aloud: “Allow reading any secret whose team tag equals my own team tag.” Dispatch's role is tagged team=dispatch, so it reads secrets tagged team=dispatch and nothing else; a new team needs a tag, not a new policy. This is attribute-based access control (ABAC) from Chapter 6, and Chapter 12 uses it with single sign-on. It has one catch: whoever can change tags can change access. Protect tagging itself (only the platform team may set team), or ABAC becomes a polite suggestion.

Built-in roles such as Storage Blob Data Reader cover most needs; a custom role is a JSON role definition whose DataActions cover data (reading blobs) and Actions cover management (creating the storage account). Narrowing within a bucket uses an IAM Condition such as resource.name.startsWith("projects/_/buckets/larder-dispatch-prod/objects/config/").

9.9Writing a least-privilege policy: a method

Least privilege (Chapter 6) is easy to agree with and hard to write. This method gets you there without guessing:

  1. List what the code does, in plain words, from the code and its owners: “reads its config file”, “writes tonight's route plans”.
  2. Map each to actions with the Service Authorization Reference. Remember the hidden extras (a kms:Decrypt, a ListBucket).
  3. Narrow the resources to exact ARNs or prefixes. "*" only for actions that accept nothing else.
  4. Add conditions where they're cheap and meaningful: a prefix, a tag, the organisation.
  5. Validate with IAM Access Analyzer (in the lab), which catches typos, impossible combinations and risky patterns before anything is attached.
  6. Test the real workload in a non-production environment, including the things it should not be able to do.
  7. Watch CloudTrail for AccessDenied from the role for a few days after rollout (Chapter 11 shows how).

At Larder: solved

Eli walks the method through Dispatch with Ben's team. Step 1 gives three sentences: Dispatch reads its zone and depot settings from config/; Engine A writes each evening's van route plans to routes/; and Dispatch reads the maps provider's API key. Read aloud, it's four sentences, and each one maps to something Dispatch does. Things worth noticing:

  • No delete. Dispatch overwrites route plans but never deletes them, so a bug or an intruder can't empty the bucket. Old versions are kept by bucket versioning, set on the bucket.
  • Listing is limited to two prefixes by the s3:prefix condition. Listing the whole bucket, or orders/, is denied.
  • The secret's random suffix is matched with ?????? rather than *, so a secret later named maps-api-key-old isn't included by accident.
  • The secret uses the default AWS managed key for Secrets Manager, so no kms:Decrypt statement is needed. With a customer managed key it would be (Chapter 18).

You need the AWS CLI v2, signed in to a sandbox account with administrator access (Appendix C), and a Unix shell.   1. Set up names, a bucket and two files. Bucket names are global, so the name gets a random suffix. orders/ stands in for data Dispatch must never read.

{ "Version": "2012-10-17",
  "Statement": [

Key idea

Allows add up; one deny ends the discussion. Grant with allows, and draw lines that nobody may cross with denies.

Watch out: a guardrail only guards what it's attached to

An identity-based deny protects only from the identities it's attached to. Every user, group and role you forget, including the next one somebody creates, is outside it. That's the gap Marco's question found. Guardrails that must hold for everyone in an account belong one level up, in an SCP (10.8, Chapter 20), or, for resources that support them, in a resource-based policy.

10.4Resource-based policies in the same account

Step ④ is easy to miss. Within one account, if a resource-based policy (a bucket policy, a KMS key policy, a role's trust policy) allows a specific principal, that's enough: the principal doesn't also need an identity-based allow. That's why a trust policy that names user/eli lets Eli assume the role, while one that names the whole account (…:root) also needs Eli's own policies to allow sts:AssumeRole (Chapter 8, 8.6).

It also means resource policies deserve the same review as identity policies: a bucket policy that grants s3:* to a role gives that role full access to the bucket, whatever its identity policies say.

KMS is differentKMS keys are stricter: a key policy must allow access, either directly or by delegating to IAM policies with a statement for the account. Without that, even an administrator can't use the key (Chapter 18).

When the principal and the resource are in different accounts, there's no short cut at step ④. Each account controls its own side, and both must allow:

Assuming a role in another account works the same way: the caller's own account must allow sts:AssumeRole on that role's ARN, and the role's trust policy in the other account must trust the caller. 10.6Permissions boundaries: safe delegation

A permissions boundary is a managed policy set on a user or role as its ceiling: the identity can do only what both its own policies and the boundary allow. It grants nothing by itself.

Boundaries exist to solve one problem well: letting teams create their own roles without letting them create roles more powerful than they should. Without a boundary, anyone allowed to create roles and attach policies can create an administrator role and assume it. With one, you allow role creation only if the new role carries the boundary:

{
  "Sid": "CreateTeamRolesOnlyWithTheBoundary",
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:AttachRolePolicy", "iam:PutRolePolicy"],
  "Resource": "arn:aws:iam::111122223333:role/team-*",
  "Condition": { "StringEquals": {
    "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/team-boundary" } }
}

Pair it with a deny on iam:DeleteRolePermissionsBoundary and iam:PutRolePermissionsBoundary, and on editing the boundary policy itself, or the ceiling can simply be removed. Now a team can create team-reporting with AdministratorAccess attached and it still can only do what team-boundary allows. Put your guardrail denies inside the boundary too, and every role created this way carries them.

10.7Session policies

A session policy is passed when a role session is created (aws sts assume-role --policy … or --policy-arns …). The session gets the intersection of the role's permissions and the session policy. It's how a broker service can hand out one shared role, narrowed per request: “this session may only read tenant-42/”. People rarely write session policies by hand, but they explain some surprising denials, and IAM Identity Center and other services use them behind the scenes.

10.8SCPs and RCPs: the organisation's ceiling

When accounts belong to an AWS Organization (Chapter 20), two more ceilings apply, set centrally:

  • Service control policies limit what principals in member accounts may do, including those accounts' root users. A deny in an SCP applies to every role and user in the account, however created, which closes the gap from 10.3.
  • Resource control policies limit what anyone may do to resources in member accounts, including principals from outside the organisation. They support a growing list of services, starting with S3, STS, KMS, SQS and Secrets Manager.

Neither ever grants anything; by default each account has a policy allowing everything (FullAWSAccess, RCPFullAWSAccess), and you add denies or replace the default with an allow-list. Two exceptions to remember: SCPs and RCPs don't apply to the management account, and SCPs don't restrict service-linked roles.

On Azure

Azure RBAC is additive: a principal's permissions are the union of its role assignments at every scope above the resource, and there's no way for you to write a general-purpose deny. Guardrails come from elsewhere: Azure Policy stops non-compliant resources being created or changed (no public storage accounts, only these regions), and resource locks (CanNotDelete, ReadOnly) protect critical resources from deletion by anyone, owners included.

On Google Cloud

Google Cloud evaluates IAM deny policies first, then the union of allow-policy bindings inherited down the resource hierarchy. Deny policies attach to the organisation, folders or projects and can exempt principals, which makes them the nearest equivalent to an AWS guardrail with an exception. Configuration rules (such as “no external IPs”) are organisation policy constraints, a separate system.

# evaluate.py · AWS policy evaluation logic for one request, simplified for learning
from fnmatch import fnmatchcase

def as_list(x):
    return x if isinstance(x, list) else [x]

def statement_matches(st, req, check_principal=False):
    if not any(fnmatchcase(req["action"].lower(), a.lower()) for a in as_list(st.get("Action", []))):
        return False
    if not any(fnmatchcase(req["resource"], r) for r in as_list(st.get("Resource", "*"))):
        return False
    if check_principal:
        allowed = as_list(st.get("Principal", {}).get("AWS", []))
        account_root = f"arn:aws:iam::{req['principal_account']}:root"
        names = {req["principal"], req["context"]["aws:PrincipalArn"], account_root, "*"}
        if not names & set(allowed):
            return False
    for op, tests in st.get("Condition", {}).items():
        for key, want in tests.items():
            have = req["context"].get(key)
            if op == "StringEquals" and have not in as_list(want):
                return False
            if op == "StringNotLike" and (have is None or any(fnmatchcase(have, w) for w in as_list(want))):
                return False
            if op == "Bool" and str(have).lower() != str(want).lower():
                return False
    return True

def decide(req, identity=(), resource=None, boundary=None, session=None, scp=None, rcp=None):
    policies = {"identity-based policy": identity, "resource-based policy": resource or [],
                "permissions boundary": boundary or [], "session policy": session or [],
                "SCP": scp or [], "RCP": rcp or []}
    def hits(kind, effect):
        return any(st["Effect"] == effect and statement_matches(st, req, kind == "resource-based policy")
                   for st in policies[kind])
    for kind in policies:                                         # 1. any explicit deny wins
        if hits(kind, "Deny"):
            return f"DENY   explicit deny in {kind}"
    if rcp is not None and not hits("RCP", "Allow"):              # 2. RCPs must allow
        return "DENY   no RCP allows it"
    if scp is not None and not hits("SCP", "Allow"):              # 3. SCPs must allow
        return "DENY   no SCP allows it"
    same_account = req["principal_account"] == req["resource_account"]
    by_resource = hits("resource-based policy", "Allow")
    if same_account and by_resource:                              # 4. same account: resource policy is enough
        return "ALLOW  by resource-based policy"
    if not hits("identity-based policy", "Allow"):                # 5. identity policy must allow
        return "DENY   no identity-based policy allows it"
    if boundary is not None and not hits("permissions boundary", "Allow"):
        return "DENY   permissions boundary doesn't allow it"     # 6. boundary caps it
    if session is not None and not hits("session policy", "Allow"):
        return "DENY   session policy doesn't allow it"           # 7. session policy caps it
    if not same_account:                                          # cross-account needs both sides
        return ("ALLOW  identity- and resource-based policies both allow it" if by_resource
                else "DENY   cross-account: no resource-based policy allows it")
    return "ALLOW  by identity-based policy"

    The identity policy protects only from the identities it's attached to; any other or new identity bypasses it. An SCP applies to every principal in the member account, however it was created, including the root user.

  5. Design a way for Larder's product teams to create roles for their own services without being able to give themselves more power than the platform team allows. design

    Show answer

    A team-boundary policy with the services teams may use and the guardrail denies. Teams may create and modify roles named team-* only with that boundary (condition on iam:PermissionsBoundary), may pass only team-* roles, and are denied removing or changing boundaries and editing the boundary policy itself.

  6. Compare how you'd stop anyone deleting a production database on AWS and on Azure. compare

    Show answer

    AWS: an explicit deny on the delete action (in an SCP to cover everyone, with an exception for a break-glass role), plus RDS deletion protection. Azure: a CanNotDelete resource lock, which blocks deletion even by owners until someone with permission removes the lock, and Azure Policy for configuration rules.

  • Azure: resource locks. Google Cloud: IAM deny policies.

11.1A method

“Access denied” is a symptom, and like any symptom it has several possible causes. Guessing (adding permissions until it works) usually fixes it by granting far more than needed, and sometimes doesn't fix it at all, because the cause was never a missing permission. Work through it in order:

  1. Who am I? Confirm the exact principal making the call: which role, which session, which account (11.2).
  2. What exactly was asked? The action, the resource ARN, the region. Not “S3”: s3:PutObject on arn:aws:s3:::larder-dispatch-staging/routes/2026-12-09/van-1.json.
  3. Read the error all the way to the end. It increasingly names the type of policy that said no (11.3).
  4. Find it in CloudTrail, including any calls made on your behalf by another service (11.4).
  5. Walk the evaluation order from Chapter 10 for that request: deny, RCP, SCP, resource policy, identity policy, boundary, session policy.
  6. Rule out look-alikes: expired credentials, the wrong account or region, clock skew, a missing object (11.6).
  7. Fix the one responsible policy with the smallest change, validate it, and test the original request again (11.7).

Key idea

Find out exactly who asked for exactly what, then let AWS tell you which policy said no. Don't add a permission until you know which one is missing.

11.2Who am I, really?

A surprising share of permission problems are identity problems: the call wasn't made by who you think. Leftover environment variables from an earlier session, a default profile pointing at another account, a container that picked up the node's role instead of its own (Chapter 8, 8.8). Always start with:

aws sts get-caller-identity
{
    "UserId": "AROAEXAMPLEID:engine-a-7f9c",
    "Account": "444455556666",
    "Arn": "arn:aws:sts::444455556666:assumed-role/dispatch-task/engine-a-7f9c"
}

This call always works, whatever your permissions. For code, log the same thing at start-up: the SDK has the same call. Check the account number as carefully as the role name: production and staging roles often share names.

11.4Find it in CloudTrail

CloudTrail records API calls made in your account: who, what, when, from where, and whether it failed. Denied calls are recorded with an errorCode such as AccessDenied or Client.UnauthorizedOperation and, usually, the same errorMessage the caller saw. What to know before you go looking:

  • Management events (creating, changing and deleting resources, and many reads) are recorded by default and searchable for 90 days in the console's Event history or with aws cloudtrail lookup-events, per region.
  • Data events (S3 object reads and writes, Lambda invocations, DynamoDB item calls) are not recorded unless a trail is configured for them, because there are so many. Larder records S3 data events for its production buckets (Chapter 23).
  • Global services such as IAM and STS log in us-east-1 (or the region of the STS endpoint used).
  • Events appear after a delay, typically a few minutes and occasionally up to about 15.

The most useful field for puzzles like Larder's is userIdentity.invokedBy. When S3 needs a KMS key to encrypt an object you upload, S3 calls KMS as you, and CloudTrail records that KMS call with invokedBy: s3.amazonaws.com. If that call is denied, your upload fails with an error from S3, but the cause lives in a different service's event.

11.5Tools that walk the flowchart for you

  • IAM policy simulator (aws iam simulate-principal-policy, or the console): evaluates an existing user's or role's policies for given actions, resources and context keys, and says which statement allowed or denied. It covers identity policies, boundaries and SCPs; resource policies only if you pass them in.
  • IAM Access Analyzer policy validation: catches impossible policies before you blame AWS: misspelled actions, actions that don't support the resource you named (Chapter 9).
  • Last accessed information (in IAM's Access Advisor tab): shows which services a role has actually used, which helps when narrowing a policy without breaking it.

11.7Fixing it well

Once you know which policy said no, the fix is usually one statement. Keep it small:

  • Add the exact action on the exact resource, not a wildcard. If the message says kms:GenerateDataKey on one key, that's what to allow, on that key.
  • Fix it where it belongs. If a guardrail blocked something legitimate, change the guardrail's exception deliberately, or use the approved path (such as Larder's db-change role), rather than removing the guardrail.
  • Sometimes the fix isn't a permission at all. A staging setting that doesn't match production, a request to the wrong region, a missing object.
  • Validate, then repeat the original request. Also try one request that should still fail, so you know you didn't open more than you meant to.
  • Write it down in the commit message or ticket: which call, which reason, which statement changed. The next person will thank you.

Watch out: “just for now” wildcards

A wildcard added to make an error go away under pressure is almost never removed: the error is gone, so nobody looks again. Larder's s3:* on * started exactly that way in April. If you must unblock something urgently, add the narrowest statement you can, with a Sid that says it's temporary and a ticket to replace it.

11.9At Larder: the error was in another service

At Larder: solved

Eli's twenty minutes went like this. Engine A's logs showed the identity was right (dispatch-task, in the staging account). The upload's error ended with the reason in Figure 11.1: the denied action was kms:GenerateDataKey, not anything in S3. CloudTrail in the staging account confirmed it: one denied KMS call per van, each invokedBy: s3.amazonaws.com. The staging bucket, it turned out, had been set in 2025 to encrypt new objects by default with a customer managed KMS key, during an experiment nobody remembered. Production's bucket uses S3-managed keys. The config/ files read fine because the deploy pipeline uploads them with S3-managed encryption explicitly; Engine A's uploads took the bucket's default.

So the policy was right, and staging was wrong. Eli changed the staging bucket's default encryption to match production, the team re-ran the evening's planning, and every route plan was written. Ben's s3:* was never needed. Two follow-ups went on the list: compare staging and production bucket settings automatically, and decide properly whether Larder wants customer managed keys at all (Chapter 18), in which case Dispatch's policy will need kms:GenerateDataKey and kms:Decrypt on that one key.

from collections import Counter

def events(path):
    text = open(path).read().strip()
    if text.startswith("["):                             # aws cloudtrail lookup-events ... --output json
        return [json.loads(x) if isinstance(x, str) else x for x in json.loads(text)]
    if '"Records"' in text[:200]:
        return json.loads(text)["Records"]               # a CloudTrail log file from S3
    return [json.loads(line) for line in text.splitlines() if line.strip()]   # one event per line

def who(e):
    u = e["userIdentity"]
    name = u.get("sessionContext", {}).get("sessionIssuer", {}).get("arn") or u.get("arn", u.get("type"))
    return name + (f" (via {u['invokedBy']})" if "invokedBy" in u else "")

def why(e):
    msg = e.get("errorMessage", "")
    if " because " in msg:
        return msg.split(" because ", 1)[1].split(". Encoded")[0]
    if " with an explicit deny " in msg:
        return "explicit deny " + msg.split(" with an explicit deny ", 1)[1]
    if "Encoded authorization failure message" in msg:
        return "encoded: run aws sts decode-authorization-message"
    return msg or "(no message)"

DENIED = ("AccessDenied", "UnauthorizedOperation", "Forbidden")
counts, first = Counter(), {}

    counts[key] += 1
    first.setdefault(key, e["eventTime"])
