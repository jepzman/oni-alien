OAuth 2.0 and OpenID Connect

“Sign in with…”, “Allow this app to read your calendar?”, a CLI that opens a browser to log you in, a pipeline that deploys to the cloud without a key: all of these are OAuth 2.0 and OpenID Connect. This chapter explains the two standards from the problem they solve, walks through the one flow you'll use most, and gives you the checklist that keeps it safe.

By the end you can

  • Name the four OAuth roles in any real integration.
  • Walk through the authorization code flow with PKCE, and say what each parameter protects against.
  • Choose the right grant for a web app, a mobile app, a CLI and a backend service.
  • Tell an ID token from an access token, and validate each where it belongs.

At Larder

On Tuesday 1 December 2026, Korenwolf's finance team emailed Mo, Larder's key account manager. Their expense system, a SaaS product called Spendwise, could import supplier invoices automatically. All it needed, the email said, was the Larder username and password of one of Korenwolf's office managers, “so it can log in and download the PDFs each month”.

Mo forwarded it to Eli with one line: “Is this OK?” It isn't. Spendwise would hold a password that can also place and cancel orders, change delivery addresses and see every office's history. It would work until the office manager changed jobs, and then break, or keep working for someone who's gone. The problem has a standard answer, and section 4.9 shows Larder adopting it.

4.1The problem: access without the password

Spendwise's request is the password anti-pattern: one application asks for your password to another. It gives the app everything you can do, for as long as the password lasts, and you can't take it back from that app alone. It also teaches people to type passwords into other sites, which is exactly what phishing relies on (Chapter 2).

OAuth 2.0 (RFC 6749) solves delegated authorisation: letting an application act on your behalf, with limited permissions, without ever seeing your password. You sign in at the service that holds your data, approve exactly what the app may do, and the app receives a token for that and nothing more. You can revoke it at any time without changing your password.

OAuth on its own says nothing about who you are; it's about what an app may do. OpenID Connect (OIDC) is a thin layer on top that adds sign-in: it tells the app who authenticated. Section 4.6 separates them.

4.2Four roles

Every OAuth integration has the same four parties. Name them first, and the rest of the protocol makes sense:

Table 4.1 · The four OAuth roles, in the Spendwise case
RoleWhat it isHere
Resource ownerthe person who can grant access to the dataKorenwolf's office manager
Clientthe application that wants accessSpendwise
Authorization serverauthenticates the owner, asks for consent, issues tokenslogin.larder.example
Resource serverthe API holding the data; accepts access tokensapi.larder.example (invoices)

Clients also come in two kinds, and the difference matters for every flow. A confidential client runs on a server and can keep a secret (a client secret or a private key) to authenticate itself to the authorization server; Spendwise is one. A public client runs on the user's device (a single-page app, a mobile app, a CLI) where anything it contains can be extracted, so it can't keep a secret.

4.3The authorization code flow with PKCE

The flow you'll use for nearly every app that acts for a person is the authorization code flow, with PKCE (Proof Key for Code Exchange, pronounced “pixie”, RFC 7636). It's worth learning step by step:

Each parameter is there to stop a specific attack:

  • redirect_uri: where the code is sent. The authorization server must compare it exactly with the URIs registered for this client. A loose match (any path, any subdomain) lets an attacker send codes to a page they control.
  • state: a random value the client stores and checks when the browser returns. It ties the response to the request this browser started, which stops an attacker from injecting their own code into your session (a form of CSRF).
  • code: a one-time, short-lived (seconds to minutes) reference to the grant, safe to pass through the browser because it's useless on its own.
  • code_verifier and code_challenge: PKCE. The client makes a random verifier, sends only its SHA-256 hash (the challenge) in step ①, and reveals the verifier only on the back channel in step ⑤. Someone who steals the code from a redirect, a log or a malicious app on the same phone can't redeem it without the verifier.

Key idea

Use the authorization code flow with PKCE for every client that acts for a person: web, mobile, single-page or CLI, public or confidential.

PKCE was invented for mobile apps, which can't keep a client secret, but current guidance (OAuth 2.0 Security Best Current Practice, RFC 9700, and the upcoming OAuth 2.1) recommends it for confidential clients too, because it also protects against code injection. Confidential clients additionally authenticate at the token endpoint with their secret or, better, a signed assertion with a private key.

4.4Scopes and consent

A scope names a slice of access the client asks for: invoices:read, orders:write, openid. The authorization server shows the requested scopes on a consent screen, the user approves them (or a company administrator approves them for everyone), and the access token carries only the approved ones. The API must check the scope on every request, in addition to its own rules about the user: a token with invoices:read for an office manager lets the client read that manager's invoices, not anyone's.

Good scope design is coarse enough to understand on a consent screen and fine enough that common integrations need little: separate read from write, and money-moving actions from everything else. Ask for the minimum, and ask for more later when a feature needs it (incremental consent).

Consent phishingAttackers register real OAuth apps with convincing names and ask for broad scopes, such as reading all mail. Nothing is stolen; the user grants it. Companies limit which apps employees may approve, and review granted apps (Chapter 23).

4.6OpenID Connect: adding sign-in

People used OAuth for sign-in long before it was designed for it: “if this token can read my profile, I must be this person”. That's unsafe, because an access token says what a client may do, not who logged in to this client; a token issued to another app could be replayed. OpenID Connect fixes this by adding:

  • The openid scope, which asks for sign-in.
  • An ID token: a JWT for the client, saying who authenticated, when and how. Its aud is the client's own ID.
  • A nonce, sent in step ① and returned inside the ID token, so the client can check the token was made for this sign-in.
  • A UserInfo endpoint for extra profile details, and discovery: every OIDC provider publishes its endpoints, supported features and signing keys (JWKS) at /.well-known/openid-configuration.
Table 4.3 · ID token or access token?
ID tokenAccess token
Defined byOpenID ConnectOAuth 2.0
Meant forthe client (aud = client ID)the API (resource server)
Sayswho signed in, when, how (sub, auth_time, amr)what the client may do (scopes)
Formatalways a JWTJWT or opaque; the client shouldn't care
Neversend it to an API as an access tokenuse it as proof that a user logged in

The client validates an ID token with the checklist from Chapter 3 (3.5), with two OIDC specifics: aud must be its own client ID, and the nonce must match the one it sent. Once validated, the stable identifier for the person is the pair iss + sub, not the email address, which can change or be reassigned.

4.7The security checklist

  1. Authorization code with PKCE for every client acting for a person. No implicit, no password grant.
  2. Exact redirect URI matching, registered per client; HTTPS only (or the platform's app-link schemes on mobile).
  3. state and nonce generated per request, stored, and checked.
  4. Mobile and desktop apps use the system browser, not an embedded web view, so the app can't read the password and the user's existing session (and passkeys) work.
  5. Minimal scopes, checked by the API on every call, together with its own rules about the user.
  6. Short access tokens, rotating refresh tokens (Chapter 3), revoked when the user disconnects the app.
  7. Validate tokens with a maintained library, configured with the issuer, audience and algorithms.

On Azure

The Microsoft identity platform uses the same flows with its own vocabulary: an app registration defines the client; a service principal is that app's identity in a tenant; scopes for Microsoft Graph look like User.Read; and administrators can grant consent for the whole organisation. Restricting which apps users may consent to is one of the first settings to review in a new tenant.

On Google Cloud

OAuth clients live in a project with a configured consent screen; apps that ask for sensitive Google scopes, such as reading Gmail, must pass Google's verification before they can be used by the public. Google's ID tokens are also used to call your own Cloud Run services, where the audience is the service's URL.

4.9At Larder: Spendwise, done properly

At Larder: solved

Eli's reply to Mo: no passwords, but yes to Spendwise. Larder's login service already speaks OAuth and OIDC for its own apps, so in the second week of December Eli's team registered Spendwise as a confidential client with one exact redirect URI, added a new scope, invoices:read, and made the invoices API check it. An office manager clicks “Connect Larder” in Spendwise, signs in at login.larder.example (with a passkey, if they have one), and approves one line: Spendwise wants to read your office's Larder invoices. Spendwise never sees a password, can't place orders, and is disconnected from the office manager's account page with one click, or automatically when the person leaves Korenwolf.

The work turned up one more thing. Larder's own mobile app had been using the deprecated password grant since 2024: it collected the password in its own screen and posted it to the token endpoint. Dee's team moved it to the system browser with code + PKCE in the same release, which is also what made passkeys (Chapter 2) work in the app.

4.10Lab: play out the flow

Lab 4 · Authorization code with PKCE, in one file

You'll compute a PKCE challenge and check it against the standard, build an authorization request, play a tiny authorization server that refuses a stolen code, then validate an ID token as the client and an access token as the API. You need Python 3 and tokens.py from Lab 3 in the same folder. Cost: nothing. (Real authorization servers sign with RS256 and publish keys; this lab reuses Lab 3's HS256 to stay small.)

oauth.pyPython 3.8+, next to tokens.py

# oauth.py · the authorization code flow with PKCE, played out in one file
# Save next to tokens.py from Lab 3; it reuses sign() and verify().
import base64, hashlib, hmac, json, secrets
from urllib.parse import urlencode
from tokens import sign, verify, unb64url

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def challenge_for(verifier):
    return b64url(hashlib.sha256(verifier.encode()).digest())   # the S256 method

# 1. Check against RFC 7636, appendix B
rfc_verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
print("RFC 7636 vector:", challenge_for(rfc_verifier) == "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM")

# 2. The client (an expense tool) starts the flow
CLIENT_ID, REDIRECT = "spendwise", "https://app.spendwise.example/callback/larder"
verifier = secrets.token_urlsafe(32)          # kept secret by the client
state, nonce = secrets.token_urlsafe(16), secrets.token_urlsafe(16)
print("\nsend the browser to:")
print("https://login.larder.example/authorize?" + urlencode({
    "response_type": "code", "client_id": CLIENT_ID, "redirect_uri": REDIRECT,
    "scope": "openid invoices:read", "state": state, "nonce": nonce,
    "code_challenge": challenge_for(verifier), "code_challenge_method": "S256"})[:96] + "…")

# 3. The authorization server: the user signs in and consents; a one-time code is issued
KEY, ISS, NOW = b"lab-only-key-printed-in-a-book-1", "https://login.larder.example", 1795597200
CODES = {}
def authorize(challenge, redirect_uri, nonce):
    code = secrets.token_urlsafe(16)
    CODES[code] = {"challenge": challenge, "redirect_uri": redirect_uri, "nonce": nonce,
                   "sub": "office-manager-207", "scope": "openid invoices:read"}
    return code

def token(code, code_verifier, redirect_uri):
    grant = CODES.pop(code, None)                   # a code works once
    if grant is None:
        return "error: invalid_grant (unknown or used code)"
    if redirect_uri != grant["redirect_uri"]:
        return "error: invalid_grant (redirect_uri)"
    if not hmac.compare_digest(challenge_for(code_verifier), grant["challenge"]):
        return "error: invalid_grant (PKCE verifier)"
    access = sign({"iss": ISS, "sub": grant["sub"], "aud": "larder-api", "iat": NOW,
                   "exp": NOW + 600, "scope": "invoices:read"}, KEY)
    id_token = sign({"iss": ISS, "sub": grant["sub"], "aud": CLIENT_ID, "iat": NOW,
                     "exp": NOW + 600, "nonce": grant["nonce"]}, KEY)
    return {"access_token": access, "id_token": id_token, "token_type": "Bearer", "expires_in": 600}

code = authorize(challenge_for(verifier), REDIRECT, nonce)

# 4. An attacker who intercepted the code, but not the verifier, tries first
print("\nattacker:", token(code, secrets.token_urlsafe(32), REDIRECT))
code = authorize(challenge_for(verifier), REDIRECT, nonce)   # the user tries again
result = token(code, verifier, REDIRECT)
print("client:  ", sorted(result))
print("again:   ", token(code, verifier, REDIRECT))

# 5. The client checks the ID token (it's for the client), the API checks the access token
print("\nID token for client:   ", verify(result["id_token"], KEY, ISS, CLIENT_ID, now=NOW + 5))
print("nonce matches:         ", json.loads(unb64url(result["id_token"].split(".")[1]))["nonce"] == nonce)
print("access token for API:  ", verify(result["access_token"], KEY, ISS, "larder-api", now=NOW + 5))
print("ID token sent to API:  ", verify(result["id_token"], KEY, ISS, "larder-api", now=NOW + 5))

✓Chapter summary

  • OAuth 2.0 is delegated authorisation: an app gets a scoped, revocable token instead of your password. OpenID Connect adds sign-in with an ID token.
  • Four roles: resource owner, client, authorization server, resource server.
  • Use authorization code + PKCE for anything acting for a person; client credentials for services acting for themselves; the device grant for devices without a browser.
  • redirect_uri (exact), state, one-time codes and PKCE each block a specific attack.
  • Scopes limit the client; the API still applies its own rules about the user.
  • ID tokens are for the client, access tokens for the API. Identify people by iss + sub.

Key terms

OAuth 2.0
A framework for granting applications limited access to resources on a user's behalf.
OpenID Connect
An identity layer on OAuth 2.0 that adds sign-in and ID tokens.
Client
The application requesting access; confidential (can keep a secret) or public.
Authorization server
Authenticates the user, collects consent and issues tokens.
Scope
A named slice of access a client requests and a token carries.
Authorization code
A short-lived, one-time reference exchanged for tokens on the back channel.
PKCE
Proof Key for Code Exchange: a secret verifier that proves the redeemer of a code started the flow.
ID token
An OIDC JWT, addressed to the client, describing the authentication.
Discovery
The /.well-known/openid-configuration document describing a provider.

Check your understanding

  1. Name the four OAuth roles when you let a photo-printing website read your photos from a cloud drive. recall

    Show answer

    Resource owner: you. Client: the printing website. Authorization server: the cloud drive provider's sign-in service. Resource server: the cloud drive's photo API.

  2. An attacker's app on the same phone intercepts the redirect carrying an authorization code. Why can't it get tokens? explain

    Show answer

    The token endpoint needs the PKCE code verifier, which only the real app has; the redirect carried only the code, and the challenge sent earlier is a one-way hash.

  3. Which grant would you use for: a nightly job that pulls Larder's invoices for Korenwolf's finance system with no person present; a smart TV app; a single-page web app? apply

    Show answer

    A person must consent once, so: the authorization code flow once, then refresh tokens for the nightly job (or client credentials if Larder offers business-level access without a user). Device authorization for the TV. Authorization code + PKCE for the single-page app, ideally through a backend for frontend.

  4. Your API receives an ID token in the Authorization header. What should it do, and why? apply

    Show answer

    Reject it: its audience is the client, not the API, and it carries no scopes. Accepting it would let any app that received an ID token for the user call your API as them.

  5. Design the scopes for Larder's business API, used by Spendwise and future integrations. design

    Show answer

    Something like invoices:read, orders:read, orders:write, standing-orders:write and account:read, keeping money-moving and address-changing actions separate from reading. Every call also checks that the user belongs to the business account whose data is requested.

  6. Compare how you'd register an app that signs in employees on Azure and on AWS. compare

    Show answer

    Azure: an app registration in Entra ID with redirect URIs and credentials, assigned to users or groups as an enterprise application. AWS: an application in IAM Identity Center (or a Cognito user pool federated with the company IdP), assigned to users or groups.
