The AWS account and its root user

Everything in AWS lives inside an account, and every account starts with one identity that can do anything in it, including closing it: the root user. This chapter explains what an account is as a security boundary, what the root user can do that nobody else can, and how to lock it away so well that you never use it, while still being able to get it back on the day you need it.

By the end you can

  • Explain what an AWS account isolates, and why it's the strongest boundary AWS offers.
  • List the tasks only the root user can do.
  • Secure a root user: no keys, strong MFA, a company-owned email and phone, monitored sign-ins.
  • Recover root access when the email, password or MFA device is lost.
  • Read a credential report and find the risky credentials in an account.

At Larder

On Monday 23 November 2026, a week after the backup incident (Chapter 1), Eli starts his audit with the account itself: the one Jasper opened in March 2024, which still runs everything in production. The credential report has bad news on its first line. The root user has an active access key, created minutes after the account itself, last used in March 2025.

Then it gets worse. The root user's email address is jasper@larder.example, a mailbox that was switched off when Jasper left in August 2025. Its MFA device was an app on Jasper's phone, now wiped. Nobody knows the password. Larder's most powerful identity has a working key that nobody controls, and no working way in for anyone who should. Section 7.8 shows how Eli got it back.

7.1What an account is

An AWS account is a container for resources, identities and a bill. Each has a 12-digit account ID (111122223333 in this book's examples) and is isolated from every other account by default:

  • Resources: a bucket, database or VPC belongs to exactly one account.
  • Identities: IAM users and roles exist inside one account, and by default can only touch that account's resources.
  • Permissions: nothing crosses an account boundary unless both sides allow it (Chapter 10, Chapter 21).
  • Quotas and billing: limits (such as the number of VPCs) and costs are per account.

That makes the account AWS's strongest security boundary, which is why companies use many of them: one per environment, per team, per workload (Chapter 20). A mistake or a breach in the development account then can't reach production. Larder has two: Jasper's original account, which runs production (and still holds the network hub from Handbook 1), and a second account for development and staging that Eli opened in 2025. They aren't part of an organisation yet.

Is an account ID secret?No: it appears in every ARN, and AWS doesn't treat it as a secret. But it tells an attacker which account to target, so don't publish it needlessly. Never rely on its secrecy.

7.2The root user

When you create an account, you give an email address and a password. That pair is the root user: an identity with complete, unrestricted access to everything in the account. Three properties make it special:

  • IAM policies can't limit it. There's no policy you can attach to root. The only thing that restricts a root user is an organisation-level guardrail (an SCP) when the account is a member of an AWS Organization (Chapter 20).
  • It can do a few things no one else can (Table 7.1).
  • It's tied to an email address, and whoever controls that mailbox can reset the password.
Table 7.1 · Tasks that need the root user (at the time of writing)
TaskWhen you'd need it
Change the root email address or passwordhanding over or recovering the account
Create or delete root access keysonly ever to delete them
Close the accountend of life
Restore IAM permissionswhen the only IAM administrator has locked themselves out
Remove an S3 bucket policy or SQS queue policy that denies everyoneafter a policy mistake locks out all IAM principals

Configure MFA delete on an S3 bucketprotecting critical buckets from deletion
Register as a seller in the Reserved Instance Marketplace; sign up for GovCloudrarely

That's the whole list. Everything else, from creating users to deleting databases, can and should be done by IAM principals with the right permissions. The root user is for emergencies and a handful of account-level chores.

7.3Locking it away

Because it can't be limited, the root user must be impossible to use casually and hard to steal. The checklist:

  1. No access keys. Root keys give unlimited programmatic access and can't be restricted. Delete any that exist, after checking when they were last used and by what.
  2. Phishing-resistant MFA, more than one device. Register two or more FIDO2 security keys or passkeys (an account's root user can have up to eight MFA devices), kept in different places. AWS now requires MFA for root users in most accounts.
  3. A long, random password in the company's password vault, ideally readable only by two people together.
  4. A company-owned email address that's a group, such as aws-root@larder.example, delivered to several trusted people. Never a personal address, and never one person's work mailbox, which disappears when they leave.
  5. A company-owned phone number as the account's primary contact, because AWS uses it to verify you during recovery (7.4).
  6. Alternate contacts for billing, operations and security, so AWS's security notices reach a team, not a former employee.
  7. Alerts on root sign-in. Any use of root should page someone (Chapter 23). If root is used, it should be because you planned to.

Key idea

Treat the root user like the deeds to a building: kept safe, owned by the company, needed rarely, and missed immediately if anyone touches them.

7.4Getting root back

Root access is lost more often than it's stolen: the person who set it up leaves, a phone is replaced, a mailbox is closed. AWS's recovery paths all depend on the account's contact details, which is why 7.3 insists they belong to the company:

  • Lost password: “Forgot password” on the root sign-in page sends a reset link to the root email address.
  • Lost MFA device: the sign-in page offers to sign in with alternative factors: AWS verifies the root email address, then calls the account's primary contact phone number.
  • Lost email or phone too: AWS Support can help, but expect identity checks and time.

Watch out: root on someone's personal email

If the root email is a founder's personal address, or a freelancer's, that person owns your account in every way that matters. They can reset the password, and you can't. Moving root to a company group address is one of the first jobs in any AWS account review.

7.5Seeing every credential: the credential report

The credential report is a CSV file listing every IAM user in the account, plus the root user, with the state of each credential: whether a password is set and when it was last used, whether MFA is on, and for each access key when it was created and last used, in which region and for which service. It's generated on request (at most once every four hours) and is the fastest way to see what's lying around in an account. The lab reads one.

Two other quick views help: aws iam get-account-summary reports whether the root user has MFA (AccountMFAEnabled) and access keys (AccountAccessKeysPresent); and the IAM console's dashboard shows the same as security recommendations.

7.6Root in an organisation

When accounts belong to an AWS Organization (Chapter 20), root works differently:

  • The management account, which pays for and governs the organisation, has a root user that nothing can restrict. Secure it most carefully of all, and run no workloads in that account.
  • The root users of member accounts are limited by service control policies, like every other principal there.
  • With centralised root access, the organisation can remove root credentials (password, keys, MFA) from member accounts entirely. When a root-only task is needed, such as unlocking a bucket policy that denies everyone, an administrator in the management account performs it through a short-lived, task-scoped root session (sts:AssumeRoot). New member accounts then never have root credentials at all.

7.7Across providers

Azure and Google Cloud have no single “root user” per subscription or project, but they have the same problem one level up: a few all-powerful administrator identities that must be locked away and never lost.

Table 7.2 · The all-powerful identities at the big three
AWSAzureGoogle Cloud
Boundaryaccounttenant (directory); subscriptions inside itorganisation; projects inside it
Most powerful identityroot user of each account (management account's is unrestricted)Global Administrator in Entra ID, who can elevate to manage every subscriptionsuper administrator in Cloud Identity / Workspace
Recommended practiceno keys, FIDO2 MFA, group email, centralised root access for memberstwo cloud-only emergency access accounts with FIDO2 keys, monitored; few Global Administratorsdedicated super admin accounts with security keys, not used day to day; a backup super admin

On Azure

A Global Administrator can turn on Elevate access to become User Access Administrator over every subscription in the tenant. Keep Global Administrators to a handful, give them separate admin accounts from their daily ones, and keep two emergency access (“break-glass”) accounts that don't depend on federation or a single MFA method, with alerts on every sign-in.

On Google Cloud

Super administrators of the Cloud Identity or Workspace account can grant themselves any role in the organisation. Google recommends using them only for administration, protecting them with security keys, keeping at least one backup, and granting the day-to-day Organization Administrator role to ordinary accounts instead.

7.8At Larder: getting root back

At Larder: solved

Larder still owns the domain, so the fix started with email: on 24 November, Larder's IT administrator restored jasper@larder.example as an alias delivering to a new group, aws-root@larder.example (Eli, Femke and Marco). A password reset link arrived within a minute. For MFA, Eli used sign in with alternative factors: AWS verified the email address, then called the account's primary contact number, which turned out to be Femke's mobile, from the week the founders opened the account. Femke read out the code.

Once signed in, Eli and Femke worked through 7.3 together. The root access key had last been used on 4 March 2025, by S3, which matched a nightly export script on an old virtual machine retired that month; the key was deleted. Two FIDO2 security keys were registered, one for the office safe and one kept by Femke. The root email became aws-root@larder.example, the primary phone a company number, and the alternate contacts the platform team's address. The new password went into the company vault. Root hasn't been used since. When Larder creates an organisation in January (Chapter 12), this account joins it as a member, and its root credentials can then be removed altogether (Chapter 20).

7.9Lab: audit an account's credentials

Lab 7 · Root status and the credential report

You'll check your account's root user from the CLI, download its credential report, and run a script that lists what needs fixing, first on a sample shaped like Larder's account, then on yours. You need the AWS CLI v2 with read access to IAM (the IAMReadOnlyAccess policy is enough) and Python 3. Cost: free; nothing is created.

  1. Check root from the CLI. 
    aws iam get-account-summary \
  --query 'SummaryMap.{RootMFA: AccountMFAEnabled, RootKeys: AccountAccessKeysPresent}'
    You want RootMFA to be 1 and RootKeys to be 0. If either isn't, fix it first, signed in as root, following 7.3.
  2. Check the contacts. aws account get-alternate-contact --alternate-contact-type SECURITY shows who receives AWS's security notices. An error saying none is set means nobody does.
  3. Save this script as credcheck.py:

    credcheck.pyPython 3.8+

    # credcheck.py · read an IAM credential report and list what needs fixing
import csv, sys
from datetime import datetime, timezone

TODAY = datetime(2026, 11, 23, 12, 0, tzinfo=timezone.utc)  # use datetime.now(timezone.utc) for real
STALE = 90                                                 # days

def age(value):
    """Days since a timestamp in the report, or None for N/A, not_supported, no_information."""
    try:
        return (TODAY - datetime.fromisoformat(value)).days
    except ValueError:
        return None

def findings(row):
    user, out = row["user"], []
    if user == "<root_account>":
        if row["access_key_1_active"] == "true" or row["access_key_2_active"] == "true":
            out.append("ROOT has an active access key: delete it")
        if row["mfa_active"] != "true":
            out.append("ROOT has no MFA")
        used = age(row["password_last_used"])
        if used is not None and used < STALE:
            out.append(f"root signed in {used} days ago: find out why")
        return out
    if row["password_enabled"] == "true" and row["mfa_active"] != "true":
        out.append("console password without MFA")
    if row["password_enabled"] == "true" and (age(row["password_last_used"]) or 0) > STALE:
        out.append(f"password unused for {age(row['password_last_used'])} days")
    for n in ("1", "2"):
        if row[f"access_key_{n}_active"] != "true":
            continue
        rotated, used = age(row[f"access_key_{n}_last_rotated"]), age(row[f"access_key_{n}_last_used_date"])
        out.append(f"access key {n}: {rotated} days old, "
                   + (f"last used {used} days ago" if used is not None else "never used"))
    return out

path = sys.argv[1] if len(sys.argv) > 1 else "sample-report.csv"
for row in csv.DictReader(open(path, newline="")):
    for f in findings(row):
        print(f"{row['user']:<15} {f}")

    aws cloudtrail lookup-events --max-results 20 \

✓Chapter summary

  • An account isolates resources, identities, permissions, quotas and billing. It's AWS's strongest boundary.
  • The root user can do everything and can't be limited by IAM policies; only SCPs restrict it, in member accounts.
  • Only a short list of tasks needs root. Do everything else with IAM principals.
  • Lock root away: no keys, two or more FIDO2 keys, a vaulted password, a company group email and phone, alternate contacts, alerts on use.
  • Recovery depends on the root email and the account's phone number. Make sure the company owns both.
  • The credential report lists every credential in the account; read it regularly.
  • In an organisation, member accounts can have no root credentials at all.

Key terms

AWS account
A container for resources, identities and billing, isolated from other accounts.
Account ID
The 12-digit number identifying an account, part of every ARN.
Root user
The account's original email-and-password identity, with unrestricted access.
Credential report
A CSV of every IAM user and root, with password, MFA and access key status.
Alternate contacts
Billing, operations and security contacts AWS uses for notices.
Management account
The account that creates and pays for an AWS Organization.
Centralised root access
Removing member accounts' root credentials and doing root tasks through scoped sessions.

Check your understanding

  1. Why can't you limit the root user of a standalone account with an IAM policy? recall

    Show answer

    IAM policies attach to users, groups and roles; the root user isn't one of them. Only an organisation's SCPs apply to a member account's root.

  2. An administrator applied a bucket policy that denies all actions to every principal. Every IAM user now gets “access denied”, including admins. How do you fix it? apply

    Show answer

    Sign in as the root user (or, in an organisation with centralised root access, use a task-scoped root session from the management account) and delete the bucket policy. That's one of the root-only tasks.

  3. The credential report shows a root access key last used yesterday. What do you do, in order? apply

    Show answer

    Treat it as a possible incident: find out from CloudTrail what it was used for and from where. If it's an unknown use, rotate root's password and MFA, and investigate. Then move whatever legitimately used it to a role, and delete the key.

  4. Explain why the root email address should be a group, not a person. explain

    Show answer

    Whoever receives that mail can reset the password and helps pass MFA recovery. A personal mailbox disappears or leaves with its owner; a group survives staff changes and can't be used by one person alone without others seeing.

  5. Design root security for a new company with one AWS account today and an organisation planned next year. design

    Show answer

    Today: group root email and company phone, two FIDO2 keys in separate places, vaulted password, no keys, alternate contacts, an alert on root sign-in. Next year: make this account the management account with no workloads, create members from it, and turn on centralised root access so members have no root credentials.

  6. Compare the AWS root user with Azure's Global Administrator. compare

    Show answer

    Root is one per account and can't be restricted there; Global Administrator is a role in an Entra ID tenant that several accounts can hold, and can elevate to manage every subscription. Both should be few, use phishing-resistant MFA, have emergency fallbacks and be monitored.
