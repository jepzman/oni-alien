E

Answers to the exercises

Every “check your understanding” question in the book, with its worked answer. Try each question in its chapter first; come here to check.

1Who are you, and what may you do?

  1. A user enters the right password but gets “You don't have permission to view this page”. Which of the four questions failed?

    Authorisation. Authentication succeeded (the password was right); the system then decided this identity may not do this action on this resource.

  2. Split this request into principal, action, resource and context: “At 23:40, from a hotel Wi-Fi, Eli signed in with his security key and tried to delete the staging database.”

    Principal: Eli. Action: delete. Resource: the staging database. Context: 23:40, the hotel network's address, MFA with a security key.

  3. Why is a short-lived token safer than a long-lived API key, even if both are stored equally carefully?

    Storage fails eventually: logs, backups, screenshots, laptops. When a short-lived token leaks, it stops working by itself within minutes or hours. A long-lived key keeps working until someone notices and revokes it.

  4. Your team shares one admin login for a SaaS tool, and someone leaves. List what you have to do, and what you can't do.

    You must change the password and tell everyone who still needs it, and re-enrol any MFA tied to it. You can't tell what the leaver did with it, or prove they no longer have access through a saved session or copied password. With personal accounts you'd just disable theirs.

  5. Design the access for Larder's stock tool: who are the principals, and what context would you check before allowing a stock change?

    Principals: store managers, pickers, operations staff, and the sync service from the picker app. Context worth checking: that the user's store matches the item's store, that they signed in with MFA, and (for large changes) the device. Every decision is logged with the person's identity.

  6. Compare where people's identities live on AWS and on Azure.

    On AWS, people should come from IAM Identity Center, connected to an external IdP or its own directory; IAM users exist but are legacy. On Azure, people live in Entra ID, the same directory used for Microsoft 365, and Azure RBAC grants them roles.

2Passwords, MFA and passkeys

  1. Larder's password hashes were never stolen, yet 310 accounts were taken over. Name the attack and two defences that would have helped.

    Credential stuffing. Breached-password checks, MFA or passkeys, and rate limits with alerting on the overall failure rate. Strong hashing doesn't help, because the attacker logs in normally.

  2. Why does adding a salt not make a single password any harder to crack, and why use it anyway?

    The salt is stored next to the hash, so an attacker cracking one record uses it. Its value is across records: every password must be attacked separately, identical passwords aren't revealed, and precomputed tables don't work.

  3. A login server checks 200 passwords a second at peak, and an Argon2id check takes 40 ms of CPU. How many cores does hashing need?

    200 × 0.04 s = 8 core-seconds per second, so eight cores, plus headroom for spikes and attacks (which also arrive as login attempts).

  4. An administrator uses an authenticator app code. Explain how a real-time phishing proxy gets into their account, and what would stop it.

    The proxy shows the real login page, relays the password and code to the real site as they're typed, and keeps the session cookie the real site returns. A passkey or security key stops it, because the browser signs for the fake origin and the real site rejects the signature.

  5. Design authentication for Larder's three groups: customers, pickers on shared store tablets, and engineers with production access.

    Customers: passkeys first, passwords with breached checks and rate limits, step-up for risky actions. Pickers: personal badges or short PINs on a managed device, with short sessions, since the tablet is shared but the identity shouldn't be. Engineers: single sign-on with hardware security keys or device-bound passkeys, two each, and recovery through a verified call with their manager.

  6. Compare how you'd require phishing-resistant MFA for administrators on Azure and on Google Cloud.

    Azure: a Conditional Access policy for the administrator roles requiring the phishing-resistant MFA authentication strength. Google Cloud: in the Cloud Identity or Workspace admin console, enforce 2-Step Verification with security keys only for the administrators' organisational unit.

3Sessions and tokens

  1. Why didn't changing her password stop the thief at Larder?

    The phone held an access token and a refresh token, neither tied to the password. The API accepted the access token for 24 hours, and nothing revoked the refresh token when the password changed.

  2. You receive a JWT whose signature is valid. List what else you must check before acting on it.

    That the algorithm was one you allow (checked before the signature), the issuer is the one you trust, the audience is your service, it hasn't expired and isn't used before nbf, and then whether this subject is authorised for this request.

  3. Explain why an identity provider uses RS256 or ES256 rather than HS256 for tokens many APIs will check.

    With HS256, every API that can verify a token holds the same secret and could also forge one. With an asymmetric algorithm, only the provider holds the private signing key; APIs verify with the public key, which can't sign.

  4. A security reviewer says “your access tokens last 15 minutes, so a fired employee keeps access for up to 15 minutes”. When is that acceptable, and what would you add when it isn't?

    Acceptable for most actions, since refresh is revoked immediately. For sensitive actions (payments, admin changes, data exports), check a denylist of token IDs or a per-user “valid after” time, or require fresh authentication.

  5. Which cookie attribute stops a script injected into your page from reading the session cookie, and which stops another site making the user's browser send it?

    HttpOnly hides it from JavaScript. SameSite=Lax or Strict stops it being sent on most cross-site requests.

  6. Compare how you'd cut off a compromised identity's cloud API access early on AWS and on Azure.

    AWS: temporary credentials can't be recalled, so attach a policy that denies everything for sessions issued before now (aws:TokenIssueTime), which the console's “Revoke active sessions” does for roles, and disable the source identity. Azure: revoke the user's refresh tokens and disable the account; Continuous Access Evaluation makes supporting services reject existing access tokens quickly.

4OAuth 2.0 and OpenID Connect

  1. Name the four OAuth roles when you let a photo-printing website read your photos from a cloud drive.

    Resource owner: you. Client: the printing website. Authorization server: the cloud drive provider's sign-in service. Resource server: the cloud drive's photo API.

  2. An attacker's app on the same phone intercepts the redirect carrying an authorization code. Why can't it get tokens?

    The token endpoint needs the PKCE code verifier, which only the real app has; the redirect carried only the code, and the challenge sent earlier is a one-way hash.

  3. Which grant would you use for: a nightly job that pulls Larder's invoices for Korenwolf's finance system with no person present; a smart TV app; a single-page web app?

    A person must consent once, so: the authorization code flow once, then refresh tokens for the nightly job (or client credentials if Larder offers business-level access without a user). Device authorization for the TV. Authorization code + PKCE for the single-page app, ideally through a backend for frontend.

  4. Your API receives an ID token in the Authorization header. What should it do, and why?

    Reject it: its audience is the client, not the API, and it carries no scopes. Accepting it would let any app that received an ID token for the user call your API as them.

  5. Design the scopes for Larder's business API, used by Spendwise and future integrations.

    Something like invoices:read, orders:read, orders:write, standing-orders:write and account:read, keeping money-moving and address-changing actions separate from reading. Every call also checks that the user belongs to the business account whose data is requested.

  6. Compare how you'd register an app that signs in employees on Azure and on AWS.

    Azure: an app registration in Entra ID with redirect URIs and credentials, assigned to users or groups as an enterprise application. AWS: an application in IAM Identity Center (or a Cognito user pool federated with the company IdP), assigned to users or groups.

5SAML and federation

  1. In the Larder–Korenwolf setup, which is the IdP, which is the SP, and where is the person's password checked?

    Korenwolf's Entra ID is the IdP and checks the password and MFA. Larder's login service is the SP; it never sees the password.

  2. Why does an SP keep the IDs of the AuthnRequests it sends, and of the assertions it has accepted?

    Request IDs let it check that a response answers a sign-in this SP started (InResponseTo). Assertion IDs let it reject a captured response that's replayed while still within its time window.

  3. An assertion is correctly signed by a partner's IdP and names finance@yourcompany.example. What should happen, and why?

    Reject it. The partner's connection may only vouch for its own verified domains and its own tenant; a valid signature proves who made the statement, not that the partner is entitled to make it.

  4. Korenwolf disables an office manager's account at 10:00. They had signed in to Larder at 09:00. When does their Larder access end, and how would you make it sooner?

    With just-in-time accounts, when Larder's session ends: up to eight hours after 09:00. Sooner: shorter sessions, and SCIM deprovisioning so Larder hears about the disabled account and ends its sessions at once.

  5. A start-up is adding enterprise SSO to its new web and mobile app. Should it start with SAML or OIDC?

    Start with OpenID Connect, which suits mobile and APIs and is easier to get right; add SAML when an enterprise customer's IdP requires it, ideally through an identity service that handles both.

  6. Compare how a partner's staff could be given access to your app on Azure and on AWS.

    Azure: invite them as B2B guests in your Entra ID tenant, signing in with their home organisation, governed by cross-tenant access settings; or add their IdP to Entra External ID. AWS: add their IdP (SAML or OIDC) to a Cognito user pool, one IdP per partner, mapped to that partner's account in your app.

6Access models: roles, attributes and relationships

  1. Which model fits each: a shared slide deck; “store managers can adjust stock at their store”; “Korenwolf's admin sees all its offices' orders”?

    An ACL (owner-controlled sharing); ABAC (job plus a store attribute), or RBAC with attributes; ReBAC (organisation → office → order).

  2. Why did ABAC fix Tomás's leftover access, when RBAC didn't?

    ABAC reads his store from the HR system, which was updated when the cover ended; RBAC depended on someone remembering to remove a role assignment, which nobody did.

  3. An API checks that the caller has the orders:read scope, then returns /orders/{id} for any ID. What's wrong, and what's the fix?

    Broken object-level authorisation: any caller with the scope can read any order. Check that the caller is related to that order (owner, or manager of its office) before returning it.

  4. Give one example of separation of duties at Larder, and how you'd enforce it.

    Refunds over €100: support staff can propose, a team lead must approve, and nobody can approve their own. Enforce it in the refund tool's policy: the approver must hold the lead role and differ from the requester.

  5. What new risks does ABAC introduce, and how do you control them?

    Whoever can change attributes or tags can change access, missing attributes can be mistaken for “match all”, and it's harder to list who can reach a resource. Source attributes from a trusted system, restrict who can change them, deny when they're missing, and evaluate rules regularly to produce access reports.

  6. Compare how inheritance works in Azure RBAC and Google Cloud IAM.

    Both inherit downwards: Azure from management groups to subscriptions, resource groups and resources; Google Cloud from organisation to folders, projects and resources. In both, a grant high up applies to everything below it, so grant at the lowest scope that works.

7The AWS account and its root user

  1. Why can't you limit the root user of a standalone account with an IAM policy?

    IAM policies attach to users, groups and roles; the root user isn't one of them. Only an organisation's SCPs apply to a member account's root.

  2. An administrator applied a bucket policy that denies all actions to every principal. Every IAM user now gets “access denied”, including admins. How do you fix it?

    Sign in as the root user (or, in an organisation with centralised root access, use a task-scoped root session from the management account) and delete the bucket policy. That's one of the root-only tasks.

  3. The credential report shows a root access key last used yesterday. What do you do, in order?

    Treat it as a possible incident: find out from CloudTrail what it was used for and from where. If it's an unknown use, rotate root's password and MFA, and investigate. Then move whatever legitimately used it to a role, and delete the key.

  4. Explain why the root email address should be a group, not a person.

    Whoever receives that mail can reset the password and helps pass MFA recovery. A personal mailbox disappears or leaves with its owner; a group survives staff changes and can't be used by one person alone without others seeing.

  5. Design root security for a new company with one AWS account today and an organisation planned next year.

    Today: group root email and company phone, two FIDO2 keys in separate places, vaulted password, no keys, alternate contacts, an alert on root sign-in. Next year: make this account the management account with no workloads, create members from it, and turn on centralised root access so members have no root credentials.

  6. Compare the AWS root user with Azure's Global Administrator.

    Root is one per account and can't be restricted there; Global Administrator is a role in an Entra ID tenant that several accounts can hold, and can elevate to manage every subscription. Both should be few, use phishing-resistant MFA, have emergency fallbacks and be monitored.

8Users, groups and roles

  1. You find AKIAQEXAMPLE… in a public repository. What kind of credential is it, and why does that make it worse than ASIA…?

    A long-lived IAM user (or root) access key. It works until deleted, whereas an ASIA key is part of a temporary session that expires within hours. Deactivate it now, then investigate its use in CloudTrail.

  2. A trust policy names arn:aws:iam::111122223333:root. Can every user in that account assume the role?

    Only those whose own identity policies allow sts:AssumeRole on this role. Naming the account delegates the choice to that account's administrators; it doesn't mean the root user, and it doesn't mean everyone.

  3. Write a trust policy for a role that ECS tasks in your account use.

    {"Effect": "Allow", "Principal": {"Service": "ecs-tasks.amazonaws.com"}, "Action": "sts:AssumeRole", "Condition": {"StringEquals": {"aws:SourceAccount": "111122223333"}}}, optionally with aws:SourceArn limited to your cluster's tasks.

  4. A developer may create Lambda functions and has iam:PassRole on *. Explain how they could become an administrator.

    They create a function, pass it an existing administrator role, and invoke it: the function's code runs with administrator permissions and can, for example, attach AdministratorAccess to the developer. Restrict PassRole to specific roles.

  5. Six engineers share a powerful role. Design it so that CloudTrail still shows which of them did what, and nobody can pretend to be another.

    Require sts:SetSourceIdentity with sts:SourceIdentity equal to ${aws:username} (or the IdP's user attribute with SSO), require MFA, and keep sessions to an hour. Every event then carries a source identity that the person couldn't choose freely.

  6. Compare how a person gets temporary admin rights on AWS and on Azure.

    AWS: they assume a role (directly or through an SSO permission set) and get a time-limited session. Azure: they're made eligible for a role in Privileged Identity Management and activate it for a few hours, with justification or approval; there's no separate identity to assume.

9Reading and writing IAM policies

  1. Read this aloud as one sentence: {"Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "arn:aws:s3:::larder-dispatch-prod/routes/*"}.

    “Deny deleting any object under routes/ in the bucket larder-dispatch-prod.” Because it's an explicit deny, no other policy can allow it.

  2. A role has s3:ListBucket on arn:aws:s3:::reports/*, and aws s3 ls s3://reports/ is denied. Why, and what's the fix?

    ListBucket acts on the bucket, but the resource names objects, so the statement never matches. Use arn:aws:s3:::reports, optionally with an s3:prefix condition.

  3. Why is "Action": "s3:Get*" riskier than it looks, even if every Get action today seems harmless?

    It already includes reading bucket policies, ACLs and other configuration, and it will include any matching action AWS adds in future, without anyone reviewing the change.

  4. Write a statement that lets a role read only secrets tagged with the same team as the role. What must you also control for it to be safe?

    Allow secretsmanager:GetSecretValue on "*" with StringEquals "aws:ResourceTag/team": "${aws:PrincipalTag/team}". You must also control who can set the team tag on roles and secrets, or anyone who can tag can grant themselves access.

  5. A condition block has StringEquals on aws:RequestedRegion with two regions, and Bool on aws:SecureTransport. A request comes from eu-west-1 over plain HTTP. Does the statement apply?

    No. The region matches one of the two values (OR), but the two operators must both hold (AND), and the request didn't use TLS.

  6. Compare how you'd let one service read one storage bucket on AWS and on Google Cloud.

    AWS: write a policy with the read actions and the bucket's ARNs, and attach it to the service's role. Google Cloud: bind a role such as roles/storage.objectViewer to the service account in the bucket's allow policy; the scope of the binding decides which resource it covers.

10How AWS decides: policy evaluation logic

  1. Which policy types can grant access, and which can only take it away?

    Identity-based and resource-based policies (and legacy ACLs) can grant. Permissions boundaries, session policies, SCPs and RCPs can only limit.

  2. A role has AdministratorAccess and a permissions boundary allowing only s3:*. Can it create an IAM user? Can it delete a bucket?

    No: the boundary doesn't allow iam:CreateUser. Yes: both the identity policy and the boundary allow s3:DeleteBucket, unless something denies it explicitly.

  3. A bucket in account A has a policy allowing a role in account B to read it. The role's own policies allow nothing. Can it read the bucket? What if the role were in account A?

    From account B, no: across accounts both sides must allow, and B's side doesn't. In account A, yes: within one account a resource-based policy naming the principal is enough.

  4. Why is an explicit deny in an identity policy a weaker guardrail than the same deny in an SCP?

    The identity policy protects only from the identities it's attached to; any other or new identity bypasses it. An SCP applies to every principal in the member account, however it was created, including the root user.

  5. Design a way for Larder's product teams to create roles for their own services without being able to give themselves more power than the platform team allows.

    A team-boundary policy with the services teams may use and the guardrail denies. Teams may create and modify roles named team-* only with that boundary (condition on iam:PermissionsBoundary), may pass only team-* roles, and are denied removing or changing boundaries and editing the boundary policy itself.

  6. Compare how you'd stop anyone deleting a production database on AWS and on Azure.

    AWS: an explicit deny on the delete action (in an SCP to cover everyone, with an exception for a break-glass role), plus RDS deletion protection. Azure: a CanNotDelete resource lock, which blocks deletion even by owners until someone with permission removes the lock, and Azure Policy for configuration rules.

11Debugging “access denied”

  1. What's the first command to run when a script gets “access denied”, and why?

    aws sts get-caller-identity (or its SDK equivalent from inside the script): it shows which principal, in which account, is really making the calls, and works regardless of permissions.

  2. An error ends “with an explicit deny in a service control policy”. Will adding the action to the role's policy help?

    No. An explicit deny wins over any allow, and an SCP is set by the organisation. The fix is to use an approved path or ask the platform team for a deliberate exception.

  3. An upload to S3 fails with “access denied”, and the role clearly has s3:PutObject on the prefix. Name two causes outside the role's S3 permissions.

    The bucket encrypts with a customer managed KMS key, and the role lacks kms:GenerateDataKey on it (or the key policy doesn't allow it); a bucket policy, VPC endpoint policy, SCP or RCP denies the request; or the request comes from a different identity or account than expected.

  4. You can't find a denied S3 GetObject in CloudTrail's Event history. Why might that be?

    GetObject is a data event, which isn't in Event history and is recorded only by a trail configured for S3 data events on that bucket. It might also simply not have arrived yet, or be in another region's history.

  5. Design a weekly report that would have caught Larder's staging problem before the trial evening.

    Run a denial summary like denied.py over each account's CloudTrail events daily and post new principal/action/reason combinations to the team channel; and compare key settings (bucket encryption, public access, versioning) between staging and production buckets, flagging differences.

  6. Compare what you'd look at first for a denied call on AWS and on Google Cloud.

    AWS: the error's reason (which policy type) and the CloudTrail event, then the simulator. Google Cloud: the missing permission named in the error, then Policy Troubleshooter for that principal, permission and resource, which shows bindings and deny policies.

12Single sign-on with IAM Identity Center

  1. What three things does an account assignment connect, and what does Identity Center create as a result?

    A user or group, a permission set and an AWS account. It creates (and maintains) an IAM role named AWSReservedSSO_PermissionSet_suffix in that account, trusted only by Identity Center.

  2. Why does single sign-on for AWS accounts usually start with creating an organisation, and why from a new account?

    Only an organisation instance of Identity Center can grant access to AWS accounts. The management account can't be restricted by SCPs and controls all members, so it should hold no workloads; a new, empty account is the simplest way to guarantee that.

  3. An engineer needs to read one bucket's objects in production for a week. How do you grant it without changing ViewOnly for everyone?

    Create (or reuse) a narrow permission set for that bucket, assign it to a small group in production, add the engineer to the group with an end date, and remove them after the week, ideally through the time-limited process of Chapter 14.

  4. After moving to Identity Center, a guardrail's exception for role/db-change no longer lets the database owners make changes. Why, and what's the fix?

    Their sessions now come from AWSReservedSSO_DbChange_suffix under the /aws-reserved/sso.amazonaws.com/ path. Change the exception to match that pattern with wildcards, and test it with the policy simulator or a real session.

  5. Design the permission sets and groups for a company with three product teams, a platform team, finance and support, and four accounts.

    Roughly: ViewOnly for all engineers in production; Developer (with a boundary) for each team in development and staging; ProdOperator for on-call, time-limited; PlatformAdmin for platform, time-limited in production; Billing for finance in the management account; support gets application tools, not AWS access. All assigned to groups, ideally with a team attribute for ABAC.

  6. Compare how a person gets admin rights in one subscription on Azure with one account on AWS.

    Azure: their Entra ID group gets a role assignment (such as Owner or Contributor) at the subscription scope; they use their own identity. AWS: their group gets an account assignment of an admin permission set; they sign in through the portal and receive a session of the role Identity Center created in that account.

13Joiners, movers and leavers

  1. What's the difference between what SAML does and what SCIM does for an app?

    SAML (or OIDC) signs people in: the app trusts the IdP to say who's there. SCIM provisions: the IdP creates, updates and deactivates the person's account and group memberships in the app.

  2. An engineer is disabled in the IdP at 17:00. They have an Identity Center PlatformAdmin session from 16:45, with a one-hour duration. When does their AWS access end, and how could you end it sooner?

    The role session's credentials work until about 17:45. Sooner: end the user's sessions in Identity Center (so no new credentials are issued), and add a deny statement conditioned on their identitystore:UserId to the permission sets or an SCP, which blocks the credentials already issued. The AWSReservedSSO_ role itself can't be edited.

  3. Why are movers more dangerous than joiners for least privilege?

    Joiners complain when access is missing; movers never complain about access they no longer need. Without automatic removal on a move, old access accumulates silently.

  4. Your access review shows 400 items per manager and everyone clicks “approve all”. Redesign it.

    Remove birthright access from the review (it's governed by rules); show only requested, hand-made and privileged access; add last-used dates; review privileged access monthly and the rest quarterly; remove access that isn't confirmed after a reminder.

  5. Identity Center provisioning stopped a month ago and nobody noticed. What probably happened, and what would have caught it?

    The SCIM access token expired after a year. A calendar reminder before expiry, alerts on provisioning errors in the IdP, and a daily comparison of HR leavers with Identity Center's active users.

  6. Compare how a leaver loses access to Azure and to AWS when the company's IdP is Entra ID.

    Azure: disabling the Entra ID account stops sign-in to the portal and every subscription at once; refresh tokens can be revoked, and Continuous Access Evaluation cuts many sessions quickly. AWS: Entra ID's SCIM deactivates the user in Identity Center, which stops new sign-ins; existing role sessions run until they expire unless revoked.

14Privileged access and break-glass

  1. An administrator says, “I'm trustworthy, so I don't need just-in-time access.” What's the answer?

    It isn't about their trustworthiness: it's about how long a powerful credential exists that an attacker could steal or misuse through their browser, laptop or session. Just-in-time access shrinks that exposure from all the time to the few hours it's used.

  2. Why should a permission set used for elevation have a session duration no longer than the grant?

    Removing the assignment stops new sessions but not ones already started. A twelve-hour session started near the end of a one-hour grant would keep the privilege for eleven more hours.

  3. Larder's first break-glass test found the runbook was in the wiki. Why is that a problem, and what else would you check?

    The wiki signs in through the IdP, which might be the thing that's down. Also check: alarm delivery doesn't depend on SSO-protected tools, the security keys aren't registered only on IdP-managed devices, passwords haven't expired, and the people who know the safe's combination aren't all the same two people.

  4. Design elevation for a team of four engineers where everyone is on call and the CTO is usually unreachable.

    All four eligible for an operator set, self-approved during incidents with next-day review; database and admin sets approved by any other engineer, never yourself; one-hour grants and sessions; break-glass with two people for when nobody else is reachable; the CTO reviews the weekly elevation log rather than approving each one.

  5. What makes an action deserve a two-person rule rather than just an approval?

    Approval happens before; the approved person then acts alone and could do more than approved. For actions that are catastrophic or could disable oversight (SCPs, logging, account deletion), the second person must see and accept the exact change, as in a mandatory code review, with direct changes denied to everyone.

  6. Compare just-in-time elevation on Azure and on AWS.

    Azure has it built in: Privileged Identity Management makes people eligible for roles, which they activate with MFA, justification and optional approval for a limited time. AWS Identity Center has no eligible state, so a tool (such as TEAM) or time-limited IdP groups create and remove account assignments.

15Identities for workloads

  1. Where does code running on an EC2 instance with an instance profile get its credentials, and who rotates them?

    From the instance metadata service at 169.254.169.254. AWS issues and rotates the role's temporary credentials; the SDK fetches fresh ones before the old ones expire.

  2. Explain why IMDSv2 stops a typical SSRF bug from stealing credentials, but doesn't make the bug harmless.

    A typical SSRF bug can only make the server send a GET to a chosen URL; IMDSv2 needs a PUT with a special header first, and refuses proxied token requests. But the bug can still reach other internal services, so it must be fixed in the application too.

  3. An ECS task can't start: “unable to pull image”. Which role do you look at? And if the app gets “access denied” writing to S3?

    Pulling the image is the task execution role's job (ECR permissions). Writing to S3 is the application's job, so the task role.

  4. A Lambda function returns its full environment in an error message to the caller. Why is that a credential leak?

    Lambda places the execution role's temporary credentials in environment variables. Anyone who sees the error gets a working key, secret and session token until they expire.

  5. Design the identities for a new service with an API on ECS, a nightly batch job on Lambda, and a script on a store's back-office PC.

    An ECS task role and execution role for the API; a separate execution role for the batch function; IAM Roles Anywhere with a device certificate (or a narrowly scoped OIDC federation) for the PC. Each role narrow, tagged with the owning team, with PassRole restricted to the deployment pipeline.

  6. Compare how Azure and Google Cloud protect their metadata endpoints from SSRF with how AWS does.

    Azure requires a Metadata: true header and Google a Metadata-Flavor: Google header, which a GET-only SSRF usually can't add. AWS's IMDSv2 requires a PUT to obtain a session token, then a token header on every request, plus a hop limit and a refusal of proxied token requests.

16Kubernetes and workload identity

  1. A pod reads an S3 bucket and lists pods in its namespace. Which permission system decides each?

    Reading S3 is decided by IAM, using the pod's AWS credentials. Listing pods is decided by Kubernetes RBAC, using its service account.

  2. Why is create on pods in a namespace roughly as powerful as everything any service account there can do?

    Whoever can create a pod chooses which service account it runs as, so the pod gets that account's RBAC permissions and its associated cloud role.

  3. Every pod in a cluster can read a bucket that only one application should. Name the two likely causes.

    The bucket permission is on the node role, and pods can reach the node's metadata service. Or a shared service account (such as default) is associated with a role that has the permission.

  4. Write the conditions an IRSA trust policy needs, and say what goes wrong without the sub condition.

    StringEquals on …:sub = system:serviceaccount:namespace:name and …:aud = sts.amazonaws.com. Without sub, any service account in the cluster can assume the role.

  5. Design people's access to a new EKS cluster for a company already using Identity Center with just-in-time admin.

    Access entries: ViewOnly's role gets view on all namespaces; each team's Developer role gets edit on its namespace; the just-in-time PlatformAdmin role gets cluster admin. Remove the creator's bootstrap admin, and record changes in CloudTrail.

  6. Compare how GKE and EKS stop pods using the node's cloud identity.

    GKE's metadata server, with Workload Identity Federation, hides the node's service account from pods and serves only the pod's own identity. On EKS you must do it yourself: hop limit 1 or a network policy blocking IMDS, and a minimal node role.

17CI/CD without long-lived keys

  1. What's in GitHub's OIDC token that tells AWS which repository and environment a job belongs to?

    The sub claim, such as repo:larder/larder-core:environment:production, plus claims like repository, ref and environment.

  2. A role trusts the GitHub OIDC provider with only an aud condition. Describe the attack.

    An attacker creates any GitHub repository, writes a workflow that requests a token with audience sts.amazonaws.com, and calls AssumeRoleWithWebIdentity on your role's ARN. The token is genuinely signed by GitHub, and nothing checks which repository it came from.

  3. Why should production trust an environment rather than the main branch?

    An environment can carry protection rules, such as required reviewers and allowed branches, so the approval in GitHub is the only path to production credentials. Trusting main gives every push to main production access, approved or not.

  4. Write the iam:PassRole statement for a pipeline that deploys one ECS service with a task role and an execution role.

    Allow iam:PassRole on exactly those two role ARNs, with StringEquals iam:PassedToService = ecs-tasks.amazonaws.com, as in 17.6.

  5. Design CI access for a monorepo that deploys three services to staging and production, with Terraform for infrastructure.

    Per environment: a deploy role per service (or one with per-service resources) trusted by the matching protected environment; a Terraform plan role (read-only, trusted by pull requests from the same repository, in a sandbox or with read-only access); a Terraform apply role behind its own environment with approval. All exact sub conditions, one-hour sessions, boundaries, pinned actions.

  6. Compare how you'd restrict which GitHub repositories can use your cloud identity on AWS and on Google Cloud.

    AWS: conditions on the sub (and aud) claims in each role's trust policy. Google Cloud: an attribute condition on the workload identity pool provider (for example on repository_owner_id), which Google requires for GitHub, plus role grants to specific mapped principals.

18Secrets and encryption keys

  1. Why isn't deleting a committed password from the repository enough?

    It stays in the history and in every clone and fork, and may have been copied before the deletion. Only rotating it makes the leaked value useless.

  2. An administrator with AdministratorAccess can't decrypt a file in S3 encrypted with a customer managed key. Is that a bug?

    Not if the key policy doesn't delegate to IAM and doesn't name them: KMS requires the key policy to allow use, whatever IAM says. That's the intended second gate.

  3. Explain what encryption context adds, using S3 as the example.

    S3 binds each object's data key to the object's ARN. The wrapped key can't be used for another object; every decrypt is recorded in CloudTrail with the ARN; and key policies can require specific context values.

  4. An application caches a database password for a day; rotation runs every 30 days. What breaks, and how do you fix it?

    After rotation, new connections fail with the stale password until the cache expires. Retry once with a freshly fetched secret on authentication failure, use alternating users so the previous password stays valid during the switch, and keep the cache short.

  5. Decide which of these deserve customer managed keys: application logs; customer order exports; RDS snapshots copied to a backup account; public product images.

    Order exports (a separate decision about who may read them) and snapshots copied cross-account (required to share encrypted snapshots). Logs and public images: default keys are fine, unless logs contain sensitive data that needs a separate gate.

  6. Compare how you'd let one workload read one secret on AWS and on Google Cloud.

    AWS: allow secretsmanager:GetSecretValue on that secret's ARN in the workload role's policy (and, with a customer managed key, kms:Decrypt through the key policy). Google Cloud: grant roles/secretmanager.secretAccessor on that one secret to the workload's service account.

19Service-to-service and API access

  1. Name two things SigV4 protects against that a bearer token doesn't.

    Altering a captured request (the signature covers it) and replaying it later (signatures expire within minutes). Also, the long-term secret never crosses the network.

  2. Your team proposes API Gateway API keys to authenticate partners. What do you say?

    They're meant for usage plans and metering; AWS advises against using them for authorisation. Use a JWT authoriser with OAuth client credentials, mTLS, or a Lambda authoriser with properly managed keys, and keep usage-plan keys for quotas.

  3. Why must a webhook signature be checked against the raw body rather than parsed and re-encoded JSON?

    The sender signed specific bytes. Parsing and re-encoding can change spacing, key order or number formatting, which breaks genuine signatures; and code that parses first may act on unverified data.

  4. An API's list endpoint filters by the caller's office, but the detail endpoint doesn't check. Design a fix that stays fixed.

    One shared function that loads an object for a principal and refuses unrelated callers; all endpoints must use it (enforced by review or a lint rule); and a test per endpoint that requests another customer's object and expects a refusal.

  5. Design credentials for a partner whose system can only send a static header.

    An API key per partner integration, from the portal, with a prefix, stored hashed, expiring after 90 days with reminders, two active at once for rotation, scoped to the partner's account and needed operations, with last-used shown; mTLS in addition if the partner can manage certificates.

  6. Compare how one service calls another privately on Google Cloud and on AWS.

    Google Cloud: the caller fetches an ID token with the target's URL as audience from its metadata server; the platform checks it and roles/run.invoker. AWS: the caller signs with SigV4 using its role; API Gateway (IAM auth), a function URL or VPC Lattice checks IAM and the target's resource policy.

20AWS Organizations and guardrails

  1. An OU has only an allow-list SCP permitting S3 and EC2. A role in an account below it has AdministratorAccess. Can it create a DynamoDB table?

    No. Every level must allow the action, and that OU's SCPs don't allow DynamoDB; IAM never gets asked.

  2. Why is moving protect-orders-db from an identity policy to an SCP a real improvement?

    The identity policy only protected identities it was attached to; any new or forgotten role bypassed it, and account admins could detach it. The SCP applies to every principal in the account, including future ones and the root user, and can only be changed from the organisation's management.

  3. A region-restriction SCP denies everything outside eu-central-1. Engineers can no longer create IAM roles. Why, and what's the fix?

    IAM is a global service whose requests are made in us-east-1, so the deny catches them. Exempt global services with NotAction, as in 20.4.

  4. Someone proposes running the CI/CD tooling in the management account, “since it deploys to everything”. What do you say?

    No: SCPs don't restrict the management account, and a compromise of tooling there would control the whole organisation. Run it in a tooling account under Infrastructure, assuming narrowly scoped roles in workload accounts.

  5. Design the OUs and SCPs for a company adding a data-science team that needs GPUs in a second region.

    A new OU (say Workloads/Data) whose accounts may also use the second region: the root's region guardrail moves down to each OU, or gains an exception condition for that OU's accounts. Keep IMDSv2, audit-trail and leave-organisation denies at the root; add a budget alarm and tag policy for GPU spend.

  6. Compare where you'd enforce “resources only in approved regions” on AWS and on Azure.

    AWS: an SCP denying requests outside the approved regions (exempting global services). Azure: an Azure Policy assignment with the “Allowed locations” definition at a management group, which denies creating resources elsewhere.

21Cross-account access and resource sharing

  1. Name the two ways to give account A's role access to a bucket in account B, and what each side must allow.

    Assume a role in B (A allows sts:AssumeRole on it; B's role trusts A's role and grants the bucket access), or a bucket policy in B naming A's role (B's bucket policy allows it; A's identity policy allows the S3 actions).

  2. Explain why an external ID works even though it isn't secret.

    The protection comes from who chooses it: the vendor generates it per customer and always sends the ID belonging to the tenant it's acting for. Another customer can't make the vendor send yours, so knowing it doesn't help them.

  3. A bucket in the production account, encrypted with aws/s3, must be readable by the analytics account. What's in the way, and what do you change?

    Objects encrypted with an AWS managed key can't be decrypted from another account. Switch the bucket to a customer managed key whose key policy allows the analytics role to decrypt (via S3), then grant it in the bucket policy and in the analytics role's identity policy.

  4. A vendor's onboarding guide says: trust our account, attach ReadOnlyAccess. Review it.

    Trust their specific role, require their generated external ID, replace ReadOnlyAccess (which reads all data) with the few actions and resources the integration needs, tag the role with owner and contract, and plan the offboarding.

  5. Why put backup copies in a separate account with a vault lock, rather than just another region?

    An attacker with administrator access to the production account can delete backups in any of its regions. A separate account with its own access, and a vault lock that forbids early deletion even by administrators, survives the production account's compromise.

  6. Compare how a service provider gets access to a customer's environment on Azure and on AWS.

    Azure: Azure Lighthouse delegates role assignments on the customer's subscriptions to the provider's tenant, approved and removable by the customer. AWS: the customer creates a role trusting the provider's role, with the provider's external ID, and narrow permissions.

22Data perimeters

  1. Which perimeter stops each: a bucket policy that grants "Principal": "*"; a compromised build job uploading source code to its own bucket; a leaked access key used from a hotel?

    Identity perimeter; resource perimeter; network perimeter (for data and credentials it covers).

  2. Why does the identity perimeter need a separate statement for AWS services?

    AWS services aren't in your organisation, so the first statement exempts them; but without a check they could be pointed at your resources by someone else (a confused deputy). The second statement allows services only when aws:SourceOrgID is your organisation.

  3. After enforcing the network perimeter, the finance team's monthly report fails. What do you do?

    Don't remove the rule: move the job to run inside the VPC (or through a service covered by aws:ViaAWSService), with its own role. If it truly can't, add a narrow, documented exception, and fix the process that let it go unnoticed before enforcement.

  4. A vendor needs to read one Larder bucket. Should it get a bucket-policy grant or a role in Larder's account, given the perimeter?

    A role in Larder's account with an external ID, tagged as the vendor's perimeter exception: only the assume-role step needs the exception, its sessions are then inside Larder's organisation, and Larder controls the permissions. A direct bucket grant would need an exception on the bucket itself, and still meets the network rule for restricted data.

  5. Why roll out perimeters with data-event analysis first, rather than relying on testing?

    Perimeters apply to every request, including forgotten jobs and rare paths that tests don't cover. Real traffic from CloudTrail data events shows every request that would be denied, so exceptions can be written before anything breaks.

  6. Compare how Google Cloud and AWS stop data being copied to an outside storage bucket.

    Google Cloud: a VPC Service Controls perimeter around the projects blocks copying data to resources outside it. AWS: an SCP (and endpoint policies) denying requests whose aws:ResourceOrgID isn't your organisation.

23Auditing and detecting misuse

  1. Why should the organisation trail's bucket live in a separate security account?

    So that someone who compromises a workload account, or its administrators, can't delete or alter the record of what they did. Combined with the SCP protecting the trail and Object Lock, the evidence survives.

  2. Which tool answers “can anyone outside our organisation read this bucket?”, and why not CloudTrail?

    IAM Access Analyzer, which reasons about what policies allow. CloudTrail records what happened, so it can only show access that has already been used.

  3. The watch list paged at 03:00 for a root sign-in to the management account. Write the first three steps.

    Ask the people who can use root (the vault holders) whether it was them; if not, treat it as an incident: check what the session did in CloudTrail and reset root's password and MFA through the recovery path; then review how the credentials could have been used and by whom.

  4. Why does a new client federation connection in your own login service belong on the same watch list as AWS events?

    It changes who can sign in to your application as a business customer's staff, as powerful as an IAM trust change, and no AWS tool can see it. Its audit event must be shipped and alerted on like any other identity change.

  5. Design the routing for Table 23.1: which events page, which create tickets, and who reviews tickets?

    Page for events that could mean an active attacker with power now: root, break-glass, open trust, high-severity GuardDuty. Tickets for changes that need checking within a day: new federation, assignments outside the tool, key policy changes, trail tampering attempts, new users or keys. The platform team reviews tickets each morning, with a named owner per rule.

  6. Compare where you'd look for a suspicious new administrator on Azure and on AWS.

    Azure: Entra ID audit logs (role assignments and PIM activations) and the activity log for Azure RBAC. AWS: CloudTrail for Identity Center assignment and permission set changes and IAM policy changes, plus the identity provider's own audit log.

24Identity as code and least privilege at scale

  1. Name three things a repository gives you for identity that a console doesn't.

    Any three of: one source of truth, so drift is detectable; review before change with named approvers; history that answers audit questions; automatic checks on every change; reuse through modules.

  2. Why does check-no-new-access suit trust policies better than a text diff?

    It reasons about what the policy allows, not how it's written. A text diff of one changed condition can't tell whether the role is now open to more principals; the check proves whether any new access was granted, regardless of wildcards or rewording.

  3. Policy generation from 90 days of activity proposes a narrower policy for finance-reports. What would you check before merging it?

    Whether every scheduled job ran in the window: quarter-end and year-end reports may need actions not seen in 90 days. Also replace placeholder resources with real ARNs, and keep conditions the old policy had (such as aws:ViaAWSService for KMS).

  4. An engineer can edit .github/workflows/apply.yml in a branch. How could that become organisation admin, and what stops it?

    If the apply role trusted any branch, their workflow could assume it and do anything. It's stopped by trusting only main in a protected environment, branch protection with two approvals, and code owners on workflow files.

  5. Design the review rule for a pull request that changes wmsb-nightly-file's trust policy.

    Checks: lint, validate, and check-no-new-access against main. If it fails, the new-access label adds the security reviewer; approvals from platform and security, neither being the author. The plan is posted, and the perimeter exception tag is checked as well, since the RCP depends on it.

  6. Compare how a Terraform mistake can lock you out on Google Cloud and how break-glass protects you on AWS.

    On Google Cloud, an authoritative google_project_iam_policy replaces all bindings, so a missing one removes access, perhaps your own. On AWS, a bad SCP or permission set could do the same, but the break-glass users and break-glass-admin sit outside the pipeline and are excepted in the guardrails, so there's a way back in.

25Capstone: Larder's identity end to end

  1. What four things does the inventory record for each kind of principal?

    Who it is, how it proves its identity, what it gets access to, and who owns it.

  2. Why might break-glass work in a test but fail in a region outage?

    If the test only simulated SSO being down, it may still have relied on the primary region: the STS endpoint the CLI used, a runbook or vault stored there, or a region-restricting SCP that doesn't allow the recovery region. Test it with the region treated as gone.

  3. In the laptop tabletop, why doesn't the identity perimeter stop the attacker, and what does?

    The identity perimeter only allows Larder's identities, and the attacker is using a Larder identity. What limits them: least privilege (ViewOnly can't read objects), TEAM's approvals, the network rule on restricted buckets, and short sessions. Binding sessions to managed devices would stop the stolen cookie working at all.

  4. Larder adds a city in Switzerland. List the identity questions you'd raise.

    Does ADR 0026's trigger (a city outside the EU) fire, and with it a new region? Data-protection rules for the new market and where data may live; any new region in SCPs, keys, detection and perimeter; new staff in the IdP with the same joiner process; new partners (stores, payment providers) with their own access to inventory and review.

  5. Design a tabletop for “a vendor's AWS account is compromised”, using WMS B as the vendor.

    The attacker has WMS B's delivery role and the external ID. They can reach only wmsb-nightly-file: PutObject on one prefix. Questions: what if they upload a malicious file (validate files before import); would Larder notice (unusual time or address for the upload, file validation failures); how to cut them off (remove the trust, or deny with a condition, while WMS B rebuilds); who calls WMS B, and is it in the contract?

  6. Compare what “just in time” looks like at the three big providers.

    AWS has no built-in feature for it; tools like TEAM create and remove Identity Center assignments. Azure has Entra PIM, with eligible role assignments activated for a period, with approval. Google Cloud has Privileged Access Manager, with entitlements granting roles temporarily on request.
