Identities for workloads

Code needs credentials too: to read a bucket, send an email, publish an event. The worst place for them is where people usually put them first: in the code, an environment file, a container image. On AWS, the platform hands every workload short-lived credentials for its own role, refreshes them automatically, and never lets anyone see a key. This chapter shows how that works on EC2, ECS and Lambda, and how to stop an attacker borrowing those credentials through your own application.

By the end you can

  • Explain how code on EC2, ECS and Lambda gets role credentials without any key being stored.
  • Explain why the instance metadata service is a target, and require IMDSv2.
  • Tell an ECS task role from a task execution role, and give each the right permissions.
  • Give each workload its own narrow role, owned by a team.
  • Choose the right identity for workloads outside AWS.

Before you start

  • Roles, service roles, iam:PassRole and the credential chain (Chapter 8).
  • Writing a least-privilege policy (Chapter 9, 9.9).

At Larder

On Monday 15 March 2027, an email arrived at security@larder.example from a security researcher. Larder Core, the original application, still running on three virtual machines, has a small endpoint that resizes product images: /img?url=…. It fetched any URL it was given. The researcher had asked it for http://169.254.169.254/latest/meta-data/iam/security-credentials/, and it had politely answered with a role name: larder-core. “I stopped there,” the email said. “The next request would have returned that role's credentials.”

The role had AmazonS3FullAccess and full access to the email-sending service. Section 15.9 shows what Larder did that afternoon, and the next week.

15.1The problem with keys in code

A workload is any software that calls cloud APIs: an application, a background job, a function. It needs credentials, and the tempting answer is an access key in a configuration file or environment variable. That key is long-lived (Chapter 1), so it ends up in backups, container images, crash dumps, logs and Git history, and works for whoever finds it until someone rotates it, which nobody does because rotation might break production.

On AWS the answer is always the same: give the workload a role, and let the platform deliver that role's temporary credentials to the code at run time (Chapter 8). The SDK's credential chain finds them automatically and refreshes them before they expire. Nobody, not the developer, not the deployment, not the attacker who reads the config, ever sees a key.

15.2How it works on EC2

An EC2 instance gets a role through an instance profile, a container for one role, attached at launch or later. Inside the instance, the instance metadata service (IMDS), reachable at the link-local address 169.254.169.254, serves that role's current temporary credentials. AWS rotates them automatically; the SDK fetches new ones before the old ones expire.

15.3Protecting the metadata service: IMDSv2

“Only answers requests from inside the instance” is exactly what makes IMDS a target. Any bug that makes your application send a request for an attacker, a server-side request forgery (SSRF) like Larder's image proxy, an open proxy, a misconfigured firewall, comes from inside the instance. With the original metadata service, IMDSv1, a single GET returns the role's credentials, and an attacker can then use them from anywhere.

IMDSv2 makes the metadata service session-oriented:

  1. The caller first asks for a session token with an HTTP PUT to /latest/api/token, with a header saying how long the token should live.
  2. Every metadata request must then carry that token in a header.

Most SSRF bugs can only make the application send a GET to a URL; they can't choose the method or add headers. IMDSv2 also refuses to issue tokens to requests carrying an X-Forwarded-For header (a sign of a proxy), and the token response has a hop limit, the network packet's time-to-live: with a hop limit of 1, the response can't travel beyond the instance itself, so it can't reach a container running behind the host's network. Set it to 2 only if containers on the instance genuinely need the instance's role, and usually they shouldn't (15.4).

Key idea

Require IMDSv2 on every instance. It costs nothing, every current SDK supports it, and it turns the commonest cloud SSRF from a credential leak into an error.

Make it the default everywhere: set HttpTokens=required on running instances, in launch templates and AMIs, and as the account's default for new instances in every region. Later, deny launching instances without it, with the condition key ec2:MetadataHttpTokens in an SCP (Chapter 20). For defence in depth, condition keys such as aws:EC2InstanceSourceVPC let a policy accept an instance's credentials only when they're used from inside your own network (Chapter 22).

15.4ECS: two roles per task

Containers on ECS (on EC2 or on Fargate) don't use the instance's metadata service for their own identity. Each task definition names up to two roles, and confusing them is one of the commonest ECS mistakes:

Each task gets its own credentials, even when several tasks share an instance. On ECS on EC2, block containers from reaching the instance's metadata service (the ECS agent setting ECS_AWSVPC_BLOCK_IMDS, or a hop limit of 1), so a container can't step up to the instance's role.

15.5Lambda

A Lambda function has an execution role. Lambda assumes it and places the temporary credentials in the function's environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN) for the SDK to find. There's no metadata service to forge requests to, but there is an environment to leak: a function that echoes its environment in an error message, or reads arbitrary files (Linux exposes the environment at /proc/self/environ), hands out its role's credentials. Never log the environment, and give every function its own role.

15.6One role per workload

  • One role per workload, never one shared “app role”: a leak or a bug in one service then exposes only that service's permissions, and CloudTrail tells you which service did what (Chapter 1).
  • Least privilege, with the method from Chapter 9: list what the code does, map to actions, narrow resources, validate, test, watch.
  • An owning team, as a tag (team=dispatch), so the role isn't orphaned when people move (Chapter 13).
  • Pass only what you mean to. Whoever launches the workload needs iam:PassRole on its role, and only its role (Chapter 8, 8.7).

Watch out: “it already has a role” isn't the end

Moving from keys to roles removes the long-lived secret, but not the blast radius. A role with AmazonS3FullAccess is just as dangerous in an attacker's hands for the few hours its credentials last; they need minutes. Larder Core's problem wasn't a key; it was a broad role reachable through a bug.

15.7Workloads outside AWS

Code that runs elsewhere still shouldn't hold access keys:

  • CI/CD systems and other clouds that issue OIDC tokens exchange them for role sessions (AssumeRoleWithWebIdentity), as Chapter 17 does for GitHub Actions.
  • Servers in your own data centre or stores can use IAM Roles Anywhere: they authenticate with an X.509 certificate issued by a certificate authority you register with AWS, and get role sessions in return. The certificate's private key, ideally in a hardware module, replaces the access key.
  • Third-party SaaS that acts in your account gets a cross-account role with an external ID (Chapter 21).

On Azure

A managed identity is a service principal Azure creates and rotates for you. System-assigned identities live and die with one resource; user-assigned identities are separate resources you can share between, say, a pool of identical VMs. Code requests tokens for a specific resource (Storage, Key Vault, Graph) from the local metadata endpoint, which requires a Metadata: true header, the same anti-SSRF idea as IMDSv2's token.

On Google Cloud

VMs and serverless services run as a service account; tokens come from the metadata server, which requires a Metadata-Flavor: Google header. Avoid the Compute Engine default service account, which in many projects has the broad Editor role: give each workload its own service account with narrow roles, and stop new projects granting Editor to it with the organisation policy for automatic default grants.

15.9At Larder: an image proxy and a broad role

At Larder: solved

Within the hour, Ben's team limited the image proxy to Larder's own image hosts and made it refuse private and link-local addresses. Eli required IMDSv2 on the three Larder Core instances, with a hop limit of 1, which took one command each and no restart; the application's SDK had supported it for years. He set IMDSv2 as the default for new instances in both accounts' regions, and searched CloudTrail for any use of larder-core's credentials from outside Larder's network in the last 90 days: there was none. Larder thanked the researcher, and started a page about how to report vulnerabilities.

The next week, larder-core lost AmazonS3FullAccess and full email-service access, replaced by a policy written with the method from Chapter 9: two buckets, one sending identity, one queue. The same review removed the SSH key the engineers had shared since 2024 and the rule letting the office reach port 22: shell access now goes through Session Manager, which is authorised by Identity Center sessions and logged (Chapter 14).

15.10Lab: SSRF against IMDSv1 and IMDSv2

Lab 15 · A fake metadata service and a real bug

You'll run a small imitation of the instance metadata service on your own machine, then call it two ways: like the AWS SDK does, and like an SSRF bug does, with tokens optional and then required. You need Python 3; for the optional step, the AWS CLI. Cost: nothing. The credentials in it are fake, and it listens only on 127.0.0.1.

imds.pyPython 3.8+

# imds.py · a fake instance metadata service, an SSRF bug, and what IMDSv2 changes
# Usage: python3 imds.py optional   (IMDSv1 allowed)   |   python3 imds.py required   (IMDSv2 only)
import json, secrets, sys, threading, urllib.request
from http.server import BaseHTTPRequestHandler, HTTPServer

MODE = sys.argv[1] if len(sys.argv) > 1 else "optional"
BASE = "http://127.0.0.1:8169"                 # the real one is http://169.254.169.254
ROLE = "larder-core"
CREDS = {"Code": "Success", "AccessKeyId": "ASIAEXAMPLEFAKEKEY01", "SecretAccessKey": "fake/secret",
         "Token": "fake-session-token", "Expiration": "2027-03-15T16:00:00Z"}
TOKENS = set()

class IMDS(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def reply(self, code, body):
        self.send_response(code)
        self.end_headers()
        self.wfile.write(body.encode())

    def do_PUT(self):
        if self.path != "/latest/api/token" or "X-aws-ec2-metadata-token-ttl-seconds" not in self.headers:
            return self.reply(400, "bad request")
        if "X-Forwarded-For" in self.headers:          # the real IMDS refuses tokens to proxied requests
            return self.reply(403, "forbidden")
        token = secrets.token_urlsafe(24)
        TOKENS.add(token)
        self.reply(200, token)

    def do_GET(self):
        token = self.headers.get("X-aws-ec2-metadata-token")
        if token not in TOKENS and (MODE == "required" or token is not None):
            return self.reply(401, "unauthorized")
        if self.path == "/latest/meta-data/iam/security-credentials/":
            return self.reply(200, ROLE)
        if self.path == f"/latest/meta-data/iam/security-credentials/{ROLE}":
            return self.reply(200, json.dumps(CREDS))
        self.reply(404, "not found")

def fetch_image(url):
    """Larder Core's product-image proxy: fetches whatever URL a request names. The SSRF bug."""
    try:
        with urllib.request.urlopen(url, timeout=2) as r:
            return r.read().decode()[:60]
    except Exception as e:
        return f"error: {e}"

def sdk_get_credentials():
    """What the AWS SDK does: get a session token with PUT, then read with it."""
    put = urllib.request.Request(f"{BASE}/latest/api/token", method="PUT",
                                 headers={"X-aws-ec2-metadata-token-ttl-seconds": "21600"})
    token = urllib.request.urlopen(put, timeout=2).read().decode()
    get = urllib.request.Request(f"{BASE}/latest/meta-data/iam/security-credentials/{ROLE}",
                                 headers={"X-aws-ec2-metadata-token": token})
    return json.loads(urllib.request.urlopen(get, timeout=2).read())["AccessKeyId"]

if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", 8169), IMDS)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    print(f"metadata service, tokens {MODE}")
    print("  SDK, with a token:      ", sdk_get_credentials())
    print("  attacker via the proxy: ", fetch_image(f"{BASE}/latest/meta-data/iam/security-credentials/"))
    print("                          ", fetch_image(f"{BASE}/latest/meta-data/iam/security-credentials/{ROLE}"))
    server.shutdown()
  1. Tokens optional (IMDSv1 allowed). Run python3 imds.py optional: 
    metadata service, tokens optional
  SDK, with a token:       ASIAEXAMPLEFAKEKEY01
  attacker via the proxy:  larder-core
                           {"Code": "Success", "AccessKeyId": "ASIAEXAMPLEFAKEKEY01", "
    Two GETs through the image proxy: the first finds the role's name (the researcher's request), the second returns its credentials.
  2. Tokens required (IMDSv2). Run python3 imds.py required: 
    metadata service, tokens required
  SDK, with a token:       ASIAEXAMPLEFAKEKEY01
  attacker via the proxy:  error: HTTP Error 401: Unauthorized
                           error: HTTP Error 401: Unauthorized
    The application still works, because the SDK does the PUT first. The bug is still there, but it no longer leads anywhere.
  3. Break it on purpose. Make the proxy “smarter”: let it accept a method and headers from the request (urllib.request.Request(url, method=…, headers=…)) and use it to do the PUT. Now it can get a token, unless it adds X-Forwarded-For, as many proxies do: add that header and the token request is refused with 403. This is why SSRF fixes belong in the application too: IMDSv2 is a seat belt, not a reason to keep the bug.
  4. Optional: check your account. List instances that still allow IMDSv1, and make IMDSv2 the default for new instances in the current region (free, nothing is launched): 
    aws ec2 describe-instances --query \
  'Reservations[].Instances[?MetadataOptions.HttpTokens==`optional`].[InstanceId]' --output text
aws ec2 modify-instance-metadata-defaults --http-tokens required --http-put-response-hop-limit 1
aws ec2 get-instance-metadata-defaults
    To fix one instance: aws ec2 modify-instance-metadata-options --instance-id i-… --http-tokens required --http-put-response-hop-limit 1.

✓Chapter summary

  • Workloads get roles, and the platform delivers short-lived credentials; no key is stored or seen.
  • EC2: instance profile → role → credentials from the metadata service, refreshed by the SDK.
  • IMDSv2 (PUT for a token, token on every request, hop limit) turns SSRF credential theft into an error. Require it everywhere.
  • ECS: a task role for the app, a task execution role for the agent. Lambda: an execution role, with credentials in the environment.
  • One narrow role per workload, owned by a team; restrict who can pass it.
  • Outside AWS: OIDC federation, IAM Roles Anywhere, cross-account roles; never access keys.

Key terms

Workload identity
The identity software uses to call cloud APIs.
Instance profile
The container that attaches a role to an EC2 instance.
Instance metadata service
The link-local endpoint that serves an instance's details and role credentials.
IMDSv2
The session-oriented metadata service: PUT for a token, then token on each request.
SSRF
Server-side request forgery: making a server send requests on an attacker's behalf.
Hop limit
How many network hops IMDSv2's token response may travel.
Task role / execution role
An ECS task's role for its code, and the ECS agent's role for starting it.
IAM Roles Anywhere
Role sessions for workloads outside AWS, authenticated with X.509 certificates.

Check your understanding

  1. Where does code running on an EC2 instance with an instance profile get its credentials, and who rotates them? recall

    Show answer

    From the instance metadata service at 169.254.169.254. AWS issues and rotates the role's temporary credentials; the SDK fetches fresh ones before the old ones expire.

  2. Explain why IMDSv2 stops a typical SSRF bug from stealing credentials, but doesn't make the bug harmless. explain

    Show answer

    A typical SSRF bug can only make the server send a GET to a chosen URL; IMDSv2 needs a PUT with a special header first, and refuses proxied token requests. But the bug can still reach other internal services, so it must be fixed in the application too.

  3. An ECS task can't start: “unable to pull image”. Which role do you look at? And if the app gets “access denied” writing to S3? apply

    Show answer

    Pulling the image is the task execution role's job (ECR permissions). Writing to S3 is the application's job, so the task role.

  4. A Lambda function returns its full environment in an error message to the caller. Why is that a credential leak? apply

    Show answer

    Lambda places the execution role's temporary credentials in environment variables. Anyone who sees the error gets a working key, secret and session token until they expire.

  5. Design the identities for a new service with an API on ECS, a nightly batch job on Lambda, and a script on a store's back-office PC. design

    Show answer

    An ECS task role and execution role for the API; a separate execution role for the batch function; IAM Roles Anywhere with a device certificate (or a narrowly scoped OIDC federation) for the PC. Each role narrow, tagged with the owning team, with PassRole restricted to the deployment pipeline.

  6. Compare how Azure and Google Cloud protect their metadata endpoints from SSRF with how AWS does. compare

    Show answer

    Azure requires a Metadata: true header and Google a Metadata-Flavor: Google header, which a GET-only SSRF usually can't add. AWS's IMDSv2 requires a PUT to obtain a session token, then a token header on every request, plus a hop limit and a refusal of proxied token requests.
