Passwords, MFA and passkeys

Authentication is where most breaches start: a reused password, a code typed into the wrong site, a help desk talked into a reset. This chapter explains why passwords fail and how to store them so a leak doesn't hurt, then compares second factors by the one property that matters most: whether they stop phishing. It ends with passkeys, which do.

By the end you can

  • Name the four ways passwords get broken, and the defence for each.
  • Store passwords with a salted, slow hash, and choose its settings.
  • Explain how a one-time code is calculated, and why it can still be phished.
  • Explain how passkeys stop phishing, and where they still need care.
  • Choose authentication for customers, staff and administrators.

At Larder

On the night of Saturday 21 November 2026, Larder's login endpoint received about 40,000 sign-in attempts in four hours, from about 2,000 different addresses. Each tried one email address and one password, and moved on. 310 of them worked. By the time the pattern was spotted on Sunday morning, the attackers had used saved payment methods to send 41 orders to addresses that weren't the customers'.

Nobody had stolen anything from Larder. Its password database was intact, and properly hashed since Jasper first built it. The attackers had a list of email addresses and passwords leaked from other sites, and 310 Larder customers had used the same password here. Section 2.1 names the attack; section 2.9 shows what Larder changed.

2.1How passwords fail

A password is a secret that the user and the system both know. That design has four weak points, and it helps to keep them apart because each has a different defence:

Table 2.1 · Four ways passwords get broken
AttackHow it worksMain defence
GuessingTry common passwords against many accounts (“password spraying”), or many passwords against one.Rate limits and lockouts; reject common passwords (2.3)
Credential stuffingReplay email–password pairs leaked from other sites, betting on reuse.Check against breached passwords; MFA; passkeys
PhishingA fake site, email or call gets the user to type the password, and often the second factor, for the attacker.Phishing-resistant factors (2.4, 2.6)
Stolen databaseThe attacker copies your password store and cracks it offline, at their own speed.Salted, slow hashing (2.2)

Larder's Saturday night was credential stuffing. It's cheap for attackers, because billions of leaked pairs circulate, and it works because people reuse passwords. Strong hashing doesn't help against it: the attacker isn't attacking your database, just logging in. Only the defences in the last column do.

2.2Storing passwords: salted, slow hashes

You must be able to check a password without being able to read it. The tool is a hash function: a one-way calculation that turns any input into a fixed-size fingerprint. You store the fingerprint; at login you hash what was typed and compare. Never store passwords as they are, and never encrypt them: encryption can be reversed by anyone who gets the key, and in a breach they often do.

A plain hash such as SHA-256 isn't enough, for two reasons:

  • It's fast. Fast is good for checking files and bad for passwords: an attacker with your database can try billions of guesses a second on graphics cards. In the lab, one laptop core manages millions.
  • It's the same for everyone. Two customers with the password winter2026 get the same hash, so cracking one cracks both, and precomputed tables of common passwords work instantly.

The fix has two parts. A salt, a random value generated for each password and stored next to it, makes every hash unique even for identical passwords. A password hashing function is deliberately slow and, in modern designs, needs lots of memory, so that each guess costs real time and real hardware.

Table 2.2 · Password hashing functions, in order of preference
FunctionStarting settings (OWASP, at the time of writing)Notes

scryptN = 217, r = 8, p = 1 (128 MiB)Memory-hard; in Python's standard library

Pick the slowest settings your login servers can afford at peak, and measure: if a check takes 50 ms of one core, a login spike of 100 attempts a second needs five cores just for hashing. Better still, don't store passwords at all: use a managed identity service (Amazon Cognito, Microsoft Entra External ID, Google's Identity Platform, or a specialist provider), which does this for you.

2.3Password rules that actually help

Many familiar password rules make things worse. People forced to add a symbol write Password1!; people forced to change every 90 days write Winter2026, then Spring2027. NIST's Digital Identity Guidelines (SP 800-63B, revised in 2025) reflect what the evidence shows:

  • Length over complexity. At least 15 characters when a password is the only factor, at least 8 when it's combined with MFA; allow at least 64. No rules about mixing character types.
  • Check against breached and common passwords at sign-up and at password change, and reject matches. Services such as Have I Been Pwned's Pwned Passwords let you check without revealing the password: you send the first five characters of its SHA-1 hash and compare the returned list yourself.
  • No forced periodic changes. Force a change only when there's evidence of compromise.
  • Let password managers work: allow pasting, and don't block autofill.
  • Limit failed attempts per account, and watch failure rates across all accounts, which is how stuffing shows up.

2.4Second factors, and which ones stop phishing

Multi-factor authentication adds something you have to something you know. All of the factors below stop credential stuffing, because the attacker has the password but not the phone or key. They differ sharply against phishing.

Table 2.3 · Second factors compared
FactorHow it worksPhishingOther weaknesses
SMS or voice codeA code sent to your phone numberPhishable: you type it into the fake siteSIM swapping; the code travels over the phone network
Authenticator app code (TOTP)A code calculated from a shared secret and the time (2.5)PhishableThe secret sits on the server too
Push approval“Is this you signing in?” on a phone appPhishable; and push fatigue: attackers send prompts until someone taps yesNumber matching (type the number shown on screen) helps a lot
Security key or passkey (FIDO2/WebAuthn)The device signs a challenge with a private key for this exact site (2.6)Resistant: the signature only works for the real siteAccount recovery must be as strong (2.7)

Why can codes be phished? Because a code is just a value. A real-time phishing proxy sits between the user and the real site: it shows the real login page, passes along everything the user types, including the code, and keeps the session cookie the real site sends back. 2.5How a one-time code is made

An authenticator app's six-digit code is a TOTP, a time-based one-time password (RFC 6238). It's worth knowing exactly how it works, because it explains both its strengths and its limits:

  1. At enrolment, the server generates a random secret and shows it as a QR code. The app stores it; so does the server.
  2. Both sides count time steps: the Unix time divided by 30, rounded down. Every 30 seconds, the number goes up by one.
  3. Both compute an HMAC (a keyed hash, here with SHA-1) of the time step, using the secret as the key.
  4. Both take four bytes from the result, at a position chosen by its last byte, and keep the last six decimal digits. That's the code.

The server accepts the current code, usually plus or minus one step for clock drift, and should refuse a code that's already been used. Nothing is sent anywhere, which is why it works offline. But the server must store the secret in a form it can use, so a server breach exposes every secret; and a code is a value, so it can be phished.

2.6Passkeys and WebAuthn

A passkey replaces the shared secret with a key pair. It's built on the FIDO2 standards; the part browsers implement is called WebAuthn. At registration, the user's device creates a new key pair just for this site. The private key never leaves the device (or the user's password manager or platform keychain); the site stores only the public key.

At sign-in:

  1. The site sends a random challenge.
  2. The browser asks the device to sign it, and adds the origin it's actually on (https://larder.example) to what gets signed. The user unlocks the key with a fingerprint, face or PIN, which never leaves the device.
  3. The site checks the signature with the stored public key, and checks that the origin is its own.

Key idea

Passkeys resist phishing because the browser, not the user, decides which site a signature is for. There's no secret for the user to type into the wrong place.

There's also nothing worth stealing on the server: a database of public keys is useless to an attacker. Passkeys come in two kinds. Synced passkeys are backed up by the platform (Apple, Google, Microsoft or a password manager) across a person's devices; they're convenient and right for most customers. Device-bound passkeys live on one hardware security key and can't be copied; use them for administrators, where you want to know exactly where the key is.

Passkey or MFA?A passkey combines something you have (the device) with something you are or know (the unlock), so on its own it counts as phishing-resistant MFA. A security key used as a second factor after a password gives the same protection.

2.7Recovery: the back door

Every authentication system has a way in for people who've lost their phone or forgotten their password, and attackers know it. A strong passkey is worthless if “I lost my phone” to the help desk gets a new one by email. Design recovery as carefully as login:

  • Offer several registered factors (two passkeys, or a passkey and recovery codes), so losing one isn't a recovery event.
  • Give one-time recovery codes at enrolment, to be stored offline.
  • For staff, recovery goes through verified identity: a video call with a manager who knows them, or showing ID in person, never a phone call alone. Help-desk social engineering is behind many well-known breaches.
  • Notify on every change of factor or email address, through the old channel as well as the new.
  • Slow down sensitive changes after recovery: no payout-address changes for 24 hours, for example.

2.8Across providers

For your cloud accounts, you won't store passwords yourself: the provider or your identity provider does. What you choose is which factors are allowed, and for whom.

On Azure

Microsoft Authenticator push uses number matching by default (the user types the number shown on the sign-in screen), which blunts push-fatigue attacks. For administrators, a Conditional Access policy requiring the built-in phishing-resistant MFA authentication strength allows only passkeys, FIDO2 keys, Windows Hello for Business and certificates.

On Google Cloud

Google Cloud console access is a Google account sign-in, so the controls live in the Cloud Identity or Workspace admin console: enforce 2-Step Verification, and for administrators allow only security keys. Google's Advanced Protection Program goes further for the highest-risk people.

2.9Choosing for customers, staff and administrators

There's no single right answer, because the people and the risks differ. A reasonable baseline:

  • Customers: offer passkeys and make them the easy path; keep passwords with breached-password checks and rate limits; ask for extra verification on risky actions (a new delivery address with a saved card) rather than on every login.
  • Staff: single sign-on with MFA for everything (Chapter 12); push with number matching at minimum, passkeys preferred.
  • Administrators and production access: phishing-resistant factors only: device-bound passkeys or hardware security keys, two per person.

At Larder: what changed

By Sunday afternoon, the 310 accounts were locked and their owners emailed; the 41 orders were refunded, and Lena reported the incident to the Dutch data protection authority within the 72 hours GDPR allows. In the following two weeks, Dee's mobile team and Eli shipped four changes: failed-login limits per account and per address, with an alert when the overall failure rate jumps; a breached-password check at sign-up, login and password change; a step-up check (a code sent to the account's email) before a saved card can pay for an order to a new address; and passkeys in the app and on the web. Within a month, 18 % of active customers had added a passkey.

For staff, the incident started a harder conversation. Engineers used push approvals without number matching, and the ops user from Chapter 1 had no second factor at all. Eli ordered two hardware security keys for each of the nine people with production access; Chapter 12 puts them to use.

2.10Lab: hash a password, and make a one-time code

Lab 2 · Slow hashes, salt and TOTP

You'll measure how much slower a password hash is than a plain hash, see what salt does, store and verify a password, then build TOTP from scratch, check it against the standard's test vectors and, if you like, compare it with your own authenticator app. You need Python 3.8 or later, nothing else. Cost: nothing.

passwords.pyPython 3.8+ (hashlib.scrypt needs OpenSSL, as standard builds have)

# passwords.py · fast hashes, slow hashes, salt, and a storage format
import hashlib, hmac, os, time

def fast(password):
    return hashlib.sha256(password.encode()).hexdigest()

def slow(password, salt, n=2**14, r=8, p=1):
    return hashlib.scrypt(password.encode(), salt=salt, n=n, r=r, p=p,
                          maxmem=64 * 1024 * 1024).hex()

def guesses_per_second(fn, seconds=1.0):
    count, start = 0, time.perf_counter()
    while time.perf_counter() - start < seconds:
        fn()
        count += 1
    return count / seconds

# 1. How fast can an attacker try guesses against each kind of hash?
salt = os.urandom(16)
print(f"sha256: {guesses_per_second(lambda: fast('correct horse')):>12,.0f} guesses/s")
print(f"scrypt: {guesses_per_second(lambda: slow('correct horse', salt)):>12,.0f} guesses/s")

# 2. Two customers with the same password
print("same without salt:", fast("winter2026") == fast("winter2026"))
print("same with salt:   ", slow("winter2026", os.urandom(16)) == slow("winter2026", os.urandom(16)))

# 3. What you store, and how you check a login against it
def store(password):
    salt = os.urandom(16)
    return f"scrypt$16384$8$1${salt.hex()}${slow(password, salt)}"

def verify(password, stored):
    _, n, r, p, salt, digest = stored.split("$")
    attempt = slow(password, bytes.fromhex(salt), int(n), int(r), int(p))
    return hmac.compare_digest(attempt, digest)

record = store("winter2026")
print(record[:40] + "…")
print("right password:", verify("winter2026", record))
print("wrong password:", verify("Winter2026", record))

totp.pyPython 3.8+

# totp.py · time-based one-time passwords (RFC 6238), from scratch
import base64, hashlib, hmac, struct, time

def hotp(key, counter, digits=6):
    mac = hmac.new(key, struct.pack(">Q", counter), hashlib.sha1).digest()
    offset = mac[-1] & 0x0F                                  # dynamic truncation
    code = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(code % 10 ** digits).zfill(digits)

def totp(key, at=None, step=30, digits=6):
    now = time.time() if at is None else at
    return hotp(key, int(now // step), digits)

def check(key, code, at=None, window=1):
    now = time.time() if at is None else at
    return any(hmac.compare_digest(totp(key, now + d * 30), code)
               for d in range(-window, window + 1))

# 1. The test vectors from RFC 6238, appendix B (SHA-1, 8 digits)
key = b"12345678901234567890"
for t, want in [(59, "94287082"), (1111111109, "07081804"), (1234567890, "89005924")]:
    got = totp(key, t, digits=8)
    print(f"{t:>10}  {got}  {'ok' if got == want else 'WRONG'}")

# 2. A secret like the one inside an authenticator app's QR code
secret = base64.b32encode(b"larder-lab-not-real!").decode()
print("otpauth://totp/Larder:lab?secret=" + secret + "&issuer=Larder")
code = totp(base64.b32decode(secret))
print("code now:", code, "| accepted:", check(base64.b32decode(secret), code))
print("code from 5 minutes ago accepted:",
      check(base64.b32decode(secret), totp(base64.b32decode(secret), time.time() - 300)))
  1. Run it with python3 totp.py. The first three lines must say ok: your code now matches the standard. Then: 
    otpauth://totp/Larder:lab?secret=NRQXEZDFOIWWYYLCFVXG65BNOJSWC3BB&issuer=Larder
code now: 960043 | accepted: True
code from 5 minutes ago accepted: False
    Your code will differ, because the time does.
  2. Compare with a real app. In any authenticator app, add an account manually with the secret NRQXEZDFOIWWYYLCFVXG65BNOJSWC3BB, then run the script again: both show the same code. Delete the account from the app afterwards; this secret is printed in a book, so it protects nothing.
  3. Break it on purpose. Change window=1 to window=10 in check: a code from five minutes ago is now accepted, giving a phisher ten minutes instead of one. Then change step=30 to step=60 in totp and compare with the app: the codes no longer match, because both sides must agree on every parameter.

Stretch goal. Make check remember the last time step each secret was used, and refuse a code from that step or earlier. That's the replay protection RFC 6238 asks for.

✓Chapter summary

  • Passwords fail four ways: guessing, stuffing, phishing and stolen databases. Each needs its own defence.
  • Store passwords with a salt and a slow, memory-hard hash (Argon2id or scrypt), with the settings stored alongside; or don't store them at all.
  • Good password policy is length, breached-password checks and rate limits, not composition rules or forced changes.
  • Every second factor stops credential stuffing; only passkeys and security keys stop phishing.
  • A TOTP code is an HMAC of the time with a shared secret: offline and simple, but phishable.
  • Passkeys sign a challenge bound to the real origin; the server stores only public keys.
  • Recovery is part of authentication. Make it as strong as login.

Key terms

Credential stuffing
Logging in with username–password pairs leaked from other sites.
Salt
A random per-password value hashed with it, so identical passwords give different hashes.
Password hashing function
A deliberately slow, often memory-hard hash such as Argon2id, scrypt or bcrypt.
MFA
Multi-factor authentication: two or more different kinds of factor.
TOTP
Time-based one-time password: an HMAC of the current 30-second step and a shared secret.
Phishing-resistant
An authenticator whose output can't be relayed to a site other than the one it was made for.
Passkey
A FIDO2/WebAuthn credential: a per-site key pair whose private key stays on the user's device or keychain.
Origin
The scheme, host and port of a web page, such as https://larder.example.

Check your understanding

  1. Larder's password hashes were never stolen, yet 310 accounts were taken over. Name the attack and two defences that would have helped. recall

    Show answer

    Credential stuffing. Breached-password checks, MFA or passkeys, and rate limits with alerting on the overall failure rate. Strong hashing doesn't help, because the attacker logs in normally.

  2. Why does adding a salt not make a single password any harder to crack, and why use it anyway? explain

    Show answer

    The salt is stored next to the hash, so an attacker cracking one record uses it. Its value is across records: every password must be attacked separately, identical passwords aren't revealed, and precomputed tables don't work.

  3. A login server checks 200 passwords a second at peak, and an Argon2id check takes 40 ms of CPU. How many cores does hashing need? apply

    Show answer

    200 × 0.04 s = 8 core-seconds per second, so eight cores, plus headroom for spikes and attacks (which also arrive as login attempts).

  4. An administrator uses an authenticator app code. Explain how a real-time phishing proxy gets into their account, and what would stop it. explain

    Show answer

    The proxy shows the real login page, relays the password and code to the real site as they're typed, and keeps the session cookie the real site returns. A passkey or security key stops it, because the browser signs for the fake origin and the real site rejects the signature.

  5. Design authentication for Larder's three groups: customers, pickers on shared store tablets, and engineers with production access. design

    Show answer

    Customers: passkeys first, passwords with breached checks and rate limits, step-up for risky actions. Pickers: personal badges or short PINs on a managed device, with short sessions, since the tablet is shared but the identity shouldn't be. Engineers: single sign-on with hardware security keys or device-bound passkeys, two each, and recovery through a verified call with their manager.

  6. Compare how you'd require phishing-resistant MFA for administrators on Azure and on Google Cloud. compare

    Show answer

    Azure: a Conditional Access policy for the administrator roles requiring the phishing-resistant MFA authentication strength. Google Cloud: in the Cloud Identity or Workspace admin console, enforce 2-Step Verification with security keys only for the administrators' organisational unit.
