Appendix

A

Policy cookbook

The policies from this book for the jobs you'll meet most, collected in one place, with what each is for and what to change. Larder's names, account IDs and organisation ID are placeholders: replace them with yours, validate with IAM Access Analyzer (Chapter 9), and try each on staging before production.

Before you copy

Every policy here is valid JSON and was checked against the evaluation rules in Chapter 10, but a policy is only right for the job it was written for. Read each line, replace every ARN, and keep the conditions: they do most of the work. Statements shown on their own (without Version) go inside a policy's Statement list.

A.1Permissions for workloads

Read one prefix, write another, read one secret

A service's whole job in four statements: list and read its config, write its output without delete, read one secret. Change the bucket, prefixes and secret name. From Chapter 9.

dispatch-task-policy.jsoncustomer managed, attached to role dispatch-task

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOwnPrefixes",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::larder-dispatch-prod",
      "Condition": { "StringLike": { "s3:prefix": ["config/*", "routes/*"] } }
    },
    {
      "Sid": "ReadConfig",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::larder-dispatch-prod/config/*"
    },
    {
      "Sid": "WriteRoutePlans",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::larder-dispatch-prod/routes/*"
    },
    {
      "Sid": "ReadMapsKey",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:eu-central-1:111122223333:secret:dispatch/prod/maps-api-key-??????"
    }
  ]
}

Each team's own secrets, by tag

Attribute-based access: one policy for every team, matching the principal's team tag to the secret's. Only the platform team may set team tags, or anyone could tag themselves into another team. From Chapter 9.

team-secrets.jsonattribute-based access control

{
  "Sid": "ReadOwnTeamsSecrets",
  "Effect": "Allow",
  "Action": "secretsmanager:GetSecretValue",
  "Resource": "*",
  "Condition": {
    "StringEquals": { "aws:ResourceTag/team": "${aws:PrincipalTag/team}" }
  }
}

Deploy one container service

For a CI role: push one image repository, register task definitions, update one service, and pass only that service's two roles. ecr:GetAuthorizationToken and task definition actions don't support resource-level permissions, so they need *. From Chapter 17 and Chapter 24.

policies/github-deploy-prod.jsonJSON

{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "PushImage", "Effect": "Allow",
     "Action": ["ecr:BatchCheckLayerAvailability", "ecr:InitiateLayerUpload", "ecr:UploadLayerPart",
                "ecr:CompleteLayerUpload", "ecr:PutImage"],
     "Resource": "arn:aws:ecr:eu-central-1:111122223333:repository/larder-core"},
    {"Sid": "EcrLogin", "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*"},
    {"Sid": "TaskDefinitions", "Effect": "Allow",
     "Action": ["ecs:RegisterTaskDefinition", "ecs:DescribeTaskDefinition"], "Resource": "*"},
    {"Sid": "Deploy", "Effect": "Allow", "Action": ["ecs:UpdateService", "ecs:DescribeServices"],
     "Resource": "arn:aws:ecs:eu-central-1:111122223333:service/prod/larder-core"},
    {"Sid": "PassServiceRoles", "Effect": "Allow", "Action": "iam:PassRole",
     "Resource": ["arn:aws:iam::111122223333:role/larder-core",
                  "arn:aws:iam::111122223333:role/larder-core-execution"]}
  ]
}

A.2Trust policies

A role for container tasks

Lets the container service assume the role for tasks in one account and region only. The source conditions stop another account's tasks using your role through the service (the confused deputy, Chapter 21). From Chapter 15.

task role trust policyECS

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ecs-tasks.amazonaws.com"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "ArnLike": {
          "aws:SourceArn": "arn:aws:ecs:eu-central-1:111122223333:*"
        },
        "StringEquals": {
          "aws:SourceAccount": "111122223333"
        }
      }
    }
  ]
}

One GitHub repository and environment

Only jobs in the production environment of one repository can assume the role. Match sub exactly with StringEquals; never trust a whole organisation's repositories with a wildcard. From Chapter 17.

github-deploy-prod trust policyproduction account

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:larder/larder-core:environment:production"
      }
    }
  }]
}

A vendor's role, with an external ID

Trust one role in the vendor's account, and require the external ID the vendor generated for you. Grant the role as little as possible: here, one prefix of one bucket. From Chapter 21.

wmsb-nightly-file trust policyproduction account

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::999911112222:role/wmsb-file-delivery" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "sts:ExternalId": "wmsb-3c9e51a07d2b4f18" } }
  }]
}

Pods in one Kubernetes namespace

EKS Pod Identity: the cluster's agent assumes the role and tags the session; conditions on those tags pin the role to one cluster, namespace and service account. From Chapter 16.

engine-a-pod-role trust policyEKS Pod Identity

{ "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow",
                  "Principal": { "Service": "pods.eks.amazonaws.com" },
                  "Action": ["sts:AssumeRole", "sts:TagSession"] }] }

Named people, with MFA (IAM users only)

For accounts that still have IAM users: only named users, with MFA, and the session must carry their own name. With single sign-on (Chapter 12) you don't need this: use permission sets instead. From Chapter 8.

prod-operator-trust.jsontrust policy

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "EngineersWithMfaAndTheirOwnName",
    "Effect": "Allow",
    "Principal": { "AWS": [
      "arn:aws:iam::111122223333:user/ben",
      "arn:aws:iam::111122223333:user/eli"
    ] },
    "Action": ["sts:AssumeRole", "sts:SetSourceIdentity"],
    "Condition": {
      "Bool": { "aws:MultiFactorAuthPresent": "true" },
      "StringEquals": { "sts:SourceIdentity": "${aws:username}" }
    }
  }]
}

A.3Resource policies

Bucket: encrypted connections only

Refuses any request to the bucket over plain HTTP. Add it to every bucket; it costs nothing and breaks nothing that should work.

bucket policy statementS3

{
  "Sid": "OnlyEncryptedConnections",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::larder-dispatch-prod",
    "arn:aws:s3:::larder-dispatch-prod/*"
  ],
  "Condition": {
    "Bool": {
      "aws:SecureTransport": "false"
    }
  }
}

Bucket: restricted data only from our networks

The network perimeter for restricted data: requests must come through the production VPC, or from an AWS service working for a Larder principal. Break-glass is excepted. Search CloudTrail with S3 data events for everything it would deny before enforcing. From Chapter 22.

{
  "Sid": "RestrictedDataOnlyFromOurNetworks",
  "Effect": "Deny", "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::larder-settlements", "arn:aws:s3:::larder-settlements/*"],
  "Condition": {
    "StringNotEqualsIfExists": { "aws:SourceVpc": ["vpc-0prod1a2b3c4d5e6f"] },
    "BoolIfExists": { "aws:ViaAWSService": "false", "aws:PrincipalIsAWSService": "false" },
    "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/break-glass-admin" }
  }
}

KMS key: administrators manage, two roles decrypt through S3

Separates managing a key from using it, and lets the two roles use it only when S3 calls on their behalf. Keep an administration statement for a role that will always exist, and the break-glass role, or you can lock yourself out. From Chapter 18.

order-exports key policyLarder, production

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PlatformAdminsManageButCannotUse",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": ["kms:Describe*", "kms:Get*", "kms:List*", "kms:Enable*", "kms:Disable*", "kms:Put*",
                 "kms:Update*", "kms:Revoke*", "kms:TagResource", "kms:UntagResource",
                 "kms:ScheduleKeyDeletion", "kms:CancelKeyDeletion"],
      "Resource": "*",
      "Condition": { "ArnLike": { "aws:PrincipalArn":
        "arn:aws:iam::111122223333:role/aws-reserved/sso.amazonaws.com/*AWSReservedSSO_PlatformAdmin_*" } }
    },
    {
      "Sid": "ExportJobAndFinanceUseItOnlyThroughS3",
      "Effect": "Allow",
      "Principal": { "AWS": ["arn:aws:iam::111122223333:role/order-export-job",
                               "arn:aws:iam::111122223333:role/finance-reports"] },
      "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
      "Resource": "*",
      "Condition": { "StringEquals": { "kms:ViaService": "s3.eu-central-1.amazonaws.com" } }
    }
  ]
}

A.4Guardrails

Protect a database and its backups

Only the database-change role may modify or delete the database, and nobody may delete its snapshots. Use it as a permission policy (Chapter 10) or, better, as an SCP (Chapter 20).

protect-orders-db.jsoncustomer managed policy, Larder

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OnlyDbChangeMayAlterOrdersDb",
      "Effect": "Deny",
      "Action": ["rds:ModifyDBInstance", "rds:DeleteDBInstance"],
      "Resource": "arn:aws:rds:eu-central-1:111122223333:db:orders-prod",
      "Condition": { "StringNotLike": { "aws:PrincipalArn": [
        "arn:aws:iam::111122223333:role/db-change",
        "arn:aws:iam::111122223333:role/break-glass-*"
      ] } }
    },
    {
      "Sid": "NobodyDeletesBackups",
      "Effect": "Deny",
      "Action": ["rds:DeleteDBSnapshot", "rds:DeleteDBInstanceAutomatedBackup"],
      "Resource": "*"
    }
  ]
}

Baseline SCP for every account

Stay in the organisation, keep the audit trail, require IMDSv2 and stay in approved regions. Attach it to a sandbox OU for a week before the root. The region statement's NotAction list exempts global services; check it against your services. From Chapter 20.

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "StayInTheOrganisation", "Effect": "Deny",
      "Action": "organizations:LeaveOrganization", "Resource": "*" },
    { "Sid": "KeepTheAuditTrail", "Effect": "Deny",
      "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail"],
      "Resource": "*",
      "Condition": { "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/break-glass-admin" } } },
    { "Sid": "OnlyIMDSv2", "Effect": "Deny",
      "Action": "ec2:RunInstances", "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": { "StringNotEquals": { "ec2:MetadataHttpTokens": "required" } } },
    { "Sid": "OnlyFrankfurt", "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "sts:*", "sso:*", "identitystore:*", "support:*",
                    "cloudfront:*", "route53:*", "budgets:*", "ce:*", "health:*", "account:*"],
      "Resource": "*",
      "Condition": { "StringNotEquals": { "aws:RequestedRegion": "eu-central-1" } } }
  ]
}

Identity perimeter (RCP)

No request reaches your resources unless it comes from your organisation or from an AWS service working for you. The tag exception is for vendor roles assumed from outside, such as A.2's. From Chapter 22.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OnlyOurIdentities",
      "Effect": "Deny", "Principal": "*",
      "Action": ["s3:*", "kms:*", "secretsmanager:*", "sqs:*", "sts:AssumeRole"],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:PrincipalOrgID": "o-a1b2c3d4e5",
                                     "aws:ResourceTag/perimeter-exception": "vendor-role" },
        "BoolIfExists": { "aws:PrincipalIsAWSService": "false" }
      }
    },
    {
      "Sid": "AWSServicesOnlyWhenWorkingForUs",
      "Effect": "Deny", "Principal": "*",
      "Action": ["s3:*", "kms:*", "secretsmanager:*", "sqs:*", "sts:AssumeRole"],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:SourceOrgID": "o-a1b2c3d4e5" },
        "Bool": { "aws:PrincipalIsAWSService": "true" }
      }
    }
  ]
}

Resource perimeter (SCP statement)

Your identities may only use resources in your organisation, so they can't copy data to someone else's bucket. Add exceptions for AWS-owned and partner resources you really use. From Chapter 22.

{
  "Sid": "OnlyOurResources",
  "Effect": "Deny",
  "Action": ["s3:*", "sqs:*", "secretsmanager:*", "kms:*"],
  "Resource": "*",
  "Condition": { "StringNotEqualsIfExists": { "aws:ResourceOrgID": "o-a1b2c3d4e5" } }
}

A.5Checking a policy before you use it

  1. Validate: aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY --policy-document file://policy.json (use RESOURCE_POLICY for trust and resource policies, SERVICE_CONTROL_POLICY for SCPs).
  2. Prove it doesn't grant what it mustn't: check-access-not-granted with your never-grant list (Chapter 24).
  3. Prove a change adds nothing: check-no-new-access against the current version, for trust and resource policies.
  4. Try it with the policy simulator or on staging: one request that must work and one that must fail (Chapter 11).
