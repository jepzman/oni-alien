Part IV · Access for software

17

CI/CD without long-lived keys

A deployment pipeline needs to change production, which makes its credentials some of the most powerful in the company, and they usually sit in a CI system's secret store, readable by every workflow and every third-party action it runs. This chapter replaces that stored key with OpenID Connect federation: each job proves who it is with a short-lived token from the CI system, and AWS gives it a role session for exactly that repository, branch and environment.

By the end you can

  • Explain how a CI job's OIDC token becomes an AWS role session.
  • Read the claims in a GitHub Actions token, and choose which to trust.
  • Write a trust policy that admits one repository and environment, and no others.
  • Split deployment into per-environment roles with deploy-time least privilege.
  • Reduce what a compromised workflow or third-party action can do.

Before you start

  • OIDC and ID tokens (Chapter 4); trust policies and conditions (Chapter 8, Chapter 9).
  • Workload identity (Chapter 15). Basic GitHub Actions workflows.

At Larder

On Sunday 21 March 2027, the maintainers of a popular third-party GitHub Action announced that its version tags had been quietly pointed at malicious code for nineteen hours. The new code printed every secret available to the workflow into the job's log, encoded to slip past log masking. Larder's main repository used that action in its deployment workflow, which ran three times in the window.

Among the secrets in those logs: the access key of deploy-bot, the IAM user Larder had deployed with since 2024, with AdministratorAccess in production (Chapter 7, Chapter 10). The logs were private to Larder's GitHub organisation, but nobody could say where else the action had sent them. Eli rotated the key within two hours. Section 17.9 shows why there's no longer a key to rotate.

17.1The deploy key problem

A stored deploy key combines every weakness from Part I: it's long-lived, it's shared by every job that can read the secret, it usually has broad permissions because deployments touch many things, and it's exposed to every piece of code the pipeline runs, including third-party actions, build tools and test dependencies. Rotating it is a chore that breaks deploys, so it rarely happens: Larder's was two and a half years old.

The fix is the same idea as workload identity (Chapter 15), across a boundary: the CI system already knows exactly which repository, branch and environment a job belongs to, and can vouch for it with a signed token. AWS can be configured to trust that token, and nothing secret needs to be stored at all.

17.2How OIDC federation works

Two things are configured once in AWS: an IAM OIDC identity provider for https://token.actions.githubusercontent.com, with sts.amazonaws.com as its allowed audience; and, per role, a trust policy that names that provider and says which tokens to accept (17.4). In the workflow, the job must be allowed to request a token (permissions: id-token: write), and the official aws-actions/configure-aws-credentials action does the exchange.

17.3What's in the token

GitHub's token is a JWT (Chapter 3) with standard claims and many about the run. The ones that matter for trust:

Table 17.1 · GitHub Actions OIDC claims worth knowing
ClaimExampleNotes
isshttps://token.actions.githubusercontent.comchecked by the IAM OIDC provider
audsts.amazonaws.comwho the token is for; always check it
subrepo:larder/larder-core:environment:productionthe main claim to trust; its form depends on the trigger (below)
repository, repository_ownerlarder/larder-core, lardernames, which can be renamed and reused
repository_id, repository_owner_idnumbersstable IDs; never reused
ref, environment, event_namerefs/heads/main, production, pushwhat ran, where, why
job_workflow_reflarder/larder-core/.github/workflows/deploy.yml@refs/heads/mainwhich workflow file; useful for reusable workflows

By default, sub takes one of these forms: repo:owner/repo:environment:name when the job uses an environment; repo:…:ref:refs/heads/branch (or a tag) for other pushes; and repo:…:pull_request for pull requests. You can customise it per repository or organisation, for example to include the stable owner and repository IDs.

17.4Writing the trust policy

github-deploy-prod trust policyproduction account

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:larder/larder-core:environment:production"
      }
    }
  }]
}

Read aloud: “Allow a session for any GitHub Actions token meant for AWS whose subject is exactly the production environment of larder/larder-core.” Everything else, including other branches, pull requests, other Larder repositories and the rest of GitHub, is refused.

Key idea

The OIDC provider says “GitHub signed this”. Only the sub condition says “and it's our repository”. A trust policy without it trusts every repository on GitHub.

Watch out: three ways to trust too much

No sub condition: anyone with a GitHub account can create a repository, request a token with your audience, and assume the role; this misconfiguration has been found in real companies. Wide wildcards such as repo:larder/*: every repository in the organisation, and every branch and pull request in them, gets the role. Names alone: if an organisation or repository is deleted and its name re-registered by someone else, name-based conditions trust them; include the stable repository_owner_id in a customised sub when that risk matters.

17.5One role per environment

Don't give one role every environment. Map GitHub's controls onto AWS's:

  • Staging: a role in the staging account trusting pushes to main (repo:larder/larder-core:ref:refs/heads/main). Every merge deploys to staging.
  • Production: a role in the production account trusting only the production environment, which in GitHub has protection rules: required reviewers, deployment branches limited to main. The approval in GitHub becomes the only way to get production credentials.
  • Pull requests: no deploy role at all. If tests need AWS, a separate role with read-only access to test fixtures, in a sandbox account. Pull request code is untrusted until reviewed.

17.6Deploy-time least privilege

“The pipeline deploys” sounds like it needs administrator rights. It rarely does. List what a deploy actually does (Chapter 9, 9.9). For a container service, that's typically: push an image to one ECR repository, register a new task definition, update one ECS service, and pass two specific roles to ECS:

{ "Sid": "PassOnlyDispatchRoles", "Effect": "Allow", "Action": "iam:PassRole",
  "Resource": ["arn:aws:iam::111122223333:role/dispatch-task",
               "arn:aws:iam::111122223333:role/dispatch-task-execution"],
  "Condition": { "StringEquals": { "iam:PassedToService": "ecs-tasks.amazonaws.com" } } }

Infrastructure changes (Terraform plans and applies) are a different job with different risks; give them their own roles, with plan read-only and apply behind its own protected environment (Chapter 24). Keep sessions at one hour, give the roles the permissions boundary from Chapter 10, and let the guardrails apply to them like to anyone.

17.7Shrinking what a bad workflow can do

OIDC removes the stored secret, but a malicious action running inside your deploy job can still use the job's token while the job runs. Defence in depth:

  • Pin third-party actions to a full commit SHA, not a tag. Tags can be moved, which is exactly what happened at Larder; a SHA can't.
  • Set permissions: explicitly in every workflow, with id-token: write only on jobs that deploy, and contents: read by default.
  • Keep deploy jobs small: no third-party actions you don't need in the job that holds production credentials.
  • Watch CloudTrail for the deploy roles: what they did, and from which job (sourceIdentity and the session name record the run).

On Azure

A federated identity credential says “trust tokens from this issuer with exactly this subject”, such as repo:larder/larder-core:environment:production. Matching is exact, which avoids the wildcard trap, but means one credential per environment or branch. The workflow logs in with the identity's client ID and tenant ID, and no client secret exists.

On Google Cloud

A workload identity pool with an OIDC provider for GitHub maps token claims to attributes; an attribute condition on the provider rejects everything else up front. Google requires a condition for GitHub providers, precisely because of the “any repository” mistake. Roles are then granted to principals in the pool, such as all jobs from one repository.

17.9At Larder: the last IAM user goes

At Larder: solved

The rotated key was a stopgap. In the two weeks after 21 March, Eli added the GitHub OIDC provider to the staging and production accounts and created two roles: github-deploy-staging, trusting pushes to main of larder/larder-core, and github-deploy-prod, trusting only its production environment, which requires one tech lead's approval in GitHub. Their policies were written from what a deploy actually does: ECR push for the service's repository, task definitions, one ECS service per deploy, and iam:PassRole for the service's two roles only. Both carry team-boundary, so the backup guardrail applies to them as well.

The same change pinned every third-party action to a commit SHA and set permissions: in every workflow. CloudTrail showed no use of the leaked key from outside GitHub's runners before it was rotated. On 9 April 2027, deploy-bot was deleted: the last IAM user in either account that wasn't a break-glass account. Larder now stores no AWS secret anywhere.

17.10Lab: who could assume this role?

Lab 17 · Trust conditions against token claims

You'll test four trust policies against five kinds of GitHub job, including a stranger's, then optionally set up a real OIDC role for a repository of your own. You need Python 3; for the optional part, the AWS CLI as an administrator of a sandbox account and a GitHub repository you control. Cost: free.

oidc_trust.pyPython 3.8+

# oidc_trust.py · which GitHub Actions jobs could assume your role? Trust conditions vs token claims
from fnmatch import fnmatchcase

P = "token.actions.githubusercontent.com"
JOBS = {   # the claims GitHub puts in each job's OIDC token (the ones trust policies use)
    "push to main":         {"aud": "sts.amazonaws.com", "sub": "repo:larder/larder-core:ref:refs/heads/main"},
    "deploy, production":   {"aud": "sts.amazonaws.com", "sub": "repo:larder/larder-core:environment:production"},
    "pull request":         {"aud": "sts.amazonaws.com", "sub": "repo:larder/larder-core:pull_request"},
    "another Larder repo":  {"aud": "sts.amazonaws.com", "sub": "repo:larder/website:ref:refs/heads/main"},
    "a stranger's repo":    {"aud": "sts.amazonaws.com", "sub": "repo:mallory/anything:ref:refs/heads/main"},
}
TRUSTS = {   # role → its trust policy's Condition block
    "aud only":           {"StringEquals": {f"{P}:aud": "sts.amazonaws.com"}},
    "any Larder repo":    {"StringEquals": {f"{P}:aud": "sts.amazonaws.com"},
                           "StringLike":   {f"{P}:sub": "repo:larder/*"}},
    "staging: main only": {"StringEquals": {f"{P}:aud": "sts.amazonaws.com",
                                            f"{P}:sub": "repo:larder/larder-core:ref:refs/heads/main"}},
    "prod: environment":  {"StringEquals": {f"{P}:aud": "sts.amazonaws.com",
                                            f"{P}:sub": "repo:larder/larder-core:environment:production"}},
}

def allowed(condition, claims):
    for op, tests in condition.items():
        for key, want in tests.items():
            have = claims[key.split(":")[-1]]
            if op == "StringEquals" and have != want:
                return False
            if op == "StringLike" and not fnmatchcase(have, want):
                return False
    return True

print(f"{'':<22}" + "".join(f"{role:<20}" for role in TRUSTS))
for job, claims in JOBS.items():
    print(f"{job:<22}" + "".join(f"{'ASSUMES' if allowed(c, claims) else '-':<20}" for c in TRUSTS.values()))

  2. Try a tempting shortcut. Change the staging role's condition to StringLike with repo:larder/larder-core:*, “so tags work too”. Which jobs can now deploy to staging? (Pull requests, and production-environment jobs.)
  3. Optional: set it up for real. In a sandbox account, create the provider and a role trusted by one of your repositories' main branch (replace YOU/REPO): 
    ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
aws iam create-open-id-connect-provider --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com
cat > trust.json <<EOF
{ "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::$ACCOUNT:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": { "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:YOU/REPO:ref:refs/heads/main" } } }] }
EOF
aws iam create-role --role-name github-lab --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name github-lab \
  --policy-arn arn:aws:iam::aws:policy/job-function/ViewOnlyAccess
    (Older CLI versions also ask for --thumbprint-list; current ones don't need it.) Then add a workflow to the repository, with the action pinned to a commit SHA you look up on its releases page: 
    name: whoami
on: { push: { branches: [main] } }
permissions: { id-token: write, contents: read }
jobs:
  whoami:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@<full commit SHA>   # v4

          role-to-assume: arn:aws:iam::<ACCOUNT>:role/github-lab

17.11Common mistakes

MistakeWhat happensInstead
Access keys in CI secretsEvery workflow and action can read a long-lived key.OIDC federation; no stored AWS secret.
Trust policy without a sub conditionAny repository on GitHub can assume the role.Exact sub and aud with StringEquals.
Wildcards over the organisation or branchesPull requests and unrelated repositories get deploy rights.One role per environment, exact subjects.
Administrator rights for deploysA compromised job owns the account.Deploy-time least privilege; narrow PassRole.
Production without an approval gateAny merge, or any branch, can deploy to production.A protected environment trusted only by the production role.
Third-party actions by tagA moved tag runs new code with your credentials.Pin to commit SHAs; explicit, minimal permissions:.

✓Chapter summary

  • A stored deploy key is long-lived, shared and exposed to everything the pipeline runs.
  • With OIDC federation, each job gets a signed token from the CI system and exchanges it with AssumeRoleWithWebIdentity for a one-hour session.
  • The sub claim names the repository and branch, environment or pull request; trust it exactly, with aud.
  • One role per environment; production trusts only a protected environment with required approval.
  • Deploy roles get what deploys do, not administrator rights; boundaries and guardrails still apply.
  • Pin actions to SHAs and set minimal workflow permissions.

Key terms

OIDC federation
Trusting tokens from an external OpenID Connect issuer to grant role sessions.
IAM OIDC identity provider
The IAM resource that tells AWS to trust an issuer's tokens.
AssumeRoleWithWebIdentity
The STS call that exchanges an OIDC token for role credentials.
sub claim
The token's subject; for GitHub, the repository plus branch, environment or pull request.
Protected environment
A GitHub environment with deployment rules such as required reviewers.
Deploy-time least privilege
Giving a pipeline only the permissions a deployment needs.

Check your understanding

  1. What's in GitHub's OIDC token that tells AWS which repository and environment a job belongs to? recall

    Show answer

    The sub claim, such as repo:larder/larder-core:environment:production, plus claims like repository, ref and environment.

  2. A role trusts the GitHub OIDC provider with only an aud condition. Describe the attack. explain

    Show answer

    An attacker creates any GitHub repository, writes a workflow that requests a token with audience sts.amazonaws.com, and calls AssumeRoleWithWebIdentity on your role's ARN. The token is genuinely signed by GitHub, and nothing checks which repository it came from.

  3. Why should production trust an environment rather than the main branch? explain

    Show answer

    An environment can carry protection rules, such as required reviewers and allowed branches, so the approval in GitHub is the only path to production credentials. Trusting main gives every push to main production access, approved or not.

  4. Write the iam:PassRole statement for a pipeline that deploys one ECS service with a task role and an execution role. apply

    Show answer

    Allow iam:PassRole on exactly those two role ARNs, with StringEquals iam:PassedToService = ecs-tasks.amazonaws.com, as in 17.6.

  5. Design CI access for a monorepo that deploys three services to staging and production, with Terraform for infrastructure. design

    Show answer

    Per environment: a deploy role per service (or one with per-service resources) trusted by the matching protected environment; a Terraform plan role (read-only, trusted by pull requests from the same repository, in a sandbox or with read-only access); a Terraform apply role behind its own environment with approval. All exact sub conditions, one-hour sessions, boundaries, pinned actions.

  6. Compare how you'd restrict which GitHub repositories can use your cloud identity on AWS and on Google Cloud. compare

    Show answer

    AWS: conditions on the sub (and aud) claims in each role's trust policy. Google Cloud: an attribute condition on the workload identity pool provider (for example on repository_owner_id), which Google requires for GitHub, plus role grants to specific mapped principals.
