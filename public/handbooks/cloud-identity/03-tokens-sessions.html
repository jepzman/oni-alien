Sessions and tokens

Nobody types a password for every click. After authentication, a person or program carries something instead: a session cookie, a bearer token, temporary cloud credentials. Whoever holds that thing is you until it expires. This chapter shows what these tokens contain, how to check one properly, and how to keep their lives short enough that losing one isn't a disaster.

By the end you can

  • Explain the difference between a server-side session and a self-contained token.
  • Read a JSON Web Token and list every check a server must make before trusting it.
  • Set cookie attributes that stop the common browser attacks.
  • Design token lifetimes, refresh and revocation, including “sign out everywhere”.

At Larder

On Tuesday 24 November 2026, a customer's phone was stolen on the tram. That evening she changed her Larder password on the website, and felt safe. The next morning, two orders were placed from the Larder app on her stolen phone, paid with her saved card.

Changing the password hadn't touched the phone at all. The app hadn't seen her password since she first signed in, months earlier. It held two tokens: an access token the API accepted for 24 hours, and a refresh token that could fetch new ones for a year. Neither knew anything about passwords. Section 3.6 shows what Larder changed.

3.1Why sessions exist

HTTP is stateless: each request stands alone, and the server doesn't remember the last one. So after a person authenticates, the server hands back a session credential, something the client sends with every following request to say “it's still me”. There are two ways to build one:

  • A server-side session: the server stores the session (who, since when, what was proved) and gives the client only a long random session ID, usually in a cookie. To check a request, the server looks the ID up.
  • A self-contained token: the server writes the facts into the token itself and signs it. To check a request, any server with the right key verifies the signature and reads the facts, with no lookup.
Table 3.1 · Two ways to remember who's asking

Neither is better. Self-contained tokens scale and cross boundaries easily; server-side sessions are easy to end. Most real systems use both, and the art is in combining them (3.6).

3.2Cookies, done properly

In a browser, session credentials usually travel in a cookie, which the browser stores and sends back automatically with every request to the site that set it. That automatic sending is what makes cookies convenient, and also what attackers abuse. A cookie's attributes are its defences:

Table 3.2 · Cookie attributes for a session
AttributeEffectDefends against
Securesent only over HTTPStheft on an unencrypted network

Path=/, no Domainsent only to the exact host that set itleaking to other subdomains

__Host- name prefixthe browser enforces Secure, Path=/ and no Domainother subdomains overwriting it

A good session cookie looks like this:

Set-Cookie: __Host-session=k3Pz9Vq7xTn2Lw8RcY4bHs1dMf6Ga0Ue; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=28800

Sessions also need two timeouts: an idle timeout (end the session after, say, 30 minutes without activity) and an absolute timeout (end it after eight hours, however active). Issue a new session ID at login and whenever privileges change, so an attacker who planted an ID before login can't ride on it (session fixation).

3.3Bearer tokens

APIs and mobile apps usually skip cookies and send a token in a header:

GET /v1/orders HTTP/1.1
Host: api.larder.example
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOi...

A bearer token is exactly what the name says: whoever bears it gets access. There's no proof that the sender is the party it was issued to. That makes bearer tokens simple, and it makes every copy dangerous: in a log line, a crash report, a screenshot, a browser's history, a support ticket. Treat them like passwords, and keep them short-lived.

Bearer tokens come in two forms. An opaque token is a random string; the API asks the issuer what it means (introspection), so it behaves like a server-side session. A structured token carries its own facts, signed, and the commonest format is the JWT.

Sender-constrained tokensStandards such as DPoP and mutual TLS bind a token to a key the client holds, so a stolen copy is useless without the key too. They're increasingly common in banking and high-risk APIs.

3.4Inside a JSON Web Token

A JSON Web Token (JWT, often pronounced “jot”) is three parts separated by dots: a header, a payload of claims, and a signature. The first two are JSON, encoded with base64url (base64 with URL-safe characters and no padding). Encoded is not encrypted: anyone who has a JWT can read it.

The registered claims you'll see everywhere:

  • iss (issuer): who signed it, usually a URL.
  • sub (subject): who it's about: a user or client ID.
  • aud (audience): which API or app it's meant for.
  • exp (expiry), nbf (not before), iat (issued at): Unix times.
  • jti (JWT ID): a unique ID, useful for revocation lists and replay detection.

Plus whatever the issuer adds: scopes, roles, group names, tenant IDs. Keep that short and non-sensitive: tokens end up in logs, and every request carries the whole thing.

3.5Checking a token: every step

The signature is only the beginning. An API that receives a JWT must check all of this, in this order, before it believes a single claim:

  1. Algorithm: accept only the algorithms you expect (an allow-list), whatever the header says. Never accept none.
  2. Key: find the right key for this issuer. For asymmetric tokens, issuers publish their public keys at a JWKS URL, and the header's kid says which key signed it. Cache the keys; refresh them when an unknown kid appears.
  3. Signature: verify it, comparing in constant time.
  4. Issuer: iss must be exactly the issuer you trust.
  5. Audience: aud must be you. A valid token for another API must fail here.
  6. Time: exp in the future and nbf in the past, allowing a small leeway (30–60 seconds) for clock differences.
  7. Then authorise: the token says who; your rules still decide whether this request is allowed (Chapter 1).

Watch out: letting the token choose the algorithm

Two famous bugs come from trusting the header. With "alg": "none", some libraries skipped the signature check entirely. With algorithm confusion, an attacker changes RS256 to HS256 and signs with the issuer's public key as if it were a shared secret; a library that picks the method from the header then verifies it. Always tell your library which algorithms and keys to accept, and use a well-maintained library rather than writing your own.

HS256 or RS256? HS256 uses one shared secret to sign and verify, so every API that checks tokens could also create them: fine inside one service, wrong across many. Asymmetric algorithms (RS256, ES256) sign with a private key only the issuer has, and verify with a public key anyone can have. Identity providers use asymmetric signatures for exactly that reason.

3.6Expiry, refresh and revocation

A self-contained token can't be taken back: every API that trusts the signer will accept it until exp. So the main defence is a short life. But nobody wants to sign in every ten minutes. The standard answer is two tokens:

  • An access token: self-contained, sent with every API call, short-lived (5–15 minutes).
  • A refresh token: opaque, sent only to the identity provider to get a new access token, longer-lived, and recorded server-side, so it can be revoked.

Refresh token rotation issues a new refresh token every time one is used, and treats a second use of an old one as theft: it revokes everything descended from that sign-in. Combine that with short access tokens, and you have revocation that works within minutes:

  • Sign out revokes this device's refresh token.
  • Sign out everywhere, password change and account lock revoke all of the user's refresh tokens.
  • If you need faster than the access token's lifetime, keep a small denylist of revoked token IDs (jti) or a per-user “sessions valid after” time, and check it on sensitive actions such as payments.

Key idea

A token you can't take back must die young. Keep the power to end a session in something you can revoke.

At Larder: solved

Ben's and Dee's teams made four changes, live on 10 December. Access tokens now last 10 minutes instead of 24 hours. Refresh tokens rotate on every use, with reuse detection, and expire after 30 days without use. A password change, “sign out everywhere” (new, under Account → Devices, which lists every signed-in device) and an account lock all revoke every refresh token. And paying with a saved card checks a per-customer “sessions valid after” time, so a revoked phone can't order even in its last ten minutes.

Replayed against the new design, Tuesday's theft ends within ten minutes of the password change, and the thief's next refresh fails.

3.7Where tokens should live

  • Browsers: keep tokens out of JavaScript's reach. Storing an access token in localStorage means any injected script can read and send it. The safer pattern is a backend for frontend: the browser holds only an HttpOnly session cookie for your own server, which holds the tokens and calls the APIs.
  • Mobile apps: the platform's secure storage (Keychain on iOS, Keystore-backed storage on Android), never plain preferences or files.
  • Servers and workloads: in memory, fetched from the platform when needed (Chapter 15), not in environment files committed to Git.
  • Never in URLs (they end up in logs, browser history and the Referer header), and never logged in full. If you must log one, log its jti or a hash.

3.8Across providers

The clouds themselves run on the same ideas. When you assume a role on AWS, sign in to Azure or run code on Google Cloud, you get short-lived tokens, and the long-lived things (passwords, keys) stay elsewhere:

Table 3.3 · Short-lived credentials at the big three

On Azure

Continuous Access Evaluation lets supporting services (Exchange, SharePoint, Microsoft Graph and others) learn about critical events, such as a disabled account, a password reset or a changed network location, and reject a still-valid access token straight away, instead of waiting for it to expire.

On Google Cloud

Google's access tokens are opaque strings, not JWTs; Google's ID tokens are JWTs. Workloads ask the metadata server for an access token when they need one, so there's nothing long-lived on disk to steal (Chapter 15).

3.9Lab: make and check a JWT

Lab 3 · Sign, read, verify and attack a token

You'll build an HS256 JWT by hand, read it without the key, and write a verifier that rejects a forged subject, an expired token, alg: none and a token for another API. Then you'll remove checks and watch attacks get through. You need Python 3. Cost: nothing. (In real code, use a maintained library such as PyJWT; writing one teaches what the library does for you.)

tokens.pyPython 3.8+

# tokens.py · make and check a JSON Web Token (HS256) with the standard library
import base64, hashlib, hmac, json, time

def b64url(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def unb64url(text):
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))

def encode(part):
    return b64url(json.dumps(part, separators=(",", ":")).encode())

def sign(claims, key):
    signing_input = encode({"alg": "HS256", "typ": "JWT"}) + "." + encode(claims)
    signature = hmac.new(key, signing_input.encode(), hashlib.sha256).digest()
    return signing_input + "." + b64url(signature)

def verify(token, key, issuer, audience, now=None, leeway=30):
    now = time.time() if now is None else now
    try:
        h64, p64, s64 = token.split(".")
        header, claims = json.loads(unb64url(h64)), json.loads(unb64url(p64))
    except ValueError:
        return "rejected: malformed"
    if header.get("alg") != "HS256":                  # an allow-list; never obey the header
        return f"rejected: alg {header.get('alg')}"
    expected = hmac.new(key, f"{h64}.{p64}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(expected, unb64url(s64)):
        return "rejected: bad signature"
    if claims.get("iss") != issuer:
        return "rejected: wrong issuer"
    if claims.get("aud") != audience:
        return "rejected: wrong audience"
    if now > claims.get("exp", 0) + leeway:
        return "rejected: expired"
    scope = f" may {claims['scope']}" if "scope" in claims else ""
    return f"ok: {claims['sub']}{scope}"

if __name__ == "__main__":
    KEY = b"lab-only-key-printed-in-a-book-1"
    NOW = 1795597200                                   # 25 Nov 2026, 09:00 UTC
    ISS, AUD = "https://login.larder.example", "larder-api"
    claims = {"iss": ISS, "sub": "customer-48213", "aud": AUD,
              "iat": NOW, "exp": NOW + 600, "scope": "orders:write"}
    token = sign(claims, KEY)
    print(token, "\n")
    print("anyone can read it:", unb64url(token.split(".")[1]).decode(), "\n")

    h64, p64, s64 = token.split(".")
    forged_claims = encode(dict(claims, sub="customer-1"))
    none_token = encode({"alg": "none", "typ": "JWT"}) + "." + p64 + "."
    tests = [
        ("as issued",            token,                          NOW + 60),
        ("someone else's id",    f"{h64}.{forged_claims}.{s64}", NOW + 60),
        ("an hour later",        token,                          NOW + 3600),
        ('alg "none"',           none_token,                     NOW + 60),
        ("for another API",      sign(dict(claims, aud="larder-admin"), KEY), NOW + 60),
    ]
    for name, t, at in tests:
        print(f"{name:<20} {verify(t, KEY, ISS, AUD, now=at)}")

  3. Break it on purpose. Remove the two lines that check aud, and run again: the token meant for larder-admin is now accepted by larder-api. Put them back. ✓Chapter summary

  • After authentication, a session credential stands in for the person: a server-side session ID or a self-contained signed token.
  • Session cookies need Secure, HttpOnly, SameSite, a narrow scope, and idle and absolute timeouts.
  • A bearer token works for whoever holds it. Treat every copy like a password.
  • A JWT is a readable header and payload plus a signature. Check algorithm, key, signature, issuer, audience and time, then authorise.
  • Self-contained tokens can't be taken back: keep access tokens short, and put revocable power in rotating refresh tokens.
  • Password changes and “sign out everywhere” must revoke refresh tokens.
  • Keep tokens out of JavaScript, URLs and logs.

Key terms

Session
The state that lets a server recognise later requests after one authentication.
Bearer token
A token that grants access to whoever presents it.
JWT
JSON Web Token: base64url-encoded header and claims, plus a signature.
Claim
A statement in a token, such as sub, aud or exp.
Audience
The service a token is meant for; others must reject it.
Access token
A short-lived token sent to APIs.
Refresh token
A longer-lived, revocable token used only to get new access tokens.
Rotation
Issuing a new refresh token at each use, and treating reuse as theft.
JWKS
JSON Web Key Set: an issuer's published public keys.

Check your understanding

  1. Why didn't changing her password stop the thief at Larder? recall

    Show answer

    The phone held an access token and a refresh token, neither tied to the password. The API accepted the access token for 24 hours, and nothing revoked the refresh token when the password changed.

  2. You receive a JWT whose signature is valid. List what else you must check before acting on it. apply

    Show answer

    That the algorithm was one you allow (checked before the signature), the issuer is the one you trust, the audience is your service, it hasn't expired and isn't used before nbf, and then whether this subject is authorised for this request.

  3. Explain why an identity provider uses RS256 or ES256 rather than HS256 for tokens many APIs will check. explain

    Show answer

    With HS256, every API that can verify a token holds the same secret and could also forge one. With an asymmetric algorithm, only the provider holds the private signing key; APIs verify with the public key, which can't sign.

  4. A security reviewer says “your access tokens last 15 minutes, so a fired employee keeps access for up to 15 minutes”. When is that acceptable, and what would you add when it isn't? design

    Show answer

    Acceptable for most actions, since refresh is revoked immediately. For sensitive actions (payments, admin changes, data exports), check a denylist of token IDs or a per-user “valid after” time, or require fresh authentication.

  5. Which cookie attribute stops a script injected into your page from reading the session cookie, and which stops another site making the user's browser send it? recall

    Show answer

    HttpOnly hides it from JavaScript. SameSite=Lax or Strict stops it being sent on most cross-site requests.

  6. Compare how you'd cut off a compromised identity's cloud API access early on AWS and on Azure. compare

    Show answer

    AWS: temporary credentials can't be recalled, so attach a policy that denies everything for sessions issued before now (aws:TokenIssueTime), which the console's “Revoke active sessions” does for roles, and disable the source identity. Azure: revoke the user's refresh tokens and disable the account; Continuous Access Evaluation makes supporting services reject existing access tokens quickly.
