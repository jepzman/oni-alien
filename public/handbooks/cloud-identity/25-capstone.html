Capstone: Larder's identity end to end

Twenty-four chapters built Larder's identity one piece at a time. This chapter looks at the whole thing: an inventory of every way in, a review of the design against the principles from Part I, a check on what a second region changes, and a tabletop exercise where an attacker has an engineer's laptop. It ends with a method you can use on your own organisation.

By the end you can

  • Inventory every way people, software and partners get access.
  • Review an identity design layer by layer: people, workloads, guardrails, perimeter, detection.
  • Work out what a new region or a big change means for identity.
  • Run a tabletop exercise and turn its gaps into work.

Before you start

  • The whole book helps; each section links back to the chapters it builds on.

At Larder

On 24 January 2028 ADR 0026 decided Larder would stay in one region, Frankfurt, with a pilot light in Paris for Tier 1: a database replica and the infrastructure code to rebuild the rest in four hours. Ana's review asked one question about identity: if Frankfurt is gone, can the people doing the recovery even sign in?

Eli realised he couldn't answer from memory, and that nobody had looked at Larder's identity as a whole since the account audit of November 2026, fifteen months and two dozen changes ago. He booked two afternoons in February: one to review the whole design, one for a tabletop with Lena, Dee, Cho and Marco.

Then check the principles from Chapter 6 across layers, since they're easy to lose between them: separation of duties (can anyone approve their own access? Only on-call, for ProdOperator during an incident, reviewed the next morning, as designed in Chapter 14), default deny (do new accounts start with guardrails? yes, through the OU), and least privilege over time (are unused-access findings being closed? 31 open in February, owners assigned).

25.3What a second region changes

Big changes elsewhere in the architecture almost always touch identity. A second region is a good example, because identity services aren't all global in the same way:

  • IAM is global: roles, policies and IAM users exist in every region. Sign-in and STS work from regional endpoints, so set your SDKs and CLI to use the recovery region's STS endpoint, not one that might be down.
  • IAM Identity Center runs in the region where you enabled it. If that region has a serious outage, signing in through it may fail. Plan as if it will: break-glass IAM users are your way in, and they must be tested with Frankfurt unavailable, not just with SSO broken.
  • SCPs that allow only certain regions (Chapter 20) must allow the recovery region before you need it, for the accounts and services the pilot light uses.
  • KMS keys are regional. The database replica in Paris needs a key in Paris, either a multi-Region replica key or its own key. Its key policy needs the same review as the original (Chapter 18).
  • Detection is mostly regional. The organisation trail covers all regions, but EventBridge rules, GuardDuty and Access Analyzer must be enabled in Paris too, or the watch list goes quiet there.
  • Perimeter network rules (Chapter 22) list VPC endpoints and address ranges; the recovery VPC's endpoints must be added, or the restore fails on access denied.
  • Pipelines deploy the pilot light, so the apply and deploy roles' policies must allow the recovery region, and the runbook must say how to run them if GitHub itself is impaired.

The same exercise elsewhere

On Azure, Entra ID is a global service, but managed identities and Key Vaults are regional, and Conditional Access may block sign-ins from a recovery site's addresses. On Google Cloud, IAM is global, but organisation policies restricting resource locations, Cloud KMS key rings and VPC Service Controls perimeters all need the recovery region added.

25.4Tabletop: an engineer's laptop

A tabletop exercise walks through an incident on paper: one person reads out what happens, step by step, and the others say what they'd see and do. It finds gaps without breaking anything. Pick a realistic scenario; for identity, stolen sessions are the most common way in today, because they skip passwords and MFA alike.

Larder's scenario: on a Tuesday afternoon a developer installs a browser extension that pretends to be a PDF tool. It copies the browser's cookies and the files in the home folder to an attacker. Nobody notices until the next morning. The group walked through it with the inventory on the screen:

  1. What does the attacker have? Session cookies for the company IdP, GitHub and the business portal's admin view; the AWS CLI's cached SSO token (~/.aws/sso/cache, valid for the rest of the 8-hour session); no passwords and no security keys.
  2. What can they reach? As the developer: Developer in dev-staging, ViewOnly in prod (no S3 object reads), the code in GitHub. Through TEAM they could request elevation, but a tech lead must approve. Pull requests need two approvals. The identity perimeter doesn't help, because these are Larder's own identities; the network rule on restricted buckets does, because the attacker isn't in the prod VPC.
  3. What would Larder see? GuardDuty might flag API calls from an unusual address. The IdP logs a session used from a new country. But neither was on the watch list as a page, so the first sign might be a TEAM request at an odd hour.
  4. How would Larder respond? Revoke the developer's IdP sessions, end their Identity Center sessions, revoke active role sessions in dev-staging (Chapter 13, Chapter 3), sign them out of GitHub and revoke their tokens; then search the trail for everything those sessions did (Chapter 11).

What the tabletop found

Four gaps, each now a ticket with an owner. Sessions weren't bound to devices: a stolen IdP cookie worked from anywhere, so the IdP now requires a managed, compliant device for the AWS and GitHub apps. No alert on sign-ins from new countries: added to the watch list as a ticket, as a page for anyone in a production on-call group. The revoke steps were in three places: now one runbook, “contain a person”, practised in the next break-glass test. GitHub allowed classic personal access tokens with no expiry: the organisation now allows only fine-grained tokens, with 30-day expiry.

25.6At Larder: where it ended up

At Larder: solved

The design review on 15 February 2028 and the tabletop on 22 February produced seven tickets: the four from the tabletop, and three for the second region. By the end of March: eu-west-3 added to the region SCP for the Prod OU and the backup account; a multi-Region replica of the snapshot key in Paris, with the same key policy; GuardDuty, Access Analyzer and the watch list rules enabled in Paris; the recovery VPC's endpoints in the perimeter's network rule; and a break-glass test run as if Frankfurt were down, with STS's Paris endpoint and the printed runbook. It took 26 minutes, seven more than the first test in 2027, because the runbook's Paris steps had never been read aloud.

Eli wrote the summary for Marco in five lines: one identity per person, phishing-resistant; no standing admin; no long-lived keys anywhere; guardrails no admin can switch off; every change reviewed, and every way in watched. Then he added a sixth: review all of it again in a year, or when the next ADR touches it.

25.7Exercise: review your own

Exercise 25 · Inventory, review and tabletop

You'll apply this chapter's method to an organisation you know: your employer, a side project, or your sandbox account from the labs. You need a document, about an hour and a half, and ideally two colleagues. Cost: nothing; no cloud changes.

  1. Inventory (30 minutes). Fill in Table 25.1's four columns for every kind of principal. Include the uncomfortable ones: shared accounts, old keys, the contractor's access, the CI system, the SaaS tools connected to your cloud. Mark every cell you couldn't fill in.
  2. Review (30 minutes). Answer Table 25.2's questions. For each “no” or “not sure”, write the smallest change that would turn it into a “yes” and the chapter that shows how.
  3. Tabletop (30 minutes). Pick one: a stolen laptop session (25.4); a leaked CI token; a vendor's account compromised; a departing administrator who is angry. For each, answer: what does the attacker have, what can they reach, what would you see, how would you stop it? Write down every “we'd have to check”.
  4. Prioritise. Sort the gaps by how much access they expose and how cheap they are to close. Do the top three this month.
  5. Optional, in your sandbox. Run the credential report check from Chapter 7's lab and IAM Access Analyzer from Chapter 23's, and check the findings against your inventory: anything they show that your inventory missed is a finding in itself.

✓Chapter summary

  • Start every review with an inventory of every way in: who, how they prove it, what they get, who owns it.
  • Review layer by layer with four questions: least privilege, temporary, watched, owned.
  • Check the principles across layers: separation of duties, default deny, least privilege over time.
  • Every big architecture change, like a second region, has identity work: SCP regions, regional keys, detection, perimeter, break-glass.
  • Tabletop realistic attacks, especially stolen sessions, and turn every gap into an owned ticket.

Key terms

Access inventory
A list of every kind of principal, how it authenticates, what it can reach and who owns it.
Tabletop exercise
Walking through an incident scenario on paper to find gaps.
Pilot light
A minimal copy of critical systems in another region, ready to be scaled up in a disaster.
Session theft
Stealing an authenticated session's cookie or token, skipping passwords and MFA.

Check your understanding

  1. What four things does the inventory record for each kind of principal? recall

    Show answer

    Who it is, how it proves its identity, what it gets access to, and who owns it.

  2. Why might break-glass work in a test but fail in a region outage? explain

    Show answer

    If the test only simulated SSO being down, it may still have relied on the primary region: the STS endpoint the CLI used, a runbook or vault stored there, or a region-restricting SCP that doesn't allow the recovery region. Test it with the region treated as gone.

  3. In the laptop tabletop, why doesn't the identity perimeter stop the attacker, and what does? explain

    Show answer

    The identity perimeter only allows Larder's identities, and the attacker is using a Larder identity. What limits them: least privilege (ViewOnly can't read objects), TEAM's approvals, the network rule on restricted buckets, and short sessions. Binding sessions to managed devices would stop the stolen cookie working at all.

  4. Larder adds a city in Switzerland. List the identity questions you'd raise. apply

    Show answer

    Does ADR 0026's trigger (a city outside the EU) fire, and with it a new region? Data-protection rules for the new market and where data may live; any new region in SCPs, keys, detection and perimeter; new staff in the IdP with the same joiner process; new partners (stores, payment providers) with their own access to inventory and review.

  5. Design a tabletop for “a vendor's AWS account is compromised”, using WMS B as the vendor. design

    Show answer

    The attacker has WMS B's delivery role and the external ID. They can reach only wmsb-nightly-file: PutObject on one prefix. Questions: what if they upload a malicious file (validate files before import); would Larder notice (unusual time or address for the upload, file validation failures); how to cut them off (remove the trust, or deny with a condition, while WMS B rebuilds); who calls WMS B, and is it in the contract?

  6. Compare what “just in time” looks like at the three big providers. compare

    Show answer

    AWS has no built-in feature for it; tools like TEAM create and remove Identity Center assignments. Azure has Entra PIM, with eligible role assignments activated for a period, with approval. Google Cloud has Privileged Access Manager, with entitlements granting roles temporarily on request.
