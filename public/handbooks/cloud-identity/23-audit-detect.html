Auditing and detecting misuse

Every control in this book can be misconfigured, bypassed or abused by someone who already has access. So you need two more things: a record that can't be quietly edited of who did what, and alerts on the handful of events that change who can get in. This chapter sets up both on AWS: the organisation trail, IAM Access Analyzer, GuardDuty and a short list of rules, small enough that every alert gets read.

By the end you can

  • Set up an organisation-wide CloudTrail whose logs workload accounts can't change.
  • Use IAM Access Analyzer to find external and unused access.
  • Explain what GuardDuty adds, and where to run it.
  • Write an identity watch list: which events page someone, which open a ticket.
  • Respond to an identity alert: ask, contain, fix.

Before you start

  • CloudTrail and reading events (Chapter 11); the organisation and its security account (Chapter 20).
  • Break-glass and the elevation tool (Chapter 14).

23.1Evidence and detection

Auditing serves two different purposes, and they pull in different directions:

  • Evidence: a complete, tamper-resistant record of who did what, kept long enough for investigations, audits and the occasional “who changed this in March?”. More is better.
  • Detection: noticing, within minutes, the few events that matter now. Fewer is better: an alert stream nobody reads detects nothing.

Get evidence right with a central trail that nobody in a workload account can touch. Get detection right with a short list of rules about identity, each with an owner and a response.

23.2The organisation trail

An organisation trail is a CloudTrail trail created in the management account (or by the delegated administrator) that records every member account's events, existing and future, into one S3 bucket. Put that bucket in the security account (Chapter 20), where:

  • workload accounts can't read, change or delete the logs, and the baseline SCP stops anyone but break-glass from stopping the trail;
  • S3 Object Lock keeps each log file for its retention period, so even the security account's administrators can't delete history;
  • log file validation lets you prove a file wasn't altered;
  • a customer managed key (Chapter 18) controls who can read the logs, which contain sensitive information about everyone's work.

Management events are recorded by default. Add data events where they matter: object-level access to restricted buckets (Chapter 22) and secrets reads. Data events cost per event, so choose them deliberately. Keep at least a year online and longer in cheap storage, whatever your regulators require.

23.3IAM Access Analyzer

Access Analyzer answers questions you can't easily answer from CloudTrail, because they're about what's possible, not what happened:

  • External access: which resources (buckets, keys, roles, queues, secrets…) can be reached from outside your organisation, and by whom. Each grant is a finding to approve or remove. StockPilot's bucket access was one, closed when the contract ended (Chapter 21).
  • Unused access (a paid feature): roles, access keys and permissions that haven't been used for a period you choose. It's the best evidence for access reviews (Chapter 13) and for narrowing policies.
  • Policy checks: validation and custom checks before deployment (Chapter 9, Chapter 24).

Create the analyzers with the organisation as their zone of trust, administered from the security account.

23.4GuardDuty

Amazon GuardDuty analyses CloudTrail, VPC flow logs, DNS logs and more for signs of compromise, using AWS's threat intelligence and behaviour models. For identity, its most valuable findings include: instance credentials used from outside AWS (the SSRF of Chapter 15, after the fact), API calls from known malicious addresses or Tor, unusual root usage, and anomalous behaviour by a principal, such as a role suddenly listing every bucket. Enable it in every account and region you use, with the security account as delegated administrator, and route its high-severity findings into the same alerting as your own rules.

On AWS, each CloudTrail-based rule is an EventBridge rule with an event pattern (the break-glass alarm in Chapter 14 is one), in the region where the event is recorded; or a query over CloudTrail Lake or your log platform. The lab writes the same rules in a few lines of Python, which is a good way to design and test them before deploying.

Key idea

Alert on changes to who can get in, not on everything that happens. A short list everyone reads beats a long one nobody does.

23.6Identity events outside AWS

CloudTrail only sees AWS. Several of the most important identity changes happen elsewhere: a new federation connection in your customer login service, a new admin in your identity provider, a new OAuth app granted access to company data (Chapter 4), a change to a SaaS tool's SSO settings. Make sure each of those systems writes an audit log, ship the logs to the same place, and put their identity events on the same watch list. The October review's finding was exactly this: a powerful change, made in Larder's own application, that no AWS tool would ever see.

23.7Responding to an identity alert

  1. Ask first. Most identity alerts are someone doing their job without saying so. Message the person named in the event: was this you, and why? Make it normal to be asked, and normal to announce planned changes beforehand.
  2. If it wasn't expected, contain: end the person's sessions (Chapter 13), deny the role's existing sessions (Chapter 3), deactivate keys, revert the policy change.
  3. Investigate with the trail: everything the principal did from its first suspicious action, across accounts (Chapter 11).
  4. Fix the cause, and tune the rule if it fired for something you'll always want to allow, by narrowing it, not deleting it.

On Azure

Identity events live in Entra ID's audit and sign-in logs, not just the Azure activity log: role activations in PIM, new app registrations and consents, changes to Conditional Access. Entra ID Protection scores sign-ins and users for risk (impossible travel, leaked credentials) and can force MFA or a password reset automatically.

On Google Cloud

Admin Activity audit logs are always on and free; Data Access logs must be enabled per service. An organisation-level log sink sends every project's logs to a bucket in a locked-down project, Google's equivalent of the organisation trail.

23.10Lab: write the watch list

Lab 23 · Detection rules over a day of events

You'll run seven identity rules over Larder's 2 December 2027, decide which alerts were real, and add a rule of your own. Optionally, you'll turn on IAM Access Analyzer's external access findings in a sandbox account. You need Python 3; for the optional part, the AWS CLI. Cost: free (external access analysis is free; unused access analysis is not).

detect.pyPython 3.8+

# detect.py · a few identity detection rules over a day of events, and who gets told
import json, sys

TEAM_ROLE = "assumed-role/team-elevation/"          # the elevation tool (Chapter 14)

def who(e):
    u = e.get("userIdentity", {})
    if u.get("type") == "Root":
        return f"root of account {e['recipientAccountId']}"
    return e.get("actor") or u.get("userName") or u.get("arn", "?").split("/")[-1] or u.get("type")

RULES = [   # (severity, name, test)
    ("page", "root user signed in",
     lambda e: e.get("eventName") == "ConsoleLogin" and e["userIdentity"]["type"] == "Root"),
    ("page", "break-glass user signed in",
     lambda e: e.get("eventName") == "ConsoleLogin" and e["userIdentity"].get("userName", "").startswith("break-glass")),
    ("page", "trust policy opened to everyone",
     lambda e: e.get("eventName") == "UpdateAssumeRolePolicy" and '"AWS":"*"' in e["requestParameters"]["policyDocument"].replace(" ", "")),
    ("ticket", "new federation trust (client identity provider)",
     lambda e: e.get("event") == "federation.connection.created"
               or e.get("eventName") in ("CreateSAMLProvider", "CreateOpenIDConnectProvider")),
    ("ticket", "account assignment made outside the elevation tool",
     lambda e: e.get("eventName") == "CreateAccountAssignment" and TEAM_ROLE not in e["userIdentity"]["arn"]),
    ("ticket", "KMS key policy changed",
     lambda e: e.get("eventName") == "PutKeyPolicy"),
    ("ticket", "attempt to stop the audit trail",
     lambda e: e.get("eventName") in ("StopLogging", "DeleteTrail")),
]

path = sys.argv[1] if len(sys.argv) > 1 else "watch-events.jsonl"
events = [json.loads(line) for line in open(path) if line.strip()]
for e in events:
    for severity, name, test in RULES:
        if test(e):
            outcome = f" ({e['errorCode']})" if "errorCode" in e else ""
            print(f"{e['eventTime'][11:16]}  {severity.upper():<6} {name}{outcome}: {who(e)}")
print(f"\n{len(events)} events, {sum(any(t(e) for _, _, t in RULES) for e in events)} raised an alert")

✓Chapter summary

  • Auditing is evidence (complete, tamper-resistant, kept) and detection (few, fast, read).
  • An organisation trail into the security account, with Object Lock and a managed key, is the evidence.
  • Access Analyzer shows what's possible: external and unused access. GuardDuty finds known bad patterns.
  • Your own watch list covers changes to who can get in: root, break-glass, open trust, new federation, assignments outside the tool, key policies, trail tampering.
  • Include identity events from outside AWS. Respond by asking first, then containing, investigating and fixing.

Key terms

Organisation trail
A CloudTrail trail recording every account in an organisation.
S3 Object Lock
Write-once storage that prevents deletion before a retention date.
IAM Access Analyzer
Finds external and unused access, and checks policies.
GuardDuty
AWS's managed threat detection service.
Watch list
The short set of events that raise alerts, each with a response.

Check your understanding

  1. Why should the organisation trail's bucket live in a separate security account? recall

    Show answer

    So that someone who compromises a workload account, or its administrators, can't delete or alter the record of what they did. Combined with the SCP protecting the trail and Object Lock, the evidence survives.

  2. Which tool answers “can anyone outside our organisation read this bucket?”, and why not CloudTrail? explain

    Show answer

    IAM Access Analyzer, which reasons about what policies allow. CloudTrail records what happened, so it can only show access that has already been used.

  3. The watch list paged at 03:00 for a root sign-in to the management account. Write the first three steps. apply

    Show answer

    Ask the people who can use root (the vault holders) whether it was them; if not, treat it as an incident: check what the session did in CloudTrail and reset root's password and MFA through the recovery path; then review how the credentials could have been used and by whom.

  4. Why does a new client federation connection in your own login service belong on the same watch list as AWS events? explain

    Show answer

    It changes who can sign in to your application as a business customer's staff, as powerful as an IAM trust change, and no AWS tool can see it. Its audit event must be shipped and alerted on like any other identity change.

  5. Design the routing for Table 23.1: which events page, which create tickets, and who reviews tickets? design

    Show answer

    Page for events that could mean an active attacker with power now: root, break-glass, open trust, high-severity GuardDuty. Tickets for changes that need checking within a day: new federation, assignments outside the tool, key policy changes, trail tampering attempts, new users or keys. The platform team reviews tickets each morning, with a named owner per rule.

  6. Compare where you'd look for a suspicious new administrator on Azure and on AWS. compare

    Show answer

    Azure: Entra ID audit logs (role assignments and PIM activations) and the activity log for Azure RBAC. AWS: CloudTrail for Identity Center assignment and permission set changes and IAM policy changes, plus the identity provider's own audit log.
