Data perimeters

Every chapter so far has been about granting the right access. This one is about a backstop for when something goes wrong anyway: a bucket policy that's too generous, a leaked access key, code that copies data somewhere it shouldn't. A data perimeter is a small set of organisation-wide rules that say only our identities may touch our data, our identities may only send data to our resources, and the most sensitive data may only be reached from our own networks. Each rule is a few lines; together they turn whole classes of mistakes into denials.

By the end you can

  • Explain the identity, resource and network perimeters, and what each prevents.
  • Write the perimeter conditions with aws:PrincipalOrgID, aws:ResourceOrgID, aws:SourceVpc and their friends.
  • Choose where each perimeter lives: RCPs, SCPs, resource policies or VPC endpoint policies.
  • Design exceptions for AWS services and partners without punching holes.
  • Roll a perimeter out without breaking production.

Before you start

  • SCPs and RCPs (Chapter 20); cross-account access and the confused deputy (Chapter 21).
  • Workload credentials and aws:EC2InstanceSourceVPC (Chapter 15). VPC endpoints help (Handbook 1, Chapter 12).

At Larder

On 25 October 2027, Lena and Ana finished classifying Larder's data into four classes: public, internal, confidential and restricted. Two S3 buckets came out as restricted: the order exports (Chapter 18) and the payment providers' daily settlement files. A week later Lena asked Eli the question a data protection officer should ask: “For restricted data, can you show me that only Larder can reach it, even if somebody's key leaks, or somebody writes a bad bucket policy?”

Eli's honest answer was: mostly, but not provably. Every protection depended on each policy being right. Section 22.6 shows the three rules that changed the answer.

22.1Three perimeters

A data perimeter is a set of coarse, preventive guardrails around everything your organisation owns. It doesn't replace least privilege; it catches what least privilege misses. It's built from three questions, each answered by one kind of rule:

Table 22.1 · The three perimeters
PerimeterRulePreventsEnforced onMain condition key

Resourceour identities may access only trusted resourcescopying data out to an attacker's bucketour identities: SCPs, VPC endpoint policiesaws:ResourceOrgID

22.2The identity perimeter

The identity perimeter makes one statement for the whole organisation: no request reaches our resources unless it comes from an identity in our organisation, or from an AWS service working for us. A resource control policy (Chapter 20) is the natural place, because it applies to every resource in every member account, whatever its own policy says:

identity perimeterRCP attached to the organisation root

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OnlyOurIdentities",
      "Effect": "Deny", "Principal": "*",
      "Action": ["s3:*", "kms:*", "secretsmanager:*", "sqs:*", "sts:AssumeRole"],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:PrincipalOrgID": "o-a1b2c3d4e5",
                                     "aws:ResourceTag/perimeter-exception": "vendor-role" },
        "BoolIfExists": { "aws:PrincipalIsAWSService": "false" }
      }
    },
    {
      "Sid": "AWSServicesOnlyWhenWorkingForUs",
      "Effect": "Deny", "Principal": "*",
      "Action": ["s3:*", "kms:*", "secretsmanager:*", "sqs:*", "sts:AssumeRole"],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:SourceOrgID": "o-a1b2c3d4e5" },
        "Bool": { "aws:PrincipalIsAWSService": "true" }
      }
    }
  ]
}

Read aloud: “Deny any request to these services from a principal outside our organisation, unless it's an AWS service, or the resource is tagged as a vendor role. Deny an AWS service, unless it's acting for something in our organisation.” The second statement is the confused-deputy protection from Chapter 21, applied everywhere at once. (Conditions under one operator are ANDed, so the first statement denies only when both the caller is an outsider and the resource isn't tagged.)

Notice how vendors pass. When WMS B assumes its role in Larder's account (Chapter 21), the sts:AssumeRole call itself comes from WMS B's account, outside the organisation, so it needs an exception: the tag perimeter-exception=vendor-role on that one role, which only the platform team may set (Chapter 6, 6.4). Once assumed, WMS B acts as Larder's role, inside the organisation, and needs nothing more. A partner reaching your bucket directly through a bucket policy, as StockPilot once did, would need an exception on every resource it touches. That's why partners should come in through a few tagged roles you control.

Key idea

A perimeter doesn't grant anything. It makes the worst mistakes impossible: no policy anyone writes, in any account, can open our data to the outside world.

22.3The resource perimeter

The opposite direction: our identities may only use resources in our organisation. Without it, code with legitimate access to customer data, or an attacker who has taken over that code, can copy the data to a bucket in an account they own, and the request looks perfectly normal: an authorised principal writing to S3.

resource perimeterSCP attached to the Workloads OU

{
  "Sid": "OnlyOurResources",
  "Effect": "Deny",
  "Action": ["s3:*", "sqs:*", "secretsmanager:*", "kms:*"],
  "Resource": "*",
  "Condition": { "StringNotEqualsIfExists": { "aws:ResourceOrgID": "o-a1b2c3d4e5" } }
}

This one needs care. Some legitimate work reads resources AWS owns (operating-system package repositories in S3, AWS-published datasets) or resources partners own (WMS B's API isn't on AWS, but some partners' buckets are). List those as exceptions by account or ARN. VPC endpoint policies (Handbook 1, Chapter 12) apply the same idea at the network edge: the S3 endpoint in Larder's VPCs only lets requests through to Larder's buckets and the named exceptions.

22.4The network perimeter

The identity perimeter stops strangers, but a stolen key belongs to one of your identities. The network perimeter adds: restricted data may only be reached from our networks, or by an AWS service working for us. For Larder's two restricted buckets, the bucket policies carry:

{
  "Sid": "RestrictedDataOnlyFromOurNetworks",
  "Effect": "Deny", "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::larder-settlements", "arn:aws:s3:::larder-settlements/*"],
  "Condition": {
    "StringNotEqualsIfExists": { "aws:SourceVpc": ["vpc-0prod1a2b3c4d5e6f"] },
    "BoolIfExists": { "aws:ViaAWSService": "false", "aws:PrincipalIsAWSService": "false" },
    "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/break-glass-admin" }
  }
}

aws:SourceVpc is only present when a request arrives through a VPC endpoint, so a request from the internet has no value, …IfExists treats it as “not equal”, and the deny applies. aws:ViaAWSService exempts calls a service such as Athena or Glue makes for a Larder principal. For credentials issued to EC2 instances, the condition keys aws:EC2InstanceSourceVPC and aws:EC2InstanceSourcePrivateIPv4 (Chapter 15) let an SCP reject an instance's credentials when they're used anywhere but from that instance's own VPC.

Watch out: perimeters fail loudly, and in production

A perimeter applies to every request, including the ones nobody remembered: a nightly job that reads from an AWS-owned bucket, a service calling from outside the VPC, a support engineer's console session. Before enforcing, search CloudTrail (with S3 data events) for every request that would be denied, write exceptions for the legitimate ones, enforce on staging, then production. Keep the break-glass role as an exception, and test it.

22.6At Larder: an answer Lena could check

At Larder: solved

Eli spent November 2027 on the perimeter, in the order above. First, a fortnight of looking: with the S3 data-event trail (Chapter 23) he listed every request to Larder's buckets from outside the organisation or outside its VPCs in the previous 30 days. There were three kinds: the finance team's reconciliation script, run from laptops; Athena queries; and a nightly job reading AWS's public package repositories. The finance script moved off laptops into a small scheduled task inside the production VPC, running as the finance-reports role (Chapter 18); Athena is covered by aws:ViaAWSService; the package repositories became a named exception in the resource perimeter.

Then enforcement, staging first: the identity perimeter RCP on the root, with a single tagged exception (WMS B's delivery role, the only role an outside account may assume); the resource perimeter SCP on Workloads; and the network rule on the two restricted buckets. Lena got her answer as three short policies and a list of tested cases, the same cases as the lab below: a stolen finance key used from a laptop is refused; a bucket policy that accidentally named a stranger is overruled; code copying exports to an outside bucket is refused. The same month, Eli closed the medium review finding from October (Chapter 19), alerting on any new federation trust, which is Chapter 23's subject.

On Azure

Azure's network perimeter is mostly a resource setting: storage accounts, Key Vaults and databases can disable public network access and accept traffic only through private endpoints (and, more recently, network security perimeters around groups of PaaS resources). Tenant restrictions stop your users and devices signing in to other organisations' tenants, closing the “copy it to my personal tenant” route.

On Google Cloud

VPC Service Controls draw a perimeter around a set of projects and services: data can't be moved out of it, and API calls from outside are refused unless an access level (network, device, identity) allows them. It covers all three of AWS's perimeters in one feature, and needs the same careful dry-run mode before enforcement.

22.8Lab: test the perimeter before it's real

Lab 22 · Eight requests, three perimeters

You'll run Larder's test cases through a model of the three perimeters, then break each perimeter to see what it was stopping. Optionally, you'll add a network rule to a bucket of your own. You need Python 3; for the optional part, the AWS CLI in a sandbox account. Cost: free.

perimeter.pyPython 3.8+

# perimeter.py · the three data perimeters: trusted identities, trusted resources, expected networks
ORG = "o-a1b2c3d4e5"                     # Larder's organisation
OUR_VPCS = {"vpc-prod", "vpc-staging"}
RESTRICTED = {"larder-order-exports", "larder-settlements"}

def check(req):
    ours_resource = req["resource_org"] == ORG
    ours_principal = req["principal_org"] == ORG
    service = req.get("aws_service", False)
    # 1. identity perimeter (RCP on our resources): only our identities, or AWS services working for us
    if ours_resource and not ours_principal and not (service and req.get("source_org") == ORG) \
            and not req.get("tagged_exception"):
        return "DENY  identity perimeter: caller isn't in our organisation"
    # 2. resource perimeter (SCP on our identities): only resources in our organisation
    if ours_principal and not ours_resource and not service:
        return "DENY  resource perimeter: target isn't in our organisation"
    # 3. network perimeter (restricted buckets' policies): only from our networks, or via an AWS service
    if req["bucket"] in RESTRICTED and req.get("source_vpc") not in OUR_VPCS and not service and not req.get("via_aws_service"):
        return "DENY  network perimeter: not from our networks"
    return "ALLOW (now IAM, resource policies and SCPs decide)"

def r(who, bucket, principal_org=ORG, resource_org=ORG, **extra):
    return dict(who=who, bucket=bucket, principal_org=principal_org, resource_org=resource_org, **extra)

cases = [
    r("finance-reports job in the prod VPC",           "larder-settlements", source_vpc="vpc-prod"),
    r("finance-reports keys, stolen, from a laptop",  "larder-settlements"),
    r("Athena querying exports for a Larder role",    "larder-order-exports", via_aws_service=True),
    r("a stranger, via a too-generous bucket policy", "larder-wmsb-inbound", principal_org="o-zz9stranger"),
    r("Larder code copying data to an outside bucket", "exfil-bucket", resource_org="o-zz9stranger", source_vpc="vpc-prod"),
    r("WMS B assuming its role (tagged exception)",    "role/wmsb-nightly-file", principal_org="o-wmsb", tagged_exception=True),
    r("WMS B, as that role, writing the nightly file", "larder-wmsb-inbound"),
    r("WMS B assuming any other Larder role",          "role/prod-operator", principal_org="o-wmsb"),
    r("CloudTrail writing Larder's logs",              "larder-org-trail", principal_org=None, aws_service=True, source_org=ORG),
    r("CloudTrail, for someone else's organisation",   "larder-org-trail", principal_org=None, aws_service=True, source_org="o-zz9stranger"),
]
for c in cases:
    print(f"{c['who']:<48} {check(c)}")

    An ALLOW here only means the perimeter steps aside; every other policy still applies. Notice the three WMS B lines: one tagged role is the vendor's only way in, and once inside, it's an ordinary Larder session.
  2. Break each perimeter. Comment out one if block at a time and run again. Without the identity perimeter, the stranger, the misdirected CloudTrail and WMS B's attempt on prod-operator get in. (Point the stranger at a restricted bucket instead and the network perimeter still stops them: defence in depth.) Without the resource perimeter, the copy to an outside bucket goes through. Without the network perimeter, the stolen key works. Each rule stops exactly one kind of failure.
  3. Add an exception carefully. Add a case for StockPilot's role reading larder-order-exports directly, from outside the organisation, as it did before September 2027. It's denied. Now add an exception for it to the identity check; which other check still denies it, and why is that a good thing? (The network perimeter: the exports are restricted, and StockPilot's systems aren't in Larder's VPCs.)
  4. Optional: a network rule for real. In a sandbox account, add the statement from 22.4 to a test bucket's policy, using the ID of a VPC you have (or a made-up one), and with your own role's ARN as the aws:PrincipalArn exception so you can remove it again. From your laptop, aws s3 ls s3://bucket as another role is refused with an explicit deny in a resource-based policy. Remove the statement afterwards.

✓Chapter summary

  • A data perimeter is a few organisation-wide guardrails that make whole classes of mistakes harmless.
  • Identity: only our identities (or AWS services working for us) reach our resources; an RCP with aws:PrincipalOrgID.
  • Resource: our identities reach only our resources; an SCP and endpoint policies with aws:ResourceOrgID.
  • Network: restricted data, and credentials, only from expected networks; aws:SourceVpc, aws:ViaAWSService, EC2 source keys.
  • Partners enter through a few tagged roles, the perimeter's only exceptions; after that they act inside it.
  • Look before you enforce, roll out by environment, keep break-glass working.

Key terms

Data perimeter
Preventive guardrails ensuring only trusted identities reach trusted resources from expected networks.
aws:PrincipalOrgID
The organisation of the calling principal.
aws:ResourceOrgID
The organisation that owns the resource being accessed.
aws:SourceOrgID
The organisation of the resource an AWS service is acting for.
aws:SourceVpc / aws:SourceVpce
The VPC or VPC endpoint a request came through.
aws:ViaAWSService
True when an AWS service makes a request on a principal's behalf.

Check your understanding

  1. Which perimeter stops each: a bucket policy that grants "Principal": "*"; a compromised build job uploading source code to its own bucket; a leaked access key used from a hotel? recall

    Show answer

    Identity perimeter; resource perimeter; network perimeter (for data and credentials it covers).

  2. Why does the identity perimeter need a separate statement for AWS services? explain

    Show answer

    AWS services aren't in your organisation, so the first statement exempts them; but without a check they could be pointed at your resources by someone else (a confused deputy). The second statement allows services only when aws:SourceOrgID is your organisation.

  3. After enforcing the network perimeter, the finance team's monthly report fails. What do you do? apply

    Show answer

    Don't remove the rule: move the job to run inside the VPC (or through a service covered by aws:ViaAWSService), with its own role. If it truly can't, add a narrow, documented exception, and fix the process that let it go unnoticed before enforcement.

  4. A vendor needs to read one Larder bucket. Should it get a bucket-policy grant or a role in Larder's account, given the perimeter? design

    Show answer

    A role in Larder's account with an external ID, tagged as the vendor's perimeter exception: only the assume-role step needs the exception, its sessions are then inside Larder's organisation, and Larder controls the permissions. A direct bucket grant would need an exception on the bucket itself, and still meets the network rule for restricted data.

  5. Why roll out perimeters with data-event analysis first, rather than relying on testing? explain

    Show answer

    Perimeters apply to every request, including forgotten jobs and rare paths that tests don't cover. Real traffic from CloudTrail data events shows every request that would be denied, so exceptions can be written before anything breaks.

  6. Compare how Google Cloud and AWS stop data being copied to an outside storage bucket. compare

    Show answer

    Google Cloud: a VPC Service Controls perimeter around the projects blocks copying data to resources outside it. AWS: an SCP (and endpoint policies) denying requests whose aws:ResourceOrgID isn't your organisation.
