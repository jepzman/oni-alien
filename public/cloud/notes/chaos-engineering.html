Chaos Engineering

TL;DR

Failover, retries, autoscaling and runbooks are claims until something fails. Chaos engineering tests them with planned experiments on a running system: define a steady state (a user-facing metric), write a hypothesis (“if a zone fails, checkout stays above 99%”), inject the fault in a small, abortable way, and observe. Start in staging and with game days; move to production carefully. Every surprise becomes a fix.

  • Family: resilience
  • Started at: Netflix (Chaos Monkey, 2011)
  • Faults: kill instances · zone loss · latency · dependency outage · clock skew
  • Vol. 4 cousin: fault injection tests inside the test suite

1The problem why do we even need this?

The diagram says the database fails over automatically. In the first real zone outage, the standby is promoted on time, but the application's connection pool never reconnects and its DNS cache holds the old address for an hour. The failover worked on paper and failed in practice, and its first test was a real outage.

  • Resilience mechanisms are rarely exercised, so they rot: configs change, assumptions break.
  • Distributed systems fail in combinations no design review imagines.
  • On-call people meet each failure for the first time during the incident.

2Real-life analogy a vaccine

A vaccine is a small, measured dose of something harmful, given on purpose while the body is healthy, so it learns to cope before the real thing arrives. The patient is watched, and it's stopped if the reaction is too strong.

3How it solves it the experiment loop

Each experiment is a small scientific test. The steady state is a metric users feel; the hypothesis says it stays within limits during a specific fault; the blast radius is kept small; an abort condition stops the fault automatically if the metric drops too far. A disproved hypothesis is the point: it's a weakness found on your schedule, not the incident's.

  1. Pick a weakness you suspect

    Failover, a slow dependency, losing a zone, a full disk, an expired certificate.

  2. Define steady state

    A user-facing metric with a normal range: checkout success, search latency.

  3. Write the hypothesis and limits

    What should happen, how much traffic is in scope, and when to abort.

  4. Run it, small and watched

    Staging first, then production in a small slice, during working hours, with the owners present (a game day).

  5. Fix and repeat

    Turn findings into fixes, re-run to confirm, then schedule it to run automatically.

Vocabulary for the exam

Chaos engineering
Experimenting on a system to build confidence it can withstand turbulent conditions.
Steady state
The normal range of a metric users care about.
Hypothesis
What you expect to stay true during the fault.
Blast radius
How much of the system and its users the experiment can affect.
Abort condition
The rule that stops the experiment automatically.
Game day
A planned session where a team runs failure experiments together.
zone-failure.yamlChaos Mesh (Kubernetes)
# hypothesis: if orders loses its pods in zone b, checkout success stays >= 99% and recovers within 2 min
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: { name: orders-zone-b-loss, namespace: chaos }
spec:
  action: pod-kill
  mode: all
  selector:
    namespaces: [shop]
    labelSelectors: { app: orders }
    nodeSelectors: { topology.kubernetes.io/zone: eu-west-1b }
  duration: "10m"
---
# abort: stop the experiment if checkout success drops below 98.5% (alert wired to delete the PodChaos)
# run in staging first; in production, during a game day, with the orders team watching

4Gains vs losses nothing is free

What we gain

  • Failover and recovery are proven, not assumed.
  • Weaknesses found on your schedule, during working hours.
  • Practised on-call: the team has seen the failure before.
  • Better runbooks and alerts from every experiment.

What we lose

  • Real risk if the blast radius or abort is wrong.
  • Needs good observability first, or you can't see the result.
  • Time: planning, game days, follow-up work.
  • Trust to earn with the business before production experiments.

6Common pitfalls the usual ways this goes wrong

  • Chaos without a hypothesis

    Killing random things and watching what happens teaches little and scares everyone. Fix → one suspected weakness, a written hypothesis and a steady-state metric per experiment.

  • No abort condition

    An experiment keeps running while customers suffer. Fix → an automatic stop tied to the steady-state metric, and a person ready to stop it.

  • Starting in production

    The first experiment ever takes down checkout. Fix → staging and game days first; production with a tiny blast radius once trust is earned.

  • Findings without fixes

    The same weakness shows up in every game day. Fix → track findings as tickets with owners, and re-run the experiment to confirm the fix.

7When to use it (and when not)

Use it when…

  • Systems with failover, redundancy or autoscaling you rely on.
  • Before peak events (sales, launches) to test the plan.
  • Teams with good monitoring and an on-call rotation.

Skip it when…

  • No observability yet: you won't be able to tell what happened.
  • Known weaknesses already waiting to be fixed: fix them first.
  • A system that can't take any risk and has no staging copy (build one first).

8Self-check quiz

What are the parts of a chaos experiment?

A steady-state metric, a hypothesis, a fault with a limited blast radius, an abort condition, and observation of the result.

Why define steady state with a user-facing metric?

It measures what matters (users succeeding), not whether a single server is up.

Why start in staging and with game days?

To learn safely and build trust before running small, controlled experiments in production.

How is chaos engineering different from fault injection tests?

Chaos experiments run against a whole running system and its operations; fault injection tests run inside the test suite against code.

what would you do?Leadership wants to “turn on Chaos Monkey in production” next week. There's no steady-state metric for checkout, and alerts are mostly on CPU. What do you propose instead?

First define steady-state SLIs (checkout success, latency) with alerts on them. Then run a game day in staging with one hypothesis (an instance or zone loss), fix what it finds, and only then run small, abortable experiments in production during working hours.

try it

Pick one resilience claim in your system (“if one instance dies, users don't notice”). Write it as a hypothesis with a steady-state metric, then test it in staging: delete one pod or stop one instance while a load generator runs, and watch the metric. Write down what happened, what surprised you, and one fix.

remember!!

A small dose, on purpose, with a hand on the stop button.
