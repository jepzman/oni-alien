Canary Releases

TL;DR

Release a new version to a small slice of traffic first (1–5%), compare its metrics (errors, latency, business signals) with the stable version, and widen in steps only while it stays healthy. If any check fails, shift traffic back automatically. A bad release hurts a few users for a few minutes, not everyone.

  • Family: progressive delivery
  • Tools: Argo Rollouts, Flagger, AWS CodeDeploy, Cloud Run, Spinnaker/Kayenta
  • Signals: error rate, p95 latency, saturation, business KPIs
  • Pairs with: SLOs, observability, feature flags

1The problem why do we even need this?

Some bugs only show up with real traffic: a device type, a data shape, a load pattern. If every user gets the new version at once, every affected user hits the bug before anyone notices.

  • Staging passed, production broke for 5% of users, all at once.
  • Alerts fire after the damage is done.
  • Rollback decisions are made by a tired human under pressure.

2Real-life analogy the canary in the coal mine

Miners once carried a canary underground. The bird reacted to bad air long before people would, so the miners got out in time. Only the canary was exposed first.

  • The canary is the small slice of traffic on the new version.
  • Watching the bird is automated analysis.
  • Getting out is automatic rollback.

3How it solves it small slice, compare, widen

The key is comparison: canary vs stable at the same time, so normal daily ups and downs don't fool the analysis.

  1. Split traffic

    Weighted routing in the load balancer, ingress or service mesh.

  2. Define health

    Error rate, p95 latency, saturation and a business signal (checkouts per minute).

  3. Compare against stable

    Same window, same metrics; thresholds or statistical analysis.

  4. Step up

    1% → 5% → 25% → 50% → 100%, pausing at each step.

  5. Automate rollback

    Any failed check sends all traffic back to stable without a human.

  6. Keep it sticky when needed

    Route the same user consistently so they don't flip between versions.

rollout.yamlArgo Rollouts
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: checkout }
spec:
  strategy:
    canary:
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - analysis: { templates: [{ templateName: error-rate-vs-stable }] }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
# AnalysisTemplate: fail if canary 5xx rate > stable + 0.5% or p95 > 400 ms
# a failed analysis aborts the rollout and returns traffic to stable

tools: Argo Rollouts, Flagger (with Istio, Linkerd, NGINX, Gateway API), AWS CodeDeploy / Lambda aliases, Google Cloud Run and Cloud Deploy, Spinnaker with Kayenta, mobile staged rollouts (Play Console, App Store phased release).

4Gains vs losses nothing is free

What we gain

  • Small blast radius for bad releases.
  • Real-traffic validation, not just staging.
  • Automatic rollback.
  • Confidence to deploy often.

What we lose

  • Needs good metrics and enough traffic.
  • Slower full rollout.
  • Two versions live: data and API compatibility.
  • More tooling (mesh, rollout controller).

6Common pitfalls the usual ways this goes wrong

  • Too little traffic

    1% of 50 requests/min tells you nothing. Fix → longer steps or a bigger first slice.

  • Only technical metrics

    No errors, but checkouts dropped 30%. Fix → include a business signal.

  • Manual watching

    Someone has to stare at dashboards. Fix → automate analysis and rollback.

  • Incompatible versions

    v1 and v2 write data the other can't read. Fix → backward-compatible APIs and schemas.

7When to use it (and when not)

Use it when…

  • Services with steady traffic and good metrics.
  • High-risk changes and frequent releases.
  • Mobile and desktop apps (staged rollouts).

Skip it when…

  • Very low traffic (use flags for internal users instead).
  • Changes that can't run side by side with the old version.

8Self-check quiz

Why compare the canary with the stable version rather than a fixed threshold?

Traffic and error rates vary over the day; comparing at the same time removes that noise.

What should happen when canary analysis fails?

Traffic is automatically shifted back to the stable version.

Why add a business metric?

A release can be technically healthy while breaking something users care about, like checkout.

When is canary a poor fit?

Very low traffic, or changes that can't run alongside the old version.

remember!!

Send the canary first, watch it closely, and leave the mine if it struggles.
