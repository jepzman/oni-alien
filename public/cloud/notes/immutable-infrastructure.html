Immutable Infrastructure

TL;DR

Never change a running server. Bake everything (OS, patches, runtime, app) into an image, launch instances from it, and to change anything bake a new image and replace the old instances. Servers become identical and disposable (cattle, not pets), drift disappears, and rollback is launching the previous image.

  • Family: infrastructure
  • Phrase: “cattle, not pets” (Bill Baker / Randy Bias)
  • Tools: containers, Packer, managed instance groups, Bottlerocket
  • Pairs with: build once, IaC, autoscaling

1The problem why do we even need this?

Servers that are patched by hand slowly become unique snowflakes. Nobody knows exactly what's on them, they can't be recreated, and everyone is afraid to touch them.

  • “It works on web-01 but not web-03.”
  • A security patch applied to 9 servers out of 10.
  • Rebooting is a risk; replacing is impossible.

2Real-life analogy paper cups vs the treasured mug

A treasured mug gets chipped, glued and repaired, and when it finally breaks it's a crisis. Paper cups are all identical; if one is damaged you just take a fresh one from the stack. Nobody repairs a paper cup.

  • The mug is a pet server.
  • Paper cups are instances from an image.
  • The stack of cups is your image, reproducible on demand.

3How it solves it replace, don't repair

Containers made this the default for apps; the same idea applies to VMs (golden images) and even to node operating systems.

  1. Bake images in CI

    Container images or VM images (Packer) with OS patches and the app.

  2. Launch from images only

    Instance groups or Kubernetes pull a specific image version.

  3. Externalise state

    Data in databases, object storage and volumes, not on the instance disk.

  4. Roll out by replacement

    Rolling, blue–green or canary replacement of instances.

  5. Remove SSH

    Use logs, metrics and ephemeral debug sessions instead of shell access.

  6. Rebuild regularly

    Bake weekly even without app changes, to pick up patches.

  instance_type = "t3.small"
  source_ami_filter { filters = { name = "al2023-ami-*-x86_64" } most_recent = true owners = ["amazon"] }

build {
  sources = ["source.amazon-ebs.web"]
  provisioner "shell" { inline = ["sudo dnf -y update", "sudo dnf -y install nginx"] }
  provisioner "file"  { source = "dist/", destination = "/srv/web" }
}

4Gains vs losses nothing is free

What we gain

  • No drift: every instance is identical.
  • Easy rollback: launch the previous image.
  • Fearless replacement and autoscaling.
  • Smaller attack surface without SSH.

What we lose

  • Every change needs a bake and rollout.
  • Image pipelines to build and maintain.
  • State must live elsewhere.
  • Debugging without shell access takes new habits.

6Common pitfalls the usual ways this goes wrong

  • Data on the instance

    Uploads stored on local disk vanish on replacement. Fix → object storage, databases, persistent volumes.

  • Break-glass SSH becomes normal

    “Just this once” edits return. Fix → audit any access; bake the fix into the next image.

  • Stale images

    Images built months ago with old patches. Fix → rebuild on a schedule.

  • Slow bakes

    45-minute image builds discourage fixes. Fix → layered images, caching, smaller base images.

7When to use it (and when not)

Use it when…

  • Stateless app servers, workers, container nodes.
  • Fleets that autoscale.
  • Security-sensitive environments.

Skip it when…

  • Stateful databases without a managed service (handle carefully).
  • Legacy systems that can't be automated yet (start by codifying them).

8Self-check quiz

What does “cattle, not pets” mean?

Servers are identical and replaceable rather than unique and hand-maintained.

How do you patch an immutable server?

Bake a new image with the patch and replace the instances.

What must happen to state?

It must live outside the instance (databases, object storage, volumes).

Why remove SSH?

It prevents drift from manual changes and removes an attack path.
