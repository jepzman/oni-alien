Preview Environments

TL;DR

Give every pull request its own short-lived environment with a unique URL: the app, its dependencies and a seeded database, created by the pipeline from your infrastructure code. Reviewers, designers and product managers can try the change before merge. When the PR is merged or closed, everything is destroyed, with a time-to-live as a safety net.

  • Family: developer workflow
  • a.k.a.: ephemeral / review apps, PR environments
  • Tools: Vercel, Netlify, Render, Argo CD ApplicationSet, Neon branches
  • Pairs with: IaC, build once, feature flags

1The problem why do we even need this?

A single shared staging environment becomes a queue and a battlefield: one broken branch blocks everyone, and non-developers can't see changes until they're merged.

  • Teams wait for their turn on staging.
  • Someone's half-finished change breaks it for everyone else.
  • Design and product review happens after merge, when fixes are slower.

2Real-life analogy pop-up market stalls

At a market, each vendor gets a pop-up stall for the day, set up in minutes from a standard kit. Customers can try things, and in the evening it's packed away. Nobody has to share one stall and wait their turn.

  • Each stall is a preview environment.
  • The standard kit is your IaC + build.
  • Packing up is automatic teardown.

3How it solves it create on open, destroy on close

The hardest part is usually data: use seeded fixtures or cheap database branches, never a copy of production personal data.

  1. Make environments cheap to create

    IaC modules and small, scaled-down resources.

  2. Trigger from PR events

    On open/push: build, deploy to pr-<n>; post the URL.

  3. Seed the data

    Fixtures or database branches (Neon, PlanetScale); no production PII.

  4. Stub expensive dependencies

    Shared sandbox accounts for payments and email.

  5. Destroy automatically

    On merge/close, plus a TTL for idle environments.

  6. Protect them

    SSO or basic auth in front; they're not public sites.

.github/workflows/preview.ymlper-PR namespace
on:
  pull_request: { types: [opened, synchronize, reopened, closed] }

jobs:
  preview:
    if: github.event.action != 'closed'
    steps:
      - run: ./build.sh                             # image tagged with the PR sha
      - run: |
          helm upgrade --install pr-${{ github.event.number }} ./chart \
            --namespace pr-${{ github.event.number }} --create-namespace \
            --set image.digest=$DIGEST --set db.branch=pr-${{ github.event.number }} \
            --set ingress.host=pr-${{ github.event.number }}.preview.acme.dev
      - run: gh pr comment ${{ github.event.number }} --body "Preview ready"

  teardown:
    if: github.event.action == 'closed'
    steps:
      - run: kubectl delete namespace pr-${{ github.event.number }}

tools: Vercel and Netlify preview deploys, Render/Heroku review apps, Argo CD ApplicationSet pull-request generator, Okteto, Uffizzi, Neon / PlanetScale / Supabase database branching, kube-janitor for TTL cleanup.

4Gains vs losses nothing is free

What we gain

  • No staging queue.
  • Review the real thing before merge.
  • Isolated: one broken PR breaks only itself.
  • Proves IaC works many times a day.

What we lose

  • Cloud cost if teardown fails.
  • Data seeding takes effort.
  • Not production-sized: performance differs.
  • External integrations need sandboxes.

6Common pitfalls the usual ways this goes wrong

  • No teardown

    200 forgotten environments on the bill. Fix → destroy on close + TTL + cost alerts.

  • Copying production data

    Customer PII in dozens of temporary environments. Fix → seeded fake data or anonymised subsets.

  • Public preview URLs

    Unreleased features indexed by search engines. Fix → SSO/basic auth, noindex.

  • Full-size infrastructure per PR

    Each preview costs as much as staging. Fix → scale down; share heavy dependencies.

7When to use it (and when not)

Use it when…

  • Web apps and APIs with frequent PRs.
  • Teams where design and product review matter.
  • Several teams sharing one staging environment.

Skip it when…

  • Systems too heavy to clone (use shared integration environments + flags).
  • Very early prototypes with one developer.

8Self-check quiz

What triggers a preview environment's creation and deletion?

Opening/updating a pull request creates or updates it; merging or closing destroys it.

Why add a TTL?

To clean up environments that were never torn down and keep costs under control.

What data should previews use?

Seeded fake data or database branches from safe data, never raw production PII.

What's the main benefit over shared staging?

No queue and no interference: each change is reviewed in isolation before merge.
