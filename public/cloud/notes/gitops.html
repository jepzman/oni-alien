GitOps

TL;DR

Keep the desired state of each environment (what image, how many replicas, which config) in a git repository. An agent inside the cluster (Argo CD, Flux) pulls that repo and continuously reconciles reality to match. All changes go through pull requests; manual changes show up as drift and are reverted; rollback is git revert.

  • Family: deployment / operations
  • Coined by: Weaveworks (2017)
  • Tools: Argo CD, Flux, Rancher Fleet
  • Pairs with: IaC, build once, immutable infrastructure

1The problem why do we even need this?

When CI pushes into clusters with admin credentials and people also change things by hand, nobody can say what's running, and every change path is a different risk.

  • A manual hotfix is silently overwritten by the next deploy.
  • CI holds cluster-admin keys, a high-value target.
  • Rolling back means rebuilding someone's memory of the last good state.

2Real-life analogy the thermostat

You set a thermostat to 21 °C. It measures the room all day and turns the heating on or off to match. Open a window and it corrects automatically. You change the setting, never the heater directly.

  • The setting is the git repo.
  • The thermostat is the GitOps agent.
  • The open window is drift from manual changes.

3How it solves it pull and reconcile

Because the agent pulls from inside the cluster, CI never needs cluster credentials: it only opens a PR (or commits) bumping the image digest.

  1. Separate config from app code

    A config repo (or folder) per environment with manifests, Helm values or Kustomize overlays.

  2. Install the agent

    Argo CD or Flux in each cluster, with read access to the repo.

  3. CI updates git, not the cluster

    After a build, CI opens a PR bumping the digest for staging.

  4. Promote by PR

    Promotion to prod is a reviewed change to the prod folder.

  5. Self-heal and alert on drift

    Auto-sync reverts manual edits; alerts tell you it happened.

  6. Roll back with git

    git revert the bad change; the agent syncs.

Vocabulary for the exam

Desired state
What should be running, written in git.
Reconciliation
Making actual state match desired state.
Pull-based deploy
The cluster fetches changes instead of CI pushing.
Sync
Applying differences to the cluster.
Drift
Live state differing from git.
Environment promotion
Moving a version to the next environment via PR.
apps/web-prod.yamlArgo CD Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: web-prod, namespace: argocd }
spec:
  project: storefront
  source:
    repoURL: https://github.com/acme/deploy-config
    path: envs/prod/web            # kustomization with the image digest
    targetRevision: main
  destination: { server: https://kubernetes.default.svc, namespace: web }
  syncPolicy:
    automated:
      prune: true                  # delete what git no longer lists
      selfHeal: true               # revert manual changes (drift)
# CI's only job after building: open a PR changing the digest in envs/staging/web

tools: Argo CD, Flux, Rancher Fleet, Kargo (promotion), Kustomize and Helm for manifests, Renovate or image-updater bots for digest bumps, Terraform/Crossplane for GitOps-managed cloud resources.

4Gains vs losses nothing is free

What we gain

  • Git is the truth for what runs.
  • Rollback = git revert.
  • No cluster credentials in CI.
  • Drift detected and fixed automatically.

What we lose

  • More repos and moving parts.
  • Secrets need a separate approach (sealed secrets, external secrets).
  • Emergency changes still go through git.
  • Mostly Kubernetes-centric tooling.

6Common pitfalls the usual ways this goes wrong

  • Secrets in the config repo

    Plain-text secrets in git. Fix → External Secrets, Sealed Secrets or SOPS.

  • Manual changes during incidents

    Someone kubectl-edits; the agent reverts it mid-incident. Fix → make the fix in git, or pause sync deliberately.

  • CI pushes and agent syncs

    Two systems fighting over the same resources. Fix → one source of truth: git.

  • Huge monorepo of manifests

    Every sync touches everything. Fix → split by team or app; use app-of-apps.

7When to use it (and when not)

Use it when…

  • Kubernetes platforms with several services and environments.
  • Teams that need audit trails and easy rollback.
  • Many clusters that should stay consistent.

Skip it when…

  • A single small app on a PaaS (its own deploy is enough).
  • Infrastructure without a reconciling agent (use IaC pipelines).

8Self-check quiz

What does the GitOps agent do?

Continuously compares the cluster with the desired state in git and syncs any difference.

Why is pull-based deployment more secure?

CI doesn't need cluster credentials; the in-cluster agent pulls changes.

How do you roll back?

Revert the commit in the config repo; the agent syncs the previous state.

What happens to a manual kubectl change?

It's detected as drift and reverted (with self-heal on).
