Health Checks & Probes

TL;DR

Let the platform ask every instance two different questions: “are you alive?” (liveness: if not, restart it) and “can you serve traffic right now?” (readiness: if not, stop sending requests until it recovers). Add a startup check for slow boots. Keep liveness cheap and local, so a slow database doesn't trigger a restart storm.

  • Family: runtime operations
  • Probes: startup, liveness, readiness
  • Used by: Kubernetes, load balancers, ECS, Cloud Run
  • Pairs with: autoscaling, blue–green, circuit breaker (Vol. 1)

1The problem why do we even need this?

“The process is running” isn't the same as “it works”. Without real health checks, a stuck or half-started instance keeps receiving traffic, and every request it gets fails.

  • A deadlocked instance serves errors for hours.
  • New instances get traffic before they've warmed up.
  • A bad health check restarts every pod when the database is slow.

2Real-life analogy the ward round

On her round, a nurse asks each patient two different questions: “are you alive and breathing?” and “are you ready for visitors today?”. A patient can be alive but not ready for visitors, and that needs a very different response.

  • “Alive?” is the liveness probe; “no” means call the doctor (restart).
  • “Visitors?” is readiness; “no” means no traffic for now.

3How it solves it three probes, three actions

The classic mistake is making liveness check dependencies. If the database is slow, every instance fails liveness and restarts, turning a slowdown into an outage.

  1. Add endpoints

    /livez (process responsive) and /readyz (can serve: warmed up, critical deps reachable).

  2. Keep liveness local

    No database or downstream calls; just “is my event loop alive?”.

  3. Make readiness honest

    Fail while starting, while draining on shutdown, or when a critical dependency is down.

  4. Tune timings

    Startup probe for slow boots; failure thresholds that avoid flapping.

  5. Drain on shutdown

    On SIGTERM: fail readiness, finish in-flight requests, then exit.

  6. Wire them everywhere

    Kubernetes probes, load balancer health checks, deploy gates.

Vocabulary for the exam

Liveness
Is the process alive and not stuck?
Readiness
Can this instance serve traffic right now?
Startup probe
Gives slow apps time before liveness starts.
Graceful shutdown
Stop taking traffic, finish work, then exit.
Flapping
Rapidly switching between healthy and unhealthy.
Restart storm
Many instances restarting at once.
deployment.yaml + health.tsKubernetes + Express
startupProbe:   { httpGet: { path: /livez,  port: 8080 }, failureThreshold: 30, periodSeconds: 2 }
livenessProbe:  { httpGet: { path: /livez,  port: 8080 }, periodSeconds: 10, failureThreshold: 3 }
readinessProbe: { httpGet: { path: /readyz, port: 8080 }, periodSeconds: 5,  failureThreshold: 2 }

// health.ts
let draining = false;
app.get("/livez", (_req, res) => res.sendStatus(200));          // local only
app.get("/readyz", async (_req, res) => {
  if (draining || !cache.warm) return res.sendStatus(503);
  const dbOk = await db.ping({ timeoutMs: 300 }).catch(() => false);
  res.sendStatus(dbOk ? 200 : 503);                              // stop traffic, don't restart
});
process.on("SIGTERM", () => { draining = true; setTimeout(() => server.close(), 10_000); });

4Gains vs losses nothing is free

What we gain

  • Broken instances stop getting traffic.
  • Stuck processes heal by restart.
  • Safe rollouts: new pods only get traffic when ready.
  • Graceful shutdowns without dropped requests.

What we lose

  • Badly designed checks can cause outages.
  • Tuning timings takes care.
  • Readiness can hide a problem if nobody alerts on it.

6Common pitfalls the usual ways this goes wrong

  • Dependencies in liveness

    DB slows down; every pod restarts; full outage. Fix → liveness local only; deps in readiness.

  • No startup probe

    Slow-booting apps get killed in a restart loop. Fix → startup probe or initial delay.

  • Health endpoint does heavy work

    Probes cause load themselves. Fix → make checks cheap; cache dependency status briefly.

  • Ignoring SIGTERM

    In-flight requests fail on every deploy. Fix → fail readiness, drain, then exit.

7When to use it (and when not)

Use it when…

  • Every service behind a load balancer or orchestrator.
  • Rolling, blue–green and canary deployments.
  • Workers that can get stuck.

Skip it when…

  • Short-lived batch jobs (use timeouts and exit codes).

Related patterns

8Self-check quiz

What's the difference between liveness and readiness?

Liveness asks if the process is stuck (restart it); readiness asks if it can serve now (stop sending traffic).

Why shouldn't liveness check the database?

A slow database would make all instances fail liveness and restart at once.

What does a startup probe protect against?

Slow-booting apps being killed by liveness before they finish starting.

What should an app do on SIGTERM?

Fail readiness, finish in-flight requests, then exit.

remember!!

Ask “alive?” and “ready?” separately. Alive isn't ready.
