Build Once, Deploy Many

TL;DR

Build your app exactly once per commit into an immutable artefact (a container image, a bundle), identify it by digest, test it, and promote that same artefact through test, staging and production. Each environment supplies its own configuration and secrets at runtime. What you tested is, byte for byte, what you ship.

  • Family: delivery pipeline
  • Artefacts: container images, JARs, bundles, AMIs
  • Identify by: content digest + commit SHA
  • Pairs with: blue–green, GitOps, supply-chain hygiene (Vol. 5)

1The problem why do we even need this?

When each environment gets its own build, dependencies, compilers and base images can differ between them. The code that passed testing is not the code that ships.

  • Production pulled a newer library than staging tested.
  • Environment-specific values are baked in at build time.
  • Nobody can say exactly what's running in production.

2Real-life analogy the sealed shipping container

A shipping container is packed and sealed once at the factory. It moves from truck to train to ship without being opened, and the seal number proves it. Only the address label changes along the way.

  • The sealed container is the artefact.
  • The seal number is the digest.
  • The address label is runtime config.

3How it solves it one artefact, many environments

Promotion becomes a pointer change (“prod now runs digest 9c1e…”), which also makes rollback a pointer change.

  1. Build in CI only

    No laptop builds for deploys; reproducible inputs (lockfiles, pinned base images).

  2. Tag by commit and digest

    Human-readable tag + immutable digest; deploy by digest.

  3. Keep config out of the build

    Environment variables, config maps and secrets injected at runtime (12-factor).

  4. Promote, don't rebuild

    The pipeline moves the same digest from test → staging → prod.

  5. Record what's where

    A deploy log or GitOps repo states which digest runs in each environment.

  6. Roll back by pointer

    Redeploy the previous digest.

Vocabulary for the exam

Artefact
The built, deployable output of a commit.
Immutable
Never changed after it's built.
Digest
A content hash that uniquely identifies an artefact.
Promotion
Moving an artefact to the next environment.
12-factor config
Config from the environment, not the build.
Reproducible build
Same inputs always produce the same output.
.github/workflows/release.ymlbuild once, promote by digest
jobs:
  build:
    outputs: { digest: ${{ steps.push.outputs.digest }} }
    steps:
      - uses: actions/checkout@v5
      - id: push
        uses: docker/build-push-action@v6
        with: { push: true, tags: "ghcr.io/acme/web:${{ github.sha }}" }

  deploy-staging:
    needs: build
    steps:
      - run: ./deploy.sh staging ghcr.io/acme/web@${{ needs.build.outputs.digest }}

  deploy-prod:
    needs: [build, deploy-staging]
    environment: production              # approval gate
    steps:
      - run: ./deploy.sh prod ghcr.io/acme/web@${{ needs.build.outputs.digest }}

tools: container registries (GHCR, ECR, Artifact Registry), artefact repositories (Artifactory, Nexus), Docker Buildx / Bazel for reproducible builds, deploy-by-digest in Kubernetes and Cloud Run, Kustomize/Helm for per-environment config.

4Gains vs losses nothing is free

What we gain

  • Tested = shipped, byte for byte.
  • Faster pipelines: no rebuilds.
  • Clear inventory of what runs where.
  • Simple rollback to a previous digest.

What we lose

  • Config discipline: nothing environment-specific at build time.
  • Registry storage for many artefacts.
  • Frontend builds that inline env vars need rework.

6Common pitfalls the usual ways this goes wrong

  • Baking config into the build

    API_URL inlined at build time per environment. Fix → load config at runtime (or a config.json served per environment).

  • Deploying by mutable tag

    :latest or :staging changes underneath you. Fix → deploy by digest.

  • Laptop builds

    “Quick fix” built and pushed from a laptop. Fix → only CI builds deployable artefacts.

  • Rebuilding for a hotfix

    The emergency fix skips the pipeline. Fix → same pipeline, just faster gates.

7When to use it (and when not)

Use it when…

  • Any service deployed to more than one environment.
  • Container-based and serverless deployments.
  • Regulated environments that need traceability.

Skip it when…

  • Truly single-environment scripts.
  • Static sites whose content is the build (still: build once per content change).

8Self-check quiz

Why not rebuild for each environment?

Dependencies and tools can differ between builds, so the shipped code isn't what was tested.

Why deploy by digest rather than tag?

Tags can be moved; a digest always identifies the exact same artefact.

Where should environment-specific values come from?

Runtime configuration and secrets, not the build.

How does rollback work?

Redeploy the previous known-good digest.

remember!!

Pack it once, check the seal, change only the label.
