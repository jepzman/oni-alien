Progressive Delivery

TL;DR

A canary tests a change on a small slice. Progressive delivery extends that to the whole rollout: the same build moves through rings (staff, a small canary, one region, then the rest, one at a time), with a bake time and an automated gate between rings that compares errors, latency, a business metric and the SLO burn rate with the old version. A failing gate rolls back on its own. Feature flags do the same for features inside a deploy.

1The problem why do we even need this?

A release passed its canary: 5% of one region for 15 minutes. Then it went to all six regions at once. A bug that only showed with one region's payment provider took down checkout there, and a config value missing in another region took that one down too, at the same time, on the same evening.

  • A single canary can't see problems that depend on region, tenant, time of day or scale.
  • After the canary, the next step is usually everything: the largest possible blast radius.
  • Humans watching dashboards decide “looks fine” differently at 6 p.m. on a Friday.

2Real-life analogy opening a new metro line

A new metro line doesn't open to rush hour on day one. Staff ride it first, then a few off-peak trains with passengers, then one branch at rush hour, then the whole line. An inspector checks a list before each step, and if anything is off, they stop and go back one step.

3How it solves it rings, bake times, automatic gates

Define the rings once, as part of the pipeline. Each ring has a size, a bake time long enough to see real traffic (including a peak if possible), and a gate: queries that compare the new version with the old on errors, latency, a business signal, and the SLO burn rate. Passing gates promote the build; failing gates roll back and stop the rollout, without anyone needing to be awake.

  1. Define the rings

    Internal → 1% canary in one region → that region → other regions one by one (or by cell or tenant group).

  2. Set bake times

    Long enough to see normal traffic: 30–60 minutes per ring, longer for changes that touch nightly jobs.

  3. Write the gates as queries

    Error rate, p99 latency and a business metric (checkout success), each compared with the stable version, plus SLO burn.

  4. Roll back automatically

    A failed gate shifts traffic back and pages the owner; promotion past it needs a fix, not a click.

  5. Use flags for features

    Deploy dark, then enable the feature ring by ring with flags, using the same gates.

Vocabulary for the exam

Progressive delivery
Rolling out in stages with automated checks between them.
Ring
A group of users, hosts or regions that gets a release together.
Bake time
How long a release runs in a ring before the next step.
Gate
An automated check that decides promote or roll back.
Blast radius
How many users a bad change can reach.
Cell
An independent copy of the stack serving a slice of users.
rollout.yamlArgo Rollouts, one region (generic)
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: checkout }
spec:
  strategy:
    canary:
      steps:
        - setWeight: 1
        - pause: { duration: 30m }          # bake
        - analysis: { templates: [{ templateName: checkout-gate }] }
        - setWeight: 25
        - pause: { duration: 60m }          # includes the evening peak when possible
        - analysis: { templates: [{ templateName: checkout-gate }] }
        - setWeight: 100
---
kind: AnalysisTemplate
metadata: { name: checkout-gate }
spec:
  metrics:
    - name: checkout-success-vs-stable       # business signal, canary minus stable
      successCondition: result[0] >= -0.5      # at most 0.5 points worse
      failureLimit: 1
      provider: { prometheus: { query: "{{ checkout_success_canary - checkout_success_stable }}" } }
# the pipeline runs this per region, one region at a time, and stops on the first failure

tools: Argo Rollouts, Flagger, Spinnaker / Kayenta, AWS CodeDeploy and AppConfig, Google Cloud Deploy, Azure Deployment Environments, LaunchDarkly / Unleash / OpenFeature for flag rollouts.

4Gains vs losses nothing is free

What we gain

  • Small blast radius at every step.
  • Problems that need scale or a region show up early and in one place.
  • No one has to watch dashboards: gates decide, consistently.
  • Faster, calmer releases overall: more deploys, fewer incidents.

What we lose

  • Slower full rollout: hours instead of minutes.
  • Good metrics are required: gates are only as smart as the queries.
  • Mixed versions run side by side for longer.
  • Pipeline complexity: rings, analysis templates, region ordering.

6Common pitfalls the usual ways this goes wrong

  • Gates on averages only

    Overall error rate looks fine while one tenant or region is broken. Fix → compare canary with stable, and split by region or tenant where it matters.

  • Bake times too short

    15 minutes at 3 a.m. sees almost no traffic. Fix → bake long enough to see real load, or until enough requests have passed.

  • Manual promotion

    A person clicks “promote” after a glance, and the gates are ignored. Fix → let passing gates promote; overriding a failure needs a recorded reason.

  • Database changes in the rollout

    The schema change can't be rolled back with the code. Fix → change schemas separately with expand and contract, before the code rollout.

7When to use it (and when not)

Use it when…

  • Services with many users, several regions or tenants.
  • Teams that release often and want to stop watching dashboards.
  • Changes whose failures depend on scale or region.

Skip it when…

  • A small internal tool with one instance.
  • No reliable per-version metrics yet: build those first.
  • Urgent security fixes, where speed beats staging (still watch closely).

8Self-check quiz

How is progressive delivery different from a single canary?

The whole rollout is staged in rings, each with a bake time and an automated gate, instead of canary then everywhere.

What should a gate compare?

The new version with the stable one on errors, latency and a business metric, plus the SLO burn rate.

What happens when a gate fails?

Traffic shifts back to the old version automatically and the rollout stops.

Why roll out region by region?

Some problems depend on a region's data, providers or config; one region at a time limits the damage.

what would you do?A release passes the canary and region A, then breaks checkout in region C because of a missing config value only C needs. The rollout had moved to B, C and D together. What do you change?

Roll out one region at a time after the first, with a gate per region that includes checkout success, so C's failure stops the rollout with only C affected. Also check required config per region in the pipeline before deploying.

try it

In a local cluster, install Argo Rollouts and convert one Deployment to a Rollout with steps at 10%, 50% and 100% and a short pause between. Add an analysis step that queries an error rate (even a fake Prometheus metric), make the new version fail it, and watch the rollout abort and return to the stable version.
