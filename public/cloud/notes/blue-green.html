Blue–Green Deployment

TL;DR

Keep two identical environments. One (blue) serves users; deploy the new version to the other (green), test it with no user traffic, then switch the router in one step. Rollback is switching back, in seconds. The catch: both versions share data, so database changes must be backward compatible.

  • Family: deployment strategy
  • Popularised by: Dan North & Jez Humble; Martin Fowler (2010)
  • Switch with: load balancer, DNS, service mesh, ingress
  • Pairs with: build once, expand & contract (Vol. 3)

1The problem why do we even need this?

Updating servers in place means a window where some are down or half-updated, and if the new version is broken, rolling back is the same slow process in reverse.

  • Users see errors or a maintenance page during each deploy.
  • Deploys are scheduled for nights and weekends, so they're rare and big.
  • Rollback takes as long as the deploy, while things are on fire.

2Real-life analogy the theatre turntable

Some theatres have a turntable stage. While the audience watches the front, the crew builds the next scene on the back. When it's ready, the stage rotates, and the new scene is there instantly. If a prop is missing, they rotate back.

  • The front stage is blue (live); the back is green (next).
  • Rotating is the router switch.
  • Rotating back is rollback in seconds.

3How it solves it two environments, one switch

The switch is all-or-nothing: simple and instant, but every user moves at once. For gradual exposure, see canary releases (note 02).

  1. Two identical stacks

    Same infrastructure code for blue and green; only the version differs.

  2. Deploy to the idle one

    Install the new build on green while blue serves traffic.

  3. Test green privately

    Smoke tests and health checks via an internal URL.

  4. Switch

    Point the load balancer or ingress at green; drain blue's in-flight requests.

  5. Watch, then keep blue warm

    Monitor errors and latency; keep blue ready for a quick switch back.

  6. Handle data carefully

    Use expand-and-contract migrations so both versions work with the same schema.

4Gains vs losses nothing is free

What we gain

  • Zero-downtime deploys.
  • Instant rollback: switch back.
  • Test the real environment before users see it.
  • Simple model to explain.

What we lose

  • Double infrastructure during deploys.
  • All users switch at once: no gradual exposure.
  • Shared data needs compatible migrations.
  • Long-lived sessions and queues need draining.

6Common pitfalls the usual ways this goes wrong

  • Breaking schema changes

    Green migrates the database; blue starts failing. Fix → expand-and-contract migrations.

  • Tearing blue down immediately

    Rollback now means a full redeploy. Fix → keep blue warm until green has proven itself.

  • Drifting environments

    Blue and green were configured by hand and differ. Fix → build both from the same infrastructure code.

  • Forgetting background work

    Old workers keep consuming jobs with old logic. Fix → switch workers and queues deliberately too.

7When to use it (and when not)

Use it when…

  • Services where downtime is unacceptable.
  • Releases that need a fast, reliable rollback.
  • Teams moving away from maintenance windows.

Skip it when…

  • Huge stateful systems where doubling is impractical (use rolling or canary).
  • When you need gradual exposure (canary).

8Self-check quiz

How does rollback work in blue–green?

Switch the router back to the previous environment, which is still running.

What's the main data risk?

Both versions share the database, so schema changes must be backward compatible.

What's the cost trade-off?

You run two full environments during the switch.

How is blue–green different from canary?

Blue–green switches all traffic at once; canary shifts a small share first and widens gradually.
