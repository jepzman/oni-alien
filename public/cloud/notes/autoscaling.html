Autoscaling

TL;DR

Let the platform add instances when load rises and remove them when it falls, based on a signal that tracks real demand (requests per instance, queue depth, CPU), within min and max limits. Scale up fast and down slowly. You get capacity for spikes without paying for idle servers at night, as long as instances are stateless and start quickly.

  • Family: capacity
  • Kinds: horizontal, vertical, scheduled, event-driven, scale-to-zero
  • Tools: Kubernetes HPA, KEDA, cloud autoscaling groups, Cloud Run
  • Pairs with: health checks, immutable infrastructure, competing consumers (Vol. 1)

1The problem why do we even need this?

Fixed capacity is always wrong: too little at peak (timeouts, lost sales), too much off-peak (wasted money). Manual scaling is slow and happens after the outage starts.

  • The lunchtime spike overloads the fleet.
  • At night 95% of the capacity sits idle.
  • Someone has to remember to scale up before the big launch.

2Real-life analogy supermarket checkout lanes

A good supermarket opens more lanes when queues grow and closes them when it's quiet. The manager watches the queue length, not how tired the cashiers look, and knows a new lane takes a minute to open, so they open one a little early.

  • Lanes are instances.
  • Queue length is the scaling metric.
  • Opening early is headroom.

3How it solves it target tracking within limits

Pick a metric that leads load (requests, queue depth) rather than one that lags (memory). And make sure new instances are ready fast: autoscaling can't help if boot takes ten minutes.

  1. Make instances stateless

    Sessions and data outside the instance; any instance can serve any request.

  2. Pick the right signal

    Web: requests/instance or CPU; workers: queue depth or lag.

  3. Set min, max and target

    Min for redundancy (≥ 2–3), max for cost and downstream safety.

  4. Up fast, down slow

    Short scale-up window; longer scale-down stabilisation.

  5. Make boot fast

    Small images, readiness probes, pre-warmed caches.

  6. Schedule known peaks

    Scale ahead of launches and daily patterns.

Vocabulary for the exam

Horizontal scaling
More or fewer instances.
Vertical scaling
Bigger or smaller instances.
Target tracking
Adjust capacity to keep a metric near a target.
Cooldown / stabilisation
Waiting before scaling again, to avoid flapping.
Scale to zero
No instances when idle; start on demand.
Headroom
Spare capacity kept for sudden spikes.
hpa.yaml + keda.yamlKubernetes HPA and KEDA
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 0 }
    scaleDown: { stabilizationWindowSeconds: 300 }    # down slowly
---
# workers: scale on queue length with KEDA
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: invoice-worker }
spec:
  scaleTargetRef: { name: invoice-worker }
  minReplicaCount: 0
  maxReplicaCount: 50
  triggers: [{ type: aws-sqs-queue, metadata: { queueURL: "…", queueLength: "20" } }]

tools: Kubernetes HPA / VPA, KEDA, Karpenter and Cluster Autoscaler (nodes), AWS Auto Scaling groups and ECS service autoscaling, GCP managed instance groups, Cloud Run / Lambda (automatic, scale to zero).

4Gains vs losses nothing is free

What we gain

  • Capacity for spikes.
  • Lower cost off-peak.
  • No manual scaling under pressure.
  • Scale to zero for idle workloads.

What we lose

  • Cold starts and lag during sudden spikes.
  • Downstream overload: more instances, more DB connections.
  • Tuning metrics and windows.
  • Runaway cost without a max.

6Common pitfalls the usual ways this goes wrong

  • Scaling on a lagging metric

    Memory rises after the overload; scaling comes too late. Fix → scale on requests or queue depth.

  • No max

    A bug or attack scales you to 500 instances. Fix → set max and budget alerts.

  • Forgetting downstream limits

    30 pods × 20 connections overwhelm the database. Fix → connection pooling and limits (Vol. 3).

  • Slow boot

    New pods take 5 minutes; the spike is over. Fix → smaller images, startup tuning, headroom.

7When to use it (and when not)

Use it when…

  • Variable or spiky traffic.
  • Queue-based workers.
  • Stateless services.

Skip it when…

  • Steady, predictable load (right-size and reserve instead).
  • Stateful systems that can't add nodes quickly.

Related patterns

  • Health checks & probes
  • Immutable infrastructure
  • Cost visibility (FinOps)
  • Connection pooling (Vol. 3)

8Self-check quiz

Why scale up fast and down slowly?

To catch spikes quickly while avoiding flapping when load dips briefly.

What makes a good scaling metric?

One that tracks demand early, like requests per instance or queue depth.

Why set a maximum?

To cap cost and protect downstream systems from too many instances.

What must be true of instances?

They must be stateless and start quickly.

remember!!

Watch the queue, open lanes early, close them slowly.
