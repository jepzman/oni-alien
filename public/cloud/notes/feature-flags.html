Feature Flags

TL;DR

Separate deploying from releasing. Merge unfinished or risky code to main behind a flag that's off, deploy it any time, then turn it on for staff, a percentage, a country or a customer without a deploy. A kill switch turns it off in seconds. Flags are temporary: delete them once a feature is fully launched.

  • Family: progressive delivery
  • Kinds: release, experiment, ops (kill switch), permission
  • Tools: LaunchDarkly, Unleash, Flagsmith, OpenFeature
  • Pairs with: canary releases, trunk-based development

1The problem why do we even need this?

Without flags, “not ready yet” means a long-lived branch, and “launch” means a deploy at a precise moment. Both are risky and slow.

  • Feature branches drift for weeks and end in painful merges.
  • The launch time is set by marketing, so the deploy is too.
  • Turning a broken feature off means another deploy, under pressure.

2Real-life analogy the lights on switches

An electrician wires every light in the house weeks before the party, each on its own switch. On the night you just flick on the rooms you want, and if a bulb flickers you flick it off. Nobody rewires the house during the party.

  • Wiring is deploying the code.
  • Flicking switches is releasing.
  • Turning a flickering bulb off is the kill switch.

3How it solves it deploy dark, release by rule

Flags make deploys boring and releases a product decision, but each flag is technical debt with an expiry date.

  1. Wrap the change

    One check at the entry point: if (flags.isOn("new-checkout", user)).

  2. Default to off (safe)

    If the flag service is unreachable, fall back to the old behaviour.

  3. Roll out by rule

    Staff → beta customers → 10% → 100%, watching metrics.

  4. Keep a kill switch

    Ops flags for risky dependencies and expensive features.

  5. Set an expiry

    Each release flag gets an owner and a removal ticket.

  6. Delete it

    Remove the flag and the old code path once fully launched.

checkout.tsOpenFeature SDK
import { OpenFeature } from "@openfeature/server-sdk";
const flags = OpenFeature.getClient();

export async function checkoutPage(req: Request) {
  const useNew = await flags.getBooleanValue(
    "new-checkout",                    // owner: payments · remove by 2027-01-31
    false,                             // safe default if the flag service is down
    { targetingKey: req.user.id, country: req.user.country, plan: req.user.plan },
  );
  return useNew ? renderNewCheckout(req) : renderLegacyCheckout(req);
}
// rules live in the flag service: staff → NL 10% → all
// after 100% for two weeks: delete the flag and renderLegacyCheckout

4Gains vs losses nothing is free

What we gain

  • Deploy any time; release when ready.
  • Kill switch without a deploy.
  • Gradual rollouts and targeted betas.
  • Short-lived branches: merge daily.

What we lose

  • Flag debt and dead code.
  • More code paths to test.
  • A runtime dependency on the flag service.
  • Confusing when many flags interact.

6Common pitfalls the usual ways this goes wrong

  • Never deleting flags

    300 flags, half forgotten, some contradicting. Fix → owner + expiry per flag; delete after launch.

  • Unsafe defaults

    Flag service down → new, half-finished feature shown. Fix → default to the safe (old) path.

  • Flags inside flags

    Combinations nobody has tested. Fix → keep flags independent; test both paths of each.

  • Using flags for permissions forever

    Paid features live in a release-flag tool. Fix → use real entitlements for long-term access rules.

7When to use it (and when not)

Use it when…

  • Trunk-based development.
  • Launches timed by product or marketing.
  • Risky changes needing a kill switch.
  • Betas and experiments.

Skip it when…

  • Tiny, low-risk changes (just ship them).
  • Permanent configuration (use config, not flags).

8Self-check quiz

What does “separate deploy from release” mean?

Code can be in production but switched off; turning it on for users is a separate, runtime decision.

What should a flag default to if the service is down?

The safe, existing behaviour.

What's a kill switch?

An operational flag that disables a feature or dependency instantly without a deploy.

Why delete flags after launch?

Old flags leave dead code and untested combinations: flag debt.

remember!!

Wire early, switch on the night, and take the old switches off the wall.
