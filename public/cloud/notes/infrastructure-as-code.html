Infrastructure as Code

TL;DR

Describe networks, databases, queues, DNS and permissions in code files in git (Terraform, OpenTofu, Pulumi, CloudFormation), and change them only through pull requests that show a plan of exactly what will change. A pipeline applies it. Environments become reproducible, changes become reviewable, and git becomes the history of your infrastructure.

  • Family: infrastructure
  • Tools: Terraform / OpenTofu, Pulumi, CloudFormation, CDK, Bicep
  • Key idea: declarative desired state + plan
  • Pairs with: GitOps, immutable infrastructure

1The problem why do we even need this?

Infrastructure built by clicking in a console lives only in that account and in someone's memory. Environments drift apart, changes aren't reviewed, and disaster recovery is guesswork.

  • Staging and production differ in dozens of small settings.
  • “Who opened port 22 to the world?” No record.
  • Rebuilding after an account loss would take weeks.

2Real-life analogy the blueprint

Builders follow an architect's blueprint, so you can build identical houses again and again. Changes are drawn on the plan first, checked, then built. Nobody knocks down a wall without updating the drawing.

  • The blueprint is your IaC code.
  • Checking the drawing is reviewing the plan.
  • A wall knocked down without updating plans is drift.

3How it solves it plan, review, apply

Most IaC tools are declarative: you describe the end state, the tool works out the steps. The plan is the most important safety feature: read it before every apply.

  1. Start with what hurts

    Import or codify the most critical resources first (network, databases, IAM).

  2. Use modules

    Reusable building blocks (web-service, postgres) with environment variables.

  3. Remote state with locking

    S3 + DynamoDB, Terraform Cloud, or your tool's backend.

  4. Plan in every PR

    Post the plan as a comment; reviewers read it.

  5. Apply only from CI

    Short-lived credentials; no laptop applies to production.

  6. Detect drift

    Scheduled plans that alert when reality differs from code; lock down console write access.

4Gains vs losses nothing is free

What we gain

  • Reproducible environments.
  • Reviewed changes with a visible plan.
  • History in git: who changed what and why.
  • Faster recovery: rebuild from code.

What we lose

  • Learning curve and state management.
  • Plans can surprise (replacements, deletions).
  • Slower for one-off experiments.
  • Drift if people still click in consoles.

6Common pitfalls the usual ways this goes wrong

  • Applying from laptops

    Two people apply at once; state corrupts. Fix → apply only from CI with locking.

  • Not reading the plan

    A rename destroys and recreates the database. Fix → review plans; protect critical resources (prevent_destroy).

  • One giant state file

    Every plan takes 20 minutes and touches everything. Fix → split state by service and environment.

  • Secrets in code or state

    Passwords committed in .tf files. Fix → reference a secrets manager; encrypt state.

7When to use it (and when not)

Use it when…

  • Any cloud infrastructure that matters.
  • Multiple environments that should match.
  • Teams that want reviewed, auditable changes.

Skip it when…

  • Throwaway sandbox experiments (but codify what survives).
  • Fully managed platforms with nothing to configure.

8Self-check quiz

What does declarative mean in IaC?

You describe the desired end state; the tool works out how to reach it.

Why review the plan?

It shows exactly what will be created, changed or destroyed before anything happens.

What is drift?

Differences between real infrastructure and the code, usually from manual changes.

Why apply only from CI?

Locking, consistent credentials, audit trail, and no conflicting applies from laptops.

remember!!

Change the blueprint first, review it, then build.
