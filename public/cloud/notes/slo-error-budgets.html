SLOs & Error Budgets

TL;DR

Agree, in numbers, how reliable is reliable enough. Pick an SLI that reflects what users feel (share of fast, successful checkouts), set an SLO (99.9% over 28 days), and treat the remainder as an error budget to spend on change. Alert on burn rate, not on every blip. Budget left: ship. Budget spent: prioritise reliability.

  • Family: reliability engineering
  • Origin: Google SRE (2016)
  • Terms: SLI, SLO, SLA, error budget, burn rate
  • Pairs with: observability, canary releases, postmortems

1The problem why do we even need this?

Product wants speed; operations wants stability. Without a shared definition of “reliable enough”, every release is a negotiation, and teams either freeze or break things.

  • Aiming for 100% makes every change look dangerous.
  • Alerts fire on every CPU spike; real user pain goes unnoticed.
  • Reliability work never gets prioritised until there's an outage.

2Real-life analogy the monthly data allowance

A phone plan gives you 10 GB a month. You stream freely while there's plenty left, and slow down when you're near the limit. The allowance was agreed up front, so nobody argues about each video.

  • The allowance is the error budget.
  • Data used is bad events (failed or slow requests).
  • Your usage alert is a burn-rate alert.

3How it solves it measure what users feel, then budget

100% is the wrong target: users can't tell 99.99% from 100% through their own Wi-Fi, and chasing it stops all change. The budget makes the trade-off explicit.

  1. Pick user journeys

    Sign-in, search, checkout: what users actually care about.

  2. Define SLIs

    Good events ÷ valid events, measured as close to the user as possible.

  3. Set SLOs

    Realistic, based on history and user needs; a 28-day rolling window.

  4. Agree the policy

    What happens when the budget is spent (freeze risky launches, fix top causes).

  5. Alert on burn rate

    Multi-window alerts: page on fast burn, ticket on slow burn.

  6. Review regularly

    Adjust SLOs as users and systems change.

Vocabulary for the exam

SLI
Service level indicator: a measure of good service.
SLO
Service level objective: the target for an SLI.
SLA
A contract with consequences, usually looser than the SLO.
Error budget
Allowed unreliability: 100% − SLO.
Burn rate
How fast the budget is being used.
Toil
Repetitive manual operational work.
slo.yamlOpenSLO-style + Prometheus burn alert
apiVersion: openslo/v1
kind: SLO
metadata: { name: checkout-availability }
spec:
  service: checkout
  indicator:
    ratioMetric:
      good:  { metricSource: { spec: { query: 'sum(rate(http_requests_total{route="/checkout",code!~"5..",le_400ms="true"}[5m]))' } } }
      total: { metricSource: { spec: { query: 'sum(rate(http_requests_total{route="/checkout"}[5m]))' } } }
  timeWindow: [{ duration: 28d, isRolling: true }]
  objectives: [{ target: 0.999 }]

# page: burning 14.4× budget over 1h AND 5m (≈2% of the 28-day budget in an hour)
# ticket: burning 1× over 3 days

4Gains vs losses nothing is free

What we gain

  • A shared, numeric definition of reliable enough.
  • Fewer, better alerts tied to user pain.
  • Explicit trade-off between speed and stability.
  • Reliability work gets prioritised by data.

What we lose

  • Hard to choose good SLIs at first.
  • Needs organisational buy-in for the budget policy.
  • Measurement work to get accurate SLIs.
  • Can be gamed if SLIs don't reflect users.

6Common pitfalls the usual ways this goes wrong

  • 100% targets

    Every change becomes too risky. Fix → realistic SLOs below 100%.

  • SLIs users don't feel

    CPU usage as an SLI. Fix → measure success and latency of user journeys.

  • No budget policy

    Budget is spent and nothing changes. Fix → agree consequences up front.

  • Too many SLOs

    Forty SLOs nobody reads. Fix → a few per critical journey.

7When to use it (and when not)

Use it when…

  • Services with real users and frequent changes.
  • Teams arguing about speed vs stability.
  • Replacing noisy alerting.

Skip it when…

  • Internal prototypes with no users yet.
  • Batch jobs (use freshness and completion SLOs instead of availability).

8Self-check quiz

What's the difference between an SLO and an SLA?

An SLO is an internal target; an SLA is a contract with consequences, usually set looser than the SLO.

How do you calculate the error budget?

100% minus the SLO, e.g. 0.1% of requests for a 99.9% SLO.

Why alert on burn rate?

It pages when user-facing reliability is actually at risk, not on every blip.

Why not aim for 100%?

It's unreachable and stops all change; users can't tell the difference beyond a point.

remember!!

Agree the allowance, watch the burn, and slow down near the limit.
