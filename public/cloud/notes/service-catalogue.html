Service Catalogue

TL;DR

With dozens or hundreds of services, the questions that matter at 2 a.m. are simple and hard to answer: what does it do, who owns it, how do I run it, what depends on it? A service catalogue answers them in one place. Each service keeps a small metadata file in its own repository (owner, on-call, tier, links, dependencies); a portal collects them, draws the graph, and checks that every service meets the basics.

  • Family: running it
  • Common tool: Backstage (CNCF), or Port, Cortex, OpsLevel
  • Lives in: a catalog-info.yaml next to each service's code
  • Pairs with: golden paths, incident response, cost visibility

1The problem why do we even need this?

At 2 a.m. an alert fires for ledger-sync. Nobody on call knows what it does, who owns it, where its dashboards are, or what breaks if it stays down. Fifty minutes and four people later, someone finds the team that wrote it two years ago.

  • Knowledge of who owns what lives in people's heads and old chat threads.
  • Wikis listing services go out of date within months.
  • Nobody can answer “which services handle personal data?” or “who still runs the old Java version?”

2Real-life analogy the lobby directory

A building's directory board lists every office: company, floor, contact and emergency number. When a pipe bursts on floor 6, the caretaker reads the board and calls the right person, instead of knocking on every door. Tenants update their own line when they move.

3How it solves it a file per service, one portal for all

Each team describes its services in a small YAML file next to the code, so it's reviewed and changed with the code. The catalogue collects every file, links each service to its team, dashboards, runbook and docs, and draws who depends on whom. Scorecards check the basics automatically (an owner, an on-call, a runbook, alerts, a supported runtime) and show what's missing.

  1. Start with ownership

    One required field first: every service has an owning team. Import the list from your repos and deploy tooling.

  2. Put the file in the repo

    catalog-info.yaml next to the code, so changes are reviewed and it moves with the service.

  3. Add the 2 a.m. links

    On-call rotation, dashboards, runbook, logs, docs, tier.

  4. Record dependencies

    APIs it provides and consumes, data stores, queues; draw the graph.

  5. Add scorecards slowly

    A few checks that matter (owner, runbook, alerts), visible per team; avoid a wall of red on day one.

Vocabulary for the exam

Service catalogue
A searchable list of every service with its metadata.
Owner
The team accountable for a service, day and night.
Tier
How critical a service is, which sets its expectations.
Scorecard
Automated checks of a service against agreed standards.
Dependency graph
Which services call or rely on which.
Developer portal
A site combining the catalogue, docs and self-service templates.
catalog-info.yamlBackstage format
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: ledger-sync
  description: Copies settled payments into the finance ledger every 5 minutes.
  annotations:
    pagerduty.com/service-id: P4LEDGR
    grafana/dashboard-selector: "service=ledger-sync"
    backstage.io/techdocs-ref: dir:.
  links:
    - { url: https://runbooks.internal/ledger-sync, title: Runbook }
  tags: [payments, personal-data]
spec:
  type: service
  lifecycle: production
  owner: team-ledger
  system: payments
  tier: 1                                  # customer-facing: money is late without it
  dependsOn: [component:payments-api, resource:ledger-db]
  providesApis: [ledger-events]

tools: Backstage (CNCF) with its catalogue, TechDocs and scorecard plugins, Port, Cortex, OpsLevel, Compass (Atlassian), GitHub CODEOWNERS and custom properties as a starting point.

4Gains vs losses nothing is free

What we gain

  • Faster incidents: the owner and runbook are one search away.
  • Answers to fleet questions: who handles personal data, who runs an old version.
  • Clear ownership: no orphan services.
  • A home for golden paths: new services start from templates that fill in the entry.

What we lose

  • Upkeep: entries rot if nothing checks them.
  • A portal to run (Backstage is real work) or to pay for.
  • Adoption: teams must see value, not paperwork.
  • Dependency data written by hand drifts; better generated from traces.

6Common pitfalls the usual ways this goes wrong

  • A spreadsheet catalogue

    A central list that one person updates, out of date within weeks. Fix → keep each entry in its service's repo and check it in CI.

  • Twenty required fields on day one

    Teams see paperwork and fill in junk. Fix → start with owner and on-call; add fields when someone needs them.

  • Owners that are people

    The owner left the company a year ago. Fix → own by team, linked to the org chart and the on-call tool.

  • Hand-written dependencies

    The graph says A calls B; traces say A calls B, C and D. Fix → generate dependencies from tracing or the mesh where you can.

7When to use it (and when not)

Use it when…

  • More services than one person can keep in their head (often around 20+).
  • Several teams sharing on-call or platforms.
  • Audits asking which systems hold which data.

Skip it when…

  • A handful of services owned by one team: a README is enough.
  • No one will maintain it or check it.
  • You need a CMDB for hardware assets: a different job.

8Self-check quiz

What four questions should a catalogue answer at 2 a.m.?

What does it do, who owns it, how do I run or fix it (runbook, dashboards), and what depends on it.

Why keep the entry in the service's own repository?

It's reviewed and updated with the code by the owning team, so it doesn't rot in a central list.

What is a scorecard?

Automated checks of each service against agreed basics, such as having an owner, a runbook and alerts.

Why should owners be teams, not people?

People move on; a team with an on-call rotation stays accountable.

what would you do?An auditor asks which services store customer addresses, and who owns each. It takes three weeks of emails to answer, and two services turn out to have no owner. What do you set up so the next answer takes minutes?

A catalogue with an entry per service in its repo: owning team, on-call, and data tags such as personal-data, with a CI check that every service has an owner. Then the audit is a search, and orphan services show up on a scorecard instead of in an audit.

try it

Write a catalog-info.yaml for three services you know, with owner, on-call, links and dependencies. Run Backstage locally (npx @backstage/create-app) and register them, or simply list them in a table. Then try answering “who do I call if this one is down?” and “what breaks if that one stops?” in under a minute.

remember!!

Every service has a name, an owner and a runbook, and they live next to the code.
