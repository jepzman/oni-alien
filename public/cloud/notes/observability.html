Logs, Metrics & Traces

TL;DR

Emit three kinds of signals from every service: metrics (cheap numbers over time: rate, errors, duration) to notice problems, traces (one request's journey across services) to find where, and structured logs (events with context) to see why. Link them with a shared trace id, collect them with OpenTelemetry, and you can answer questions you didn't plan for.

  • Family: operations
  • Standard: OpenTelemetry (CNCF)
  • Starter metrics: RED: rate, errors, duration · USE for resources
  • Pairs with: SLOs, audit logging (Vol. 5), canary releases

1The problem why do we even need this?

With many services, “it's slow for some users” is a needle in a haystack: text logs on many machines, dashboards that show averages, and no way to follow one request end to end.

  • Averages hide the 1% of users with 10-second checkouts.
  • Log lines can't be joined across services.
  • Every incident starts with “add more logging and redeploy”.

2Real-life analogy the parcel tracking number

A parcel has one tracking number. Every depot scans it with a timestamp, so you can see its whole journey and exactly where it got stuck. The company also counts parcels per hour on a dashboard, and each depot keeps a detailed diary.

  • The tracking number is the trace id; each scan is a span.
  • Parcels per hour is a metric.
  • The depot diary is logs, mentioning the tracking number.

3How it solves it three signals, one id

Observability isn't more dashboards. It's being able to ask a new question (“which tenant on which version is slow?”) without shipping new code.

  1. Instrument with OpenTelemetry

    Auto-instrumentation for HTTP, databases and queues; vendor-neutral.

  2. Propagate context

    Pass the trace context (traceparent) across HTTP and message headers.

  3. RED metrics per service

    Request rate, error rate, duration histograms (p50/p95/p99), by route.

  4. Structured logs

    JSON with trace_id, user/tenant id, version; no secrets.

  5. Add business attributes

    tenant, plan, feature flag state on spans: that's what answers “for some users”.

  6. Sample wisely

    Keep all errors and slow traces; sample the boring ones.

Vocabulary for the exam

Metric
A number measured over time.
Trace
The full journey of one request across services.
Span
One step in a trace, with timing.
Structured log
A log event as key–value data (JSON).
Cardinality
How many distinct values a label has.
Percentile (p95)
95% of requests are faster than this.
checkout.tsOpenTelemetry JS
import { trace, metrics } from "@opentelemetry/api";
const tracer = trace.getTracer("checkout");
const duration = metrics.getMeter("checkout").createHistogram("checkout.duration", { unit: "ms" });

export async function checkout(req: Req) {
  return tracer.startActiveSpan("checkout", async (span) => {
    span.setAttributes({ "tenant.id": req.tenantId, "cart.items": req.items.length,
                         "flag.new_checkout": req.flags.newCheckout });
    const t0 = performance.now();
    try {
      const order = await placeOrder(req);              // child spans: db, payments
      logger.info({ msg: "order placed", orderId: order.id, traceId: span.spanContext().traceId });
      return order;
    } catch (e) {
      span.recordException(e as Error); span.setStatus({ code: 2 });
      throw e;
    } finally {
      duration.record(performance.now() - t0, { route: "/checkout" });
      span.end();
    }
  });
}

4Gains vs losses nothing is free

What we gain

  • Find where and why quickly.
  • Answer new questions without redeploying.
  • See tail latency, not just averages.
  • Vendor-neutral instrumentation with OpenTelemetry.

What we lose

  • Data volume and cost.
  • High-cardinality traps in metrics.
  • Instrumentation effort and consistency.
  • Privacy risk if personal data leaks into telemetry.

6Common pitfalls the usual ways this goes wrong

  • Averages only

    Mean latency 120 ms; p99 is 9 s. Fix → histograms and percentiles.

  • User ids as metric labels

    Millions of time series; the bill explodes. Fix → high-cardinality data on spans and logs, not metric labels.

  • Broken context propagation

    Traces stop at the queue. Fix → propagate traceparent through messages too.

  • Logging personal data

    Emails and tokens in logs. Fix → redact; log ids, not secrets.

7When to use it (and when not)

Use it when…

  • Any production service, especially distributed ones.
  • Canary analysis and SLO alerting.
  • Debugging “only some users” problems.

Skip it when…

  • Don't skip; for a tiny app, start with RED metrics and structured logs.

8Self-check quiz

What does each signal answer?

Metrics: is something wrong? Traces: where? Logs: why?

What links the three?

A shared trace id, propagated across services.

Why use percentiles instead of averages?

Averages hide slow outliers that real users experience.

Where should high-cardinality data (user id) go?

On spans and logs, not on metric labels.
