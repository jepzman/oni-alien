Backups & Disaster Recovery

TL;DR

Decide how much data you can afford to lose (RPO) and how fast you must be back (RTO), then design for it: 3-2-1 backups with at least one immutable copy in a separate account and region, infrastructure as code to rebuild the platform, and regular restore drills that prove you can hit the targets. An untested backup is a hope, not a plan.

  • Family: resilience
  • Targets: RPO (data loss), RTO (downtime)
  • Strategies: backup/restore, pilot light, warm standby, active–active
  • Pairs with: IaC, replication (Vol. 1), postmortems

1The problem why do we even need this?

Most teams have backups. Far fewer have backups that survive the disaster and that they have actually restored. Ransomware, a deleted account or a bad migration reveals the difference.

  • Backups in the same account are deleted along with production.
  • Nobody knows how long a full restore takes.
  • The database is restored, but the infrastructure around it isn't.

2Real-life analogy the spare key and the fire drill

Sensible families keep a spare key with a trusted neighbour, not under the doormat, and practise a fire drill so everyone knows the way out and the meeting point. A plan that's never been practised fails at the worst moment.

  • The spare key next door is an off-site, separate-account backup.
  • The drill is a restore test.
  • The meeting point is your runbook.

3How it solves it targets, copies, rebuild, rehearse

Choose a strategy per system based on RPO/RTO and cost: backup & restore (hours), pilot light or warm standby (minutes), active–active (seconds, expensive).

  1. Set RPO and RTO per system

    With the business: what does an hour of downtime or data loss cost?

  2. Follow 3-2-1

    Three copies, two media, one off-site; plus immutability (object lock).

  3. Separate the blast radius

    Backups in a different account with separate credentials and region.

  4. Back up the platform too

    Infrastructure as code, secrets, DNS and configuration.

  5. Drill restores

    Quarterly: restore to a clean environment, time it, fix what's slow.

  6. Write the runbook

    Who decides, who does what, in which order, how to communicate.

Vocabulary for the exam

RPO
Recovery point objective: maximum acceptable data loss.
RTO
Recovery time objective: maximum acceptable downtime.
3-2-1 rule
3 copies, 2 media, 1 off-site.
Immutable backup
Can't be modified or deleted for a set period.
Pilot light / warm standby
Minimal or scaled-down copy of production ready elsewhere.
Point-in-time recovery
Restoring a database to a specific moment.

resource "aws_backup_plan" "prod" {
  name = "prod-daily"
  rule {
    rule_name         = "daily-35d"
    target_vault_name = aws_backup_vault.local.name
    schedule          = "cron(0 3 * * ? *)"
    lifecycle { delete_after = 35 }
    copy_action {                                   # copy to the isolated DR account/region
      destination_vault_arn = "arn:aws:backup:eu-central-1:999999999999:backup-vault:dr"
      lifecycle { delete_after = 90 }
    }
  }
}

# in the DR account: vault lock = nobody (not even admins) can delete early
resource "aws_backup_vault_lock_configuration" "dr" {
  backup_vault_name  = "dr"
  min_retention_days = 30
}
# + continuous PITR on the database (RPO ≈ 5 min) + quarterly restore drill

4Gains vs losses nothing is free

What we gain

  • Survive the worst day: deletion, ransomware, region loss.
  • Known recovery times, proven by drills.
  • Clear expectations with the business.
  • Calmer incidents: there's a plan.

What we lose

  • Storage and standby costs.
  • Drills take time and planning.
  • Complexity for warm standby and active–active.
  • Immutability makes deleting data on request harder.

6Common pitfalls the usual ways this goes wrong

  • Backups in the same account

    Ransomware or a deleted account takes them too. Fix → separate account, credentials and region; vault lock.

  • Never testing restores

    The backup is corrupt or takes days. Fix → quarterly restore drills with timing.

  • Only backing up data

    Data restored, but no infrastructure to run it. Fix → IaC for the platform; back up config and secrets.

  • No owner for the decision

    During the disaster nobody knows who calls failover. Fix → runbook with roles and decision points.

7When to use it (and when not)

Use it when…

  • Every production data store.
  • Systems with business or legal recovery requirements.
  • Anything ransomware could reach.

Skip it when…

  • Truly disposable data (caches, rebuildable indexes): document that instead.

8Self-check quiz

What's the difference between RPO and RTO?

RPO is how much data you can lose; RTO is how long you can be down.

What is the 3-2-1 rule?

Three copies of data, on two kinds of storage, with one off-site.

Why keep backups in a separate account?

So an attacker or mistake in production can't delete them too.

Why run restore drills?

To prove backups work and to measure real recovery time.
