Modular Monolith First

TL;DR

Start as one deployable application, but split it inside into business modules with hard rules: each module owns its data, others reach it only through a small public API, and a CI check fails the build when someone breaks a boundary. You get most of the structure of microservices without the network, the eight pipelines and the eight on-call rotas. When one module really needs to be separate, it's ready to lift out.

  • Family: first shapes
  • Origin: Simon Brown, “modular monoliths” (2015); Martin Fowler, “MonolithFirst” (2015)
  • Lives in: one repo and one deploy, folders per module
  • Pairs with: bounded contexts, fitness functions, strangler fig

1The situation Larder, two bad options

Larder Core is one Django app where every part reads every table. Last month a change to pricing broke the picking export. Ben's answer is to split it into eight microservices. But Larder has 14 engineers: under two per service, each needing its own pipeline, monitoring and on-call. And the event storming was three weeks ago: nobody is sure yet where the boundaries are.

  • A tangled monolith makes every change risky.
  • Microservices fix the tangle but add a network, distributed data and heavy operations.
  • Cutting services along wrong boundaries is the most expensive mistake to undo.

2Real-life analogy the bento box

A bento box is carried as one thing, but rice, fish, salad and fruit each have their own compartment and nothing leaks between them. If the fruit one day needs to stay cold, you lift that compartment out into its own container. Compare a pot of stew, where everything has mixed, or eight separate takeaway boxes, which are a lot to carry for one lunch.

3How it solves it one deploy, hard walls inside

The value is in the rules, not the folders. Without enforcement, a modular monolith decays back into mud within months. With it, the boundaries can be moved cheaply while you learn: moving code between folders is a refactor; moving it between services is a migration.

  1. Draw modules from the domain

    Use bounded contexts from the event storming, not technical layers.

  2. Give each module its data

    Its own schema or table prefix. No other module reads or writes it.

  3. Expose a small public API

    One interface per module (functions or events). Everything else is internal.

  4. Enforce it in CI

    An import or architecture test fails the build on a forbidden dependency.

  5. Communicate by events where possible

    In-process events today become messages tomorrow, if a module moves out.

  6. Extract only with a reason

    Different scaling, availability, release pace or team: write an ADR for each extraction.

Vocabulary for the exam

Modular monolith
One deployable app made of strictly separated business modules.
Module
A business area with its own code, data and public API.
Public API (of a module)
The only way other modules may use it.
Big ball of mud
A system with no clear structure; everything depends on everything.
Extraction
Moving a module out into its own service.
Distributed monolith
Microservices that must all be deployed together: the worst of both.

Rules (ADR 0002), checked by CI (see .importlinter):
 1. A module's tables are its own. Table names start with the module name.
 2. Other modules import only <module>.api and <module>.events.
 3. No module imports another's _internal, models or tables.

Dispatch is a separate service (repo: dispatch/). Ordering publishes
OrderReadyForDispatch; Dispatch publishes CourierAssigned and OrderDelivered.

tools: import-linter (Python), ArchUnit (Java), dependency-cruiser (JS/TS), Spring Modulith, Packwerk (Ruby), .NET NetArchTest. Each turns the module rules into a failing test.

4Gains vs losses nothing is free

What we gain

  • Simple to run: one deploy, one database, one on-call.
  • Clear ownership: each module has an owner and its own data.
  • Cheap to fix boundaries: moving code between modules is a refactor.
  • Ready to extract: a well-kept module can become a service later.
  • Fast local calls: no network between modules.

What we lose

  • One deploy for all: a bad change in one module ships with the rest.
  • Scaling together: you can't scale one module alone (until you extract it).
  • Discipline needed: without CI rules, it decays into mud.
  • One tech stack: every module uses the same language and runtime.

6Common pitfalls the usual ways this goes wrong

  • Folders without rules

    Modules exist on paper; imports cross everywhere. Fix → enforce boundaries with a failing CI check from day one.

  • Shared tables

    Two modules write the same orders table. Fix → one owner per table; others go through the owner's API or events.

  • Technical modules

    Modules named controllers, services, repositories. Fix → split by business area (bounded contexts), not by layer.

  • Extracting for fashion

    A module becomes a service because services are “better”. Fix → extract only for a written reason: scaling, availability, team, release pace.

7When to use it (and when not)

Use it when…

  • New systems or rebuilds with teams under about 30 engineers.
  • When the domain boundaries aren't settled yet.
  • Untangling a ball-of-mud monolith step by step.
  • When operations capacity is small.

Skip it when…

  • Parts with very different scaling or availability needs: extract those.
  • Large organisations where many teams need fully independent releases.
  • When parts must use different languages or runtimes.

8Self-check quiz

What are the three rules of a modular monolith?

Each module owns its data; others use only its public API; the rules are enforced by an automated check.

Why is it cheaper to fix boundaries in a modular monolith than between services?

Moving code between modules is a refactor in one repo; moving it between services is a data and network migration.

What's a distributed monolith?

Services that must be deployed together because they're tightly coupled: all the costs of both styles.

Why did Larder extract Dispatch?

It's real-time (courier locations every 5 s) and scales differently from the rest.

try it

Pick two areas in your codebase that should be separate (for example, billing and notifications). Count how many places one reaches into the other's tables or internals. Write the one rule that would stop it, and find the tool that could check it in CI.

remember!!

One box, hard walls. Lift a compartment out only when you have a reason.
