System Context Diagram

TL;DR

Draw your system as one box in the middle. Around it, draw the people who use it and the external systems it talks to, and label every line with what crosses it. Nothing inside the box, nothing about technology. It takes an hour, fits on one slide, and settles the most expensive early question: where does our system end, and what do we depend on?

1The situation Larder, scoping Rotterdam

Ana asks three people to estimate the Rotterdam work. Ben says seven months, Dee four, Joost five. It turns out they're estimating three different systems: Ben's includes changing StockPilot, the warehouse system Larder only rents; Dee's leaves out the support tool; Joost's includes the couriers' phones. An hour of the meeting goes on “is that in scope?”

  • Everyone has a picture of “the system” in their head, and the pictures don't match.
  • External dependencies (vendors, providers) are forgotten until they break or block.
  • Estimates, contracts and security reviews all need a clear boundary.

2Real-life analogy the site plan

Before an architect designs the rooms, they draw a site plan: the house as one block, the plot boundary, the road access, and the water, power and sewer connections. The neighbours appear as blocks too; nobody draws their kitchens. It answers one question: what's ours, and what crosses the line?

Translating it to the job
In real lifeOn the project
The house as one blockYour system as one box, no internals
The plot boundaryThe scope: what you build, run and are responsible for
Water, power, sewer connectionsExternal systems you depend on: payments, StockPilot, SMS
The road and the visitorsThe people who use the system: customers, pickers, couriers
Not drawing the neighbours' kitchensNot modelling other systems' insides

3How it solves it one box, everything around it, every line labelled

The trick is what you leave out: no databases, no services, no technologies. Only the people, the outside systems and what flows between them. That's what makes it readable by Femke, Lena and the vendor alike.

  1. Draw one box for your system

    Name it the way the business does: “Larder platform”, not “k8s cluster”.

  2. Add the people

    Every role that uses it: customers, pickers, couriers, support agents, store managers.

  3. Add the external systems

    Everything it talks to that you don't own: providers, SaaS tools, partner APIs, other teams.

  4. Label every line

    With what crosses it, in plain words: “charges, refunds”, “stock levels every 5 min”.

  5. Walk it with stakeholders

    Ask each one: who's missing? What else do we send or receive?

  6. Keep it as code

    Write it in a diagram-as-code tool and keep it in the repo, so it gets updated.

Vocabulary for the exam

System context
The system as a black box among its users and neighbours.
System boundary
The line between what you own and what you depend on.
Actor / person
A role that uses the system.
External system
A system you integrate with but don't build or run.
Relationship
A labelled line: what flows, and which way.
Diagram as code
A diagram described in text, versioned with the code.
docs/architecture/context.dslStructurizr DSL, C4 level 1
workspace "Larder" {
  model {
    customer = person "Customer"      "Orders groceries in the app or web shop"
    picker   = person "Picker"        "Picks and packs orders in a dark store"
    courier  = person "Courier"       "Delivers orders by e-bike"
    agent    = person "Support agent" "Answers questions, issues refunds"

    larder   = softwareSystem "Larder platform" "Shop, orders, picking, dispatch"

    psp        = softwareSystem "Payment provider" "Cards, iDEAL, Bancontact"
    stockpilot = softwareSystem "StockPilot"       "Warehouse stock (SaaS)"
    helpdesk   = softwareSystem "Helpdesk tool"    "Support tickets (SaaS)"
    messaging  = softwareSystem "SMS & email"      "Order updates"

    customer -> larder     "Orders, tracks delivery"
    picker   -> larder     "Picks, packs, reports out-of-stock"
    courier  -> larder     "Collects, delivers, shares location"
    agent    -> larder     "Looks up orders, refunds"
    larder   -> psp        "Charges, refunds"
    larder   -> stockpilot "Reads stock levels, every 5 min"
    larder   -> helpdesk   "Creates tickets"
    larder   -> messaging  "Sends order updates"
  }
  views { systemContext larder { include * ; autolayout lr } }
}

tools: Structurizr (DSL above), PlantUML with the C4 library, Mermaid's C4 diagrams, or draw.io / Excalidraw for a first sketch. A whiteboard photo is fine in week one; move it to code once it settles.

4Gains vs losses nothing is free

What we gain

  • One agreed scope: estimates and contracts talk about the same thing.
  • Dependencies are visible: every vendor and provider is on the page.
  • Readable by anyone: no technology, so executives and lawyers can review it.
  • A starting point for security reviews, data flows and integration plans.
  • Cheap: an hour to draw, minutes to update.

What we lose

  • Too high-level for builders: they need container and component views too.
  • Boundary arguments surface early, and can be uncomfortable.
  • Goes stale unless it's kept as code and reviewed.
  • Hides the hard parts: one line can hide a very messy integration.

6Common pitfalls the usual ways this goes wrong

  • Drawing the insides

    The context diagram shows services, queues and databases. Fix → one box only; inside detail belongs in the container view.

  • Unlabelled lines

    Arrows connect boxes but say nothing about what flows. Fix → label every line with what crosses it, in plain words.

  • Forgetting the humans

    Only systems are drawn; pickers and support agents are missing. Fix → add every role that uses it, especially internal staff.

  • A picture in a slide deck

    Drawn once in a deck, never updated, wrong by month three. Fix → keep it as diagram-as-code in the repo and review it with changes.

7When to use it (and when not)

Use it when…

  • The start of every new system or major change.
  • When estimates or scope discussions don't match.
  • Before a security review, a data protection review or a vendor contract.
  • Onboarding: the first diagram a new joiner should see.

Skip it when…

  • Inside a single component where the boundary is obvious.
  • As the only diagram for builders: add container and component views.
  • When an up-to-date one exists: update it instead.

8Self-check quiz

What goes inside the system box on a context diagram?

Nothing: the system is one black box. Internals belong in other views.

What are the two kinds of things around the box?

People (roles that use it) and external systems it talks to.

Why label every line?

So readers know what flows and which way: the label is where most misunderstandings surface.

Why keep it as code?

It's versioned and reviewed with the code, so it stays current.

try it

Draw your system's context diagram from memory in 15 minutes, with every line labelled. Then show it to someone in operations or support and ask “who or what is missing?” Count how many boxes they add.

remember!!

Draw the plot line before the rooms. One box for you, and label everything that crosses it.
