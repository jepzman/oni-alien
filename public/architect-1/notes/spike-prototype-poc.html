Spike vs Prototype vs PoC

TL;DR

When the next decision depends on something you don't know, run a small, timeboxed experiment, and pick the right kind. A spike answers a technical question (“can X do Y?”) in a few days. A prototype tests whether an idea is right with real users. A proof of concept proves something works for real against agreed success criteria. Write the question, the timebox and the success criteria before you start, and decide up front that the code will be thrown away.

1The situation Larder, two old experiments

Larder has been burned by experiments twice. In 2024 someone wrote a quick prototype cron job to assign couriers; it's still running in production, assigning every courier every 30 seconds. Last spring a “quick look” at search engines had no question and no timebox; it ran for three weeks and ended without a decision. Now Ana has three real unknowns, and she wants each one answered in days, not weeks.

  • Using the wrong kind of experiment answers the wrong question.
  • Experiments without a timebox drift; experiments without criteria never “finish”.
  • Prototype code that works “well enough” quietly becomes production.

2Real-life analogy the wedding caterer

A caterer preparing a wedding tastes a spoon of a new spice (does it work?), shows the couple a sample plate (is this what you want?), and cooks one full table in the real kitchen at full speed (can we do this for 200?). Each answers a different question, none of them is the banquet, and nobody serves the tasting spoon to the guests.

3How it solves it pick by the question, timebox first

Start from the question, not the technology. If it's “can it?”, spike. If it's “should we?” or “will they like it?”, prototype. If it's “will it work here, at our scale, with our data?”, run a proof of concept with written success criteria. Every experiment ends in a decision, usually an ADR.

  1. Write the question

    One sentence that the experiment will answer with yes, no or a number.

  2. Pick the kind

    Technical question → spike. Is it right? → prototype. Works for real? → proof of concept.

  3. Set the timebox

    Days for a spike, up to two weeks for a prototype, up to four for a PoC. Stop when it's up.

  4. Agree the success criteria

    “≥ 50 req/s per store”, “4 of 5 pickers finish without help”, “p95 < 2 s for 300 couriers”.

  5. Run it, cheaply

    Hard-code, skip tests, use sandboxes. It's a question, not a product.

  6. Decide and throw away

    Write the result and the decision (an ADR); delete or archive the code.

Vocabulary for the exam

Spike
A short, timeboxed investigation to answer a technical question.
Prototype
A rough version of an idea, built to get feedback.
Proof of concept (PoC)
An experiment proving an approach works for real, against criteria.
MVP
Minimum viable product: the smallest real product for real users. Not an experiment.
Timebox
A fixed amount of time; when it's up, you stop and decide.
Success criteria
Measurable conditions agreed before the experiment starts.

# Experiment: can StockPilot's API serve six cities?             SPIKE

Question      Can we read and update stock for 12 stores (6 cities × 2) through
              StockPilot's API fast enough to stay within 1 minute of reality?
Why now       Assumption A-1; the Rotterdam plan depends on it.
Owner         Ben (+ Cho)           Timebox: 2 days, 19–20 Nov 2025
Success       ≥ 50 req/s sustained per account, with no throttling; p95 < 300 ms
Approach      Script against the StockPilot sandbox; ask their support about limits.
              Throwaway code in spikes/stockpilot/ (not merged to main).

Result        ✗ Hard limit 10 req/s per account (HTTP 429 above it), confirmed by
              StockPilot support. Bulk endpoint: 500 items per call, 1 call/s.
              p95 at 10 req/s: 180 ms.
Decision      Cache stock per store in our Stock module; sync from StockPilot by
              bulk calls and its webhooks. → ADR 0005 (proposed 2025-11-24)
Code          Deleted. Notes and numbers kept here.

tools: whatever is quickest: scripts, notebooks, vendor sandboxes, Figma or paper prototypes, a load-test tool for PoCs. Keep experiment cards in the repo next to the ADRs they lead to.

4Gains vs losses nothing is free

What we gain

  • Decisions on evidence, not opinion or vendor slides.
  • Bad news early: StockPilot's limit found in November, not April.
  • Cheap: days of effort against months of building on a guess.
  • Right question, right method: users test ideas, load tests test scale.
  • No accidental production code when throwaway is agreed up front.

What we lose

  • Time away from delivery, which can feel slow.
  • Partial answers: a sandbox isn't production.
  • Throwing away working code feels wasteful.
  • Can become procrastination: one more spike instead of deciding.

6Common pitfalls the usual ways this goes wrong

  • No timebox

    The “quick look” runs for three weeks. Fix → set the timebox first; when it's up, decide with what you have.

  • Prototype goes to production

    The demo worked, so it shipped. Fix → agree up front it will be thrown away; rebuild properly.

  • Criteria after the fact

    The PoC “succeeded” because the criteria were written to fit. Fix → write success criteria before starting, with the sponsor.

  • Wrong kind

    A load test to find out if pickers like the flow. Fix → pick by the question: can it, should we, will it work here?

7When to use it (and when not)

Use it when…

  • Any assumption the plan depends on.
  • Choosing between options when the deciding fact is unknown.
  • New technologies, vendors or user flows.
  • Before committing a date or budget that depends on an unknown.

Skip it when…

  • When the answer is cheap to look up (docs, a vendor call).
  • Decisions that are easy to reverse: just try it in the product.
  • When you already know and are seeking comfort: decide.

8Self-check quiz

Which experiment answers “can StockPilot's API handle our load?”

A spike: a short technical investigation.

How is a prototype different from an MVP?

A prototype tests an idea and is thrown away; an MVP is a real product for real users.

What must be written before a proof of concept starts?

The question, the timebox and measurable success criteria agreed with the sponsor.

What happens to experiment code?

It's thrown away or archived; the result and the decision are kept.

try it

Pick the biggest unknown in your current plan. Write an experiment card: the question, the kind (spike, prototype or PoC), a timebox, success criteria and an owner. Show it to your lead and ask for the timebox, not more.

remember!!

Pick the experiment by the question. Set the timebox first. Never serve the tasting spoon.
