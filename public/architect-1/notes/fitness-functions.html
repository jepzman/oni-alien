Fitness Functions

TL;DR

Architecture decisions decay quietly: an import here, 20 ms there. A fitness function turns an architecture rule into an automated check: module boundaries, latency at peak, no personal data in logs, dependency rules. Run them in the pipeline (on every merge or nightly), link each one to the ADR or requirement it protects, and let a failure break the build or open a ticket. The architecture then defends itself, without the architect reviewing every pull request.

  • Family: validating early
  • Origin: Neal Ford, Rebecca Parsons & Patrick Kua, Building Evolutionary Architectures (2017)
  • Lives in: the CI pipeline, next to the tests
  • Pairs with: quality attribute scenarios, modular monolith, ADRs

1The situation Larder, January 2026

Two months after deciding on a modular monolith, Ana looks at the code. There are 23 new imports from ordering straight into payments' internals. Checkout p95 has crept from 420 to 690 ms over six weeks, still “fine”, but heading for the 800 ms limit. And a log line with customer addresses is back. Every decision is still in its ADR. None of them is being checked.

  • Decisions written down aren't decisions enforced.
  • Drift is slow: each change is small and looks reasonable.
  • An architect reviewing every pull request doesn't scale, and becomes a bottleneck.
meanwhile, in Grace’s notebook
  • Leading vs Lagging Indicators (Grace, vol. 1): Grace's leading indicators do for the product what these checks do for the architecture: catch drift daily, not quarterly.

2Real-life analogy the spirit level

A good bricklayer puts a spirit level on every row as the wall goes up. If a row is off, it's one row to fix. A wall checked only when it's finished can be leaning badly, and by then the fix is knocking it down. The level is cheap, fast, and used constantly.

3How it solves it rules become checks in the pipeline

Go through your ADRs and quality scenarios and ask: “how would we know if this stopped being true?” Whatever you can measure automatically becomes a check. Fast ones run on every merge; slow ones (load tests) nightly. Each check names the decision it protects, so a failure explains itself.

  1. List the rules

    From ADRs, ASRs and scenarios: boundaries, latency, data rules, dependencies.

  2. Ask “how would we know?”

    For each rule, what can be measured automatically?

  3. Pick the trigger

    Fast and cheap → every merge. Slow (load, security scans) → nightly or weekly.

  4. Link to the decision

    The check's name or message points to ADR 0002 or QAS-1.

  5. Decide what failure does

    Break the build for hard rules; open a ticket for trends.

  6. Review them

    When an ADR is superseded, update or delete its fitness function.

Vocabulary for the exam

Fitness function
An objective, automated check of an architectural characteristic.
Atomic / holistic
Checks one thing alone / checks how several interact.
Triggered / continual
Runs on an event (a merge) / runs all the time (monitoring).
Architecture test
A unit-test-style check of structure (imports, layers).
Evolutionary architecture
An architecture designed to change, guarded by fitness functions.
Threshold
The limit a check enforces (p95 < 800 ms).

# .importlinter: protects ADR 0002 (modular monolith)          runs on every merge
[importlinter]
root_package = larder_core

[importlinter:contract:modules-use-public-api]
name = Modules talk only through api and events (ADR 0002)
type = forbidden
source_modules = larder_core.ordering
forbidden_modules =
    larder_core.payments._internal
    larder_core.payments.models
    larder_core.fulfilment._internal
    larder_core.fulfilment.models

# load/checkout.js (k6): protects QAS-1                         runs nightly
export const options = {
  scenarios: { kings_day: { executor: "constant-arrival-rate", rate: 3000,
                            timeUnit: "1s", duration: "10m", preAllocatedVUs: 400 } },
  thresholds: {
    "http_req_duration{journey:checkout}": ["p(95)<800"],   // QAS-1
    "checks{check:order_confirmed}": ["rate==1.0"],          // ASR-4: nothing lost
  },
};

tools: import-linter, ArchUnit, dependency-cruiser and NetArchTest for structure; k6, Gatling or Locust for performance; Semgrep and log scanners for data rules; Dependabot or Renovate plus licence checkers for dependencies; SLO alerts for continual checks.

4Gains vs losses nothing is free

What we gain

  • Decisions defend themselves: drift is caught in the pull request that causes it.
  • The architect isn't a bottleneck: no need to review every change.
  • Trends are visible: 420 → 690 ms shows up before 800.
  • Safe to change: teams refactor boldly, knowing the checks will catch a break.
  • Living documentation: the checks say what really matters.

What we lose

  • Building and maintaining checks takes engineering time.
  • Slow checks (load tests) cost infrastructure and CI minutes.
  • False alarms: flaky load tests erode trust.
  • Not everything is measurable: some qualities still need human review.

6Common pitfalls the usual ways this goes wrong

  • Checks with no reason

    A rule fails the build and nobody knows why it exists. Fix → name the ADR or ASR in every check's message.

  • Flaky thresholds

    The load test fails one night in four, so people ignore it. Fix → stable environments and margins; alert on trends, not single runs.

  • Everything breaks the build

    Teams spend days fighting checks for minor trends. Fix → hard rules break the build; trends open a ticket.

  • Outliving the decision

    ADR 0002 is superseded but its check still blocks merges. Fix → update or delete checks when their decision changes.

7When to use it (and when not)

Use it when…

  • Any architecture rule that has been broken once already.
  • Module boundaries in a modular monolith.
  • Quality scenarios with clear measures (latency, error rate, size).
  • Data rules (no personal data in logs, residency).

Skip it when…

  • Rules that can't be measured: keep them in reviews.
  • One-off decisions with nothing to drift (a vendor choice).
  • Very early prototypes where the rules aren't settled yet.

8Self-check quiz

What is a fitness function?

An automated, objective check of an architectural rule or quality, usually run in the pipeline.

Which question turns a decision into a fitness function?

“How would we know if this stopped being true?”

When should a check break the build, and when open a ticket?

Hard rules (boundaries, data rules) break the build; slow trends (latency creep) open a ticket.

Why link each check to an ADR or ASR?

So a failure explains itself, and the check is updated when the decision changes.

try it

Pick one ADR from your project. Write down how you'd know automatically if it stopped being true, and find the tool that could check it. Add it to CI as a warning first; after a week of no false alarms, make it fail the build.

remember!!

Check every row, not the finished wall. A decision nobody checks is a wish.
