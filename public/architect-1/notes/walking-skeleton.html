Walking Skeleton

TL;DR

Before building any part fully, build the thinnest possible end-to-end path through every part of the architecture: one tiny feature that goes from the user's screen through every service, store and integration, deployed by the real pipeline to a production-like environment, with an automated end-to-end test. Then add flesh slice by slice. Integration problems show up in week two, not month five, and the architecture is proven by running code, not slides.

1The situation Larder, the second Amsterdam store

When Larder opened its second Amsterdam store in 2024, the team built it layer by layer: the store app was done in month two, the stock sync in month three, payments in month four. Each part passed its own tests. In month five they connected them, and integration broke for weeks: ids that didn't match, a missing field, a timeout nobody had tested. For Rotterdam, with a fixed opening date, that can't happen again.

  • Parts built alone look finished, but the risk sits in the connections.
  • Deployment, environments and pipelines are left for “later”, and later is launch week.
  • Nobody can see the architecture working until it's too late to change it cheaply.

2Real-life analogy the kite and the bridge

To start a suspension bridge across a wide river, engineers once flew a kite across with a thin thread. The thread pulled a rope, the rope pulled a cable, and the cables carried the bridge. From the first day something connected both banks, and every step after that made the connection stronger, never started a new one.

Translating it to the job

3How it solves it thin, complete, deployed, tested

“Thin” means almost no features: one test product, one payment method, one courier. “Complete” means every part and every integration is touched, including the pipeline, environments, monitoring and the real third-party sandboxes. If a part isn't in the skeleton, its risk isn't retired.

  1. Pick the thinnest real journey

    One that touches every part: “order one item, pay, pick, deliver”.

  2. Include the boring parts

    Pipeline, environments, config, logging, the real vendor sandboxes.

  3. Stub nothing you can reach

    Use the payment provider's test account and StockPilot's sandbox, not mocks.

  4. Automate one end-to-end test

    It runs on every change; it's the thread you never cut.

  5. Deploy it like production

    Same pipeline, same infrastructure-as-code, a production-like environment.

  6. Add flesh slice by slice

    Each week: one more real feature through all the layers, never one layer alone.

Vocabulary for the exam

Walking skeleton
A tiny end-to-end implementation through every architectural part.
Vertical slice
A feature that goes through every layer, from UI to data.
Tracer bullet
Similar idea (The Pragmatic Programmer): code that lights up the path end to end.
Integration risk
The risk that parts that work alone fail together.
Sandbox
A vendor's test environment that behaves like production.
Production-like
Same pipeline, config and infrastructure as production, without real customers.

          the PSP's test card, a picker picks it on the picker app, a courier
          accepts it in the courier app and marks it delivered.

Must touch
  [x] customer app (TestFlight / internal track)   [x] Ordering module
  [x] Payments module + PSP test account          [x] Stock module + StockPilot sandbox
  [x] Fulfilment module + picker app              [x] Dispatch service + courier app
  [x] events: OrderPlaced → OrderPacked → OrderDelivered
  [x] city config for “Rotterdam” (ASR-1: no code change)

Must run on
  [x] the real CI/CD pipeline, infrastructure as code
  [x] staging-rtm (production-like), logs and dashboards on
  [x] one automated end-to-end test, run on every merge (≈ 4 min)

Out of scope (flesh, weeks 7+): real catalogue, substitutions, slots, promotions,

tools: Playwright or Detox for the end-to-end test, your CI/CD system, infrastructure as code, and the vendors' sandbox accounts. The skeleton is code like any other; it just comes first.

4Gains vs losses nothing is free

What we gain

  • Integration risk retired early: broken connections show up in week two.
  • The architecture is proven by running code, not slides.
  • Pipeline and environments ready from the start.
  • Always shippable: every slice after it is end to end.
  • Visible progress stakeholders can watch: “the banana got delivered”.

What we lose

  • Slow-looking start: weeks of work with “only one banana” to show.
  • Touches every team at once, so it needs coordination.
  • Vendor sandboxes can be slow to get and unlike production.
  • Temptation to skip the boring parts (pipeline, monitoring).

6Common pitfalls the usual ways this goes wrong

  • Mocking the scary parts

    The skeleton calls a fake payment provider. Fix → use the real sandbox: the real integration is the risk you're retiring.

  • Too much flesh

    The “skeleton” has 12 features and takes three months. Fix → one journey, one item, one of everything; add features after.

  • Skipping deployment

    It runs on a laptop. Fix → it must ship through the real pipeline to a production-like environment.

  • Cutting the thread

    The end-to-end test is disabled when it gets flaky. Fix → fix it first; it's the only proof the parts still connect.

7When to use it (and when not)

Use it when…

  • New systems, new architectures and big rebuilds.
  • When several teams or vendors must integrate.
  • When a launch date is fixed and integration risk is high.
  • Proving a chosen architecture really works.

Skip it when…

  • Small features inside a working system: it already walks.
  • Pure research spikes where no product will follow.
  • When the only risk is in one component: spike that component instead.

8Self-check quiz

What makes a walking skeleton “complete”?

It touches every architectural part and integration, and ships through the real pipeline with an automated end-to-end test.

Why use vendor sandboxes instead of mocks?

The real integration is the risk; a mock hides exactly what you need to find.

What comes after the skeleton?

Vertical slices: each adds one real feature through all layers.

How is it different from a prototype?

A prototype tests an idea and is thrown away; the skeleton is production code that becomes the system.

try it

For your next new feature or system, write a one-paragraph “skeleton journey” that touches every part, and a checklist of the parts it must pass through. Count how many of those parts you'd normally connect only at the end.

remember!!

Fly the thread across the river first. Then make it stronger, never start again.
