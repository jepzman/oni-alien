Bounded Contexts

TL;DR

In a real business, one word means different things in different places: an “order” is a basket to sales, a pick list to the warehouse, a drop to delivery. Don't force one model on everyone. Draw a boundary wherever the meaning changes; inside it, one team owns one consistent model and its own words. Contexts share ids and events, not tables. Those boundaries are your best first guess for modules, services and team ownership.

  • Origin: Eric Evans, Domain-Driven Design (2003)
  • Lives in: a context map and one canvas per context
  • Pairs with: event storming, modular monolith, anti-corruption layer

1The situation Larder, the 64-column table

Larder Core has one orders table with 64 columns, used by everyone. When Ordering adds a tip_eur column for couriers, the picking export breaks, because it reads the same table. Ask three teams what an order is and you get three answers: a basket with prices, a pick list with shelf positions, a drop with an address and a slot. One table is trying to be all three.

  • One shared model grows until nobody understands or dares change it.
  • Words drift: “product” means a catalogue item to one team and a shelf SKU to another.
  • Every change needs every team's agreement, so everything slows down.

2Real-life analogy the hospital

In a hospital, “the patient” means something different in each department. Reception keeps appointments and insurance. The ward keeps the bed, medication and charts. Billing keeps invoices. Each keeps its own file with only what it needs, in its own words, linked by the patient number. One giant shared file would be unreadable and dangerous.

3How it solves it draw boundaries where meaning changes

The event storming gives you the hints: clusters of events, different actors, and places where people use the same word differently. Draw a boundary there. Then draw a context map: how contexts relate, who is upstream, and what crosses the border (ids and events, never tables).

  1. Start from the event storm

    Group events that change together and are done by the same people.

  2. Listen for words that change meaning

    “Order”, “product”, “customer”: each meaning hints at a separate context.

  3. Name each context and its model

    Ordering → Order. Fulfilment → PickList. Dispatch → Drop.

  4. Give each one owner

    One team per context (a team can own several; a context never has two owners).

  5. Draw the context map

    Arrows for upstream/downstream, labelled with events or APIs; only ids cross.

  6. Make them modules

    Each bounded context becomes a module in the modular monolith, or later a service.

Vocabulary for the exam

Bounded context
A boundary inside which one model and its words are consistent.
Ubiquitous language
The shared words of a context, used by experts and code alike.
Context map
A diagram of contexts and how they relate.
Upstream / downstream
Who publishes and who depends on what is published.
Anti-corruption layer
A translator that protects a context from another's model.
Subdomain
A part of the business problem (core, supporting, generic).

4Gains vs losses nothing is free

What we gain

  • Smaller, clearer models: each team understands its own.
  • Changes stay local: a courier tip doesn't break picking.
  • Clear ownership: one team per context.
  • Natural seams for modules, services and teams.
  • Better conversations: code uses the same words as the business.

What we lose

  • Duplication: the same order id and some data appear in several contexts.
  • Integration work: events and translations between contexts.
  • Hard to get right: early boundaries are guesses and will move.
  • Learning curve: DDD vocabulary can put people off.

6Common pitfalls the usual ways this goes wrong

  • Contexts by technology

    “Database context”, “API context”. Fix → draw boundaries by business meaning and people, not tech.

  • One context per entity

    Order context, Product context, Customer context: CRUD in disguise. Fix → group by business capability and language, not by noun.

  • Sharing tables anyway

    Contexts on the diagram, one orders table in the database. Fix → each context owns its data; others get ids and events.

  • Set in stone

    The first map is treated as final. Fix → revisit boundaries as you learn; cheap in a modular monolith.

7When to use it (and when not)

Use it when…

  • A business with several departments using the same words differently.
  • Splitting a monolith into modules or services.
  • Deciding team ownership.
  • When one shared model has become too big to change safely.

Skip it when…

  • Small apps with one simple model and one team.
  • Generic subdomains you buy (helpdesk, email): use the vendor's model behind a translator.
  • When the domain isn't understood yet: event-storm first.

8Self-check quiz

What signals a boundary between two contexts?

The same word changes meaning, different people do the work, and events cluster separately.

What may cross a context boundary?

Ids, events and API calls; never shared tables or internal models.

Why can “order” be three different models at Larder?

Ordering, Fulfilment and Dispatch need different data and rules: a basket, a pick list, a drop.

How do bounded contexts relate to the modular monolith?

Each bounded context becomes a module; later, some may become services.

try it

Pick the most-used noun in your system (order, account, booking). Ask three people from different teams to define it in one sentence each. Write down how many different meanings you get, and which tables or classes are trying to hold all of them.

remember!!
