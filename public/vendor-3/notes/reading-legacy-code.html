How Do We Read Code Nobody Owns?

TL;DR

When nobody can say for sure what old code does, stop arguing and measure it. Run real inputs through it and record every output: a characterisation test, or golden master. It describes what the code does, right or wrong. Run the new system on the same inputs, compare field by field, and treat every difference as either a bug or a hidden business rule someone must decide about.

1The situation The Grid, 27 October 2027

CUSTBL07, written in 1999, is 6,400 lines of COBOL that prepare customer bills before they go to Halvorsen. Lodestar must reproduce what it does for every migrated customer.

  • Bert remembers it “rounds down”. The 2006 document says it “rounds normally”. Hana's reading suggests it rounds half down, sometimes.
  • A rounding difference of a penny on 380,000 bills is £3,800 a month, and a regulator question.
  • Nobody can prove which explanation is right, and nobody owns the code anymore.

2Both sides of the table the same moment, seen twice

MetroVolt Nkem and Customer Ops

MetroVolt cares about one thing: bills must not change when customers move to Lodestar, unless MetroVolt decides they should. A different penny on 380,000 bills means complaints, a regulator letter and a headline.

“Same bill, or a decision. Never an accident.”

Wrenfield Hana and Oskar

Wrenfield has to rebuild behaviour nobody can describe reliably. Reading the code is slow and error-prone; asking people gives three answers. They need a way to prove what the old code does.

“Let the code tell us, with real data.”

Old code is the most accurate specification the client has. It's just written in a language nobody reads anymore.

3Real-life analogy the recipe nobody wrote down

A bakery's founder made the best bread in town and never wrote the recipe down. Her daughter doesn't argue about what's in it. She bakes the founder's last batch alongside her own, tastes and weighs both, and changes her recipe until nobody can tell them apart, noting every surprise (“she always added salt twice”).

4How it works record real behaviour, compare, explain every difference

Oskar and Hana pick 10,000 real accounts covering every tariff and odd case Bert can name. They run them through CUSTBL07 in MAVIS's test region and record every output field. That record is the golden master: what the program actually does today, right or wrong.

Then the new billing-preparation code runs on the same inputs, and a comparison tool checks every field of every account. The first run shows 2,914 differences. Each one is either a bug in the new code (most of them) or a hidden rule in the old. Three hidden rules emerge. Rule 7: since 1999, pro-rata standing charges for accounts with a meter exchange in the month are rounded half down.

Hidden rules aren't Wrenfield's to decide. Each one goes to Nkem and Customer Ops with the evidence: keep it (customers' bills unchanged) or fix it (a deliberate change, communicated). They keep rule 7 for wave 1. The golden master becomes a permanent regression test.

  1. Choose real inputs that cover the cases

    Ask the expert for the odd ones.

  2. Record every output of the old code

    The golden master: behaviour, not intent.

  3. Run the new code on the same inputs

    Same data, same period.

  4. Compare field by field

    Automate it.

  5. Classify every difference

    New bug, or hidden rule.

  6. Let the client decide hidden rules

    Keep or change, deliberately, in writing.

Vocabulary

Characterisation test
A test that records what code currently does, so changes can be detected.
Golden master
A recorded set of outputs used as the reference.
Hidden business rule
Behaviour the business relies on that nobody documented.
Regression test
A test that checks nothing that worked has broken.
Parallel run
Running old and new side by side on the same inputs.
Rounding half down
Rounding exact halves down instead of up.

5.3 Migrated customers' bills shall be calculated identically to MAVIS, except where MetroVolt instructs a change.

“identically”. the golden master is how we prove it.

Sch. 4, M3 Balances reconcile 100 % (MAVIS ↔ new platform).

rounding is reconciliation. a penny is a failed criterion.

In plain words: if the contract says bills must be identical, you need proof, not explanations. A golden master is that proof, and it turns hidden rules into decisions the client owns.

9Common pitfalls the usual ways this goes wrong

  • Trusting explanations

    Three people, three answers. Fix → measure the code's behaviour.

  • Too few cases

    Odd tariffs aren't covered. Fix → ask the expert for every odd case.

  • Fixing hidden rules yourself

    Bills change without a decision. Fix → the client decides each one.

  • Comparing totals only

    Errors cancel out. Fix → field by field, account by account.

  • A one-off check

    Later changes break it again. Fix → keep it as a regression test.

10When to use it (and when not)

Use it when…

  • Rebuilding behaviour from code nobody can explain.
  • Outputs customers or regulators see.
  • Before refactoring or replacing old code.

Skip it when…

  • The behaviour is fully specified and already covered by tests.

11Self-check quiz

What is a characterisation test?

A test that records what code currently does, right or wrong, as a reference.

What is a golden master?

The recorded outputs of the old code for a set of real inputs.

What two things can a difference mean?

A bug in the new code, or a hidden rule in the old.

Who decides what to do with a hidden rule?

The client (here Nkem and Customer Ops), with evidence.

What is rule 7?

Pro-rata standing charges on a meter exchange are rounded half down, since 1999.

what would you do?A MetroVolt manager says rule 7 is “obviously a bug, just fix it”. What do you do?

Agree it may be, and take it to Nkem as a decision: fixing it changes some customers' bills, which needs a deliberate choice and communication. Record the decision either way.

try it

Pick a piece of old code whose behaviour people argue about. Run twenty real inputs through it and record the outputs. Did anything surprise you?

remember!!

Don't argue about what old code does. Record it, then make every difference a bug or a decision.
