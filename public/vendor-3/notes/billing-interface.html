What Does the Billing System Really Need?

TL;DR

Another vendor's interface specification describes what they think their system does. Test it against the real system early, write down every surprise, and turn the specification into contract tests both firms run. Keep their model at the edge with a translation layer (an adapter), so their quirks don't leak into your design. And put a version on every file.

  • Family: the data and its seams
  • Lives in: integration/billing-adapter/ · contract tests

1The situation The Grid, 2 November 2027

Halvorsen delivered its interface specification on 30 July, on time: dependency D-03 met. Version 1.1: 41 fields on twelve pages. In October Hana tests real files against Halvorsen's test system.

  • She finds six behaviours the spec doesn't mention.
  • The worst: if field 17 (town) isn't in capitals, Halvorsen silently drops the record. No error, no bill.
  • Lodestar's addresses, cleaned to the national format, need a fourth address line. Version 1.1 has three.

2Both sides of the table the same moment, seen twice

MetroVolt Sven and Halvorsen

Halvorsen's spec was written from what the system was designed to do in 2016. The quirks are known to Halvorsen's engineers and to nobody else. Sven doesn't want his system to look broken in front of MetroVolt, and doesn't want blame for MAVIS's data either.

“It's always worked with MAVIS's files.”

Wrenfield Hana and Ines

Wrenfield must feed billing correctly for 380,000 customers, through a system it doesn't control. Silent drops would mean customers without bills, discovered months later. It needs the real behaviour written down and tested, and a fourth address line.

“Let's turn the spec into tests we both run.”

An interface spec is a promise about behaviour. A test suite is a promise you can check every day.

3Real-life analogy the plug adapter

Travelling abroad, you don't rewire your hairdryer for each country. You carry a plug adapter that turns their socket into yours, and you test it before you trust it with your laptop. If their sockets have a quirk (one only works when the switch is on), you write it on the adapter.

4How it works test the real thing, adapter at the edge, tests both sides run

Test the real system. Hana sends 2,000 realistic records through Halvorsen's test system and compares what was billed with what was sent. Six surprises: town names must be in capitals or the record is dropped; dates only day-first; amounts never signed; three more about tariff codes.

Keep their model at the edge. Lodestar keeps its own customer model. A billing adapter translates it into Halvorsen's file: capitals, date order, signs, codes. If Halvorsen changes, only the adapter changes.

Turn the spec into tests. With Sven's engineer, Hana writes 58 contract tests: given this record, Halvorsen produces this bill line, or this error. Both firms run them, Wrenfield on every build. Silent drops become a test failure.

Version everything. On 2 November Sven signs spec v1.2: address line 4 added, all six behaviours written down, and a version number in every file header. Sven's comment: “We should have written these down in 2016.” It goes into IA-01. (Remember the version header; it matters in May.)

  1. Test the real system early

    Realistic records through their test environment.

  2. Write down every surprise

    With examples.

  3. Put an adapter at the edge

    Their model stops there.

  4. Write contract tests together

    Given input, expected output or error.

  5. Both sides run them

    On every build.

  6. Version the spec and every file

    So mismatches show immediately.

Vocabulary

Interface specification
A description of the format and behaviour of a connection between systems.
Contract test
A test that checks one system meets what another relies on.
Adapter (translation layer)
Code that converts between two models at the boundary.
Anti-corruption layer
An adapter that keeps another system's model out of yours.
Silent failure
A failure that produces no error.
Versioning
Labelling each format so both sides know which they're using.

5What the contract says the dependency, met and improved

Lodestar SOW · Appendix C, D-03 · IA-01 §52 Nov 2027
v1.2

D-03 The billing supplier provides the interface specification by 30 July 2027.

met. on time. and incomplete, through nobody's bad faith.

IA-01, 5 Each file carries a header stating the specification version. A receiving system that does not support the stated version shall reject the file with an error.

a rejected file at 02:15 beats 11,000 missing bills in March.

In plain words: a dependency can be delivered on time and still be incomplete. Testing early and writing the real behaviour into the interface agreement turns that into a shared improvement instead of a blame war.

9Common pitfalls the usual ways this goes wrong

  • Trusting the document

    Real behaviour differs. Fix → test the real system early.

  • Their model in your core

    Every quirk spreads. Fix → an adapter at the edge.

  • Tests only on your side

    Their next release breaks you. Fix → both sides run them.

  • No version on files

    Mismatches are invisible. Fix → a version in every header.

  • Gloating about quirks

    You lose the partner you need. Fix → make it a joint improvement.

10When to use it (and when not)

Use it when…

  • Feeding or reading another vendor's system.
  • A spec written long ago.
  • Any boundary where silent failure is possible.

Skip it when…

  • Never skip the tests; the adapter can be thin if the formats already match.

11Self-check quiz

What was wrong with D-03, if it was delivered on time?

Nothing in bad faith, but the spec missed six real behaviours, including silent drops.

What does the billing adapter do?

Translates Lodestar's model into Halvorsen's format, keeping their quirks at the edge.

What is a contract test?

Given an input, the other system produces an agreed output or error.

Why a version in every file header?

So a system expecting another version rejects the file loudly.

What did v1.2 add?

Address line 4 and the six behaviours written down.

what would you do?A Halvorsen release changes how credits are handled, and contract test CT-31 fails on Wrenfield's build. What do you do?

Tell Sven's team and Hollis the same day with the failing test; under IA-01 format changes need 30 days' notice. Agree whether to adapt or roll back, and update the spec version.

try it

Take an interface you depend on. Send ten realistic records and compare what happens with what the spec says. Write one contract test for the most dangerous difference.

remember!!
