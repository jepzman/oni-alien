Four notes in sixty seconds

Gist OAuth with PKCE starts a session, short-lived tokens keep it going, password hashing protects what the provider stores, and CSRF protection guards the cookie. Together they form one system, and the hard questions are about the whole: how long a customer is signed in, what sign-out ends, and how access is taken back.

The security volume has four notes that are really one system. Customer 7 signs in to the mug shop on a laptop. The password is typed at the identity provider, never at the shop. The shop's backend receives tokens and gives the browser a cookie. The Orders API checks a token on every call.

NoteIn one lineIts part of the system
OAuth 2.0 with PKCEsign in at the provider; the app swaps a one-time code and a secret for tokenshow a session starts
Short-Lived Tokensaccess tokens that live minutes, refresh tokens that rotate on every usehow a session continues
Password Hashingstore slow, salted hashes, or better, no passwords at allwhat the provider keeps
CSRF Protectiona cookie is sent whichever site asks; check the request really came from your pagewhat a cookie session must defend
The OAuth note's own going-deeper chapter covers where tokens live and how an API checks one. This dive starts from there.

Each note is correct on its own. Put them together and the questions change. How long is customer 7 actually signed in, and by which of the four credentials? What does “sign out” end, and what keeps working for another ten minutes? When the shop removes someone's admin rights, when does the system notice? The answers are design decisions, and most teams make them by accident. This deep dive makes them on purpose.

chapter 2 · 2 min

Four layers, four clocks

Gist A signed-in customer is held up by a provider session, the shop's own session, a refresh token and an access token, each with its own lifetime. Sessions need idle and absolute expiry. Risky actions such as changing the email address ask for a recent sign-in instead of shortening every session.

Ask a team “how long does a session last?” and you will get four different answers, all correct. A signed-in customer is held up by four separate credentials, each with its own clock.

LayerLives inTypical lifeEnds when
Provider sessiona cookie on the identity provider's own domaindaysthe customer signs out at the provider, or it expires
Shop sessiona cookie on the shop's domain, and a row in the shop's session store30 idle days, 90 days at mostsign-out deletes the row, or it expires
Refresh tokenthe shop backend, or the phone's keychainreplaced on every use; 14 idle daysit is used, revoked or expires
Access tokenthe backend's memory; sent to the APIs10 minutesit expires. Usually nothing can end it earlier
The ID token is missing on purpose. It says who signed in, once. It is not a session and it is not for calling APIs.

What one request does

  1. The browser sends the shop cookie. The backend looks up the session row: does it exist, has it expired?
  2. The row points at the stored tokens. If the access token has more than a minute left, use it.
  3. If not, send the refresh token to the provider. Store the new access token and the new refresh token; the old refresh token is now dead.
  4. Call the Orders API with the access token. The API checks the signature, issuer, audience and expiry.

Two kinds of expiry appear in the table, and a design needs both. Idle expiry ends a session nobody is using: 30 days without a visit. Absolute expiry ends every session eventually, however busy: 90 days, then sign in again. Idle without absolute gives a stolen session eternal life as long as the thief keeps it busy.

Recent sign-in for risky actions

A 30-day session is right for browsing mugs and wrong for changing the email address on the account. The usual answer is not a shorter session. It is asking again for the few actions that matter: change email, change password, add a payment card, see stored addresses. The session records when the customer last proved who they are, and those actions require that to be within ten minutes. If it is older, the shop sends the customer to the provider with a request to sign in again (in OpenID Connect, max_age or prompt=login) and checks the time in the new ID token.

That way a stolen laptop with an open session can buy mugs, which is annoying, but cannot take over the account, which is a disaster.

checkpoint

A stolen laptop has an open 30-day session. What stops the thief from taking over the account?

Changing the email or password requires a sign-in within the last ten minutes, which the thief cannot do without the password or passkey.

Why have absolute expiry when idle expiry already ends unused sessions?

A session that is used regularly, for example by a thief, would otherwise never end.

Session ids or tokens

Gist A session id must be looked up but can be ended at once. A signed token needs no lookup and cannot be ended early. Most systems use both: an opaque cookie between browser and backend, short signed access tokens between services, and an opaque refresh token kept on the server.

There are two ways to remember that someone signed in, and the argument between them has gone on for years. Both are right in different places.

A session id (stateful)A self-contained token (JWT)
What the client holdsa random id that means nothing by itselfsigned data: who, which roles, until when
Checking itlook the id up in a storecheck the signature; no lookup
Ending it earlydelete the row; works on the next requesthard. It stays valid until it expires
Sizeabout 30 bytesoften 1 KB or more, on every request
Who can read itnobody: it is a random numberanyone. It is encoded, not encrypted
Fitsa browser talking to its own backendone service calling another; APIs called by many clients
“Stateless sessions” is a slogan. The day you need a sign-out button, you have state again.

The shape most systems end up with

LinkCredentialWhy
browser → shop backendan opaque session cookieshort, unreadable, ends the moment the row is deleted
shop backend → APIsa 10-minute JWT access tokenAPIs check it without a call to anyone; short life limits the damage
shop backend → provideran opaque refresh token, stored server sideused rarely, checked by lookup, so it can be revoked
set-cookie.httpthe shop's session cookie
Set-Cookie: __Host-sid=k7Qe3w...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=2592000

Each attribute does one job. Secure: only over HTTPS. HttpOnly: no script in the page can read it, so a cross-site scripting bug cannot steal it. SameSite=Lax: not sent with forms posted from other sites, which removes most CSRF attacks. The __Host- prefix makes the browser refuse the cookie unless it is Secure, has Path=/ and no Domain, so a careless subdomain cannot overwrite it.

What goes inside an access token

Little. The user id, the audience, the expiry, the scopes. Every claim is a promise that cannot be withdrawn until the token expires (drill 4), and anyone holding the token can decode it. No email address, no name, no address: if a token ends up in a log, it should not also be a data leak.

The checks an API makes are listed in the OAuth note's going-deeper chapter. Two are worth repeating because they are skipped so often. Check the audience: a token issued for the Loyalty API must not be accepted by the Orders API, or one weak service can lend its tokens to all the others. And fix the algorithm in configuration: never let the token's own header choose it.

checkpoint

Why is a JWT a poor choice for the browser's session cookie?

It is large, readable by anyone who holds it, and stays valid until it expires, so sign-out cannot end it. A random id does none of that.

The Orders API accepts any valid token from the provider. What is missing?

The audience check. A token issued for another service, perhaps a weaker one, would be accepted.

Failure drills

Gist Six ways sessions go wrong: a stolen refresh token, two tabs that look like a theft, a sign-out that leaves the provider session open, a removed admin whose token still says admin, a session id chosen by the attacker, and one server with a fast clock.

Cover the bottom half of each card. What happens next?
  • 1 · stolen refresh token
  • 2 · two tabs
  • 3 · sign-out
  • 4 · former admin
  • 5 · fixation
  • 6 · fast clock
Drill 1

The refresh token is copied off the phone

Timeline
Malware on customer 7's phone copies the refresh token r5. From another machine the attacker uses it and receives a fresh pair, r6 and an access token. A minute later the real app, still holding r5, tries to refresh.
Without rotation
Nothing happens at all. A refresh token that is never replaced works for the attacker for 14 days, renewing itself each time, and nobody can tell the two users apart.
What saves you
Rotation with reuse detection. r5 was already used, so its second appearance means two parties hold it. The provider cannot tell which is real, so it revokes the whole family: r6 stops working too. Both are signed out. The customer signs in again with a password or passkey; the attacker cannot.

Rule: rotate refresh tokens on every use, and treat a reused one as theft: revoke everything that descends from it.

Drill 2

Two tabs refresh at the same moment

Timeline
Customer 7 has the shop open in two browser tabs that each hold tokens (a design the shop later dropped). Both access tokens expire at 10:00. Both tabs refresh within 40 ms using the same r3.
What you see
The second request looks exactly like drill 1. The family is revoked and a paying customer is signed out for no reason. Support hears “your site keeps logging me out”, mostly from the most active customers.
What saves you
Make refreshing happen in one place: the backend holds the tokens and refreshes under a lock per session, so concurrent requests wait for one refresh. Where clients must refresh themselves, give reuse a short grace period: within a few seconds, a repeat from the same client gets the same new pair back instead of a revocation.

Rule: real clients race with themselves. Serialise the refresh, or forgive an immediate repeat.

Drill 3

Signed out, and signed straight back in

Timeline
On a library computer customer 7 clicks “Sign out”. The shop deletes its cookie. The next person clicks “Sign in”, is sent to the provider, and is let straight through: the provider session is still alive. They are now customer 7.
What else is still alive
The refresh token, if the shop only cleared its cookie and kept the tokens. And the last access token, for up to ten minutes, wherever it was copied.
What saves you
Sign-out ends every layer you can reach: delete the session row, revoke the refresh token at the provider, then send the browser to the provider's sign-out endpoint so its session ends too (in OpenID Connect, RP-initiated logout). The access token's remaining minutes are the price of not checking it; chapter 5 shows how to shorten that window when it matters.

Rule: sign-out must end the provider session and the refresh token, not just your own cookie.

Drill 4

The admin who is no longer an admin

Timeline
At 10:00 a staff member's admin role is removed because they are leaving. Their access token, issued at 9:58, contains "role": "admin" and expires at 10:08. At 10:05 they export the customer list.
What you see
The audit log shows an admin export after the role was removed. Every system did what it was told: the token was valid, and it said admin. With the 24-hour tokens some teams use, the window is a day.
What saves you
Treat claims in a token as a promise that lasts until expiry, and choose what you put in that promise. Keep privileged tokens short. For the few dangerous actions (exports, refunds, role changes), check the permission at the source at the moment of the action, not from the token. And push removals through one of the revocation mechanisms in chapter 5.

Rule: whatever a token says stays true until it expires. Check dangerous permissions live.

Drill 5

The session id the attacker chose

Timeline
The shop gives every visitor a session cookie before sign-in, to hold the basket. An attacker visits, gets sid=abc, and plants that cookie in the victim's browser through a vulnerable subdomain. The victim signs in. The shop marks abc as signed in.
What you see
The attacker, holding abc, is now signed in as the victim. No password was stolen and no token was copied.
What saves you
Issue a new session id at sign-in and at every change of privilege, and copy the basket across. The old id stays an anonymous basket. The __Host- cookie prefix from chapter 3 also stops a subdomain from setting the cookie in the first place.

Rule: a session id never survives sign-in. Always issue a new one.

Drill 6

One server's clock is three minutes fast

Timeline
One of six API servers lost its time sync after a host move. Its clock is three minutes ahead. Every access token it sees in the last three minutes of its life is already expired.
What you see
About one request in six gets a 401 near the end of a token's life, the client refreshes, and sometimes the refresh lands in drill 2. The reports say “random logouts”. Nobody can reproduce them on a laptop.
What saves you
Keep clocks synced and alert when one drifts by more than a second or two. Allow a small leeway, 30 to 60 seconds, when checking exp and nbf. Refresh tokens a minute before they expire, not after a 401.

Rule: token checks depend on clocks. Sync them, watch them, and allow a minute of leeway.

What the six drills add up to

DecisionDrill
refresh tokens rotate; reuse revokes the family1
refreshing happens in one place, or tolerates an immediate repeat2
sign-out reaches the provider and revokes the refresh token3
tokens carry few privileges; dangerous actions check live4
a new session id at every sign-in5
synced clocks and a small leeway6

checkpoint

Customers who keep many tabs open are being signed out several times a day. Which drill, and which fix?

Drill 2: concurrent refreshes look like reuse. Refresh in one place under a lock, or allow a short grace period for immediate repeats.

After sign-out on a shared computer, the next person signs in as the previous customer without a password. What did sign-out miss?

The provider session. Sign-out must also send the browser to the provider's sign-out endpoint.

Taking access back: the hard problem

Gist A token nobody checks cannot be taken back, so revocation means buying back some checking. Revoking refresh tokens stops renewals; a user version in every token, checked with a short cache, ends all older tokens within seconds; dangerous actions check permissions live. Choose the mechanism per event.

Short-lived tokens were adopted to avoid a hard problem: checking, on every request, whether a credential is still good. A token nobody checks again cannot be taken back. Revocation is buying back some of that checking, and it is worth deciding how much you need for each kind of event.

Six events that should end access

EventHow fast must it work?
customer signs out on this devicenow, on this device
“sign out of all devices”within a minute
password changed or resetwithin a minute, everywhere except the device that changed it
phone reported stolennow
admin role removed, employee leavesnow for dangerous actions; minutes for the rest
a token appears in a log or a public repositorynow

Six mechanisms, cheapest first

MechanismHowCostDelay
Waitdo nothing; the access token expiresnoneup to its lifetime: 10 minutes
Revoke the refresh tokendelete it at the providernone extrano new access tokens; the current one lives on
Delete the session rowthe shop backend stops using the sessiona lookup the backend already doesimmediate for the web app
User versiontokens carry sv: 7; the user record holds 7; bump it to 8 to end every older tokenone cached lookup per request, per useras long as the cache: say 30 seconds
Deny listlist revoked token ids (jti); entries expire when the tokens wouldone lookup per requestseconds
Introspectionask the provider about every tokena network call per request; the provider becomes criticalnone
The user-version row is the workhorse: one number per user, and every token older than it is dead.
require-current-user.tsend every older token by bumping one number
export async function requireCurrentUser(token: Claims) {
  // cached for 30 s: a revocation takes effect within half a minute
  const current = await cache.get(`user-version:${token.sub}`, 30, () =>
    db.value("SELECT session_version FROM users WHERE id = $1", [token.sub]));

  if (token.sv < current) throw new Unauthorized("Session ended, please sign in again");
}

// "sign out everywhere", password change, role removal:
// UPDATE users SET session_version = session_version + 1 WHERE id = $1;

Choosing per event

EventUse
sign out on this devicedelete the session row, revoke its refresh token, end the provider session (drill 3)
sign out of all devices, password changebump the user version; revoke every refresh token of the user
phone stolenrevoke that device's refresh token family; bump the user version if in doubt
admin role removedbump the user version, and check dangerous actions live anyway (drill 4)
token leaked in a logdeny-list its id until it would expire; find out why tokens reach logs
signing key leakedrotate the key. Every token signed with it dies, which signs everyone out. Accept it

Most of the shop needs nothing beyond the first two mechanisms and the user version. Introspection on every request is rarely worth it; if a service needs that much certainty, it can call introspection for the few calls that matter.

When the provider can tell you

Identity providers can also push events to the applications that rely on them. OpenID Connect back-channel logout sends a signed message to the shop when a session ends at the provider, so the shop can delete its own row. Newer standards for sharing security signals between services (CAEP, part of the OpenID Shared Signals framework) carry events such as “credentials changed” or “session revoked”. They do not remove the need for short lifetimes, because a message can be lost. They shorten the window on a good day.

checkpoint

Why is a user version cheaper than a deny list of tokens?

It is one number per user, cached, and one bump ends every older token. A deny list needs an entry for each token and a lookup of each one.

A signing key has leaked. What is the only complete fix, and its cost?

Rotate the key at once. Every token signed with it stops working, so every user signs in again.

Lifetimes, worked out

Gist Each lifetime follows from what it protects: ten-minute access tokens bound how long a revoked user keeps going, fourteen idle days keep returning shoppers signed in, and a recent sign-in guards risky actions. Shorter access tokens multiply refresh traffic. Rotate signing keys in steps so both keys are published for a while.

Lifetimes are usually copied from a tutorial. Here they are worked out for the shop, each from what it protects.

SettingReasoningValue
Access tokenthe longest a revoked user may keep calling an API without a live check10 min
Refresh token, idlea shopper who comes back after a fortnight should not have to sign in14 days
Refresh token, absoluteevery device proves itself again eventually90 days
Shop session, idle and absolutethe same as the refresh token it uses30 / 90 days
Recent sign-in for risky actionslong enough to finish changing an email address10 min
Clock leewaycovers small drift, not a broken clock (drill 6)60 s
Refresh before expiryno request ever meets an expired token1 min early
Refresh gracean immediate repeat from the same client is not theft (drill 2)10 s
User-version cachehow late “sign out everywhere” may take effect30 s
Write the reasoning next to each number in the config. Next year somebody will want to change it.

What the refresh traffic costs

At the evening peak 20,000 customers are active. Each refreshes once per access-token lifetime, every ten minutes: 20,000 ÷ 600 s ≈ 33 refreshes a second. Shortening access tokens to two minutes would make it 167 a second, five times the load on the provider, to close a window that the user version already closes in 30 seconds. Shorter is not automatically safer; it is a cost you should be able to name.

Rotating the signing key

APIs check access tokens against the provider's public keys, published as a JSON Web Key Set and cached. Each token names its key with kid. A key change done in one step signs everyone out: new tokens are signed with a key the APIs have not fetched yet, and old tokens stop verifying the moment the old key disappears.

WhenStep
day 0publish the new key in the key set, next to the old one. Keep signing with the old key
day 1start signing with the new key. Every API has fetched the set by now
day 1 + 10 min + cache timethe last token signed with the old key has expired
day 2remove the old key from the set

APIs cache the key set for a few hours and fetch it again when they meet an unknown kid, with a limit on how often, so a stream of tokens with made-up key ids cannot turn into a stream of fetches.

checkpoint

Halving the access-token lifetime from 10 to 5 minutes: what does it cost, and what does it buy if user versions are already in place?

It doubles refresh traffic to the provider. It buys little: the user version already ends revoked tokens within 30 seconds.

Why publish the new signing key a day before using it?

APIs cache the key set. They must have the new key before any token signed with it arrives.

The front door: login and recovery

Gist Stolen passwords from other sites are tried against every login page, so limit attempts per account, per address and on the overall failure rate, refuse leaked passwords, and offer passkeys. The slow hash needs a cap of its own. Account recovery is part of sign-in and must be as strong.

Everything so far starts after sign-in. The sign-in itself, and the paths around it, are where accounts are actually taken. If the shop runs its own passwords instead of using a provider, this chapter is its job; if not, it is a list of things to check that the provider does.

Credential stuffing

Billions of email and password pairs from other sites' leaks are for sale. Attackers try them against every login page, slowly and from many addresses. The password-hashing note protects stolen hashes; it does nothing against a correct password that was stolen somewhere else.

DefenceStops
limit attempts per account, with growing delaysmany guesses at one customer
limit attempts per address and per networkone machine trying many accounts
watch the overall failure ratethe slow, spread-out attack the first two miss: an alert when failures jump from 5 % to 40 %
refuse passwords that appear in known leaksthe reused password at the door; checked by sending a short hash prefix, never the password
a second factor, or passkeysa correct password on its own
Passkeys end this chapter's first half: there is nothing to stuff. Offer them, and make them the default where you can.

The hash on the login path

QuantityValue
Argon2id settings64 MB of memory, 3 passes: about 50 ms per hash
Logins at the evening peak40 a second
CPU busy hashing40 × 0.05 s = 2 cores
Memory while hashing40 × 0.05 × 64 MB ≈ 130 MB in flight
An attacker sending 2,000 a second100 cores. Cap concurrent hashes and refuse early

The slow hash that protects a leaked table is also an easy way to overload the login service. Put the rate limits in front of the hash, and a bulkhead around it: a fixed number of hashes at once, and a fast “try again” beyond that.

verify-password.tscheck, and upgrade old hashes on the way
export async function checkPassword(user: User | null, password: string) {
  // unknown email: hash anyway, so the answer takes the same time
  const stored = user?.passwordHash ?? DUMMY_HASH;
  const ok = await argon2.verify(stored, password);
  if (!user || !ok) return false;

  if (argon2.needsRehash(stored, CURRENT_SETTINGS)) {        // settings raised since this hash was made
    await users.setPasswordHash(user.id, await argon2.hash(password, CURRENT_SETTINGS));
  }
  return true;
}

Two habits are in those lines. An unknown email address takes the same time and gets the same message as a wrong password, so the login form cannot be used to find out who has an account. And old hashes are upgraded the next time their owner signs in, which is the only moment the shop ever has the password in hand.

Recovery is the real front door

An account is only as strong as the easiest way to get back into it. A reset email that anyone can trigger, with a link that never expires, is a password that the attacker gets to choose.

  • Reset links work once, expire in 30 minutes, and are stored as a hash, like a password.
  • A completed reset ends every other session (bump the user version) and sends a notice to the customer.
  • Changing the email address needs a recent sign-in and a confirmation at the old address, or the first thing an attacker does is move the account out of reach.
  • Support staff who can reset accounts by phone are part of the sign-in system. Their process needs the same thought as the code.

checkpoint

Why hash a dummy value when the email address is unknown?

So the answer takes the same time as a wrong password, and the form cannot be used to discover which emails have accounts.

A reset link is valid for 7 days and can be used repeatedly. Name two problems.

Anyone who sees the email later, or finds it in a forwarded thread, can take the account; and it remains usable after the customer has reset their password.

Running it

Gist Graph sign-in success, refresh failures and token rejections, each split by reason, so a key problem, a fast clock and a refresh race look different. Keep an audit log of every security event. Redact credentials from logs and keep tokens out of URLs.

Sign-in fails in two ways that look alike from outside. Customers cannot get in, or customers keep falling out. The graphs need to tell those apart.

MetricHealthyIt means trouble when
Sign-in success ratesteady, most attempts succeedit falls: an outage, or a stuffing attack raising the failures
Refresh failures, by reasona few expired, almost no reusereuse jumps: drill 2 after a front-end change, or real theft
Token rejections at the APIs, by reason: expired, signature, audience, not yet validalmost all “expired”“signature” rises: key rotation went wrong. “Not yet valid”: a fast clock
Sessions per customera few devicesone account with hundreds: a shared or stolen account
Resets and email changesa steady tricklea spike: someone is taking accounts through recovery
Splitting rejections by reason is the single most useful graph here. One number for “401s” hides every cause.

Audit log

Record sign-in, sign-out, refresh-token reuse, password and email changes, second-factor changes, role changes and every revocation. Each entry says who, from which device and network, when, and why. This is the log the security team will read on its worst day.

Never log a credential

Tokens leak into logs more than anywhere else: an Authorization header in a request dump, a token in a URL, a session cookie in an error report. Redact those fields in the logging library, not in each service, and test that the redaction works. Keep tokens out of URLs altogether, since a URL ends up in browser history, proxy logs and the Referer header sent to other sites.

Runbook: “customers are being logged out at random”

  1. Look at the rejection reasons. “Signature” points at keys. “Not yet valid” or early “expired” points at a clock. Reuse in the refresh failures points at drill 2.
  2. Did keys change? An old key removed before its tokens expired, or an API that cached the key set and never fetched the new one.
  3. Did cookies change? A new cookie name, domain or SameSite setting in the last release can drop sessions for some browsers.
  4. Did servers change? Two versions of the backend behind one load balancer, each with a different cookie secret, sign each other's customers out.

Runbook: “a token has leaked”

  1. An access token: deny-list its id until it would expire, or bump the user's version. Find how it reached the place it leaked.
  2. A refresh token: revoke its family. The customer signs in again.
  3. Many tokens, or a signing key: rotate the key at once and accept that everyone signs in again. Then tell the customers what happened.

checkpoint

Token rejections with reason “signature” jump after a deploy. Likely cause?

A signing-key change: tokens signed with a key the APIs have not fetched, or the old key removed too early.

Why should log redaction live in the logging library and not in each service?

One missed service is enough to leak tokens, and a shared library is tested once and applies everywhere.

Testing it

Gist Write the drills as short tests: expiry with leeway, wrong audience, unknown key, refresh reuse with and without the grace period, sign-out, a new session id at sign-in, password change ending other devices, CSRF. Check the real cookie flags in a browser, and keep the provider's settings under review.

Sign-in code is usually tested on the happy path: sign in, see the page. The failures above are all about tokens and sessions in the wrong state, and each can be written as a short test.

refresh.test.tsdrill 1, as a test
test("a reused refresh token revokes the whole family", async () => {
  const { refresh: r1 } = await signIn("customer-7");
  const { refresh: r2 } = await refreshWith(r1);       // normal rotation

  await clock.advance("1m");
  await expect(refreshWith(r1)).rejects.toThrow("reuse");   // r1 again: theft
  await expect(refreshWith(r2)).rejects.toThrow("revoked"); // and r2 is dead too
});

Check the cookie, not just the code

A unit test can pass while the real response sends the cookie without HttpOnly, because a proxy or framework setting changed it. Add one end-to-end check that signs in through a real browser and reads the cookie's flags as the browser stored them. The same test can try a cross-site form post against the real stack and expect it to fail.

Test the provider's settings too

Much of this system is configuration at the identity provider: lifetimes, rotation, reuse detection, allowed redirect addresses. Export that configuration, keep it in the repository, and review changes to it like code. A refresh lifetime changed from 14 days to 14 months in a console, by one person on a Friday, is a security change with no pull request.

checkpoint

All unit tests pass, but the session cookie arrives without HttpOnly. How?

Something between the code and the browser changed it: a proxy or framework setting. Only a test through a real browser sees the cookie as stored.

Why export the identity provider's settings into the repository?

Lifetimes and rotation rules are security decisions. Kept as files, changes to them are reviewed like code.

Build or buy, a lab and the checklist

Gist Buy the provider and the client library; keep your session, CSRF defences, revocation checks and permissions, because only your code can do them. The lab adds “sign out of all devices” and admin removal within a minute, and the checklist turns the deep dive into review questions.

Lab

The shop adds two features. Customers get a “Sign out of all devices” button in their account settings. Staff get an admin area, and when a staff member's admin role is removed, it must stop working within one minute, and exports must stop at once.

  1. What happens, layer by layer, when “Sign out of all devices” is pressed on the laptop?
  2. What does the phone app see, and when?
  3. How do you meet “within one minute” for the admin role without checking the provider on every request?
  4. How do you meet “at once” for exports?
  5. A staff member is in the middle of a 40-minute export when the role is removed. What should happen?

model answer

1 · The button

The shop bumps customer 7's user version, revokes every refresh token the provider holds for that user, deletes the session rows for the other devices, and keeps the laptop's own session, re-issuing its tokens with the new version. Optionally it ends the provider sessions too, so no device can sign straight back in (drill 3).

2 · The phone

Its current access token carries the old version. Within 30 seconds, when the cache expires, the APIs reject it. The app tries to refresh, the refresh token is revoked, and it shows the sign-in screen. Worst case: about 30 seconds, not ten minutes.

3 · Within a minute

Removing the role bumps the staff member's user version. Every API already checks the version with a 30-second cache, so their tokens die within half a minute. New tokens are issued without the role.

4 · Exports at once

The export endpoint does not trust the token's role. It asks the permission store, live, at the moment the export starts. One extra lookup on a rare, dangerous action is cheap.

5 · The long export

The job checks the permission again between batches and stops when it fails, recording who started it, when it stopped and why. A long job that only checked at the start is the long-lived token problem in another shape.

The review checklist

Sessions

  • Every layer is listed with its lifetime: provider, shop, refresh, access
  • Sessions have idle and absolute expiry
  • Risky actions require a recent sign-in
  • A new session id at every sign-in and privilege change

Cookies and the browser

  • Session cookie is __Host-, Secure, HttpOnly, SameSite=Lax or Strict
  • The browser holds no tokens; the backend holds them
  • State-changing requests check a CSRF token or the Origin
  • No state changes on GET

Tokens

  • Access tokens live minutes and carry few claims, none personal
  • APIs check signature, issuer, audience, expiry, with the algorithm fixed
  • Refresh tokens rotate; reuse revokes the family; immediate repeats are forgiven
  • Signing keys rotate in steps, with both keys published for a while
  • Clocks are synced and checks allow a small leeway

Ending access

  • Sign-out deletes the session, revokes the refresh token and ends the provider session
  • A user version lets one update end every older token
  • Dangerous actions check permissions live
  • Password reset and email change end other sessions and notify the customer

The front door

  • Rate limits per account, per address and on the overall failure rate
  • Leaked passwords are refused; passkeys are offered
  • Unknown accounts get the same answer in the same time
  • Reset links are single-use, short-lived and stored hashed

Tests and operations

  • Tests cover expiry, audience, reuse, sign-out, fixation and CSRF
  • A real-browser test reads the cookie flags
  • Token rejections are graphed by reason
  • Credentials are redacted from logs, and tokens never appear in URLs
  • Provider settings are kept and reviewed in the repository
