chapter 1 · 1 min

Three notes in sixty seconds

Gist An index lets a query jump to its rows, batch loading replaces one query per row with one query per set, and keyset pagination keeps deep pages fast. Behind all three sits the planner, which chooses how to run each query from statistics. This deep dive is about that planner and the workload it serves.

The orders table has 10 million rows. Customer 42 opens “my orders”, which asks for their 20 newest orders. Without the right index the database reads all 10 million rows to find 312. Three notes from the data volume deal with making reads like this fast.

NoteIn one line
Indexinga sorted copy of some columns with pointers to the rows, so a query jumps instead of scanning
Batch Loading (Fixing N+1)fetch related rows in one query, not one query per row
Keyset Paginationask for rows after the last one shown, not for page 5,000
The indexing note's going-deeper chapter covers reading a plan in four lines and choosing column order. This dive starts there.

The notes teach the tools. This deep dive is about the system that uses them: a planner that decides from statistics, which can be wrong; a table that serves many queries at once, so indexes are chosen for a workload, not a query; and a plan that can change overnight with no deploy. The goal is to be able to answer the most common question in database work: “this was fast yesterday, why is it slow today?”

How the planner decides

Gist The planner estimates how many rows each step returns from sampled statistics, prices the page reads, and picks the cheapest plan. A full scan is right when a query wants a large share of the table. Plans go wrong when statistics are stale, columns are correlated, or costs are set for old disks.

SQL says what you want, never how to get it. For the “my orders” query the planner could read the whole table and sort, or walk an index on customer_id, or walk an index on placed_at backwards until it has found 20 rows for customer 42. It estimates the cost of each option and picks the cheapest.

Where the estimates come from

StatisticKept per columnUsed to guess
number of distinct valuesabout 9 million customers… or 4 statuseshow many rows = x matches
most common values and how commonDELIVERED 90 %, PENDING 0.1 %matches for frequent values
a histogram of the restplaced_at spread over five yearsmatches for ranges such as “last week”
correlation with physical orderplaced_at follows insert order closelywhether index reads are scattered or sequential
Statistics are a sample, refreshed by ANALYZE. Until then, the planner plans for the table as it was.

From these, the planner estimates how many rows each step returns, multiplies by the cost of reading pages, and adds up. The costs are in arbitrary units: reading a page in sequence costs 1, reading a page at random costs 4 by default.

When a full scan is the right answer

An index lookup reads a few index pages and then one table page per matching row, at random. A full scan reads every page, but in sequence. If a query wants a large share of the table, the scan wins.

Query matchesLikely planWhy
312 rows of 10 millionindex scana few hundred random reads beat 125,000 sequential ones
5 % of the tableit depends500,000 random reads is close to reading everything
40 % of the tablefull scanthe index would visit most pages anyway, out of order

“The planner ignored my index” is often the planner being right. Check the actual row count before arguing with it.

Three ways the guesses go wrong

CauseExampleFix
stale statistics2 million rows loaded an hour ago; the planner thinks the table is small (drill 3)ANALYZE after bulk loads
correlated columnscity = 'Rotterdam' AND country = 'NL': the planner multiplies two probabilities as if unrelated and expects 50 times too few rowsextended statistics: CREATE STATISTICS … (dependencies)
costs set for old disksrandom reads priced at 4 on an SSD where they cost about the same as sequential oneslower random_page_cost to about 1.1 on SSDs

The third row is worth checking on every database you run. With the default setting on fast storage, the planner will prefer full scans in many places where an index would be quicker.

Asking for the plan safely

EXPLAIN on its own shows the plan the planner would choose and its estimates, without running anything. EXPLAIN ANALYZE runs the query and adds what really happened, which is what you need to compare estimates with reality. Two cautions. It really runs: an UPDATE or DELETE under EXPLAIN ANALYZE changes data, so wrap it in a transaction and roll back. And it runs with the values you typed; to see the plan the application gets, use the same parameter values, and for prepared statements, the same way of sending them (drill 4).

checkpoint

A query matches 40 % of the table and uses a full scan. Is the planner wrong?

Probably not. Reading every page in order is cheaper than visiting most of them at random through an index.

Why lower random_page_cost on SSDs?

The default assumes random reads cost four times sequential ones, which is true for spinning disks. On SSDs it makes the planner avoid indexes it should use.

Reading a real plan

Gist Read EXPLAIN ANALYZE from the most indented line up. Look at the scan type, rows removed by filter, estimated against actual rows, any Sort node and the pages read. In joins, figures on an inner line are per loop. Compare plans by pages read, not milliseconds.

The page also shows each order's lines. The join adds a node with two children, and a new number to watch: loops.

The inner scan ran 20 times, once for each order, returning about 2 rows each time. The figures on a looped line are per loop: multiply by loops for the total. A nested loop with loops=200000 and a slow inner side is the most common shape of a join gone wrong.

Join methodHowGood when
Nested loopfor each outer row, look up matching inner rowsthe outer side is small and the inner side has an index on the join column
Hash joinbuild a hash table of one side, stream the other through itboth sides are large, equality join, no useful order
Merge joinwalk two inputs already sorted on the join keyboth sides come sorted, often from indexes

None is good or bad by itself. A nested loop is perfect for 20 orders and a disaster for 2 million, which is what happens when the planner expected 20 (drill 3).

Two more scan types

ScanWhat it doesWhen you see it
Bitmap Index Scan + Bitmap Heap Scancollects every matching row's position from the index first, sorts them by page, then reads each table page oncemedium result sizes, or when two indexes are combined with AND or OR
Index Only Scananswers from the index without visiting the tableevery column the query needs is in the index, and the table is recently vacuumed

An Index Only Scan line also reports Heap Fetches: rows it had to check in the table after all, because the page was not yet marked as fully visible. A high number there means vacuum is behind, and the index-only scan is quietly doing the table reads it was meant to avoid.

checkpoint

Estimated rows 200, actual 2,000,000, nested loop. What happened, and the first step?

The planner expected few rows and chose a per-row lookup. Run ANALYZE and check the estimate again.

An inner Index Scan shows rows=2 loops=20. How many rows did it return in total?

40: the figures are per loop.

chapter 4 · 5 min

Failure drills

Gist Six queries that used to be fast: a function on an indexed column, a parameter of the wrong type, statistics that lag behind a bulk load, a generic plan for a skewed value, a page that makes sixty-one queries, and a table so heavily indexed that every write is slow.

Each of these is a query that “used to be fast”. Guess the cause before reading it.
  • 1 · lower()
  • 2 · wrong type
  • 3 · after the import
  • 4 · the rare status
  • 5 · 61 queries
  • 6 · fourteen indexes
Drill 1

The index on email that never gets used

Timeline
Sign-in looks up WHERE lower(email) = lower($1), so that capital letters do not matter. There is an index on email. The plan is a full scan of 9 million customers.
Why
The index is sorted by email, not by lower(email). A function on the column means the database must compute it for every row before comparing.
What saves you
Index the expression the query uses: CREATE INDEX ON customers (lower(email)). Or store emails lowercase in the first place, or use a case-insensitive type. The same applies to date(placed_at), col + 1 and anything else that wraps the column.

Rule: an index helps only when the query compares the indexed value itself. Wrap the column, lose the index.

Drill 2

The id that arrived as the wrong type

Timeline
After an ORM upgrade, order lookups by customer go from 1 ms to 2 seconds. The SQL text looks the same. The plan shows Filter: ((customer_id)::numeric = '42'::numeric).
Why
The new driver sends the parameter as a decimal number. To compare a whole-number column with a decimal, the database converts the column, on every row, which is drill 1 in disguise.
What saves you
Make parameter types match column types: declare them in the query or the mapping. Read the plan's filter line after any driver or ORM upgrade: a :: cast on the column side is the sign. MySQL has the same trap with text columns compared to numbers.

Rule: a type mismatch converts the column, and a converted column cannot use its index.

Drill 3

The plan changed after the nightly import

Timeline
At 02:00 a job loads 2 million order lines from a partner. At 02:05 the reconciliation report starts. Yesterday it took 40 seconds. Today it is still running at 06:00.
What you see
The plan expects 200 rows from the new lines and chooses a nested loop with an index lookup per row. There are 2 million. Statistics are from yesterday, because the automatic analyse had not run yet.
What saves you
Run ANALYZE at the end of every bulk load, as part of the job. Log the plans of slow queries automatically (chapter 8), so a plan change is visible the next morning, not in a 4-hour incident.

Rule: after a bulk change, refresh the statistics before anything queries the new data.

Drill 4

Fast for one status, slow for another

Timeline
The warehouse screen runs WHERE status = $1 ORDER BY placed_at, as a prepared statement. For PENDING, 0.1 % of rows, it is instant. After a few calls it becomes slow for PENDING too.
Why
After five executions PostgreSQL may switch a prepared statement to a generic plan, one made without looking at the value. That plan is chosen for an average status, which is DELIVERED at 90 %: a full scan.
What saves you
Give the rare value its own index and query: a partial index ON orders (placed_at) WHERE status = 'PENDING' serves the warehouse screen exactly and stays tiny. Where a value-dependent plan is essential, the statement can be told to plan for each value (plan_cache_mode).

Rule: skewed data needs value-aware plans. Rare values deserve their own partial index.

Drill 5

Sixty-one queries for one page

Timeline
The order history page shows 20 orders, each with its lines and each line's product name. Every query is under a millisecond. The page takes 900 ms.
What you see
One query for the orders, 20 for the lines, 40 for the products: 61 round trips. Each is fast; the waiting between them is not. With a slow network to the database it is 3 seconds.
What saves you
Batch loading, from the note: one query for the orders, one for all their lines (WHERE order_id = ANY($1)), one for all their products. Three round trips, whatever the page size. Add a test that counts queries per request (chapter 9), because N+1 returns every time someone adds a field.

Rule: count queries per request. A page should make a fixed number, not one per row.

Drill 6

Fourteen indexes on one table

Timeline
Over three years each new screen added an index to orders. There are now fourteen. Checkout has slowed down by 40 %, and the write-ahead log has tripled.
Why
Every insert writes the row and fourteen index entries. Every update to an indexed column, and updated_at is indexed, writes new entries in every index, because PostgreSQL can only skip index updates when no indexed column changed.
What saves you
Find indexes that are never used and drop them: nine of the fourteen had no scans in a month, on the leader and on every replica. Merge indexes that share leading columns. Do not index columns that change on every update unless a frequent query needs them.

Rule: every index is paid for on every write. Keep only the ones a real query uses.

The plan shows Filter: ((customer_id)::numeric = 42). Why is the index unused?

Indexing a workload: the hard problem

Gist Rank queries by total time, then find the smallest set of indexes that serves the important ones: shared leading columns let one index serve several queries, partial indexes serve rare subsets cheaply, and reports go elsewhere. Drop indexes nobody uses, after checking every replica.

Indexing one query is easy: put its equality columns first, then its sort, then its ranges. The hard problem is that a table serves many queries, every index costs every write, and the best set is the smallest one that serves the queries that matter.

Start from where the time goes

Rank queries by total time, calls × average time. A 2-second report run twice a day matters less than a 4 ms query run 3,000 times a second.

Three questions for every new index: which query, how often, and which existing index could serve it instead?

Shapes worth knowing

ShapeExampleUse when
composite(customer_id, placed_at)queries filter on one column and sort or range on another
covering(customer_id, placed_at) INCLUDE (total, status)a hot query needs a few extra columns; the database answers from the index alone (Index Only Scan)
partial… WHERE status = 'PENDING'queries always target a small, well-defined subset
expression(lower(email))queries compare a computed value (drill 1)
GINon a JSONB column or a text search vectorqueries look inside documents, arrays or words
BRINon placed_at of a huge append-only tablerows are stored roughly in the column's order; tiny, but coarse

One composite index or two single ones?

With separate indexes on customer_id and on placed_at, the planner can combine them with a bitmap AND. It works, but it has to read every entry for customer 42 and every entry in the date range, intersect them, and then sort, because a bitmap loses the index order. The composite index (customer_id, placed_at DESC) walks straight to customer 42's newest orders and stops after 20. Combining single-column indexes is a reasonable fallback for rare ad-hoc filters, such as an admin screen with ten optional fields. For the queries that carry the product, give them the composite index they need.

Finding what to drop

unused-indexes.sqlnever scanned since statistics were last reset
SELECT relname AS table_name, indexrelname AS index_name, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Three cautions before dropping anything. The counts are per server, so check every replica: a report may use an index only there. Unique indexes enforce a rule even if no query ever scans them. And a monthly job will look unused if statistics were reset two weeks ago. When in doubt, mark the index invisible first where the database supports it, or drop it in a quiet week with its CREATE statement at hand.

checkpoint

A 40-second monthly report and a 4 ms query run 900 times a second. Which matters more?

The 4 ms query: about 3.6 seconds of database time every second, against 40 seconds a month.

An index shows zero scans on the leader. Why not drop it at once?

A replica may use it, it may enforce uniqueness, or a monthly job may need it since statistics were last reset.

Indexes in numbers

Gist A B-tree on 10 million rows is three levels deep, so a lookup reads three index pages and then one page per row. Depth grows very slowly with size. Every index adds a write to every insert and competes for memory. Keyset pages read the same 20 rows however deep you go.

A few numbers make index behaviour predictable instead of mysterious.

QuantityReasoningValue
entries per index page8 KB page, about 30 bytes per entry for two columns and a pointerabout 250
levels for 10 million rows250 × 250 = 62,500 leaves can hold 15 million entries3
levels for 10 billion rows250 × 250 × 250 × 2505
index size10 million × 30 bytes, plus room in pagesabout 400 MB
table size10 million rows × about 100 bytesabout 1 GB, 125,000 pages
full scan125,000 pages, sequential1–2 s from disk
index lookup for 20 rows3 index pages + 20 table pagesunder 1 ms, mostly from memory
Depth grows with the logarithm: a thousand times more rows adds two levels. That is why indexes keep working as tables grow.

An export that walks all 500,000 orders of a big customer with OFFSET reads 6 billion rows in total; with keyset it reads 500,000. The keyset pagination note explains the query; the index from chapter 5, with id added as a final tie-breaker, makes it work.

checkpoint

Roughly how many levels for 10 billion rows?

About five, with around 250 entries per page.

Why does an export with OFFSET get slower page by page?

Each page re-reads every row before it, so the work grows with the page number; keyset reads only the page itself.

chapter 7 · 3 min

Batching, paging and asking less

Gist Load related rows in one query per set, page by the last key shown with a unique tie-breaker, select only the columns you show, and avoid exact counts on big lists. Put equality columns before the range in an index, because a range ends the useful part.

Many slow pages are not one bad query but a bad pattern of queries. Three patterns account for most of them.

1 · Batch the related rows

order-history.tsthree queries, whatever the page size
const orders = await db.many(
  `SELECT id, placed_at, total FROM orders
   WHERE customer_id = $1 ORDER BY placed_at DESC, id DESC LIMIT 20`, [customerId]);

const lines = await db.many(
  `SELECT order_id, product_id, qty FROM order_lines WHERE order_id = ANY($1)`,
  [orders.map((o) => o.id)]);

const products = await db.many(
  `SELECT id, name FROM products WHERE id = ANY($1)`,
  [[...new Set(lines.map((l) => l.product_id))]]);

Each ANY query needs an index on the column it looks up: order_lines(order_id) and the primary key of products. A JOIN would also work; the point is the fixed number of round trips. ORMs offer the same thing as eager loading, and GraphQL servers as a DataLoader.

2 · Page by key

next-page.sqlkeyset: the last row shown is the bookmark
SELECT id, placed_at, total
FROM orders
WHERE customer_id = $1
  AND (placed_at, id) < ($2, $3)      -- the last row of the previous page
ORDER BY placed_at DESC, id DESC
LIMIT 20;
-- served by an index on (customer_id, placed_at DESC, id DESC)
The index order must match the ORDER BY exactly, tie-breaker included, or the database sorts again.

3 · Ask only for what you show

HabitWhy it matters for plans
select named columns, not *a covering index can answer the query alone; * always visits the table
avoid exact count(*) on big listscounting 2 million rows reads them all; show “more than 1,000” or an estimate
filter in SQL, not in codefetching 10,000 rows to keep 20 moves the full scan into your application
one query per screen region, not per itemthe same rule as batch loading, applied to the whole page

OR, IN and optional filters

Search screens with optional fields tend to produce one query with many ORs: (status = $1 OR $1 IS NULL) AND (placed_at > $2 OR $2 IS NULL). It looks tidy and plans badly, because the planner must choose one plan that works whether or not each filter is set, and that is usually a full scan. Build the WHERE clause from the filters actually given, so each combination gets its own plan. A list of values, status = ANY($1), is fine: an index handles it as several lookups.

Ranges and the column order

The indexing note's rule, equality columns first, then sort, then ranges, has one consequence that surprises people. In an index on (customer_id, placed_at, status), a query with a range on placed_at can only filter by status, not jump to it: the range ends the useful part. If status is often an equality condition, put it before the range: (customer_id, status, placed_at).

checkpoint

Why does SELECT * prevent an index-only scan?

The index holds only some columns, so the database must visit the table for the rest.

Index (customer_id, placed_at, status), query with a range on placed_at and status = 'PENDING'. What happens to status?

It can only be filtered row by row; the range on placed_at ends the part of the index that can be searched.

Running it: watching plans change

Gist Keep pg_stat_statements on and review the top queries by total time. Log the plans of slow queries automatically. Watch rows read per row returned and calls per request. When a query slows overnight, compare plans, refresh statistics, then look for casts, functions and generic plans.

Plans change without deploys: data grows, statistics refresh, values shift. Running a database well means seeing those changes before customers do.

ToolShowsSetting for the shop
pg_stat_statementsevery query shape with calls, total time, rows and pagesalways on; review the top 10 by total time weekly
auto_explainthe actual plan of any query slower than a threshold, in the loglog plans slower than 500 ms, with timing for a sample
slow query logthe text of slow querieson, at 500 ms
pg_stat_user_tablessequential scans per table, last analyse timealert on a table with many large scans that used to have none
Rank by total time, not by slowest. The worst query is usually a fast one called very often.

Graphs per query shape

GraphMeans trouble when
slow-case response timeit jumps on a day without a deploy: a plan changed
rows read per row returnedit climbs: the query is filtering more and more; an index stopped fitting
calls per requestit grows with page size: N+1
pages read from disk, not memoryit rises for an index-heavy query: the working set no longer fits in memory

Runbook: “this query was fast yesterday”

  1. Get today's plan from auto_explain, and yesterday's if you logged it. Compare the bottom nodes and the estimated against actual rows.
  2. Estimates far off? Run ANALYZE on the tables involved and look again (drill 3). If they are still off, look for correlated columns.
  3. Estimates fine, plan still bad? Look for a cast on a column (drill 2), a function on a column (drill 1), or a generic plan for a skewed value (drill 4).
  4. Same plan, more time? More data, or less memory: compare pages read from disk. The fix is usually an index that fits, or partitioning old rows away (the Sharding & Partitioning dive).
  5. Did an index disappear? Check recent migrations. A dropped “unused” index that a monthly job needed shows up exactly like this.

Does the working set fit in memory?

An index lookup of three pages is fast when those pages are in memory and much slower when each is a disk read. The pages that matter are the hot ones: the upper levels of every index (always in memory, they are small) and the leaves and table pages for recent data. Watch the share of pages served from memory per query shape. When it falls for an index-heavy query, the hot data has outgrown memory: more memory, fewer or smaller indexes, or partitioning old rows away will help; a new index will not.

Changing indexes on a live table

Build indexes with CREATE INDEX CONCURRENTLY so writes continue, give the statement a lock timeout, and check afterwards that it finished valid. The Zero-Downtime Change dive has the details; the short version is that an ordinary CREATE INDEX on a busy table blocks every write until it is done.

checkpoint

Rows read per row returned for a query climbs from 1 to 400 over a month. What does it suggest?

The query increasingly filters instead of seeking: an index no longer fits the query, or the data shifted under it.

Why build indexes CONCURRENTLY on live tables?

An ordinary CREATE INDEX blocks writes to the table until it finishes.

Testing query performance

Gist Assert a maximum number of queries per request to stop N+1. Check the plans of key queries on seeded data with realistic volume and skew. Lint migrations for unsafe or excessive indexes, try indexes hypothetically before building them, and keep expected plans for core queries in the repository.

Query performance is hard to test because it depends on data size and shape, which test databases rarely have. A few kinds of test still catch most regressions.

order-history.test.tstwo guards in one test
test("order history: fixed query count, uses the index", async () => {
  const counter = db.countQueries();
  await request(app).get("/customers/42/orders").expect(200);
  expect(counter.total()).toBeLessThanOrEqual(3);            // orders, lines, products

  const plan = await db.explain(
    "SELECT id FROM orders WHERE customer_id = 42 ORDER BY placed_at DESC, id DESC LIMIT 20");
  expect(plan).toContain("Index Scan using orders_customer_placed");
  expect(plan).not.toContain("Seq Scan on orders");
});

The plan check only means something on a table big enough that the planner would choose differently. A few hundred thousand rows with a realistic spread usually suffice; the seed script is worth more than any individual test, because every query test uses it.

Seed data with the right shape

Real shapeSeed it as
most customers have a few orders, a few have thousandsorder counts drawn from a long-tailed distribution, plus a handful of giant customers
90 % of orders are DELIVERED, 0.1 % PENDINGthe same proportions, not one row of each
five years of history, most reads on the last monthdates spread over five years, with recent months fuller
emails with mixed case, product names in many languagesreal-looking text, so expression indexes and collations are exercised

Review plans like code

For the few queries that carry the product, keep their expected plan shape in the repository next to the query: which index, which join method, roughly how many pages. When a change makes the plan test fail, the pull request shows the old and new plans side by side, and a person decides whether the new one is better. That turns “the database got slow” from a mystery into a diff.

checkpoint

Why does a plan test on a 1,000-row table prove little?

At that size the planner may scan everything whatever the indexes are; plans only match production on realistic volume and skew.

What does a query-count test catch that a plan test does not?

N+1: each query has a good plan, but the page makes one per row.

Lab

Support gets a new screen: find orders by customer email, optionally by status, within a date range, newest first, 50 per page. Most searches cover the last 30 days. PENDING is 0.1 % of orders; DELIVERED is 90 %.

  1. Emails are stored as typed by customers. How does the search find the customer?
  2. Which index serves “this customer's orders in a date range, newest first”? Can an existing one be reused?
  3. “All PENDING orders this week” with no customer: what serves it?
  4. How is paging done, and what index does it need?
  5. Support also wants “total orders found”. What do you show?

model answer

1 · The email

An expression index on lower(email) in customers, and the query compares lower(email) = lower($1) (drill 1). That gives the customer id in one index lookup.

2 · Date range

The existing (customer_id, placed_at DESC) already serves it: equality on the customer, then a range and sort on the date. Adding id DESC at the end makes it serve keyset paging too. No new index.

3 · Pending this week

The partial index (placed_at) WHERE status = 'PENDING' from chapter 5. It is tiny, and the query is a short range scan of it. A filter on DELIVERED without a customer would match most of the table and should be refused or sent to the warehouse.

4 · Paging

Keyset on (placed_at, id), with the index ordered the same way, tie-breaker included. No OFFSET: support staff do page deep into busy customers.

5 · The total

An exact count can read millions of rows. Count up to 1,000 with a limited subquery and show “1,000 or more”, or show the planner's estimate labelled as approximate.

The review checklist

Finding the work

  • pg_stat_statements is on and reviewed by total time
  • Slow plans are logged automatically with auto_explain
  • Every index has a named query it serves

Designing indexes

  • Equality columns first, then sort, then range
  • One index serves several queries where they share leading columns
  • Rare values use partial indexes; computed comparisons use expression indexes
  • Hot queries that need a few extra columns use covering indexes
  • Frequently updated columns are indexed only when needed

Queries

  • No functions or casts on indexed columns in WHERE
  • Parameter types match column types
  • Pages make a fixed number of queries; related rows are batched
  • Lists page by key with a unique tie-breaker, never deep OFFSET
  • Big counts are capped or estimated

Statistics and plans

  • ANALYZE runs after every bulk load
  • random_page_cost suits the storage
  • Correlated columns have extended statistics
  • Skewed values are checked against generic plans

Change and cleanup

  • Indexes are built concurrently, with a lock timeout
  • Unused indexes are checked on every replica before dropping
  • Index count on hot tables is reviewed in migration lint

Tests

  • Request tests assert a maximum query count
  • Key queries are plan-checked on realistic, skewed data
  • Expected plans for core queries are kept in the repository
