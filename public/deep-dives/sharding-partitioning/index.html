Read first: ShardingTable Partitioning

chapter 1 · 1 min

Two notes in sixty seconds

Gist Partitioning splits one big table into smaller tables inside one database. Sharding splits data across many databases by a key. They solve different problems and are often used together. Sharding is the step that is hardest to undo, so it comes last.

The shop did well. The orders database is 4 TB, grows 300 GB a month, and takes 40,000 writes a second at the evening peak. Next to it, a table of order events holds two billion rows from five years. Two notes cover the two tools for this.

NoteIn one lineWhere it happens
Table Partitioningsplit one big table into smaller tables behind one name, usually by monthinside one database
Shardingsplit the data across many databases by a key, and route each query to the right oneacross many databases
The sharding note has a going-deeper chapter on moving shards, hot keys and cross-shard queries. This dive builds on it.

The two words are often used as if they were one idea. They are not. Partitioning reorganises a table inside one database and is mostly invisible to the application. Sharding splits the data across machines and changes how almost every query, transaction and unique id works. This deep dive covers when each is worth it, the one decision that sharding hangs on, and what running a sharded system is like on an ordinary Tuesday.

chapter 2 · 3 min

Partition first

Gist Partitioning a huge table by month lets queries read only recent partitions, lets old data leave in a second, and keeps maintenance small. Every query should filter on the partition key, unique constraints must include it, and partitions must exist before their rows arrive.

Start inside one database. The events table is slow because it is huge, not because the machine is too small. Partitioning by month turns one two-billion-row table into sixty tables of about 33 million rows each, behind the same name.

order-events.sqlone parent, one partition per month
CREATE TABLE order_events (
  order_id   BIGINT      NOT NULL,
  at         TIMESTAMPTZ NOT NULL,
  type       TEXT        NOT NULL,
  data       JSONB,
  PRIMARY KEY (order_id, at)              -- must include the partition key
) PARTITION BY RANGE (at);

CREATE TABLE order_events_2026_11 PARTITION OF order_events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
What you gainWhy
queries for recent data read only recent partitionsthe planner skips partitions that cannot match the WHERE (pruning)
old data leaves in a secondDROP or DETACH a partition instead of deleting a billion rows
maintenance in small piecesvacuum, reindex and backup work per partition
indexes that fit in memoryeach partition's index is small, and the hot ones are recent
Partitioning makes big tables manageable. It does not make one machine bigger.

The rules that bite

RuleConsequence
every query should filter on the partition keyWHERE order_id = 42 with no date checks all sixty partitions
primary keys and unique constraints must include the partition keyyou cannot enforce “one event id is unique” across the whole table by itself
partitions must exist before rows arrivea job creates next month's partition ahead of time (drill 6)
a default partition catches rows with no homeuseful as a safety net; but once it holds rows for a month, creating that month's partition has to move them
thousands of partitions slow down planningkeep partitions large: tens of GB, or one per month

Choosing the partition key

Choose the column that nearly every query filters on, and by which old data leaves. For events, logs and metrics that is time, and the partitions are months. For data that is kept for ever and read by owner, partitioning by a hash of the owner spreads maintenance but rarely speeds up queries. If no single column appears in most queries, partitioning will make reads slower, not faster.

Partitioning is also a good rehearsal for sharding. The same questions come up: which key, what happens to queries without it, what happens to unique constraints. They are much cheaper to answer inside one database.

Partitioning a table that already exists

The events table already holds two billion rows, and a table cannot be turned into a partitioned one in place. There is a gentle route that needs no big copy.

  1. Create the new partitioned parent with a new name, and partitions for this month and the next three.
  2. Attach the whole old table to it as one partition, covering everything up to today. Add the matching CHECK constraint first, validated separately, so attaching it does not scan two billion rows under a lock.
  3. Swap the names in one short transaction. New rows now land in monthly partitions; old rows stay in the one big partition.
  4. Leave the big partition alone until it ages out, or move one month at a time into proper partitions during quiet hours.

It is the expand-and-contract idea again: a new shape beside the old one, then a switch that takes a second.

checkpoint

A query on the partitioned events table filters only by order id. What happens?

It checks every partition, because nothing in the WHERE clause lets the planner skip any.

Why can't a partitioned table enforce that an event id alone is unique?

Unique constraints are enforced per partition, so they must include the partition key.

chapter 3 · 2 min

Before you shard

Gist Shard for writes or storage that one machine will not handle, measured and projected. Reads, huge tables and slow backups have cheaper fixes: indexes, caching, read copies, partitioning, archiving, or giving one part of the product its own database.

Sharding is the step at the top of the ladder because it is the hardest to undo. Before taking it, be sure what problem you are solving, and that a cheaper step does not solve it.

SymptomTry firstShard when
reads are slowindexes (deep dive 10), a cache, read copiesrarely: reads alone almost never need sharding
the table is huge, queries on recent data are slowpartitioning, archiving old rowsnever for this alone
writes are at the limit of one primarybatching, fewer indexes, a larger machinethe largest sensible machine is still not enough
storage grows faster than one machine can holdmove cold data to cheaper storageeven the hot data will not fit in a year
backups and restores take too longincremental backups, partitioned maintenancea restore of the whole database is longer than you can be down
one part of the product dominatessplit that part into its own service with its own databasethat part on its own still outgrows one machine
Splitting by function, orders here and payments there, is often the cheapest “sharding” of all.

For the shop, two rows are tinted, and the numbers decide. The orders database grows 300 GB a month; in two years it will be 11 TB. Peak writes are 40,000 a second and rising; tested on the largest machine the team will run, one primary sustains about 10,000 with all its indexes. Both say the same thing: one database will not be enough, and partitioning will not change that.

What sharding costs, said out loud

  • Every query must know its shard key, or ask every shard.
  • Every transaction must fit in one shard, or become a saga.
  • Every unique id and constraint must be designed to work across shards.
  • Every operational task, from backups to migrations, now runs on many databases.
  • Every engineer must learn where the line between shards is.

None of these is a reason not to shard. All of them are reasons to shard once, with a key chosen carefully, and not to start before the numbers say so.

checkpoint

Reads are slow and the CPU is busy with reporting queries. Shard?

No. Move reports to a read copy or warehouse, and fix the indexes.

What is the cheapest kind of split, often overlooked?

By function: giving one part of the product, such as payments, its own database.

chapter 4 · 3 min

The shard key: the hard problem

Gist The shard key decides which queries are cheap, which transactions are possible and where load lands, and it is very costly to change. It should appear in most queries, group rows that change together, have many values, spread today's writes and never change. Ids must be designed to work across shards.

The shard key decides which queries are cheap, which transactions are possible, and where the load lands. It is also the hardest decision to change later, because changing it means moving every row. A good key has five properties.

PropertyQuestionWhy
In most queriesdo the common queries say which key they want?a query without the key asks every shard
Groups what changes togetherdo the rows one transaction touches share the key?a transaction can only be atomic inside one shard
Many valuesare there far more key values than shards?few values cannot be spread evenly
Even loadis any one value much busier than the rest?one busy value makes one hot shard
Never changescan a row's key be updated?a changed key means moving the row to another shard

Candidates for the shop's orders

KeyIn most queriesGroups changesEvenVerdict
customer idyes: order history, checkout, accountyes: a customer's orders, basket, addressesmostly; a few big business customerschosen
order idonly lookups by idno: the customer's other data is elsewhereyesspreads well, groups nothing
countryoftenpartlyno: one country is most of the traffictoo few values
order datefor reportsnono: all writes go to today's sharda hot shard by design (drill 1)
A shard key is chosen for the writes and the common reads. Everything else is answered another way (chapter 8).

Ids that know their shard

Sharding by customer creates a new problem: a request arrives with only an order id. Which shard holds order 7713? Two answers work.

ApproachHowCost
a lookup tablea small global table: order id → customer idone extra read for every lookup by order id; one more system
put the shard in the idthe order id is made with the customer's logical shard inside itids must be generated by your code, not a database sequence
order-id.ts64-bit ids that carry their logical shard
// 41 bits of milliseconds since 2024 · 10 bits of logical shard (0-1023) · 12 bits of counter
export function newOrderId(customerId: bigint, now = Date.now()): bigint {
  const shard = logicalShard(customerId);                 // hash(customerId) % 1024
  return (BigInt(now - EPOCH_2024) << 22n) | (BigInt(shard) << 12n) | nextCounter();
}

export const shardOfOrder = (orderId: bigint) => Number((orderId >> 12n) & 1023n);

Ids made this way also sort roughly by time, which keeps index inserts near the end of the index, and they never collide across shards, which a sequence in each database would. Database sequences are the first thing that breaks when a team shards without planning.

When no single key fits

Sometimes two access paths are equally important and want different keys. A messaging feature is read by conversation and also listed per user. A ride-sharing trip belongs to a rider and to a driver. Three honest options exist.

  • Pick the path that writes, shard by its key, and serve the other path from a second copy filled from events (chapter 8). Writes stay atomic; the second path lags by seconds.
  • Use a composite key for very large owners: customer id for most customers, customer and branch for the café chain. The router needs to know which customers are split, which the shard map can record.
  • Store it twice on purpose, once per key, written by a saga. This is the most work and the right answer only when both paths must be fast and current.

What does not work is choosing a key that serves neither path well as a compromise. A key is either in the query or it is not.

checkpoint

Why is order date a poor shard key and a good partition key?

As a shard key it sends every current write to one shard. As a partition key inside one database it only decides which table rows land in, and lets old months be dropped.

A request arrives with only an order id. Name two ways to find its shard.

A lookup table from order id to customer id, or an order id that carries its logical shard in some of its bits.

chapter 5 · 5 min

Failure drills

Gist Six ways sharded and partitioned systems hurt: a key that sends today's writes to one shard, one customer bigger than a shard, a search that asks every shard, a change that crosses two shards, writes lost during a shard move, and a missing partition at midnight on the 1st.

Each of these is cheap to avoid before sharding and expensive after.
  • 1 · today's shard
  • 2 · the giant
  • 3 · the fan-out
  • 4 · two shards, one change
  • 5 · the move
  • 6 · the 1st of the month
Drill 1

Every write goes to one shard

Timeline
A team shards its events by date range: one shard per quarter. It looks tidy. Every new event is from today, so every write goes to the current quarter's shard. The other eleven sit idle.
What you see
One shard at 100 % CPU, the rest under 5 %. Sharding has added complexity and removed no load.
What saves you
Never shard by a value that moves with time. Shard by something with many values that are written in parallel, such as a customer id, hashed. Inside each shard, partition by month if you also want old data to leave cheaply. Time is a fine partition key and a poor shard key.

Rule: a shard key must spread today's writes, not just the total.

Drill 2

One customer bigger than a shard

Timeline
A café chain signs up as a business customer and orders for 900 branches through one account. Its orders, all under one customer id, are 8 % of all writes. With 32 shards, its shard carries three times the load of the others.
What you see
One shard always behind, its replicas lagging, and every other customer who happens to hash to it suffers. Moving shards does not help: one key cannot be split across shards.
What saves you
Measure load per key, not just per shard, so a giant is seen early. Then give it its own place: route that customer to a dedicated shard through the shard map. If even that is not enough, make the key more precise for that customer only, for example customer and branch.

Rule: averages hide giants. Watch the busiest keys, and give a giant its own shard.

Drill 3

The search that asked every shard

Timeline
Support's “find orders by email address” screen does not know the customer id, so it asks all 32 shards and merges the results. At first it is used a few times an hour. Then a fraud tool starts calling it 50 times a second.
What you see
Every shard does 50 extra queries a second, and the search's response time is the slowest of 32 shards, so it is often slow even when the shards are fine. One feature has put load on the entire fleet.
What saves you
Treat a query without the shard key as an exception that needs a design. Keep a small lookup table from email to customer id, sharded by email, and the search becomes two single-shard lookups. Count fan-out queries in a metric and review every new one.

Rule: a query without the shard key costs every shard. Give common ones a lookup of their own.

Drill 4

One change across two shards

Timeline
Two customer accounts are merged after a duplicate sign-up. The code moves orders from customer A, on shard 5, to customer B, on shard 19: insert on 19, then delete on 5. The process is restarted between the two.
What you see
Orders that exist under both customers. There is no transaction that covers two databases, so nothing rolled the first step back.
What saves you
Accept that a change across shards is not atomic and design it as a saga: each step idempotent, recorded, and resumable or reversible (the Saga deep dive). Better still, make such changes rare by choosing a key that keeps related rows together.

Rule: atomicity ends at the shard boundary. Anything that crosses it is a saga.

Drill 5

Writes lost during a shard move

Timeline
Logical shard 371 is moved to a new machine. The copy has caught up, the map is switched, and the old copy is deleted. But some app servers cached the old map for a minute and kept writing to the old machine after the switch.
What you see
A few hundred orders written to a database that was then deleted. Customers were charged; the orders are gone.
What saves you
Make the switch impossible to miss. Pause writes to the moving shard, let the copy catch up, change the map and bump its version, and have the old copy refuse writes for that shard from then on. Every write carries the map version it was routed with, so a stale router gets an error and fetches the new map instead of writing to the wrong place. Keep the old copy for days, not minutes.

Rule: a shard move ends when the old copy refuses writes, not when the map changes.

Drill 6

Midnight on the 1st

Timeline
The job that creates next month's event partition failed quietly in October. At 00:00 on 1 November, every insert into order_events fails: there is no partition for November.
What you see
Checkout fails at midnight, because placing an order writes an event. The fix takes a minute; finding it takes forty, in the middle of the night.
What saves you
Create partitions well ahead: three months, not one. Alert when fewer than two future partitions exist. A default partition prevents the outage, but rows that land there must be moved before the real partition can be created, so it is a safety net with its own runbook, not a fix.

Rule: partitions are created months ahead, and an alert counts them.

checkpoint

Shard load is even on average but one shard is always behind. What do you look at first?

The busiest keys on that shard: one giant key is the usual cause, and moving shards will not fix it.

What makes a shard move safe from routers with an old map?

The old machine refuses writes for the moved shard, and every write carries its map version so a stale router is told to reload.

Routing and the shard map

Gist Hash keys into a large fixed number of logical shards, and keep a small, versioned map from logical shards to machines. Routing can live in the app, in a proxy or in the database. Moves copy, catch up, pause briefly, switch the map and fence the old copy, one logical shard at a time.

The sharding note's going-deeper chapter introduced logical shards: hash every key into a large fixed number of slots, and keep a small map from slots to machines. This chapter is about living with that map.

Where the router livesHowGood for
a library in the appevery app instance holds the map and connects to shards directlyfew services, one language, full control
a proxythe app talks to one endpoint; the proxy routes (Vitess, Citus coordinator, ProxySQL)many services and languages; the app looks unsharded
the database itselfa distributed database splits and moves ranges by itselfteams that would rather not build any of this
The map is tiny and read constantly. Cache it everywhere, and give it a version so a stale copy is detected.

The map is critical state

Every request depends on it, so it is stored in a consistent store (a consensus store, or a table that only an admin tool writes), cached by every router, and checked by version. A router that sends a write with map version 17 to a shard that knows version 18 gets a clear error and reloads. That one check is what drill 5 was missing.

A move, with the checks that make it safe

#StepCheck before the next step
1copy the logical shard's rows to the new machinerow counts match for that shard
2stream later changes until the copy is seconds behindlag under a few seconds, steady
3pause writes for that logical shard onlyno writes in flight
4wait for the copy to catch up completelylag zero; a checksum of the rows matches
5update the map, version + 1; old machine refuses that shardrouters report the new version
6resume writes; keep the old copy for a weekno errors on the moved shard

The pause in step 3 lasts a second or two and affects about 1/1,024 of customers. Moving in many small pieces is what makes resharding routine instead of a weekend project.

The first split is the hard one

Moving a logical shard between two shards is routine once the router exists. Going from one database to many for the first time is the risky project, and it is much safer done in phases, months apart.

PhaseWhat changesWhat it proves
1 · shard-aware, one shardthe router, the map and the new ids go live; every logical shard maps to the existing databaseevery query carries its key; nothing fans out by accident; ids work
2 · fix what phase 1 foundlookup tables, second copies, sagas for the cross-customer changesthe code no longer needs everything in one place
3 · move logical shards offone range at a time to new machines, with the checks aboveeach move is small, reversible and boring

Phase 1 changes no data at all, so it can be rolled back with a deploy, and it surfaces every query that assumed one database while that assumption is still true. Teams that skip it discover those queries on the day the data is split, when rolling back means moving terabytes back.

How many logical shards?

Enough that you will never need more machines than slots: 1,024 or 4,096 is usual. Each machine holds a range of slots, so going from 32 machines to 64 means moving half the slots of each, one at a time. The number of logical shards is the one number you cannot change cheaply, so err on the large side.

checkpoint

Why 1,024 logical shards for 32 machines?

So machines can be added later by moving logical shards, without ever changing how keys hash.

Which number in this design can you not change cheaply?

The number of logical shards, because changing it changes the shard of every key.

Sizing, worked out

Gist Size for two years: storage per shard small enough to restore quickly, writes per shard with headroom; start with the larger answer and many logical shards. A query that asks every shard waits for the slowest: with 32 shards, more than a quarter of such queries hit a slow one.

The fan-out tax

A query that asks every shard waits for the slowest one. If each shard answers within 50 ms 99 times in 100, the chance that all 32 do is 0.9932, about 72 %. So more than one fan-out query in four is slower than the shards' own slow case. With 64 shards it is nearly one in two.

Headroom for moving

A move reads a whole logical shard from a busy machine and writes it to another. Do it at 60 % of capacity and nobody notices. Do it at 95 %, because the shard is nearly full, and the extra reads push the source over the edge on the day you most need it to behave. Plan moves from the growth graph, months before a shard reaches its size limit, not from an alert.

This is why chapter 8 works so hard to keep queries on one shard. The arithmetic gets worse as the system grows, which is exactly when the fan-out queries become popular.

Inside each shard, the same rule applies: the events of that shard's customers are partitioned by month. Sharding and partitioning are not alternatives; large systems use both, for different reasons.

Each of 64 shards answers within 50 ms 99 % of the time. What share of fan-out queries are slower than that?

Queries that don't fit the key

Gist Lookups by another unique field get their own table sharded by that field. Lists by another dimension get a second copy filled from events. Reports go to a warehouse. Small reference data is copied to every shard. Changes across shards are sagas, and schema changes run shard by shard.

The shard key serves the common path. Every system also has queries that cut across it. Each has a standard answer, and none of them is “query every shard and hope”.

NeedAnswer
look up by another unique field: email, order ida lookup table sharded by that field, or the shard inside the id (chapter 4)
list by another dimension: all orders for a producta second copy of the data shaped for it, kept up to date from events (the CQRS and Reliable Messaging dives)
reports and totals over everythinga data warehouse fed by change data capture; never the live shards
small reference data: products, prices, countriescopied to every shard, so joins stay local
a unique rule across customers: one account per emailenforce it in the email lookup table, sharded by email, before creating the customer
a change touching two shardsa saga (drill 4)
Every row in this table is a second copy of something. Sharding turns one database into a small system of copies.

Lookup tables

email-lookup.sqlon the shard that owns the email, not the customer
-- sharded by hash(email); one row per email address
CREATE TABLE email_owner (
  email        TEXT PRIMARY KEY,
  customer_id  BIGINT NOT NULL
);
-- sign-up: claim the email first (unique here), then create the customer on its own shard

The order of steps matters. Claim the email in its lookup shard first, then create the customer. If the second step fails, a sweeper releases claims older than an hour that have no customer. The other order leaves customers whose email anyone else can claim.

Tables that join stay together

Orders, order lines, baskets and addresses are all sharded by customer id, so a customer's rows land on the same shard and join locally. This is called co-location, and it is the reason to shard related tables by the same key even when a table could use its own. A table sharded by its own id, such as order lines by line id, would turn every “show my order” into a fan-out. When choosing the key for a new table, ask first: which existing table does it join with most?

Reference data, copied everywhere

Products and prices change rarely and are joined constantly. A copy in every shard, updated from an event stream, keeps the order history page a single-shard query. Accept that a price change reaches the 32 shards a few seconds apart, and never charge from the copy: the Caching dive's rule, “show from a copy, decide on the original”, applies here too.

Schema changes on 32 databases

A migration now runs 32 times. Run it shard by shard, with the expand and contract steps from the Zero-Downtime Change dive, and make the code accept both schemas, because for an hour some shards will have the new column and some will not. A tool that runs a migration across all shards and reports which have it is worth building early.

checkpoint

Why claim the email in the lookup table before creating the customer?

So two sign-ups cannot both get the same email. A failed second step leaves only a claim, which a sweeper releases.

Product prices are copied to every shard. Can checkout use the copy?

Show from it, yes; charge from it, no. The price for payment is read from the source.

Testing it and running it

Gist Never test with one shard. Check routing, fail on hidden fan-out, crash sagas between steps, rehearse moves and test the end of the month. Watch size, skew and the busiest keys per shard, the fan-out queries and the future partitions, and rehearse restoring a single shard.

Sharding bugs hide in single-database test setups, because with one database every query happens to find its rows. The first rule of testing is to never have just one shard.

TestHowCatches
Four shards in every test environmenteven locally: four small databases, or four schemasqueries that only work because everything is in one place
Routingfor random keys, the row is written to and found on the shard the router namesa hash or map mismatch between services
No hidden fan-outthe test fails if a request touches more than one shard, unless allowed by namedrill 3, before it ships
Cross-shard sagascrash between steps; rerun; check no duplicates or orphansdrill 4

Partition clockset the clock to the last day of the month, insert, advance, insertdrill 6
One shard in tests is like one thread in a concurrency test: everything passes and proves nothing.

Runbook: one shard is hot

  1. Which keys? The top-keys list for that shard. One key: drill 2. Many keys: the shard holds too many logical shards.
  2. One giant key: move it to its own shard through the map; then talk to the product team, because a customer that size probably needs its own limits.
  3. Many keys: move some logical shards to a quieter or new machine, one at a time (chapter 6).
  4. Neither: look for a fan-out query or a report pointed at the shards by mistake.

Runbook: a shard is nearly full

  1. How soon? The growth graph says when it passes the limit. More than a month away: plan moves. Less than a week: move the biggest logical shards first.
  2. Is it one key? A single customer growing fast is drill 2 in slow motion; give it its own shard.
  3. Is old data still here? Partitions that should have been detached are the cheapest space to recover.
  4. Then move logical shards to a new machine, one at a time, with the checks from chapter 6.

Backups and restores

Thirty-two databases back up independently, so a restore of “the system at 14:00” restores 32 databases to slightly different moments. For a single customer, all data is on one shard, so a restore is consistent for that customer. Across customers, accept small differences, or use point-in-time recovery on every shard to the same timestamp. Rehearse restoring one shard: it is the most likely real case.

checkpoint

Why does a single-database test environment hide sharding bugs?

Every query finds its rows wherever it looks, so wrong routing and hidden fan-out never fail.

The skew ratio for one shard is 2.4. Next step?

Look at the busiest keys on that shard to tell a giant key from too many logical shards on one machine.

Lab

The shop opens a marketplace: independent sellers list their own mugs. Customers still see their order history. Sellers get a dashboard of their own orders, and the biggest seller will have 5 % of all orders.

  1. Keep customer id as the shard key, or change it?
  2. How is the seller dashboard served?
  3. An order with mugs from three sellers is placed. What is atomic and what is not?
  4. What happens to the biggest seller's dashboard load?
  5. Old orders must be kept for seven years but are rarely read. Where do they go?

model answer

1 · The key

Keep customer id. Placing an order and reading one's history are the busiest paths and both are per customer. Changing the key would also mean moving 11 TB.

2 · Seller dashboard

A second copy of order lines, sharded by seller id, filled from the order events (outbox or CDC). The dashboard reads only that copy, one shard per seller, and may be a few seconds behind, which a dashboard can be.

3 · Three sellers

The order and its lines are written in one transaction on the customer's shard: atomic. The three sellers' copies are updated from events afterwards, each idempotently: not atomic, and that is fine because nothing is decided from them.

4 · The biggest seller

In the seller-sharded copy it is a giant (drill 2). Give it its own shard through the map, and cache its dashboard figures for a minute.

5 · Seven years

Inside each shard, order lines are partitioned by month. After two years a partition is detached and exported to cheap object storage in a columnar format; the warehouse can still query it, and the live shards stay small.

The review checklist

Before sharding

  • The problem is writes or storage, measured and projected two years ahead
  • Indexes, partitioning, archiving, read copies and a larger machine were considered
  • Splitting by function was considered first

Partitioning

  • The partition key is in nearly every query
  • Unique constraints include the partition key, or uniqueness is enforced elsewhere
  • Partitions are created three months ahead and counted by an alert
  • Old partitions are detached or dropped on a schedule

The shard key

  • It is in the common queries and groups what changes together
  • It has many values and spreads today's writes, not just the total
  • It never changes for a row
  • Ids are generated across shards and carry or find their shard

Routing

  • Keys hash into a fixed, large number of logical shards
  • The shard map is versioned, cached and checked on every write
  • Moves fence the old copy and verify counts and checksums

Queries that cross

  • Fan-out queries are named, counted and reviewed
  • Lookups by other unique fields have their own sharded tables
  • Reports read a warehouse, not the shards
  • Changes across shards are sagas

Operations

  • Every test environment has several shards
  • Size, skew and the busiest keys are watched per shard
  • Migrations run shard by shard and report progress
  • Restoring a single shard has been rehearsed
