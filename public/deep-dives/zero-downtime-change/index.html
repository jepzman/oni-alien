Four notes in sixty seconds

Gist Expand and contract changes the shape of data in small compatible steps. Blue–green, canary and feature flags control which version runs, for how many users, with which behaviour. A real change uses all four in a fixed order. This deep dive follows one column rename through every step.

The expand and contract note had one example: the users table has a column name, and it should be called full_name. The table has 200 million rows and the site may not go down. The note's answer was five small deploys. Three notes from the cloud volume described how code gets out.

NoteIn one lineIt controls
Expand & Contractadd the new thing beside the old, move over in steps, remove the old thing lastthe shape of the data
Blue–Greenrun the new version beside the old one, switch all traffic at oncewhich version runs
Canarysend a small share of traffic to the new version and widen while it stays healthyhow many users get it
Feature Flagsship code switched off; turn it on later without a deploywhich behaviour is on
Four notes, four dials. A real change turns all four, in a fixed order.

Each note is one tool. A real change, even one as dull as renaming a column, uses all of them over one or two weeks, and the order matters. This deep dive follows that single rename from the first ALTER TABLE to the last DROP COLUMN: what is deployed at each step, what must be true before the next, what can go wrong, and how to go back. The rename is trivial on purpose. Everything hard about it is hard for every change.

chapter 2 · 2 min

A deploy is never instant

Gist During every deploy, old and new code run together against one database. Old code also lives on in queued jobs, caches, mobile apps and any rollback. So the database must always work for the running version, the next one, and the one you might go back to. That rule forces a change to be split into steps.

The picture in most heads is: the old version stops, the new one starts. It has never been true. A deploy replaces instances a few at a time, so for a while both versions serve requests, and they share one database.

The window is longer than the deploy, because the old version lives on in other places.

Where old code or old data still livesFor how long
app instances not yet replacedminutes
requests and jobs that started before the deployseconds to hours
messages in a queue, written by the old versionuntil they are consumed, or replayed
pages and API responses in a cachetheir TTL
the previous version, if you roll backany time in the next days
mobile apps that users have not updatedmonths
other teams' reports and scripts that read your tablesuntil someone tells them
Rollback is the one people forget. It means the OLD code must work with whatever the NEW code already did.

The rule everything follows from

At every moment, the database must work for the version that is running, the version about to run, and the version you might roll back to.

Try the naive rename against that rule. One migration renames the column, one deploy ships code that uses the new name.

Schema: nameSchema: full_name
Code v1 (uses name)workscrashes: column does not exist
Code v2 (uses full_name)crashes: column does not existworks

Whichever is changed first, schema or code, one of the tinted cells is live for the length of the window. There is no order that works, and rolling back the code lands in a tinted cell as well.

The fix is to never be in a column of that table that only one version understands. For a while the schema has both names, and every version works. That in-between schema is the whole idea of expand and contract. The cost is that one change becomes several, each of which is safe alone.

Three things carry a version: the code, the schema, and the data already in the rows. They change at different speeds. Code changes in minutes. A schema change takes seconds, or hours on a large table. Data follows last, as fast as a backfill can copy it. A plan is a sequence in which the three never disagree.

checkpoint

Why is there no safe order for “rename the column” and “deploy code that uses the new name”?

Whichever goes first, one version of the code meets a schema it does not understand for the length of the deploy window, and again on a rollback.

Name two places old code or data survives after all instances are replaced.

Any of: jobs and messages already queued, cached responses, mobile apps not yet updated, other teams' scripts, and the previous version if you roll back.

chapter 3 · 2 min

The change, step by step

Gist Seven steps: add the new column, write both, backfill old rows, verify, switch reads behind a flag, stop writing the old column, drop it. Going back is cheap through step 5, needs a data repair after step 6 and is impossible after step 7. Wait between steps on purpose.

Here is the rename as it is really done: seven steps over about two weeks. Each step is a small deploy or a script, and each leaves the system working for old and new code.

#StepKindBefore you go on
1Expand: add full_name, empty and optionalschemathe column exists; nothing uses it
2Dual-write: code writes name and full_namecode deployevery instance runs it; new rows have both
3Backfill: copy name into full_name for old rowsscript, hoursit has finished
4Verify: count rows where the two differquerythe count is zero and stays zero
5Switch reads to full_name, behind a flag, 1 % then allflag100 % for several days, no surprises
6Stop writing name; code no longer mentions itcode deploya full release cycle passes; nobody else reads it
7Contract: drop nameschemadone
The note had five steps. Verify and the flag are the two it folded in, and they are where problems are caught.

How to go back, at each step

After stepGoing back meansCost
1nothing. An unused column harms no onenone
2redeploy the previous code. full_name goes stale, so the backfill must run again laterlow
3, 4stop the scriptnone
5turn the flag off. Reads use name again, which is still being writtenseconds
6redeploy dual-write code, and copy full_name back into name for every row written sincea data repair
7restore the column from a backupeffectively impossible

The plan has the same shape as a saga. Steps 1 to 5 are easy to undo. Step 6 is the pivot: after it, the old column starts to rot, and going back needs a repair. Step 7 cannot be undone. So the time between steps is not idle. The days after step 5 are the soak period, in which rolling back is still a flag flip. Do not shorten them to finish the ticket.

Why dual-write comes before the backfill

It is tempting to backfill first, since it is the slow part. But a backfill copies rows as they are at that moment. If any code is still writing only name, rows it touches after the backfill passed them have a stale or empty full_name, and nothing will ever fix them (drill 3). With dual-write running everywhere first, every row written from then on is already right, and the backfill only has to catch up the past.

checkpoint

After step 5, a bug appears in how names are displayed. What do you do, and why is it safe?

Turn the flag off. Reads go back to name, which is still correct because the code is still writing both columns.

Why is step 6 the one to wait before?

Once the old column is no longer written, it goes stale. Rolling back after that needs every newer row copied back.

Failure drills

Gist Six ways a small change becomes an incident: an instant schema change that queues behind a slow query, one enormous update, rows written between the backfill and dual-write, a column dropped while something still read it, a canary that could not see wrong data, and a forgotten flag with a dead branch.

Each of these has turned a five-minute change into an incident. Guess before reading.
  • 1 · the lock queue
  • 2 · the big update
  • 3 · the gap
  • 4 · early contract
  • 5 · the quiet canary
  • 6 · the old flag
Drill 1

The instant change that froze the site

Timeline
Step 1 is ALTER TABLE users ADD COLUMN full_name text. It takes a millisecond. But a report query has been reading users for four minutes. The ALTER needs the table to itself for that millisecond, so it waits. Every query that arrives after it now waits behind the ALTER.
What you see
All requests that touch users hang. Connection pools fill. The site is down until the report finishes, and the “instant” migration is blamed, correctly.
Why
A schema change needs an exclusive lock, even briefly. Locks are granted in order of arrival. A waiting exclusive request blocks everyone behind it, including plain reads that would otherwise have run alongside the report.
What saves you
Tell the migration to give up quickly: SET lock_timeout = '2s', and retry a few times. If it cannot get the lock in two seconds it fails and nothing queues behind it. Check for long-running transactions before starting.

Rule: a fast schema change can still wait for a slow query, and everything waits behind it. Always set a lock timeout.

Drill 2

One UPDATE for 200 million rows

Timeline
Step 3 is run as UPDATE users SET full_name = name. One statement, one transaction, 200 million rows.
What you see
The statement runs for hours and holds a lock on every row it has touched, so sign-ups and profile edits start to time out. The replicas fall an hour behind, and pages that read from them show old data. If it is cancelled at 90 %, everything is rolled back and nothing was gained.
What saves you
Copy in small batches, a few thousand rows at a time, each in its own short transaction, with a pause between them. Walk the table by primary key. Watch replica lag and slow down when it grows. Record the last id done so the script can be stopped and resumed (chapter 5).

Rule: backfill in small, resumable batches that the live traffic does not notice.

Drill 3

The rows that fell through the gap

Timeline
The backfill is run first, to save time. It finishes on Tuesday. The dual-write code is deployed on Wednesday. On Tuesday night, 40,000 users signed up or edited their names.
What you see
Nothing, for days. Then reads are switched to full_name, and 40,000 users have a blank name or an old one. The ones who changed their name after getting married are the ones who write in.
What saves you
Order: dual-write on every instance first, then backfill. And step 4 exists for this: before any read is switched, count the rows where full_name differs from name. The count must be zero, and must still be zero the next day. A count that keeps growing means some writer is still not dual-writing: an old instance, a nightly job, an admin script, another service.

Rule: dual-write before backfill, and verify with a count before trusting the new column.

Drill 4

Someone was still using the old column

Timeline
The team's own code no longer mentions name, so the column is dropped. That night the finance team's export fails. So does a worker running last month's build. So do the old app instances in the middle of a deploy, even though they never show the name: their database library lists every column it knows in each query.
Why
“Our code doesn't use it” was checked by searching one repository. The column had readers that the search could not see.
What saves you
Before step 7, look at the database, not the code: its statistics show whether the column is still read. Tell the library to ignore the column one release before dropping it. Ask the other teams. Some teams first rename the column to name_unused for a week: anything that still needs it fails loudly, and the fix is a rename back, not a restore.

Rule: contract only when the database itself shows that nothing reads the old thing.

Drill 5

The canary that had nothing to say

Timeline
Reads are switched to full_name for 1 % of traffic. Error rate and response time on that 1 % are perfect for an hour, so it goes to 100 %. A week later support notices that accounts created before 2019 show no name.
What you see
No error anywhere. A blank name is a valid string. The canary measured crashes and slowness, and this bug was neither.
What saves you
Measure the thing that can go wrong. Before switching any read, read both columns in production and count the cases where they differ, without showing the new one to anybody. This is a shadow read. Zero mismatches over a few days of real traffic tells you more than any error graph. Then widen by groups that matter, such as old accounts and each country, not only by percentage.

Rule: a canary only sees what it measures. For data changes, compare old and new values, not just error rates.

Drill 6

The flag nobody removed

Timeline
The read-full-name flag has been at 100 % for five months. The code still has both branches. The column name was dropped in the spring. During an unrelated incident someone looks through the flag dashboard for things to turn off “to be safe”, and turns this one off.
What you see
Every page that shows a name fails at once. The off branch reads a column that no longer exists. The incident now has a second cause, created by the response to the first.
What saves you
A release flag has an owner and an end date. Removing the flag and its dead branch is a step of the plan, done after step 5 has soaked and before step 6. A flag whose off position no longer works is a trap, and the flag list should not contain any.

Rule: delete the flag before you delete what its other branch depends on.

What the six drills add up to

HabitDrill
every schema change has a lock timeout and a retry1
data is moved in small, resumable batches, watching the replicas2
dual-write first, backfill second, then count the differences3
the old thing is dropped only when the database shows no readers4

flags are removed on schedule, before the contract step6

checkpoint

An ALTER TABLE that takes a millisecond has blocked the site for three minutes. What was missing?

A lock timeout. The statement was waiting for a long-running query, and every later query queued behind it.

The mismatch count after the backfill is 12 and rises by a few each hour. What does that tell you?

Some writer is still writing only the old column: an old instance, a job, a script or another service.

chapter 5 · 3 min

Backfill and verify: the hard part

Gist Copy old rows in small batches by primary key, safe to rerun, resumable, and slowing down when replicas lag. Estimate the duration first. Then verify twice with a count of differences, and compare old and new values on real reads before any user sees the new column.

Steps 3 and 4 are where a migration spends most of its calendar time and where the data is actually at risk. They deserve more care than the two ALTER statements people worry about.

A backfill that production does not notice

backfill.tssmall batches, by id, resumable
let lastId = await checkpoint.load("users.full_name") ?? 0;
const maxId = await db.value("SELECT max(id) FROM users");

while (lastId < maxId) {
  await db.query(
    `UPDATE users SET full_name = name
     WHERE id > $1 AND id <= $2 AND full_name IS NULL`,   // IS NULL: safe to run twice
    [lastId, lastId + 5_000]);

  lastId += 5_000;
  await checkpoint.save("users.full_name", lastId);       // stop any time, resume here
  while (await replicaLagSeconds() > 5) await sleep(1_000); // let the replicas catch up
  await sleep(100);
}
ChoiceWhy
Batches of a few thousand rowseach transaction is short, so locks are held for milliseconds
Walk by primary key rangeeach batch finds its rows directly. “The next 5,000 where full_name is empty” rescans from the start every time and gets slower as it goes
AND full_name IS NULLthe script can be rerun without undoing newer values written by dual-write
A saved checkpointa deploy, a crash or a nervous operator can stop it without losing progress
Slow down on replica lagthe backfill yields to live traffic, never the reverse
The note's version used LIMIT 1000 in a loop. Fine for a million rows. At 200 million, walk by id.

How long will it take?

QuantityValue
Rows200,000,000
Batch5,000 rows, about 150 ms, plus a 100 ms pause
Rate4 batches a second, 20,000 rows a second
Total10,000 seconds: under 3 hours, if nothing slows it
Plan fora working day, with replica pauses and peak hours

Work this out before starting. If the answer is three weeks, the batch size, the hours it may run, or the approach needs to change, and it is better to learn that from arithmetic.

Verify: the step people skip

verify.sqlrun on a replica, in id ranges
SELECT count(*)
FROM users
WHERE id > 0 AND id <= 1000000
  AND full_name IS DISTINCT FROM name;   -- also catches NULL on one side

The total must be zero. Then run it again a day later. A stable zero means every writer is dual-writing. A number that grows means one is not (drill 3), and the list of ids tells you which rows it touches, which usually tells you who.

Shadow reads

The count checks the data at rest. A shadow read checks it under real traffic, on the real code path.

get-user.tsread both, compare, show the old one
const row = await db.one("SELECT name, full_name FROM users WHERE id = $1", [id]);

if (row.full_name !== row.name) {
  metrics.count("users.full_name.mismatch");        // nobody sees this; we just count
  log.warn("full_name mismatch", { id });
}
return flags.on("read-full-name", user) ? row.full_name : row.name;

For a week this costs nothing and proves the new column on every read. When the mismatch counter has been at zero for days, turning the flag on is a formality.

When the data does not convert cleanly

A rename is the easy case: copy the value. Most real changes transform it: dollars to cents, one name field into first and last, free text into a list of codes. Then some rows will not convert: empty names, a single word, a company where a person was expected. Decide the rule for those rows before the backfill, write them to a list, and have someone look at the list. A backfill that guesses silently has moved the problem to step 5, where customers find it.

checkpoint

Why include AND full_name IS NULL in the backfill's update?

So a rerun does not overwrite values that dual-write has already set, possibly with newer data.

What does a shadow read tell you that the verify count does not?

It checks the real read path under real traffic, continuously, including rows changed after the count was run.

chapter 6 · 3 min

Schema changes that do not block

Gist Know for each change whether it is instant, blocks writes or rewrites the table. Adding an optional column is instant; indexes are built concurrently; NOT NULL and foreign keys are added unvalidated and validated separately; type changes and renames go through expand and contract. Always set a lock timeout, and run migrations as their own step.

Drill 1 showed that even an instant change can hurt. Not all changes are instant. Before any migration, know which kind it is. The table is for PostgreSQL; other databases differ in the details and the same questions apply.

ChangeOn a large, busy tableDo this
Add an optional columninstantas it is, with a lock timeout
Add a column with a fixed defaultinstant on current versionsas it is
Add an indexblocks writes while it buildsCREATE INDEX CONCURRENTLY
Add NOT NULLscans the whole table under a lockadd a CHECK … NOT VALID, then VALIDATE it separately
Add a foreign keyscans and locks both tablesadd it NOT VALID, then VALIDATE
Change a column's typeusually rewrites the tablenew column, expand and contract
Rename a column or tableinstant, and breaks all running codeexpand and contract
Drop a columninstantonly as a contract step (drill 4)
“Instant” means the change itself. It still has to get the lock.
0042_expand.sqla migration that cannot cause a pile-up
SET lock_timeout = '2s';        -- give up, do not queue
SET statement_timeout = '10s';  -- and never run long by surprise

ALTER TABLE users ADD COLUMN full_name text;

The two “not valid, then validate” rows are the same trick. The first statement is quick and makes the rule apply to new rows from now on. The second checks the old rows, and it does so while reads and writes carry on. One slow blocking step has become one instant step and one slow harmless step.

Migrations are their own deploy

Many frameworks run pending migrations when the app starts. With 20 instances starting together, 20 processes try to run the same migration, and the new code is live before anyone has looked at the result. Run migrations as a separate, single job in the pipeline, before the code that needs them, and after checking that the code currently running is happy with the new schema. It is by definition: expand steps are backward compatible.

Pipeline stepContains
1 · migrateexpand-only schema changes; one runner; lock timeout; stops the pipeline if it fails
2 · deploycode that works with the schema both before and after step 1
3 · later, separatelybackfills, as jobs you can watch, pause and resume
4 · much latercontract migrations, on their own, on a quiet day

Let a linter say no

Nobody remembers the table above under deadline. A migration linter in the build does: it fails a pull request that adds an index without CONCURRENTLY, sets NOT NULL in one step or renames a column. It is cheap to add, and it turns this chapter from knowledge into a rule.

checkpoint

Why not run migrations when the application starts?

Many instances start together and race to run the same migration, and the new code is live before anyone has checked the result.

What does “add the constraint NOT VALID, then VALIDATE” buy you?

The rule applies to new rows at once with an instant change; the slow check of old rows then runs without blocking reads and writes.

chapter 7 · 3 min

Rolling out the code: deploys, canaries, flags

Gist A deploy decides which build runs, a canary how much traffic it gets, and a flag which behaviour is on. Use a canary for risky write-path code and a flag for switching reads. With blue–green, migrate expand-only before the switch and contract only after the old environment is gone.

The schema steps are covered. The code steps, 2, 5 and 6, each have to reach production, and there are three tools for that. They are often confused because all three “release gradually”. They control different things.

ToolControlsUnitUndo
Rolling or blue–green deploywhich build is runninginstances, or the whole environmentredeploy or switch back: minutes
Canaryhow much traffic the new build getsa share of requestsshift traffic back: seconds to minutes
Feature flagwhich behaviour is on, inside a builda user, a group, a percentageflip it: seconds, no deploy
Deploy: the code is on the servers. Release: users get the behaviour. The flag is what separates the two.

Which tool for which step

StepRiskUse
2 · dual-writea bug in the write path affects every writecanary deploy: watch error rate and write latency on a small share first
5 · switch readswrong data shown, with no errorsa flag, widened by group, after shadow reads show zero mismatches
6 · stop writing the old columngoing back needs a repairordinary deploy, after the soak; nothing to widen

Step 5 uses a flag, not a deploy, for three reasons. Turning it off takes seconds and no pipeline. It can be widened by meaningful groups, such as staff, then accounts created before 2019, then one country. And it is independent of whatever else is being deployed that week.

Blue–green and the shared database

Blue–green gives each version its own servers and one shared database. The note called that “the catch”. With the plan from chapter 3 it stops being one, as long as two rules hold.

  • Before the switch, green's migrations are expand-only. Blue is still serving, and must not notice them.
  • Contract only after blue is gone for good. While blue is kept warm as the way back, its schema needs are still live. Dropping a column blue reads turns the instant rollback into a crash.

The same holds for anything else the two share: a queue, a cache, uploaded files. A message written by green and consumed by blue after a switch back is the mixed-version window again, in a different pipe.

What a canary should compare

SignalCatchesMisses
error rate, canary against stablecrashes, failed querieswrong answers that are valid
response time, typical and slow casea missing index, extra queriesproblems on rare paths
database load per requestan accidental full scan
business numbers: sign-ups, checkouts completedbroken flows that return 200slow-moving effects
data comparison: mismatches between old and newwrong data (drill 5)needs to be built for each change

Run the canary long enough to include the traffic that matters. Ten minutes at three in the afternoon says nothing about the nightly export or Monday's invoice run.

checkpoint

Why switch reads with a flag and not with a canary deploy?

A flag turns off in seconds with no pipeline, can be widened by meaningful groups, and is independent of other deploys.

Blue is kept warm for a week as the rollback. Can you drop the old column on day two?

No. Blue still reads it. Dropping it makes the rollback crash.

chapter 8 · 3 min

Beyond the database

Gist The same steps apply to API fields, messages, cache formats, job arguments and configuration. Ask who still has the old shape and for how long. Teach every reader a new shape before any writer produces it. Mobile apps stretch the window to months, so the contract step needs a date and a minimum supported version.

Nothing in the plan was really about columns. It works for anything where producers and consumers of a shape are updated at different times. The steps keep their names. What changes is who still has the old shape, and for how long.

What changesWho still has the old shapeExpandContract when
a database columnrunning code, other teams' queriesadd the new columnthe database shows no reads
an API fieldevery client, including ones you do not ownadd the new field; keep sending the oldrequest logs show no client using the old one
a message or eventconsumers, and old messages in the logpublish the new version beside the oldconsumers have moved and old messages can no longer be replayed
a cache entry's formatentries written by the old codeput a version in the keyold keys have expired
a background job's argumentsjobs already queuedthe worker accepts both shapesthe queue holds no old jobs
a configuration valueinstances not yet restartedcode reads new, falls back to oldall instances restarted
The Reliable Messaging and Caching dives each had this rule for their own pipe. It is one rule.

Reader first, writer second

For any new shape, the order is the same: teach every reader to accept it before any writer produces it.

ExampleWrong orderRight order
a new order status, PAUSEDdeploy code that sets it; old instances and old apps crash on the unknown valuefirst a release that understands PAUSED everywhere; then one that sets it
a new field in an eventconsumers that validate strictly reject the messageconsumers ignore unknown fields first
a new job argumentold workers fail jobs queued by new codeworkers accept it first; producers send it next release

This is what makes rollback safe as well. If the writer is rolled back, readers that understand the new shape lose nothing. If readers were rolled back while new-shaped data already exists, the old readers meet data they cannot read. So a release that starts writing a new shape can only be rolled back to a version that can still read it, and that version must have gone out first.

Mobile apps stretch the window to months

A web client is replaced on the next page load. A mobile app is replaced when its owner feels like it. A version released today will still be sending requests in a year.

ConsequencePractice
the API's contract step may be a year awayplan it as a date, not as “after the release”
you need to know which versions are still aliveevery request carries the app version; a dashboard shows the share of each
some day the old shape really must goa minimum supported version, and a polite “please update” screen that old versions already know how to show

The “please update” screen has to exist in the app before it is needed. It is the reader-first rule again, applied to the one message every old version must be able to understand.

checkpoint

You want to add a new order status. What ships first?

A release in which every reader, including the apps, understands the new status. Only a later release starts setting it.

When can an old API field be removed?

When request logs show that no client version still reads it, or a minimum supported version has been enforced.

Testing it and running it

Gist Run the production version's tests against the new schema. Time the migration on production-size data. Rehearse a rollback with new data present. Keep a one-page plan with the check before each step, watch locks, replica lag and mismatches while it runs, and ship contract steps alone, early in the week.

A migration is production-only code that runs once. That makes it the least tested code a team writes, on the most valuable thing the team has. Four kinds of check close most of the gap.

CheckHowCatches
Old code, new schemain the build, apply the pending expand migrations, then run the test suite of the version currently in productiona migration that is not backward compatible (chapter 2)
Real sizerun the migration and the backfill on a copy with production row counts; time them; watch locksdrills 1 and 2: the ten-second step that takes four hours
Rollback rehearsaldeploy the new version to a test environment, write data, deploy the previous version, use the siteold code that cannot read new data (chapter 8)
Twicerun every migration and backfill a second timescripts that fail or corrupt when rerun after a partial failure
“Old code, new schema” is one extra job in the pipeline. It would have caught the naive rename in chapter 2 before a human looked at it.

 7  drop name            deploy   1 Dec   -

Go back: steps 1-5 see runbook; step 6 needs reverse backfill; step 7 cannot.

It shows anyone where the change is, what has to be true to continue, and that step 7 exists. Half-finished migrations, with two columns kept for ever because nobody remembers whether the old one is safe to drop, are the usual way this pattern fails. The document is the cure.

Runbook: a step went wrong

  1. Which step are you on? The plan says. Steps 1 to 5 go back cheaply; do that first and investigate afterwards.
  2. Schema step hanging? Cancel it. With a lock timeout it will have cancelled itself.
  3. Backfill hurting? Stop it. The checkpoint keeps your place.
  4. Wrong data after the read switch? Flag off. The old column is still correct, because you are still writing it.
  5. After step 6? Do not improvise. Redeploy dual-write, run the reverse backfill from the plan, then decide.

checkpoint

What does running the production version's tests against the new schema prove?

That the expand migration is backward compatible: the code running now will keep working once the schema changes.

A migration has had two columns for eight months. What went wrong?

Nobody owned the contract step. Without a written plan and a date, the last steps are forgotten.

When it is too much, a lab and the checklist

Gist For a small table, an internal tool or a product not yet launched, one step or a short announced downtime is cheaper and fine. Use the full plan when the table is large, the system must stay up or others depend on the shape. The lab converts an order total from dollars to cents.

When this is too much

Seven steps over two weeks is a real cost, and not every change is worth it.

SituationDo instead
a small table, a change that takes a secondone migration with a lock timeout, at a quiet moment. Still expand-only if code is running
an internal tool used in office hoursannounce ten minutes of downtime in the evening and do it in one step
a product not launched yetchange the schema freely. There is no old data and no old client
a column nobody reads, added last weekdrop it. Check the statistics first
Planned downtime is a legitimate tool. Ten announced minutes at night can be cheaper than two weeks of care.

The full plan is for tables that are large or busy, systems that must stay up, and shapes that other people depend on. Use the question from chapter 2 to choose: who still has the old shape, and for how long? If the answer is “nobody, for no time”, you do not need seven steps.

Lab

The orders table stores total as a decimal number of dollars: 49.00. Rounding bugs keep appearing, so the team wants total_cents as a whole number: 4900. The table has 500 million rows. The finance team's nightly export reads total. The mobile app receives total in the order API.

  1. List the steps. Which is the one where going back gets expensive?
  2. The backfill does 20,000 rows a second. How long does it take, and what do you check afterwards?
  3. What does the shadow read compare?
  4. When can total be dropped from the table? When from the API?
  5. A row has total = 49.005. What now?

model answer

1 · The steps

Add total_cents. Dual-write both. Backfill. Verify. Switch reads behind a flag, with shadow reads first. Remove the flag. Stop writing total. Drop it. Going back gets expensive at “stop writing total”, because from then on the old column is out of date.

2 · The backfill

500,000,000 ÷ 20,000 = 25,000 seconds, about seven hours of pure run time; plan for a day or two with pauses. Afterwards, count rows where total_cents is not equal to round(total × 100). It must be zero now and zero tomorrow.

3 · The shadow read

On every order read in production, compare total_cents with total × 100 and count mismatches, while still showing total. Also compare sums: the day's revenue computed from each column should be identical.

4 · Dropping it

From the table: when the finance export has moved to total_cents and the database's statistics show no reads of total. Ask finance early; their export is the hidden reader of drill 4. From the API: much later. The API sends both fields until the share of app versions that read total is close to zero, which may take a year.

5 · The half cent

It does not convert cleanly. Do not let the backfill round it silently. Decide the rule with finance first, list every such row, and have a person look at the list. Those rows are probably the rounding bugs that started the project.

The review checklist

The plan

  • The change is split into expand, migrate and contract steps, written down with an owner
  • Each step works with the running version, the next one and the one you would roll back to
  • The way back is stated for every step, and the step where it gets expensive is marked
  • There is a soak period before that step
  • The contract step has a date

Schema changes

  • Every migration sets a lock timeout and retries
  • Each change is known to be instant, or uses the online form
  • Migrations run as one job before the code deploy, not at app start
  • A linter blocks unsafe migrations in the build

Data

  • Dual-write is on every instance before the backfill starts
  • The backfill runs in small batches by key, is resumable and safe to rerun
  • It slows down when replicas lag, and its duration was estimated
  • Rows that do not convert are listed and reviewed, not guessed
  • A mismatch count is zero, twice, before reads switch

Rolling out

  • Readers accept a new shape before any writer produces it
  • Risky write-path code goes out as a canary
  • Read switches use a flag, after shadow reads show zero mismatches
  • The canary compares data and business numbers, not only errors
  • The flag is removed before the contract step

Contract

  • The database's own statistics show no reads of the old thing
  • Other teams, jobs, scripts and old app versions were checked
  • The database library ignores the column one release before it is dropped
  • Contract runs alone, early in the week, with the owner watching

Tests

  • The production version's tests pass against the new schema
  • The migration was timed on production-size data
  • A rollback was rehearsed with new data present
  • Every script was run twice
