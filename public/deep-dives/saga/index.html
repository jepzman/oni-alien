chapter 1 · 1 min

The note in sixty seconds

Gist A saga replaces one big transaction with a chain of small local ones. Each step commits on its own. If a later step fails, you run compensations for the earlier ones. The note taught the shape. This deep dive is about everything that goes wrong inside that shape.

Our shop sells mugs. Placing order 42 touches four services, each with its own database. The note ended with this plan:

#StepIf we must undoType
1Order: create as PENDINGmark CANCELLEDcompensatable
2Inventory: reserve 2 mugsrelease the reservationcompensatable
3Payment: charge $49none: this is the pivotpivot
4Shipping: book the courierkeep retryingretriable
5Order: mark APPROVEDkeep retryingretriable
compensatable → pivot → retriable. If you remember one thing from the note, this.

That plan reads well on a whiteboard. It also hides the questions the note only touched. Where does the saga remember how far it got? What happens when a machine dies between two lines of code? What do other requests see while the saga is half done? How long may it take, how do you test it, and who fixes it at night? The chapters take them in that order.

chapter 2 · 2 min

A saga is a state machine with a diary

Gist Stop thinking of a saga as a function that runs top to bottom. Think of it as a row in a table that moves between named states. The orchestrator can die at any moment, so it writes down what it is about to do, then does it, then writes down that it is done.

The code in the note was a for loop over steps. A loop keeps its position in memory, and memory is gone after a crash. The real design has two parts.

  1. States. Every place the saga can rest gets a name. Order 42 is always in exactly one of them.
  2. A saga log. Before each command goes out, the orchestrator writes a row. When the reply comes back, it updates the row. The log lives in the orchestrator's own database.

The saga log for order 42

This is the whole memory of the saga. One row per step, written by the orchestrator.

sagastepcommand keystatusupdated
42create-order42:1DONE10:00:00.120
42reserve-stock42:2DONE10:00:00.310
42charge-card42:3STARTED10:00:00.315
STARTED = “I may or may not have sent this.” That honesty is what makes recovery possible.

The pink row is the interesting one. STARTED with no DONE means the orchestrator does not know whether the card was charged. It may have crashed before sending, after sending, or after the charge succeeded but before the reply arrived.

The recovery rule

When an orchestrator starts, it reads every saga that is not in a final state and applies one rule:

For a step that is STARTED, send the same command again with the same command key.

That rule only works if every service treats a repeated key as “you already asked me this, here is the answer I gave before”. So the state machine forces a requirement onto every participant: commands are idempotent, keyed by saga id plus step number. This is the Idempotent Consumer note, now mandatory.

Two writes that must not drift

Writing the log row and sending the command are two actions. If the orchestrator writes STARTED and crashes before sending, recovery re-sends: fine. If it sent first and wrote second, a crash in between would leave a charge that the log knows nothing about. So the order is fixed: write, then send. In practice the command goes into an outbox table in the same local transaction as the log row, and a relay publishes it. That is the Transactional Outbox note, also now mandatory.

checkpoint

The log says step 3 is STARTED and the orchestrator has just restarted. Should it compensate steps 1 and 2?

No. It does not know that step 3 failed. It re-sends the charge command with key 42:3 and acts on the reply.

Why is the command key 42:3 and not a fresh random id on each attempt?

A fresh id makes each retry look like a new request, so the customer could be charged twice. A stable key lets Payment recognise the repeat.

chapter 3 · 4 min

Failure drills

Gist Five things that will happen to your saga in production. Each drill shows the timeline, what you would see, why, and the design rule that prevents it. If you only skim, read the green rule at the bottom of each card.

Try to answer “what happens next?” before reading each drill. That is the exercise.
  • 1 · crash between steps
  • 2 · timeout
  • 3 · undo arrives first
  • 4 · undo fails
  • 5 · double click
Drill 1

The orchestrator dies between two steps

Timeline
Inventory reserves two mugs and replies OK. The orchestrator crashes before it writes DONE for step 2.
What you see
Two mugs are held. Order 42 shows PENDING. Nothing moves. Without recovery it stays that way, and the mugs are unsellable.
What saves you
On restart the log shows step 2 as STARTED. The orchestrator re-sends ReserveStock with key 42:2. Inventory finds the key, returns the earlier OK and reserves nothing new. The saga continues to step 3.

Rule: every step is safe to send twice, and the orchestrator resumes from its log, never from memory.

Drill 2

The payment call times out

Timeline
The orchestrator sends ChargeCard $49. Two seconds pass. No reply.
The tempting mistake
Treat the timeout as a failure and compensate: release the mugs, cancel the order. Then the payment provider finishes the charge it was working on. The customer has paid $49 for a cancelled order.
Why
A timeout carries no information about the outcome. It means “I stopped waiting”. The request may never have arrived, may be running now, or may have finished with the reply lost on the way back.
What saves you
Retry the same command with the same key until you get a definite answer: charged or declined. Only a definite “declined” starts the compensations. If you run out of patience, the saga moves to NEEDS_ATTENTION. It does not guess. Chapter 5 shows a way to get a definite answer on demand.

Rule: a timeout is a question, not an answer. Never compensate on “I don't know”, least of all at the pivot.

Drill 3

The undo arrives before the thing it undoes

Timeline
ReserveStock is stuck in a slow queue. The saga's overall deadline passes, so the orchestrator sends ReleaseStock. Inventory has nothing to release and replies OK. A minute later the delayed ReserveStock finally arrives and reserves two mugs for an order that is already cancelled.
What you see
Stock that slowly leaks away. Each leaked reservation belongs to a cancelled order, so no process will ever release it. Someone notices weeks later when the warehouse count and the system disagree.
What saves you
Two behaviours in the participant. First, a compensation for a step that never ran must succeed and do nothing. Second, it must leave a tombstone: “42:2 was cancelled”. When the late command arrives, Inventory sees the tombstone and refuses it.

Rule: compensations work even when there is nothing to undo, and they block the late original.

Drill 4

The compensation itself fails

Timeline
Payment declines the card. The orchestrator sends ReleaseStock. Inventory is down for a deploy.
The tempting mistake
Catch the error, log it and mark the order CANCELLED anyway. The order looks finished, the mugs stay reserved, and nobody is told.
What saves you
A compensation is a retriable step: it has no “undo of the undo”, so it must eventually succeed. Retry with backoff for as long as it is reasonable. The saga stays in COMPENSATING, which is visible on a dashboard. After a limit it moves to NEEDS_ATTENTION with the failed step named.

Rule: compensations may be slow but they may not be optional. Design them so the only possible failures are temporary.

Drill 5

The customer double-clicks “Place order”

Timeline
Two identical requests arrive 80 ms apart. Two sagas start. Both reserve mugs, both charge $49.
Why the earlier rules don't help
Idempotent steps protect one saga from repeating itself. Here there are two sagas with two ids, and each is behaving correctly.
What saves you
The saga id must come from the client's intent, not from the server's clock. The checkout page generates one idempotency key when it loads. The orchestrator has a unique constraint on that key, so the second request finds saga 42 already running and returns its status.

Rule: starting a saga must be idempotent too. One customer intent, one saga id.

What the five drills add up to

Every participant must…Because of
recognise a repeated command key and return the first resultdrills 1, 2
accept a compensation for a step it never sawdrill 3
reject a step whose compensation already randrill 3
offer compensations that only fail temporarilydrill 4

This is the real cost of a saga. The orchestrator is the small part. The contract that every service has to honour is the large part, and it is the part teams skip.

checkpoint

Inventory receives Release 42:2 but has no reservation for 42. What are the two things it must do?

Reply OK without changing stock, and record that 42:2 was cancelled so a late Reserve 42:2 is refused.

A colleague proposes: “on timeout, compensate; if the charge turns out to have succeeded, refund it later.” What is wrong with that?

It turns an uncertain moment into a certain bad experience: the customer is charged for a cancelled order and waits days for a refund. It also needs a process that notices the late charge, which is the same work as waiting for a definite answer.

next · chapter 4The missing letter: no isolation →

chapter 4 · 2 min

The missing letter: no isolation

Gist A database transaction hides its half-finished work from everyone else. A saga cannot: each step commits and is visible at once. Other requests can read, and change, data that the saga may still undo. There are six standard countermeasures, and you choose them per step.

ACID has four letters. A saga keeps atomicity in a weaker form (all steps finish, or all are compensated), keeps consistency and durability inside each service, and drops isolation completely. Three things follow.

Three anomalies, with mugs

AnomalyWhat happens in the shop
Dirty readOrder 42 reserves the last two mugs. Order 43 sees zero stock and tells its customer “sold out”. Then 42's card is declined and the mugs come back. Order 43 lost a sale because of data that was never final.
Lost updateWhile order 42 waits for payment, the customer changes the delivery address. Step 5 then saves the order using the copy it read at step 1. The new address is gone.
Fuzzy readStep 1 reads the mug price as $24.50. Marketing changes it to $27 before step 3. The order confirmation says $49 and the card is charged $54.
None of these is a bug in one service. Each service did its job. The bug is in the gaps.

Six countermeasures

CountermeasureIdeaIn the shop
Semantic lockMark the record as mid-saga so others can reactOrder is PENDING; address edits are refused or queued until it is final
Commutative updatesDesign changes so their order doesn't matterStock moves by +2 and -2, never “set stock to 8”
Pessimistic viewReorder steps so risky data shows up lateLoyalty points are added after the pivot, so nobody spends points from an order that gets cancelled
Reread valueCheck the data hasn't changed before writingStep 5 rereads the order's version number and restarts if it moved
By valueCarry the facts inside the sagaThe $49 total travels in the saga's context; no step looks the price up again
Version fileRecord operations so they can be reorderedPayment logs “authorise” and “cancel” per order, so a cancel that arrives first still wins

Semantic lock is the one you will use most, and it comes with a decision. When another request meets a locked record, it can fail fast (“this order is being processed, try again”) or wait until the saga ends. Failing fast is simple and pushes the retry to the caller. Waiting is friendlier and brings back a problem sagas were meant to avoid: two sagas waiting on each other's locks is a deadlock, and now you need a timeout to break it.

For the dirty read on stock there is a product answer as well as a technical one. Many shops show “2 left, reserved in another basket” for a few minutes. The half-finished state becomes something the customer can see and understand. That is often cheaper than hiding it.

checkpoint

Which countermeasure fixes the fuzzy read on price, and why is it the cheapest?

By value: put the price in the saga's context at step 1. No lock, no reread, no extra call. The customer pays what the confirmation page showed.

Your refund step sets balance = 120. What breaks, and how do you rewrite it?

If another saga changed the balance in between, its change is overwritten. Rewrite it as a commutative update: balance = balance + 49.

chapter 5 · 3 min

Timeouts, deadlines and the stuck saga

Gist Every resting state gets a maximum age. Three clocks do the work: a timeout per attempt, a budget per step and a deadline for the whole saga before its pivot. Timers are stored as rows, and a sweeper job wakes the sagas that have slept too long.

A saga that never fails and never finishes is the most common production problem. The cause is nearly always a state with no clock on it. Give the saga three clocks.

ClockWhat it limitsOrder sagaWhen it rings
Attempt timeoutone call to one service5 s for the charge, 2 s elsewhereretry the same command, same key
Step budgetall attempts of one step4 attempts, about 30 streat the step as failed, if the outcome is known
Saga deadlinethe time before the pivot5 minutesstop going forward and compensate
Set the attempt timeout a little above the service's slow-day response time. Too short and you create your own timeouts.

After the pivot there is no deadline that cancels anything. Retriable steps get a long budget (booking a courier may retry for a day) and then the saga goes to NEEDS_ATTENTION.

Getting a definite answer from payment

Drill 2 left a gap. The saga deadline rings while the charge is still STARTED, and we are not allowed to guess. The usual fix is to split the payment in two, the way card payments already work.

#StepIf we must undoType
3aPayment: authorise $49 (hold the money, take nothing)void the authorisationcompensatable
3bPayment: capture the $49nonepivot

Void 42:3a follows the rules from drill 3: it works when the authorisation exists, it works when the authorisation never arrived, and it blocks a late one. So sending it always ends in a definite state, “no money held”. The dangerous step is now compensatable, and the pivot is a capture on money that is already reserved, which rarely fails.

Timers must survive a crash too

A timer in memory dies with the process, exactly like the for loop in chapter 2. So a deadline is stored as data: each saga row has a wake_at column. A small job, the sweeper, runs every few seconds and picks up sagas whose time has come.

sweeper.sqlruns every 5 s
SELECT saga_id, state
FROM saga
WHERE state NOT IN ('APPROVED', 'CANCELLED')
  AND wake_at < now()
ORDER BY wake_at
LIMIT 100
FOR UPDATE SKIP LOCKED;   -- several sweepers can run side by side

For each row the sweeper feeds a TimerFired event into the state machine, the same way a reply would arrive. The machine decides what it means in that state: retry, compensate or ask for a human. The sweeper also acts as the recovery job from chapter 2, because a saga whose orchestrator crashed is simply a saga that slept past its wake_at.

What the customer sees meanwhile

Internal states are too many and too technical to show. Map them to three.

Customer seesInternal statesNote
Processing your order…PENDING, STOCK_RESERVED, COMPENSATINGa spinner for seconds; after 10 s, “we'll email you”
Order confirmedPAID and everything after itconfirm at the pivot, not at the end
Order cancelled, you were not chargedCANCELLEDsay what happens to the money in the same sentence

Confirming at the pivot is safe because every later step is retriable. A saga in NEEDS_ATTENTION after the pivot still shows “confirmed” to the customer. Support sees the flag; the customer should not have to.

checkpoint

The saga deadline fires while the saga is in PAID. What should the state machine do?

Not compensate. After the pivot a timer only means “retry the current step”, and after the step's budget, NEEDS_ATTENTION.

Why does splitting payment into authorise and capture solve drill 2?

Because a void is a compensation that always ends in a known state, whether or not the authorisation arrived. The saga can stop waiting without guessing.

chapter 6 · 2 min

Orchestration and choreography, side by side

Gist The same saga can be run by one coordinator or by services reacting to each other's events. The drills apply to both. What changes is who is responsible for each rule: in orchestration one component, in choreography every team.

The note gave a rule of thumb for choosing. Here is the detail behind it.

QuestionOrchestrationChoreography
Where is the flow written down?one state machinenowhere; it is the sum of who listens to what
Where is order 42 right now?one row in the saga logask four services, or build a tracking view
Who owns the deadline?the orchestratornobody, unless you appoint someone
Who starts compensation?the orchestrator sends undo commandseach service reacts to a failure event
Adding a stepchange the orchestratorchange who subscribes to what, in several teams
Couplingorchestrator knows every serviceservices know each other's events

The five drills, run against choreography

DrillWhat changes
1 · crash between stepsEach service must save its change and publish its event atomically (outbox). If one forgets, the chain stops silently and no component notices, because no component expects the next event.
2 · timeoutNobody is waiting for a reply, so nobody times out. A stuck saga looks like silence. In practice the Order service sets a timer on PENDING, which makes it a small orchestrator.
3 · undo arrives firstMore likely than before. PaymentDeclined can reach Inventory before OrderCreated does, because the two events travel on different topics. The tombstone rule is unchanged.
4 · undo failsThe broker redelivers until the consumer succeeds. The dead-letter queue plays the part of NEEDS_ATTENTION, so someone has to watch it.
5 · double clickUnchanged: the first service needs the unique key.
Choreography doesn't remove the orchestrator's work. It hands a piece of it to every team.

Two problems only choreography has

Cycles. Order listens to Payment's events to mark itself paid. Payment listens to Order's events to know what to charge. Each service now depends on the other's event format, and a change on either side breaks both. In orchestration the dependencies all point one way, toward the orchestrator.

An invisible flow. A new engineer cannot open one file and read what happens to an order. The remedy is discipline: every event carries the saga id, and a tracking service or a trace view rebuilds the story from the events (chapter 8).

Choosing

ChooseWhen
Choreographytwo to four steps, in a line, no deadline to enforce, and the teams want to stay independent
Orchestrationbranches, deadlines or human steps; or the business asks “where is my order?”
Bothevents between business areas, an orchestrator inside one area. Common and sensible

checkpoint

In a choreographed saga, which service notices that order 42 has been PENDING for an hour?

None, unless one was given that job. Usually Order owns a timer on its PENDING state.

Why is drill 3 more likely with choreography?

The step and its undo are triggered by different events on different topics, so nothing guarantees their order of arrival.

chapter 7 · 3 min

Testing a saga

Gist Test the state machine as a plain function with a table of cases. Then crash the orchestrator after every single log write and check that the saga still ends correctly. Then give every participant the same four contract tests.

The happy path of a saga is easy to test and tells you almost nothing. The bugs live in the moments between steps. Three kinds of test reach them.

1 · The state machine as a plain function

Write the saga's logic as a function with no database and no network: given a state and an event, return the new state and the commands to send. Then test it with a table.

order-saga.test.tsone row per (state, event) pair
const cases = [
  // state            event               new state         commands
  ["STOCK_RESERVED", "PaymentCaptured",  "PAID",           ["BookCourier"]],
  ["STOCK_RESERVED", "PaymentDeclined",  "COMPENSATING",   ["ReleaseStock"]],
  ["STOCK_RESERVED", "TimerFired",       "COMPENSATING",   ["VoidPayment", "ReleaseStock"]],
  ["PAID",           "TimerFired",       "PAID",           ["BookCourier"]],   // retry, never undo
  ["PAID",           "PaymentCaptured",  "PAID",           []],                // duplicate reply
  ["CANCELLED",      "StockReserved",    "CANCELLED",      ["ReleaseStock"]],  // late reply
];

for (const [state, event, next, commands] of cases) {
  test(`${state} + ${event}`, () => {
    expect(step(state, event)).toEqual({ state: next, commands });
  });
}

The last three rows are the valuable ones. Every state must have an answer for every event, including the ones that “cannot happen”. In production they happen.

2 · Kill the orchestrator at every write

Chapter 2 claimed that the saga survives a crash at any point. This test proves it. Run the saga against in-memory fakes of the four services. Count the writes to the saga log in a normal run, say 12. Then run the saga 12 more times, and on run k stop the orchestrator right after write k, start a fresh one, and let it finish.

crash-recovery.test.tsevery crash point, one assertion
for (let k = 1; k <= totalWrites; k++) {
  test(`crash after log write ${k}`, async () => {
    const world = new FakeWorld();                 // fake Order, Inventory, Payment, Shipping
    await runUntilWrite(k, world).catch(() => {});  // the orchestrator "dies" here
    await new Orchestrator(world).recover();        // a fresh process reads the log

    expect(world.order(42).status).toBe("APPROVED");
    expect(world.effects("capture")).toBe(1);       // charged exactly once
    expect(world.effects("reserve")).toBe(1);
    expect(world.effects("bookCourier")).toBe(1);
  });
}

Repeat it with a card that declines, and assert the opposite: order CANCELLED, nothing reserved, nothing captured. If a write-then-send is in the wrong order anywhere, one of these runs fails.

3 · A contract test for every participant

The four rules from chapter 3 turn directly into four tests. Each service team runs them against its own command handler.

TestSendExpect
repeatReserve 42:2 twiceone reservation, the same reply both times
empty undoRelease 42:2 with no earlier reserveOK, nothing changes
late originalRelease 42:2, then Reserve 42:2the reserve is refused
repeat undoRelease 42:2 twiceOK both times, stock released once

These are small and dull, and they are what stands between you and drill 3 in production. Put them in a shared test kit so a new participant gets them for free.

checkpoint

Your crash test passes for all 12 crash points on the happy path. What have you not tested yet?

Crashes during compensation. Run the same loop with a declining card, so the crash points fall inside COMPENSATING.

Why does the table include CANCELLED + StockReserved?

It is the orchestrator's side of drill 3: a late reply for a saga that already gave up. The machine must answer with a release, not ignore it.

Running it: dashboards and repair

Gist Watch three numbers: sagas in flight per state, the age of the oldest one, and how many need a human. Put the saga id on every message and log line. Repair stuck sagas through admin actions that use the normal commands, and let a nightly job check that the services agree.

A saga's promise is “eventually”. Running one means being able to see how long eventually is taking, and being able to help when it stalls.

Three numbers

MetricHealthyAlert when
Sagas in flight, per statea few, changing constantlyone state keeps growing: its next step is stuck
Age of the oldest unfinished sagasecondsolder than the saga deadline plus a margin: the sweeper is not doing its job
Sagas in NEEDS_ATTENTIONzeroabove zero: each one is a customer waiting
Also worth a graph: the share of sagas that end CANCELLED. A jump means a participant is failing, not that customers changed their minds.

One id everywhere

Every command, event, log line and trace carries the saga id. Then one search tells the story of order 42 across four services:

timeservicemessage
10:00:00.120ordersaga=42 order created PENDING
10:00:00.310inventorysaga=42 key=42:2 reserved 2 × mug
10:00:05.320orchestratorsaga=42 step=charge attempt=1 timeout
10:00:06.900paymentsaga=42 key=42:3 duplicate key, returning earlier result: captured
10:00:06.940orchestratorsaga=42 PAID

That is drill 2 as it looks from the outside: a timeout, a retry with the same key, and a payment service that had already done the work.

Runbook: a saga is stuck

  1. Read the saga log. Which step is STARTED, and since when?
  2. Ask the participant. Every service offers “status of command 42:3”. That endpoint is a requirement, and this is the moment you need it. Now you know more than the orchestrator does.
  3. Look at the pivot. Before it, the safe direction is backward: compensate. After it, the only direction is forward: fix what blocks the step and retry.
  4. Use the admin actions: “retry step”, “compensate now” or “mark step done, with a reason”. They go through the same state machine and the same idempotent commands as normal traffic.
  5. Write down what you did on the saga itself, so the next person sees it.

What you never do is edit rows by hand in four databases. A manual fix skips the tombstones and idempotency records, and the next late message undoes it.

Reconciliation: proof that “eventually” arrived

Once a night a job compares the services with each other and reports anything that breaks these three sentences.

  • No order is CANCELLED while stock is still reserved for it.
  • No order is CANCELLED while money is held or captured for it.
  • No order is APPROVED without a captured payment and a courier booking.

The job should find nothing. When it finds something, you have discovered a broken participant rule before the customer or the warehouse did.

Changing the saga while sagas are running

You deploy a new version with an extra step, “check fraud score”, between 2 and 3. At that moment hundreds of sagas are in STOCK_RESERVED under the old definition. Store a definition version on each saga row. A saga finishes under the version it started with; new sagas use the new one. Remove the old code only when the count of old-version sagas reaches zero.

checkpoint

A saga is stuck in STOCK_RESERVED and Payment's status endpoint says “no such command 42:3”. Forward or backward?

Either is safe, because the charge never arrived. Retrying is the normal choice; if you compensate, the void still has to be sent so that a late charge is blocked.

Reconciliation finds a CANCELLED order with stock reserved. Which rule was broken, and where?

Most likely Inventory accepted a reserve after its release (drill 3, no tombstone), or a compensation was skipped (drill 4).

chapter 9 · 2 min

Tools, and when to stop writing your own

Gist A workflow engine gives you the durable log, recovery, retries, timers and a dashboard. It gives you nothing for idempotent participants or isolation. Adopt one when you have many workflows or long waits; a table, an outbox and a sweeper are enough for one or two short sagas.

Everything in chapters 2 and 5 is plumbing: a durable log, recovery, retries, timers. Workflow engines sell exactly that plumbing. It helps to be precise about what they cover.

You needChapterAn engine gives you
Durable state and crash recovery2yes
Retries with backoff, durable timers5yes
A view of every running saga8yes, usually a good one
Running compensations in order2yes; you still write each compensation
Idempotent participants, tombstones3no. This is in your services
Isolation countermeasures4no. This is in your data model
Versioning running sagas8partly; each engine has rules you must follow
An engine replaces the orchestrator you would have written. It does not replace the contract with the participants.

Four families

FamilyExamplesThe flow is written as
Durable executionTemporal, Azure Durable Functionsordinary code that the engine can replay after a crash
State machine serviceAWS Step Functionsa JSON definition of states and transitions
Process engineCamundaa BPMN diagram that business people can read
Saga support in a messaging libraryMassTransit, NServiceBus, Axona state machine class next to your message handlers

Each has a cost that is easy to miss. Durable execution replays your workflow code to rebuild its state, so that code has to be deterministic: no random numbers, clock reads or direct network calls outside the engine's own functions. A state machine service keeps logic in a definition file that needs its own tests. A process engine adds a modelling tool and people who can use it. All of them are one more system to run, upgrade and understand at 3 a.m.

Build or adopt?

Write your own (a table, an outbox, a sweeper)Adopt an engine
one or two sagasmany workflows, or new ones every quarter
a handful of steps, minutes longlong waits: days, human approvals, reminders
the team already runs a database and a broker wellthe team wants the dashboard and history without building them

Either way, chapters 3 and 4 remain your work. Teams that adopt an engine and skip those chapters get the same incidents, with better dashboards.

Lab and review checklist

Gist Design a return-and-refund saga for order 42, then compare with the model answer. The checklist at the end is the whole deep dive as questions to ask in a design review.

Order 42 was delivered. A week later the customer wants to send the mugs back and get the $49 refunded. Design the return saga. You have five services: Order, Shipping (books a pickup), Warehouse (a person inspects the parcel), Payment and Inventory.

  1. List the steps in order. Mark each as compensatable, pivot or retriable.
  2. Where does the refund go, and why there?
  3. One step waits for a human. How long may it wait, and what happens then?
  4. What stops the customer from starting two returns for the same order?
  5. Which of the five drills would cost real money here?

Why the refund comes after the pivot

A refund is the step you cannot take back: charging the customer again needs their consent. So it goes after everything that can still fail, including the inspection. The note's rule, hard-to-undo last, decides the order.

The human step

The saga rests in AWAITING_PARCEL with a wake_at 14 days ahead. If the parcel never arrives, the timer fires and the saga compensates: cancel the pickup, cancel the return. If the inspector rejects the parcel, that is a definite “no” and it compensates the same way. Two weeks in one state is normal for a saga, and it is the reason timers are stored as data.

Two returns for one order

A semantic lock. Step 1 moves the order to RETURN_IN_PROGRESS, and a second return request for an order in that state is refused. The saga id is derived from the return request, so a double click is also covered.

The expensive drill

Drill 2 on the refund step. A timeout followed by a retry with a new key refunds $98. The refund command must carry a stable key such as return-42:4, and the payment service must recognise it.

The review checklist

Take this to the design review of any saga. Each line is a question from one of the chapters.

Steps

  • Every step is typed: compensatable, pivot or retriable
  • The pivot is named, and nothing hard to undo comes before it
  • Every compensation can only fail temporarily

State

  • Every resting state has a name and a maximum age
  • The log is written before the command is sent, through an outbox
  • The saga id comes from the customer's intent

Participants

  • A repeated key returns the first result
  • An undo for an unknown step succeeds and leaves a tombstone
  • A step after its undo is refused
  • Each participant can report the status of a command key

Isolation

  • Every record another request can touch mid-saga has a countermeasure
  • Money and stock change by amounts, not by overwriting
  • Values the customer saw travel inside the saga

Time

  • Attempt timeout, step budget and saga deadline are set
  • Timers are rows, picked up by a sweeper
  • The customer is told at the pivot

Tests and operations

  • A test crashes the orchestrator after every log write
  • The three numbers are on a dashboard with alerts
  • There is a runbook and admin actions, and nobody edits rows by hand
  • A nightly reconciliation checks the services against each other
