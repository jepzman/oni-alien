Three notes in sixty seconds

Gist The outbox gets an event out of the producer safely. The broker copies it to every subscriber. The idempotent consumer survives a repeat. Each note fixed one hop. This deep dive follows one event across all of them, because the failures live between the hops.

Order 42 is placed: two mugs, $49. The Order service saves it and announces OrderPlaced. Three services care. Shipping creates a shipment, Email sends a confirmation, Loyalty adds 49 points. Three notes described the parts.

NoteIn one line
Transactional Outboxsave the order and the event in one transaction; a relay publishes the event later
Publish–Subscribe, Competing Consumersone event, a copy for every subscriber; several workers share each subscriber's load
Idempotent Consumerremember the ids you have handled, so a repeat does nothing
Each note fixed one hop. Nobody showed me the whole trip.

The notes are each correct. The trouble is in the joins. The relay can publish twice. The broker can deliver twice, or in a different order. The consumer can crash after the work and before the ack. This deep dive follows the event across all five points and makes the whole path reliable, which is a different job from making each part reliable.

chapter 2 · 2 min

What the guarantees really promise

Gist A sender that gets no confirmation must either resend, and risk a duplicate, or not resend, and risk a loss. There is no third option, so exactly-once delivery does not exist. What you can build is exactly-once effect: deliver at least once, and make repeats harmless.

Vendors and documentation use three phrases. Two of them describe what a hop can do. The third describes a result that you build.

PhraseMeaningWhat you see when things fail
At most oncesend it and don't checklost messages, never duplicates
At least onceresend until someone confirmsduplicates, never losses
Exactly oncethe effect happens oncenothing, if you did the work in this deep dive

Why delivery can't be exactly once

The relay sends OrderPlaced to the broker and waits for a confirmation. None arrives. There are two possible worlds: the message was lost on the way there, or the confirmation was lost on the way back. From the relay's chair they look identical. It has two choices.

  • Don't resend. In the first world the event is gone. That is at most once.
  • Resend. In the second world the broker now has two copies. That is at least once.

There is no third choice, and adding confirmations of confirmations only moves the doubt one step along. Every hop in the figure faces the same fork.

So “exactly once” on a product page always means: at least once, plus someone throwing away the repeats.

The ack decides which one you get

For a consumer, the choice is made by one line of code: where the ack goes.

Order of eventsCrash in the middle meansGuarantee
ack, then do the workthe broker thinks it's done; the work never happenedat most once
do the work, then ackthe work happened; the broker sends the message againat least once

Losing an order event is almost always worse than seeing it twice, so nearly every business system picks the second row. That choice has a price: duplicates are now a normal event, and every consumer must make them harmless. The rest of this deep dive is about paying that price properly.

A useful way to say it: delivery is at least once, processing is effectively once. The first is the transport's job. The second is yours.

checkpoint

A consumer acks the message as soon as it arrives, then starts the work. Which guarantee is that, and what is lost in a crash?

At most once. The broker believes the message is handled, so the work that was in progress never happens.

A product says “exactly-once delivery”. What question do you ask?

Exactly once between which two points? It usually covers the broker's own storage, not the effect in your database or an email.

chapter 3 · 3 min

The outbox, for real

Gist The outbox is a table with an id, an event id, a key and a sent mark. The relay publishes first and marks second, so it sometimes sends twice and never loses. Select rows by “unsent”, never by “higher than the last id I saw”, or late commits will be skipped.

The note said “write the event to an outbox table, and a relay publishes it”. Here is what that table and that relay look like when you have to build them.

place-order.sqlone transaction, two inserts
BEGIN;
INSERT INTO orders (id, customer_id, total, status)
VALUES (42, 7, 49.00, 'PLACED');

INSERT INTO outbox (event_id, key, type, payload)
VALUES ('e-9f31', 'order-42', 'OrderPlaced',
        '{"orderId": 42, "total": 49.00, "version": 1}');
COMMIT;
ColumnWhy it is there
idan increasing number, so the relay can read in order
event_idthe event's identity for its whole life; consumers dedupe on it (chapter 6)
keywhat must stay in order together: here, everything about order 42 (chapter 5)
type, payloadwhat happened, as the consumers will read it
sent_atempty until the relay has published the row
The event id is created here, once, by the producer. Not by the relay, not by the broker.

The relay, as a poller

relay.sqlevery 200 ms
BEGIN;
SELECT id, event_id, key, type, payload
FROM outbox
WHERE sent_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

-- publish each row to the broker and wait for its confirmation

UPDATE outbox SET sent_at = now() WHERE id IN (101, 102, 103);
COMMIT;

Publish first, mark second. If the relay crashes between the two, the rows are still unsent and go out again. So the relay is an at-least-once sender, by design.

The trap: “give me everything after id 102”

A tempting optimisation is to remember the highest id published and ask only for newer rows. It is faster than scanning for empty sent_at. It also loses events, because ids are handed out when a row is inserted and rows become visible when their transaction commits. Those are different moments.

TimeWhat happensRelay's high-water mark
10:00:00.000transaction A inserts outbox row 101, keeps working100
10:00:00.010transaction B inserts row 102 and commits100
10:00:00.200relay asks for id > 100, sees only 102, publishes it102
10:00:00.300transaction A commits; row 101 becomes visible102
10:00:00.400relay asks for id > 102. Row 101 is never read102

An event silently missing is the exact failure the outbox was meant to prevent. Selecting on sent_at IS NULL does not have this hole: row 101 is picked up on the next round, a little late and after 102. Late is acceptable here because the two rows belong to different orders.

Polling or reading the log

The other way to build the relay is change data capture: a connector reads the database's own transaction log and publishes each committed outbox insert.

PollerLog reader (CDC)
Order of eventsby id, with late commits arriving lateexact commit order
Delaythe polling intervalmilliseconds
Load on the databasea query every interval, even when idlealmost none
What you runa small loop in your servicea connector, its offsets and its monitoring
Still at least once?yesyes: the connector can re-read after a restart

Start with the poller. Move to the log reader when the polling delay or the query load starts to hurt, or when you already run CDC for other reasons.

Two housekeeping rules

  • One relay per key at a time. Two relays running side by side each take a batch and publish at their own speed, so events for the same order can overtake each other. Run one active relay, or split the outbox by key so each relay owns its slice.
  • Delete what you sent. An outbox that only grows makes every poll slower. A nightly job removes rows sent more than a few days ago. Keep those few days: they are your evidence when someone asks “did we publish it?”

checkpoint

Why does the relay publish before it marks the row as sent, and not the other way round?

Marking first and crashing before the publish would lose the event for good. Publishing first can only cause a repeat, which consumers handle.

You run three relay instances to go faster. What breaks?

Order within a key: two instances can publish events for the same order in the wrong sequence. Use one active relay, or give each a separate slice of keys.

Failure drills

Gist Six things that will happen to your events in production: a relay crash, a consumer crash, a message that can never succeed, the wrong order, a slow worker and a duplicate that arrives after you forgot its id. Each card ends with the rule that prevents it.

Same exercise as in the Saga dive: guess what happens next before you read on.
  • 1 · relay crash
  • 2 · consumer crash
  • 3 · poison message
  • 4 · wrong order
  • 5 · slow worker
  • 6 · forgotten id
Drill 1

The relay publishes, then dies

Timeline
The relay publishes OrderPlaced e-9f31. The broker confirms. The relay crashes before it sets sent_at.
What you see
After the restart the row still looks unsent, so it is published again. Shipping, Email and Loyalty each receive the event twice, a few seconds apart.
What saves you
Nothing at the relay: this is the fork from chapter 2, and resending is the right branch. The second copy carries the same event_id, and each consumer recognises it.

Rule: the relay will repeat itself. Give every event one id at birth, and never change it on a resend.

Drill 2

The consumer does the work, then dies

Timeline
Loyalty receives the event and adds 49 points. It crashes before the ack. The broker delivers the event to another Loyalty worker, which adds 49 more.
The tempting mistake
Keep a list of handled ids in a cache: check the list, do the work, add the id. A crash between “do the work” and “add the id” leaves the same hole. Adding the id first moves the hole: now a crash loses the points.
Why
The work and the memory of the work are two writes. If they can be separated by a crash, one of them will be missing sooner or later. It is the outbox problem again, on the receiving side.
What saves you
Put the id and the work in one transaction in the consumer's own database: insert the id into a processed_events table, add the points, commit, then ack. A repeat fails on the insert and skips the work.

Rule: the record that you handled a message lives in the same transaction as the handling.

Drill 3

A message that can never succeed

Timeline
An OrderPlaced arrives with a postcode that Shipping's parser rejects. Shipping throws, the broker redelivers, Shipping throws again.
What you see
One of two pictures. On a queue, the bad message cycles for ever and burns CPU. On an ordered log, it is worse: the worker cannot move past it, so every later order on that partition waits. One bad postcode has stopped shipping.
What saves you
Count the attempts. Errors that might pass later (a timeout, a lock) get a few retries with growing waits. Errors that will never pass (a parse failure, a broken rule), and anything still failing after the limit, go to a dead-letter queue with the reason attached. The worker acks and moves on. Chapter 7 covers what happens to the letter after that.

Rule: every message leaves the main flow in bounded time: done, or set aside where a person will see it.

Drill 4

The cancel arrives before the order

Timeline
The customer places order 42 and cancels it two seconds later. Shipping sees OrderCancelled first. It finds no shipment to cancel and ignores the event. Then OrderPlaced arrives and a shipment is created for a cancelled order.
Why
Several things reorder messages: two relays, two workers on one queue, or a retry that sends the first event to the back of the line. Any one is enough.
What saves you
Two layers. First, keep related events in line: publish with key = order-42 so they share a partition and a single worker. Second, make the consumer able to tell: each event carries the order's version (1, 2, 3…), and the consumer stores the last version it applied. An event with an older version is ignored. An event that skips a version is parked until the gap is filled.

Rule: ask for order by key, and carry a version anyway, because order is the first thing a failure takes away.

Drill 5

The worker is slow, so the broker gives up on it

Timeline
Email takes 40 seconds to send during a provider slowdown. The broker waits 30 seconds for an ack, decides the worker is dead and hands the event to a second worker. Both send the confirmation.
What you see
Duplicates that appear only on slow days, which makes them hard to reproduce. The usual “check the id, then work” does not help: both workers checked while neither had finished.
What saves you
Three things together. Set the broker's wait well above the slowest normal processing time. Have long jobs tell the broker they are still alive. And claim before working: insert the id first, under a unique constraint, so the second worker's insert fails at once.

Rule: two workers can hold the same message at the same moment. Only a unique constraint settles who owns it.

Drill 6

The duplicate that arrives after you forgot

Timeline
Loyalty deletes processed ids after 7 days to keep the table small. On day 9 an operator replays last week's events to repair a different service. Loyalty no longer knows the ids and adds every customer's points again.
Why
Deduplication has a memory, and the memory has a length. A duplicate older than that length is treated as new.
What saves you
Keep ids for longer than a message can possibly come back: the broker's retention period plus your replay window. Better still, where the operation allows it, do not rely on memory at all. “Points for order 42 = 49”, stored once per order, stays correct however late the repeat arrives.

Rule: know how long your dedupe memory is, and make sure nothing can be redelivered from further back.

checkpoint

Loyalty checks a cache for the event id, adds the points, then writes the id to the cache. Name two drills this fails.

Drill 2: a crash after the points and before the cache write repeats the points. Drill 5: two workers both check before either writes.

Why is a poison message worse on an ordered log than on a plain queue?

On a log the worker reads in sequence and cannot pass the failing message, so every later event on that partition waits behind it.

Ordering: the hard problem

Gist Order across everything is unaffordable. Order per key is cheap: pick a key, and the broker keeps that key's events in one line with one reader. Retries, extra workers and resizing still break it sometimes, so carry a version in every event and let the consumer keep the newest.

“Events arrive in order” can mean two things, and only one of them is affordable.

Kind of orderMeaningCost
Total orderevery event in the system, one after anotherone line, one worker: no parallel work at all
Order per keyevents about the same thing stay in sequence; different things are independentparallel across keys

Nobody needs order 43's payment to wait for order 42's cancellation. What matters is that order 42's own events are seen as placed, paid, cancelled. So choose a key, and ask for order within it.

Choosing the key is a design decision. Order id? Customer id? It decides what can run in parallel.

How order gets lost anyway

CauseWhat happens
Several workers on one plain queuethe note's competing consumers: fast, and no order at all
A retryevent 2 fails and is retried later; event 3 has already gone through
The number of partitions changesthe same key now hashes to a different partition; old and new events are read by different workers
Two relaysfrom chapter 3: each publishes its batch at its own pace

The retry dilemma

The second row deserves a decision, because you cannot have everything. When event 2 for order 42 fails:

ChoiceYou keepYou pay
Block: retry in place until it passesordereverything behind it on that partition waits. One bad event stalls many orders (drill 3)
Step aside: move it to a retry queue, carry onflowevent 3 is processed before event 2
Step aside per key: park event 2 and later events for order 42 onlyboth, for every other orderthe consumer must remember which keys are parked

Most teams start with “step aside” and make the consumer safe against the reordering. The third option is the best behaviour and the most code.

Design events so that order matters less

The cheapest defence is in the event itself.

Event styleExampleIf it arrives late or twice
Delta“add 49 points”wrong total. Needs dedupe and order
Fact with identity“order 42 earned 49 points”safe to repeat: one row per order
State with version“order 42 is CANCELLED, version 3”safe to repeat and to reorder: keep the highest version

An event that carries the current state and a version lets the consumer apply a simple rule: if this version is higher than mine, take it; otherwise ignore it. Late and duplicate events both fall out for free. The cost is a larger event, and consumers that only learn the latest state, not each step in between.

checkpoint

You key order events by customer id, not order id. What do you gain and lose?

All of a customer's orders stay in sequence, which helps anything computed per customer. You lose parallelism: one busy customer's events all queue behind each other.

Why does “state with version” survive both a duplicate and a late arrival?

A duplicate has the same version as the stored one and a late event has a lower one. The rule “apply only if higher” ignores both.

The idempotent consumer, in depth

Gist Three techniques: operations that are naturally repeatable, a dedupe table written in the same transaction as the work, and a version check. Dedupe on the producer's event id. When the work happens outside your database, pass the id on or route the work through an outbox of your own.

The note gave the idea: remember ids. In practice there are three techniques, and a consumer usually needs to pick one per kind of work.

TechniqueHowFits
Naturalthe operation gives the same result when repeated: set a status, upsert a row keyed by orderstate changes, “one row per order” facts
Dedupe tableinsert the event id under a unique constraint, in the same transaction as the workanything that changes your own database
Version checkapply only if the event's version is newer than the stored onekeeping a copy of someone else's state
handle-order-placed.sqlLoyalty: claim, work, commit, then ack
BEGIN;
INSERT INTO processed_events (consumer, event_id)
VALUES ('loyalty', 'e-9f31')
ON CONFLICT DO NOTHING;
-- 0 rows inserted? It is a repeat: COMMIT, ack, stop.

UPDATE loyalty_accounts
SET points = points + 49
WHERE customer_id = 7;
COMMIT;
-- only now: ack the message
Three consumers, three dedupe tables. Shipping having seen e-9f31 says nothing about Loyalty.

Which id?

CandidateVerdict
The event_id the producer wrote into the outboxyes. It is the same on every resend, from every hop
The broker's message id or offsetno. A resend by the relay is a new broker message with a new id
A hash of the payloadno. Two real orders for the same mugs at the same price look like one

When the work is outside your database

Email cannot put “send the confirmation” inside a database transaction. The claim and the work are separated again, and a crash can fall between them. There are three ways out, in order of preference.

  1. Pass the id on. If the email provider or payment API accepts an idempotency key, send the event_id with the call. Now a repeat is the provider's duplicate to drop.
  2. Use your own outbox. In one transaction, claim the event id and write “email to send” to an outbox of your own. A relay performs the send. You have turned an external side effect into the problem already solved in chapter 3.
  3. Accept the rare repeat, on purpose. For a confirmation email, two copies once in a great while may be an acceptable cost. For a payment it is not. Write the decision down so it is a choice and not an accident.

Keeping a copy of someone else's state

Shipping keeps a small table of orders so it does not have to call the Order service. The version check keeps that copy correct whatever the arrival order.

apply-order-event.sqlduplicates and stale events change nothing
INSERT INTO order_copy (order_id, status, version)
VALUES (42, 'CANCELLED', 3)
ON CONFLICT (order_id) DO UPDATE
SET status = EXCLUDED.status, version = EXCLUDED.version
WHERE order_copy.version < EXCLUDED.version;

No dedupe table is needed for this handler. A repeat has an equal version and a late event has a lower one, and both leave the row alone.

checkpoint

Why is the broker's message id a poor dedupe key?

The relay's resend creates a new broker message with a new id, so the two copies look different.

Email's provider has no idempotency key. How do you avoid a double send after a crash?

Claim the event id and write “email to send” to Email's own outbox in one transaction; a relay does the send. A repeat of the event then finds the id already claimed.

Dead letters, retries and replay

Gist Retry in tiers: a few times at once, then with growing delays, then the dead-letter queue. That queue needs an alert, an owner and a way to send letters back. Replay re-reads old events to repair or rebuild, and it is safe only if handlers are idempotent beyond any time window and outside side effects are guarded.

Drill 3 ended with the bad message in a dead-letter queue. That is where many teams stop, and where the message stays until someone finds four thousand of them a year later.

Retry in tiers

TierWaitFor
1 · at oncenone, up to 3 timesa lock, a dropped connection
2 · delayed10 s, 1 min, 10 mina dependency that is down or slow
3 · dead letteruntil a person actserrors that will not pass, and anything that used up tiers 1 and 2

The delayed tier matters most. A consumer that retries at once, for ever, against a database that is restarting turns one problem into two. The waits use the same growing, randomised delays as the Retry note.

Classify the error before choosing a tier. A timeout may pass later. “Unknown postcode format” will not, so it skips straight to tier 3.

A dead-letter queue is a process

StepWhat it needs
Noticean alert when the queue is not empty; the count on a dashboard
Understandeach letter keeps the original event, the error text, the attempt count and the time
Fixdeploy the handler fix, or correct the data at its source
Redrivea button or script that sends the letters back to the main queue
Closethe queue returns to zero; someone writes down the cause
If nobody owns the dead-letter queue, it is a slower way of losing messages.

Redriving is safe only because consumers are idempotent. Some of those letters may have been partly handled before they failed, and some may be sent back twice by an impatient operator.

Replay

A broker that keeps its events lets you read them again from an earlier point. That is useful in three situations.

SituationReplay
A new service needs historyLoyalty launches in March and reads every order since January to compute starting balances
A bug damaged dataShipping mis-read weights for two days; fix the code, replay those two days
A copy was lostrebuild a search index or a read model from the first event

Replay is powerful and it is where drills 4 and 6 meet. Before you allow it, check three things.

  • Handlers are idempotent beyond the dedupe window. Replayed events are old. Natural idempotency and version checks survive that; a seven-day id table does not (drill 6).
  • Side effects are guarded. Replaying January must not email ten thousand customers “your order is confirmed”. Handlers that talk to the outside world either check a replay flag on the consumer or skip events older than a cut-off time.
  • The events still exist. Retention is a decision. Seven days of history supports bug repair. Rebuilding from the first event needs the topic kept for good, or a snapshot plus recent events.

checkpoint

An event fails with “connection refused” to the database. Which tier, and why not the dead-letter queue?

Tier 2, delayed retries. The error will pass when the database is back; sending it to a person would be noise.

What makes redriving a dead-letter queue safe?

Idempotent consumers. A redriven letter may have been partly handled before, or may be sent twice.

Running it: lag, numbers and a runbook

Gist Watch four numbers: the age of the oldest unsent outbox row, each consumer's lag measured in time, the share of redeliveries and the dead-letter count. Put the event id in every log line. When a customer says “it never arrived”, walk the path from the outbox forward.

A messaging path fails quietly. Nothing throws; events just arrive later and later. Four numbers make that visible.

MetricWhereHealthyIt means trouble when
Outbox age: age of the oldest unsent rowproducerunder a secondit climbs: the relay is down or the broker refuses
Consumer lag: events published but not yet handled, and the age of the oldesteach consumersecondsit climbs steadily: the consumer is too slow or stuck on one message
Redelivery rate: share of deliveries that are repeatseach consumerwell under 1 %it jumps: timeouts are too short, or a worker keeps crashing
Dead letters: count waitingeach consumerzeroabove zero
Measure lag in time, not only in messages. “4,000 behind” means little. “Shipping is 6 minutes behind” means a lot.

Follow one event

Every log line carries the event_id, and the event carries the id of whatever caused it. One search then shows the whole trip:

Numbers worth working out once

The shop takes 50 orders a second at peak, and each order produces about 3 events.

SettingReasoningValue

When the consumer cannot keep up

Lag that grows during a peak and shrinks afterwards is the queue doing its job. Lag that only grows needs action, in this order: find out whether one message is blocking the line (drill 3); add workers, up to the number of partitions; make the handler cheaper, often by batching its database writes; and only then add partitions, remembering from chapter 5 that this reshuffles keys.

Runbook: “the customer never got a shipment”

  1. Find the order's row in the outbox. Missing? The bug is in the producer's transaction. Unsent? Look at the relay.
  2. Sent? Search the logs for the event_id on the consumer side.
  3. No trace there? Check the consumer's lag: the event may simply not have been reached yet.
  4. A trace ending in an error? Look in the dead-letter queue, fix, redrive.
  5. Marked handled but no shipment? The handler claimed the id and then lost the work, which means the two were not in one transaction (drill 2).

checkpoint

Outbox age is flat at zero but Shipping's lag keeps growing. Where is the problem?

On the consumer side: Shipping is too slow or stuck on one message. The producer and relay are fine.

The redelivery rate jumps from 0.2 % to 15 % during a slow afternoon. Likely cause?

Handling time has grown past the broker's wait for an ack, so messages are handed to a second worker while the first is still busy (drill 5).

Testing, and events as contracts

Gist Cause the bad moments on purpose: deliver everything twice, shuffle events within a key, crash the relay and the consumer at the worst point. Treat an event's shape as a public interface: add optional fields freely, and never remove, rename or change the meaning of one without a new version.

Most messaging bugs need a crash or a repeat at an exact moment, which never happens on a developer's laptop. So the tests have to cause those moments on purpose.

TestHowCatches
Deliver everything twicea test broker hands each message to the handler two timesany handler that is not idempotent (drills 1, 2)
Shuffle within a keydeliver order 42's events in every possible sequencehandlers that assume order (drill 4)
Crash the relaystop it after publish, before the mark; restartevents lost or stuck (chapter 3)
Crash the consumerstop it after commit, before the ack; redeliverwork done twice (drill 2)
Two workers, one messagestart the same message on two workers at oncecheck-then-work races (drill 5)
Poisonsend a message that always failsmissing retry limit or dead-letter route (drill 3)
loyalty.test.tsthe cheapest, most valuable test
test("every event twice gives the same balance as once", async () => {
  const events = [orderPlaced(42, 49), orderPlaced(43, 20), orderCancelled(43)];

  const once = await run(events);
  const twice = await run(events.flatMap((e) => [e, e]));

  expect(twice.balanceOf(7)).toBe(once.balanceOf(7));
});
Run the whole consumer test suite in “everything twice” mode. If it still passes, the consumer is idempotent.

Events are contracts

The producer cannot see its consumers, which was the point of publish–subscribe. It also means the producer cannot see whom it breaks. Rename total to amount and Loyalty starts awarding zero points, with no error anywhere. An event's shape is a public interface and needs the same care as an API.

ChangeSafe?Why
Add an optional fieldyesold consumers ignore it
Add a new event typeyesconsumers that don't know the type must skip it, not crash
Remove or rename a fieldnoconsumers reading it get nothing
Change a field's meaning or unitnothe worst kind: nothing fails, the numbers are just wrong
Make an optional field requirednoold events in the topic, and replays, do not have it

Two habits keep this manageable. Consumers are tolerant readers: they take the fields they need and ignore the rest. And a breaking change is made as a new version beside the old one: publish OrderPlaced.v2 as well as v1, move consumers across one by one, then stop publishing v1. It is the expand-and-contract move from the data volume, applied to events.

A schema registry or a contract test in the producer's build makes the rule automatic: the build fails if a change would break a registered consumer. Remember that replay makes old events live for ever, so “every consumer has upgraded” does not mean old shapes are gone.

checkpoint

You change total from dollars to cents. No test fails. Why is this the most dangerous kind of change?

Every consumer still parses the event, so nothing errors. Loyalty simply awards a hundred times the points until someone notices.

All consumers have moved to OrderPlaced.v2. Can handlers drop support for v1?

Only if no v1 events can come back. A replay of an older period still contains them.

Brokers, a lab and the checklist

Gist Queues hand a job to one worker and forget it; logs keep events in order per partition and let you read them again. Neither makes your consumer idempotent. The lab applies the whole deep dive to a stock counter, and the checklist turns it into review questions.

Rule of thumb from class: commands and jobs like queues, facts like logs.

Three product claims are worth reading carefully.

  • “Exactly-once” in a log broker usually means: reading from one topic and writing to another can be made atomic inside the broker. Your own database, an email or a payment call are outside that boundary, and chapters 4 and 6 still apply.
  • Built-in deduplication in a queue service works on an id you supply and remembers it for a limited window, often minutes. It removes quick repeats from a producer. It is not a replacement for an idempotent consumer.
  • Outbox support exists in CDC connectors and in several messaging libraries. It saves you writing the relay. The table, the key and the event id are still your design.

Lab

The shop adds a Stock service. It must lower the stock count when an order is placed and raise it again when an order is cancelled. The warehouse also sends a nightly StockCounted event with the true number on the shelf.

  1. What is the key for these events, and why?
  2. OrderPlaced for two mugs arrives twice. Which technique from chapter 6 do you use?
  3. OrderCancelled arrives before OrderPlaced. What does Stock do?
  4. StockCounted says 80. How do you apply it safely next to the order events?
  5. Someone replays last week. What must not happen, and what guarantees it?

model answer

1 · The key

The product, not the order. Stock for mugs is the thing that must change in sequence, and one order can touch several products. So the Order service publishes one stock-relevant event per order line, keyed by product id. Orders for different products run in parallel.

2 · The duplicate

“Lower by 2” is a delta, so it is not naturally idempotent. Store a reservation row per order line, (order 42, mug) = 2, under a unique constraint, and compute stock as the count minus the reservations. A repeat hits the constraint and changes nothing. That is the “fact with identity” style, and it needs no id memory that could expire.

3 · Cancel first

Record the cancellation for (order 42, mug) even though no reservation exists. When OrderPlaced arrives later, Stock sees the cancellation and creates nothing. It is the tombstone from the Saga deep dive, and the order's version number makes the check simple.

4 · The nightly count

StockCounted is state with a version: “80 on the shelf as of 02:00”. Store the count and its time. Reservations made before 02:00 for orders already picked are inside that number; later ones are subtracted from it. Applying the same count twice changes nothing, and an older count than the stored one is ignored.

5 · Replay

Stock must not be lowered a second time for last week's orders. Reservation rows per order line guarantee it, because they do not depend on a dedupe window. A seven-day processed_events table on its own would not.

The review checklist

Producer

  • The state change and the event are written in one transaction
  • Every event has an id created once, a key and a version
  • The relay publishes, then marks, and selects by “unsent”, not by highest id
  • One active relay per key; sent rows are cleaned up

Consumer

  • The ack comes after the commit
  • The id claim and the work are in one transaction, under a unique constraint
  • Dedupe uses the producer's event id
  • Outside side effects pass the id on, or go through the consumer's own outbox

Order

  • The key is chosen on purpose and written down
  • Handlers ignore older versions and cope with a gap
  • It is decided what a failing event does: block, step aside, or park its key

Failure

  • Retries are bounded and delayed; permanent errors skip them
  • The dead-letter queue has an alert, an owner and a redrive tool
  • Dedupe memory is longer than retention plus the replay window
  • Replay cannot repeat outside side effects

Contracts

  • Consumers ignore fields and event types they don't know
  • Breaking changes ship as a new version beside the old
  • A build check protects registered consumers

Tests and operations

  • The consumer suite passes with every message delivered twice
  • Events for one key are tested in shuffled order
  • Outbox age, lag in time, redelivery rate and dead letters are on a dashboard
  • One search by event id shows the whole trip
