Four notes in sixty seconds

Gist Write–audit–publish gates what users see, contracts catch changes in the producer's CI, quality checks quarantine bad rows and stop bad batches, and the DAG knows what feeds what. Week 23 had all four in some form, and still let four of five incidents through.

Week 23 at the shop. The pipeline from the dive on app databases and warehouses is running: CDC, raw, staging, marts, a revenue dashboard. It has tests. Five things go wrong in five days, and the tests catch one of them.

Every incident here comes from a real category of data failure: freshness, uniqueness, schema, distribution, completeness.

Each note solves one piece. This dive is about the system they make together: where each kind of check belongs, why most pipelines test the wrong things, how strict to be without drowning in alerts, how to test the tests themselves, and what to do in the hour after a check fires. By the end, all five of week 23's incidents are caught before the dashboard, four of them automatically.

Why the tests gave false confidence

The shop had 41 tests and a green CI badge. Every one of them passed during week 23, and every one was correct. They checked that columns weren't null, that statuses were known, that prices were positive: properties of individual rows. None checked whether the data had arrived, whether all of it had arrived, or whether it agreed with the source. A test suite can be thorough and still miss everything that matters, if it measures the wrong dimension.

chapter 2 · 3 min

The real mechanism: six checkpoints

Gist Checks can run in the producer's CI, on arrival, on rows in staging, as an audit before publish, as monitors on published tables, and as a nightly reconciliation. Each catches different failures. Sorted by the five quality dimensions, most pipelines test validity and forget freshness, completeness and consistency.

A check is only useful where it can stop something. The pipeline has six places to check data, and each catches a different kind of failure at a different cost.

What each checkpoint is for

CheckpointChecksOn failureWeek 23
1 · contract (producer CI)schema changes against the agreed contractthe producer's build failsWed, before release
2 · arrival (raw)file or batch present, row count, schemastop the run, alert the source ownerMon
3 · rows (staging)not null, types, accepted values, ranges, foreign keysrow to quarantine; too many → stopThu, with the right range
4 · audit (before publish)unique keys, counts and sums by segment, reconciliation of the batchdon't publish; yesterday staysTue, Fri
5 · monitor (after publish)freshness, volume and distribution over timealert; banner on the dashboardMon, as a backstop
6 · reconcile (nightly)counts and sums per day against the sourcea named day to replayeverything else
Checkpoints 1 to 4 prevent. Checkpoints 5 and 6 detect. You need both, because prevention is only as good as your imagination.

The five dimensions of data quality

Every check tests one of five things. Sorting the shop's existing tests this way showed the gap at once: almost all of them tested validity, and none tested completeness or freshness.

DimensionQuestionTypical checkShop's tests before week 23
freshnessis it recent?newest event time vs now0
volume / completenessis it all there?row counts by segment vs the usual1 (total only)
uniquenessis anything doubled?key unique in every published table2 (staging only)
validityare values allowed?not null, types, ranges, accepted values37
consistencydoes it agree with elsewhere?reconciliation, sums across layers0

Validity tests are easy to write, so pipelines collect them. Freshness, completeness and consistency are the ones that catch outages, and they are the ones people forget.

Where results go

A check that only prints to a log can't be trended, alerted on consistently or shown on a dashboard. Every check writes one row per run to a results table: the check, the table, the partition, the status, the measured value, the threshold, and the severity. Chapter 6's alert arithmetic, chapter 7's fault tests and chapter 8's health dashboard are all queries on this one table.

check_results.sqlone row per check per run
CREATE TABLE check_results (
  run_id text, run_day date, checked_at timestamp,
  check_name text, table_name text, partition_key text,
  dimension text,            -- freshness | volume | uniqueness | validity | consistency
  severity text,             -- block | quarantine | warn
  status text,               -- passed | warned | quarantined | blocked
  measured numeric, threshold_low numeric, threshold_high numeric
);

Checks belong in the DAG

A check scheduled separately from the pipeline can run before the data it checks, or after users have already seen it. Make checks steps in the same DAG: arrival checks between landing and staging, the audit between building and publishing, so a blocking failure stops everything downstream by itself. Monitors and reconciliation run after the publish step, as their own branch, so their failures alert without holding anything back.

checkpoint

Which checkpoints prevent and which detect?

Contract, arrival, row checks and the audit prevent bad data being published; monitors and reconciliation detect after.

Which quality dimensions catch outages most often?

Freshness, completeness and consistency, the ones pipelines usually don't test.

Failure drills

Gist Six incidents: a green job that loaded nothing, a replayed hour duplicated in the fact table, prices in cents that passed a wide range, a missing shop hidden in a normal total, a new status that blocked everything, and a real alert lost among false ones.

Each drill is one day of week 23, with the check that would have caught it.
  • 1 · green and empty
  • 2 · replayed hour
  • 3 · cents
  • 4 · a shop missing
  • 5 · new status
  • 6 · the ignored alert
Drill 1

Green and empty

Timeline
Monday 05:00 the marketplace partner's file arrives with a header and no rows. The load runs, inserts zero rows, and succeeds. The scheduler shows green. The dashboard shows Sunday's marketplace sales as €0, which looks like a slow Sunday.
Tempting mistake
Make the job fail on zero rows. Then a genuine quiet holiday fails it too, and the next time someone adds “allow empty” to make it pass.
Why
Job status says the code ran without error. It says nothing about the data. An empty or stale input is not an error to the code.
What saves you
Check the data, not the job: on arrival, compare row count with the same weekday's usual (zero against 3,200 fails); on the dashboard's tables, alert when the newest event is older than its freshness target. Show “data as of” on the dashboard, so users see staleness themselves.

Rule: a green job is not fresh data. Monitor the data's age and volume, not the scheduler.

Drill 2

The hour that happened twice

Timeline
Tuesday the CDC connector restarts after a deploy and replays an hour of order-line events from its last saved position. Staging dedupes them; the fact load appends from a temporary table that didn't. 4,100 lines are doubled in fct_sales. Revenue for Tuesday morning is up 30 %.
Tempting mistake
Add a dedupe step to the fact load. Right fix for this load, but the next table built by someone else will have the same gap.
Why
Uniqueness was tested where it was easiest (staging), not where it matters (every published table). Replays are normal for at-least-once systems.
What saves you
Make the fact load idempotent (a MERGE on the line id), and test the primary key of every published table in the audit before publish. The unique test on fct_sales.order_line_id stops the publish; yesterday's correct table stays up.

Rule: test keys where data is published, not where it is convenient. Replays will happen.

Drill 3

Prices in cents

Timeline
Thursday a firmware update on Delft's tills sends unit prices in cents. The €39 kettle arrives as 3,900. The range check allows prices up to €10,000 (there's a €4,000 sofa), so every row passes. Delft's revenue for the day is €1.4 million.
Tempting mistake
Tighten the range to €2,000. Then the sofa is quarantined every time it sells.
Why
A range across all products is too wide for any one product. The rows were valid in isolation; the change was in their distribution.
What saves you
Check against each product's own history: unit price within ±50 % of the product's list price, or a distribution check per shop (median price per line jumping 100× in one shop). Add a batch check on revenue per shop against its usual for the weekday.

Rule: valid in isolation isn't right. Compare values with their own history, per product or per shop.

Drill 4

The shop that wasn't there

Timeline
Friday the Rotterdam shop's till upload fails. The day's total is €640,000 instead of about €690,000: 7 % low, well inside the ±30 % volume band. Nothing fires. Rotterdam's manager asks on Monday why their shop sold nothing on Friday.
Tempting mistake
Narrow the band to ±5 %. Then normal weather and promotions fire it twice a week.
Why
One shop is 7 % of the total. A completeness check on the total can't see a missing part smaller than the total's normal variation.
What saves you
Check completeness by segment: every shop that was open has rows today, and each shop's volume is within its own band. A missing segment is a hard fail, however small. The list of expected segments comes from a dimension (shops open today), not from yesterday's data.

Rule: completeness is checked per segment. A missing part hides inside a healthy total.

Drill 5

The status nobody expected

Timeline
The app team adds an order status, partially_refunded. The accepted-values test on status fails, the run stops, and the dashboard stays on yesterday's data for a day while two teams argue whether the test or the app is wrong.
Tempting mistake
Remove the accepted-values test, because it “breaks every release”.
Why
The test was right to notice; the response was wrong. A new value isn't bad data, it's an undeclared change. Failing the whole publish for it treated a contract gap as corrupt data.
What saves you
Put accepted values in the data contract, so the app's CI flags the new status before release and the data team adds handling first. In the pipeline, make unknown values a warn that quarantines the affected rows and alerts, rather than an error that blocks everything; reserve errors for what makes the published numbers wrong.

Rule: a new value is a contract change. Catch it in the producer's CI; in the pipeline, quarantine and warn, don't block everything.

Drill 6

The alert that cried wolf

Timeline
The shop has 240 tests and 30 anomaly monitors. Each fires falsely about once a month. That's eight or nine alerts a day in the team channel. On the Thursday of week 23 the real alert for Delft's prices is the sixth message that morning. Nobody opens it.
Tempting mistake
Mute the noisy channel. The real alerts go with it.
Why
Alert volume, not alert quality, decides whether alerts are read. Many slightly-wrong checks are worse than a few strong ones.
What saves you
Tier by consequence: page or message only for checks protecting published numbers (freshness, keys, segment completeness, reconciliation); send the rest to a daily digest. Measure each check's false alert rate and fix or remove any above one a quarter. Every alert names the table, the dashboards affected (from lineage) and the owner.

Rule: few strong alerts that get read beat many weak ones that don't.

What the six drills add up to

HabitDrill

checkpoint

A shop's sales are missing but the daily total is within its band. Which check catches it?

Completeness per segment: every open shop has rows, from the shop dimension.

Why not make every failed check block the publish?

New values and edge-of-band volumes aren't wrong numbers; blocking for them stops the pipeline often until checks get disabled.

The hard problem: which checks, how strict

Gist Start from what users need: data SLOs for freshness, completeness, uniqueness and accuracy, written in their words. Derive checks from them, prefer hard rules over statistical bands, use calendar-aware bands where values vary, and give every check a severity: block, quarantine or warn.

Writing checks is easy. Deciding which checks, how strict, and what happens when they fire is the hard part. Too loose and week 23 happens; too strict and the pipeline stops for every holiday, until someone disables the checks. The way out is the same as for services: decide what users need from the data, write it down as objectives, and derive the checks from them.

Data SLOs for the revenue dashboard

ObjectiveTargetMeasured byWeek 23 would have…
freshnessdata at most 45 min old in opening hours, 99 % of the timenewest event time in fct_salescaught Monday
completenessevery open shop present, every dayshops with rows vs shops opencaught Friday
uniquenessno duplicate order lines, everunique test on publishcaught Tuesday
accuracydaily revenue within 0.1 % of the source after 24 hnightly reconciliationcaught Thursday by morning
A data SLO is a promise to the dashboard's users, not to the engineers. Write it in their words: “at most 45 minutes old”.

Each objective tells you what to check, where, and how bad a miss is. Freshness and completeness block nothing; they alert and show a banner, because old-but-correct beats nothing. Uniqueness blocks the publish, because duplicated revenue is worse than yesterday's revenue. Accuracy is measured after the fact and points at a day to replay.

An error budget for data

A 99 % freshness objective in opening hours (about 300 hours a month) allows three hours a month of stale data. That budget is useful in two directions. When it is nearly spent, the team stops adding features to the pipeline and fixes reliability. When it is barely touched month after month, the team can stop gold-plating and accept a riskier change, such as moving to a new connector. Week 23 spent the whole monthly budget on Monday morning alone.

Setting thresholds that survive holidays

ApproachExampleGood forWatch out
fixedrow count > 50,000nothing that variesfails every Sunday and holiday
same weekday bandwithin ±30 % of the median of the last 6 same weekdaysdaily volumeholidays and big promotions
calendar-awareband from the same weekday, holidays from dim_date excluded or modelledretail with seasonalityneeds a maintained calendar
learned anomalya tool fits a seasonal model per tablemany tables, little timeopaque; review what it flags
hard ruleevery open shop has rowscompleteness, keysnone: it's a definition

Use hard rules wherever a check can be stated as a definition (keys, required segments, reconciliation), and statistical bands only for genuinely variable quantities. Most of week 23's failures were catchable with hard rules.

Block, quarantine or warn

SeverityUse whenEffect
block (error)the published number would be wrong: duplicate keys, a missing segment, failed reconciliation of the batchdon't publish; yesterday stays; page the owner
quarantinesome rows are bad, the rest fine: invalid values, unknown codesrows set aside; publish the rest; alert if over 1 %
warnsomething changed that may be fine: a new value, a volume at the edge of its bandpublish; daily digest; review

Every check gets one of the three, chosen from the objective it protects. The common mistake is making everything a block (the pipeline stops weekly, checks get disabled) or everything a warn (week 23).

checkpoint

What should a freshness miss do to the dashboard?

Alert and show a banner with the data's age; old but correct beats nothing.

When is a statistical band the right check?

Only for genuinely variable quantities like daily volume; definitions such as keys and required segments are hard rules.

Four ways to data quality

Gist Tests in the transform detect after tables are visible. Adding write–audit–publish turns them into a gate. An observability tool watches every table for the unexpected. Contracts move schema and value changes into the producer's CI. The backbone is the gate; the others are nets.

Four common ways to get data quality, compared on week 23. Real pipelines combine them; the question is which to start with.

Variant A alone tests tables that users can already see, so a failure is detected, not prevented. Adding write–audit–publish (B) turns the same tests into a gate. An observability tool (C) watches everything continuously and learns seasonal patterns, which covers what nobody thought to test, but it sees problems after publishing and needs its alerts tuned (drill 6). Contracts (D) catch schema and value changes in the producer's pull request, the cheapest moment, but only for producers that adopt them.

An observability tool, tuned

Switched on across all 400 tables, a monitoring tool's first week at the shop produced 60 anomaly alerts, most of them correct statistically and useless in practice: a staging table nobody reads, a backfill that was planned. Tuning took a month: monitors only on tables with a consumer (from lineage), the shop's holiday calendar fed in, planned backfills announced to the tool, and each monitor given an owner and a tier. After that it caught two things nobody had a test for in its first quarter: a slow drift in the share of web orders without a customer, and a lookup table that stopped updating.

Why do tests alone not stop bad data reaching users?

They run after the tables are built and visible; without a gate, failures are detected, not prevented.

What does an observability tool add?

Continuous freshness, volume and distribution monitoring on every table, including things nobody wrote a test for.

chapter 6 · 2 min

Data quality in numbers

Gist Two hundred and seventy checks that each fire falsely once a month make nine interruptions a day. Tiering cuts that to one every few days, and real incidents get seen. Checks are cheap if scoped to the partitions a batch touched. Detection time depends on where the check runs.

Data quality has a budget: compute for the checks, and attention for the alerts. Attention runs out first.

The alert arithmetic

BeforeAfter tiering
checks270270
false alert rate per check~1 a month~1 a quarter (tuned or removed)
alerts that interrupt someone~9 a day~0.3 a day (only blocking and SLO checks)
alerts in the daily digest0~3 a day
share of real incidents seen within an hour~20 %~90 %
A check that fires falsely once a month looks harmless. Two hundred of them are nine interruptions a day.

What the checks cost to run

Most checks are an aggregate over one day's partition: a count, a sum, a group by shop. On the shop's warehouse each costs well under a second and a few megabytes scanned. Uniqueness on a published table is the expensive one if done naively (a full scan for duplicates); restrict it to the partitions the batch touched, which is enough because untouched partitions were checked when they were published. The nightly reconciliation reads 60 days of source data from a replica: the biggest single check, and the most valuable.

Choosing a band width, worked

Rotterdam's Friday revenue over the last six Fridays: €46k, €51k, €44k, €49k, €62k (a promotion), €48k. The median is €48.5k. A band of ±30 % around it (€34k to €63k) contains every normal Friday, including the promotion. A missing upload (€0) is far outside. A till that drops half its rows (€24k) is outside too. A ±10 % band would have fired on the promotion and on one ordinary Friday. The rule of thumb the shop uses: set the band just wide enough that the last eight same weekdays all pass, then check that the faults you care about (zero, half, double) all fail. If they don't, the quantity is too noisy for a band and needs a hard rule instead.

Detection time is set by where the check runs and when the data arrives. A check on arrival detects within minutes of the source failing; a check on the dashboard's tables only after the next publish; a user only when they look.

checkpoint

Why scope uniqueness tests to touched partitions?

Untouched partitions were checked when published; a full scan every run is cost without benefit.

What decides how fast an incident is detected?

Where the check runs relative to the failure: on arrival within minutes, after publish later, by a user last.

chapter 7 · 3 min

Testing the checks

Gist Inject faults into a test environment (an empty file, a replay, a rename, prices × 100, a missing shop, a new value) and assert the right check fires at the right severity. Keep a coverage map by table and quality dimension, and make every new check name its objective and proving fault.

Checks are code, and untested code is wrong in ways you find out about later. The shop learned in week 23 that 37 validity tests had given it confidence and no protection. The fix is to test the checks the way you'd test a smoke alarm: make some smoke.

Fault injection for data

Fault injected (in a test environment)Check that must fireSeverity expected

If a fault can't be injected safely, at least write it down. A list of failures you can't detect is more useful than confidence you haven't earned.

Run the suite in CI against a small seeded copy of the warehouse whenever checks or models change, and quarterly against a full-size test environment. Each fault has an expected check and severity; a test fails if the wrong check fires, or the right one fires at the wrong severity.

faults/missing_shop.sqlinject, run the pipeline, assert
-- 1 · inject: remove Rotterdam from today's till batch in the test environment
DELETE FROM test_raw.till_sales
WHERE  shop_code = 'RTM' AND sold_at::date = :test_day;

-- 2 · run the normal pipeline for :test_day (same DAG, test target)

-- 3 · assert: the completeness check blocked the publish
SELECT 1 FROM check_results
WHERE  check_name = 'segment_completeness_shops'
  AND  run_day = :test_day AND status = 'blocked';   -- must return one row

Replaying a real bad week

Synthetic faults test what you imagined. Real incidents test what happened. The shop kept week 23's raw files and change events, so it can replay the whole week through the new pipeline in a test environment and check that all five incidents are now caught, at the right checkpoint and severity. Every future incident's raw data is kept the same way, for 90 days, and added to the replay suite. Over a year that becomes a library of real failures, which is worth more than any list of imagined ones.

A coverage map

List the published tables down the side and the five quality dimensions across, and mark which have a check with a tested fault. Week 23's map was full of validity and empty everywhere else. The map is the quickest way to see where the next incident will come from, and it fits on one page for a review.

Reviewing new checks

Every new check in a pull request answers three questions in its description: which objective does it protect, what severity, and what fault proves it works. Checks that can't answer the first question are usually validity tests nobody needs.

checkpoint

What does a fault-injection test assert?

That a specific fault triggers the expected check at the expected severity, and no other.

What three things should a new check's pull request state?

The objective it protects, its severity, and the fault that proves it works.

Running it: data incidents

Gist Acknowledge, tell consumers with a banner and the lineage list, contain (write–audit–publish keeps yesterday), fix and replay through the normal pipeline, and review in ten minutes. A data health dashboard shows SLOs, blocked publishes, quarantine and the false-alert leaderboard.

When a check fires, the next hour decides whether people keep trusting the dashboard. Data incidents deserve the same handling as service incidents, scaled down.

StepWhat it looks like
1 · acknowledgethe owner named in the alert takes it within 15 minutes in opening hours
2 · tell consumersthe dashboard banner says what is affected and since when; lineage lists the reports
3 · containyesterday's published data stays (WAP did this); quarantine holds the bad rows
4 · fix and replayfix at the source or in staging; replay the affected days through the normal pipeline
5 · learna short review: which checkpoint caught it, which should have, what check to add
Most data incidents need no all-hands. They need one owner, one banner, and one replay.

Impact from lineage

Every alert includes what lineage says is downstream: “fct_sales not published for 2026-06-05. Affects: revenue dashboard, regional report, franchisee portal (Delft), board pack draft.” The people who own those see it once, in their own channel, instead of finding out from a user.

alert.txtwhat a good data alert says
[BLOCKED] fct_sales · 2026-06-05 · segment_completeness_shops
  Missing: RTM (Rotterdam). Expected 31 open shops, got 30.
  Published data stays at 2026-06-04 23:59.
  Downstream: revenue dashboard, regional report, franchise portal (RTM)
  Owner: data-platform on call · Source owner: retail-it (tills)
  Runbook: wiki/data/runbooks/missing-shop

Telling users, in their words

The dashboard banner is the most important message in a data incident, and the easiest to get wrong. “Pipeline failure in fct_sales” means nothing to a regional manager. “Friday's sales for Rotterdam are missing. Other shops are complete. Expected fix: Saturday 10:00.” tells them what they can and can't use. The banner text comes from the check: the check knows the segment, the day and the dimension, so the message can be generated, not written in a hurry.

On call for data

The shop doesn't run a night rota for data. Blocking checks page the data platform's on-call engineer in opening hours (07:00 to 22:00), and everything outside those hours waits for the morning, because yesterday's data stays published and a few hours of staleness is inside the error budget. The exception is month-end close week, when finance needs fresh data at night and the rota extends for five days.

The review after an incident

Five questions, ten minutes: what happened, how it was detected and how long that took, which checkpoint should have caught it earlier, what check or contract change prevents it, and what fault test proves the new check works. Week 23's five reviews produced the plan in chapter 5.

checkpoint

What should every data alert include?

The table, the failed check, what stays published, the downstream reports from lineage, the owners and a runbook link.

How is a bad day fixed?

Fix at the source or in staging, then replay the affected days through the normal pipeline.

Dagster's asset checks and Airflow's data-aware scheduling put checks in the DAG itself, so a failed check stops downstream steps without extra glue.

Build or buy

The checks in chapters 2 to 4 are mostly SQL, and a pipeline framework runs them for free. What is worth buying is what's tedious to build: learned seasonal baselines for hundreds of tables, column-level lineage across warehouse and BI tools, and an incident view that groups related alerts. The shop's rule: build the checks that protect its SLOs (they encode business knowledge), and consider a tool once there are more tables with consumers than people can watch, which happened at about 150.

chapter 10 · 3 min

A lab and the checklist

Gist The lab onboards a marketplace that drops a nightly CSV, sometimes twice, sometimes late, with columns that change unannounced: arrival checks, idempotent corrections, SLOs, a self-written contract and the faults to inject. The checklist turns the dive into review questions.

The lab. The shop starts selling through a second marketplace. The marketplace drops a CSV of orders on an SFTP server every night around 03:00, sometimes twice (a correction file), sometimes late. Its columns change without warning about twice a year. Marketplace sales will appear on the revenue dashboard and in the franchisee portal.

  1. What do you check on arrival, and what happens if the file isn't there by 05:00?
  2. The correction file repeats yesterday's orders with some changes. How do you stay correct?
  3. Write the data SLOs for marketplace revenue on the dashboard.
  4. The marketplace won't sign a contract. What do you do instead?
  5. Which faults do you inject before go-live?

model answer

1 · Arrival

File present, header matches the expected columns, row count within the same-weekday band, file not seen before (checksum). Not there by 05:00: alert the marketplace owner, publish everything else, and show “marketplace data as of yesterday” on the dashboard. Don't block the shop's own sales for a partner's file.

2 · Corrections

Land every file in raw with its name and arrival time. Load by MERGE on the marketplace's order id, newer file wins, so the correction replaces the original rows (idempotent loads). A unique test on the published table catches any slip.

3 · SLOs

Freshness: marketplace data at most 30 hours old (it's a daily file). Completeness: one file per day. Uniqueness: no duplicate marketplace order ids. Accuracy: daily totals match the marketplace's settlement report within 0.5 % after a week.

4 · No contract

Write the contract yourself, as your expectation, and enforce it on arrival: a changed header blocks the marketplace load (not the rest), quarantines the file, and alerts. Keep the column mapping in staging so a rename is a one-line fix and a replay.

5 · Faults

Missing file, empty file, the same file twice, a correction file, a renamed column, prices in a different currency or unit, and one day's file arriving two days late. Each with its expected check and severity.

The review checklist

Objectives

  • Every published table people use has freshness and completeness objectives
  • Objectives are written in the users' words
  • Each check names the objective it protects

Checkpoints

  • Contracts in producers' CI where possible
  • Arrival checks: presence, schema, volume
  • Row checks quarantine with reasons
  • Audit before publish: keys, segments, batch reconciliation
  • Monitors on published tables; nightly reconciliation

Strictness

  • Hard rules wherever a check is a definition
  • Bands use the same weekday and the calendar
  • Each check is block, quarantine or warn, chosen deliberately

Alerts

  • Only blocking and SLO checks interrupt people
  • Every alert names table, impact and owner
  • False alert rate tracked per check

Testing

  • A fault for every important check, run in CI
  • A coverage map by table and dimension
  • New checks state objective, severity and proving fault

Incidents

  • Owner, banner, contain, replay, review
  • Lineage includes dashboards and exports
  • A data health dashboard the team looks at weekly
