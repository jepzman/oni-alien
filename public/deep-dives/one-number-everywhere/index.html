Four notes in sixty seconds

Gist Conformed dimensions share one calendar and one product list, wide tables serve tools, a metrics layer defines each number once, and aggregates keep it fast. The Monday meeting with three revenues for one week is what happens without them working together.

Monday, 09:00. Week 14 revenue is €1.92M on the finance dashboard, €2.31M on marketing's and €2.05M in the spreadsheet the regional managers use. Average order value disagrees too. Forty minutes go on reconciling, and nobody decides anything. Four notes in the volume deal with this; together they are a system.

NoteIn one line
Conformed Dimensionsone product, one customer, one calendar, shared by every fact
One Big Table vs Starmodel as a star, serve wide tables to the tools that want them
Metrics Layerdefine each business number once, in code, and let every tool ask for it
Aggregates & Rollupspre-compute summaries at the grains people ask for, so it's fast
Nothing here is a bug in the usual sense. Every query does what it says. They just say different things.

The metrics layer note says “define it once”. This dive is about what that takes in practice: the joins that silently multiply numbers, the definitions nobody wrote down, how a metrics layer turns a question into SQL, how to keep it fast and cheap when 300 managers open it at once, and how to change a definition without breaking last quarter's board pack.

The real mechanism: a compiler for questions

Gist A metrics layer takes a question (metric, dimensions, filters, time grain) and writes SQL from a semantic model that knows each table's grain, how tables join through entities, and how each measure aggregates. Ratios and two-fact metrics are computed part by part and combined last.

A metrics layer is a compiler. You give it a question (a metric, some dimensions, filters, a time grain) and it writes the SQL, using a semantic model that knows the tables, how they join, and how each measure aggregates.

What the model knows

PartFor the shopUsed to
semantic modelsales on fct_sales, grain order lineknow what one row is
entitiesorder_line (primary), order, product, customer, shopfind safe join paths between models
dimensionsorder_date (time), category, region, channelgroup and filter
measuresamount_net (sum), orders (count distinct order_id)aggregate correctly at any grain
metricsrevenue, orders, average order valuethe names people use, with filters and owners
Entities are the key idea. They tell the layer that sales and returns can both be reached from product, and that order is coarser than order line.

The SQL it writes

For “revenue by category by ISO week, web channel only”, the layer writes roughly this. Note what it decides for you: which table, which join, where the filter goes, how the week is computed.

generated.sqlwhat the layer sends to the warehouse
SELECT
  date_trunc('week', s.order_date)       AS metric_time__week,
  p.category                             AS product__category,
  sum(s.amount_net)                      AS revenue
FROM fct_sales s
LEFT JOIN dim_product p ON s.product_key = p.product_key
WHERE s.channel = 'web'
  AND NOT p.is_gift_card                  -- the metric's own filter
GROUP BY 1, 2

Ratios are computed last

Average order value is a ratio metric: revenue divided by orders. The layer computes both at the requested grain and divides at the end, so AOV by region is region revenue over region orders, never the average of shops' averages (drill 3).

ratio.sqlnumerator and denominator at the same grain
WITH num AS (SELECT region, sum(amount_net) AS revenue FROM … GROUP BY region),
     den AS (SELECT region, count(DISTINCT order_id) AS orders FROM … GROUP BY region)
SELECT region, revenue / nullif(orders, 0) AS average_order_value
FROM num JOIN den USING (region)

The same goes for metrics built from two facts, such as return rate (returns over sales): each side is aggregated on its own and joined on the shared dimensions, the drill-across from the conformed dimensions note, done automatically.

Questions the layer refuses

A good layer says no. Ask for “conversion rate by product category” and sessions have no product, so there is no correct answer; the layer returns an error instead of a number. Ask for revenue by a dimension reachable only through a many-to-many path (products in several promotions) and it refuses, because any answer would double count. These refusals feel annoying the first week. They are the reason the numbers can be trusted afterwards: hand-written SQL would have produced something, and someone would have put it on a slide.

Symmetric aggregates

Some tools (Looker most famously) take a different route around fan traps: when a join could repeat a coarse row, they sum distinct values keyed by the coarse row's primary key, so order 9001's discount counts once however many lines it joins. It works, and it is why every model must declare primary keys correctly. A wrong key there produces a quietly wrong number, so test keys for uniqueness in the pipeline before the layer relies on them.

checkpoint

What do entities give the layer?

Safe join paths between semantic models, and which grains are coarser or finer.

How is average order value by region computed?

Region revenue divided by region orders, both aggregated at region level; never the average of shop averages.

Failure drills

Gist Six ways a correct-looking query gives a wrong number: an order discount summed per line, two facts joined through a dimension, an average of averages, weekly unique customers added up, three definitions of a week, and a ratio filtered on one side only.

Every drill here passed review and ran for months. The numbers were plausible, just wrong.
  • 1 · fan trap
  • 2 · chasm trap
  • 3 · average of averages
  • 4 · customers summed
  • 5 · which week
  • 6 · half a filter
Drill 1

The discount counted per line

Timeline
Marketing wants revenue after discounts. Discounts are stored per order (orders.discount), revenue per line. The dashboard joins orders to lines and sums both. Order 9001, two lines and a €5 discount, shows a €10 discount. Across the week, discounts are overstated by 2.5×, the average lines per order.
Tempting mistake
Divide the discount by the number of lines in the dashboard formula. It fixes this tile and breaks the next one, where lines are filtered by category and the divisor is wrong again.
Why
A fan trap: a measure at a coarse grain (order) joined to a finer grain (line) is repeated once per fine row, then summed.
What saves you
Keep each measure at its own grain and aggregate it there: order measures from the order fact, line measures from the line fact, joined after aggregation. Or allocate the discount to lines in the pipeline (by line amount), so it becomes a line measure with a documented rule. A metrics layer that knows the grains refuses to sum an order measure through a join to lines.

Rule: a measure is summed only at its own grain. Coarse numbers joined to fine rows multiply.

Drill 2

Sales and returns, multiplied

Timeline
The category manager's report puts units sold and units returned side by side. The SQL joins fct_sales and fct_returns to dim_product in one query and sums both. For the kettle, 400 sales and 12 returns become 4,800 and 4,800.
Tempting mistake
Add DISTINCT to the sums. Two kettle sales of the same quantity then count once, and the numbers become wrong in a new, quieter way.
Why
A chasm trap: two facts joined through a shared dimension in one query produce every sale × every return for each product. Each sum is multiplied by the other side's row count.
What saves you
Drill across: aggregate each fact to the shared dimension first, then join the small results. Never join two fact tables row to row. In a metrics layer, declare both as separate semantic models with the product entity; the layer generates the two-step query.

Rule: two facts meet only after each has been aggregated.

Drill 3

The average of averages

Timeline
The regional AOV is computed by averaging the shops' AOVs. Delft has 2,000 orders at €44; the small Leiden pop-up has 40 orders at €90. The region's AOV comes out at €67. The real one, all revenue over all orders, is €44.90.
Tempting mistake
Weight the average by orders in the dashboard. That is the ratio of sums written by hand, and the next author won't know to do it.
Why
An average of averages gives every shop the same weight whatever its size. It is only right when every group is the same size.
What saves you
Store and aggregate the parts (revenue, orders) and divide last, at whatever grain is asked. Make AOV a ratio metric, so no tool can average it. The same applies to conversion rate, margin percentage and every other ratio.

Rule: ratios are sums divided at the end, never averages of ratios.

Drill 4

More customers than people

Timeline
The monthly dashboard sums weekly unique customers: 61,000 + 58,000 + 63,000 + 60,000 = 242,000 “customers in March”. The CRM says 180,000 people bought in March. Regulars who buy every week were counted four times.
Tempting mistake
Label the tile “customer-weeks”. Honest, but nobody reads labels, and the board still hears 242,000 customers.
Why
Distinct counts don't add up across periods or groups that share members. Each week's set overlaps the others.
What saves you
Count distinct at the grain asked, from the fact table, or store mergeable sketches (HyperLogLog) in aggregates and merge them. Mark the measure non-additive in the semantic model so a tool can't sum it.

Rule: distinct counts are recounted or merged, never summed.

Drill 5

Which week is week 14?

Timeline
Finance's week 14 is the ISO week, Monday to Sunday. The spreadsheet's week starts on Sunday. Marketing's dashboard truncates UTC timestamps. Easter Sunday's €160,000 of sales lands in three different weeks.
Tempting mistake
Ask everyone to set their tool to ISO weeks. Some tools can't, defaults come back with every new dashboard, and the time zone problem remains.
Why
“Week” has at least three definitions, and the time zone moves sales near midnight. Each tool picked its own default.
What saves you
One calendar dimension (dim_date) with ISO week, fiscal week and fiscal period as columns, keyed on the local date computed once in the pipeline. The metrics layer exposes only those, so “week” means the business's week everywhere.

Rule: time grains come from one calendar, in the business's time zone.

Drill 6

Conversion with half a filter

Timeline
Web conversion rate is orders divided by sessions. A dashboard filters “channel = app” by joining the filter to orders only. App orders over all sessions: conversion drops from 3.1 % to 0.9 %, and the app team spends a week investigating a problem that doesn't exist.
Tempting mistake
Tell the app team to filter sessions too. They will, on this dashboard, until the next ratio someone builds.
Why
A filter applied to the numerator but not the denominator changes what the ratio means. Hand-written SQL makes this easy; nothing complains.
What saves you
Ratio metrics in the layer apply every filter to both parts, or refuse when a dimension isn't available on one of them (sessions have no product category, so “conversion by category” must be refused or defined separately).

Rule: a ratio's filters apply to both parts, or the question is refused.

Discounts are 2.5× too high after joining orders to lines. Name the trap.

A fan trap: an order-level measure repeated for each line and then summed.

The hard problem: deciding what a number means

Gist The three revenues were correct SQL for different definitions. Defining a metric means deciding VAT, returns, discounts, gift cards, dates and as-was categories, writing the answers next to the code, giving it an owner, and changing it like an API: versioned, diffed and announced.

The drills are traps a good layer prevents. The harder problem is that the three revenues in chapter 1 are all correct SQL for different definitions, and nobody chose between them. A metrics layer makes a definition executable; it doesn't make the decision. Defining a number means answering a handful of questions explicitly, and getting the right person to sign it.

The questions behind “revenue”

QuestionOptionsThe shop's answer
VAT?gross incl. VAT · netnet
returns?ignore · on the return date · against the original saleagainst the original sale
gift cards?when sold · when redeemed · excludedexcluded; redemptions count when spent
discounts?before · after, allocated to linesafter, allocated by line amount
shipping fees?included · excludedexcluded (other income)
cancelled orders?included until cancelled · nevernever
which date?placed · paid · shippedplaced, local time
which category?as it was · as it isas it was (type 2)
Returns and the category choice moved more money between the three dashboards than anything else.

Each row is a business decision. The finance director owns revenue; marketing can have its own metric, gross_merchandise_value, with its own owner, as long as it is never labelled “revenue”. Names are part of the definition.

Naming rules

Most disagreements start with two things sharing a name. The shop adopts three rules. One name, one definition: there is exactly one revenue, and variants carry what makes them different in the name (revenue_incl_vat, gross_merchandise_value). Units in the name when they aren't obvious (margin_pct, delivery_days). No people or teams in names (revenue_marketing means nothing a year later). The layer enforces the first rule mechanically, because two metrics can't share a name.

Writing it down so it can't drift

Every certified metric gets a short specification next to its code: the answers above, the owner, the grain, the additivity, and a sentence a non-engineer can read. The code implements the specification; review checks they match.

metrics/revenue.ymldefinition and specification in one place
metrics:
  - name: revenue
    label: Revenue
    description: >
      Net of VAT, after discounts (allocated to lines), returns booked against
      the original sale, excluding gift cards, shipping and cancelled orders.
      Dated by order placed, Europe/Amsterdam. Categories as they were.
    type: simple
    type_params: { measure: amount_net_after_returns }
    filter: |
      {{ Dimension('product__is_gift_card') }} = false
      and {{ Dimension('order__is_cancelled') }} = false
    meta: { owner: finance-director, certified: true, since: 2026-12-01 }

Returns, worked through

Order 9001 was placed on 31 March for €45.45 net. One mug, €6.61 net, came back on 3 April. Where does the return go?

Booking ruleMarch revenueApril revenueConsequence
ignore returns€45.45€0overstates revenue; return-heavy categories look better than they are
on the return date€45.45−€6.61March is final at close; April carries March's returns
against the original sale€38.84€0March is right but keeps changing for 60 days after close

The shop chooses “against the original sale” for analysis, because category managers want return-adjusted performance by the month it was sold, and files a snapshot at close for finance (chapter 8). Accounting books the return in April. The difference between the two is real, predictable and documented, so the monthly reconciliation can explain it line by line instead of arguing about it.

Changing a definition

Definitions change: the business decides shipping is revenue after all. Changing the metric in place rewrites every past report, including the board pack filed last quarter. Treat it like an API change: publish the new definition under a version or a new name, show both side by side for a period, tell every consumer, record the change with a date, then switch the main name and keep the old one available but marked deprecated. Filed numbers stay filed (the history deep dive covers why).

checkpoint

Marketing wants revenue including VAT. What do you do?

Give it its own name and owner (e.g. gross merchandise value); “revenue” stays the finance definition.

Why not change a definition in place?

It silently rewrites every past report, including filed ones; version it, show both, then switch.

Four ways to one number

Gist Definitions in every tool is where the problem starts. A documented wide table helps but can't stop averaging. A semantic model inside one BI tool works until a spreadsheet or portal needs the number. A headless metrics layer serves every consumer from one model.

There are four common ways to get one number everywhere. Here is each one run against the drills and the shop's tools: two BI tools, spreadsheets, notebooks and the embedded franchisee portal.

A · definitions in each toolB · one big table, documentedC · semantic model inside one BI toolD · headless metrics layer
where revenue livesevery dashboard's SQLa column per measure in a wide tableLookML, a Power BI modeldbt Semantic Layer, Cube
drill 1, fan trapeach author's problembaked in if the table mixes grainsprevented by declared grainsprevented by declared grains
drill 3, ratioseach author's problemusers average the columnratio measuresratio metrics
reaches spreadsheets, notebooks, the portalcopiesyes, it's a tableonly that BI toolyes, by API and SQL
new questionsnew SQL each timeonly the columns that existany joinable dimensionany joinable dimension
effort to startnonelowmediummedium to high
Most shops end up with D behind their main BI tool, or with C when one tool really is all they use.

Variant A is where everyone starts and why the Monday meeting happens. Variant B is a sensible first step: one wide table per subject (obt_sales) with clearly named, pre-computed measure columns removes most disagreement, but it can't stop someone averaging the AOV column, and every new question needs a new column. Variant C is excellent when one BI tool is the only consumer: Looker and Power BI models know grains and ratios. But the spreadsheet and the franchisee portal can't use it, so their numbers drift. Variant D puts the model outside any tool, so every consumer asks the same layer.

Variant B, done well

If a layer is not possible yet, a wide table can still remove most of the Monday arguments. Give it one grain per table, pre-computed measure columns named after the agreed definitions (revenue, never amount), the parts of every ratio rather than the ratio itself (revenue and orders, not aov), a calendar from dim_date, and column descriptions copied from the specification. It is variant D's definitions without the compiler, and it makes the later move to a layer a matter of pointing the model at tables that are already right.

The shop's choice

ConsumerReads
finance and management dashboardsthe metrics layer, through the BI tool's connector
regional managers' spreadsheetsthe metrics layer's spreadsheet add-in, or a scheduled extract it produces
analysts' notebooksthe metrics layer's SQL or Python API for metrics; raw marts for exploration
the franchisee portalthe layer's API with a security context per franchisee
ad-hoc explorationmarts directly, clearly labelled “not certified”

Exploration stays free. Only numbers that leave the analytics team need to come from the layer.

Getting from A to D without a big bang

  1. Find the numbers that matter. List the ten metrics that appear in management reports. Ignore the other four hundred for now.
  2. Define them, one meeting each. Owner, specification, code, fixtures. Put them in the layer and certify them.
  3. Move the top dashboards. Repoint the five most-viewed dashboards' tiles to the layer, compare old and new values side by side for two weeks, explain every difference, then switch.
  4. Mark the rest. Every tile not coming from the layer gets a “not certified” label. People stop putting those on slides on their own.

At the shop this took six weeks for revenue, orders, AOV, margin and return rate. The Monday meeting got shorter after the second week, when finance and marketing were looking at the same tile with two clearly named metrics on it.

checkpoint

Why isn't a BI tool's semantic model enough for the shop?

Spreadsheets, notebooks and the franchisee portal can't use it, so their numbers drift.

Does exploration have to go through the layer?

No; only numbers that leave the analytics team, labelled certified.

Keeping it fast

Gist Three hundred dashboard opens on a Monday are 2,400 queries. Pre-aggregations at day × shop × category answer most of them from a few million rows in milliseconds. Sketches make distinct counts mergeable. Invalidate caches on publish, not on a timer.

A metrics layer adds a hop to every query, and it concentrates load: everybody's dashboards now run through it. The numbers decide whether it feels instant.

Monday morning, worked out

Without cachingWith pre-aggregations
dashboard opens 08:55–09:15300300
queries per open (tiles)88
queries reaching the warehouse2,400~40 (cache misses and refreshes)
rows scanned per query60 M lines (a year)~20,000 (daily aggregate rows)
median tile time4–6 s< 300 ms
Pre-aggregations are aggregates (Vol. 9) that the layer builds and routes to by itself.

A latency budget

People decide whether to trust a dashboard partly by how it feels. Set targets and measure them per tile: under one second for the management dashboard's tiles (pre-aggregated, cached), under five seconds for exploratory questions the layer compiles to the fact tables, and an honest spinner with a message beyond that. Tiles that regularly miss the first target are the list of pre-aggregations to build next.

Sizing the pre-aggregations

The common dashboard grain is day × shop × category: 365 × 31 × 200 = about 2.3 million rows a year, a few dozen megabytes. Week × region × category is under 100,000. The layer answers any question at or above a stored grain from it (summing additive measures, merging sketches) and falls back to the fact for anything finer. Refresh only the days a batch touched, as with any aggregate.

Distinct counts, approximately

Unique customers can't be summed (drill 4). A HyperLogLog sketch with 214 registers is about 16 KB and accurate to about ±0.8 %. Stored per day × shop × category, merged at query time, it answers “unique customers by region this quarter” from the aggregate. Mark such metrics as approximate in their description; finance reports that need exact counts query the fact.

Cache freshness

A cache keyed on the query and invalidated when the underlying data publishes (write–audit–publish gives a clean moment) is always consistent with the warehouse. A time-based cache of 15 minutes is simpler, but after a correction the dashboard and the warehouse disagree for up to 15 minutes, which is exactly the kind of disagreement this whole exercise was meant to end.

What the layer itself costs

A headless layer is a small service: a couple of containers for the API and the cache, plus the storage for pre-aggregations. At the shop's size that is far less than the warehouse compute it saves on Monday mornings. The real cost is people: someone has to own the model, review metric changes and answer “why is this number different”. Budget a part-time owner from the start; a metrics layer nobody maintains drifts back into variant A within a year, with extra steps.

checkpoint

Why invalidate the cache on publish rather than every 15 minutes?

So the dashboard never disagrees with the warehouse after a correction.

How are unique customers answered from an aggregate?

Store HyperLogLog sketches per row and merge them at query time.

Testing numbers

Gist Pin numbers down: hand-computed fixtures for each metric, a metric diff on every pull request, the same metric through every consumer path, monthly reconciliation with the finance ledger, and additivity checks.

Metric bugs look like plausible numbers. Tests must therefore pin numbers down: known inputs with known outputs, the same metric through different paths, and agreement with the books.

TestChecksCatches

The metric diff on pull requests is the single most useful habit: reviewers see “revenue for March changes by −€41,200” before merging.
metric_fixture.ymlorder 9001 as a test
# two lines, an order discount of €5 incl. VAT (€4.13 net), one mug returned
given:
  orders:      [{order_id: 9001, discount_net: 4.13, placed: 2026-03-31}]
  order_lines: [{line: 1, order_id: 9001, sku: K-100, amount_net: 32.23},
                {line: 2, order_id: 9001, sku: M-210, amount_net: 13.22}]
  returns:     [{line: 2, qty: 1, amount_net: 6.61, returned: 2026-04-03}]
expect:
  revenue:             {2026-03-31: 34.71}   # 45.45 − 4.13 discount − 6.61 return
  orders:              {2026-03-31: 1}
  average_order_value: {2026-03-31: 34.71}

Write the expected values by hand from the specification, not by running the query. The point is that a person and the code agree on what the definition means. When they don't, one of them is wrong, and it is worth finding out which before the board does.

Reconciling with the ledger, worked

Finance's general ledger for March says €7.912M net sales. The layer says €7.884M. The gap is €28,000, 0.35 %, above the 0.1 % threshold. Broken down by cause:

CauseAmountExpected?
returns booked in April by accounting, against March by the layer+€41,200 in the layer's favouryes, documented
shipping fees: ledger books them as sales, the layer excludes them−€63,800yes, documented
two days of Delft till sales missing from the warehouse−€5,400no: a pipeline gap

The first two lines are definitions and stay. The third is a bug the reconciliation found: a till upload that never arrived. After replaying it, the unexplained part is zero, which is the real target. The threshold is for the unexplained remainder, not for the total gap.

Testing through the tools

Once a week, a job asks every consumer path for the same three numbers (revenue, orders, AOV for last week): the layer's API, the BI tool's export, the spreadsheet extract, the franchisee portal for one franchisee summed with the others. Any difference means a path has its own SQL somewhere. It is the cheapest way to find the dashboard someone built straight on the marts last month.

checkpoint

What does a metric diff in CI show reviewers?

How much each key metric changes over recent periods if the pull request is merged.

Why write expected fixture values by hand?

So a person and the code independently agree on what the definition means.

Running it: governance

Gist Every certified metric has an owner, a badge, a change log and a deprecation path; definitions freeze at month end. Watch how much traffic goes through the layer, the Monday cache hit rate, and uncertified numbers in management reports.

Running a metrics layer is mostly governance: who owns which number, how definitions change, and which numbers people may trust.

PracticeHow it looks at the shop
ownersevery certified metric has a named business owner who approves changes
certificationcertified metrics carry a badge in every tool; everything else says “not certified”
change logeach definition change has a date, a reason and the size of the effect on the last 12 months
deprecationold metrics stay queryable for a quarter, marked deprecated, then retired
month-end freezeno definition changes between the last working day and the close
A metric without an owner is a metric that will be changed by whoever is in a hurry.

Retiring a metric

Metrics accumulate: revenue_old, revenue_marketing_2024, aov_excl_outliers. Each one is a chance for the Monday meeting to come back. Every quarter, list metrics with no queries in 90 days and propose retiring them to their owners; list duplicates that differ only in one filter and merge them into one metric with a dimension. Retiring is as deliberate as adding: marked deprecated, announced, removed after a quarter. The certified list should get shorter as often as it gets longer.

Announcing a change

When shipping fees become part of revenue, the owner sends one short note to everyone who uses the metric: what changes, from which date, the effect on the last twelve months (from the metric diff: +3.1 % on average, +4.8 % in December), what happens to filed reports (nothing: they stay as filed), and where the old definition can still be found (revenue_v1, until the end of the quarter). Five sentences prevent five meetings.

Tools

Gist dbt's Semantic Layer and Cube are headless layers reachable from many tools; LookML and Power BI models live inside their BI tool. All compile questions to SQL and help with traps and speed. None decides what revenue means.

Metrics layers come in two kinds: inside a BI tool, or standalone (“headless”) and reachable from many tools. All of them compile questions into SQL from a semantic model; they differ in reach, caching and how much modelling they expect.

ToolKindGives youLeaves to you
dbt Semantic Layer (MetricFlow)headless, in the dbt projectmetrics next to the models, safe joins via entities, ratio and cumulative metrics, APIs and BI connectorscaching depends on the platform; the definitions

Looker's symmetric aggregates solve the fan trap by de-duplicating on primary keys inside the sum. It's clever, and it's why declaring primary keys matters in every tool.

chapter 10 · 3 min

A lab and the checklist

Gist The lab defines gross margin and return rate for franchisees and the board: ratios from line-level parts, costs fixed at the sale date, returns against the sale, security through the layer. The checklist turns the dive into review questions.

The lab. Franchisees join the portal in July. They want three numbers for their own shops: revenue, gross margin percentage and return rate. Head office wants the same numbers across all shops for the board. The product cost table is maintained by purchasing and changes monthly; returns can arrive up to 60 days after the sale.

  1. Define gross margin percentage: what are its parts, and at which grain are they stored?
  2. Return rate: units or money? Against which date? Where can it be computed?
  3. Which cost applies to a sale in March if the cost changes in April?
  4. How does a franchisee see only their shops, through the same metrics?
  5. The board wants “margin by region” as a single number per region. A slide averages shops' margins. What do you say?

model answer

1 · Gross margin %

A ratio metric: (revenue − cost of goods) / revenue, both summed at the line grain and divided last. Store cost_of_goods on each sales line at load time, so it is a line measure like revenue.

2 · Return rate

Decide with the owner; the shop picks money: returned revenue / revenue, returns booked against the original sale date. It needs both facts, so it is a drill-across metric on the shared dimensions (product, shop, date of sale). Recent periods are incomplete for 60 days: say so on the dashboard.

3 · Which cost

The cost valid on the sale date, looked up at load time from a type 2 cost history and stored on the line. Then March margin never changes when April's cost is entered.

4 · Franchisees

The portal calls the layer with a security context from a signed token; the layer adds the franchisee's shops as a filter to every query, on both parts of every ratio. Same definitions, fewer rows.

5 · The slide

An average of shop margins is drill 3: it weights the pop-up the same as Delft. Ask the layer for margin by region; it sums revenue and cost per region and divides.

The review checklist

Definitions

  • Every certified metric has an owner and a written specification
  • Names are unique: no two metrics called revenue
  • VAT, returns, discounts, gift cards and dates are decided, not defaulted
  • Changes are versioned, diffed and announced

Model

  • Each semantic model has a stated grain and primary key
  • Measures declare additivity
  • Ratios are numerator and denominator, divided last
  • Facts meet only through conformed dimensions

Time

  • One calendar dimension with ISO and fiscal weeks
  • Local business dates computed once in the pipeline
  • Late-arriving periods are labelled incomplete

Reach

  • Dashboards, spreadsheets, notebooks and the portal all read the layer
  • Exploration on marts is labelled “not certified”
  • Row-level security passes through the layer

Speed

  • Pre-aggregations at the common grains
  • Cache invalidated on publish
  • Approximate metrics say so

Tests

  • Metric unit tests with hand-computed fixtures
  • Metric diff on every pull request
  • Monthly reconciliation with the ledger
  • Weekly cross-path consistency check
