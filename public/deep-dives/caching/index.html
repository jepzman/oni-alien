Read first: Cache-AsideServer-State Cache

chapter 1 · 1 min

Two notes in sixty seconds

Gist Cache-aside keeps a copy of hot data next to the database, with an expiry, and deletes it on a write. The server-state cache does the same in the browser. This deep dive is about what the copies do to the whole system: the database shrinks to fit, five layers expire at five different times, and some of them you cannot clear.

The cache-aside note was about a fridge. Product 42, the mug, is read thousands of times a minute and changes about once a month, so the app keeps a copy in Redis under product:42 for five minutes. A read checks Redis first. A write updates the database and deletes the key.

NoteIn one line
Cache-Asidecheck the cache; on a miss read the database and keep a copy with an expiry; on a write, delete the copy
Server-State Cachethe browser shows the copy it has at once and fetches a fresh one in the background
Both notes are the same idea at different distances from the database.

The notes showed the happy path and named the famous problem, invalidation. This deep dive is about what a cache does to a system once it is there: the database gets sized for the traffic the cache lets through, copies in five places expire at five different times, and a fix deployed at noon is still invisible to some shoppers at a quarter past. A cache is easy to add and hard to remove, so it is worth knowing the cost first.

chapter 2 · 2 min

A cache is a bet

Gist Caching bets that an answer will be asked for again before it changes. Every cached item needs three decisions: how old it may be, how it learns it changed, and what a miss costs. The database feels the miss rate, not the hit ratio, and a system that cannot run without its cache has turned it into a database.

A cache is a bet: this answer will be asked for again before it changes. When the bet wins, you skip the work. When it loses, you either did extra work for nothing, or you served an answer that is no longer true. Every cached thing needs three decisions.

QuestionFor product:42
How old may the copy be?a description may be hours old; a price, a minute; the price used to charge a card, zero
How do we learn that it changed?wait for it to expire, or be told
What happens when the copy is missing?one 40 ms query, or five hundred of them at once
If nobody can answer question 1 for a piece of data, it is not ready to be cached.

The number that matters is the miss rate

People quote the hit ratio. The database only feels the misses.

Hit ratioTypical readReads reaching the database, of 2,000 a second
0 % (no cache)40 ms2,000. It can do 400
90 %about 5 ms200
95 %about 3 ms100
99 %about 1.4 ms20

From 95 % to 99 % looks like a small step. It is five times less load on the database. And the first row is the important one: without the cache, this shop does not work at all.

When a cache becomes load-bearing

A cache starts as an optimisation. Traffic grows, and nobody resizes the database, because the cache is absorbing the growth. One day the database can serve a fifth of the read traffic, and the cache is no longer an optimisation. It is a part the system cannot run without, and it was never designed as one: it has no backup, it starts empty, and the code treats it as optional.

Two honest positions exist.

PositionMeans
The cache is optionalthe database can carry all the traffic, slowly. Losing the cache is a bad afternoon
The cache is requiredtreat it like a database: replicas, a warm-up plan, load shedding for when it is empty (drill 3)

The dangerous place is in between: required in fact, optional in everyone's head. A yearly test that switches the cache off in a load-test environment tells you which position you are really in.

What a cache does not fix

If a query takes 40 ms because an index is missing, the cache hides the slow query from most users and leaves it in place for the rest, including every user after a restart. Fix the query first. Cache what is still too slow or too frequent after that.

checkpoint

The hit ratio improves from 98 % to 99 %. What happens to database load from reads?

It halves: misses go from 2 % to 1 % of reads.

How do you find out whether your cache is optional or required?

Switch it off, or start it empty, under realistic load in a test environment, and see whether the database carries the traffic.

chapter 3 · 2 min

Five ways to read and write

Gist Cache-aside and read-through load on a miss and leave the database as the truth. Write-through and write-behind send writes through the cache, and write-behind can lose confirmed data. Refresh-ahead reloads popular keys before they expire. For most data, use cache-aside and delete the key on a write.

Cache-aside is one of five arrangements. They differ in who talks to the database and when the copy is written.

PatternReadWriteMain risk
Cache-asideapp checks cache, then database, then fills the cacheapp writes database, deletes the keythe app must remember every key it affects
Read-throughapp asks the cache; the cache loads from the database itselfas cache-asidethe cache needs to know how to load each kind of data
Write-throughfrom the cacheapp writes the cache; the cache writes the database before answeringevery write pays for both; the cache fills with data nobody reads
Write-behindfrom the cacheapp writes the cache; the database is updated later, in batchesa cache crash loses writes that were already confirmed
Refresh-aheadfrom the cacheas cache-asidethe cache reloads popular keys before they expire; wasted work on keys that stop being popular
Write-behind makes the cache the source of truth for a while. Only for data you can afford to lose, like view counters.

Which to use

SituationChoose
Most application datacache-aside, or read-through if your library offers it. Only data that is asked for gets cached, and a cache failure leaves the database correct
A few very hot keys that are slow to rebuildadd refresh-ahead for those keys (chapter 6)
Counters, “last seen”, statisticswrite-behind is acceptable; say so in the code
Money, stock, anything a decision is based ondo not read it from a cache when deciding (chapter 5)

Why “delete”, not “update”, on a write

The note said to delete the key after a write and not to set the new value. The reason is two writers.

TimeWriter A (price 25)Writer B (price 26)Cache holds
1updates database to 2524.50
2updates database to 2624.50
3sets cache to 2626
4sets cache to 2525, and the database says 26

The cache writes arrived in a different order from the database writes, and the wrong value stays until the TTL. A delete has no value to get wrong: whoever deletes last, the key is gone and the next read loads the truth. Deleting does leave one smaller race, between a reader and a writer. That is drill 1.

checkpoint

Why does cache-aside delete the key on a write and not set the new value?

Two writers can update the cache in a different order from the database, leaving the older value cached. A delete has no value to get wrong.

Page-view counters are written through the cache and flushed every minute. What is the risk, and is it acceptable?

A cache crash loses up to a minute of counts. For view counters that is usually fine; for orders it would not be.

chapter 4 · 5 min

Failure drills

Gist Six things that will happen: a reader puts an old value back after a write, hundreds of requests rebuild the same key at once, the cache restarts empty, a delete is lost, requests for things that do not exist bypass the cache, and a value is stored under a key that says too little.

Guess first. Each of these has happened to a shop like ours.
  • 1 · stale put-back
  • 2 · stampede
  • 3 · cold start
  • 4 · lost delete
  • 5 · missing things
  • 6 · wrong key
Drill 1

The reader puts the old price back

Timeline
The key has just expired. A reader misses and reads the price from the database: 24.50. Before it can fill the cache, an admin changes the price to 26 and deletes the key, which is already empty. Then the reader writes its 24.50 into the cache.
What you see
The database says 26 and the product page says 24.50 for the next five minutes. The delete happened, the logs say so, and the page is still wrong.
What saves you
The TTL is the safety net: it bounds the damage to five minutes, which is why every key has one. To narrow the race further, delete the key a second time about a second after the write, or store the row's version with the value and let the cache accept a write only if its version is newer.

Rule: delete-on-write still has a race. A TTL on every key is what makes it a small problem.

Drill 2

Five hundred requests rebuild the same thing

Timeline
The home page shows “bestsellers”, a query that takes 2 seconds. It is cached for ten minutes and requested 500 times a second. The key expires. For the next two seconds every request misses, and each one starts the 2-second query.
What you see
A thousand copies of the heaviest query in the system, all at once. The database slows down, so the queries take longer, so more requests pile in. Every ten minutes the site stutters.
What saves you
Let one request rebuild the value while the others wait for it or are given the old value. This is called single flight. Combine it with a soft expiry, so the old value is still there to serve, and with a random spread on TTLs so that many keys do not expire in the same second (chapter 6).

Rule: a miss on a hot key must cause one rebuild, not one per waiting request.

Drill 3

The cache restarts empty

Timeline
Redis is restarted for an upgrade and comes back with nothing in it. The hit ratio is zero. All 2,000 reads a second go to a database that can serve 400.
What you see
The database is overloaded. Queries time out, so nothing is written to the cache, so the cache stays empty. The system cannot warm itself up: a metastable failure, as in the Resilience Stack deep dive.
What saves you
Plan for an empty cache as a normal event. Keep a replica so a restart does not empty it. Warm the top few thousand keys from a script before taking traffic. And put a limit on concurrent cache-miss queries, so that the database serves 400 a second well and the rest get a fast “try again” while the cache fills.

Rule: if the system cannot start with an empty cache, the cache is a database and needs to be run like one.

Drill 4

The delete never arrived

Timeline
The admin changes the price. The database commits. The DEL product:42 that follows hits a two-second network blip and fails. The request has already told the admin “saved”.
Why
Two systems were written one after the other with no transaction around them. It is the dual-write problem from the outbox note, with a cache where the broker was.
What saves you
The TTL, again, limits it to five minutes. To do better, take the delete out of the request: write an invalidation record in the same transaction as the price, or let change data capture read the database's log, and have a small worker delete keys with retries. That also covers changes made by scripts and by hand, which never ran your application code.

Rule: invalidation that happens after the commit can be lost. Make it retryable, and keep the TTL.

Drill 5

Asking for things that do not exist

Timeline
A crawler requests /product/900001, /product/900002 and so on. None exist. Each request misses the cache, queries the database, finds nothing, and stores nothing. The next request for the same id does it all again.
What you see
Database load that grows with junk traffic. The hit ratio falls and nobody changed anything. A related case: a real lookup fails with an error, and the error page is cached for five minutes.
What saves you
Cache the answer “not found” too, with a short TTL such as 30 seconds. Reject ids that cannot be valid before any lookup. And never cache a failure as if it were data: a timeout or a 500 is not an answer.

Rule: “nothing” is an answer worth caching briefly. An error is not an answer at all.

Drill 6

The right value under the wrong key

Timeline
Trade customers get the mug for 19.00. The page for product 42 is rendered for a logged-in trade customer and stored under product:42. For the next five minutes every shopper sees the trade price. The same thing at the CDN is worse: a page containing “Hello, Sam” and Sam's saved address, served to strangers.
Why
The key named less than the value depended on. Anything that changes the answer and is missing from the key is a leak waiting for the right request order.
What saves you
The key lists everything the value depends on: product:42:price-list:trade. Cache the shared parts and the personal parts separately. Mark personal responses Cache-Control: private or no-store so that no shared cache keeps them.

Rule: a cache key must contain everything that can change the answer. Personal data never goes in a shared cache.

What the six drills add up to

DecisionDrill
every key has a TTL, with a random spread1, 2, 4
one rebuild per key at a time; the old value served meanwhile2
a plan for an empty cache: replica, warm-up, a cap on miss queries3
invalidation that survives a failed delete4
“not found” is cached briefly; errors are never cached5
keys name everything the value depends on6

checkpoint

A key has no TTL “because we always delete on write”. Which drills make that dangerous?

Drills 1 and 4. A stale put-back or a lost delete then stays wrong for ever, with nothing to correct it.

After a cache restart the database is overloaded and the hit ratio stays near zero. Why does it not recover by itself?

Queries time out under the load, so no results are written to the cache, so every read stays a miss.

chapter 5 · 3 min

Invalidation: the hard problem

Gist One change has many copies: the item, the lists that contain it, search results, rendered pages. Combine five strategies: expiry, delete on write, events, versioned keys and tags. Agree with the business how stale each kind of data may be, and never make a decision on a cached value.

The old joke says there are two hard things in computing, and cache invalidation is one of them. It is hard for a plain reason: the code that changes the data has to know about every copy of it, and the copies were added later, by other people, for other screens.

One price change, five copies

Where the mug's price appearsKey
its product pageproduct:42
the “Mugs” category listcategory:mugs:page:1
search results for “mug”search:mug:page:1
bestsellers on the home pagebestsellers
baskets that contain itbasket:c-7, and many more
The first key is obvious. The other four are how stale prices actually reach customers.

Five ways to invalidate

StrategyHowGood forWeak at
Expiry onlya TTL and nothing elsedata where “a few minutes old” is fine: bestsellers, countsanything that must change quickly
Delete on writethe code that writes also deletes the keyssingle-item keys such as product:42derived keys; writers that bypass the code
Eventsa worker hears “price of 42 changed” (outbox or CDC) and deletes keys, with retriesmany keys per change; changes from anywhereyou still need to know which keys
Versioned keysthe key contains a version: product:42:v17. A change makes a new key; the old one is never read again and expiresimmutable content; build assets; avoiding the races entirelyreaders must learn the current version from somewhere
Tagseach entry is labelled with what it contains: this list page “contains 42”. Invalidate everything tagged 42lists, search results, rendered pagesneeds a cache or CDN that supports it

Real systems mix them. For the shop: the product page is deleted on write through an event worker. List and search pages carry tags, or simply a short TTL of a minute. Bestsellers expire on their own. Static files such as scripts and images get versioned names and are cached for a year, because a new version is a new name.

Decide the staleness, then the mechanism

The useful conversation is with the business, about question 1 from chapter 2.

DataMay be stale forSo
Product description, photosan hourlong TTL, delete on write
Price shown on a pagea minuteshort TTL plus event-driven delete
“In stock” labela minute, and it may be wrongshort TTL; the label is a hint
Bestsellersten minutesexpiry only
Price and stock at checkoutnot at allread from the database, inside the transaction

The rule that removes most of the fear

Cache what is shown. Never decide on a cached value. The product page may show 24.50 from a copy that is forty seconds old. The checkout reads the price from the database when it creates the order, and if it has changed, tells the shopper. With that one rule, a stale cache can produce a surprised customer, and it cannot produce a wrong charge. Stock works the same way: the page says “in stock” from a cache, and the reservation is made against the real number.

checkpoint

The product page shows the new price and the category page shows the old one. What kind of key was missed?

A derived key: a list that contains the product. The writer only invalidated the item's own key.

Why can static files be cached for a year?

Their names contain a version or content hash. A change produces a new name, so the old copy is never asked for again.

chapter 6 · 3 min

TTLs, worked out

Gist A key's hit ratio is about one minus one over its reads per TTL. Hot keys reach 99.9 % with a TTL of seconds, and cold keys gain nothing from any TTL. Use a soft expiry so stale values are served while one request refreshes, spread expiries randomly, and size the cache for the hot few.

A TTL is usually picked by feel: “five minutes sounds right”. It can be worked out, from how often the key is read.

Hit ratio of one key ≈ 1 − 1 ÷ (reads per second × TTL in seconds)

In each TTL period the first read misses and the rest hit.

KeyReadsTTLReads per TTLHit ratio
product 42, the popular mug80 a second5 min24,00099.996 %
the same80 a second10 s80099.9 %
a typical product1 a minute5 min580 %
a rarely viewed product1 an hour5 min0.08about 0 %
Row 2 is the surprise: for a hot key, ten seconds is plenty.

Two lessons. For a hot key a very short TTL already gives nearly all the benefit, so you can have fresh data and a high hit ratio together. For a cold key no reasonable TTL helps: it is written to the cache, never read and evicted. Most catalogues have a few hot items and a long tail of cold ones, and the cache earns its keep on the hot few.

Soft and hard expiry

get-product.tsserve stale, refresh once
const inFlight = new Map<string, Promise<Product>>();      // single flight, per instance

export async function getProduct(id: string): Promise<Product> {
  const key = `product:${id}`;
  const hit = await cache.get(key);                        // { value, softExpiry }
  if (hit && Date.now() < hit.softExpiry) return hit.value;  // fresh
  if (hit) { refresh(key, id); return hit.value; }           // stale: serve, refresh behind
  return refresh(key, id);                                   // gone: wait for the load
}

function refresh(key: string, id: string) {
  if (!inFlight.has(key)) {
    inFlight.set(key, loadAndStore(key, id).finally(() => inFlight.delete(key)));
  }
  return inFlight.get(key)!;                                 // everyone shares one load
}

This is the fix for drill 2, and it is the same idea as the browser's stale-while-revalidate from the server-state cache note. No shopper waits for a rebuild unless the value is entirely gone, and there is one rebuild however many are asking. Across several app instances, a short lock in Redis keeps it to one rebuild in total.

Spread the expiries

If ten thousand keys are written in the same minute, for instance after a deploy or a warm-up script, they expire in the same minute too. Add a random part to every TTL, such as five minutes plus or minus thirty seconds, so the reloads arrive as a trickle.

Sizing the memory

QuantityReasoningValue
Entries worth cachingthe products that get most of the views; not all 200,000about 20,000
Size of one entrythe product as JSONabout 2 KB
Memory needed20,000 × 2 KB, plus overheadabout 60 MB
When fullevict what was used least recentlyLRU

A cache that is too small evicts entries that would have been hits. The sign is a rising eviction count together with a falling hit ratio. A cache that is far too big only costs money, with one exception: very large single values, such as a 5 MB list under one key, slow every read of that key and are better split up.

checkpoint

A key is read 10 times a second with a 30-second TTL. Hit ratio?

1 − 1/300, about 99.7 %.

Product wants prices at most 10 seconds old. Does that ruin the hit ratio for popular products?

No. At 80 reads a second a 10-second TTL still gives 99.9 %. It only costs anything on rarely read products, which were not benefiting anyway.

The layers, from browser to database

Gist Browser, CDN, app memory and Redis each hold a copy with its own expiry. Their staleness adds up, so the TTLs together must fit what the business agreed. You can clear Redis and the CDN but not a browser, so the browser gets the shortest life. Files named by version can be cached for a year.

Chapter 1 showed five places that hold a copy. Each is a cache with its own expiry, its own key and its own way of being wrong.

LayerShared byWho can clear itTypical risk
Browserone personnobody but that personyou cannot take back what you allowed it to keep
CDNeveryone in a regionyou, with a purge callpersonal pages cached for all (drill 6)
App memoryone app instancea restart, or its own TTLtwo instances disagree; a refresh flips the price back and forth
Redisall app instancesyour codethe drills in chapter 4
Databaseits own internal caches. Leave them to it
The further a cache is from the database, the less control you have over it. Give the far ones the shortest lives.

The staleness adds up

Five minutes in Redis, five at the CDN and five in the browser is not five minutes. A copy can be read from Redis at the end of its life, stored by the CDN for five more, and then kept by the browser for five more.

LayerTTLWorst-case age when the shopper sees it
Redis5 min5 min
+ CDN5 min10 min
+ browser5 min15 min

If the business said “one minute” in chapter 5, the three TTLs together must fit in one minute, or the outer layers must be invalidated as well.

Speaking to the outer layers

The browser and the CDN are controlled by response headers. A handful covers most needs.

HeaderMeaning
Cache-Control: max-age=60anyone may keep this for 60 seconds
s-maxage=300shared caches such as the CDN may keep it for 300; overrides max-age for them
stale-while-revalidate=30after expiry, serve the old copy for up to 30 s more while fetching a new one
privateonly the person's own browser may keep it; no shared cache
no-storenobody keeps it. For anything personal or secret
ETag with If-None-Match“has it changed since version abc?” The server answers 304 with no body if not

A good pattern for a product page: a short max-age for browsers, a longer s-maxage for the CDN, and a purge of the CDN when the price changes. The CDN is the outer layer you can clear, so let it hold the page longest, and give the browser, which you cannot clear, very little.

Files that never change

Scripts, styles and images are the easy case, if they are named by their content: app.3f9a1c.js. The file under that name never changes, so it can be cached for a year with immutable. A new build produces a new name. This is the versioned-key strategy from chapter 5, and it is the only kind of invalidation with no race in it.

The cache inside the app

A small in-memory cache in each app instance, in front of Redis, removes even the 1 ms network hop and protects Redis from a very hot key. Keep its TTL tiny, one to five seconds. Each instance expires on its own schedule, so for those seconds two instances can give different answers, and a shopper who refreshes may see the price change and change back.

checkpoint

Redis 60 s, CDN 60 s, browser 60 s. How old can the price on screen be?

Up to three minutes.

Two app instances each cache the price in memory for 5 seconds. What might a shopper notice?

Refreshing the page can show the new price, then the old one again, as requests land on different instances.

Running it: graphs and runbooks

Gist Watch the hit ratio per key family, the miss queries reaching the database, evictions and refresh failures. For stale data, walk outward from the database to find the layer holding the old copy, and clear from the inside out. For a cache outage: short timeouts, a capped fallback, and a warm start.

A cache fails in two ways. Loudly, when it is down. And quietly, when it is up and serving the wrong thing, or serving very little. The quiet failures need graphs.

MetricHealthyIt means trouble when
Hit ratio, per kind of keysteady, high for hot datait drops: keys changed, TTLs shortened, junk traffic (drill 5), or the cache is too small
Miss queries reaching the databasea small, steady streamspikes on a regular beat: stampedes (drill 2)
Evictionsfewmany, with a falling hit ratio: not enough memory
Stale serves and refresh failuressome stale serves, no failuresrefreshes failing: the cache is hiding a database problem
Cache response timeabout a millisecondit rises: a huge value, a hot key, or the cache server is saturated
Age of served data, where you can measure itwithin what was agreedolder than the business said was acceptable
Split the hit ratio by key family. One overall number hides a broken family behind a healthy one.

Runbook: “customers still see the old price”

  1. Check the truth. What does the database say? If it is wrong there, this is not a cache problem.
  2. Walk outward. Read the key in Redis. Request the page from an app instance directly. Request it through the CDN and look at its Age header. The first layer that shows the old value is where the copy is stuck.
  3. Clear from the inside out. Redis first, then the CDN. Clearing the CDN first only makes it refill from a stale Redis.
  4. Accept what you cannot clear. Browsers keep their copy until it expires. That is why their TTL was short.
  5. Find the missed key. Which copy was not invalidated, and why did the writer not know about it? That is the real fix (chapter 5).

Runbook: the cache is down or slow

  1. The app must not hang on it. Cache calls have a short timeout, tens of milliseconds, and a circuit breaker. A slow cache is worse than no cache, exactly as in the Resilience Stack deep dive.
  2. Fall back with a limit. On a cache failure the app reads the database, through the cap on miss queries from drill 3. Without the cap, the fallback is what takes the database down.
  3. Bring it back warm. Run the warm-up script for the hottest keys before sending full traffic.

Hot keys and big keys

Two shapes cause trouble at scale. A hot key takes a large share of all reads: the home page, or one product in a television advert. In a cache split over several servers, that one server gets the whole load. The cure is the tiny in-memory layer from chapter 7 for those keys. A big key holds megabytes: a whole category in one value. Every read moves all of it. Split it into pages, or cache ids and fetch the items separately.

Flushing everything

“Just flush the cache” fixes a stale-data incident and starts drill 3. If you must, do it by key family, one at a time, with the miss cap in place, at a quiet hour.

checkpoint

Why clear Redis before the CDN?

The CDN refills from the app. If Redis still holds the old value, the CDN caches the old page again.

Miss queries spike every ten minutes exactly. What is happening?

A hot key with a ten-minute TTL expires and many requests rebuild it together: a stampede.

Testing a cache

Gist Cache bugs need a second read or two things at once. Test read-after-write for every copy of the data, one database query for many concurrent misses, and two audiences on the same key. Run the whole suite with the cache switched off, and run one load test from an empty cache.

Cache bugs hide from ordinary tests, because a test usually reads once and writes once, and a cache only misbehaves on the second read, or when two things happen at once.

TestHowCatches
Read after writeread, change the price, read again: the second read shows the new pricea forgotten invalidation
Every copyafter a price change, read the product page, the category list and the search resultderived keys nobody invalidates (chapter 5)
One rebuild100 concurrent reads of a cold key: the database sees one querystampedes (drill 2)
Reader against writerpause a reader between its database read and its cache write; run a write; resumethe stale put-back (drill 1)
Not foundask twice for a missing id: one database querydrill 5
Two audiencesread as a trade customer, then as a guestkeys missing a dimension (drill 6)
Cache offrun the whole test suite with the cache disabledcode that only works because of what is cached
Cache downmake every cache call time out: pages still load, within the time limita missing timeout or fallback
“Cache off” is the cheapest and finds the most. The app must be correct with no cache at all.
product-cache.test.tsthe stampede, as a test
test("a cold hot key causes one database query", async () => {
  await cache.delete("product:42");
  db.resetQueryCount();

  await Promise.all(Array.from({ length: 100 }, () => getProduct("42")));

  expect(db.queryCount("products")).toBe(1);
});

Test with a cold cache under load

Load tests are nearly always run warm, because the test has been running for a while by the time anyone looks. Add one run that starts with an empty cache at full traffic. It answers the question from chapter 2: is the cache optional or required? If the system does not recover by itself, you have found drill 3 on a quiet afternoon instead of during an upgrade.

Make stale data visible

In test and staging environments, have responses say where they came from: a header such as X-Cache: hit, age=212. The runbook in chapter 8 becomes a matter of reading headers, and testers can tell a caching bug from a data bug without asking a developer.

checkpoint

The suite fails with the cache switched off. What does that tell you?

Some code depends on a cached value being there, for correctness. The cache has become a source of truth by accident.

Why does a normal load test miss drill 3?

By the time results are read, the cache is warm. Only a run that starts empty at full traffic shows whether the system can recover.

When not to cache, a lab and the checklist

Gist Fix the query, add a replica or build a summary table before adding a cache. Do not cache what decisions are made on, what is rarely read or what is personal in a shared cache. The lab designs caching for a category page with a one-minute freshness rule, and the checklist turns the deep dive into review questions.

Before you add a cache

A cache adds a second copy of the truth and every problem in this deep dive. Try the cheaper things first.

SymptomTry first
one slow queryan index, or a better query
many reads, the database is busya read replica
an expensive sum or join, read oftena materialised view or a summary table, updated on write
the same data fetched many times in one requestload it once per request
still too slow or too frequent after thosenow a cache

Lab

The “Mugs” category page lists 24 products with names, photos and prices. It is requested 300 times a second. Its query takes 400 ms. Prices change a few times a day and the business wants a change visible within one minute. Trade customers see different prices.

  1. What is the cache key?
  2. How is the page invalidated when one mug's price changes?
  3. What TTLs do you set in Redis, at the CDN and in the browser?
  4. What happens when the key expires at 300 requests a second?
  5. A shopper adds a mug to the basket at the listed price. Where does the checkout get the price?

model answer

1 · The key

category:mugs:page:1:prices:retail. It names the category, the page and the price list. Without the price list in the key, trade prices leak to everyone (drill 6). Better still, cache the list of product ids and names once, and the prices per price list separately.

2 · Invalidation

The writer of a price does not know which lists contain the product, so delete-on-write is not enough. Either tag the entry with the product ids it contains and invalidate by tag from an event worker, or rely on a short TTL. With “within one minute” as the requirement, a 30-second TTL alone is acceptable and much simpler.

3 · TTLs

They must add up to under a minute. For example Redis 20 s, CDN 20 s for the retail page, browser 10 s. The trade version is marked private and is not stored by the CDN at all. At 300 requests a second, a 20-second TTL still gives a hit ratio of 99.98 %.

4 · Expiry under load

Without protection, 400 ms × 300 a second is about 120 copies of the query at once. With single flight and a soft expiry, shoppers keep getting the old page for those 400 ms and exactly one query runs.

5 · Checkout

From the database, inside the transaction that creates the order. If it differs from what the page showed, the shopper is told before paying. The cached price was for display only.

The review checklist

Before caching

  • The slow query was fixed or indexed first
  • Someone has said how stale this data may be
  • No decision is made on the cached value; checkout and permissions read the source
  • It is known whether the system can run without the cache

Keys and values

  • The key names everything the answer depends on
  • Shared and personal data are cached separately
  • Personal responses are private or no-store
  • “Not found” is cached briefly; errors are never cached
  • No single value is megabytes in size

Expiry and rebuild

  • Every key has a TTL with a random spread
  • Hot keys use a soft expiry and one rebuild at a time
  • TTLs across layers add up to less than the agreed staleness
  • The browser gets the shortest TTL; static files have versioned names

Invalidation

  • Writes delete keys; they do not set them
  • Every copy of the data is listed: item, lists, search, pages
  • Invalidation is retried, through an outbox or the database's log
  • Changes made outside the application also invalidate

Failure

  • Cache calls have a short timeout and a breaker
  • Miss queries to the database are capped
  • There is a warm-up script and a replica
  • Nobody flushes everything during business hours

Tests and operations

  • The test suite passes with the cache switched off
  • A test shows one database query for many concurrent misses
  • A load test starts from an empty cache
  • Hit ratio per key family, miss queries and evictions are on a dashboard
  • Responses can say which layer served them and how old the copy is
