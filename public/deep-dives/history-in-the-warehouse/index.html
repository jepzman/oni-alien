Four notes in sixty seconds

Gist History tables keep past versions, bitemporal data adds when you knew, slowly changing dimensions decide per column, and late-arriving data files events by when they happened. In a warehouse they meet in one question: which version of the past does this report mean?

Four notes deal with the past. In a warehouse they meet, because every report about last year has to decide which version of the world to use.

NoteIn one line
History Tables (Vol. 3)keep every past version of a row, with when it was valid
Bitemporal Data (Vol. 3)record when a fact was true and when you knew it
Slowly Changing Dimensions (Vol. 9)per column, overwrite (type 1) or add a dated version with a new key (type 2)
Late-Arriving Data (Vol. 9)file each event in the period it happened, even when it reaches you late
The SCD note covers types 1 to 6 on one product. This dive is about running them for years.

The notes describe each idea on one row. The warehouse holds thousands of changing rows, facts that point at them, and people asking for the past in three different ways without saying which. This dive follows three changes at the shop through one year and answers the questions they cause: why March changed, why the same customer counts twice, and what the report said on 15 July.

Three people, three questions about last year

WhoAsksWhich past they mean
finance“What was Kitchen's revenue in March?”as it was: the category when it was sold

The real mechanism: versions and keys

Gist A type 2 dimension keeps one row per version, with a surrogate key, the natural key, a half-open validity range and a hash of the tracked columns. Each load closes changed versions and inserts new ones. Facts find their version by event time once, at load, and store its key.

A type 2 dimension is a history table with two extra promises: each version has its own surrogate key, and facts store that key, so they keep the version they were loaded with.

The columns, and why each exists

ColumnPurpose
product_keysurrogate key per version; facts store it, so joins are one equality
skunatural key from the source; ties all versions together
tracked columnscategory, brand: a change here creates a version
type 1 columnsdescription, spelling: a change here updates every version
valid_from, valid_tohalf-open range in business time: >= from AND < to
is_currenta convenience for “as it is” joins; derivable from valid_to
hashdiffhash of the tracked columns, to detect a change cheaply
loaded_atwhen the warehouse wrote the row (the other clock, chapter 4)
Use a far-future date such as 9999-12-31 for the open end, not NULL. Range joins and BETWEEN-style checks stay simple.

One load, step by step

Each run compares today's source rows with the current dimension rows. Three outcomes per natural key: new (insert a first version), changed in a tracked column (close the current version, insert a new one), changed only in type 1 columns (update all versions in place).

dim_product_load.sqltwo statements, one transaction
BEGIN;
-- 1 · close current versions whose tracked columns changed
UPDATE dim_product d
SET    valid_to = s.effective_from, is_current = false
FROM   stg_products s
WHERE  d.sku = s.sku AND d.is_current AND d.hashdiff <> s.hashdiff;

-- 2 · insert new versions (changed keys) and first versions (new keys)
INSERT INTO dim_product (sku, name, category, brand, valid_from, valid_to, is_current, hashdiff, loaded_at)
SELECT s.sku, s.name, s.category, s.brand,
       coalesce(s.effective_from, DATE '1900-01-01'), DATE '9999-12-31', true, s.hashdiff, now()
FROM   stg_products s
LEFT JOIN dim_product d ON d.sku = s.sku AND d.is_current
WHERE  d.sku IS NULL;           -- no current row: new key, or just closed above
COMMIT;

Where does effective_from come from? Ideally from the source: the date the category change takes effect. If the source has none, the load date is used, which is the origin of drill 3.

Facts pick their version once

The fact load joins on the natural key and the event time, finds exactly one version, and stores its surrogate key. After that, every report joins facts to dimensions on one integer column, and the past never moves.

fact_lookup.sqlpoint-in-time lookup, at load time
SELECT s.order_line_id, p.product_key, s.amount
FROM   stg_order_lines s
JOIN   dim_product p
  ON   p.sku = s.sku
 AND   s.sold_at >= p.valid_from
 AND   s.sold_at <  p.valid_to;

Order 9001's kettle, sold on 31 March, gets key 812 and will say Kitchen forever. A kettle sold on 20 May gets 977.

When a member disappears

Products are discontinued and customers close accounts. Deleting the dimension row would break every fact that points at it, so a delete in the source becomes a closed version: set valid_to to the deletion time, is_current to false, and insert nothing. The natural key then has no current version, which is exactly right: “current products” no longer includes it, and last year's sales still join. If the same SKU comes back later, the load sees a new key and inserts a fresh first version; the gap between the two versions is real and the no-gaps test (chapter 7) should allow it for keys that were deleted. Personal data is different: a customer who asks to be forgotten is anonymised in every version (chapter 8), not closed.

checkpoint

Why use a far-future date instead of NULL for the open end?

Range conditions stay simple and index-friendly; no special case for the current version.

When does a fact find its dimension version?

Once, at load time, by matching the natural key and the event time to a validity range; then it stores the surrogate key.

Failure drills

Gist Six ways history goes wrong: a natural-key join that doubles sales, a midnight boundary that belongs to two versions, a backdated move dated by load time, a fact dropped before its customer arrived, a fast-changing column that explodes the dimension, and changes between snapshots that were never seen.

Each drill is a report that looked fine until someone compared it with something else.
  • 1 · sold twice
  • 2 · midnight
  • 3 · backdated
  • 4 · no version yet
  • 5 · 700 million rows
  • 6 · lost change
Drill 1

The kettle that sold twice

Timeline
An analyst writes a quick report joining fact_sales to dim_product on sku, because the fact table also has the SKU. Since 12 May the kettle has two versions. Every kettle sale now joins to both rows, and kettle revenue for the year doubles.
Why
The natural key identifies the product, not the version. Joining on it matches every version. The error appears only after the first type 2 change, so it passes every test written before that.
What saves you
Join facts on the surrogate key, always. If a natural key must be on the fact (for debugging), name it so nobody joins on it by accident, and add a test that the join on the surrogate key and the sum of facts give the same total. Grant analysts a view that has only the safe join.

Rule: facts join dimensions on the surrogate key. A natural-key join multiplies rows the day history begins.

Drill 2

The sale at midnight

Timeline
The kettle's category change is stored with valid_to = 2026-05-12 00:00 on the old row and valid_from = 2026-05-12 00:00 on the new one. The lookup uses BETWEEN valid_from AND valid_to. A sale at exactly 00:00:00 on 12 May matches both versions; one in the web shop's time zone at 23:30 UTC on 11 May matches the wrong one.
Why
BETWEEN includes both ends, so a shared boundary belongs to two versions. And the change was dated in local time while sales were in UTC.
What saves you
Half-open ranges everywhere (>= from AND < to) and one time zone for every validity column and every event time, converted once in staging. Add a test that every fact matches exactly one version.

Rule: half-open ranges, one time zone. A boundary belongs to the next version only.

Drill 3

Customer 77 moved before we knew

Timeline
Customer 77 moves to Rotterdam on 1 February and tells the shop on 20 February. The CRM changes the city that day. The dimension load dates the new version from 20 February, the day it saw the change. Three orders between 1 and 20 February stay in Utrecht in the regional report forever.
Why
The pipeline used load time as business time. The CRM knew the move date (the customer gave it), but the extract only copied the current city.
What saves you
Extract the effective date when the source has one (moved_on), and date versions by it. Then decide what to do with facts already loaded: re-key the three February orders to the Rotterdam version (as was, corrected), or leave them and record the correction (as reported). Both are valid; the choice must be made, written down and applied the same way every time (chapter 4).

Rule: date versions by when the change took effect, not when you saw it, and decide how corrections reach old facts.

Drill 4

The order that arrived before its customer

Timeline
A new customer signs up and orders within a minute. Orders arrive by CDC every 15 minutes; customers arrive from the CRM nightly. At 00:15 the order's lookup finds no customer version. The inner join drops it, and the day is €55 short until someone reloads it.
Why
Facts and dimensions come from different sources on different schedules. “No version yet” was treated as “no customer”.
What saves you
Never drop a fact for a missing version. Insert an inferred member: a version for the natural key with placeholder attributes, flagged as inferred, valid from the beginning of time. The nightly load then updates that inferred version in place (it never had real attributes to preserve) rather than adding a new one. Monitor how many facts point at inferred members.

Rule: facts always load; a missing version becomes an inferred member, filled in when the dimension arrives.

Drill 5

Seven hundred million customers

Timeline
last_login_at is on the CRM's customer table, and the snapshot tracks every column. Each day about 1.9 million of the 2 million customers log in or are touched. After a year dim_customer has 700 million rows, the fact lookup takes an hour, and “customers by city” needs a de-duplication nobody understands.
Why
Type 2 on a fast-changing column turns a slowly changing dimension into a daily snapshot. Every version is a copy of every other column.
What saves you
Track type 2 only on columns people group or filter by (city, segment, tier). Exclude fast-changing columns from change detection, or move them out: last login becomes an activity fact, and banded values (age band, spend band) go in a small mini-dimension referenced from the fact.

Rule: type 2 is for slow, meaningful changes. Fast-changing columns belong in facts or mini-dimensions.

Drill 6

The change that never happened

Timeline
The kettle's brand is changed by mistake at 10:00 and changed back at 15:00. The nightly snapshot sees no difference and records nothing. That is fine. But the price team made a real change at 09:00 and another at 16:00 on the same day, and only the 16:00 value was recorded. A report on promotions that ran that afternoon uses the wrong price.
Why
A periodic snapshot (dbt snapshots run nightly, or any daily compare) sees only the state at each run. Changes between runs are lost, and short-lived values never existed as far as the warehouse knows.
What saves you
Decide the resolution history needs. For most dimensions, daily is fine and losing a five-hour typo is a feature. Where intra-day changes matter (prices, stock), build history from the change log (CDC events, with their commit times) instead of from snapshots, or from the source's own history table.

Rule: a snapshot only knows what it saw. If changes between runs matter, build history from the change log.

Kettle revenue doubled after 12 May. First thing to check?

Whether a report joins facts to the dimension on the natural key instead of the surrogate key.

Why not track last_login_at as type 2?

It changes daily for most customers, turning the dimension into a daily copy; it belongs in a fact.

The hard problem: three pasts

Gist People mean three things by “last year”: as it was (type 2 in valid time), as it is (current attributes applied to the past), and as it was reported (what the warehouse knew on a date). Keep valid and recorded time apart, and write down one rule for corrections that reach into the past.

Customer 77's move has two dates: it happened on 1 February and it was recorded on 20 February. A report about February asked on 10 February and the same report asked on 1 March should give different answers, and both answers were right when given. Holding both is what the bitemporal note is about, and it is the hard problem of warehouse history.

Three questions, three mechanisms

QuestionCalledAnswered by
“Kitchen revenue in March”as it wastype 2 versions in valid time; facts keep their surrogate key
“This year by today's regions”as it istype 1 columns, or the current attributes copied onto every version (type 6), or a join through the natural key to the current row
“What did the report say on 15 July?”as it was reportedversions also stamped with recorded time (bitemporal), or a filed snapshot of the report itself
If nobody will ever ask the third question, don't build for it. Regulated businesses will be asked.

Answering “as it is” without breaking “as it was”

Type 6 adds current_region to every version of every shop, updated in place whenever the shop changes. A report groups by region for as it was and by current_region for as it is, from the same facts and the same join. The cost: every change touches every old version of that shop, which is cheap for 30 shops and expensive for 2 million customers. For large dimensions, join from the version to its current row through the natural key instead:

as_is.sqltoday's region for the whole year
SELECT cur.region AS region_today, sum(f.amount) AS revenue
FROM   fact_sales f
JOIN   dim_shop  v   ON v.shop_key = f.shop_key                 -- the version sold under
JOIN   dim_shop  cur ON cur.shop_code = v.shop_code AND cur.is_current
WHERE  f.order_date >= DATE '2026-01-01'
GROUP  BY 1;

Answering “as it was reported”

Add recorded time to the dimension: recorded_from and recorded_to. A correction never updates a row; it closes the old row's recorded range and inserts new rows. To see what the warehouse believed on 15 July, filter versions by recorded_from <= '2026-07-15' AND recorded_to > '2026-07-15' and then join by valid time as usual. Facts need the same treatment if they are corrected, which is why the cheaper answer is often to snapshot the report at filing time (chapter 8): store the numbers that were sent, with the date.

Corrections: the rule you must write down

Drill 3 forces a choice whenever a change arrives with an effective date in the past:

RuleOld factsGood for
Correct the pastre-keyed to the corrected versionanalysis: the truth as best known now
Keep what was loadedunchanged; the version starts at the load dateoperational reports that must not move
Both (bitemporal)corrected in valid time, old belief kept in recorded timeaudit and regulated reporting

Most shops pick the first for analysis and file a snapshot of each closed month for audit. That covers all three questions with one type 2 dimension and a folder of filed reports.

checkpoint

Which mechanism answers “this year by today's regions”?

Current attributes on every version (type 6) or a join through the natural key to the current row.

What's the cheapest way to answer “what did the report say on 15 July”?

Store the filed report's numbers when it is sent, with the date.

Four ways to keep history

Gist Type 2 with keys on facts makes as-it-was joins cheap. Type 6 adds as-it-is columns for small dimensions. A history table with point-in-time joins at query time makes corrections free but every query pays. Daily snapshots are simple and honest about what you knew, and costly in size.

Variant C is how many lakehouses work now: cheap compute makes range joins affordable, and backdating gets easy.

Variant A is the classic and still the default for facts that are queried many times: the range join happens once, at load time. Variant B adds as-is reporting for small dimensions. Variant C moves the range join to query time, which costs every query but makes corrections trivial: change a version's dates and every report follows, no fact reloads. It needs a view or metrics layer that always writes the date condition, or drill 1 returns. Variant D is the simplest to build (copy the table daily) and the most honest about what you knew each day, but it costs a full copy per day and loses intra-day changes.

Making variant C safe

The danger of query-time joins is drill 1 on every report someone writes. Give analysts a view that already contains the date condition, and grant them only the view:

sales_as_it_was.sqlvariant C, the only way analysts reach products
CREATE VIEW sales_as_it_was AS
SELECT f.*, p.category, p.brand
FROM   fact_sales f
JOIN   product_history p
  ON   p.sku = f.sku
 AND   f.sold_at >= p.valid_from
 AND   f.sold_at <  p.valid_to;

Mixing them is normal. What must be consistent is the rule for corrections (chapter 4) and the habit of joining on keys or always writing the date condition.

checkpoint

Which variant makes backdated corrections easiest?

A history table joined at query time: re-date the version and every report follows, without re-keying facts.

Why is type 6 costly on large dimensions?

Every change to a current attribute updates every version of that member.

History in numbers

Gist Products grow from 40,000 to 160,000 versions a year; customers from 2 to 2.5 million; tracking last login would make 700 million. Range joins cost seconds once at load, or on every query at query time. A daily snapshot of customers is 146 GB a year compressed.

The shop's dimensions are small next to its facts: 60 million order lines a year against a few million dimension rows. The numbers that matter are growth rates and join costs.

How fast dimensions grow

DimensionBase rowsTracked changes a yearRows after 1 yearAfter 5 years
products40,000~3 per product160,000640,000
customers (city, segment)2,000,000~10 % move, ~15 % change segment2,500,0004,500,000
customers (every column, drill 5)2,000,000~1.9 M touched a day~700,000,000billions
shops31~2 re-orgs~90~350
A dimension that grows faster than its fact table is a sign that something which should be a fact was modelled as an attribute.

Where the range join is paid

Variant A pays the point-in-time lookup once per fact row, at load: about 160,000 new order lines a day joined to 160,000 product versions, which takes seconds. Every report afterwards joins on an integer. Variant C pays it on every query: a year of sales, 60 million lines, range-joined to 160,000 versions. Modern warehouses do this in a few seconds for one report; a dashboard opened 300 times on a Monday pays it 300 times. Pre-join in an aggregate (by day, category as it was) and the difference disappears for the common reports.

The cost of type 6

Every change to a current attribute updates all versions of that member. For 31 shops a re-org touches a few hundred rows. For 2 million customers, a nightly segment recalculation that changes 300,000 customers' current segment updates every version of each of them, about 400,000 rows, every night. Fine in a columnar warehouse, but it makes the dimension a full rewrite target; prefer the join through the natural key for large dimensions.

Sizing a mini-dimension

Drill 5's fix moves fast-changing attributes into bands. Customers get an age band (6 values), a spend band over the last 12 months (5), a loyalty tier (4) and a newsletter flag (2). Every combination is one row: 6 × 5 × 4 × 2 = 240 rows, whatever the number of customers. Each fact stores both customer_key and customer_profile_key, looked up at load time, so “sales by spend band at the time” is a plain join. The bands change every month for many customers; the mini-dimension never grows. Keep bands coarse: if the combinations go past a few hundred thousand, it is a fact table in disguise.

Daily snapshots, priced

A daily copy of 2 million customers with 40 columns is about 400 MB compressed per day, 146 GB a year. Storage is cheap; scanning it is not. Point-in-time queries on snapshots must always filter by date first, or they scan the year. Partition by snapshot date and keep, for example, daily copies for 90 days and month-end copies after that.

checkpoint

A dimension grows faster than its fact table. What does that suggest?

A fast-changing value is modelled as an attribute instead of as a fact.

Where does variant A pay for the range join?

Once per fact row, at load time; reports join on integer keys afterwards.

Testing history

Gist Test the shape of history on every load: one current version per key, no overlaps, no gaps, every fact inside its version, and joins that don't multiply. Unit test the load with the drills as cases, and rebuild filed reports to check they don't move.

History bugs don't fail loudly: a report is a little off, and only for periods after a change. Tests must check the shape of the history itself, on every load.

TestChecksCatches
one current versionexactly one is_current row per natural keyhalf-applied loads
no overlapsno two versions of a key share a momentdrill 2, double matches
no gapseach version's valid_to equals the next one's valid_fromfacts that match no version
facts match their versioneach fact's event time is inside its version's rangere-keying bugs, drill 3
joins don't multiplysum of facts equals sum after joining every dimensiondrill 1
version growthnew versions per day within the usual banddrill 5 before it costs a fortune
The overlap test is the one to write first. Almost every history bug ends in two versions claiming the same moment.
test_no_overlap.sqlreturns the offending pairs; must return none
SELECT a.sku, a.product_key, b.product_key
FROM   dim_product a
JOIN   dim_product b
  ON   a.sku = b.sku
 AND   a.product_key < b.product_key
 AND   a.valid_from < b.valid_to
 AND   b.valid_from < a.valid_to;

Facts that point at the wrong version

After any re-keying (chapter 8) or a change to the lookup, check that each fact's event time lies inside the version it stores. It is a join on the key and a range check, cheap enough to run on the last 60 days every night.

test_fact_in_version.sqlmust return no rows
SELECT f.order_line_id, f.sold_at, p.product_key, p.valid_from, p.valid_to
FROM   fact_sales f
JOIN   dim_product p ON p.product_key = f.product_key
WHERE  f.order_date >= current_date - 60
  AND  NOT (f.sold_at >= p.valid_from AND f.sold_at < p.valid_to);

Unit tests for the load

Feed the dimension load small, hand-made sequences and assert the resulting versions. The useful cases are exactly the drills:

  • A change, then nothing: one closed version, one current.
  • A change and its undo within one run: no new version (or two, if history is built from the log; test whichever you chose).
  • A backdated change: the new version starts at the effective date, and the old one ends there.
  • A type 1 change: no new version, every version updated.
  • An inferred member followed by the real one: one version, updated, still the same key.
  • The same batch loaded twice: no change (idempotent).

Testing the three pasts

Write one small fixture with all three of this year's changes in it: the kettle sold in March and in June, customer 77's February orders, and a Delft sale in May and one in August. Then assert one answer per question. March Kitchen revenue includes the March kettle and not the June one (as it was). The whole year by today's regions puts both Delft sales in South (as it is). The February regional report rebuilt with the correction puts customer 77 in Rotterdam, and the filed February report still says Utrecht (as it was reported). Three questions, five rows of data, and every later change to the dimension load is checked against them in seconds.

Report tests across a change

Pick a filed report, say March by category, and keep its numbers as a fixture. After any change to the dimension load, rebuild and compare: March must not move unless a deliberate correction says so.

checkpoint

Which single test catches most history bugs?

No overlapping versions per natural key.

How do you check a load change didn't rewrite the past?

Rebuild a filed report from the warehouse and compare it with the kept numbers.

Running it

Gist Watch new versions per day, unfilled inferred members and backdated changes. Keep a runbook for bulk-update explosions, backdated corrections, rebuilding from raw, erasure across every version, and re-organisations. File reports that leave the team.

History is a slow-moving thing to operate. Most of the work is noticing the unusual day and handling corrections with a rule rather than a script.

MetricMeansAlert when
new versions per day, per dimensionhow fast history growsmore than 3× the usual (a bulk update or a new tracked column)
inferred members still unfilledfacts waiting for their dimensionolder than 2 days, or over 1 % of yesterday's facts
backdated changes per daycorrections reaching into closed periodsany into a filed month
A spike in new versions is nearly always one script upstream that touched every row.

The runbook

SituationDo
a bulk update created a version for every rowdelete the versions created by that run (by loaded_at), reopen the previous ones, exclude the touched column from change detection, rerun
a backdated change arrives for a filed monthapply the written rule (chapter 4): re-key facts for analysis; the filed report snapshot stays as filed; log the correction
the dimension load had a bug for weeksrebuild the dimension from raw (all change events or daily copies are still there), then re-key facts for the affected period
a customer asks to be forgottenerase or anonymise the personal columns in every version, in raw and in snapshots; keep keys so facts still add up
regions are reorganiseda new version per shop with the new region from the effective date; current_region updated; publish both views to managers

Re-keying facts after a correction

When customer 77's move is backdated to 1 February, the three February orders still point at the Utrecht version. If the written rule is “correct the past”, re-key them in one idempotent statement, restricted to the affected key and dates, and log what changed:

rekey_customer_77.sqlonly the facts the correction touches
UPDATE fact_sales f
SET    customer_key = c.customer_key
FROM   dim_customer c
WHERE  c.customer_no = :customer_no
  AND  f.customer_no = c.customer_no
  AND  f.sold_at >= c.valid_from AND f.sold_at < c.valid_to
  AND  f.customer_key <> c.customer_key
  AND  f.order_date >= :effective_from;   -- the corrected range only

Run it after the dimension load, inside the same write–audit–publish cycle, so aggregates and reports are rebuilt for the touched days before anyone sees a half-corrected February.

Filing reports

For anything sent outside the analytics team (month-end to finance, quarterly to the board, anything to a regulator), store what was sent: the numbers, the date, the version of the definitions. A table of filed results is cheaper and clearer than a bitemporal warehouse, and it answers the auditor's question exactly.

filed_reports.sqlkeep what you sent
INSERT INTO filed_report_lines (report, period, filed_on, dimension_value, measure, value)
SELECT 'monthly_revenue_by_category', '2026-03', current_date, category, 'revenue', revenue
FROM   rpt_revenue_by_category
WHERE  month = '2026-03';

checkpoint

New versions per day jump 50×. Likely cause?

A bulk update upstream touched every row, or a fast-changing column started being tracked.

A customer asks to be forgotten. Where must you act?

Every version in the dimension, plus raw and any snapshots; keep keys so facts still add up.

Tools

Gist dbt snapshots build type 2 tables, temporal tables keep system-time history, the SQL:2011 period extensions add both clocks, and lakehouse time travel shows past table states. Each gives one clock well; effective dates, resolution and the corrections rule stay yours.

Many tools build history for you. Each gives one of the two clocks well and leaves the other, and the corrections rule, to you.

Choosing the resolution

Every snapshot-based tool records history at the frequency it runs. Run the customer snapshot nightly and a customer who changes segment twice in a day appears to have changed once. That is usually right for dimensions: reports group by the state that lasted, not by an hour-long typo. For the few attributes where every change matters (prices during a promotion, stock levels), take history from the change stream instead, where each event carries its own commit time, and keep the snapshot for everything else.

The shop's snapshot, configured

snapshots/customers.sqldbt: tracked columns only, effective date from the source
{% snapshot customers_snapshot %}
{{ config(unique_key='customer_no',
          strategy='check',
          check_cols=['city', 'segment'],     -- not last_login_at (drill 5)
          hard_deletes='invalidate') }}
select customer_no, city, segment, moved_on,  -- effective date travels along
       name, email                             -- type 1: fixed up in the dimension model
from {{ ref('stg_customers') }}
{% endsnapshot %}

The snapshot dates versions by its run time. The dimension model on top of it then uses moved_on, when present, as valid_from, which handles drill 3 without hand-written version logic.

dbt snapshots are the most common starting point. Feed them an effective date column where the source has one, track only the columns that matter, and you have variant A or C with very little code.

A lab and the checklist

Gist The lab reorganises regions mid-year: finance wants the filed half-year, managers want the year in new regions, the auditor wants proof June didn't move, and a franchisee wants their shop's whole history. The checklist turns the dive into review questions.

The lab. On 1 July the shop reorganises: regions North and South become North, South and Coast, and the Delft shop moves from North to South. Franchisees join the same month and will see their own shops' history. Three requests arrive the same week:

  1. Finance: “The half-year report by region, exactly as we filed it on 5 July.”
  2. The new regional managers: “The whole of this year by the new regions, so we have a baseline.”
  3. The auditor: “Show that the June figures in the filed report haven't changed since.”
  4. A franchisee who bought the Delft shop: “My shop's sales since 1 January, by month.”
  5. Someone proposes making region type 1, “so everything is in the new regions and simple”. What do you answer?

model answer

1 · As filed

From the filed report table: the half-year numbers stored on 5 July. Not recomputed: the point is that they don't change.

2 · As it is

dim_shop as type 6: each shop has a new version from 1 July with the new region, and current_region on every version. The managers' report groups by current_region over the whole year.

3 · Unchanged since

Rebuild June by region as it was (type 2 versions) and compare with the filed table. If a backdated correction has touched June since, the difference is listed in the corrections log with its date and reason.

4 · The franchisee

Join through the natural key (the shop code), not the version, so all of Delft's history counts, whatever region it was in. Row-level security on the shop code keeps other shops out (Vol. 9, embedded reporting).

5 · Type 1 region

No. It would silently rewrite the filed half-year report and every past regional comparison. Type 6 gives the managers the “everything in new regions” view with one column, without changing the past.

The review checklist

Design

  • Every column is classified: type 0, 1 or 2
  • Fast-changing attributes are facts or mini-dimensions
  • Validity is half-open, in one time zone
  • The open end is a far-future date

Loading

  • Versions are dated by effective date where the source has one
  • Change detection uses a hash of tracked columns only
  • Missing versions become inferred members
  • Loads are idempotent

Facts

  • Facts store the surrogate key, found by event time
  • Nobody joins facts on the natural key
  • Re-keying after corrections follows a written rule

Three questions

  • As it was: type 2 joins
  • As it is: type 6 or a join through the natural key
  • As reported: filed report snapshots, or recorded time

Tests

  • One current version per key
  • No overlaps, no gaps
  • Every fact inside its version's range
  • Filed reports rebuilt and compared after load changes

Operations

  • New versions per day monitored
  • Unfilled inferred members alerted
  • Erasure covers every version, raw and snapshots
