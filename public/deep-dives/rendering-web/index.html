Three notes in sixty seconds

Gist Server rendering sends HTML early and hydrates it, islands hydrate only the interactive parts, and code splitting loads code when it is needed. They sit on one line: how much of the page's work happens in the shopper's browser. The decision is which point on that line suits each page, measured on a mid-range phone.

The Caching deep dive followed the product page for product 42 through five layers of copies. This one follows the same page into the browser: how its HTML gets there, how much JavaScript comes with it, and when a shopper on a mid-range phone can see the mug and tap “Add to basket”. Three notes from the frontend volume set out the tools.

NoteIn one line

Islands Architectureship static HTML and hydrate only the small interactive parts
Code Splitting & Lazy Loadingload only the code a screen needs now, fetch the rest when needed
The SSR note's going-deeper chapter covers reading a page-load timeline, streaming and caching rendered pages. This dive builds on it.

Each note presents one option. The real decision is which option for which page, measured on the phone your customers actually own. A developer's laptop on office wifi makes every approach look fast. A three-year-old Android phone on a train shows the differences, and that phone is the median customer. This deep dive measures one page four ways, follows the six ways rendering goes wrong, and ends with budgets the build can enforce.

chapter 2 · 2 min

What “fast” means

Gist Three Core Web Vitals score a page: LCP for when the main content appears, INP for how quickly it responds to taps, and CLS for how much it jumps. Judge them on real visits at the 75th percentile, split by page and device; use lab runs on a simulated mid-range phone to find causes.

“The page is slow” means different things at different moments. Browsers and tools agree on a handful of named moments, and three of them, the Core Web Vitals, are what search engines and most teams use as the scoreboard.

MetricMeasuresGood at the 75th percentile
LCP, largest contentful paintwhen the main thing (the mug photo) appears2.5 s or less
INP, interaction to next painthow long the page takes to respond to taps and keys, over the whole visit200 ms or less
CLS, cumulative layout shifthow much content jumps around while loading0.1 or less
TTFB, time to first bytehow long the server took to start answeringabout 0.8 s or less
FCP, first contentful paintwhen anything at all appears1.8 s or less
INP replaced an older metric (first input delay) in 2024. It watches every interaction, not just the first.

Lab numbers and field numbers

There are two ways to measure, and they disagree for good reasons.

LabField
Howone controlled load, in Lighthouse or WebPageTest, on a simulated phonereal visits, measured in real browsers and sent to you
Good forcomparing two builds; finding whyknowing what customers experience
Missesreal devices, real networks, real caches, and INP (a lab load has no shopper tapping)the cause: it tells you that, not why

Use the field numbers to decide whether there is a problem, and the lab to find and fix it. Report the field numbers at the 75th percentile, split by page type and by device class. An average across all visits mixes the fast office laptops with the slow phones and hides exactly the customers who leave.

Who the median customer is

For the shop's analytics, the most common device is a mid-range Android phone about three years old. Its processor runs JavaScript three to five times slower than a developer laptop, and in the evening, on mobile data, its connection is closer to slow 4G than to the office network. Every number in this deep dive is for that phone. If the page is good there, it is good everywhere.

checkpoint

Why can't a Lighthouse run measure INP?

INP measures how the page responds to the shopper's taps and keys during a visit. A lab load has nobody interacting with it.

Why report the 75th percentile and not the average?

The average mixes fast laptops with slow phones and hides the customers having the worst experience.

chapter 3 · 2 min

One page, four ways

Gist Client-only rendering shows the product late. Server rendering shows it early but becomes usable no sooner, because the same JavaScript must hydrate it. Static pages win on first byte with the same hydration cost. Islands ship a fraction of the JavaScript and are usable almost as soon as visible. Choose per page type, not per site.

The team built the product page four ways and measured each on the simulated mid-range phone. The page shows a photo, name, price, description, reviews, an “Add to basket” button and a size picker. The numbers are the shop's, rounded; yours will differ, but the pattern rarely does.

JavaScript sent (compressed)310 KB310 KB310 KB, or less with islands38 KB
Server work per visitnonerender every time: 120 msnone; served from the CDNnone, or render once
LCP4.1 s2.2 s1.6 s1.5 s
Interactive (hydration done)4.6 s4.4 s4.3 s1.9 s
Risk to INPhigh while loadinghigh while loadinghigh while loadinglow
Price is currentyes, fetchedyes, renderedas of the last rebuildas of the last rebuild; live price can be an island
Server rendering fixed when the mug appears. It did not fix when the button works. Only shipping less JavaScript did.

What the table says

  • Client only loses on LCP because nothing can appear until the JavaScript has downloaded, run and fetched the data, one after another.
  • Server rendering moves the mug photo two seconds earlier. The button still works at 4.4 s, because the same 310 KB of JavaScript must still download and run to hydrate the page.
  • Static wins on first byte, because the HTML comes straight from the CDN, but has the same hydration cost.
  • Islands hydrate only the size picker, the basket button and the review form. Everything else is HTML that needs no JavaScript at all.

Choosing per page, not per site

A shop is not one kind of page. Each page type gets the approach that fits what it is.

PageNatureApproach
home, category, productdocuments with a few controls; most visits from search and linksstatic or cached server render, with islands
search resultsa document whose content depends on the queryserver render, cached briefly per query; filters as an island
basket and checkoutpersonal, a form, must be currentserver render per request, small JavaScript, forms that work without it
account pagespersonal, read mostlyserver render, not cached by the CDN
the shop's admin toolan app used all day by staff on laptopsclient-rendered app; fine there

Most modern frameworks let different routes use different approaches in one codebase. The mistake is choosing once, for the whole site, based on the page type the team works on most, which is usually the admin tool.

checkpoint

Server rendering moved LCP from 4.1 s to 2.2 s but the page became usable only at 4.4 s. Why?

The same 310 KB of JavaScript still had to download and run to hydrate the page.

Why is a client-rendered admin tool acceptable when a client-rendered product page is not?

Staff load the admin tool once a day on laptops; customers arrive at the product page on phones and leave within seconds.

Failure drills

Gist Six ways rendering goes wrong: a hydration mismatch from dates and time zones, a button that looks ready but does nothing, a page that jumps as late content arrives, requests that wait for each other, a cached page showing someone else's basket, and a bundle that grows month by month.

Each of these has been seen on a real shop. Try to name the cause before reading it.
  • 1 · mismatch
  • 2 · dead button
  • 3 · jumping page
  • 4 · the waterfall
  • 5 · someone's basket
  • 6 · the creeping bundle
Drill 1

The page that rendered twice

Timeline
The product page shows “Order in the next 3 hours for delivery tomorrow”. The server renders it at 14:00:00 in its own time zone. The browser hydrates at 14:00:03 in the shopper's time zone and gets a different text.
What you see
A flicker as the text changes, a console warning about a hydration mismatch, and on some framework versions the whole section rendered again from scratch, or event handlers attached to the wrong elements.
Why
Hydration assumes the browser's first render produces exactly the HTML the server sent. Anything that differs between the two runs breaks that: the clock, the time zone, random ids, the window size, data read from local storage.
What saves you
Render the same thing on both sides, then change it after hydration. Send times as timestamps and format them in an effect that runs only in the browser, or render them as a small island. Use the framework's stable id helper, never random numbers. Log mismatch warnings from real visits so they are noticed.

Rule: the first render in the browser must match the server's HTML exactly. Anything that can differ waits until after hydration.

Drill 2

The button that did nothing

Timeline
The photo appears at 1.6 s. The shopper taps “Add to basket” at 2.0 s. Hydration finishes at 4.3 s. Nothing happened at the tap; they tap again, then again.
What you see
Rage taps in the analytics, a poor INP, and sometimes three mugs in the basket once the queued taps are replayed. Customers describe the site as “broken”, not “slow”.
What saves you
Make the important controls work before JavaScript arrives. A real form with a POST to the basket works the moment the HTML is there; JavaScript can improve it later. Hydrate the button first or make it an island. And keep the gap short, because every control cannot be a form.

Rule: a page that looks ready must be ready. Use real links and forms for the actions that matter.

Drill 3

The page that jumped

Timeline
The shopper starts reading the description. The reviews widget loads above it and pushes it down. A web font arrives and the text reflows. A promotion banner slides in at the top. They tap “Add to basket” just as it moves, and hit “Remove” on the line below.
What you see
CLS of 0.35, and mis-taps that feel like the shop is fighting the customer.
What saves you
Reserve space for everything that arrives late: width and height on images, a fixed-height placeholder for the reviews and the banner, and a fallback font sized to match the web font. Never insert content above what the reader is looking at unless they asked for it.

Rule: everything that loads late gets its space reserved before it arrives.

Drill 4

One thing after another

Timeline
The client-rendered page loads HTML, then the JavaScript bundle, then runs it, which requests the product, which, once it arrives, requests the reviews, which contain image addresses, which are then requested. Each step waits for the one before.
What you see
Six round trips in a row on a connection where each costs 150 ms or more before any bytes arrive. The page is slow even though every single request is fast.
What saves you
Break the chain. Fetch data on the server, where round trips to the database are short, and send it with the HTML. Start independent requests at the same time instead of one after another. Tell the browser early about the hero image with a preload hint, so it does not wait to discover it. The performance panel's network view shows a chain as a staircase.

Rule: count the steps that wait for each other. On a phone, the chain is slower than any request in it.

Drill 5

Someone else's basket

Timeline
The product page is server-rendered and cached at the CDN for 60 seconds to cut server load. Its header shows “Basket (3)” and the signed-in shopper's first name. The first visitor after each expiry decides what everyone sees for the next minute.
What you see
Strangers greeted as “Hi Sam” with someone else's basket count. In the worst version the cached page included part of an address.
What saves you
This is drill 6 of the Caching deep dive, at the rendering layer. Keep cached HTML free of anything personal: render the shared page for everyone, and fill the personal parts in the browser or at the edge, from a request that is never cached. Mark personal responses private so no shared cache keeps them.

Rule: a page that is cached for everyone must contain nothing that belongs to anyone.

Drill 6

The bundle that crept back

Timeline
In March the product page shipped 38 KB of JavaScript. A developer adds a date-formatting library to the shared component that shows delivery dates. Another adds an analytics helper to the layout. By September the page ships 290 KB, and nobody decided that.
What you see
INP and LCP slowly worsening month after month in the field data, with no single change to blame.
What saves you
A budget the build enforces: the product page's JavaScript may not exceed, say, 60 KB compressed, and the pull request that crosses it fails with the size difference shown. Check what a new dependency costs before adding it. Look at the bundle map once a quarter.

Rule: JavaScript grows by default. Only a budget that fails the build keeps it small.

A delivery-time message flickers after the page loads. Which drill, and the fix?

chapter 5 · 3 min

The cost of hydration: the hard problem

Gist Hydration downloads code for every component, downloads the data a second time, and reruns the server's work on the slowest computer in the system, all to attach event handlers. Progressive hydration reorders that work; islands, server components and resumability avoid most of it.

Chapter 3's table had one stubborn number: the page was visible at 1.6 s and usable at 4.3 s, and server rendering did not change the second number. That gap is the hard problem of modern rendering, and it comes from what hydration has to do.

Hydration has to…Cost
download the code for every component on the pagethe 310 KB, even for paragraphs that never change
download the data again, embedded as JSON in the pagethe product appears twice: as HTML and as data
run every component again in the browserthe same work the server already did
attach event handlers to the existing elementssmall; the only part that was really needed
Hydration is doing the server's work a second time, on the slowest computer in the system.

Four ways to do less of it

ApproachIdeaTrade-off
Progressive hydrationhydrate the important parts first, the rest when idle or visiblethe total work is the same; it is just ordered better
Islandsonly marked components get JavaScript at allsharing state between islands needs care; suits documents, not apps
Server componentscomponents marked as server-only render to HTML and never send their code; client components hydrate as usualtwo kinds of component with rules about which can contain which; needs a framework that supports it
Resumabilitythe server records where it stopped; the browser resumes on the first interaction instead of re-running everythinga different programming model; fewer frameworks

They share one idea: most of a page is a document, and documents do not need code in the browser. The approaches differ in who decides which parts are interactive. With islands you mark the interactive parts. With server components you mark them too, from the other direction: everything is server-only unless it says it needs the browser. Progressive hydration keeps one kind of component and only changes the order.

The product page with server components

product-page.tsxonly the marked parts send code to the browser
// server component: runs on the server, sends HTML, sends no JavaScript
export default async function ProductPage({ id }: { id: string }) {
  const product = await db.product(id);                 // straight to the data, no API round trip
  return (
    <main>
      <ProductPhoto product={product} />               {/* server-only */}
      <h1>{product.name}</h1>
      <Price amount={product.price} />                 {/* server-only */}
      <SizePicker sizes={product.sizes} />             {/* "use client": hydrates */}
      <AddToBasket productId={id} />                   {/* "use client": hydrates */}
      <Reviews productId={id} />                       {/* server-only, streamed */}
    </main>
  );
}

The two client components are the only code the browser receives for this page, which is how the island column in chapter 3 got to 38 KB without a separate framework. Whichever approach you choose, measure the hydration gap on the median phone before and after. It is the number that tells you whether the choice worked.

checkpoint

What does a server component send to the browser?

Its HTML only. Its code is never downloaded, so it is not hydrated.

Progressive hydration makes the page usable sooner. Why doesn't it reduce the total work?

It still hydrates every component; it only changes the order, doing the important ones first.

chapter 6 · 3 min

Loading less JavaScript

Gist JavaScript costs on the network and again on the processor. Split code by route, by interaction, by visibility and until idle, prefetch on intent, and avoid chains of tiny chunks. Third-party scripts are often the biggest cost and need owners, budgets and lightweight stand-ins.

JavaScript is the most expensive thing a page sends. An image of 300 KB is decoded quickly and mostly off the main thread. A script of 300 KB must be downloaded, parsed, compiled and run, on the main thread, before the page can respond to a tap. On the median phone, the running alone often takes over a second.

Split by when it is needed

SplitLoadsFor the product page
by routewhen the page is visitedthe product page never loads checkout's code
by interactionwhen the shopper starts to use itthe review form's editor loads when “Write a review” is tapped
by visibilitywhen it scrolls into viewthe “you might also like” carousel
after loadwhen the browser is idleanalytics and the chat widget
reviews.tsxthe editor is downloaded only when someone wants to write
const ReviewEditor = lazy(() => import("./ReviewEditor"));   // a separate chunk

function WriteReview() {
  const [open, setOpen] = useState(false);
  return open
    ? <Suspense fallback={<p>Loading the editor…</p>}><ReviewEditor /></Suspense>
    : <button onMouseEnter={() => import("./ReviewEditor")}   // start early on hover
              onClick={() => setOpen(true)}>Write a review</button>;
}
Prefetch on hover or when the link scrolls into view. The chunk then arrives in the 200 ms between pointing and tapping.

Don't split too finely

Each chunk is a request, and chunks that import other chunks form the chain from drill 4. Forty tiny chunks for one screen can load slower than four sensible ones. Split along the lines in the table above, then check the network panel for a staircase.

Third-party scripts

On many shops the largest JavaScript is not the shop's own: a tag manager, two analytics tools, a chat widget, a reviews provider, an A/B testing script that hides the page until it has decided. They are added by other teams, outside the code review, and they run on the same main thread.

ScriptBetter
chat widgeta static button that loads the real widget when tapped (a facade)
analyticsafter load, or sent from the server where possible
A/B test that hides the pagedecide on the server or at the edge, so the page arrives already chosen
video embeda thumbnail image that becomes the player when tapped
tag manageran owner, a review of every tag, and the same budget as your own code

Smaller code, not just later code

Splitting moves code later; deleting it is better. Check what each dependency costs before adding it; many have smaller alternatives or are replaced by features the browser now has. Send modern JavaScript to modern browsers instead of compiling everything for ten-year-old ones. And look at the bundle map: a treemap of what is in each chunk shows the 70 KB locale file that nobody knew was there.

checkpoint

Why is a 300 KB script more expensive than a 300 KB image?

The script must be parsed, compiled and run on the main thread before the page can respond; the image is mostly decoded off it.

A chat widget adds 200 KB to every page. What is a facade?

A lightweight button that looks like the widget and loads the real one only when tapped.

Budgets, worked out

Gist Work back from LCP under 2.5 s on the median phone: connection, first byte, HTML and CSS, the hero image, and a margin. The hero image is the largest single item. Set per-page budgets for JavaScript, images and lab metrics that fail the build, and keep every task under 50 ms for INP.

Targets become real when they are turned into budgets that the build can check. Here is the product page's, worked back from “LCP under 2.5 s for three customers in four”.

Budgets differ by page because pages differ. The admin tool is used on laptops by staff who load it once a day; a big bundle there costs little. The product page is the first contact with customers who came from a search result and will leave in three seconds.

INP is a budget on long tasks

The browser can respond to a tap only between tasks. Any piece of JavaScript that runs longer than 50 ms is a long task, and a tap that arrives during one waits for it to finish. Hydration, large re-renders, heavy event handlers and third-party scripts are the usual long tasks. The budget is therefore: no single task over 50 ms after the page appears, and expensive work split into pieces that let the browser respond in between, or moved off the main thread altogether.

What a kilobyte costs

As a rule of thumb from the shop's own measurements on the median phone: each 100 KB of compressed JavaScript on the critical path added about 0.3 s to download on slow 4G and about 0.5 s of main-thread work. The exact numbers depend on the code, but the shape does not: JavaScript costs twice, once on the network and once on the processor, and the second cost does not shrink with a faster connection.

checkpoint

Which single item usually dominates the path to LCP?

The hero image: its size, format and how early the browser knows to fetch it.

Why does a faster connection not fix a heavy JavaScript bundle?

Half of its cost is running on the phone's processor, which the network does not change.

Caching and streaming HTML

Gist Cache the parts of a page that are the same for everyone, fetch personal parts separately, and check current values where decisions are made. Stream the shell first and slow parts later into reserved space, but decide the status code before streaming starts. Render at build time, near the data, or at the edge according to what the page needs.

A server-rendered page is only fast if the server is. The going-deeper chapter of the SSR note introduced streaming and caching rendered HTML; this chapter puts them together for the shop.

Cache what is the same for everyone

Part of the product pageSame for everyone?Served from
photo, name, description, sizesyescached HTML at the CDN, refreshed when the product changes
priceyes, but changescached with a short life, or a small island that fetches it
reviewsyes, slow to computestreamed in after the rest, cached separately
“Basket (3)”, “Hi Sam”nothe browser, from an uncached request after the page loads
stock for the chosen sizeyes, but must be current at checkoutshown from a short cache; checked for real when added to the basket
Same rule as the Caching dive: show from a copy, decide on the original.

Streaming: send the shell first

With streaming, the server sends the top of the page as soon as it is ready, and slower parts follow in the same response as they complete. The photo and name go first; the reviews, which need a slow query, arrive half a second later and slot into a reserved space (drill 3).

The status code is sent first

Streaming has one consequence that surprises teams. The HTTP status code is part of the first bytes. Once the shell has been sent with 200 OK, the server cannot change its mind if the reviews query fails or the product turns out not to exist. So decide everything that affects the status before streaming starts: does the product exist (404), is the shopper allowed to see it, should this be a redirect. Stream only the parts whose failure the page can survive, and give each a fallback that renders in its slot.

Search engines and link previews

Crawlers increasingly run JavaScript, but link previews in chat apps and many smaller crawlers do not, and those that do may not wait for slow data. A product page whose name, price and photo are in the first HTML is indexed and previewed correctly by everything. That alone is often the business reason for server rendering, separate from speed.

Moving between pages

The first page load gets the attention, but a shopper looks at five or six pages per visit. Two approaches handle the next page differently.

Full page loadsClient-side navigation
Next pagethe browser fetches new HTML, as on the first visitJavaScript fetches data and renders the new page in place
Costa new document each time; shared files come from cachethe router and every route's code must be loaded first
Strengthssimple; the back button restores the old page instantly from the browser's page cachesmooth transitions; state such as an open basket drawer survives
Watchmake it fast with prefetching and cached HTMLscroll position, focus for screen readers, and memory over a long visit

Browsers have closed much of the gap. Prefetching the likely next page on hover, and view transitions that animate between full page loads, give documents most of the smoothness of an app without its JavaScript. For a shop, full page loads with prefetching are usually the better default; the basket drawer can be an island.

Where to render

checkpoint

The product does not exist, but the page was already streaming with 200 OK. What went wrong?

The existence check should have happened before streaming started, so the server could answer 404.

Why render personalisation at the edge but not database-heavy pages?

The edge is near the shopper but far from the database; several queries from there cost many long round trips.

Testing it and running it

Gist In every pull request, check bundle sizes against budgets, run Lighthouse on key pages, test the key action with JavaScript off and fail on hydration warnings. In production, collect Core Web Vitals from real visits by page and device, and graph conversion next to them.

Rendering performance decays quietly: a few kilobytes here, an extra script there, a slower query. It stays good only when it is measured on every change and watched in the field.

In the pull request

Lab runs are noisy. Run three, take the median, and set budgets with a little room.

In the field

A small script in every page measures the Core Web Vitals in real visits and sends them to your analytics, with the page type, device class and connection type. The dashboard shows the 75th percentile per page type, per week.

vitals.tsreal numbers from real phones
import { onLCP, onINP, onCLS } from "web-vitals";

function send(metric) {
  navigator.sendBeacon("/vitals", JSON.stringify({
    name: metric.name, value: metric.value,
    page: document.body.dataset.pageType,          // "product", "category", "checkout"

  }));
}

Runbook: “LCP got worse”

  1. Which pages and devices? The field dashboard, split. One page type: a change to that page. All pages: something shared, like the layout, a font or a third-party script. Only low-end devices: JavaScript or image weight.
  2. Which part of the timeline? A lab run of the same page: is the extra time in first byte (server or cache), in the hero image, or in waiting for scripts?
  3. First byte: the CDN hit rate for HTML, then the server's render time. A page that stopped being cacheable shows up here.
  4. Hero image: its size, format and whether it is still announced early. A redesign often swaps in a 2 MB image.
  5. Scripts: the bundle map and the list of third-party scripts against last month's.

Watch the business number too

Put conversion rate next to LCP and INP on the same dashboard, by device class. The point of all this is shoppers who stay and buy, and the shop found that phones in the slowest quarter converted at half the rate of the fastest. That graph is what keeps the budgets funded.

checkpoint

LCP worsened only on low-end devices, on all page types. Where do you look first?

Something shared and heavy: JavaScript or image weight in the layout, or a new third-party script.

What does loading the page with JavaScript disabled prove?

That the key actions, such as adding to the basket, work before scripts load, which is what shoppers on slow phones depend on.

The framework matters less than the page-by-page choice and the budget. Every one of these can ship a slow page.

Lab

The shop's search results page shows 24 products for a query, with filters for size, colour and price, and a sort order. Most visits come from the shop's own search box; some from search engines. The page currently is client-rendered: LCP 4.3 s and INP 380 ms on the median phone.

  1. Which approach from chapter 3 fits, and why not static?
  2. What can be cached, and for how long?
  3. How do the filters work before JavaScript has loaded?
  4. Where does the 380 ms INP probably come from, and what do you do?
  5. Set the JavaScript budget, and say what the pull-request check does when someone adds a 90 KB date picker for the delivery-date filter.

model answer

1 · Approach

Server render per query, with the filter panel and the sort control as the only hydrated parts. Static does not fit: the content depends on the query, and the combinations are endless.

2 · Caching

The HTML for a query and filter combination is the same for everyone, so it can be cached at the CDN for a minute, keyed by the normalised query string. The basket count and greeting are fetched separately in the browser (drill 5). Prices shown are display only; the basket checks them.

3 · Filters without JavaScript

The filter panel is a real form with GET, so choosing filters and pressing “Apply” loads the filtered page as a normal link. JavaScript later makes it update without the button. Every filtered state then also has its own address that can be shared and cached.

4 · INP

Most likely each filter change re-renders all 24 product cards and runs the whole client-side search logic in one long task. With server rendering, a filter change fetches new HTML for the list; the client work per tap becomes small. Check the performance panel for long tasks after a tap to confirm.

5 · Budget

About 50 KB compressed for the page. The date picker alone would almost double it, so the check fails and shows the import. The fix is to load the date picker only when that filter is opened (chapter 6), or to use the browser's own date input.

The review checklist

Choosing

  • Each page type has its own rendering approach, chosen for what it is
  • Documents ship as HTML with JavaScript only for interactive parts
  • Personal and current data is never inside shared cached HTML

Measuring

  • Field Core Web Vitals at the 75th percentile, by page type and device class
  • Lab runs on a simulated mid-range phone, not a laptop
  • Conversion is graphed next to speed

The first view

  • The hero image is sized, compressed, in a modern format and announced early
  • Data is fetched on the server or in parallel, never in a chain
  • Late content has reserved space; fonts have a matched fallback
  • The status code is decided before streaming starts

Interaction

  • Key actions work as links and forms before JavaScript loads
  • The first browser render matches the server's HTML
  • No task over 50 ms after the page appears
  • Interactive parts hydrate first, or are islands

JavaScript

  • Code is split by route, interaction and visibility, not into dozens of tiny chunks
  • Third-party scripts have owners, budgets and facades
  • Each new dependency's size is checked before it is added

In the build

  • Per-page JavaScript budgets fail the pull request
  • Lighthouse CI checks LCP and blocking time on key pages
  • End-to-end tests fail on hydration warnings and run once without JavaScript
