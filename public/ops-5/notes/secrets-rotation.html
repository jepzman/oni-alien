Rotating the Keys

TL;DR

Passwords, API keys, signing secrets and certificates are the keys to your systems, and old keys get copied, leaked and forgotten. Keep every secret in a vault (never in files or the repository), give each an owner, a purpose and a maximum age, rotate automatically where you can, scan the pipeline so none slip in, and hold a yearly rotate-everything drill. Then rotating after a leak or a leaver is an hour's work, not a crisis.

1The situation Larder, April 2028

After 9 March, Eli inventories Larder's secrets: 61 in all, from database passwords and payment provider keys to webhook signing secrets and certificates. 19 have never been rotated. The oldest is the payment provider key Jasper created in 2024. Three are in a configuration file in the repository's history. Ana's October 2027 security review had already found business API keys that never expired. Nobody knows who owns half of them, or what breaks if one changes.

  • An old secret has had years to be copied somewhere.
  • Rotating feels risky because it has never been done.
  • When someone leaves, their secret knowledge doesn't.

2Real-life analogy the office key cabinet

A well-run office has a key cabinet with a list: which key opens what, who has a copy, when the lock was last changed. Locks are changed every few years, and immediately when someone leaves with a key. The first time, it takes a whole day to find out which doors each old key opened. After that, it takes an hour.

3How it solves it a vault, owners and ages, automatic rotation, and a yearly drill

Bram leads the work in April and May:

  • In the vault: every secret moves to the vault. The three in the repository's history are rotated first, and from then on the pipeline scans every change for secrets and refuses to merge one.
  • Owner, purpose, maximum age: database passwords rotate automatically every 30 days; API keys and signing secrets every 90 days; certificates are on automatic renewal. Business API keys for clients expire after a year, with a reminder to the client.
  • A rotation drill: on Tuesday 23 May, rotate everything in one day. 58 of 61 are done by 17:00. Three needed the vendor's help, and those are done that week. Jasper's 2024 payment key is finally retired.

The drill is held every year, and the relevant secrets are rotated whenever someone with secret access leaves. Rotating after an incident like 9 March is now an hour's work.

  1. Inventory every secret

    Where it lives, what uses it, who owns it.

  2. Move them into a vault

    Out of files, chats and repositories.

  3. Rotate anything ever exposed, first

    Like secrets in git history.

  4. Set a maximum age per kind

    And automate rotation where possible.

  5. Scan the pipeline

    So new secrets can't slip in.

  6. Drill a full rotation yearly

    And after leavers with secret access.

Vocabulary for the exam

Secret
Anything that grants access: password, API key, token, private key.
Vault
A system that stores secrets securely and controls access to them.
Rotation
Replacing a secret with a new one and retiring the old.
Maximum age
How long a secret may live before rotation.
Secret scanning
Checking code and history for secrets.
Short-lived credential
A secret that expires by itself within minutes or hours.

4The maturity ladder where are we, and what is the next rung?

1By hand

secrets anywhere, never rotated

  • Files, git, chats.
  • Owners unknown.

2Written down Larder now

  • Automatic where possible.
  • Pipeline scan.

3Scripted

short-lived credentials

  • Services get credentials that expire in hours.
  • Few long-lived secrets.

4Automatic

secretless where possible

  • Workload identity instead of keys.
  • Rotation rarely needed.

6Common pitfalls the usual ways this goes wrong

  • Secrets in git history

    Deleting the file doesn't remove it. Fix → rotate it, then scan.

  • No owner

    Nobody dares rotate it. Fix → an owner and a purpose per secret.

  • Rotation never practised

    The first one breaks production. Fix → a yearly drill.

  • Keys that never expire

    Clients' keys live forever. Fix → expiry with reminders.

7When to use it (and when not)

Use it when…

  • You can't list your secrets and their owners.
  • A secret may have leaked.
  • Someone with access to secrets leaves.
  • A client or auditor asks about key management.

Skip it when…

  • Systems already using short-lived, automatic credentials end to end.

8Self-check quiz

What did the inventory find?

61 secrets, 19 never rotated, the oldest from 2024, and three in the repository's history.

What happens to a secret found in git history?

It's rotated (deleting the file isn't enough), and the pipeline scans for secrets from then on.

What are Larder's maximum ages?

Database passwords 30 days (automatic), API keys and signing secrets 90 days, certificates auto-renew, client API keys 1 year.

What was the drill's result?

58 of 61 rotated by 17:00 on 23 May; 3 with vendors that week.

When else are secrets rotated?

When someone with access to them leaves.

what would you do?An engineer pastes a database password into a team chat by mistake. What happens?

Rotate that password now (it's in the vault, so it's quick), delete the message, and note it as a near miss. No blame; the fix is the rotation, not the apology.

try it

List ten secrets your service depends on. For each: where is it stored, who owns it, when was it last rotated? Rotate the oldest one this week, and time how long it takes.

remember!!

Every secret has an owner and an age. Keep them in a vault, rotate on a schedule, and practise rotating everything once a year.
