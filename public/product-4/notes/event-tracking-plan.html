Event Tracking Plan

TL;DR

Product numbers are only as good as the events behind them. Before (or as) you build, write a tracking plan: one row per event, with a consistent name (object_action), exactly when it fires, its properties, and an owner. Use the same names on every platform, check the events in the definition of done, and change the plan through review. Three dashboards with three answers usually means no plan.

  • Family: instrumenting
  • Origin: product analytics practice (Segment, Amplitude and Mixpanel tracking plans)
  • Lives in: a table in the repo, next to the code that fires the events
  • Pairs with: funnels, definition of done, dashboards

1The situation Larder, 4 May 2026

Approvals has been live in Amsterdam for three weeks. Grace asks a simple question: what share of customers answer within two minutes? iOS sends swap_answered, Android sends SwapAnswer with different properties, the web shop sends nothing. Three dashboards give three answer rates: 71, 79 and 84 %. Nobody can say which is right.

  • Each platform names and shapes events its own way.
  • “When does it fire?” is decided by whoever writes the code.
  • Numbers disagree, so nobody trusts any of them.

2Real-life analogy match statistics

A football club's analysts agree, before the season, exactly what counts as a shot (on or off target), a pass (completed or not), a tackle (won or lost), and who records each. Without that, two analysts watching the same match produce different numbers, and the coach stops reading the sheet.

3How it solves it one table, the same everywhere

Grace and Dee wrote the tracking plan for approvals in an afternoon: four events following the swap from offered to applied, each with when it fires and its properties. All three platforms were fixed to the same names in a week; the definition of done now includes “tracking events firing as in the plan”. The real answer rate in May: 77 %.

  1. Start from the questions

    What do you need to know? Work back to the events that answer it.

  2. Name events consistently

    object_action, lower case: swap_answered.

  3. Say exactly when each fires

    “When the customer taps yes or no”, not “on answer”.

  4. List the properties

    With types and allowed values: answer = yes / no.

  5. Give each event an owner

    Usually the team that builds the feature.

  6. Check it in the definition of done

    And change the plan by review, like code.

Vocabulary for the exam

Tracking plan
The agreed list of events, when they fire, and their properties.
Event
A record that a user or system did something.
Property
A detail attached to an event (answer, seconds).
object_action
A naming style: thing, then what happened to it.
Instrumentation
The code that sends events.
Data quality
How complete and correct the events are.

4Gains vs losses nothing is free

What we gain

  • One answer instead of three.
  • Trust in product numbers.
  • Faster questions: events already exist.
  • Same events everywhere, so platforms compare.
  • No personal data leaking into analytics.

What we lose

  • Upfront work per feature.
  • Discipline: plans drift without review.
  • Old events need fixing or retiring.
  • Can over-track if every click gets an event.

6Common pitfalls the usual ways this goes wrong

  • Tracking everything

    An event per click, nobody reads them. Fix → start from the questions; track what answers them.

  • Vague firing rules

    “On answer.” Fix → say exactly when: “when the customer taps yes or no”.

  • Platform drift

    iOS and Android diverge again. Fix → check events in the definition of done.

  • Personal data in properties

    Names and addresses in analytics. Fix → IDs only; check with your DPO.

7When to use it (and when not)

Use it when…

  • Every feature you want to measure.
  • When dashboards disagree.
  • Multi-platform products.
  • Before an A/B test.

Skip it when…

  • Prototypes and fake doors: count simply and throw away.

8Self-check quiz

What's in each row of a tracking plan?

Event name, exactly when it fires, its properties, and an owner.

Why the same names on every platform?

So numbers can be combined and compared.

Where are events checked?

In the definition of done.

What was Larder's real answer rate in May?

77 %, once all platforms sent the same events.

try it

Pick one feature and one question about it. Write the events that answer it as a four-column table (name, fires when, properties, owner). Check what your three platforms actually send today and list the differences.

remember!!
