Living Diagrams

TL;DR

Diagrams drawn by hand, even as code, show what someone intended. Living diagrams are generated from what's real: the code's dependency graph, the infrastructure code, production traces. Then compare the generated picture with the intended model and flag the differences: a dependency nobody drew, a service nobody uses. The intended diagram explains; the generated one checks.

1The situation Larder, 26 January 2027

Since November the C4 model lives as code, and teams update it in their pull requests. It says Customer Care talks to Dispatch only through Kafka. Then Eli looks at the production traces: there's a direct HTTP call from Customer Care to Dispatch's courier-location API, added in December for the support tool. The code changed; the intended picture didn't, and nobody noticed for six weeks.

  • Docs as code relies on people remembering to update the diagram.
  • Unplanned dependencies are the ones most worth knowing about.
  • Nobody compares the picture with reality until an incident does.

2Real-life analogy the printed map and live traffic

A printed road map shows the roads as planned. A satnav's live traffic view shows where cars actually drive today, including the diversion nobody printed. You need both: the printed map to understand the region, the live view to see what's really happening, and the difference tells you where the map is wrong.

3How it solves it generate, compare, flag

Eli and Ana set up three generators: the module graph from the import linter (already used as a fitness function), a deployment picture from the infrastructure code, and a runtime service map from traces. A weekly CI job compares them with the intended model. The first run found the direct call (now a documented exception, with an ADR to replace it by an event) and two Kafka topics nobody had consumed since October.

  1. Keep an intended model

    The C4 model as code: what the architecture should be.

  2. Generate from code

    Module and package dependencies (import linter, dependency tools).

  3. Generate from infrastructure

    What's deployed, from the infrastructure code or cloud APIs.

  4. Generate from runtime

    Who calls whom, from traces (OpenTelemetry) or service meshes.

  5. Compare and flag

    A weekly diff report; module rules break the build.

  6. Resolve each difference

    Fix the code, update the model, or record an exception with an ADR.

Vocabulary for the exam

Living diagram
A diagram generated from the running system or its code.
Intended model
What the architecture should be, kept as code.
Service map
Calls between services, built from traces.
Drift
The gap between the intended model and reality.
Architecture recovery
Rebuilding the architecture from code and runtime data.
Exception
An accepted difference, recorded with a reason.
.github/workflows/architecture-drift.ymlweekly drift check (shortened)
name: architecture-drift
on:
  schedule: [{ cron: "0 6 * * 1" }]          # Mondays 06:00
  pull_request: { paths: ["core/**", "dispatch/**", "infra/**", "docs/architecture/**"] }
jobs:
  drift:
    steps:
      - run: lint-imports                      # module rules: fail the build (ADR 0002)
      - run: tools/module-graph > out/modules.json
      - run: tools/deployed-from-infra infra/ > out/deployed.json
      - run: tools/service-map --from traces --days 7 > out/calls.json
      - run: tools/compare docs/architecture/c4/workspace.dsl out/*.json > out/drift.md
      - run: tools/post-report out/drift.md   # to #architecture, every Monday
# First run, 26 Jan 2027: Care → Dispatch HTTP (undocumented) · 2 unused topics

tools: import-linter, deptry or ArchUnit for code; Structurizr (with its import tools), cloud inventory tools for infrastructure; OpenTelemetry with a service-map view (Jaeger, Grafana Tempo, your APM) for runtime.

4Gains vs losses nothing is free

What we gain

  • Drift found in a week, not at the next incident.
  • Unplanned dependencies become visible.
  • Unused parts show up for removal.
  • Trust in the intended diagram returns.
  • Builds on existing tools: linter, traces, infra code.

What we lose

  • Setup work: generators and a compare step.
  • Noise until the model and reality are aligned.
  • Generated diagrams are ugly: they check, they don't explain.
  • Traces need good coverage to be complete.

6Common pitfalls the usual ways this goes wrong

  • Generated only

    Unreadable auto-diagrams replace the intended one. Fix → keep both: intended to explain, generated to check.

  • Report nobody reads

    A weekly diff in a channel nobody opens. Fix → an owner resolves each difference.

  • Everything breaks the build

    Teams disable the check. Fix → break the build only for agreed rules; report the rest.

  • Partial traces

    Half the services aren't instrumented. Fix → instrument first, or label the map as partial.

7When to use it (and when not)

Use it when…

  • Systems with more than a handful of services or modules.
  • After moving docs to code, as the next step.
  • When incidents reveal surprise dependencies.
  • Audits that need evidence of the real architecture.

Skip it when…

  • Small systems where one person sees every change.
  • Before an intended model exists: write that first.

8Self-check quiz

What's the difference between an intended and a generated diagram?

Intended shows what should be and explains it; generated shows what is and checks it.

Name three sources for generated diagrams.

Code dependencies, infrastructure code, production traces.

What did Larder's first run find?

A direct HTTP call from Customer Care to Dispatch, and two unused Kafka topics.

What happens to each difference?

Fix the code, update the model, or record an exception with an ADR.

try it

Generate one picture of your system from reality: a dependency graph from your code, or a service map from a week of traces. Put it next to your intended diagram and list every difference. Decide, for each one, whether the code or the diagram is wrong.

remember!!

Keep the printed map, and check it against live traffic every week.
