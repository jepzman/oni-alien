Docs as Code

TL;DR

Documentation goes stale when it lives somewhere the code doesn't. Docs as code means writing docs and diagrams as plain text in the repository (Markdown, Structurizr DSL, Mermaid), changing them in the same pull request as the code they describe, reviewing them like code, and letting CI render diagrams, check links and publish the site. The docs then change when the system changes, because it's the same change.

  • Family: documents
  • Origin: Write the Docs community (2013–); Anne Gentle, Docs Like Code (2017)
  • Lives in: docs/ in the main repo, published by CI
  • Pairs with: C4 model, arc42, living diagrams

1The situation Larder, 24 November 2026

The C4 container diagram from 6 October was drawn in a drawing tool and exported as an image. Seven weeks later it's already wrong: the new business-accounts work isn't on it, and Engine A's box has an old name. The source file is on Ana's laptop. Nobody else can update it, and nobody remembers to when the code changes.

  • Diagrams in separate tools aren't part of any code review.
  • Exported images can't be diffed, reviewed or searched.
  • Updating docs becomes a heroic tidy-up, done twice a year.

2Real-life analogy corrections to the chart

A ship's navigator trusts the chart because it's kept current by numbered Notices to Mariners: each change (a new buoy, a moved wreck) is published, applied to the chart, and logged in its margin. Nobody redraws the chart from memory once a year; every change is a small, reviewed correction.

Translating it to the job
In real lifeOn the project
The chartThe docs and diagrams in the repo
A Notice to MarinersA pull request that changes the system
Applying the correctionUpdating the diagram in the same PR
The log in the marginGit history of the docs
Trusting the chartEngineers trusting the docs again

3How it solves it same repo, same PR, same review

Ana moved the C4 model into Structurizr DSL and the flows into Mermaid, all in docs/. The pull request template gained one line: does this change the architecture? update the diagram and link the ADR. CI renders the diagrams, checks links and publishes the site from main. Within two weeks Ben's team had updated the container diagram themselves, in the PR that added business accounts.

  1. Pick text formats

    Markdown for pages; Structurizr DSL or Mermaid for diagrams.

  2. Move docs into the repo

    Next to the code they describe; archive the old copies with a pointer.

  3. Add a PR checklist line

    “Changes the architecture? Update the diagram, link the ADR.”

  4. Render and check in CI

    Diagrams to images, link checks, spelling if you like.

  5. Publish from main

    A docs site (or the repo's own rendering) that's always current.

  6. Review docs like code

    Reviewers look at the diagram diff too.

      dispatch = container "Dispatch" "Couriers, vans, assignment" "Python + Engine A"

      kafka    = container "Event bus" "" "Managed Kafka" "Queue"

    apps -> core "HTTPS / JSON"
    core -> kafka "order.ready_for_dispatch (outbox)"

  }

tools: Structurizr (DSL, Lite, CLI), Mermaid, PlantUML, MkDocs or Docusaurus for the site, docToolchain for arc42, a link checker (lychee) in CI.

4Gains vs losses nothing is free

What we gain

  • Docs change with the code, in the same PR.
  • Reviewable diffs for diagrams.
  • Anyone can update, not just the author.
  • History for free in git.
  • Published automatically, always current.

What we lose

  • Text diagrams look plainer than hand-drawn ones.
  • Layout control is limited with auto-layout.
  • Non-engineers may find the repo harder to edit.
  • Setup time for CI and the site.

6Common pitfalls the usual ways this goes wrong

  • Docs in a separate repo

    Same staleness, different place. Fix → keep docs next to the code they describe.

  • No checklist line

    Nobody remembers to update. Fix → add it to the PR template.

  • Pixel-perfect obsession

    Hours tuning auto-layout. Fix → accept plain; clarity beats beauty.

  • Locking out non-engineers

    Lena can't fix a typo. Fix → offer the web editor, or accept suggestions via comments.

7When to use it (and when not)

Use it when…

  • Any team that works in pull requests.
  • Diagrams that keep going stale.
  • Architecture docs that several teams edit.
  • Regulated settings that need a change history.

Skip it when…

  • One-off presentations and sketches.
  • Documents mainly written by non-engineers: a shared doc may suit better.

8Self-check quiz

What does docs as code mean?

Docs and diagrams as text in the repo, changed in the same PR as the code, reviewed and published by CI.

Why do exported images go stale?

They're outside code review, can't be diffed, and only their author can edit the source.

What one line did Larder add to the PR template?

“Changes the architecture? Update the diagram and link the ADR.”

Name two text formats for diagrams.

Structurizr DSL and Mermaid (also PlantUML).

try it

Take your most-used architecture diagram and redraw it as Mermaid or Structurizr DSL in the repo. Add one line to your PR template asking whether a change affects it. After a month, count how many PRs updated it without you.

remember!!

Every change is a numbered correction. Same repo, same pull request.
