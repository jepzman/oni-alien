Deployment Diagrams

TL;DR

A container diagram says what the parts are; a deployment diagram says where they run: which region, which network, which machines or managed services, how many copies, and how traffic gets in and out. It's the first page on-call needs at 3 a.m., and it's what security, auditors and new platform engineers ask for. Keep it small, current and close to the infrastructure code.

1The situation Larder, 29 October 2026

A network rule change at 18:10 on a Thursday cuts Dispatch off from the database. The on-call engineer, three weeks into the job, needs to know where Dispatch runs, which network it's in and how it reaches Postgres. It's all in Eli's head, and Eli is on a train. It takes 25 minutes to find the rule; couriers are assigned by hand for most of that time.

  • Nobody but one engineer knows the physical layout.
  • Incidents become archaeology when the deployment isn't drawn.
  • Security and audit questions get a different answer each time.

2Real-life analogy the fire brigade's plan

Big buildings keep a plan for the fire brigade: where the gas main and the fuse box are, which doors connect which rooms, where the exits are. Not the furniture, not who works where. When the brigade arrives at 3 a.m., they don't have time to ask the caretaker.

3How it solves it where it runs, and how it's reached

Ana and Eli drew it the following week: one region, one private network, managed containers for Dispatch and Engine A, three VMs for Larder Core, managed Postgres and Kafka, and the outside world on the right: stores with their 4G backup, phones, and five SaaS services. It's generated from a short description next to the infrastructure code and linked from the on-call runbook's first line.

  1. Draw the boundary

    Region, account, network: the outer boxes.

  2. Place each container

    On the managed service, VM or device it runs on; say how many copies.

  3. Show the data stores

    Databases and brokers, with replicas.

  4. Show the ways in and out

    Users, stores, partners; which network path they take.

  5. Keep it close to the infrastructure code

    Generated or reviewed with every infra change.

  6. Link it from the runbook

    On-call's first page, with the dashboard links.

Vocabulary for the exam

Deployment node
Where something runs: a VM, a managed service, a device.
Region
A cloud provider's data-centre area (here, Frankfurt).
Private network
A network not reachable from the internet directly.
Replica
A copy of a database for safety or reads.
Runbook
Step-by-step instructions for operating or fixing a system.
Ingress / egress
Traffic coming in / going out.

4Gains vs losses nothing is free

What we gain

  • Faster incidents: on-call knows the layout.
  • Security and audit answers from one page.
  • Onboarding for platform engineers.
  • Cost visibility: every paid service on the page.
  • Less key-person risk: not just in Eli's head.

What we lose

  • Changes often with infrastructure.
  • Can expose sensitive details if shared widely.
  • Too much detail (IPs, ports) makes it unreadable.
  • Another document to keep current.

6Common pitfalls the usual ways this goes wrong

  • Only in someone's head

    Eli knows; Eli is on a train. Fix → draw it, and link it from the runbook.

  • Every IP and port

    An unreadable network dump. Fix → show nodes and paths; details in the infra code.

  • Drawn once

    Last spring's layout. Fix → review it with every infrastructure change.

  • Shared everywhere

    The network layout on a public wiki. Fix → keep sensitive details internal.

7When to use it (and when not)

Use it when…

  • Any system with on-call.
  • Security reviews and audits.
  • Before and after infrastructure changes.
  • Onboarding platform engineers.

Skip it when…

  • Pure SaaS products with nothing of your own deployed.
  • Explaining what the system does: use C4.

8Self-check quiz

What does a deployment diagram show that a container diagram doesn't?

Where things run: region, network, nodes, copies, and how traffic gets in and out.

Who needs it first?

On-call engineers during an incident.

Where should it live?

Next to the infrastructure code, reviewed with infra changes, linked from the runbook.

What should be left out?

Every IP and port: keep those in the infrastructure code.

try it

Without looking anything up, sketch where your system runs: regions, networks, managed services, how users reach it. Then check it against the infrastructure code and mark every mistake. Fix it, and link it from your on-call runbook.

remember!!

Draw it for the fire brigade: where things are, and how to get in.
