C4 Model

TL;DR

Most architecture diagrams fail because nobody can tell what a box is or how far in we've zoomed. The C4 model gives four fixed zoom levels: Context (the system and the people and systems around it), Containers (the deployable things: apps, services, databases), Components (the parts inside one container) and Code (almost never drawn). Every box says its name, type, technology and job, every arrow says what flows, and every diagram has a title and a legend.

1The situation Larder, 6 October 2026

Larder now has 18 engineers, four of them new this year. The wiki holds eleven architecture diagrams: clouds, cylinders, coloured boxes with no legend, arrows that might mean calls or data or “talks to, somehow”. One still shows Dispatch inside Larder Core, a year after it moved out. A new engineer asks Ana the simplest question: which one is true?

  • Every author invents a notation, so every diagram needs its author to explain it.
  • Diagrams mix zoom levels: a database next to a whole partner company.
  • Nobody knows which diagrams are current, so nobody trusts any.

2Real-life analogy zoom levels on a map

A map app doesn't show every house on the map of Europe. You zoom: country, city, street, house. Each level shows what that level's question needs, the symbols are the same every time, and you only zoom as far as you need. Nobody draws their own symbols for motorways.

Translating it to the job
In real lifeOn the project
The countryContext: Larder and everything around it
The cityContainers: apps, Core, Dispatch, databases
The streetComponents: the modules inside Larder Core
The houseCode: rarely needed on a diagram
The map's legendEvery box's type and technology, every arrow's label

3How it solves it four levels, one notation

Ana replaced the eleven diagrams with four: one context diagram (updated from Vol. 1's), one container diagram, and component diagrams for Larder Core and Dispatch. Each box says what it is and what it's built with; each arrow says what it carries. The old diagrams went into an archive folder with a note pointing to the new ones.

  1. Start at context

    One box for your system, the people who use it, the systems it talks to.

  2. Draw the containers

    Every separately deployed or run thing: apps, services, databases, queues.

  3. Components only where needed

    Inside a container that's big or contested, like Larder Core.

  4. Label everything

    Box: name, type, technology, one-line job. Arrow: what flows, how.

  5. Title and legend on every diagram

    Scope, level, date, and what shapes and colours mean.

  6. Retire the rest

    Archive old diagrams with a link to the new ones.

Vocabulary for the exam

Context diagram
Level 1: the system, its users and neighbouring systems.
Container
Level 2: a deployable or runnable unit: app, service, database.
Component
Level 3: a grouping inside one container.
Supplementary diagram
Sequence, deployment or data views that add to C4.
Notation
The agreed meaning of shapes, lines and colours.
Legend
The key that explains the notation on each diagram.

4Gains vs losses nothing is free

What we gain

  • One notation: anyone can read any diagram.
  • Right detail for the reader: context for executives, components for a team.
  • Fewer, trusted diagrams instead of many stale ones.
  • Faster onboarding for new engineers.
  • Tool support: diagrams as code, generated sites.

What we lose

  • Learning the rules takes an hour or two.
  • Not everything fits: flows and deployment need extra diagrams.
  • Still goes stale unless kept as code and reviewed.
  • Tempting to draw every level for every container.

6Common pitfalls the usual ways this goes wrong

  • Mixed levels

    A database next to a partner company. Fix → one level per diagram; zoom on a separate one.

  • Unlabelled arrows

    Lines that mean “related somehow”. Fix → every arrow says what flows and how.

  • No legend

    Colours that only the author understands. Fix → title, scope and legend on every diagram.

  • Drawing every level

    Component diagrams nobody reads. Fix → components only where a container is big or contested.

7When to use it (and when not)

Use it when…

  • Onboarding and shared understanding of a system.
  • Replacing a pile of inconsistent diagrams.
  • Explaining a system to people at different levels.
  • Before a design discussion or review.

Skip it when…

  • Code-level detail: read the code.
  • Runtime flows and infrastructure: add sequence and deployment diagrams.

8Self-check quiz

What are the four C4 levels?

Context, Containers, Components, Code.

What's a container in C4?

Something separately deployed or run: an app, a service, a database, a queue.

What must every box say?

Its name, type, technology and job.

Which level is rarely drawn?

Code: the code itself is the diagram.

try it

Find every architecture diagram your team has. Redraw just two of them in C4: one context and one container diagram, with labelled boxes and arrows, a title and a legend. Ask a new joiner which version helps them more, then archive the old ones.

remember!!

Zoom like a map: country, city, street, house. Label every box and arrow.
