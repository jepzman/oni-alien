arc42 Template

TL;DR

Architecture documents are hard to use when every one has a different shape. arc42 is a free template with twelve fixed sections: goals, constraints, context, solution strategy, building blocks, runtime, deployment, cross-cutting concepts, decisions, quality requirements, risks and glossary. Use it as a skeleton, not a form: fill what's needed, link what already exists (ADRs, diagrams, debt register), and leave a one-line “not needed, because…” where a section doesn't apply.

1The situation Larder, 17 November 2026

A new engineer spends her first week looking for Larder's architecture. It's in the wiki, the repo, shared documents and a few slide decks, each shaped differently. She finds the ADRs and the new C4 diagrams, but asks Ana: where are the quality requirements? the risks? the rules everyone follows, like the outbox? They exist, somewhere.

  • Every author structures documents their own way.
  • Some topics (quality goals, cross-cutting rules) have no obvious home.
  • Readers can't tell what's missing from what's elsewhere.

2Real-life analogy the cookbook

In a good cookbook every recipe is laid out the same way: serves and time, ingredients, method, tips. On any page you know where to look, and if a recipe has no cooking time, you notice at once. The layout doesn't make the food better; it makes the book usable.

3How it solves it twelve sections, mostly links

Ana mapped what Larder already had onto the twelve sections in an afternoon. Most were links: drivers, constraints, C4 diagrams, sequence diagrams, the ADR log, the debt register. Two sections needed new writing: cross-cutting concepts (outbox, offline-first, city configuration, idempotency) and quality requirements (the scenarios from Vol. 1, gathered in one place). The glossary was scheduled for February.

  1. Create the twelve files

    docs/architecture/01-goals.md … 12-glossary.md, each with its arc42 heading.

  2. Link what exists

    ADRs, diagrams, the debt register: link, never copy.

  3. Write the gaps

    Usually cross-cutting concepts and quality requirements.

  4. Mark what's not needed

    One line: “not needed, because…”, so readers know it's not missing.

  5. Start with the one-pager

    The README is the one-pager; arc42 is the next layer.

  6. Review with changes

    When an ADR or diagram changes, check its section.

# 8. Cross-cutting concepts                              arc42 · Larder · Nov 2026

8.1 Events leave a transaction through the outbox
    Every module that publishes writes to its outbox in the same transaction;
    the relay sends to Kafka. Consumers dedupe on the event id. (ADR 0007)
8.2 A city is configuration
    Stores, zones, hours, prices and VAT live in the city config, never in code.
    Exceptions are technical debt (TD-1). (ADR 0003)
8.3 Offline-first in the store
    The picker app works 30 minutes without Wi-Fi; answers sync at packing. (ADR 0004)
8.4 Idempotent commands
    Every payment and order command carries a client key; retries are safe.
8.5 Personal data
    Customer data stays in the EU; see the data view and Lena's register.

Sections not needed yet: none. Section 12 (glossary): planned February 2027.

tools: the arc42 templates (Markdown, AsciiDoc, Confluence) from arc42.org; docToolchain to build arc42 docs from the repo; Structurizr can embed diagrams into the sections.

4Gains vs losses nothing is free

What we gain

  • A known shape: readers know where to look.
  • Gaps are visible: empty sections stand out.
  • Homes for orphan topics: concepts, quality, risks.
  • Free and widely known, with tooling.
  • Reuses existing work through links.

What we lose

  • Can become form-filling if every section is forced.
  • Twelve files feel heavy for small systems.
  • Duplication if people copy instead of link.
  • Unfamiliar names at first.

6Common pitfalls the usual ways this goes wrong

  • Form-filling

    Every section filled with filler. Fix → write only what helps; mark the rest “not needed, because…”.

  • Copying

    The ADRs pasted into section 9, then edited separately. Fix → link, never copy.

  • A separate tool

    arc42 in a wiki nobody updates with code changes. Fix → keep it in the repo, next to the code.

  • No entry point

    Twelve files and no summary. Fix → the one-pager is the README.

7When to use it (and when not)

Use it when…

  • Systems with more than one team.
  • When architecture information is scattered.
  • Audits and partner due diligence.
  • Long-lived systems with turnover.

Skip it when…

  • Small, short-lived projects: a one-pager and ADRs are enough.
  • As a substitute for talking: documents support conversations.
