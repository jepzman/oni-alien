Views & Viewpoints (4+1)

TL;DR

No single diagram can answer every stakeholder's question. A viewpoint is a kind of question (where does data flow? what runs where?); a view is the drawing that answers it for your system. Kruchten's 4+1 gives a starting set: logical (what the parts are), process (what happens at runtime), development (how code and teams are organised), physical (what runs where), tied together by scenarios. Add the views your stakeholders actually ask for, such as a data view for the DPO.

  • Family: diagrams
  • Origin: Philippe Kruchten, “The 4+1 View Model of Architecture” (IEEE Software, 1995); ISO/IEC/IEEE 42010
  • Lives in: docs/architecture/views/, one page per view
  • Pairs with: C4 model, stakeholder map, sequence and deployment diagrams

1The situation Larder, 13 October 2026

The new container diagram is popular, so everyone brings Ana their question. Lena, the DPO, needs to know where customer data goes before Larder for Business signs more clients. Joost wants to know what happens in a store when the Wi-Fi drops. Ben asks which module owns business accounts. Eli asks what runs where. The one diagram answers none of them well, and adding everything to it would make it unreadable.

  • One “master diagram” tries to answer every question and answers none.
  • Some stakeholders (legal, operations) never get a picture made for them.
  • Questions about data, runtime and infrastructure need different drawings.

2Real-life analogy a drawing for each trade

A house has a floor plan for the family, a wiring plan for the electrician, a plumbing plan for the plumber and an elevation for the planning office. It's one house; each trade gets the drawing that answers its questions. Nobody puts the pipes on the family's floor plan.

3How it solves it a view per question

Ana listed the questions first, then picked views to answer them: the logical view (modules and ownership) for the teams, the process view (an order's journey, with the store offline) for Joost, the physical view for Eli, and a data view for Lena that traced every place a customer's address and phone number go, including the helpdesk and the billing service. Two scenarios tie them together.

  1. List the stakeholders' questions

    From the stakeholder map: what does each person need to know?

  2. Group them into viewpoints

    Structure, runtime, code and teams, infrastructure, data, security.

  3. Draw one view per viewpoint

    Only the views someone asked for. Reuse C4 notation where it fits.

  4. Tie them with scenarios

    Two or three key journeys walked through every view.

  5. Name each view's audience

    On the page: “for Lena”, “for on-call”.

  6. Check views agree

    A module in the logical view must appear in the physical view too.

Vocabulary for the exam

Viewpoint
A kind of question and the conventions for answering it.
View
The drawing that answers a viewpoint for this system.
4+1
Logical, process, development, physical, plus scenarios.
Scenario
A key journey walked through every view.
Data view
Where data, especially personal data, lives and flows.
ISO 42010
The standard for describing architectures with views.

4Gains vs losses nothing is free

What we gain

  • Each stakeholder gets an answer in their terms.
  • Legal and operations finally have pictures.
  • Simpler diagrams: each does one job.
  • Scenarios check consistency across views.
  • Gaps show up: the helpdesk held addresses nobody listed.

What we lose

  • More diagrams to keep current.
  • Views can disagree if maintained separately.
  • Over-documenting if you draw views nobody asked for.
  • Vocabulary (viewpoint vs view) confuses at first.

6Common pitfalls the usual ways this goes wrong

  • The master diagram

    Everything on one page. Fix → one view per question, linked together.

  • Views nobody asked for

    A development view nobody reads. Fix → start from stakeholders' questions.

  • No scenarios

    Views that quietly disagree. Fix → walk two or three journeys through every view.

  • Forgetting data

    Nobody can say where addresses go. Fix → draw a data view whenever personal data is involved.

7When to use it (and when not)

Use it when…

  • Systems with many kinds of stakeholders.
  • Before a privacy review or audit.
  • When one diagram keeps growing.
  • Onboarding operations and on-call staff.

Skip it when…

  • Small systems where one context diagram answers everything.
  • Views nobody has a question for.

8Self-check quiz

What's the difference between a viewpoint and a view?

A viewpoint is a kind of question; a view is the drawing that answers it for your system.

Name the 4+1 views.

Logical, process, development, physical, plus scenarios.

Which view did Larder add, and for whom?

A data view, for Lena, the DPO.

What are scenarios for?

Walking key journeys through every view, which ties them together and checks they agree.

try it

Write down the questions three different stakeholders ask about your system. For each, sketch the simplest view that answers it, in 20 minutes each. Walk one scenario through all three and note anything that disagrees.
