DNSit's always DNS

dig skips /etc/hosts; getent doesn't. Changed a record? Old answers live until the TTL runs out. Flush: resolvectl flush-caches.

Reachability

No ping reply ≠ down: many hosts and clouds block ICMP. Test the real port instead.

Ports: who listens, who answers

Listening on 127.0.0.1:8080 = only this machine. On 0.0.0.0 / [::] = every interface.

Firewalls & filters

  • Host: sudo nft list ruleset · iptables -L -n -v · ufw status
  • Cloud: security group and network ACL and route table
  • Kubernetes: a NetworkPolicy may deny by default
  • Corporate: proxy, VPN split tunnel, egress allow-list
  • Both ways: the reply has to get back too

TLS errors decoded

expired
check notAfter; renew; automate it
name mismatch
host not in SAN; wrong -servername (SNI)
unable to get local issuer
missing intermediate on the server, or a corporate CA not trusted by the client
self-signed
trust that CA explicitly; never -k in prod
handshake failure
no common TLS version / cipher; mTLS cert missing

Proxies & trust

  • HTTPS_PROXY, HTTP_PROXY, NO_PROXY (some tools only read lowercase)
  • NO_PROXY must list internal hosts, localhost, cluster domains
  • TLS-inspecting proxy? Add its CA: /usr/local/share/ca-certificates + update-ca-certificates
  • Node, Python, Java keep their own trust stores: NODE_EXTRA_CA_CERTS, REQUESTS_CA_BUNDLE, keytool

SSH & tunnelsreach private hosts safely; forward ports both ways

5/5card

← swipe the diagram →

Tunnels-N = no shell, just the tunnel

Read a forward

-L 5432:db.internal:5432 bastion

1st
port opened on your side
2nd
target host, resolved by the bastion
3rd
target port
last
the SSH server in the middle

-R is the mirror: the 1st port opens on the server, the target is reached from your side. Tunnels listen on 127.0.0.1 unless you say otherwise.

~/.ssh/configthen: ssh db-tunnel

Keys & basics

SSH errors decoded

Permission denied (publickey)
wrong user or key; chmod 700 ~/.ssh, 600 on the key; check ssh -v
Host key verification failed
the host changed (rebuilt?) or something is in the middle. Verify, then ssh-keygen -R host
Too many authentication failures
the agent offers every key: IdentitiesOnly yes
bind: Address already in use
local port taken: lsof -i :5432, pick another
channel open failed: administratively prohibited
server has AllowTcpForwarding no
connect failed: Connection refused
the bastion can't reach the target host:port

Safer habits

  • -J instead of -A: agent forwarding lets the bastion use your keys
  • Keep forwards on 127.0.0.1; GatewayPorts only on purpose
  • Close tunnels when done: ~. quits a stuck session
  • Cloud options without open port 22: AWS SSM, gcloud … --tunnel-through-iap, Azure Bastion, kubectl port-forward
