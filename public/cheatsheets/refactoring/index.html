Bloaters

Long Function
you scroll to read it; comments label its sections
Large Class
too many fields and methods; several jobs in one
Long Parameter List
five arguments, some always passed together
Data Clumps
the same three fields travel together everywhere
Primitive Obsession
money as number, email as string

Change preventers

Divergent Change
one module changed for many unrelated reasons
Shotgun Surgery
one change needs small edits in many modules
Repeated Switches
the same switch on a type in several places
Global Data
anyone can change it, nobody knows who did
Mutable Data
values change under you; bugs far from the cause

Couplers

Feature Envy
a function uses another module's data more than its own
Insider Trading
two modules swap private details
Message Chains
a.b().c().d(): callers know the whole path
Middle Man
a class that only forwards calls

Dispensables

Duplicated Code
the same logic in two places, slowly drifting
Lazy Element
a class or function that adds nothing
Speculative Generality
hooks and parameters “in case we need it”
Dead code
unreachable or unused; version control remembers it
Comments
explaining what unclear code does (fix the code)
Mysterious Name
you need the body to know what it does

OO abusers

Temporary Field
a field set only in some situations
Refused Bequest
a subclass ignores what it inherits
Data Class
fields and getters, all logic elsewhere
Alternative Classes
two classes do one job with different method names
Loops
a loop where a pipeline (filter, map) reads better

Sniff test: five questions

  • Can I say what this function does in one sentence, without “and”?
  • Would a new teammate guess it from the name alone?
  • To make my change, how many files must I touch?
  • Is the same rule written twice?
  • Does this code use someone else's data more than its own?

Tools help find candidates: ESLint complexity rules, SonarQube, CodeScene hotspots (complex code that changes often matters most).

Big-step moves

  • Split Phase: parse → compute → render as separate steps, a data structure between
  • Replace Function with Command: a long function becomes an object; temps become fields
  • Combine Functions into Transform: enrich a record once, not derived values everywhere
  • Replace Superclass with Delegate: stop inheriting what you don't want

Names of the moves

Every refactoring has an inverse: Extract ↔ Inline, Encapsulate ↔ expose, Move there ↔ move back. Pick by what makes the next change easier, not by a rule.

Fowler's 2nd edition (2018) renamed several classics: Extract Method → Extract Function; Replace Method with Method Object → Replace Function with Command; Rename Method → Change Function Declaration. Catalogue: refactoring.com/catalog.

Code smells at a higher level

  • God service: split by actor or use case (vertical slices)
  • Anemic model, rich rules: Move Function onto the entities
  • Leaky vendor types: an adapter or anti-corruption layer at the border

Refactoring safelysmall steps, two hats, and legacy code

4/4card

← swipe the diagram →

Definition

Refactoring: changing the structure of code without changing its behaviour, in small steps that each keep it working.

Not refactoring: rewriting, “refactoring sprints” that break the build for a week, or a behaviour change hidden in a cleanup.

Read: Fowler, Refactoring, 2nd ed. (2018) · Feathers, Working Effectively with Legacy Code (2004) · Beck, Tidy First? (2023) · Ellnestam & Brolund, The Mikado Method (2014).

The two hats

Adding a feature
new behaviour, new tests; no restructuring
Refactoring
same behaviour, tests unchanged; only restructuring

Wear one hat at a time. Swap often, but say which one you're wearing, in the commit message too.

When to refactor

Preparatory
“make the change easy, then make the easy change” (Kent Beck)
Comprehension
rename and extract while you read, to record what you learned
Litter-pickup
leave it a little better than you found it
Rule of three
third time you write the same thing, extract it
Not when
the code works, nobody needs to change it, or a rewrite is cheaper

Legacy code without tests

  • Characterization tests first: record what it does today, right or wrong
  • Find a seam: a place to substitute behaviour (a parameter, an interface)
  • Use automated refactorings only until tests exist (rename, extract, move)
  • Sprout new code in a new, tested function; call it from the old
  • Big change? Mikado method: try, note blockers, revert, fix leaves first
  • Whole system? Strangler fig, not a big-bang rewrite

Pull requests

  • Separate refactor commits from behaviour commits
  • Big renames and moves in their own PR, merged fast
  • Tests unchanged in a refactor-only commit (a tell if not)
  • Prefix commits: refactor: vs feat:
