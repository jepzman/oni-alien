Found a bug? Where to branchdecide first

  1. Not released yet, found in DEV / SITbugfix/* from develop → PR into develop
  2. In the release, found in UATbugfix/* from release/x.y.0 → PR into the release, then back-merge to develop
  3. In PROD, it can waita normal bugfix/* on develop; it ships with the next release
  4. In PROD, it can't waithotfix/x.y.z from main → main (tag) + develop

Golden rules

  1. main is production. Every merge into main is a release and gets a tag.
  2. No direct commits on main, develop or release/*: protect them, use PRs.
  3. Everything flows back. Whatever lands on main or a release must reach develop.
  4. A release branch is frozen: only fixes, version bumps and release notes.
  5. Short-lived branches. Sync with the parent daily; merge within days.
  6. One fix, one branch, one PR, with a test that failed before the fix.

Merge strategies: pick per target branch

Merge commit --no-ff

Keeps every commit and where the branch joined.

Use for release → main, hotfix → main, all back-merges.

Squash --squash

One tidy commit per feature; branch commits are dropped.

Use for feature/bugfix → develop. Never for release/hotfix.

Rebase + fast-forward rebase

Straight-line history; rewrites the branch's commits.

Use for updating your own private branch. Never on shared branches.

Feature: start → mergedthe daily loop

Bug fix, not yet released

Found in UAT or PROD instead? Turn the page.

Keep your branch up to date

A · rebase your own branch

B · merge shared branch

Do it daily: small syncs = small conflicts.

Resolve a conflict

  1. git status lists the conflicted files
  2. Edit each one: keep the right code, delete the <<<<<<< ======= >>>>>>> markers
  3. Run the tests, then git add <file>
  4. Finish: git commit (merge) or git rebase --continue

In a rebase, --ours and --theirs are swapped: “ours” is the branch you rebase onto.

PR checklist

  • Base branch is right (develop · release/* · main)
  • Title has the ticket: PROJ-123 …
  • Branch is up to date with its base
  • CI green, tests added for the change
  • Reviewed: 1+ approval, comments resolved
  • Strategy picked: squash or merge commit
  • Delete the branch after merging

Releases & UATcut, test, fix, sign off, go live

3/4card

← swipe the diagram →

1 · Cut the releasefeature freeze

2 · Fix a UAT bugUAT fix

3 · Back-merge to develop

After every UAT fix, or at least daily, so develop never loses a fix. Merge, don't squash.

4 · Sign-off → go livefinish

Release scenarios

A feature fails UAT and must come out
Revert it on the release: git revert -m 1 <merge-sha> (merged) or git revert <sha> (squashed). Back-merge as usual. ! To ship it later, first revert the revert on develop: git revert <revert-sha>.
New work is ready during UAT
It merges into develop and waits for the next release. Never merge features into a release.
The release needs one fix that's already on develop
git switch release/1.4.0 then git cherry-pick -x <sha> (-x records where it came from).
UAT drags on, develop has moved far ahead
Keep fixing on the release. Don't re-cut it from develop: that pulls in untested work.
Two releases at once
Avoid it. Finish 1.4.0 first, then cut 1.5.0 from develop. If you must, merge 1.4.0's fixes forward into 1.5.0 too.

Go-live checklist

  • Version bumped on the release branch
  • Release notes / changelog written
  • UAT sign-off recorded (who, when)
  • DB migrations reviewed, backward compatible
  • Rollback plan: previous tag, data steps
  • Merged with --no-ff, tag pushed
  • Back-merged to develop, branch deleted

Emergency scenarios

The release is bad, roll back now
Redeploy the previous tag (v1.4.0) from the pipeline: no git change. Then fix forward with a hotfix.
Undo a merge that's already on main
git revert -m 1 <merge-sha> on a hotfix branch → PR → tag v1.4.2. -m 1 keeps main's side.
Forgot to bring a hotfix back
git switch develop, git merge --no-ff v1.4.1. Spot it: git log --oneline develop..main should show only merge commits.
Also needed on an older version
git switch -c support/1.3 v1.3.2, git cherry-pick -x <sha>, tag v1.3.3.
Committed on develop by mistake (not pushed)
git branch feature/x, git reset --hard origin/develop, git switch feature/x.
Pushed a password or key
Rotate it first: it is already leaked. Then scrub history with git filter-repo, with the whole team.

Undo table

Unstage a filegit restore --staged f
Throw away local editsgit restore f
Fix the last commit (unpushed)git commit --amend
Undo last commit, keep changesgit reset --soft HEAD~1
Undo a pushed commitgit revert <sha>
Park work in progressgit stash push -m wip · git stash pop
Find a “lost” commitgit reflog

Pushed? Then revert, don't reset: others already have those commits.
