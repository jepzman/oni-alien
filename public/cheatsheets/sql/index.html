NULL rules

  • NULL = NULL is unknown, not true: use IS NULL
  • WHERE keeps only true rows; unknown is dropped
  • COUNT(*) counts rows, COUNT(col) skips NULLs
  • SUM, AVG ignore NULLs; all-NULL → NULL
  • COALESCE(a, b, 0) first non-NULL
  • NULLIF(x, 0) avoids divide-by-zero
  • ! NOT IN (subquery) with a NULL inside returns nothing: use NOT EXISTS
  • Postgres: a IS DISTINCT FROM b = NULL-safe <>

Join syntaxpostgres

Join traps

  1. Fan-out: joining two one-to-many tables multiplies rows, so sums double. Aggregate each side first, then join.
  2. ON vs WHERE in a LEFT JOIN: a condition on B in WHERE turns it into an inner join. Put it in ON.
  3. Missing ON (or a wrong one) = an accidental cross join.
  4. NOT IN + NULL returns no rows. Use NOT EXISTS.
  5. Join on columns with the same type; casts kill indexes.

Set operations

UNION
stack + remove duplicates (sorts: slower)
UNION ALL
stack, keep all: the default choice
INTERSECT
rows in both
EXCEPT
rows in the first, not the second (MINUS in Oracle)

Same number of columns, compatible types, names from the first query.

Subquery or CTE?

CTEs read top to bottom; use them for steps. A correlated subquery runs per row: fine with an index, slow without.

Semi-join: EXISTS vs IN vs JOIN

EXISTS
“has at least one”; stops at the first match; NULL-safe
IN
fine for small lists and non-NULL subqueries
JOIN
only when you need B's columns; watch for duplicates

Index rules

  1. Leftmost prefix: (a, b, c) serves a, a,b, a,b,c, not b alone.
  2. Equality first, range column last: (customer_id, created_at).
  3. Keep columns bare: created_at >= '2026-01-01', not date(created_at) = …; or index the expression.
  4. LIKE 'abc%' can use an index; '%abc' can't (use trigram / full-text).
  5. Index foreign keys you join on.
  6. Covering: INCLUDE (total) lets the index answer alone.
  7. Every index slows writes and costs disk: drop unused ones.

Read EXPLAIN

Seq Scan
reads the whole table: fine if small, else index?
Index Scan
index, then table rows
Index Only
answered from the index alone
Bitmap
many matches gathered, then fetched
Nested Loop
good for few rows with an index
Hash Join
big unsorted sets, needs memory
Merge Join
both sides already sorted

Look for: estimated vs actual rows far apart (run ANALYZE), sorts spilling to disk, the slowest node.

Isolation levels

dirtynon-rep.phantom
Read uncommittedyesyesyes
Read committed—yesyes
Repeatable read——yes*
Serializable———

yes = can happen. Defaults: Postgres, SQL Server = read committed; MySQL InnoDB = repeatable read. *Postgres and InnoDB prevent most phantoms here too. Serializable can fail with retry errors: retry the transaction.

Change data safely

Write the WHERE first. Run it as a SELECT before the UPDATE / DELETE. Keep transactions short; lock rows in the same order to avoid deadlocks.

Schema changes in production

  • Add columns nullable (or with a constant default)
  • CREATE INDEX CONCURRENTLY (Postgres) · ALGORITHM=INPLACE (MySQL)
  • Rename = add new, copy, switch reads, drop old later
  • Backfill big tables in batches
  • Set a lock_timeout on migrations
  • Migrations in git, reviewed, reversible
  • Backup tested by restoring it
