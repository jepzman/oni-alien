Release or Deploy?

TL;DR

Deploying puts new code into production; releasing lets people use it. Done together, the risk of the code and the risk of the launch arrive at once, and the only way back is undoing the deploy. Done apart, code goes out dark in small, frequent deploys, and the release is a flag turned on in steps: staff first, then a few customers, then everyone. A problem is fixed by turning the flag off, not by rolling back.

  • Family: deciding about changes
  • Lives in: the flag service, the release plan for each launch
  • Pairs with: feature flags, the change calendar, rollback plans

1The situation Larder, March 2027

Femke decides on 1 March that Larder Plus, a €7.99 monthly delivery subscription, launches in June. The first plan from the team building it: eight weeks on a branch, merge the night before, deploy on launch morning and switch it on for everyone at once. The risk of new code and the risk of a launch, stacked on the same morning. If anything breaks, the only way back is undoing the whole deploy, along with everything else that went out with it.

  • Big merges hide conflicts until the last minute.
  • A launch-morning deploy is a large normal change at a sensitive time.
  • Product and engineering both feel the pressure of one moment.

2Real-life analogy the set behind the curtain

A theatre doesn't build the set on opening night. The set goes on stage days before, behind the closed curtain, and it's tried out with a small invited audience. On opening night the only thing that happens is the curtain goes up. If a prop breaks during the preview, they fix the prop; they don't rebuild the stage.

3How it solves it dark deploys, then a release in steps by flag

Eli and Ben rewrite the plan:

  • From 10 May, Plus code goes out in 46 small deploys, each a standard change through the pipeline, behind a flag that is off. Nobody outside the team can see it.
  • 24 May: released to Larder staff.
  • Tuesday 1 June: released to 5 % of Amsterdam customers. On day two a renewal bug charges two test customers twice. The flag goes off for 2 hours while the bug is fixed and deployed, the charges are refunded, and the flag goes back on. Nothing is rolled back.
  • Tuesday 8 June, 10:00, outside every window: released to everyone.

The release itself is a flag change, which is a standard change. The risk of the code was taken earlier, in small steps. From now on, Eli's rule for any launch is two plans: a deploy plan (engineering, small, frequent) and a release plan (product, in steps, with a flag as the way back).

  1. Deploy small and often, behind a flag

    Code in production, nobody sees it.

  2. Write a release plan separately

    Who sees it when: staff, a few, everyone.

  3. Choose release times by the calendar

    Never in a window, never on a Friday evening.

  4. Make the flag the way back

    Off in seconds, no deploy undone.

  5. Watch signals at each step

    Errors, support tickets, the business number.

  6. Remove the flag after the release

    Old flags are debt.

Vocabulary for the exam

Deploy
Putting a new version of code into an environment, such as production.
Release
Making a change available to users.
Dark launch
Code deployed to production but not visible to users.
Feature flag
A switch that turns a feature on or off without a deploy.
Progressive release
Releasing to a growing share of users, step by step.
Flag debt
Old flags left in the code after the release is finished.

4The maturity ladder where are we, and what is the next rung?

1By hand

deploy = release

  • Big deploys on launch day.
  • Rollback is the only way back.

2Written down Larder now

dark deploys, flagged releases

  • Release plan in steps.
  • Flag off as the way back.

3Scripted

automated progressive release

  • The flag service raises the share as signals stay good.
  • Stops by itself on bad signals.

4Automatic

release as a product decision

  • Engineers deploy all day.
  • Product releases when ready, no engineering event.

6Common pitfalls the usual ways this goes wrong

  • Big-bang launch morning

    Deploy and release together, at a busy time. Fix → deploy dark first, release in steps.

  • Flags that never go

    Hundreds of old switches nobody understands. Fix → remove the flag after the release.

  • Flags as the only test

    Dark code still runs in production and can break it. Fix → dark doesn't mean untested.

  • Data changes behind a flag

    A flag can't undo data that's been written. Fix → plan data changes separately (next notes).

7When to use it (and when not)

Use it when…

  • A launch has a date and a marketing push.
  • Deploys are big and rare.
  • Rollback is your only way back.
  • Product and engineering argue about launch-day risk.

Skip it when…

  • Tiny internal changes nobody needs to be told about.

8Self-check quiz

What's the difference between deploying and releasing?

Deploying puts code into production; releasing lets people use it.

What is a dark launch?

Code deployed to production behind a switch that is off, so users don't see it.

How was the Plus renewal bug handled?

The flag was turned off for 2 hours while the fix was deployed; nothing was rolled back.

Who owns the release plan, and who owns the deploy plan?

Product (Grace) owns release; engineering (Ben) owns deploys.

Why remove flags after a release?

Old flags pile up as debt: confusing, untested paths in the code.

what would you do?Marketing wants Plus “live” at 18:00 on a Friday to match an email. What do you suggest?

Release it at 10:00 on a weekday, before the email, to a growing share, then send the email when it's on for everyone. Or send the email later. A release in the Friday window is exactly what the calendar exists to prevent.

try it

Take your next feature with a launch date. Write two plans: the deploy plan (small, dark, frequent) and the release plan (who sees it when, which signals, what's the flag). How much risk moves off launch day?

remember!!

Deploy the set behind the curtain, release by raising it in steps. The flag is the fastest way back.
