The Urgent Fix at 17:00 on a Friday

TL;DR

An emergency change is one that can't wait, usually to stop harm during an incident. It gets fewer checks, never none. First look for the smallest undo that stops the harm (a flag, a config, a rollback), because that often makes the real fix non-urgent. If new code must ship now: the incident lead approves, two people do it, it's marked in the feed, someone watches it, and it's written up within a day.

1The situation Larder, Friday 12 March 2027

At 16:52 on a Friday an alert fires: discounts per order are four times normal. Thursday's deploy has let the promo code WELCOME10, €10 off a first order, work on every order: about €40 a minute. Ben has a fix ready in ten minutes, but at 17:00 the Friday window starts and the pipeline will refuse it. Two people start arguing whether to break the rule or wait three hours.

  • A window rule with no emergency path forces a choice between harm and bypassing.
  • Under pressure, “ship the fix” feels like the only option.
  • Rushed code in the peak window is how one incident becomes two.

2Real-life analogy the ambulance at a red light

An ambulance may cross a red light. Its lights and siren go on, it slows at the junction, a second paramedic watches the road, and the crossing is logged afterwards. That's allowed, and it isn't careless. Emergency means fewer rules, never none.

3How it solves it smallest undo first; if code must ship, a light path with two people

Dee, the incident lead, stops the argument with one question: what's the smallest undo that stops the harm? The answer is the promo-code flag. Turning it off is a standard change and allowed in the window. At 17:01 it's off, and the losses stop. New customers can't use codes for the evening, which costs far less. With the harm stopped, the code fix isn't urgent any more. It waits until Monday as a normal change. Total loss: about €320 instead of the roughly €7,000 three hours of waiting would have cost.

Eli writes the path down that weekend:

  1. Smallest undo first: a flag, a config, a rollback of the last change.
  2. If new code must ship now: the incident lead approves, two people do it (one writes, one reviews in the same call), the deploy is labelled “emergency” with the lead's name (which the pipeline accepts in a window and posts to the feed), and someone watches for 30 minutes.
  3. Written up within a working day, like a normal change after the fact.

From February to June there are 3 emergency changes, and all 3 are written up.

  1. Ask for the smallest undo first

    Flag, config, or roll back the last change.

  2. Stop the harm, then decide about the fix

    Often it can wait for a normal change.

  3. If code must ship: the lead approves

    One named person decides.

  4. Two people do it

    Write and review in the same call.

  5. Label it and watch it

    “Emergency” + name; a watcher for 30 minutes.

  6. Write it up within a day

    And review whether the path worked.

Vocabulary for the exam

Emergency change
A change that must be made as soon as possible, often to restore service.
Mitigation
Reducing harm now, without fixing the cause.
Smallest undo
The quickest, least risky action that stops the harm.
Emergency CAB
ITIL v3's small group for approving emergencies; at Larder, the incident lead.
Retroactive record
The write-up of a change after it's been made.
Kill switch
A flag that turns a feature off instantly.

4The maturity ladder where are we, and what is the next rung?

1By hand

break the rules or wait

  • Arguments under pressure.
  • Rushed code in the peak.

2Written down Larder now

a written emergency path

  • Smallest undo first.
  • Two people, a label, a write-up.

3Scripted

kill switches everywhere

  • Every risky feature has a flag.
  • Most emergencies need no code.

4Automatic

automatic mitigation

  • Signals turn off a misbehaving feature by themselves.
  • People decide the fix calmly.

6Common pitfalls the usual ways this goes wrong

  • Jumping to new code

    A rushed fix in the peak causes a second incident. Fix → smallest undo first.

  • No emergency path

    People bypass the pipeline entirely. Fix → a light, named path that the pipeline accepts.

  • Emergency as a shortcut

    “Emergency” used to skip review on a normal day. Fix → only during an incident, with the lead's name.

  • No write-up

    Nobody learns how often this happens. Fix → written up within a working day.

7When to use it (and when not)

Use it when…

  • An incident needs a change during a window or freeze.
  • Harm is growing every minute.
  • A fix is ready and people want to ship it now.
  • Designing risky features (add a kill switch).

Skip it when…

  • Anything that can wait until the window closes: it's a normal change.

8Self-check quiz

What's the first question in an emergency change?

What's the smallest undo that stops the harm?

How did Dee stop the WELCOME10 losses?

She turned off the promo-code flag at 17:01, a standard change allowed in the window.

Why did the code fix wait until Monday?

Once the harm had stopped it wasn't urgent, so it went through as a normal change.

If code must ship in an emergency, what's needed?

The lead's approval, two people, the emergency label with the lead's name, a watcher, and a write-up within a day.

What's the risk of “emergency” as a label?

That it becomes a shortcut to skip review on normal days.

what would you do?At 07:20 on a Tuesday, business orders fail because of a bug in this morning's 06:50 deploy. There's no flag. What do you do?

Smallest undo: roll back the 06:50 deploy (emergency label, lead's name), watch the business orders, and fix the bug as a normal change after 09:00.

try it

List your three riskiest features. Does each have a kill switch you could turn off in a minute? For the one that doesn't, write down what the smallest undo would be in an emergency.

remember!!

In an emergency, stop the harm with the smallest undo first. The fix can usually wait, and when it can't: two people, a name, a write-up.
