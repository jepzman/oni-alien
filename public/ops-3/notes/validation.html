Is It Really Ready?

TL;DR

A test is only as good as the place it runs in. Build staging from the same infrastructure code as production, smaller but with the same parts (replicas, poolers, network rules, masked real data). Accept that some things can only be tested in production: failover, real vendors, real load. Test those there, carefully: at a quiet hour, announced, with a watcher and a way back. Record where each change was tested.

1The situation Larder, February 2027

ADR 0017 promises failover in under 2 minutes. On 15 February the fix is tested in staging and passes in 50 seconds. But staging's database has no replica, so the “failover” there is just a restart. On Tuesday 23 February at 10:00, the first production test takes 6 minutes 10 seconds: the Dispatch containers cache the database's address for five minutes. Staging couldn't find it, because staging isn't built the same way.

  • A passed test in the wrong place is false comfort.
  • Staging was built by hand and drifted from production.
  • Nobody had planned to test the real failover, in the real place.

2Real-life analogy the fire drill in the real building

Practising an evacuation in an empty car park tells you nothing about the real building: the stairwell door that sticks, the lift people try to use. The useful drill happens in the real building, at a quiet time, with people told in advance and someone timing it.

3How it solves it a staging that's honest, and careful tests in production

Two changes, from March:

  • Staging is built from the same infrastructure code as production, just smaller: the same replica, the same connection pooler, the same network rules, and masked copies of real data. Bram rebuilds it on 2 March. The differences that remain are listed on one page.
  • Some things are tested in production, because nothing else is real enough: failover, real vendor behaviour, real load. Each test has a quiet hour (Tuesday 10:00), an announcement in the incident channel and to Sam, a watcher, and a way back.

After Dispatch is changed to refresh the database address every 10 seconds, the monthly production failover test (second Tuesday, 10:00) gives 1:40 on 9 March, 1:35 in April, 1:38 in May. Every change now records where it was tested, and the risk score counts “staging only” as 2, not 1.

  1. List how staging differs from production

    Every difference is a blind spot.

  2. Build staging from the same code

    Smaller, not different.

  3. Use masked real data

    Edge cases live in real data.

  4. Name what only production can test

    Failover, vendors, real load.

  5. Test those carefully in production

    Quiet hour, announced, watcher, way back.

  6. Record where each change was tested

    And let the risk score use it.

6Common pitfalls the usual ways this goes wrong

  • Trusting a pass in a different place

    Staging lacks the part that fails. Fix → list the differences; test those in production.

  • Staging by hand

    It drifts within weeks. Fix → build it from the same code.

  • Production tests without care

    A test becomes an incident. Fix → quiet hour, announced, watcher, way back.

  • Fake data only

    Edge cases never appear. Fix → masked real data.

7When to use it (and when not)

Use it when…

  • A test passed and production still failed.
  • Staging was built by hand.
  • You promise a recovery time (failover, restore).
  • Vendors behave differently from their sandboxes.

Skip it when…

  • Simple, flagged code changes: a canary tests them in production anyway.

8Self-check quiz

Why did the failover pass in staging and fail in production?

Staging had no replica, so its “failover” was a restart; it couldn't show Dispatch caching the address.

How should staging be built?

From the same infrastructure code as production, smaller, with masked real data.

What can only be tested in production?

Things like failover, real vendor behaviour and real load.

What makes a production test careful?

A quiet hour, an announcement, a watcher and a way back.

What were the monthly failover times after the fix?

About 1 minute 40, under the 2-minute target.

what would you do?A vendor's sandbox accepts every test payment, but production payments sometimes fail. How do you test the change?

In production, carefully: a small real payment at a quiet hour, announced, with a watcher, or a canary to a small share of customers. The sandbox can't show real behaviour.

try it

Write down every way your staging differs from production. For the top three, decide: make staging match, or test that part in production with a quiet hour, an announcement, a watcher and a way back.

remember!!

A test is only as honest as the place it runs. Build staging like production, and test the rest in production, carefully.
