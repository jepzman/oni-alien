Patching Without Fear

TL;DR

Patching by hand is toil that never ends and stops when the person is away. Split it by size. Small security updates install automatically, one machine at a time, at night. Bigger updates go in a monthly window. Critical vulnerabilities are fixed within a set time (72 hours). Where you can, rebuild machines from code instead of repairing them: a fresh, patched machine is simpler to trust than a five-year-old one.

1The situation Larder, March 2027

Since 2025, Eli's Monday mornings have gone on patching Larder Core's three VMs by hand, one at a time: about five hours a week, still the biggest line in his toil log. When he's on holiday, nobody patches. In March a critical fix for the operating system's SSL library comes out on a Thursday. The VMs get it the following Tuesday, five days later, because Monday was full.

  • Security depends on one person's Mondays.
  • Every VM is patched slightly differently over time.
  • Critical fixes wait in the same queue as routine ones.

2Real-life analogy the van fleet's servicing

A delivery company checks small things automatically every morning, like tyre pressure. Bigger services happen on a fixed day each month, one van at a time, so deliveries never stop. And an old van isn't patched forever: it's replaced with a new one built to the same spec.

3How it solves it nightly, monthly, critical in 72 h, and rebuild instead of repair

Bram and Eli set up the routine in April:

  • Nightly: security updates install automatically on the Core VMs, one VM at a time between 02:00 and 04:00, with a reboot if needed. Core keeps serving from the other two (any two of three is enough).
  • Monthly: bigger updates (kernel, database minor versions) on the first Tuesday at 10:00, as normal changes, never in a window.
  • Critical: anything scored 9 or more is fixed within 72 hours, as an emergency or normal change depending on exposure.
  • Containers: Dispatch's images are scanned weekly and rebuilt from fresh base images.
  • Rebuild, don't repair: in June the three VMs are rebuilt from infrastructure code on Ubuntu 24.04, one at a time (this volume, end-of-life).

Patching drops from 5 hours a week to about 30 minutes of reading the reports. During Eli's holiday in July, the VMs are patched every night without him. The March SSL fix would now take one night.

  1. Split patches by size

    Small automatic, bigger in a window, critical with a deadline.

  2. Automate the small, one machine at a time

    At night; keep the service up on the others.

  3. Set a monthly window for the rest

    Outside critical windows, as normal changes.

  4. Set a deadline for critical fixes

    72 hours is common; write it down.

  5. Scan images and rebuild them

    Fresh base images, weekly.

  6. Rebuild machines from code

    Replace, don't repair, when you can.

Vocabulary for the exam

Patch
An update that fixes a bug or a security hole.
Vulnerability
A weakness that could be exploited; often scored 0–10 (CVSS).
Unattended upgrades
Updates that install automatically without a person.
Rolling update
Updating one machine at a time so the service stays up.
Immutable infrastructure
Replacing machines with fresh ones instead of changing them.
Image scanning
Checking container images for known vulnerabilities.

6Common pitfalls the usual ways this goes wrong

  • Patching all machines at once

    A bad patch takes everything down. Fix → one at a time, with the service up on the others.

  • No deadline for critical fixes

    They wait in the routine queue. Fix → 72 hours, written down.

  • Repairing old machines forever

    Each one drifts and nobody knows how it was built. Fix → rebuild from code.

  • Patching without watching

    Failures go unnoticed. Fix → post results; alert on failures.

7When to use it (and when not)

Use it when…

  • Patching is manual and depends on one person.
  • Critical fixes take days.
  • Machines drift apart.
  • Auditors or clients ask how fast you patch.

Skip it when…

  • Fully managed services that patch themselves: check their reports instead.

8Self-check quiz

How are small security updates handled now?

Automatically, every night, one VM at a time between 02:00 and 04:00.

What's the deadline for a critical vulnerability?

72 hours.

Why one VM at a time?

Core keeps serving from the other two; a bad patch only affects one.

What does “rebuild, don't repair” mean?

Replace machines with fresh ones built from code, instead of changing old ones over years.

What happened to patching toil?

5 hours a week → about 30 minutes reading reports.

what would you do?A critical vulnerability (score 9.8) in the web server is announced on Friday at 16:00 and Core is exposed to the internet. What happens?

It's within the 72-hour rule, and exposed: an emergency change. Apply the fix or a mitigation before 17:00 if possible (the window starts then), otherwise with the incident lead's approval, one VM at a time, and watch.

try it

List every machine and image you run with how it's patched and how long the last critical fix took. Pick one thing to automate this month: nightly updates, a rolling reboot, or an image scan.

remember!!

Small patches every night, automatically, big ones monthly, critical ones in 72 hours. And when you can, rebuild, don't repair.
