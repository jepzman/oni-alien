How Do We Undo It?

TL;DR

Every change needs a way back, written down before it's made: how, how long, and tested where. For code, that's usually a flag or a redeploy. But data, events, messages and vendor changes don't roll back with the code, so those need a way forward: expand and contract, a backup taken just before, a replay. The few changes with no way back need a practised restore, a planned time and someone watching.

1The situation Larder, 14–16 April 2027

On Wednesday 14 April, two days after Utrecht opens, a deploy renames the field store to store_id in the order.placed event. It looks harmless: the team's own consumers are updated. Billing, one of nine consumers, quietly stops creating invoice lines. On Friday the 16th someone notices. Rolling back the deploy stops new damage, but two days of events have already gone out in the new shape, and undoing the code can't undo them.

  • “We can always roll back” was assumed, not checked.
  • Data and events outlive the deploy that made them.
  • Nobody had written down what the way back was.

2Real-life analogy the tailor's pins and the cut

A tailor shortening trousers pins and tacks first, and that undoes in a minute. The cut doesn't undo. So before cutting he measures twice, keeps the offcut, and knows how he'd let the hem down with a false hem if he had to. Some steps undo and some only go forward, and he plans for both kinds before he starts.

3How it solves it undo, way forward, or a practised restore, written before the change

The fix for 14 April is forward, not back. Ben publishes both fields for a while (expand), the two days of events are replayed to billing, and 312 invoice lines are restored by 20 April. Ana's ADR 0020 (19 April) then makes events change only compatibly, through expand and contract.

From 26 April every normal change states its way back, how long it takes, and where it was tested:

  • Undo: flag off, or redeploy the previous version. Fine for most code.
  • Way forward: when the change touches data, events, messages or a vendor. Expand and contract for schemas, a backup taken just before, a replay, a script to repair.
  • No way back: rare. It needs a practised restore, a planned time and a watcher. The Postgres upgrade in May is the first (this volume).

The reviewer's job includes one question: has the way back been tried, or only imagined?

  1. Write the way back before the change

    How, how long, tested where.

  2. Ask what doesn't roll back

    Data, events, messages, vendors, emails sent.

  3. Plan forward for those

    Expand and contract, backup, replay, repair script.

  4. Test the way back too

    Where the change was tested.

  5. For no-way-back changes, practise the restore

    Planned time, watcher.

  6. Review what happened when it was used

    Did it work as written?

Vocabulary for the exam

Rollback
Returning to the previous version of code or configuration.
Roll forward
Fixing a problem with a new change instead of undoing the old one.
Back-out plan
The written steps to undo a change.
Expand and contract
Add the new shape alongside the old, move everyone, then remove the old.
Replay
Re-sending events or messages to rebuild what a consumer missed.
One-way door
A change that can't easily be undone (Ana's term).

4The maturity ladder where are we, and what is the next rung?

1By hand

“we can always roll back”

  • Assumed.
  • Data and events forgotten.

2Written down Larder now

the way back written and tested

  • Undo, way forward or practised restore.
  • Checked by the reviewer.

3Scripted

undo built in

  • Expand and contract by default.
  • Replays and backups one command.

4Automatic

automatic undo

  • Canary signals trigger rollback by themselves.
  • One-way doors rare and known.

6Common pitfalls the usual ways this goes wrong

  • Assuming rollback works

    It was never tried. Fix → test the way back where the change was tested.

  • Forgetting data and events

    The code rolls back; the data doesn't. Fix → ask what doesn't roll back.

  • Renaming in one step

    Every consumer breaks at once. Fix → expand and contract.

  • Backups nobody restored

    The way back fails when it's needed. Fix → practise the restore (vol. 5).

7When to use it (and when not)

Use it when…

  • Every normal change.
  • Changes to schemas, events or vendor settings.
  • Upgrades of databases or platforms.
  • After a rollback that didn't fix things.

Skip it when…

  • Standard changes whose recipe already includes the undo.

8Self-check quiz

Why couldn't the 14 April deploy simply be rolled back?

Two days of events had already gone out in the new shape; undoing the code couldn't undo them.

What are the three kinds of way back?

Undo (flag, redeploy), way forward (expand and contract, backup, replay), and a practised restore for no-way-back changes.

What usually doesn't roll back with code?

Data, published events, messages and emails sent, vendor settings, payments, installed device updates.

What is expand and contract?

Add the new shape alongside the old, move every consumer, then remove the old.

What does the reviewer ask about the way back?

Has it been tried, or only imagined?

what would you do?A change adds a required column to the orders table. The author writes “way back: redeploy previous version”. What do you ask?

Will the old version still work with the new column, and what about rows written in between? Probably add it as optional first (expand), then make it required later (contract), with a backup before.

try it

Take your next three changes and write their way back: how, how long, tested where. For each, list anything that won't roll back with the code. Which one needs a way forward instead?

remember!!

The code rolls back; data and events don't. Write the way back before the change, and try it, don't imagine it.
