Soft Delete

TL;DR

Instead of DELETE, set deleted_at = now(). Normal reads filter deleted rows out (ideally through a view or a default scope), a restore clears the stamp, and a purge job hard-deletes rows once the undo window has passed, which also keeps you honest about privacy laws.

  • Family: data lifecycle
  • Column: deleted_at timestamptz
  • Variants: archive table, status column
  • Pairs with: history tables, partial indexes

1The problem why do we even need this?

Hard deletes are instant and permanent. Users make mistakes, support needs to see what happened, and other rows still point at the one you removed.

  • “I deleted it by accident” has no answer except restoring a backup.
  • Foreign keys either block the delete or cascade and wipe related data too.
  • Reports for last month change because their rows vanished.

2Real-life analogy the recycle bin

On your computer, “delete” moves a file to the recycle bin. It's out of sight, but one click brings it back. The bin is emptied after 30 days, and only then is the file truly gone.

  • Moving to the bin is setting deleted_at.
  • The desktop not showing binned files is your filtered view.
  • Emptying the bin is the purge job, and you need one.

3How it solves it a stamp, a filter and a purge

Soft delete is three small pieces. The column is easy; the filter everywhere and the purge are what make it safe.

  1. Add the column

    deleted_at timestamptz NULL (a timestamp tells you when, which a boolean can't).

  2. Read through a filter

    A view like active_projects, a row-level policy, or an ORM default scope, so nobody forgets the WHERE.

  3. Fix uniqueness

    Use a partial unique index so a deleted slug can be reused: UNIQUE (slug) WHERE deleted_at IS NULL.

  4. Decide what cascades

    Soft-deleting a project may soft-delete its tasks too; write that rule down.

  5. Purge on a schedule

    Hard-delete rows older than the undo window, and anything a user asked to be erased.

Vocabulary for the exam

Hard delete
Physically removing the row with DELETE.
Soft delete
Marking a row deleted but keeping it.
Tombstone
A marker that says “this was deleted”.
Partial index
An index over only the rows that match a WHERE.
Purge
The real delete that happens later.
Right to erasure
GDPR rule: personal data must really go when asked.
soft_delete.sqlPostgreSQL
ALTER TABLE projects ADD COLUMN deleted_at timestamptz;

-- slugs only need to be unique among live rows
CREATE UNIQUE INDEX projects_slug_live
  ON projects (slug) WHERE deleted_at IS NULL;

CREATE VIEW active_projects AS
  SELECT * FROM projects WHERE deleted_at IS NULL;

-- "delete" and "undo"
UPDATE projects SET deleted_at = now() WHERE id = 42;
UPDATE projects SET deleted_at = NULL  WHERE id = 42;

-- nightly purge: the bin really gets emptied
DELETE FROM projects WHERE deleted_at < now() - interval '30 days';

tools: Rails discard/paranoia, Laravel SoftDeletes, Django django-safedelete, Prisma middleware, Hibernate @SoftDelete. PostgreSQL row-level security can hide deleted rows for every query.

4Gains vs losses nothing is free

What we gain

  • Undo for users and support.
  • Related rows stay valid; no surprise cascades.
  • Audit and reports keep their history.
  • Cheap deletes: one small UPDATE.

What we lose

  • Every query must filter, or deleted data leaks.
  • Unique constraints get tricky (partial indexes needed).
  • Tables keep growing until you purge.
  • Privacy risk: “deleted” personal data that isn't.

6Common pitfalls the usual ways this goes wrong

  • Forgetting the filter

    A new report counts deleted orders as real. Fix → read through a view, a default scope or row-level security.

  • A boolean is_deleted

    You know it's deleted, not when, so you can't purge after 30 days. Fix → use deleted_at (and maybe deleted_by).

  • Never purging

    “Deleted” personal data lives forever and breaks GDPR. Fix → schedule a purge and honour erasure requests with a real DELETE.

  • Plain UNIQUE constraints

    A user can't recreate the slug they deleted yesterday. Fix → partial unique index on live rows only.

7When to use it (and when not)

Use it when…

  • Users can delete things they may want back (projects, posts, files).
  • Rows are referenced by history you need to keep (orders, invoices).
  • Support needs to see what was deleted and when.

Skip it when…

  • High-churn data like sessions, carts or caches.
  • Personal data that must be erased on request (purge for real).
  • You need full history anyway, so use history tables instead.

8Self-check quiz

Why is deleted_at better than is_deleted?

It records when the row was deleted, which you need for undo windows, purge jobs and audits.

How do you stop deleted rows from appearing in reads?

Read through a filtered view, an ORM default scope or a row-level security policy.

What breaks with a normal UNIQUE (slug)?

Deleted rows still hold the slug, so it can't be reused; use a partial unique index WHERE deleted_at IS NULL.

Does soft delete satisfy “delete my data”?

No. Personal data must be really erased (or anonymised), so a purge with a hard DELETE is still needed.
