Optimistic Locking

TL;DR

Give each row a version number. When you save, say UPDATE … SET version = version + 1 WHERE id = ? AND version = ? with the version you read. If 0 rows match, someone else changed it first: reload, merge or retry instead of silently overwriting. No locks are held while the user thinks.

  • Family: concurrency control
  • Opposite: pessimistic locking (SELECT … FOR UPDATE)
  • HTTP cousin: ETag + If-Match
  • Pairs with: idempotent consumer, history tables

1The problem why do we even need this?

Read, edit, save. When two people (or two requests) do it on the same row at once, the second save silently wipes out the first. This is the lost update, and nothing errors.

  • Two admins edit a product; one price change disappears.
  • Two requests add to a counter; one increment vanishes.
  • Locking the row while the user edits for ten minutes blocks everyone else.

2Real-life analogy the version stamp

Imagine checking out a copy of a shared document stamped v3. When you hand it back, the librarian looks at the master. Still v3? Your changes go in, and the master becomes v4. Already v4? Someone got there first, so you're asked to merge before trying again.

  • Nobody is blocked while you work: it's optimistic that conflicts are rare.
  • The stamp check happens in one step at hand-in: a conditional UPDATE.

3How it solves it a conditional update

The check and the write are one atomic statement, so there's no gap for another writer to sneak in. The database does the hard part.

  1. Add a version column

    version int NOT NULL DEFAULT 0 (or use updated_at, or PostgreSQL's xmin).

  2. Send it to the client

    Include it in the form or as an HTTP ETag.

  3. Update conditionally

    … WHERE id = $1 AND version = $2, bumping the version.

  4. Check the row count

    1 = saved. 0 = conflict: return HTTP 409 / 412 with the latest data.

  5. Decide the conflict policy

    Show a merge screen, retry automatically (for counters), or let the user choose.

Vocabulary for the exam

Lost update
A write that overwrites another without noticing.
Optimistic locking
Detect conflicts at write time; no locks held.
Pessimistic locking
Lock the row first (SELECT … FOR UPDATE).
Version column
A counter bumped on every write.
Compare-and-set
Write only if the value is still what you saw.
ETag / If-Match
HTTP headers for the same idea.
save_page.tsnode-postgres
// the client sends back the version it loaded
async function savePage(id: number, body: string, version: number) {
  const r = await db.query(
    `UPDATE pages SET body = $1, version = version + 1, updated_at = now()
     WHERE id = $2 AND version = $3
     RETURNING version`,
    [body, id, version],
  );
  if (r.rowCount === 0) {
    const latest = await db.query("SELECT * FROM pages WHERE id = $1", [id]);
    throw new Conflict(409, latest.rows[0]);   // UI shows a merge screen
  }
  return r.rows[0].version;                    // the new version for next time
}

// simple counters don't need versions: let the database do the maths
// UPDATE stock SET qty = qty - 1 WHERE sku = $1 AND qty > 0

4Gains vs losses nothing is free

What we gain

  • No lost updates: conflicts are detected, not hidden.
  • No locks held while users think.
  • Scales well when conflicts are rare.
  • Works across HTTP with ETags.

What we lose

  • Conflicts must be handled in the UI or with retries.
  • Wasted work when conflicts are frequent.
  • Every write path must check the version.
  • One more column on each table.

6Common pitfalls the usual ways this goes wrong

  • Checking, then writing

    SELECT the version, compare in code, then UPDATE: another write sneaks in between. Fix → put the check in the UPDATE's WHERE clause.

  • Ignoring the row count

    The UPDATE matched 0 rows and the app said “Saved!”. Fix → treat 0 rows as a conflict, every time.

  • Optimistic under heavy contention

    A hot counter retries forever. Fix → use atomic SQL (qty = qty - 1) or a pessimistic lock.

  • Bypass paths

    Admin scripts update rows without bumping the version. Fix → bump it in a trigger, or in every write path.

7When to use it (and when not)

Use it when…

  • Forms and editors where people edit the same records.
  • APIs where clients read, change and write back.
  • Low-to-medium contention on any given row.

Skip it when…

  • Hot rows updated many times per second (use atomic SQL or a queue).
  • Insert-only data that's never updated.
  • Short transactions where SELECT … FOR UPDATE is simpler.

8Self-check quiz

What is a lost update?

Two read-modify-write cycles overlap and the second save overwrites the first without any error.

Why put the version check in the WHERE clause?

Check and write happen atomically; there's no gap where another writer can change the row.

What should the API return on a conflict?

An error like HTTP 409 or 412 with the latest data so the client can merge or retry.

When is pessimistic locking better?

When contention is high and retries would waste lots of work, for short transactions.
