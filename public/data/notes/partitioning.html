Table Partitioning

TL;DR

Split one huge table into partitions, smaller tables behind one name, by a key you always filter on (usually time, sometimes tenant or region). Queries touch only the partitions they need (pruning), maintenance runs per partition, and old data is removed by dropping a partition in a second instead of a giant DELETE. All inside one database.

  • Family: scaling data
  • Kinds: range, list, hash
  • Built in: PostgreSQL 10+, MySQL, SQL Server, Oracle
  • Not the same as: sharding (many databases)

1The problem why do we even need this?

Append-heavy tables like events, logs, orders and metrics grow forever. At billions of rows, everything gets heavy, even the queries that only want last week.

  • Indexes no longer fit in memory, so “recent” queries slow down too.
  • VACUUM, reindexing and backups take days.
  • Deleting old data with DELETE is slow, bloats the table and floods replicas.

2Real-life analogy the filing cabinet

An office files receipts in a cabinet with one drawer per year. Looking for March 2026? Open the 2026 drawer only. Time to throw away 2019? Pull out the whole drawer and empty it, without sorting through the others.

  • Each drawer is a partition.
  • “Look only in 2026” is partition pruning.
  • Emptying a drawer is DROP / DETACH PARTITION.

3How it solves it one name, many smaller tables

The app still queries events. The database routes rows to the right partition on insert, and skips partitions that can't match the WHERE clause on read.

  1. Pick the key you always filter on

    Usually time (created_at); queries without it must check every partition.

  2. Pick the size

    Partitions of roughly 10–100 GB, or one per month; hundreds is fine, tens of thousands isn't.

  3. Create partitions ahead of time

    A job (or pg_partman) creates next month's partition before rows arrive; add a DEFAULT partition as a safety net.

  4. Index per partition

    Indexes on the parent are created on every partition and stay small.

  5. Retire old data by dropping

    DETACH PARTITION … CONCURRENTLY, archive it, then drop.

Vocabulary for the exam

Partition
One piece of a partitioned table.
Partition key
Column(s) deciding which partition a row goes to.
Range / list / hash
Split by ranges, by listed values, or by a hash.
Partition pruning
Skipping partitions that can't match the query.
Detach
Turning a partition back into a standalone table.
Sharding
Partitioning across separate database servers.
events.sqlPostgreSQL 14+
CREATE TABLE events (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  account_id bigint NOT NULL,
  kind       text   NOT NULL,
  at         timestamptz NOT NULL,
  PRIMARY KEY (id, at)                 -- the key must include the partition column
) PARTITION BY RANGE (at);

CREATE TABLE events_2026_11 PARTITION OF events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;

CREATE INDEX ON events (account_id, at);   -- created on every partition

-- only events_2026_11 is scanned (see "Partitions removed" in EXPLAIN)
SELECT count(*) FROM events WHERE at > now() - interval '7 days';

-- retention: seconds, not hours
ALTER TABLE events DETACH PARTITION events_2025_10 CONCURRENTLY;
DROP TABLE events_2025_10;

tools: PostgreSQL declarative partitioning + pg_partman, TimescaleDB hypertables (automatic time partitions), MySQL partitioning, SQL Server partition schemes, BigQuery/Snowflake partitioned and clustered tables, Citus for partitioning across servers.

4Gains vs losses nothing is free

What we gain

  • Fast recent queries thanks to pruning and small indexes.
  • Instant retention: drop a partition, not 400M rows.
  • Maintenance per partition: vacuum, reindex, archive.
  • Cold partitions can move to cheaper storage.

What we lose

  • Queries without the key scan every partition.
  • Unique keys must include the partition column.
  • Partitions must be created ahead of time.
  • More objects to manage and monitor.

6Common pitfalls the usual ways this goes wrong

  • Partitioning by a column you don't filter on

    Every query scans all 60 partitions. Fix → partition by the column in almost every WHERE.

  • Too many tiny partitions

    Daily partitions for 10 years: planning gets slow. Fix → aim for fewer, bigger partitions.

  • Forgetting to create next month

    Inserts fail at midnight on the 1st. Fix → automate with pg_partman; keep a DEFAULT partition and alert on it.

  • Expecting it to scale writes

    One server still takes all writes. Fix → for more write capacity, shard across servers (Vol. 1).

7When to use it (and when not)

Use it when…

  • Time-series, events, logs, metrics, audit and history tables.
  • Data with a retention policy (keep 13 months).
  • Tables past ~100 GB where most queries hit a recent slice.

Skip it when…

  • Tables that fit comfortably in memory.
  • Queries that rarely filter on any one column.
  • When you need more write throughput than one server (shard instead).

8Self-check quiz

What is partition pruning?

The planner skipping partitions that can't contain rows matching the WHERE clause.

Why is dropping a partition better than DELETE for retention?

It removes a whole table instantly, with no row-by-row delete, bloat or vacuum.

How is partitioning different from sharding?

Partitioning splits a table within one database server; sharding spreads data across several servers.

Why must the primary key include the partition column (in PostgreSQL)?

Uniqueness is enforced per partition, so the key must determine the partition to be globally unique.
