Upserts

TL;DR

When you don't know whether a row exists yet (imports, syncs, counters, “save settings”), don't check first and then write: two writers will both see “not there”. Put a unique constraint on the natural key and use one atomic statement: INSERT … ON CONFLICT … DO UPDATE (PostgreSQL, SQLite), MERGE (SQL standard) or ON DUPLICATE KEY UPDATE (MySQL). Add a condition so old data never overwrites newer data.

  • Family: writing safely
  • Needs: a unique constraint on the key
  • Also called: merge, insert-or-update
  • Pairs with: idempotent consumer, change data capture

1The problem why do we even need this?

A nightly job imports 10,000 prices. For each one it asks “does this SKU exist?”, then inserts or updates. With two workers, both ask about SKU 812 at the same moment, both hear “no”, both insert, and one crashes with a duplicate-key error halfway through.

  • Check-then-write races: the gap between the SELECT and the INSERT is where the second writer gets in.
  • Without a unique constraint, the race doesn't crash: it silently creates two rows for one SKU.
  • Retried messages and re-run imports must not create duplicates or fail on rows they already wrote.

2Real-life analogy the hotel front desk

At a hotel desk you give your booking reference. If there's a booking, the clerk changes the dates; if not, the clerk makes one. Both happen at the desk, in one step, and the reference is unique, so two clerks can't create two bookings for it.

3How it solves it one statement, decided by the unique key

The database tries the insert. If it would break the unique constraint, it updates the existing row instead. Both halves happen under the same row lock, so there's no gap for another writer. The rows that were proposed are available as EXCLUDED (PostgreSQL) or source (MERGE).

  1. Pick the natural key

    What makes a row “the same row”: the SKU, the email, the partner's id, (user_id, setting).

  2. Make it unique

    A UNIQUE constraint or index on exactly those columns. Without it, there is nothing to conflict on.

  3. Write one statement

    INSERT … ON CONFLICT (sku) DO UPDATE SET …, or MERGE, or MySQL's ON DUPLICATE KEY UPDATE.

  4. Guard the update

    Skip it when nothing changed (IS DISTINCT FROM) or when the incoming row is older.

  5. Batch it

    Upsert hundreds of rows per statement with a multi-row VALUES list or UNNEST; it's far faster than one round trip per row.

Vocabulary for the exam

Upsert
Insert a row, or update it if its key already exists.
Natural key
The real-world value that identifies a row (SKU, email).
ON CONFLICT
PostgreSQL and SQLite's upsert clause.
MERGE
The SQL standard statement for insert / update / delete by match.
EXCLUDED
The row you tried to insert, inside DO UPDATE.
Race condition
A bug that depends on two operations interleaving.
import_prices.sqlPostgreSQL 15+
-- the natural key must be unique, or there is nothing to conflict on
ALTER TABLE products ADD CONSTRAINT products_sku_key UNIQUE (sku);

-- one statement for a whole batch: insert new SKUs, update known ones
INSERT INTO products (sku, price_cents, updated_at)
SELECT * FROM unnest($1::text[], $2::int[], $3::timestamptz[])
ON CONFLICT (sku) DO UPDATE
   SET price_cents = EXCLUDED.price_cents,
       updated_at  = EXCLUDED.updated_at
 WHERE products.updated_at < EXCLUDED.updated_at          -- never let old data win
   AND products.price_cents IS DISTINCT FROM EXCLUDED.price_cents;

-- the standard spelling (PostgreSQL 15+, SQL Server, Oracle)
MERGE INTO products p
USING staging_prices s ON p.sku = s.sku
WHEN MATCHED AND s.updated_at > p.updated_at THEN
  UPDATE SET price_cents = s.price_cents, updated_at = s.updated_at
WHEN NOT MATCHED THEN
  INSERT (sku, price_cents, updated_at) VALUES (s.sku, s.price_cents, s.updated_at);

tools: PostgreSQL ON CONFLICT and MERGE, SQLite ON CONFLICT, MySQL ON DUPLICATE KEY UPDATE, SQL Server / Oracle MERGE, ORMs: Prisma upsert, Django update_or_create and bulk_create(update_conflicts=True), Rails upsert_all.

4Gains vs losses nothing is free

What we gain

  • No races: the check and the write are one atomic step.
  • Safe to re-run: imports and retried messages don't duplicate rows.
  • Fast in batches: one statement for hundreds of rows.
  • Simpler code: no “does it exist?” branch.

What we lose

  • Needs a unique key, which some legacy tables don't have.
  • Dialects differ: ON CONFLICT, MERGE and MySQL's syntax aren't interchangeable.
  • Easy to overwrite newer data without a guard.
  • Hidden work: triggers, sequences and row locks still fire on the conflict path.

6Common pitfalls the usual ways this goes wrong

  • No unique constraint

    ON CONFLICT has nothing to conflict on, so every run inserts new rows. Fix → add the UNIQUE constraint first, and clean up existing duplicates.

  • Old data wins

    A delayed retry with yesterday's price overwrites today's. Fix → guard the update with a version or timestamp comparison.

  • DO NOTHING hides problems

    Conflicting rows are skipped silently, including ones that should have updated. Fix → use DO NOTHING only when the existing row is always right; count what was skipped.

  • MERGE assumed to be race-free

    On some databases (SQL Server) MERGE can still race without a lock hint. Fix → read your database's notes; add HOLDLOCK / SERIALIZABLE where advised, or use ON CONFLICT.

7When to use it (and when not)

Use it when…

  • Imports and syncs from another system.
  • Consumers that may receive the same message twice.
  • Settings and preferences: one row per user and key.
  • Counters and aggregates keyed by day or by item.

Skip it when…

  • The key isn't really unique in your domain (two people can share an email).
  • Creating and updating need different rules or permissions; keep them separate.
  • You need to know which happened and act differently; use RETURNING (xmax) or two explicit paths.

8Self-check quiz

Why does “SELECT, then INSERT” fail under concurrency?

Two writers can both run the SELECT before either inserts; both see “not there” and both try to insert.

What does ON CONFLICT need in order to work?

A unique constraint or unique index on the columns you name; that's what defines a conflict.

What is EXCLUDED?

The row you tried to insert, available inside DO UPDATE so you can copy its values.

How do you stop a late, older message from overwriting newer data?

Add a WHERE to the update that compares a version or timestamp: update only if the incoming row is newer.

what would you do?A partner sends product updates as webhooks, sometimes twice and sometimes out of order. Your handler does SELECT, then INSERT or UPDATE, and you see duplicate products and prices going backwards. What do you change?

Add a unique constraint on the partner's product id, replace the handler's branch with one upsert, and guard the update with the partner's updated_at (or a version), so duplicates collapse and older messages can't overwrite newer ones.

try it

Write an import that does SELECT then INSERT, and run two copies at once against the same 1,000 rows. Count the duplicate-key errors (or the duplicate rows, if there's no unique constraint). Replace it with INSERT … ON CONFLICT DO UPDATE on a unique key, run both copies again, and then re-run the whole import to check it changes nothing.

remember!!

One unique key, one statement. And never let old data win.
