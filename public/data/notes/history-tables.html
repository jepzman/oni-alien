History Tables (Audit Trail)

TL;DR

Keep the main table for the current state, and file every old version of a row in a history table with valid_from, valid_to and who changed it, usually via a trigger or built-in system-versioned (temporal) tables. Then “what was it on that day, and who changed it?” is a query, not an argument.

  • Family: data lifecycle / auditing
  • Standard: SQL:2011 system-versioned tables
  • Built in: SQL Server, MariaDB, Db2, Oracle Flashback
  • Pairs with: soft delete, change data capture

1The problem why do we even need this?

An UPDATE overwrites the past. That's fine for a typo, but terrible for prices, permissions, salaries or contracts, where someone will eventually ask what the value was.

  • A customer disputes a charge, and you can't prove last week's price.
  • An admin role appeared on an account, and nobody knows who granted it.
  • Reports for last quarter change every time the data is corrected.

2Real-life analogy the medical chart

A doctor never rubs out an old reading. Each visit adds a new dated line. The chart shows today's numbers at the bottom, and the whole story above it.

  • The bottom line is the current row.
  • Every line above is a history row with a date range.
  • The doctor's signature is changed_by.

3How it solves it current table + versioned copies

Each change closes the old version's time range and opens a new one. Then any point in time maps to exactly one version.

  1. Create the history table

    Same columns as the main table, plus valid_from, valid_to, changed_by and the operation.

  2. Capture every change

    A trigger on UPDATE and DELETE copies the old row; or use built-in system versioning.

  3. Record who

    Pass the app user to the database (for example SET LOCAL app.user = 'ana') so the trigger can store it.

  4. Query by time

    WHERE valid_from <= :t AND :t < valid_to, or FOR SYSTEM_TIME AS OF where supported.

  5. Plan retention

    History grows forever; partition it by month and archive or drop what you no longer need.

Vocabulary for the exam

Audit trail
A record of who changed what and when.
System time
When the database stored the change.
Valid (business) time
When the fact was true in the real world.
Bitemporal
Tracking both system time and valid time.
Temporal table
A table the database versions for you.
Insert-only
Rows are added, never updated or deleted.
history.sqlPostgreSQL trigger
CREATE TABLE products_history (
  LIKE products,
  valid_from  timestamptz NOT NULL,
  valid_to    timestamptz NOT NULL DEFAULT now(),
  changed_by  text,
  op          text NOT NULL
);

CREATE FUNCTION keep_history() RETURNS trigger AS $$
BEGIN
  INSERT INTO products_history
  SELECT OLD.*, OLD.updated_at, now(),            -- products has updated_at
         current_setting('app.user', true), TG_OP;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER products_history AFTER UPDATE OR DELETE ON products
  FOR EACH ROW EXECUTE FUNCTION keep_history();

-- what did the lamp cost on 4 Nov?
SELECT price FROM products_history
WHERE id = 7 AND valid_from <= '2026-11-04' AND '2026-11-04' < valid_to;

tools: SQL Server and MariaDB system-versioned tables, Oracle Flashback, PostgreSQL temporal_tables extension or triggers, Django simple-history, Rails paper_trail, Hibernate Envers. Change data capture (note 11) can feed a history store too.

4Gains vs losses nothing is free

What we gain

  • Answer “what was it then?” for any date.
  • Who changed what: real audit trails.
  • Reproducible reports for past periods.
  • Undo by copying an old version back.

What we lose

  • Every write does extra work (the trigger).
  • Storage grows with every change.
  • Schema changes must be applied to both tables.
  • Time-range queries are trickier to write.

6Common pitfalls the usual ways this goes wrong

  • History in the app only

    Some code paths (scripts, admin SQL) skip it. Fix → capture in the database (trigger or system versioning).

  • No “who”

    You know it changed, but not by whom. Fix → pass the app user into the session and store it.

  • Forgetting schema changes

    A new column exists in products but not in history, so the trigger fails. Fix → migrate both tables together; test the trigger in CI.

  • Unbounded growth

    A hot table makes history 50× bigger than the data. Fix → partition history by month; archive old partitions.

7When to use it (and when not)

Use it when…

  • Prices, permissions, contracts, salaries, medical or financial data.
  • Auditors or regulators ask “who changed this?”
  • You need reports “as of” a past date.

Skip it when…

  • Write-heavy, low-value data (sessions, counters, caches).
  • Data that's already insert-only (events, logs).
  • You're already using event sourcing for that data.

Related patterns

8Self-check quiz

Why put history capture in a trigger rather than the app?

Every write path, including scripts and admin SQL, then records history; the app can't forget.

How do you find the value at time t?

Pick the version where valid_from ≤ t < valid_to (or use FOR SYSTEM_TIME AS OF).

What's the difference between system time and valid time?

System time is when the database recorded it; valid time is when it was true in the real world. Tracking both is bitemporal.

How do you stop history from growing forever?

Partition it by time and archive or drop partitions past the retention period.
