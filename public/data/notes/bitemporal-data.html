Bitemporal Data

TL;DR

A history table answers “what was the value on that day?”. Some questions need more: “what did we believe on 5 March about the price on 1 March?” Bitemporal rows carry two time ranges: valid time (when the fact was true in the world) and recorded time (when the database held that belief). A correction never updates in place: it closes the old row's recorded range and adds a new row, so every past report can be reproduced exactly.

  • Family: modelling time
  • Builds on: history tables (one time axis)
  • Standard: SQL:2011 application-time and system-versioned tables
  • Pairs with: event sourcing, audit logging

1The problem why do we even need this?

An invoice on 5 March used a price of €10 valid from 1 March. On 20 March someone finds the price was really €12 and fixes the row. Correct, and now nobody can explain the invoice: the database says the 1 March price was €12, and the €10 it believed at the time is gone.

  • A plain history table keeps versions over time, but a back-dated correction rewrites what that time looked like.
  • Auditors, regulators and support ask “why did the system do that, on that day?” and need the data as it was known then.
  • Insurance, payroll, pricing and contracts change in the past all the time: retroactive raises, late claims, corrected rates.

2Real-life analogy a ship's logbook

A ship's log is never rubbed out. When the navigator finds on Thursday that Monday's position was wrong, they add a correction in red ink, dated Thursday, next to the Monday entry. You can now read two things: where the ship really was on Monday, and what the log said on any given day.

3How it solves it two time ranges per row

Each row says: this value applied for this period (valid time), and we held this belief for this period (recorded time). The database sets recorded time itself, from the transaction clock; people set valid time. A query fixes both: “price valid on 1 March, as recorded on 5 March”.

  1. Decide which facts need it

    Prices, rates, contracts, entitlements: facts that are corrected after they've been used. Most tables only need a history table.

  2. Add both ranges

    valid_period and recorded_period as ranges (or four timestamp columns), with “open” meaning until further notice.

  3. Forbid overlaps

    An exclusion constraint (or the database's temporal support) stops two current beliefs about the same moment.

  4. Correct by closing and inserting

    In one transaction: end the old row's recorded range now, insert the corrected row with recorded time from now.

  5. Query with both times

    “As known now” for normal screens; “as known on date X” to reproduce a past report or invoice.

Vocabulary for the exam

Valid time
When a fact was true in the real world (also: application or business time).
Recorded time
When the database held the fact (also: transaction or system time).
Bitemporal
Tracking both time axes on the same row.
As-of query
A query fixed to a past recorded time.
Retroactive change
A correction that applies to a period in the past.
Exclusion constraint
A PostgreSQL rule that stops overlapping ranges for the same key.
prices_bitemporal.sqlPostgreSQL ranges
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE prices (
  sku            text      NOT NULL,
  price_cents    int       NOT NULL,
  valid_period   daterange NOT NULL,                            -- when it applied
  recorded_period tstzrange NOT NULL DEFAULT tstzrange(now(), NULL),  -- when we believed it
  EXCLUDE USING gist (sku WITH =, valid_period WITH &&, recorded_period WITH &&)
);

-- correct the price for March, on 20 March: close the old belief, add the new one
BEGIN;
UPDATE prices SET recorded_period = tstzrange(lower(recorded_period), now())
 WHERE sku = '812' AND valid_period && '[2026-03-01,2026-04-01)' AND upper_inf(recorded_period);
INSERT INTO prices (sku, price_cents, valid_period) VALUES ('812', 1200, '[2026-03-01,2026-04-01)');
COMMIT;

-- what did we believe on 5 March about the price on 1 March?
SELECT price_cents FROM prices
 WHERE sku = '812' AND valid_period @> date '2026-03-01'
   AND recorded_period @> timestamptz '2026-03-05 12:00';

tools: PostgreSQL ranges + exclusion constraints (temporal_tables / periods extensions), SQL Server and MariaDB system-versioned tables (recorded time), IBM Db2 and Oracle bitemporal support, XTDB (bitemporal by design), Datomic (recorded time).

4Gains vs losses nothing is free

What we gain

  • Every past report can be reproduced, exactly as it was.
  • Corrections are safe: they never destroy what was believed.
  • Clear audit answers: what we knew, and when we knew it.
  • Retroactive changes (late raises, corrected rates) fit naturally.

What we lose

  • Harder queries: every read must pick both times.
  • More rows: every correction adds one.
  • Easy to get wrong by hand; constraints and helpers are a must.
  • Patchy database support for valid time.

6Common pitfalls the usual ways this goes wrong

  • Bitemporal everything

    Every table gets four timestamps and every query gets harder. Fix → use it only for facts that are corrected after they're used; keep history tables elsewhere.

  • Updating in place

    Someone “just fixes” a price with a plain UPDATE. Fix → allow changes only through a function or procedure, and revoke direct UPDATE.

  • Overlapping beliefs

    Two current rows claim different prices for the same day. Fix → an exclusion constraint on (key, valid range, recorded range).

  • App clock for recorded time

    Recorded time set by the app drifts or can be faked. Fix → let the database set it from the transaction time.

7When to use it (and when not)

Use it when…

  • Prices, rates, tariffs and contracts used in invoices.
  • Insurance, payroll and benefits, where changes are back-dated.
  • Regulated reporting that must be reproducible.
  • Any “why did the system decide that, then?” question.

Skip it when…

  • Facts are never corrected after use; a history table is enough.
  • You only need “who changed what, when”; use an audit log.
  • The team can't keep every query honest about both times.

8Self-check quiz

What is the difference between valid time and recorded time?

Valid time is when a fact was true in the world; recorded time is when the database held it as its belief.

Why can't a history table answer “what did we believe on 5 March”?

A back-dated correction rewrites the version for that period, so the earlier belief is lost.

How is a correction stored?

Close the old row's recorded range at now, and insert the corrected row with recorded time from now, in one transaction.

Who should set recorded time?

The database, from the transaction clock, so it can't drift or be faked.

what would you do?A customer disputes a March invoice. The rate table was corrected in April with a back-dated change, and support can't see the rate the invoice used. What should the table have been, and what do you do now?

Bitemporal: corrections close the old belief and add a new row, so “rate for March as known on the invoice date” stays answerable. Now: use backups or the audit log to reconstruct the old rate for this dispute, and convert the rate table so the next correction keeps both.

try it

Take a table of prices or rates you own. Add valid and recorded ranges in a copy (with the exclusion constraint above), load a few months of data, then make a back-dated correction. Write two queries: the current price for a past date, and the price for that date as known a week before the correction.

remember!!
