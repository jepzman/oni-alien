Star Schema

TL;DR

For analytics, shape data as a fact table of events with numbers (sales lines: quantity, amount) in the middle, surrounded by dimension tables that describe them (date, product, customer, store). Every report is “sum the facts, group by dimension columns”, a one-hop join that warehouses run very fast. Keep it in a separate analytics database, loaded from the app's data.

  • Family: analytics modelling
  • Origin: Ralph Kimball, dimensional modelling (1990s)
  • Lives in: Snowflake, BigQuery, Redshift, ClickHouse, DuckDB
  • Pairs with: change data capture, materialized views

1The problem why do we even need this?

The app's normalized schema is great for writing orders, and painful for asking questions. “Sales by category, by month, by country” becomes a twelve-table join, run on the same database that takes payments.

  • Every analyst rebuilds the same joins, slightly differently, with different answers.
  • Report queries scan huge tables and slow checkout down.
  • History is lost: when a product changes category, last year's report changes too.

2Real-life analogy receipts and labels

Think of a shop's till receipts. Each line is a fact: this product, this many, this price. Around them are labels: the date, the shop, the product's category, the customer's loyalty card. Any summary you can imagine is just “add up receipt lines, grouped by labels”.

  • Receipt lines are the fact table; labels are dimensions.
  • Drawn on paper, the fact sits in the middle with dimensions around it: a star.

3How it solves it facts in the middle, dimensions around

Dimensions are deliberately denormalized (category sits right on the product row), so every question is one join away from the fact table, and columnar warehouses scan just the columns they need.

  1. Pick the grain

    One fact row = one what? “One order line” is the usual answer; state it explicitly.

  2. List the measures

    The numbers you add up: quantity, amount, discount, cost.

  3. Build dimensions

    Flat, descriptive tables with a surrogate key: date (with month, quarter, holiday), product (with category), customer, store.

  4. Keep history in dimensions

    Type 2: when a product changes category, add a new dimension row with valid dates, so old facts keep the old label.

  5. Load it separately

    ETL/ELT (often with dbt) from the app database or a CDC stream into a warehouse, on a schedule.

reports.sqlany warehouse
CREATE TABLE fact_sales (
  date_key     int    NOT NULL REFERENCES dim_date,
  product_key  int    NOT NULL REFERENCES dim_product,
  customer_key int    NOT NULL REFERENCES dim_customer,
  store_key    int    NOT NULL REFERENCES dim_store,
  qty          int    NOT NULL,
  amount       numeric(12, 2) NOT NULL       -- grain: one order line
);

-- sales by category, month and country: one hop to each dimension
SELECT p.category, d.month, c.country, sum(f.amount) AS revenue
FROM fact_sales f
JOIN dim_product  p ON p.product_key  = f.product_key
JOIN dim_date     d ON d.date_key     = f.date_key
JOIN dim_customer c ON c.customer_key = f.customer_key
WHERE d.year = 2026
GROUP BY p.category, d.month, c.country
ORDER BY revenue DESC;

tools: Snowflake, BigQuery, Redshift, ClickHouse, DuckDB, dbt for building facts and dimensions, Fivetran/Airbyte/Debezium for loading, BI tools like Metabase, Looker and Power BI that expect star schemas.

4Gains vs losses nothing is free

What we gain

  • Fast, simple reports: sum facts, group by dimensions.
  • One shared definition of revenue, customers and products.
  • History kept with slowly changing dimensions.
  • Analytics off the app database: checkout stays fast.
  • BI tools understand it out of the box.

What we lose

  • A pipeline to build and run (ETL/ELT, scheduling).
  • Data is a little behind the app.
  • Duplicated, denormalized data in dimensions.
  • Bad for transactional writes: it's for reading.

6Common pitfalls the usual ways this goes wrong

  • Fuzzy grain

    Some fact rows are orders, some are order lines; totals double. Fix → write down the grain; one fact table per grain.

  • Overwriting dimensions

    A product moves category and last year's report changes. Fix → use type 2 slowly changing dimensions where history matters.

  • Snowflaking everything

    Dimensions normalized into sub-tables; joins are back. Fix → keep dimensions flat unless they're huge.

  • Querying the app database directly

    Analysts run heavy reports on production. Fix → load into a warehouse (or at least a read replica).

7When to use it (and when not)

Use it when…

  • Dashboards, BI and business reporting.
  • Questions that slice numbers by many attributes.
  • Teams that need one shared definition of key metrics.

Skip it when…

  • Transactional app tables (keep those normalized).
  • Tiny datasets where a few SQL queries are enough.
  • Real-time operational views that must be exact right now.

8Self-check quiz

What goes in a fact table, and what in a dimension?

Facts hold events with numeric measures at a fixed grain; dimensions hold descriptive attributes to filter and group by.

What is the grain?

The precise meaning of one fact row, for example one order line.

Why denormalize dimensions?

So every question is one join from the fact table, which is simpler and faster for analytics.

What does a type 2 slowly changing dimension do?

Adds a new dimension row (with validity dates) when an attribute changes, so old facts keep their old labels.
