Change Data Capture

TL;DR

Don't make the app write the same change to the database and the search index and the cache. Write only to the database, and let a connector read the database's own log (the WAL or binlog) and publish every committed insert, update and delete as an event. Other systems follow the stream, in order, and catch up after outages.

  • Family: data integration
  • Reads: PostgreSQL WAL, MySQL binlog, SQL Server CDC, Mongo change streams
  • Tools: Debezium, Kafka Connect, AWS DMS, Fivetran
  • Pairs with: transactional outbox, materialized views

1The problem why do we even need this?

Data rarely stays in one place: search, caches, analytics and other services all want a copy. Making the app write to every one of them (dual writes) means any failure leaves the copies out of sync.

  • The database commits, the search call times out: search is missing the order forever.
  • Nightly batch exports are hours stale and hammer the database.
  • Changes made by scripts or admin SQL never reach the other systems.

2Real-life analogy the court stenographer

In court, nobody stops the judge to ask what was just said. A stenographer types every word into a transcript, in order. Newspapers, lawyers and the archive all read the transcript, each at their own pace.

  • The database already keeps that transcript for crash recovery: the write-ahead log.
  • CDC just lets other systems read it.

3How it solves it tail the log, publish the changes

Because CDC reads committed changes from the log, it catches every write path (app, scripts, admin SQL), keeps their order, and never sees a transaction that rolled back.

  1. Enable logical decoding

    PostgreSQL: wal_level = logical plus a publication; MySQL: row-based binlog.

  2. Run a connector

    Debezium (on Kafka Connect or Debezium Server) takes a snapshot, then streams changes.

  3. Publish events

    One topic per table: {op, before, after, source.lsn}, keyed by primary key so a row's changes stay in order.

  4. Consume idempotently

    Consumers upsert by key and can replay from an offset after an outage.

  5. Watch the slot

    A stalled consumer makes the database keep WAL forever; alert on replication slot lag.

  6. Decide the contract

    Raw table events leak your schema; for other teams, publish curated events (outbox) instead.

Vocabulary for the exam

CDC
Change data capture: streaming row changes out of a database.
WAL / binlog
The database's own ordered log of changes.
Log-based CDC
Reading the log (vs. polling or triggers).
Replication slot
PostgreSQL bookmark for where a consumer is in the WAL.
Snapshot
Initial full copy before streaming changes.
Dual write
The app writing to two systems itself (the anti-pattern).

-- keep an eye on how far behind consumers are
SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn))
FROM pg_replication_slots;

4Gains vs losses nothing is free

What we gain

  • One write, many copies, always in sync eventually.
  • Catches every write path, including scripts and admin SQL.
  • Ordered and replayable: consumers catch up after outages.
  • Near real time instead of nightly exports.
  • Little extra load on the database (reads the log).

What we lose

  • More infrastructure: connectors, Kafka, monitoring.
  • Eventual consistency for the copies.
  • Your table schema becomes an API if others consume raw events.
  • Stuck slots can fill the database disk.

6Common pitfalls the usual ways this goes wrong

  • A forgotten replication slot

    A consumer stops, PostgreSQL keeps every WAL file, the disk fills. Fix → alert on slot lag; set max_slot_wal_keep_size.

  • Exposing raw tables to other teams

    Renaming a column breaks three downstream services. Fix → publish curated events (transactional outbox) for external contracts.

  • Non-idempotent consumers

    A connector restart replays events and doubles counts. Fix → upsert by key, track offsets.

  • Forgetting deletes

    The search index keeps rows deleted in the database. Fix → handle op = d and tombstones.

7When to use it (and when not)

Use it when…

  • Keeping search indexes, caches and warehouses in sync.
  • Replacing nightly batch exports with near-real-time feeds.
  • Migrating data to a new database with little downtime.
  • Audit streams of every change.

Skip it when…

  • A single database with no copies to keep in sync.
  • Publishing business events to other teams (prefer the outbox).
  • Teams that can't run and monitor streaming infrastructure yet.

8Self-check quiz

Why are dual writes unsafe?

The two writes aren't atomic; if one fails after the other succeeds, the systems drift apart silently.

Why does log-based CDC never emit rolled-back changes?

It reads committed transactions from the write-ahead log.

What happens if a CDC consumer stops for a week in PostgreSQL?

The replication slot keeps WAL from being removed, so disk usage grows until the consumer resumes or the slot is dropped.

CDC or outbox for events other teams consume?

Outbox: it publishes deliberate business events, so your internal table schema isn't a public contract.
