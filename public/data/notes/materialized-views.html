Materialized Views

TL;DR

A materialized view stores the result of an expensive query as real rows, which you can index and read in milliseconds. You refresh it on a schedule or after changes, accepting that readers see data that's a few minutes old. Perfect for dashboards, leaderboards and reports that many people read and nobody needs to the second.

  • Family: read optimisation
  • Built in: PostgreSQL, Oracle, SQL Server (indexed views), Snowflake
  • Trade: freshness for speed
  • Pairs with: star schema, CQRS

1The problem why do we even need this?

Some questions are expensive: sales per region per day across 50 million orders. A normal view just re-runs the query every time, so every viewer pays the full cost.

  • Dashboards take 12 seconds to load, every time.
  • Twenty people opening it at 9 a.m. means twenty heavy queries at once.
  • The reporting load slows down checkout on the same database.

2Real-life analogy the departure board

A station doesn't make every traveller phone the drivers. It computes a departure board and refreshes it every minute. Thousands of people read it instantly. It might be a minute out of date, and nobody minds.

  • The board is the materialized view.
  • “Updated every minute” is the refresh schedule.
  • For the exact second a train leaves, you ask the platform staff: query the source.

3How it solves it compute once, read many times

A materialized view is a cache that lives in the database. It's queried with plain SQL, can have indexes, and its freshness is set by how often you refresh it.

  1. Find the heavy, popular query

    Read many times, changes slowly, and slightly stale is fine.

  2. Create the view

    CREATE MATERIALIZED VIEW daily_sales AS SELECT ….

  3. Index it

    A unique index is needed for concurrent refresh, plus indexes for the dashboard's filters.

  4. Refresh without blocking

    REFRESH MATERIALIZED VIEW CONCURRENTLY keeps readers working during the refresh.

  5. Schedule it

    pg_cron, a job runner, or after a batch load; show “last updated” to users.

  6. Go incremental when it's too slow

    Summary tables updated by triggers or CDC, or a database with incremental views.

Vocabulary for the exam

View
A saved query; re-runs every time.
Materialized view
A saved query whose result is stored.
Refresh
Recomputing the stored result.
Staleness
How old the stored result can be.
Incremental maintenance
Updating only what changed, not everything.
Summary table
A hand-maintained table of precomputed totals.
daily_sales.sqlPostgreSQL + pg_cron
CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_trunc('day', o.placed_at) AS day, o.region,
       sum(i.qty * i.price) AS total, count(DISTINCT o.id) AS orders
FROM orders o JOIN order_items i ON i.order_id = o.id
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON daily_sales (day, region);  -- needed for CONCURRENTLY

-- every 15 minutes, without blocking readers
SELECT cron.schedule('*/15 * * * *',
  'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales');

-- the dashboard: milliseconds
SELECT * FROM daily_sales WHERE day >= now() - interval '30 days';

tools: PostgreSQL materialized views + pg_cron, Oracle fast refresh, SQL Server indexed views, Snowflake/BigQuery materialized views, dbt incremental models, Materialize and RisingWave for always-fresh incremental views.

4Gains vs losses nothing is free

What we gain

  • Fast reads for expensive questions.
  • Less load: the heavy query runs once per refresh.
  • Plain SQL: readers don't know it's precomputed.
  • Indexable, unlike a normal view.

What we lose

  • Stale data between refreshes.
  • Refresh cost: full recompute by default.
  • Extra storage for the stored result.
  • One more thing to schedule and monitor.

6Common pitfalls the usual ways this goes wrong

  • Blocking refresh

    A plain REFRESH locks the view, so the dashboard hangs for a minute. Fix → use CONCURRENTLY with a unique index.

  • Refreshing too often

    A 3-minute refresh every minute: refreshes pile up. Fix → refresh no faster than it can finish; consider incremental tables.

  • Hidden staleness

    Users think the numbers are live and make decisions on old data. Fix → show “last updated” in the UI.

  • Using it for live data

    Stock levels from a 15-minute-old view. Fix → keep exact, fast-changing reads on the source tables.

7When to use it (and when not)

Use it when…

  • Dashboards, leaderboards and reports read by many people.
  • Heavy aggregations over data that changes slowly.
  • Offloading reporting queries from transactional work.

Skip it when…

  • Data that must be exact right now (balances, stock).
  • Queries that are already fast with the right index.
  • Source data that changes faster than you can refresh.

8Self-check quiz

Difference between a view and a materialized view?

A view re-runs its query every time; a materialized view stores the result and is refreshed explicitly.

What does REFRESH … CONCURRENTLY need, and why use it?

A unique index on the view; it lets readers keep querying during the refresh.

What's the main trade-off?

Freshness for speed: reads are fast but can be as old as the last refresh.

When would you use incremental maintenance instead?

When full refreshes are too slow or you need near-real-time results.
