Expand & Contract Migrations

TL;DR

Never change the schema and the code in one risky step. Expand first (add the new column or table alongside the old one), migrate code and data in small, backward-compatible deploys (dual-write, backfill, switch reads), and only contract (drop the old thing) once nothing uses it. Every step can be rolled back, and there's no downtime.

  • Family: schema evolution
  • a.k.a.: parallel change, zero-downtime migration
  • Tools: Flyway, Liquibase, gh-ost, pgroll
  • Pairs with: feature flags, blue–green deploys

1The problem why do we even need this?

During a deploy, old and new code run at the same time. A migration that renames or drops a column breaks whichever version doesn't expect it, and big ALTERs can lock a busy table.

  • Old servers crash with “column name does not exist”.
  • An ALTER on a 200M-row table holds a lock and the site stalls.
  • The code rollback fails because the schema already moved on.

2Real-life analogy moving a road without closing it

To move a road, engineers don't close the old one and start digging. They build the new road beside it, open both, move the signs so traffic shifts over, and only when the old road is empty do they dig it up. Traffic never stops.

  • Building the new road is the expand migration.
  • Both roads open is dual-writing.
  • Digging up the old road is the contract migration.

3How it solves it small steps, each backward compatible

The rule: every migration must work with the code that's currently running and the code about to run. Splitting a change into expand → migrate → contract makes that true.

  1. Expand

    Add the new column/table as nullable or with a default; no locks, no breakage.

  2. Dual-write

    Deploy code that writes old and new (or a trigger that syncs them).

  3. Backfill

    Copy existing data in small batches (say 1,000 rows at a time) to avoid long locks and replication lag.

  4. Switch reads

    Deploy code that reads the new column; keep writing both so rollback works.

  5. Contract

    Stop writing the old column, wait a release, then drop it. Add NOT NULL with a validated CHECK first, not in one lock-heavy step.

Vocabulary for the exam

Backward compatible
The old code still works with the new schema.

Dual-write

Backfill

Online schema change
Altering a table without blocking traffic.
migrations/one file per deploy
-- 0042_expand.sql            (deploy 1)
ALTER TABLE users ADD COLUMN full_name text;   -- nullable: instant

-- app v2 writes both name and full_name     (deploy 2)

-- 0043_backfill.sql          (run in batches until 0 rows)
UPDATE users SET full_name = name
WHERE id IN (SELECT id FROM users WHERE full_name IS NULL LIMIT 1000);

-- app v3 reads full_name, still writes both  (deploy 3)

-- 0044_not_null.sql          (cheap validation, no long lock)
ALTER TABLE users ADD CONSTRAINT full_name_nn CHECK (full_name IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT full_name_nn;

-- app v4 stops writing name                  (deploy 4)
-- 0045_contract.sql          (deploy 5, a release later)
ALTER TABLE users DROP COLUMN name;

4Gains vs losses nothing is free

What we gain

  • Zero downtime schema changes.
  • Every step can roll back.
  • Small, boring deploys instead of a big-bang night.
  • Works with rolling deploys and many app versions.

What we lose

  • More deploys and more calendar time.
  • Temporary duplication (two columns, dual writes).
  • Easy to forget the contract step.
  • Backfills need care on huge tables.

6Common pitfalls the usual ways this goes wrong

  • Never contracting

    Three years later the table has name, full_name and display_name. Fix → ticket the contract step when you start; track it.

  • One huge backfill UPDATE

    A single statement rewrites 200M rows, bloats the table and lags replicas. Fix → batch it, pause between batches, watch lag.

  • Locking ALTERs

    Adding NOT NULL or a default on old databases rewrites the table under a lock. Fix → use NOT VALID + VALIDATE, and set a short lock_timeout.

  • Renaming in place

    RENAME COLUMN breaks the running code instantly. Fix → add new, migrate, drop old, or use a view as an alias.

7When to use it (and when not)

Use it when…

  • Any production database with traffic during deploys.
  • Rolling or blue–green deployments with several app versions live.
  • Large tables where locks would hurt.

Skip it when…

  • Brand-new tables nobody uses yet.
  • Apps where a short maintenance window is genuinely fine.
  • Prototypes and local databases.

8Self-check quiz

Why is renaming a column in one step dangerous?

During the deploy old code still uses the old name and crashes, and rolling back the code no longer matches the schema.

What are the three phases?

Expand (add new), migrate (dual-write, backfill, switch reads), contract (remove old).

Why backfill in batches?

To avoid long locks, table bloat and replication lag from one giant UPDATE.

How do you add NOT NULL safely to a big PostgreSQL table?

Add a CHECK … IS NOT NULL constraint as NOT VALID, then VALIDATE it separately.
