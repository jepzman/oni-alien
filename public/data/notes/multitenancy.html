Multitenancy

TL;DR

Serve many customers (tenants) from one system while keeping their data apart. Choose a model: shared tables with a tenant_id (cheapest, most common), a schema per tenant, or a database per tenant (strongest isolation). With shared tables, let the database enforce isolation with row-level security, so one forgotten WHERE can't leak data.

  • Family: SaaS data design
  • Models: shared · schema-per-tenant · database-per-tenant
  • Guard: row-level security (RLS)
  • Pairs with: partitioning, sharding, connection pooling

1The problem why do we even need this?

A SaaS app holds data for hundreds of companies. Running a database for each is expensive; putting them all in one table is cheap but one missing filter away from a leak. And one big customer can slow everyone down.

  • A new query forgets WHERE tenant_id = ? and shows another company's data.
  • One tenant's heavy export slows every other tenant (noisy neighbour).
  • An enterprise customer asks for their data in their own region, or deleted on request.

2Real-life analogy the apartment block

An apartment block shares the foundation, lift and plumbing, which keeps rent low. But every flat has its own locked door. Someone who wants total privacy can rent a house of their own, at a much higher price.

  • The building is your shared database; flats are rows tagged with tenant_id.
  • The lock on each door is row-level security.
  • A house each is database per tenant.

3How it solves it pick a model, then lock the doors

Most SaaS products start with shared tables and add row-level security, then move their biggest or most demanding customers to dedicated databases later.

  1. Choose the model

    Shared tables for many small tenants; schema or database per tenant for few, large or regulated ones. Hybrids are common.

  2. Put tenant_id everywhere

    On every tenant-owned table, first in composite indexes and keys: (tenant_id, id).

  3. Enforce it in the database

    Enable row-level security with a policy that compares tenant_id to the session's app.tenant_id setting.

  4. Set the tenant per request

    SET LOCAL app.tenant_id = … at the start of each transaction (pooler-safe).

  5. Plan for big tenants

    Per-tenant limits, partitioning or sharding by tenant_id, and a way to move a tenant to its own database.

tenancy.sqlPostgreSQL row-level security
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;      -- applies to the table owner too

CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);

CREATE INDEX ON invoices (tenant_id, created_at DESC);

-- per request, inside the transaction (safe with transaction poolers)
BEGIN;
SET LOCAL app.tenant_id = '42';
SELECT * FROM invoices;            -- only tenant 42's rows, even without WHERE
COMMIT;

4Gains vs losses nothing is free

What we gain

  • Low cost per tenant with shared tables.
  • One schema, one deploy for everyone.
  • Isolation enforced by the database, not just app code.
  • A path to dedicated databases for big customers.

What we lose

  • Noisy neighbours share resources.
  • tenant_id everywhere: keys, indexes, joins.
  • Per-tenant restore is harder in shared tables.
  • Mistakes are expensive (a leak is a breach).

6Common pitfalls the usual ways this goes wrong

  • Isolation only in app code

    One new endpoint forgets the filter: breach. Fix → enforce with RLS; test that tenant A can't read tenant B.

  • Session settings with a pooler

    A SET leaks to the next request on the same connection. Fix → use SET LOCAL inside a transaction.

  • tenant_id not first in indexes

    Queries for one tenant scan everyone's rows. Fix → lead keys and indexes with tenant_id.

  • Schema per tenant at 10,000 tenants

    Migrations take hours and catalogs bloat. Fix → use shared tables for the long tail.

7When to use it (and when not)

Use it when…

  • SaaS products serving many organisations.
  • Tenants with similar schemas and features.
  • You need cheap onboarding for many small customers.

Skip it when…

  • A handful of huge, regulated customers (give each a database).
  • Single-customer internal apps.
  • Tenants needing very different schemas.

8Self-check quiz

Name the three classic multitenancy models.

Shared tables with a tenant_id, schema per tenant, and database per tenant.

What does row-level security add?

The database filters rows by tenant automatically, so a query that forgets WHERE tenant_id can't see other tenants' data.

Why SET LOCAL rather than SET with a connection pooler?

SET LOCAL lasts only for the transaction, so the setting can't leak to the next request that reuses the connection.

Why put tenant_id first in indexes?

Queries always filter by tenant, so a tenant-first index jumps straight to that tenant's rows.
