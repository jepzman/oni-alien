Keyset Pagination

TL;DR

Instead of LIMIT 20 OFFSET 100000, remember the sort key of the last row you showed and ask for rows after it: WHERE (created_at, id) < (:last_at, :last_id). With an index on those columns, every page is as fast as page 1, and new inserts don't make items repeat or vanish.

  • Family: query performance
  • a.k.a.: seek method, cursor pagination
  • Needs: a unique, indexed sort order
  • Pairs with: indexing, infinite scroll

1The problem why do we even need this?

OFFSET pagination is easy, but the database still has to read every skipped row. Deep pages get slower and slower, and the results shift under your feet.

  • Page 5,000 reads 100,020 rows to return 20.
  • Someone inserts a row while you page, and an item appears twice.
  • Crawlers and exports that walk every page hammer the database.

2Real-life analogy the bookmark

When you stop reading a novel you leave a bookmark. Tomorrow you open the book there. You don't count 4,000 lines from the first page. And if the publisher adds a preface, your bookmark is still in the right place.

  • The bookmark is the cursor: the last row's sort key.
  • Opening at it is an index seek.
  • Counting lines from the start is OFFSET.

3How it solves it seek, don't skip

The trick is a unique, stable sort order (add the id as a tie-breaker) and an index that matches it. Then “rows after X” is a single index seek.

  1. Pick a stable order

    Sort by something meaningful plus a unique tie-breaker: ORDER BY created_at DESC, id DESC.

  2. Index it

    CREATE INDEX ON posts (created_at DESC, id DESC).

  3. Return a cursor

    Send the last row's (created_at, id), encoded as an opaque token.

  4. Seek on the next request

    Row-value comparison: WHERE (created_at, id) < ($1, $2).

  5. Design the UI for it

    Next/previous and infinite scroll work well; “jump to page 731” doesn't.

Vocabulary for the exam

OFFSET pagination
Skip n rows, then take a page.
Keyset / seek
Continue after the last row's key.
Cursor
Token holding the last row's sort key.
Tie-breaker
A unique column that makes the order total.
Row-value comparison
(a, b) < (x, y) compares pairs in order.
Page drift
Items repeating or vanishing as data changes.
feed.sqlPostgreSQL
CREATE INDEX posts_feed ON posts (created_at DESC, id DESC);

-- first page
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- next page: continue after the last row we sent
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < ($1, $2)     -- $1, $2 = last row's values
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- API: { items: [...], next: base64('2026-11-12T09:41Z|9041') }

tools: most APIs with a next_cursor (Stripe, Slack, GitHub GraphQL) use it. GraphQL Relay connections, Django REST CursorPagination, Prisma cursor, jOOQ seek().

4Gains vs losses nothing is free

What we gain

  • Constant speed: page 5,000 = page 1.
  • No duplicates or gaps when rows are inserted.
  • Cheap full walks for exports and syncs.
  • Natural fit for infinite scroll and APIs.

What we lose

  • No “jump to page 731”.
  • Total counts are separate (and still expensive).
  • Needs a matching index and unique order.
  • Cursor logic is fiddlier with many sort options.

6Common pitfalls the usual ways this goes wrong

  • A non-unique sort

    Ordering by created_at alone skips rows with the same timestamp. Fix → always add a unique tie-breaker (id).

  • Index doesn't match the order

    The seek turns into a scan plus sort. Fix → index the exact columns and directions.

  • Exposing raw values

    Clients build their own cursors and break when you change the sort. Fix → encode the cursor as an opaque token.

  • COUNT(*) on every page

    The pagination is fast, the total count isn't. Fix → show “more” instead, or cache an estimate.

7When to use it (and when not)

Use it when…

  • Feeds, timelines, infinite scroll and activity logs.
  • Public APIs that return lists.
  • Exports, syncs and batch jobs that walk a whole table.

Skip it when…

  • Small result sets where OFFSET is instant.
  • UIs that really need numbered pages you can jump between.
  • Ad-hoc admin screens with many sortable columns.

8Self-check quiz

Why does OFFSET get slower on deep pages?

The database still reads every skipped row before discarding it.

Why add the id to the sort?

To make the order unique, so rows sharing the same timestamp aren't skipped or repeated.

What index supports ORDER BY created_at DESC, id DESC?

A composite index on (created_at DESC, id DESC).

What can't keyset pagination do easily?

Jump straight to an arbitrary page number.
