Normalization

TL;DR

Store each fact in exactly one place, and let other tables point to it with a key. Then a change is one update, and the data can't disagree with itself. When reads get too slow, denormalize on purpose: copy a fact into a read-friendly shape, and keep a clear rule for how the copy stays fresh.

  • Family: data modelling
  • Origin: E. F. Codd, 1970–71 (normal forms)
  • Usual target: third normal form (3NF)
  • Pairs with: indexing, materialized views, star schema

1The problem why do we even need this?

The quickest schema is one wide table that looks like a spreadsheet. It works on day one. Then the same fact, like a customer's email, is copied onto every row that mentions it, and the copies start to drift.

  • Update anomaly: Ana changes her email, one row gets updated, two don't.
  • Delete anomaly: deleting Ben's only order also deletes everything you knew about Ben.
  • Insert anomaly: you can't store a new customer until they've ordered something.
  • Storage and backups grow with every copy.

2Real-life analogy the school's one address book

A school doesn't let every teacher keep parents' phone numbers in their own class list. The office keeps one address book. Class lists just say student #17. When a family moves, the office fixes one line, and every class list is right again.

  • The address book is the customers table; student #17 is a foreign key.
  • The head teacher still keeps a printed summary for assemblies: a deliberate copy, reprinted each term.

3How it solves it split until every fact has one home

Normal forms are a checklist for “one fact, one place”. In practice, aiming for third normal form covers almost everything: every column describes the key, the whole key, and nothing but the key.

  1. List the facts

    Write down the nouns (customer, order, product) and what you know about each.

  2. 1NF: one value per cell

    No comma lists like tags = 'a,b,c'; give repeating things their own rows or table.

  3. 2NF: depend on the whole key

    In a table keyed by (order_id, product_id), the product's name belongs in products, not in the line item.

  4. 3NF: nothing but the key

    If city depends on zip, not on the customer, it moves out (or you accept it, knowingly).

  5. Add constraints

    Foreign keys, NOT NULL and UNIQUE make the database enforce the design.

  6. Denormalize with a reason

    Measure first. If a join is really too slow, copy the column into a read model and write down who refreshes it.

Vocabulary for the exam

Normal form
A rule a schema can satisfy (1NF, 2NF, 3NF, BCNF…).
Anomaly
A bug caused by duplicated facts (update, insert, delete).
Foreign key
A column that must match a key in another table.
Functional dependency
A → B: knowing A tells you B.
Denormalization
Copying a fact on purpose to make reads cheaper.
Source of truth
The one table that owns a fact; copies follow it.
schema.sqlPostgreSQL
-- each fact has one home
CREATE TABLE customers (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name   text NOT NULL,
  email  text NOT NULL UNIQUE
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers (id),
  item        text   NOT NULL,
  placed_at   timestamptz NOT NULL DEFAULT now()
);

-- Ana's new email: one row, everywhere at once
UPDATE customers SET email = 'ana@new.com' WHERE id = 17;

-- the join brings the facts back together for reading
SELECT o.id, c.name, c.email, o.item
FROM orders o JOIN customers c ON c.id = o.customer_id;

tools: any relational database (PostgreSQL, MySQL, SQL Server, SQLite). ER diagram tools like dbdiagram.io or DBeaver help you see the shape. Document databases still benefit: embed what's read together, reference what changes on its own.

4Gains vs losses nothing is free

What we gain

  • No contradictions: one fact, one place.
  • Cheap, safe updates: change one row, not hundreds.
  • Smaller tables and backups.
  • Flexible queries: join the pieces any way you like.
  • The database guards the rules with foreign keys.

What we lose

  • More joins for everyday reads.
  • More tables to understand at first.
  • Reporting queries get long without views.
  • Over-normalizing (a table for every attribute) hurts more than it helps.

6Common pitfalls the usual ways this goes wrong

  • Normalizing to the extreme

    A table for every attribute, and a 9-way join to show a name. Fix → stop at 3NF unless a real anomaly pushes you further.

  • Copies with no owner

    A denormalized customer_name on orders that nobody updates. Fix → every copy gets a written refresh rule: trigger, job or event.

  • Comma lists in a column

    tags = 'red,blue' can't be indexed, joined or constrained. Fix → use a join table (or a real array/JSON type with care).

  • No foreign keys “for speed”

    Orphan rows appear and nobody notices for months. Fix → keep FKs; they're cheap with an index on the referencing column.

7When to use it (and when not)

Use it when…

  • Any transactional (OLTP) system: orders, users, bookings, payments.
  • Data that changes often and must stay consistent.
  • You don't yet know every question you'll ask of the data.

Skip it when…

  • Analytics warehouses where reads dominate (see star schema, note 15).
  • Write-once logs and events, which never get updated.
  • A measured hot path where a deliberate copy is clearly cheaper.

8Self-check quiz

What are the three classic anomalies?

Update (copies disagree), insert (can't store a fact without another one) and delete (removing one fact loses another).

Summarise 3NF in one sentence.

Every non-key column depends on the key, the whole key, and nothing but the key.

When is denormalizing a good idea?

When a measured read path is too slow, the copied data changes rarely, and there's a clear rule that keeps the copy fresh.

Why keep foreign keys?

The database then refuses orphans and dangling references, so integrity doesn't depend on every app being perfect.
