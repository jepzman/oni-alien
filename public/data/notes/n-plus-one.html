Batch Loading (Fixing N+1)

TL;DR

The N+1 problem: load a list with one query, then run one more query per row to load something related. Fix it by batch loading: collect the ids and fetch the related rows in one query (a JOIN, WHERE id = ANY(…), an ORM's eager loading, or a DataLoader). The number of queries stays constant however long the list gets.

  • Family: query performance
  • Usual cause: ORM lazy loading in a loop
  • Fixes: JOIN, eager loading, IN / ANY, DataLoader
  • Pairs with: indexing, keyset pagination

1The problem why do we even need this?

Each query is fast, so nobody notices. But a page that loads 50 posts and then each post's author makes 51 round trips. With comments and likes it's 151. Latency adds up, and the database drowns in tiny queries.

  • ORMs make it invisible: post.author.name looks like a field, but it's a query.
  • Fine in development with 5 rows; slow in production with 500.
  • GraphQL resolvers make it worse: every field can trigger its own query.

2Real-life analogy the shopping list

You need 20 things from the shop. You could drive there, buy one, drive home, and repeat twenty times. Or you could take the whole list in one trip. The driving, not the shopping, is what takes time.

  • Each drive is a round trip to the database.
  • Writing the list first is collecting the ids.
  • Fetching everything at once is batch loading.

3How it solves it collect, fetch once, match

The fix is always the same shape: don't query inside a loop. Either join in SQL, or gather the keys and make one batched query per relationship.

  1. Spot it

    Count queries per request (ORM logs, APM traces). A count that grows with the list size is the tell.

  2. Join when it's one-to-one

    JOIN authors brings the author along on each post row.

  3. Batch when it's one-to-many

    Comments per post: a second query with WHERE post_id = ANY(…), avoiding a giant row-multiplying join.

  4. Use the ORM's eager loading

    includes (Rails), select_related / prefetch_related (Django), include (Prisma), JOIN FETCH (JPA).

  5. In GraphQL, use DataLoader

    It collects every key requested in one tick and makes one batched call.

  6. Guard it in tests

    Assert the query count for key pages so a regression fails CI.

Vocabulary for the exam

N+1 query
1 query for a list + 1 per item.
Lazy loading
Related data is fetched when first accessed.
Eager loading
Related data is fetched up front, in batches.
Round trip
Send a query, wait for the answer.
DataLoader
A helper that batches and caches lookups per request.
Row explosion
A join that multiplies rows (posts × comments).
posts.tsnode-postgres
// ✗ N+1: one query per post
for (const p of posts) {
  p.author = (await db.query("SELECT * FROM authors WHERE id = $1", [p.author_id])).rows[0];
}

// ✓ batch: two queries, however many posts
const posts = (await db.query("SELECT * FROM posts ORDER BY id DESC LIMIT 50")).rows;
const ids = [...new Set(posts.map((p) => p.author_id))];
const authors = (await db.query("SELECT * FROM authors WHERE id = ANY($1)", [ids])).rows;
const byId = new Map(authors.map((a) => [a.id, a]));
for (const p of posts) p.author = byId.get(p.author_id);

// the same with an ORM (Prisma): include = eager loading
await prisma.post.findMany({ take: 50, include: { author: true } });

tools: ORM eager loading, GraphQL DataLoader, Bullet (Rails) and nplusone (Django) detectors, Sentry/Datadog “N+1 query” detection, query-count assertions in tests.

4Gains vs losses nothing is free

What we gain

  • Constant query count: 2 queries for 10 or 10,000 rows.
  • Much lower latency: round trips dominate small queries.
  • Less database load: fewer parses, fewer connections held.
  • Predictable pages as data grows.

What we lose

  • A little more code (or ORM hints) per relationship.
  • Over-fetching if you eager-load things you don't show.
  • Big joins can multiply rows if used for one-to-many.
  • Huge id lists need chunking.

6Common pitfalls the usual ways this goes wrong

  • Eager-loading everything

    Every request loads comments, likes and tags it never shows. Fix → load only what the view renders.

  • A JOIN for one-to-many

    Posts × comments returns 50,000 rows for 50 posts. Fix → use a second batched query for collections.

  • Batching without an index

    WHERE post_id = ANY(…) still scans the table. Fix → index the foreign key column.

  • Fixing it once

    A new field in a template brings the N+1 back. Fix → assert query counts in tests or use a detector.

7When to use it (and when not)

Use it when…

  • Any list page that shows related data.
  • GraphQL APIs (use DataLoader by default).
  • Background jobs that loop over many rows.

Skip it when…

  • Detail pages that load a single row and its relations.
  • Relations that are rarely accessed and expensive to load.
  • When a denormalized read model already holds what you need.

Related patterns

8Self-check quiz

How do you recognize an N+1 problem?

The number of queries per request grows with the number of rows shown.

JOIN or second query for comments per post?

A second batched query: a JOIN multiplies post rows by comment rows.

What does DataLoader do?

Collects all the keys requested during one tick and loads them in one batched call, caching per request.

Why are 50 fast queries slower than 1 medium one?

Each has a network round trip and per-query overhead; latency adds up even if each query is quick.

remember!!

Never query in a loop. Write the list, make one trip.
