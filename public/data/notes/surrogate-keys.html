Surrogate Keys

TL;DR

Make every table's primary key a meaningless, stable id (an identity number or a UUID), and keep real-world values like email or SKU as UNIQUE columns. References point at the id, so real-world changes stay one-row updates, and joins stay small and fast.

  • Family: data modelling
  • Kinds: identity / sequence, UUID v4, UUID v7, ULID
  • Opposite: natural keys
  • Pairs with: normalization, sharding

1The problem why do we even need this?

A natural key, like an email, a username or a product code, feels free: it's already unique. But real-world values change, get reused, and turn out to be less unique than promised.

  • A user changes their email, and every table that stores it must change too.
  • “Unique” national ids get typos, reissues and foreign formats.
  • Wide text keys make every index and foreign key bigger.
  • Keys show up in URLs and logs, leaking personal data.

2Real-life analogy the coat-check ticket

At a coat check you get ticket 042. The number tells nobody your name, your coat's colour or your phone number. That's the point: you can change your hat, your name or your mind, and 042 still finds the coat.

  • The ticket is the surrogate key; your name is a natural key.
  • The staff still check your name on the list: keep the natural key UNIQUE.

3How it solves it ids for linking, natural values for rules

Keep two jobs separate: the id is for linking rows; the natural key is a business rule (“no two users share an email”), enforced with UNIQUE.

  1. Add an id to every table

    bigint GENERATED ALWAYS AS IDENTITY for one database, or a UUID if ids are made in many places.

  2. Keep natural keys UNIQUE

    Email, SKU, slug: still unique, just not the primary key.

  3. Reference the id

    Foreign keys point at users.id, never at users.email.

  4. Pick the id type on purpose

    Sequential ids are small and index-friendly but guessable; random UUID v4 is safe to share but scatters inserts; UUID v7 / ULID are time-ordered and shareable.

  5. Don't expose sequential ids carelessly

    Use a separate public id or slug if “user 1,042” leaks your growth or invites guessing.

Vocabulary for the exam

Natural key
A real-world value that identifies a row (email, ISBN).
Surrogate key
An id with no meaning outside the database.
Identity column
A column the database fills with 1, 2, 3…
UUID
A 128-bit id that can be generated anywhere.
UUID v7 / ULID
Time-ordered unique ids: sortable and index-friendly.
Composite key
A primary key made of several columns.
users.sqlPostgreSQL 13+
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- for linking
  public_id  uuid NOT NULL DEFAULT gen_random_uuid() UNIQUE,  -- safe for URLs
  email      text NOT NULL UNIQUE,                           -- business rule
  name       text NOT NULL
);

CREATE TABLE sessions (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id  bigint NOT NULL REFERENCES users (id)
);

-- a new email is one row; sessions don't care
UPDATE users SET email = 'ana@new.com' WHERE id = 7;

tools: identity columns (PostgreSQL, SQL Server, Oracle), AUTO_INCREMENT (MySQL), gen_random_uuid(), UUID v7 libraries, ULID. Many ORMs default to a surrogate id.

4Gains vs losses nothing is free

What we gain

  • Stable references: real-world changes are one-row updates.
  • Small, fast joins on 8-byte integers.
  • Uniform design: every table has an id.
  • No personal data in keys and URLs (with a public id).

What we lose

  • An extra column and an extra unique index.
  • Easy to forget the natural UNIQUE, and then duplicates creep in.
  • Ids mean nothing when you read raw data.
  • Random UUIDs scatter inserts across the index.

6Common pitfalls the usual ways this goes wrong

  • Dropping the natural UNIQUE

    Two rows for ana@mail.com because only the id is unique. Fix → keep UNIQUE on the business identifier.

  • Random UUID v4 as a clustered key

    Inserts land all over the index, causing page splits and cache misses. Fix → use bigint, UUID v7 or ULID when insert order matters.

  • Sequential ids in public URLs

    /invoice/1043 invites guessing the next one. Fix → add a random public id and check permissions anyway.

  • Meaning sneaks into the id

    “Ids starting with 9 are test users.” Fix → use a real column (is_test); ids stay meaningless.

7When to use it (and when not)

Use it when…

  • Almost every OLTP table.
  • Natural keys that can change, be reused or contain personal data.
  • Ids generated in many services or offline clients (UUID / ULID).

Skip it when…

  • Join tables, where (user_id, group_id) is a fine composite key.
  • Truly immutable codes like ISO country codes.
  • Small lookup tables where the code is the meaning (status = 'paid').

8Self-check quiz

Why not use email as the primary key?

Emails change and are personal data; every foreign key would need rewriting and would leak the email.

If the id is the PK, how do you stop duplicate users?

Keep a UNIQUE constraint on email (often case-insensitive).

Why are random UUID v4 keys slow for inserts?

Each new key lands at a random spot in the B-tree, causing page splits and poor cache use; time-ordered ids append at the end.

When is a composite natural key fine?

In join tables like (user_id, role_id), where the pair is the identity and never changes.
