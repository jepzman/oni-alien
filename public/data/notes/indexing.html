Indexing

TL;DR

An index is a sorted copy of one or more columns with pointers back to the rows, usually a B-tree. Queries that filter, join or sort on those columns jump straight to the rows instead of scanning the whole table. Every index makes writes a little slower and takes space, so index the queries you actually run, and check with EXPLAIN.

  • Family: query performance
  • Default type: B-tree
  • Others: hash, GIN, GiST, BRIN, partial, covering
  • Check with: EXPLAIN ANALYZE

1The problem why do we even need this?

A table without the right index is a book without an index: to answer “which orders belong to customer 42?”, the database must read every row. Fine at 1,000 rows. A disaster at 10 million.

  • Pages get slower every month as data grows, with no code change.
  • One slow query holds locks and connections, so everything else queues up.
  • Throwing a bigger server at it buys weeks, not years.

2Real-life analogy the index at the back of the book

To find every page about photosynthesis you don't read the whole textbook. You flip to the index: words in alphabetical order, each with page numbers. Because it's sorted, you find the word in seconds and jump to the pages.

  • Every new edition must update the index too: indexes slow down writes.
  • An index of every word would be as big as the book: don't index everything.
  • “Words starting with ph” is easy; “words ending in -sis” isn't: column order and leading wildcards matter.

3How it solves it sorted keys, a few hops down a tree

A B-tree keeps keys sorted in pages. Finding one key among millions takes only 3–4 page reads, and once you're there, ranges and ORDER BY come for free.

  1. Find the slow queries

    Use pg_stat_statements or your APM; sort by total time, not just the slowest single call.

  2. Read the plan

    EXPLAIN (ANALYZE, BUFFERS): a Seq Scan reading millions of rows for a few results is the signal.

  3. Index what you filter, join and sort on

    Equality columns first, then range or sort columns: (customer_id, placed_at).

  4. Use special shapes when they fit

    Partial (WHERE status = 'open'), covering (INCLUDE (total)), expression (lower(email)), GIN for JSON and full text.

  5. Build it without blocking

    CREATE INDEX CONCURRENTLY on busy tables.

  6. Prune

    Drop indexes nobody uses (pg_stat_user_indexes.idx_scan = 0); they only slow writes.

Vocabulary for the exam

indexes.sqlPostgreSQL
-- the query we run all day
SELECT id, total FROM orders
WHERE customer_id = 42 ORDER BY placed_at DESC LIMIT 20;

-- equality first, then the sort column; INCLUDE makes it covering
CREATE INDEX CONCURRENTLY orders_customer_recent
  ON orders (customer_id, placed_at DESC) INCLUDE (total);

-- only open tickets are ever searched: index just those
CREATE INDEX tickets_open ON tickets (assignee_id) WHERE status = 'open';

-- case-insensitive email lookups need an expression index
CREATE UNIQUE INDEX users_email_ci ON users (lower(email));

EXPLAIN (ANALYZE, BUFFERS) SELECT …;   -- Seq Scan → Index Only Scan

＋Going deeper reading plans, column order, the cost of writes

The note says “index what you filter, join and sort on, then measure”. This chapter is the measuring part: how to read a plan in four lines, how to pick the column order of a composite index, what each index costs on the write side, and the usual reasons the planner walks past an index you built.

1Reading a plan in four lines

Run the slow query with EXPLAIN (ANALYZE, BUFFERS). The output is a tree; the most indented line runs first and feeds the line above it. For most problems you only need four things from it:

  • The scan type at the bottom. Seq Scan reads the whole table. Index Scan uses the index and then visits the table. Index Only Scan answers from the index alone. Bitmap Heap Scan collects matches from an index first, then reads the table pages in order: good for medium-sized results.
  • Rows removed by filter. 2,400,000 read to keep 31 means the database is doing the filtering the index should do.
  • Estimated vs actual rows. If the planner expected 10 and got 300,000, its statistics are wrong: run ANALYZE on the table and look again.
  • A Sort node. A sort above a scan means the index doesn't deliver rows in the order you asked for. Often the fix is the same index with the sort column added.

Then read Buffers: pages read from cache and disk. Time changes with load; pages read are a steadier way to compare two plans.

2Choosing the column order

A composite index is sorted by the first column, then by the second inside each value of the first, and so on, like a phone book by surname then first name. That gives a simple rule for most queries: columns you compare with = first, then the column you sort by, then columns you compare with a range (<, >, BETWEEN).

For WHERE customer_id = 42 ORDER BY placed_at DESC LIMIT 20, the index (customer_id, placed_at DESC) puts customer 42's orders in one run, newest first. The database reads 20 entries and stops. The index (placed_at, customer_id) holds the same data, but customer 42's orders are spread across every date, so the database reads many more entries and sorts them.

Two more points. A range column ends the useful part of the index: in (customer_id, placed_at, status) with a range on placed_at, the status column can only be filtered, not searched. And one index can serve several queries that share its leading columns: (customer_id, placed_at) also serves WHERE customer_id = 42 on its own, so you don't need a separate index for that.

3What every index costs

Each index is a second copy of some columns that must stay in step with the table. Insert one order into a table with six indexes and the database writes the row, six index entries, and the write-ahead log for all seven. Updates to an indexed column do the same work again. Indexes also take disk and, more importantly, memory: the hot parts of every index compete with the table for the cache.

So check what you are paying for. In PostgreSQL, pg_stat_user_indexes counts scans per index since the statistics were last reset. An index with idx_scan = 0 after a month of normal traffic (and after checking replicas and month-end jobs) is a candidate to drop. Indexes that are a prefix of another, such as (customer_id) next to (customer_id, placed_at), are usually redundant too.

Drop with DROP INDEX CONCURRENTLY, one at a time, and keep the definition in a migration so it can come back in minutes.

4Why the planner ignores your index

When an index exists but the plan still shows a Seq Scan, the reason is usually one of these:

  • The filter matches too much. status = 'delivered' matches 90% of rows; reading the table in order is cheaper than jumping around. Index the rare values with a partial index instead.
  • The column is wrapped. WHERE lower(email) = … or WHERE placed_at::date = … can't use a plain index on the column. Index the expression, or rewrite the filter as a range.
  • The types don't match. Comparing a text column to a number can force a cast on every row.
  • The pattern starts with a wildcard. LIKE '%lamp' can't use a B-tree. Use a trigram index or full-text search.
  • Statistics are stale after a large load. Run ANALYZE.
  • The table is small. A few hundred rows fit in a couple of pages; a scan is genuinely the fastest plan. That's fine.

Don't force the planner with hints. Fix the reason, then read the plan again.

4Gains vs losses nothing is free

What we gain

  • Huge read speedups: seconds to milliseconds.
  • Cheap ORDER BY and ranges on indexed columns.
  • Uniqueness enforced by unique indexes.
  • Less load: fewer pages read, fewer locks held.

What we lose

  • Slower writes: every index is updated on insert/update.
  • Disk and memory for each index.
  • Easy to get wrong: wrong column order, unused indexes.
  • Bloat on heavily updated tables needs maintenance.

6Common pitfalls the usual ways this goes wrong

  • Indexing every column

    Twelve single-column indexes, and writes crawl. Fix → index real queries; prefer one good composite.

  • Wrong column order

    An index on (placed_at, customer_id) for WHERE customer_id = ?. Fix → equality columns first, then range/sort.

  • Functions on the column

    WHERE lower(email) = ? ignores an index on email. Fix → use an expression index or store it normalized.

  • Guessing instead of measuring

    An index is added and the plan doesn't use it. Fix → always confirm with EXPLAIN ANALYZE on real data.

7When to use it (and when not)

Use it when…

  • Columns in frequent WHERE, JOIN and ORDER BY clauses.
  • Foreign key columns (joins and cascading deletes).
  • Uniqueness rules (unique indexes).
  • Large tables where a query returns a small share of rows.

Skip it when…

  • Tiny tables, where a scan is already instant.
  • Columns with few distinct values (a boolean), unless partial.
  • Write-heavy tables where the query is rare (log tables).

8Self-check quiz

Why does column order matter in a composite index?

The index is sorted by the first column, then the second; it helps queries that filter on a leading prefix of the columns.

What's a covering index?

One that contains every column the query needs, so the database never has to visit the table (an index-only scan).

Why can too many indexes hurt?

Each one must be updated on every write and takes disk and memory.

How do you know an index is used?

EXPLAIN ANALYZE shows an Index Scan or Index Only Scan, and index usage stats show scans over time.

what would you do?A query filters orders by customer_id and sorts by created_at descending. There is an index on created_at only, and the query takes 2 seconds. Which index do you add, and how do you check it helped?

A composite index on (customer_id, created_at DESC): the equality column first, then the sort column. Run EXPLAIN ANALYZE before and after, and look for an index scan with no separate sort step.

try it

Fill a table with a million rows (generate_series), run a filtered and sorted query with EXPLAIN ANALYZE, then add a single-column index and a composite one in both column orders. Write down the plan and time for each.

remember!!

Don't read the whole book. Check the index, but don't index every word.
