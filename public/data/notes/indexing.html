Indexing

TL;DR

An index is a sorted copy of one or more columns with pointers back to the rows, usually a B-tree. Queries that filter, join or sort on those columns jump straight to the rows instead of scanning the whole table. Every index makes writes a little slower and takes space, so index the queries you actually run, and check with EXPLAIN.

  • Family: query performance
  • Default type: B-tree
  • Others: hash, GIN, GiST, BRIN, partial, covering
  • Check with: EXPLAIN ANALYZE

1The problem why do we even need this?

A table without the right index is a book without an index: to answer “which orders belong to customer 42?”, the database must read every row. Fine at 1,000 rows. A disaster at 10 million.

  • Pages get slower every month as data grows, with no code change.
  • One slow query holds locks and connections, so everything else queues up.
  • Throwing a bigger server at it buys weeks, not years.

2Real-life analogy the index at the back of the book

To find every page about photosynthesis you don't read the whole textbook. You flip to the index: words in alphabetical order, each with page numbers. Because it's sorted, you find the word in seconds and jump to the pages.

  • Every new edition must update the index too: indexes slow down writes.
  • An index of every word would be as big as the book: don't index everything.
  • “Words starting with ph” is easy; “words ending in -sis” isn't: column order and leading wildcards matter.

3How it solves it sorted keys, a few hops down a tree

A B-tree keeps keys sorted in pages. Finding one key among millions takes only 3–4 page reads, and once you're there, ranges and ORDER BY come for free.

  1. Find the slow queries

    Use pg_stat_statements or your APM; sort by total time, not just the slowest single call.

  2. Read the plan

    EXPLAIN (ANALYZE, BUFFERS): a Seq Scan reading millions of rows for a few results is the signal.

  3. Index what you filter, join and sort on

    Equality columns first, then range or sort columns: (customer_id, placed_at).

  4. Use special shapes when they fit

    Partial (WHERE status = 'open'), covering (INCLUDE (total)), expression (lower(email)), GIN for JSON and full text.

  5. Build it without blocking

    CREATE INDEX CONCURRENTLY on busy tables.

  6. Prune

    Drop indexes nobody uses (pg_stat_user_indexes.idx_scan = 0); they only slow writes.

Vocabulary for the exam

B-tree
Balanced sorted tree; the default index type.
Sequential scan
Reading the whole table, row by row.
Selectivity
How few rows a condition matches; high = good for an index.
Composite index
An index on several columns, in a set order.
Covering index
Holds every column the query needs: no table visit.
Query plan
The database's step-by-step recipe; see it with EXPLAIN.
indexes.sqlPostgreSQL
-- the query we run all day
SELECT id, total FROM orders
WHERE customer_id = 42 ORDER BY placed_at DESC LIMIT 20;

-- equality first, then the sort column; INCLUDE makes it covering
CREATE INDEX CONCURRENTLY orders_customer_recent
  ON orders (customer_id, placed_at DESC) INCLUDE (total);

-- only open tickets are ever searched: index just those
CREATE INDEX tickets_open ON tickets (assignee_id) WHERE status = 'open';

-- case-insensitive email lookups need an expression index
CREATE UNIQUE INDEX users_email_ci ON users (lower(email));

EXPLAIN (ANALYZE, BUFFERS) SELECT …;   -- Seq Scan → Index Only Scan

tools: EXPLAIN ANALYZE, pg_stat_statements, explain.depesz.com, pgMustard, MySQL EXPLAIN FORMAT=TREE, SQL Server execution plans, the “use-the-index-luke.com” guide.

4Gains vs losses nothing is free

What we gain

  • Huge read speedups: seconds to milliseconds.
  • Cheap ORDER BY and ranges on indexed columns.
  • Uniqueness enforced by unique indexes.
  • Less load: fewer pages read, fewer locks held.

What we lose

  • Slower writes: every index is updated on insert/update.
  • Disk and memory for each index.
  • Easy to get wrong: wrong column order, unused indexes.
  • Bloat on heavily updated tables needs maintenance.

6Common pitfalls the usual ways this goes wrong

  • Indexing every column

    Twelve single-column indexes, and writes crawl. Fix → index real queries; prefer one good composite.

  • Wrong column order

    An index on (placed_at, customer_id) for WHERE customer_id = ?. Fix → equality columns first, then range/sort.

  • Functions on the column

    WHERE lower(email) = ? ignores an index on email. Fix → use an expression index or store it normalized.

  • Guessing instead of measuring

    An index is added and the plan doesn't use it. Fix → always confirm with EXPLAIN ANALYZE on real data.

7When to use it (and when not)

Use it when…

  • Columns in frequent WHERE, JOIN and ORDER BY clauses.
  • Foreign key columns (joins and cascading deletes).
  • Uniqueness rules (unique indexes).
  • Large tables where a query returns a small share of rows.

Skip it when…

  • Tiny tables, where a scan is already instant.
  • Columns with few distinct values (a boolean), unless partial.
  • Write-heavy tables where the query is rare (log tables).

8Self-check quiz

Why does column order matter in a composite index?

The index is sorted by the first column, then the second; it helps queries that filter on a leading prefix of the columns.

What's a covering index?

One that contains every column the query needs, so the database never has to visit the table (an index-only scan).

Why can too many indexes hurt?

Each one must be updated on every write and takes disk and memory.

How do you know an index is used?

EXPLAIN ANALYZE shows an Index Scan or Index Only Scan, and index usage stats show scans over time.
