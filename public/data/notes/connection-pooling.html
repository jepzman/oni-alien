Connection Pooling

TL;DR

Opening a database connection is slow and expensive (a process, memory, a TLS handshake), and databases allow only a few hundred. Keep a small pool of open connections and lend one per request or transaction. Use the pool in your app, and an external pooler (PgBouncer, RDS Proxy) when many app instances or serverless functions share one database.

  • Family: scaling access
  • In-app: HikariCP, node-postgres Pool, SQLAlchemy pool
  • External: PgBouncer, pgcat, Supavisor, RDS Proxy
  • Pairs with: multitenancy, bulkhead (Vol. 1)

1The problem why do we even need this?

Each PostgreSQL connection is a whole server process using megabytes of memory, and connecting takes a TCP + TLS + auth round trip. When every request or function opens its own, the database runs out of connections long before it runs out of CPU.

  • Autoscaling to 50 app pods × 20 connections = 1,000 connections: “too many clients”.
  • Serverless functions open a fresh connection on every cold start.
  • Thousands of mostly idle connections still cost memory and slow the database down.

2Real-life analogy the taxi rank

Nobody buys a car for a single trip across town. A taxi rank keeps a few cars ready; travellers take the next free one and it comes back for the next person. If all taxis are out, you wait a moment in the queue.

  • Each taxi is an open connection.
  • The rank is the pool; the dispatcher is the pooler.
  • The queue is how a pool protects the database from overload.

3How it solves it few connections, shared quickly

Databases do best with a small number of busy connections, roughly a few per CPU core. A pool turns many short-lived clients into that shape.

  1. Pool in the app

    Create one pool per process at start-up; never connect per request.

  2. Size it small

    Start near cores × 2 on the database side, then measure; bigger pools often make things slower.

  3. Add an external pooler for many clients

    Many pods or serverless functions → PgBouncer/RDS Proxy in transaction mode.

  4. Always return connections

    Use try/finally or the pool's helper; a leaked connection is gone for good.

  5. Set timeouts

    Acquire timeout, statement timeout and idle-in-transaction timeout, so one stuck request can't hold a connection forever.

Vocabulary for the exam

Connection pool
A set of open connections reused by many requests.
Pooler
A proxy that pools connections for many clients.
Session pooling
A client keeps one connection for its whole session.
Transaction pooling
A connection is lent only for one transaction.
Connection leak
Borrowing a connection and never returning it.
Acquire timeout
How long to wait for a free connection.
db.tsnode-postgres
import { Pool } from "pg";

// one pool per process, created once
export const pool = new Pool({
  max: 10,                          // per app instance; total = instances × max
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000,   // fail fast instead of hanging
  statement_timeout: 5_000,
});

export async function inTx<T>(fn: (c: PoolClient) => Promise<T>) {
  const c = await pool.connect();   // borrow
  try {
    await c.query("BEGIN");
    const out = await fn(c);
    await c.query("COMMIT");
    return out;
  } catch (e) { await c.query("ROLLBACK"); throw e; }
  finally { c.release(); }          // always give it back
}

tools: HikariCP (Java), node-postgres Pool, SQLAlchemy and Django CONN_MAX_AGE, Prisma Accelerate, PgBouncer, pgcat, Odyssey, Supavisor, Amazon RDS Proxy, ProxySQL (MySQL).

4Gains vs losses nothing is free

What we gain

  • No connection storms: the database sees a steady, small number.
  • Lower latency: no handshake per request.
  • Less database memory spent on idle connections.
  • Back-pressure: queueing protects the database under load.

What we lose

  • Pool sizing needs measuring and tuning.
  • Transaction pooling breaks session features (SET, advisory locks, some prepared statements).
  • Another hop and component with an external pooler.
  • Leaks quietly drain the pool.

6Common pitfalls the usual ways this goes wrong

  • Huge pools

    max = 200 per pod “to be safe”; the database thrashes. Fix → keep pools small and measure; more connections ≠ more speed.

  • Session state in transaction mode

    A SET search_path leaks to other clients or vanishes. Fix → use SET LOCAL inside transactions, or session mode.

  • Forgetting release()

    After an exception path the pool slowly empties and requests hang. Fix → always release in finally; enable leak detection.

  • Connect per serverless call

    Each cold start opens a new connection. Fix → put a pooler or data proxy between functions and the database.

7When to use it (and when not)

Use it when…

  • Every app that talks to a relational database.
  • Many app instances, autoscaling or serverless functions.
  • Databases with expensive connections (PostgreSQL).

Skip it when…

  • Embedded databases like SQLite in a single process.
  • HTTP-based database APIs that pool for you.
  • A one-off script that runs a few queries.

8Self-check quiz

Why are PostgreSQL connections expensive?

Each is a separate backend process with its own memory, and creating one needs a TCP, TLS and authentication round trip.

Session vs transaction pooling?

Session pooling ties a server connection to a client for its whole session; transaction pooling lends it only for one transaction, allowing far more clients.

Why can a bigger pool make things slower?

Too many active connections compete for CPU, locks and memory, causing contention and context switching.

How do you avoid connection leaks?

Always release connections in a finally block (or use the pool's helpers) and set acquire timeouts.
