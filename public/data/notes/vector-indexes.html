Vector Indexes

TL;DR

Search by meaning turns text, images or products into embeddings: long lists of numbers where similar things are close together. Finding the closest ones by comparing against every row is exact but slow. An approximate nearest-neighbour (ANN) index, usually HNSW or IVF, finds almost all of the true nearest items in milliseconds. You trade a little recall for a lot of speed, so measure recall, and plan how filters and re-embedding work before you rely on it.

  • Lives in: pgvector, a search engine, or a vector database

1The problem why do we even need this?

“Budget trainers” should find “cheap running shoes”: no shared words, same meaning. Embeddings make that possible, but finding the nearest of 5 million vectors by comparing each one takes 2.4 seconds and a whole CPU core per search.

  • A normal B-tree index can't help: “close in meaning” isn't a sort order.
  • Exact search grows with the table; ten times more products means ten times slower.
  • Search, recommendations and retrieval for AI features all need this lookup, many times per page.

2Real-life analogy a library arranged by topic

In a library arranged by topic, you don't read every spine. You go to the sports floor, then the running section, then look along nearby shelves. You find almost everything you'd want in seconds. Now and then a book shelved somewhere odd is missed: that's the price of not checking everything.

3How it solves it search a graph, not the whole table

HNSW links each vector to its nearest neighbours in several layers. A search enters at the sparse top, hops greedily toward the query, drops a layer, and repeats, comparing a few hundred vectors instead of millions. IVF instead groups vectors into clusters and searches only the few clusters nearest the query. HNSW is usually faster and more accurate; IVF builds faster and uses less memory.

  1. Store embeddings with their model

    A vector column plus the model name and version, so you know which vectors belong together.

  2. Choose the distance

    Cosine for most text models (or inner product on normalised vectors); use the one the model was trained for.

  3. Build an ANN index

    pgvector: CREATE INDEX … USING hnsw (embedding vector_cosine_ops); or IVF with a list count.

  4. Measure recall

    Run 100 real queries exactly (no index) and with the index; recall@10 = share of the true top 10 the index found. Tune until it's good enough, often 95%+.

  5. Plan filters and updates

    Decide how “in stock, in the shopper's country” combines with the search, and how you re-embed when the model changes.

Vocabulary for the exam

Embedding
A vector of numbers that places similar items close together.
Nearest-neighbour search
Finding the vectors closest to a query vector.
ANN
Approximate nearest neighbour: fast, finds most of the true nearest.
HNSW
Hierarchical navigable small world: a layered graph index.
IVF
Inverted file index: vectors grouped into clusters.
Recall@k
Share of the true top k results the index returns.
search.sqlPostgreSQL + pgvector 0.8
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE products ADD COLUMN embedding vector(768);       -- from one embedding model
ALTER TABLE products ADD COLUMN embedding_model text;          -- which one (re-embed on change)

CREATE INDEX products_embedding_hnsw ON products
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

-- per query: look wider for better recall, and keep filtering inside the index scan
SET hnsw.ef_search = 100;
SET hnsw.iterative_scan = relaxed_order;   -- keep searching if filters remove too many

SELECT id, name, embedding <=> $1 AS distance      -- <=> is cosine distance
  FROM products
 WHERE in_stock AND country = $2
 ORDER BY embedding <=> $1
 LIMIT 10;

tools: pgvector (PostgreSQL), OpenSearch / Elasticsearch k-NN, Redis vector search, SQLite sqlite-vec, Qdrant, Weaviate, Milvus, FAISS (library), ann-benchmarks.com for comparing index types.

4Gains vs losses nothing is free

What we gain

  • Milliseconds instead of seconds at millions of vectors.
  • Search by meaning, not just matching words.
  • One store with pgvector: vectors next to the rows they describe.
  • Tunable: trade recall for speed per query.

What we lose

  • Approximate: some true matches are missed.
  • Memory hungry: HNSW indexes like to fit in RAM.
  • Slow builds and slower inserts than a B-tree.
  • Filters are tricky and model changes mean re-embedding everything.

6Common pitfalls the usual ways this goes wrong

  • Filtering after the search

    The index returns the 10 nearest, then the WHERE removes 9 out-of-stock ones, and the shopper sees one result. Fix → use iterative or filtered index scans, partial indexes per common filter, or ask for more candidates.

  • Mixing models

    New products embedded with a new model, old ones with the old model: distances mean nothing. Fix → store the model with each vector; re-embed everything before switching queries.

  • Never measuring recall

    The index silently returns worse results after a parameter change. Fix → keep a fixed set of queries with exact answers and check recall@10 in CI or a nightly job.

  • Index bigger than memory

    HNSW pages are read from disk and latency jumps. Fix → size RAM for the index, use smaller vectors (or half precision), or quantize.

7When to use it (and when not)

Use it when…

  • Semantic search, “similar items” and recommendations.
  • Retrieval for AI features (RAG) over your own documents.
  • Deduplicating near-identical text or images.
  • More than a few thousand vectors per query.

Skip it when…

  • A few thousand vectors: exact search is fast enough and has perfect recall.
  • Keyword or exact-match search does the job (SKUs, names, codes).
  • You can't afford to re-embed when the model changes, and need results to stay stable.

8Self-check quiz

Why can't a B-tree index speed up nearest-neighbour search on embeddings?

A B-tree orders values along one dimension; closeness in a 768-dimension space isn't a sort order.

What does recall@10 measure?

The share of the true 10 nearest items (from exact search) that the approximate index returned.

HNSW or IVF: which is usually faster and more accurate, and what does it cost?

HNSW; it costs more memory and slower builds than IVF.

Why store the model name with each vector?

Vectors from different models aren't comparable; you must know which to re-embed when the model changes.

what would you do?Product search uses pgvector with HNSW. In one country, shoppers often get only two or three results, though many products match. The query filters by country after ordering by distance. What is happening, and what do you change?

The index returns its nearest candidates first, and the country filter removes most of them. Use iterative index scans (or raise ef_search), add a partial index per large country, or include the country in the search, and measure recall for filtered queries specifically.

try it

Load 100,000 sentences or product titles with embeddings into PostgreSQL with pgvector. Time 100 queries with exact search, then build an HNSW index and time them again. Compute recall@10 for the index against the exact results, then change hnsw.ef_search from 40 to 200 and watch speed and recall move together.
