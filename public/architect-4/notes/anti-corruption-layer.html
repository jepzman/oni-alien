Anti-Corruption Layer

TL;DR

When you integrate with a system whose model differs from yours, its words and shapes tend to leak into your code until you're speaking the vendor's language everywhere. An anti-corruption layer is a thin translation layer at the border: it turns their concepts into yours (and back), so the rest of your system never sees the other model. Keep it in one place, and enforce that nothing else talks to the other system directly.

  • Family: boundaries
  • Origin: Eric Evans, Domain-Driven Design (2003)
  • Lives in: the integrating module's adapter, guarded by a fitness function
  • Pairs with: bounded contexts, integration style, strangler fig

1The situation Larder, 22 March 2027

Two weeks into the WMS B work, Ana reviews a few pull requests and finds the vendor's words everywhere. Ordering has started storing WMS B's article_id; Fulfilment talks about “waves”; a picker screen shows bin codes. The vendor's model is replacing Larder's own: products, store locations, pick lists. In two years, leaving WMS B would mean rewriting half the system.

  • Vendor concepts leak into every module that touches them.
  • Your own domain language erodes, and with it, clarity.
  • Every leak is another place to change when you leave.

2Real-life analogy the embassy interpreter

At a meeting between two delegations, an interpreter sits at the border of the conversation and translates both ways. Each side keeps speaking its own language; nobody has to learn the other's, and nothing gets lost in a half-understood word. If one delegation changes, only the interpreter needs to adapt.

3How it solves it translate at the border, both ways

The Stock module already had the only StockPilot adapter (ADR 0005); Ana made the WMS B adapter an explicit anti-corruption layer. It translates article → product, bin → store location, wave → pick batch, WMS B's units → items, and turns webhooks into stock.changed in Larder's terms. The three leaks were rewritten; a fitness function now fails the build if any other module imports the WMS B client.

  1. Name both models

    List the other system's concepts and yours, side by side.

  2. Put one adapter at the border

    In the module that owns the integration; nowhere else.

  3. Translate both ways

    Their concepts to yours on the way in; yours to theirs on the way out.

  4. Publish in your own terms

    Events and APIs out of the adapter use only your language.

  5. Guard the border

    A fitness function: nothing else imports the vendor client.

  6. Review for leaks

    Search for the vendor's words in code reviews and docs.

# The only place in Larder that knows WMS B's words.  (ADR 0018, fitness function FF-07)

def to_stock_changed(webhook: dict) -> StockChanged:
    """WMS B 'article.qty.updated' → Larder 'stock.changed'."""
    product = products.by_wms_article(webhook["article"]["code"])
    location = locations.by_wms_bin(webhook["bin"]["id"])
    items = units.to_items(webhook["qty"], webhook["uom"])   # e.g. 2 CRATE → 24 items
    return StockChanged(product_id=product.id, store_id=location.store_id,
                        location=location.code, available=items, source="wms_b")

def to_wms_pick_wave(batch: PickBatch) -> dict:
    """Larder pick batch → WMS B 'wave'."""
    return {"wave_ref": batch.id, "lines": [
        {"article": products.wms_article(l.product_id), "qty": l.items, "uom": "EA"}
        for l in batch.lines]}

tools: a module boundary and an adapter package; import-linter or ArchUnit rules to keep vendor clients inside it; contract tests against the vendor sandbox.

4Gains vs losses nothing is free

What we gain

  • Your language stays yours: products, not articles.
  • Leaving is cheap: replace the adapter only.
  • Vendor changes stay local.
  • Clearer code for everyone outside the adapter.
  • Enforceable with a fitness function.

What we lose

  • Translation code to write and test.
  • Some concepts don't map neatly (units of measure).
  • A little latency and indirection.
  • Temptation to bypass “just this once”.

6Common pitfalls the usual ways this goes wrong

  • Leaky adapter

    The adapter passes WMS B objects straight through. Fix → translate every field into your model.

  • Several adapters

    Ordering and Fulfilment each call WMS B. Fix → one adapter, guarded by a fitness function.

  • Vendor words in events

    stock.changed carries article_id. Fix → publish only your own terms.

  • Forcing a fit

    Pretending units of measure are always items. Fix → translate explicitly; record the odd cases.

7When to use it (and when not)

Use it when…

  • Integrating with vendors and SaaS.
  • Legacy systems you're migrating away from.
  • Partners whose model differs from yours.
  • Any external model you don't control.

Skip it when…

  • Two contexts that really share a language.
  • Short-lived integrations you'll delete soon.

8Self-check quiz

What does an anti-corruption layer protect?

Your own model and language from another system's.

Where should it live?

In one adapter, in the module that owns the integration.

How do you stop it being bypassed?

A fitness function that fails the build if others import the vendor client.

What changes when you leave the vendor?

Only the adapter.
