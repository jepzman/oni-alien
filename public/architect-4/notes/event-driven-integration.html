Event-Driven Integration

TL;DR

Events let a producer announce “this happened” without knowing who listens, which is exactly what makes them easy to break. Treat events as published contracts: every event has an owner, a schema in a registry, and a catalogue entry listing its consumers. Allow only backward-compatible changes (add optional fields); a breaking change means a new version published alongside the old one for a while. Let CI check compatibility before a producer deploys.

1The situation Larder, 19 April 2027

Utrecht opened on 12 April; the city work had added more consumers to Larder's events. Then Ordering renamed one field in order.placed, from store to store_id, a tidy-up. Nine consumers read that event. Billing failed silently for two days: business invoices missed their store, and nobody noticed until Mo's monthly check. Nobody knew who consumed what.

  • Producers don't know their consumers, so they can't warn them.
  • Schemas live in code, so changes aren't reviewed as contracts.
  • Breaks are silent: events still flow, just wrong.

2Real-life analogy the newspaper

A newspaper publishes to readers it doesn't know. So it keeps its sections in the same place, announces format changes in advance, and keeps a subscriber list. It can add a new supplement any day; it doesn't move the TV listings to the sports pages overnight.

3How it solves it contracts, a registry, compatible changes

ADR 0020 set the rules. Every event has one owner, a schema in a schema registry and a page in the event catalogue listing its consumers. Only backward-compatible changes are allowed; a rename means order.placed.v2, published alongside v1 for three months while consumers move. CI checks compatibility against the registry, so the store_id rename would now fail the build.

  1. Give every event an owner

    The producing team owns the schema and its changes.

  2. Register every schema

    In a schema registry (Avro, JSON Schema, Protobuf), versioned.

  3. Catalogue the consumers

    One page per event: owner, schema, consumers, examples.

  4. Allow compatible changes only

    Add optional fields; never rename, remove or retype.

  5. Version breaking changes

    New version alongside the old; a dated end for the old one.

  6. Check in CI

    Compatibility check before a producer can deploy.

4Gains vs losses nothing is free

What we gain

  • No silent breaks: incompatible changes fail CI.
  • Producers know their consumers.
  • Safe evolution: add fields freely; version breaks.
  • Onboarding: one page per event.
  • Loose coupling kept loose.

What we lose

  • Registry and CI checks to set up.
  • Two versions at once during migrations.
  • Catalogue upkeep as consumers change.
  • Slower tidy-ups: renames need a version.

6Common pitfalls the usual ways this goes wrong

  • Unowned events

    Anyone edits order.placed. Fix → one owner per event.

  • Silent renames

    A tidy-up breaks billing. Fix → renames are breaking: new version.

  • Forever versions

    v1, v2 and v3 all live for years. Fix → a dated end for old versions.

  • No consumer list

    Nobody to warn. Fix → catalogue consumers; ask on subscribe.

7When to use it (and when not)

Use it when…

  • Events consumed by more than one team.
  • Integrations with vendors via webhooks turned into events.
  • Growing event-driven systems.
  • After the first silent break.

Skip it when…

  • Events inside one module.
  • Short-lived prototypes.

8Self-check quiz

What makes events easy to break?

Producers don't know their consumers, and changes look like internal tidy-ups.

Which changes are backward compatible?

Adding optional fields or new events.

How do you make a breaking change?

Publish a new version alongside the old one, with a dated end.

What would have caught the store_id rename?

A compatibility check against the schema registry in CI.

try it

List your three most-used events. For each, write the owner and every consumer you can find, then register the schema and add a compatibility check to the producer's CI. Count how many consumers nobody knew about.

remember!!

Publish like a newspaper: keep the sections still, announce changes, know your readers.
