Data Ownership & Master Data

TL;DR

When the same data lives in several systems and each is edited directly, the copies drift apart. Decide, for each important kind of data (product, price, customer, stock), one master system and one owner. Everyone else holds a read-only copy that subscribes to changes; fixes happen in the master, never in the copies. Write it down as a short table, and enforce it in the integrations.

1The situation Larder, 2 August 2027

A pre-launch test for Antwerp compares product data across systems. The same apples are “Pommes Elstar 1 kg” in the Catalogue, “APPLE ELSTAR 1KG” in WMS B and “Elstar apples” in billing, which also has the wrong VAT category. 212 products disagree. Each system was edited directly by a different team, each sure their copy was the real one.

  • Several systems, each editable, each “the truth” to someone.
  • Fixes in one copy don't reach the others.
  • A new country multiplies the fields (languages, VAT) that can drift.
meanwhile, in Grace’s notebook
  • Localisation for a New Country (Grace, vol. 6): The same week, Grace's Antwerp testers found the 212 product mismatches that ADR 0024 fixes.

2Real-life analogy the family address book

A family keeps one master address book; everyone's phone syncs from it. When cousin Lisa moves, the master is changed once and every phone updates. If people edited their own phone's copy instead, within a year nobody would know where Lisa lives.

3How it solves it one master, one owner, everyone subscribes

ADR 0024 named a master and an owner for six kinds of data. Product (including French and Dutch names and the VAT category) lives in the Catalogue, owned by Grace's team; WMS B and billing receive it by events and their edit screens for product fields were switched off. The 212 differences were fixed in the Catalogue and pushed out in a day; a nightly check now compares the copies and reports drift.

  1. List the important kinds of data

    Product, price, customer, account, stock, courier…

  2. Name one master each

    The system where it's created and changed.

  3. Name one owner each

    A person or team accountable for its quality.

  4. Make copies read-only

    Others subscribe to change events; turn off edit screens.

  5. Fix in the master

    Drift is corrected at the source and pushed out.

  6. Check for drift

    A periodic comparison of copies with the master.

Vocabulary for the exam

Master data
Core business data used by many systems: products, customers.
Master system
The one system where that data is created and changed.
Data owner
Accountable for a kind of data's quality and meaning.
Golden record
The single trusted version of an entity.
Drift
Copies diverging from the master.
Data steward
Someone who looks after data quality day to day.

4Gains vs losses nothing is free

What we gain

  • One truth per kind of data.
  • Fixes happen once and spread.
  • Clear accountability for data quality.
  • New fields (languages, VAT) added in one place.
  • Drift detected, not discovered.

What we lose

  • Edit screens removed from some teams' tools.
  • Owners need time for data quality.
  • Events to build for every copy.
  • Edge cases: data with two natural homes.

6Common pitfalls the usual ways this goes wrong

  • Several masters

    Product names editable in three tools. Fix → one master; switch off edit screens elsewhere.

  • No owner

    Data owned by “the business”. Fix → a named team per kind of data.

  • Fixing copies

    Support corrects the helpdesk's copy. Fix → fix in the master; let it flow.

  • No drift check

    Divergence found at launch. Fix → compare copies with the master regularly.

7When to use it (and when not)

Use it when…

  • Data shared by several systems: products, customers, prices.
  • Before a new market, language or legal entity.
  • When reports disagree about basic facts.
  • Integrating new SaaS that wants its own copy.

Skip it when…

  • Data used by one system only.
  • Temporary copies in caches (keep them short-lived).
