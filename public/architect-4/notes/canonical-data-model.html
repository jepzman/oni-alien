Canonical Data Model (and Its Traps)

TL;DR

A canonical data model, one shared model of “order” or “customer” that every system translates to, sounds like order out of chaos. In practice it often becomes a huge model nobody owns, changed by committee, right for no one, coupling every system to every other. What usually works better: each bounded context keeps its own model, and only a small published language (a few shared events or messages with few fields, owned and versioned) crosses the borders, with translation at each edge.

1The situation Larder, 5 July 2027

With WMS B, billing, Dispatch, analytics and the Business API all exchanging orders, a new senior engineer proposes a canonical Larder Order: one model, 140 fields, that every system translates to and from. It sounds tidy. Ana has seen it before, at her last company: a model nobody owned, changed by committee, that every team quietly worked around.

  • A model for everyone has every field and fits no one.
  • Every change needs every team's agreement, so nothing changes.
  • Systems become coupled through the shared model.

2Real-life analogy the universal government form

Imagine one universal form for every government department: tax, health, driving, passports. It grows to forty pages; each department fills in a tenth of it; no department can change it alone. Within a year each one has its own unofficial form again, plus a team that copies data from it into the universal one.

3How it solves it own models, a small shared language

Ana wrote ADR 0023 with the engineer who proposed it, starting from the problem he wanted to solve (inconsistent order data in analytics). Each context keeps its own model; between them, a small published language: order.placed, stock.changed and delivery.completed, each with a few fields everyone agrees on, owned and versioned in the registry. Analytics builds its own consistent view from those events.

  1. Start from the real problem

    Inconsistent reports? Many integrations? Name it first.

  2. Keep models per context

    Each bounded context owns its own shape of “order”.

  3. Agree a small published language

    A few shared events or messages, few fields each.

  4. Give each shared message an owner

    Versioned in the registry, with compatibility rules.

  5. Translate at the borders

    Anti-corruption layers in each context.

  6. Build shared views where needed

    Analytics composes its own view from the events.

# 23. No canonical order model; a small published language instead
Status: Accepted · 2027-07-05 · Driver: Ana · with the proposer, Ben, Eli, analytics

Problem     Order data is inconsistent across systems, especially in analytics.
Rejected    A canonical Larder Order (140 fields) used by every system:
            no single owner, committee changes, couples every system to every other.
Decision    - Each context keeps its own model (basket, pick list, drop, invoice line).
            - Published language, owned and versioned in the registry:
                order.placed (Ordering) · stock.changed (Stock) · delivery.completed (Dispatch)
              each ≤ 15 fields; compatibility rules as ADR 0020.
            - Translation at each border (anti-corruption layers).
            - Analytics builds one consistent order view from the three events.
Revisit     If more than 5 contexts need the same new field, discuss adding it.

tools: the schema registry and event catalogue (ADR 0020); context maps from DDD; a data warehouse view built from events for analytics.

4Gains vs losses nothing is free

What we gain

  • Each context keeps a model that fits it.
  • Shared messages stay small and owned.
  • Changes stay local to one context.
  • Analytics still gets consistency, from events.
  • No committee for every field.

What we lose

  • More translation code at the borders.
  • Some duplication of data across contexts.
  • Harder to explain than “one model”.
  • The published language needs governance too.

6Common pitfalls the usual ways this goes wrong

  • The 140-field model

    Every field anyone ever needed. Fix → small shared messages, few fields.

  • No owner

    The canonical model belongs to everyone. Fix → one owner per shared message.

  • Shared language grows

    Three events become thirty. Fix → add only what several contexts need; review yearly.

  • Ignoring the real problem

    Analytics still inconsistent. Fix → build the consistent view from events.

7When to use it (and when not)

Use it when…

  • When someone proposes “one model for everything”.
  • Systems with several bounded contexts exchanging data.
  • Analytics needing consistent views across systems.
  • Integration platforms with many systems.

Skip it when…

  • A small number of systems that truly share one model.
  • Industry standards you must use (then translate at the border).

8Self-check quiz

Why do canonical models often fail?

Nobody owns them, changes need everyone's agreement, and they fit no one well.

What's a published language?

A small, shared, owned format for exchanging data between contexts.

What three events form Larder's published language?

order.placed, stock.changed and delivery.completed.

How does analytics get consistent orders?

By building its own view from the shared events.

try it

If your organisation has (or wants) a canonical model, count its fields and how many each system really uses. Then list the three or four messages that actually need to cross team boundaries, with the fields each needs, and compare.
