Transition Architectures

TL;DR

Big changes pass through in-between states where old and new run side by side, held together by temporary bridges: comparison jobs, dual feeds, fallbacks, copies. Design those states on purpose. For each, write what runs, which parts are temporary, who owns each one and the date it goes. Don't call the change finished until every bridge is removed: temporary with no end date is permanent.

1The situation Larder, 16 August 2027

Planning the end of the warehouse move, Ana goes looking for anything else still connected to old paths, and finds three temporary bridges from the 2026 Dispatch extraction still running: the old courier cron as a fallback, a database view Dispatch was meant to stop reading, and a nightly copy job for one report. Nobody remembered they were temporary. Each one still costs money, attention and risk.

  • Migrations are planned as start and end; the middle is improvised.
  • Temporary parts have no owner and no end date.
  • “Done” is declared when the new system works, not when the old bits are gone.

2Real-life analogy scaffolding with a date

A renovation needs scaffolding in between: nobody can paint the top floor without it. On a good project, the scaffolding is on the plan, with a date to come down and a person responsible. On a bad one, it stays up for years, rusting, because the building “works” and nobody's job is to remove it.

3How it solves it name the states, date the bridges

Ana wrote the warehouse move as three states: A (StockPilot only), B (both, with the router) and C (WMS B only). For B she listed every temporary bridge (shadow comparison jobs, finance files from both systems, StockPilot read-only as a way back), each with an owner and an end date, and added them to the debt register. State C was declared only on 30 September, when all were gone. The three old Dispatch bridges were removed in the same sweep.

  1. Name the states

    Before, each in-between state, after: what runs in each.

  2. List the temporary parts

    Comparison jobs, dual feeds, fallbacks, copies, flags, routers.

  3. Give each an owner and an end date

    And put them in the technical debt register.

  4. Define exit criteria per state

    What must be true to move to the next one.

  5. Declare done only at the end

    When every temporary part is removed.

  6. Sweep for old bridges

    Look for leftovers from earlier migrations.

4Gains vs losses nothing is free

What we gain

  • The middle is designed, not improvised.
  • Temporary parts get removed, on dates.
  • Honest “done”: the old bits are gone.
  • Lower running cost after the change.
  • Old leftovers found in the sweep.

What we lose

  • More planning up front.
  • Removing bridges takes real work at the end.
  • States can multiply if over-planned.
  • The finish takes longer than “it works”.

6Common pitfalls the usual ways this goes wrong

  • Undated scaffolding

    “Temporary” fallback, no end date. Fix → every temporary part gets an owner and a date.

  • Done too early

    Declared done when the new system works. Fix → done when the bridges are removed.

  • No exit criteria

    State B lasts forever. Fix → what must be true to move on.

  • Not looking back

    Leftovers from the last migration. Fix → sweep for old bridges at each new one.

7When to use it (and when not)

Use it when…

  • Migrations that run old and new side by side.
  • Extractions from a monolith.
  • Programmes with several releases before the target.
  • Any change with temporary workarounds.

Skip it when…

  • Changes with no in-between state.
  • Small swaps finished in a day.

8Self-check quiz

What's a temporary bridge?

Something that exists only to get through a transition: comparison jobs, dual feeds, fallbacks.

What must every temporary bridge have?

An owner and an end date (and a line in the debt register).

When is a migration done?

When the target state is reached and every temporary bridge is removed.

What did Ana's sweep find?

Three bridges from the 2026 Dispatch extraction still running.

try it

Pick your last finished migration. List every temporary part it needed and check whether each is really gone. For the next one, write the states and the temporary bridges, with owners and end dates, before you start.

remember!!

Put the scaffolding on the plan, with a date to come down.
