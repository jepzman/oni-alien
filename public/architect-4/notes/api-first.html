API-First Design

TL;DR

When an API is built first and described afterwards, it mirrors the builder's internals, and clients find out too late. API-first reverses the order: write the contract (OpenAPI) first, in the consumer's language; review it with the consumers; publish a mock so they can start building; then implement and test against the same contract. Changing a contract costs an edit; changing a shipped API costs everyone.

  • Family: integration styles
  • Origin: contract-first design; OpenAPI (formerly Swagger, 2011–); “API design first” practice
  • Lives in: an OpenAPI file in the repo, reviewed as a pull request
  • Pairs with: API versioning strategy, backend for frontend, solution design document

1The situation Larder, 15 March 2027

Korenwolf's facilities team wants to top up pantry orders from their own facilities system, not by emailing Mo. Ben's team starts building an API straight from Larder's internal order model. Four weeks later Korenwolf's IT sees it for the first time: field names like pick_ref, no cost centre, and a different idea of what an order is. The contract was an afterthought, and now it has to change.

  • Inside-out APIs expose internal names and shapes.
  • Consumers find problems after the work is done.
  • Both sides work in sequence instead of in parallel.

2Real-life analogy the floor plan

Before a building goes up, the floor plan is agreed with the people who'll live there: where the doors, sockets and windows go. Moving a door on the plan costs an eraser; moving it in a built wall costs a builder. And while the walls go up, the tenants can already order furniture that fits.

3How it solves it contract, review, mock, build

Ana and Ben restarted with the contract: /business/v1 in Korenwolf's words (standing orders, cost centres, offices, delivery windows), opened as a pull request with Korenwolf's IT lead and Mo as reviewers. A mock server went up the same week, so Korenwolf built their side in parallel. The real API passed the same contract tests and went live in May (ADR 0019).

  1. Name the consumers and their tasks

    Who calls it, to do what, in their words.

  2. Write the contract first

    OpenAPI: resources, fields, errors, examples. No code yet.

  3. Review it with consumers

    As a pull request; their names for things win.

  4. Publish a mock

    Generated from the contract, so they can build now.

  5. Implement against the contract

    Contract tests in CI; the contract is the source of truth.

  6. Version from day one

    /v1 in the path, and a policy for changes.

Vocabulary for the exam

API-first
Designing the contract before the implementation.
Contract
The agreed description of an API: endpoints, fields, errors.
OpenAPI
A standard format for describing HTTP APIs.
Mock server
A fake API generated from the contract.
Contract test
A test that the implementation matches the contract.
Consumer
A system or team that calls the API.
api/business/openapi.yamlthe start of the Business API contract (excerpt)
openapi: 3.1.0
info: { title: Larder Business API, version: 1.0.0 }
paths:
  /business/v1/standing-orders:
    post:
      summary: Create or replace an office's weekly standing order
      requestBody:
        content:
          application/json:
            schema: { $ref: "#/components/schemas/StandingOrder" }
            example:
              office: KW-AMS-HQ
              cost_centre: "4100-FAC"
              delivery_window: { day: TUE, from: "07:00", to: "09:00" }
              items: [ { sku: "FRT-APPLE-1KG", quantity: 12 } ]
      responses:
        "201": { description: Created }
        "422": { description: Unknown office, item or cost centre }

tools: OpenAPI with an editor (Stoplight, Swagger Editor), mock servers (Prism), contract tests (Schemathesis, Dredd, Pact for consumer-driven contracts), linting (Spectral).

4Gains vs losses nothing is free

What we gain

  • Consumers shape the API in their language.
  • Problems found on paper, not after building.
  • Parallel work via the mock.
  • One source of truth: the contract.
  • Docs for free, generated from the contract.

What we lose

  • Upfront time before code starts.
  • Contract and code can drift without tests.
  • Over-design if every field is debated.
  • Needs consumers available to review.

6Common pitfalls the usual ways this goes wrong

  • Contract after code

    The OpenAPI file is generated from the implementation. Fix → write it first; generate code or tests from it.

  • Internal names

    pick_ref, ord_ln. Fix → use the consumer's words.

  • No mock

    Consumers wait for the real thing. Fix → publish a mock the day the contract is agreed.

  • No contract tests

    Code and contract drift apart. Fix → test the implementation against the contract in CI.

7When to use it (and when not)

Use it when…

  • APIs used by other teams or clients.
  • Partner and B2B integrations.
  • When consumers and providers can build in parallel.
  • Public or long-lived APIs.

Skip it when…

  • Internal calls inside one module.
  • Throwaway prototypes.

8Self-check quiz

What's written first in API-first design?

The contract (e.g. an OpenAPI file), before any implementation.

Whose language should the contract use?

The consumer's.

What does a mock server allow?

Consumers to build against the API before it's implemented.

How do you keep code and contract aligned?

Contract tests in CI.

try it

For the next API another team will call, write the OpenAPI contract with one example per endpoint before any code. Open it as a pull request with the consumer as reviewer, publish a mock, and note what changed in review.

remember!!

Agree the floor plan with the tenants. An eraser, not a builder.
