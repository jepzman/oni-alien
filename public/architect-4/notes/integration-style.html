Choosing an Integration Style

TL;DR

There are four basic ways for systems to share information: a shared database, file transfer, remote calls (APIs) and messaging (events). Each fits a different need. Choose per need, not per system: “tell me when it changes” wants events; “do this and tell me if it worked” wants an API; “all of yesterday” wants a file; a shared database almost always couples you too tightly. One integration can, and often should, use more than one style.

  • Origin: Gregor Hohpe and Bobby Woolf, Enterprise Integration Patterns (2003)
  • Lives in: the ADR for each integration
  • Pairs with: anti-corruption layer, event-driven integration, batch & file transfer

1The situation Larder, 8 March 2027

The warehouse move to WMS B (ADR 0016) starts with an integration meeting. The vendor offers four ways in: a database view, a nightly file, an API and webhooks. Ben likes the database view (“quickest”); Eli likes webhooks; Joost just wants stock to be right. Each person picks by taste, and nobody has written down what Larder actually needs from WMS B.

  • One style for everything forces some needs into the wrong shape.
  • The quickest option (a shared database) creates the tightest coupling.
  • The style is picked before the needs are listed.

2Real-life analogy four ways to share with a neighbour

Two neighbours can share information four ways: a shared notebook on the fence they both write in (until one tears out a page), a letter in the post each night (everything at once, a day late), a phone call when one needs an answer now, or a doorbell that rings when something happens. Sensible neighbours use several, each for what it's good at.

Translating it to the job
In real lifeOn the project
The shared notebookShared database: both systems use the same tables

3How it solves it list the needs, pick a style per need

Ana listed what Larder needs from WMS B and picked per need. Stock changes must arrive within a minute: webhooks, turned into Larder events. Larder must tell WMS B what to pick and what arrived, and know it worked: the API. Finance needs all of yesterday's movements to reconcile: a nightly file. The database view was ruled out: Larder would depend on WMS B's tables. All three sit behind the Stock module's one adapter (ADR 0018).

  1. List the needs first

    What must flow, in which direction, how fast, and what happens if it fails.

  2. Match each need to a style

    Changed → events. Do this → API. All of a period → file. Shared tables → almost never.

  3. Check the vendor's options

    What they really support, with limits (rate, size, retries).

  4. Mix styles where needed

    One integration often needs two or three.

  5. Hide it behind one adapter

    So the rest of the system sees one interface.

  6. Record it

    An ADR per integration: needs, styles, why not the others.

Vocabulary for the exam

Shared database
Two systems reading and writing the same tables.
File transfer
Exchanging files on a schedule (batch).
Remote procedure call
Calling another system and waiting for the answer (APIs).
Messaging
Sending messages or events through a broker or webhooks.
Coupling
How much one system depends on another's internals.
Webhook
An HTTP call a system makes to you when something happens.

Consequences: three mechanisms to run; one adapter in the Stock module hides them
(as ADR 0005 did for StockPilot). Webhooks can be missed → the nightly file reconciles.

tools: the Enterprise Integration Patterns catalogue (enterpriseintegrationpatterns.com); OpenAPI for APIs, AsyncAPI for events, plain SFTP or object storage for files.

4Gains vs losses nothing is free

What we gain

  • Each need gets the right shape: speed, confirmation, completeness.
  • Loose coupling: no shared tables.
  • Safety nets: the nightly file catches missed events.
  • Clear reasoning in the ADR.
  • Swappable later behind one adapter.

What we lose

  • Several mechanisms to build and run.
  • More to monitor: webhooks, API, files.
  • Consistency between styles needs care.
  • More upfront thinking than “just use the API”.

6Common pitfalls the usual ways this goes wrong

  • Shared database as a shortcut

    Reading the vendor's tables. Fix → never couple to another system's schema.

  • One style for all

    Polling the API every second for changes. Fix → events for changes; API for commands.

  • No reconciliation

    A missed webhook means wrong stock forever. Fix → a periodic full comparison (the nightly file).

  • Style before needs

    “We'll use webhooks” before listing needs. Fix → list needs, then match styles.

7When to use it (and when not)

Use it when…

  • Every new integration with another system or vendor.
  • Reviewing an integration that keeps breaking.
  • Vendor selection: which styles do they support?
  • Replacing a shared-database integration.

Skip it when…

  • Calls inside one module.
  • Trivial one-off data loads.

8Self-check quiz

What are the four integration styles?

Shared database, file transfer, remote calls (APIs), messaging (events).

Which style fits “tell me when stock changes”?

Messaging: events, here via webhooks.

Why was the database view rejected?

It couples Larder to WMS B's internal tables.

Why keep the nightly file if there are webhooks?

To reconcile: webhooks can be missed.
