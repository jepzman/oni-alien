Batch & File Transfer

TL;DR

Files on a schedule are the oldest integration style, and still the right one for “all of yesterday”: settlements, reconciliations, reports, bulk loads. Do it properly: a known arrival time, checks (checksum, row count, a trailer), load each file exactly once (record what you've loaded), stage before applying, alert when a file is late or wrong, and report mismatches to the people who act on them.

  • Family: integration styles
  • Origin: file transfer, the first of Hohpe and Woolf's integration styles; decades of banking practice
  • Lives in: a scheduled job with monitoring, owned by a named team
  • Pairs with: integration style, idempotency, SaaS & vendor integration

1The situation Larder, 10 May 2027

Every morning someone in Marco's finance team downloads the two payment providers' settlement files by hand, pastes them into a spreadsheet and matches them with orders. In April one file arrived twice and was counted twice; in May a file was a day late and nobody noticed for a week. The most boring integration was causing the most expensive errors.

  • Manual file handling fails quietly: duplicates, gaps, wrong days.
  • Nobody owns “the file didn't come”.
  • Batch gets less design attention than APIs, though money flows through it.

2Real-life analogy the bank's night safe

Shops drop their takings in a bank's night safe: sealed, numbered bags, one per shop per day. In the morning the bank counts each bag once (even if a shop dropped it twice by mistake), checks it against the slip, and calls any shop whose bag didn't arrive by 10:00. Nobody finds out at the end of the month.

3How it solves it arrive, check, load once, alert

Cho and Eli built the pipeline in a week. Providers drop files by 05:00; a job checks the checksum and row count, records the file name so it's never loaded twice, stages the rows and matches them with orders. No file by 07:00 means an alert to finance and on-call. Marco's team now reads a one-page mismatch report instead of building a spreadsheet; the same pattern later took WMS B's nightly stock file.

  1. Agree the contract

    File name pattern, format, columns, trailer with row count, arrival time.

  2. Check before loading

    Checksum, row count, date in the name, schema.

  3. Load exactly once

    Record each file processed; ignore repeats.

  4. Stage, then apply

    Load into a staging table; apply only if checks pass.

  5. Alert on late or bad files

    A deadline per file; alert the owner and on-call.

  6. Report mismatches to who acts

    A short daily report, not a dump.

Vocabulary for the exam

Batch
Processing a set of records together, on a schedule.
Settlement file
A provider's list of payments paid out, per day.
Idempotent load
Loading the same file twice has the same effect as once.
Trailer
A last line with totals or a row count, for checking.
Staging table
A temporary table to check data before applying it.
Reconciliation
Matching two records of the same thing.
jobs/settlements/README.mdthe settlement file contract and job (excerpt)
# Settlement files · owner: Cho (payments) · alerts: finance + on-call

Arrival     SFTP /in/settlements/ by 05:00 CET, one file per provider per day
Name        {provider}_settlement_{YYYY-MM-DD}.csv     e.g. psp1_settlement_2027-05-09.csv
Trailer     last line: TRAILER,<row_count>,<sum_amount_cents>
Job 05:15   1 already loaded? (processed_files table) → skip, log
            2 checksum, row count and sum match the trailer? → else quarantine + alert
            3 load into staging_settlements; match with orders and refunds
            4 write mismatches to the daily report (finance channel, 08:00)
Deadline    07:00 · no file → alert "psp1 settlement missing for 2027-05-09"

tools: SFTP or object storage drops, a scheduler (cron, Airflow, a cloud scheduler), a processed-files table, checksum tools, alerts in your monitoring.

4Gains vs losses nothing is free

What we gain

  • No double counting: each file loaded once.
  • Missing files noticed by 07:00, not a week later.
  • Bad files quarantined, not applied.
  • Finance freed from manual downloads.
  • A reusable pattern for every file integration.

What we lose

  • Latency: yesterday's data, by design.
  • Another job to run and monitor.
  • Vendors change formats without warning.
  • Not for real-time needs.

6Common pitfalls the usual ways this goes wrong

  • Loading twice

    The same file counted twice. Fix → record processed files; skip repeats.

  • No deadline

    A missing file noticed a week later. Fix → an arrival time and an alert.

  • Applying unchecked

    A half-written file loaded. Fix → checksum, row count, staging first.

  • Dumping everything

    A 4,000-row report nobody reads. Fix → report only mismatches, to who acts.

7When to use it (and when not)

Use it when…

  • Settlements, reconciliations, reports, bulk loads.
  • Vendors that only offer files.
  • Safety nets for event integrations.
  • Large volumes where real time isn't needed.

Skip it when…

  • Anything that must be seen within minutes: use events.
  • Commands that need an answer: use an API.

8Self-check quiz

When is file transfer the right style?

For “all of a period”: settlements, reconciliations, bulk loads.

How do you avoid loading a file twice?

Record each processed file and skip repeats.

What's a trailer for?

A row count and totals to check the file is complete.

What happens if a file is late?

An alert at a set deadline, to the owner and on-call.

try it

Find a file your team or finance receives regularly. Write its contract (name, arrival time, trailer), then check: would a duplicate be loaded twice? Would a missing file be noticed today? Fix the worse of the two.

remember!!

Numbered bags, counted once, and a call by 10:00 if one's missing.
