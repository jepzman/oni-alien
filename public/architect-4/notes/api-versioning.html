API Versioning Strategy

TL;DR

A published API is a promise to systems you don't control. Have a versioning policy before the first breaking change: within a version, only additive changes (new optional fields, new endpoints); a breaking change (rename, remove, retype, change meaning) means a new major version. Run old and new side by side, give a dated end with plenty of notice, signal it in the API (deprecation and sunset headers), and watch who still calls the old one.

  • Lives in: a policy page linked from the API docs
  • Pairs with: API-first design, event-driven integration, backend for frontend

1The situation Larder, 21 June 2027

The Business API went live in May; Korenwolf and two other offices now order through it. Korenwolf asks for several delivery addresses per office and a cost centre per line. Ben's first change renames delivery_address to deliveries, which would break three clients' systems overnight. There's no policy for changing a published API, so the fix depends on who notices in review.

  • Consumers you don't control can't upgrade on your schedule.
  • “Small” renames are breaking changes.
  • Without a policy, every change is a negotiation, or an accident.

2Real-life analogy the power socket

New appliances add features all the time, but the plug stays the same. When a country changes its socket standard, it announces a date years ahead, sells adapters, and old sockets keep working until then. Nobody wakes up to find their kettle doesn't fit.

3How it solves it add within, break in a new version

Ana and Ben wrote the policy that week. The cost centre per line went into v1 as an optional field: additive, nobody broke. Several addresses per office changed the meaning of an order, so it became v2, shipped in September. v1 runs for twelve months after v2, with six months' notice before the end and a Sunset header on every response; telemetry shows who still calls v1, and Mo phones each client.

  1. Version in the path from day one

    /business/v1: cheap now, priceless later.

  2. Define breaking

    Rename, remove, retype, make optional required, change meaning.

  3. Additive within a version

    New optional fields and endpoints; consumers ignore what they don't know.

  4. Breaking → new major version

    Run both side by side.

  5. Announce a dated end

    Notice period, deprecation and Sunset headers, docs, a call from the account manager.

  6. Watch usage

    Telemetry per version and client; don't switch off until it's zero, or agreed.

Vocabulary for the exam

Breaking change
A change that makes existing consumers fail.
Additive change
A new optional field or endpoint; safe for consumers.
Major version
A new version allowed to break the old contract.
Deprecation
Announcing that something will be removed.
Sunset
The date a version stops working (HTTP Sunset header, RFC 8594).
Tolerant reader
A consumer that ignores fields it doesn't know.
api/business/VERSIONING.mdLarder Business API versioning policy, 21 June 2027
# Business API · versioning policy                              owner: Ben · contact: Mo

1. The major version is in the path: /business/v1, /business/v2.
2. Within a version, only additive changes: new optional fields, new endpoints,
   new enum values documented as "may grow". Clients must ignore unknown fields.
3. Breaking = rename, remove, retype, optional → required, change of meaning.
   Breaking changes ship only in a new major version.
4. Old and new run side by side for 12 months after the new version ships.
5. 6 months before the end: email + Mo calls each client; every v1 response carries
   Deprecation and Sunset headers (RFC 8594).
6. Telemetry per version and client; v1 is switched off only at zero calls or by agreement.

2027: v1 + lines[].cost_centre (Jun, additive) · v2 deliveries[] per office (Sep)

tools: path versioning in the API gateway or router; OpenAPI files per version; breaking-change detection (oasdiff, openapi-diff) in CI; Deprecation and Sunset headers; usage analytics per client.

4Gains vs losses nothing is free

What we gain

  • No client broken overnight.
  • Additive changes ship freely.
  • Clear rules instead of negotiations.
  • Planned upgrades with notice.
  • Visibility of who still uses old versions.

What we lose

  • Two versions to run for a year.
  • Policy overhead for small changes.
  • Clients still upgrade late.
  • Tempting to never remove old versions.

6Common pitfalls the usual ways this goes wrong

  • No version in the path

    The first breaking change has nowhere to go. Fix → /v1 from day one.

  • Renames as tidy-ups

    “Just a better name.” Fix → renames are breaking: new version or keep both.

  • No end date

    v1 runs forever. Fix → a dated end, announced, with telemetry.

  • Silent deprecation

    Clients find out when it stops. Fix → headers, email, and a call from the account manager.

7When to use it (and when not)

Use it when…

  • Any API consumed by systems you don't control.
  • B2B and partner APIs.
  • Public APIs.
  • Before the first breaking change, ideally before launch.

Skip it when…

  • APIs used only by one team that deploys both sides together.
  • Private calls inside one module.

8Self-check quiz

Name four kinds of breaking change.

Rename, remove, retype, optional → required (or change of meaning).

What may change within a version?

Additive changes: new optional fields and endpoints.

How long did Larder run v1 alongside v2?

Twelve months, with six months' notice before the end.

How do you know when v1 can go?

Telemetry shows zero calls, or each client has agreed.

try it

Write your API's versioning policy in six lines, using Larder's as a model. Add a breaking-change check (an OpenAPI diff) to CI. Then find out, from logs, every client calling your oldest version.

remember!!

Keep the plug. A new standard comes with a date and adapters.
