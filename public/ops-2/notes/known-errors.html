We Know the Bug, Now What?

TL;DR

A known error is a problem whose cause, or at least whose workaround, is known but not yet fixed. Write each one down where the first line will find it: the symptom in users' words, how to recognise it, the workaround as steps, who can apply it, and the fix date if there is one. It stops engineers being interrupted for things already solved, and it's the list that tiered support runs on.

1The situation Larder, September 2026

From 1 September Sam's team handles store tickets first, but the fixes they could use are in engineers' heads and old chat threads. The picker app freezing after an Android update, the label printer printing blank labels, the courier app's login loop: each one is known and has a workaround. Each still comes back to an engineer every time, and the Rotterdam printer took four hops and two days.

  • The first line can only forward what they can't look up.
  • Engineers solve the same thing again from memory.
  • Workarounds differ depending on who you ask.

2Real-life analogy the car service bulletin

When a car model has a known fault, the manufacturer sends every garage a service bulletin: “warning light in cold weather; harmless; reset it with steps 1–3; permanent fix in the March software update”. A mechanic who meets it doesn't spend an hour rediscovering it, and the customer gets the same answer at every garage.

3How it solves it one line per known error, in store words, retired when fixed

Eli and Sam start ops/known-errors.md in September, and the helpdesk can search it. Each entry has a number, the symptom in store words (“labels print blank”, not “printer driver fault”), how to recognise it (to avoid applying the wrong fix), the workaround as numbered steps, who can apply it (store lead, first line, on-call), the problem it belongs to, and the fix date if there is one.

By October there are 11 known errors. KE-03 (stock sync stuck) is retired when PRB-003's fix lands. KE-04 (picker app freezes after an Android system update: restart from the device tool) stays until Dee's team defers system updates to 23:30. KE-07 (blank labels: power-cycle and reload the roll) stays for good, because it's the printer's own quirk. Each new fix from a swarm becomes a new entry before the ticket is closed. In October Sam's team fixes 38 % of store tickets straight from the list.

  1. Collect fixes people apply from memory

    Old chats, repeat tickets, engineers.

  2. Write the symptom as users say it

    That's what the first line searches for.

  3. Say how to recognise it

    So the wrong workaround isn't applied.

  4. Write the workaround as steps

    With who is allowed to apply it.

  5. Link it to its problem and fix date

    So it can be retired.

  6. Retire it when the fix lands

    A stale workaround is a new bug.

Vocabulary for the exam

Known error
A problem with a documented cause or workaround, not yet fixed.
Known error database (KEDB)
The list of known errors, searchable by the people who need it.
Workaround
Steps that reduce or remove the effect until the fix.
Symptom
What the user sees and says.
Retire
Remove an entry once its fix has landed and been checked.
First-line fix rate
The share of tickets fixed by the first line alone.

4The maturity ladder where are we, and what is the next rung?

1By hand

in engineers' heads

  • Same fix rediscovered.
  • First line forwards everything.

2Written down Larder now

a searchable list in store words

  • Workarounds as steps.
  • Linked to problems; retired when fixed.

3Scripted

suggested automatically

  • The helpdesk suggests entries from ticket text.
  • Usage counted per entry.

4Automatic

fixed at the source

  • Entries with high usage get prioritised fixes.
  • The list shrinks over time.

6Common pitfalls the usual ways this goes wrong

  • Engineer words

    “Driver fault in CUPS queue” nobody searches for. Fix → write the symptom as the store says it.

  • No way to recognise it

    A workaround applied to the wrong problem. Fix → say how to tell it's this one.

  • Never retired

    Old workarounds applied after the fix, breaking things. Fix → link to the problem; retire on fix.

  • A list instead of a fix

    Known errors pile up for years. Fix → high-use entries push their problems up the queue.

7When to use it (and when not)

Use it when…

  • The first line forwards things engineers fix in a minute.
  • The same workaround is explained again and again.
  • Problems are open with no fix date yet.
  • Before giving stores self-service (vol. 4).

Skip it when…

  • A fault that's fixed today: no entry needed.

8Self-check quiz

What is a known error?

A problem with a documented cause or workaround that isn't fixed yet.

Why write the symptom in store words?

That's what the first line and the stores search for.

Why include “how to recognise it”?

So the workaround isn't applied to a different problem with a similar symptom.

When is an entry retired?

When its problem's fix has landed and been checked.

Why is KE-07 permanent?

It's a quirk of the printer, not a fault Larder can fix.

what would you do?Dee's team ships the fix for KE-04 on Tuesday. On Thursday Sam's team still restarts frozen handhelds from the list. What went wrong, and what's the fix?

KE-04 wasn't retired when its fix shipped. Retire it now, check whether the freezes really stopped (if not, reopen PRB-005), and make retiring entries part of closing a problem.

try it

Write down five fixes you apply from memory. For each, write the symptom as the user would say it, how to recognise it, the workaround as steps and who can apply it. Give the list to whoever answers first.

remember!!

A fix in one engineer's head gets rediscovered every week. Write it as the user says it, and retire it when the real fix lands.
