Performance Budgets

TL;DR

A performance budget is an agreed limit on something users feel (load time, response time) or something that causes it (bundle size, number of calls), with an owner and an automatic check. Without one, performance erodes by small, reasonable changes until it's bad. With one, a breach fails the build and is fixed while it's small.

  • Family: size & speed
  • Origin: web performance practice (Tim Kadlec, Addy Osmani); SLOs for APIs
  • Lives in: CI checks and a budgets page
  • Pairs with: quality attribute scenarios, load profiles, fitness functions

1The situation Larder, 15 November 2027

Antwerp brought French to the apps and the web shop. On a mid-range Android phone over 4G, the web home page went from 1.9 to 3.4 seconds between September and November; the app's JavaScript grew to 410 KB. Each change (translations, a new font, a promotions banner) was small and reasonable. Nobody had agreed a limit, so nothing failed.

  • Performance erodes in small steps nobody notices.
  • Developers test on fast laptops and fast Wi-Fi.
  • “Fast” means something different to everyone.

2Real-life analogy the baggage allowance

An airline agrees a baggage allowance (23 kilos) and checks it at the desk. Every traveller wants to add just one more thing; the scale stops it at the desk, early and cheaply, not when the plane is too heavy to take off.

3How it solves it limits users feel, owners, CI checks

Ana, Dee and Ben agreed five budgets, each with an owner: home page ≤ 2.5 s on a mid-range Android over 4G, JavaScript ≤ 300 KB compressed (Dee); checkout API p95 ≤ 800 ms at 5× (ASR 3) and search ≤ 300 ms (Ben); picker scan to next item ≤ 1 s (Eli). Lighthouse CI and the load-test thresholds check them; a breach fails the build. Dee lazy-loaded the language files: home page 2.2 s.

  1. Pick what users feel

    Load time, response time, time to the next task.

  2. Set limits on real devices

    Mid-range phones, real networks, peak load.

  3. Add cause budgets

    Bundle size, image weight, calls per screen.

  4. Give each an owner

    Who decides when it's breached.

  5. Check automatically

    In CI, on every change; fail the build.

  6. Review quarterly

    Tighten as you improve; never loosen silently.

A breach fails the build. Exceptions: the owner decides, in writing, for one release only.

tools: Lighthouse CI or WebPageTest, bundle-size checks, k6 or Gatling thresholds, real-device testing; a budgets page in the docs.

4Gains vs losses nothing is free

What we gain

  • Erosion stopped at the first step.
  • “Fast” defined in numbers.
  • Real devices, not laptops.
  • Owners decide exceptions.
  • Cheap fixes, caught early.

What we lose

  • Builds fail for performance.
  • Setting good limits takes data.
  • Measurement noise can be annoying.
  • Pressure to loosen budgets.

6Common pitfalls the usual ways this goes wrong

  • Fast-laptop limits

    Measured on the developer's Mac. Fix → mid-range phones, real networks.

  • No owner

    Breaches argued in chat. Fix → one owner decides.

  • Warnings only

    Yellow warnings everyone ignores. Fix → fail the build.

  • Too many budgets

    Thirty numbers. Fix → a handful users feel, plus key causes.

7When to use it (and when not)

Use it when…

  • Customer-facing apps and web shops.
  • APIs with response-time requirements.
  • Before adding languages, markets or features that add weight.
  • Operational tools where seconds matter (pickers).

Skip it when…

  • Batch jobs where only the end time matters (use a deadline instead).

8Self-check quiz

What makes a performance budget work?

An agreed limit, an owner and an automatic check that fails the build.

Why measure on mid-range phones over 4G?

That's what many customers use; laptops on Wi-Fi hide slowness.

What went wrong at Larder?

Small changes for Antwerp made the home page 3.4 s with no limit to stop them.

What fixed it?

Lazy-loading language files: back to 2.2 s.

try it

Pick the screen or API your customers use most. Measure it on a mid-range phone or at peak load, set a budget slightly better than today, name an owner, and add a check to CI that fails the build when it's broken.

remember!!

Weigh the bag at the desk, not on the runway.
