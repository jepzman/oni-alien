## 0. Starting a new handbook: the mechanics

Everything below already works; a new book is mostly configuration.

1. **Outline**: `content/handbooks/<key>/book.py`, same format as `cloud-identity/book.py`: `key`, `series`, `no`,
   `title`, `subtitle`, `shelf_blurb`, `audience`, `promise`, `example`, `parts` (each chapter is
   `(num, slug, title, summary, topics)`), and `appendices` as **4-tuples** `(letter, slug, title, desc)`. Set
   `next=<n>` to badge the first chapter to be written; remove it when the book is complete.
2. **Register it**: add the key to `BOOKS` in `scripts/build_handbooks.py`. With no chapter written, the book gets only
   a contents page ("This book is being written…", a "next up" badge), no `all.html`, no PDF and no `journals.json`
   entry, and its shelf card says "coming soon · N chapters planned". (Restored 2026-11-27; tested with an empty book.)
3. **Cover**: add `.book--hb<no> { --cover: …; --band: …; }` to `public/assets/bujo.css`. Taken: Handbook 1 ink blue
   `#16384A`/`#3FB4CE`, Handbook 2 aubergine `#2E2650`/`#A08BE8`. Suggested: **3** pine `#1F3D2E`/`#5CC98A`,
   **4** rust `#4A2A1C`/`#E08A4F`, **5** slate blue `#22324A`/`#7FA6E0`, **6** plum `#3D1F3A`/`#D47FC0`,
   **7** olive `#36381C`/`#C8C45A`, **8** graphite `#2A2A2A`/`#B5B5B5`.
4. **Chapters**: `content/handbooks/<key>/<nn>-<slug>.html` (body only; a chapter is "written" when its file exists).
   IDs must be unique across the book (`s<n>-<m>`, `fig<n>-<m>`, markers `c<n>…`, `sum<n>`); cross-references
   `href="#ch<n>"` and `href="#appX"`.
5. **Appendices**: A–C hand-written as `appendix-<x>-<slug>.html`; **D (glossary) and E (answers) are generated by the
   build** from every chapter's `<dl class="terms">` and `<ol class="quiz">`. Keep `<dt>…</dt><dd>…</dd>` on one line
   and one `<p>` question + `<details>` answer per quiz item, or the generators miss them.
6. **PDFs**: never-rendered PDFs always render; also add `handbooks/<key>` to `rebuild` in `pdf-build.json` for the
   first deploy, and check with `node scripts/build-pdf.mjs --dry-run`.
7. **Story**: new Larder facts go into `docs/larder-casebook.md` under "Series 3 · <title> (handbook facts)". Each book
   gets its own `docs/HANDOFF-handbook-<no>-<key>.md` once approved (copy the structure of the identity handoff).
8. **Checks per part** (scripts live only in the session scratchpad; rewrite them, they're short): every printed lab
   script byte-identical to the file actually run, outputs pasted from real runs; unique ids, aria-labelledby and
   marker references resolve, no unresolved `#ch`/`#app` links; figures at 1280 px and 375 px, light and dark, no
   horizontal overflow; print clipping of `all.html` (Playwright, `emulateMedia('print')`).

## 1. Series-wide decisions for the owner

1. **Order**: 3 Kubernetes, 4 Terraform, 5 PostgreSQL, then 6 Observability, 7 CI/CD, 8 Linux? (Linux could also go
   earlier as a foundation book; it's the most beginner-friendly.)
2. **Length**: Handbooks 1–2 have 25 chapters. Proposed: 3, 4 and 5 at **24–25**; 6–8 at **18–20** (narrower topics).
3. **Provider**: AWS stays the main worked provider where a cloud matters (EKS, Terraform's AWS provider, RDS/Aurora),
   with Azure and Google Cloud in an "Across providers" section. Handbook 5 is mostly provider-neutral (plain
   PostgreSQL), with managed services compared in Part V.
4. **Labs**: local and free wherever possible (kind, Terraform with local providers, Postgres in a scratch directory),
   optional cloud steps under ~$1 with clean-up, as before.
5. **Larder stays** the running example, moving forward in time (see §2).

## 3. Handbook 3 · Kubernetes in Practice

**Subtitle**: *From one pod to a platform teams can use.* **Audience**: developers and operators who deploy
containers and have used `kubectl apply` without being sure what happens next. **Outcome**: run, debug and operate
workloads on Kubernetes; design a cluster and a platform for several teams on EKS; read the same on AKS and GKE.
**Labs**: `kind` on a laptop for nearly everything (free), optional EKS steps (an EKS cluster costs about $0.10/hour
plus nodes, so those labs are short with strict clean-up).

**Story**: November 2028. Larder runs about 40 containerised services on ECS, plus Engine A's batch runs and a few VM
jobs. Five product teams, the golden path, and the reliability team. Pain points: per-service ECS task definitions and
pipelines copied 40 times, batch jobs fighting for capacity at 05:00, cost per order (FF-10), and Lotte's experience.
Eli reopens the 2027 recommendation with Ana: ADR 0030, move to EKS in stages, staging first, Dispatch last (its tier-1
readiness is due in 2029). Ends with Larder's platform running on EKS, mid-2029. Ties: H1 ch. 19 (pod networking,
the `/20` exhaustion, custom networking with `100.64.0.0/16`), H2 ch. 16 (Pod Identity, access entries, RBAC).

## 4. Handbook 4 · Infrastructure as Code with Terraform

**Subtitle**: *State, modules and pipelines you can trust.* **Audience**: engineers who've written some Terraform
by copying, and been scared of `terraform apply` since. **Outcome**: structure, test and run Terraform for a real
organisation: state, modules, environments, drift, refactoring, CI, and policy as code. **Labs**: mostly with
providers that need no cloud account (`local`, `random`, `null`, `http`, a local Postgres via the `postgresql`
provider) so they're free and repeatable; optional AWS steps under $1. OpenTofu noted alongside Terraform throughout.

**Story** (a retrospective, chapters move forward in time as Handbook 2 did): November 2026, Larder's production was
built by hand in Jasper's console; Handbook 1's network was the first Terraform. Episodes already in the canon, told
from the code's side: staging rebuilt from code (Bram, 2 Mar 2027); VMs rebuilt from code (June 2027); the identity

minutes (Aug 2028). New episodes to add: a state file edited by two applies at once (no locking yet), a

orders database, a module refactor done with `moved` blocks.

## 5. Handbook 5 · Running PostgreSQL in Production

**Subtitle**: *Schemas, queries, backups and upgrades, without the 3 a.m. surprises.* **Audience**: application
developers who use Postgres through an ORM, and operators who inherited a database. **Outcome**: design schemas and
indexes, read query plans, size connections, run backups and restores you've tested, replicate, upgrade and migrate
without downtime; choose and run a managed service (RDS/Aurora, Azure Database for PostgreSQL, Cloud SQL/AlloyDB).
**Labs**: real PostgreSQL 16 in a scratch directory (`initdb`, `pg_ctl`), free; `pgbench` for load; optional RDS step.

**Story** (a retrospective from the database's side, October 2025 → August 2028; the richest existing canon on the
shelf): Larder Core's single Django-on-Postgres database with shared tables; (new) a slow checkout query at the first
Christmas, 2025; the 29 Oct 2026 network cut; the 12 Nov 2026 backup retention change (H2 ch. 1); the 18 Dec 2026 failover
with stuck connection pools; Postgres 13 → 16 on 18 May 2027 with logical replication; restores from 3 h 40 to 22
minutes in 2028; ADR 0027, Ordering's own database (expand, shadow, Eindhoven first, contract on 21 Aug 2028);
Haarlem born on the new database. Ben and Bram are the main characters, with Eli. New detail to add: one slow query
and its plan, one bloat episode, one lock queue behind a migration.

| Part | Chapters |
| --- | --- |
| I · How Postgres works | 1 A database you can reason about (processes, memory, files, MVCC in one picture) · 2 Transactions and isolation (new episode: one courier assigned two orders by two concurrent requests) · 3 Data types and constraints that do your validation · 4 Schema design for an application that will grow |
| II · Queries and indexes | 5 Reading a query plan (`EXPLAIN (ANALYZE, BUFFERS)`) · 6 Indexes (B-tree, partial, expression, multicolumn, GIN, BRIN) · 7 Fixing slow queries (statistics, `pg_stat_statements`, N+1 from the ORM) · 8 Pagination, counting and reporting queries |

| V · Change and scale | 17 Schema migrations without downtime (expand/contract; Django migrations) · 18 Major-version upgrades (13 → 16 with logical replication) · 19 Partitioning and archiving · 20 Splitting a database (ADR 0027: Ordering's own database) · 21 Managed Postgres compared (RDS, Aurora, Azure, Cloud SQL, AlloyDB) |
