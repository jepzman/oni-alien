## 0. Starting a new handbook: the mechanics

Everything below already works; a new book is mostly configuration.

1. **Outline**: `content/handbooks/<key>/book.py`, same format as `cloud-identity/book.py`: `key`, `series`, `no`,
   `title`, `subtitle`, `shelf_blurb`, `audience`, `promise`, `example`, `parts` (each chapter is
   `(num, slug, title, summary, topics)`), and `appendices` as **4-tuples** `(letter, slug, title, desc)`. Set
   `next=<n>` to badge the first chapter to be written; remove it when the book is complete. The `example` text
   introduces the running story (Stagedoor), not Larder.
2. **Register it**: add the key to `BOOKS` in `scripts/build_handbooks.py`. With no chapter written, the book gets only
   a contents page ("This book is being written…", a "next up" badge), no `all.html`, no PDF and no `journals.json`
   entry, and its shelf card says "coming soon · N chapters planned". (Restored 2026-11-27; tested with an empty book.)
3. **Cover**: add `.book--hb<no> { --cover: …; --band: …; }` to `public/assets/bujo.css`. Taken: Handbook 1 ink blue
   `#16384A`/`#3FB4CE`, Handbook 2 aubergine `#2E2650`/`#A08BE8`. Suggested: **3** graphite `#2A2A2A`/`#B5B5B5`,
   **4** pine `#1F3D2E`/`#5CC98A`, **5** rust `#4A2A1C`/`#E08A4F`, **6** slate blue `#22324A`/`#7FA6E0`,
   **7** plum `#3D1F3A`/`#D47FC0`, **8** olive `#36381C`/`#C8C45A`.
4. **Chapters**: `content/handbooks/<key>/<nn>-<slug>.html` (body only; a chapter is "written" when its file exists).
   IDs must be unique across the book (`s<n>-<m>`, `fig<n>-<m>`, markers `c<n>…`, `sum<n>`); cross-references
   `href="#ch<n>"` and `href="#appX"`. Story boxes keep the class `.box-story` (label "At Stagedoor").
5. **Appendices**: A–C hand-written as `appendix-<x>-<slug>.html`; **D (glossary) and E (answers) are generated by the
   build** from every chapter's `<dl class="terms">` and `<ol class="quiz">`. Keep `<dt>…</dt><dd>…</dd>` on one line
   and one `<p>` question + `<details>` answer per quiz item, or the generators miss them.
6. **PDFs**: never-rendered PDFs always render; also add `handbooks/<key>` to `rebuild` in `pdf-build.json` for the
   first deploy, and check with `node scripts/build-pdf.mjs --dry-run`.
7. **Story**: once Stagedoor is approved, create `docs/stagedoor-casebook.md` from §2 and add every new fact there,
   book by book. Each book gets its own `docs/HANDOFF-handbook-<no>-<key>.md` when its writing starts.
8. **Checks per part** (scripts live only in the session scratchpad; rewrite them, they're short): every printed lab
   script byte-identical to the file actually run, outputs pasted from real runs; unique ids, aria-labelledby and
   marker references resolve, no unresolved `#ch`/`#app` links; figures at 1280 px and 375 px, light and dark, no
   horizontal overflow; print clipping of `all.html` (Playwright, `emulateMedia('print')`).

## 3. Handbook 3 · Linux for Cloud Engineers

**Subtitle**: *The server under everything, explained.* **Audience**: developers and new operations people who can
`ssh` in and `cd` around, but freeze when a server misbehaves. **Outcome**: run, secure, automate and troubleshoot Linux
servers in the cloud with confidence; understand what containers are made of. **Labs**: a terminal on any Linux (a
container, WSL, or a disposable VM with Multipass for systemd and networking labs); free. Optional: one EC2 instance
for an hour (about $0.01) for cloud-init and instance metadata.

**Story**: January to October 2026. Rafaela inherits Stagedoor's three servers, nobody's notes, and a root password in
the team chat. Tiago starts a month later and learns alongside her. Episodes: the on-sale night the disk filled with
logs (logrotate wasn't set up for the app); Postgres killed by the OOM killer when a report ran during a sale; "too
many open files" at nginx in the first ten minutes of a big on-sale; a cron job that worked by hand but not at 03:00
(PATH); an uploads directory set to 777; a contractor's SSH key still in `authorized_keys`; a certificate that expired
on a Sunday; a deploy that killed requests mid-flight (signals). Ends with servers rebuilt from a checklist and a
script, ready for the move to AWS (Handbook 5).

| II · Processes and services | 5 Processes and signals (graceful shutdown, the deploy that dropped requests) · 6 systemd: services, units and timers (replacing the cron job; the PATH bug) · 7 Logs (journald, syslog, logrotate; the full disk) · 8 Packages and updates (apt, unattended upgrades, when to reboot) |

## 6. Handbook 6 · Running PostgreSQL in Production

**Subtitle**: *Schemas, queries, backups and upgrades, without the 3 a.m. surprises.* **Audience**: application
developers who use Postgres through an ORM, and operators who inherited a database. **Outcome**: design schemas and
indexes, read query plans, size connections, run backups and restores you've tested, replicate, upgrade and migrate
without downtime; choose and run a managed service (RDS/Aurora, Azure Database for PostgreSQL, Cloud SQL/AlloyDB).
**Labs**: real PostgreSQL 16 in a scratch directory (`initdb`, `pg_ctl`), free; `pgbench` for load; optional RDS step.

**Story** (spans 2023–2028, chapters move forward in time): Sasha owns the schema; Tiago learns databases through it.
Episodes: the 2023 schema Leonor wrote in a weekend; two fans sold the same seat in 2026 (a race between two requests,
fixed with constraints and `SELECT … FOR UPDATE SKIP LOCKED` for seat holds); an `ALTER TABLE` stuck behind a long
report, with every checkout queued behind it; bloat on the seat-holds table; the move to RDS with the AWS migration
(Handbook 5); connection exhaustion at an on-sale, fixed with a pooler; read replicas for the event pages; a restore
that took four hours and then fifteen minutes once practised; a major-version upgrade with logical replication;
partitioning the tickets table; splitting payments into their own database.
