Observing and troubleshooting networks

Every chapter so far ended with “when it doesn't work”. This one is about doing that well, every time: a method that finds network faults in minutes instead of hours, the patterns that point straight at a cause, and the tools that let you see what the network actually did rather than what you think it should have done.

By the end you can

  • Work through a connectivity problem with a repeatable method.
  • Recognise the common failure patterns and what each points to.
  • Read and query VPC flow logs, and know what they don't show.
  • Choose between configuration analysis, flow logs, packet captures and metrics.

Before you start

  • The whole of Parts I and II; in particular, errors by layer (Chapter 1) and both directions of a path (Chapter 4).
  • Security groups and NACLs (Chapter 9).

At Larder

The orders team launches a new cache cluster to speed up product pages. Within an hour, dashboards show about a third of cache calls timing out after two seconds. Not all of them, not none: about a third, steadily, at every hour of the day. Ben's team suspects the cache client library. The cache's own metrics look healthy.

“About a third” is a very specific number in a system that runs in three zones. Section 22.4 shows how Eli confirmed it in ten minutes with one flow-log query.

22.1The big picture

Network problems feel mysterious because the network is invisible. They stop being mysterious when you replace guessing with three habits: describe the symptom precisely, follow the packet's path hop by hop in both directions, and prove each step with data before changing anything. Tools help, but the method matters more than any tool.

22.2A method

  1. Name the exact error. Timeout, refused, reset, DNS failure, certificate error, or an HTTP status? Each points at a different layer (Chapter 1, Chapter 3). “It doesn't work” is not a symptom.
  2. Find the scope. All requests or some? From every source or one subnet, one zone, one store? Since when? “Some” is the most useful answer of all: something differs between the working and failing cases.
  3. Ask what changed. Deploys, rule changes, new subnets, certificate renewals, provider maintenance. Most incidents follow a change (Eli's change feed, in Book 5 of the notebooks, exists for this).
  4. Walk the path, both ways. For one failing source and destination: DNS answer, source security group out, source NACL, route table, gateways, destination NACL, destination security group in, and the listening process. Then the same for the reply.
  5. Prove it with data. Configuration analysis (does the path exist?), flow logs (did packets flow, and were they accepted?), and a test from the failing source.
  6. Fix one thing, then verify with a new connection. Existing connections can hide both breakage and fixes (Chapter 9).

22.4VPC flow logs

VPC flow logs record the traffic through network interfaces: who talked to whom, on which ports, how much, and whether security groups and NACLs accepted or rejected it. You can turn them on for a VPC, a subnet or one interface, and send them to CloudWatch Logs, S3 or a stream. Each record summarises one flow over an aggregation window of up to a minute or ten:

2 111122223333 eni-0a1b2c3d 10.20.33.18 10.20.64.40 51734 6379 6 4 240 1764151200 1764151260 REJECT OK

At Larder: solved

Eli ran one query over the cache subnets' flow logs: rejected flows to port 6379, grouped by source subnet. Every rejection came from 10.20.32.0/20 and 10.20.48.0/20, zones b and c; none from zone a. The new cache's security group allowed Redis from 10.20.16.0/20, zone a's app subnet, written by someone testing from a single pod. Requests are spread evenly over three zones, so two in three should have failed; the client's retry onto another connection rescued some, which is why it looked like a third. The fix, a rule allowing sg-app instead of a range (Chapter 9), took a minute.

What flow logs don't show

  • Packets dropped for lack of a route are not rejections: you'll see an ACCEPT at the source and nothing at the destination. Silence at the far end is the clue.
  • Some traffic isn't logged at all: queries to the VPC's DNS resolver (use Resolver query logs, Chapter 15), the instance metadata service, time sync and DHCP.
  • Contents: flow logs are metadata. For packets, use captures (22.6).
  • Which rule rejected a flow: flow logs say REJECT, not why. Configuration analysis does.
Extra fieldsCustom formats add useful fields: tcp-flags (see SYNs without replies), flow-direction, pkt-srcaddr (the original address behind a NAT or load balancer) and traffic-path (how traffic left the VPC: NAT, internet gateway, TGW, endpoint).

22.5Configuration analysis

Flow logs show what happened; configuration analysis shows what could happen.

  • Reachability Analyzer takes a source, a destination and a port, and works out from route tables, security groups, NACLs, gateways and load balancers whether a path exists. If not, it names the component that blocks it. You've used it since Chapter 9.
  • Network Access Analyzer asks the opposite question across a whole account: “find every path from the internet to anything in the data subnets”, or “anything in production reachable from development”. It's how you check segmentation (Chapter 11) and catch the accidentally public database before someone else does.

22.8Lab: watch the internet knock

Lab 22 · Flow logs, a rejection and a query

You'll start a small instance with a public address and no inbound rules, turn on flow logs, knock on it from your laptop, and query the rejections, including the ones from strangers scanning the internet. You need the AWS CLI and Terraform; the instance part is Lab 18's. Cost: a t4g.nano and a few kilobytes of logs, well under $0.10 for an hour.

Start from Lab 18's main.tf without the DNS Firewall resources (or keep them; they don't matter here), and add:

flowlogs.tfTerraform ≥ 1.5, AWS provider 5.x

resource "aws_cloudwatch_log_group" "flow" {
  name              = "/handbook/lab22/flow"
  retention_in_days = 1
}
resource "aws_iam_role" "flow" {
  name = "handbook-lab22-flow"
  assume_role_policy = jsonencode({
    Version   = "2012-10-17"
    Statement = [{ Effect = "Allow", Action = "sts:AssumeRole",
                   Principal = { Service = "vpc-flow-logs.amazonaws.com" } }]
  })
}
resource "aws_iam_role_policy" "flow" {
  role = aws_iam_role.flow.id
  policy = jsonencode({
    Version   = "2012-10-17"
    Statement = [{ Effect = "Allow", Resource = "*",
                   Action = ["logs:CreateLogStream", "logs:PutLogEvents", "logs:DescribeLogStreams"] }]
  })
}
resource "aws_flow_log" "vpc" {
  vpc_id                   = aws_vpc.lab.id
  traffic_type             = "ALL"
  log_destination_type     = "cloud-watch-logs"
  log_destination          = aws_cloudwatch_log_group.flow.arn
  iam_role_arn             = aws_iam_role.flow.arn
  max_aggregation_interval = 60
}
output "public_ip" { value = aws_instance.vm.public_ip }
  1. Create it with terraform init and terraform apply.
  2. Knock. From your laptop: nc -vz -w 3 $(terraform output -raw public_ip) 22 and the same for port 5432. Both time out: the security group has no inbound rules, and it drops silently.
  3. Wait a few minutes for records to arrive, then query in CloudWatch Logs Insights on the log group (or with aws logs start-query): 
    fields @timestamp, srcAddr, dstPort, action
| filter action = "REJECT"
| stats count(*) as attempts by dstPort
| sort attempts desc
| limit 10
    Find your own attempts on 22 and 5432, and very likely others: strangers' scanners find any new public address within minutes.
  4. Find yourself. Change the filter to srcAddr = "<your public IP>" (from curl https://checkip.amazonaws.com) and match each record to your nc attempts.
  5. Clean up with terraform destroy.

Stretch goal. Switch the flow log to a custom format with ${tcp-flags} and ${flow-direction}, repeat the knock, and find the SYN flag (value 2) on your rejected attempts.

22.9Common mistakes

MistakeWhat happensInstead
Changing things before describing the symptomThe original evidence is gone; new problems are added.Exact error, scope, timeline first.
Checking only the request pathHours spent on a route that's fine; the reply's is broken.Both directions, every time.
No flow logs until the incidentNo history to compare with.Flow logs on by default, with short, cheap retention.
Reading “no REJECT” as “network fine”Missed missing routes, which aren't rejections.Look for traffic at both ends.
Testing a fix with an existing connectionFalse confidence, either way.Verify with a new connection.
Ignoring instance network allowances“Random” drops at peak blamed on the app.Watch the ENA allowance metrics.

✓Chapter summary

  • Method beats tools: exact symptom, scope, what changed, both directions hop by hop, prove with data, fix one thing, verify with a new connection.
  • Patterns such as “a steady fraction fails” or “small works, big hangs” point straight at causes.
  • Flow logs record accepted and rejected flows per interface; missing routes show as silence, not rejection; DNS isn't in them.
  • Reachability Analyzer checks one path from configuration; Network Access Analyzer finds unintended paths across an account.
  • Use tcpdump, mtr and Traffic Mirroring for packets, and alarm on NAT, load balancer, VPN, TGW and instance allowance metrics.

Key terms

VPC flow logs
Records of traffic through network interfaces, with accept or reject.
Aggregation interval
The window over which a flow log record summarises a flow.
Reachability Analyzer
Checks whether a specific path exists, from configuration.
Network Access Analyzer
Finds paths that match a pattern across an account.
Traffic Mirroring
Copies an interface's packets to an analysis target.
Network allowance
An instance's limits on bandwidth, packets per second and tracked connections.

Check your understanding

  1. About half of requests from a service to a database time out, steadily. The service runs in two zones. What do you check first? apply

    Show answer

    What differs between the zones: the database's security group or NACL rules (a range covering only one zone's subnet), each zone's route tables, or a per-zone component such as a NAT gateway or endpoint. Flow logs grouped by source subnet will show it quickly.

  2. Flow logs show ACCEPT at the source and nothing at the destination. What does that suggest? explain

    Show answer

    The packets left the source but never arrived: usually a missing or wrong route (or a gateway dropping them), not a security group or NACL, which would show as REJECT at the destination.

  3. Why might a name-resolution problem not show up in flow logs at all? recall

    Show answer

    Queries to the VPC's own resolver aren't captured by flow logs. Use Route 53 Resolver query logs to see DNS activity.

  4. When would you use Network Access Analyzer instead of Reachability Analyzer? explain

    Show answer

    When the question is “which paths exist that shouldn't?” across many resources, such as anything reachable from the internet in the data subnets, rather than “does this one path from A to B work?”.

  5. A busy service drops packets at peak, its CPU is at 40% and nothing is rejected in flow logs. Where do you look? apply

    Show answer

    At the instance's network allowance metrics (bw_in_allowance_exceeded, pps_allowance_exceeded, conntrack_allowance_exceeded): it may be hitting its bandwidth, packet-rate or tracked-connection limits. Fixes: a larger or network-optimised instance type, more instances, or fewer connections.
