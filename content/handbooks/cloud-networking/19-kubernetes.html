Containers and Kubernetes networking

Kubernetes adds a second network inside your VPC: every pod gets its own address, services get virtual addresses that belong to no machine, and traffic is routed and filtered by software on each node. On a cloud provider, that inner network is woven into the outer one, which is powerful and easy to get wrong. This chapter explains how pods get addresses, how services and ingress find them, and how to keep a cluster from eating your address plan.

By the end you can

  • Explain the Kubernetes network model and what a CNI plugin does.
  • Compare overlay and VPC-native pod networking, and size subnets for pods.
  • Explain how Services, cluster DNS, Ingress and the Gateway API route traffic.
  • Restrict pod-to-pod traffic with network policies and security groups.

  • Security groups (Chapter 9) and load balancers (Chapter 16).

At Larder

Larder's platform team moves its services onto a managed Kubernetes cluster (EKS), with nodes in the three app subnets, 10.20.16.0/20 and friends: 4,091 usable addresses per zone. For a month, all is well. Then, during a big deploy that briefly doubles the number of pods, new pods hang in ContainerCreating with the event failed to assign an IP address to container. The cluster has CPU and memory to spare. Zone a's subnet has 11 free addresses.

Fewer than 900 pods were running in that zone. Where did 4,000 addresses go? Section 19.3 explains.

19.1The big picture

Kubernetes doesn't ship its own network. It defines a model and lets a plug-in implement it. The model has three rules: every pod gets its own IP address; every pod can reach every other pod by that address, without NAT; and agents on a node can reach all pods on it. A CNI plugin (Container Network Interface) makes it true, by giving pods addresses and setting up routes on each node.

On top of pod addresses, Kubernetes adds three things you'll configure constantly:

  • Services: stable virtual addresses and names for a changing set of pods.
  • Ingress and the Gateway API: rules for routing outside HTTP traffic to services.
  • Network policies: firewall rules between pods.

19.2Where pod addresses come from

There are two families of CNI plugin, and the difference decides how a cluster fits into your VPC:

EKS uses the Amazon VPC CNI by default: VPC-native. It's why load balancers can send traffic straight to pods (Chapter 16, IP targets), and why a cluster can burn through a subnet.

19.3How the VPC CNI hands out addresses

Each EC2 instance can hold a limited number of network interfaces (ENIs), and each ENI a limited number of addresses, both depending on the instance type. The VPC CNI attaches extra ENIs to each node and gives their secondary addresses to pods. Two consequences:

  • Max pods per node follows from the instance type: ENIs × (addresses per ENI − 1) + 2. An m5.large has 3 ENIs with 10 addresses each, so 3 × 9 + 2 = 29 pods, however much CPU is left.
  • Warm pools. To start pods quickly, the CNI keeps spare addresses ready on every node. By default it keeps a whole spare ENI's worth (WARM_ENI_TARGET=1): on an m5.large, about 9 addresses held in reserve per node, used or not.

At Larder: solved

Zone a ran about 100 nodes with about 9 pods each. The CNI attaches whole ENIs, with all their addresses, and keeps one more ENI spare: a node running 9 pods held two ENIs of pod addresses plus a warm one, about 28 addresses in all, for 9 pods. A hundred nodes made about 2,800. The rolling deploy's extra pods and nodes, and the other services in the same subnet, did the rest, and the /20 was gone.

Eli made three changes. Custom networking: a secondary VPC range, 100.64.0.0/16, with one pod subnet per zone, so pods no longer draw from the app subnets at all; traffic from pods to anything outside the VPC is translated to the node's address, so stores and other VPCs never see 100.64 addresses and the range can be reused by every cluster (Chapter 10). Prefix delegation: each address slot on an ENI now holds a /28 of 16 addresses, which raises max pods per node and reduces API calls. And smaller warm targets (WARM_IP_TARGET and MINIMUM_IP_TARGET) instead of a whole spare ENI. The app subnets went back to holding only nodes and load balancers.

Key idea

With VPC-native pods, size subnets for pods plus warm pools plus deploy surges, or give pods their own non-routed range.

19.4Services and cluster DNS

Pods come and go, and their addresses with them. A Service gives a group of pods (chosen by labels) one stable virtual address and a DNS name. The types you'll use:

Table 19.2 · Kubernetes Service types
TypeWhat it gives youUse for
ClusterIPA virtual address reachable only inside the clusterService-to-service calls (the default)
NodePortA port opened on every node that forwards to the serviceRarely directly; older load balancer setups
LoadBalancerA cloud load balancer created for the service (an NLB on AWS, with the AWS Load Balancer Controller)Non-HTTP services exposed outside the cluster
Headless (clusterIP: None)No virtual address; DNS returns the pods' own addressesDatabases and clients that pick pods themselves

A ClusterIP belongs to no machine. On each node, kube-proxy (with iptables or IPVS rules) or an eBPF data plane such as Cilium catches packets to that address and rewrites them to a healthy pod's address. Cluster DNS (CoreDNS) answers names like stock.orders.svc.cluster.local with the service's address.

The ndots surprisePods' DNS settings default to ndots:5 with several search domains, so a lookup of api.payments.example first tries api.payments.example.orders.svc.cluster.local and friends. Busy clients can multiply DNS load several times. Use fully qualified names with a trailing dot, or lower ndots for those pods.

19.5Getting traffic in: Ingress and Gateway API

For HTTP, you rarely give each service its own load balancer. An Ingress resource describes host and path rules (“api.larder.example/checkout → service checkout”), and an ingress controller implements them. On EKS, the AWS Load Balancer Controller turns Ingress resources into an ALB with listeners and rules (Chapter 16). In IP mode it registers pod addresses directly as targets, so traffic goes from the ALB straight to a pod, skipping node ports and a hop.

The Gateway API is Kubernetes' newer, more expressive replacement for Ingress. It splits responsibilities: a platform team owns the Gateway (the load balancer and its listeners), and each application team attaches its own HTTPRoutes. Larder's platform team uses it so that teams can add routes without touching the shared load balancer's settings.

19.6Filtering pod traffic

By default, every pod can reach every other pod in the cluster, across all namespaces. A network policy limits that, using labels instead of addresses, very much like security group references (Chapter 9):

policy.yamlallow only the API to reach the stock service

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: stock-from-api
  namespace: orders
spec:
  podSelector:
    matchLabels: { app: stock }        # the pods this policy protects
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api }   # who may connect
      ports:
        - { protocol: TCP, port: 8080 }

Once any policy selects a pod, only traffic that some policy allows reaches it. A common start is a default-deny policy per namespace plus explicit allows. Policies are enforced by the CNI or a companion agent; the Amazon VPC CNI enforces them when you turn on its network policy support, and Calico and Cilium do it on any cluster. A policy written for a CNI that doesn't enforce it does nothing at all, silently.

For traffic leaving the cluster to VPC resources, EKS can also give individual pods security groups. Then the database's security group can allow “the stock pods' group” rather than the whole node fleet, exactly like Figure 9.2.

19.9Lab: pods, a service and a policy on your laptop

Lab 19 · kind, a Service, cluster DNS and a NetworkPolicy

You'll run a local Kubernetes cluster, see pod and service addresses, resolve a service by name, and block traffic with a network policy. The cloud parts of this chapter work the same way, with VPC addresses instead of local ones. You need Docker, kind 0.24 or later (its default network plugin enforces network policies) and kubectl. Cost: nothing.

  1. Create a cluster: kind create cluster --name lab19, then kubectl get nodes -o wide. Note the node's address.
  2. Run a service. 
    kubectl create namespace orders
kubectl -n orders create deployment stock --image=nginx --replicas=3
kubectl -n orders expose deployment stock --port=80
kubectl -n orders get pods -o wide        # one address per pod, from the pod range
kubectl -n orders get service stock       # a ClusterIP from a different range
  3. Call it by name from a throwaway client pod: 
    kubectl -n orders run client --rm -it --image=busybox:1.36 --labels=app=api -- sh
  nslookup stock          # → the ClusterIP; full name stock.orders.svc.cluster.local
  wget -qO- stock | head -4
  cat /etc/resolv.conf    # the search domains and ndots from 19.4
  exit
  4. Deny, then allow. Apply a default-deny policy for the namespace: 
    kubectl -n orders apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny }
spec: { podSelector: {}, policyTypes: [Ingress] }
EOF
    Repeat step 3: wget now times out. Then apply the policy from 19.6 with the port changed to 80 (nginx's pods already carry the label app=stock). The client labelled app=api gets through again; start one with --labels=app=other and it still times out.
  5. Clean up: kind delete cluster --name lab19.

Stretch goal. On EKS (if you have one), run kubectl get pods -o wide and compare pod addresses with your VPC subnets; then look up your node type's max pods with kubectl get node <name> -o jsonpath='{.status.allocatable.pods}' and check it against the formula in 19.3.

✓Chapter summary

  • Kubernetes' model: every pod has an address, pods reach each other without NAT; a CNI plugin implements it.
  • Overlay CNIs use a private pod range; VPC-native CNIs use VPC addresses, so load balancers and security groups reach pods directly.
  • The VPC CNI's ENI limits set max pods, and warm pools hold extra addresses; use custom networking, prefix delegation and tuned targets.
  • Services give stable virtual addresses and DNS names; Ingress and the Gateway API route outside HTTP traffic, on EKS through ALBs with pod targets.
  • Network policies filter by labels; default deny per namespace; confirm your CNI enforces them.

Key terms

Pod
The smallest unit Kubernetes runs; one or more containers sharing an address.
CNI plugin
The component that gives pods addresses and connects them.
Overlay network
Pod traffic wrapped in node-to-node packets, using a private pod range.
VPC-native networking
Pods with real VPC addresses, routed by the VPC.
Warm pool
Spare addresses a node keeps ready for new pods.
Prefix delegation
Assigning /28 blocks instead of single addresses to node interfaces.
Service (Kubernetes)
A stable virtual address and name for a set of pods.
Ingress / Gateway API
Kubernetes resources describing HTTP routing into the cluster.
Network policy
Label-based rules allowing traffic between pods.

Check your understanding

  1. What's the maximum number of pods on a node with 4 ENIs of 15 addresses each, using the VPC CNI without prefix delegation? apply

    Show answer

    4 × (15 − 1) + 2 = 58 pods.

  2. Why can an ALB in IP mode send traffic straight to pods on EKS, but not on a cluster with an overlay CNI? explain

    Show answer

    With the VPC CNI, pod addresses are real VPC addresses that the VPC routes, so the ALB can reach them. With an overlay, pod addresses exist only inside the cluster; outside traffic must enter through nodes (NodePort) or a component on them.

  3. Pods in 100.64.0.0/16 call an API in another VPC over the transit gateway. What source address does that VPC see, and why does it matter? apply

    Show answer

    The node's address in the app subnet: the CNI translates pod traffic leaving the VPC. That's why the 100.64 range never needs routing outside the VPC and can be reused in every cluster, but also why the other side can't tell pods apart by address.

  4. You apply a NetworkPolicy and nothing changes: every pod can still reach the protected one. Name two possible causes. apply

    Show answer

    The CNI doesn't enforce network policies (or the feature isn't turned on); or the policy's podSelector doesn't match the pods' actual labels or namespace, so it selects nothing.

  5. Design question: a platform team wants teams to add their own HTTP routes without editing the shared load balancer. Which Kubernetes API fits, and how is responsibility split? design

    Show answer

    The Gateway API: the platform team owns the Gateway (load balancer, listeners, certificates) and allows routes from team namespaces; each team owns its HTTPRoute objects attaching to that gateway.
