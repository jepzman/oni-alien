Logs

Logs are how a server tells you what happened while you weren't looking. This chapter shows where Linux keeps them, how to find the five lines that matter among five million, and how to keep logs from doing the one thing they must never do: fill the disk on the busiest night of the year.

By the end you can

  • Say where a given program's logs go: the journal, a syslog file or its own file.
  • Filter the journal by unit, priority, time and boot.
  • Free space taken by a deleted log that's still open, without restarting anything.
  • Configure logrotate, and choose between create, copytruncate and a signal.
  • Set limits so logs can't fill a disk, and decide what to ship off the machine.

Before you start

  • Chapter 6: services and the journal. Chapter 3: deleted-but-open files.
  • A VM where PID 1 is systemd, with sudo (Appendix C).

7.1Where logs go

A Linux server has three kinds of log, and a given program uses one or more of them. The first question about any log is which one you're looking at.

  • The journal. systemd's logging service, journald, collects the standard output and error of every service, messages sent through the old syslog interface, and the kernel's messages. It stores them in a structured, indexed format in /var/log/journal/, with limits on its own size. You read it with journalctl.
  • Syslog files. Syslog is the traditional Unix logging interface. On Ubuntu, rsyslog receives a copy of everything from journald and writes the familiar text files: /var/log/syslog (everything), /var/log/auth.log (logins, sudo), /var/log/kern.log. Handy for grep and for old tools.
  • Programs' own files. nginx writes /var/log/nginx/access.log and error.log itself; PostgreSQL, some apps and many vendor agents do the same. Nothing limits these files except log rotation (7.4), if somebody set it up.

Every log line carries a priority (also called severity or level), from 0 to 7: emerg, alert, crit, err, warning, notice, info, debug. Application frameworks use the same idea (Python's DEBUG, INFO, WARNING, ERROR). The level is the cheapest volume control you have: DEBUG can easily produce a hundred times what INFO does.

7.2Reading the journal

journalctl with no arguments shows everything, oldest first, which is rarely what you want. Filters combine, and a handful cover nearly every question:

Table 7.1 · journalctl filters
You wantCommand
one servicejournalctl -u stagedoor (several -u are allowed)
follow livejournalctl -u stagedoor -f
the last lines, newest lastjournalctl -u stagedoor -n 50; -r for newest first
a time window--since "2026-03-20 09:55" --until "10:10", or --since "-15min"

Each journal entry is a set of fields, not just a line of text: who wrote it (_UID, _PID, _SYSTEMD_UNIT), when, on which boot, at which priority. Fields starting with _ are added by journald itself and can't be faked by the program, which makes them trustworthy for questions like “which user ran this?”. Reading other users' and system entries needs sudo, or membership of the adm or systemd-journal group.

Is the journal kept?On Ubuntu, the journal is stored on disk in /var/log/journal and survives reboots. On some minimal images it's kept only in memory, in /run/log/journal, and lost at every reboot. If journalctl --list-boots shows only one boot, check Storage= in journald.conf.

7.3When logs fill the disk

A full filesystem breaks things that seem to have nothing to do with logs: uploads, temporary files, database writes, package installs, even logins on some systems. When it happens, the order of work matters:

  1. Find what's big. df -h shows which filesystem is full; sudo du -xh /var --max-depth=2 | sort -h | tail walks down to the culprit (Chapter 11 does this properly).
  2. Free space without losing what you need. If a running program has the file open, deleting the name frees nothing (Chapter 3). Truncate it instead: : > /var/log/stagedoor/stagedoor.log (or truncate -s 0) sets its length to zero, and the space comes back at once. If you need the contents, copy the last part somewhere else first.
  3. If you already deleted it, find the open file through /proc (ls -l /proc/*/fd 2>/dev/null | grep deleted, or sudo lsof +L1) and truncate it through its descriptor: : > /proc/<pid>/fd/<n>. Or restart the program, which closes it.
  4. Then stop it happening again: rotation, limits, a sensible log level and an alert on disk usage.

Watch out: don't free space by deleting the wrong thing

Under pressure, it's tempting to delete whatever is big. Never delete files under /var/lib (database files, package state) or a database's write-ahead log to make room: that's data, not logs, and the damage outlasts the incident. Logs, caches (/var/cache, apt clean) and old releases are the safe candidates.

7.4Rotation with logrotate

Log rotation means: every so often (or when a file gets too big), move the current log aside, start a new one, compress the older ones, and delete the oldest. On Ubuntu, logrotate does this once a day, started by logrotate.timer, for every file listed in /etc/logrotate.d/. Packages such as nginx install their own entry; for your app's files, you write one.

/etc/logrotate.d/stagedoorlogrotate

/var/log/stagedoor/*.log {
    daily
    rotate 7
    maxsize 100M
    compress
    delaycompress
    missingok
    notifempty
    create 0640 root adm
}

Read it as: for each .log file in that directory, rotate daily or as soon as it passes 100 MB at a daily check; keep seven old files; compress them, except the most recent (so it can still be read easily, and so a program that is still writing to it isn't compressed underneath); don't complain if there's no file; skip empty files; and create the new file as root:adm, mode 640.

The hard part of rotation isn't the schedule. It's the program that has the file open. Renaming a file doesn't change the program's file descriptor (Chapter 3): after stagedoor.log becomes stagedoor.log.1, the program carries on writing to .1, and the new stagedoor.log stays empty for ever. There are three ways out:

nginx's packaged entry, /etc/logrotate.d/nginx, is a good example of the first method:

/var/log/nginx/*.log {
	daily
	missingok
	rotate 14
	compress
	delaycompress
	notifempty
	create 0640 www-data adm
	sharedscripts
	prerotate
		if [ -d /etc/logrotate.d/httpd-prerotate ]; then \
			run-parts /etc/logrotate.d/httpd-prerotate; \
		fi \
	endscript
	postrotate
		invoke-rc.d nginx rotate >/dev/null 2>&1
	endscript
}

invoke-rc.d nginx rotate sends nginx SIGUSR1, which makes it reopen its log files (Chapter 5). sharedscripts runs that once for all the files, rather than once per file.

Test a new entry before you trust it: sudo logrotate --debug /etc/logrotate.d/stagedoor shows what it would do without doing it, and sudo logrotate --force /etc/logrotate.d/stagedoor rotates now. logrotate refuses to work in a directory that others may write to, and says so.

7.5Limits, levels and shipping

Rotation keeps files from growing for ever; three more habits keep logs useful and safe:

  • Cap the journal. By default journald uses at most 10% of the filesystem (and never more than 4 GB) and leaves 15% free. To set your own numbers, add a drop-in such as /etc/systemd/journald.conf.d/size.conf with [Journal], SystemMaxUse=2G and SystemKeepFree=10G, then sudo systemctl restart systemd-journald. sudo journalctl --vacuum-size=1G trims it now.
  • Log at INFO in production, and make the level something you can change at runtime or with a config reload, with a reminder to change it back. Debug logging is a tool for an investigation, not a setting.
  • Ship logs off the machine. A log on the server that crashed, or that an attacker controls, is the log you can't read when you need it. A shipper (Vector, Fluent Bit, the CloudWatch agent, Promtail) sends copies to a central service where they're kept, searchable and alertable. Ship what you'd search; don't ship secrets: check that passwords, tokens and card numbers never reach a log in the first place.

Key idea

Every log needs an owner, a level, a size limit and a destination. A log with none of these is a disk-full incident with a date not yet set.

7.6Writing logs worth reading

When you control the program, make its logs easy for the next person, who may be you at 10:04 on a Friday:

  • One event per line, with a level and the things you'll search by: order ID, event ID, request ID. checkout failed order=88213 event=4500 reason=payment_timeout beats a paragraph.
  • Structured where you can: key-value pairs or JSON lines make shippers and jq work without regular expressions.
  • Timestamps with a time zone, ideally UTC, so lines from three servers can be merged. journald adds its own; files need the program to.
  • Errors with context, once. Log an error where it's handled, not at every level it passes through, or one failure becomes six lines.

7.9Common mistakes

MistakeWhat happensInstead
An app writing its own file with no rotationIt grows until the disk is full.Log to stdout and the journal, or add a logrotate entry the day the file appears.
Deleting a big open logNo space is freed; the file is now hard to find.Truncate it; or truncate through /proc/<pid>/fd.
Rotating with create for a program that can't reopenThe program writes to the renamed file for ever.copytruncate, or a postrotate signal the program supports.
DEBUG in production, “for now”Volume multiplies; secrets and personal data leak into logs.INFO by default; time-limited debug switches.
Logs only on the serverLost with the server, or altered by whoever broke in.Ship them to a central service.
Reading the journal without sudoYou see only your own entries and think the rest is missing.sudo journalctl, or the adm group.

✓Chapter summary

  • Logs go to the journal (services' output, syslog, the kernel), to syslog files written by rsyslog, or to programs' own files.
  • journalctl filters by unit (-u), priority (-p), time (--since), boot (-b) and field; fields starting with _ are added by journald and trustworthy.
  • When a disk fills with logs: find it, truncate rather than delete, and if it's already deleted, truncate through /proc/<pid>/fd.
  • logrotate rotates files listed in /etc/logrotate.d/. A program holding the file open needs a signal to reopen it, or copytruncate.
  • Cap the journal, log at INFO, alert on disk usage, and ship logs off the machine.

Key terms

journald
systemd's logging service, which collects services' output, syslog messages and kernel messages into the journal.
Journal
journald's indexed, structured store of log entries, read with journalctl.
Syslog
The traditional Unix logging interface and protocol; on Ubuntu, rsyslog writes it to text files in /var/log.
Priority
A log entry's severity, from 0 (emerg) to 7 (debug).
Log rotation
Periodically moving a log aside, starting a new one, compressing and eventually deleting old ones.
copytruncate
A logrotate method that copies a log and truncates the original, so a program can keep writing to the same open file.
Log shipping
Sending copies of logs from a server to a central service where they are stored and searched.

Check your understanding

  1. Where would you look first for: why sudo was denied, what nginx served at 10:02, and why stagedoor.service restarted? recall

    Show answer

    sudo: /var/log/auth.log or journalctl -t sudo. nginx's requests: its own file, /var/log/nginx/access.log. The restart: journalctl -u stagedoor, which has both the app's output and systemd's messages about it.

  2. Write a journalctl command for errors or worse from stagedoor.service between 09:55 and 10:15 on 20 March 2026, newest first. apply

    Show answer

    sudo journalctl -u stagedoor -p err --since "2026-03-20 09:55" --until "2026-03-20 10:15" -r.

  3. Explain why, after a create-style rotation, a program can still be writing to app.log.1, and why this eventually fills the disk anyway. explain

    Show answer

    Renaming changes the directory entry, not the open file: the program's descriptor still refers to the same inode, now named app.log.1. Each later rotation renames and compresses it, and finally deletes it, but the program keeps it open, so its space is never freed and keeps growing until the program reopens or restarts.

  4. df says / is 100% full, but du -xsh / adds up to 40 GB on a 160 GB disk. What's the likely cause, and how do you confirm and fix it without a reboot? debug

    Show answer

    Deleted files still held open: du only counts files with names, df counts all used blocks. Confirm with sudo lsof +L1 or ls -l /proc/*/fd | grep deleted. Fix by truncating through /proc/<pid>/fd/<n>, or by restarting the program holding them, then stop the cause (rotation that the program supports).

  5. Design the logging for a new service on Stagedoor's servers so it can never fill a disk and its logs survive the server. design

    Show answer

    Log to standard output at INFO, one structured line per event, with order and event IDs; run as a systemd service so the journal stores it; cap the journal (SystemMaxUse, SystemKeepFree); ship the journal to a central log service with retention; alert on disk usage above 80%; and make DEBUG a time-limited runtime switch.

  6. Compare copytruncate with a postrotate signal. When would you choose each? compare

    Show answer

    A signal (or systemctl reload) loses nothing and needs no extra disk space, but works only if the program can reopen its log files; use it for nginx, PostgreSQL and other daemons that support it. copytruncate works with any program, but needs space for the copy and can lose lines written between the copy and the truncate; use it for programs you can't change.
