The shell, properly

You can type commands; this chapter shows what happens to them before they run. Once you know how the shell splits, expands and connects what you type, pipelines stop being magic spells copied from the internet and become sentences you can read, write and trust with a real question.

By the end you can

  • Describe what the shell does with a line before any program runs.
  • Redirect standard output and standard error, and connect commands with pipes.
  • Answer a question from a log file with a pipeline of small tools, and check the answer.
  • Quote correctly, and predict what *, $var and $( … ) turn into.
  • Use exit codes to tell success from failure, including inside a pipeline.

Before you start

  • A terminal on any Linux (Appendix C). Chapter 1 helps but isn't required.
  • Python 3, only to generate the lab's sample log.

2.1What the shell does with a line

The shell is an ordinary program (on servers, usually bash) whose job is to read a line of text, turn it into one or more programs with arguments, run them, and wait. Most surprises come from not knowing that the shell rewrites the line before anything runs.

Two consequences follow. First, a program can't tell whether you typed *.log or the list of names the shell turned it into. Second, when a command does something odd, the question is usually “what arguments did it actually get?”, and echo is the quickest way to find out: put echo in front of the command, and the shell prints the expanded line instead of running it.

bash, sh, dashYour login shell on a server is usually bash. /bin/sh is a simpler shell for scripts: on Ubuntu and Debian it's dash, which lacks some bash features. A script that starts with #!/bin/sh but uses bash syntax works on one distribution and fails on another.

2.2Commands, options and arguments

After splitting, the first word is the command and the rest are its arguments. By convention, arguments starting with - are options: short ones are a single letter and can be combined (ls -l -a is ls -la); long ones start with -- (ls --all). Some options take a value: head -n 5, sort --key=2. A lone -- means “no more options”, which matters when a file name starts with a dash: rm -- -oops.txt.

The command itself is one of three things, and type tells you which:

  • A builtin, part of the shell itself: cd, echo, export, type. It has to be: cd changes the shell's own current directory, which a separate program couldn't do.
  • An alias or function defined in your shell's startup files, such as Ubuntu's ll for ls -alF.
  • A program: a file somewhere on disk. The shell looks for it in each directory listed in the PATH variable, in order, and runs the first match.
type cd ll grep         # cd is a shell builtin · ll is aliased to `ls -alF' · grep is /usr/bin/grep
echo "$PATH"            # /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin…

Watch out: PATH is not the same everywhere

Your interactive shell's PATH is set by its startup files. Programs started by cron or as services get a much shorter one. A command that works when you type it can fail with “command not found” at 03:00. Stagedoor meets exactly this in Chapter 6; the fix is to use full paths, or set PATH explicitly, in anything that runs unattended.

2.3Standard streams and redirection

Every program starts with three open channels, called standard streams, each identified by a small number, its file descriptor:

  • 0, standard input (stdin): where it reads input from. By default, your keyboard.
  • 1, standard output (stdout): where it writes its results. By default, your terminal.
  • 2, standard error (stderr): where it writes errors and progress messages. Also your terminal, which is why the two look the same until you separate them.

The split between 1 and 2 is what makes pipelines work: results flow on to the next program, while errors still reach you. Redirection tells the shell to connect a stream to a file instead:

Table 2.1 · Redirection, the forms you'll use every day
You writeIt means
cmd > out.txtstdout to out.txt, replacing the file if it exists
cmd >> out.txtstdout appended to out.txt
cmd 2> err.txtstderr to err.txt; stdout still to the terminal
cmd > all.txt 2>&1stdout to all.txt, then stderr to wherever stdout now goes. Order matters: 2>&1 > all.txt sends stderr to the terminal
cmd 2> /dev/nullthrow stderr away. /dev/null is a device that discards whatever is written to it
cmd < in.txtstdin from in.txt
cmd1 | cmd2stdout of cmd1 becomes stdin of cmd2
cmd | tee out.txtshow the output and save a copy

One more form is common in documentation: sudo cmd > /etc/file fails with “Permission denied” even though cmd runs as root. The redirection is done by your shell, as you, before sudo even starts. Write cmd | sudo tee /etc/file > /dev/null instead.

2.4Pipes and the small tools

A pipe connects one program's standard output to the next one's standard input. All the programs in a pipeline run at the same time; each reads what the previous one writes, as it's written. That's why grep error huge.log | head -5 returns at once: when head has its five lines it exits, and grep is stopped the next time it writes.

The Unix habit is to combine small programs that each do one thing. A handful cover most questions you'll ask of a server:

Table 2.2 · Small tools for text

grepkeeps lines matching a patterngrep -i error app.log, grep -v healthcheck (lines not matching), grep -c (count)
awksplits each line into fields $1, $2…, filters and printsawk '$9 >= 500 {print $7}'

Build pipelines one step at a time, and look at the output after each step (add | head while you work). A pipeline you built and checked step by step is one you can trust; a pipeline you pasted is a guess with a confident number at the end.

Key idea

Before you trust a count, look at what you counted. Replace | wc -l with | head and read the lines.

2.5Expansion and quoting

Step 3 of Figure 2.1 is where most shell bugs live. Before running anything, bash performs several expansions on each word:

  • Tilde: ~ becomes your home directory.
  • Variables: $name or ${name} becomes the variable's value. $? (last exit status), $$ (the shell's process ID) and $1 (a script's first argument) are special variables.
  • Command substitution: $(cmd) becomes cmd's output, as in Lab 1's server card.
  • Arithmetic: $((2 * 60)) becomes 120.
  • Word splitting: the result of an unquoted expansion is split again at spaces, tabs and newlines.
  • Globbing (pathname expansion): an unquoted word containing *, ? or […] becomes the list of matching file names. If nothing matches, bash leaves the word as it is.

Quoting switches expansions off:

  • Single quotes '…' switch off everything. What you write is what the program gets.
  • Double quotes "…" allow variables, $( ) and arithmetic, but switch off word splitting and globbing. The result stays one argument, spaces and all.
  • A backslash switches off the special meaning of the next character.

In a directory containing only access.log, with event=os-lumes:

echo *.log; echo "*.log"; echo $event "$event" '$event'
access.log
*.log
os-lumes os-lumes $event

The dangerous case is a variable holding a space. Unquoted, it becomes two arguments:

f="on-sale report.txt"; touch "$f"; ls $f; ls "$f"
ls: cannot access 'on-sale': No such file or directory
ls: cannot access 'report.txt': No such file or directory
on-sale report.txt

The unquoted ls $f looked for two files, on-sale and report.txt. With ls that's an error message. With rm it deletes the wrong files, and with rm -rf $dir/ and an empty $dir, it's the classic way to delete far more than intended.

Key idea

Put double quotes around every variable and every $( ), unless you can say why not. Use single quotes for text that must reach the program untouched, such as awk and grep patterns.

2.6Exit codes

Every program finishes with an exit status, a number from 0 to 255. 0 means success; anything else means some kind of failure, and the program's manual page says which. The shell keeps the last one in $?. grep is a good example, because it distinguishes “no match” from “something went wrong”:

grep -q '" 504 ' access.log; echo $?     # a line with status 504 exists
grep -q '" 503 ' access.log; echo $?     # none with 503
grep -q 504 nosuch.log; echo $?          # the file doesn't exist
0
1
grep: nosuch.log: No such file or directory
2

A few codes are set by the shell itself: 126 means the file exists but can't be executed (Lab 1), 127 means command not found, and 128 + n means the program was killed by signal n (so 137 is 128 + 9, SIGKILL, which you'll meet in Chapter 5 and Chapter 10).

Exit codes drive the shell's logic. a && b runs b only if a succeeded; a || b runs b only if a failed; a; b runs both regardless. if tests an exit status, not a true/false value: if grep -q ERROR app.log; then ….

A pipeline's exit status is, by default, the status of its last command. That hides failures:

grep 500 nosuch.log | wc -l; echo "status: $?"
set -o pipefail
grep 500 nosuch.log | wc -l; echo "status: $?"
grep: nosuch.log: No such file or directory
0
status: 0
grep: nosuch.log: No such file or directory
0
status: 2

Without pipefail, the pipeline “succeeded” and printed a count of 0, because wc happily counted nothing. In a script, that zero would be reported as a fact. With set -o pipefail, the pipeline fails if any part fails. Chapter 17 makes this and two other settings the start of every script.

2.7Getting help and moving fast

Nobody remembers every option. What you need is to know where the answers are:

  • man grep opens the manual page. Pages are grouped in numbered sections: 1 for commands, 5 for file formats (man 5 crontab), 8 for administration commands. Search inside with /; quit with q. man -k word searches page titles.
  • grep --help prints a shorter summary for most programs; help cd does the same for bash builtins.
  • Examples are often the fastest help: the EXAMPLES section near the end of many man pages, or a community tool such as tldr.
Minimal imagesCloud and container images often leave out manual pages to save space. On Ubuntu, sudo unminimize puts them back; or read them on your own machine, or at manpages.ubuntu.com.

And a few keys save hours: Tab completes commands and file names (press it twice to see choices); Ctrl+R searches your command history; Ctrl+C interrupts the running program; Ctrl+D ends input (and logs you out of an empty prompt); Ctrl+A and Ctrl+E jump to the start and end of the line. history lists what you typed, which, on a shared server, is also a way to learn what the last person did.

Watch out: secrets in your history

Anything you type is saved to ~/.bash_history when the shell exits, including a password passed as an argument (mysql -p'secret', curl -u user:secret). Prefer tools that prompt for secrets or read them from a file or environment variable. Arguments are also visible to other users in ps while the program runs.

2.8Across distributions

bash and the core tools behave the same on every distribution in this book: Ubuntu, Debian, the RHEL family and Amazon Linux all ship GNU bash, GNU coreutils, GNU grep and an awk. The differences you'll notice are small:

On the RHEL family and Amazon Linux

/bin/sh is bash itself (running in a compatibility mode), not dash. Scripts that start with #!/bin/sh but use bash features work there and break on Ubuntu and Debian, so write #!/usr/bin/env bash when you use bash features. awk is GNU awk (gawk) here, while Ubuntu and Debian install the smaller mawk by default; both handle everything in this chapter.

On your Mac

macOS uses zsh as the default shell and BSD versions of the core tools, whose options sometimes differ (sed -i, date, base64 -D). When a command from this book behaves strangely on a Mac, run it on the server or in a Linux container instead.

2.9Lab: how many fans got an error?

Lab 2 · Answer Joana's question, and check the answer

You'll generate a sample of the access log from Stagedoor's on-sale, reproduce Tiago's wrong count, find out why it's wrong, and build the right answer one pipe at a time. You need a Linux terminal and Python 3. Cost: nothing. Clean-up: delete the lab directory.

  1. Make the log. Create a directory, save this script in it as makelog.py, and run it. It writes 2,000 lines in nginx's default (“combined”) format; its random choices are seeded, so you get exactly the same file as everyone else.

    makelog.pyPython 3.8+

    # makelog.py · a sample nginx access log for the 10:00 on-sale on Friday 30 January 2026
import random

rng = random.Random(2026)
NETS = ["198.51.100", "203.0.113", "192.0.2"]
PAGES = [("GET", "/events/os-lumes-porto"), ("GET", "/static/app.js"),
         ("GET", "/api/seats?event=4500"), ("POST", "/api/hold"), ("POST", "/api/checkout")]

for i in range(2000):
    t = 9 * 3600 + 58 * 60 + int(i * 0.36)          # 09:58:00 onwards, about 3 requests a second
    stamp = f"30/Jan/2026:{t // 3600:02d}:{t // 60 % 60:02d}:{t % 60:02d} +0000"
    ip = f"{rng.choice(NETS)}.{rng.randint(1, 254)}"
    method, path = rng.choices(PAGES, weights=[30, 25, 20, 15, 10])[0]
    status = 200
    if path == "/static/app.js" and rng.random() < 0.5:
        status = 304
    elif path == "/api/hold" and rng.random() < 0.2:
        status = 409                                   # someone else got the seat first
    elif path == "/api/checkout" and "10:01" <= stamp[12:17] <= "10:04" and rng.random() < 0.3:
        status = rng.choice([500, 502, 504])
    size = 0 if status == 304 else rng.randint(150, 9000)
    agent = rng.choice(["Mozilla/5.0 (iPhone)", "Mozilla/5.0 (Android)", "Mozilla/5.0 (Windows NT 10.0)"])
    print(f'{ip} - - [{stamp}] "{method} {path} HTTP/1.1" {status} {size} "-" "{agent}"')
    mkdir -p ~/lab2 && cd ~/lab2       # save makelog.py here first
python3 makelog.py > access.log

✓Chapter summary

  • The shell reads a line, splits it, expands it, finds each program and runs it. Programs see only the final arguments.
  • Programs have three standard streams: input (0), output (1) and error (2). Redirection connects them to files; pipes connect one program's output to the next one's input.
  • Small tools (grep, awk, sort, uniq, wc, head) answer most questions about a server, built one step at a time.
  • Quote every variable with double quotes; use single quotes for patterns and programs.
  • Exit status 0 means success. A pipeline returns its last command's status unless pipefail is set.
  • Look at what you counted before you trust the count.

Key terms

Shell
The program that reads commands, expands them and runs programs; usually bash on servers.
PATH
The list of directories the shell searches, in order, to find a program by name.
Standard streams
The three channels every program starts with: standard input (0), standard output (1) and standard error (2).
File descriptor
A small number a process uses to refer to an open file, pipe or socket.
Redirection
Connecting a program's standard stream to a file instead of the terminal, with >, >>, 2> or <.
Pipe
A connection from one program's standard output to another's standard input, written |.
Expansion
The shell's rewriting of a word before running a command: variables, command substitution, arithmetic, word splitting and globbing.
Globbing
Turning a word containing *, ? or […] into the list of matching file names.
Quoting
Switching off expansions: single quotes switch off all of them, double quotes all but variables and command substitution.
Exit status
The number a program returns when it finishes; 0 means success.

Check your understanding

  1. Which file descriptor does a program write error messages to, and why does it matter for pipelines? recall

    Show answer

    Standard error, file descriptor 2. Pipes only carry standard output (1), so error messages reach the terminal instead of being mixed into the data the next program processes.

  2. Write a pipeline that lists the five client addresses with the most requests in access.log, most first. apply

    Show answer

    awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5. The first sort groups equal addresses so uniq -c can count them; the second sorts by count, numerically and in reverse.

  3. dir= is accidentally empty. What does rm -rf $dir/* do, and how would quoting and a check have helped? explain

    Show answer

    The shell expands it to rm -rf /*: every top-level directory on the machine. Quoting alone ("$dir"/*) gives the same result with an empty variable; what helps is refusing to run with an empty value: rm -rf "${dir:?}"/* stops with an error if dir is empty or unset, and set -u (Chapter 17) catches unset variables in scripts.

  4. A script runs grep ERROR /var/log/app.log | wc -l and reports 0 errors every night. The log file was renamed a month ago. Why didn't anyone notice, and what's the fix? debug

    Show answer

    grep failed (exit 2, “No such file or directory” on stderr, which nobody reads in a cron job), but the pipeline's status was wc's, which succeeded and counted zero lines. Fix: set -o pipefail (or check that the file exists) so the failure is reported, and send the script's stderr somewhere someone reads.

  5. Joana now asks for the number of fans who lost a seat race (status 409) and later completed a checkout. Sketch how you'd answer it from the log, and say what the log can't tell you. design

    Show answer

    Collect the addresses with a 409 on /api/hold (awk '$9 == 409 {print $1}' | sort -u > lost.txt), the addresses with a 200 on /api/checkout (… | sort -u > bought.txt), and count the lines in both (comm -12 lost.txt bought.txt | wc -l). The log can't tell you about people: addresses are shared and change, and it doesn't know which order belongs to whom. The order database can.

  6. Compare single and double quotes: what does each switch off, and when do you use each? compare

    Show answer

    Single quotes switch off every expansion; use them for text that must reach a program unchanged, such as awk programs and grep patterns containing $. Double quotes keep variable and command substitution but switch off word splitting and globbing; use them around variables and $( ) so the value stays one argument.
