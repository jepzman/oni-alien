Hardening a server

Hardening is least privilege applied to a whole machine: fewer things running, fewer ways in, less power for each thing that runs, and a record of what happened. This chapter turns the fixes scattered through the book into a baseline you can apply, check and rebuild from, and shows how far systemd's sandboxing can shrink what a compromised service could do.

By the end you can

  • Inventory a server's attack surface: listening services, enabled units, privileged programs, accounts.
  • Sandbox a service with systemd and measure the result with systemd-analyze security.
  • Write a hardening baseline as a checklist and as cloud-init, and validate it.
  • Explain what an audit trail and a benchmark (CIS, Lynis) add, and their limits.
  • Say what AppArmor and SELinux do, and how to spot when they're the reason something fails.

Before you start

  • Most of the book: 4 (permissions, sudo), 6 (units), 8 (updates), 15 (firewalls) and 16 (SSH).
  • A VM with systemd and sudo; sudo apt install cloud-init lynis.

18.1What hardening is for

Hardening assumes something will eventually go wrong (an unpatched bug in the app, a stolen laptop with a key on it, a mistake in a firewall rule) and arranges the server so that one failure doesn't become everything.

Three principles run through every layer: least function (don't run, install or expose what you don't need), least privilege (give each thing only the access its job requires, Handbook 2, Chapter 6), and verify, don't assume (measure the result, and keep checking it).

18.2Attack surface: what's there to attack?

Start with an inventory, using commands from earlier chapters:

Table 18.1 · An attack-surface inventory
QuestionCommandReduce it by

Every item on the list is something that could have a vulnerability, a misconfiguration or a forgotten credential. The cheapest hardening is removal: a service that doesn't run can't be exploited, and a package that isn't installed doesn't need patching. Cloud images help by starting small; “minimal” images start smaller still.

18.3Sandboxing services with systemd

A service running as its own user (Chapter 4) can't read other users' files, but it can still read most of the system, write wherever that user may, see devices, load code into memory as it likes, and make any system call. If an attacker gets code execution in the app, all of that is theirs. systemd can remove most of it before the process starts (Chapter 6 previewed this):

hardening.confsystemd drop-in

# /etc/systemd/system/stagedoor.service.d/hardening.conf · take away what the app doesn't need
# (systemd allows comments only on lines of their own, never after a setting)
[Service]
# no setuid programs, no gaining privileges, and no root powers at all
NoNewPrivileges=yes
CapabilityBoundingSet=
# the whole filesystem read-only, except the app's own data
ProtectSystem=strict
ReadWritePaths=/var/lib/stagedoor
ProtectHome=yes
PrivateTmp=yes
# no devices, no changes to the kernel, its logs, the clock or the hostname
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
ProtectClock=yes
ProtectHostname=yes
RestrictNamespaces=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
LockPersonality=yes
# only IP and local sockets, only the system calls a normal service makes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
SystemCallArchitectures=native
SystemCallFilter=@system-service
SystemCallFilter=~@privileged @resources
  • Filesystem: ProtectSystem=strict mounts everything read-only for this service, ReadWritePaths= opens exactly the paths it writes, ProtectHome hides home directories, PrivateTmp gives it an empty /tmp of its own.
  • Privileges: NoNewPrivileges blocks setuid programs (so sudo or su are useless from inside), and an empty CapabilityBoundingSet removes every root capability, even if the process somehow became root.
  • Kernel and devices: no hardware devices, no changing kernel settings, modules, logs, the clock or the hostname.
  • System calls: SystemCallFilter=@system-service allows the calls a normal service makes and refuses the rest (mounting, rebooting, loading kernel modules, tracing other processes); RestrictAddressFamilies allows only IP and local sockets.

systemd-analyze security scores a unit's exposure from 0 (locked down) to 10 (nothing restricted) and lists each missing setting. In the lab, Stagedoor's app goes from 9.2 to 1.5 with this drop-in, and still works. Add settings in small groups and test the app after each: a service that writes somewhere you forgot fails with “Read-only file system”, and one that needs a refused system call is killed with SIGSYS, both of which the journal records.

Key idea

Assume the app will one day run an attacker's code. Decide now what that code may touch, and let systemd enforce it.

18.4An audit trail

Logs (Chapter 7) record what programs say. An audit trail records what happened, from the kernel's point of view, whether or not any program mentions it: who changed /etc/sudoers, who ran a command as root, which process opened a sensitive file. On Linux this is the kernel's audit system, configured with auditd (sudo apt install auditd):

# writes or attribute changes to sudoers and the SSH configuration, tagged for searching
-w /etc/sudoers -p wa -k sudoers
-w /etc/sudoers.d/ -p wa -k sudoers
-w /etc/ssh/sshd_config.d/ -p wa -k sshd
# commands run as root by a real person (audit UID 1000 and up)
-a always,exit -F arch=b64 -S execve -F euid=0 -F auid>=1000 -F auid!=-1 -k root-commands

Rules like these go in /etc/audit/rules.d/; sudo ausearch -k sudoers -i finds the events, each with the audit UID: the person who logged in, which stays the same through sudo and su. That's the accountability question from Handbook 2, Chapter 1, answered at the level of the kernel. The audit trail is only useful if it survives an attacker: ship it off the server with the other logs. (The test system for this book is a container, where the kernel's audit system isn't available, so these rules are shown, not run.)

18.5A baseline: written, built and checked

A baseline is the written description of a correctly set-up server, the thing Stagedoor lacked. It works only if it's written in a form that can be applied and checked, not just read. For Stagedoor's web servers, collected from this book:

Then make it executable in two forms. A first-boot configuration in cloud-init (Chapter 1) builds the parts that belong to every server; the lab validates one with cloud-init schema, which catches typos and wrong types before a server boots with them. And a build script does the rest and can check itself, which is Chapter 21's capstone. Configuration-management tools (Ansible, Salt, Puppet) are the grown-up version of both: the same idea, with modules that are idempotent by design.

18.6Benchmarks and scanners

You don't have to invent a baseline from nothing. The CIS Benchmarks are detailed, versioned hardening guides per distribution, with hundreds of checks in two levels (Level 1: sensible for most servers; Level 2: stricter, may break things). Ubuntu Pro's Ubuntu Security Guide (usg) can apply and audit them automatically; OpenSCAP does the same for RHEL. Lynis, a free scanner, runs a few hundred checks and prints suggestions and a “hardening index” from 0 to 100.

Use them as a second opinion, not a goal. A score measures how many boxes are ticked, not whether the server is safe for what it does: some suggestions don't apply (a web server needs its web port open), some cost more than they're worth, and the most important controls in this book (no shared accounts, no long-lived keys, patches actually running) are things a scanner can only partly see. Read the suggestions, apply what fits, write down why you skipped the rest, and track the score over time so that it doesn't quietly fall.

18.7A few kernel settings

A handful of sysctl settings (Chapter 12) are worth including in a baseline. Ubuntu already sets several; check each with sysctl before adding it:

# hide kernel addresses, and the kernel log, from unprivileged users
kernel.kptr_restrict = 2
kernel.dmesg_restrict = 1
# no BPF programs for ordinary users
kernel.unprivileged_bpf_disabled = 1
# drop packets with impossible source addresses; ignore ICMP redirects
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.all.accept_redirects = 0
# the /tmp symlink tricks from Chapter 17's warning
fs.protected_symlinks = 1

18.8Across distributions: AppArmor and SELinux

Both families add a second, mandatory access-control layer on top of permissions (Chapter 4): a policy, set by the administrator, that even a process running as root can't override. They do with policy files what this chapter's systemd settings do per service.

AppArmor (Ubuntu, Debian) and SELinux (RHEL family, Amazon Linux)

AppArmor confines programs by path: a profile lists the files and capabilities a program may use. Ubuntu ships profiles for several services; sudo aa-status lists them, and denials appear in the journal as apparmor="DENIED". SELinux labels every file and process with a context and allows interactions by rules between labels (Chapter 3 and Chapter 4's boxes). It's on in enforcing mode by default on RHEL; getenforce shows the mode, sudo ausearch -m avc -ts recent the denials, and restorecon fixes labels on moved files. The common mistake on both is switching them off at the first denial: read the denial, then fix the label or the profile.

18.10Common mistakes

MistakeWhat happensInstead
Hardening by hand, server by serverEach server slightly different; nobody knows the intended state.A written baseline, applied by cloud-init and scripts, checked regularly.
Chasing a scanner's scoreBoxes ticked, real risks (shared accounts, old keys) untouched.Use scores as a second opinion; decide per suggestion.
Applying every sandbox setting at onceThe service breaks and the whole drop-in is reverted.Small groups, test after each, read the journal.
Disabling AppArmor or SELinux at the first denialThe whole mandatory layer is gone, for one mislabelled file.Read the denial; fix the label or profile.
Audit logs only on the serverThe intruder deletes them.Ship them off immediately.

✓Chapter summary

  • Hardening limits what one failure can lead to: layers from the network to the data, each assuming the outer one might fail.
  • Start with the attack surface: listening services, enabled units, root processes, setuid programs, accounts and keys. Remove what isn't needed.
  • systemd sandboxing (ProtectSystem, NoNewPrivileges, capabilities, system-call filters) limits a compromised service; systemd-analyze security measures it.
  • An audit trail (auditd) records privileged actions and changes by the person who logged in; ship it off the server.
  • Write a baseline and make it executable (cloud-init, scripts) and checkable; use CIS, Lynis and similar as second opinions.
  • AppArmor (Ubuntu) and SELinux (RHEL) add mandatory access control; fix denials, don't disable the layer.

Key terms

Hardening
Reducing a system's attack surface and the privileges of what runs on it, so a single failure does less damage.
Attack surface
Everything an attacker could try to use: listening services, accounts, credentials, privileged programs, installed software.
Sandboxing
Restricting what a process may access (files, devices, system calls, privileges) beyond ordinary permissions.
Capability
One of the separate privileges into which Linux divides root's power, such as binding low ports or overriding file permissions.
Audit trail
A record of security-relevant actions from the kernel's point of view, tied to the person who logged in.
Baseline
The written, checkable description of a correctly configured server.
Mandatory access control
Access rules set by policy that processes, even root ones, can't override; AppArmor and SELinux on Linux.

Check your understanding

  1. Name four things to list when measuring a server's attack surface, and a command for each. recall

    Show answer

    Listening sockets (sudo ss -tlnp), enabled services (systemctl list-unit-files --state=enabled), setuid programs (sudo find / -xdev -perm -4000 -type f), accounts and keys that can log in (getent passwd plus the authorized_keys audit); also sudo rules and installed packages.

  2. A payouts timer writes its CSV to /var/lib/stagedoor/payouts/ and reads /etc/stagedoor/stagedoor.env. Write the filesystem part of its sandbox. apply

    Show answer

    ProtectSystem=strict, ReadWritePaths=/var/lib/stagedoor/payouts, ProtectHome=yes, PrivateTmp=yes. Reading /etc/stagedoor needs nothing extra (strict makes it read-only, not invisible); the file permissions still decide whether the service's user may read it.

  3. Explain why NoNewPrivileges=yes matters even for a service that never runs sudo. explain

    Show answer

    It's about what an attacker could do with the service's process, not what the service does. Without it, code running in the service could run a setuid program (sudo, su, a vulnerable helper) and gain privileges; with it, setuid bits and file capabilities are ignored for that process and its children.

  4. After you add a sandbox drop-in, a service starts but its file uploads fail with “Read-only file system”, and another service dies with signal SYS. What happened in each case, and how do you fix them? debug

    Show answer

    The first writes to a path not in ReadWritePaths= under ProtectSystem=strict: find the path in the error and add it (or use StateDirectory=/CacheDirectory=). The second made a system call outside SystemCallFilter=: the journal or journalctl -k names it; allow that group (or call), or reconsider whether the service should be making it.

  5. Design how Stagedoor keeps four servers matching its baseline over a year. design

    Show answer

    The baseline lives in Git as a checklist, cloud-init and a build script, all reviewed. New servers are built from it, never by hand. A scheduled check (the build script in verify mode, plus Lynis, systemd-analyze security scores and the SSH and sudo audits) runs weekly and reports differences. Fixes go into the baseline first, then onto servers, ideally by rebuilding. Scores and decisions are dated in the wiki.

  6. Compare systemd sandboxing with AppArmor for confining the app. compare

    Show answer

    systemd's settings are per unit, short and readable, apply to everything the service starts, and need no extra framework; they can't express fine-grained per-file rules as easily. An AppArmor profile is per program, can list exactly which files it may read and write, and applies however the program is started, but profiles take more effort to write and maintain. Using both is possible; for your own services, systemd's sandbox is the easier first step.
