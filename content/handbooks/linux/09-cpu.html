9

CPU, load and scheduling

“The load is 14!” is one of the most common alarms in operations, and one of the most misread. This chapter explains how Linux shares CPUs between processes, what load average actually counts, how to tell a machine that's busy computing from one that's stuck waiting, and how to tell the scheduler what matters more.

By the end you can

  • Explain what load average measures on Linux, and judge it against the number of CPUs.
  • Read the CPU breakdown in top and vmstat: user, system, idle, I/O wait, steal.
  • Tell CPU saturation from I/O waiting in two commands.
  • Lower a job's CPU and disk priority with nice, ionice and systemd settings.
  • Recognise cloud-specific CPU effects: vCPUs, steal time, burstable instances.

Before you start

  • Chapter 5: process states, especially R and D. Chapter 6: services and timers.
  • A Linux machine with at least 2 CPUs and a few GB of free disk (Appendix C).

9.1CPUs, cores and vCPUs

To Linux, a CPU is anything that can run one thread of instructions at a time. nproc counts them; lscpu describes them.

On physical hardware, a processor has several cores, and each core may run two hardware threads (Intel calls this Hyper-Threading, AMD SMT). Two threads on one core share its execution units, so they're worth less than two cores: perhaps 1.2 to 1.3 times one core for typical server work. Linux counts each hardware thread as a CPU.

In the cloud, you rent vCPUs. On most instance types one vCPU is one hardware thread of a physical core shared with other customers' VMs; on some, two vCPUs are the two threads of one dedicated core. Either way, nproc on an “8 vCPU” server says 8, and that's the number to compare load against. The lab machine for this chapter:

9.2How the scheduler shares CPUs

At any moment, most processes are sleeping (S, Chapter 5): waiting for a network packet, a timer, a lock. The ones that could use a CPU right now are runnable (R). If there are more runnable threads than CPUs, the extras wait in a run queue, and the kernel's scheduler switches between them every few milliseconds so each gets a fair share. Each switch is a context switch; it costs a few microseconds, which is nothing until a machine does hundreds of thousands a second.

A third group neither runs nor waits for a CPU: threads in uninterruptible sleep (D), waiting inside the kernel for disk I/O (or a network filesystem) to finish. They can't use a CPU even if one is free; they're waiting for the disk.

9.3Load average

The load average is the three numbers at the start of uptime, top and /proc/loadavg: the average number of threads that were running, runnable or in uninterruptible sleep, over roughly the last 1, 5 and 15 minutes. They're exponentially smoothed, so a sudden change shows up gradually: in the lab, eight busy processes take more than a minute to push the 1-minute figure near 8.

Three rules make the numbers useful:

  1. Divide by the number of CPUs. A load of 8 is idle-ish on a 64-CPU machine and badly overloaded on a 2-CPU one. Below the CPU count, there's usually spare capacity; persistently above it, something is waiting.
  2. Compare the three numbers. 1-minute higher than 15-minute: getting worse. Lower: recovering. The trend matters more than the value.
  3. Find out what kind of waiting. On Linux (unlike most other Unix systems), load includes D-state threads. Look at the CPU breakdown (9.4) and the r and b columns of vmstat before deciding a machine needs more CPU.

Key idea

Load average says that things are waiting, not what they're waiting for. Before buying CPUs, check whether the waiting is for CPUs.

9.4Where the CPU time goes

The kernel accounts for every tick of every CPU in one of a few categories. top shows them on its %Cpu(s) line, and vmstat in its last columns:

Two more columns of vmstat 1 complete the picture: r, the number of runnable threads (running plus queued), and b, the number blocked in D state. With these, the first question about a loaded machine takes one command:

  • r well above the CPU count, us + sy near 100: CPU saturation. Something is computing too much, or there's too little CPU.
  • b high, wa high, id non-zero: waiting for I/O. More CPUs won't help; find what's using the disk.

To find which process: top sorted by CPU (press P), ps -eo pid,stat,pcpu,comm --sort=-pcpu | head, and for D states ps -eo pid,stat,wchan:20,comm | awk '$2 ~ /D/' (the wchan column names the kernel function it's waiting in). The sysstat package adds mpstat -P ALL 1 (per CPU, to spot one CPU at 100% while the rest idle: a single-threaded bottleneck), pidstat 1 (per process, over time) and iostat -x 1 (per disk).

9.5Priorities: nice, ionice and systemd

The scheduler gives runnable threads CPU time in proportion to a weight, set by the process's nice value, from −20 (most favoured) to 19 (least). The default is 0. Each step changes the weight by about 25%, so the gaps are large: a nice-19 process competing for one CPU with a nice-0 one gets around 1.5% of it, as the lab shows. Nice only matters when CPUs are contended; on an idle machine, a nice-19 job runs at full speed.

  • nice -n 10 cmd starts a command with a lower priority; renice -n 10 -p 2187 changes a running one. Only root may raise priority (negative values).
  • ionice -c 3 cmd puts a process in the idle I/O class: it gets the disk only when nobody else wants it. -c 2 -n 7 is best-effort at the lowest priority. The effect depends on the disk's I/O scheduler, and is strongest on local disks.
  • For services and timers, put it in the unit: Nice=10, IOSchedulingClass=idle, or with cgroups, CPUWeight=20 (default 100) and CPUQuota=50% (a hard cap: half of one CPU).

Lowering the priority of what can wait is almost always better than raising the priority of what can't: a database at nice −10 can starve the very processes it depends on, such as its own log writer or sshd when you need to log in and fix it.

9.6CPU on a cloud VM

Three cloud effects appear in the numbers above:

  • Steal time (st) is time your vCPU was ready to run but the hypervisor ran another VM on that physical CPU. A few percent is normal on shared instances (the lab machine showed 1–3%); sustained double digits means you're not getting what you pay for, and moving to another host (stop and start the instance) or a different instance family helps.
  • Burstable instances (AWS T family, Azure B series, Google Cloud's shared-core types) give you a baseline, say 20% of a vCPU, plus credits saved while idle. When the credits run out, the vCPU is throttled to the baseline, often visible as high steal. They're good for small, spiky servers and a trap for anything with sustained load, like an on-sale.
  • vCPU counts are threads, not cores (9.1). A CPU-bound app that scales to 8 cores may not scale to 8 vCPUs on 4 cores.

9.7Across distributions

The scheduler, load average and /proc are the kernel's, identical everywhere. top, vmstat, ps and nice come from procps on every distribution in this book. mpstat, pidstat and iostat come from sysstat, which isn't installed by default on Ubuntu, Debian or Amazon Linux (apt install sysstat, dnf install sysstat); it also records history every ten minutes for sar once enabled, which is very useful for “what happened at 03:00?”.

On the cloud

Cloud consoles graph “CPU utilisation” from outside the VM, as busy time over all vCPUs. It doesn't show I/O wait or load, and it ignores steal from the VM's point of view, so a VM can look 30% busy in the console while its users wait. The provider's agent (CloudWatch agent, Azure Monitor agent, Ops Agent) can send the in-guest numbers too.

9.8Lab: busy, nice and blocked

Lab 9 · Three kinds of load

You'll overload the CPUs and watch the load climb, share one CPU between a nice and a not-nice process, then create load with the CPUs nearly idle by making processes wait for the disk. You need a Linux VM (not a laptop you're using for other things) with 2 or more CPUs and 2 GB of free disk. Cost: nothing. Clean-up: every step stops itself with timeout; delete the files at the end. Outputs come from a 4-vCPU test VM.

  3. Nice in action. Pin two burners to the same CPU with taskset, one at the default priority and one at nice 19: 
    taskset -c 0 timeout 40 ./burn.sh &

    Both on CPU 0 (PSR); the nice-19 one got about 1.5% of it. Run the nice one alone and it gets 100%: nice only matters under contention.

Stretch goals. (1) Install sysstat and run step 2 again with mpstat -P ALL 1 3: every CPU at 100%. Then run a single burner: one CPU at 100%, the others idle, a load of 1. (2) Repeat step 4 with ionice -c 3 on the writers while a fourth, normal dd runs: does the normal one get more of the disk? (3) Run a burner as a transient service with a cap, sudo systemd-run --unit=capped -p CPUQuota=25% ./burn.sh (from the lab directory, with a full path), and watch it in top: 25%, however idle the machine.

At Stagedoor: the backup at the wrong time

vmstat 1 on door-1 shows r between 2 and 4, b around 10, and wa above 50. The processes in D are PostgreSQL's, plus pg_dump and gzip: a full backup is running. It's the new weekly full backup, added in April as a timer with OnCalendar=Fri 08:00, meant to finish long before any on-sale. door-1's clock is UTC; since the clocks changed in March, 08:00 UTC is 09:00 in Lisbon, and on an arena on-sale, with the database busy, the backup takes eighty minutes instead of forty. Exactly Chapter 6's warning about time zones.

Rafaela stops the backup at 10:05 (it will run again that night), and seat holds are fast again within a minute. Nobody buys a bigger server. The timer moves to OnCalendar=Sun 04:00 Europe/Lisbon, with Nice=10 and IOSchedulingClass=idle. The alert on load average is replaced by two: CPU busy (us + sy) above 80% for ten minutes, and I/O wait above 30%, each naming the machine and showing the top processes. Handbook 6 returns to this backup: taking it from a replica instead of the busy primary is the real fix.

✓Chapter summary

  • Linux counts every hardware thread, and every cloud vCPU, as a CPU; nproc gives the number to compare against.
  • The scheduler shares CPUs between runnable threads; extras wait in the run queue.
  • Load average is the smoothed number of threads running, waiting for a CPU, or in D state waiting for the disk, over 1, 5 and 15 minutes.
  • CPU time splits into user, system, nice, idle, I/O wait, interrupts and steal. r and us high: CPU saturation. b and wa high: waiting for I/O.
  • nice, ionice and systemd's Nice=, IOSchedulingClass=, CPUWeight= and CPUQuota= decide who gets contended resources.
  • In the cloud, watch for steal time and burstable instances that run out of credits.

Key terms

vCPU
A virtual CPU rented in the cloud, usually one hardware thread of a physical core.
Scheduler
The part of the kernel that decides which runnable thread runs on which CPU, and for how long.
Run queue
The runnable threads waiting for a CPU.
Context switch
The CPU switching from running one thread to running another.
Load average
The average number of threads running, runnable or in uninterruptible sleep over the last 1, 5 and 15 minutes.
I/O wait
CPU time that was idle while at least one thread was waiting for I/O to complete.
Steal time
Time a virtual CPU was ready to run but the hypervisor was running something else.
Nice value
A process's scheduling priority, from −20 (most favoured) to 19 (least); 0 by default.

Check your understanding

  1. A 4-vCPU server shows a load average of 3.1 5.6 7.9. What do the three numbers tell you? recall

    Show answer

    Over the last 15 minutes the load averaged about 7.9, almost twice the CPU count; over the last 5 minutes 5.6, and over the last minute 3.1, now below the CPU count. Something was overloaded and is recovering.

  2. vmstat 1 shows r 1 b 9 us 4 sy 3 id 41 wa 52 on an 8-vCPU database server. What's the bottleneck, and what would you look at next? apply

    Show answer

    The disk: nine threads blocked in I/O, half the CPU time spent waiting for I/O, CPUs mostly idle. Next: ps -eo pid,stat,wchan:20,comm | awk '$2 ~ /D/' for which processes, iostat -x 1 or pidstat -d 1 for which disk and who's using it (Chapter 11).

  3. Explain why a nice-19 backup job still runs at full speed on an idle server, and why that can still hurt the database at night. explain

    Show answer

    Nice only changes the share of CPU when CPUs are contended; with free CPUs, the job gets as much as it wants. And nice affects CPU, not the disk: a backup's I/O can still slow the database. Add ionice -c 3 or IOSchedulingClass=idle, and schedule it when the database is quiet.

  4. A web server's console graph shows 35% CPU, but its users report slowness and top inside the VM shows st at 40%. What's happening? debug

    Show answer

    The hypervisor isn't giving the VM the CPU time it wants: either a noisy neighbour on a shared host, or (very often) a burstable instance that has run out of CPU credits and is throttled to its baseline. Check the credit balance; move to a fixed-performance instance type, or stop and start to land on another host.

  5. Design monitoring alerts for CPU on Stagedoor's servers that would have pointed at the real problem on 8 May. design

    Show answer

    Alert on CPU busy (user + system) above about 80% for several minutes, per server, and separately on I/O wait above about 30%, each with the top processes by CPU and the processes in D attached. Graph load per CPU for context rather than alerting on it. Add steal time for cloud VMs.

  6. Compare Nice=10 and CPUQuota=50% for a reporting service. compare

    Show answer

    Nice=10 lowers its share only when CPUs are contended; when the machine is idle it can use every CPU. CPUQuota=50% is a hard ceiling of half a CPU, even on an idle machine. Use nice (or CPUWeight=) to be polite; use a quota when the job must never take more than a fixed amount.
