Shell scripts that don't bite

Every server accumulates shell scripts: deploys, backups, clean-ups, checks. Most are written in ten minutes and run for years, unattended, as root. This chapter shows how a short script turns into a disaster, and the handful of habits (strict mode, quoting, validation, traps, dry runs and ShellCheck) that make the same ten minutes produce a script you can trust at 03:00.

By the end you can

  • Explain what set -euo pipefail does, and where it doesn't help.
  • Quote variables and use arrays so file names with spaces and empty values can't hurt you.
  • Validate inputs, clean up with trap, and make a script safe to re-run.
  • Read ShellCheck's warnings and fix them.
  • Decide when a task has outgrown the shell and belongs in Python.

Before you start

  • Chapter 2 (expansion, quoting, exit codes, pipefail) and Chapter 3 (the release layout).
  • A Linux terminal with bash and sudo apt install shellcheck.

17.1How a three-line script deletes the wrong thing

Here is the script, exactly as it ran (the lab reproduces it with the variable set but empty, which has the same effect):

cleanup-v1.shbash (don't use this)

#!/bin/bash
# cleanup-releases.sh (first version) · keep the five newest releases, delete the rest
cd $RELEASES_DIR
ls -t | tail -n +6 | xargs rm -rf
echo "cleanup done"

Each line has a small problem, and together they're a disaster:

Shell scripts fail this way because the shell was designed for people typing at a prompt: it reports an error and waits for the next command. In a script, nobody is waiting, so the next command runs, in whatever state the failure left behind. The rest of this chapter is about telling bash to behave like a program instead.

17.2Strict mode

Start every bash script with these two lines:

#!/usr/bin/env bash
set -euo pipefail
  • -e (errexit): exit as soon as a command fails (returns non-zero). The cd in Figure 17.1 would have ended the script.
  • -u (nounset): using an unset variable is an error, instead of silently becoming empty. A typo in a variable's name stops the script.
  • -o pipefail: a pipeline fails if any command in it fails, not only the last (Chapter 2).

Together they're often called bash's “strict mode”. It isn't perfect, and knowing its gaps keeps you from trusting it too much:

  • Commands tested by if, while, && or || don't trigger -e, which is how you handle expected failures: if ! grep -q x file; then …. But that also switches -e off inside any function called from such a test.
  • local x=$(cmd) hides cmd's failure, because local itself succeeded. Declare first, assign separately: local x; x=$(cmd). (ShellCheck catches this: SC2155.)
  • A variable that's set but empty passes -u. For values that must not be empty, use ${VAR:?message}, which stops with the message if the variable is unset or empty. Give defaults with ${VAR:-default}.

Key idea

A script should stop at the first thing it didn't expect. set -euo pipefail plus ${VAR:?} for every required input makes that the default.

17.3Quoting, arrays and options

Chapter 2's rule applies with full force in scripts: put double quotes around every variable and every $( ). Three more habits finish the job:

  • Arrays for lists. A list of file names or command arguments belongs in an array, expanded as "${files[@]}": each element stays one argument, spaces and all. Build commands the same way: args=(--archive --delete); rsync "${args[@]}" "$src/" "$dst/".
  • Globs, not ls. for f in /var/log/stagedoor/*.log gives exact names; parsing ls output breaks on spaces and newlines in names (ShellCheck's SC2012). Add shopt -s nullglob so a glob that matches nothing becomes nothing, not the literal pattern.
  • -- before file names in commands like rm, cd and cp: it ends the options, so a name starting with - can't be read as one (rm -rf -- "$r").
  • "$@" passes a script's or function's arguments on unchanged; $* and unquoted $@ re-split them.

17.4Structure: inputs, functions and exit codes

A script that runs unattended needs to say clearly what it needs and what happened. A skeleton worth copying:

#!/usr/bin/env bash
# name.sh · one line saying what it does, and how to run it
set -euo pipefail

# 1. inputs: required ones stop the script if missing, optional ones get defaults
target=${TARGET:?TARGET must be set}
keep=${KEEP:-5}

# 2. helpers: messages to stderr, so stdout stays clean for data
log() { echo "$(date -Is) $*" >&2; }
die() { log "error: $*"; exit 1; }

# 3. checks before doing anything
[[ -d $target ]] || die "$target is not a directory"
[[ $keep =~ ^[0-9]+$ ]] || die "KEEP must be a number, got '$keep'"

# 4. the work, in functions with names that say what they do
main() {
  log "starting in $target"
  …
}
main "$@"

Exit with 0 only when the job is done; with non-zero, and a message on stderr, when it isn't. systemd records the status (systemctl status, Chapter 6), and an alert on failed units turns a failing script into a notification the same morning. A script that prints “done” and exits 0 after failing, like Figure 17.1's, defeats all of that.

17.5Safety: clean-up, locks, dry runs, idempotence

  • Temporary files come from mktemp (mktemp -d for a directory), never from a fixed name in /tmp, which another user could create first. Remove them with a trap: trap 'rm -rf -- "$work"' EXIT runs however the script ends, on success, on an error under set -e, or on Ctrl+C.
  • One at a time. A job started by a timer can overlap with a manual run. A lock stops the second: exec 9>/run/lock/cleanup.lock; flock -n 9 || die "already running". (A systemd service can't overlap with itself anyway, Chapter 6.)
  • A dry run (DRY_RUN=1) that prints what would be changed, for anything that deletes or moves. Run it first, read it, then run for real.
  • Idempotence: running the script twice should be as safe as running it once. Check before acting (mkdir -p, id user || useradd …, “skip if already deleted”). It's what lets you re-run a script that failed halfway, and it's the core of Chapter 21's build script.
  • Narrow targets. Delete only what matches what you expect (names like 2026.10.3), and refuse to touch anything else, however the inputs went wrong.

17.6ShellCheck and testing

ShellCheck is a static analyser for shell scripts: it reads a script without running it and points out quoting bugs, unhandled failures, unused variables and dozens of other traps, each with a code (SC2086…) and a wiki page explaining it. It found two of Figure 17.1's three problems in a fraction of a second. Run it on every script, in your editor and in CI, and treat its warnings like compiler errors; for the rare false alarm, disable that one check on that one line with a comment (# shellcheck disable=SC2016) and say why.

Beyond that: bash -n script.sh checks syntax without running; bash -x (or set -x in the script) prints every command as it runs, the fastest way to see what a script actually did; and for scripts that matter, a scratch directory with fake data, as in the lab, is a test suite you can build in five minutes. Frameworks such as bats make it repeatable.

17.7When to switch to Python

The shell is excellent at running programs and connecting them. It's poor at data structures, arithmetic, parsing JSON, HTTP, and error handling more subtle than “stop”. Rough signs that a script has outgrown it:

  • it's longer than a screen or two, or has more than a few functions;
  • it parses JSON, YAML or CSV, or calls an HTTP API (use Python's json and urllib, or jq for one-off queries);
  • it needs retries, timeouts, or to carry on past one failure and report all of them;
  • it handles money, dates across time zones, or anything where a silent mistake is expensive.

Python 3 is on every server in this book, and subprocess.run([...], check=True) calls programs as safely as the shell does, without its quoting traps. Stagedoor's payouts report and the load-test client in Chapter 21 are Python for exactly these reasons.

17.8Across distributions

On Debian, Ubuntu, Alpine and macOS

Bash features ([[ ]], arrays, mapfile, pipefail on older shells) don't exist in sh. On Debian and Ubuntu /bin/sh is dash, on Alpine it's BusyBox ash, so a script must start with #!/usr/bin/env bash if it uses them (Chapter 2); ShellCheck reads the shebang and checks for the right shell. macOS ships bash 3.2 from 2007, without mapfile or associative arrays: test scripts on the system they'll run on. On the RHEL family, /bin/sh is bash, which hides the problem until the script moves to Ubuntu.

    cleanup-releases.shbash

    #!/usr/bin/env bash
# cleanup-releases.sh · keep the newest KEEP releases in RELEASES_DIR, delete older ones, never the live one
set -euo pipefail

releases_dir=${RELEASES_DIR:?RELEASES_DIR must be set, e.g. /opt/stagedoor/releases}
keep=${KEEP:-5}
dry_run=${DRY_RUN:-0}

cd -- "$releases_dir"
live=$(basename -- "$(readlink -f ../current)")          # the release "current" points to

shopt -s nullglob
releases=( [0-9][0-9][0-9][0-9].[0-9][0-9].[0-9]* )      # only names like 2026.10.3
if (( ${#releases[@]} == 0 )); then
  echo "no releases found in $releases_dir"
  exit 0
fi
mapfile -t sorted < <(printf '%s\n' "${releases[@]}" | sort -V)
count=${#sorted[@]}
if (( count <= keep )); then
  echo "nothing to delete: $count releases, keeping $keep"
  exit 0
fi

for r in "${sorted[@]:0:count-keep}"; do                 # all but the newest $keep

    echo "would delete $r"

    rm -rf -- "$r"
    echo "deleted $r"

done

17.10Common mistakes

MistakeWhat happensInstead
No set -eA failed step is followed by the next one, in the wrong state.set -euo pipefail at the top.
Unquoted variables in cd, rm, cpEmpty values vanish; spaces split names."$var", and -- before names.
Required inputs without a checkAn empty variable silently changes what the script does.${VAR:?message}.
Parsing lsBreaks on unusual names; matches more than you meant.Globs with nullglob, or find -print0.
Fixed temporary file namesRaces and symlink attacks in /tmp; leftovers.mktemp and a trap … EXIT.

Deleting without a dry run or a name checkOne wrong input deletes the wrong things.DRY_RUN=1, and only delete names you expect.
Growing a script to 400 linesUnreadable and fragile; JSON and retries in bash.Python, with subprocess for the commands.

✓Chapter summary

  • Shell scripts carry on after errors by default; that's how a failed cd becomes a deleted directory.
  • set -euo pipefail stops at failures, unset variables and failed pipelines; ${VAR:?} catches empty required inputs. Know where -e doesn't apply.
  • Quote every variable, use arrays for lists, globs instead of ls, and -- before file names.
  • Validate inputs first, log to stderr, exit non-zero on failure. Use mktemp and trap … EXIT, locks for jobs that mustn't overlap, dry runs for anything destructive, and make scripts idempotent.
  • Run ShellCheck on every script, in CI too. Move to Python when a script needs data structures, JSON, HTTP or careful error handling.

Key terms

Strict mode
The bash settings set -euo pipefail: exit on errors, on unset variables and on failures anywhere in a pipeline.
trap
A bash command that runs given code when the script receives a signal or exits.
mktemp
A command that safely creates a uniquely named temporary file or directory.
Idempotent
Safe to run more than once: later runs leave the system in the same state as the first.
Dry run
A mode in which a script reports what it would change without changing anything.
ShellCheck
A static analysis tool that finds bugs and risky patterns in shell scripts.

Check your understanding

  1. What does each of -e, -u and -o pipefail do? recall

    Show answer

    -e: exit when a command fails (outside tests such as if). -u: treat use of an unset variable as an error. -o pipefail: a pipeline's status is that of the last command that failed, not only of the last command.

  2. Rewrite cp $SRC/*.conf $DEST so it's safe with empty variables, names with spaces, and no matching files. apply

    Show answer

    src=${SRC:?SRC must be set}; dest=${DEST:?DEST must be set}; shopt -s nullglob; files=( "$src"/*.conf ); (( ${#files[@]} )) || { echo "no .conf files in $src" >&2; exit 1; }; cp -- "${files[@]}" "$dest"/.

  3. Explain why local result=$(curl -sf "$url") doesn't stop a script under set -e when curl fails. explain

    Show answer

    The exit status of that line is local's, which succeeded in declaring the variable; curl's failure is lost. Write local result; result=$(curl -sf "$url"), so the assignment's status is curl's and -e sees it.

  4. A backup script works when you run it, but from its timer it leaves files called /tmp/backup.tmp behind and sometimes produces truncated archives. What would you look for? debug

    Show answer

    Overlapping runs (a manual run and the timer, both writing the same fixed temporary file: use mktemp and a flock lock); no trap to remove temporary files on failure; and a failure in the middle of a pipeline that's hidden without pipefail (for example pg_dump | gzip > file where pg_dump fails and gzip happily writes a short file). Also the timer's different environment: PATH, working directory, user (Chapter 6).

  5. Design the safety features for a script that deletes old database dumps from a backup directory. design

    Show answer

    Strict mode; the directory as a required input checked with ${…:?} and [[ -d ]]; only names matching the dump pattern (stagedoor-YYYY-MM-DD.sql.gz) are candidates; keep at least N newest whatever their age, and never delete if fewer than N exist; a dry-run mode; a lock; output listing what was deleted; exit non-zero on any failure; ShellCheck clean; run by a timer as a user that can only write to that directory.

  6. Compare writing Stagedoor's payouts report in bash and in Python. compare

    Show answer

    The report queries the database, totals money per venue, handles dates and writes a CSV for the bank. In bash, that means psql output parsing, arithmetic on currency (bash has only integers) and fragile CSV quoting. Python has proper decimals, the csv module, database drivers, exceptions and tests. Bash is fine for the wrapper that runs it; the report itself belongs in Python.
