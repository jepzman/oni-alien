Memory, swap and the OOM killer

Linux uses memory differently from how most people expect: it fills “free” memory with cache on purpose, promises programs more than it has, and, when the promises can't all be kept, picks a process and kills it. This chapter explains each of those, how to read memory numbers without alarm, and how to make sure that when something must die, it isn't your database.

By the end you can

  • Read free correctly, and say why “available” matters more than “free”.
  • Tell virtual size from resident memory, and find the processes really using memory.
  • Explain what swap is for, and when a server should have it.
  • Explain how the OOM killer chooses a victim, find its traces, and protect a process from it.
  • Contain a memory-hungry job with a cgroup limit.

Before you start

  • Chapter 5: processes, signals, exit status 137. Chapter 6: units and systemd-run.

At Stagedoor

Friday 5 June 2026, 10:12, twelve minutes into a summer festival's on-sale: for forty seconds, every request to the database fails, on both web servers at once. Then everything recovers. PostgreSQL's log on door-1 tells the story in three lines: one server process “was terminated by signal 9: Killed”; the database then “terminating any other active server processes”; then “database system was not properly shut down; automatic recovery in progress”.

Nobody sent signal 9. The kernel did. journalctl -k has the matching line: Out of memory: Killed process 31877 (postgres), with 19 GB of resident memory. One PostgreSQL process, on a 32 GB machine, had grown to 19 GB. Rafaela and Sasha set out to find out which query it was running, and why the kernel chose it.

10.1Virtual memory

Every process sees its own private, contiguous range of memory addresses, its virtual address space. The kernel maps pieces of it, in pages of 4 KB, onto real memory (RAM) only when the process actually touches them.

This explains the two memory columns in ps and top:

  • VSZ (virtual size, VIRT in top): everything mapped, used or not. It's often huge and almost meaningless: a Java or Go program can map gigabytes it never touches.
  • RSS (resident set size, RES): pages actually in RAM. This is the number to watch, with one caveat: shared pages (libraries, a database's shared buffers) are counted in the RSS of every process that uses them, so adding up RSS over-counts. smem or /proc/<pid>/smaps_rollup gives PSS, which divides shared pages fairly.

Because pages are handed out only when touched, the kernel lets programs reserve more memory in total than the machine has. This is overcommit, and it's usually right: most reservations are never fully used. When they are, the kernel has a problem it can only solve by taking memory back from someone (10.4).

10.2Reading free

               total        used        free      shared  buff/cache   available
Mem:            15Gi       673Mi        14Gi        12Mi       739Mi        15Gi
Swap:             0B          0B          0B
Table 10.1 · The columns of free
ColumnMeans
usedmemory programs and the kernel are using, not counting cache
freememory nobody is using for anything, not even cache
buff/cachethe page cache and kernel buffers: copies of files, kept in case they're read again
availablean estimate of how much could be given to programs right now without swapping: free plus cache that can be dropped

Linux uses otherwise idle RAM to cache files, because reading from RAM is thousands of times faster than from disk, and gives that memory back the moment a program needs it. On a healthy server that has been up for a while, free is small and buff/cache is large, and that's a good sign, not a warning. The lab reads a 2 GB file and watches buff/cache grow by 2 GB while available doesn't move.

Key idea

Watch available, not free. Free memory is memory doing nothing; cache is memory doing something useful until it's needed elsewhere.

10.3Swap

Swap is disk space the kernel can move memory pages to when RAM is short: a swap partition, or a swap file. Pages of program memory that haven't been used for a while are written out (“swapped out”) and read back when touched again. It isn't a substitute for RAM, since disk is far slower, but it does two useful things: it lets the kernel move genuinely idle memory out of the way to make room for cache and active work, and it turns a sudden memory shortage into a gradual slowdown that a person or alert can notice, instead of an instant kill.

free shows swap's size and use; vmstat 1's si and so columns show pages swapped in and out each second. Swap used isn't a problem; continuous swapping in and out (“thrashing”) is, and makes a machine crawl. vm.swappiness (0–200, default 60) tunes how readily the kernel swaps program memory rather than dropping cache.

Swap on cloud VMsMost cloud images, including Ubuntu's, ship with no swap at all, as did the lab machine. Adding a swap file is a few commands (Chapter 11); whether to is a judgement: for a database server, a small amount buys warning time; for a container host, many teams prefer no swap and strict limits.

10.4When memory runs out

When a program touches a page and the kernel can't find RAM for it, the kernel works down a ladder:

The OOM killer (out of memory) chooses by a score, /proc/<pid>/oom_score: mostly how much memory the process uses, so the biggest process is usually the victim. Each process also has /proc/<pid>/oom_score_adj, from −1000 to +1000, added to its score; −1000 exempts it entirely. In a unit file it's OOMScoreAdjust=. The victim gets SIGKILL (exit status 137, Chapter 5), and the kernel log records it: journalctl -k | grep -i "out of memory" or dmesg, with the process's memory use at the moment of death.

Watch out: the biggest process is often the most important one

On a database server, the database is the biggest process by far, so it's the OOM killer's favourite target, even when a careless report or a leaky script caused the shortage. For PostgreSQL, killing even one backend with SIGKILL makes the whole server restart all connections and run crash recovery, because shared memory might be corrupt: a few seconds to minutes of outage for everyone. Protect the database's main process, cap what other jobs on the machine may use, and keep memory headroom.

10.5Limits with cgroups

A cgroup (control group) is a group of processes that the kernel accounts and limits together. systemd puts every service in its own cgroup (Chapter 6), so memory limits are one line in a unit:

  • MemoryMax=2G: a hard limit. If the service's processes need more and nothing can be reclaimed within the cgroup, the OOM killer kills one of them, not something else on the machine.
  • MemoryHigh=1.5G: a soft limit. Above it, the kernel reclaims the cgroup's memory aggressively and slows it down, which is often enough to keep it from reaching MemoryMax.
  • MemorySwapMax=0: no swap for this service.

For a one-off job, sudo systemd-run --unit=report -p MemoryMax=4G -p User=$USER command runs it in its own limited cgroup, which is what the lab does. Containers use the same mechanism: docker run --memory=2g, and Kubernetes' memory limits (Handbook 4), so a container killed with 137 and OOMKilled: true hit its own limit, not the machine's.

10.6Who is using the memory?

ps -eo pid,rss,vsz,comm --sort=-rss | head        # biggest resident first (KB)
top                                               # press M to sort by memory
grep -E 'VmRSS|VmSwap' /proc/2187/status          # one process: resident and swapped
systemd-cgtop                                     # memory per service (cgroup), live
grep -E 'MemAvailable|Dirty|Shmem' /proc/meminfo  # the whole machine, in detail

Two traps when the numbers don't add up: shared memory is counted in every process that maps it (10.1), and memory used by the kernel itself (slab caches, page tables) appears in no process at all; /proc/meminfo and slabtop show it.

10.7Across distributions

Memory management, the OOM killer and cgroups are the kernel's, so they behave the same everywhere. What differs is the plumbing around them:

On newer systems: systemd-oomd

Ubuntu Desktop (since 22.04) and Fedora run systemd-oomd, a user-space killer that acts earlier than the kernel, when memory pressure (time spent waiting for memory, from /proc/pressure/memory) stays high, and kills a whole cgroup rather than one process. It's configured per slice with ManagedOOMMemoryPressure=; on servers it's often not installed or not active, so check systemctl status systemd-oomd. If something was killed and the kernel log has no OOM line, check journalctl -u systemd-oomd. RHEL and Amazon Linux don't enable it by default.

10.8Lab: cache, residence and a kill

Lab 10 · Watch memory being cached, reserved and taken back

You'll see the page cache fill without hurting available, compare a process's virtual and resident size, change its OOM score, then run a memory hog inside a 200 MB limit and find the kernel's record of killing it. You need a Linux VM with systemd, sudo, Python 3 and 3 GB of free disk. Cost: nothing. Clean-up: delete big.bin and hog.py. Steps 1–3 ran on a 16 GB test VM, step 4 on the systemd test system of Lab 6.

  1. The page cache. Make a 2 GB file, empty the cache (harmless: the kernel just forgets cached copies), then read the file and compare: 
    mkdir -p ~/lab10 && cd ~/lab10
head -c 2G /dev/urandom > big.bin
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches > /dev/null
free -h | head -2; cat big.bin > /dev/null; free -h | head -2
                   total        used        free      shared  buff/cache   available
Mem:            15Gi       616Mi        15Gi        12Mi       319Mi        15Gi
               total        used        free      shared  buff/cache   available
Mem:            15Gi       618Mi        13Gi        12Mi       2.3Gi        15Gi
    buff/cache grew by 2 GB and free shrank by 2 GB, but available stayed at 15 GiB: that cache can be given back at any time. Read the file again and time it (time cat big.bin > /dev/null): from cache, it's much faster than the first read. Never use drop_caches on a production server to “free memory”; you'd only make the next reads slow.
  2. Virtual and resident. Start a Python process that maps 4 GB without touching it and fills 300 MB, and look at it: 
    python3 -c "import mmap, time; m = mmap.mmap(-1, 4 << 30); b = bytearray(300 << 20); time.sleep(20)" &
sleep 2; ps -o pid,vsz,rss,comm -p $!; grep -E "VmSize|VmRSS" /proc/$!/status
      PID    VSZ   RSS COMMAND
12866 4537064 317596 python3
VmSize:	 4537064 kB
VmRSS:	  317596 kB
    4.3 GB virtual, 310 MB resident. The untouched 4 GB costs nothing until it's written.
  3. The OOM score of the same process, before and after making it a preferred victim (no sudo needed to raise your own; lowering it below 0 needs root): 
    cat /proc/$!/oom_score; echo 500 > /proc/$!/oom_score_adj; cat /proc/$!/oom_score
    679
1012
    The adjustment moved it up the list. A process with oom_score_adj of −1000 is never chosen; setting a negative value needs root (and some sandboxed machines refuse even that). Stop it with kill $!.
  4. A kill, contained. Save this hog as hog.py:

    hog.pyPython 3.8+

    # hog.py · take memory 10 MB at a time, say so every 50 MB, and never give it back
import time

held = []
for n in range(1, 1001):
    held.append(bytearray(10 * 1024 * 1024))   # bytearray fills its memory with zeros, so it's really used
    if n % 5 == 0:
        print(f"holding {n * 10} MB", flush=True)
    time.sleep(0.02)
print("finished: holding 10 GB")
    Run it as a transient service with a 200 MB memory limit and no swap, and wait for it to finish: 
    sudo systemd-run --wait --unit=hog -p User=$USER -p MemoryMax=200M -p MemorySwapMax=0 /usr/bin/python3 $HOME/lab10/hog.py
    Running as unit: hog.service; invocation ID: 9d1ab0c9e70e433babfc971be1cfd8e4
Finished with result: signal
Main processes terminated with: code=killed/status=KILL
Service runtime: 524ms
    Killed by signal 9 after half a second. Its output and what systemd saw: 
    sudo journalctl -u hog --no-pager -o cat | tail -6
    Started hog.service - /usr/bin/python3 /home/tiago/hog.py.
holding 50 MB
holding 100 MB
holding 150 MB
hog.service: Main process exited, code=killed, status=9/KILL
hog.service: Failed with result 'signal'.
    It reached 150 MB and died before 200. The kernel's side: 
    sudo dmesg | grep -i "killed process" | tail -1
    [ 3881.215523] Memory cgroup out of memory: Killed process 12758 (python3) total-vm:220000kB, anon-rss:204288kB, file-rss:6456kB, shmem-rss:0kB, UID:1001 pgtables:456kB oom_score_adj:0
    “Memory cgroup out of memory”: the limit was the cgroup's, so the rest of the machine never noticed. anon-rss (about 200 MB) is the memory it had written to; UID:1001 is the user it ran as. On a system using cgroup v2 throughout, systemd may also report the result as oom-kill rather than signal.
  5. Clean up: sudo systemctl reset-failed hog; rm ~/lab10/big.bin ~/lab10/hog.py.

Stretch goals. (1) Run the hog again with -p MemoryHigh=150M -p MemoryMax=200M and watch it with systemd-cgtop: does it slow down before it dies? (2) Run it with no limit at all on a small VM (1 GB) and find which process the global OOM killer chose; were you surprised? (3) Read /proc/pressure/memory during step 4 of a run with MemoryHigh=.

At Stagedoor: the 19 GB query

PostgreSQL's log shows what process 31877 was doing: a settlement report from an analyst's dashboard, grouping three years of ticket rows by venue and seat category. The analyst's session had raised work_mem, the memory each sort or hash step may use, to 4 GB “so the report would finish”. A single query can use work_mem several times over, and this one used it five times. With 8 GB of shared buffers and two hundred checkout connections on top, a 32 GB server with no swap ran out, and the biggest process on it was that one PostgreSQL backend.

Sasha and Rafaela change four things. Reports get their own database role with work_mem capped at 64 MB and a statement timeout; they run on a schedule outside on-sales. door-1 gets an 8 GB swap file, to turn the next shortage into a slowdown with an alert instead of a restart. PostgreSQL's main process (the postmaster) gets OOMScoreAdjust=-1000 in a drop-in, with the environment settings PostgreSQL's documentation describes so that its child processes stay killable, so if anything must be killed, it isn't the process whose death restarts everything. And an alert fires when MemAvailable stays below 10%. The real fix, a read-only replica for reports, belongs to Handbook 6.

10.9Common mistakes

MistakeWhat happensInstead
Alerting on low freeConstant false alarms on every healthy server.Alert on MemAvailable, and on swapping in and out.
Judging a process by VSZHuge numbers that use no memory.RSS (or PSS for shared memory).
Dropping caches to “free memory”Every following read goes to disk; nothing is gained.Leave the cache alone; it's given back when needed.

✓Chapter summary

  • Each process has a virtual address space; pages use RAM only when touched. VSZ is mapped, RSS is resident.
  • The kernel fills idle RAM with the page cache and gives it back on demand; available is the number that matters.
  • Swap moves idle pages to disk, buying time and turning sudden shortages into slowdowns; continuous swapping is thrashing.
  • When memory runs out, the kernel reclaims cache, swaps, then the OOM killer sends SIGKILL to the process with the highest oom_score, adjusted by oom_score_adj, and logs it.
  • cgroup limits (MemoryMax=, MemoryHigh=, container limits) contain a hungry job so the OOM killer chooses only within it.

Key terms

Virtual address space
The private range of memory addresses a process sees, mapped by the kernel onto RAM page by page.
Page
The unit of memory the kernel manages, usually 4 KB.
RSS
Resident set size: the part of a process's memory currently in RAM.
Page cache
RAM holding copies of file contents, kept for fast re-reading and released when programs need memory.
Overcommit
The kernel allowing programs to reserve more memory in total than the machine has.
Swap
Disk space used to hold memory pages moved out of RAM.
OOM killer
The kernel mechanism that kills a process to free memory when none can otherwise be found.
oom_score_adj
A per-process value from −1000 to 1000 added to its OOM score; −1000 means never kill.
cgroup
A control group: a set of processes the kernel accounts for and limits together.

Check your understanding

  1. free -h shows total 32Gi, used 6Gi, free 400Mi, buff/cache 25Gi, available 25Gi. Is the server short of memory? recall

    Show answer

    No. Programs use about 6 GB; most of the rest is page cache, which the kernel gives back on demand, so about 25 GB is available. Low free on a long-running server is normal.

  2. A container exits with 137. How do you find out whether it was out of memory, and whose limit it hit? apply

    Show answer

    docker inspect shows OOMKilled: true if the container hit its own memory limit. The kernel log (dmesg or journalctl -k) has “Memory cgroup out of memory: Killed process …” for a cgroup limit, or “Out of memory: Killed process …” for a machine-wide shortage. If neither appears, something else sent SIGKILL, such as a stop timeout.

  3. Explain why adding up the RSS of all PostgreSQL processes gives more than the machine's RAM. explain

    Show answer

    PostgreSQL's shared buffers are shared memory mapped by every backend. Each backend's RSS includes the shared pages it has touched, so the same pages are counted many times. PSS (from smem or smaps_rollup) splits shared pages between the processes using them.

  4. A server becomes extremely slow for minutes at a time but nothing is killed. vmstat 1 shows si and so in the thousands. What's happening, and what would you do? debug

    Show answer

    Thrashing: memory demand exceeds RAM, and pages are continuously swapped out and back in. Find the processes with the largest resident and swapped memory (VmSwap in /proc/<pid>/status), reduce or limit them (a cgroup MemoryMax=), or add RAM. Swap bought time; the shortage is real.

  5. Design memory protection for a server that runs PostgreSQL and, at night, a Python export job that sometimes uses a lot of memory. design

    Show answer

    Run the export as a systemd service or timer with MemoryHigh= and MemoryMax= well below what PostgreSQL needs, so it's killed first and alone. Give the postmaster OOMScoreAdjust=-1000. Size PostgreSQL's memory settings (shared buffers, work_mem per connection) with headroom. Add a little swap for warning time and alert on MemAvailable. Better still, run the export elsewhere, against a replica.

  6. Compare MemoryHigh= and MemoryMax=. compare

    Show answer

    MemoryHigh= is soft: above it, the kernel reclaims the cgroup's memory hard and throttles it, slowing it down, but nothing is killed. MemoryMax= is hard: the cgroup can't exceed it, and if reclaim fails the OOM killer kills one of its processes. Use High as a brake a little below Max.
