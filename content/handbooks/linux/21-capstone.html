Capstone: Stagedoor's servers end to end

In January, Stagedoor had three servers that nobody could describe. This chapter puts the whole book to work: a web server built from a written baseline by one idempotent script, checked for drift, then put through an on-sale drill until it holds. By the end you can

  • Turn a server baseline into a build script that's idempotent and has a check mode.
  • Build a web server from nothing with it, and detect and repair drift.
  • Run a load drill and a crash drill, and read what they tell you.
  • Deploy a fix as a new release through the same script.
  • Hand a server over with a short, honest list of what isn't covered yet.

21.2From baseline to server

The script follows one pattern for every item: a check function that answers “is this item as the baseline says?” and a fix function that makes it so. The script runs the check; if it fails, it runs the fix and the check again, and stops if it still fails. That gives three properties for free:

  • Idempotent (Chapter 17): a second run finds every item ok and changes nothing, so it's always safe to run again, including after a half-finished first run.
  • A check mode: with --check, it reports what differs and changes nothing. Run on a schedule, that's drift detection: a hand edit or a stray package shows up the next morning.
  • Small, visible changes: each line of output says whether that item was already right or was fixed.

This is exactly what configuration-management tools such as Ansible do, with a library of ready-made, tested “check and fix” modules and many machines at once. The book's script is the same idea at a size you can read in one sitting; Stagedoor will move to Ansible or to images built by CI when it moves to the cloud (Handbook 5).

Key idea

A server you can rebuild from a script in minutes is a server you can test, replace, scale and trust. A server you can only repair is a pet.

21.3What writing the script taught

The script below was tested on a fresh Ubuntu 24.04 system, and the testing found four bugs in its first drafts, each one a lesson from an earlier chapter turning up again:

  1. set -e is off inside if (Chapter 17). The checks run inside a test, so a check with several commands reported success whenever its last command succeeded. Every check now joins its tests with && or || return 1.
  2. grep -q plus pipefail (Chapter 2). sshd -T | grep -q … failed although the line was there: grep -q exits at the first match, sshd dies writing to the closed pipe (SIGPIPE), and pipefail reports that as a failure. After a long-output command, use grep … >/dev/null.
  3. A new release isn't running until the service restarts (Chapter 5, Chapter 8). The first draft switched current to the new release and reported success while the old code kept running. The fix restarts the service when its release changes.
  4. sshd -t needs /run/sshd, which Ubuntu 24.04 creates only when ssh.socket first starts sshd. On a fresh server nobody has connected to yet, the check failed with “Missing privilege separation directory”. The script creates it.

None of these would have been found by reading. All four were found by running the script on a machine built for the purpose and throwing it away afterwards, which is the habit this chapter is really about.

21.4Drills

A server that builds cleanly can still fail under load, and the only way to know is to load it. Two drills cover most of what goes wrong on an on-sale:

  • A load drill. More concurrent requests than the busiest real moment, through the same path as real traffic (nginx in front of the app), while you watch everything Chapter 20 taught: first5.sh, nginx's error and access logs, listen-queue overflows. ab (Apache Bench) is enough to start; hey, wrk, k6 and Locust do more realistic traffic.
  • A failure drill. Kill something on purpose during the load (the app, a whole server), and measure what users see and how long recovery takes. It tests restart policies, health checks and whether there's a second server to take over.

Run drills against a copy, never against the servers fans are using; announce them; stop at the first sign of harm to anything real; and write down the numbers, because the next drill compares with them.

    build-web.shbash

    #!/usr/bin/env bash
# build-web.sh [--check] · build a Stagedoor web server from the baseline, or check one against it.
# Run as root from the directory holding files/ and keys/. Safe to run again: it fixes only what differs.
set -euo pipefail
cd -- "$(dirname -- "$0")"

mode=build; [[ ${1:-} == --check ]] && mode=check
release=${RELEASE:-2026.11.1}
problems=0

# ensure "description" CHECK FIX: run CHECK; if it fails, run FIX and CHECK again (or, in --check mode, report it).
# CHECK functions run inside "if", where set -e is off (Chapter 17), so each one joins its tests with && or "|| return 1".
# After a long-output command, use "grep … >/dev/null", not "grep -q": -q exits early, the writer dies of SIGPIPE,
# and pipefail turns that into a failure.
ensure() {
  local what=$1 check=$2 fix=$3
  printf '%-50s ' "$what"
  if "$check" >/dev/null 2>&1; then echo "ok"; return; fi
  if [[ $mode == check ]]; then echo "DIFFERS"; problems=$((problems + 1)); return; fi
  "$fix" >/dev/null
  if "$check" >/dev/null 2>&1; then echo "fixed"; else echo "FAILED"; exit 1; fi
}
same() { cmp -s "files/$1" "$2"; }                    # is the installed file exactly our copy?
put()  { install -D -m "${3:-644}" "files/$1" "$2"; }  # install our copy

# 1. packages (Chapter 8)
pkgs=(nginx nftables openssh-server unattended-upgrades needrestart python3)
c_pkgs() { for p in "${pkgs[@]}"; do dpkg-query -W -f='${Status}' "$p" | grep -q "install ok installed" || return 1; done; }
f_pkgs() { apt-get update -q && DEBIAN_FRONTEND=noninteractive apt-get install -y -q "${pkgs[@]}"; }
ensure "packages installed" c_pkgs f_pkgs

# 2. people: personal accounts in sudo and ssh-users, password locked, key from keys/ (Chapters 4, 16)
c_people() {
  getent group ssh-users || return 1
  for k in keys/*.pub; do
    u=$(basename "$k" .pub)
    id -nG "$u" | grep -qw ssh-users && id -nG "$u" | grep -qw sudo &&
      cmp -s "$k" "/home/$u/.ssh/authorized_keys" || return 1
  done
}
f_people() {
  getent group ssh-users || groupadd ssh-users
  for k in keys/*.pub; do
    u=$(basename "$k" .pub)
    id "$u" >/dev/null 2>&1 || useradd --create-home --shell /bin/bash "$u"
    usermod -aG sudo,ssh-users "$u"; passwd -l "$u"
    install -d -o "$u" -g "$u" -m 700 "/home/$u/.ssh"
    install -o "$u" -g "$u" -m 600 "$k" "/home/$u/.ssh/authorized_keys"
  done
}
ensure "people and their SSH keys" c_people f_people

c_app_files() {
  id stagedoor &&
  same app.py "/opt/stagedoor/releases/$release/app.py" &&
  [[ $(readlink /opt/stagedoor/current) == "releases/$release" ]] &&
  same stagedoor.env /etc/stagedoor/stagedoor.env &&
  [[ $(stat -c '%U:%G %a' /etc/stagedoor/stagedoor.env) == "root:stagedoor 640" ]] &&
  [[ $(stat -c '%U:%G %a' /var/lib/stagedoor) == "stagedoor:stagedoor 750" ]]
}
f_app_files() {
  id stagedoor >/dev/null 2>&1 || useradd --system --user-group --no-create-home --shell /usr/sbin/nologin stagedoor
  put app.py "/opt/stagedoor/releases/$release/app.py"
  ln -s "releases/$release" /opt/stagedoor/current.new && mv -T /opt/stagedoor/current.new /opt/stagedoor/current
  install -d -o root -g stagedoor -m 750 /etc/stagedoor
  install -o root -g stagedoor -m 640 files/stagedoor.env /etc/stagedoor/stagedoor.env
  install -d -o stagedoor -g stagedoor -m 750 /var/lib/stagedoor
  if systemctl is-active -q stagedoor; then systemctl restart stagedoor; fi   # new code runs only after a restart
}
ensure "app release $release, config and data" c_app_files f_app_files

# 5. the app as a sandboxed service (Chapters 6, 12, 18)
c_app_unit() {
  same stagedoor.service /etc/systemd/system/stagedoor.service &&
  same hardening.conf /etc/systemd/system/stagedoor.service.d/hardening.conf &&
  systemctl is-enabled stagedoor && systemctl is-active stagedoor

f_app_unit() {
  put stagedoor.service /etc/systemd/system/stagedoor.service
  put hardening.conf /etc/systemd/system/stagedoor.service.d/hardening.conf

# 6. nginx in front, with limits for on-sales (Chapters 12, 14)
c_nginx() {
  same nginx-site.conf /etc/nginx/sites-available/stagedoor &&
  [[ $(readlink /etc/nginx/sites-enabled/stagedoor) == /etc/nginx/sites-available/stagedoor ]] &&
  [[ ! -e /etc/nginx/sites-enabled/default ]] &&
  grep -q "worker_rlimit_nofile 65536;" /etc/nginx/nginx.conf &&
  grep -q "worker_connections 8192;" /etc/nginx/nginx.conf &&
  same nginx-limits.conf /etc/systemd/system/nginx.service.d/limits.conf &&
  nginx -tq && systemctl is-active nginx
}
f_nginx() {
  put nginx-site.conf /etc/nginx/sites-available/stagedoor
  ln -sfn /etc/nginx/sites-available/stagedoor /etc/nginx/sites-enabled/stagedoor
  rm -f /etc/nginx/sites-enabled/default
  grep -q "worker_rlimit_nofile" /etc/nginx/nginx.conf || sed -i "s/^worker_processes auto;/&\nworker_rlimit_nofile 65536;/" /etc/nginx/nginx.conf
  sed -i "s/worker_connections [0-9]*;/worker_connections 8192;/" /etc/nginx/nginx.conf
  put nginx-limits.conf /etc/systemd/system/nginx.service.d/limits.conf
  nginx -tq; systemctl daemon-reload; systemctl restart nginx
}
ensure "nginx site, limits and backlog" c_nginx f_nginx

At Stagedoor: ready for the next on-sale, and for the cloud

The real drill on Tuesday 24 November went the way the lab did. door-5 built in four minutes, packages included, and a second run changed nothing. The first load drill, at three times July's peak, failed 3% of requests: the app was started with --backlog 64, copied from a 2023 configuration that nobody had looked at since. Release 2026.11.2 went out through the script; the second drill had no failures. The crash drill showed what everyone half knew: with one app process per server, a crash is a full outage on that server for two seconds, so door-5 joins door-3 behind Atlantica's load balancer, whose health check now takes a server out in one second.

On Thursday 26 November, door-2 is switched off. In January, Rafaela found three servers nobody could describe. In November, every server Stagedoor runs can be described, checked and rebuilt from a repository, with the incidents of the year written into it as rules. That's also the first step of the move to AWS in 2027, which Handbook 5 tells: the same baseline, expressed as Terraform and images instead of a script, on servers that nobody will ever need to repair by hand.

21.7Review: is this server ready?

Before a server takes real traffic, go through these questions; each points to the chapter that answers it. A “no” isn't a failure, but it should be on the handover list (Table 21.2).

  1. Can it be rebuilt from the repository alone, and has that been tested on a fresh machine? (1, 21)
  2. Is its release supported for at least another year? (1, 8)
  3. Does every person log in as themselves, with a key, and is there no other way in? (4, 16)
  4. Does every service run as its own user, sandboxed, restarting on failure and stopping gracefully? (5, 6, 18)
  5. Can logs, disks, memory or file descriptors run out without an alert first? (7, 9–12)
  6. Is everything that listens supposed to, reachable only from where it should be? (13, 15)
  7. Do certificates renew themselves, and does something warn before they expire? (14)
  8. Has it survived a load drill above the expected peak, and a crash drill? (12, 20, 21)
  9. Is there a check that would notice tomorrow if someone changed it by hand today? (21)

✓Chapter summary

  • A baseline becomes useful when it's executable: a script of check-and-fix items, idempotent, with a --check mode for drift.
  • Build servers from the repository on fresh machines; never edit a server you could rebuild.
  • Test the script itself on throwaway machines: that's where its bugs are found.
  • Drills find limits before fans do: a load drill above the peak, and a crash drill, watched with the method from Chapter 20.
  • Deploy fixes through the same path, as new releases, and drill again.
  • Hand over with an honest list of what isn't automated yet.

Key terms

Build script
A script that turns a fresh machine into a server matching the baseline, item by item.
Drift
Differences between a running server and its baseline, usually from changes made by hand.
Check mode
Running a build or configuration tool so that it reports what differs without changing anything.
Load drill
A planned test that sends more traffic than the expected peak to a copy of the system to find its limits.
Failure drill
A planned test that breaks a component on purpose to measure the effect and the recovery.
Configuration management
Tools (Ansible, Salt, Puppet) that apply and check a declared configuration across many machines.

Check your understanding

  1. What two properties make a build script safe to run on a server that's already in service? recall

    Show answer

    Idempotence (it changes only what differs from the baseline, so a correct server is left alone) and checks before fixes (each item is tested first, and a fix is verified by testing again). A check mode adds a third: you can see what it would change before letting it.

  2. Write a check and a fix function, in the script's style, for “/etc/stagedoor is owned by root:stagedoor with mode 750”. apply

    Show answer

    c_etc() { [[ $(stat -c '%U:%G %a' /etc/stagedoor) == "root:stagedoor 750" ]]; } and f_etc() { install -d -o root -g stagedoor -m 750 /etc/stagedoor; }, then ensure "/etc/stagedoor ownership" c_etc f_etc.

  3. Explain why the first drill failed even though nginx's limits had been raised in Chapter 12's style. explain

    Show answer

    The bottleneck had moved inward: nginx accepted the connections, but the app behind it listened with a backlog of 5, so its accept queue overflowed and nginx's connections to it timed out (504). Limits apply at every layer of a request's path; raising one layer moves the bottleneck to the next.

  4. After a deploy with the build script, readlink /opt/stagedoor/current shows the new release, but the app still behaves like the old one. What do you check? debug

    Show answer

    Whether the running process started before the switch: systemctl show stagedoor -p ActiveEnterTimestamp or ps -o lstart= -p $(systemctl show -p MainPID --value stagedoor). If so, it never restarted (the first draft's bug): restart it, and make the script restart the service when the release changes. Also check that the new code is really in the new release directory, and that nothing caches the old path.

  5. Design the drills Stagedoor should run before Maré Festival's on-sale in 2028, when 200,000 fans arrive in ten minutes. design

    Show answer

    On a full copy of production: a load drill ramping to well above the expected peak, with realistic traffic (logins, seat holds, checkouts in the right proportions), watched at every layer (load balancer, web, app, database, payment stubs) for saturation, errors and queue overflows; a crash drill killing an app process, a whole server and the database primary during load; a dependency drill with the payment provider slowed down. Each with numbers written down and compared with the last run, and a go/no-go review. Handbook 4's capstone does exactly this.

  6. Compare this chapter's build script with configuration-management tools and with machine images built by CI. compare

    Show answer

    The script is short, readable and dependency-free, but every check and fix is hand-written and it handles one machine at a time. Configuration-management tools provide tested, idempotent modules, inventories of many machines and check modes, at the cost of learning the tool. Images built by CI go further: the server is built once, tested, and every instance starts identical; changes mean a new image, not changes to running machines. Many teams combine images for the base and configuration management for the last mile.
