Kubernetes and workload identity

A Kubernetes cluster on a cloud has two permission systems stacked on top of each other: Kubernetes' own RBAC, which decides who may do what to the cluster, and the cloud's IAM, which decides what pods may do to everything else. Each has its own traps, and the gap between them, where a pod quietly borrows its node's cloud role, is the biggest trap of all. This chapter covers both, and how to join them safely on EKS, AKS and GKE.

By the end you can

  • Explain the two permission systems in a managed cluster, and which one each request goes through.
  • Read and write Kubernetes Roles, ClusterRoles and bindings, and spot the dangerous ones.
  • Give people cluster access from your identity provider, without shared kubeconfigs.
  • Give each pod its own AWS role with EKS Pod Identity or IRSA, and keep pods away from the node's role.

Before you start

  • Workload identity and the metadata service (Chapter 15); OIDC tokens and audiences (Chapter 3, Chapter 4).
  • Roles, attributes and relationships (Chapter 6). Basic Kubernetes words: pod, namespace, deployment.

At Larder

Larder runs its containers on ECS (Chapter 15), and in March 2027 the question came up that every growing team asks: should we move to Kubernetes? Eli and Dee built a proof of concept in the staging account: an EKS cluster running Engine A, the route planner, in a namespace called dispatch-poc.

Two weeks in, Dee ran a throwaway debugging pod in that namespace and found she could read Engine A's route plans in S3 from it, and list every secret in the cluster. Neither was intended, and neither was a bug in Kubernetes. Section 16.7 explains both, and what Larder decided.

16.1Two permission systems

In a managed Kubernetes cluster, every action goes through one of two doors:

  • Requests to the cluster (create a deployment, read a secret, exec into a pod) go to the Kubernetes API server and are decided by Kubernetes RBAC.
  • Requests to the cloud (read a bucket, publish to a queue) go to the cloud's APIs and are decided by IAM, using whatever cloud credentials the pod has.

People need an identity in both (to deploy, and sometimes to look at cloud resources); pods need one in both too (a Kubernetes service account for the API, a cloud role for everything else). The cloud provider glues them together, and the glue is where the security decisions are.

16.2Kubernetes RBAC

Kubernetes RBAC (Chapter 6, in its role-based form) has four objects:

  • A Role lists rules (API groups, resources, verbs) inside one namespace. A ClusterRole does the same cluster-wide, or as a reusable template.
  • A RoleBinding grants a Role, or a ClusterRole, to subjects within one namespace. A ClusterRoleBinding grants a ClusterRole everywhere.
  • Subjects are users, groups and service accounts. Kubernetes has no user database: users and groups are whatever the authenticator says (on EKS, mapped from IAM; 16.4).

Everything is allow-only and default deny, like AWS security groups (Handbook 1, Chapter 9). Some permissions are far more powerful than they look, because they let you become someone else:

Table 16.1 · Kubernetes permissions that are really admin
PermissionWhy it's dangerous
get / list on secretsreads every secret in the namespace, including other service accounts' credentials

create on pods/execa shell inside someone else's running pod

Watch out: bindings to groups you didn't think about

Every service account belongs to the groups system:serviceaccounts and system:serviceaccounts:namespace, and every authenticated identity to system:authenticated. Binding a role to one of these, often copied from an installation guide “to make the chart work”, grants it to every pod in the namespace, or the cluster, including ones created later.

16.3Service accounts and their tokens

Every pod runs as a Kubernetes service account, the namespace's default one unless you choose another. Kubernetes mounts a token for it into the pod, which the pod uses to call the API server. Modern clusters issue projected tokens: JWTs (Chapter 3) bound to the pod, with an audience and an expiry of about an hour, refreshed by the kubelet. Three habits:

  • One service account per workload, never default, so permissions and cloud roles attach to exactly one thing.
  • No API token unless needed: most application pods never call the Kubernetes API. Set automountServiceAccountToken: false on them.
  • Bind narrowly: a Role and RoleBinding in the workload's namespace, for the few resources it needs.

16.4People into the cluster

On EKS, people authenticate with their AWS identity: aws eks get-token (run for you by kubectl) produces a short-lived token from their current role session, and the API server checks it with IAM. Access entries then map IAM principals to Kubernetes permissions, either through AWS-managed access policies (cluster admin, admin, edit, view; cluster-wide or per namespace) or through Kubernetes groups that your own RoleBindings use.

Combine that with Identity Center (Chapter 12) and cluster access follows the same groups as everything else: an access entry for the AWSReservedSSO_Developer_… role with view on all namespaces and edit on the team's own, and one for the elevated PlatformAdmin role with cluster admin, which itself is only granted just in time (Chapter 14). No kubeconfig contains a long-lived credential. Turn off the default that makes the cluster's creator a permanent admin, once access entries exist.

aws-authOlder EKS clusters map IAM to Kubernetes users through a ConfigMap called aws-auth in kube-system. Anyone who can edit it can make themselves admin, and a typo can lock everyone out. Access entries replace it and are managed through the EKS API, with CloudTrail recording every change.

16.5Pods into AWS

Every EKS worker node is an EC2 instance with an instance profile: the node role, which the node needs to join the cluster, pull images and manage pod networking. Here's the trap: unless you stop it, any pod on the node can reach the node's metadata service (Chapter 15) and get the node role's credentials. Add an application permission to the node role, “just so Engine A can read its config”, and every pod on every node has it.

EKS offers two ways to give a pod its own role, both based on its service account:

Then close the trap: keep the node role to the AWS-managed node policies and nothing else, and stop pods reaching the node's metadata service (IMDSv2 with a hop limit of 1 on the nodes, or a network policy that blocks 169.254.169.254). A pod without an association then has no AWS access at all, which is the right default.

Key idea

In a cluster, the service account is the workload's identity in both worlds. Give each workload its own, bind it narrowly in Kubernetes, and associate it with its own role in the cloud.

On Azure

Microsoft Entra Workload ID uses the cluster's OIDC issuer: you add a federated identity credential to a user-assigned managed identity saying “trust tokens for service account engine-a in namespace dispatch-poc from this cluster”. The pod exchanges its projected token for an Entra token, much like IRSA. For people, Entra ID groups can be used directly in Kubernetes RoleBindings, or Azure RBAC can govern Kubernetes objects too.

On Google Cloud

With Workload Identity Federation for GKE, you grant IAM roles directly to a Kubernetes service account's principal identifier, and the GKE metadata server on each node gives pods tokens for it while hiding the node's own service account. It's on by default in Autopilot clusters, which removes the node-role trap entirely.

16.7At Larder: the experiment, and the decision

At Larder: solved

Dee's two findings had two causes. The route plans: to get Engine A working on the first day, someone had added read access to the route-plan bucket to the node role, and the nodes allowed pods to reach the metadata service, so every pod, debugging pods included, could read them. The secrets: Engine A's Helm chart documentation suggested a ClusterRoleBinding of cluster-admin to the namespace's service accounts group, “to make installation simple”, and that binding was still there, so every pod in dispatch-poc was cluster admin.

Fixing both took a morning: an Engine A service account with a Pod Identity association to its own role, the S3 permission removed from the node role, IMDS blocked for pods, the binding replaced by a Role for the two config maps Engine A reads, and access entries for the Identity Center roles. But the exercise answered the bigger question too. On 30 April 2027, Eli and Dee recommended staying on ECS: a team of Larder's size gets per-task roles there by default, with one permission system instead of two. They wrote down the identity rules above for the day the question comes back, and deleted the cluster that afternoon.

16.8Lab: ask “can I?”

Lab 16 · Kubernetes RBAC, by hand and for real

You'll answer kubectl auth can-i questions from the experiment's Roles and bindings with a small evaluator, find the dangerous binding, fix it, then (optionally) repeat it in a real local cluster. You need Python 3; for the optional part, Docker, kind and kubectl. Cost: nothing; kind runs on your machine.

kube_rbac.pyPython 3.8+

# kube_rbac.py · answer "kubectl auth can-i" from Roles, ClusterRoles and their bindings
CLUSTER_ROLES = {
    "cluster-admin": [{"resources": ["*"], "verbs": ["*"]}],
    "view":          [{"resources": ["pods", "configmaps", "deployments", "services"],   # no secrets
                       "verbs": ["get", "list", "watch"]}],
}
ROLES = {   # (namespace, name) → rules
    ("dispatch-poc", "engine-a-config"): [{"resources": ["configmaps"], "verbs": ["get"]}],
}
BINDINGS = [   # (kind, namespace or None, role kind, role name, subjects)
    ("ClusterRoleBinding", None, "ClusterRole", "view", ["Group:larder:engineers"]),
    ("RoleBinding", "dispatch-poc", "Role", "engine-a-config",
     ["ServiceAccount:dispatch-poc:engine-a"]),
    ("ClusterRoleBinding", None, "ClusterRole", "cluster-admin",            # "to make the chart install"
     ["Group:system:serviceaccounts:dispatch-poc"]),
]

def identity(subject):
    """A subject string → (name, groups), as the API server sees it."""
    kind, rest = subject.split(":", 1)
    if kind == "ServiceAccount":
        ns, name = rest.split(":")
        return f"system:serviceaccount:{ns}:{name}", {"system:serviceaccounts",
                                                      f"system:serviceaccounts:{ns}", "system:authenticated"}
    name, groups = rest.split("|")
    return name, set(groups.split(",")) | {"system:authenticated"}

def matches(binding_subject, name, groups):
    kind, value = binding_subject.split(":", 1)
    if kind == "ServiceAccount":
        ns, sa = value.split(":")
        return name == f"system:serviceaccount:{ns}:{sa}"
    return value in groups if kind == "Group" else value == name

def can_i(subject, verb, resource, namespace=None):
    name, groups = identity(subject)
    for kind, ns, role_kind, role, subjects in BINDINGS:
        if not any(matches(s, name, groups) for s in subjects):
            continue
        if kind == "RoleBinding" and ns != namespace:       # a RoleBinding only works in its namespace
            continue
        rules = CLUSTER_ROLES[role] if role_kind == "ClusterRole" else ROLES[(ns, role)]
        for r in rules:
            if ("*" in r["resources"] or resource in r["resources"]) and ("*" in r["verbs"] or verb in r["verbs"]):
                return f"yes  ({kind} → {role})"
    return "no"

if __name__ == "__main__":
    DEE = "User:dee@larder.example|larder:engineers"
    ENGINE = "ServiceAccount:dispatch-poc:engine-a"
    DEBUG = "ServiceAccount:dispatch-poc:default"
    for who, verb, res, ns in [(DEE, "list", "pods", "dispatch-poc"), (DEE, "get", "secrets", "dispatch-poc"),
                               (ENGINE, "get", "configmaps", "dispatch-poc"), (ENGINE, "get", "secrets", "kube-system"),
                               (DEBUG, "delete", "nodes", None), ("ServiceAccount:other:default", "get", "secrets", "other")]:
        print(f"{who.split('|')[0].split(':', 1)[1]:<28} {verb:<6} {res:<10} {ns or '(cluster)':<13} {can_i(who, verb, res, ns)}")

✓Chapter summary

  • A managed cluster has two permission systems: Kubernetes RBAC for the cluster API, IAM for the cloud.
  • RBAC: Roles and ClusterRoles, bound per namespace or cluster-wide to users, groups and service accounts. Some permissions (secrets, create pods, exec, bind, impersonate) are admin in disguise.
  • Each workload gets its own service account with projected, short-lived tokens, mounted only if needed.
  • People come in through their cloud identity: access entries on EKS, mapped from SSO roles.
  • Pods get their own AWS roles with Pod Identity or IRSA; keep the node role minimal and block pods from IMDS.

Key terms

Kubernetes RBAC
Kubernetes' allow-only, role-based authorisation for its API.
Role / ClusterRole
Rules within a namespace / cluster-wide (or reusable).
RoleBinding / ClusterRoleBinding
Grants of a role to subjects in a namespace / everywhere.
Service account
A pod's identity for the Kubernetes API, and the anchor for its cloud role.
Projected token
A short-lived, audience-bound service account JWT mounted into a pod.
Access entry
An EKS mapping from an IAM principal to Kubernetes permissions.
Node role
The IAM role of an EKS worker node.
EKS Pod Identity / IRSA
Two ways to give a service account its own IAM role.

Check your understanding

  1. A pod reads an S3 bucket and lists pods in its namespace. Which permission system decides each? recall

    Show answer

    Reading S3 is decided by IAM, using the pod's AWS credentials. Listing pods is decided by Kubernetes RBAC, using its service account.

  2. Why is create on pods in a namespace roughly as powerful as everything any service account there can do? explain

    Show answer

    Whoever can create a pod chooses which service account it runs as, so the pod gets that account's RBAC permissions and its associated cloud role.

  3. Every pod in a cluster can read a bucket that only one application should. Name the two likely causes. apply

    Show answer

    The bucket permission is on the node role, and pods can reach the node's metadata service. Or a shared service account (such as default) is associated with a role that has the permission.

  4. Write the conditions an IRSA trust policy needs, and say what goes wrong without the sub condition. apply

    Show answer

    StringEquals on …:sub = system:serviceaccount:namespace:name and …:aud = sts.amazonaws.com. Without sub, any service account in the cluster can assume the role.

  5. Design people's access to a new EKS cluster for a company already using Identity Center with just-in-time admin. design

    Show answer

    Access entries: ViewOnly's role gets view on all namespaces; each team's Developer role gets edit on its namespace; the just-in-time PlatformAdmin role gets cluster admin. Remove the creator's bootstrap admin, and record changes in CloudTrail.

  6. Compare how GKE and EKS stop pods using the node's cloud identity. compare

    Show answer

    GKE's metadata server, with Workload Identity Federation, hides the node's service account from pods and serves only the pod's own identity. On EKS you must do it yourself: hop limit 1 or a network policy blocking IMDS, and a minimal node role.
