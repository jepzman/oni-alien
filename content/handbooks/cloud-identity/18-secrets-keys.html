Secrets and encryption keys

Roles removed most secrets from Larder's systems, but not all: databases still have passwords, partners still issue API keys. This chapter covers where the remaining secrets should live and how they rotate, then turns to encryption keys, where AWS KMS adds a second permission system beside IAM: who may use a key is decided by the key's own policy, and that turns encryption into an access control you can reason about.

By the end you can

  • Choose between Secrets Manager and Parameter Store, and have applications fetch secrets at run time.
  • Rotate a secret without downtime.
  • Explain envelope encryption, data keys and encryption context.
  • Read and write a KMS key policy, and know how it combines with IAM.
  • Decide when a customer managed key is worth it.
  • Find leaked secrets, and respond in the right order.

Before you start

  • Workload roles (Chapter 15).

At Larder

After the compromised action in March (Chapter 17), Larder turned on GitHub's secret scanning for every repository. On Thursday 6 May 2027, the first scan of larder-core's full history found a file called .env.production, committed by Jasper in June 2024 and deleted the next day. It contained the password of the orders database's application user, and the password had never been changed. It was also in /etc/larder/env on each of Larder Core's three virtual machines, where the application read it at start-up.

The same week, Eli had to settle a question left over from December (Chapter 11): staging's forgotten customer managed key. Should Larder use them at all? Section 18.9 has both answers.

18.1The secrets that remain

After workloads use roles (Chapter 15) and pipelines use federation (Chapter 17), what's left are secrets AWS can't replace: database passwords, third-party API keys (a maps provider, a payment provider), signing keys for webhooks and tokens (Chapter 19), and certificates' private keys. Each one is a long-lived credential, so the rules from Chapter 1 apply: as few as possible, each stored in exactly one place, readable by exactly the workloads that need it, and rotated.

They leak from the same places every time: source code and its history, environment files on servers, container images, CI logs (Chapter 17), chat messages and tickets, laptops' shell history. Notice that Larder's password was in two of them, and that deleting a file from a repository doesn't remove it from the history.

Use Secrets Manager for anything that should rotate; Parameter Store for settings, including the odd secret that genuinely can't. Either way, access is IAM like everything else: the workload's role is allowed secretsmanager:GetSecretValue on exactly its own secrets, as Dispatch's policy did in Chapter 9.

Have applications fetch secrets at run time, through the SDK, with a short cache, rather than receiving them once in an environment variable at start. Then a rotated secret is picked up without a restart. ECS can inject secrets into containers' environments at start (through the task execution role, Chapter 15), which is better than a file, but means a restart after every rotation.

18.3Rotation without downtime

Rotation fails when there's a moment where the new password isn't valid yet, or the old one no longer is, but something still uses it. Secrets Manager's rotation works in four steps to avoid that: create the new secret value, set it in the database, test it, then mark it current. The safest pattern for databases is alternating users: two database users take turns, so while one's password is being changed, the other's still works. For RDS master passwords, RDS can manage the secret itself, including rotation, with no function to write.

Clients must cope: fetch the current secret when a connection fails authentication, rather than retrying the cached one forever. Rotate often enough that it's routine (every 30 to 90 days), and immediately when a secret may have leaked.

18.4Encryption keys and envelope encryption

AWS KMS holds encryption keys inside hardware security modules: a KMS key never leaves KMS in plain form. You don't send gigabytes to KMS to encrypt them; you use envelope encryption:

Three consequences matter for access control:

  • Reading the data needs two permissions: access to where it's stored (S3, a database) and kms:Decrypt on the key. That's why Larder's staging uploads needed kms:GenerateDataKey (Chapter 11).
  • Encryption context is a set of key–value pairs bound to the encryption: decrypting needs the same pairs, they're recorded in CloudTrail, and policies can require them. S3, for example, uses the object's ARN.
  • Disabling or deleting the key makes every piece of data encrypted under it unreadable, which is either a disaster or, deliberately, a way to destroy data you can't otherwise find (“crypto-shredding”).

18.5Key policies: the second permission system

Every KMS key has a key policy, a resource-based policy (Chapter 10) that is the primary control on the key. KMS is stricter than most services: no principal, not even the account's administrators, can use or manage a key unless its key policy allows it, either directly or by delegating to IAM. The default key policy delegates with one statement:

{ "Sid": "Enable IAM User Permissions", "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  "Action": "kms:*", "Resource": "*" }

That means “let this account's IAM policies decide”, so anyone with AdministratorAccess can decrypt. To make the key a real second gate, replace it with statements that name who may administer the key and who may use it, and keep the two apart:

      "Effect": "Allow",

      "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
      "Resource": "*",
      "Condition": { "StringEquals": { "kms:ViaService": "s3.eu-central-1.amazonaws.com" } }
    }
  ]
}

Read aloud: “Platform admins may manage this key but not use it. The export job and the finance reporting job may use it, and only through S3.” An engineer with production PlatformAdmin can now read the export bucket's object list, but not one export's contents. They could still edit the key policy to let themselves in, but that's a deliberate, logged change you can alert on (Chapter 23), not a side effect of being an administrator. In a key policy, "Resource": "*" means “this key”.

Key idea

A customer managed key turns “who can decrypt this data?” into one short policy you can read, independent of everything IAM grants.

Watch out: locking yourself out

A key policy that names nobody able to manage it makes the key unmanageable: only AWS Support can help, and data under it may be lost. KMS refuses a new key policy that would stop you changing it, unless you explicitly bypass that safety check. Don't. Keep an administration statement for a role that will always exist, and include the break-glass role (Chapter 14).

Services that use keys on your behalf, such as EBS attaching an encrypted volume, use grants: temporary, narrow permissions on a key that the service creates and retires. You'll see them in aws kms list-grants; you rarely create them yourself.

Every option encrypts the data. What a customer managed key adds is control: a separate decision about who can read, cross-account sharing (copying an encrypted database snapshot to another account needs one), a per-use audit trail, and the ability to switch everything off. Use one where those matter; use the defaults elsewhere. With S3 and customer managed keys, turn on S3 Bucket Keys, which cut KMS requests, and their cost, by orders of magnitude.

18.7When a secret leaks

  1. Rotate first. A leaked secret is compromised the moment it's visible; investigation can wait an hour, rotation can't. Deleting the file or rewriting history doesn't un-leak it.
  2. Look for use between the leak and the rotation: database logs, CloudTrail, the provider's dashboard.
  3. Remove the copies you control: history rewrites, old images, environment files, tickets. This limits the next leak, not this one.
  4. Prevent the next one: secret scanning with push protection on every repository, pre-commit hooks for developers, and fewer secrets overall.

On Azure

Key Vault holds secrets, keys and certificates. Use the Azure RBAC permission model rather than the older vault access policies, so that data-plane roles such as Key Vault Secrets User can be assigned to managed identities per vault or per secret. Turn on soft delete and purge protection, so a deleted vault or key can be recovered.

On Google Cloud

Cloud KMS keys live in key rings, and access is plain IAM: roles/cloudkms.cryptoKeyEncrypterDecrypter granted on one key to one service account. There's no separate key policy, so the separation of duties comes from granting admin roles and use roles to different principals. Secret Manager stores versioned secrets with rotation notifications.

18.9At Larder: a password from 2024, and a key decision

At Larder: solved

The password was rotated within the hour, following 18.7, and the database's connection logs showed no logins from anywhere but Larder Core's three hosts. Then the root cause: Ben's team moved the database credentials into Secrets Manager with rotation every 30 days using two alternating database users, and changed Larder Core to fetch the secret through the SDK with a five-minute cache, retrying once with a fresh copy when authentication fails. /etc/larder/env lost its last secret, and the larder-core role (Chapter 15) gained GetSecretValue on exactly that secret. Secret scanning with push protection now runs on every repository.

Eli's key decision, written up on 14 May: S3-managed keys remain the default everywhere. Customer managed keys are used where they buy something: for the order exports bucket, with the key policy in 18.5, so that platform admins can't read customers' order histories; and for the database's snapshots, so that a copy can go to a separate backup account (Chapter 20). Staging's forgotten key from Chapter 11: CloudTrail showed no use since December, so it was scheduled for deletion with the maximum 30-day waiting period, in case something nobody remembered still needed it. Nothing did.

18.10Lab: envelope encryption by hand

Lab 18 · A pretend KMS, then the real one

You'll encrypt an order export the way S3 does with KMS, then see what the encryption context, tampering and a disabled key do; optionally, you'll repeat the key ideas with a real KMS key. You need Python 3 and the cryptography package (pip install cryptography); for the optional part, the AWS CLI. Cost: the Python part is free; a real KMS key costs $1 a month, charged by the hour, so a few cents if you schedule its deletion at the end.

envelope.pyPython 3.8+, cryptography

# envelope.py · envelope encryption the way KMS does it, with a pretend KMS
# Needs: pip install cryptography
import json, os
from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

class PretendKMS:
    """Holds the key-encryption key. In AWS it never leaves KMS's hardware; here, it never leaves this object."""
    def __init__(self):
        self._kek, self.enabled = AESGCM.generate_key(bit_length=256), True

    def _aad(self, context):
        return json.dumps(context, sort_keys=True).encode()

    def generate_data_key(self, context):
        if not self.enabled:
            raise PermissionError("KMS: key is disabled")
        data_key, nonce = AESGCM.generate_key(bit_length=256), os.urandom(12)
        wrapped = nonce + AESGCM(self._kek).encrypt(nonce, data_key, self._aad(context))
        return data_key, wrapped                    # like GenerateDataKey: Plaintext + CiphertextBlob

    def decrypt(self, wrapped, context):
        if not self.enabled:
            raise PermissionError("KMS: key is disabled")
        return AESGCM(self._kek).decrypt(wrapped[:12], wrapped[12:], self._aad(context))

def encrypt(kms, plaintext, context):
    data_key, wrapped = kms.generate_data_key(context)
    nonce = os.urandom(12)
    blob = {"wrapped_key": wrapped, "nonce": nonce, "data": AESGCM(data_key).encrypt(nonce, plaintext, None)}
    del data_key                                    # only the wrapped copy is kept
    return blob

def decrypt(kms, blob, context):
    data_key = kms.decrypt(blob["wrapped_key"], context)
    return AESGCM(data_key).decrypt(blob["nonce"], blob["data"], None)

def attempt(label, fn):
    try:
        print(f"{label:<34} {fn()}")
    except InvalidTag:
        print(f"{label:<34} refused: authentication failed")
    except PermissionError as e:
        print(f"{label:<34} refused: {e}")

if __name__ == "__main__":
    kms = PretendKMS()
    ctx = {"bucket": "larder-order-exports", "file": "2027-05-11.csv"}
    blob = encrypt(kms, b"order,total\nB-1042,312.40\n", ctx)
    print("stored:", {k: f"{len(v)} bytes" for k, v in blob.items()}, "\n")
    attempt("decrypt with the right context", lambda: decrypt(kms, blob, ctx))
    attempt("decrypt claiming another file", lambda: decrypt(kms, blob, dict(ctx, file="2027-05-12.csv")))
    tampered = dict(blob, data=blob["data"][:-1] + bytes([blob["data"][-1] ^ 1]))
    attempt("decrypt after one bit changed", lambda: decrypt(kms, tampered, ctx))
    kms.enabled = False
    attempt("decrypt after the key is disabled", lambda: decrypt(kms, blob, ctx))

  2. Break it on purpose. In encrypt, remove the line del data_key and add blob["plain_key"] = data_key, as a hurried implementation might “for debugging”. The data now decrypts without ever asking KMS: the key policy, the audit trail and the off switch are all gone.

✓Chapter summary

  • The secrets left after roles and federation are database passwords, third-party keys, signing keys and private keys.
  • Store them in Secrets Manager (or Parameter Store), fetch at run time, rotate automatically with alternating users.
  • Envelope encryption: data keys encrypt data locally; KMS keys wrap data keys and never leave KMS. Encryption context binds and records each use.
  • A key policy is the primary control on a KMS key; a customer managed key can separate who manages it from who can decrypt.
  • Use customer managed keys where control, cross-account sharing or audit matter; defaults elsewhere.
  • When a secret leaks: rotate, check for use, clean up, prevent.

Key terms

Secrets Manager
AWS's service for storing and rotating secrets.
Rotation
Replacing a secret's value regularly, without downtime.
KMS key
A key held in AWS KMS's hardware, used to wrap data keys or encrypt small data.
Data key
A key generated per object or batch to encrypt data locally.
Envelope encryption
Encrypting data with a data key and the data key with a KMS key.
Encryption context
Key–value pairs bound to an encryption, required to decrypt and logged.
Key policy
The resource-based policy that controls a KMS key.
Grant
A temporary, narrow permission on a KMS key, usually created by a service.

Check your understanding

  1. Why isn't deleting a committed password from the repository enough? recall

    Show answer

    It stays in the history and in every clone and fork, and may have been copied before the deletion. Only rotating it makes the leaked value useless.

  2. An administrator with AdministratorAccess can't decrypt a file in S3 encrypted with a customer managed key. Is that a bug? explain

    Show answer

    Not if the key policy doesn't delegate to IAM and doesn't name them: KMS requires the key policy to allow use, whatever IAM says. That's the intended second gate.

  3. Explain what encryption context adds, using S3 as the example. explain

    Show answer

    S3 binds each object's data key to the object's ARN. The wrapped key can't be used for another object; every decrypt is recorded in CloudTrail with the ARN; and key policies can require specific context values.

  4. An application caches a database password for a day; rotation runs every 30 days. What breaks, and how do you fix it? apply

    Show answer

    After rotation, new connections fail with the stale password until the cache expires. Retry once with a freshly fetched secret on authentication failure, use alternating users so the previous password stays valid during the switch, and keep the cache short.

  5. Decide which of these deserve customer managed keys: application logs; customer order exports; RDS snapshots copied to a backup account; public product images. design

    Show answer

    Order exports (a separate decision about who may read them) and snapshots copied cross-account (required to share encrypted snapshots). Logs and public images: default keys are fine, unless logs contain sensitive data that needs a separate gate.

  6. Compare how you'd let one workload read one secret on AWS and on Google Cloud. compare

    Show answer

    AWS: allow secretsmanager:GetSecretValue on that secret's ARN in the workload role's policy (and, with a customer managed key, kms:Decrypt through the key policy). Google Cloud: grant roles/secretmanager.secretAccessor on that one secret to the workload's service account.
