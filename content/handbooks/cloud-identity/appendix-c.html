C

Lab setup and safety

Most of this book's labs need nothing but Python 3. The optional AWS steps need an account you can break without consequences. This appendix sets one up, connects the CLI without access keys, puts alarms on spending, and lists what to delete when you're done.

C.2A sandbox account

If your employer has an AWS Organization, ask for a sandbox account: many companies have a Sandbox OU with a budget and an allow-list SCP, like Larder's (Chapter 20). On your own:

  1. Create a new account with an email address only you read. Don't reuse an account that has ever held real data.
  2. Secure the root user straight away (Chapter 7): a strong unique password, MFA with a passkey or security key, no access keys. Then stop using root.
  3. Turn on IAM Identity Center in one region (it's free) and create one user for yourself with the AdministratorAccess permission set, as in Chapter 12. This is how you'll sign in from now on.
  4. Pick one region for every lab and stick to it; the book uses eu-central-1.

C.3The CLI with single sign-on, no keys

aws configure sso
# SSO session name: sandbox
# SSO start URL: the AWS access portal URL from Identity Center
# SSO region: the region where you enabled Identity Center
# then choose the account and the AdministratorAccess role; profile name: sandbox
aws sso login --profile sandbox
export AWS_PROFILE=sandbox
aws sts get-caller-identity

The last command shows an assumed-role ARN with AWSReservedSSO_AdministratorAccess in it. The credentials expire with the session; aws sso login gets new ones. Never create an access key for the labs: nothing in this book needs one, and a key in a lab folder is the classic way keys leak (Chapter 17).

  --budget '{"BudgetName": "labs", "BudgetLimit": {"Amount": "5", "Unit": "USD"},
             "TimeUnit": "MONTHLY", "BudgetType": "COST"}' \

      "ComparisonOperator": "GREATER_THAN", "Threshold": 50, "ThresholdType": "PERCENTAGE"},
      "Subscribers": [{"SubscriptionType": "EMAIL", "Address": "you@example.com"}]}]'

C.5Safety rules for the labs

  • Sandbox only. Several labs deliberately break access or open a policy too wide to see what happens. Never run them where real people or data are.
  • Use the book's placeholder IDs only in text. Account IDs like 111122223333 and 999911112222 are AWS's documentation examples. When a step needs a real account ID, use your own sandbox's.
  • Don't trust real outside accounts. A trust policy naming an account you don't control lets its owner in. Labs that need a second account use a second sandbox of your own.
  • Don't test SCPs on the organisation root. Attach them to an OU with one sandbox account in it (Chapter 20).
  • Keep a way back in. Before changing a key policy, a trust policy or an SCP, make sure you're signed in with a role it doesn't affect.

C.6Cleaning up

Each lab ends with its own clean-up commands. If you skipped them, these find what's left. Delete anything you no longer need:

# roles you created (AWS service roles live under /aws-service-role/ and /aws-reserved/: leave them)
aws iam list-roles --query 'Roles[?!starts_with(Path, `/aws-`)].[RoleName, CreateDate]' --output table
# IAM users and access keys (there should be none)
aws iam list-users --query 'Users[].UserName'
aws iam generate-credential-report >/dev/null; sleep 5
aws iam get-credential-report --query Content --output text | base64 -d | cut -d, -f1,9,14
# OIDC and SAML providers
aws iam list-open-id-connect-providers
aws iam list-saml-providers
# customer managed keys and secrets (both cost money)
aws kms list-aliases --query 'Aliases[?!starts_with(AliasName, `alias/aws/`)].AliasName'
aws secretsmanager list-secrets --query 'SecretList[].Name'
# analyzers and running instances
aws accessanalyzer list-analyzers --query 'analyzers[].name'
aws ec2 describe-instances --filters Name=instance-state-name,Values=running \
  --query 'Reservations[].Instances[].InstanceId'

To delete a role, first detach its managed policies and delete its inline ones (aws iam list-attached-role-policies, detach-role-policy, list-role-policies, delete-role-policy), then aws iam delete-role. A KMS key can't be deleted at once: aws kms schedule-key-deletion --pending-window-in-days 7 is the shortest wait. When you're finished with the book, you can close the sandbox account itself; check first that nothing in it is still in use.
