Part IV · Access for software

19

Service-to-service and API access

Software calls software: your services call AWS, call each other, and call partners; partners call your APIs and send you webhooks. Each call has to say who's calling and prove it, without a person typing anything. This chapter shows how AWS signs its own API calls, how to put authentication in front of your own APIs, how to give partners keys that expire, and how to trust a webhook. It ends with the security review where Larder found three of these going wrong.

By the end you can

  • Explain what Signature Version 4 signs, and why it's stronger than a bearer token.
  • Choose an authoriser for an API on AWS: IAM, JWT, Lambda or mutual TLS.
  • Design partner API keys that expire, rotate and can be traced.
  • Verify webhooks: signature, freshness and replay.
  • Check object-level access on every endpoint, not just most of them.

Before you start

  • HMAC (Chapter 2), bearer tokens and JWT checks (Chapter 3), OAuth client credentials (Chapter 4).
  • Relationship-based checks (Chapter 6); workload roles (Chapter 15); secrets (Chapter 18).

At Larder

This chapter moves forward in time. By October 2027, Larder for Business has a portal for office managers, a Business API that some customers' procurement systems call directly, federated sign-in for clients' staff, and a billing provider that tells Larder about payments by webhook. Each piece was built and reviewed by its own team, feature by feature, and three more office clients were about to start.

On 11 October, Ana, Larder's solution architect, ran a security architecture review of the whole design with Cho, Ben, Eli and an external reviewer: two half-days, with the trust boundaries marked on the diagram. Eleven findings, three of them high. Every one of the three was about software calling software. Section 19.8 has them, and their fixes.

19.1How AWS authenticates every API call

When the SDK calls an AWS service, it doesn't send your secret access key. It sends a signature: Signature Version 4 (SigV4), an HMAC (Chapter 2) computed over the request itself. AWS recomputes it with its copy of the key and compares. The signature covers:

  • the method, path, query string and chosen headers (always host and the date);
  • a SHA-256 hash of the body;
  • the date, region and service, as a credential scope.

Compared with a bearer token (Chapter 3), this buys three things. A captured request can't be altered, because any change breaks the signature. It can't be replayed much later, because AWS rejects signatures more than a few minutes from its own clock. And the long-term secret never crosses the network. With temporary credentials, the session token travels as a signed header, and the session itself expires (Chapter 8).

Your own services can use SigV4 too: API Gateway (with IAM authorisation), Lambda function URLs and VPC Lattice can accept SigV4-signed calls and evaluate them against IAM, so a service calls another with nothing but its own role.

Watch out: API Gateway's “API keys” aren't authentication

API Gateway has a feature called API keys, used with usage plans for throttling and quotas. AWS says plainly not to rely on them for authorisation: they identify a customer's quota, they're sent in the clear in a header, and they don't expire. Authenticate with one of the options in Table 19.1, and use usage-plan keys only for metering.

Whatever authenticates the call, the API must still authorise it, per request and per object. A valid token says who's calling and what kind of thing they may do; only your code knows whether this office manager may see order 1043.

19.3Inside: services calling services

For calls between your own services, prefer identities the platform already gives you over secrets you have to manage:

  • IAM-authenticated calls (SigV4 with each service's role) where the target supports them: API Gateway with IAM authorisation, function URLs, VPC Lattice. The callee's resource policy names exactly which roles may call it.
  • OAuth client credentials (Chapter 4) where services already speak OAuth: each service gets a client identity and asks for tokens with narrow scopes.
  • Mutual TLS with short-lived certificates, typically from a service mesh (Handbook 1, Chapter 21).

Avoid the pattern most systems start with: one shared “internal API key” in every service's configuration. It's every problem from Chapter 1, inside your own walls.

19.4Partners calling you: keys that expire

The best credential for a partner's system is OAuth client credentials or a federated token: short-lived, scoped, revocable. But many partners' systems can only send a static key, and you'll issue API keys anyway. Issue them properly:

19.5Webhooks: trusting a call nobody logged in for

A webhook is a partner calling an endpoint of yours to say something happened: an invoice was paid, a payment failed. There's no session and no user; the endpoint is public, so anyone who learns its URL can post to it. The standard protection is a signature: the sender and you share a secret, and the sender attaches an HMAC of the timestamp and the exact body.

  1. Verify the signature over the raw body bytes, before parsing them, comparing in constant time.
  2. Check freshness: reject timestamps more than a few minutes old, so a captured request can't be replayed next week.
  3. Reject duplicates by event ID, since senders retry and attackers replay within the window.
  4. Treat the content as a hint for important events: “invoice paid” can trigger a call back to the provider's API to confirm, rather than marking the invoice paid on the webhook's word alone.
  5. Keep the secret in Secrets Manager, and support two at once during rotation.

When you send webhooks to customers, do the same for them: sign every delivery, document how to verify, and include a timestamp and event ID.

Key idea

Sign the request, not just the sender: a signature over the exact request, with a timestamp, proves who sent it, that nobody changed it, and that it's new.

19.6Every endpoint checks the object

Chapter 6 warned about broken object-level authorisation: checking that a caller may “view orders” but not whether they may view this order. It's worth repeating here because APIs grow: a list endpoint that filters by the caller's office is written carefully, and six months later a detail, export or receipt endpoint takes an ID from the path and passes it straight to the backend, which only checks the role. Make the object check structural, not a habit: a single function that loads an object for a principal and refuses if they aren't related, which every endpoint must use, and a test for each endpoint that tries another customer's ID.

On Azure

A calling service uses its managed identity (Chapter 15) to get an Entra ID token for the target's app registration; the target checks the token's audience and an app role assigned to the caller's identity. No secret exists on either side. API Management can enforce the same checks at the gateway with its validate-jwt policy.

On Google Cloud

To call a private Cloud Run service, the caller fetches an ID token from its metadata server with the service's URL as the audience, and the platform checks it against IAM (roles/run.invoker) before the request reaches your code: service-to-service authentication with nothing to store.

19.8At Larder: three high findings, fixed in two weeks

At Larder: solved

Business API keys never expired (internet → Business API). Some had been created when a client first integrated in early 2027, and sent to them by email. Ben's team reissued every key under the rules in Table 19.2: 90-day expiry with reminders, two active keys per client, created and revealed only in the portal by the client's own administrator, hashed at rest, with an lb_live_ prefix registered with GitHub's secret scanning. New integrations are steered to OAuth (Chapter 4). Done 22 October.

Another office's orders by ID (portal → Larder Core). The portal had been designed to check orders by relationship (Chapter 6), and its list and search screens did. But an order-detail call added in the summer passed the order number from the address straight to Larder Core, which only checked that the caller was an office manager. Changing the number showed another office's order. The fix, done 18 October: one function that loads an order for a principal and checks the office relationship, used by every portal and Business API endpoint, with a test per endpoint that tries someone else's order.

Billing webhooks weren't signature-checked (billing provider → Larder). The endpoint accepted any well-formed request, so anyone who found its address could have marked an invoice paid. Cho's team added verification as in 19.5, with the signing secret in Secrets Manager, rejected unsigned deliveries, and made “invoice paid” confirm with the provider's API before changing anything. Done 20 October. One of the medium findings went to Eli: no alert when a new client identity provider is trusted (Chapter 5); that one is Chapter 23's.

19.9Lab: sign a request, verify a webhook

Lab 19 · SigV4 by hand, and a webhook receiver

You'll implement AWS's request signing and check it against a case from AWS's published test suite, then write the verification Larder's billing webhooks were missing and attack it four ways. You need Python 3. Cost: nothing. (In real code, let the SDK sign; this shows what it does.)

sigv4.pyPython 3.8+

# sigv4.py · sign an AWS request by hand (Signature Version 4), checked against AWS's test suite
import hashlib, hmac

def h(data):
    return hashlib.sha256(data.encode()).hexdigest()

def hm(key, msg):
    return hmac.new(key, msg.encode(), hashlib.sha256).digest()

def sign(method, host, path, query, headers, body, access_key, secret_key, amz_date, region, service):
    date = amz_date[:8]
    headers = {k.lower(): v.strip() for k, v in {**headers, "host": host, "x-amz-date": amz_date}.items()}
    signed = ";".join(sorted(headers))
    canonical = "\n".join([method, path, query,
                           "".join(f"{k}:{headers[k]}\n" for k in sorted(headers)),
                           signed, h(body)])
    scope = f"{date}/{region}/{service}/aws4_request"
    to_sign = "\n".join(["AWS4-HMAC-SHA256", amz_date, scope, h(canonical)])
    key = hm(hm(hm(hm(("AWS4" + secret_key).encode(), date), region), service), "aws4_request")
    signature = hmac.new(key, to_sign.encode(), hashlib.sha256).hexdigest()
    return f"AWS4-HMAC-SHA256 Credential={access_key}/{scope}, SignedHeaders={signed}, Signature={signature}"

if __name__ == "__main__":
    # The "get-vanilla" case from AWS's Signature Version 4 test suite (example credentials)
    auth = sign("GET", "example.amazonaws.com", "/", "", {}, "",
                "AKIDEXAMPLE", "wJalrXUtnFEMI/K7MDENG+bPxRfiCYEXAMPLEKEY",
                "20150830T123600Z", "us-east-1", "service")
    print(auth)
    print("matches the test suite:", auth.endswith("5fa00fa31553b73ebf1942676e86291e8372ff2a2260956d9b8aae1d763fbf31"))
    tampered = sign("GET", "example.amazonaws.com", "/admin", "", {}, "",
                    "AKIDEXAMPLE", "wJalrXUtnFEMI/K7MDENG+bPxRfiCYEXAMPLEKEY",
                    "20150830T123600Z", "us-east-1", "service")
    print("same signature for another path:", tampered == auth)

webhooks.pyPython 3.8+

# webhooks.py · verify signed webhooks: HMAC over timestamp + raw body, a time window, and no replays
import hashlib, hmac, json

SECRET = b"whsec_lab_only_printed_in_a_book"     # shared with the billing provider, kept in Secrets Manager
TOLERANCE = 300                                # seconds
SEEN = set()                                   # event IDs already processed

def signature(timestamp, raw_body):
    return hmac.new(SECRET, f"{timestamp}.".encode() + raw_body, hashlib.sha256).hexdigest()

def verify(headers, raw_body, now):
    try:
        parts = dict(p.split("=", 1) for p in headers["Billing-Signature"].split(","))
        timestamp, sig = int(parts["t"]), parts["v1"]
    except (KeyError, ValueError):
        return "rejected: missing or malformed signature"
    if not hmac.compare_digest(sig, signature(timestamp, raw_body)):
        return "rejected: bad signature"
    if abs(now - timestamp) > TOLERANCE:
        return "rejected: too old"
    event = json.loads(raw_body)
    if event["id"] in SEEN:
        return "rejected: already processed"
    SEEN.add(event["id"])
    return f"accepted: {event['type']} for {event['account']}"

if __name__ == "__main__":
    NOW = 1823148000                                                # 10 Oct 2027, 06:00 UTC
    body = b'{"id": "evt_81", "type": "invoice.paid", "account": "korenwolf", "amount": 12480.00}'
    good = {"Billing-Signature": f"t={NOW},v1={signature(NOW, body)}"}
    forged_body = body.replace(b"korenwolf", b"someone-else")
    tests = [
        ("as sent by the provider",    good, body,        NOW + 2),
        ("the same delivery again",    good, body,        NOW + 9),
        ("no signature header",        {},   body,        NOW + 2),
        ("body changed in transit",    good, forged_body, NOW + 2),
        ("captured, replayed later",   good, body,        NOW + 3600),
    ]
    for name, headers, raw, at in tests:
        print(f"{name:<28} {verify(headers, raw, at)}")
  1. Run it with python3 webhooks.py: 
    as sent by the provider      accepted: invoice.paid for korenwolf
the same delivery again      rejected: already processed
no signature header          rejected: missing or malformed signature
body changed in transit      rejected: bad signature
captured, replayed later     rejected: too old
    Before the October fix, Larder's endpoint would have accepted all five.
  2. Break it on purpose. Move the duplicate check and the SEEN.add line to the top of verify, before the signature check, then send a forged, unsigned body carrying the genuine event's ID before the real delivery arrives: the forgery is rejected, but the genuine event is then refused as “already processed”. Record an event as seen only after it has passed every other check. Then parse the JSON first and sign json.dumps(event) instead of the raw bytes: harmless re-encoding (spacing, key order) now breaks genuine signatures. Verify the exact bytes you received, first.

Stretch goal. Make verify accept two secrets at once, so the provider can rotate without a moment where deliveries fail.

✓Chapter summary

  • SigV4 signs each request with a key derived for one day, region and service; the secret never travels, and requests can't be changed or replayed later.
  • API Gateway authorises with IAM, JWTs, Lambda authorisers or mTLS; its API keys are for usage plans only.
  • Between your services, use roles, client credentials or mTLS, never a shared key.
  • Partner API keys must expire, rotate with two active keys, be stored hashed and be issued only through your portal.
  • Webhooks: verify an HMAC over the raw body and timestamp, reject old and repeated events, confirm important ones.
  • Every endpoint checks the object, through one shared function.

Key terms

SigV4
AWS Signature Version 4: HMAC signing of API requests with derived keys.
Canonical request
The normalised form of a request that gets hashed and signed.
Credential scope
Date, region and service that a SigV4 signature is valid for.
Authoriser
The component that authenticates callers in front of an API.
Mutual TLS
TLS where the client also presents a certificate.
Webhook
An HTTP callback a partner sends to report an event.
Replay
Re-sending a captured, valid request.

Check your understanding

  1. Name two things SigV4 protects against that a bearer token doesn't. recall

    Show answer

    Altering a captured request (the signature covers it) and replaying it later (signatures expire within minutes). Also, the long-term secret never crosses the network.

  2. Your team proposes API Gateway API keys to authenticate partners. What do you say? explain

    Show answer

    They're meant for usage plans and metering; AWS advises against using them for authorisation. Use a JWT authoriser with OAuth client credentials, mTLS, or a Lambda authoriser with properly managed keys, and keep usage-plan keys for quotas.

  3. Why must a webhook signature be checked against the raw body rather than parsed and re-encoded JSON? explain

    Show answer

    The sender signed specific bytes. Parsing and re-encoding can change spacing, key order or number formatting, which breaks genuine signatures; and code that parses first may act on unverified data.

  4. An API's list endpoint filters by the caller's office, but the detail endpoint doesn't check. Design a fix that stays fixed. design

    Show answer

    One shared function that loads an object for a principal and refuses unrelated callers; all endpoints must use it (enforced by review or a lint rule); and a test per endpoint that requests another customer's object and expects a refusal.

  5. Design credentials for a partner whose system can only send a static header. design

    Show answer

    An API key per partner integration, from the portal, with a prefix, stored hashed, expiring after 90 days with reminders, two active at once for rotation, scoped to the partner's account and needed operations, with last-used shown; mTLS in addition if the partner can manage certificates.

  6. Compare how one service calls another privately on Google Cloud and on AWS. compare

    Show answer

    Google Cloud: the caller fetches an ID token with the target's URL as audience from its metadata server; the platform checks it and roles/run.invoker. AWS: the caller signs with SigV4 using its role; API Gateway (IAM auth), a function URL or VPC Lattice checks IAM and the target's resource policy.
